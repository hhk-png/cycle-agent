# 第 20 章 压缩与编码

列存给了你两个好处。第一个是第 05 章讲过的"只读需要的列";第二个是压缩,而且它常常比第一个更值钱。这一章讲清楚:为什么列存的压缩率天生比行存高、ClickHouse 的专用编码各利用了数据的什么性质、`CODEC` 的链式规则为什么长这样,以及怎么按数据形态选编码、怎么量出效果、怎么避开那些让 CPU 白烧的坑。

## 20.1 压缩是列存的第二个利润来源

压缩的基本原理是"找重复、去冗余"。而通用压缩算法要能工作,前提是**相邻的字节里有模式**。行存格式里,相邻的字节属于同一行的不同列——一个时间戳、一个 URL、一个价格、一个布尔位——**它们的类型不同、分布也不同**,通用算法很难在这种混合流里找到长重复。列存把同一列的所有值连续放:一整列都是时间戳(单调递增的整数)、一整列都是 URL(低基数字符串)、一整列都是价格(小范围的浮点)。**同一列的值类型相同、分布相似**,于是相邻字节里的模式密集得多,通用算法能拿到比行存高得多的压缩率——在分析类负载上,列存相对行存常见能到**十倍以上**的差距,具体倍数取决于列的基数与有序性(单调递增的时间戳、低基数的状态码差距最大,高熵随机 ID 则几乎不差)。这不是"顺带的好处",而是列存的一个**设计动因**——衡量一种存储格式时,除了看"能不能只读几列",也要看"它把同一列放在一起了没有"。

**"十倍以上"是量级描述,不是对你那张表的承诺;要拿数字只能自己量。** 库内最直接的一条路是查 `system.columns` 的 `data_compressed_bytes` 与 `data_uncompressed_bytes`,算出**每一列各自的压缩比**(§20.6 给了三层入口,§20.14 的 `benchmark_codecs()` 则在几类代表性列上把"哪种编码压到多少"当场跑出来)。想做对照实验,最干净的一对基准是**同一种数据、同一列,只把 `CODEC` 在 `NONE` 与 `LZ4` 之间切换**——`NONE` 给出"完全没压"的原始体量,`LZ4` 给出通用压缩单独能拿到多少,两者的差是"压缩"贡献的部分,而不是"列存"贡献的部分。列存相对行存的那份红利则取决于列的**基数与有序性**:单调递增的时间戳、低基数的状态码差得最多,高熵随机 ID 几乎不差。所以请把"十倍以上"读成"分析型负载上列存常见能比行存小一个数量级左右",而不要当成一条可以照搬的倍数。

## 20.2 专用编码先于通用压缩

如果只讲通用压缩(LZ4/ZSTD),你会漏掉 ClickHouse 压缩体系里最关键的一条设计:**专用编码先做,通用压缩后做**。

```text
列字节流                    专用编解码器                 通用编解码器         磁盘
┌──────────────┐        ┌─────────────────────┐     ┌──────────────┐
│ ts UInt64 ...│───①───▶│ Delta / DoubleDelta │────▶│ LZ4 / ZSTD   │───②───▶ block
│ (原始 8N 字节)│        │ 变换数值,不压小     │     │ 压任意字节    │
└──────────────┘        └─────────────────────┘     └──────────────┘
    单调递增的时间戳        变成"差值"后全是 0/小数      把 0 和小数真的压掉
```

为什么必须是这个顺序?因为两类编码器的能力**恰好互补**:

- **专用编码器**(Delta/DoubleDelta/Gorilla/T64/FPC)**只能作用于数值列**。它们要么在**值**上做算术(Delta/DoubleDelta 的差分),要么按固定元素宽度在**字节/位**上重新排布(Gorilla/T64 的平面转置)(§20.3 逐个讲),**看不懂字符串、看不懂任意字节流**——输入的元素宽度或类型不对,输出就是垃圾。所以叫"非通用"。
- **通用编码器**(NONE/LZ4/ZSTD)**能压任意字节流**,但它们不知道"这 8 个字节是一个 `UInt64`"。对一串单调递增的整数,LZ4 找不到重复片段(每个值都不同),几乎压不动;而先做 Delta 之后,数据变成"一堆 0 加一个小的低字节",LZ4/ZSTD 立刻就能压出几十倍。

所以 `CODEC(Delta, ZSTD)` 的两步是互补的:**专用编码器负责把数据变规整,通用编码器负责把规整的数据真的压小**。理解了这一点,§20.4 那条"单独写 `CODEC(Delta)` 会被拒绝"的规则就不奇怪了。

## 20.3 逐个编码

下面逐个说清每一种编码**利用了数据的什么性质**,以及什么时候用、什么时候不用。

### 20.3.1 Delta:值级差分

Delta 做的是**值级**一阶差分:对整列每个元素,存的是它与前一个元素之差,`delta[i] = value[i] - value[i-1]`(第一个值存原值)。解码端反过来逐值累加:`value[i] = value[i-1] + delta[i]`。因为减法是在**整个 T 类型**上做的,进位/借位会正常传播——`UInt64` 相减为负时按该类型回绕、`Int64` 则是有符号差,和你在 SQL 里写 `n - lag(n) OVER (...)` 得到的结果一致,并**不是**"逐字节各算各的、不管进位"。

```text
原始:       1000, 1003, 1006, 1009     (等距递增)
Delta 之后: 1000,   3,    3,    3      ← 差值很小且大量相同 → 好压
```

它利用的性质是**相邻值接近、单调**:对单调递增的整数/时间戳极其有效,对随机值完全无效。

有两个点常被混为一谈,这里说清。**第一,别把 Delta 和 T64 搅在一起。** Delta 是"跨**值**做减法"(值语义),T64(§20.3.4)才是"把整数拆成字节/位平面再转置"(字节语义)——前者靠"差值小",后者靠"高位大面积为常量",两者正交、还可以先后叠用(`CODEC(T64, Delta, ZSTD)` 就是先转置、再对转置后的流做值级差分)。**第二,Delta 自己不缩小体积**:输出与输入等长(每个值仍按 T 类型宽度编码),它只是把数据变得"更规整",必须再配一个通用编码器真的压下去。另外它的头部会记一个 `delta_bytes_size`(取 1/2/4/8),告诉解码端差值按几字节宽存——差值的幅度常常比原值小,这一步本身也能省。

### 20.3.2 DoubleDelta

DoubleDelta 在 Delta 的基础上再差一次:

```text
delta[i] = value[i] - value[i-1]
dd[i]    = delta[i] - delta[i-1]        ← 这才是要编码的东西
```

对**匀速递增**的时间戳(等间隔采样,比如每秒一个点),`delta` 恒等于 1,于是 `dd` 恒等于 0——一整列 8 字节的时间戳,二阶差分起来**全是 0**。编码时,`dd = 0` 只花**一个 bit**;`dd ≠ 0` 时先写一个 1,再用变长编码把 zigzag 后的值写出去。于是对等间隔时间戳,除了开头两个 8 字节(首值和首个 delta),**每个值只花约 1 bit(零差分时)**。100 万个值原本 8 MiB,压完约 125 KiB——压缩比在 50 倍以上。这就是 DoubleDelta 被称为"时间戳神器"的原因。

它利用的性质是**匀速或近似匀速**:对等间隔的时间戳、序列号、自增 ID 极有效,对随机值无效。

### 20.3.3 Gorilla

Gorilla 来自 Facebook 那篇著名的时序数据库论文(《Gorilla: A Fast, Scalable, In-Memory Time Series Database》,2015)。它的核心观察是:时间序列里**相邻的浮点数往往很接近**,二进制表示只有低位不同、高位常一模一样。所以先算 `xor = value[i] ^ value[i-1]`——相同的位变成 0,不同的位留下;两个值完全相同则 `xor = 0`,只写**一个 bit** 就完事。否则去掉 `xor` 前面的一串 0(前导零)和后面的一串 0(后缀零),只把中间"有意义的位"写出去;若这次的零范围比上次窄,还能复用上次的范围。

它利用的性质是**浮点相邻值的位模式相似**,专为**浮点传感器数据**设计;对缓慢变化的浮点效果好,对跳变剧烈的浮点效果一般。

### 20.3.4 T64:字节/位平面的转置

T64 处理的是**字节/位布局**,和 Delta 的"值级差分"是两回事。它取 **64 个整数排成一个 64×64 的位矩阵**——每个整数一行、每个位一列,然后**转置**这个矩阵。转置之后,原来"同一位置(第 k 位)跨 64 个值"的那一列变成连续的一段,于是"高位大面积为 0"这类冗余就暴露成了长串的常量。

```text
64 个值排成 64 行 × 64 位,转置后按"位位置"成列:
  bit 0 … bit k   (低位,变化多,留下)
  …
  bit 63          (高位,常常整列都是同一个值 → 丢掉)
```

它接着做两件事:**裁掉在整个 part 的 max/min 之间不变的位**——如果某个位位置在这一批值(即 part 的最小/最大值区间)里从不变化,高位常是全 0、或负数的符号扩展全是 1,就只记"这一位是常量",整列不存;以及**按剩余位宽打包**,把用不到的位去掉。之所以是"在整个 part 的 max/min 之间",是因为 T64 关心的是"这一批 64 个值里到底有哪些位在变",把这个区间取在 part 级的最小/最大值之间,能丢掉更多恒定位。

它利用的性质是**值范围受限**——高位有大片冗余。适合范围受限的整数(状态码、小计数器);对铺满 64 位的高熵整数(哈希值)无收益。

**一个实用开关:byte 与 bit 两种粒度。** T64 可以按**字节**转置(默认),也可以按**位**转置。位粒度对高位冗余的利用更彻底,但它产出的流对 **ZSTD 更友好、对 LZ4 反而更差**——ZSTD 的熵编码能吃下位级别的稀疏,而 LZ4 只找字节级重复,位粒度的输出反而更"碎"。所以这一列后面如果接的是 LZ4,别盲目上位粒度。

### 20.3.5 FPC

FPC(Fast Parallel Compression)来自 Burtscher 与 Ratanaworabhan 的论文《FPC: A High-Speed Compressor for Double-Precision Floating-Point Data》。它和 Gorilla 解决同一类问题(相邻值接近),但办法不同:Gorilla 是"XOR + 零计数",FPC 是"**拿两个预测器去猜下一个值**"——一个猜值(FCM)、一个猜步长(DFCM),对每个值分别用两个预测器算出 XOR,选**前导零更多**的那个,再用一个 **2 位选择子**告诉解码端选了哪个。它为浮点设计,利用的性质是**浮点数据的可预测性**。

它的实参是 `FPC(level, float_size)`:`level` 是预测器哈希表的大小(大致按 `2^level × float_size` 字节算),取值 1–28,**默认 12**;`float_size` 是被压浮点的字节宽度,只能取 4 或 8,**默认按列类型定**(`Float32`→4、`Float64`→8)。`FPC` 只能用于 `Float32`/`Float64` 列,喂别的类型会报错。

### 20.3.6 LZ4 / LZ4HC / ZSTD

这三个是**通用压缩**,定位是"速度 vs 压缩率"的三角:

- `LZ4`:最快,压缩率一般。它是 ClickHouse 的默认块压缩。
- `LZ4HC`("HC" = high compression):压缩端的搜索更狠,压得更小,但**压缩慢**(解压速度和 LZ4 一样快,因为字节格式相同)。
- `ZSTD`:压得最好,压缩与解压都比 LZ4 慢一些。适合"一次写、多次读"、且存储成本敏感的场景。

两个通用的压缩器都带一个**可选的等级参数**,这是需要记住的两个数字:**`LZ4HC(level)` 的 `level` 取值 `[1, 12]`、默认 `9`**(推荐落在 `[4, 9]` 一带;更老的文档写的是 `[3, 12]`,以你那一版的 `CODEC` 文档为准),**`ZSTD(level)` 的 `level` 取值 `[1, 22]`、默认 `1`**。等级调的是**压缩端**的搜索强度——等级越高压得越狠、压缩越慢。它给后面几节出现的 `ZSTD(1)`/`ZSTD(3)`/`ZSTD(9)` 划出了范围边界(它们离上限 `22` 还很远),也是 §20.8"等级过高"那笔账的依据:同一条链上把 `1` 换成 `9`,换到的是个位数百分比的压缩率,付出的是高得多的压缩 CPU。

它们的区别在**压缩端的搜索强度与熵编码**:LZ4 是浅哈希链,ZSTD 是深哈希链 + 熵编码。`LZ4` 与 `LZ4HC` 甚至**共用一个方法字节**(解压端不需要区分)。另外 `NONE` 合法且有用:它是**对照组**——想知道 Delta 带来多少收益,和 `NONE` 比就知道;它也用在"已经压不动、不想再花 CPU"的列上(比如加密过的 blob)。

**硬件加速的两档**值得知道存在,但都要特定 CPU 支持、且要构建时打开,不是默认可用:`ZSTD_QAT` 把 ZSTD 的熵编码交给 Intel QuickAssist 硬件;`DEFLATE_QPL`(常简称 **QPL**)用 Intel QuickAssist 做 DEFLATE 压缩。它们在支持的机器上能把压缩 CPU 打下来,但**换机器就得确认新机器也有同样的加速器**,否则建表能过、实际跑起来才发现不可用。选它们前先确认集群每台机器都支持。

### 20.3.7 GCD

`GCD` 是一个**前置变换编码**,和 Delta 一样只改布局、不缩小体积,必须再配一个通用编码。它利用的性质很具体:**一整列整数如果都含一个大于 1 的公因子**,先把公因子拎出来。比如一列都是"毫秒时间戳对齐到秒"的值、或都是以 1000、以 1024 为步长的 ID。

做法是:求出整列的最大公约数 `g`(以及处理不了负数时退回的符号约定),把每个值除以 `g` 存下**商**,把 `g` 记在流头;解码时再乘回去。除以 `g` 之后,值的幅度整体缩小,后续的通用编码(甚至再叠 Delta)更容易找到重复。典型写法:

```sql
CREATE TABLE events (
    id UInt64 CODEC(GCD, ZSTD)
) ENGINE = MergeTree ORDER BY id;
```

它对"ID 共享一个步长"这种数据有效,对没有公因子的随机整数毫无作用(公因子是 1,等于没变)。判断方法很直接:算一下这一列的 `gcd` 是不是 1——是 1 就别用。

### 20.3.8 加密编码:AES_128_GCM_SIV / AES_256_GCM_SIV

这两个不是"压缩",而是**在磁盘上加密**这一列:`AES_128_GCM_SIV` 与 `AES_256_GCM_SIV`(GCM-SIV 是"误用不致命"的 AEAD 模式,密钥重复使用也不会像普通 GCM 那样灾难性失败)。要满足三个前提:

- 服务端构建时带 SSL/加密支持(不是所有包都带);
- 密钥在下发前的服务器配置里配好(配置节 `<encryption_codecs>`,可取环境变量或从命令读),**密钥不进 SQL**;
- 加密编码必须排在整条链的**最后**——先变换、再压缩、最后加密。顺序写错(比如把加密放在 ZSTD 之前)会被拒绝。

典型:`CODEC(Delta, LZ4, AES_128_GCM_SIV)`。注意加密之后这列就是高熵字节了,再想压它已经晚了——压缩必须在加密**之前**这一步完成,这正是"加密放最后"的原因。

## 20.4 CODEC(...) 的语法与链式规则

在列定义里用 `CODEC(...)` 指定编码:

```sql
CREATE TABLE metrics (
    ts      DateTime CODEC(DoubleDelta, ZSTD),
    value   Float64  CODEC(Gorilla, ZSTD),
    status  UInt8    CODEC(T64, ZSTD),
    url     String   CODEC(ZSTD)
) ENGINE = MergeTree ORDER BY ts;
```

**链式规则一句话:最后一环必须是通用编码。** 一个数据变换编码(专用编码)后面**应当**跟一个通用压缩,因为前者只把数据"变规整"、不缩小体积,必须由后者真的压小。所以:

```sql
CODEC(Delta, ZSTD)     -- ✔ 专用 + 通用,典型写法
CODEC(Delta)           -- ✘ 会被拒绝
CODEC(ZSTD, Delta)     -- ✘ 也会被拒绝
```

单独写 `CODEC(Delta)` 会被拒绝,因为一个非通用编解码器后面必须跟一个通用编解码器,否则数据既没变小、又不再能直接被别的系统读。`CODEC(ZSTD, Delta)`(通用在前、专用在后)同样会被拒——那等于把已压成字节流的数据再当数值去差分。拒绝时报错类似 `Code: 49. DB::Exception: The combination of compression codecs is invalid. (LOGICAL_ERROR)`。**这里有一个逃生开关:`allow_suspicious_codecs`** —— 上面这两条拒绝是一道"安全检查";如果你确实清楚自己在做什么,把它设成 `1` 就能让 `CODEC(Delta)` 这类"可疑组合"通过。它默认是 `0`(拒绝),开它属于自担风险,不是常规做法。`CODEC(NONE)` 与单独的 `CODEC(ZSTD)` 合法(常见组合见 §20.5)。

把链式规则说得更完整:**顺序是"前置变换 → 通用压缩 → 加密",每一段都在它该在的位置上。** 前置变换(`Delta`/`DoubleDelta`/`Gorilla`/`T64`/`FPC`/`GCD`)只重排数值字节,通用压缩(`LZ4`/`ZSTD`/…)把规整后的字节压小,加密(`AES_*_GCM_SIV`)最后把结果变成密文。所以 `CODEC(Delta, LZ4, AES_128_GCM_SIV)` 合法,而把 `AES` 放到 `LZ4` 前面(先加密、后压缩)会被拒——对密文做通用压缩几乎白费力气,也让解码路径无法成立。

## 20.5 怎么选

按**数据形态**选,而不是按"哪个名字听起来厉害"选:

- **单调递增的时间戳** → `CODEC(Delta, ZSTD)`(专用编码一定配通用压缩)。
- **等间隔时间戳(匀速采样)** → `CODEC(DoubleDelta, ZSTD)`,这是时间戳的最优组合。
- **随机整数 / 高熵 ID** → 只 `ZSTD`(或 `LZ4`)。专用编码对随机值无收益,加了白花 CPU。
- **低基数、范围受限的整数** → `T64` 配 `ZSTD`。
- **含大于 1 的公因子的整数**(对齐步长的 ID、秒对齐的毫秒时间戳)→ `GCD, ZSTD`;先算一下这列的 `gcd`,是 1 就别用(§20.3.7)。
- **浮点传感器数据** → `Gorilla` 配 `ZSTD`(或 `FPC`,两者都对浮点有效,可都试);较新的 `ALP`(§20.12)是另一条"把浮点先映射成整数再压"的路线,确有其物、但属实验特性(要用得打开 `allow_experimental_codecs`)。
- **字符串** → `ZSTD`;字符串没有"数值差分"的余地,低基数字符串再考虑 `LowCardinality`(见 §20.10)。
- **高熵、已压缩的二进制**(哈希值、加密 blob)→ 不压,或只 `LZ4`。
- **要落盘加密** → 在链尾加 `AES_128_GCM_SIV` / `AES_256_GCM_SIV`(§20.3.8),并确认服务端构建与密钥已就绪。

## 20.6 怎么评估

不要凭感觉,要看数字。看"每一列到底压了多少"有三个层次的入口,别只记得第一个:

- **`system.columns`** 的 `data_compressed_bytes` / `data_uncompressed_bytes`:把该表**所有活跃 part** 按列汇总,一眼算出每列的总压缩比,也能看出"哪一列其实没压动"。这是最快的总览。
- **`system.parts_columns`** 的 `column_data_compressed_bytes` / `column_data_uncompressed_bytes`:这才是**按列、按 part** 的明细,也是排查"哪一列、哪个 part 压不动"的正确地方——`system.columns` 只是它的聚合视图,要看单个 part 的真相得来这张表。改完编码后最有用的一点是:它能把**新写的 part** 和**还没重写的老 part** 分开看,直接告诉你重写进行到哪了。**但有一个必须知道的例外:它对 Compact part 不计列级大小统计**——官方说明里,那些 part 的这两个列报 **0**。原因正是第 05 章 §05.10 讲过的:Compact part 把所有列挤进同一个文件,压根没有"每列各自的字节"可分。所以如果你按列查出来一片 0,先确认这些 part 是不是 Compact(看 `system.parts.part_type`),别当成"这一列没压动"。
- **`system.parts`** 的 `bytes_on_disk`:按 part(整个 part 目录)看落盘总字节,含元数据、索引与块头,用于看总量。

想看到编码改动带来的效果,可以用 `OPTIMIZE TABLE t FINAL` 触发一次重写(它按当前的列定义重写 part),再看上面这几张表里的数字。注意 `OPTIMIZE ... FINAL` 对**大表**是一次全量重写,要估好代价再跑;评估时也分清"压缩率"与"总落盘字节"——后者含元数据、索引与块头开销,小 part 上占比很高。

## 20.7 改 CODEC 要重写数据

改 `CODEC` 是 `MODIFY COLUMN` 的一种:

```sql
ALTER TABLE metrics MODIFY COLUMN ts DateTime CODEC(DoubleDelta, ZSTD);
```

**它会触发一次后台重写任务**——已存在的数据必须按新编码重写一遍才能体现新设置;数据量大时这不是轻量操作,会占用磁盘 I/O 与后台合并线程。若只想"顺带重压",可以用 `TTL` 的 `RECOMPRESS` 动作:

```sql
ALTER TABLE metrics MODIFY TTL ts + INTERVAL 30 DAY RECOMPRESS CODEC(ZSTD(9));
```

`TTL ... RECOMPRESS CODEC(...)` 在 TTL 阶段(数据老化时)顺带把列重新压一遍——把"重压"这件事搭在本来就要发生的重写车上,比事后专门跑一次 `MODIFY COLUMN` 划算。

## 20.8 压缩的代价与陷阱

压缩不是免费的,下面几条都是"看着省了空间、实际烧了 CPU"的典型:

- **压缩等级过高会拖慢写入、抬高解压 CPU。** `ZSTD(9)` 的压缩率通常只比 `ZSTD(1)` 高**个位数百分比**,CPU 却贵很多,而且**压缩和解压两头都更慢**(等级越高,解码时要做的回溯也越多)。默认 `ZSTD(1)` 或 `ZSTD(3)` 在大多数场景就够了——**收益的差距通常远小于 CPU 的差距**。
- **`LowCardinality` 与 `CODEC` 会叠加,得看清作用对象。** `LowCardinality(String)` 本身就把一列拆成了"字典 + 下标"两条流(下标是小整数),它自己已经在做列编码了(§20.10);这时再给它套一个 `CODEC`,这笔优化划不划算取决于它究竟压在哪条流上——那一点在 §20.9 标为**未确认**,理由与出处也写在那一节,这里不重复论证。实践上只给一条稳妥的建议:动手前先把"给 `LowCardinality` 列换 `CODEC`"的收益、和"不用 `LowCardinality`、直接 `ZSTD` 一整列"比一遍,别默认前者一定更省。
- **`Nullable` 会削弱压缩。** `Nullable(T)` 在磁盘上是"数据流 + 一条单独的 null 标志流"。null 标志本身很好压,但它**把数据流切断了**:同一列的值不再是紧挨着的连续序列,`Delta`/`DoubleDelta` 这类依赖"相邻值接近"的编码效果会下降,而且多一份流就多一份块头开销。所以 §19.17 里说"别让推断把所有列都推成 `Nullable`"不只是省空间的事,也是为了不破坏压缩。
- **"已经压过的字节再压一次"是白白烧 CPU。** 一个 `String` 列里放着 gzip 包、JPEG、加密 blob,再套 `ZSTD`,压缩器对着高熵字节几乎压不动;判断依据是"这一列的字节本身是不是已经压过了"。注意"给 `Native`/`Parquet` 列写 `CODEC` 是双重压缩"是个误解——`CODEC` 作用在 part 存储上,与 `FORMAT` 无关(完整辨析见 §19.15)。
- **专用编码喂错类型会产出垃圾。** Delta/DoubleDelta/Gorilla/T64/FPC/GCD 都要求输入是**定宽数值**;把它们用在字符串列上,得到的不是"压得差",而是**读不回来**。所以选编码前先确认列类型。
- **加密编码有运维成本。** `AES_*_GCM_SIV` 要求构建带 SSL 支持、密钥在服务器配置里下发(§20.3.8);换密钥、跨机迁移时还要同步——它不是"顺手加一句"能了事的。

## 20.9 默认编码:不写 CODEC 时你拿到什么

前面讲的都是"怎么选",但**大多数人从不写 `CODEC`**——那你手里到底是什么?这一节回答这个最实际的问题。

**结论先给:所有列默认都用 `LZ4`。** 这就是"块压缩"层的默认方法。所以"我没配压缩,是不是没压?"——不是,`LZ4` 一直在压,只是它只求快、压缩率一般。

想统一换默认,不必逐列写 `CODEC`,用 MergeTree 的**表级设置 `default_compression_codec`**:它给"没有显式 `CODEC` 的列"指定默认编码(不设时相当于 `LZ4`)。例如整张表都想用更省空间的 ZSTD,不必在每列上写一遍:

```sql
CREATE TABLE metrics (
    ts    DateTime,
    value Float64
) ENGINE = MergeTree
ORDER BY ts
SETTINGS default_compression_codec = 'ZSTD(3)';
```

还有几类列,**它们的"默认编码"不是 `CODEC` 能决定的,而是由类型本身决定的**,理解它们才能解释"为什么某列没写 CODEC 却压得特别好或特别差":

- **`LowCardinality(T)`**:列被拆成"字典 + 下标"两条流(§20.10),逐行存的已经不是原值,而是指向字典的小整数下标。这时你写的 `CODEC` 与 `default_compression_codec` 到底落在**哪条流**上、收益有多大,**未确认**——通行说法是它们作用在**字典**那条流上,于是给 `LowCardinality` 列换 `CODEC` 收益常常有限(§20.8),但我未能在官方文档里找到逐条的说明,具体以你的版本实现为准。这一点值得标出来,是因为它决定"该不该给低基数列加 `CODEC`"这个很常见的判断,而不是一句可忽略的细节。
- **`Array`/`Tuple`/`Map`/`Nested` 等复合类型**:列的 `CODEC` 会**递归作用到每个叶子子列**;磁盘上一列其实是一组子流,mark 也按子流记。
- **`Nullable(T)`**:多出一条 null 标志子流(§20.8)。
- **`Enum8`/`Enum16`**:磁盘上存的是 `Int8`/`Int16` 整数,不是字符串(§20.10)。

这些结构性的事实说明一件事:**你以为"一列一份字节",其实一列可能是好几条流**,`data_compressed_bytes` 看到的是它们的合计。搞清楚有几条流,才看得懂压缩数字。

## 20.10 列编码:标题里的"编码"不只是 CODEC

本章标题是"压缩与编码",但前面只讲了 `CODEC`——那只是"编码"的一半。"编码"分两层:**`CODEC(...)`**(本章主体)作用在**一列的字节**上,是"通用压缩 + 数值前置变换";另一层是**列编码(column encoding)**,作用在**类型层面**,由建表时的类型决定、不需要写 `CODEC`——它改变的是"值怎么摆成字节",而不是"摆好之后怎么压"。

三类最主要的列编码,一张表对照(完整讨论见第 03 章 §03.7 与 §03.10):

| 列编码 | 做什么 | 代价 |
|---|---|---|
| `LowCardinality(T)` | 去重成"字典 + 每行下标",低基数时列变得很小 | 高基数时字典膨胀,**反而更大更慢** |
| `Enum8` / `Enum16` | 把固定取值映射成 `Int8` / `Int16`,磁盘上就是整数 | 取值集合固定,新增要 `MODIFY COLUMN` |
| `Dictionary` 类型 | 列里存**键**,查询时用外部字典翻成值 | 依赖那份字典可用 |

这层和 `CODEC` 是**叠加**关系:类型先做列编码(比如 `LowCardinality` 把字符串变成下标),再对结果字节套 `CODEC`。所以两件事要一起看——**先把列编码选对(类型选对),再考虑 `CODEC`**;顺序反过来,等于在一个选错类型的列上花力气调压缩。这里只点明它属于"编码"的另一半,别把它漏掉。

## 20.11 通用压缩的定位

除了列级的 `CODEC`,ClickHouse 还有一层**服务器级的压缩配置**:它规定"多大以上的 part 用哪种通用压缩",**整块数据**统一处理,粒度比列级 `CODEC` 粗。配置长这样(在服务器的 config 里,一个 `compression` 节下挂多个 `case`):

```xml
<compression>
    <case>
        <!-- 条件:part 至少 100 MB,且不小于整表的 1% -->
        <min_part_size>104857600</min_part_size>
        <min_part_size_ratio>0.01</min_part_size_ratio>
        <!-- 命中这个 case 时用什么通用压缩 -->
        <method>zstd</method>
        <level>1</level>
    </case>
    <!-- 可以再写若干 case;按顺序匹配,第一个命中的生效 -->
</compression>
```

几个要点:**case 按书写顺序逐条匹配,命中第一个就停**;每个 case 的条件是 `min_part_size`、`min_part_size_ratio`(两者都要满足)等;`<method>` 是通用压缩名(`zstd`/`lz4` 等),`<level>` 是等级。所有 case 都没命中时,落到内置的默认(`LZ4`)。这一层和列级 `CODEC` 的关系是"外层兜底":列级显式写的 `CODEC` 优先,服务器配置管的是**没写 `CODEC` 的那些列**在**多大 part** 上用哪种通用压缩——所以它常和 §20.9 的 `default_compression_codec` 配合理解。大多数情况下列级 `CODEC` 已经够用;只有"整台机器的默认压缩策略要统一调整"时才需要动这一层。

## 20.12 ALP 与自适应编码选择

前面这些编码都要"人工按数据形态挑"。较新的版本里加了一条更自动的路线。**这里先分清"已确认"与"未确认":`ALP` 这个编码名确有其物,但属实验特性(要 `SET allow_experimental_codecs = 1` 才用得上,较新的版本还出现了按编码单独放行的 `enable_alp_codec`);而"自动挑编码"的那个设置名我未找到官方确证,仍按未确认对待——具体名字与默认值以你那一版的 `system.settings` 与列编码文档为准。**

**`ALP`(Adaptive Lossless floating-Point)** 是一个**面向浮点的无损编码**,定位与 Gorilla / FPC 相同——都是把"相邻接近的浮点"压得更小——但走的是另一条路线:它尝试先把浮点值映射成整数表示,再交给整数侧的编码(必要时可再叠 Delta)。名字里的 "Adaptive" 指它会**按数据特征自适应地选表示**,遇到不适合的数据就退回更朴素的编码。对**小数位有限、量程受控的浮点**(指标、传感器读数)通常比 Gorilla 更省。

至于"**自动挑编码**"这个开关——通行说法是打开后系统会在写入/重写时**自动为合适的列挑选编码**(比如给浮点列挑 `ALP`、给时间戳列挑 `Delta`),省掉逐列手写 `CODEC` 的试错,影响的是"**不写 `CODEC` 时用什么默认**",列上显式写的 `CODEC` 仍然优先,和 §20.9 的表级 `default_compression_codec` 是同一类"兜底"角色。**但它的确切设置名我没能找到官方确证**(我能确认的是"启用实验性编码"要靠 `allow_experimental_codecs`),别照搬名字,以目标版本的 `system.settings` 为准。

真要落地,先在目标版本上确认:`ALP` 是否被接受(以及是否要先 `SET allow_experimental_codecs = 1`)、自动挑编码的开关究竟叫什么。

## 20.13 压缩块的边界:min/max_compress_block_size 与块头

前面一直说"把一列压下去",但压缩不是"整列一把过"——列数据会被切成一个个**压缩块**(compressed block)分别压。块的大小由两个设置框定:`min_compress_block_size` 是"至少攒到这么大才切一个块"(默认 **65536**,即 64 KiB),`max_compress_block_size` 是"最多长到这么大就必须切块"(默认 **1048576**,即 1 MiB)。两者都请以 `system.merge_tree_settings` 的实测值为准。

**为什么要切块,而不是整列一把压?** 其一,**随机读**:如果整个 part 只有一个大块,想读最后一页也得先解开前面全部;切成固定大小的块之后,可以定位到"要读的那块"直接解、别的块不必碰——这正是"随机读"的前提(本章末的 mini 实现也按 1 MiB 分块,做法一致,见 §20.14)。其二,**压缩率的边际递减**:通用压缩在开头几百 KB 上命中率最高,块再大收益有限,却把"读一个值要碰到的数据量"撑大。

块也不是裸字节,每个块前面有**块头**:记着"这块压缩前多大、压缩后多大",以及**校验和**。真实 ClickHouse 用 **CityHash128**(16 字节)做校验;有了这个头,读取端才知道"要解出多少原始字节、这块有没有损坏"。所以**改块大小不只是调压缩率,还牵动随机读的粒度**——块越小,能跳过的数据越多,但每块的固定开销(头 + 校验)占比越高。

## 20.14 与 mini-clickhouse 的对照

mini-clickhouse 的压缩实现在 `minich/compression.py`,是一个**诚实但有限**的实现,读它时要把下面几条分清楚。

**哪些是"真实算法的实现"。** `DoubleDelta`/`Gorilla`/`T64`/`FPC` 实现了与上游相同的**算法思想**,但**具体的位布局在少数细节上与上游不同**——每一处都在对应类的文档里画了图并标注了差异(例如 Gorilla 把论文里的 `lz` 字段从 5 bit 放宽到 6 bit,以覆盖完整 64 位范围)。这些差异不影响压缩率的量级,只影响"逐字节能不能和上游对上"。

这里要特别标出 **`Delta` 的偏差**:真实 ClickHouse 的 `CompressionCodecDelta` 是在**整个 T 类型**上做**值级**差分(§20.3.1,进位/借位会传播),而这个实现走的是**逐字节平面**的变体——按固定的 `element_size`,对每个字节做 `data[i] - data[i-w]`(无进位、按 256 取模)。两者对同一列会产出**不同的字节流**,所以 mini 的 `Delta` **不是**与上游字节兼容的实现,只是一条"同样能把单调序列变规整"的近似路线。另外真实 ClickHouse 的编码器按列类型推元素宽度、支持 1..N 字节,而这个实现按参数取宽度(`Delta` 与 `T64` 可配参数)。

**哪些是"同类的算法、不是兼容的格式"。** 这一点必须讲清楚,否则会误导人:

- `LZ4`/`LZ4HC` **不是与官方 lz4 库字节兼容的**。它自己写了一个**同类的 LZ77 块压缩器**(哈希链匹配 + 长度/距离对 + 字面量 run),token 流沿用了 LZ4 块格式的约定,但**多了 6 字节魔数 `MCHLZ1` + 4 字节原始长度**的头,而真正的 LZ4 块格式**没有这个头**——所以本实现的输出喂给 lz4 库一定报错,反过来也一定被魔数挡回去。
- `ZSTD` **不是与真实 zstd 字节兼容的**。它是一个**自研的 LZ77 + 自适应算术编码**压缩器,与真实 zstd(其熵编码是 FSE/Huffman)在算法上同源但**格式完全不同**,同样带 `MCHZS1` 魔数。

换句话说,这几个名字代表的是「与真实实现同类的算法」,而不是「与真实实现兼容的格式」。要一个能和其他系统互通的压缩层,请用 Python 的 `lz4` / `zstandard` 包;这个实现的价值在于把"压缩到底做了什么"摊开给你看。

**块头与校验。** 真实 ClickHouse 的压缩块用 **CityHash128**(16 字节)做校验;这个实现用的是 **crc32**(4 字节)——这是**有意的替换**,两者都能检出损坏,但校验值不同、长度不同,所以它的块头比真实 ClickHouse 短 12 字节。它的 `CompressedWriteBuffer` 把一个输入切成最多 1 MiB 的块,每块单独压缩、单独校验——"读第 3 个块"不必先解开前两个块,是「随机读」的前提(与真实 ClickHouse 一致)。

**怎么量效果。** `benchmark_codecs()` 在一组代表性列(单调时间戳、随机 `UInt64`、低基数字符串)上跑遍所有编码器,返回 `(列名, codec 名, 原始字节数, 压缩率, 压缩耗时毫秒)`。**这些压缩率是真实的**,直接印证 §20.3 的结论:通用编码在随机字节上几乎压不动(压缩率 ≈ 1.0),在低基数字符串上非常好,数值专用编码在单调时间戳上大放异彩、在随机 `UInt64` 上基本无收益。代码刻意**不把压缩率写死**(数字会过期),而是让你现场跑出来。

**没有实现的,就是没有。** 这个实现里没有 `Parquet`/`ORC`/`Avro` 等格式自带的压缩、没有 `LowCardinality` 与 `CODEC` 的叠加优化、也没有服务器级的压缩配置节。查不到的名字不要假设能用。

## 20.15 小结

压缩是列存的第二个利润来源,它的关键设计是**专用编码先于通用压缩**:专用编码(Delta/DoubleDelta/Gorilla/T64/FPC/GCD/ALP)负责把数据"变规整",通用编码(LZ4/LZ4HC/ZSTD)负责真的把字节压小。所以**链的最后一环必须是通用编码**——单独写 `CODEC(Delta)`、或写反成 `CODEC(ZSTD, Delta)`,都会被拒(除非显式打开 `allow_suspicious_codecs`);完整顺序是**前置变换 → 通用压缩 → 加密**(`AES_128/256_GCM_SIV` 只能放在链尾)。选编码按**数据形态**而非名字:单调或等间隔的时间戳用 `Delta`/`DoubleDelta`,范围受限的整数用 `T64`,共享步长的整数用 `GCD`,浮点用 `Gorilla`/`FPC`(或实验性的 `ALP`),字符串与高熵二进制交给 `ZSTD` 或干脆不压。每个编码利用了数据的什么性质、参数怎么给、什么时候纯属白烧 CPU,§20.3 与 §20.5 逐个讲过,这里不再重抄参数表。

**不写 `CODEC` 时每列默认 `LZ4`**(块压缩的默认方法),想统一换默认用表级 `default_compression_codec`,更外一层还有服务器级的 `compression` 配置节(§20.11)。要记住"一列可能由**多条流**组成"——`LowCardinality` 的字典加下标、`Nullable` 的 null 标志流、复合类型递归到每个叶子——这是看懂压缩数字的前提。标题里的"编码"还有另一半**列编码**:`LowCardinality`、`Enum`、`Dictionary` 类型,由类型本身决定、与 `CODEC` 叠加(完整讨论在第 03 章)。

**怎么量:** 用 `system.columns`(按列汇总)、`system.parts_columns`(按列按 part 的明细,查单列压缩的正确入口;注意 Compact part 的列级字节报 `0`)、`system.parts`(按 part 总量)这三层入口,`OPTIMIZE ... FINAL` 触发重写。改 `CODEC` 本质是一次 `MODIFY COLUMN`、会触发后台重写;想把重压搭在本来就要发生的重写车上,用 `TTL ... RECOMPRESS CODEC`(§20.7)。

**陷阱:** 等级过高收益小、CPU 贵(`ZSTD(9)` 对比 `ZSTD(1)`);`LowCardinality` 与 `CODEC` 叠加时压的究竟是哪条流,**见 §20.9** 那一处的**未确认**说明;`Nullable` 会切断数据流、削弱 `Delta` 系编码;给已经压过的字节再套通用压缩是纯浪费;专用编码喂错类型不是"压得差",而是**读不回来**;加密编码有构建与密钥的运维成本。压缩还是按**压缩块**进行的(`min/max_compress_block_size` 框定块大小,每块带一个大小头与 CityHash128 校验),块越小越利于随机读、但每块的固定开销占比越高。

**mini-clickhouse 的对照:** `DoubleDelta`/`Gorilla`/`T64`/`FPC` 是算法思想一致、位布局有差异,而 `Delta` 是**逐字节平面的近似实现**(真实 ClickHouse 是值级差分,两者字节流不同);`LZ4`/`ZSTD` 是**自研的同类算法,不是字节兼容的格式**;`benchmark_codecs()` 能给出真实的压缩率。列上声明的 `CODEC(...)` 在它里面是真的生效的(写入、后台合并、mutation 重写共用一处解析),所以可以拿它做"同一种数据、同一列、只换 `CODEC`"的实验;但磁盘上一个压缩块只带**一个** method 字节、表达不了整条链,链里真正生效的只是**链尾的通用编解码器**——`CODEC(Delta, ZSTD(3))` 会跳过 Delta 预变换,这正是"专用编码先于通用压缩"这条收益在 mini 里**拿不到**的地方;而 `CODEC(Delta)` 这种非法写法它仍会**正确拒绝**(`ILLEGAL_TYPE_OF_ARGUMENT`),与真实 ClickHouse 一致(§20.14)。
