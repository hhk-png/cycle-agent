# 第 01 章 认识 ClickHouse

学 ClickHouse 的人常常走两条弯路。第一条是把它当成"更快的 MySQL":照着旧经验建表、写 SQL,直到某条查询慢了一百倍,才发现问题不在 SQL,而在这套系统的形状。第二条是直接跳到参数和调优,背下一堆设置项,却说不清"为什么需要它"——于是每条经验都只在那一个场景里成立。

这一章要挡住这两条弯路。它不教你操作(那是 `第 02 章` 的事),只做一件事:把 ClickHouse 之所以长成这样的**那几次取舍**讲清楚——列式换来了什么、无事务放弃了什么、MPP 的边界又在哪。这些取舍不是背景知识,它们正是后面三十多章里每一句"为什么"的源头。

读完这一章,你应该能回答三个问题:**它解决的是哪一类问题**、**它和"行存 + B+ 树"的根本分歧落在哪一层**、以及**什么负载不该用它**。最后一个问题最容易被跳过,却最能防止一次失败选型。

## 01.1 五个词,五次取舍

"ClickHouse 是一个列式、MPP、向量化、无事务的 OLAP 数据库"——这句话信息量其实很大,但大多数人读过去就当背景音了。逐个拆开看,每个词都同时带来一个能力**和**一个代价。理解 ClickHouse 的过程,基本就是理解这五次取舍。

**列式(column-oriented)。** 数据按列连续存放:一整列的值排在一起,而不是一行的字段挤在一起。能力是:当你只读 3 列时,另外 300 列根本不碰;而且同一列的值类型相同、分布相近,压缩率可以做到十倍以上。代价是:按行取整条记录变得很贵——要拼出完整的一行,得从每一列各取一个值。这就是为什么 ClickHouse 的点查(按主键取一行)并不比行存数据库快,而 `SELECT count(*)` 只读一列,快得离谱。

**MPP(massively parallel processing)。** 一条查询会被拆成很多小任务,同时在多核、多机器上跑,再把结果汇总。能力是:单机也能吃满几十个核;集群层面可以线性扩展到几十上百个分片。代价是:协作是有开销的——任务分发、部分聚合结果合并、跨节点传输都是成本。小查询在 MPP 下反而会因为调度开销变慢,这是"大查询快、小查询慢"这个刻板印象的来源之一。

**向量化(vectorized)。** 执行引擎一次处理一批值(几百到几千行,称为一个 block 或 chunk),而不是逐行调用函数。能力是:CPU 的分支预测和缓存命中率大幅提升,同样的运算量能快一个数量级;SIMD 指令才有用武之地。代价是:延迟敏感的逐行处理不划算,而且很多"看起来很自然"的写法(比如逐行调用一个昂贵的表达式)在向量化模型里会被放大成整批的成本。

**无事务(或者说:有限的事务)。** ClickHouse 没有传统意义上的事务:多个 SQL 语句不能组成一个可回滚的原子单元,跨表的一致性靠写入端的幂等设计而不是数据库的锁。能力是:没有事务意味着没有锁、没有 MVCC 版本链、没有回滚段,写入可以一路追加,查询不需要等待。代价是:你**不能**把 ClickHouse 当成 OLTP 库用——不能靠数据库帮你保证"这两张表要么都成功要么都不动"。

关于"有限"这两个字要精确一点:单条 `INSERT` 到单个表 (具体到单分区) 的写入可以做到原子——要么整个 part(一次写入落成的不可变数据目录)可见,要么完全不可见。但**跨表、跨语句的原子性没有**。所以"无事务"更准确的说法是"有 part 级的写入原子性,没有多语句事务"。

**OLAP(online analytical processing)。** 面向上分析:一次查询要扫很多行、只输出少量聚合结果。能力是:整个系统从存储布局到执行引擎都为"大范围扫描 + 聚合"优化。代价是:为 OLTP 设计的访问模式(高频点更新、短事务、强一致读)在这里是逆着设计走的。

## 01.2 历史与出身

ClickHouse 不是"先做出来一个通用数据库,再想办法找场景",而是被一个具体到不能再具体的负载逼出来的:Yandex 自家的网站分析产品 **Yandex.Metrica**。2009 年前后,Metrica 面对的是这样一件事——每个被统计的网站、每个访客的每一个动作都要记下来,数据以每天数十亿条的速度累积,而用户随时会在后台按任意维度去翻这些明细。Yandex 当时试过的方案要么撑不住这个量,要么必须预先物化一大堆汇总表,把"任意维度"变成"预先枚举的组合"。ClickHouse 就是在 Yandex 内部为了解决这件事而起步的,团队由 Alexey Milovidov 带领。

它在 Yandex 内部用了六七年,直到 **2016 年 6 月**才以 Apache 2.0 许可开源。**2021 年**,开发这个项目的团队从 Yandex 分拆出来,成立 **ClickHouse Inc.**,负责商业化(Cloud 与支持服务)。要区分清楚的是:公司负责主导开发和商业化,但代码库本身仍是 Apache 2.0 的开源项目——本书讲的每一条行为,都能在开源版本上验证,不需要任何商业授权。

这段出身解释了后面反复出现的"性格"。它的设计不是从"兼容某个标准"或"支持所有负载"出发的,而是从"每天几十亿行点击流、要秒级出报表"这一个场景出发的:列式存储、排序键兼作稀疏索引、无事务的追加写,全都是这条需求线的直接推论。所以它的强项和短板是**同一个来源**——为了把一种负载做到极致,它在别的负载上就故意不做妥协。理解了这一点,后面那些"为什么它这里很奇怪"的问题,大半都能自己推出来。

## 01.3 它到底解决什么问题

把上面五条揉成一句具体的需求:**单表扫几十亿行做聚合,还要在秒级返回。**

举个有量级的例子。一个中等规模的网站,一天的点击流日志大致是这样的:

- 每天新增事件 1 亿到 5 亿条(页面浏览、按钮点击、接口调用);
- 每条事件有十几个字段:时间戳、用户 ID、会话 ID、URL、来源、设备、地区、耗时……
- 单条事件原始大小约 200–500 字节,一天就是 20–100 GB 原始文本;
- 保留 90 天到一年,常见规模在几 TB 到几十 TB。

在这份数据上,典型的日常问题是:"过去 7 天,按小时、按来源渠道统计独立访客数和 P95 加载耗时,只看移动端。"翻译成 SQL 是:扫 7 亿行左右,按三四个维度分组,算一个 `uniq` 和一个分位数。

在行存数据库上,这个查询要么慢到不可接受(几十秒到几分钟),要么需要预先物化好一大堆汇总表、把"任意维度组合"变成"预先枚举所有组合"。ClickHouse 的答案是:直接在明细上跑,几亿行的 `GROUP BY` 落在亚秒到几秒。**它替换掉的不是 MySQL,而是"为了跑分析而维护的一整套预聚合链路"。**

这也解释了为什么 ClickHouse 的典型部署是"宽表 + 明细":把需要一起查的字段冗余进同一张表,而不是靠 JOIN 在查询时拼。第 15 章会讲清楚这个取舍的代价。

## 01.4 与"行存 + B+ 树"的根本分歧

"为什么 MySQL 加好索引也搞不定,ClickHouse 不加索引就很快?"这个问题的答案,在于两种设计**优化的访问模式完全不同**。

B+ 树索引优化的是**选择性查询**:在一亿行里找到那 100 行满足条件的。它的工作方式是分层的:根节点到叶子节点几次跳转,每次跳转排除掉绝大部分数据,最后只读少数几个数据页。所以"扫 1% 的数据"这类查询,B+ 树是最优解——它读的页数正比于结果集大小,而不是表的大小。

但 B+ 树有个前提:**你读的是少数行**。一旦查询要扫全表做聚合——比如"统计所有订单的总金额"——B+ 树的每一层跳转都白费了:反正每个叶子页都要读,索引带来的那点定位优势,换来的却是额外的随机 I/O 和一层间接寻址。行存数据库此时退化成"逐页扫描",而且因为行是混存的,读一列也得把整行拉进来。

反过来,ClickHouse 的**稀疏索引**优化的是另一个极端。它的索引不指向"某一行",而是指向"每一段 8192 行(granule)的起点",索引本身因此小到可以常驻内存——一亿行只有一万两千个索引项。查询时它先在索引里二分、排除掉不可能命中的 granule,剩下的数据再按 mark(记录每段数据在列文件里的字节位置)跳过去**顺序读**。granule 为什么是 8192 行、mark 文件里究竟记了什么、一次查询到底跳过了哪些 granule,是 `第 05 章` 的主题,索引侧的另一半在 `第 11 章`;`§00.4` 的术语表给过这四个词最小的定义,这里不重复。

要记住的只是结论:**剩下的数据是顺序读的**。这对机械硬盘和 SSD 都友好。而如果查询真的需要全表聚合,那就没有 granule 可以排除——ClickHouse 老老实实把整列顺序读一遍。因为列式存储 + 高压缩,这个"读一遍"的成本远比行存低:只读需要的列,而且读完就能直接向量化聚合。

所以两种设计的分歧不在"谁更先进",而在**假设**。B+ 树假设"你会精确定位少数行";ClickHouse 假设"你会大范围扫、然后聚合"。各自的假设之外,对方都更快。

| 访问模式 | 行存 + B+ 树 | ClickHouse |
| --- | --- | --- |
| 按主键取 1 行 | 极快(几次页跳转) | 一般(定位 granule 后仍需拼列) |
| 取 1% 的行 | 快(读的页正比于结果) | 中等(可能读了一整个 granule) |
| 全表聚合 | 慢(退化成逐页扫) | 极快(顺序读 + 向量化) |
| 只读 3 列的宽表扫 | 慢(整行都要读) | 极快(其他列不碰) |
| 高频单行更新 | 快 | 很慢(异步重写 part) |

这张表值得记在心里:它几乎解释了后面所有"ClickHouse 该用/不该用"的判断。

## 01.5 与其它系统的定位

选型的讨论最容易滑向"谁更快",而"谁更快"恰恰是最不该在这本书里下结论的问题:同一个查询在两套系统上的胜负,取决于数据形状、集群规模、版本和配置,任何脱离具体负载的排名都是耍流氓。可以放心说的是**设计取向**——每套系统把哪件事做成了强项、又是以牺牲什么换来的。

**Doris / StarRocks。** 同样是 MPP + 列存 + 面向 OLAP,和 ClickHouse 正面竞争。它们的强项在多表关联和优化器上:有基于统计信息的代价模型,能自己决定多表 JOIN 的顺序与数据分布方式;写入侧也更支持"按主键 upsert / 实时更新"这类形态。ClickHouse 在这两点上相对弱——它的 JOIN 模型是右表进内存建哈希表(第 15 章),更新则是异步重写 part(第 18 章)。所以"要频繁关联维表、要做准实时的明细更新"这类需求,值得先把它们放在候选里。

**Greenplum。** 基于 PostgreSQL 的 MPP 数仓:SQL 方言、优化器、运维习惯都继承 PG 的血统,存量 PG 生态的 SQL 迁移更平滑,复杂查询的规划能力也来自多年打磨。它的设计重心不是"单表大扫吞吐拉满",压缩率和扫描效率通常不是这类系统的卖点。另有一条现状值得知道:Broadcom 收购 VMware 之后,**Greenplum 的开源发行在 2024 年 5 月被终止**——上游仓库被归档、转为纯商业产品(VMware Tanzu Greenplum),社区版本不再有新的公开发布。原 Greenplum 的开发者另起炉灶做了 **Apache Cloudberry**(2024 年 10 月进入 Apache 孵化器),EDB 那边有 WarehousePG,Arenadata 有 Greengage,都是这条血脉的延续。要迁移评估,先看清自己依赖的是哪一支。

**Druid / Pinot。** 面向**实时 OLAP** 的另一条路线:为"流式摄入 + 亚秒级响应"设计,存储模型是段(segment)加倒排/位图索引,擅长带时间范围和高基数维度过滤的看板查询,原生支持流式数据的持续摄入与维度更新。反过来说,在宽表上做临时的、不可预知的大范围聚合,吞吐与压缩通常不如 ClickHouse。两者的差别与其说是快慢,不如说是"为哪种查询形状优化"。本书不给出具体的吞吐倍数——这类对比数字高度依赖负载与调优,应以双方公开发布的官方 benchmark 为准,别拿二手 benchmark 下结论。

**DuckDB。** 嵌入式分析库,可以粗略理解成"分析场景的 SQLite":以库的形式嵌进你的 Python / R / CLI 程序,直接读 Parquet、CSV、DataFrame,单机多核、零运维。它是**库而不是服务**——没有端口、没有并发用户管理、没有集群。所以它和 ClickHouse 常常是配合关系而不是替代关系:先用它在小样本上把 SQL 写对、把数据探清楚,要并发服务和几十 TB 常驻时再交给 ClickHouse。

**Snowflake / BigQuery / Redshift。** 完全托管的云数仓,卖点是存算分离、弹性伸缩、免运维:你不选机器、不调内核参数,按用量付费。ClickHouse OSS 恰好相反——性能上限与运维成本都归你。所以在同一份需求面前,这往往不是"谁快"的取舍,而是"谁替你承担运维和扩缩容"的取舍;真要比较,也得拿 ClickHouse Cloud 去比才公平。

**Elasticsearch。** 强项是**全文检索**:倒排索引、分词、相关度排序,这些是它的看家本领。聚合是后来补上的能力,偏向"结果正确、能出数",而不是大规模数值聚合的最优解;真正的瓶颈常常是内存而不是磁盘。所以业界的常见架构是 ES 管检索、ClickHouse 管分析,把两份索引各用在刀刃上,而不是二选一。

归纳成一条判断法:面对一份新需求,先问四个问题——要不要 JOIN 一堆表、要不要毫秒级的流式摄入与更新、要不要全文相关度排序、要不要别人替你运维。四个都答"不"、而真正的痛点是"宽表很大、聚合很多",那么 ClickHouse 的取舍就是最划算的那一档。

## 01.6 组件清单

ClickHouse 不是一个进程,而是一套工具。看发行包里的可执行文件,就能大致理解"一个集群由哪些角色组成":

| 可执行文件 | 干什么 |
| --- | --- |
| `clickhouse-server` | 服务端进程:监听端口、管理表和后台合并。说"起一个 ClickHouse"通常指的就是它。 |
| `clickhouse-keeper` | 一致性组件,是 ZooKeeper 的替代实现,给复制表存元数据、做分布式协调(第 22 章)。 |
| `clickhouse-client` | 原生 TCP 协议的交互式客户端,也是脚本里最常用的入口(第 02 章 §02.3)。 |
| `clickhouse-local` | 免服务端的查询工具:不监听端口、不起服务端进程,直接在本地文件上跑 SQL(第 02 章 §02.1)。 |
| `clickhouse-copier` | 跨集群、跨表搬数据的工具,常用于分片方案变更之后的数据重分布(第 23 章)。 |
| `clickhouse-disks` | 磁盘抽象层的管理工具,用来查看和操作配置里定义的各种磁盘(本地、对象存储等)。 |
| `clickhouse-benchmark` | 压测工具:把一批查询按指定并发重复执行,给出 QPS 与延迟分位数。 |
| `clickhouse-obfuscator` | 数据脱敏工具:保持结构和分布特征的前提下把真实数据混淆成可分享的样本。 |

这张表不是一份并列的功能列表,而是按角色分层的:两个**长期运行的服务进程**(`server` 是数据面,`keeper` 是它的协调中枢),加上几个跑完即退的**工具**。工具里又能再分一层——`copier`、`disks`、`benchmark`、`obfuscator` 都要**连到某个服务端或集群上去干活**,它们自己不存数据;而 `client` 和 `local` 是**查询入口**,两者的区别只在"要不要一个服务端"。

这个区别值得单独说清,因为它不只是"开不开服务"这么简单。`clickhouse-client` 走的是服务端的**原生 TCP 协议**(默认 9000),它只是把 SQL 发过去、把结果收回来——真正执行查询的永远是服务端。`clickhouse-local` 则完全不联网:它在自己进程里建一个临时上下文,直接执行查询。于是两者的**上下文**也不同:`local` 里没有你建的库表元数据、没有用户与权限;它能"看见"的反而是**本地文件系统**,可以直接把 `data.csv`、`data.parquet` 当成表来查。

系统表这一层要说准确,因为"local 没有系统表"是个流传很广但不成立的简化:`local` **默认就把 system 表挂着**,`system.settings`、`system.functions`、`system.one` 这类"设置与元数据"表可以直接查(不想要可以加 `--no-system-tables` 关掉)。它缺的是服务端在**运行期生成**的那一类——`system.query_log`、`system.parts`、`system.processes` 全靠服务端进程在写,本地没有这个进程,所以它们为空或干脆不存在。定位由此分出:`client` 是"连到我的集群去查数据",`local` 是"不装服务端,就地处理一个文件"。所以想验证一条**类型或函数行为**,`local` 最轻便;一旦涉及库表、权限或后台合并,就只能连真服务端。

那为什么这些名字大多是**同一个多调用二进制**(multi-call binary)?发行时它就是一个 `clickhouse` 可执行文件,可以用 `clickhouse server`、`clickhouse client`、`clickhouse local` 这样的子命令调用,也可以继续用 `/usr/bin/clickhouse-server` 这类同名入口——后者其实只是指向同一个二进制的同名链接,两种写法等价,不必纠结。这么设计有两个实在的理由:**一是分发简单**,所有工具及其依赖库打进一个文件,不会出现版本对不上;**二是客户端与服务端天然同版本**,免去协议版本不匹配的坑。代价是这个文件很大(含 JIT、压缩、各种格式支持),但在容器与 CI 里"一个文件搞定所有事"通常更划算。至于 `copier`、`disks` 这些工具的具体参数与能力边界,版本之间会变,用之前以 `--help` 和目标版本的文档为准。

## 01.7 部署形态阶梯

ClickHouse 的部署形态基本是四级台阶,每一级都是被上一级解决不了的问题逼出来的。先记住这条阶梯的形状,具体机制后面章节再展开。

**一级:单机。** 一个 `clickhouse-server` 进程、几张 `MergeTree` 表。能扛多大数据取决于单机的磁盘和内存,没有副本、没有容错——机器坏了就停。本书前 19 章的例子全部停在这一级,它也是绝大多数团队真正开始的地方。

**二级:复制。** 同一份数据在多个节点上各存一份(`ReplicatedMergeTree`,协调依赖 Keeper),解决的问题是**可用性**:任意一台挂了,集群照常读写。它不增加存储容量(每份数据仍然完整地存在每个副本上),但加上新版本的并行副本能力,读吞吐也能随副本数分摊。

**三级:分片。** 数据按分片键切开,分散到多台机器:`总容量 = 各分片之和`,`写入带宽` 也近似线性扩展。代价是复杂度——跨分片查询要经过 Distributed 表(第 23 章),分片键选错之后想重分布是一桩大工程。

**四级:对象存储 / 分层存储。** 把冷数据(或全部数据)放到 S3 之类的对象存储上,本地只保留需要频繁访问的部分。云上的 `SharedMergeTree` 是这条路的极致形态——存算彻底分离、计算节点秒级伸缩;但它是 **Cloud 侧的能力,不在开源发行版里**。

第 22 章(复制与 Keeper)、第 23 章(分片与分布式查询)、第 29 章(生产部署与运维)基本上就是顺着这四级往上爬。要提醒一句:阶梯越高,复杂度增加得比能力快,别一上来就上分片。

## 01.8 生态全景

围绕开源内核,近年长出几层:

**ClickHouse Cloud。** 官方托管的云服务,底层用的是一套共享存储架构(SharedMergeTree):存算分离,计算节点可以秒级伸缩,存储放在对象存储上。这解决了自建集群最难的两件事——扩容和副本同步。计费与运维细节不在本书范围内,但需要知道"Cloud 上的某些行为(比如副本管理)和自建不一样"。

**ClickStack。** 官方推出的可观测性栈,把 ClickHouse 当作日志、指标、追踪的统一后端。这正是第 38 章要亲手搭一遍的那类系统:一条链路从采集、入库、查询到看板。

**向"更多工作负载"扩张。** 传统上 ClickHouse 只做分析。近几年的方向明显在往外扩,而扩法有共同的思路:**与其把数据搬出去喂给另一套系统,不如把那种查询的加速手段搬进来**。下面三条在 25.3 上都能找到落到实处的机制,但也都带着明确的边界。

**向量搜索。** 做法是给一列向量(`Array(Float32)` 或 `Array(Float64)`)建一个**跳数索引**,类型名 `vector_similarity`,底层是 **HNSW** 近邻图;用法是把"最相似的 N 条"写成普通的 `ORDER BY 距离函数(向量列, 参考向量) LIMIT N`,索引让这个排序不必逐一向量算距离。它的边界有三条:这是**近似(ANN)检索**,召回率与延迟要靠索引参数权衡,拿不到精确答案;索引在**写入与合并时构建**,所以写入会明显变慢,它面向"读多写少"的负载;而且在 25.3 上它仍是**实验特性**,要显式打开对应开关(类型名与开关名都随版本变过)。建法与参数细节在第 30 章 §30.12,版本演化在第 32 章 §32.7,这里只记结论。

**全文索引。** 做法是给 `String` / `FixedString` 列建一份**倒排结构**,加速"某个词是否出现"这类**词级谓词**。它写在 DDL 的 `INDEX` 子句、也被 `system.data_skipping_indices` 收录,但机制上**不是按 granule 裁剪的跳数索引**——官方文档明说它映射的是**行号**而非 granule 号,所以 `GRANULARITY` 对它**没有意义**(语法上还得写,值被忽略)。**类型名与开关分版本**:25.3 里它叫 `full_text`、是**实验特性**,要 `SET allow_experimental_full_text_index = true`,当时也不在 Cloud 上支持;更晚的版本改过名、也换过参数语法。完整的改名链、以及"怎么在你那一版上当场确认自己建出来的到底是什么类型",统一放在第 11 章 §11.9(机制侧)与第 32 章 §32.7(演化侧)。它的边界很明确:**加速的是"过滤",不是"相关度排序"**——它不会像 Elasticsearch 那样给结果打分、做相关性排名,分词器也只有有限的几种。所以它能替掉"分析库 + ES 两套"里的**过滤**那一半,替不掉检索那一半。

**湖仓集成。** 做法是让 ClickHouse **直接读** Iceberg / Delta Lake 这类开放表格式,数据不必先搬迁。机制上分两层:一层是表函数或表引擎(如 `iceberg()`、`IcebergS3` 等),按表的元数据去列文件、按格式解析;另一层是库引擎(`DataLakeCatalog`,25.3 引入),它连的是一个外部 catalog(Glue、Unity Catalog 等),把 catalog 里登记的表自动发现成一整库可查的表(详见第 30 章 §30.4)。要记住的是它**主要是只读集成**:官方对 Iceberg 表引擎的表述就是"read-only",并且明确提示 ClickHouse 原本不是为"外部会改 schema"设计的,某些特性可能不可用,建议优先用表函数而非表引擎。具体的写入支持与成熟度在不同格式、不同版本之间差异较大,**这一点本书不做断言**,以目标版本文档为准。

这三条都在快速演进,具体能力和边界在版本之间变化较大,**不建议把某个具体功能的成熟度当成稳定事实**——用到时以目标版本文档为准。

## 01.9 2026 年的现状

**版本节奏。** 版本号形如 `YY.M`:年份加该年的第几次发布。近年是**每月一个特性版本**(25.1、25.2、25.3 这样递增),由于节奏是每月一发,`M` 在多数年份里也正好等于月份——这一条是可以放心用的。

**LTS 支持策略。** 与"每月一版"并行的是 **LTS(长期支持)**线:被标为 LTS 的版本获得更长的补丁窗口,而**非 LTS 只被维护到下一版发布前后,官方只给最近三个 stable 版本发补丁**。可以放心用的是这一条**方法**:官方仓库的**版本回移(backport)**机制围绕 `release/<YY.M>` 分支组织,LTS 分支的维护期明显长于普通分支——这是能在仓库里直接观察到的证据,本书基线 25.3 正是其中一条 LTS。

可以给出确切的口径了:ClickHouse **每年发两条 LTS,分别在 3 月与 8 月**(版本号形如 `YY.3`、`YY.8`,25.3、25.8 就是这样一对),并且**同时支持两条 LTS,每条至少支持 12 个月**;与之并行的 **Stable 版每月一发**,但**只有最近三个 stable 版本拿补丁**。本书基线 `25.3` 发布于 **2025-03-20**,支持到 **2026-03-20**。这些数字会随官方支持政策调整,所以**做升级或采购决策时,仍应以官方 release notes 里的版本标注与官方支持政策页为准**,而不是任何二手表格(包括这一页)。

**把这两个日期和本书的写作时间放在一起,结论不太好看。** 本书写于 2026 年 10 月,而基线的支持期在 2026-03-20 就结束了——按"同时支持两条 LTS"的规则,接替它的那条 LTS 已经发布半年多。也就是说:**25.3 是一条已经走出支持窗口的版本**。这不影响本书的读法(所有陈述仍以这一个版本为准,每一条都带着版本号、可以逐条核对),但它直接影响你的落地决定:**不要把 25.3 当成"现在该上的生产基线"**。要部署,先去官方 release notes 挑一条仍在支持期内的 LTS;本书真正想让你带走的是那条**方法**——生产环境只跟 LTS 线并在两条 LTS 之间滚动打补丁,拿到任何一个版本号,先去 release notes 确认它属于哪条线、支持到什么时候。

**已经 GA 的重要特性。** 几个改变了"能不能用"边界的东西:

- **`JSON` / `Variant` / `Dynamic` 类型**。半结构化数据不用再"塞进 String 然后查询时解析"。这三个类型在 25.3 达到可生产状态,并且 `enable_json_type` 的默认值从 `false` 改成了 `true`——也就是说 25.3 及以后开箱可用。这补上了 ClickHouse 相对 ES 最大的短板之一。
- **轻量级删除(Lightweight DELETE)**。以前删除数据要等一次异步的 Mutation 重写 part;轻量级删除让 `DELETE` 变成标记式删除,立即返回,后台再真正清理。这让"删除"第一次变成了可以在交互里使用的操作。
- **并行副本(Parallel Replicas)**。一条查询可以同时下发给同一个分片的多个副本,每个副本只读一部分数据,再合并。第一次让"加副本"同时提升了查询能力,而不只是提升可用性。
- **查询条件缓存(Query Condition Cache)**。25.3 新引入的一件"白捡"的加速:把"某段数据(granule)一定不满足某条 `WHERE`"这个结论缓存下来,下次遇到同样的过滤条件就直接跳过这些 granule——等于把过滤结果当成一份临时索引复用。它由会话设置 `use_query_condition_cache` 控制,**25.3 上默认值是 `0`(关闭)**、**从 25.4 起默认值翻成 `1`**(上游 PR #79080),所以是一条**版本敏感**的行为:换版本时别照搬,用 `SELECT name, value FROM system.settings WHERE name = 'use_query_condition_cache'` 当场确认当前取值。
- **共享合并树(SharedMergeTree)**。即上面说的存算分离架构,是 ClickHouse Cloud 的基础;它是 **Cloud 侧的专有能力,不在开源发行版里**——OSS 侧的多副本/高可用用 `ReplicatedMergeTree`(第 22 章),两者不是"同一个引擎的不同配置"。

需要提醒的是,**这些特性的成熟标签在版本之间会变**:某个功能在这一版是 Beta、下一版可能 GA,参数的默认值也可能翻转。上面两条核对过的默认值(`enable_json_type` 在 25.3 为 `true`、`use_query_condition_cache` 在 25.3 为 `0`、25.4 起为 `1`)就是例子。如果你用的是别的版本,别照搬。`第 32 章 §32.2` 把这些能力的成熟度做成一张速查表,`§32.10` 讲怎么读 release notes、怎么跟踪这一类变化——本章不逐条重复。

## 01.10 什么负载不该用它

判断"该不该用 ClickHouse",比记住它的优点更重要。下面几类负载,用了大概率会后悔:

**高频点查。** 比如每秒几万次"按 ID 取用户最新状态"。列存要为每次查询拼列,而且没有为单行查找优化的缓冲池。这类需求用 KV 存储或行存数据库。

**强事务 OLTP。** 转账、库存扣减、订单状态机——需要跨表原子性和行级锁的场景。ClickHouse 没有多语句事务,硬做只能靠应用层补偿,复杂度会失控。

**频繁更新单行。** 每次更新都会触发一次 part 重写或删除标记。如果一张表的数据会被反复修改(而不是"只追加、偶尔批量修正"),维护成本会随着 part 数量爆炸。需要经常改数据的场景,考虑 ReplacingMergeTree 这类去重引擎,或者干脆换个存储。

**复杂的多表事务型 JOIN。** ClickHouse 的 JOIN 是"右表装进内存做哈希建表"的模型,大表关联大表很容易吃光内存。星型模型的宽表可以,但把它当成有强优化器的 OLTP 查询库用,会一直和计划器较劲。

换个说法:**如果"数据的写入方式是追加、读取方式是聚合"成立,ClickHouse 值得考虑;只要这条不成立,先想想别的方案。**

## 01.11 小结

列式、MPP、向量化、无事务、OLAP——每个词都是一次能力与代价的交换,ClickHouse 的适用面正是这些交换的交集:**追加写、批量读、大范围扫描、聚合出少量结果**。它和"行存 + B+ 树"的分歧不在快慢,而在假设:一个优化"精确定位少数行",一个优化"排除大部分数据后顺序读";而这些假设连同它的短板,都是当年为 Yandex.Metrica 的点击流一次选定的。

选型上记住两条:横向比,多表 JOIN 与优化器看 Doris / StarRocks,复杂 SQL 迁移看 Greenplum,流式实时摄入看 Druid / Pinot,单机嵌入式分析看 DuckDB,免运维托管看 Snowflake / BigQuery / Redshift,全文检索看 Elasticsearch;纵向铺,按"单机 → 复制 → 分片 → 对象存储"四级阶梯往上爬,别一上来就上分片。落地要用到的组件清单与版本线的判读方式,分别见 `§01.6`、`§01.9`——后者还交代了一件必须说清的事:**本书对标的 25.3 已经走出了支持窗口**,把它当生产基线之前先确认升级路径。

最后记住不该用的四类场景:高频点查、强事务 OLTP、频繁单行更新、复杂多表事务。
