# 附录 E:MySQL 与 PostgreSQL 迁移 playbook

前面各章把"从 MySQL / PostgreSQL 迁过来"当成一条独立的阅读路径反复提起:第 02 章 §02.8 讲五个心态转变,第 03 章 §03.5 与 §03.9 讲类型语义,第 15 章讲 JOIN 要小心,第 17 章 §17.22 挑出"同名不等价"的那批函数,第 18 章讲更新是异步的,第 28 章给反模式清单。那些都是**筛选器**:告诉你哪些地方会咬人。这一份是**流程**:先做什么、后做什么、每一步的产出物是什么、什么算做完。

两份东西的差别很大。筛选器回答"这里有个坑",流程回答"我现在该打开哪个文件、跑哪条命令、拿什么当验收标准"。真正让迁移失败的不是没意识到某个坑,而是**顺序错了**——先改 schema 再想清楚要迁哪些表,先写查询再对齐类型,count 一对上就宣布完工。下面按一个真实迁移项目的时间线组织:范围判断(E.1)、盘点(E.2)、类型映射(E.3)、重写 schema(E.4)、搬数据(E.5)、改查询(E.6)、验证(E.7)、切换与回滚(E.8),然后是一个完整的例子(E.9),最后是可以照着抄的清单(E.10)和几种把迁移做死的方式(E.11)。

**关于可执行性。** 本附录里的 MySQL / PostgreSQL 语法是通用形态,不需要特定版本;ClickHouse 侧的 DDL 与查询按 25.3 书写,但本书的写作环境**没有安装真实的 ClickHouse**,所以这些语句没有在真实实例上执行过,凡是涉及具体默认值、报错文本、精确类型推断行为的地方,都以"**未确认**"标注或明确指向讲透它的正文小节。它们在配套实现 `mini-clickhouse` 上能验证"机制是不是这样",但那不是真实引擎,别拿它当行为基准。配套的工程手册在附录 B,排错在附录 D,端到端实战在附录 F。

## E.1 先判断该不该迁:范围、"读写比"与"两个都要"

一个迁移项目的第一份交付物不是 schema,而是一个**决定**。几乎每个失败案例都能追到一个被跳过的问题:这套负载到底该不该搬到 ClickHouse 上。

判断的根,是两种存储引擎为完全相反的访问形态而设计。行存 + B+ 树的 OLTP 引擎优化的是"按主键定位一行、改一行,并在事务里保证这几行一致";列存 + 稀疏索引的 ClickHouse 优化的是"扫一大片行、只取其中几列、做聚合,写入基本只追加"。第 01 章 §01.10 把"什么负载不该用它"单列了一节,那一节是这一节的底稿。

**"读写比"这个直觉怎么用。** 常见说法是"读多写少的系统适合分析库",这句话太粗,会把人带偏——OLTP 系统也是读多写少。真正有区分力的问法是**每一行的生命周期里,它被怎么对待**:

- 一行数据**写一次、之后基本不改**,并且它会被**反复地、成批量地**读去做聚合——这是分析负载。事件的、日志的、指标的都是这个形状。这类数据的"写"是一次性成本,读是持续收益,列存把读的那一侧收益放到最大。
- 一行数据在它的生命周期里被**按行反复读写**:下单改库存、支付改余额、心跳更新会话状态、任务队列改状态位。每次操作都只碰一行或几行,但要低延迟、要事务、要唯一约束。这类数据搬到 ClickHouse 上会立刻失灵——第 28 章 §28.5.1 把它列为反模式"把 ClickHouse 当 OLTP 用"。

所以逐条负载问两个问题就够了:**写入形态**是"只追加"还是"频繁按行改"?"只追加"是迁的前提,**频繁按行改**基本就该留下。**读取形态**是"按主键取一行或几行"还是"按时间范围扫一片、只取少数列、做分组聚合"?后者才是 ClickHouse 的主场。两个问题都偏分析侧,才进候选名单。

**哪些负载真的该迁。** 事件流与日志、指标与追踪(第 38 章 §F.2 到 §F.4 的整套模型就是这个形状);交易/订单明细的**只读副本**(上游仍在写,这边只做分析);需要保留原始明细、同时又频繁做 rollup 的大事实表;任何"报表要扫几个月数据、按几个维度分组"的查询。这些的共性是:数据大、几乎只追加、查询是聚合而不是点查。

**哪些负载该留在原地。** 需要唯一约束、外键、多语句事务的账务核心与库存;高频按行 UPDATE 的状态表(余额、库存、会话、锁、队列);要求低延迟的"读己之写";任何把数据库当"带索引的持久化字典"用、每次只碰一行的地方。还要提醒一件事:即便某张表符合"只追加 + 聚合读",如果它**很小**(几百行),搬过来除了多一套系统没有收益——小表在 OLTP 引擎里聚合也就几毫秒。

**最常见的场景是"两个都要"。** 现实里几乎不存在"把业务库整体换成 ClickHouse"。正确的形态是**双系统**:OLTP 引擎继续当写主库(system of record),ClickHouse 作为它的一份**分析副本**,数据靠 CDC 或批处理单向同步过来。这条路线的最大价值是一个安全阀——写路径**完全不动**,于是迁移失败的上限是"报表暂时不可用",而不是"业务停摆"。本附录从头到尾讲的都是这份副本怎么建,不是怎么替换主库。

顺带一句运维判断:起步阶段不必先上集群。第 29 章 §29.1 的第一问就是"先问要不要集群"——单机足以扛住相当规模的分析查询,先跑起来、把模型和查询验证对,再谈分片与副本(第 22、23 章)。

## E.2 动手改 schema 之前:盘点与评估

决定要迁之后,下一步**不是**打开 `SHOW CREATE TABLE` 去逐表翻译。几百张表的库如果逐表翻译,你会把一半的工作量花在永远没人查的表上。这一步的产出物是一张**目标表清单**,以及每张表"为什么迁、它的主要查询是什么"。

**第一步:把表的清单和体量导出来。** 从元数据里拿一份全表清单,至少带上行数、磁盘占用、列数、最近是否被写。MySQL 走 `information_schema.tables`(`table_rows` 是估算值,看量级够用,要精确再 `count(*)`),PostgreSQL 走 `pg_class`(`reltuples` 同样是估算)。这一步不判断,只摆事实:哪些表几十行、哪些几亿行、哪些几个月没动过。

**第二步:找出值得迁的查询,而不是值得迁的表。** 这是整个盘点里最容易做反的一步。迁表的目的是让某些**查询**变快或变可行,所以起点是查询。来源有三个:数据库的慢查询日志;BI 工具/报表平台里被**真正点开**的看板与报表;定时跑的批处理报表。挑出来的共性很明确:**大范围扫描 + 少量维度分组 + 时间范围过滤**。反过来,那些"按主键取一行"的高频查询,即便很慢也不该迁——它们正是 ClickHouse 不擅长的形状。

拿到查询清单后,把它们反过来映射到表:哪些表**被这些查询扫**?一张很大的表如果从没出现在任何慢查询或看板里,它的优先级可以往后放。会有一个反直觉的发现:**最值得迁的往往不是最大的表,而是被全表扫得最狠的表**——为报表做全表聚合的明细表,哪怕只有几千万行,也比没人查的十亿行归档表更该先迁。

**第三步:给每张候选表贴一个标签。** 三类:

- **事实型**——大、只追加(或极少改)、行里带时间、几乎总是被聚合。这是迁移的主体,也是要花力气设计排序键与分区键的那一类。
- **维度型**——小(几十到几万行)、变化慢、常被拿来补属性(店铺名、品类名、客户等级)。这类迁过来,但**首选不是当普通表 JOIN**,而是做成字典(第 21 章 §21.2)或在写入时摊平进事实表(第 14 章 §14.5、§14.6)。
- **不迁**——纯 OLTP 操作表、配置表、会话表、队列、锁、以及任何"热点按行更新"的小表。明确写下"不迁"和写下"迁"同样重要,否则半年后有人会问"这张表怎么没有"。

**第四步:列级裁剪。** 一张表搬过来**不需要把每一列都搬**。只聚合/过滤/展示用得上的列才留;OLTP 专用列(乐观锁的版本号、审计用的宽 JSON、没有 JOIN 需求的外键约束列本身)可以只留 id、不留约束。列裁剪的收益是线性的(第 05 章 §05.9:一列占多少字节,直接等于查询要不要为它花 IO),也是迁移时唯一"免费"的瘦身机会——生产环境里想 ALTER 掉一列代价很高(第 09 章 §09.3)。

盘点做完,你手上应该有一份东西:**目标表清单**,每张表一行,写着它属于事实/维度、它的主要查询是哪几条、迁移理由是什么。这份清单是 E.3 到 E.4 所有决定的输入。没有它就开始写 DDL,等于在猜——这一步和"选排序键"的第一步(第 14 章 §14.3:先列查询清单,不要列实体清单)是同一个道理。

## E.3 类型映射:从两套类型系统到一套

类型映射是迁移里**看起来最机械、实际最危险**的一步,因为很多映射**不报错**——`VARCHAR(255)` 变成 `String` 能存能查,`DATETIME` 变成 `DateTime` 也能存能查,但语义已经悄悄换了。危险的不是"存不下",是"存下了、也查得出,只是答案不一样"。

### E.3.1 整数、自增键与序列

整数映射本身很直:两边都是定宽补码,位宽对上就行。三处要注意。

**符号性要成对决定。** MySQL 的 `INT UNSIGNED` 这类无符号列,在 ClickHouse 里有 `UInt32` 精确对应,别一律映射成有符号——第 03 章 §03.2 有一条容易被忽略的规则:有符号与无符号混合运算会触发**位宽加倍**(`Int8 + UInt8 → Int16`),一张表里混着 `Int64` 和无符号的 `UInt64` 一起算,可能凭空贵一档。整张模型里尽量统一是否带符号。

**没有 24 位的类型。** MySQL 的 `MEDIUMINT` 是 24 位,ClickHouse 的整数族是 8/16/32/64/128/256,没有 24 这一档。映射到 `Int32`/`UInt32`:值不会变(拓宽是安全的),但每行多占一个字节——几亿行上是实打实的存储差异。

**自增键是硬的语义改变。** 这是整数这一节真正的问题。MySQL 的 `AUTO_INCREMENT`、PostgreSQL 的 `SERIAL`/`BIGSERIAL`,本质是"由数据库维护一个**序列**,每次插入自动发一个**唯一、递增**的号"。ClickHouse 的 MergeTree **没有序列,也没有自增列**。这是设计,不是缺功能:唯一性在 ClickHouse 里根本不归数据库管(见 §E.3.7)。于是迁移时只有两条路:

- **把值带过来。** 源库里每一行已经有它的 id,那就把这个 id 当普通列原样迁入(`UInt64`)。这是最稳的:所有下游对 id 的引用继续成立。代价是**新增的行**没有"下一个号"可用。
- **让上游/应用负责生成新 id。** 新写入的行,id 由应用侧生成(UUID、雪花 id、或应用自己维护一段号段),再作为普通列写进 ClickHouse。

**不要用"在 ClickHouse 里现算一个 id"来替代序列。** 拿一个哈希函数对整行求值当 id,看着优雅,但它把 id 从"稳定标识"变成了"内容指纹":内容一改,id 就变,任何把这个 id 当外键用的地方全断。这在迁移里是最隐蔽的一类错——不报错,只是关联静默错位。

还有一层要接受的事:即便你保留了 id 列,它也**通常不再是排序键**。OLTP 里 id 是聚簇键、是访问入口;在 ClickHouse 里排序键要从**查询的过滤模式**推导(第 14 章 §14.3),而分析查询几乎从不按 id 过滤。所以 id 在 ClickHouse 里降格成一个**载荷列**——留着,但不再是索引的主角。这个转变值得在 E.4 再讲一次。

### E.3.2 日期时间:时区是列属性,精度会静默丢

日期时间是整个映射里**最容易被静默改掉**的一处,因为两边的"日期时间"根本不是同一个概念。先把两边的模型对齐。

MySQL 的两个类型语义**不同**:`DATETIME` 存的是**不带时区的墙上时间**(写入什么就是什么,换个会话也不变),范围大约 1000 到 9999 年;`TIMESTAMP` 存的是**一个瞬间**,写入时按会话时区换算成 UTC 存,读出时再按会话时区换算回来,范围受 32 位限制、只到 2038 年。PostgreSQL 的 `timestamp`(不带时区)对应 MySQL 的 `DATETIME`,`timestamptz` 对应 `TIMESTAMP`(存的是瞬间,按会话时区显示)。

ClickHouse 侧(第 03 章 §03.6):`DateTime` 底层是 UTC 秒数,`DateTime64(P)` 是带小数位的刻度数;**时区是列的属性,不是查询的属性**——建表时写 `DateTime('Asia/Shanghai')` 还是 `DateTime('UTC')`,决定这一列怎么被解析和显示,同一个底层值在两列上打印出来可能不一样。不写时区参数时用服务器配置的时区。

把这两套模型一对,映射里的坑就清楚了:

**第一,`DATETIME`/无时区 `timestamp` 迁过来,必须决定它代表哪个时区。** 源库里它没有时区,ClickHouse 里 `DateTime` 一定带时区。如果源值本来是"上海墙上时间",你把它原样塞进一个默认时区为别处的 `DateTime`,查询里 `toDate()` 出来的"天"就可能差一天。判据很简单:这些时间戳在业务上代表哪个时区的事件?想清楚,然后**在建表时把时区写死**,别依赖服务器默认。

**第二,瞬间类型(`TIMESTAMP`/`timestamptz`)统一按 UTC 存。** 它们本来就是瞬间,`DateTime('UTC')` 是自然落点。这样分区键、按天聚合也都走 UTC,不受任何人的会话时区影响。要展示成"本地日"时,到查询或展示层再 `toTimeZone`——第 03 章 §03.6 讲夏令时时给的就是这条原则:**把"怎么存"和"怎么看"分开**,存一律 UTC。

**第三,精度会静默丢。** PostgreSQL 的 `timestamp` 默认精度是**微秒**(6 位小数),MySQL 的 `DATETIME(6)`/`TIMESTAMP(6)` 也是微秒。ClickHouse 的 `DateTime` **只有秒精度**;要小数位必须用 `DateTime64(P)`,P 是小数位数(3 毫秒、6 微秒、9 纳秒)。如果你把 `DATETIME(6)` 直接映射成 `DateTime`,那些微秒会被**丢掉**,而且不报错——任何依赖亚秒排序或亚秒去重的查询就开始出错了。带小数位的源列,请映射到 `DateTime64(6)`。反过来要留意 §03.6 的另一条:`P` 越大,可表示的范围越小,纳秒精度大约只覆盖 1677 到 2262 年。

**第四,范围对不上要显式处理,而且两边的"上界"都够不着。** MySQL `DATETIME` 能装到 9999 年,ClickHouse `DateTime` 上限是 2106 年(第 03 章 §03.6);PostgreSQL 的 `timestamp`/`timestamptz` 跨度更夸张,约从公元前 4713 年到公元 294276 年,远超 `DateTime`(2106)乃至 `DateTime64` 的范围——这是比 MySQL 侧大得多的一个范围问题。`DATE` 也一样:MySQL `DATE` 能到 9999 年,而 `Date` 只到 2149-06-06、`Date32` 到 2299-12-31,多出来的那截照样装不下。真有超出范围的日期值会怎样?第 03 章 §03.6 已经讲透:由设置 `date_time_overflow_behavior` 决定,而它的**默认值是 `ignore`——静默忽略、结果是未定义的**,典型表现是回绕成一个看起来合理的日期,**既不是插入失败,也不是截断**。也就是说默认情况下没人会提醒你。所以迁之前先用源库查一遍 `MAX(时间列)`/`MIN(时间列)`,超出目标类型的范围就在源头处理;要主动抓到越界,显式 `SET date_time_overflow_behavior = 'throw'`(或用 `'saturate'` 做保护性截断)再把导入跑一遍。

**第五,没有 `TIME` 类型。** 单存的"一天里的时刻"两边都没有自然落点;用整型秒或 `String` 承载,并接受任何按时刻排序/比较的查询都得自己处理。

### E.3.3 Decimal:精度和标度带得过来,算术规则带不过来

`DECIMAL(P,S)`(MySQL)与 `numeric(p,s)`(PostgreSQL)映射到 ClickHouse 的 `Decimal(P,S)` 是直译,`P` 与 `S` 一对一带过来。金额类数据**必须**用 Decimal,绝不能用 `Float`(第 03 章 §03.4),这条在源库里多半已经遵守,迁移时别打破。

三件事带不过来:

**范围上限。** ClickHouse 的 `Decimal` P 最大到 76(底层 `Int256`,见 §03.4)。MySQL 的 `DECIMAL` P 上限是 65,落在范围内。但 PostgreSQL 的 `numeric` **不写精度时是不限精度的**(可以远超 76 位),这类列**不能原样映射**——要么显式给它定一个 `(P,S)`(并接受精度损失),要么用 `String` 存(放弃数值运算)。这是 PostgreSQL 特有的坑,MySQL 侧不会遇到。

**算术规则不一样。** 这是最隐蔽的一处。第 03 章 §03.4 把 ClickHouse 的规则讲得很细:加减法取较大的 scale;**乘法把 scale 相加**(两位小数乘两位小数得四位小数,而且连乘会撞 scale 上限);除法沿用被除数的 scale、**不放大**;小数位超出时**丢弃(截断),不做舍入**——想要四舍五入得自己 `round`。同一列 `Decimal(18,2)` 上的 `a * b`,在源库和 ClickHouse 里可能得到**不同的小数位和不同的最后一位**。这不是迁移错误,是两套 Decimal 实现的固有差异,只能靠"迁移后别在 CH 里重算金额派生值、改用源库算好的值"来规避。

**溢出检查有断档。** §03.4 的另一条硬事实:`decimal_check_overflow` **默认打开**,但**对 `Decimal128`/`Decimal256` 没有实现**——宽 Decimal 一旦整数部分溢出,**不报错,直接给一个错的值**。迁移时如果为了容纳大金额用了宽 Decimal,请对这条格外小心。

结论:金额的**存储**照搬没有问题,**在 ClickHouse 侧做 Decimal 乘法或除法**要单独验证。凡是源库里已经算好、存成 Decimal 的派生金额,优先原样带过来。

### E.3.4 字符串与二进制:长度约束会丢掉

MySQL 的 `VARCHAR(n)`、`TEXT`、`CHAR(n)`,PostgreSQL 的 `varchar(n)`/`text`/`char(n)`,ClickHouse 侧**全部塌缩成 `String`**——第 03 章 §03.5 讲得很直接:`CHAR`/`VARCHAR`/`TEXT`/`BLOB` 这一堆名字在 ClickHouse 里都是 `String` 的别名。二进制类型(`VARBINARY`/`BLOB`/`bytea`)也是 `String`,因为 `String` **二进制安全、不校验编码**,存什么字节都行。

直译不报错,但会带来三处**静默**的变化,都出自"长度参数被忽略":

**长度约束消失了。** `VARCHAR(255)` 迁成 `String` 之后,不再截断、不再报错、也不省空间——列能装任意长度。源头那条"数据库会拒绝超长字符串"的不变量没了。**什么会坏**:写入侧一旦有 bug 塞进一条超长串,它会被安静地存下来,然后在某个 `GROUP BY` 或排序里把内存打爆。如果你的业务真的依赖这条约束,把它挪到**写入侧**校验(ETL 里 `lengthUTF8(x) <= n`),或对确知定长的列用 `FixedString(N)`。

**`CHAR(N)` 的补齐没了。** 传统 `CHAR(N)` 用空格把值补到定长,所以 `'ab'` 和 `'ab '` 在存储上是同一个定长串;ClickHouse 的 `CHAR` 只是 `String` 别名,`CHAR(16)` 给不了定长。要定长必须显式写 `FixedString(N)`,而它的补齐方式**不一样**——用**零字节**补齐,不是空格;超过 N 字节**直接报错**,不是截断(§03.5)。所以 `CHAR(N)` 映射到 `FixedString(N)` 也不是无脑直译,尾部补齐字符换了会改变相等判断。

**排序规则与字符集没了。** MySQL 的默认排序规则常常**不区分大小写**(`utf8mb4_general_ci` 之类),ClickHouse **按字节比较、没有排序规则**,`'a'` 和 `'A'` 永远不等,`'Z' < 'a'`(第 03 章 §03.5、第 17 章 §17.22)。后果是"不区分大小写的去重/分组"迁过来**不报错,只是多出几组**。需要这种行为,就显式 `lower()`/`upper()`,或用 `COLLATE`(第 16 章 §16.3,它只该出现在最后一步)。

### E.3.5 JSON 与半结构化:归一化与"什么时候解析"

MySQL 的 `JSON`、PostgreSQL 的 `json`/`jsonb` 迁到 ClickHouse,有两条路径,选哪条取决于你打算怎么用它。

**路径一:原生 `JSON` 类型。** 25.3 起 `enable_json_type` 默认为开(第 03 章 §03.13),`JSON` 会把路径提升成真正的**子列**,于是 `data.user.id` 能类型安全地读。至于"给子列建跳数索引"这一能力——**它在 25.3 上支持到什么程度,第 03 章 §03.13 同样标为未确认**(与下面"类型推断不稳定"同一档口径),别把它当成已核实的承诺。适合"要按路径过滤/聚合、团队里多人反复查它"的场景。

**路径二:`String` + `JSONExtract*`。** 整份原文塞进 `String`,查询时用 `JSONExtractInt`/`JSONExtractString`/`JSONExtract` 现场解析(第 17 章 §17.14)。适合"结构极不稳定、只是偶尔抠一两个字段"的场景。判据在 §03.13 里给过:`JSONExtract*` 是"查询时付费",原生 `JSON` 是"写入时付费、查询时收割"。

三处要留意:

**`jsonb` 会归一化,`json` 不会。** PostgreSQL 的 `jsonb` 是**解析后的二进制形态**:它会去掉键的重复与空白、按某种内部顺序组织键;`json` 则保留原文(包括重复键与空白)。MySQL 的 `JSON` 更接近 `jsonb`。如果源库里存的是 `jsonb`,它的"值"和原文可能对不上——迁移时按**解析后的值**迁,而不是按原始字符串迁。

**类型推断不稳定。** 第 03 章 §03.13 明确把"`JSON` 路径类型推断的稳定性"列为**未确认**:同一条路径这次推断成 `Int64`、下次可能不同。要用原生 `JSON` 做设计,先在目标版本上跑一遍,别照搬任何一版的文档。真要在某条路径上**排序或建索引**,§03.13 的建议是用**物化列**(把路径 `JSONExtract` 出来存成真列)最稳,而不是只依赖类型提示。

**键的语义。** 半结构化的"键"在 ClickHouse 侧不参与稀疏索引:把 JSON 里经常过滤的那个键提升成**真正的列**并放进排序键,才是让它被索引加速的唯一办法(第 14 章 §14.5 的第一原则:能提前固定的字段,就不要塞进 `JSON`)。

### E.3.6 布尔、枚举、UUID、数组

**布尔。** MySQL 的 `BOOLEAN` 是 `TINYINT(1)` 的别名,PostgreSQL 的 `boolean` 是真正的类型。ClickHouse 侧的惯例是用 `UInt8`(0/1)表示布尔——**不要指望有一个和它们完全对应的独立布尔类型**。较新版本里出现过一个 `Bool` 类型,它本质上是 `UInt8` 的别名,其确切可用性与语义**本书未在 25.3 上核对,以目标版本文档为准**;迁移时按 `UInt8` 规划最稳,别把查询写成依赖"布尔类型"本身的样子。

**枚举。** MySQL 的 `ENUM('pending','paid','shipped')` 可以映射到 ClickHouse 的 `Enum8`/`Enum16`(第 03 章 §03.7),但有两处语义差异。一是**取值集固定**:新增一个取值要 `ALTER TABLE ... MODIFY COLUMN`,插入集合外的值会**直接报错**(这其实是好事,是强校验)。二是**排序与比较按底层整数走,不按名字字母序**——§03.7 特别点出这一条容易忘。所以映射时要**按源库 ENUM 的原有顺序**给成员分配整数,才能保住原来的排序语义;随便分配整数会让 `ORDER BY 这个列` 的结果和源库不一致。取值经常变的列,改用 `LowCardinality(String)`(§03.10)。

**UUID。** PostgreSQL 的 `uuid` 是 16 字节原生类型,ClickHouse 有对应的 `UUID`(同样 16 字节),直译即可。MySQL 里 UUID 常存成 `CHAR(36)` 或 `BINARY(16)`——迁成 `UUID` 类型能省空间也能做类型校验,但要注意**别把 UUID 当排序键**:如果原来的查询依赖 `CHAR(36)` 的字典序,换成原生 `UUID` 后排序结果可能不同(两者底层表示不一样)。UUID 作为**通用唯一标识**很合适,作为**排序维度**要谨慎。

**数组。** PostgreSQL 有原生数组(`int[]`、`text[]`),MySQL 没有(用 JSON 或子表模拟)。`int[]`/`text[]` 映射到 `Array(Int32)`/`Array(String)`。两处语义差异(第 03 章 §03.8):下标从 1 开始,以及**越界不报错**。两边的越界**都不抛错**,但返回的东西不同:PostgreSQL 返回 **`NULL`**(`SELECT (ARRAY[1,2,3])[5]` 得到 `NULL`,后续比较/聚合按 `NULL` 语义传播),ClickHouse 返回元素类型的**零值**(数值列是 `0`,字符串列是空串)。所以同一个越界索引,PG 侧的症状是"多出一个 NULL",CH 侧的症状是"多出一个看起来合法的 0/空串"——后者正是排查"为什么结果是 0"的常见坑,和 PG 那边是**不同的失败症状**。另外,`Array`/`Map` 这类**变长容器进不了排序键**(§03.8)——如果原来有个数组列参与过滤,得先想好它在 ClickHouse 里靠什么加速。

### E.3.7 `NULL` 与主键:两处"不是翻译,而是决定"

前面几节都是映射,这一节是两处**必须做设计决定**的地方——它们没有直译,做错了后果最大。

**`NULL`-ability 是一个设计决定。** 在 MySQL/PostgreSQL 里,列默认可为 `NULL`,迁过来时最省事的做法是全部包成 `Nullable(...)`。第 03 章 §03.9 把这条列为反面做法,理由是可算的:`Nullable(T)` **每行多一个字节的空值位图**,比较和聚合要先判空、**打断向量化**,而且**默认不能进排序键**;它还会**传染**——很多函数遇到 `Nullable` 返回 `Nullable`,一路往上传。ClickHouse 的惯例是**用类型自带的零值表示缺失**:空字符串表示未知字符串,`0` 表示未知数值,`1970-01-01` 表示"没有日期"。只有"**零值和缺失必须区分**"时才用 `Nullable`——§03.9 给的判据是"温度 0 度"和"没测到温度"是两回事,这才需要 `Nullable`。所以迁移时逐列问一句:这个列的 `NULL` 在业务上代表"未知/缺失",还是"某个真实的零值"?前者用零值替代,后者才留 `Nullable`。有一个逃生口 `allow_nullable_key = 1` 能让 `Nullable` 进排序键,但 §03.9 讲得很清楚:它只是把报错挪走,没消掉代价,定位是"迁移旧表时先让它建起来",不是"新设计里就该这么写"。

**主键的"目的"完全变了。** 这是所有迁移里最重要的一个认知转变。在 MySQL/PostgreSQL 里,`PRIMARY KEY` 意味着**唯一约束 + 聚簇索引**:它保证不重复,是访问入口。在 ClickHouse 里,第 06 章 §06.4 讲得很直白:`PRIMARY KEY` **既不唯一、也不是行标识**,它只表达一件事——**哪些前缀会被写进稀疏索引**。两条硬规则:**它必须是 `ORDER BY` 的前缀**;**不写时默认等于 `ORDER BY`**。所以源库的"主键是 id"**不能**翻译成 ClickHouse 的"主键是 id":

- id 变成一个**普通列**(载荷),是否当排序键要按查询模式重新推导(第 14 章 §14.3),不是照抄。
- **唯一性彻底不归数据库管**。往表里插两行"主键相同"的行,你会得到两行(第 02 章 §02.8、第 06 章 §06.4)。要去重,语义由**引擎**提供——`ReplacingMergeTree` 在后台合并时对排序键相同的行只留版本最大的那条,而且**是最终一致的**(第 08 章 §08.6、第 18 章)。这个转变会在 E.4 里展开成具体的建表决定。

把这一节的结论记成一句话:**源库用约束表达的那部分语义(唯一、非空、外键),在 ClickHouse 里要重新分派**——唯一交给引擎去重,非空交给类型设计,外键交给建模时的摊平或字典。这不是"迁移没迁全",这是两个引擎对"约束"这件事的根本分歧(第 01 章 §01.4)。

## E.4 重写 schema:从访问模式推导,而不是翻译

类型定好了,下一步是给每张目标表定 `ENGINE`、`ORDER BY`、`PARTITION BY`。这一步的原则只有一条:**这三个东西从表的访问模式推导,不从源表的 DDL 翻译**。源表的 DDL 里没有这三个概念的任何对应物,照抄只会得到一张能建起来但查不动的表。

推导的方法论在正文里已经给了完整的流程,这里只做迁移语境的衔接:排序键怎么选看第 14 章 §14.3(先列查询清单 → 按"过滤后剩下的 granule 数"给过滤列排序 → 等值列排范围列前面 → 控制宽度),分区键怎么选看 §14.4(**它是生命周期单位,不是查询加速手段**)。把这两条直接套到迁移上,就是下面几个决定。

**排序键:从"这个表被怎么查"推出,而不是从"这个表有什么主键"推出。** 分析查询的形状高度一致:**高基数等值维度 + 时间范围**。所以最经典的排序键是 `(tenant_id, ts)` 或 `(shop_id, event_time)` 这样的形状——等值的高选择性维度放最左,时间范围紧随其后(§14.3 第三步)。源表的自增主键在这里通常**用不上**:分析查询几乎不按它过滤,把它放最左只会白白加宽索引、稀释区分度。id 留着,但不进排序键。

**分区键:从"这条数据的保留期"推出。** §14.4 的核心论断是分区管**淘汰**,不管加速:`DROP PARTITION` 是 O(1) 的元数据操作(第 09 章 §09.7、第 18 章 §18.7),删历史数据靠它;真正把七天数据裁到几个 granule 的是排序键,不是分区键。所以迁移时问一句:"这条数据多久清一次?"订单明细留一年、日志留 30 天——分区键就跟这个保留期对齐,最常见的是 `toYYYYMM(ts)` 或 `toYYYYMMDD(ts)`。别按源表的主键分区,也别按高基数列分区(§14.4 列的三个必须避开的错误)。

**引擎:默认 `MergeTree`,按语义换子族。** 只追加的事实表用 `MergeTree` 就够。有"更新"语义的表,换 `ReplacingMergeTree`(见下)。要预聚合的 rollup 用 `AggregatingMergeTree`(第 13 章、第 12 章 §12.10)。第 04 章 §04.3 讲每个子族在解决什么具体问题,§04.10 给了按工作负载选引擎的表。

**自增主键:降格成载荷,新的"身份"由排序键承担。** 这一步在 E.3.1 讲过原理,落到建表上就是:id 列用 `UInt64` 保留(下游还引用它),但排序键另起炉灶,按访问模式选。如果应用需要"同一 id 只留最新一条",那是 `ReplacingMergeTree(version)` 的职责——它按**排序键**判重,所以排序键里必须包含能唯一标识一行的那组列(通常是 id 或 id + 一个时间)。

**外键与 JOIN 模式:换成摊平或字典。** OLTP 里为了范式把维度拆成独立表,靠外键 + 运行时 JOIN 补属性;ClickHouse 里这两条都不划算。第 15 章 §15.11 给了替代 JOIN 的手段清单,迁移时最常用的两个是:**把维度在 ETL 阶段摊平进事实表**(第 14 章 §14.5、§14.6——列裁剪让"用不上的列"几乎零成本,摊平省掉一次运行时 JOIN),和**把维度做成字典**(第 21 章 §21.2、`dictGet`),后者在维度会变、又不该每行冗余时更合适。摊平有个前提(§14.5):被摊平的维度要么慢变、要么你接受"历史行保存当时的快照"。源表的外键约束本身**不用迁**——ClickHouse 不强制外键,参照完整性由 ETL 和验证(E.7)保证。

**UPDATE 密集的表:换成"追加新版本"。** 这是从 OLTP 迁过来最需要换思路的一类。源库里 `UPDATE t SET status=... WHERE id=...` 是家常便饭;在 ClickHouse 里,`ALTER TABLE ... UPDATE` 是异步的 mutation,**提交后立刻查可能还是旧值**,它重写受影响的 part(第 09 章 §09.3、第 18 章 §18.8);较新的轻量级路径也仍是异步、而且对表有额外前置条件(第 18 章 §18.15)。所以高频小批量的 `UPDATE` **不该迁成 mutation**——第 17 章 §17.22 把它点名为"这个引擎上最典型的用法错位"。正确做法是把"更新"建模成"**再插一条更晚的版本**":用 `ReplacingMergeTree(版本列)`,让去重发生在后台合并时(第 08 章 §08.6 有完整例子)。代价要记住:去重是**最终一致**的,`INSERT` 刚返回时可能看到两行,想立刻收敛要 `FINAL`(有成本,第 18 章)。成对的"插入/撤销"语义用 `CollapsingMergeTree` 的 `sign` 抵消(第 04 章 §04.3、第 18 章)。

**二级索引:全部丢掉,换别的手段。** 源库里的普通索引、联合索引、唯一索引,迁过来没有对应物——ClickHouse 没有 B+ 树(第 11 章 §11.1)。按原索引的**意图**找替代:

- 加速等值/范围过滤的索引 → **排序键**(第 14 章 §14.3)。
- 加速某个非前缀列过滤的索引 → **跳数索引**(第 11 章 §11.4;注意它只跳 granule、不做定位)。
- 加速多种访问路径的索引 → **projection**(第 11 章 §11.12)。
- 加速聚合的"物化索引" → 先用**物化视图 + 预聚合表**(第 13 章),再看要不要 projection。
- **唯一索引 → 没有替代**。这是唯一一条查不回来的:唯一性在 ClickHouse 里必须靠上游保证,或靠 `ReplacingMergeTree` 的最终一致去重。源库里靠唯一索引挡住的重复,迁过来要靠 ETL 去重和 E.7 的校验兜住。

总结这一节:**源表的 DDL 提供的是"有哪些列、什么类型",提供不了"怎么建表"**。建表决定要从 E.2 那张"查询清单"里推出来。这也解释了为什么 E.2 必须排在 E.4 前面——没有查询清单,排序键就是在猜。

## E.5 数据搬运:回填与稳态是两件不同的事

表建好了,把数据搬进去。这里最该建立的一个认知是:**首次回填和持续同步通常是不同的工具、不同的管道**。把它们混成一个"同步方案",是迁移里很常见的返工来源。

**首次回填:一次性快照,用批量导入。** 存量数据有几千万到几十亿行,这是一次**批量**动作。工具按第 08 章 §08.5 的实践来:整文件交给客户端(`INSERT ... FORMAT CSVWithNames` / `FROM INFILE`),或先 `clickhouse-local` 洗一遍再灌(第 08 章 §08.5 给了完整例子),或数据已在对象存储/别处就用表函数让服务端自己去取(`s3()`、`file()`、`input()`)。格式优先选列式的 `Native`/`Parquet`,少一层解析。回填的形态是"把一个时间段的存量切成几批,批量写进全新的分区"。

**稳态同步:持续、增量、低延迟,用 CDC 或消息队列。** 存量搬完之后,新的变更要持续跟上。第 30 章 §30.2 和 §30.3 把路径列全了,定位很清楚:

- **外部 CDC 工具 + Kafka(最主流)。** Debezium 读 MySQL binlog / PostgreSQL 逻辑复制,把变更打成 Kafka 消息,再用 `Kafka` 引擎 + 物化视图接进来(§30.2 的铁律:**Kafka 是门不是仓库,必须配 MV 落盘**)。这是最可控的做法——你能自己决定怎么把 `INSERT`/`UPDATE`/`DELETE` 映射成 ClickHouse 的写入(通常就是"插入新版本 + `ReplacingMergeTree` 去重",对应 E.4 的更新建模)。
- **ClickHouse 自带的数据库引擎。** `MaterializedPostgreSQL` 是数据库级引擎,能把上游库镜像进来,但**仍是实验特性**,要开 `allow_experimental_database_materialized_postgresql`,Cloud 上不支持;名字更顺口的 `MaterializedMySQL` 命运更差——**22.8 被标记为弃用,24.1 起默认禁用,随后被移除**(PR #73879),25.3 上不要指望它(§30.3)。要走这条,先在目标版本实测。
- **异构库的一次性读取** 用 `jdbc()`/`odbc()`(§30.3);注意 `jdbc()` 依赖独立部署的 clickhouse-jdbc-bridge。

**一个反复要强调的反面做法:别用表函数当同步方案。** `mysql('host', 'db', 'orders', ...)`、`postgresql(...)` 这类表函数是**每次查询都打到上游库**的拉取式读取(§30.3),小维度表偶尔补一下没问题,拿它当持续同步会**拖垮上游**。这是迁移里很常见的"图省事"陷阱。

**几条实操规则。**

**大批量插入,避免海量小 part。** 这是第 08 章 §08.4 的核心:一个 part 的查询成本主要不是它多大,而是"打开它"本身——每个 part 都有一套完整元文件。所以"一次插 100 万行"和"一万次插 100 行"写进去的行数一样,但后者的 part 数是一万,直接撞 `Too many parts`。回填和稳态同步都必须**攒批**:回填按百万行一批,稳态靠 Kafka 的批量消费或 CDC 的批提交。这与 E.4 的分区键选择也耦合——分区越细,单批数据触及的分区越多,越容易触发单次插入的分区数上限(第 06 章 §06.5、第 28 章 §28.6.1)。

**回填与稳态要对齐"衔接点",否则不是空档就是重复。** 快照是"某一时刻的存量",CDC 是"从某个位点开始的变更流"。两者必须**严丝合缝**:如果快照取到 `id <= 1000000`,CDC 就要从"这条快照对应的 binlog 位点/事务号"开始,而不是从"当前位点"开始——否则快照与流之间那段变更会**丢失**。反过来,如果两者重叠,会**重复**一段。重复通常可以容忍(靠幂等去重),**丢失不行**。§30.3 的 CDC 路线天然给出位点,回填时要记下快照对应的位点。

**为 at-least-once 做幂等设计。** 消息队列与 CDC 的语义是"至少一次"(第 30 章 §30.2 讲了 Kafka offset 导致重复消费的成因),所以**必然会有重复**。不要祈祷不重复,要让下游幂等:表带版本列、用 `ReplacingMergeTree` 去重,或利用块级去重(第 08 章 §08.6、第 13 章 §13.5 讲了 `insert_deduplicate`、`insert_deduplication_token` 以及那个"聚合型 MV 可能误判重复"的坑)。**注意**:普通 `MergeTree` 的非复制去重窗口默认是关的(§08.6),所以幂等别只指望块级去重,引擎去重才是主路径。

**回填先落新分区,再校验、再对外。** 把回填数据写进一个**全新的、还没被查询的分区范围**(或一张临时表),校验通过(见 E.7)之后再让它进入服务范围。这样回填出错时不用回滚已有的正确数据。

## E.6 查询改写:一份能逐条对照跑的清单

数据进来了、schema 也对了,还有一层:查询本身。这一节给一份**清单**——你可以拿它对着自己的 SQL 一条条扫。需要细节的地方直接指向正文,不重复。

**1. upsert 写法没有对应物。** `INSERT ... ON DUPLICATE KEY UPDATE`、`REPLACE INTO`(MySQL)、`INSERT ... ON CONFLICT`(PostgreSQL)这类"按主键 upsert"的语句在 ClickHouse 里**没有直接对应**。替代是**引擎层面的去重**:`ReplacingMergeTree` 保留版本最大的一行,`CollapsingMergeTree` 用 `sign` 成对抵消,或查询时 `FINAL`(第 17 章 §17.22、第 04 章、第 18 章)。要把"更新"重新理解成"再插一条更晚的版本"。

**2. `UPDATE`/`DELETE` 是异步的。** 语法存在,但机制是异步重写 part(mutation)或轻量级删除标记(第 09 章 §09.3、第 18 章 §18.8 与 §18.9),不是"立即生效、锁定行"。脚本里"改完立刻读"要设 `mutations_sync`(第 18 章 §18.15),但那是给脚本用的同步开关,不是常态。高频小批量 `UPDATE` 请回头改建模(E.4)。

**3. 事务与隔离级别基本没有。** 只有很窄的适用范围(第 09 章 §09.13),没有 MySQL 那套隔离级别与行锁可利用。任何跨多行的"要全程一致性可见"的逻辑,不能靠 ClickHouse 的事务表达。

**4. `GROUP BY` / `ORDER BY` 的列位置与严格度。** 两点。其一,别照搬 `ORDER BY 1`、`GROUP BY 1` 这类**位置序号**写法——两边的位置语义不一定一致,而且 ClickHouse 允许 `GROUP BY`/`HAVING`/`ORDER BY` 引用 `SELECT` 别名(与 SQL 标准不同),别名还会**内联展开**;别名作用域与求值顺序的规则见第 07 章 §07.1 与 §07.2,那里有一个"别名与真实列同名时由别名胜出"的坑。用**显式表达式或不会撞名的别名**最稳。其二,ClickHouse 对 `GROUP BY` 是**严格**的:出现在 `SELECT` 里的非聚合列必须在 `GROUP BY` 里,否则报"not under aggregate function"。MySQL 5.7 之后默认也严(`ONLY_FULL_GROUP_BY`),但老库迁过来时会有惊喜——这类 SQL 会**成批报错**(这其实是好事,错误暴露在迁移期)。

**5. 隐式类型转换基本没有。** MySQL 会默默把字符串转成数字来比较;ClickHouse 不做这种"贴心"转换,类型对不上通常直接报错或按明确规则处理(第 17 章 §17.22、第 03 章 §03.16)。依赖隐式转换的老 SQL 会**成批失败**,要一条条把 `CAST`/`toUInt64` 写清楚。总体是好事:错误在迁移期暴露,不在上线后暴露。

**6. 同名不同义的函数集,单独扫一遍。** `length`(数字节不是字符)、`position` 的实参顺序、`dateDiff` 的单位与符号、`GROUP_CONCAT`/`groupConcat`、大小写比较、日期格式化占位符、`IFNULL`——**全部**在第 17 章 §17.22,那里是"筛选器",不再在这里重复。迁移时把 SQL 扫一遍,命中"字符串长度 / 位置查找 / 日期差 / 大小写比较 / 格式化串 / upsert / 更新"这几处的逐条到目标版本上跑一次对照;其余大多数函数(`upper`/`lower`/`trim`/`replace`/`concat`/`abs`/`round`/`min`/`max`/`sum`/`avg`)名字与语义基本一致,不必逐个怀疑。判断永远以当场 `SELECT` 的结果为准,不以名字像不像为准。

**7. 不带 `ORDER BY` 的 `LIMIT` 结果不保证。** 两家都不保证"LIMIT 出来的就是前几行",但 ClickHouse 的并行读取与多 part 让它更明显地不确定——同一个查询跑两次可能给不同的行。任何"取前 N 条"的查询,没写 `ORDER BY` 就是错的,补上。

**8. 大小写与排序规则。** 见 E.3.4:ClickHouse 按字节比较、无排序规则。"不区分大小写的分组/去重"迁过来**不报错、只是多出几组**(第 17 章 §17.22)。要么显式 `lower()`/`upper()`,要么用 `COLLATE`(第 16 章 §16.3)——而 §16.3 强调 `COLLATE` 只该出现在最后一步,别在中间层用。

**9. 日期格式化是两个词汇表。** `DATE_FORMAT`/`to_char` 与 ClickHouse 的 `formatDateTime` 都写 `%Y-%m-%d` 这类占位符,但**可用的指令并不完全重合**(第 17 章 §17.10、§17.22)。别只换函数名,格式化串要逐条对着看。

**10. 深分页不会变快。** `LIMIT m, n`(跳过 m 行取 n 行)在两边是**同一个意思**,可以照搬;但它仍然要**读、排序、再丢掉**前面 m 行,迁到 ClickHouse 不会变快(第 17 章 §17.22、第 16 章 §16.6)。该用键集分页(记住上一页最后一行,用 `WHERE key > ?` 续)就得改写法。

**11. JOIN 要自己选边。** ClickHouse 的 `JOIN` 默认把**右表**装进内存建哈希表(第 15 章 §15.7),右表大了就爆内存、就慢——它不像 MySQL 优化器那样自己选方向(第 02 章 §02.8)。所以迁移时把大表放左边、小表放右边;能用字典/`IN`/`ASOF` 替代的就别用 JOIN(第 15 章 §15.11)。分布式下还常要写 `GLOBAL JOIN`(第 15 章 §15.10)。另有 `join_use_nulls` 的默认值偏离 SQL 标准(第 15 章 §15.6),迁 `LEFT JOIN` 时留意。

**12. `FINAL` 的代价。** 如果你的表用了 `ReplacingMergeTree`(E.4),查询时想要**立刻**看到去重结果要加 `FINAL`(第 07 章 §07.14、第 18 章),但它有成本,宽表大表上要谨慎。能容忍最终一致就别用 `FINAL`,或改在写入侧收敛。

把这 12 条当成一个**回归清单**:每改一条 SQL,就对着清单过一遍,而不是等出错了再回头找。

## E.7 验证方法学:怎么证明搬对了

验证是本书正文里没有单独成节的一块,而它恰恰是迁移质量的分水岭。这里给一套分层的、可重复的方法。核心信条一条:**"行数对上了"不等于"搬对了"**——最常见的事故就是 count 相等、数值不等,而且差得不多,没人发现。

**第一层:行数与分组计数对账。** 最粗一层,两边跑 `count()`,但别只看总数——总数相等可能掩盖"这边多几行、那边少几行"。按**天**(按分区键)在两边分组计数,再逐组比:能一眼看出差在哪个时间段,直接把排查范围缩小到那几天的数据。时间边界上的差异(见下)最常在这里现形。

**第二层:校验和,而不是逐行 diff。** 逐行比较不可行(几亿行),退而求其次是算一个**两边都能复现的聚合校验和**:把要校验的键**规范化成整数**(整型列原样、日期取天数或秒数、字符串按固定规则映射成整数),再在 MySQL 侧用 `BIT_XOR(键)`、ClickHouse 侧用 `groupBitXor(键)` 各求一个异或值,两边比这一个数。

这一层**只对整数、或能被规范编码成整数的键成立**,别把它套在"看起来该逐字节相同"的字符串列上:**MySQL 和 ClickHouse 没有一个输出完全相同的哈希函数**可以通用——ClickHouse 的 `sipHash64`/`cityHash64` 在 MySQL 侧没有对应物(配套实现里的 `cityHash64` 也只是 `sipHash64` 的别名),而两边同名的 `MD5`/`CRC32` 实现与字节序也未必一致。要比字符串,先统一大小写与编码、取其数值摘要再异或,或干脆降级到第三层的聚合对账。

**但有个前提**:只有**哪些列应该完全相同**才参与——时间戳、金额这些经过类型映射、时区转换、Decimal 算术的列**本来就不保证逐字节相同**,把它们放进校验和只会得到必然的差异。校验和只用来证明"**键集合**和**确实不该变的列**没丢没错",不用来证明"每个值都一样"。

**第三层:同一查询两边跑,比聚合而非比行。** 这是最有价值的一层。挑出 E.2 里那几条业务查询,在源库和 ClickHouse 上各跑一遍,**比结果集中的数值**(GMV、订单数、买家数),而不比原始行——因为两边的**排序本来就不一样**(见下)。比"按天按品类的 GMV 总和"这类聚合,能把"值算错"和"顺序不同"这两件事分开。

**顺序差异要先用 `ORDER BY` 归一,再比。** ClickHouse 的多 part、并行读取决定了它**不保证任何默认顺序**,源库的"通常按主键顺序返回"也不该被依赖。两边要比,就**给两边都加上同一个显式的 `ORDER BY`**,或干脆只比聚合值。忘了归一顺序,会把"顺序不同"误报成"数据不同",白白排查半天。

**近似函数让精确比对变得不可能。** 这是 ClickHouse 特有的陷阱:生产查询为了快常用 `uniq`、`quantile` 这类**近似**函数(第 12 章 §12.6 把它们按"状态"分成四族)。近似函数在两边跑出来的值**本来就可能不同**,拿它们比对毫无意义。做法是:**验证时用精确版**(`uniqExact` 替代 `uniq`,精确分位替代近似分位),把"业务语义对不对"验掉;**验证通过后**,生产查询再换回近似版,并为近似误差单独接受一个容差。把验证用的精确结果留成基线。

**时区与取整会在日期边界上变成差一天。** 第 03 章 §03.6 讲透了两件事:时区是列属性,而且夏令时会让某些本地日不是 24 小时。后果是"按本地日分组"在切换日附近,两边可能给出**差一天**的归属。做法:**两边都在同一个时区下按同一粒度分桶**(推荐 UTC),`toStartOfDay`/`toDate` 的输入先 `toTimeZone` 成同一个区。验证时专门盯住时间边界:比对两边的 `MIN(时间列)`/`MAX(时间列)`,以及那几个跨日/跨月的分组的计数。

**浮点求和不会逐位相等。** 浮点加法不满足结合律,两边的聚合顺序不同,`sum(float_col)` 的**最后几位小数**不一样是正常的。所以:金额**本来就该用 `Decimal`**(E.3.3、第 03 章 §03.4),那就不该有这个问题;真要对浮点比对,加一个**相对容差**(比如偏差小于 1e-9 视为相等),别用等号。

**基数与边界也是校验项。** 除了 count 和 sum,再比几项便宜又灵敏的:去重键的个数(`uniqExact` 两边比)、`NULL`/零值哨兵的计数(E.3.7 把 `NULL` 换成了零值,这一项会变,要确认是"按预期变"还是"丢数据")、以及一组**人工核对过的"黄金一天"**——挑一天数据,把几个关键指标手算一遍,和系统输出对。人工核对是唯一能抓住"两边都算错"的手段。

**把验证固化成回归集,每次 schema 变更都跑。** 上面这一整层做完,得到的是"今天是对的";要让它**明天还是对的**,就得固化:把少量业务查询 + 期望结果存成一份**回归集**,每次改 schema、加列、调排序键都跑一遍。这正是第 28 章 §28.16 的纪律——"一次测量是观察,回归测试是约束"。§28.16 还给了把"与机器无关的指标"(`SelectedMarks`/`SelectedRows`/读取字节数)写成断言的思路,迁移后如果同时在意"结果不变"和"性能没退",把这两类断言分开建。

一句话收束:**验证的目的是把"我觉得搬对了"变成"我能证明搬对了,而且能持续证明"**。count 相等是最弱的那一层证明,不是终点。

## E.8 切换、回滚与"双跑"

数据搬完、查询改完、验证通过,最后一步是让业务用起来。这一步的关键是**保持 OLTP 主库的权威地位**,并**分批、可逆地**把读取流量挪过来。

**OLTP 继续当写主库,ClickHouse 只读。** 这条贯穿全篇:写路径**不动**(E.1 的安全阀)。用户、业务逻辑、事务都还在 OLTP 引擎上;ClickHouse 只是它的一份分析副本。这样,"迁移"影响的只是**读分析查询的那部分**,风险被隔离。

**切换分阶段,从风险最低的开始。** 一个稳的次序:

1. **影子期(shadow)**:ClickHouse 里建表、回填、接 CDC、跑验证,但**没有任何用户**在用它。这段的目标只有一个:让 E.7 的验证集连续通过。
2. **双跑期(dual-run)**:挑一两条**结果可对照**的查询,同时在源库和 ClickHouse 上跑,**逐日对比**结果(用 E.7 的方法)。这段是发现"类型映射/时区/近似函数"这类静默差异的唯一机会——它们只有两边并排跑才看得见。
3. **单报表切换**:把**风险最低的一个报表/看板**切到 ClickHouse,其余不动。观察一周:查询正确性、延迟、资源占用(第 27 章的系统表、第 29 章 §29.16 的事故清单)。
4. **扩大**:一个接一个把报表迁过来,每个都走一遍"双跑 → 切换 → 观察"。**OLTP 侧的对应查询保持可运行**,作为退路。
5. **收尾**:没有等"把所有东西迁完"——走到这一步时,源库那份查询仍然在,只是没人点它了。

**回滚的成本随采用度增长,要在切换前想清楚。** 这是最容易被低估的一条。影子期回滚 = 丢掉 ClickHouse,**零成本**。一旦用户/看板依赖了新表,回滚就意味着要么在源库上重建那些报表(可能源库根本扛不住,否则你也不会迁),要么让报表不可用。所以**回滚成本是采用度的函数**,不是固定的。对策是**把切换门禁前置**:在"切第一个报表"之前,要求验证集连续通过足够多天;切换过程中,始终保留"源库查询仍然可跑"这条退路;一旦发现差异,能**退回双跑**而不是"只能往前走"。

**双写要有节制。** 一个诱人的想法是"应用同时写 OLTP 和 ClickHouse",这样两边都最新。**不推荐**作为主路径:它把两套系统的**一致性**绑进了应用逻辑,而它恰恰是要取消的东西。优先用 CDC 从 OLTP 的日志里取变更(第 30 章 §30.3),让"同步"是**单向、可重放**的,而不是"应用要保证两边都对"。真需要双写,也要先想清楚写失败一边怎么办。

**保持两套系统"诚实"的运维习惯。** 迁移不是一个有终点的项目,是一段**长期运行**的关系。几条习惯:

- **每日对账**:一个定时任务,按天比源库与 ClickHouse 的行数/关键聚合(E.7 第一、三层),差异超阈值就告警。这是唯一能持续发现"同步悄悄断了"的手段。
- **监控同步延迟与表健康**:CDC 的滞后、`system.parts` 的 part 数、复制状态(第 27 章、第 29 章 §29.16)。同步断了不会自己告诉你。
- **冻结窗口**:改源库 schema 时(加列、改类型),要有一个"冻结期"——先确认 ClickHouse 侧的映射跟着改完,再放开。源库改一列而副本没跟上,是静默错位的温床。
- **活文档**:维护一份**源列 → 目标列 → 转换规则**的映射表,每改一处都更新。E.3 那张类型映射表就是它的起点。没有它,半年后没人说得清某个字段是怎么来的。
- **保留退路**:源库那几条核心查询**永远不要删**。它们是回滚的实体。

## E.9 一个端到端的例子:MySQL 订单库

把前面八节的流程在一套具体 schema 上走一遍。为了让例子能和正文对上,这张表沿用第 14 章 §14.12 的"电商订单"场景——那节讲的是**从零设计**,这里讲的是**从一份 MySQL DDL 迁过来**,两者应当落到同一套模型上。

### E.9.1 源库:MySQL 订单库

```sql
-- MySQL 8.0,InnoDB,utf8mb4
CREATE TABLE customers (
  id          BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  shop_id     INT UNSIGNED NOT NULL,
  name        VARCHAR(64)  NOT NULL,
  level       ENUM('bronze','silver','gold') NOT NULL DEFAULT 'bronze',
  created_at  DATETIME     NOT NULL
) ENGINE=InnoDB;

CREATE TABLE orders (
  id          BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  customer_id BIGINT UNSIGNED NOT NULL,
  shop_id     INT UNSIGNED NOT NULL,
  category    VARCHAR(32)  NOT NULL,
  amount      DECIMAL(18,2) NOT NULL,
  paid        TINYINT(1)   NOT NULL DEFAULT 0,
  created_at  DATETIME     NOT NULL,
  KEY idx_shop_time (shop_id, created_at),
  CONSTRAINT fk_orders_customer FOREIGN KEY (customer_id) REFERENCES customers(id)
) ENGINE=InnoDB;

CREATE TABLE order_items (
  id          BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  order_id    BIGINT UNSIGNED NOT NULL,
  product_id  BIGINT UNSIGNED NOT NULL,
  quantity    INT UNSIGNED NOT NULL,
  price       DECIMAL(18,2) NOT NULL,
  CONSTRAINT fk_items_order FOREIGN KEY (order_id) REFERENCES orders(id)
) ENGINE=InnoDB;
```

这套 schema 带着 OLTP 的全部特征:自增主键、外键、`DATETIME`、`DECIMAL`、`ENUM`、`TINYINT(1)` 当布尔、二级索引 `idx_shop_time`。它的历史数据是"只追加"的(订单一旦产生基本不改),这正是它能迁的前提。

### E.9.2 评估:哪些查询值得迁

按 E.2,先列查询,不列表。这套库上真正反复跑的**分析查询**是(对照第 14 章 §14.12.1 的四类):

1. 某店铺、某时间范围内的 GMV、订单数、买家数、件数——最高频,占比可能过半。
2. 某一天的品类销售排行。
3. 某买家的历史订单明细——低频,通常只看最近几单。
4. 最近 30 天的 GMV 趋势——看板,每小时刷新。

这四条的共同形状是"高基数等值维度(店铺)+ 时间范围 + 分组聚合",正是 ClickHouse 的主场。反过来,这套库里如果有"根据 id 查一单详情"的高频点查,那是 OLTP 查询,**留在源库**。结论:`orders` 与 `order_items` 是**事实型**候选,`customers` 是**维度型**,源库本身继续当写主库。

### E.9.3 推导 ClickHouse DDL

按 E.4,从访问模式推 `ORDER BY`/`PARTITION BY`/引擎。这里把 `orders` 做成一张**订单粒度**的事实表(与第 14 章 §14.12.3 同款模型:一行一单),把 `order_items` 的件数在写入前按单汇总进来,`customers` 的属性做成字典(第 21 章)。

```sql
-- 事实表:一行一单(order_items 的件数在写入前汇总进这一行;不带明细行)
CREATE TABLE order_events (
  order_id    UInt64,
  customer_id UInt64,
  shop_id     UInt32,
  category    LowCardinality(String),
  amount      Decimal(18,2),
  quantity    UInt32,
  paid        UInt8,
  event_time  DateTime('UTC')
) ENGINE = MergeTree
PARTITION BY toYYYYMMDD(event_time)
ORDER BY (shop_id, event_time);
```

逐个决定,理由都来自 E.4:

- **`ORDER BY (shop_id, event_time)`**:查询清单里最常出现在 `WHERE` 的是 `shop_id`(等值、高选择性)和 `event_time`(范围),按第 14 章 §14.3 的流程,"高基数等值维度 + 时间范围"就是最经典的排序键形状。`category` 是低基数、只用于分组,不进排序键——它靠 `LowCardinality` 编码加速分组(§14.5)。
- **`PARTITION BY toYYYYMMDD(event_time)`**:保留期是明细一年,查询多带"最近几天/几十天"的范围(第 14 章 §14.12.2)。按天分区让"删掉 N 天前的明细"变成几次 `DROP PARTITION`(第 14 章 §14.4、第 18 章 §18.7)。一年产生几百个分区,在舒适区内(第 06 章 §06.5)。
- **`amount Decimal(18,2)`**:金额原样保留 Decimal,**绝不用 `Float`**(第 03 章 §03.4、E.3.3)。这里的 `amount` 是**订单级**金额(对应源库 `orders.amount`),不是明细行金额——所以 `sum(amount)` 直接等于源库的 `SUM(o.amount)`,这正是下面校验能两边对上账的前提。
- **`quantity` 是订单的件数合计**:源库的件数在 `order_items` 上(一行一个商品),写入前按 `order_id` 汇总成"一行一个值"(`SUM(order_items.quantity)`)再摊进订单粒度。`item_id` 与逐行的 `price` **不带过来**——订单粒度下它们没有落点,本节的四类查询也从不按商品分析。
- **`customer_id` 保留但不做排序键**:它是 E.3.1 说的"降格成载荷列"。查询 3(买家历史明细)按 `customer_id` 过滤,和主排序键的 `shop_id` 对不上——按第 14 章 §14.12.4 的处理,**接受它裁不到,用别的机制补**(给 `customer_id` 建跳数索引,或另建一张排序键为 `(customer_id, event_time)` 的明细表),而不是把 `customer_id` 塞进主排序键、破坏主查询路径的裁剪。这是排序键"排他性"的典型取舍。
- **`paid UInt8`**:`TINYINT(1)` 的布尔,按 E.3.6 用 `UInt8`。
- **没有 `Nullable`**:源库的 `NOT NULL` 约束本来就意味着没有空值,自然不用(§03.9、E.3.7)。
- **`event_time DateTime('UTC')`**:源库 `DATETIME` 不带时区,迁移时按 E.3.2 明确决定"这些时间戳代表哪个时区",这里统一按 UTC 语义写入并声明列时区。

维度表 `customers` 走**字典**(第 21 章 §21.2),而不是每次 JOIN:

```sql
CREATE DICTIONARY dim_customer (
  id    UInt64,
  name  String,
  level String
)
PRIMARY KEY id
SOURCE(CLICKHOUSE(TABLE 'customers_src'))
LAYOUT(HASHED())
LIFETIME(MIN 300 MAX 600);
```

`customers_src` 是 ClickHouse 侧的一张普通表,由 CDC 或定期快照从 MySQL `customers` 同步。查询里补客户等级用 `dictGet('dim_customer', 'level', customer_id)`,不走 JOIN(第 15 章 §15.11 讲字典是维表补全的首选)。

预聚合按第 14 章 §14.12.3 建一张按"店铺 × 品类 × 天"的 rollup,存**状态**而不是结果(第 12 章 §12.10、第 13 章):

```sql
CREATE TABLE dws_shop_category_day (
  stat_date   Date,
  shop_id     UInt32,
  category    LowCardinality(String),
  gmv_state   AggregateFunction(sum, Decimal(18,2)),
  order_state AggregateFunction(uniq, UInt64),
  buyer_state AggregateFunction(uniq, UInt64),
  qty_state   AggregateFunction(sum, UInt32)
) ENGINE = AggregatingMergeTree
ORDER BY (shop_id, category, stat_date);

CREATE MATERIALIZED VIEW mv_dws TO dws_shop_category_day AS
SELECT toDate(event_time) AS stat_date, shop_id, category,
  sumState(amount)      AS gmv_state,
  uniqState(order_id)   AS order_state,
  uniqState(customer_id) AS buyer_state,
  sumState(quantity)    AS qty_state
FROM order_events
GROUP BY stat_date, shop_id, category;
```

注意 `buyer_state` 用的是 `uniqState`(存状态)而不是 `count(DISTINCT ...)`——去重计数不能事后相加,这正是第 14 章 §14.12.3 那个"买家数必须存状态"的教训。

### E.9.4 搬运

**回填**按 E.5 用批量导入:在 MySQL 侧先把数据归纳成**订单粒度**的结果集——`SELECT o.id, o.customer_id, o.shop_id, o.category, o.amount, COALESCE(SUM(i.quantity), 0) AS quantity, o.paid, o.created_at FROM orders o LEFT JOIN order_items i ON i.order_id = o.id GROUP BY o.id`,把这批结果导出成列式文件(`Native`/`Parquet`),再 `clickhouse-client ... FORMAT Native < snapshot.native` 灌进 `order_events`(第 08 章 §08.5 的批量导入实践)。回填的 CSV/文件里 `DATETIME` 按 UTC 语义写出,`DECIMAL` 原样写出。

**稳态**按 E.5 走 CDC:Debezium 读 MySQL binlog,变更打成 Kafka 消息,`Kafka` 引擎表 + 物化视图落进 `order_events`(第 30 章 §30.2 的经典模式)。源库的 `UPDATE` 与 `DELETE` 在这里被映射成"插入新版本",`order_events` 视需要换成 `ReplacingMergeTree(版本列)` 去重(E.4、第 18 章)。回填与 CDC 的衔接点按 E.5 对齐 binlog 位点,避免空档。

### E.9.5 两条查询的前后对照

**查询一:某店铺、某时间范围的 GMV 与买家数。**

在 MySQL 上(改写前):

```sql
SELECT o.shop_id,
       SUM(o.amount)            AS gmv,
       COUNT(DISTINCT o.id)     AS orders,
       COUNT(DISTINCT o.customer_id) AS buyers
FROM orders o
WHERE o.shop_id = 10
  AND o.created_at >= '2024-03-01 00:00:00'
  AND o.created_at <  '2024-04-01 00:00:00'
GROUP BY o.shop_id;
```

在 ClickHouse 上,打预聚合表(改写后,对应查询 1 的主力路径):

```sql
SELECT shop_id,
       sumMerge(gmv_state)  AS gmv,
       uniqMerge(order_state) AS orders,
       uniqMerge(buyer_state) AS buyers
FROM dws_shop_category_day
WHERE shop_id = 10
  AND stat_date >= '2024-03-01' AND stat_date < '2024-04-01'
GROUP BY shop_id;
```

如果查的是**明细粒度**(不按天预聚合),就落到 `order_events`:

```sql
SELECT shop_id, sum(amount) AS gmv, uniqExact(order_id) AS orders
FROM order_events
WHERE shop_id = 10
  AND event_time >= '2024-03-01 00:00:00'
  AND event_time <  '2024-04-01 00:00:00'
GROUP BY shop_id;
```

`ORDER BY (shop_id, event_time)` 让 `WHERE shop_id = 10 AND event_time BETWEEN ...` 直接裁到一小段 granule(第 14 章 §14.3)。

**查询二:某一天的品类销售排行。**

在 MySQL 上(改写前):

```sql
SELECT category, SUM(amount) AS gmv
FROM orders
WHERE created_at >= '2024-03-01 00:00:00'
  AND created_at <  '2024-03-02 00:00:00'
GROUP BY category
ORDER BY gmv DESC
LIMIT 10;
```

在 ClickHouse 上,打按天的 rollup:

```sql
SELECT category,
       sumMerge(gmv_state) AS gmv
FROM dws_shop_category_day
WHERE stat_date = '2024-03-01'
GROUP BY category
ORDER BY gmv DESC
LIMIT 10;
```

注意两个改写点:**`stat_date` 是 `Date`,过滤用日期字面量而不是时间戳**(类型对齐,第 03 章 §03.6);**`LIMIT` 带了 `ORDER BY`**(E.6 第 7 条)。

### E.9.6 验证这几张表

按 E.7 逐层验:

- **行数/分组计数**:按天比 `order_events` 与 MySQL `orders` 的订单数,逐天对齐,先把时间边界钉死。
- **聚合对账**:上面两条查询,在 MySQL 与 ClickHouse 上跑,比 `gmv`/`orders`/`buyers` 数值。买家数这一项要两边都用**精确去重**(MySQL 的 `COUNT(DISTINCT)`,ClickHouse 的 `uniqExact`/`uniqMerge`——rollup 里存的是 `uniq` 状态,验证时可以先用明细表的 `uniqExact` 当基线)。
- **边界**:比 `MIN(event_time)`/`MAX(event_time)`,以及跨月那天(3 月 1 日)的分组计数;确认时区统一后没有差一天。
- **金额**:`Decimal` 两边应逐位一致;`sum(amount)` 若在 CH 侧用了任何浮点中间量,加容差(这里不该有)。
- **黄金一天**:挑 2024-03-01,人工把店铺 10 的 GMV 手算一遍,和系统输出对——第 14 章 §14.12.3 就给过一个手工核对(`1137.00`)的例子,同一种做法。
- 把这几个查询存成**回归集**,以后每次改 schema 都跑(E.7 最后一条、第 28 章 §28.16)。

- [ ] `UPDATE` 密集的表换成了"追加新版本"。
- [ ] 源库的二级索引逐条找到了替代,或明确接受丢掉(唯一索引尤其)。

**搬运**
- [ ] 回填用批量导入,不是逐行插;批足够大,part 数受控。
- [ ] 稳态用 CDC/消息队列,不是表函数轮询上游。
- [ ] 回填与 CDC 的衔接点对齐(不丢、尽量不重)。
- [ ] 为 at-least-once 做了幂等(版本列 / `ReplacingMergeTree` / 去重 token)。
- [ ] 回填先落新分区,校验通过再对外。

**查询**
- [ ] 对着 E.6 的 12 条清单逐条扫过自己的 SQL。
- [ ] upsert、异步 `UPDATE`/`DELETE`、事务用法都改掉了。
- [ ] 所有 `LIMIT` 都带了 `ORDER BY`。
- [ ] 大小写比较、日期格式化、隐式转换都显式处理了。

**验证**
- [ ] 行数按天对账,不只对总数。
- [ ] 用聚合对账,不是逐行 diff;两边都加了显式 `ORDER BY` 归一。
- [ ] 验证时用了精确函数(`uniqExact` 等),生产再换近似。
- [ ] 时区统一,时间边界专门核对过。
- [ ] 有一组人工核对过的"黄金数据"。
- [ ] 业务查询回归集建好了,每次 schema 变更都跑。

**切换**
- [ ] 走完影子期 → 双跑期 → 单报表切换。
- [ ] 回滚成本评估过,退路(源库查询)保留着。
- [ ] 每日对账任务、同步延迟监控、schema 冻结窗口就位。

## E.11 让迁移失败的几种方式

最后列几种把迁移做死的方式。它们不是技术难点,是**顺序和心态**上的错——上面每一节其实都在防它们。

**大爆炸式切换。** 一次性把所有权重切过来,没有影子期、没有双跑、没有回退点。任何一处静默差异,后果都是直接暴露给用户。防法是 E.8 的分阶段。

**逐条翻译查询,不做改写。** 把 MySQL 的 SQL 原样贴进 ClickHouse,指望它跑。它会跑,只是语义悄悄变了(`length` 数了字节、`dateDiff` 符号反了、`LIMIT` 没序、`ON DUPLICATE KEY` 报错)。防法是 E.6 的清单。

**把 ClickHouse 当 drop-in 的 OLTP 替代品。** 在它上面做高频单行更新、指望唯一约束、指望事务。第 28 章 §28.5.1 把这个列成反模式。防法是 E.1 的范围判断。

**因为 count 相等就跳过验证。** 最危险的一种,因为"看起来通过了"。行数相等完全可能掩盖"时区差一天""近似函数偏差""Decimal 截断"这些数值错。防法是 E.7 的分层验证——count 是最弱的一层。

**什么表都迁。** 把几百张表全搬,包括永远没人查的小表和纯 OLTP 操作表。工作量翻倍,收益减半,还引入了大量不必要的同步链路。防法是 E.2 的盘点。

**到处用 `Nullable`。** "源列允许 NULL 就包成 Nullable"看着忠实,实则每行多一字节、打断向量化、还进不了排序键(第 03 章 §03.9)。防法是 E.3.7:逐列问"零值和缺失要不要区分"。

**把自增主键照抄成排序键。** 分析查询不按 id 过滤,拿它当排序键等于白建索引。防法是 E.4:排序键从查询模式推。

**用表函数当同步方案。** 拿 `mysql()`/`postgresql()` 表函数持续拉上游,把源库拖垮(第 30 章 §30.3)。防法是 E.5:稳态用 CDC/消息队列。

**小批量高频写。** 稳态同步写得很碎,part 数爆炸,撞 `Too many parts`(第 08 章 §08.4)。防法是 E.5:攒批。

**没有对账、没有回滚路径。** 同步断了没人知道,出了差异退不回去。防法是 E.8 的运维习惯。

**先追性能,后管正确性。** 迁移还没验证对,就急着调排序键、换引擎、上投影。顺序反了——先把"结果对不对"钉死(E.7),再谈"快不快"(第 28 章 §28.16 把这两类断言分开建的思路)。

这几种方式有个共同点:**它们都不是被某个技术细节打败的,而是被"跳过了一步"打败的**。这份 playbook 的全部内容,就是把被跳过的那几步按正确顺序摆回原位。
