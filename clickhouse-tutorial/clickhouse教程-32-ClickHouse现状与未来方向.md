# 第 32 章 ClickHouse 现状与未来方向

这一章解决什么问题:前面三十一章讲的是 ClickHouse 的**机制**——它怎么存、怎么算、怎么写。但工程师选型时真正要回答的往往是另外几个问题:它现在到哪个阶段了?哪些是板上钉钉的事实,哪些只是官方画的饼?它跟别的系统比优势在哪?以及"我该不该押注它"。这一章把这些判断摊开讲,而且**严格区分三类内容**:已经是事实的、官方宣称在做的、以及作者个人的主观判断。三者的可信度天差地别,混在一起讲就是耍流氓。

这一章也是全书**时效性最强**的一章,所以它的组织方式刻意与其他章不同:它不追求"讲全",而追求**把每条结论的依据等级和核对方法写清楚**。一条断言如果没有可靠来源,正文里写的是"**未确认**",而不是一个看起来很像样的默认值——后者恰恰是这类章节最容易犯、也最有害的错误。记住全书的标注规则:**无标注** = 官方文档级事实;`(25.x 起)` 这类 = 有版本依据;**未确认** = 检索不到可靠来源,或来源之间互相冲突。来源冲突与"查不到"同等对待——两个官方口径打架时,正确做法是承认自己不知道,而不是挑一个顺眼的抄下来。

## 32.1 确定的事实

这一节只放**既成事实**:不是路线图,不是"官方打算",而是"在本书基线 25.3 上有明确文档、并且有能当场跑出来的自检手段"的东西。判断一条内容够不够格进这一节,用两个动作:一,官方文档里有没有对应页面;二,有没有一条命令能在你自己的实例上把它验出来(`system.settings` 里读默认值、`system.functions` 里查函数在不在、`system.data_skipping_indices` 里看索引类型认不认)。两个都不满足的,一律不进这一节,而是挪到 §32.3 或直接标"未确认"。

**存储与执行侧的事实。** 列式 + 向量化执行是它速度的根本来源,也是从第一版起就坚持的路线(第 10 章 §10.2)。围绕它的是一整套多年未变形的机制:**part 不可变 + 后台合并**(第 18 章 §18.1)、**稀疏主键索引按 granule 裁剪**(第 11 章)、**两阶段聚合与聚合状态**(第 10 章 §10.9)。这些不是"特性",而是这套系统的形状本身。放在这一节是因为它解释了一个常见误判:很多关于 ClickHouse 的争论根本不是在讨论版本,而是在讨论这个前提。

**半结构化类型已经是默认能力。** 原生 `JSON` / `Variant` / `Dynamic` 三个类型在 25.3 上可用,而且 `enable_json_type` 的默认值**自 25.3 起改成 `true`**——也就是说在本书的基准版本上,不需要额外开关就能定义 `JSON` 列(第 03 章 §03.13)。但要分清两件事:**"类型可用"不等于"它内部每一项特性都生产就绪"**。`JSON` 里声明的路径类型怎么推、未声明路径落成动态子列还是溢出的共享结构、`max_dynamic_paths`(文档默认 1024)与 `Dynamic(max_types = N)`(文档默认 32)这些上限的行为,在版本之间一直在调(第 03 章 §03.13 给了这些默认值,并提示"具体默认值以目标版本文档为准")。要在生产里依赖某个具体行为(比如某个路径一定落成独立子列、能不能在这个子列上建跳数索引),先在本版本上实测,别照抄别的版本的结论。

**旧写法已经退役。** `Object('json')` 是原生 `JSON` 类型的前身,已经被移除;早期用它建过、如今还在跑的表,会在升级时暴露出来。**最后一个仍支持 `Object('json')` 的具体版本号本书未确认**——没有核实到确定的官方版本锚点(流传的"25.10"一说没有可靠来源),请以目标版本的 release notes 为准;方向是确定的:**升级前必须把它迁到原生 `JSON` / `Variant` / `Dynamic`**。

**删除与更新。** 轻量级删除(`DELETE FROM`,区别于重量级的 `ALTER ... DELETE` mutation)已经可用,25.3 上默认开启(`enable_lightweight_delete` 默认 1,旧名 `allow_experimental_lightweight_delete`),它把"删几行却要重写整个 part"的问题变成了标记式删除(第 18 章 §18.9)。**轻量级更新(`UPDATE ... SET`)是另一回事**:它用 `_block_number` / `_block_offset` 这两个虚拟列定位行,是更晚的能力——**到 25.8 才进入 Beta**,所以**本书对标的 25.3 上并没有它**(第 18 章 §18.15)。最省事的自检是直接问实例:

```sql
SELECT toTypeName(_block_number) FROM your_table LIMIT 1;   -- 报错即该版本没有这条路径
```

**读的并行。** 并行副本(parallel replicas)已经在 25.3 可用:一次查询把**同一份**数据在多个副本之间切着读、各自部分聚合、再合并结果,和"按分片切数据"的分布式表是两回事(第 10 章 §10.6、第 23 章 §23.11)。要补的限制是:它在 25.3 上**仍需显式启用**——功能开关在 25.3 默认 0——**它的声明名是 `allow_experimental_parallel_reading_from_replicas`,`enable_parallel_replicas` 是它的 `ALIAS`**(25.3 的 `src/Core/Settings.cpp` 里就是这么写的,没有发生过"改名";该特性这一版已是 **BETA** 档),而 `max_parallel_replicas` 的默认值已经是 1000 且**它不是开关**(第 23 章 §23.11)。另外还有几项前置条件:需要 **23.3+**、**同一分片内得真有副本**,并配好 `max_parallel_replicas` 与 `cluster_for_parallel_replicas`。所以"确定的事实"在这里指的是"能力存在且可用",不是"默认就在跑"。本书稿早前记过一条"更激进的默认值出现在 25.4"——这一条我没有在 25.4 的 release notes 上复核过,**未确认**;升级或调优前,请在你自己版本上跑:

```sql
SELECT name, value, default FROM system.settings WHERE name LIKE '%parallel_replicas%';
```

**生态侧的事实。** 数据连通性这块有几件事已经落地:内置的 MySQL / PostgreSQL wire protocol 让现成驱动直接连进来,`Arrow` / `Parquet` / `ORC` 这类列式格式是**双向**的(第 30 章 §30.7);`clickhouse-local` 与 chDB 让"不装服务端也能做分析"成立(第 01 章 §01.6)。共同点是:只需要装一个官方的多调用二进制、或一个 Python 包。

最后提醒这一节的读法:它写的是"25.3 上确定的事实",而确定的事实会过期。**自检命令比结论寿命长**——记不住结论,记住那几条命令就够。

## 32.3 官方路线与在研方向

这一节的内容**全部是"官方声明或文档提到的方向"**,不是既成事实。每条后面标出依据等级(高 / 中 / 低),低等级的要当成"作者的读法",不是官方原话。这一节比过去多写了一层:**除了"往哪走",还写"为什么难"**——因为一个方向值不值得下注,取决于它卡在什么地方,而"卡在哪"往往能从既有章节的机制里读出来,不需要额外的官方声明。

**`SharedMergeTree` 与存算分离。** 在云环境里,数据不再绑定在节点本地盘上,而是放在共享的对象存储里,计算节点无状态、可弹性伸缩。依据:**高**(这是 ClickHouse Cloud 的核心架构方向,官方架构文档反复描述)。**为什么难**:难的不是"把数据放对象存储",而是把整套建立在"本地盘 + `fsync` + part 不可变"假设上的机制搬过去——延迟从微秒级变成毫秒级,小文件与请求计费改变了合并与分层的经济性,副本一致性也不再由复制日志而是由存储层负责。这也是为什么它**没有回流到 OSS**:第 22 章 §22.10 记过一个很说明问题的细节——OSS 侧曾经有过一条"零拷贝复制 / 远程文件系统"的路(`allow_remote_fs_zero_copy_replication`,自 22.8 起默认关闭),而源码注释直接写着"不要在生产使用"。**官方自己在 OSS 侧劝退过这条路**,云侧靠托管的对象存储与调度把它做成了产品。所以"OSS 也会很快有 `SharedMergeTree`"这类预期,依据是不足的。

**对象存储原生。** 让对象存储不只是"慢盘",而是能承载冷数据乃至主数据的存储层;这条线上还连着**开放表格式的原地读写**(`Iceberg` / `DeltaLake` / `Hudi` 的**读**已经可用,把数据 `INSERT` 回去则是更晚的能力:Iceberg 的 `INSERT` 自 26.2 起才进入 beta,Delta 写入仍实验,Hudi / Paimon 只读——**25.3 上没有任何湖表写入能力**)。依据:**高**(方向与上一条同源;写入部分的版本边界见 §32.8)。**为什么难**:读侧难在"没有本地索引,只能靠分区裁剪和谓词下推",以及元数据(manifest / 事务日志)的读取本身要花时间;写侧难在"外部会改 schema"——ClickHouse 假设一张表的 schema 由它自己说了算,而湖表的事务日志允许多个写入者,两套假设凑在一起需要额外的一致性协议(第 30 章 §30.4 因此建议把它当"读为主")。

**全文索引与向量索引。** 补齐"关键词检索"和"近似最近邻"两类能力,让一部分原本交给搜索引擎/向量库的场景能留在 ClickHouse 里。依据:**中**(能力确实在加,但类型名、实验开关、成熟度逐版本变化:全文索引在 25.3 叫 `full_text`、到 25.6 一路改到 `text`,向量索引在 25.6 起转 beta)。**为什么难**:向量索引是货真价实的跳数索引,粒度单位是 granule(第 11 章 §11.10);文本索引只借了跳数索引的名——它按 part 组织、映射到行号,`GRANULARITY` 对它没有意义(机制见 §32.7)。但共同点是它们都只能回答"这一块 / 这一行要不要读",回答不了"相关的排多前"——相关度排序需要词频、文档长度归一、打分模型,这些在"每 granule 一条摘要"的结构里没有位置。所以它们**必然长期停留在"过滤加速"的定位上**。细节见 §32.7。

**查询优化器朝代价模型演进。** ClickHouse 的优化器长期以**规则**为主;官方明确提到要让优化器更"聪明",引入代价估计来选 join 顺序、选算法。依据:**中**(方向被公开提到,但到 25.3 为止"规则驱动"仍是主要特征,**落地程度未确认**)。**为什么难**:代价模型需要**统计信息**,而 ClickHouse 的取舍恰好是"不要统计信息"——第 24 章 §24.1 讲得很清楚:规则驱动的好处是改写确定、可解释、不需要 `ANALYZE`。要引入代价,就得同时引入统计信息的采集、存储、过期与 `ANALYZE` 这一类新负担,还要接受"同一份 SQL 在不同机器上可能得到不同计划"这个调试上的坏消息。这不是加一个模块,而是改一条产品哲学。

**`analyzer`(新查询分析器)的推进与旧分析器的退役。** 新的 analyzer 逐步成为默认,旧 analyzer 计划退出。依据:**中**。这件事在 25.3 上已经走到很前面:第 24 章 §24.3 与 §24.17 记下,**正式名是 `enable_analyzer`**,新分析器**自 24.3 起默认开启**;`allow_experimental_analyzer` 是**自 24.8 起**的**遗留别名**(`enable_analyzer` 由它改名而来,旧名只为兼容保留)。**为什么难**:难点不在实现,而在**行为的可观察差异**——新旧分析器对同一条 SQL 的别名作用域、谓词下推位置、`EXPLAIN` 输出都可能不同,而用户会把这些差异当成 bug 上报。推进方式因此只能是"逐版本把默认值翻过去 + 让 `EXPLAIN QUERY TREE` 这类新观测面先长出来"。

**JOIN 与子查询能力的补齐。** 依据:**中**。**为什么难**:ClickHouse 的哈希连接是"右表(build 侧)整体进内存"的模型(第 15 章 §15.7),它决定了天花板——大表 JOIN 大表要么吃光内存,要么溢出到磁盘(第 25 章 §25.3)。要真正改善,得先解决"谁是 build 侧"的决策问题,而这正是上一条"代价模型"要解决的问题,所以 JOIN 的进步与优化器的进步是**同一件事的两面**。分布式下还有第二层难度:`GLOBAL JOIN` 是正确性问题不是优化问题(第 15 章 §15.10)。

**写入路径的改进**(异步插入、mutation 的处理方式)。依据:**低到中**。它关系到 ClickHouse 最常被吐槽的一对矛盾:**为了吞吐要攒大批次,为了可见延迟要尽快落盘**。"part 太多"的闸门(第 08 章 §08.4)、异步插入、mutation 的异步性(第 18 章 §18.8)都是这对矛盾的产物;往哪个方向走没有公开答案,所以依据给"低到中",**具体内容未必与作者描述一致(未确认)**。

对这些条目的正确态度是:**方向可以参考,时间表和具体形态不要当真**。上面每一条"为什么难"都比"什么时候有"更值得记住——难点不变,时间表天天变。

## 32.4 版本、LTS 与升级策略

这一节回答一个很具体的问题:**如果你的生产环境要用 ClickHouse,你该跟哪条版本线、什么时候升、升级时最可能被什么东西咬到。** 事实部分与政策部分严格分开,政策部分以官方为准。

**命名与节奏。** 版本号形如 `YY.M`:年份加该年的第几次发布。近年是**每月一个特性版本**(25.1、25.2、25.3 这样递增);因为节奏是每月一发,`M` 在多数年份里也正好等于月份——这一条可以放心用(第 01 章 §01.9)。"每月一版"直接决定了你的运维负担:打算跟每一个版本,升级本身就成了日常工作;所以真实的选择从来不是"要不要升",而是"跟哪条线、升得多快"。

**LTS 与 stable 的取舍。** 与"每月一版"并行的是 **LTS(长期支持)**线:被标为 LTS 的版本获得更长的支持(补丁)窗口,非 LTS 版本通常只被维护到下一版发布前后。生产环境的主流做法只有一条:**跟 LTS 线,并在两条 LTS 之间滚动打补丁**。

**LTS 的节奏是确定的:每年两条**,分别落在**三月的 `YY.3`** 与**八月的 `YY.8`**(25.3、25.8 即这一对);官方**同时支持最近两条 LTS、每条至少 12 个月**。与之并行的 stable 线每月一发,但**只有最近三个版本还能拿到补丁**。具体到本书基线:**25.3 发布于 2025-03-20,官方支持到 2026-03-20**。这里要把结论说透:本书写于 2026 年 10 月,也就是说**基线版本已经走出支持窗口半年多**——标它对标是为了对齐一套稳定的机制,不等于生产上该停在 25.3;升级前先确认你实际跑在哪个版本、它还剩多久窗口。可以放心用的是那个**方法**:拿到任何版本号,先去官方 release notes 确认它属于哪条线、支持到什么时候;官方仓库的**版本回移(backport)**机制是围绕 `release/<YY.M>` 分支组织的,LTS 分支的维护期明显长于普通分支(第 01 章 §01.9)——这是能在仓库里直接观察到的证据。

**升级窗口怎么选。** 三条经验:**一,跟着 LTS 之间的节奏走**,不要"看到新特性就想升"。**二,滚动升级,永远保留一个"好"的副本**:从分片的**一个副本**开始,升级、启动、`SYSTEM SYNC REPLICA` 追平,确认无误再动下一个副本(第 29 章 §29.12 给了完整步骤)。**三,Keeper 与 server 的顺序是"先 Keeper、后 server"**,避免出现"server 想用新协议、Keeper 还不认识"的窗口。选日子时避开写入高峰——滚动升级期间副本会落后,读的冗余也会暂时下降。

**向后兼容的真实风险面。** "ClickHouse 升级会不会出问题"这个问法太笼统,拆成五类才有用:

- **表结构层面**:新版本对某些类型或表达式的默认行为可能变了(第 29 章 §29.12)。
- **有状态引擎的二进制格式**:`AggregatingMergeTree` 这类引擎把**聚合状态**按二进制存进 `-State` 列(第 10 章 §10.9、第 13 章 §13.4),这些状态的序列化格式跨大版本时可能变化——旧状态新版本读不出来,或读出来不对(第 29 章 §29.12)。
- **设置默认值翻转**:这是**最容易被忽略的一类**——它不报错、不改 schema,只是行为悄悄变了。本书已经抓到三个实例:`enable_json_type`(25.3 翻成开)、`use_query_condition_cache`(25.3 默认 0,25.4 起默认 1,见 §32.2)、`max_parallel_replicas`(**25.1** 从 `1` 提到 `1000`,导致"设成大于 1 就启用"的老经验作废,第 23 章 §23.11)。**同一条查询升级后变快或变慢,先查这几类默认值,别先怀疑硬件。**
- **一条被"从源码定案"的旧悬案**:`max_parallel_replicas` 翻到 1000 的**版本号**,本书前几轮一直标"未确认"(二手资料分成 24.12 与 25.4 两说)。核对 `ClickHouse/ClickHouse@v25.3.*` 分支的 `src/Core/SettingsChangesHistory.cpp` 后可以确认它落在 **25.1** 的 `addSettingsChanges(...)` 块内,`src/Core/Settings.cpp` 的 `DECLARE` 也写成 `1000`。**教训值得记**:文档站上的设置页只服务最新版、且版本标注常缺失,而 release 分支里的 `SettingsChangesHistory.cpp` 是逐版本记账的 —— **那个文件比文档措辞可靠**。
- **观测输出的形态**:第 24 章 §24.12 那条预警是最好的例子——更高版本把索引裁剪下推到读数据阶段后,`EXPLAIN PLAN indexes = 1` 的输出会比你习惯的复杂;这不是查错了,是输出变了。
- **回滚的可行性**:滚回旧版本**不保证可行**。新版本若已用自己的格式重写过 part,旧版本可能读不了——升级前的全量备份是回滚的唯一后路(第 29 章 §29.12)。

**`compatibility` 设置:一个缓冲层,不是兼容层。** 它可以让服务端按**某个旧版本的行为**运行——把一个 `'YY.M'` 形式的版本串(如 `'22.3'`,空串 = 关闭)传进去,就把一批受版本影响的默认值切回旧版,给"升级后行为变了但暂时不想改 SQL"的场景一个过渡期(官方文档级事实)。三条纪律:**覆盖不到全部行为差异**(表格式、引擎二进制格式这类变化它管不了);**官方没有给出文档化的支持区间**(未确认);**它是过渡措施,不是长期姿势**。

**跳跃升级。** 官方通常支持**相邻大版本**的升级路径,而**跨多个大版本直跳往往不被支持**——中间版本可能有 part 格式或元数据的迁移步骤必须经过。第 29 章 §29.12 已经写过这一点,并标了"具体支持矩阵以官方升级文档为准(**未确认**)"。

**升级前后该跑的几条自检。** 起来了不等于好了——那几条(版本、`system.build_options`、`system.warnings`、只读副本、积压的 mutation / merge、错误计数)第 29 章 §29.12 已经列全,**这里不重复**。

真正属于**这一节新增**的是下面这条:**升级前,把 `system.settings_changes` 里落在"从你的旧版本到新版本"这段区间内的记录拉出来看一遍**(第 01 章 §01.9 提到过这张表)。它比 release notes 更聚焦——release notes 告诉你"新增了什么特性",而它告诉你"**什么默认值变了**",后者才是升级事故的主要来源。

```sql
-- 这张表记录了设置项的历史变更;升级前按版本区间过一遍
SELECT * FROM system.settings_changes ORDER BY version;
```

## 32.5 ClickHouse Cloud 与开源版的功能分界

本书正文只讲开源版,但**选型时必须知道边界在哪**——因为有些"官方能力"其实只在 Cloud 上存在,而有些你在 Cloud 上找不到的东西,恰恰是文档里写得最响的。

**架构基石:`SharedMergeTree`。** Cloud 的存储架构以 `SharedMergeTree` 为核心:数据与元数据放在共享的对象存储上,计算节点无状态、可以弹性伸缩,副本之间**不需要复制 part**——一致性由存储层负责(第 04 章 §04.3、第 01 章 §01.8、第 22 章 §22.14)。它和 OSS 侧的多副本方案**不是"同一个引擎的不同配置"**:OSS 的高可用是 `ReplicatedMergeTree` 加 Keeper 协调(第 22 章)。这个区别决定了后面所有分界。另外注意一个日常细节:**Cloud 上的默认表引擎就是 `SharedMergeTree`**(第 06 章提到 `default_table_engine` 在 Cloud 上的取值),所以在 Cloud 上 `CREATE TABLE` 不写引擎,不等于 OSS 上的行为。

**托管带来的能力面。** Cloud 把自建集群里最麻烦的部分接了过去:托管的 Keeper(第 22 章 §22.12)、自动备份与恢复、监控与告警、以及**计算与存储分开计费**的弹性模型;数据接入侧也推出了托管管道(ClickPipes 一类)。计费规则、套餐与组件命名属于商务与产品细节,**本书不做断言(未确认)**。

**哪些是 Cloud 独有、哪些已经回流到 OSS。** 判据只有一条:**一个能力出现在上游 OSS 仓库里,它就会到 OSS;只出现在云侧产品与控制台里的,就只属于 Cloud。** 按这条判据,`SharedMergeTree` 属于例外(它是 Cloud 架构本身);查询层的能力——类型、函数、索引、引擎——几乎都是**先在 OSS 落地**的,Cloud 只是把它们托管起来。所以"Cloud 是不是功能更多"这个问法不太对:Cloud 提供的是**运维与弹性**,不是另一套 SQL 方言。

**一个反方向的例子。** 云侧不是 OSS 的超集。第 01 章 §01.8 记过一个具体反例:全文索引在 25.3 上是"OSS 有、Cloud 不支持"的实验特性。理由很正当(托管服务不能随便放开会改行为的实验开关),但它对选型有直接含义:**依赖某个实验特性时,先确认它在 Cloud 上是否可用**;也不要假设所有 `allow_experimental_*` 开关都能在控制台里翻。

**对选型者的三条结论。** 第一,**要共享存储与秒级弹性,就得接受托管**——`SharedMergeTree` 不是自建能开的开关,OSS 侧对应的位置是 `ReplicatedMergeTree` 加分片(第 23 章)。第二,**知识是通用的**:存储结构、索引、聚合、优化在 Cloud 上照样成立,因为内核是同一个;不一致的主要是"默认值、默认引擎、可用开关"这三处。第三,**两者之间有一个不可逆的分界**:一旦架构依赖云侧的弹性与托管协调,Keeper 运维、副本同步、扩缩容这些能力就不再是你团队的知识——这是省钱的地方,也是锁定。把这笔账算清楚再决定,比比较性能数字重要得多。

## 32.6 半结构化与 AI 相邻能力

这一节把"半结构化"与"AI 相关"两类能力放在一起讲,因为它们在选型里常被同一个问题触发:"我的数据没有固定 schema,而且里面可能有向量,ClickHouse 行不行?"

**半结构化类型的成熟度曲线。** 这条曲线在本书里有完整的三段:**`String` + 解析函数**(丢进字符串,查询时用 `JSONExtract*` 现场解析,既慢又建不了索引)→ **`Object('json')`**(前身,已移除,见 §32.1)→ **原生 `JSON` / `Variant` / `Dynamic`**(第 03 章 §03.13)。第三段在 25.3 上是**默认能力**。它值得记住的是**方向**:ClickHouse 选择了"把半结构化数据当成一等类型",而不是"提供一堆解析函数"。

**成熟不等于无限制。** 三种类型各有自己的形状,而形状决定了代价:`Dynamic` 按每一行的实际值推类型,单块内不同子类型各占一段独立子列,超出上限的部分落进一块共享结构(仍能读,但更慢更耗内存);`Variant` 把可能性在建表时列举固定,读某一支用子列;`JSON` 在 `Dynamic` 之上把每个路径提升成真正的子列,于是 `json.user.id` 既能类型安全地读、也能建跳数索引,还能用 `SKIP` 省掉"永远不查"的路径(第 03 章 §03.13 给了完整语义与默认值)。要确认"某个路径落成了独立子列还是溢出到共享结构":

```sql
SELECT JSONAllPaths(data)        AS all_paths,
       JSONDynamicPaths(data)    AS dynamic_paths,
       JSONSharedDataPaths(data) AS spilled_paths
FROM your_table LIMIT 1;
```

**哪些还没定。** 三件事属于"能用但别赌":路径类型的**推断稳定性**、动态子列在合并时的**重排行为**、**跳数索引对 `JSON` 子列的支持程度**——这三条本书**未确认**。

**半结构化不是"免建模"的借口。** 三个类型解决的是"schema 不确定的部分怎么先存进来",但它们不改变列存的基本代价:`JSON` 把每个路径提升成一个子列,路径一多,part 的列数与元数据就膨胀;`max_dynamic_paths` 到顶后多出来的路径会落进共享结构,查询随之变慢、也更耗内存。所以实用的做法是**把确定要反复查的路径显式声明、其余交给动态子列**,而不是"整条记录原样丢进 `JSON` 就不管了"——这与宽表建模要做的取舍是同一件事,只是把决定推迟到了写入之后。

**那什么时候该用它?** 两条:一是**上游 schema 你控制不了**(第三方事件、埋点、日志字段频繁变),先原样接进来、再逐步物化出热点列;二是**同一张表里字段子集因来源而异**(A 类事件有 5 个字段、B 类有 30 个),用 `Variant`/`Dynamic` 比"建一张几百列、大多数列恒为 NULL 的宽表"更省。反过来,如果字段是**已知且稳定的**,老老实实建普通列——那才是列存最擅长的形状,半结构化只会带来额外开销。

**向量与 embedding 的位置。** 需要说清一个边界:**ClickHouse 不做推理**——它不生成 embedding、不做模型调用,只负责"把向量和结构化数据放在一起存、并用近似最近邻检索召回出来"(机制见 §32.7)。第 30 章 §30.15 因此把它在 ML 里的位置定为**离线特征库与特征回填**:在线按实体低延迟取特征那一环通常落到 KV 存储,因为它是点查——而点查是 ClickHouse 明确的弱项(§32.13)。

**"把 AI 相关的数据留在 ClickHouse 里"成立吗?** 有条件成立,条件三条,缺一条就该换专用向量库:**检索是召回优先、可接受近似**;**向量基本不变、读多写少**(索引在写入与合并时构建);**规模装得下**。三条都成立时,"语义检索 + 结构化过滤 + 聚合"能在一条 SQL 里写完,这是它相对"向量库 + 数据仓库"两套系统的真实优势(第 01 章 §01.8)。

## 32.7 索引与检索能力的补齐:全文索引与向量索引

上一节讲了"AI 相邻能力"的整体定位,这一节专门讲**让这两类能力落地的索引机制**,以及与外部引擎的分工边界。两者的共同点是:**它们都不是新引擎,都写在 `INDEX` 子句里、也被 `system.data_skipping_indices` 收录(第 11 章 §11.9),但机制并不相同**——向量索引是真正按 granule 裁剪的跳数索引,文本索引只借了这个名。

**全文(倒排)索引。** ClickHouse 的全文检索不是靠 `LIKE '%keyword%'` 扫全表,而是在列上建一种**反向结构(倒排结构)**:把文本按词或 n-gram 切开,建立"词 → 出现它的**行**"的映射,查询时对不上的行直接不读(第 11 章 §11.9)。两个要点:**它加速的是词级谓词**——`hasToken` / `hasAllTokens` / `hasAnyTokens` 这类"串里含这个整词"的写法,以及能配合它的 `match`、`LIKE` 过滤;**它不改变结果**——它只负责跳过,真正的判定仍要读数据。它和 `tokenbf_v1` / `ngrambf_v1` 解决同一类问题,但用的是更专门的索引结构,所以正在逐步取代那两种 bloom 版索引(第 11 章 §11.9)。

**类型名与开关随版本变。** 25.3 里它叫 `full_text`,是**实验特性**,要 `SET allow_experimental_full_text_index = true` 才可用,当时也不在 Cloud 上支持;它更早叫过 `inverted`(`inverted` → `full_text` 这一步在 25.3 之前)。**25.3 之后又改了两次名**:`full_text` → `gin`(上游 #79024),`gin` → `text`(上游 #80855),这两步记录在 v25.6 的 changelog 系列里,并把位置参数换成 `tokenizer = '...'` 键值语法(如 `text(tokenizer = 'splitByNonAlpha')`);旧名字仍能加载但会抛异常——**用哪个名字、要不要开关,以你目标版本的文档为准**。另外要点破一件事:**文本索引不是跳数索引**——它按 part 组织、映射到**行号**,创建时给的 `GRANULARITY` **没有意义**(位置照写,值被忽略)。可以放心用的是**自检方法**:

```sql
-- 25.3 的写法(实验开关 + 位置参数)
SET allow_experimental_full_text_index = true;
ALTER TABLE logs ADD INDEX idx_msg msg TYPE full_text(0) GRANULARITY 1;
-- 更晚的版本改成 TYPE text(tokenizer = '...');先把候选名在你自己版本上试一遍,
-- 能建出来、且 system.data_skipping_indices 认它,才算数
SELECT database, table, name, type FROM system.data_skipping_indices;
```

上面两种写法**分属不同版本**,不要互相照抄:`full_text(0)` 是 25.3 的形态,`text(tokenizer = '...')` 是更晚版本的形态(改名链与它落在哪些版本,上一段已经说清);**转正(GA)的版本仍未确认**——它到底还算不算"实验特性"、要不要那个开关,只能在你自己的版本上查。所以别从别的版本抄建索引语句,先在你自己实例上试出来再用,这是这一块最容易踩的坑。

**向量相似度索引(ANN)。** 能力确实存在:给一列向量(`Array(Float32)` 或 `Array(Float64)`)声明一个 ANN 索引,查询侧写成 `ORDER BY 距离函数(向量列, 参考向量) LIMIT k`,索引让这个排序不必和所有向量逐一算距离(第 01 章 §01.8)。**类型名是 `vector_similarity`,底层是 HNSW**(分层图结构,用 **USearch** 库实现,距离计算有 SIMD 加速);参数依次是"**算法**(25.3 只支持 `hnsw`)、**距离函数**(`cosineDistance` / `L2Distance` 等)、**维度**、**量化方式**"。25.3 上它仍是**实验特性**,要显式打开 `allow_experimental_vector_similarity_index`;**25.6 起该能力转为 beta**,开关去实验前缀改名为 `enable_vector_similarity_index`,旧名保留为别名;更早的实验类型 `annoy` / `usearch`(基于随机投影树 / 图结构的老实现)**已被它取代**(上游 PR #63675;旧类型仍可加载,但写入与检索会抛 `ILLEGAL_INDEX`)——**用哪个名字、要不要开关,以你目标版本的文档为准**(建法与参数细节见第 30 章 §30.12,机制与类型名的完整版本链见第 11 章 §11.9)。查询侧要用的是距离函数这一族——以 `Distance` 结尾的 `L2Distance`、`cosineDistance` 等,以及 `dotProduct`(它不以 `Distance` 结尾,但同属这一族);具体名单与签名请查 `system.functions`(下面这条按名字匹配,只覆盖名字里带 `Distance` 的那批):

```sql
SELECT name FROM system.functions WHERE name ILIKE '%Distance%' ORDER BY name;
```

**与外部引擎的分工边界。** 三条,都很硬:**全文索引替不掉 Elasticsearch 的"检索"那一半**——它加速过滤、不做相关度打分(没有词频权重、没有 BM25),能替掉的是"分析库 + ES 两套"里**靠过滤粗筛**的那部分(第 01 章 §01.8);**向量索引替不掉专用向量库**——它是近似检索,召回率与延迟要靠索引参数权衡,且索引在写入与合并时构建;**两者的成熟度都不该当成稳定事实**——类型名与开关逐版本在变(见本节与 §32.2):全文索引在 25.3 叫 `full_text`、到 25.6 一路改到 `text`,向量索引到 25.6 才转 beta。所以别把某个版本的类型名当成稳定结论,这条纪律在第 30 章 §30.17 同样成立。

**那它们值不值得用?** 值得,但要放在正确的场景里:"在日志里按关键词粗筛、再叠加结构化过滤",或者"在已存的 embedding 上做召回优先的语义检索"——这类"顺带做一点"的场景,省下一套系统是净收益;如果检索本身是你的核心业务,它应该有自己的专用系统。

## 32.8 湖仓与开放表格式:读与写的成熟度差

这一节讲"不搬数据也能分析"这条线。它在选型里的分量越来越重,因为它的价值主张很朴素:**与其把数据复制进 ClickHouse,不如让 ClickHouse 去读数据所在的地方。**

**读:已经是事实。** 三种湖表格式(`Iceberg` / `DeltaLake` / `Hudi`)外加 Paimon,都有表函数与表引擎两级接入,`DataLakeCatalog` 再往上一层把整个 catalog 挂成库——每级入口的名字、能力边界,以及 Paimon"只点名、不给结论"的处理,§30.4 已经逐个讲过,**这里不重复**。读侧的成熟度一句话概括:**读得到、也算能用,但官方对 Iceberg 表引擎的表述始终是 "read-only",并且明确提示 ClickHouse 原本不是为"外部会改 schema"设计的。**

**读的性能代价。** 对象存储上的文件没有本地索引,扫描天然比本地 `MergeTree` 慢;ClickHouse 只能靠**分区裁剪**与**谓词下推**减少读取(第 30 章 §30.4)。所以"读得动不动"多半不由 ClickHouse 决定,而由**湖表自己的组织方式**决定——文件是否按常用维度分区、大小是否合理、元数据要读多少个文件才能定出扫描范围。同一个 Iceberg 表,分区方式改一下,查询时间能差一个量级。

**写:还不是,而且在 25.3 上是完全没有。** 把 ClickHouse 查询的结果 `INSERT` 回湖表,是 25.3 之后才出现的能力,而且到今天仍是实验 / beta 形态——Iceberg 的 `INSERT` 自 26.2 起才进 beta、Delta Lake 写入仍实验、Hudi 与 Paimon 只读(**开关名与版本锚点见 §30.4 与 §32.2 的表**)。所以**本书对标的 25.3 上没有任何一种湖表写入能力**。

**所以这条线现在是一条很干净的分界:"把湖表当数据源读"是事实,"把 ClickHouse 当湖表的写入口"还不是。** 实践中这意味着:如果你的架构是"Spark/Flink 负责生产湖表,ClickHouse 负责服务查询",今天就可以落地,而且相当稳;如果你想让 ClickHouse 往湖里回写,先做小规模验证,不要排进关键路径。第 30 章 §30.13 给的"重计算交给 Flink/Spark、ClickHouse 做服务层"的分工,正是因为这一条才成立。

**一个容易混的区分。** "湖表"和"S3 盘"是两回事:前者读的是别人组织好的文件,后者是把对象存储当成你自己数据的存储层。技术细节第 30 章 §30.4 与 §29.13 已经讲过,这里只留那句记法:**"S3 盘是我的存储层,湖表函数是别人的文件。"**

## 32.9 部署形态的扩散:chDB、Wasm 与嵌入式

前面几章讲的 ClickHouse 默认是**常驻服务**:一个 `clickhouse-server` 进程,监听端口,管着库表、权限、后台合并(第 01 章 §01.6)。但近几年它长出了别的形态,而它们解决的是完全不同的一类问题。

**`clickhouse-local`:免服务端的一次性查询。** 它不监听端口、不需要服务端上下文,直接在本地文件上跑 SQL——把 `data.csv`、`data.parquet` 当表查(第 01 章 §01.6)。适用面是**临时分析**:验证一个类型或函数的行为、看一眼 Parquet 文件、跑一段一次性的转换。它没有库表元数据、没有用户权限、也没有运行期生成的 `system` 表(第 01 章 §01.6)——这正是它启动便宜的原因。

**chDB:把引擎嵌进进程。** chDB 把 ClickHouse 的引擎嵌进宿主进程(比如 Python),让"不装服务端、不起端口、不运维"地跑查询成立(§32.2)。它和 `clickhouse-local` 的区别是**形态**:一个是命令行工具,一个是能被程序 `import` 的库。**最小形态**大致是:先 `pip install chdb` 装上那个 Python 包,再在脚本里 `import chdb`,然后调用 `chdb.query("SELECT ...")` 直接取结果(可指定返回格式)——**这只是官方 README 展示的入门形状,确切的函数名、返回对象、内存表与会话 API 请以 chDB 官方仓库的 README 与文档为准**,本书不在没有实测的情况下把它写死。

**chDB 与常驻服务、`clickhouse-local` 的取舍。** chDB 换来的是**零部署**:没有端口、没有守护进程、没有权限体系,适合放进数据处理脚本、Notebook、CI 流水线,或嵌进一个桌面应用里。代价有两层:一是**功能子集**——进程内形态缺了常驻服务的几样关键东西(下一段会细说);二是**单机**——它拿不到分布式表的算力,数据规模受宿主内存与磁盘限制。三者其实是一条"部署形态"的谱:**`clickhouse-local` 适合"人在终端里跑一次",chDB 适合"程序在代码里跑很多次",常驻服务适合"长期开着、被很多客户端连"**。分界线在部署形态,不在 SQL——查询语法与函数集基本同源,但**具体覆盖以各自版本的文档与 `system.functions` 为准**。

**Wasm 构建。** 把 ClickHouse 编到 WebAssembly,让它跑在浏览器或边缘环境里;价值在于把部署面再往外推一格(无需服务端、按请求拉起、数据不出浏览器)。但它同时受三条限制:包体积大、可用的编译目标与依赖有限、功能覆盖是子集——所以它更像"一种探索性的部署面",而不是可以当作生产首选来押注的形态。**本书不给它成熟度标签**(生态、包体积、功能覆盖与稳定性**未确认**):需要它时,先去官方仓库与文档确认当前构建**支持哪些功能、体积多大、有没有现成的发布产物**,而不是假设"能编到 Wasm 就等于功能齐全"。

**嵌入式形态缺少什么,值得单独说。** 常驻服务之所以是常驻服务,不只是因为"要高并发"。它带来了三样嵌入形态没有的东西:**后台调度器**(merge、mutation、TTL 这些异步任务,第 18 章 §18.1)、**多用户与资源控制**(配额、内存上限、并发限制,第 25 章)、以及**可观测性**(第 27 章那套 `system` 表)。嵌入形态里这些要么没有、要么退化。本书的配套实现 mini-clickhouse 走的就是嵌入式形态:第 31 章 §31.14"明确不做什么"列出的东西——多线程流水线、后台调度器、`Distributed` 分片、对象存储——恰好就是嵌入形态缺的那部分。

**那该选哪个形态?** **要服务多个用户、要被别的系统连、要长期跑着攒数据 → 常驻服务**;**要在一个脚本或笔记本里对文件或小数据集做一次分析 → `clickhouse-local` 或 chDB**;**要嵌进一个没有网络、没有部署权的运行环境 → 看 Wasm,但先验证**。"单机嵌入式分析"这块地盘上最常被拿来比较的是 **DuckDB**,本章 §32.12 补一句结论。

## 32.10 怎么读 release notes、怎么跟踪演化

前面几节告诉了你现在是什么、打算去哪、边界在哪。这一节换个角度:**未来一年里,你怎么自己跟踪它的变化?** 这一节故意不列"重点特性清单"——那种清单三个月就过期了——而是给**方法**。

**唯一可靠的一手来源是官方 changelog 与 release notes。** 博客、二手总结、乃至本书,都只是解读,而且会过期(第 30 章 §30.17 也是这个口径)。这不是"官方才准"的教条,而是一个很实际的判断:**任何关于某个设置默认值、某个函数名、某个开关的说法,都必须能追到一个带版本号的官方条目**;追不到,就标未确认。

**release notes 的分节结构本身就是一张风险地图。** 官方 changelog 按固定类别分节,而不同类别对你生产环境的风险量级是不同的:

```text
Backward Incompatible Change   ← 逐条读。语法、类型语义、引擎行为的破坏性变化都在这
Performance Improvement        ← 扫一眼。可能让某条查询变快,也可能改变"内存峰值"
Improvement                    ← 按你依赖的特性名检索
New Feature / Experimental Feature  ← 关心就记,不关心就跳过;实验特性默认不用
Bug Fix                        ← 只有当它修的是你正踩的坑时才有意义
```

读法上有两条**反直觉**的建议:**最该逐条读的是 `Backward Incompatible Change` 这一节**——它最短、最枯燥,却是升级事故的主要来源;**新特性那一节可以快速略过**——新特性默认不会打开,真正会咬你的是"旧行为变了"。把注意力反过来分配,收益最大。

**怎么自检默认值:三条命令。** 这是本书反复强调的纪律,这里收成一处:

```sql
SELECT name, value, changed, default FROM system.settings WHERE changed = 1 ORDER BY name;
-- ↑ 查询层设置:哪些被改过、默认值是什么(changed=1 那一行往往就是"行为异常"的答案)

SELECT name, value FROM system.merge_tree_settings WHERE name IN
    ('index_granularity', 'parts_to_delay_insert', 'parts_to_throw_insert');
-- ↑ 由建表 SETTINGS 或服务端 <merge_tree> 段控制的 MergeTree 参数,不随会话变化

SELECT * FROM system.settings_changes ORDER BY version;
-- ↑ 设置项的历史变更记录:什么时候引入、什么时候改了默认值
```

前两条与第 27 章 §27.14 讲的是同一件事(设置属于哪张表,是最常见的混淆点),第三条是**跟踪演化时最有用的一条**:它把"默认值变了"从 release notes 的正文里抽出来,变成一张能按版本过滤的表。三条合起来回答:"**我依赖的这个行为,在我的版本上到底是什么?**"

**建立你自己的一份"版本—行为"清单。** 这是本节唯一一条针对**你**的建议:把你依赖的每一条**版本敏感行为**(设置的默认值、函数的签名、DDL 的写法、引擎的格式)记成一张表,每行写清"我依赖它做什么、在哪个版本上验过"。本章标着"未确认"的地方,**都该是这张表上的第一行**。

## 32.11 作者的判断(主观)

以下**全部是作者的个人判断**,不是官方立场。写出来是因为选型时读"事实"只能告诉你它现在是什么,告诉不了你"三年后它大概会是什么"。

**存算分离 + 对象存储是不可逆的方向。** 理由不是"它更快",而是**经济性**:在云上,把存储和计算绑在一起意味着你为"闲置的存储容量"也付着计算的钱。把数据放进对象存储、让计算按需拉起,能显著改善成本曲线。只要云还是主流部署环境,这个方向就不会回头。代价是对象存储的延迟远高于本地盘,所以"存算分离能不能胜任你的延迟要求"才是那个真问题。补一句:**这条路的收益主要落在"弹性"和"成本",而不是"单查询延迟"**——负载是"稳定的高并发低延迟查询"时,共享存储在延迟上大概率不是加分项。

**半结构化类型会吃掉一部分宽表建模。** 传统做法是"把所有可能的字段都建成列",结果是几百列的宽表,加一个字段就要一次 `ALTER`。`JSON`/`Variant`/`Dynamic` 让"不确定 schema 的部分"能先原地存进来、之后再物化出热点列。这不会消灭宽表(热点列依然要拍平才快),但会改变"先建模再入库"的老流程。需要克制的地方也很明确:**跳数索引在动态子列上的可用性还不稳**(§32.6),所以"把什么都丢进 `JSON`"会换来一个查询很慢、又看不到哪儿慢的表。

**优化器是它下一步最大的技术挑战。** 列式 + 向量化解决的是"怎么把已经确定要读的数据读得飞快";优化器解决的是"怎么少读、按什么顺序读"。ClickHouse 在这件事上的历史欠账是实打实的——它快是因为扫描快,不是因为它特别会规划。把它从规则驱动推进到代价驱动,是难度最高、也最能拉开差距的一步(难点见 §32.3)。

**它的边界在哪:永远不会变成 OLTP。** 这一点要说得斩钉截铁。ClickHouse 没有行级事务、不强一致的点更新、不适合每秒几千次的主键点查——这不是"还没做",而是它的架构选择决定的(列存、批量写、part 不可变)。任何"用 ClickHouse 替代 MySQL"的想法都会撞到同一面墙。它的定位永远是**分析**,不是**交易**。

**全文与向量检索会长期停在"够用但不专精"。** 这是与上面几条不同的判断——**我不认为这两条线会追上专用系统**,理由是结构性的:它们的落地形态都是跳数索引,粒度是 granule,所以只能做过滤、做不了打分(§32.7)。官方投入它们的目的很清楚:让现有用户少接一套系统,而不是去抢搜索引擎的市场。把这句读成"ClickHouse 会取代 ES"是误读;读成"两套系统的边界会往 ClickHouse 这边挪一点"更准确。

## 32.12 竞争格局

比较系统时,真正有用的不是"谁更快",而是"各自的优势场景在哪"。以下涉及竞品具体现状的主张,凡不能确认的一律标注。

- **Doris / StarRocks / Greenplum 等 MPP 数据库**。它们的相对优势在**复杂的多表 JOIN 和更接近传统数仓的优化器**——这正是 ClickHouse 的短板(§32.13)。ClickHouse 的相对优势在**极致的单表扫描性能、写入吞吐、以及成熟的 MergeTree 存储与压缩**。选谁,很大程度取决于你的负载是"宽表强扫描"还是"多表复杂关联"。这类系统的具体版本能力**未确认**。
- **DuckDB(单机分析)**。它嵌入进进程,面向"单机、单用户、分析文件"的场景,开发和探索体验极好。它和 ClickHouse 不太正面竞争:一个偏"库"(嵌入、单机、探索),一个偏"服务"(常驻、多用户、高吞吐)。第 01 章 §01.5 给过同样的定位区分;这里补一句:**chDB 与 Wasm 的出现(§32.9)让两者第一次有了重叠**,但重叠区很窄。具体的性能对比**不做断言(未确认)**。
- **BigQuery / Snowflake 等云数仓**。优势在**全托管、存算分离、生态与企业特性**;代价是成本模型和厂商绑定。ClickHouse 的优势在**成本可控、可自托管、延迟低**;权衡更多是组织性的(有没有团队运维)而非纯技术。一个对照点:拿自建的 OSS 去比云数仓是**不对等**的——公平的比较对象是 ClickHouse Cloud,而那时你其实是在两个托管服务之间选(§32.5)。
- **Elasticsearch(日志场景)**。ES 的强项是**全文检索与相关度排序**,以及成熟的日志采集生态;弱项是**大范围聚合分析**时资源消耗大。ClickHouse 的取舍正好相反:聚合飞快,全文检索是后来补的短板。**这条边界不会因为全文索引的出现而消失**(§32.7):ClickHouse 补上的是"按关键词粗筛",补不上的是"打分排序"。
- **专用向量库(Milvus / Qdrant / Pinecone 这一类)**。它们的强项是**高召回、低延迟、面向在线检索**的工程优化(索引构建与更新、过滤与向量混合查询、水平扩展);ClickHouse 的向量索引是"顺带做一点语义检索"的定位(§32.6、§32.7)。当嵌入量上亿、要求毫秒级召回、且向量每天大量新增时,专用库仍是主场。**这些产品的具体能力未做核对(未确认)**,这里的比较只到"定位"这一层。

## 32.13 批评与争议

这一节按本书一贯的做法,把 ClickHouse 常被诟病的地方摆出来,并逐条说明"官方有没有正面回应"。

- **JOIN 能力长期偏弱。** 大表 JOIN 大表容易 OOM、算法选择不够智能、跨分片 JOIN 代价高。**官方回应**:持续投入,新增 join 算法、改进 analyzer 对 join 的处理;但"彻底解决"在 25.3 上**未确认**。根子在"build 侧整体进内存"的连接模型和"不替你选左右表"的优化器上(§32.3),所以它不会因为某一次版本更新而消失。
- **优化器是规则驱动的,局限明显。** 复杂查询的执行计划可能不是最优,而用户很难干预。**官方回应**:把优化器朝代价模型演进列为方向(§32.3),但成熟度**未确认**。用户侧的实际应对不是等官方,而是"把写法调到规则的触发器上"(第 24 章 §24.1:别问优化器为什么不够聪明,要问自己的形状有没有落在某条规则上)。
- **`NULL` 与默认值的语义包袱。** ClickHouse 里 `Nullable` 不只是语义标记,它有真实的性能和存储代价;加入 `Nullable` 可能让查询慢数倍(第 28 章 §28.4)。**官方回应**:把它作为明确的设计取舍——用"默认值"而非 `NULL` 表示缺失,是 ClickHouse 的选择;文档里解释了原因,但**没有打算改变**。
- **升级的兼容性风险。** 大版本升级可能影响表结构、有状态引擎的二进制格式。**官方回应**:通过 release notes 和兼容性说明来管理,并提供 LTS 版本降低频率;但**风险本身不减**(第 29 章 §29.12),实际应对手段见 §32.10。
- **单表扫描强,但并发点查弱。** 高并发按主键取一行这类负载,ClickHouse 表现很差。**官方回应**:这基本被定位为"**不是目标场景**"——它面向分析,不对点查做承诺。这一条与其说是缺陷,不如说是边界(§32.11)。
- **实验特性停留期过长。** 有些能力多年停在"实验"状态,类型名、开关、参数逐版本变化,让人不敢用。**官方回应**:**未确认**——我没有找到官方对"实验特性一般需要多久转正"的公开承诺。从产品角度它合理,从使用者角度它就是不确定性:实验特性的东西,就按实验特性的价值来用它。

## 32.14 给读者的行动建议

**该学什么。** 优先掌握三样:存储模型(part / 分区 / 排序键 / 稀疏索引,第 05 章)、聚合与 JOIN 的执行代价(第 10 章 §10.9、第 15 章 §15.7)、以及"怎么定位慢查询"(第 24 章、第 28 章 §28.13)。这三样决定了你能不能把 ClickHouse 用对。函数库背不完,也不要背——会查文档就行。

**该怎么评估"要不要用"。** 用你自己的**真实数据和真实查询**压一遍,而不是看 benchmark。重点验证四件事:最重的几条查询能不能满足延迟要求;写入吞吐能不能跟上;最坏情况下的内存峰值会不会 OOM;以及最关键的——**你的查询模式是不是"宽表强扫描"**。如果是"多表复杂关联"或"高并发点查",那 ClickHouse 大概率不是最佳选择,先看 §32.12。

**怎么跟踪它的演化。** 只有一个可靠来源:**官方的 changelog 和 release notes**;方法(读哪一节、查哪张表、建哪份清单)在 §32.10。要留意两类变化——"LTS 版本"与"设置默认值翻转"——它们最可能影响你的生产环境。凡是本章标了**"未确认"**的地方,请一律回到官方文档核对。

**怎么把这一章用起来。** 它不是读一遍就记住的,而是用来**当索引查**的:选型看 §32.12 与 §32.15;升级看 §32.4 与 §32.10;评估新能力看 §32.6 到 §32.9;判断"到底行不行"看 §32.11 与 §32.13——但记得把"事实"和"判断"分开引用。

## 32.15 给选型者的决策清单

这一节把前面所有内容收成一份**可以直接拿去开会**的清单,分两部分:**什么信号说明你该用它**,以及**什么信号说明你该换别的**。

**该用它(信号)。** 下面这些信号同时出现两条以上,ClickHouse 大概率是对的答案:

- 写入方式基本是**追加**,很少原地改单行;数据是事件、日志、点击流、指标、明细这一类的形状。
- 读取方式以**聚合与扫描**为主:按时间范围、按几个维度分组,算出少数几行结果。
- 单表或少数几张大表是主要数据形状;JOIN 主要是"明细补维度",而不是"多张事实表互相关联"。
- 数据量已经大到单机关系库或单机分析库吃力(几亿到几百亿行),而预算不允许无限堆机器。
- 能接受**秒级到亚秒级**的查询延迟,不需要毫秒级的点查 SLA。
- 团队有意愿(或已有能力)做一点 schema 设计——尤其是**排序键与分区键**这两个决定(第 06 章 §06.3、§06.5);ClickHouse 对"没设计好的表"的惩罚比对"没写好 SQL"的惩罚大。
- 你愿意跟 LTS 线做滚动升级(§32.4)。

**该换别的(反信号)。** 下面任何一条单独出现,就该认真考虑别的方案:

- 需要**行级事务、跨表原子性、行级锁**——这是 OLTP 的地盘,不是"以后会支持"的问题(§32.11)。
- 需要**每秒几千次按主键取一行的点查**。列存要为每次查询拼列,这类负载它结构性地做不好;用 KV 或行存数据库。
- 数据会被**反复更新**,而不是"只追加、偶尔批量修正"。每次更新都可能触发重写或删除标记,维护成本随 part 数量爆炸(第 01 章 §01.10、第 18 章 §18.8)。
- 核心需求是**高召回、复杂相关度排序的全文检索**。这需要打分模型,而 ClickHouse 的检索能力建在跳数索引上,做不了打分(§32.7)。
- 核心需求是**低延迟、高并发的在线向量检索**(上亿条 embedding、毫秒级 SLA、每天大量新增)。用专用向量库(§32.12)。
- 需要**有状态的复杂流处理**——事件时间窗口、精确一次、复杂状态机;那是 Flink 的地盘(第 30 章 §30.13)。
- 团队明确**没有运维意愿**,也**不打算用托管服务**。自建的 ClickHouse 性能上限与运维成本都归你(第 29 章)。

**三个必须当场验证的问题(不要靠读文档回答)。** 落决定之前把这三条在自己环境里跑一遍:**一,你最重的三条查询**(真实数据、真实分布)在目标版本上能不能满足延迟要求;**二,你的写入峰值**——`parts_to_delay_insert` / `parts_to_throw_insert` 这两个闸门(第 08 章 §08.4、第 25 章 §25.8)会不会在你最忙的时候被撞到;**三,最坏情况下内存峰值**——一条大 JOIN 或大 `GROUP BY` 会不会 OOM(第 25 章 §25.2、第 15 章 §15.9)。三条都能在**单个实例**上验——这也是第 01 章 §01.7"别一上来就上分片"那条阶梯在选型阶段的应用。

**最后一条。** 选型里最容易被忽略的变量是**你自己的查询模式会不会变**:前面那些信号都在描述**现在**的负载,而系统的寿命通常比负载的形状长。所以还要问一句:"如果明年查询从宽表扫描变成了多表关联,我换系统的成本有多大?"——答案是"很大"时,就该留一条退路(比如把明细留在湖表里,§32.8)。

## 32.16 小结

这一章把三件事分开写了:**确定的事实**(列式向量化与不可变 part 的存储模型、半结构化类型已默认可用、轻量级删除、并行副本"可用但需显式开"、对象存储存储层、Keeper 独立演进)、**官方声明在做的方向**(存算分离、对象存储原生、全文/向量索引、优化器朝代价模型走、analyzer 推进、JOIN 与写入路径改进,每条都补了"为什么难")、以及**作者的主观判断**(存算分离不可逆、半结构化类型会改变宽表建模、优化器是最大技术挑战、边界是永远不会变成 OLTP、检索能力会长期停在"够用但不专精")。

中间那张**能力状态速查表**(§32.2)是这一章最"能用"的一节:它把散落在各章、却被本书反复依赖的能力收在一处,每行都给了 25.3 的状态、依据等级与来源。它是**事实表,不是路线图**:凡是拿不准的,表里写的是"未确认";而官方"打算往哪走"的内容统一放在 §32.3,不混进来。

围绕它的是四个**边界问题**,选型时都会真的遇到:**版本与升级**(§32.4)、**Cloud 与 OSS**(§32.5)、**新的能力面**(§32.6 到 §32.9)、以及**怎么自己跟踪演化**(§32.10);§32.15 则是可以直接拿去用的选型信号与反信号。

竞争格局上,ClickHouse 的主场是"宽表强扫描 + 高写入吞吐 + 成本可控",MPP 数据库强在多表关联,云数仓胜在托管,ES 胜在全文检索的相关度排序,专用向量库胜在在线召回。它的争议点里有些官方在改,有些是明确的设计选择,有些**官方没有任何承诺(未确认)**。整章的纪律只有一条:**事实、路线、判断三者不混**。

最后一条建议比什么都重要:**跟踪它演化的唯一可靠来源是官方 changelog**;其余一切都只是解读,包括这一章。凡是本章给了自检命令的,记住命令比结论寿命长。
