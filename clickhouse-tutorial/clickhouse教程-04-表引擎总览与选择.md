# 第 04 章 表引擎总览与选择

同样一份数据、同一条 `SELECT`,把 `ENGINE` 换一个字,执行计划就可能完全不同:一边只读几十个 granule 就返回,另一边老老实实扫完整张表;一边给出"每个键只有一条最新版本",另一边把同一个用户的五行历史全吐出来。这一章要建立的是**选型直觉**——知道每个引擎承诺了什么、放弃了什么,以及这些承诺在什么条件下会失效。

**表引擎不是"存储格式选项",它决定的是这张表的读写语义。** 在 MySQL 里换引擎主要回答"要不要事务、要不要行锁";在 ClickHouse 里换引擎回答的是一串更硬的问题:能不能按时间范围裁掉分区?同一个主键写第二次会怎样?能不能在后台把旧数据改成新值?能不能只读一列?能不能复制到另一个副本?这些都不是"性能微调",而是**你这套系统能不能成立**。

所以选引擎的正确顺序不是"哪个快",而是:先问这张表要承受什么样的写入、要回答什么样的查询、允不允许"暂时不一致",再去找语义匹配的引擎。

## 04.1 引擎决定的是读写语义

一个引擎至少要回答四个问题,每个答案都会在查询计划里留下痕迹。

**数据在哪里**——内存、本地磁盘、远端 HTTP 端点、还是另一台服务器的表。这决定了每次 `SELECT` 会不会有网络往返。

**怎么读**——有没有稀疏索引、有没有分区、能不能并行。`MergeTree` 会把 `WHERE` 翻译成"主键区间 + 分区集合",读取范围可能只剩百分之几;`Log` 家族没有索引,任何 `WHERE` 都是全表扫描(第 11 章)。

**能不能改**——只能追加、能按主键合并出新版本、还是能真正地删。ClickHouse 里绝大多数"改"都是**异步重写 part**(第 18 章)。

**后台做什么**——合并、TTL 清理、复制拉取、从 Kafka 消费。这部分"不占用户线程"的工作往往是引擎价值的一半。

性能不好可以调,语义不对只能重建表。

## 04.2 MergeTree 家族:主表的默认答案

如果没有特别理由,你的表几乎都应该是 `MergeTree` 家族的成员。它提供四件别处没有的东西:

- **按排序键物理有序**。数据在 part 内按 `ORDER BY` 排好,范围查询只触及相关 granule;
- **稀疏索引**。每 8192 行(`index_granularity` 默认值)取一个键值建索引,索引极小,能常驻内存;
- **分区**。整块地 `DROP` 或 `DETACH` 旧数据,而不是 `DELETE`;
- **后台 merge**。小 part 被逐渐合并成大 part,读放大随之下降。

代价是**只追加**:`INSERT` 进来的是一个不可变 part,后续任何"改"都只能是"写一个新 part、再把旧的合并掉"。第 05 章讲 part 的物理布局,第 18 章讲 merge、mutation 与 TTL。

## 04.3 MergeTree 的子族:每个都在解决一个具体问题

子族的差别在**merge 时怎么处理同一排序键的多行**。记住这一点,下面的清单就不需要背。

`ReplacingMergeTree` 解决"同一个主键有多个版本"。写法是 `ReplacingMergeTree([ver [, is_deleted]])`:`ver` 是可比较的版本列,merge 时保留版本最大的那一行;`is_deleted` 是 `UInt8` 列,`1` 是"墓碑行"、`0` 是正常行,它**只能在同时指定 `ver` 时使用**。默认行为是"即使最后一行是墓碑也保留",好让之后插入的低版本行仍被它压制。要把墓碑行物理清掉得用 `OPTIMIZE ... FINAL CLEANUP`,它受 `allow_experimental_replacing_merge_with_cleanup` 控制(25.3 上该设置默认 `false`,即默认不开;仍请以 `system.merge_tree_settings` 为准)。**"最终一致"就是这一族最需要警惕的地方**:合并发生在后台,你 `SELECT` 的那一刻可能还没合完,同一个键能看到多行。要看到确定的单行结果得加 `FINAL`,或者自己按 `ver` 取 `argMax`。

`SummingMergeTree([columns])` 解决"同一主键的数值列可以直接相加"。方括号里的 `columns` 是**可选的汇总列清单**:写上,就只有清单里这些列在 merge 时被求和;不写,则对所有数值列求和。清单里的列必须是数值类型、且不能出现在排序键里。merge 时,不在排序键里的数值列被求和;既不求和、又不在排序键里的列只保留其中一个值(取哪个由 merge 顺序决定,不要依赖)。它**不能替代聚合**:只有合并过的部分才已经加过,没合并的部分仍是多行,所以读的时候照样要 `sum(...) GROUP BY`。

这里有个**高频误用**,值得单独点出:很多人把它当"按键求和"用,以为"键相同,数值列就会自动加起来"。但 merge 折叠行时用的键是**整条排序键**,不是你以为的那个业务键。正确的建表姿势因此是:**把你真正想当"键"的维度列全都放进排序键**(官方在 MergeTree 文档里就是这么建议的——用这类引擎时把维度列加进排序键,让"同键的行"就等于"要被折叠到一起的行");而那些你不想要的、又希望被求和的数值列,**必须留在排序键之外**,否则它们压根不会被求和。换句话说,这条陷阱的根源是**排序键的组成**:它决定"哪些行会被折叠到一起",写错了就会出现"同一个键的行明明都塞进去了,数字却没加起来"。(另外,如果你的表单独写了 `PRIMARY KEY`、让它与排序键不同,`PRIMARY KEY` 的表达式还必须是排序键的**前缀**——这是 MergeTree 家族的硬约束。)

还有一类**嵌套列**要记住:以 `Map` 结尾的嵌套结构(老的 `Nested` 写法或 `Map` 写法)会被特殊对待——满足"第一列是数值或字符串作 key、其余是数值列作 value"的嵌套表,会被当成 `key => (values...)` 的映射,merge 时按 `key` 对齐、对 `values` 求和合并。这也是 `SummingMergeTree` 常配 `sumMap(...)` 一起用的原因。这类嵌套列**不需要**写进 `columns` 清单。

`AggregatingMergeTree` 解决"增量预聚合"。它的列类型是 `AggregateFunction(...)` / `SimpleAggregateFunction(...)`,存的是**聚合的中间状态**而不是结果,merge 时把状态合并起来。这是物化视图做增量聚合的底层机制(第 12 章讲状态与 `-State`/`-Merge` 组合子,类型侧见 §03.12)。

`CollapsingMergeTree(sign)` 用一对反向的行抵消旧记录:`sign` 必须是 `Int8`,`1` 是状态行、`-1` 是取消行,merge 时成对抵消。`VersionedCollapsingMergeTree(sign, ver)` 多了版本列,于是**插入顺序不再影响结果**——`CollapsingMergeTree` 的经典毛病就是"顺序错了就抵消不掉"。两者都啰嗦,新设计一般更愿意用 `ReplacingMergeTree`。

`ReplicatedMergeTree` 解决"同一份数据要在多个副本上"。引擎名带 `Replicated` 前缀(`ReplicatedMergeTree`、`ReplicatedReplacingMergeTree` …),通过 Keeper 协调副本。**它的构造参数(Keeper 路径、副本名、分片名)以及副本间的协调流程在第 22 章,这里不重复**——这一章只关心"它带来了复制这条能力",不关心怎么把它配起来。

`SharedMergeTree` 解决"分离存储与计算":数据与元数据放在共享对象存储上,计算节点无状态,副本之间不需要复制 part。它是 **ClickHouse Cloud 专有**的引擎,**不在开源发行版里**——这不是"你的配置没开",而是它根本不随 OSS 一起分发。开源侧想要多副本/高可用,用的是 `ReplicatedMergeTree`(第 22 章)。

`GraphiteMergeTree` 做时序数据的降采样/rollup:按一个配置段名(`graphite_rollup`)里的规则,把老数据按更粗的时间粒度聚合。该配置段定义在服务端配置里(不是建表语句里),主要字段:四个列名映射 `path_column_name` / `time_column_name` / `value_column_name` / `version_column_name`;`pattern` 下用 `regexp` 匹配指标路径、`function` 指定聚合函数(如 `max` / `avg`)、可重复的 `retention`(`age` 与 `precision` 都以秒计)定义各时间段的降采样粒度;`default` 段是不匹配任何 `pattern` 时的兜底。要查看当前实际生效的规则,查 `system.graphite_retentions`。

最后一条通用规律:**这一族的所有引擎都只是"最终一致"**。合并何时发生由后台调度决定,你可以用 `OPTIMIZE TABLE ... FINAL` 主动催一次,但对大表那是一次昂贵的全量重写,不该出现在常规流程里。

## 04.4 MergeTree 家族能力矩阵

把这一族摊成一张表,选型时对着看最快。格子里的 `✓` 表示该引擎支持这项能力(前提是建表时写了相应子句),`—` 表示不支持;"最终一致"和"只追加"是整族共同的底色,所以不单独占列。

| 引擎 | 分区 | 排序键 | 跳数索引 | TTL | mutation | 复制 | 投影 | 采样 | FINAL 语义 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| `MergeTree` | ✓ | ✓ | ✓ | ✓ | ✓ | — | ✓ | ✓ | 只合并 part,不折叠行 |
| `ReplacingMergeTree` | ✓ | ✓ | ✓ | ✓ | ✓ | — | ✓ | ✓ | 同排序键保留版本最大的一行 |
| `SummingMergeTree` | ✓ | ✓ | ✓ | ✓ | ✓ | — | ✓ | ✓ | 同排序键的数值列相加 |
| `AggregatingMergeTree` | ✓ | ✓ | ✓ | ✓ | ✓ | — | ✓ | ✓ | 同排序键合并聚合状态 |
| `CollapsingMergeTree` | ✓ | ✓ | ✓ | ✓ | ✓ | — | ✓ | ✓ | `sign` 成对抵消 |
| `VersionedCollapsingMergeTree` | ✓ | ✓ | ✓ | ✓ | ✓ | — | ✓ | ✓ | 按 `ver` 成对抵消 |
| `GraphiteMergeTree` | ✓ | ✓ | ✓ | ✓ | ✓ | — | ✓ | ✓ | 按 rollup 规则降采样 |
| `ReplicatedMergeTree` | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | 同 `MergeTree` |
| `SharedMergeTree` | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | 同 `MergeTree`(Cloud 专有) |

这张矩阵的读法是:横着看,**分区、排序键、跳数索引、TTL、mutation、投影、采样这七列**几乎整族都是 `✓`,所以它们**不构成选引擎的理由**——只要建表写了就都有。夹在中间的那列 **复制** 是例外:它对九个引擎里的七个都是 `—`,只有 `ReplicatedMergeTree` 与 `SharedMergeTree` 是 `✓`,而它表达的是**环境**而不是语义——开源侧任何子族都能换成一个 `Replicated*` 变体拿到复制。所以真正区分引擎的,是最右边那一列的 **FINAL 语义**(merge 时怎么处理同一排序键的多行)。`GraphiteMergeTree` 那一行的 `✓` 有个前提:它注册的降采样能力要配合 `graphite_rollup` 配置段才生效,配置不对时退化成普通 `MergeTree`。怎么把这张矩阵读成具体的选型判断,见 §04.11。

## 04.5 日志族:什么时候它反而够用

`TinyLog` / `Log` / `StripeLog` 是"把列式存储剥到只剩骨架"的三个引擎,共同点一句话:**一次写入就是把一个 block 追加到文件末尾,读取则是顺着文件往下读**。没有索引、没有分区、没有排序键、没有后台 merge。

要理解它们的边界,得看写入和读取这两条路径的机制。

**写入。** 每次 `INSERT` 到来,数据先被序列化、压缩成一个 block,然后**逐列追加**到列文件末尾(只往后接,不就地改)。同时,`Log` / `StripeLog` 往 marks 文件里追加一条记录,记下这个 block 的偏移和行数;`TinyLog` 连 marks 都没有。由此带来三个后果:一是**写入会锁住整张表**——`INSERT` 期间,别的读和写都得排队,没有"边写边读";二是**写入不是原子的**——写到一半服务端崩了,表就坏了,之后读它直接报错;三是每个 block **独立压缩**,block 之间不复用编码,而小批量频繁写入会累积出大量 block,每次读都得把它们挨个过一遍。这三点合起来,就是日志族"写入便宜、读写都粗糙"的全部来源。

**读取。** 读取只有一种姿势:**没有能跳过数据的索引**。`Log` / `StripeLog` 的 marks 是**块级**的(粒度是一个 block,不是 MergeTree 那种按 granule 精细定位的稀疏索引),它能让读取**并行**(一个线程读一个 block),但任何 `WHERE` 都要把候选 block 全读进来再过滤。`TinyLog` 更极端:没有 marks,**只能单线程**从头读到尾。所以"读它必须全扫"是设计要求,不是"还没来得及优化"。

三者之间的差别只影响"文件怎么摆",不影响上面这套机制:

- `TinyLog` 每列一个文件、整块一起写,文件数和文件句柄都最少、也最简单,但没有 marks、**不能并行读**,适用规模被压到百万行这一档;
- `Log` 每列一个数据文件加一个 marks 文件,**能并行读、读性能最好**,代价是文件句柄最多;
- `StripeLog` 把所有列挤进一个 `data.bin`,配 `index.mrk` 和 `sizes.json`,**文件句柄最少、最好搬运**,代价是单文件损坏等于全表损坏、读取效率略低。

什么时候它够用?**当这张表真的只是一个"落地的文件"的时候**:诊断日志、一次性导出的中间结果、只在本地调试时读的小表。判断标准很简单——你能接受"读它必须全扫、写它期间不能读",它就够用。

反过来,`Log` 家族**没有** `ALTER ... UPDATE/DELETE`、没有主键、没有分区裁剪、没有后台 merge,而且写坏一次就整表报错。一旦查询里出现"按时间范围查最近一小时",或有别的进程要边写边读,它就从"够用"变成"罪魁祸首"。

## 04.6 特殊用途引擎:一句话定位与边界

这些引擎的共同点是:**它们不是在存业务数据,而是在为某一种操作提供结构**。

`Memory`:数据全在进程内存,没有索引,重启即失。适合小维表与会话内的中间结果。注意 `TRUNCATE` 释放的是列缓冲,分配器通常不会把内存还给操作系统。

`Set`:只保存**第一列**的去重值,专为 `IN` 的半连接优化而生。多出来的列没有意义。

`Join`:一张**预建好的内存哈希表**,供 `joinGet` 与 `JOIN` 的右表使用。建表时要声明 `Join(ANY, LEFT, key)`,重启即失。

`Buffer`:在内存里攒批,达到阈值再刷入目标表。它**可能丢数据**——强杀、OOM、断电时,还在缓冲里的行永远消失。它用"可能丢一小段"换"写入更平稳";要既不丢又平稳,得让上游能重放。

`File` / `URL`:文件或 HTTP 端点本身就是表。**每次 `INSERT` 都是"读回整份、合并、整份重写"**,数据量一大就非常慢,而且两个写入者会互相覆盖。

`Null`:吞掉一切写入,读取永远为空。正经用途是做压测基线,以及当物化视图"只想要副作用"的落点。

`Values`:把一段字面量当成表,实际使用中主要以内联表函数的形式出现。

`Merge`:把同构的多张表看成一张只读虚拟表。不去重、不保证顺序,每次查询都要把所有匹配表逐个打开——适合表数量可控的老式分表架构。

## 04.7 集成与代理引擎:外部数据的门

`Distributed`、`Kafka`、`MySQL`、`PostgreSQL`、`SQLite`、`S3`、`HDFS`、`URL`、`ODBC`、`JDBC` 名字长得像表引擎,但**它们不是存储引擎,而是"外部数据的门"**。读写语义与本地表差别巨大,必须单独记:

- `Distributed` **自己不存数据**。`INSERT` 会按分片键转发到某个本地表,`SELECT` 会被拆成对各分片的子查询再汇总。这套语义成不成立,取决于两个配置:**`sharding_key` 是 `Distributed` 的建表参数**(`Distributed(cluster, db, local_table[, sharding_key[, policy]])`),决定一行按什么规则落到哪个分片——多分片集群上省略它,`INSERT` 会被**直接拒绝**(除非显式打开 `insert_distributed_one_random_shard`);**`internal_replication` 则是集群 `remote_servers` 配置里、`<shard>` 一级的开关**,`true` 表示"写入只发给分片里的一个副本、其余靠副本自己复制"(配合 `Replicated*` 本地表,这是推荐配法),`false` 表示"写给分片里的每一个副本"(只在本地表不是复制表时才需要,否则很容易写出重复数据)。也就是说,§04.12 常见误用里那条"写入落到本地 `MergeTree`、`Distributed` 只做查询入口"能不能照做,正是由这两个旋钮决定的。所以"把 `Distributed` 当本地表写"会踩两个坑:你不知道某一行落在哪,以及跨分片查询存在聚合性能上限(第 23 章 §23.2、§23.3)。
- `Kafka` 是一条**消费流**而不是存储:读的语义是"从队列取一批并推进 offset",取走的数据不在它那里。做实时入湖时一般配一张 `MergeTree` 目标表 + 物化视图(第 30 章)。
- `MySQL` / `PostgreSQL` / `SQLite` / `ODBC` / `JDBC` 是**外部表的投影**:每次查询都推到远端执行,`WHERE` 能下推多少取决于对面。把大表 join 这种外部表会很慢。
- `S3` / `HDFS` / `URL` 是"按格式读远端文件",属于**只读或低效写**,不适合做高频写入的落地表。

一句话:**这些引擎让 ClickHouse 能看见外部数据,但不提供 ClickHouse 的存储保证**。把它们当"数据源",而不是"我的表"。

除了上面这些,还有一批更窄的集成引擎,名字不常出现在入门材料里,但遇到对应系统时就是唯一入口:

- `RabbitMQ` / `NATS`:与 `Kafka` 同类的**消费流**引擎,分别从 RabbitMQ 队列、NATS 主题取消息转成行。语义和 `Kafka` 一样——取走即推进,不做存储;落库同样靠"消费引擎 + 目标 `MergeTree` + 物化视图"。
- `Redis`:把 Redis 当外部 KV 表读写,适合小数据量、低延迟的点查;它不是用来做大扫描的,别指望它替代落地表。
- `MongoDB`:把 MongoDB 集合当外部表,`WHERE` 尽量下推到 MongoDB 执行。
- `S3Queue`:与 `S3` 的"只读投影"不同,它做的是**后台摄取**——监听 S3 桶里新出现的对象并逐个导入,处理进度由 Keeper 协调(**依赖与细节以版本文档为准**)。想"把对象存储当队列"就用它。
- `AzureBlobStorage`:Azure 对象存储上的表,对应 `S3` 那一档(只读投影 / 低效写)。
- `Hudi` / `Iceberg` / `DeltaLake`:把湖表格式当外部表读,能按快照或增量读数据。**它们的写入支持与成熟度随版本变动较大,具体能力以版本文档为准**。
- `EmbeddedRocksDB`:在 ClickHouse 进程内嵌一个 RocksDB 做本地 KV 存储,适合不大的维表与点查,数据落在本地磁盘而不是内存。
- `KeeperMap`:把 ClickHouse Keeper(它本身是 ZooKeeper 兼容的协调服务)当成**持久化的键值存储**来用——表里的每个键对应 Keeper 里的一个节点。典型用途是**小体量、需要持久、又想跨副本共享的键值**:去重表、幂等写入的"已处理 ID"、任务状态这类"这点状态不值得单独建服务"的场景。它的代价很明确:**每次读写都要走一遍 Keeper**,吞吐远低于本地表;单键的值大小受 Keeper 的节点大小限制、总量受 Keeper 内存约束,所以它只适合"小而关键"的数据,不能当正式业务表。它和 `Join` / `Set` 的分工是:后两者是**进程内、不持久、不复制**的内存结构(重启即失、只在单机),`KeeperMap` 则**持久且经 Keeper 复制**,但慢得多、也小得多;它和外部字典的分工是:字典是**读多写少的查找表**(`dictGet` 按源刷新),`KeeperMap` 是**可读可写的 KV**。它的形态大致是 `CREATE TABLE kv (k UInt64, v String) ENGINE = KeeperMap('/keeper_map/kv') PRIMARY KEY k;`——引擎参数是 Keeper 里的路径前缀,表需要声明 `PRIMARY KEY`(它就是键);**确切的参数名、路径前缀相关设置与键类型限制,以你版本的引擎文档为准**(去 `KeeperMap` 的引擎页查)。
- `Dictionary`:把一份**字典**暴露成一张表,`SELECT * FROM 该表` 就是遍历字典。它让字典既能被 `dictGet` 点查,也能被当成普通表 join。
- `Executable`:把一次外部脚本调用的输出当作表来读(或当作长期运行的进程喂数据)。它把"数据源"变成了任意程序,**安全边界要自己把关**,别在服务端表定义里塞未审计的脚本。

这些引擎有两条共同的边界:**它们大多不提供本地表的存储保证**(复制、TTL、mutation 都无从谈起),而且**大多依赖外部系统的可用性**——外部那台挂了,这条表就查不动。用之前先问"外部系统挂了,我这里会怎样"。

## 04.8 视图族:普通视图与两种物化视图

`View` 是个宏:不存数据,查询时把子查询重跑一遍。它因此只读,往视图里 `INSERT` 会被告知这张表不可写。

`MaterializedView` 是最容易理解错的一个。说清它之前要先分个类:"物化视图"这个名字在 ClickHouse 里盖着**两种不一样的东西**——一种是被写入触发的**插入触发器**,另一种是定时的**可刷新任务**。默认建出来的是前者,加了 `REFRESH` 子句才是后者。

```sql
-- 形态一:插入触发器。只有这条语句**之后**写进 raw 的行才会被处理
CREATE MATERIALIZED VIEW mv TO daily
AS SELECT toDate(ts) AS d, count() AS n FROM raw GROUP BY d;

-- 形态二:定时任务。按周期把整条子查询重跑一遍,结果写进目标表
CREATE MATERIALIZED VIEW snap
REFRESH EVERY 10 MINUTE APPEND TO daily_snap
AS SELECT now() AS t, toDate(ts) AS d, count() AS n FROM raw GROUP BY d;
```

一句话区分这两形态:**默认物化视图对"新写进来的行"负责,可刷新视图对"整个源表的当前状态"负责。** 前者便宜、增量,但只处理触发之后的数据;后者贵、全量,但每次拿到的是自洽的快照。选错了,症状通常是"报表里怎么只有一半数据"——因为你要的是后者,却建成了前者。

建表时有三个点先记住:**建视图之前就已经在源表里的数据不会自动进来**(这是"我建了物化视图,怎么数据对不上"的头号根因);**`POPULATE` 与 `TO` 互斥**(前者靠视图自带的内部表做一次性回填,而 `TO` 形式根本没有内部表,两套机制互相排斥);**`POPULATE` 带竞态**(回填期间写进源表的行可能漏掉、也可能重复)。补充历史数据的正确做法在 `第 13 章 §13.7`。

还有一条容易看漏的:物化视图是**触发器**,触发发生在写入路径上——源表每收到一个插入块就执行一次视图的 SELECT,结果**追加**进目标表。所以同一分钟会被加工出很多行,目标表通常是 `AggregatingMergeTree` / `SummingMergeTree` 这类会在后台合并时收敛的引擎。这件事的完整因果在 `第 13 章 §13.1` 与 `§13.4`。

`WindowView` 是视图族里更边缘的一个:按时间窗口聚合、支持 `WATCH` 实时推送。它是**实验特性**,需要 `allow_experimental_window_view = 1`。这里有一个容易记反的地方:25.3 的文档给它挂的是 **Experimental(实验特性)**徽标,**不是 Deprecated**——真正被文档标为 **Deprecated(已废弃)**的是和 `WATCH` 搭档的另一个东西 **Live View**,两者不是一回事(第 13 章 §13.2 讲了区分)。而上游追踪其移除工作的 issue(#114738)自述:这件事"其实自 24.12 起就'事实上发生了'"——该 issue 明说**遗留的 window view 自 24.12 起就已处于 inert(失效)状态**,上游随后着手拆除它(删除相关源码、把配套开关标为废弃),并推荐改用基于 `WATERMARK` 的流式查询。也就是说,25.3 的文档虽然还可能挂着 Experimental 徽标,但这个特性实际已经不能依赖——结论不变:**不要在新设计里用它**。

视图族的完整处理——`TO` 目标表与自带内部表两种落点的差别、为什么增量聚合必须把**状态**存进 `AggregatingMergeTree`、物化视图链、`REFRESH` 的调度与依赖、回填历史数据的三种做法、以及十来条反复出现的坑——全部在 `第 13 章 物化视图与增量聚合`。本节只交代"有哪两种"和"建的时候要注意什么"。

## 04.9 数据库引擎:库也有引擎

`CREATE DATABASE` 也带引擎,它决定的是**这个库怎么组织表、怎么和副本协作**,和表引擎是两件事,别混为一谈。

`Atomic` 是**新库的默认引擎**。每个表有独立的元数据,`CREATE`/`RENAME`/`DROP` 是原子的,还支持原子地重命名多张表。新库一律用它。

`Ordinary` 是 MySQL 风格的老引擎:一个库一个磁盘目录,`RENAME`/`DROP` 不保证原子,元数据以目录结构为准。老实例里常见,**不要在新库里建**。

`Replicated` 让**库的元数据**通过 Keeper 在副本间复制,于是任意一个副本上执行的 DDL 都能扩散到全部副本。这是除了 `ON CLUSTER` 之外的另一条"DDL 自动同步"的路径。

`Memory` 是**非持久化**的库引擎:它不碰文件系统,库里的表定义只活在内存里,服务端一重启这个库就空了。它同时也是 `TEMPORARY`——临时表那个内部数据库——所用的引擎,所以它的定位就是"放临时 / 中间数据",不要拿它存需要持久化的库。

还有一类**外部库引擎**,让 ClickHouse 把别人的库"当成自己的库"来读。`MySQL`、`PostgreSQL`、`SQLite` 这几个库引擎,让 `CREATE DATABASE` 直接指向一个远端库(或本地文件形式的 SQLite 库);库里那些"表"其实就是**外部表的投影**,读写语义与 §04.7 里那批"外部数据的门"完全一致——每次查询都推到远端执行、`WHERE` 能下推多少取决于对面、**不提供 ClickHouse 自己的存储保证**(没有 part、没有 TTL、没有后台 merge),外部那台一挂这条路径就查不动。这些细节在 §04.7 讲过了,这里只记一句:定位上是"数据源",不是"我的库"。同一族里还有 `MaterializedPostgreSQL` 这种"把外部库的变更持续同步进来"的形态(依赖复制槽,细节以版本文档为准),以及 `Filesystem` / `S3` / `HDFS` / `DataLake` 这些"把一个目录或一整片湖当成库"的引擎——它们更适合探数,同样不该当主存储。

`Lazy` 只在少数场景有意义,而且**只对 `*Log` 家族的表生效**:它让库里的表在最后一次访问后,按 `expiration_time_in_seconds` 秒从内存里卸载,之后再访问时透明地重新加载——适合"有很多小 `*Log` 表、且访问间隔很长"的情形。这个参数是**必填的位置参数,没有默认值**,形如 `ENGINE = Lazy(3600)`。

关于它的版本状态,要把两件事按版本分开说,**别混成一句**。**在本书对标的 25.3 上,`Lazy` 仍然存在、也仍然可用**——这个引擎此时并没有被移除。**移除发生在 25.3 之后的某个版本**(见上游 PR #93627):从那之后,`ENGINE = Lazy` 会被当作 `Atomic` 处理。而"官方给出的替代品"——`Atomic` 库引擎上的 `lazy_load_tables` 设置(它对全部表引擎都生效,而旧 `Lazy` 只管 `*Log`)——**在 25.3 上还不存在**(它是更晚才加进来的,默认 `0`),所以 25.3 上既没有移除、也没有替代,`Lazy` 就是它自己。要写跨版本都能跑的 DDL,就别依赖 `Lazy`;要用"按需加载"这类能力,先确认你那一版是"`Lazy` 还在"还是"已经换成 `Atomic` + `lazy_load_tables`"。

`ON CLUSTER` 则是另一件事:它不改变库引擎,而是让**一条 DDL 在集群的每个节点上各执行一次**。

```sql
CREATE DATABASE IF NOT EXISTS analytics
ON CLUSTER my_cluster
ENGINE = Atomic;
```

在这样一个库里建表,写得对(带上 `ON CLUSTER`)才会在每台机器上都建出来。这也是"我只在一台上建了库,别的机器却报表不存在"的根源——那条 DDL 根本没广播出去。分布式 DDL 的机制、以及它和 `Replicated` 数据库的关系在第 23 章。

## 04.10 按工作负载选引擎

把上面的能力对着真实负载过一遍,几条常走的路径大致是:

**日志(logs)。** 典型查询是"某段时间 + 若干过滤维度的聚合"。用 `MergeTree`,`PARTITION BY toYYYYMM(ts)`(数据量很大就用更细的 `toDate`),排序键把时间放最前再跟常用过滤列。别用 `Log` 家族——日志是要**查**的,不是只落地。

**指标(metrics)。** 高频写入、按标签维度聚合、还需要降采样。用 `MergeTree` 家族;要"同一时间线只留最新"用 `ReplacingMergeTree`,要"自动累加"用 `SummingMergeTree`,降采样交给物化视图(第 18 章、第 38 章)。

**链路(traces)。** 结构和日志同构,但字段更宽、更稀疏。重点是用分区 + 排序键同时覆盖"按时间回溯"和"按 `trace_id` 精查"两类查询。

**CDC / 变更流。** 上游是数据库变更日志,每条主键会有多个版本。用 `ReplacingMergeTree(ver)` 表达"保留最新",并接受最终一致——需要确定单行时用 `FINAL` 或自己 `argMax`。

**维表查找(lookups)。** 键少、要低延迟点查。小表用 `Join` 引擎或字典(第 21 章);键多就把查找键做成 `MergeTree` 的排序键。别指望 `Map` 列帮你加速查找(§03.8)。

**队列 / 摄取(queues)。** 入口是流,不是表。用 `Kafka` / `RabbitMQ` / `NATS` / `S3Queue` 去消费,落到一张 `MergeTree` 目标表;队列引擎本身永远是"门",不是"家"。

## 04.11 决策清单

选型要的判断,其实都能从 §04.4 的矩阵里直接读出来,所以这里不再重抄一遍引擎清单,只把"读法"说清楚。

**第一,矩阵里那七列整族都是 `✓` 的(分区、排序键、跳数索引、TTL、mutation、投影、采样)通用,不构成选引擎的理由。** 只要建表时写了就都生效;夹在中间那列 **复制** 是唯一的例外(见下一条)——它既不在这七列里,也不参与区分引擎的语义。真正区分引擎的,只有最右边那一列的 **FINAL 语义**——merge 时怎么处理同一个排序键的多行。所以选型的第一步不是"要不要分区",而是"同键的多行,我希望它被怎么折叠"。

**第二,"复制""Cloud"是环境性质,不是语义性质。** 开源侧任何子族都能换成一个 `Replicated*` 变体拿到复制,`SharedMergeTree` 只在 Cloud 上有。要不要复制,不该左右你选哪个子族。

**第三,格子里的 `✓` 只表示"能力存在",不表示"适合高频用"。** mutation 全族都支持,但它永远是异步 part 重写,高频改数据在任何子族上都是反模式;`FINAL` 全族能用,也一样不该随手乱加。

把这三条和 §04.10 里几类负载的默认打法合起来看,选型就是"对号入座";剩下的都是"选错了会怎样",集中在下一节。

## 04.12 常见误用

**用 `Log` 存需要按时间查的表。** 后果:所有时间范围查询都变成全表扫描,数据一涨查询就崩。正确做法:查询里有 `WHERE time BETWEEN ...`,就用 `MergeTree` 加 `PARTITION BY toYYYYMM(time)`。

**用 `Memory` 存需要持久化的维表。** 后果:重启后 JOIN 悄悄变成空集,不报错、结果少一半。正确做法:维表用 `MergeTree`,把"想加速"的部分交给 `Join` 引擎或字典(第 21 章)。

**把 `Distributed` 当本地表写。** 后果:不知道行落在哪个分片,本地 `count()` 只看到一片;没有分片键的查询会退化成"所有分片各查一遍再汇总"。正确做法:写入落到本地 `MergeTree`,`Distributed` 只做查询入口。

**以为 `Buffer` 是可靠的缓冲。** 后果:一次 OOM 之后目标表少了几十万行,而且没有痕迹。正确做法:让上游能重放,或者干脆不用它、改在写入端攒批。

**以为物化视图会"自动补上历史数据"。** 后果:上线当天报表是空的。正确做法:建视图时就想好回填方案(触发器视图用 `TO` + 手动灌历史,或用可刷新视图)。

**把可刷新视图和触发器视图搞混。** 后果:以为每次插入都会触发加工,结果它十分钟才重算一次;或者反过来,想要周期快照却建了个只处理增量的视图。正确做法:先问"我要的是对新行负责,还是对整表状态负责",再决定加不加 `REFRESH`。

## 04.13 与 mini-clickhouse 的对照

`mini-clickhouse` 的引擎注册表在 `mini-clickhouse/minich/storages/base.py`,通过 `register_storage_engine(...)` 注册,`registered_storage_engines()` 返回 `(名字, 是否废弃, 说明)` 三元组。当前注册了 23 个引擎,覆盖了本节讲到的四个大族:

- **MergeTree 家族**(全部可用):`MergeTree`、`ReplacingMergeTree`、`SummingMergeTree`、`AggregatingMergeTree`、`CollapsingMergeTree`、`VersionedCollapsingMergeTree`、`GraphiteMergeTree`(只注册、不实现汇总规则)、`ReplicatedMergeTree`、`ReplicatedReplacingMergeTree`;
- **日志族**:`TinyLog`、`Log`、`StripeLog`;
- **特殊用途**:`Memory`、`Null`、`Set`、`Join`、`Buffer`、`Merge`、`File`、`URL`、`Values`;
- **视图族**:`View`、`MaterializedView`(`MATERIALIZED VIEW` 的"插入触发器"语义与 `TO` 目标表都实现了)。

没有一个被标记为 deprecated。

需要如实说明**没有实现**的部分:`Distributed`、`Kafka`、`MySQL`、`PostgreSQL`、`SQLite`、`S3`、`HDFS`、`WindowView`、`SharedMergeTree`,以及 §04.7 里补充的 `RabbitMQ`/`NATS`/`Redis`/`MongoDB`/`S3Queue`/`AzureBlobStorage`/`Hudi`/`Iceberg`/`DeltaLake`/`EmbeddedRocksDB`/`Dictionary`/`Executable` 这些集成引擎。同样没有实现的是**可刷新物化视图**——mini 的 `MaterializedView` 只覆盖"插入触发器 + `TO` + `POPULATE` 回填"这一形态,没有 `REFRESH EVERY` 的调度。`remote`/`cluster`/`clusterAllReplicas` 表函数注册了名字,实现依赖上下文里的 `remote_executor` —— 不挂载时会抛 `NOT_IMPLEMENTED`,而不是静默返回空结果。对 `s3`/`hdfs`/`mysql`/`postgresql`/`sqlite`/`odbc`/`jdbc`/`executable`/`dictionary`/`timeSeries*` 这些表函数,注册的是占位类,每个都带一句"为什么不实现"。

另外两点值得知道。第一,`MergeTree` 的实现分布在 `minich/storages/merge_tree/` 的 12 个模块里(不含 `__init__.py`;`part.py` 负责 part 的磁盘布局与读写、`marks.py` 负责 granule 与 mark、`key_condition.py` 负责主键区间与分区裁剪、`skip_index.py` 负责五种跳数索引、`merger.py` 负责 k 路归并与引擎家族的行折叠、`mutations.py`/`ttl.py` 负责两类后台重写),`engines.py` 把它们包装成 `IStorage` 子类并注册 —— 这正是本节说的"引擎 = 读写语义"的代码化。第二,`MergeTree` 需要 `Context(data_path=...)` 才会把 part 落到磁盘;不传 `data_path` 时它仍然能用,但数据只在内存里,重启即失 —— 这一点在第 31 章会再强调一次。

对照下来,有教学价值的几处:

- `StorageFeatures`(`base.py`)把"引擎能做什么"显式声明成一张能力表(`primary_key`、`partitions`、`sorting_key`、`skip_indexes`、`ttl`、`mutations`、`merges`、`replication`、`append_only`、`sampling`、`projections`),让优化器不必用 `isinstance` 判断引擎类型——这正是 §04.1 那句话的代码化,也是 §04.4 那张能力矩阵在代码里的样子。
- `Log` 家族共用一份 `_LOG_FEATURES = StorageFeatures(append_only=True, parallel_read=False)`;`Memory` 是 `StorageFeatures(mutations=True)`(只支持改列,不支持改数据);其余引擎普遍是 `parallel_read=False`。
- `Buffer` 的多层晋升(`num_layers`、`min_time`/`max_time`、`min_rows`/`max_rows`、`min_bytes`/`max_bytes`)与"崩溃会丢数据、`shutdown()` 尽力 flush 但不为崩溃兜底"这两个取舍都如实保留了。
- `MaterializedView` 保留了语义核心 `push()`(源表写入后把加工过的 block 推给目标)与 `populate()`(一次性回填,用 `_populated` 保证幂等),线程与内部表清理被省略;`Set` 引擎的注释明确写了"真实 ClickHouse 对多余的列直接报错,这里是忽略"。

## 04.14 小结

引擎决定了这张表的读写语义:数据在哪里、怎么读、能不能改、后台做什么。`MergeTree` 家族是默认答案,子族之间的差别几乎全在"merge 时怎么处理同一个排序键的多行"那一列,而分区、排序键、TTL、mutation、投影、采样是整族共享的能力,代价是它们全部只是最终一致。`Log` 家族够用的唯一前提是"你能接受全扫"。特殊用途引擎是给某一种操作准备的结构,`Buffer` 会丢数据、`Memory` 会失忆。集成/代理引擎是外部数据的门,不提供本地表的保证,还依赖外部系统活着。

物化视图有两种:默认的是插入触发器,只对新写进来的行负责;带 `REFRESH EVERY ...` 的是定时任务,对整表状态负责,`APPEND` 决定追加还是覆盖。`POPULATE` 和 `TO` 互斥,回填要走手动灌数据。库也有引擎,`Atomic` 是新库的默认,`ON CLUSTER` 则是让 DDL 广播到每个节点。

选型的正确姿势是先定语义(这张表承受什么写、回答什么查、允不允许暂时不一致),再看性能;日志、指标、链路、CDC、查找、队列这几类负载各有默认打法,照着 §04.10 过一遍能省掉大半试错。
