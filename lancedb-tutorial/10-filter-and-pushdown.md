# 第 10 章　标量过滤与谓词下推

上一章的实测里出现过一个难看的数字：**一张 20,000 行的表删掉 99% 的行之后，
读取量只降了 34%。** 剩下的 1% 数据凭什么要读三分之二的字节？

答案是"读取"这件事在列存里不是一个动作，而是**四层可以各自省钱的决策**：
只读哪些列、跳过哪些片段、用索引取哪些行、哪些列留到最后才读。
这四层里任意一层失效，别的层的收益就大打折扣——删除比例高的时候，
失效的正是"行范围下推"。

这一章把四层逐层拆开，每一层都用真实跑出来的字节数说话。
"下推"这个词听起来抽象，但它只回答一个问题：
**这个算子能不能让下游少读一点字节？**

## 10.1 数据集与量法

后面所有数字都来自同一张表：分 10 次写入，每次 2000 行，
所以有 10 个片段；`n` 列全局单调递增；四列分别是
`n`（数值）、`grp`（`n % 50`）、`txt`（`item-000000` 这样的定长字符串）、
`pad`（长度在 50~90 之间波动的填充字符串）。

```
片段数=10 行数=20,000 字节=384,638 每行=19.23 字节
```

量法是关键，先说清楚。字节数不是估算的，是**从对象存储那一层取差值**：
扫描前后各读一次 `InstrumentedStore` 的计数器，相减。
这样无论读路径怎么重构（换编码、加缓存、改下推策略），数字都是真的。

```python
db.instrument()                       # 把根 store 换成计量壳
db.reset_io()
scanner = ds.scanner(columns=["n"], filter="n > 19000")
scanner.to_batch()
print(scanner.stats.bytes_read)
```

量 I/O 之前还有一条必须自己确认的事：**观测路径也会断，而且断得比功能路径安静**。
`LanceDBConnection` 给每张表套了一层 `_PrefixedStore` 做子目录隔离
（`mini_lancedb/connection.py`），它继承了 `ObjectStore` 的构造函数，
于是默认自带一份全新的、永远清零的 `StoreStats`。如果这层壳只转发读写方法、
不转发 `stats`，那么 `Scanner.stats.bytes_read` 会**恒等于 0**——不报错、不警告，
只是所有 I/O 数字都变成假的，而"下推有没有生效"完全靠这些数字判断。
修法是一行：`_PrefixedStore.__init__` 里把 `self.stats` 指回内层 store。
这一行现在就在代码里（`self.stats = inner.stats`），所以本章的每一个字节数
都是真的；反过来说，**换一个代理层就要重新确认一次这一行还在不在**。

**设计课：** 装饰器/代理层很容易漏掉"旁路"接口。
转发失败的方向往往不是功能，而是**观测**——功能路径会立刻报错，
观测路径只会安静地给你 0。一个永远返回 0 的性能计数器
比没有计数器更危险，因为它看起来是工作的。

## 10.2 第一层：列投影下推

最朴素也收益最大的一层。列存把每一列单独放，所以"只要 n 列"
就真的只读 n 列的数据页。

```
1 列 ['n']                    读取字节=   43,540  往返=  40  扫描行= 20,000
2 列 ['n', 'grp']             读取字节=   58,540  往返=  50  扫描行= 20,000
3 列 ['n', 'grp', 'txt']      读取字节=  357,984  往返=  60  扫描行= 20,000
4 列 ['n', 'grp', 'txt', 'pad'] 读取字节=  383,224  往返=  70  扫描行= 20,000
全列                           读取字节=  383,224  往返=  70  扫描行= 20,000
```

值得注意 `n → n,grp` 只加了 15,000 字节，而 `+txt` 一下子加 30 万。
因为 `txt` 是字符串列，每行实际存了 12 个字符的 payload；
`n` 和 `grp` 是小整数，位打包之后每行只要几个位。
**投影下推省下的比例，取决于被省掉的那一列有多宽。**

**只读一列 vs 全列：43,540 对 383,224，差 8.8 倍。** 而扫描的行数
一行不少（都是 20,000）——省下的是字节，不是行。

往返次数（`range_reads`）的规律也很好读：**每次增加一列，往返数正好加 10**
——也就是每个片段多几次范围读。40 次 / 10 个片段 = 每片段 4 次，
这里面既有数据页，也有打开文件要付的元数据（footer、列元数据、偏移表）。
也就是说，**"打开一个片段"本身就有固定成本**，这就是片段数
不能无限增长的另一个原因（第 23 章）。

实现上的关键是**投影列的来源不只是用户要的列**：

```python
def _needed_columns(self):
    proj = self._projection()
    filt = self._filter_columns()
    out = list(proj)
    for c in filt:
        if c not in out:
            out.append(c)
    return out
```

真正要读的列是 `投影列 ∪ 过滤列`。`SELECT txt WHERE n > 100`
必须把 `n` 也读进来——这不是浪费，这正是第 4 层（延迟物化）
要处理的对象。还有一个容易写错的细节：`columns=[]`
（只要行数、不要任何列）是合法请求，所以判断必须用
`is not None` 而不是真值判断，否则它会变成"全选"。

### 投影下推在本实现里停在哪一层

投影下推还有一个更细的档位值得知道：**子列投影**。

一个 struct 列 `meta` 里可能有 `meta.x` / `meta.y` / `meta.z` 三个子字段。
理想情况下，`SELECT meta.x` 只该读 `meta.x` 那一段页，另外两个子字段
一个字节都不碰。第 5 章讲 field id 排序时说的"`c` 的子字段紧跟在 `c`
之后"，正是让这件事可做的结构前提。真实 Lance 的格式层支持这种按
子字段寻址的读取。

**本实现做不到。**实测 `select(["meta.x"])` 直接报

```
SchemaError: select 引用了不存在的列 (missing=['meta.x'])
```

原因是 `Schema.select` 只按**顶层列名**取列，没有"字段路径"这个概念：
`meta.x` 在它眼里是一个名叫 `meta.x` 的列，而表里没有这么一列。

所以本章的"投影下推"要读出准确的边界来：**它省的是"哪些顶层列"，
不是"哪些子字段"。**对一个宽 struct 列（比如塞了二十个字段的元数据），
这个差距很实在——你只想读其中一个字段，却必须把整列搬进来。
这条限制和 §10.13 里"嵌套列不参与谓词下推"是同源的，
都来自同一个简化：**本实现的列寻址只有一层。**

## 10.3 第二层：片段级 zone map 剪枝

每个数据文件在写入时记下每一列的 `min` / `max` / `null_count`。
查询时，任何一个**不可能命中**的片段直接跳过，一个字节都不读。

```
n > 19000      剪掉= 9/10 扫描片段=1 扫描行=  2,000 读取字节=    8,696 结果=   999
n > 19999      剪掉=10/10 扫描片段=0 扫描行=      0 读取字节=        0 结果=     0
n > 20000      剪掉=10/10 扫描片段=0 扫描行=      0 读取字节=        0 结果=     0
n < 0          剪掉=10/10 扫描片段=0 扫描行=      0 读取字节=        0 结果=     0
n >= 0         剪掉= 0/10 扫描片段=10 扫描行= 20,000 读取字节=   87,080 结果=20,000
```

`n > 19000` 在 10 个片段上剪掉 9 个，读取字节 **8,696**；同一条查询、
同一批列，把 zone map 关掉是 **47,888**（下面开关对照的实测值）——少了 5.5 倍。
这里要对齐口径：**47,888 不是"剪枝存在之前的基线"，而是关掉剪枝时的对照值**，
两次只差"剪没剪片段"这一个变量。`n > 19999` 是 0 字节——
一个片段都不打开，连该列的数据页都不解码。

这就是"细粒度统计本身就是索引"的意思。片段越小、统计越细、
能跳过的越多；代价在第 23 章量化过：100 个小片段让 `n > 49900`
读的字节少约 27 倍（5,344 对 142,008），但元数据开销和打开成本随之上升。
**片段大小是在"元数据开销"和"剪枝粒度"之间的权衡。**

### 为什么这一步可以是零 I/O

因为**列的统计被抄进了 manifest**。数据文件（`DataFile`）结构里
有一个 `column_stats: {列名: {min, max, null_count}}` 字段，
它和文件路径、行数、字节数一起写在 manifest 里。

于是查询规划阶段做剪枝时，**不需要打开任何数据文件**。
manifest 是每次查询本来就要读的那一份（第 7 章：全量快照），
统计信息是顺带的——剪枝的边际 I/O 成本是零。

真实 Lance 也是这么做的：fragment metadata 里带 column stats。
反过来说，如果统计要"查一下数据文件才知道"，这一层就完全没有意义了，
因为它省的 I/O 会被它自己花掉。

### 开关对照

```
开启剪枝: 剪掉=9 扫描行=  2,000 读取字节=   8,696 耗时=   2.40 ms
关闭剪枝: 剪掉=0 扫描行= 20,000 读取字节=  47,888 耗时=  11.09 ms
```

`Scanner` 提供了 `disable_zone_maps()` 用来做这类对照实验。
能随时关掉一个优化、并量出它的价值，比只写一个"已启用"的注释有用得多。

## 10.4 三态：只有 `False` 是安全的

`_stats_can_match` 的返回值是 **`True` / `False` / `None`** 三态，
不是布尔。原因是统计信息本身不完整，而"不知道"和"不可能"必须分开：

`True` —— 统计显示**可能**有行命中，保留（可能白扫）。
`False` —— 统计证明**不可能**有行命中，剪掉。**只有这一态允许剪枝。**
`None` —— 无法判断，保留。

实测：

```
n > 9999             -> False
later > 5            -> None
later IS NULL        -> True
later IS NOT NULL    -> True
n = 1                -> True
```

`n > 9999` 是 `False`：该片段的 `max` 是 999，永远不可能命中。
`later` 是后来 `add_columns` 加上的列，**老片段的文件里根本没有它**。

### "列在这个片段里没有数据"意味着什么

按 Lance 的读语义，schema 里有、但任何数据文件里都没有的列
**整列读作 NULL**。所以对老片段来说，`later` 的每一行都是 NULL。

任何比较和 NULL 相遇都是 UNKNOWN，都不会命中 `WHERE`。
所以理论上 `later > 5` 应该能返回 `False`，直接剪掉整个片段。

我们的 `_fragment_column_stats` 确实识别了这种情况，
给不出数据的列返回 `{"min": None, "max": None, "null_count": 物理行数}`。
但 `_range_might_match` 看到 `min`/`max` 是 `None` 就返回 `None`（不知道）。
实测：

```
_range_might_match('>', 5, {'min': None, 'max': None, 'null_count': 1000}) -> None
```

**所以文档里承诺的"后加的列可以放心剪"并没有实现**——它退成了
"保留，扫一下"。这不影响正确性（扫了之后确实一行都不返回），
但是一次没拿到的优化。函数文档写的是意图，代码实现的是保守版本，
两者不一致，而测试不会发现这种事——因为没有哪条断言会说
"这一行本该被剪掉"。

**设计课的正面版本：** 三态设计本身是对的。如果 `_stats_can_match`
返回布尔，那么"统计缺失"就必然被折叠成 `True` 或 `False` 之一，
而折叠成 `False` 就是**静默丢数据**。多一个 `None` 状态，
代价是调用点要写 `if verdict is False`，收益是"不知道"永远落在安全的一侧。

同一份保守还曾被推广到索引上，写成"只要这张表上有有效索引，
被统计判死的片段也一律保留（理由：这个谓词由索引负责）"。出发点是对的——
避免统计不准导致漏行；**但它的粒度粗到了整张表**，代价是把这个谓词
根本用不上的那些片段也保了下来。那条规则已经删掉了，为什么该删、
删掉之后省了多少，留给 10.7 节讲。

## 10.5 AND 可以部分下推，OR 不行

这个不对称性是查询引擎里最容易写错的地方，且写错的后果是**静默丢数据**。

**AND 允许部分下推。** `a = 1 AND b > 2` 里只有 `a` 的索引时，
可以只把 `a = 1` 交给索引，剩下 `b > 2` 由过滤器补上。
因为索引返回的是**超集**，再交一次精确过滤，结果仍然精确。

**OR 不允许部分下推。** `a = 1 OR b > 2` 里只要有一边翻译不出来，
整个 OR 就必须放弃。漏掉一个分支会让结果集**变小**——那就是丢行。

实测的翻译结果：

```
n = 5 AND grp = 5                  to_index_expr(n) -> RangeQuery
n = 5 OR grp = 5                   to_index_expr(n) -> None（退化成全表扫描）
n = 5 AND txt LIKE 'item-000005'   to_index_expr(n) -> RangeQuery
n = 5 OR txt LIKE 'item-000005'    to_index_expr(n) -> None（退化成全表扫描）
n > 5 AND n < 10                   to_index_expr(n) -> And
n > 5 OR n < 10                    to_index_expr(n) -> Or
```

前两行的对比就是规则本身：AND 里 `grp = 5` 答不了，只翻译 `n = 5`；
同一个子表达式放进 OR，整个谓词就变成 `None`。

放进真实表上量一次（30,000 行，只给 `a` 建 BTREE，谓词是 `a = 2 AND b = 1`）：

```
AND: 索引查询=1 扫描行=  4,286 结果=1428
OR : 索引查询=0 扫描行= 30,000 结果=12858
```

`AND` 让索引把扫描砍到 4,286 行（剩下的是过滤器的事），
`OR` 直接掉回全表 30,000 行。**同一个列、同一个索引，
只因为连接词不同，一个用上了、一个没用上。**

## 10.6 字符串列的剪枝为什么更弱

数值列的 `min`/`max` 是精确的，字符串列不是。
实测片段 0 的两份统计：

```
片段 0 里 txt 的统计: {'min': 'item-000000', 'max': 'item-001999', 'null_count': 0}
片段 0 里 n 的统计:   {'min': 0.0, 'max': 1999.0, 'null_count': 0}
```

这一列是定长格式的，所以统计看起来很准，剪枝效果和数值列一样：

```
txt = 'item-015000'      剪掉=9/10 读=  64,698 结果=1
txt < 'item-002000'      剪掉=9/10 读=  62,442 结果=2000
n = 15000                剪掉=9/10 读=   8,696 结果=1
```

但同样的谓词，字符串读了 64,698 字节，数值只读 8,696——
**剪枝效果一样，解码成本差 7 倍**，因为字符串的页更大。

真实的字符串列情况更糟，有三个独立原因：

**截断。** 真实 Lance 会把长字符串的统计截断保存，否则每个片段的
manifest 都要拖着一份完整的最长字符串。截断之后 `min`/`max` 变成
"实际值的一个下界/上界"，仍然安全（可能多保留，不会错误剪掉），
但筛不掉的东西变多了。

**排序语义。** 字符串比较是字节序（UTF-8 下等价于码点序），
而用户心里的"字母序"是 collation。`'Z' < 'a'` 在字节序下成立、
在大小写不敏感的字母序下不成立。用字节序做的剪枝是安全的
（它是一个一致的偏序），但"看起来更聪明的剪枝"反而容易出错。

**编码。** 变长编码让"值域"这个概念本身变模糊——
一个 2 字节的 UTF-8 序列和一个 1 字节的序列怎么比较，
取决于语言层面的规则而不是格式层面的。

**结论：字符串列能剪，但剪得比数值列粗，而且解码贵。**
真正靠字符串过滤的场景，应该用倒排索引 / ngram / FM 索引
（它们把"扫字符串"变成"查 token 字典"），而不是指望 min/max。

## 10.7 第三层：索引下推

前三节里的操作都是"少读"，这一层是**把扫描变成取行**。
标量索引（BTREE / BITMAP / LABEL_LIST / ZONEMAP）拿到的不是
一棵表达式树，而是 `ScalarIndexExpr`：区间、集合、与或非的代数。
索引的职责就是**把谓词翻译成这个代数，答不了就返回 `None`**。

实测（20,000 行、10 片段的表，只读 `n` 列）：

```
无索引 n = 12345      扫描行=  2,000 读=    8,696 索引查询=0 结果=1
有索引 n = 12345      扫描行=      1 读=  617,823 索引查询=1 结果=1
```

**扫描行从 2,000 降到 1，但读取字节从 8,696 涨到 617,823——乘以 71。**

这不是打错字，但它也不是"索引很慢"的证据——**它量的是冷缓存**。
索引在第一次用到时要从头读一遍，20,000 行的 BTREE 索引落盘是
**609,127 字节**，比它索引的那列数据（43,540 字节）大 14 倍，
所以第一次点查的读取量里几乎全是索引。

**这里有两个必须说清的点，否则这一节会被读反。**

第一，**索引是会被缓存的**。`Dataset.load_index` 的签名是
`load_index(name, *, use_cache=True)`，默认带一个**进程内**缓存，
key 是 `(uri, 索引名, 索引版本, 索引文件清单)`；索引文件不可变，
所以版本一改 key 就变了，旧条目自然读不到。`examples/verify/ch10_index_cache.py`
把冷热两次并排打出来，可以看到缓存省的字节数**恰好等于索引文件的合计大小**：

```
无索引                        读=   3,288,500  扫描行=20,000
有索引 · 第 1 次（冷）             读=   3,239,927  扫描行=     1
有索引 · 第 2 次（热）             读=   2,630,800  扫描行=     1
清空缓存之后                     读=   3,239,927  扫描行=     1

冷 − 热            = 609,127 字节
索引落盘合计        = 609,127 字节
两者相等           = True
```

所以上面那句"每次查询都要把索引完整加载一次"**是错的**，正确说法是
"每个进程、每个索引版本，只加载一次"。但第一次永远躲不掉——
**这正是冷启动问题的形状**：服务刚起来、或者索引刚重建完的
那批查询会付出这个代价，之后就好了。

**读这段输出时有一个坑，先说在前面**：上面这个脚本用的是
**一整张单片段**的表（20,000 行全在一个 `.lance` 文件里，
328,850 字节），所以"无索引"那一行的 3,288,500 字节
**是整份文件被反复读出来的结果**，不是"读一列"的正常成本——
它和本节开头那张表的 8,696 字节**不是同一种表、不能横着比**。
这个脚本要证明的**只是"冷 − 热 = 索引大小"这一个恒等式**，
绝对值它不管。**一个脚本只为一件事作证**，别从它身上顺手取别的结论——
本节前面那张表（8,696 / 617,823）是 `examples/verify/ch10_pushdown.py`
的 10 片段表，那才是"投影下推省了多少"的正确对照。

第二，**索引元数据自报的 `size_bytes` 不等于落盘字节数**，两者差近一倍，
所以引用索引大小时不能直接抄 `list_indices()[0].size_bytes`。
上面这个索引自报 **1,161,216** 字节，而它的 5 个文件加起来只有
**609,127** 字节（`ch10_index_cache.py` 会把逐个文件的大小也打出来）。
按自报的数字算会得到"每行 58 字节"，按真实落盘算是"每行 30 字节"——
差出来的那一倍足以让"建索引值不值"的判断翻向另一边。

换一张更接近真实的表（200,000 行、宽行、点查 `id = 123456`），
差别会更夸张：

```
  表: 200,000 行 10 片段 1,849,655 字节
  无索引    点查: 扫描行= 20,000 读=    28,205 耗时=  13.84 ms
  BTREE  点查: 扫描行=      1 读= 6,305,403 耗时= 765.90 ms
  BTREE 索引文件大小 = 11612864 字节
```

索引自报 11.6 MB，是整张表（1.85 MB）的 **6.3 倍**；
一次**冷**点查要读 6.3 MB、花将近一秒，无索引的路径反而快几十倍。

**这不是"索引没用"，而是"这个索引的实现把成本挪到了一个不该挪的地方"。**
索引的价值公式是：

```
索引赢 ⟺ 数据侧省下的扫描 > 索引侧付出的读取
```

对小表、宽表、以及"每次加载都要读整个索引文件"的实现来说，
右边的项会压过左边。真实系统的应对是三件事：

**索引要小。** 存 key 的压缩形式（前缀截断、字典编码），
而不是原样存每一行的 key 加行号。上面那 30 字节/行里，
`row_offsets.npy` 和 `row_ids.npy` 各占 8 字节，`keys.json`
摊到每行是 6.4 字节——**一半的空间花在"这行是谁"上，不在"这行的值是什么"上**。

**索引要能随机访问。** 真实 Lance 的索引是分页的
（`btree_page_lookup.lance` 之类的页查找表），
`col = 5` 只需要读定位到的那几页，而不是整个索引。
本实现不满足这一条：`load_index` 一次把 5 个文件全读进内存，
没有任何"只读需要的部分"的余地。

**索引缓存要有上限。** 本实现**已经有缓存**（见上面那段），
所以这一条不是"缺缓存"，而是"缓存是不封口的"：
`_INDEX_CACHE` 是一个普通 dict，没有 LRU、没有字节数上限，
条目只在索引被重写或显式 `clear_index_cache()` 时消失。
真实 Lance 把它做成了一个**有容量**的组件（老接口是
`open_table(index_cache_size=...)`，0.40 上已弃用，改成
`Session(index_cache_size_bytes=...)`），因为一个几十万行的 IVF_PQ
索引就是几百 MB，无上限地缓存等于把内存交给使用模式去决定。
**本实现没有量过"缓存无上限在长跑进程里会涨到多少"**，所以这一条
只能定性：真实系统在这里有旋钮，我们这里没有。

所以正确的表述不是"给过滤列建索引就一定快"，而是：
**索引是拿"固定的索引读取成本"换"随表大小增长的扫描成本"，
交叉点取决于索引相对表的大小与缓存的命中率。** 表越大、索引越小、
缓存越有效，索引越赢；反之（表小、行宽、缓存命中不了）就是白花。
**判断一个具体场景时，先用 `ch10_index_cache.py` 把冷热两次都量出来**——
只量冷的话，你会把"冷启动成本"误读成"索引的固有成本"。

**拿到掩码还不够：掩码必须参与片段裁剪。** 索引回答的是"哪些行命中"，
如果扫描器只在片段内部拿这个掩码过滤、却仍然把每个片段都打开读一遍，
那些"一行都不命中"的片段就白读了。实测过的形状是：一个
`WHERE n BETWEEN 100 AND 200` 在 5 万行、25 个片段的表上只命中 1 个片段里的 101 行，
但不裁片段时扫描器会打开全部 25 个片段、读 1.5 MB——**比不建索引、
靠统计剪枝还慢 60 倍**。`Scanner._run` 现在做两件事：索引掩码在某个片段上
"一行都不剩"就把整个片段跳过（这个数记在 `fragments_pruned_by_index` 里），
而且不再因为"这个谓词有索引可用"就强制保留所有片段。回归测试是
`tests/test_regressions.py` 里的 `test_index_mask_also_skips_whole_fragments`。

### 一个曾经把剪枝也弄丢的粒度 bug

这一层的保守判断很容易写粗。早期版本里有一句"只要表上存在**任何一个**
有效索引，被统计判定为不可能命中的片段也保留"——粒度是整张表，
而不是"这个片段、这个谓词"。后果是这样的：

```
txt = 'item-015000'      剪掉=9/10 读=  64,698 结果=1      （无索引时）
给 n 建 BTREE 后，同一个 txt 谓词：剪掉=0/10 扫描片段=10 读=354,703
```

索引建在 `n` 上、谓词是 `txt` 的，两者毫无关系，可 zone map 剪枝从 9/10
掉到 0/10，读取量涨了 5.5 倍。这个判断现在没有了：剪枝只问"统计能不能证明
不可能命中"，索引能不能回答谓词由 `_index_mask` 那条路径单独处理，两者互不干扰。
实测现在给 `n` 建完 BTREE 再跑同一个 `txt` 谓词，剪枝仍是 9/10、读取量 64,698，
和没有索引时一致。它值得一条专门的回归测试钉住
（`tests/test_regressions.py` 里的 `test_unrelated_index_does_not_disable_zone_map_pruning`）。

**这就是那种测试很难抓到的问题：结果仍然正确，只是慢了 5 倍。**

## 10.8 第四层：延迟物化

前三层都在减少"读多少片段、读多少行"，这一层减少的是
**读多少列的字节**。做法的名字就说清了：先只读过滤用的列，
算出掩码，**再只把活下来的行需要的投影列读回来**。

实测（20,000 行单片段表，投影 4 列，过滤列是 `n`）：

```
n >= 0      延迟物化 读=  369,340 省行=      0 | 关掉 读=  689,392 | 结果=20000
n > 15000   延迟物化 读=  224,829 省行= 45,003 | 关掉 读=  544,881 | 结果=4999
n > 19500   延迟物化 读=   80,318 省行= 58,503 | 关掉 读=  400,370 | 结果=499
```

`n > 19500` 时读取量从 400,370 降到 80,318，**省掉 80%**。
命中率越低，省得越多——这正是列存最大的杀招。

`n >= 0` 那一行的 `省行=0` 很说明问题：**筛选条件一个都不淘汰时，
延迟物化没有任何可省的东西**，它只是白多跑一遍读路径。
所以它不是一个"永远开着总没错"的开关，收益正比于过滤的**选择率**
（第 11 章会讲扫描器怎么估这个数）。

还有一条边界：**当投影列本身就是过滤列时，延迟物化无事可做。**
实测 `columns=["n"], filter="n > 19500"`：

```
投影列 = 过滤列（只读 n）时：读=32,778 省行=0
```

这也是"延迟物化省下了多少"这个统计量在真实系统里经常显示 0 的原因——
它显示的是**可省的**行数，而不是"有没有走这条路"。

### 统计量是怎么算的

```python
self.stats.late_materialization_saved_rows += int(
    (~mask).sum() * max(0, len(projection) - len(set(filter_cols) & set(projection)))
)
```

被过滤掉的行数 × 投影列里"纯投影、不参与过滤"的列数。
所以 `省行=58,503` 的含义是"省下了 58,503 行 × 3 列的读取"。
这个数字是估算（行数精确，字节数要乘以列的宽度），
但它足够回答"这一层有没有生效"。

## 10.9 行范围下推

这一层在上一章被删除打破了，这里补上它的机制。

扫描是**按片段顺序**做的，所以一个片段里要读的物理偏移
绝大多数时候就是一段**连续区间**。这时可以直接告诉 reader
"只读第 lo~hi 行"，让它跳过不相交的页：

```python
contiguous = bool(len(offsets) == 1 or np.all(np.diff(offsets) == 1))
if contiguous:
    return ds.read_fragment(frag, columns=cols, row_range=(lo, hi), include_deleted=True)
batch = ds.read_fragment(frag, columns=cols, include_deleted=True)
return batch.take(offsets)
```

两条路的差别是"少读页"和"读整段再挑"。实测（20,000 行单片段）：

```
无删除（偏移连续）                读取字节=  21,203 往返= 6 扫描行= 20,000 逻辑行=20,000
删掉一半（偏移碎裂）               读取字节=  31,235 往返= 7 扫描行= 10,000 逻辑行=10,000
只删前段（偏移连续）               读取字节=  24,625 往返= 5 扫描行=    100 逻辑行=   100
```

换成宽列（`payload` 长 50~250 字节），差距更明显：

```
窄表 无删除                   读取字节= 114,751 往返= 6 扫描行= 20,000 逻辑行=20,000
窄表 只删前段                  读取字节=  56,731 往返= 5 扫描行=    100 逻辑行=   100
```

只有 100 行存活，读 56,731 字节——**不是 100 行的字节数**，
而是"覆盖这 100 行的那些页"的字节数。这就是"页粒度"的代价，
也是为什么这一层的收益有个上限：页大小决定了下推能精确到多细。
省下的是**整页**，不是**整行**。

这里也能看到删除为什么破坏它：删掉一半之后存活的偏移是
1、3、5、…（不连续），`np.all(np.diff(offsets) == 1)` 为假，
直接掉进 `take` 分支，整段读进来——**10,000 行读得比 20,000 行还多**
（31,235 对 21,203），因为连续的 20,000 行走的是"一次读一大段"，
碎裂的 10,000 行要走"读全量 + 挑"。

## 10.10 过滤器求值的向量化

最后一层不是"少读"，是"少算"。

谓词的求值必须**在整列上算**，不能逐行 Python。
`evaluate_predicate(expr, batch)` 返回的是长度等于行数的
numpy 布尔掩码，直接喂给 `RecordBatch.filter()`。

实测 20 万行，同一条逻辑的两种写法（多次运行取最小值；
绝对的毫秒数随机器负载浮动，倍数是稳定的）：

```
纯数值 n % 7 = 0                numpy 3.0~3.6 ms | Python 5.6~6.8 ms | 比值 ~1.9x
算术 n * 3 + 1 < 100            numpy 3.5~3.6 ms | Python 6.6~6.8 ms | 比值 ~1.9x
纯字符串 starts_with(s, 'item-1')  numpy 93~100 ms | Python 6.5~7.2 ms | 比值 ~0.07x
```

数值路径 numpy 快约 1.9 倍。但**不是所有类型都赢**：

字符串上 numpy **慢约 14 倍**。原因拆开看（20 万行）：

```
object 数组 -> 定宽 unicode:     ~10 ms
然后 np.char.startswith:        ~9~15 ms
纯 Python startswith:           ~14 ms
```

`np.char.*` 家族要求定宽 unicode 数组，所以每次调用都要先把
Python 对象数组转一遍。转一次 10 ms、算一遍 15 ms，
两项加起来才 25 ms——**可实测是 93 ms 以上**，多出来的时间在别处。

第 11 章会讲到那个别处：`starts_with` / `contains` 这类 SQL 函数
在实现里走的是**逐行 Python 循环**，而 `LIKE 'item-1%'`
走的是 numpy 快速路径。同一个语义，两条实现，差 3~5 倍：

```
s LIKE 'item-1%'               24~35 ms  命中 111,111
starts_with(s, 'item-1')      100~135 ms  命中 111,111
s LIKE '%1%'                   25~36 ms  命中 140,951
contains(s, '1')               79~103 ms  命中 140,951
```

所以"向量化"不是一个形容词，是一份**逐算子的清单**：
要能说出哪些算子真的在 numpy 上算、哪些退回了 Python 循环。
只看"我们用了 numpy"是看不出这件事的。

## 10.11 优化前后：把四层下推逐项打开

同一张无索引的 10 片段表，同一批查询，逐项开关四层下推。**扫描行和读取字节
是确定值**（同一份数据、同一份 manifest，跑多少次都一样）；**耗时是单次测量**，
随机器负载波动几十个百分点，所以只用来读量级，不用来读百分比。

起点是**全表全列、不带谓词**：扫描 20,000 行、读 383,224 字节、52.05 ms。
**只加列投影下推**（只读 `n` 列）之后扫描行一行不少（还是 20,000），
读取量掉到 43,540 字节、5.55 ms——省的是字节，不是行。**再叠上片段剪枝**
（`n > 19000`，只读 `n`）：扫描行 2,000、读取 8,696 字节、1.12 ms。
从起点走到这里，383,224 → 8,696 是 **44 倍**，而且是两层乘出来的：
投影先把 383,224 压到 43,540（8.8 倍），剪枝再把 43,540 压到 8,696（5.0 倍），
合起来 8.8 × 5.0 ≈ 44。

**把同一条查询的 zone map 关掉**，立刻回到 20,000 行、47,888 字节、9.53 ms。
这一行的作用不是"优化前"，它是**证明**：唯一变的就是剪没剪片段，
而读取量差了 5.5 倍。

换一层看延迟物化。**`n > 19000`、投影 4 列、开着延迟物化**：扫描 2,000 行、
读 42,784 字节、3.69 ms；**关掉延迟物化**，同一个查询读 76,872 字节、4.35 ms。
这里省下的不是行数，是投影列的字节。

最后两行是反例。**`n = 12345`、只读 `n`、无索引**：扫描 2,000 行、
读 8,696 字节、1.01 ms。**同一个查询、给 `n` 建上 BTREE**：扫描行被压到 1 行，
但读取量变成 617,823 字节、46.49 ms——**扫描行少了三个数量级，
字节却乘以 71，最终慢了约 46 倍。** "少读"不总是赢，因为这一层的成本项
（把整个索引读一遍）和收益项（少扫的那些行）根本不在同一个尺度上。

这一串数字里最该记住的不是最大那个，而是**收益来自哪一层、
以及哪一层会反过来咬人**。

## 10.12 四个实测出来的问题，以及它们现在是什么状态

这一节集中记一下在跑数字的过程中撞到的四个东西。它们都不是"结果算错了"，
而是"看起来对、实际不对"或"慢了很多但没人发现"。**四个现在都已经修掉，
每一个都有一条回归测试钉着**（`tests/test_regressions.py`），所以本章的
实测数字里已经看不到它们了——下面保留当时的输出，是因为每个都对应一类
会反复出现的错误形状，比"结论"本身更值得记。

**一、`BETWEEN` 会被统计剪枝整个吃掉。** 四个里唯一一个**静默返回错误结果**的：

```
n BETWEEN 1500 AND 1510      开 zone map=   0  关 zone map=  11
n >= 1500 AND n <= 1510      开 zone map=  11  关 zone map=  11
count_rows('n BETWEEN 1500 AND 1510') = 0
n BETWEEN 100 AND 200 -> 0  应为 101；关剪枝 -> 101
```

`BETWEEN` 在 10 个片段上全都返回 0 行，而等价的 `>= AND <=`
写法毫发无损。单片段表也复现，所以不是片段粒度的问题。
根因在 `_stats_can_match` 的 `Between` 分支里那行
`not (expr.high < lo or expr.low > hi)`：`expr.low` / `expr.high` 是
**AST 节点（`Literal`）**，不是 Python 值。而 `Expr` 重载了 `__lt__` / `__gt__`
用来**构造比较节点**——所以 `expr.high < lo` 不返回 `False`，
它返回一个 `BinaryOp` 对象，**在布尔上下文里永远为真**。
于是 `not (True or ...)` 恒等于 `False`，每一个片段都被判成"不可能命中"。

修法是先解出字面量的值再比（`_literal_value(expr.high)`，
函数注释里专门写了这件事）。**同一个形状还出现过第二次**：负数字面量被解析成
`UnaryOp("-", Literal(1))`，直接读 `node.value` 会拿到 `None`，
于是所有带负数的范围条件都白白退化成全表扫描——现在统一走同一个解值函数。

一个更隐蔽的点在这里：`delete("n BETWEEN 0 AND 499")` 当时删掉的是**正确**的
500 行。因为删除走 `_predicate_mask`（直接对整表求值，不经过扫描器的剪枝），
而查询走 `scanner`。**同一个语义在两个代码路径上结果不一致**——
一个正确的实现和一个错误的实现并存，比两个都错更难查。

**设计课：** 运算符重载是给用户写查询用的便利，
但引擎内部的代码绝不能碰它——**引擎看到的是 AST，不是表达式**。
凡是"拿 AST 节点参与 Python 比较"的地方，都是同一个 bug 换了个形状。

**二、`explain(analyze=True)` 会把片段数报成两倍。**

```
analyze() 一次: 9 /10
explain(analyze=True) 报告: ['被 zone map 剪掉的片段: 18']
```

因为 `explain(analyze=True)` 先把查询真跑一遍（填了 10 条剪枝记录），
然后 `build_plan()` 为了生成计划又跑了一次 `_prune_fragments()`，
而 `self._pruned` 和 `self.stats.fragments_pruned_by_stats` 都是**累加**的。
于是计划里同一个片段被打印两遍，计数器是 18/10。危害恰好落在最要命的地方：
`explain(analyze=True)` 是**用户唯一能信任的"到底下推了没有"的工具**，
而这个工具在 `analyze=True` 时给出的数字是错的。
（`analyze()` 单独调用一直是准的，`explain(analyze=False)` 因为没跑数据，
也只有计划没有实测段。）

修法是两条：`_prune_fragments` 开头先把 `self._pruned` 和两个计数器**清零再累加**，
`build_plan` 在已经扫过一遍时**复用**已有的 `self._pruned` 而不是重跑。
现在同一个查询 `explain(analyze=True)` 报出来的剪枝数是 9，
计划里的片段记录正好 10 条。

**三、`Scanner.stats.bytes_read` 通过连接恒为 0。** 见 10.1 节。
这条已经修掉：`_PrefixedStore` 构造时把 `stats` 指回内层 store。

**四、给任意一列建索引会关掉整张表的 zone map 剪枝。** 见 10.7 节。
这条也修掉了：剪枝的判断里不再有"这张表有没有索引"这一项。

四个问题的共同点是：**它们都不影响"正确结果"（除了第一个），
所以测试全绿。** 第 23 章已经记过一次"全绿 ≠ 正确"，
这里补上另一半：**全绿也 ≠ 最优**。一个引擎性能的一半藏在
"本该省而没省"的地方，而那部分只有量出来才看得见。

## 10.13 这几层下推到今天为止的边界

上面讲的四层都是**已经做到**的。这一节把"没做到的那几层"摊开——
它们同样是"能不能让下游少读字节"的问题，只是答案在这台实现里是否定的，
或者答案的粒度比读者以为的粗。

### `limit` 没有下推，也没有提前终止

`Scanner` 认 `limit`（`with_limit` / `explain` 里的 `LimitExec`），
但它是**在输出边界上截断的**：`to_batches` 先把 `_run()` 整个跑完、
拿到全部结果，再按 limit 切片。也就是说**没有任何一层会因为"已经凑够 k 行"而提前停止**。
实测（10 片段、20,000 行的表，只读 `n` 列）：

```
只读 n 列，无 limit     读取字节=  43,540  扫描行= 20,000  往返= 40  结果行= 20,000
只读 n 列，limit 1      读取字节=  43,540  扫描行= 20,000  往返= 40  结果行=      1
只读 n 列，limit 100    读取字节=  43,540  扫描行= 20,000  往返= 40  结果行=    100
投影 4 列，limit 1      读取字节= 383,224  扫描行= 20,000  往返= 70  结果行=      1
```

只读 `n` 列的那三行，读取字节、扫描行、往返次数**一模一样**，只有产出的行数不同；
换成 4 列投影也一样——`limit 1` 和"全都要"读的字节分毫不差。
省下的是**结果行**，不是**读取量**。（带上 `filter='n > 19000'` 再取 `limit 1`
会小很多，但那是 zone map 的功劳，不是 limit 的——它照样把那个片段整个扫了一遍。）

这就是 top-k 下推要解决的问题：如果谓词是 `ORDER BY key LIMIT k` 这种形状，
真实系统会把 `k` 一路传到扫描器，让它"凑够 k 行就停"（配合按 key 排好序的数据
甚至能只读几个片段）。本实现的扫描器已经是惰性产出的**结构**（`_run` 是个生成器），
但 `to_batches` 里那句 `results = list(self._run())` 把它一次性拉平了——
把 limit 真正下推，改的就是这一句的语义和"谁来决定停"的问题。

### 片段级统计，不是块级统计

第 10 章这一层的统计（`DataFile.column_stats`）挂在**片段**上：一个 2,000 行的片段
一份 `min` / `max`。第 18 章 §18.5 里的 `ZONEMAP` 索引挂的是**块**：
`DEFAULT_PAGE_SIZE = 1024`，每 1,024 行一份统计，粒度细一倍以上。两者的关系是
**同一件事的两个粒度**：片段级统计抄在 manifest 里，剪枝的边际 I/O 是零；
块级统计要么落在索引文件里、要么落在页头，精度更高但"查它"本身有成本。
数据越有序，两个粒度的差距越小；数据随机，两级都失效。

写文件的时候本实现**没有**按块写 min/max 到页头（真实 Lance 有），
所以块级剪枝只能靠显式建一个 `ZONEMAP` 索引拿到，而不是像真实 Lance 那样
"什么都不建也有"。

### 没有布隆过滤器，也没有字典剪枝

真实 Lance 在数据跳过上还有两层本实现没复刻的：

**布隆过滤器。** 高基数列上的等值查询（`col = 某个值`）用位数组先判断
"这一块**肯定没有**这个值"，比 min/max 更锋利——min/max 对高基数随机数据
几乎没有区分度，布隆过滤器的假阳性率是可控的。本实现里搜不到任何 bloom 实现。

**字典编码的页级剪枝。** 低基数列走字典编码之后，一个页里只有少数几个字典下标。
如果页头记下"这一页的字典下标集合"，等值查询就能只比较这份小集合。
本实现的字典编码（`mini_lancedb/encoding/codecs.py` 的 `DictionaryNumericEncoder` /
`DictionaryByteEncoder`）只解决**空间**问题，不参与跳过决策。

顺便说清本实现里唯一"页级"的跳过是什么：`read_fragment(row_range=...)` 会跳过
与行区间不相交的页（`pages_skipped`），但那是**按行位置**跳，不涉及值域——
真正由值域决定的页级剪枝只有 `ZONEMAP` 索引那一处。

### 嵌套列上，谓词只能靠函数

`fixed_size_list` 的向量列和 `struct` 列都**不参与**前面三层：
`extract_zone_map_predicate` 只认"列 op 常量"、`IN`、`BETWEEN`，
`to_index_expr` 只认同一类形状，所以一个落在嵌套子列上的条件既剪不了片段、
也吃不上标量索引，只能整片段扫、逐行算。

更要紧的是**写法的限制**：SQL 文本里没有下标语法。`vec[0] > 2` 和 `st['k'] > 2`
都会在解析阶段报 `表达式解析完了但还剩 '[' 没处理`——分词器认 `[`，
但递归下降的那一层没有"后缀下标"这个产生式。能用的入口是函数：
`vec[0]` 在 **Python API** 里可以写（`col("vec")[0]` 走 `Expr.__getitem__`，
编译成 `list_extract(vec, 0)`），字符串里则必须显式写
`list_extract(vec, 0) > 2` 或 `array_contains(vec, 3.0)`。
第 18 章 §18.3 的 `LABEL_LIST` 索引就是为 `array_contains` 这类谓词准备的——
数组值的过滤走的是那条路，不是 min/max。

### 伪列既不能被过滤，也不能被统计

`_rowid`、`_distance`、`_score` 都不是表达式引擎里的列（第 11 章 §11.10 讲了它们
是怎么被挂上去的），所以拿它们当谓词会在**解析阶段**就失败：
`WHERE _distance < 0.5` 抛 `PlanError: 没有名为 '_distance' 的列`。
它们也因此不可能出现在统计里——没有 `min` / `max`、没有索引、没有剪枝。
要按距离筛，用的是查询层的 `distance_range(lo, hi)`；要按 `_rowid` 取行，
用的是 `Scanner.with_row_id()` 把它**取出来**，而不是把它写进 `WHERE`。

### 统计会不会过期？这一层是安全的，但理由要说清

min/max 抄进 manifest 之后，删除和更新**不会**让剪枝跳过不该跳的片段。
原因是这台实现里统计贴的是**不可变的数据文件**：删一行只是写一个删除文件
（物理行还在），更新一行是"删旧行 + 追加到新片段"。所以旧片段的 min/max
永远是它**当前物理内容**的准确统计，而物理内容只增不减——
统计相对于"活着的行"永远是**超集**，而超集只会让它少剪、不会让它误剪。

实测可以确认这一点：删掉 `n > 19000` 的那些行（也就是片段 9 的最大值所在的行）之后，
同一条查询仍然剪掉 9/10 个片段、仍然打开片段 9、返回 0 行——
片段 9 的统计还是 `{'min': 18000.0, 'max': 19999.0}`。**这里不会出现静默错误，
代价只是白扫一个片段。** 反过来说，什么时候这条推理会破？
当统计和物理内容**不再一一对应**的时候——比如"统计在 manifest 里被就地改、
而文件没重写"，或者"往一个已经写过统计的文件里再塞数据"。
前者的形状是一个静默错误：统计说 max 是 19999、文件里其实有 20001，
于是所有 `n > 19999` 的查询都少一个片段。**所以"统计跟着不可变文件走"
不是一句实现细节，它是这一层正确性的前提。**

### 全文检索是另一条路，它和谓词的关系是 prefilter

`LIKE '%abc%'` 这种子串谓词吃不上 BTREE（第 11 章 §11.7 讲过原因），
该用的是 NGRAM 索引（第 18 章 §18.4）或者倒排 / FTS。倒排索引不回答
"行号集合"意义上的谓词，它回答的是"哪些文档包含这些 token"，所以它不在这四层里，
是并列的第五种入口。但两者会碰头：一次查询同时带标量谓词和检索词时，
标量谓词可以算出一个掩码、**当作 prefilter 传给倒排索引的排序**，
让不满足谓词的文档根本不参与 top-k 竞争。这就是 `Query.where(..., prefilter=True)`
在做的事，顺序问题（先过滤还是先取 top-k）在第 18 章 §18.8 展开。

## 10.14 小结

**下推只回答一个问题：这个算子能不能让下游少读一点字节？**

**列投影下推**省的是字节不是行：只读一列 vs 全列是 43,540 对 383,224（8.8 倍）。
**片段级 zone map 剪枝**可以是零 I/O，因为列统计被抄进了 manifest——
`n > 19000` 在 10 个片段上剪掉 9 个，读取量 8,696，关掉剪枝的同一条查询是 47,888。
**索引下推**把扫描变成取行（2,000 行 → 1 行），但付出的是索引自身的读取
（617,823 字节，是同一条查询的 71 倍）。**延迟物化**的收益正比于过滤选择率
（命中 499/20,000 时省 80%，全命中时省 0）。

**统计剪枝必须是三态。** `True` 保留、`False` 剪掉、`None` 保留——
只有 `False` 允许剪枝。否则"统计缺失"会被折叠成"不可能命中"，
那就是静默丢数据。

**AND 可以部分下推，OR 不行。** AND 返回超集、下游过滤补齐仍然精确；
OR 漏一个分支就让结果变小。

**字符串列的剪枝更弱、解码更贵**（同谓词 64,698 对 8,696 字节）。
真正的字符串过滤要靠倒排 / ngram / FM 索引。

**行范围下推的前提是偏移连续**，而删除会破坏它。
省下的粒度是**页**而不是行，所以收益有上限。
删掉一半的表（10,000 行、偏移碎裂）读得比不删（20,000 行、偏移连续）还多。

**"用了 numpy"不等于快。** 数值谓词快约 1.9 倍，字符串谓词慢约 14 倍，
因为 `np.char.*` 要求定宽数组、每次都要转一遍——
真正的原因还要再往里一层看（第 11 章 §11.9）。

**边界和做到的事一样重要。** `limit` 只在输出边界截断、**没有提前终止**
（`limit 1` 和全表读一样的字节）；剪枝的统计是**片段级**的，
块级要显式建 `ZONEMAP` 索引（第 18 章 §18.5）；没有布隆过滤器、
没有字典剪枝；嵌套列只能靠 `array_contains` / `list_extract` 这类函数过滤，
SQL 文本里的 `vec[0]` 根本解析不过；`_distance` / `_rowid` 这类伪列
既不能进 `WHERE`、也进不了统计。**统计不会过期**，因为 min/max 贴的是
不可变文件、删除和更新只做追加——统计相对活着的行永远是超集。

**四个实测问题说明"测试全绿"既不等于正确，也不等于最优。**
`BETWEEN` 曾经静默返回 0 行；`explain(analyze=True)` 曾把片段数报成两倍、
又重跑一遍剪枝；计量外壳曾吞掉字节数；建一个索引曾关掉整张表的统计剪枝。
四个都修好了，各有一条回归测试在 `tests/test_regressions.py`。

下一章把这四层下面的那个东西拆开：谓词从一行 SQL 字符串，
怎么变成一棵能改写的树、一个能喂给索引的代数、和一段在整列上跑的向量化代码。
