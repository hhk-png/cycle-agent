# 第 6 章　存储抽象与对象存储

上一章讲的是表和列的语义。这一章往下走一层：这些数据文件和 manifest
究竟被放在什么东西上，以及那个东西不是本地磁盘时会发生什么。

LanceDB 最反直觉的一个设计决定是：**它不假设自己有本地磁盘。**

这句话不是营销措辞，而是一条架构约束。整个数据集被当成
"一堆按 key 寻址的不可变对象"，读写全部经过一个最小接口。
本地的 `./mydb.lance` 目录和 `s3://bucket/mydb.lance` 走的是**同一条代码路径**。
好处是同一份代码在笔记本上开发、在云上跑；代价是本地也要忍受对象存储的所有坏脾气。

## 6.1 七个方法的接口，和它的边界

接口只有这么几个方法：`get` / `get_range` / `put` / `put_if_not_exists` /
`delete` / `head` / `list`。

实测我们实现里真正要求子类实现的方法：

```
=== 接口面：ObjectStore 要求实现哪些方法 ===
 抽象方法: ['delete', 'get', 'get_range', 'head', 'list', 'put']
 抽象方法数: 6
 全部公开方法: ['child_paths', 'delete', 'delete_prefix', 'exists', 'get', 'get_range',
   'get_text', 'head', 'join', 'list', 'put', 'put_if_not_exists', 'put_text',
   'size', 'supports_conditional_put']
```

**只有 6 个是抽象的，不是 7 个。** 差的那个是 `put_if_not_exists` ——
它有一个基于 `head` + `put` 的默认实现，而那个默认实现**不是原子的**：

```python
def put_if_not_exists(self, path: str, data: bytes) -> Optional[str]:
    if self.head(path) is not None:
        return None
    return self.put(path, data)
```

两次 RPC 之间的窗口里，别人可能刚好写进去，而 `put` 会无条件覆盖。
所以真正的条件写必须由子类用存储的原生能力实现。这是一处很容易看漏的设计：
"接口有默认实现"和"接口有这个能力"是两件事。

`supports_conditional_put` 这个类属性就是用来暴露这个区别的。
没有条件写的存储，"理论上还是能跑 LanceDB"，但只能靠外部锁。

### 6.1.1 "凡是能提供这 7 个方法的存储都能跑 LanceDB"，这句话的边界在哪

这句话成立的部分是真的：**Lance 的读路径不要求任何超出这 7 个方法的能力**。
打开表要 `get` manifest（或者先 `get` 一个 hint 再 `head` 验证），
读数据要 `get_range`，列目录要 `list`。第 3 章讲过文件格式在尾部放了一个
40 字节定长 footer，读取者只要一次范围读就知道整张表在哪 ——
这个设计和"只给 `get_range`"是配套的。

但把它当成无限承诺就会踩坑。三条边界值得写下来：

**第一，条件写不是所有存储都真给。** S3 和 S3 Express 现在原生支持原子写，
LanceDB 官方文档的说法是"**LanceDB handles concurrent writers against the same
table out-of-the-box — no external commit coordinator is required**"。
但这不自动推广到所有 S3 兼容实现。真实 Lance 里有一个专门的
commit handler 叫 `TencentCosCommitHandler`，原因就是腾讯 COS
"在**桶曾经开过版本控制**后会静默忽略 put-if-not-exists 头"，
所以它默认直接报 `not_supported`，而不是假装成功。

**第二，`list` 的语义差异比想象中大。** 对象存储的 `list` 是按 key 有序的扁平命名空间，
没有"目录"，返回的是元数据不是内容，而且**可能最终一致**。
任何"靠 list 判断有哪些数据文件"的逻辑都会在云上出问题（下一节展开）。

**第三，延迟是接口合同的一部分。** 7 个方法里没有一个能表达"这个调用可能要 800 毫秒"。

## 6.2 三种实现

### 6.2.1 内存实现

`InMemoryStore` 就是一个 `dict[str, bytes]` 加一把可重入锁，测试的默认后端。
它把 `put_if_not_exists` 做成真正的原子操作（检查与写入在同一把锁里），
所以它其实是三种实现里**语义最强**的一个 —— 这一点在写测试时很容易忘：
内存里跑通的并发测试，不一定能证明 S3 上也跑得通。

### 6.2.2 本地文件实现：刻意不做目录语义

`LocalFileStore` 是本章最值得细看的部分，因为它做的事情是"**假扮对象存储**"。

官方文档有一个五档延迟表（对象存储 / 文件存储 / 第三方 / 块存储 / 本地盘），
本地盘被描述为"最快；p95 常 <10ms"。
既然本地盘这么快，为什么不干脆用它原生语义？因为**本地和云上的行为必须一致**，
否则同一份代码在两种环境里会表现出不同的正确性。
我们的代码里把这个取舍概括成 "local-first, cloud-ready"（**这是本项目自己的概括；
我们没有在 Lance/LanceDB 的官方文档里找到这个短语，未经确认**）。

具体做了三件事：

**key 一律用 `/` 拼接，哪怕在 Windows 上。**

```
  join('a','b/c','d') = 'a/b/c/d'
  join('', 'x', None) = 'x'
```

`join()` 的注释直接点明动机："如果本地实现用 `os.sep`，
同一份数据在 Windows 上和 Linux 上的 key 就不一样，manifest 里记录的路径会失效"。
这个坑很现实：manifest 里写的是 `data/3f9a....lance`，
如果 Windows 上的写入者把它拼成 `data\3f9a....lance` 存进去，
这份数据搬到 Linux 上就找不到了。

**没有"空目录"这个概念。** `list` 是靠遍历实现的
（`os.walk` + 前缀过滤 + 排序），而不是靠目录树的语义。
实测：

```
 list('data/') -> ['data/8c2dd13d83374177b5df017e5622cda7.lance']
 list('_versions/') -> ['_versions/18446744073709551613.manifest', ...]
 不存在的前缀 -> []
```

"不存在的前缀返回空列表"而不是报错，这是对象存储的行为
（S3 上列一个空前缀也是 200 + 空结果）。`child_paths()` 用来模拟
"列出某个前缀下的直接子项"，实测：

```
  child_paths('') = ['_versions/', 'data/']
```

注意它给目录项补了一个尾随 `/` —— 这是在模拟桶控制台上看到的那种展示，
但底层并没有目录对象。

**`put` 先写临时文件再 `os.replace`，`put_if_not_exists` 用 `O_EXCL`。**

```python
tmp = full + ".tmp"
with open(tmp, "wb") as fh:
    fh.write(data)
os.replace(tmp, full)
```

`O_EXCL` 是本地文件系统上的"条件写"，等价于 S3 的 `If-None-Match: *`。
实测：

```
  LocalFileStore 走的是 O_EXCL：
    1-00000031 None        <- 第二次写同一个 key 返回 None，表示"已存在"
```

还有一个容易被忽略的细节：`list` 会**跳过所有 `.tmp` 文件**
（`dirnames[:] = [d for d in dirnames if not d.endswith(".tmp")]` 和
`if fn.endswith(".tmp"): continue`）。否则正在写的中间态会被别的读者列出来。

### 6.2.3 S3 式模拟：把坏脾气显式保留下来

`S3LikeStore` 在内存实现之上刻意加了三处"毛病"，而这三处都是有教学目的的：

**没有原子重命名。** `rename()` 直接抛异常：

```
  S3LikeStore.rename -> StoreError: 对象存储没有原子重命名
   (dst='b', hint='用 put + 更新 manifest 的方式提交，不要 rename', src='a')
```

注意这个异常带着 `hint` —— 它不只是在报错，它在教你正确做法。
**这就是 manifest 存在的根本原因**：对象存储没有 rename，
所以"切换到新版本"不能靠"把新文件改名成正式名字"，
只能靠"写一个新对象 + 更新一个指针"。第 7 章会展开这套机制。

**`list` 有延迟。** `list_delay_writes=N` 表示"刚写进去的 N 个对象，
接下来的一次 list 看不到"。实测：

```
写入后立刻 list: []
再 list 一次   : ['data/1.lance']
再写一个后 list: ['data/1.lance']       <- 第二个写入的对象还没出现
```

这就是最终一致。它直接推出一条设计规则：
**不能靠 `list` 判断"有哪些数据文件"。** Lance 靠 manifest ——
manifest 里明确列出了这个版本由哪些片段、哪些数据文件组成，
`list` 只在"找最新版本"这种可以容忍延迟的场景里用，而且要有兜底。

这条规则在我们的读取路径里是硬编码的：`read_fragment()` 从
`fragment.files` 里按 field_id 找文件，从不列目录。

**条件写是原子的。** 这是对象存储唯一给得起的并发原语，
也是 `S3LikeStore` 保留给上层的东西。实测乐观并发：

```
=== 乐观并发：conditional_commit ===
  用正确的 etag 提交 -> b'v2'  conflicts = 0
  用过期 etag 提交 -> CommitConflict: 版本已被其他写入者推进
    (actual='2-00000e7c', expected='2-00000e7b', path='manifest')
  conflicts = 1
```

`conditional_commit()` 的逻辑是"只有当目标还是我看到的那个版本时才允许覆盖"。
`expected_etag` 过期就抛 `CommitConflict`，让上层重读、重做、重提交。
这就是整个 Lance 并发控制的全貌 —— 没有锁、没有事务、只有"抢到就是我的"。

## 6.3 对象存储的四个坏脾气，以及 Lance 各自的应对

把上面散落的点收拢，对象存储有四个绕不开的性质。

**坏脾气一：没有原子重命名。** 应对是**用 manifest 指针而不是 rename 提交**。
所有数据文件先以最终名字写好（名字里带随机 uuid，不会撞），
最后用一次条件写把"当前版本指向哪批片段"改掉。
只要这一次提交是原子的，整个版本切换就是原子的。

真实实现把这层差异收在一个 **commit handler** 抽象后面，按存储选策略：
本地文件系统、GCS、Azure 走 `RenameCommitHandler`（先写临时文件，
再靠 `copy_if_not_exists` 落到正式名，底层仍是条件写 —— GCS 的
`ifGenerationMatch=0`、Azure 的 `If-None-Match: *` 就是这条路上的两个面孔）；
S3 历史上默认的是一个 `UnsafeCommitHandler`（直接写正式名、不做任何检查，
并发写者会**丢更新**），后来才为 S3 补上 `ConditionalPutCommitHandler`
（靠条件 PUT / `PutMode::Create`，才真正拿到并发安全）；
此外还有前面提到的腾讯 COS 特例。提交重试的默认次数是 **20 次、约 60 秒**，
退避带抖动。**"同一个 Lance 在 S3 上和在本地上并发语义一样"这句话要加上
"用对了 commit handler"这个前提** —— 在默认配置的 S3 上它并不成立。

在连条件写都没有的存储上，Lance 还有一个逃生舱：**外部 manifest store**
（把"谁是最新版本"委托给一个支持事务的 KV 存储）。它的机制和代价
第 8.7 节展开，这里只需要记住它是"用一小块强一致的存储补一大块弱一致的存储"。

**坏脾气二：`list` 最终一致。** 应对是**不靠 list 判断数据文件**，
只用它发现版本。这里要先知道一件常被忽略的事：**对象存储的 list 本身是分页的。**
S3 的 `ListObjectsV2` 单次最多返回 **1000 个 key**，更多要靠 `IsTruncated`
加 `ContinuationToken` 一页页翻。所以"打开一个有几千个版本的表"在 list 上
不是一次请求，而是至少 ceil(版本数 / 1000) 次 —— 这正是 Lance 要把版本发现
做得很省的直接原因。两条优化都在第 7 章展开：文件名倒着数
（`u64::MAX - version`，第 7.2 节）让"取最近 N 个版本"变成"取 list 结果的
前 N 条"；`latest_version_hint.json`（第 7.3 节）让常见路径根本不 list。
规范对后者的定位很清楚：它是"**纯优化**：任何时刻删除都安全，
永不影响正确性，不理解的 reader 可忽略，writer 可以选择不写"。

我们的 `try_read_latest()` 实现的是同一套"缓存 + 权威"的分工，
实测一次打开表只要 **2 次 GET + 3 次 HEAD，1328 字节**：

```
--- 7a. 打开表（走 hint 快路径） ---
 打开的 I/O: {'gets': 2, 'puts': 0, 'deletes': 0, 'lists': 0, 'heads': 3, 'bytes_read': 1328}
对象                                                      次数          字节
_versions/18446744073709551613.manifest                  3        1314
_versions/latest_version_hint.json                       2          14
合计 2 次读 / 1328 字节，0 次写 / 0 字节
```

"整个版本的元数据 1314 字节、hint 14 字节"这个量级值得记住：
**打开一张表应该是几十到几千字节的事，不该是几兆。**

**坏脾气三：没有事务。** 应对是**条件写作为唯一原语**。
各家云上的写法不一样，细节的坑也不一样：

**S3** 用 `PutObject` 带 `If-None-Match: *`，对象已存在时返回 412。
**GCS** 用 `ifGenerationMatch=0`（"没有活着的版本才写"），冲突也是 412 ——
但它走的是**代际号（generation）**而不是 ETag，所以 CAS 能精确到
"还是我看到的第 N 代"。一个容易踩的细节：**分片上传（resumable upload）
只在最后一次 PUT 上检查这个前置条件**，发起请求会先成功，
于是多个并发上传可以都开始、只有一个能结束。
**Azure Blob** 用 `If-None-Match: *`，冲突同样返回 412；它按 ETag 做 CAS，
而且对条件头的**组合**有额外限制（不支持的组合直接 400，不是 412）。
**本地文件系统**用 `open(path, O_CREAT | O_EXCL)`。

实测这三家里我们能验的两家：

```
  第一次 put_if_not_exists: 2-00000e7b
  第二次 put_if_not_exists: None        <- 已存在，拒绝
  内容仍是: b'v1'
  普通 put 会覆盖: 2-00000e7d b'v3'      <- 所以普通 put 不能用作并发控制
```

**坏脾气四：延迟高。** 应对有四条，按重要性排：
**合并范围读**（相邻缓冲区间隔小于阈值就并成一次请求）、
**manifest 缓存 hint**（少一次 list）、
**列裁剪 + 行范围下推**（少读字节）、
以及在真实 Lance 里还有**预读**（读 manifest 时先取文件末尾 64 KiB）。

合并范围读的账很好算：一次请求的固定开销是 RTT + 鉴权 + HTTP 头，
在小对象上这个开销常常比数据本身还大。所以我们实现里的默认值是
"相邻缓冲区间隔小于 4096 字节就合并"，注释写的是
"**宁可多读字节，也要少发请求**"。实测这个阈值确实有效：

```
coalesce_gap=     0 cols=3 rows=10 -> gets=  7 bytes=    82737
coalesce_gap=  4096 cols=3 rows=10 -> gets=  6 bytes=    82793
```

少了一次请求，多读了 56 字节。56 字节换一个 RTT，在任何对象存储上都是赚的。

## 6.4 读放大是可以被数出来的

这一节是本章最实用的部分。

性能讨论最容易变成空话，因为"慢"没法验证。但对象存储的读写只是两次 RPC，
所以**我们可以直接数**：一次查询发了几次请求、读了多少字节。

`InstrumentedStore` 是给任意 store 套的一层计量壳。它记录每一次
op + path + 字节数，然后按对象聚合：

```
--- 7c. 读向量列（每行 128 float64 = 1024 B） ---
 取回行数: 100  向量维度: 128
 I/O: {'gets': 82, 'puts': 0, ..., 'bytes_read': 5154082, ...}
 平均每行字节: 51540.82
```

**先把这个实测的口径说清楚：这是"按行号取行"（散读），不是"顺序读前几行"。**
向量索引召回之后走的是 `take`（回表），索引交回的是 100 个**散布在全表各处**
的行号。这张表 5000 行、128 维、向量是 float64（Python float 推断出来的
就是 float64，见第 5.6.1 节），一行 1024 字节，100 行需要 102,400 字节。
实测散读这 100 行发了 82 次请求、读了 5,154,082 字节 —— **和读整列一模一样**。
（后面那张表里 `vector` 全列写的是 **84 次 / 5,155,041 字节**，
两个数不是对不上，差的正是每行都有的那 2 次开表请求和 959 字节的
hint/manifest：`84 - 2 = 82`，`5,155,041 - 959 = 5,154,082`。
**把口径差先减掉再比大小**，否则会以为"散读 100 行"和"读全列"
差了 2 次请求，而结论恰恰是它们一样。）
成因是页粒度：向量子列按 `target_values_per_page`（默认 8192 个值）切页，
每页再用 byte-stream-split 编成 8 个 8192 字节的缓冲区；128 维下一共 79 页，
100 个散布的行号几乎每页都落一个，于是 79 页全部要读。
**散读 100 行的放大倍数 ≈ 50 倍**，而且这个倍数几乎和数据量无关 ——
只要行号散布得够开，读 100 行和读 5000 行读的是同一批页。

换一种访问模式，放大倍数完全不同。下面每一行都是**顺序读**
（`row_range` 下推，不是 take），数字里含"打开表"的 2 次请求、
959 字节（读 hint 与 manifest），所以下表每一行都比上面那段实测多 2 次请求。
同一个 5000 行 × 128 维的表（文件 5,159,202 字节）：

| 读什么 | 请求数 | 读到的字节 |
|---|---|---|
| `id` 列全列（5000 行） | 6 | 40,104 |
| `id` 列前 5 行 | 6 | 40,104 |
| `vector` 前 100 行 | 7 | 166,113 |
| `vector` 前 1000 行 | 21 | 1,083,617 |
| `vector` 全列（5000 行） | 84 | 5,155,041 |

这张表里有两行最关键。**第二行**说明**读 5 行和读 5000 行花的请求数与字节数
完全一样** —— 5000 个 int64 装在一个页里，页是最小读取单位。**第三行**说明
顺序读前 100 行只要 166,113 字节，比上面散读的 5.15 MB 少了约 30 倍：
顺序读只碰 2 页（一页 = 8192 / 128 = 64 行），散读几乎碰满 79 页。
两种模式对着算：顺序读 166,113 / 102,400 ≈ **1.6 倍**，
散读 ≈ **50 倍**。同样是"取 100 行的向量"，差异全部来自**这些行落在几个页上**。

这条观察推出两个实践结论。**第一，`limit 5` 不省 I/O。**
默认 `limit` 只影响返回多少行，不影响读多少页；
要真的少读，得配合文件级的剪枝（第 10 章讲扫描器怎么做）。
**第二，行组切分要按"查询会读多少"来定，不是按"文件多大"来定。**
一页 8192 个值对窄列合适，对 128 维的向量列就偏大了：一页 8192 个值
除以 128 是 64 行，一次读 64 KB 只为了 64 行。

`io_report()` 把同样的数字按对象聚合，用来定位"谁被读爆了"：

```
--- 7d. 谓词过滤下推：bucket == 3 ---
 命中行数: 714
 I/O: {'gets': 9, ..., 'bytes_read': 79201, ...}
对象                                                      次数          字节
data/8c2dd13d83374177b5df017e5622cda7.lance             11       79201
```

注意这里 9 次读、79 KB 读回了 714 行 × 2 列。
`bucket` 和 `id` 都是窄列、在一个页里，所以这次过滤是很划算的。
但如果过滤条件落在向量列上，同样的 714 行就会变成几百 MB。

**"读放大"这个词只有在能被数出来的时候才有意义。**
先量，再优化，否则你优化的是想象。
`InstrumentedStore` 还有一个 `events` 属性保留原始事件序列
（`(op, path, nbytes)` 三元组），需要精确到某个 key 时可以直接翻。

## 6.5 对齐与预读粒度

页是读取的最小单位，那么页内部的字节怎么摆，就直接影响随机访问要发几次请求。

我们的文件格式里有一条硬约束：**缓冲区按绝对偏移寻址，并且 64 字节对齐。**

```
ALIGNMENT = 64
```

为什么是 64？文件头注释给了一句"64 字节对 SIMD 解码器友好，4096 字节对
direct I/O 友好"—— 这两个数字的来历第 3.3 节讲过（64 B 对着一条 AVX-512
的加载宽度，4096 B 对着 direct I/O 的扇区边界）。本节只看它在**对象存储的
请求账**上的后果：对齐把每个缓冲区的位置定死，"读这几个缓冲区"就等于
"发这几次范围读"，这个数字可以被数出来，也可以被 `coalesce_gap` 改掉。

对齐有代价：它会插入 padding。我们实测一次 `vector` 列的缓冲区布局：

```
   off=       0 size=      8 id
   off=      64 size=   1999 id
   off=    2112 size=   8192 vector.item
   off=   10304 size=   8192 vector.item
```

`id` 的第一个缓冲区只有 8 字节，下一个从 64 开始 —— 中间 56 字节是 padding。
但紧接着的 8 个 vector 缓冲区间距正好是 8192，**没有任何 padding**，
因为 8192 本身就是 64 的倍数。所以对齐的实际开销取决于数据布局：
**宽度是 64 倍数的列几乎不付这个成本，宽度奇怪的列会付一点。**

对齐和"合并范围读"是一对：对齐让每个缓冲区都能被独立、高效地读；
合并把相邻的小缓冲区攒成一次请求。两者的目标相反（一个要整齐、一个要少请求），
所以实践中需要调 `coalesce_gap` 和页大小这两个旋钮。

真实 Lance 的默认值比我们的大得多：**页大小 8 MiB**、
mini-block 默认最多 **4096 个值**（可通过 `LANCE_MINIBLOCK_MAX_VALUES`
调到 32768）、单块压缩后不超过 32 KiB。
而规范对"该不该调 mini-block 大小"给了一句很重要的限定：
"只有**通过 profiling 确认** mini-block 读放大打满带宽
（例如经受限网络访问远端对象存储）时才该调整。"
**默认值不是随便定的，调它之前先量。**

预读粒度是另一侧的事。真实 Lance 读 manifest 时会先取文件末尾
64 KiB（`PREFETCH_SIZE = 64*1024`），因为 manifest 通常是"尾部一段 + 一次完整读"。
我们的实现里对应的是 `_read_footer()`：一次 40 字节的范围读。
40 字节 vs 64 KiB 的差别说明了两种策略：
**footer 足够小就精确读，元数据藏在尾部一大段里就预读。**

## 6.6 本地盘还是对象存储

这一节给一组真实的权衡，三个维度：延迟、并发、成本。

**延迟。** 官方文档的五档表（按延迟从低到高）：
本地 SSD/NVMe "最快；p95 常 <10ms"；
块存储（EBS / GCP PD / Azure Managed Disk）"接近本地；常见 <30ms"，
但"**不可跨实例共享**"；
文件存储（EFS / GCS Filestore / Azure File）"好于对象存储；p95 通常 <100ms"；
第三方（MinIO、WekaFS）"类似 EFS，通常 <100ms"；
对象存储（S3/GCS/Azure Blob）"**最高，几百毫秒起**"。

OSS 与 Enterprise 那两组数字（延迟 500–1000 ms vs 50–200 ms、
吞吐 10–50 QPS vs 10,000 QPS）第 1.4 节列过，这里只补**从存储层看**的
增量结论：差异的来源不是算法，是**缓存**。OSS 里一个进程没有内建缓存，
官方原文是 "**LanceDB OSS has no built-in cache. Every read repeats the same
object-store round trip and pays the same latency penalty.**"
于是一次冷查询要发若干次请求（第 6.4 节数过：几十到几百次），
每次几十毫秒，加起来就是几百毫秒 —— 这个数字是**结构性的，不是调优没做好**。
Enterprise 的 50–200 ms 就是把其中大部分请求用 NVMe 缓存吃掉之后的结果。

需要强调的是：**上面所有数字都是厂商口径**（来源是 LanceDB 官方文档的
存储配置页和 Enterprise 页），不是第三方测量。作为量级参考可靠，
作为 SLA 不可靠。

**既然 OSS 没有内建缓存，"缓存"就得自己搭。** 三层做法，从近到远。
**索引缓存到本地 NVMe**：索引是只读、不可变、按名寻址的对象，天然适合
"下载一次、进程内复用"，官方也把冷启动延迟主要归给它；
**热数据目录做 read-through 本地 SSD 缓存**：key 就是对象路径，
而路径里带 uuid、对象不可变，所以缓存项**永不失效**，不需要任何失效协议 ——
这是"不可变对象"这个设计在缓存上的白拿收益；
**读副本（read replica）** 则是把整张表的目录同步到计算节点本地盘，
让查询完全不打对象存储，代价是同步延迟和容量，适合读多写少、
数据量放得下的场景。三条路的共同点：都拿"数据不可变"换"缓存可以永不失效"。

**中间地带：S3 Express One Zone。** 上面那张五档表把"对象存储"当成一档，
但 S3 Express One Zone（目录桶）落在它和文件存储之间：官方给的量级是
**稳定的个位数毫秒**延迟、比 S3 Standard **快一个数量级**、请求费用低最多 80%，
代价是**单可用区**（可用性 99.95%，而不是 S3 Standard 的跨 AZ 冗余）
和目录桶特有的一套会话鉴权。LanceDB 明确支持它，也把它算进
"S3 原生原子写"那一类。它的定位很清楚：**要对象存储的运维形态、
又受不了几百毫秒延迟**的时候用它。

**并发。** 对象存储的 QPS 上限不是硬限制，而是"并发数 × 每个请求的延迟"的倒数。
所以延迟高的存储，吞吐上限天然低。官方对 OSS 给的 10–50 QPS
和 Enterprise 的 10,000 QPS 是同一个道理的两种实现。
反过来说：**本地盘上单进程吞吐高，但扩不到多机**；
对象存储上单进程慢，但可以无状态地横向扩（"stateless, horizontally scalable"）。

**成本。** 对象存储是三者里最便宜的，官方文档也是这么排的
（成本从低到高：对象存储 → 文件存储 → 第三方 → 块存储 → 本地盘）。
但在对象存储上省钱的方式是把 I/O 换成本：
少读字节、多合并请求、加缓存。

还有一条比延迟更隐蔽的差异：**一致性默认是"不刷新"。**
官方文档写着，`read_consistency_interval` 不设（默认值）时
"**no automatic cross-process refresh checks**"，
也就是"表不会自动从别的写入者那里刷新"，
要手动看新版本得用 `checkout_latest`。
设成 `timedelta(0)` 是强一致；设成 30–60 秒是官方推荐的弱一致。
文档同时提醒："**Stronger consistency is not free**" ——
间隔越短，每次读都要多付一次刷新的成本，延迟和费用都会上去。
这条设计含义是：**在 LanceDB 里"两个读者看到不同版本"是设计行为，不是 bug。**

选型建议可以压成三句话：

**单机、延迟敏感、数据放得下** → 本地盘。没有网络、没有一致性窗口、p95 <10ms。

**多机共享、读多写少** → 文件存储或块存储是中间的甜点区：
延迟比对象存储好一个数量级，语义比对象存储干净。

**多机共享、数据量大、成本敏感** → 对象存储，然后**把延迟当成一个要管理的一等资源**：
合并范围读、加大页、开缓存、按 `read_consistency_interval` 明确写出你能接受的一致性档次。

**落地时真正会碰到的几个旋钮。** 上面都是架构层面的取舍，实际接一个云存储
要配的是这些。

**凭证。** 走标准 AWS 环境变量（`AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` /
`AWS_SESSION_TOKEN`），或者 `storage_options` 里的 `access_key_id` /
`secret_access_key` / `session_token`（`aws_` 前缀的写法也认）。两者
**大小写不敏感**：`storage_options` 里写 snake_case、环境变量写大写。
一个例外是 **AWS SSO 的 `AWS_PROFILE` 只能走环境变量**，塞不进
`storage_options`。S3 兼容存储（MinIO 之类）必须同时给 `region` 和
`endpoint`，走 http 还要显式开 `ALLOW_HTTP`。

**超时。** 三个分开的旋钮：`connect_timeout`（只算建连，默认 5 秒）、
`timeout` / `request_timeout`（整个请求，默认 30 秒）、
`client_retry_timeout`（含重试的总时限，默认 180 秒）。默认值对元数据读够用，
对大的 range 读要按带宽估。

**重试。** 客户端侧有两档：`download_retry_count`（下载没下完的重试，默认 3）、
`client_max_retries`（对象存储客户端请求的重试，默认 3），退避因子和抖动可调。
注意它和前面说的**提交重试**（第 6.3 节的 20 次）是两回事：前者是传输层重试，
后者是乐观并发冲突后的重试。

**大对象与 multipart。** S3 单次 PUT 的对象上限是 5 GiB，超过就必须走
multipart：分片上传、最后合并；分片 5 MiB–5 GiB、最多 10,000 片，
拼出来的对象上限 5 TiB。一个现实的好处是**分片可以并行**，所以写一个几 GB
的片段文件时，上传这一段的墙钟时间能被压到跟分片数成反比；代价是多了
"分片重传"和"未完成 multipart"的清理问题（没合并的分片会一直占存储并计费）。

## 6.7 小结

**LanceDB 不假设自己有本地磁盘。** 整个数据集是"一堆按 key 寻址的不可变对象"，
读写走 6 个抽象方法（第 7 个 `put_if_not_exists` 有默认实现，但那个默认实现不是原子的）。

**本地实现刻意不做目录语义。** key 一律用 `/` 拼接（Windows 上也是），
没有空目录，`list` 靠遍历，`put` 先写 `.tmp` 再 `os.replace`，
条件写用 `O_EXCL`。目的只有一个：**本地和云上的行为必须一致。**

**对象存储的四个坏脾气各有对应。** 没有原子重命名 →
用 manifest 指针提交；`list` 最终一致 → 不靠 list 判断数据文件；
没有事务 → 条件写（`If-None-Match: *` / `ifGenerationMatch=0` / `O_EXCL`）
是唯一原语；延迟高 → 合并范围读 + manifest hint + 列/行裁剪。

**读放大是可以被数出来的，而且它取决于访问模式。** 同一个表，
`id` 列读 5 行和读 5000 行都是 6 次请求 40,104 字节（页是最小读取单位）；
向量列**散读**（按行号 take）100 行读满 79 页、5.15 MB，约 50 倍放大，
而**顺序读**前 100 行只碰 2 页、166,113 字节，约 1.6 倍。
`limit` 不省 I/O 也是同一个道理。

**对齐是 64 字节对 SIMD、4096 字节对 direct I/O。** 对齐的代价是 padding，
但宽度是 64 倍数的列几乎不付这个成本。对齐和合并范围读是一对相反的旋钮。

**冷查询几百毫秒是结构性的，不是优化没做好。** OSS 没有内建缓存，
一次查询几十到几百次对象存储往返，每次几十毫秒，加起来就是这个数。
选型要同时看延迟、并发和成本，并且把一致性档位当成配置而不是默认值。

manifest 里到底有什么、时间旅行为什么是免费的、以及 GC 要小心什么。
