# 附录 C　迷你实现代码导读

这份教程带了一个从零写的 LanceDB 复刻：`mini_lancedb/`，
纯 Python 加 numpy，约 3.6 万行，配套 1144 个测试
（收集 1144 条，跑完是 1143 通过、1 跳过）。

这个附录回答三个问题：它由哪些模块组成、每个模块的关键决策是什么、
以及**在写它的过程中踩过哪些坑**。第三部分最有价值，
因为那些坑不是编出来的，是真实调试出来的。

## C.1 为什么值得写一遍

读源码和写源码是两种不同的理解方式。读 Lance 的 Rust 实现，
你会知道"它用了 k-means"；写一遍，
你会知道"k-means 的空簇要怎么办、训练样本要采多少、
质心查最近邻要不要用 HNSW 加速"。

更重要的是，**写一遍才会遇到那些"不报错但结果不对"的问题**。
这份实现在开发过程中抓出的 bug 里，绝大部分都不是崩溃，
而是静默的错误结果——这类 bug 只会在你自己动手写的时候才暴露出来。

还有一层原因：真实的 LanceDB 是 Rust + Python 混合的，
Python 侧只是薄薄一层 API，核心逻辑都在编译好的原生模块里。
想看清楚"条件写是怎么做原子提交的""页表是怎么存的"，
就必须有一个不依赖原生模块、可以逐行调试的版本。

## C.2 模块地图与依赖方向

代码的依赖是**单向**的，从下往上：

```
                 ┌──────────────────────────────────────┐
   用户 API       │ connection.py  table.py  query.py    │
                 └───────────────┬──────────────────────┘
                                 │
                 ┌───────────────▼──────────────────────┐
   数据集层       │ dataset.py  scanner.py  optimize.py  │
                 │ stats.py  namespace.py  permissions  │
                 └───────────────┬──────────────────────┘
                                 │
        ┌────────────────────────┼────────────────────────┐
        │                        │                        │
┌───────▼───────┐       ┌────────▼────────┐      ┌────────▼────────┐
│ expr/         │       │ index/  fts/    │      │ rerank/         │
│ 表达式引擎     │       │ 索引与检索       │      │ embedding/      │
└───────┬───────┘       └────────┬────────┘      └─────────────────┘
        │                        │
        └────────────┬───────────┘
                     │
         ┌───────────▼────────────┐
         │ format/  片段与版本      │
         └───────────┬────────────┘
                     │
         ┌───────────▼────────────┐
         │ encoding/  编码与压缩    │
         └───────────┬────────────┘
                     │
         ┌───────────▼────────────┐
         │ arrays.py record.py     │
         │ types.py schema.py      │
         └───────────┬────────────┘
                     │
              ┌──────▼──────┐
              │ storage/    │  对象存储抽象
              └─────────────┘
```

这条单向依赖是有意维持的。只要它成立，
"换一个存储后端"就只动最底层，"换一种索引"只动 `index/`，
而 dataset 层的代码一行都不用改。真实 Lance 的 Rust 工程也是这个形状。

下面按模块说每个模块的**关键决策**——不是"它实现了什么"，
而是"当初为什么这么选、代价是什么"。

**`types.py` + `schema.py`——类型系统。** 决策是"复刻 Arrow 的逻辑类型，
但把向量建模成普通的 `fixed_size_list`"。这一条决定了后面所有的可能性：
向量能参与投影、能享受列级编码、能被嵌套。
另一个决策是**字段必须有稳定 id**，它让删列变成纯元数据操作。

**`arrays.py`——列式数组。** 决策是"保留 Arrow 的物理布局"：
定长标量用"值缓冲区 + 有效性位图"，变长类型用"offsets + 字节缓冲区"。
好处是所有后续代码（编码器、过滤器、take）都能用同一套心智模型处理，
坏处是实现量比"直接用 Python 列表"大好几倍。

**`encoding/`——编码与压缩。** 决策是"两层正交"：
结构编码（`PageLayout`）加压缩编码，名字照抄真实格式。
关键的一个取舍是 `choose_numeric_encoding` 默认**穷举所有候选**——
在教程场景下这是对的（数据小，而且能看到每种编码的真实大小），
真实系统必须用启发式。

**`format/lance_file.py`——文件容器。** 决策是"照抄 40 字节 footer 和
64 字节对齐"，但**列元数据用 JSON 而不是 FlatBuffers**。
这个偏离让教程能直接把元数据打印出来看，代价在正文里量化过：
同样的结构，元数据体积大一个量级。

**`format/manifest.py` + `transaction.py`——版本与并发。** 决策是
"全量快照 + 条件写"，并且实现了真实的冲突矩阵。
`u64::MAX - version` 的倒序命名也照抄了，因为它带来的
"一次 LIST 取最近 N 个版本"是真实的工程收益。

**`dataset.py`——数据集。** 最重要的一个决策是
**所有"删 + 插"操作都在一次提交里完成**（`_delete_append`）。
如果分成两次提交，upsert 中途失败就等于丢数据。
另一个决策是"行映射用显式数组"——真实 Lance 用 64 位行地址，
我们为了可读性换了实现，代价是 O(行数) 内存，注释里点明了。

**`expr/`——表达式引擎。** 决策是"自己写递归下降解析器"，
并且实现了完整的三值逻辑。最值得一看的是 `Expr` 重载了比较运算符
（和 DataFusion/Polars 一样），这个设计选择带来三个后果，
在 11 章里都讲了——包括它曾经导致的"`BETWEEN` 静默返回 0 行"。

**`scanner.py`——扫描器。** 决策是"把每一层下推都做成可观测的"。
`ScanStats` 里有十几个计数器，`explain()` 逐片段报告剪枝原因。
这不是为了好看，是因为"下推有没有生效"**只能靠数字判断**。

**`index/`——索引。** 决策是"每种索引都实现 `build/search/stats/
save/load/append/remap` 全部七个方法"。其中 `remap` 是最容易被忽略的：
压实和删除都会让行号移动，不重映射就会拿到错的行。
我们的实现里 `remap` 搬不动时会**标记失效并降级成暴力检索**——
降级比崩溃好，但要能被观测到。

**`query.py` + `table.py`——用户 API。** 决策是"接口形状抄真实 LanceDB，
包括那些奇怪的地方"（`create_table` 没有 `append` 模式、
`fast_search` 是方法不是关键字参数）。这样读者在两个实现之间切换时，
肌肉记忆是可以复用的。

## C.4 踩过的坑（按类型分组）

这一节是整份附录的核心。下面按七类组织，覆盖了正文各章里讲过的坑。
它们绝大多数在 `tests/test_regressions.py` 里有对应的回归测试
（那个文件 23 条用例、分成九组），而且注释里写了"不修会怎样"。
少数没进回归文件的——LIKE 前缀+后缀快速路径、B+ 树深度分裂——
测试分别落在 `tests/test_expr.py` 和 `tests/test_index_scalar.py` 里。

**这份清单原来是漏的，而且漏掉的正好是最该记住的两条。**
`README.md` 花了大段篇幅讲那两个"会丢数据"的 bug——
`cleanup_old_versions` 把标签指向的版本的数据文件删掉、
以及全 null 列改类型写出读不回来的表——但**这一节的分类目录里
一条都没有**，它们分别是回归文件的第八组和第九组。
漏掉的原因很典型：这两个 bug 是**后来那一轮审计才查出来的**，
而这一节是按更早的分类写的，新 bug 归进了回归文件、
却没有回头补进这份索引。**索引和它索引的东西分开维护，
就一定会漂移**——所以下面把它们按同类补了进去。

### 类型一：只在某种数据分布下才出现

**delta 解码漏加基值。** 解码器写成 `out[1:] = cumsum(deltas)`，
漏了 `+ first`。首值为 0 时它完全正确——而我们的测试数据恰好
都是 `range(n)`。直到把数据**分批写入**，才发现第二批读回来是
`[10000, 1, 2, 3, ...]` 这种鬼东西。

教训：编码器的测试必须覆盖"基值非零"，只用从 0 开始的数据等于没测。

**LIKE 的前缀+后缀快速路径在短字符串上误命中。**
`'ba'` 会匹配上 `'ba%ba'`，因为快捷路径只检查了
`startswith(pre) and endswith(suf)`，没检查两部分不能重叠。
修法是加上 `len(s) >= len(pre) + len(suf)`。
它是被一个"对拍随机模式生成器"的测试抓到的。

**B+ 树深度分裂后返回错误的行。** 内部节点的 `keys[0]` 是它
**第二个**子节点的最小值，不是它子树的最小值。分隔键维护时读了
`child.keys[0]`，于是左边界悄悄偏移。这个错误在浅树（不分裂）上
完全看不出来；修好之后用 40 组随机语料 × 6 种分裂配置对拍暴力结果。

### 类型二：自洽的测试证明不了正确

**LZ4 写出了一个"谁也读不了"的文件。** 编码器产出了 offset=0 的序列
（匹配到自己），因为我们为了提升命中率，在找到匹配后顺手把
`table[src[i:i+4]] = i` 写了进去，下一个循环取出的候选就是它自己。

我们自己的解码器能读出大部分内容，直到几百字节之后才因为
"字面量超界"报错——**报错位置和真正的起因毫无关系**。
最后是拿 C 实现（`lz4` 包）对拍才定位到。

修好之后，测试里加了一条**双向交叉验证**：
我们的压缩器产出的字节 C 实现能解，C 实现产出的字节我们能解。

**FSST 解码把"每个符号"当成了"每一行"。** 手工构造的短字符串
（一行一个符号）能过，真实文档文本（一行几十个符号）会解出
错误的行数和内容，**而且不报错**。后果是把乱码喂给嵌入模型——
模型不会因为输入是乱码而报错，它只会给出一个错误的向量。

修法是在页里显式存行 offsets。

### 类型三：重载了运算符的 AST 节点永远不报错

**`BETWEEN` 在开启统计剪枝时静默返回 0 行。**
`_stats_can_match` 里写的是 `expr.high < lo`，而 `Expr.__lt__`
被重载成"构造一个比较节点"，于是这个条件**恒真**，
每个片段都被判成"不可能命中"。

最阴的地方在于：同一语义的 `>= AND <=` 写法完全正常，
删行的路径（走另一套求值）也完全正常，关掉 pruning 之后
`BETWEEN` 也"好了"。所以它很容易被误判成随机问题。

现在所有"把谓词和统计做比较"的地方都必须先经过 `_literal_value()`
解出真正的 Python 值。

### 类型四：索引与行号的生命周期

**建完索引再删行，向量检索直接崩。** 索引存的是
**建索引那一刻的逻辑行号**，删除会让逻辑行号整体前移。
症状是 `IndexError: 行号越界` 或 `掩码长度与索引行数不一致`。

现在 `_delete_append` 会把索引里的行号从旧编号搬到新编号
（纯算术：旧行 i 的新位置 = i 减去它前面被删的行数），
搬不动就标记失效。

**改向量维度被"改成功"了。** `alter_columns` 到不同的维度时，
早期版本只改了 manifest、没动数据，于是 500 行 × 8 维被当成
1000 行 × 4 维读出来——**行数静默翻倍**。
现在直接抛 `TypeMismatchError` 并说明"这是数据变换而不是类型转换"。

### 类型五：监控指标静默归零

**前缀 store 让所有 I/O 计数变成 0。** `ObjectStore.__init__`
给每个实例新建一份 `StoreStats`，所以包在表外面的前缀壳自带一份
永远是零的计数器。不报错，只是**所有 I/O 数字都是假的**——
而性能调优全靠这些数字。

**`explain(analyze=True)` 把剪枝计数算了两遍。**
`build_plan()` 又跑了一次 `_prune_fragments()`，而它是累加的。
输出里出现过"剪掉 18 个片段（总共 10 个）"这种明显不可能的数字。

**剪枝决策的粒度过粗。** `_fragment_has_index_evidence` 用的是
"这张表有没有索引"，而不是"这个谓词能不能被索引回答"。
后果是在任意一列上建索引之后，**整张表的统计剪枝全部失效**——
一个 `WHERE txt = 'item-015000'` 的查询从剪掉 9/10 个片段变成 0/10。

### 类型六：静默的空操作

**`when_matched_delete()` 不带 `where` 时什么都不做，还报删除 0 行。**
语义上"匹配上的全删"，实现上只在给了 `where` 时才算删除集合。
"以为删了其实没删"不会触发任何监控，比报错危险得多。

**`merge_insert` 遇到重复源键会把目标行更新两次**，
于是目标表凭空多出一行。真实 LanceDB 的做法是保留最后一条。

这两条都是被测试"钉住"的——把它们的行为写成断言，
让后来的人至少知道现在是这个行为。

### 类型七：写成功了，当时不报错，事后才炸

这一类是前面六类里最严重的一档，前面几类都已经补进去了，
单列出来是因为**它们的失败方式和其它所有坑都不同**：
不是"结果不对"，是"数据会没"。两条都在 `README.md` 里展开过，
这里给它们的形状和回归位置。

**标签保不住数据。** `Dataset.cleanup_old_versions` 里的 `keep_set`
（决定回收哪些数据文件）原先算在 `referenced_tags` **之前**，
于是标签保住了 manifest，数据文件却被当成垃圾回收掉了。
几天之后 `checkout("release-1")` 报 `StoreError: 对象不存在`。
根因是顺序问题——`keep_set → live_files → 回收` 这条链一旦换序，
"被保护"这个语义就反了。回归位置：第八组
（`test_cleanup_old_versions_keeps_tagged_versions_readable`）。

**测试没抓住它的原因值得单独记：** 有测标签的用例、有测清理的用例，
但**没有一条把两者串起来**。"每个函数都测了"和
"功能之间的交互有人走过"是两件事，前者不能推出后者。

**全 null 列改类型会写出读不回来的表。** 两个 bug 叠在一起：
字典编码的 `can_encode` 只挡住了 `len(data) == 0`，
而全 null 列的 `len(data)` 是 N、不为 0，于是空字典通过了校验；
修掉它之后，常量编码又把一个 0 维 ndarray 塞进页元数据，
让 JSON 序列化炸掉。**修一个 bug 会把下一个顶出来**——
所以修完必须把同一个场景再跑一遍，不能停在上一个绿灯。
回归位置：第九组。

**这一类给流程的教训只有一条：回归用例要验证"把修复回退，用例确实失败"。**
不验证这一步的回归用例是装饰品——它可能碰巧通过，也可能根本没覆盖到
被修的那个分支。上面两条都做过了这个验证。

## C.5 从迷你实现迁移到真实 LanceDB

两边的 API 形状是对齐的，切换的成本主要在三处：

**索引配置。** 迷你实现接受字符串（`config="IVF_PQ"`），
真实版本用配置对象（`config=IvfPq(num_partitions=16)`）。

**建索引的同步/异步要分清是哪一层。** 迷你实现只有同步的一档。
真实版本有两个入口：`create_index()` **会阻塞**
（本机实测 3000 行 32 维的 `IvfPq` 建了 0.15 秒，返回后
`list_indices()` 立刻能看到它覆盖了全部行），
`create_index_async()` 才返回一个 `Job`、需要 `job.wait()`。
所以"索引还没建完就开始查"这个问题，**只在你用了
`create_index_async()` 却没有 `wait()` 时才会发生**——
用的是同步入口时不用担心。第 2 章 §2.3 有这条实测，
附录 G §G.3 讲了 `Job` 上都有什么。

**几个方法带弃用警告**：`create_scalar_index`、`create_fts_index`、
`compact_files`、`cleanup_old_versions`、`table_names`。
它们正在被新接口取代。

除此之外，`search()` / `.where()` / `.limit()` / `merge_insert()` /
`checkout()` / `tags` 这些形状都是一样的。

**但也有几处必须知道的差异**（真实版本的行为，迷你实现没有完全复刻）：

`fast_search()` 在**无索引的表上返回空结果**而不是报错。
`prefilter=False` 会返回**少于 k 行**。
`.select()` 不会去掉 `_distance`（会带一个弃用警告）。
`optimize()` 返回 `None` 而不是统计对象。
`index_stats("不存在的名字")` 返回 `None` 而不抛异常。
FTS 在**没有倒排索引**时直接抛 `ValueError`。

这六条都写在附录 D 里，每一条都附了本机复现的真实报错信息。

## C.6 测试的组织方式

1144 个测试，按模块分文件：

| 文件 | 用例数 | 覆盖 |
|---|---|---|
| `test_table_api.py` | 248 | 面向用户的表 API 与查询构建器 |
| `test_expr.py` | 242 | 表达式解析、三值逻辑、索引改写 |
| `test_index_vector.py` | 147 | 八种向量索引与召回率 |
| `test_embedding.py` | 109 | 嵌入函数与注册表 |
| `test_rerank.py` | 108 | RRF / 线性融合 / cross-encoder / ColBERT |
| `test_index_scalar.py` | 103 | BTREE / BITMAP / LABEL_LIST / NGRAM / ZONEMAP |
| `test_connection.py` | 87 | 连接、命名空间、权限 |
| `test_fts.py` | 77 | 分词器、Porter 词干化、BM25 |
| `test_regressions.py` | 23 | **上面每一条坑的回归测试** |
| 合计 | 1144 | 收集数；跑完是 1143 通过、1 跳过 |

跑法：

```bash
cd lancedb-tutorial
python -m pytest tests/ -q
```

最后那个文件按用例数排是最小的一个（23 条，占全表 2%），
但它是整个套件里最值得读的。
**维护规则只有一条：修了 bug 就在这里加一条**，
而且注释里要写清楚"不修会怎样"——它比断言本身更有价值。

（它同时也是最容易被写错的一处：这一节原来在表格里写 23、
在正文里写 18，两边差 5，而且**连续几轮没人发现**——
因为表格和正文相距十几行，读的人不会去交叉验算。
`check_docs.py` 也抓不到它：它只校验"N 个测试"这种形式的**总数**，
不校验分文件的小计。所以这里的数字目前只能靠手对，
改完测试记得两边一起改。）
