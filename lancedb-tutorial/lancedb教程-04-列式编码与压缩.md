# 第 4 章　列式编码与压缩

上一章讲了文件"怎么摆"，这一章讲"页里装什么"。这一层决定了同一个数据集
在磁盘上是 10 GB 还是 100 GB，也决定了查一次要解压多少字节。

先给一个贯穿全章的核心判断：**通用压缩是最后一道防线，不是第一道。**
LZ4 和 Zstd 不知道自己在压的是时间戳还是向量分量，它们只能利用"字节重复"。
列存真正的压缩率来自**结构化编码**——在压缩之前，先按列的语义把数据
重排成"更容易压"的形态。

## 4.1 真实 Lance 的两层编码模型

这一节是理解后面所有内容的地图。Lance v2 的编码是**两层正交**的：

**第一层是结构编码（structural encoding）**，决定"值怎么铺进缓冲区"。
规范里叫 `PageLayout`，一共五种：

`mini_block` 把列切成小块，每块独立编码。**切块的边界是按"值的个数"
算的，不是按行数**：默认上限是 **4096 个值**（可用
`LANCE_MINIBLOCK_MAX_VALUES` 调到 32768），而且单块压缩后不超过 32 KiB。
好处是随机访问：要读第 5000 行，只需要解压它所在的那一小块。
代价是块间有重复的元数据。

（这里我第一版写成"按 32 行左右切成小块"，是错的——**"32"和"行"两个
要素都不对**。它出自对 mini-block 名字的想当然：名字里有 "mini"，
就以为块很小、以为按行切。真实的边界由**值数**决定，所以一个
`fixed_size_list<float32>[768]` 的列，4096 个值只有 **5 行多**——
同一句"4096 个值"在窄列和宽列上对应的行数能差三个数量级。
第 6 章 §6.5 讲预读粒度时会再回到这个数。）

`constant` 整页一个值，只存这个值本身。真实数据里出现频率远超直觉。

`full_zip` 整个页的值铺满全部缓冲区，没有块边界。压缩率最好，但随机访问要解压整页。

`blob` 用于超大对象（图片、音频），把数据外置成独立缓冲区，行里只留偏移。

`sparse` 用于极稀疏的列（大部分是 null / 0），只存非默认值的位置。

**第二层是压缩编码（compressive encoding）**，决定"这一块用什么算法压"。
规范里定义了 15 种，常用的有 `plain`（不压）、`bitpacking`、`varint`、
`rle`、`dictionary`、`fsst`、`byte_stream_split`、`range`（区间编码）、
`delta`（差分）、以及 `general`（挂 LZ4 或 Zstd 兜底）。

两层正交，组合数是 5 × 15。我们的迷你实现取了其中最常用的一小组，
但**字段名和分层方式照抄真实格式**，所以对着官方 spec 读代码能一一对上。

**三个容易混的编码，先把格式说清楚。** `varint` 是 LEB128：每个字节用低 7 位
装数据、最高位当"还有后续字节"的标志，负数先做 zigzag 映射成"小绝对值对应
小无符号数"，所以它特别适合"取值跨度大但不均匀"的列——差分后的时间戳、
变长字符串的 offsets 都落在这一类。`range` 是规范里的区间编码，本实现没有落
它，所以本章给不出它的实测数字（这一条只能按规范描述，**未经本机验证**）。
`general` 也不是一种具体算法，它是一个**包装层**——把 LZ4 或 Zstd 这类通用
压缩器挂到已经做完结构化编码的字节上（见 §4.7 的三档压缩）。这三种里，
本实现只落了 `varint`（`varint_encode` / `varint_decode`），
**`range` 与 `general` 都没有实现**，只留在字段名和文档里：
它们在教学上带来的新意不如位打包和 FSST。

**null 走的是另一条通道，不占值编码。** 每列有一张**有效性位图**
（validity bitmap），1 bit/行；**整列没有 null 时它根本不写**（元数据里留一个
`-1` 占位），所以"没有 null"是零成本的。有 null 时它是 100,000 行 12,500 字节，
和同长度的布尔列一样大。这里藏着本实现的一个不一致：`bool_bitmap` 与 `bitpack`
共用一套 LSB-first 的 `pack_bits`，而列级有效性位图用的是 numpy 的 `np.packbits`，
位序是 **MSB-first**。两边各自读写配对，所以往返测试全绿——但位序记混就会得到一张
"长度对、位置全错"的位图，而这类错误在小数据上往往测不出来。细节在 §4.3。

## 4.2 整数编码：同为 int64，收益差约 8 倍

整数列是最容易吃到红利的。下面是我们用 `compare_numeric_encodings()`
在一个 10 万行的列上实测的结果（原始 int64 是 800,000 字节）：

**单调递增 id。** 最优是 `delta`（首值 + 差分 varint），100,007 字节，
压缩比 8 倍。而把 `delta` 的结果再喂给 LZ4，会得到 412 字节 —— 因为
差分全是 `1`，LZ4 一眼就看出来了。**这就是"结构化编码 + 通用压缩"
叠加效应的最干净的例子：先做语义变换，再做字节级压缩，两者互相放大。**

**随机 id（0 到 2^62）。** 最优是 `bitpack`，775,000 字节。
这一列几乎压不动——真实的高熵数据就是这样，任何声称"列存一定省 10 倍"
的说法都是在挑好看的数据。这里的价值不在于省空间，
而在于"每值 62 bit 而不是 64 bit"这种稳定的小收益。

**状态码（取值 0 到 3）。** `bitpack` 到 25,000 字节，即每值 2 bit，
压缩比 4 倍。如果是 int64 存的状态码，那就是 32 倍的差距。

**排序后的类别（取值 0 到 7）。** `rle` 赢麻了：32 字节。
10 万个值压成 32 字节，因为排序之后每个值都是连续一大段。
没有排序的话 `rle` 会膨胀得比原始数据还大——**同一列，顺序不同，
差三个数量级。** 排序不只是为了查询，它本身就是一种压缩手段。

**常量列。** `constant` 编码 4 字节。真实数据里"租户 id""版本号""状态位"
经常整页同值。

**布尔列。** `bool_bitmap` 12,500 字节，即每值 1 bit。相比 Python 里
每个 bool 至少 28 字节（对象头都算上），是 200 倍的差距。

**递增时间戳（毫秒）。** `delta` 到 200,006 字节，再 LZ4 到 805 字节。

把这几条放在一起看，会发现一个规律：**压缩率取决于列里"信息量"有多大，
而不是取决于列的名字。** 单调递增 id 用 `delta` 压到 8 倍，随机的 int64
用 `bitpack` 也只有 1.0 倍；再换成排序过的低基数列，`rle` 能把 10 万个值
压成 32 字节。类型相同，压缩率能差三个数量级，差别全在数据里。

## 4.3 位打包的实现细节

`bitpack` 看起来简单，实现上有两个容易踩的点。

**第一是位宽的确定。** 位宽由这一页的值域决定：`max` 需要多少 bit
就打包成多少 bit。值域 0..3 只要 2 bit。这要求**逐页重算位宽**——
一整列的全局位宽会被一个离群值毁掉，而分页之后每页各自最优。

**第二是打包方向。** Lance 和 Arrow 的位图约定是 LSB-first（低位在前），
所以位打包解码器必须和位图共用同一套移位逻辑，否则会出现
"位图读对了、位打包读错了"或者反过来的诡异 bug。
本实现里 `bool_bitmap` 就是把复用做到极致的例子——`BoolBitmapEncoder.encode`
的全部内容就是 `pack_bits(data, 1)`，布尔列和位打包列因此共享同一段最容易
写错的代码，测一处就等于测了两处（区别只在元数据里多记一个 `true_count`）。
我们的 `pack_bits` / `unpack_bits` 用的是"逐值写、按位累计"的朴素实现：

```python
bitpos = 0
for i in range(n):
    x = int(v[i])
    byte = bitpos >> 3
    shift = bitpos & 7
    need = (shift + width + 7) >> 3
    chunk = (x << shift).to_bytes(need + 1, "little")
    for k in range(need):
        out[byte + k] |= chunk[k]
    bitpos += width
```

生产实现会用 SIMD 一次处理 32 或 64 个值，速度差十倍以上。
但这段朴素代码把"位是连续的、可能跨字节"这个本质讲清楚了——
`need = (shift + width + 7) >> 3` 就是在算"这个值会跨几个字节"。

## 4.4 字典编码：低基数列的万能钥匙

字典编码做两件事：把去重后的值存一张表，行里存这张表的下标；
下标再走位打包，于是每行的成本从"值的长度"降到"log2(不同值个数) 位"。

实测一个 5 万行的字符串列（内容是 `LanceDB is a multimodal lakehouse...`
这种模板化文本），原始形态（int64 offsets + UTF-8 字节）是 3,588,898 字节。
换成 `plain` 只降到 3,388,894 字节——省下的正好是 offsets 从 int64 变成
int32 的那部分，数据字节一个没动。`fsst` 把符号表、打包后的码流和行 offsets
合起来压到 953,571 字节，约 3.8 倍。

FSST 这一页由四段组成，值得拆开看：
符号表本身的 offsets 1,024 字节、符号表 1,634 字节、
打包后的码流 750,909 字节、以及**行 offsets 200,004 字节**。

码流是 3.39 MB 压到 0.75 MB（4.5 倍），但最后那 200 KB 的 offsets
把整体压到了 3.8 倍。**这 200 KB 是可以省掉的**——
符号流的每个符号长度已知，所以符号边界是自描述的；
真正需要额外信息的是"哪一行从哪个符号开始"。
真实 Lance 的做法是把行 offsets 当独立的一列，走 delta + varint：

5 万行的列有 50001 个 offsets，用 int32 平铺是 200,004 字节，
而"差分 + varint"只要 90,001 字节，**省掉 55%**。
原因很直接：变长字符串的 offsets 单调递增，差分都是小整数，
varint 一个字节就装得下。加上这一层，FSST 的整体压缩比会回到 4.3 倍左右。

这里有一个我们自己踩过的坑，值得完整讲一遍。
最早的 FSST 解码器是这么写的：把码流里每个符号直接当成一行，
依次拼起来。对"一行只有一个符号"的短字符串它能跑通，
所以单元测试全绿——测试数据恰好都是短字符串。
换成真实文本（一行要几十个符号）之后，
**解码出来的行数和内容全错**，而且不报错。

bug 被一个后来写的测试抓住：它拿真实的文档文本做往返，
而不是拿手工构造的短字符串。修法是在页里显式存行 offsets，
也就是现在这四段结构。

这个故事的教训有两条。**一是测试数据要接近真实分布**——
用手工构造的短字符串测压缩编码，等于没测。
**二是"没报错"和"对"是两件事**：
这个 bug 会一路把错误的文本交给下游的嵌入模型，
而嵌入模型不会因为输入是乱码就报错，它只会给你一个错误的向量。

字典编码也有陷阱。**它的收益与基数的关系是非线性的。** 10 万个值、
1000 个不同值，字典表 1000 条，下标 10 bit/值，总共约 125 KB，
远小于原始的 800 KB。但如果不同值有 5 万个，字典表本身就接近原始大小，
再加上下标，反而更大。所以判断标准不是"是不是字符串"，
而是"基数 / 行数"这个比值。我们的 `DictionaryByteEncoder.can_encode()`
就是拿"字典表字节 + 下标字节 + offsets 字节"和"原始字节"直接比大小，
只有真的省才用。

## 4.5 FSST：给高基数字符串的压缩器

高基数字符串（URL、日志模板、代码片段）用不了字典编码，
这时候要用 **FSST**（Fast Static Symbol Table）。

它的思路：先用数据本身训练一张"常用子串表"，
把出现频率高的 2 到 8 字节子串映射成单字节码字（最多 255 个），
然后逐个字符串做**贪心最长匹配**编码。

真实的 FSST 论文算法分三阶段：采样（sample）→ 迭代（iterate，反复
用当前符号表重新切分并统计）→ 定稿（finalize，把 256 个单字节
也算进符号表）。我们的 `build_fsst_symbol_table()` 只做了一轮贪心：
从长到短统计 n-gram 频率，按 `频次 × (长度-1)` 排序，取前若干个。

一轮的版本在模板化文本上能把码流压到 4.5 倍，而且实现只有几十行。
但要说清楚它简化在哪里，不然后面读官方实现会困惑：

- 论文版会多轮迭代，每轮用上一轮的切分结果重新统计；
- 论文版会把 256 个单字节都纳入码字空间，用"码字值是否小于符号数"
  来区分转义；我们用一个专门的转义码 255 + 原始字节，简单但多占 1 字节；
- 论文版有增益评估，会剔除"用了反而变大"的符号。

我们另外加了一条防止歧义的规则：**新符号不能是已有符号的子串**，
否则解码时贪心匹配会产生二义性。这条规则论文里没有（因为它的
迭代流程天然避免了这个），我们自己补上。

## 4.6 浮点与向量：最反直觉的一节

向量列占了文件 90% 以上的空间，所以"向量能不能压"直接决定了成本。
结论是：**不能压得太好，而且常见的优化手段会反噬。**

32 位浮点的 4 个字节按"符号 + 指数 → 尾数"排列。把 4 个字节按位置
分组（`byte_stream_split`）之后，高位字节取值集中，能压掉一大截。

我们在 2000×128 的 N(0,1) 归一化 float32 向量（**25.6 万个值**、
102.4 万字节——2000 乘以 128 是 256,000 个值，每个 4 字节）上实测：
原始数据 1,024,000 字节；直接 `plain` + LZ4 是 1,027,910 字节，
**比原始还大**；`byte_stream_split` + LZ4 是 955,075 字节，小 7.1%。
拆开看四条字节流各自的 LZ4 结果（257K / 257K / 257K / 184K）更说明问题：
前三条几乎压不动，收益全在最高位那条上——它从 256K 掉到 184K，压掉 28%。

7.1%，不是很多文章里说的 20% 到 30%。原因很直接：
随机高斯向量的低位尾数就是纯噪声，神仙也压不动。

**更值得记的是反向结果。** 我们拿"已经量化过、步长 0.05"的浮点
（尾数字节大量为 0）做同样的实验：`plain` + LZ4 是 692,642 字节，
而 `byte_stream_split` + LZ4 是 776,336 字节——**反而大了 12%**。
量化后的低字节全是 0，`plain` 布局把它们挨在一起，LZ4 一眼就压掉；
按字节位拆开之后，这种重复关系被打散了。

所以有一个必须记住的原则：**结构性变换和通用压缩是耦合的，
不能独立决策。** "浮点就上 byte_stream_split" 这种规则是错的。
真实 Lance 的做法是让编码选择由**实际数据分布驱动**——
它的 `CompressionStrategy` 是一串按优先级排列的候选，
由编码器逐个试、按压缩率选。我们的 `choose_numeric_encoding()`
走的是同一路线，只不过为了教学把候选集穷举了一遍。

顺带说一个 float16 的实测：N(0,1) 的 float16 向量，
plain+LZ4 是 513,900 字节，拆字节后是 510,203 字节，只省 0.7%。
**float16 本身已经把一半的空间省掉了**，再叠压缩的边际收益很小。
这也是为什么很多向量库默认用 float16 或 int8 存向量副本，
而不是花力气做无损压缩。

## 4.7 LZ4：自己实现一遍才明白的几个细节

通用压缩我们选了 LZ4 而不是 Zstd 或 gzip，理由是**解压速度优先**。
向量检索是延迟敏感型负载：查一次可能要解压几十上百个页，
每页解压花 100 微秒，光解压就吃掉几毫秒。
LZ4 的解压速度在 2 到 4 GB/s，比 zstd 快一个身位，比 gzip 快一个数量级；
压缩率低 20% 到 40%，但对"已经做过结构化编码"的数据，
这点差异远不如解压速度重要。

**真实 Lance 的压缩不是"一个算法"，而是"三档 + 一条短路"。** 三档是
不压缩、LZ4、Zstd：LZ4 快但压得少，Zstd 压得多但解压慢，选谁看的是
**压缩之后的字节数谁最小**。本实现没有引入 Zstd——高压缩比那一档用 zlib
代表（`COMPRESSION_ZLIB`，层级参数默认 6），既保住了三档结构，又不引入
第三方依赖，正文里量到的取舍结论因此可以原样映射过去。短路由
`compress_page()` 负责：**压缩后一旦不比原来小就退回不压缩**，
因为那意味着每次读都要多付一次解压，却一点空间都没换回来。
这就是第 24 章那句"先编码、再压缩，压不动就别压"的代码形状。

`mini_lancedb/encoding/compress.py` 里的 `lz4_compress` /
`lz4_decompress` 是**真正的 LZ4 块格式**，不是简化版：
测试里和 C 实现（`lz4` 包）做了双向交叉验证，两边能互相解压。

整个格式只有十几行伪代码：

```
sequence := token [literal_len_extra] literals offset [match_len_extra]
token    := (literal_len << 4) | (match_len - 4)
```

但有三条硬性约束，写错了 C 实现会拒绝解压：

**块的最后 5 个字节必须是字面量。** 这条约束初看莫名其妙，实际是为了
让解码器可以放心地"预读 5 个字节再判断"而不越界。

**最后一个匹配的起点距离块尾至少 12 字节。**

**offset 必须是 1 到 65535，且指向已经输出过的位置。**

我们实现时踩了一个真实的坑，值得记下来：为了提升后续命中率，
我在找到一个匹配之后顺手把 `table[src[i:i+4]] = i` 写进去，
结果下一个循环取出的候选就是它自己，算出 offset = 0，
编码器于是产出了一堆"谁也读不了"的字节。
问题在于当时的单元测试只测了"解压回来等于原文吗"——
而**我自己的解压器也容忍了这个 bug**（它读到 offset=0 才报错，
但错误出现在后面的序列里，报错信息完全没有指向真正的起因）。
最后是靠和 C 实现的交叉验证才定位到。

这个坑的教训有两层。**一是自洽的往返测试不足以证明格式正确**——
必须和独立的实现对照。**二是压缩错的症状会在很远的地方才爆发**：
一个序列的 offset 写错，解码器会在几百字节之后才因为"字面量超界"而失败。
这也是为什么真实系统的压缩/编码路径一定要有"和参考实现对拍"的测试。

## 4.8 编码选择策略

`choose_numeric_encoding()` 的做法是：**把所有可行编码都试一遍，取最小的那个。**

这在教学场景下是对的——数据小、而且"看到每种编码的实际大小"
本身就是章节内容。但真实 Lance 不能这么做，因为它要在 PB 级数据上
做同样的决策。它的做法是启发式 + 按优先级短路：

先看数据类型决定候选集，再看基数、单调性、值域这些廉价特征
决定用哪个，最后只在少数候选之间比较压缩率。
决策成本必须远小于收益，否则"选编码"本身就变成了瓶颈。

这个取舍值得展开：**编码选择是一个在线决策问题。**
每次写入都要做，做错的代价是磁盘空间和后续的读放大，
做慢的代价是写入吞吐。所以生产系统选择"足够好的启发式"，
而把"最优"让给离线重写（Lance 的 `optimize` 里就有重写路径）。

我们的实现留了一个开关：`choose_numeric_encoding(..., exhaustive=True)`。
把它设成 `False`，就会退化成"按候选顺序第一个可用的"——
和真实系统的行为更接近。两种模式都值得跑一遍对比，
因为"启发式"和"最优"的差距本身就是一个重要的工程结论。

## 4.9 frame-of-reference：先减最小值，再位打包

§4.2 的实测里每个整数列都跟着前三种可行编码，其中有三个数字出现过却没解释：
单调 id 的 `for=212,508`、随机 id 的 `for=775,008`、状态码的 `for=25,008`。
它们总是精确地比 `bitpack` 多 8 个字节——那 8 个字节就是 FOR 的全部额外开销。

**FOR（frame of reference，参考帧）的思路只有一步：先把整块的值统一减去一个
基准值，再对差值做定宽位打包。** 本实现的基准取块内最小值
（`FrameOfReferenceEncoder` 里的 `lo`），位宽由 `max - min` 决定，而不是由
`max` 决定。于是"金额都在 100 到 200 元之间"的列，基准是 100、位宽只要 7 bit，
而 `bitpack` 会老老实实按 `max = 200` 算成 8 bit。反过来，单调 id 这种从 0
开始的列 `min = 0`，两者算出的位宽完全一样——这正是那三个 `for` 数字恰好比
`bitpack` 多 8 字节的原因：多出来的只有一格 int64 的基准值。

**它和 `delta` 的区别在"减什么"。** `delta` 减的是**前一个值**，输出一串
差分、再用 `varint` 变长装，赌的是"相邻值接近"；FOR 减的是**块内最小值**，
输出一批定宽整数，赌的是"整块的值域窄"，对顺序完全不敏感。这个差别在实测
里分成了三档：

- **单调递增**：`delta` 赢。差分几乎全是常数，再叠一层 LZ4 只剩 412 字节。
  这一档里 `for=212,508` 是 `delta=100,007` 的两倍多——FOR 只能利用
  "值域 0..99999 要 17 bit"这个事实，而 `delta` 把"差全是 1"直接用上了。
- **无序但值域窄**：FOR 赢。乱序数据上 `delta` 的差分正负交替，`varint`
  每个值要好几字节；FOR 的定宽不受顺序影响。
- **无序且值域宽**：两个都赢不了。随机 id 那组 `bitpack=775,000` 对
  `for=775,008`，FOR 净亏一格基准值。

递增时间戳那一组卡在中间，正好说明 FOR 的边界：`delta=200,006`、
`bitpack=512,500`、`for=337,508`。时间戳比 id 多了一个 1.7e12 量级的基数，
基准把这部分砍掉了（位宽从 41 bit 降到 27 bit），但砍不掉增量——
那部分只有 `delta` 能利用。

**所以 FOR 的适用面是"值域窄、但顺序不重要"的列**：分桶后的数值、
改成相对某个原点偏移的坐标、已经量化过的整数特征。只要列里有单调性，
`delta` 通常更好；只要列里有离群值，FOR 的位宽就会被那个离群值拉大。
但这不是"FOR 没有退路而 `bitpack` 有"——两者本来就站在同一条起跑线上，
`plain` 恒定可行、在 §4.8 的穷举里和它们平等地比大小，压不动时大家一起
退回它。真正的差别在位宽由什么决定：FOR 减掉块内最小值、按**极差**定宽，
`bitpack` 不减、直接按**绝对值上界**定宽，所以值域窄、绝对值却很大的列
（从大基数上偏移出来的时间戳、坐标）是 FOR 的主场；而它为此要多存一格
基准值，列从 0 开始时这 8 个字节就白花了。这条规则和 §4.3 里
"位宽逐页重算"是同一件事：**一整列的全局位宽会被一个离群值毁掉，
分页之后每页各自最优**。

## 4.10 小结

这一章的核心结论可以压成四条：

**结构化编码优先于通用压缩。** 同一个 int64 列，选对编码能省 8 倍（单调 id
走 `delta`）；单纯上 LZ4 可能一点都省不下来，随机数据上甚至会变大。

**压缩率取决于列里的信息量。** 单调 id 和随机 id 都是 int64，一个压到 8 倍、
一个只有 1.0 倍；再换成排序过的低基数列，`rle` 能把 10 万个值压成 32 字节。
不要拿"某个列压缩了 10 倍"当通用结论。

**编码选择必须由数据驱动，而且是逐页的。** 同一列的不同页可以用不同编码。
把"浮点就用 byte_stream_split"这类规则写死，会在量化向量上反向吃亏 12%。

**压缩格式的正确性只能靠交叉验证。** 自洽的往返测试让一个 offset=0 的
bug 溜过去了，最后是和 C 实现对拍才抓住。
