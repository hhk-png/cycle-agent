# 附录 J　互操作：零拷贝、C Data Interface 与格式层边界

## J.1 这一篇补的是哪一层

附录 I 讲到 `LanceRead` 吐出一个 `RecordBatch` 就停了。这一篇接上
最后那一段：**这些字节是怎么交到你手里、以及怎么再交给下一个系统的。**

这一层在正文里是散开的。第 5.1 节说类型系统"借用 Arrow"，
第 26.6 节讲格式层互操作，附录 H 讲数据是怎么进来的——
**但没有一处讲数据是怎么出去的**。而"出去"这件事的关键词是
**零拷贝**：它决定了"把 LanceDB 的查询结果喂给 DuckDB"到底是
一次内存复制、一次磁盘落盘、还是一次指针传递。

这一层值得单独成篇，是因为它有一个很特殊的性质：
**它的性能差异是数量级的，但失败时的表现是"看起来也跑通了"。**
`to_pandas()` 和 `to_arrow()` 都能让你拿到数据，
两个调用都不会报错，而一个是零拷贝、一个复制了整份。
**没有一篇讲清楚这件事，"我明明用了 Arrow"就变成了一句没有信息量的话。**

验证环境照旧：`lancedb 0.40.0` + Python 3.14.6 + pyarrow 26.0.0。
这里的缺件比前几篇多——`pandas`、`polars`、`duckdb` **三个都没装**，
所以 J.4 那一节是"照实写成跑不通"的，而不是省略掉的。
能实跑的部分（Arrow 侧）每一句都有本机输出跟着。

## J.2 Arrow 的零拷贝有两条路，而且它们不等价

Arrow 有一个跨语言的 ABI，叫 **C Data Interface**。
它做的事情很具体：**让两个不同语言/不同库的实现共享同一块内存，
而不经过序列化。** 这是 Arrow 生态里"零拷贝"的物理基础，
不是一句形容词。

它有两个入口，名字只差一个词，语义却不同：

**`__arrow_c_array__`** 导出**一个** `ArrowArray`（一块连续的列式内存）。
适合"我已经算完了一个批次"这种场景。

**`__arrow_c_stream__`** 导出**一个** `ArrowArrayStream`——
注意它是一个**流的接口**，带 `get_schema` / `get_next` / `release`
三个函数指针。它不是"一块内存"，是"一个可以反复问的游标"。

**这个区分不是学术细节，它决定了消费方能怎么用。**
拿到 array 的人只能同步地立刻读完；拿到 stream 的人可以
一边拉一边处理，也可以只读前几批就放手。附录 I 讲的
拉模型（`to_batches()` 那个 `RecordBatchReader`）**就是 stream 语义**，
而 array 语义是它的退化情形。

**两条路都实现才叫"完整支持"。** 只实现一条的库，
在某些消费方那里会静默降级到"先物化再传"——
你调用的 API 没变、结果没变、只是多了一次全量复制。

## J.3 实测：LanceDB 的查询结果导出的是哪一条

把一个查询结果拿到手，看它身上有哪个方法：

```python
r = t.search([1.0, 1.0]).limit(5).to_arrow()
print(type(r))                      # <class 'pyarrow.lib.Table'>
print(hasattr(r, "__arrow_c_stream__"))   # True
print(hasattr(r, "__arrow_c_array__"))    # False
```

**`stream` 有、`array` 没有。** 这是本机 0.40.0 的实测结果，
一句话概括：**LanceDB 的结果导出走的是流式那条路。**

这个结果是对的，不是缺陷。理由在附录 I：LanceDB 的执行是拉模型，
结果本来就是一段一段来的，**用一个流接口去描述它，
比强行物化成一块连续内存更贴近它的真实形状**。
真要说代价，是消费方必须处理"分批到达"这件事——
但这件事在第 19 章讲 `limit` 下推时已经出现过一次了，
它是这个引擎的固有性质，不是导出时才冒出来的。

**验证它真的能零拷贝地用起来**，最有说服力的办法是
**拿 pyarrow 自己重新接一遍**。如果中途有复制，
行数是藏不住的：

```python
import pyarrow as pa
reader = pa.RecordBatchReader.from_stream(tbl)
print(sum(b.num_rows for b in reader))     # 5
```

能读回来、行数对得上，说明这个接口不是摆设
（很多库的 `__arrow_c_*__` 只实现了导出的一半，
对方一调就 `NotImplementedError`——**看到方法存在不等于它可用**，
这条纪律在附录 G 里已经立过一次）。

再往里看一层，Arrow 的缓冲区确实是共享的：
`r.column("vector").chunk(0).buffers()` 拿到的 `Buffer`
指向的是同一块内存，不是副本。**"Arrow 内部零拷贝"是成立的**，
这一点不受 LanceDB 影响——它只是没在这条路上加一层复制。

## J.4 本机跑不通的那三个：`to_pandas` / `to_polars` / `to_df`

查询构建器上有三个"直接出 DataFrame"的终结方法。本机三个都跑不通，
而且**失败的方式不一样**，这个差别本身有信息量：

```
to_pandas: ModuleNotFoundError: No module named 'pandas'
to_polars: ModuleNotFoundError: No module named 'polars'
to_df:     UnsupportedWarning: to_df is unsupported as of 0.4.0. Use to_pandas() instead
           ModuleNotFoundError: No module named 'pandas'
```

**`to_pandas` / `to_polars` 的报错是"缺依赖"**，装了就通。
这两个方法和 `to_arrow()` 的关系不是"另一条路"，
而是**在 Arrow 之上再包一层**：`to_pandas()` 内部还是要
先把 Arrow 表拿出来，再走 pandas 自己的 Arrow→DataFrame 桥。
所以它们的性能上限**由 Arrow 那一层决定**——
Arrow 是零拷贝的，这一层就是零拷贝的。

**`to_df` 的报错里多一条警告，那才是重点。**
`to_df is unsupported as of 0.4.0` 是一条**弃用**，不是缺依赖。
也就是说不装 pandas 的情况下它先警告、再报错；
装了 pandas 它也会警告。**`to_df` 这个名字不要再用**，
它现在只是 `to_pandas` 的旧名（附录 D 的弃用清单里有它）。

**这里要照实说清一件事：pandas / polars / duckdb 三个包本机都没有，
所以"LanceDB 到这三家的零拷贝到底成不成立"，
本书没有实测。** 能确认的只有条件那一半（Arrow 侧是零拷贝的、
导出走 stream 接口），**结论不能外推**。
要自己验的话，办法是比内存而不是比时间：
`to_arrow()` 之后量一次进程 RSS，再喂给消费方量一次——
**零拷贝的话 RSS 不该有明显增长**。比耗时没用，
耗时差几毫秒可能只是缓存命中，而复制一份 1 GB 的数据
在耗时上是看不出来的。

## J.5 "格式层互操作"和"API 层互操作"是两条不同的路

第 26.6 节划了一条线，这里把它和零拷贝接上，因为两者经常被混为一谈。

**API 层互操作**指"用 Python 把数据读出来、交给别人"——
也就是 J.3 和 J.4 讲的全部内容。它的带宽上限是内存带宽，
代价是一次可能有、也可能没有的复制。

**格式层互操作**指"**别的引擎直接读 Lance 文件**"——
DuckDB、DataFusion、Spark、Trino 这些通过 Lance 的扩展
自己去解析 `.lance` 文件，**完全不经过 LanceDB 的 Python API，
也不经过你的进程**。

**这两条路的性能模型完全不同，不能拿一条的数字去推另一条。**
API 层无论怎么优化，数据都必须穿过 Python 进程的内存；
格式层只要那个引擎实现了 Lance 的 reader，就是它自己按自己的
并行度去扫，**你的进程从头到尾不参与**。
所以第 26.6 节那句"这条路径和 Python API 是两回事"
不是措辞讲究，是两套完全不同的工程。

**这也解释了一个常见困惑**：为什么会有人问"能不能不用 LanceDB
只用 Lance"。**能**——格式层那条路本来就不需要 LanceDB，
LanceDB 提供的是索引、版本、事务和查询规划这一层。
第 1.2 节讲的"把它当成格式还是当成数据库"，
在互操作这一层有最直接的技术后果。

**本机验证不到格式层**：这一层需要别的引擎装 Lance 扩展，
而 pandas / duckdb 都没装，所以本书对格式层互操作一律标"引用文档"。
**这是本书里少见的、缺口比正文大的地方**，宁可标清楚，
也不拿 API 层的数字去冒充。

## J.6 Arrow Flight：为什么它不是"更快的 `to_arrow`"

第 29 章把 Arrow Flight 放在"未来方向"里，正文再没提过。
这里把它的定位说清楚，因为**把它当成"网络版的 `to_arrow`"
是最常见的误解**。

Flight 是 Arrow 生态里的一个 **gRPC 传输协议**，
它把 C Data Interface 那套零拷贝语义从"同进程"扩展到"跨网络"。
**关键差别在"谁去取数据"**：`to_arrow()` 是你在本地进程里
调一个函数；Flight 是**你连到一个服务端、由服务端去读数据**。

所以在 LanceDB 的语境里，Flight 解决的问题不是"传输更快"，
而是**"计算发生在哪里"**——数据在云上、你不想把它拉到本地
（或者拉不动）的时候，让服务端读、只把结果传回来。
这和"无服务器"那个定位是同一件事的两面（第 1.4 节）。

**本机实测的边界很清楚**：`lancedb` 的顶层命名空间里
**没有任何 `flight` 相关名字**，`LanceTable` 上也没有；
`pyarrow.flight` 这个协议实现本身**是装着的、可用的**。

```
lancedb 顶层 flight 名字:  []
表上的 flight 名字:        []
pyarrow.flight 可用:       True
```

**读法是这样的：传输这一端（客户端）在 Arrow 手里，
而那一端（LanceDB 的服务端）在 OSS 里不存在。**
所以"用 Flight 查 LanceDB"在开源版不是一个开关，
它要有一个提供 Flight 端点的服务——这正好落在
附录 G 那张"哪些是开源版没有的"清单的同一类里。

**顺带纠正一个容易混的说法**：把 Flight 和"零拷贝"连在一起讲时，
必须补一句——**零拷贝在 Flight 里指的是"两端都是 Arrow 实现时
可以共享缓冲区"，不是"网络上不传字节"。** 跨进程跨网络，
字节总是要走的；省掉的是**序列化和反序列化**这一步。
把它说成"不传数据"是错的。

## J.7 零拷贝的代价：它借出的是所有权

零拷贝听起来只有好处，实际上它换来的是一个约束：
**buffer 的生命周期必须比使用方长。**

C Data Interface 的协议里有一个 `release` 回调，
交付方把内存交出去的时候同时交出一个"什么时候能回收"的承诺。
消费方如果**不调 `release` 就丢掉引用**，那块内存会一直挂着；
反过来，如果交付方在消费方还在用的时候提前回收了，
就是悬垂指针——在 Rust 侧是 unsafe 边界，在 Python 侧
通常表现为一个很难复现的崩溃或读到脏数据。

这解释了两条实践上的纪律：

**第一，"零拷贝"的收益要用内存量、不要用耗时来验证。**
J.4 末尾给的就是这个办法。时间是噪声很大的量，
而"多了一份 1 GB"是确定的。

**第二，`RecordBatchReader` 这类对象不要跨线程乱传。**
J.3 里那个 stream 接口是有状态的游标，
它的 `get_next` 不是幂等的——两个线程同时拉会把批次分走。
附录 G 讲的异步接口是另一种情况（那边是显式的 `await`），
但**"看起来能并发"和"真的能并发"之间的落差**是同一条教训。

**第三，分批的粒度是有下限的。** 附录 I.5 量过
`to_batches(batch_size=7)` 得到 15 个批次——每一批都带一份
Arrow 的 schema 和缓冲区头。**批次切得太碎，元数据的开销会盖过
"流式省下的内存"**，这也是为什么 pyarrow 那个默认值给的是
131072 行（附录 H.5 那张表用的就是这个数）。
**零拷贝省的是数据复制，不是固定开销。**

## J.8 本实现为什么没有这一层

本实现**完全没有实现 `__arrow_c_array__` / `__arrow_c_stream__`**，
第 5.1 节提过这一点，这里说清为什么不补。

**第一，它的收益在单进程里体现不出来。** 本实现是纯 Python，
结果本来就以 `list[dict]` / numpy 数组的形式在内存里，
"零拷贝交给 pyarrow"省下的那一次复制，
和它自己做距离计算的开销比是零头。**优化不改变瓶颈的部分，
是在给读者制造失真的比例感。**

**第二，也更重要：C Data Interface 的正确性无法用
"往返测试"验出来。** 这是第 4.7 节那个教训的另一副面孔——
当时自己实现的 LZ4 写出了一个谁也读不了的文件，
而自洽的往返测试没发现它，最后靠和 C 实现对拍才抓住。
零拷贝比那件事更难：**它的失败模式是所有权错误，
而所有权错误的暴露需要"内存被复用了"这个前提**，
在一份小数据的短命进程里几乎不可能触发。
**写一个看起来能用的实现很容易，写一个所有权正确的很难。**

所以本实现的选择是**不写**，并且在第 5.1 节点明这个缺口。
这和第 4.7 节"宁可对拍也不要自洽"是同一个立场：
**做不到可验证，就不要假装做到了。**

## J.9 小结

**Arrow 的零拷贝有两条路，`array` 和 `stream`，语义不同。**
LanceDB 的结果导出走 `stream`（实测 `__arrow_c_stream__` 有、
`__arrow_c_array__` 没有），这和它的拉模型执行是一致的，
不是缺陷。

**"Arrow 内部零拷贝"和"LanceDB 到你的 DataFrame 零拷贝"
是两个断言，要分开验。** 前者本机确认了；
后者因为 `pandas` / `polars` / `duckdb` 都没装，
**本书没有实测结论**——条件那一半成立，结论不外推。

**`to_df` 已经弃用**（`UnsupportedWarning: to_df is unsupported
as of 0.4.0`），用 `to_pandas`。三个方法的报错方式不同这件事本身
就是信号：缺依赖和已弃用是两种问题。

**API 层互操作和格式层互操作是两条路。** 前者数据必须穿过
你的 Python 进程；后者是别的引擎直接读 Lance 文件，
你的进程不参与。**不能拿一条的数字推另一条。**

**Flight 解决的是"计算发生在哪里"，不是"传输更快"。**
开源版的 Python 侧没有任何 Flight 端点（实测顶层和表上都是空），
`pyarrow.flight` 装着但对面没有服务端。

**零拷贝借出的是所有权。** 它省掉数据复制，不省固定开销，
也不能用耗时来验证——**要验就量内存。**

到这里，正文和前面这些附录讲的都是"这个系统怎么工作"。
还有一层是"**这套东西怎么用久了不出事**"——
删除和更新在版本链上留下什么、压实什么时候该跑、
清理旧版本为什么必须留窗口、以及那些"写成功了、当时不报错、
事后才炸"的事故长什么样。那是第 23 章和附录 E 的主题，
也是读到这里最该回头重看的两处。
