# 附录 K　失败与重试：哪些错误该重试，哪些重试只会更糟

## K.1 这一篇补的是哪一层

附录 D 那份坑清单有 55 条，每条都带一个**症状标签**——
【报错】【静默】【崩溃】【文档偏离】【行为差异】。那是"**出了什么事**"。

这一篇补的是另一个轴：**出了事之后该怎么办。** 具体是两个问题——
"这个异常属于哪一族"（决定你怎么写 `except`）和
"它该不该重试"（决定你的重试逻辑是救命的还是帮倒忙的）。

这个轴在全书里一直没有正面出现过，但它散落得到处都是：
第 8 章讲提交冲突要重试、第 25.4.3 节讲重试次数要点明是谁的默认值、
附录 D 顺口提过 `RustPanic` 不该重试而 "too many concurrent writers" 该重试、
附录 G 则列了一整张 `NotImplementedError` 的清单。
**每一处都对，但读者拼不起来一张完整的图。**

拼不起来的代价很具体。**重试逻辑的形状完全取决于错误的分类**：
把"参数写错了"当成可重试的，你会把一个必然失败的请求发 N 遍；
把"暂时性冲突"当成致命错误，你的写入会在高并发下无谓地失败。
两类错误在日志里都是"报错了"，**光看有没有报错分不出来**。

验证环境照旧：`lancedb 0.40.0` + Python 3.14.6 + pyarrow 26.0.0，
没有 `pylance` / `pandas` / `polars`。下面的分类来自**十个探针的实测**，
不是从文档的异常表里抄的——事实上 `lancedb` 的 Python 侧
**没有导出任何自定义异常类**（`lancedb.exceptions` 里是空的），
所以这件事只能靠跑出来。

## K.2 实测：几乎全是 `ValueError`

对一张两列的小表（`id: int64`、`v: list<double>`）连着制造几种失败，
把异常类型和原文记下来：

```
打开不存在的表      -> ValueError: Table 'nope' was not found
建同名的表          -> ValueError: Table 't' already exists
删不存在的表        -> ValueError: Table 'nope' was not found
删不存在的索引      -> RuntimeError: lance error: Lance index not found: name=nope, ...lance-13.0.0\src\index.rs:1891:24
在不存在的列上建索引 -> ValueError: Schema Error: Field path `nope` not found in schema. Available field paths: id, v, v.item
过滤器语法错        -> ValueError: Invalid input, Error parsing statement: SELECT 1 FROM t WHERE id >>> 1 (sql parser error: ...)
过滤器引用不存在的列 -> ValueError: Invalid input, Schema error: No field named nope. Valid fields are `id`, `v`.
查询向量维度不对    -> ValueError: There is no vector column in the data. Please specify the vector column name for vector search
merge_insert 缺键列 -> ValueError: Invalid input, Merge insert key column 'nope' does not exist in schema
add 缺一列          -> （没有异常，见 K.5）
```

**九个探针里八个是 `ValueError`，剩下一个是 `RuntimeError`。**
这个分布本身是第一条结论：**`lancedb` 的 Python 层几乎不定义自己的
异常类型**，它把 Rust 侧的错误压平成 Python 的内建异常。
后果是**你没法靠 `except` 的类型去分辨"我参数写错了"和"数据有问题"**——
两种都可能是 `ValueError`，要区分只能看消息文本，而文本是不稳定的契约。

**所以正确的做法是反过来的：不要用 `except ValueError` 去接业务失败。**
`ValueError` 在这里的含义是"**这次调用不会成功，重试也没用**"，
它应该往上冒、冒到你的顶层错误处理里去，而不是被一个宽泛的
`except` 吞掉之后重试三遍。这是这一篇最实用的一条。

## K.3 四个异常族

把十个探针和前面几篇的实测合起来，实际会遇到的只有四族，
**每一族的"意思"是固定的**，记住这四句就够了。

**`ValueError` —— 你的输入或你的查询有问题。** 上面八个都是。
唯一的正确反应是**不要去重试**，把消息原样带给调用方或写进日志。
它不区分"参数名写错"和"表名写错"，所以别指望按类型分流。

**`RuntimeError` —— Rust 侧报上来的错。** 特征是消息里有
`lance error:` 前缀和**一个 crate 文件路径加行号**。
这一族**是可重试性唯一真正分裂的一族**：同一个 `RuntimeError`
既可能是"索引不存在"（重试一万次也不会出现），
也可能是 I/O 抖动（重试一次就好了）。**分辨办法是看消息里有没有
`LanceError(IO)`**——第 6 章讲的对象存储抽象那层，这类错误是它的主场。

**`NotImplementedError` —— 这个能力在你这套部署里不存在。**
附录 G §G.9 那整张清单都属于这一族，消息统一长成
`LanceDBError: not supported: <某个操作> is not supported by this database`，
覆盖 SQL、密钥、UDF 目录、视图、作业管理。**永远不要重试**，
重试不会让一个缺失的能力长出来。**但要注意它和 `ImportError` 的区别**：
前者是"这版没有"，后者是"你机器上没装"，后者的解法是 `pip install`。

**`ImportError` —— 缺可选依赖。** `pylance`（`to_lance()` / `compact_files`
/ `cleanup_old_versions`）、`pandas`（`to_pandas()`）、
`polars`（`to_polars()`）都走这一族。消息里会直接给出安装命令，
**照做就行，也不该重试**。

**这四族之外还有一族在第 0.6 节提过：进程直接崩。**
`fork` 之后用 Lance、或者在一台不支持 AVX2 的老 x86_64 上
`import lancedb`，都是**段错误级别的失败**（附录 D 第 33、34 条）——
**它连 `except` 的机会都不给你**，所以重试逻辑在这里完全无效，
只能靠进程外部的监督（第 25.5 节的进程模型）。

## K.4 该不该重试：按"谁错了"分，不按类型分

把上面四族重新按**归责方**排一遍，可重试性就一目了然了。

**归责于"调用方"的，一律不重试。** 参数写错、列名不存在、SQL 语法错、
维度不匹配、表已存在——这些都是确定性的，同样的输入永远是同样的结果。
**这一类的正确写法是"快速失败 + 消息带全上下文"**，
而 `lancedb` 的消息质量在这一类上其实相当好（K.6 会讲）。

**归责于"环境"的，一律重试，而且必须带抖动的指数退避。**
对象存储的 5xx、连接重置、限流——特征是 `LanceError(IO)`。
注意第 6 章那条纪律：**限流是对象存储的常态，不是故障**，
所以这一类的重试不是补丁，是设计的一部分。

**归责于"并发"的，重试但要带上限。** 这是第 8 章整章的主题，
也是唯一一类"重试次数本身是个可调参数"的失败。
它的特殊性在于：**冲突的概率随并发写者数上升，而重试本身
又增加并发**——所以无上限重试是一种自我强化的拥塞。
第 25.4.3 节给的那三个数字（3 / 20 与 60 秒 / 12 与 2.5 分钟）
就是三个不同层对这个上限各自的答案。

**归责于"缺失能力"的，不重试，但要降级或报清楚。**
`NotImplementedError` 和 `ImportError` 属于这一类。
它们的处理方式不是重试，是**启动时探测、把失败提前**——
这也是附录 G 反复在做的"哪些能力只在云端有"那张清单的用处。

**一句话总结：可重试性跟着"归责方"走，不跟着异常类型走。**
而 `lancedb` 恰好**没有给你按类型分流的工具**，所以只能按消息内容判断。
这听起来糟糕，但有一个补偿：真正该重试的那两类
（I/O 抖动、并发冲突）**恰好都有稳定的文本标记**
（`LanceError(IO)`、`too many concurrent writers`），
而它们都来自 Rust 侧、不是 Python 侧的措辞。

## K.5 最危险的一类失败：没有异常

前面九节讲的都是"报错了怎么办"。真正需要单独拎出来的是反面：
**该报错却什么都没报。**

**第一个例子，实测出来的：`add()` 少给一列，静默填 `null`。**
对一张 `id: int64, v: list<double>` 的表执行
`t.add([{'id': 99}])`——**没有异常、没有任何警告**，
行数从 3 涨到 4，读回来是：

```
[{'id': 0, 'v': [0.0, 1.0]}, ..., {'id': 99, 'v': None}]
```

**这一行的向量是 `None`。** 对一个向量库来说，这意味着一行
"存在但没有向量"的数据，而它会一路影响到后面所有环节：
它进不了任何 ANN 索引（第 12.6 节的 `num_unindexed_rows` 会把它算进去）、
它出现在 `count_rows()` 里、它在暴力兜底扫描里要么被跳过要么报错。
**而你从头到尾没收到任何信号。**

这条和附录 D 第 18 条（`merge_insert` 缺列写 null）是**不同的入口、
同一种形状**：`merge_insert` 那条至少在某些情况下会失败，
这一条**连失败都省了**。写 ETL 的时候，一个上游字段改名、
下游 `add()` 悄悄写出一批 `None` 向量，是最典型的
"跑了两周才发现"的事故。

**防御办法只有一个：写入前自己对 schema。**
`t.schema` 拿得到字段清单（实测输出 `id: int64` / `v: list<item: double>`），
**把它和你这一批字典的键集对一遍**，这件事应该在应用层做，
不要指望库替你拦。

**第二个例子，也是实测出来的：并发写冲突通常不会变成异常。**
8 个线程各往同一张表写 40 批，每批 1 行，跑完是：

```
rows: 321 (expect 8*40+1 = 321)
errors: 0
```

**321 行，一行不少，零异常。** 冲突确实发生了——但它被
提交协议内部的重试吃掉了（第 8.2 节那套乐观提交）。
**你观察到的是"变慢了"，不是"报错了"。** 这条对监控的含义很直接：
**在写入路径上，"错误率"是一个会骗人的指标**，
并发压力上去的时候它可能纹丝不动，而延迟已经在涨。

同一次实验还留下了一串 **WARN 日志**，它们比上面那个 0 更有意思：

```
WARN lance_table::io::commit] Failed to write version hint file for version 12:
  ...latest_version_hint.json: 拒绝访问。 (os error 5)
```

**`latest_version_hint.json` 的写入在并发下失败了，而整个操作成功了。**
这正是第 7.3 节把它称作"一个刻意的缓存"的意思——
**它是可以安全丢失的**：丢了就退化成"多读一次目录列表"，
不会丢数据。这串 WARN 就是那句话的现场证明。
（`os error 5` 是 Windows 上的"拒绝访问"，同一个临时文件被多个写者
抢着重命名；换到 Linux 上不一定能复现，但**"可以丢"这个性质不变**。）

**两个例子合起来是这一节的结论：这个系统里最危险的失败
不是抛出来的那个，是没抛出来的那个。** 而它们恰好都不在
异常体系里——所以"看有没有报错"这条最常见的正确性检查，
在这一层是不成立的。

## K.6 错误消息里有三样比类型更有用的东西

既然类型不可靠，就得会读消息。实测下来，`lancedb` 的消息里
**有三类信息是别的库不会给的**，排查时优先找它们。

**第一类是"可用值清单"。** 列名写错时报的不是"字段不存在"，
而是 `Available field paths: id, v, v.item`——**它把合法的名字列出来了**。
`merge_insert` 缺键列、过滤器引用不存在的列，报的都是这种形状。
注意最后那个 `v.item`：**它连嵌套子列都列出来了**，
这正是第 5.3 节讲的"结构化解开"在错误信息里的投影。

**第二类是"你的查询被编译成了什么"。** 过滤器语法错的时候，
消息里会带上一条完整的 SQL：

```
Error parsing statement: SELECT 1 FROM t WHERE id >>> 1 (sql parser error: ...)
```

**这直接证实了第 11 章和第 19 章反复说的那件事：`where()` 里的
字符串最终是被编译成 SQL 的。** 附录 I.2 从 `analyze_plan()` 的
DataFusion 算子名推出过同一个结论，这里是第二条独立证据。
**排查"为什么这个过滤器没生效"时，这条编译后的 SQL 比 `where()` 的原文
更有用**——你能一眼看出优先级是不是和你想的不一样。

**第三类是 Rust 侧的 crate 路径和行号。** 删不存在的索引时报的是
`.../lance-13.0.0/src/index.rs:1891:24`。这和第 0.6 节讲的
"三种版本号"接上了：**Python 包是 0.40.0，底下的 Rust crate 是 13.0.0，
两个号独立演化**。报错串里的这个路径是定位源头的直接线索，
比 Python 的 traceback 更有用——**traceback 到此为止只有一层包装**。

**反面也要说一句：不是所有消息都这么友好。**
查询向量维度给错时的消息是
`There is no vector column in the data. Please specify the vector column name
for vector search`——**这句话是误导的**：表里明明有向量列，
问题是维度对不上导致它没被认出来。**照这条消息去"指定列名"会
把你带偏**，而 `Available field paths` 那种消息不会。
所以读消息的时候还要多一层判断：**它在描述现象，还是在描述原因。**

## K.7 本实现的异常体系：一次刻意的反向选择

`mini_lancedb` 在这一层上**和真实库做了一个相反的选择**：

它有**一个根异常 `MiniLanceError` 加按阶段分层的十几个子类**
（`SchemaError` / `TypeMismatchError` / `StoreError` / `CommitConflict` /
`PlanError` / `IndexBuildError` …，完整清单在附录 A §A.19）。

也就是说：**真实库把一切压平成 `ValueError`，本实现把一切细分下去。**
这不是"本实现做得更好"——**两个选择各有一个明确的代价**。

**真实库的选择换来的是 API 表面稳定。** 用户不需要 import
一堆异常类、不需要担心版本升级时异常类改名。
代价是**调用方拿不到结构化的信息**，只能解析文本——
而文本不是契约，随时可能变。

**本实现的选择换来的是可测。** 因为有类型，
测试里可以断言 `pytest.raises(TypeMismatchError)` 而不是
匹配一段消息——**这一点直接服务于附录 E 讲的验证纪律**：
按消息匹配的断言会在消息措辞变动时假失败，或者更糟，
在措辞**碰巧相似**时假通过。按类型断言没有这个问题。

**代价同样明确：迁移时会断。** 附录 A §A.20 和附录 C §C.5
都点名了这件事——把 `except MiniLanceError` 搬到真实库上，
**一个都接不住**。所以本实现的异常类**只在本实现内部有意义**，
它们是"教学脚手架"而不是 API 的一部分。

**这也是为什么这一篇的主体是"怎么读消息"而不是"怎么接异常"**：
在真实库上你只有消息，本实现那套分层是学"该怎么设计"的样本，
不是能直接搬过去的资产。**分得清这两件事，是这一篇的最后一层。

## K.8 小结

**`lancedb` 的 Python 层不导出自定义异常。** 十个探针里八个是
`ValueError`、一个是 `RuntimeError`。**不要用 `except ValueError`
接业务失败**——它在这里的意思是"这次调用不会成功"。

**四族各有固定含义。** `ValueError` = 你的输入错了，不重试；
`RuntimeError` = Rust 侧报错，**看消息里有没有 `LanceError(IO)`
来决定重不重试**；`NotImplementedError` = 这版没这个能力；
`ImportError` = 机器上没装这个包。**后两族都不是重试能解决的。**

**可重试性跟着归责方走，不跟着类型走。** 调用方的错不重试、
环境的错必重试、并发的错带上限重试、能力缺失的错降级不重试。

**最危险的是没有异常的那一类。** `add()` 少给一列会**静默写 `null`**；
并发写冲突会**被内部重试吃掉**，8 个线程写 321 行零异常。
**"没有报错"在这个系统里不构成正确性证据。**

**消息里有三样东西比类型有用**：可用字段清单（连嵌套子列都列）、
编译后的 SQL（证实了 `where()` 走 SQL 编译）、
Rust crate 路径加行号（底下的 `lance` 是 13.0.0，不是 0.40.0）。
但它也会误导——维度写错时那条 "no vector column" 就是。

**本实现和真实库在这一点上选择了相反的路线**：真实库压平成内建异常，
本实现细分成 `MiniLanceError` 体系。前者 API 稳定但不可结构化处理，
后者可测但**迁移时一个都接不住**。**本实现的异常类只在本实现内部有意义。**

到这里，这份教程的十个附录构成了一个完整的"背面"：
F 讲派生数据、G 讲客户端运行时、H 讲数据怎么进来、
I 讲引擎里数据怎么流、J 讲数据怎么出去、K 讲出错时该怎么办。
它们和 30 章正文合起来，覆盖的是一个存储引擎从字节到生产
的每一层——**而每一层里那些"文档说 A、实际是 B"的地方，
都标了是本机实跑还是引用文档。**
