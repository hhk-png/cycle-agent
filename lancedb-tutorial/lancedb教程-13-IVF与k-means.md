# 第 13 章　IVF 与 k-means

向量检索这件事，在数据量小的时候根本不需要"算法"。把所有向量装进一个矩阵，
查询时做一次矩阵乘法，取距离最小的 k 个，就结束了——快、准、代码五行。
问题出在数据量涨上去之后。

## 13.1 先算一下暴力检索到底有多贵

假设有 100 万条 768 维的向量（这是 OpenAI `text-embedding-3-small` 之类的
模型很常见的规模），一次查询要算多少次乘加？

```
100 万 × 768 = 7.68 亿次乘加
```

这不是"大概有点慢"。在一个单核每秒 100 亿次浮点运算（10 GFLOP/s，
每次乘加算 2 FLOP）的机器上，**一次查询就要 154 毫秒**。而这只是算数的时间，
还没算把这批向量从内存里读一遍的内存带宽成本——实际上内存带宽往往是
真正的瓶颈：库侧向量本身是 3.07 GB，在 50 GB/s 的带宽下光读一遍就要 61 毫秒，
和算力成本是同一个量级。

更糟的是这个数字随 n **线性**增长。1000 万条就是 1.5 秒一次查询，
1 亿条就是 15 秒。延迟撞墙的位置远早于内存撞墙的位置：单机内存还能装下
1 亿条 768 维向量（307 GB，得上服务器），但没人能接受 15 秒的查询延迟。

这里有一条重要的经验：**暴力检索的性能是"每查询 O(n·d)"，
而任何可用的检索系统必须在 n 增长时保持延迟基本不涨。**
这就是"近似最近邻"（ANN）存在的全部理由——用可控的精度损失，
换查询复杂度从 O(n) 降到 O(log n) 或 O(1) 级别的常数。

## 13.2 IVF 的想法：先分桶，再只搜几个桶

IVF（Inverted File，倒排文件）是整个"亿级向量检索"体系的地基，
它的想法朴素到一句话能说完：

**先用 k-means 把全量向量聚成 P 个簇，每个簇的中心叫质心。
查询时先看查询离哪个质心最近，只在最近的几个簇里找。**

"最近的几个簇"里的"几个"就是 `nprobes`。于是单次查询的成本从

```
O(n · d)                        暴力
```

变成

```
O(P · d)  +  O(nprobes/P · n · d)      IVF
```

第一项是"查询到所有质心的距离"——它和 n 无关，只和分区数 P 有关，
而且 P 通常取 `sqrt(n)` 量级，所以这一项虽然不能忽略，但很小。
第二项才是大头：只在 `nprobes/P` 比例的数据上算距离。

取 P = 1000、nprobes = 10，就只看 1% 的数据。在我们的实测里，
20 个分区上探 1 个桶（5.7% 的候选）就能拿到 `recall@10 = 0.98`。

代价是**真正的最近邻可能落在没有探到的桶里**。这不是实现 bug，
而是算法本身的近似来源，也是"召回率"这个指标存在的原因。
有意思的是这个损失通常很小：k-means 的桶在空间上确实是聚簇的，
所以第 2、第 3 近的桶里装的东西，和第 1 近的桶高度相关。

这个损失有一个**在固定 `nprobes` 下的硬上界**：召回率不会超过"真近邻里
落在被探测桶内的比例"，而这个比例正随 `nprobes` 变——候选集就是被选中的那
`nprobes` 个最近桶的并集，多探一个桶，桶外的真近邻就少一些、上界就高一截。
对每一次具体的查询它又是硬的，而且是计数问题不是概率问题：候选集就是所选桶
的并集，桶外的向量根本没有被算距离的机会，`refine_factor` 再大也救不回来
（refine 只能重排候选，不能把桶外的行拉进来）。所以要估这个天花板，只需问
"每条真近邻进探测桶的概率是多少"。做一个**悲观**假设：
向量落在哪个桶和它离查询多远无关，那么每条真近邻进探测桶的概率就是
`nprobes/P`（P=20、nprobes=1 时是 5%），`recall@k` 的期望也就是这个数。
实测比它高得多：随机数据上 nprobes=1 是 0.2425（§13.9），聚簇数据上是
0.98——因为"离查询最近的几个桶"本来就比随机桶更可能装真近邻，
独立性假设太悲观。真实 embedding 落在两者之间：既不是纯噪声，
也不是 20 个完美的球。

实现上数据被存成**倒排链表**：每个桶维护一个"属于我的行号列表"。
在 mini 实现里这个结构是 CSR（`partition_offsets` + `partition_members`
两个数组），而不是"每个桶一个 Python list"——因为查询时要做的操作是
"把选中的几个桶的成员拼起来"，CSR 上就是两次切片加一次 `concatenate`，
而且它天然可以序列化成两个数组。

这套结构的开销不大，但要会算：`partition_members` 是"每行一个行号"，
1 亿行在 int32 下就是 **400 MB**；`partition_offsets` 只有 `P+1` 个整数，
可以忽略；质心矩阵是 `P × d × 4` 字节（P=1000、d=768 时约 3 MB）。
**这几百 MB 是索引本身的开销，和"压不压缩向量"无关**——`IVF_FLAT`
省下来的只是"少算距离"，一条向量的字节数一个都没少，内存反而比暴力检索
多出这张行号表。真正省内存要靠第 14 章的量化。

**真实 Lance 的一个关键实现细节：分区不是一个文件一个分区，而是同一个索引文件里的行区间。**
`IvfModel` 只存 `centroids`（质心矩阵）、`offsets`（每个分区在文件里的行偏移）
和 `lengths`（每个分区的行数），读第 p 个分区就是读 `offsets[p] .. offsets[p]+lengths[p]`
这一段行区间（`rust/lance-index/src/vector/ivf/storage.rs:27-41, 143-147`；
读取端 `rust/lance-index/src/vector/flat/storage.rs:606-618`）。
这么做的收益是"打开索引"只需要一次元数据读取，而不是列 P 个目录、
发 P 次请求。教程里常见的"IVF 是每个分区一个文件"的说法是错的。

## 13.3 k-means：比调包时看到的多得多的细节

IVF 的粗量化就是一次 k-means，质心数 = 分区数。k-means 本身是最古老的
聚类算法之一，但**要实现到能用在亿级数据上，有一堆工程细节**，
这些细节恰好是教程里最常被跳过、面试里最常被问到的部分。

**Lloyd 迭代。** 算法本体两步循环：分配（每个点归到最近的质心）
和更新（每个簇的均值成为新质心）。每一步都保证 inertia（簇内平方距离和）
不增，所以它一定收敛——但**收敛到的是局部最优**，而且严重依赖初始质心。

**初始化。** 这是 k-means 最大的分歧点。

本教程的 `kmeans()` 用的是 **k-means++**：第一个质心均匀随机，
之后每个新质心按"到已选质心最近距离的平方"（即 D²）成比例地抽。
`_kmeans_plusplus()` 的注释解释了为什么值得这么做：随机初始化在高维数据上
会频繁收敛到很差的局部最优，而 k-means++ 只要多算几轮距离，
就能把 inertia 降低一个数量级。

**但是——这里必须纠正一个流传很广的误解——真实 Lance 的常规 IVF k-means 路径没有 k-means++。**
它的初始化只有一个枚举（`rust/lance-index/src/vector/kmeans.rs:56-60`）：

```rust
pub enum KMeanInit { Random, Incremental(Arc<FixedSizeListArray>) }
```

`Random` 就是**均匀、无放回地随机抽 k 行**当初始质心
（`kmeans_random_init`，`kmeans.rs:225-246`），没有任何 D² 加权。
`Incremental` 是"用给定的质心当起点继续训练"，供层级细化用。
加权版的 k-means++ 确实存在于代码库里，但它只在**流式 coreset 路径**
（`streaming_sample_rate` 小于 `sample_rate` 时触发，
`rust/lance/src/index/vector/ivf.rs:1771-1813`、`initialize_weighted_centroids`
在 `:4462-4530`）里出现，而且用的是固定种子 `0x1f17_5eed` 以保证可复现。
常规路径用不上它。

所以正确的表述是：**`num_partitions` 走的常规 Lloyd 路径用均匀随机初始化；
只有 coreset 路径用加权 k-means++。** 两种实现都能用，随机初始化之所以
在 Lance 里够用，是因为它后面还有 `redos`、层级 k-means 和 balance factor
三道保险。

**收敛判据是相对的。** 一个很容易写错的地方：`kmeans_has_converged`
（`kmeans.rs:333-339`）判断的是

```
|previous_loss - loss| < tolerance * |loss|
```

也就是**相对变化率**小于 `1e-4`（`tolerance` 的默认值），而不是绝对差。
用绝对差的话，大数据的 inertia 动辄上亿，`1e-4` 的绝对阈值会让它跑满
`max_iters`；用相对阈值才能自适应数据的尺度。**这里的 `max_iters` 默认值
要分清属于谁**：上面那句"默认 50"说的是 **Lance 的 `KMeansParams.max_iters
= 50`**；而**本教程迷你实现的 `kmeans()` 默认是 `max_iters: int = 25`**
（`mini_lancedb/index/pq.py`）——两者不是一回事，别把 50 当成迷你实现的默认值。

本教程的迷你实现用的是绝对判据（`shift <= 1e-5`，即质心位移的无穷范数），
这在教学规模上够用，但**换到真实数据上会过早停止或跑满迭代**，
这是它和 Lance 的一个重要差异。

**`redos`：整个 Lloyd 循环重跑几次，取 loss 最小的那个。**
`KMeansParams.redos` 默认 1（`kmeans.rs:136`），IVF 建库时硬编码
`const REDOS: usize = 1`（`rust/lance/src/index/vector/ivf.rs:3242`）。
因为初始化是随机的，`redos > 1` 就等价于"多试几个随机起点，挑最好的"——
这是对"没有 k-means++"最直接的补偿，只不过 Lance 默认不开。

**层级 k-means：k 很大时的一次结构性拆解。** 单层 Lloyd 每轮是
`O(N·k·d)`，k 到几百上千时既慢、随机初始化也更容易落到坏解。Lance 的
处理是**分层**：`k > 256` 时不直接训 k 个质心，而是先用
`hierarchical_k = 16` 训一层粗质心，再在粗质心基础上细化、拼出最终的 k
（`KMeansParams.hierarchical_k`，`kmeans.rs`）。对应到初始化枚举，
就是前面那个 `Incremental`——"用给定质心当起点继续训练"正是为层级细化
准备的。**教学实现没有这一层**：`default_num_partitions()` 直接取
`sqrt(n)`（上限 256），在这个规模上单层 k-means 够用，这也是迷你实现
和真实 Lance 在"k 特别大"时的又一处差异。

**空簇处理是确定性的，而且很讲究。** 当某个质心一个点都没分到时（k 接近 n
或数据里有大量重复点时很常见），如果不处理，这个质心会永远卡在原地、
浪费一个码字。Lance 的做法分两步（`kmeans.rs:602-681` 与 `split_clusters`
在 `:253-278`）：

1. 空簇的质心先**留成全零**（不是随机重置）；
2. 然后调 `split_clusters`：对每个空簇，找出当前**最大的簇** `j`，
   把它的计数对半砍 `cnts[i] = cnts[j]/2; cnts[j] -= cnts[i];`，
   再把两个质心用一个 `eps = 1/1024` 的**交替符号微扰**分开——
   偶数维 `centroid[i] = centroid[j]*(1+eps)`、`centroid[j] *= (1-eps)`，
   奇数维反过来。

这里的两个设计决定都值得琢磨。**先耗尽最大簇**（而不是随机挑一个簇来劈）
保证了结果与随机数无关，所以带种子的训练是可复现的。
**交替符号的微扰**是为了让两个质心不只在一维上分开——如果只在一维上加 `eps`，
高维空间里它们依然几乎重合，下一次分配会把它们再次合并成同一个空簇。
注释里写得很清楚："先耗尽最大簇保证结果与随机抽样无关"。

本教程的迷你实现用了另一种（同样常见）的做法：把"离自己质心最远的那些点"
搬过来当新质心（`pq.py` 里的空簇重播种）。这也能工作，但它**引入了对数据排序的依赖**，
而且距离最近的点可能扎堆，导致新质心之间又互相重合。
Lance 的做法更稳。另外，本实现的 `kmeans()` 在 k=1 时走闭式解（均值），
省掉一整轮迭代——教学实现里这种小优化很值，因为它让"k=1 时结果精确"
这件事有了保证。

**建索引的时间都花在哪。** IVF 的建索引就是"一次 k-means + 一次全量分配"：
k-means 本体是 `O(N·P·d·I)`（I 是实际迭代轮数），但 Lance 靠采样把参与
迭代的行数压到 `k × 常数` 量级（§13.7），所以真正随数据涨的是最后"把每一
行分配到最近的质心"和倒排链表落盘这两步。本机实测（2 万行 × 64 维、
固定种子，`examples/04_index_benchmark.py`，两遍运行、挂钟时间）：
`IVF_FLAT` 建索引 **1.5 秒左右**（1.52 / 1.61 s）、`IVF_SQ` **同一量级**
（1.48 / 1.56 s，甚至略快，落在噪声里）。`IVF_SQ` 不比 `IVF_FLAT` 贵，
因为它多训的只是一个逐维量化器；同规模的 `IVF_PQ` 要 **10 秒上下**
（9.93 / 10.14 s），多出来的近十秒才是乘积码本的训练（第 14 章 §14.2）。
**"IVF 建索引要跑 k-means"听起来吓人，落到秒级数据上其实很便宜**——
这正是它比 HNSW 系更适合频繁重建的原因：建图是
`O(n·m·ef_construction)` 量级，比 IVF 贵得多（第 15 章 §15.7）。
（这些是挂钟时间，两遍能差一点几倍；量级结论是"`IVF_FLAT`/`IVF_SQ` 秒级、
`IVF_PQ` 十秒级"，别把具体小数当基准。）

## 13.4 num_partitions 怎么选，以及 sqrt(N) 规则从哪来

分区数 P 是 IVF 最重要的结构参数。太小则每个桶很大，
查询时"只搜几个桶"省不下多少；太大则每个桶里的样本太少，
k-means 训练不出好的质心，而且分区边界附近的误判变多。

流传最广的经验规则是 **`P ≈ sqrt(N)`**。本教程的
`default_num_partitions()` 就是这么定的，还加了 256 的上限：

```python
return int(max(1, min(256, round(math.sqrt(max(1, n))))))
```

**那个 256 的上限不是装饰，它很早就开始咬人了。** 因为 `sqrt(N) > 256`
等价于 `N > 65536`，所以只要行数超过 6.5 万，这个函数就恒返回 256：

```
N = 1 千      →  32
N = 1 万      → 100
N = 10 万     → 256      (sqrt 是 316，被上限截到 256)
N = 100 万    → 256      (sqrt 是 1000)
N = 1000 万   → 256      (sqrt 是 3162)
N = 1 亿      → 256      (sqrt 是 10000)
```

**这里有个容易写错的坑，我自己先写错过一次**：`measurements/` 里那段
脚本打印的是**没加上限**的 `sqrt`，于是 10 万行会印出 316、100 万行会印出
1000。如果照抄那份输出，就会得到"函数返回 1000"这个结论——而函数返回的是
256。凡是引用默认值的地方，都要回到 `mini_lancedb/index/_common.py` 的
这一行去核对，不要相信任何二手输出。

在 256 以下，量级关系确实是 `10^(k/2)`：每把 N 放大 100 倍，P 只放大 10 倍。
但这个关系只在小表上成立；超过 6.5 万行之后，本实现的 P 是常数，
**真正随规模变化的旋钮只剩 `nprobes`**——这也是为什么第 24 章的调参
流程把 `num_partitions` 排在 `nprobes` 后面：它在生产规模上多半动不了。

这个规则的来源值得说清楚，因为很多人把它当成"定理"。考虑建索引的成本：
完整的 k-means 对每个点每轮要和 P 个质心算距离，一轮是 `O(N·P·d)`，
跑 `I` 轮就是 `O(N·P·d·I)`。如果只看这一点，P 当然越小越好。

再看查询成本：查询要和 P 个质心比一遍（`O(P·d)`），再在
`nprobes/P · N` 个点上算距离。要让**建索引成本**和**查询成本**平衡，
让"每个分区里的点数"不要太大也不要太小，最优解落在 `P ∝ sqrt(N)`。
更直观的说法是：查询成本里 `P·d` 这一项随 P 线性增长，
而 `nprobes/P·N·d` 这一项随 P 反比下降，两项相等的点就是极值点，
解出来 `P ≈ sqrt(N·nprobes)`，取 nprobes 为常数就得到 sqrt(N)。

**真实 Lance 的做法和 sqrt(N) 不完全一样，值得知道。**
它按"目标分区大小"来算，而不是按 sqrt：

```
recommended_num_partitions = clamp(num_rows / target_partition_size, 1, 4096)
```

上限是 `MAX_PARTITIONS = 4096`，`target_partition_size` 由索引类型决定
（`rust/lance-index-core/src/lib.rs:266-278`）：`IvfFlat` 是 4096、
`IvfPq` 是 8192、`IvfHnsw*` 高达 `1<<20`（因为分区内还有一层 HNSW 图，
分区大一点不影响查询）。这是"按数据量定分区大小"的思路，
和"按 sqrt 定分区数"是同一件事的两种参数化。

**这一段的两半证据强度不一样，得分开标。**
`target_partition_size()` 那三个取值和行号是可以核对的
（就在上面引的那个文件里）；而上面那行
`clamp(num_rows / target_partition_size, 1, 4096)` 的公式形式、
以及 `MAX_PARTITIONS = 4096` 这个名字，**我本轮没有在源码里定位到**——
它是按"实测 2 万行 → 2 个分区、20 万行 → 24 个"这组观察反推出来的，
用 `IvfPq` 的 8192 代进去算确实对得上（`20000/8192 → 2`、
`200000/8192 → 24`），所以**算术自洽，但出处未确认**。
按这份教程的约定，这一句应该带着"未经确认"读——
**和它相邻的那三个数字可以信，这个公式的写法只能当推测。**

## 13.5 nprobes：召回率与延迟的那条曲线

`nprobes` 是 IVF 查询期唯一的精度旋钮。它决定探几个桶。真实 LanceDB 的
默认值是 **20**——这一点可以从执行计划里直接读到，`analyze_plan()` 会给
`ANNIvfPartition: minimum_nprobes=20, maximum_nprobes=Some(20)`。
下面的实测要压着这个默认值看：20 个分区上"探满"正好等于默认行为。

我们的实测（3000 × 32 维、20 个簇、20 个分区、40 条查询、k=10，
数据源固定种子，`IvfIndex` 即 `IVF_FLAT`）：探 1 个桶就有
`recall@10 = 0.9800`、平均候选比例 5.7%；探 2 个升到 1.0000、候选 10.7%；
探 4 个仍 1.0000、候选 23.6%；探 8 个 1.0000、候选 45.0%；探满全部
20 个桶还是 1.0000、候选比例 100%。

三件事值得注意。

**第一，探 1 个桶就有 0.98。** 这不是"IVF 特别好"，而是**这份数据本身聚簇很好**
——20 个真簇对 20 个分区，k-means 几乎完美复原了数据结构。换成真正难的数据，
nprobes=1 的表现会差得多（见 §13.9）。

**第二，候选比例涨得比 nprobes 快，收益却是饱和的。** nprobes 从 1 涨到 8
是 8 倍，候选比例从 5.7% 涨到 45%（慢于 8 倍，因为桶大小不均），
延迟也大致线性上涨。**延迟是线性的、收益是饱和的**——这就是"多探一个桶"
的边际收益递减：前几个桶拿回绝大部分召回率，后面几个桶只是保险。

**第三，绝对延迟数字本身不可当真。** 这些实测在 3000 行上跑，
每条查询的延迟本来就落在亚毫秒级，差别完全被 Python 解释器开销淹没，
要看的是延迟随 nprobes 的**比例关系**。
"召回率是确定性的、挂钟时间不是"这件事在 §13.10 用一次两轮实测讲透，
包括它在更大规模（50000 × 64 维）上的表现，这里不重复。

上面的召回率都隐含一个前提：**桶里装的都是活行。删除会打破它。**
向量索引的候选集是从桶里 gather 出来的，删除掩码是在 gather 之后才应用，
所以被删的行**仍然占着 `nprobes` 给出的候选名额**——这就是第 9 章 §9.4
说的"幽灵行"。删得越狠，桶里活行越少，同样的 `nprobes` 换来的有效候选
越少、召回越低。

**本教程早期版本能直接量出这个代价**：一个删到只剩 20% 的 500 行
`IVF_FLAT`（8 个分区），`nprobes=4` 时索引算了 250 个距离、
其中只有 50 个是有效行，80% 的算力花在幽灵上。
**但现在的实现已经不这样了**——删除时会把索引里的行号一起搬
（`_remap_indices_after_delete`），候选池里不再有死行；
第 9 章 §9.4 有这一条从"翻车"到"修好"的完整经过。
真实 Lance 走的是另一条路：索引保持不可变，用删除文件里的行地址
去过滤索引结果，代价同样落在读取侧。三种做法对应三种工程取舍，
没有哪一种是免费保持召回率的。

**`refine_factor` 是第二个旋钮，但它管的不是"看多少"，而是"算多准"。**
它的语义是：先用**便宜表示**取出 `k × refine_factor` 个候选，
再对这些候选算**精确距离**重排。为什么值得这么做？因为量化打分里
"排序靠前"的部分基本可信，真正容易错的是第 k 名附近的边界——
那里几条候选的距离只差零点几。多取几倍候选做一次精确重排，
通常能拿回量化损失掉的一半以上召回率，而代价只有 `O(k·refine·d)`。

真实 Lance 里 `refine_factor` **要在两个地方都做**才算数
（`rust/lance/src/index/vector/ivf.rs` 的 `lance_ivf_v2.rs:1312-1313` 与
`scanner.rs:6851-6860`）：第一，提交给子索引的 k 被放大 `refine_factor` 倍；
第二，扫描器层把候选的原始向量读回来，用 `flat::compute_distance` 精确重算距离，
并把子索引报的 `_distance` 列**丢掉**。少做第二步，`refine_factor` 就只是个
"取更多候选但用的还是近似分数"的摆设。另外 `Some(0)` 会被显式拒绝
（`"Refine factor cannot be zero"`，`scanner.rs:6825-6829`）。

## 13.6 残差向量：一个只在 L2 / cosine 上成立的技巧

朴素的 PQ（下一章的主题）直接量化原向量 `x`。但 `x` 的分布是**多峰**的——
数据本来就分簇，而 k-means 的码本只有 K 个质心，它得把全部簇的形态
硬塞进一张码本里。更好的做法是先减掉它所属分区的质心：

```
residual = x - centroid[partition(x)]
```

残差集中在原点附近、方差小得多，同样的 K 个码本能描述得精细得多。
在我们的数据上，原向量的平均范数是 18.28，残差的平均范数只有 6.67，
**降到 36.5%**。范数小了，同样的码本点数就摊得更细。

实测的收益（`IVF_PQ`，m=8、8 bit、探满所有桶）：同一个压缩率、同一套
参数，只是把量化目标从 `x` 换成 `x - c`，**对原向量 `x` 的重建中位相对
误差从 0.1596 降到 0.0925，`recall@10` 从 0.465 涨到 0.690**。
这是"零成本的精度提升"里最漂亮的一个例子。完整的对照表、以及测这件事
时最容易踩的坑（"残差版本误差反而更大"其实是个假象），在第 14 章 §14.6。

**但残差只在 L2 和 cosine 上有意义，绝不用在 dot product 上。**
Lance 源码里这个判断写得很直接（`rust/lance/src/index/vector/ivf.rs:1889-1893`）：

```rust
let ivf_residual = if matches!(metric_type, MetricType::Cosine | MetricType::L2) {
    Some(&ivf_model)
} else {
    None
};
```

`use_residual` 在 `lance-index/src/vector/pq/builder.rs:80-82` 里同样
只匹配 `L2 | Cosine`。

为什么？回忆三种度量的定义（`mini_lancedb/index/metric.py`）。
L2 关心的是 `‖x - q‖`，
减掉一个公共的质心 `c` 之后 `(x-c) - (q-c) = x - q`，距离**完全不变**，
所以残差是"免费"的预处理。cosine 在归一化之后等价于 L2，同理。
但 dot product 关心的是 `x·q`，`(x-c)·(q-c)` 展开开来是
`x·q - x·c - q·c + c·c`——**多出来三项，它改变了排序**。
减质心会系统性地惩罚那些和质心同向的向量，这不是"更准"，是"算错了"。

所以：**残差是 L2/cosine 专属的等价变换，对 dot 是一次错误的改写。**
这个区分在只有 L2 的场景下永远暴露不出来，一旦切到 dot 就会静默地错。

**上面那段 Rust 判断，本实现没有照搬——这是一个真实的、会静默出错的差距。**
`mini_lancedb/index/ivf_pq.py` 里 `residual` 的默认值是 `True`
（第 80 行），而 `_pq_targets()`（第 92-99 行）只检查
`self.residual` 和 `num_partitions`，**完全不看度量类型**。
本机实测：用 `metric='dot'` 建一个 `IVF_PQ` 索引**会成功**
（`list_indices()[0].params` 里老老实实写着 `'distance_type': 'dot'`），
加载回来 `residual` 仍然是 `True`：

```
>>> t.create_index('v', config={'index_type':'IVF_PQ','num_partitions':4,
...                             'num_sub_vectors':8, 'metric':'dot'})
>>> idx.residual
True
```

也就是说，**上面那句"绝不用在 dot product 上"在本实现里是一句没有护栏的
警告**。真实 Lance 在 Rust 侧把这条规则焊死在类型判断里，
所以那边的用户不可能违反它；这边的用户必须自己记得不要同时用
`metric='dot'` 和残差 PQ。**这类"文档里写对了、代码里没拦住"的差距，
比"文档写错了"更危险**——因为读者会以为约束已经被实现了。
第 14 章 §14.6 讲残差 PQ 的误差时会再提一次。

## 13.7 Lance 训练器里的三层采样

"在 1 亿条向量上跑 k-means"听起来吓人，但真正拿去训练的样本其实很少。
Lance 的路径上叠了**三层**采样：

**第一层，数据集层。** `build_ivf_model` 把 `sample_size_hint` 设成
`num_partitions * params.sample_rate`（`ivf.rs:1769`），其中
`sample_rate` 默认是 **256**（注释写着"See faiss"，`ivf/builder.rs:96`）。
然后 `maybe_sample_training_data`（`rust/lance/src/index/vector/utils.rs:305-372`）
在数据集上做一次真正的随机采样。这一步决定了"从 1 亿行里抓多少行出来"。

**第二层，`train_kmeans` 里的前缀截断。** 采样之后还要再切一刀：
`kmeans.rs:1961-1999` 会取数据的前 `k * sample_rate` 行。**注意是"取前缀"，
不是"再随机抽一次"**——这是个容易被误读的实现细节。

**第三层，`KMeans::train_kmeans` 里的再截断。** 再往下一层（`kmeans.rs:1063-1067`），
如果数据长度超过 `k * TRAINING_ROWS_PER_CENTROID`，就 `data.slice(0, k*512)`
（`TRAINING_ROWS_PER_CENTROID = 512`）。

三层叠下来，实际参与 k-means 迭代的行数被钉死在 `k × 常数` 的量级。
这个设计的依据是：**质心是数据的统计量**，用一小部分样本估计出来的质心
和全量相比几乎没差别，但训练时间少几个数量级。
我们实测过这件事：用 10% 的样本训练出的质心，拿到**全量**数据上评估，
inertia 是 347.6，而全量训练的基线是 387.0。小样本反而低了 10%——
这**不是"采样更准"**，而是随机初始化带来的波动：两边只差一个随机起点
的好坏，落在同一段噪声带里（k-means 收敛到的是局部最优，起点不同，
inertia 上下浮动这个幅度很正常）。**结论不是"采样精度更高"，而是
"采样精度与全量同量级"**——用 10% 的样本省掉几个数量级的训练时间，
掉的精度可以忽略。

本章（以及 14~16 章）所有数字都可以自己跑出来：
`python -X utf8 measurements/vector_index_measurements.py 13`
（不带参数就跑全部四章）。数据源是固定种子的合成聚簇数据 3000 × 32 维、
20 个真簇，和 `tests/test_index_vector.py` 用的是同一份。

这里还有一个 `MEMBERSHIP_CHUNK_BYTES = 4 MiB` 的常量（`kmeans.rs:795`），
用来控制"分配"这一步的分块大小，避免把整个 `(N, K)` 的距离矩阵
一次性物化到内存里——1 亿行 × 1000 个质心的 float32 距离矩阵就是 400 GB。

## 13.8 分区不均衡，以及它为什么疼

k-means 分出来的桶**从来不是等大的**。在我们的 3000 行、20 分区数据上：

```
桶大小: min=15  median=146  max=306  mean=150
imbalance = max/mean = 2.040
Gini 系数 = 0.1912
```

这里有两个口径的比值，别混。**`max/min = 306/15 ≈ 20.4`** 说的是最大桶
是最小桶的 20 倍；**`imbalance = max/mean = 306/150 = 2.040`** 说的是最大
桶只有平均值的两倍。`partition_size_stats()` 用的是后者，因为它直接决定
最坏情况的查询时间：某个桶是平均值的 2.04 倍，那么探到它的一次查询就要
多算 2.04 倍的距离。IVF 的延迟是由"探到的桶里最大的那个"决定的，不是
平均值——所以真正该盯的是 `max/mean`，而不是听起来更吓人的 `max/min`。

Gini 系数是另一个视角：0 表示完全均匀，0.19 表示已经明显不均。
在真实数据上这个数字经常到 0.4 以上。

Lance 对此有一个专门的机制：**balance factor**。
`compute_balance_loss`（`kmeans.rs:305-308`）在 loss 里加一项
`balance_factor * (Σ size_i² - n²/k)`——`Σ size_i²` 在桶大小均匀时最小，
所以这一项就是"惩罚不均衡"。默认 `params.balance_factor = 0.0`（普通 k-means
不启用），但 **IVF 建库时会显式 `.with_balance_factor(1.0)`**
（`rust/lance/src/index/vector/ivf.rs:3266`），而且这个值在建库路径上会被
除以训练行数（`params.balance_factor /= data.len() as f32;`，`kmeans.rs:1996`），
这样它的量级才和距离项可比。

实现方式是每轮的"有效距离"变成 `真实距离 + balance_factor × 该簇上一轮的大小`
（`lance-linalg/src/kernels.rs:93-112` 的 `argmin_value_float_with_bias`），
但**返回给调用方的距离仍然是真实距离**——平衡项只影响分配，
不污染 loss 和收敛判据。

这也是为什么真实 Lance 和"教科书 k-means"的一个区别是：
它的 IVF 分区通常比纯 k-means 更均匀，代价是 inertia 略高。
**用一点聚类质量换查询尾延迟**，这笔交易在检索场景里几乎总是划算的。

## 13.9 如果数据根本没有聚簇结构

前面所有的好成绩都建立在一个隐含前提上：这份数据是聚簇的。
如果数据在空间里是均匀随机分布的呢？IVF 的前提就直接塌了。

我们拿同一份规模、但**去掉聚簇结构**的数据（3000 × 32，标准正态），
用同样的 20 个分区、同样的参数重跑了一遍。结果是一条单调爬升的曲线：
nprobes=1 时随机数据 `recall@10` 只有 **0.2425**，2 个桶 0.3975、
4 个 0.5975、8 个 0.7950，直到探满 20 个桶才到 1.0000；而聚簇数据在
这几个点上全程 0.98 以上——探 1 个桶就 0.9800，之后一直是 1.0000。

**nprobes=1 时召回率从 0.98 掉到 0.24。** 这个数字必须诚实地报告，
因为它揭示了 IVF 的本质：**它假设"距离近"和"分在同一个桶"是相关的。**
当数据是各向同性的噪声时，这个相关性几乎不存在——k-means 把一个
均匀球体切成 20 份，每份都是相似的球瓣，落在哪个桶里几乎是随机的，
所以探 1 个桶只能覆盖大约 1/20 的真实邻居。

有意思的是随机数据的桶反而**更均匀**（min=5、max=182、imbalance=1.213、
Gini=0.0907，而聚簇数据是 2.040 / 0.1912）。这不矛盾：
均匀分布切出来的块自然大小相近，聚簇分布切出来的块大小天差地别。
但"桶均匀"和"桶有意义"是两件事——**随机数据上桶更均匀，
召回率却更差**，因为桶的边界和"哪个点更近"完全无关。

这个观察引出两条实用建议。第一，**建 IVF 之前先看数据的方差结构**：
如果原始向量经过 PCA 之后各主成分方差接近，IVF 不会有太多收益，
该考虑的是 HNSW 或者干脆暴力。第二，**很多真实 embedding 之所以适合 IVF，
不是因为它们"天然聚簇"，而是因为高维 embedding 的有效维度远低于名义维度**
（768 维的向量常常只有几十维是有信息的），k-means 正好抓住了这个低维结构。

还有一个必须说的边界：**召回率随 nprobes 单调不减**。这一点是可以证明的
——候选集是"嵌套"的（探 4 个桶的候选集严格包含探 2 个桶的候选集），
在精确打分下更大候选集只会让结果更好。所以 `test_ivf_recall_never_decreases_with_more_probes`
用了严格断言 `all(b >= a - 1e-12)`，没有任何容差。量化打分的索引
（IVF_SQ / IVF_PQ）也满足这个性质，只是它们需要容差，因为浮点噪声
和并列打破顺序会让结果抖动。

## 13.10 更大规模上的延迟，以及一段很有教育意义的翻车

前面那些延迟数字在 3000 行的规模上全是噪声。我们在一份更真实的数据上
（50000 × 64 维、50 个簇、100 条查询）重跑了一遍。

**召回率那一列是确定性的，延迟那一列不是**，而这两件事的对比本身就是
一个值得展开的教训。下面是同一份脚本、同一台机器、**两次运行**的结果。

暴力基线第一次 0.498 ms、第二次 0.709 ms。`IVF_FLAT` 探 1 个桶时
`recall@10 = 0.8800`，延迟两轮分别是 0.370 ms 和 0.124 ms；探 4 个桶
召回 1.0000，1.417 ms / 0.534 ms；探 16 个桶 5.848 ms / 3.141 ms；
探 64 个桶 20.428 ms / 11.550 ms。`HNSW` 这边，`ef=20` 召回 0.9320、
0.981 ms / 0.340 ms；`ef=50` 召回 0.9930、1.896 ms / 0.766 ms；
`ef=100` 召回 1.0000、3.279 ms / 1.186 ms。

**召回率两列完全一样（逐位相同），延迟却差了 2~3 倍，而且第一次的结论
和第二次是相反的**：第一次跑出来"除了 nprobes=1，所有 ANN 都比暴力慢"，
第二次跑出来"nprobes=1 快 5.74 倍，HNSW ef=20 快 2.09 倍"。

两次都是真数据，差别在于**第二次机器是空的，第一次机器上还跑着别的任务**。
第一次那张表差点让我写下一个错误结论：
"在 Python 规模上 ANN 会输给 BLAS 暴力"。这个结论**不成立**——
它只是负载的产物。

把这件事讲清楚，比给出一张好看的表重要得多。三条经验：

**第一，先问"这个数字是确定性的吗"。** 召回率、分区大小、
距离计算次数、字节数是确定性的，同一份数据重跑逐位相同。
挂钟时间和它旁边那个"缓存命中率"一样，是环境变量。
**一张表里混着两类数字，读者根本分不出来哪些能引用。**

**第二，跨实现比性能时必须先清场。** `FLAT` 走的是 BLAS：
`pairwise_distances` 把 L2 展开成 `‖q‖² - 2q·mᵀ + ‖m‖²`，本质是一次
`(100,64) × (64,50000)` 的 GEMM，这是 BLAS 最擅长的形状，
而且它只在主线程上跑满一个核。ANN 索引**没有任何一步能走 BLAS**——
探桶是 gather/scatter、ADC 是查表、图搜索是随机访存，
全部回到 Python 解释器。所以谁的核被抢占，结果就偏向谁。
同一个伪影在 PQ 的 ADC 上也会出现：第 14 章 §14.3 里"ADC 查表"
**反而比"解码后走 BLAS"慢一个数量级**，道理一模一样，那里只讲一次。

**第三，唯一跨环境成立的是复杂度，不是常数。** `FLAT` 是 `O(n·d)`
每查询，`IVF` 是 `O(P·d + nprobes/P·n·d)`，`HNSW` 是 `O(m·log_m n)`。
把这份数据放大 100 倍到 500 万行，`FLAT` 的延迟线性涨到 50 毫秒以上，
而 `HNSW, ef=50` 基本不变（多出来的层只多走几步）——**那时无论负载如何，
结论都不会翻**。真实 LanceDB 是 Rust + SIMD 实现的，
常数里没有解释器，所以它在 5 万行这个规模上就已经稳定地赢暴力一个数量级。

**所以这一章的正确结论不是"IVF 更快"，而是"IVF 改变了复杂度的形状"，
外加一句：在解释器里量常数是量不出结论的。**
迷你实现的正确用法是**隔离误差源、把召回率的来源一个个量出来**——
那是纯算法层面的、确定性的、可复现的结论。

## 13.11 小结

**暴力检索是 O(n·d)，100 万 × 768 维一次查询就是 7.68 亿次乘加、
约 154 毫秒。** ANN 存在的全部理由就是打破这个线性。

**IVF = 粗量化 + 倒排链表。** 查询成本变成 `O(P·d + nprobes/P·n·d)`，
精度损失全部来自"探漏了桶"。

**真实 Lance 的分区是同一个索引文件里的行区间**，不是每个分区一个文件。

**Lance 的常规 IVF k-means 没有 k-means++**，用均匀随机行采样；
加权 k-means++ 只在流式 coreset 路径里。默认 `max_iters=50`、
`tolerance=1e-4`（相对判据）、`redos=1`、`hierarchical_k=16`
（`k > 256` 时走层级 k-means）。

**空簇处理是确定性的：先归零，再把最大簇对半劈、加 `±1/1024` 的交替微扰。**
不引入随机，所以带种子的训练可复现。

**`num_partitions ≈ sqrt(N)`** 来自"查询成本两项平衡"，Lance 则按
`num_rows / target_partition_size`（上限 4096）算。

**`nprobes` 的收益是饱和的、延迟是线性的。** `refine_factor` 是另一个旋钮，
管"算多准"而不是"看多少"，而且必须"放大 k + 精确重排"两步都做。

**残差只在 L2/cosine 上成立。** 实测它把 recall@10 从 0.465 抬到 0.690，
且几乎零成本；但对 dot product 是错的。

**分区不均衡直接决定尾延迟**，Lance 用 balance factor 主动惩罚不均衡。

**数据如果本来就不聚簇，IVF 会崩。** 同样参数下 nprobes=1 的召回率
从 0.98 掉到 0.24——这是必须讲清楚的前提。

**同一个脚本跑两遍，延迟差 2~3 倍，结论能反过来。** 召回率是确定性的，
挂钟时间不是；跨实现比性能必须先清场，而唯一跨环境成立的是复杂度。
在解释器里量常数是量不出结论的。

下一章讲 IVF 上面那一层最常用的量化：乘积量化。它解决的不是
"要算多少距离"，而是"每条向量占多大地方"——那是另一个数量级的问题。
