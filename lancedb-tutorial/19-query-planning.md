# 第 19 章　查询规划与执行

前面各章分别讲了存储、索引、过滤、向量检索。这一章把它们串起来：
**一个查询从字符串走进来，到结果行出去，中间经过了哪些决策。**

这个视角很重要，因为 LanceDB 的性能问题几乎从不出现在"某个算法慢"上，
而是出现在"规划器选了错的路径"上。同一个查询，prefilter 和 postfilter
的差别可能是 50 倍延迟加上完全不同的结果集；
同一个过滤条件，走索引和走全表扫描的差别是"读 4 KB"和"读 40 MB"。

## 19.1 一个查询要经过四层决策

从 `tbl.search(...)` 到结果，规划器要回答四个问题：

**读哪些列？** 这是投影下推。用户要 3 列，过滤条件又要 2 列，
一共读 5 列——而不是全表的 200 列。

**读哪些片段？** 这是分区裁剪。用片段级的列统计（min/max/null 数）
直接排除"不可能有匹配行"的片段。这一步**不读任何数据页**，
因为统计信息被抄在 manifest 里。

**过滤和向量检索谁先谁后？** 这是 prefilter / postfilter 的选择。
它是本章最重要的一个决策。

**读出来的行怎么回表？** 这是延迟物化：先只读过滤列算出掩码，
再只取活下来那些行的投影列。

我们实现的 `Scanner` 和 `Query` 把这几步都显式化了，
并且每一步都留下可观测的数字。

## 19.2 计划长什么样

`explain()` 的输出是一个树。**这棵树来自本教程实现（`mini_lancedb`）的 `explain()`**，
不是真实 LanceDB 的 `explain_plan()`——两者的节点名有重叠也有分歧，
下面遇到时逐条标出。场景是 4000 行、32 维向量、一张 IVF_PQ 向量索引、
一张 BITMAP 标量索引、一张 FTS 索引，然后做一次"带过滤的向量检索"：

```
ProjectionExec: expr=[id@0, vector@1, text@2, n@3, cat@4, _distance@5]
  LanceRead: uri=memory:/demo.lance, version=5, num_fragments=1, projection=[id, vector, text, n, cat]
    FilterExec: cat = 'c7'   # prefilter
    ANNSubIndex: v_idx (IVF_PQ)
    ANNIvfPartition: v_idx (IVF_PQ)
    KNNVectorDistance
    TopK: limit=5
    LateMaterialization: 先定行号，再回表取投影列
```

这棵树的读法是从下往上的（数据流方向），但写给人看是从上往下。
几个节点的含义：

`LanceRead` 是叶子节点，代表"从一个 dataset 版本读片段"。
注意它带了 `version=5`——**计划里印的是查询开始时那个 dataset 的版本**
（这是本实现的观察：`LanceRead` 的 `version` 直接取自 dataset 的当前版本，
而不是查询结束后回填的）。这一点对可复现性很关键：片段集合、列统计、
索引有效性都随版本变，同一个计划在不同版本上跑可能给出不同结果。

`ANNIvfPartition` 是 IVF 的分区探测节点。
真实 Lance 的 `explain_plan()` 里这个节点下面会挂着
`ScalarIndexQuery: query=[id > 100]@btree_idx(BTree)`——
也就是"标量索引先算出行号集合，再把掩码交给分区探测"。
这正是 prefilter 的内部结构。（本实现也有 `ScalarIndexQuery` 这个节点名，
但**在向量查询里它只在 `analyze_plan()` 里出现**，见 19.7 节。
限定"向量查询"是必要的：**纯标量扫描**的查询在干计划里也会印这个节点，
因为那种查询本来就只剩"用索引筛行"这一个动作，没有分区探测要挂。
同一个节点名在两条路径上的含义不同，读到它时先看查询里有没有向量检索。）

`FilterExec` 标注了 `# prefilter`，说明谓词是在距离计算**之前**算成行掩码的。
本实现的 `explain()` 把这一行**固定印在树的这一层**：postfilter 时它不挪位置，
只是备注换成 `# postfilter`。所以**光看节点顺序分不出这两种语义，必须看备注**——
一个把 `FilterExec` 挪到 `TopK` 之后的计划会直观得多，本实现没有这么做。
具体例子见 19.5 节。

`KNNVectorDistance` 是距离计算，`TopK` 是取前 k。
真实 Lance 在 `refine_factor` 大于 1 时，这两个节点会展开成
`ANNSubIndex k=10` → `KNNVectorDistance` → `TopK(fetch=5)` 的形状，
也就是"多取候选、全部算精确距离、再截断"。

`LateMaterialization` 说明投影列是在行号确定之后才取的。

## 19.3 投影下推：最便宜的优化

这一层几乎总是有收益，而且没有副作用。

第 10 章在一个 2 万行、4 列的表上量过这一层的收益
（脚本 `examples/verify/ch10_pushdown.py`）：只读 1 列要 43,540 字节，
读 4 列要 383,224 字节，**差 8.8 倍**。这组数字我复核过，逐位可复现。

**这一层收益的上限是由"被省掉的列有多大"决定的**：省掉一个
`int64` 列只省 8 字节/行，省掉一个 768 维向量列能省 3 KB/行。
第 3 章的例子里向量列占文件 **96%** 的空间（那条实测在
`03-lance-file-format.md`，可以核对）——按这个比例，投影掉向量列
能省掉绝大部分读取量。

（这里原来还写了一句"第 10 章那个脚本换一张带向量列的表量到的是
100 倍量级"。**那句话没有出处**：`examples/verify/ch10_pushdown.py`
里根本没有向量列（`grep` 一下就知道），第 10 章正文里也没有
"100 倍"这个数。它是我从"96% ⇒ 应该很大"推出来、然后写成了
"量到的是"——**把推算说成实测，是这份教程最不能犯的一类错**。
按 96% 反推，上限大约是 25 倍（1/0.04），不是 100 倍；
但更重要的不是哪个数对，而是**它没有被量过，就不该带着"实测"的措辞出现**。）

实现上有一个容易出错的地方：**投影列不等于用户要的列。**
用户可能只要 `id`，但过滤条件写的是 `WHERE text LIKE '%x%'`，
那 `text` 列也必须读——只是读完就丢，不进入输出。
我们的 `_needed_columns()` 就是做这件事的：

```python
proj = self._projection()          # 用户要的
filt = self._filter_columns()      # 过滤条件引用的
return list(proj) + [c for c in filt if c not in proj]
```

漏掉这一步的后果是"过滤条件里的列没被读"，然后求值时报
"列不存在"——这类 bug 在小测试里不会出现，因为测试往往只查一列。

**检索路径上还有第二条规则：分数列永远保留，而且永远排在最后。**
向量查询的 `.select(["id"])` 返回的是 `['id', '_distance']`——
`_distance` 被**追加**回输出，不是插在前面。本机 0.40.0 实测
真实 LanceDB 也一样（`to_arrow().schema.names` 同样是
`['id', '_distance']`），所以这条不是本实现的怪癖。

（我原来在这里写的是 `['_distance', 'id']`，顺序反了。这不是笔误，
是个很典型的"凭印象写输出"：直觉上分数列像是被"前置"上去的，
而实现是"投影列在前、分数列追加在后"。
`mini_lancedb/query.py` 的 `_output_schema` 就是把投影字段放前面、
分数列接在后面。**列的顺序也是输出契约的一部分**——
按位置解包 `row[0]` 的代码会在这里静默取错列。）

全文查询同理（`_score`），混合查询是 `_relevance_score`。
原因是这些列不是"数据列"，是**检索算子的输出**：
`TopK` 要靠 `_distance` 排序，输出层又要靠它告诉调用方
"这个结果有多接近"，把它投影掉等于让查询失去意义。

所以检索查询的投影**不是纯投影**。这件事在第 10 章讲下推时
看不出来（那里只有扫表），只有走到检索路径上才会撞到。
第 20 章那句"`.select()` 不会去掉 `_distance`"（附录 D 第 13 条）
说的就是这个规则的结果——**它是设计，不是 bug**，
但如果你在做"精确控制返回列"的事，得知道有这么一条加回来的规则。

## 19.4 分区裁剪：零 I/O 的优化

这是列存最漂亮的地方之一。一个查询 `WHERE n > 19000` 打在
10 个片段（每个 2000 行，n 连续递增）上，规划器只需要看统计：

```
片段 1: n ∈ [0, 1999]        → 1999 < 19000，不可能命中 → 剪掉
片段 2: n ∈ [2000, 3999]     → 剪掉
...
片段 10: n ∈ [18000, 19999]  → 可能命中 → 保留
```

实测结果是 **保留 1 个片段、剪掉 9 个**，只读 `n` 一列时的字节数
从 47,888 降到 8,696——剪掉的 9 个片段一个页都没打开。
（规模是 10 个片段 × 2000 行，量法与脚本见第 10 章。）

三态判断是整个机制的契约：`_stats_can_match` 返回 True（可能）、
False（不可能）、None（不知道）。**只有 False 能剪枝。**
保守是正确的方向——统计信息不完整时，宁可多读一点，也不能漏行。

有一个细节值得单独说："列在这个片段里没有数据"这种情况。
如果表的 schema 后来加了一列，老的片段里根本没有这一列的数据。
这时读出来的全是 null，而 null 参与任何比较都是 null，都不会命中。
所以这种情况**可以放心剪掉**——它是"统计信息缺失"里唯一安全的一类。

AND 和 OR 的处理不对称，也要讲清楚：

- `a AND b`：只要有一个分支能剪，整个条件就能剪（因为 AND 更严格）；
- `a OR b`：必须两个分支都能剪才能剪（因为 OR 更宽松）。

漏掉这个不对称性，要么漏剪（性能损失），要么错剪（结果错误）。

## 19.5 prefilter 与 postfilter：正确性问题伪装成性能问题

这是全章最重要的一节。

（这一节从**查询规划**的角度讲这件事：掩码怎么产生、什么时候推进索引子树、
两种模式下返回行数的差别。如果你更关心**在向量检索里怎么用对**它，
第 18 章 §18.8 是同一件事从索引侧写的版本，含真实 Lance 的两条硬规则；
第 24 章 §24.4 则给了"该选哪一个"的量化判据。三处角度不同，不重复。）

假设表里有 100 万行，查询是"在 `cat = 'rare'` 的行里找最近的 5 个向量"，
而 `cat = 'rare'` 只命中 100 行。

**prefilter 的做法**：先用标量索引找出那 100 行的行号，
把它当掩码传给向量索引，只在掩码内做 ANN，返回 5 行。

**postfilter 的做法**：先做 ANN 拿到全局最近的 5 行，
再看它们里有没有 `cat = 'rare'` 的。可能一个都没有，
于是返回 0 行——而用户期望 5 行。

所以 postfilter **不是"另一种实现"，是"另一个查询语义"**。
真实 LanceDB 的 `.where(..., prefilter=False)` 就是后者，
而且文档里明确说了会返回少于 k 行。我们的实现保留了两条路径，
并在测试里断言它们的行数差异。

那 postfilter 还有什么用？有，而且很重要：
**当过滤条件的选择性很差时**（比如命中 90% 的行），
prefilter 要先把一个 90% 大小的掩码传给索引、索引内部还要在掩码上过滤，
这套开销超过了它省下的距离计算。这时候直接 ANN 再过滤更快。

所以选择规则大致是：**过滤后候选集远小于 k 时有本质区别（必须 prefilter），
过滤后候选集远大于 k 时两者结果相近、性能上 postfilter 可能更优。**

判断"远小于"还是"远大于"就需要选择性估计，也就是第 11 章那套东西。
我们的估计器很粗，但它是确定且可解释的——这比"准确的猜测"更重要，
因为它让计划可以被复现和调试。

从计划上看，两者的区别只写在 `FilterExec` 那一行的备注里。同一个表、
同一个索引，只把 `prefilter` 翻一下（4000 行、IVF_PQ 索引、谓词 `n > 3900`）：

```
prefilter=True   →   FilterExec: n > 3900   # prefilter
                     ANNSubIndex: v_idx (IVF_PQ)
                     ANNIvfPartition: v_idx (IVF_PQ)
                     KNNVectorDistance
                     TopK: limit=5

prefilter=False  →   FilterExec: n > 3900   # postfilter
                     ANNSubIndex: v_idx (IVF_PQ)
                     ANNIvfPartition: v_idx (IVF_PQ)
                     KNNVectorDistance
                     TopK: limit=5
```

两棵子树一模一样，唯一差别是 `# prefilter` 和 `# postfilter` 这两个词。
这是本实现的一处可读性欠缺：**语义上的本质差别（掩码在距离计算之前还是之后生效）
退化成了一个注释**。所以排查这类问题时别指望从树的形状上一眼看出——
看备注，或者更可靠地，**看结果行数**。

上面那句"postfilter 会返回少于 k 行"值得亲自跑一次，
因为它的严重程度完全由谓词的选择性决定。同一张表、同一个索引、
同一个查询向量，只翻 `prefilter` 这一个开关。

**这份配方是完整可复现的**：4000 行、`n` 取 0..3999、16 维向量用
`np.random.default_rng(0).standard_normal`（先建表把 rng 消耗在向量上，
再取查询向量），索引是 `IVF_PQ(num_partitions=32, num_sub_vectors=4)`，
`limit(5)`。跑两遍结果逐位相同：

```
谓词 n > 3900（命中 100/4000 = 2.5%）   prefilter=True  -> 5 行
                                        prefilter=False -> 1 行

谓词 n > 200 （命中 95%）               prefilter=True  -> 5 行
                                        prefilter=False -> 5 行
```

`prefilter=False` 那一列的 **1 行**是这一节的实测值，
不是"大概会比 5 少"。换个查询向量它可能就变成 0 行——
这一点很有意义，下面第二条会说。

两条结论都在里面。

**第一，postfilter 的"少返回"不是一个固定的折扣，而是随选择性剧烈变化。**
高选择性时它少到只剩 1 行——**而且这个数字还会随查询向量变**，
换一个向量可能就变成 0 行。所以它不是"少一点"，是**不可预测**。
这比"少"要严重得多：一个返回 1 行的查询和一个返回 0 行的查询，
在监控上看不出异常，在用户那里就是"搜不到东西"。

**第二，低选择性时两种模式给出完全一样的结果。**
这说明 postfilter 的问题**只在高选择性下暴露**——
而这恰好是过滤最该起作用、用户最容易依赖它的场景。
换句话说：**你没法通过"平时测着没问题"来证明 postfilter 是安全的**，
因为出问题的条件恰恰是你没测的那一档。

选择性的估算在第 11 章，判据在第 24.4 节，索引侧的两条硬规则在第 18.8 节。
这里要记的是那条**怎么把它测出来**的方法：别比延迟，比行数。

## 19.6 延迟物化：列存最大的杀招

延迟物化的意思是：**不要一次读完所有需要的列。**

传统做法是"读所有需要的列 → 过滤 → 投影"。延迟物化把它拆成两步：
先只读过滤用的列 → 算出掩码 → 再只把活下来的行的投影列读回来。

收益的量级取决于过滤的选择性。过滤命中 1% 时，
投影列的读取量就只有 1%。在一个"过滤列很小、投影列很大（比如向量）"
的查询上，这个差别是几十倍。

我们的 `ScanStats` 里有一个 `late_materialization_saved_rows` 指标。
第 10 章那次实验（2 万行、**单片段**、投影 4 列）里，`WHERE n > 19500`
这个查询的这项指标是 **58,503**——也就是 19,501 行的 3 个非过滤列
不必读了（`19,501 × 3 = 58,503`），几乎整个表。
注意它是"行 × 列"的计数而不是行数：投影列越多、这个数字越大，
把它当行数读会高估一个数量级。

实现上有两个必须做对的地方。

**第一，行范围下推。** 掩码算完之后，活下来的行号往往是连续的
（因为扫描是按片段顺序做的）。这时应该告诉 reader
"只读第 lo 到 hi 行"，让它跳过整页——而不是"把整个片段读进来再 take"。
我们的 `_read_rows()` 有一个连续检测的快速路径：

```python
contiguous = len(offsets) == 1 or np.all(np.diff(offsets) == 1)
if contiguous:
    return ds.read_fragment(frag, columns, row_range=(lo, hi), include_deleted=True)
```

**第二，"偏移连续"的判断必须在片段内部做。** 这里的偏移是
**片段内物理偏移**，不是全局行号。混淆这两者会导致
"行范围下推算出越界区间 → 读回空结果"——
而且这个 bug 只在过滤条件命中片段中一段（而不是整段）时才出现。

## 19.7 四层的协同：一个完整的例子

四层决策不必每次都用上。下面这个查询**只触发了其中三层**，
第四层（分区裁剪）是空转的——先说清楚为什么，再看计划。
一个查询只要把"哪几层真正干活了"读出来，就算读懂计划了。

```
tbl.search(query_vector).where("n > 3900", prefilter=True).limit(5)
```

计划是：

```
ProjectionExec
  LanceRead: version=5, projection=[id, vector, text, n, cat]
    FilterExec: n > 3900   # prefilter=True
    KNNVectorDistance: metric=l2
    ANNSubIndex: v_idx (IVF_PQ, nprobes=(默认))
    ANNIvfPartition: v_idx (IVF_PQ, partitions=32, indexed_rows=4000)
    ScalarIndexQuery: 谓词掩码下推给索引 (99 行候选)
    TopK: limit=5, offset=0  (按 _distance 升序)
    LateMaterialization: 先定行号，再回表取投影列
```

而 `analyze_plan()` 会附上运行时的数字：

```
index: {'nprobes': 20, 'refine_factor': 1, 'num_partitions': 32, 'exact_scan': False}
index_approximate: True
```

**先说哪几层上了场。** 树里能读出三层：`ProjectionExec` 与
`projection=[id, vector, text, n, cat]` 是**投影下推**（§19.3）；
`FilterExec: n > 3900   # prefilter=True` 是**prefilter 选择**（§19.5）；
`LateMaterialization` 是**延迟物化**（§19.6）。

**第四层分区裁剪（§19.4）在这里是空转的**，而原因是具体的：
它靠的是**片段级**统计去整段排除片段，而这张表只有一个片段
（`indexed_rows=4000` 就是全表）——只有一个片段时，
"排除掉不可能的片段"最多只能排除零个，这一层没有东西可做。
**这不是它没被实现，是这个场景让它无事可做。**
想让它在计划里显形，得先有多个片段（多写几批、或者压实前），
再让谓词落在片段统计的区间之外。这也解释了为什么
§19.4 的收益要用另一个数据集来量：**"零 I/O 的优化"的收益，
完全取决于你有多少个片段可以被排除掉。**

顺带把一处看起来像矛盾的地方说清楚：计划树里写的是 `nprobes=(默认)`，
而上面这行字典里写的是 `nprobes: 20`。两者不冲突，也不是两套默认值——
**树里印的是"这个参数没有被显式覆盖"这个事实，实测值印在 `index:` 这一行**
（本实现与真实 LanceDB 的口径一致：官方默认就是 20）。所以排查召回率时
读那行字典；读计划树只会得到"用了默认"。

`exact_scan: False` 和 `index_approximate: True` 是两个必须看的字段。
它们回答的是**"这个结果是不是精确的"**——这是向量检索里最容易被忽略的问题。
真实 LanceDB 也是这个语义，官方文档还专门给了一张表讲四种查询模式下
`_distance` 到底是什么。

那四个档位（无索引或 `.bypass_vector_index()` / 有量化索引不设 `refine_factor` /
设了 `refine_factor` 使候选被完整向量重算）的完整枚举、以及本机对四种情况的实测，
在第 12 章 §12.7——那里是讲 `_distance` 语义的主场，这里不重复一遍。
它的操作含义只有一句：**同一个 `.search()` 调用，返回的数字可能是四种不同的
东西之一。任何"拿 `_distance` 和阈值比较"的业务逻辑都必须先确认自己在哪一档**，
而确认的办法就是看计划里那两个字段。

## 19.8 计划的可解释性

一个查询规划器好不好用，一半取决于它的输出可不可读。我们的设计原则是：

**每个节点都带参数。** `ANNIvfPartition: v_idx (IVF_PQ, partitions=32,
indexed_rows=4000)` 比 `ANNIvfPartition` 有用得多。

**每个决策都留痕。** `FilterExec: cat = 'c7'   # prefilter` 里的注释
说明了"为什么这个过滤器在这个位置"。

**剪枝要逐片段报告。** `explain()` 会打印每个片段是保留还是剪掉、
以及剪掉的依据是哪条谓词。这在排查"为什么这个查询扫了全表"时
是决定性的——一眼就能看出是统计信息不对，还是谓词根本无法用统计剪枝。

**实测数字要和计划分开。** 计划是"应该怎么做"，
`analyze` 是"实际做了什么"。两者分开才能发现"计划说下推了，
实际却读了全表"这类问题。

这对应到 API 上是三个入口：`explain()` 不执行查询、只按"应该发生什么"
推一份计划；`explain_plan()` 是它的别名（实测两者输出逐字节相同）；
`analyze_plan()` 先真跑一遍，再在**同一棵树的末尾追加**一段实测 I/O。
真实 LanceDB 也是这一对（附录 A 记的是 `.explain_plan(verbose=False)`
打印计划、`.analyze_plan(...)` 打印计划加运行时指标，本实现照抄了这个形状）。

**输出格式只有一种：缩进树。** 值得说清楚的是本实现的"树"非常浅：
`ProjectionExec` 缩进 0、`LanceRead` 缩进 1，之后所有节点缩进都是 2。
换句话说它是**一棵树形状的列表**——渲染时按固定缩进逐行打印，
节点之间并不携带"谁是谁的输入"这种层级信息。后果是：从计划里读不出
"这个 `FilterExec` 作用在哪一层算子的输出上"，而这恰好是判断
prefilter / postfilter 时最想知道的事（19.5 节）。真实系统的计划树是有
父子层级的，所以它们能表达这一层关系；另一路格式是"每行一个算子、
用箭头串起来的火山模型列表"，更适合 grep。三种形状回答的是同一个问题，
但**别拿一种格式的行数去推断另一种的深度**。

## 19.9 四层之外：还没进计划的那些决策

前四层是本实现真正做到的下推。一个完整的规划器还要回答下面几个问题，
而它们的状态很不一样：有的是真实 LanceDB 做了、本实现没做，
有的是两边都把它放在检索规划器之外。分清这两种情况很重要，
否则容易把"没实现"当成"不该有"。

**`limit` 下推成 TopK，`offset` 不下推。** `limit` 会被翻译成 ANN 的 `k`
（postfilter 下还要乘 `refine_factor`），所以"取前 5 个"不必算完整个库
再截断——这就是 TopK 的提前终止。`offset` 是反面教材：本实现是在 TopK
之后切片，`offset=10000` 意味着前 10000 行照样被算出来再丢掉，
代价随 offset 线性增长。深分页的标准解法不是"把 offset 塞进 k"
（那会让候选集大到没意义），而是**键集分页**：把上一页最后一行的排序键
记下来，下一页从它之后开始。用大 offset 滚动窗口在任何列存引擎上都贵。

**排序。** 本实现的查询层没有用户可控的 `ORDER BY`，唯一的排序是
融合重排之后按 `_relevance_score` 固定降序（第 20 章）。真实 LanceDB 有
`.order_by([ColumnOrdering(...)])`，而且 **FTS 路的结果排序必须走它**——
其它排序参数会被静默丢弃（附录 D 第 20 条）。"排序 + limit"在优化器眼里
是一个 TopK：维护一个大小为 k 的堆，扫完就出结果，不必对全表做快排。
这条改写属于"只要有排序算子就该有"的标准动作。

**谓词重排。** 真实优化器会按估计的选择性把最挑食的谓词放到最前面。
本实现不做，而且**在这个执行器里重排的收益本身就有限**：过滤是整列
向量化求值的（第 11 章），掩码一次算一列，没有逐行短路的机会，
换个顺序不会少算任何一行的比较。真正吃选择率估计的是另外两处——
prefilter / postfilter 的决定（19.5 节），以及索引改写时挑哪个分支下推
（第 11 章）。更一般的经验是：**别把行式执行器的优化清单照搬到向量化执行器上。**

**跨片段的并行。** 本实现逐片段顺序扫描、单线程。片段之间天然独立
（各有自己的数据文件、统计和删除位图），所以"每个片段一个任务、
结果按片段顺序合并"是最直接的并行方案。它带一个必须处理的副作用：
**合并要保证顺序稳定**，否则同一个查询两次跑出来的行序不同，
测试会变成"既永远是绿的、又永远是假的"。本实现用顺序扫描换掉了这个
问题，代价是扫描吞吐上不去。

**计划缓存。** 本实现不缓存任何计划，每次查询重走一遍解析、统计读取、
剪枝判定。这是刻意的：**计划的输入（列统计、索引有效性、片段集合）
每次写入都在变**，缓存计划等于把决策建立在旧统计上，省下的那点 CPU
远小于"用过期统计剪掉一个该读的片段"的代价。真实系统里被缓存的是
**清单文件和索引文件本身**（第 10 章量过冷启动成本：第一次查询读的
1.5 MB 里几乎全是加载索引），不是规划结果。

**join 和子查询。** 这两件事**不在检索规划器的职责范围内**。本实现的
`Query` 上根本没有 join 或子查询这类旋钮；真实 LanceDB 的 Python 检索
API 也没有——连接发生在**格式层**，把 Lance 表挂进
DuckDB / DataFusion / Spark / Trino 之后用 SQL 做
（第 26.6 节）。由此得到一条很实用的边界：**能下推过去的只有谓词和投影**，
检索算子（ANN、BM25、重排）过不去。所以"先在 LanceDB 里检索、
再到 DuckDB 里 join"是把两段拼起来，而不是把一条查询交给一个优化器。

（我原来在这里写过"本实现的 `Query` 只有 `where` / `select` / `limit` /
`offset` 四个旋钮"，那是**错的**——而且错得很有代表性：我按"检索查询
大概就这几样"的印象写的，没去数。实际的 `mini_lancedb/query.py`
里光"会改变计划形状"的旋钮就有十三个：`limit`、`offset`、`select`、
`where`、`postfilter`、`fast_search`、`bypass_vector_index`、
`with_row_id`、`rerank`、`nprobes`、`refine_factor`、`ef`、
`distance_type`（`VectorQuery` 上还多一个 `distance_range`）。
数一遍不用一分钟，但凭印象写会一路错到读者那里。）

**嵌套字段的投影下推。** struct 列的投影可以比普通列再细一层。
本实现只能整列取值：`select(["meta"])` 可以，`select(["meta.x"])` 直接
报 `PlanError: 列不存在: 'meta.x'`。而 Lance 的格式层是按**子字段**排序和
寻址的（第 5 章讲 field id 排序时，"`c` 的子字段 `c.x` / `c.y` / `c.z`
紧跟在 `c` 之后"说的就是这个结构），所以真实 Lance 有条件只读 struct 里
真正用到的那几个子列——对"结构化元数据"这种宽 struct 列，
省下来的 I/O 是实打实的。

**两个会改计划形状的查询旋钮：`distance_range` 和 `fast_search`。**
它们很容易被当成"参数调节"，其实是**规划决策**——都会往里插一个节点。

`distance_range(lower, upper)` 把"只要距离落在这个区间里的行"变成一个
可以下推的过滤条件，计划里不再是"TopK 之后截断"，
而是"先按距离阈值筛、再排序"。这和 `limit` 下推是两种不同的改写：
`limit` 改的是**取多少**，`distance_range` 改的是**取哪些**。

`fast_search()` 则相反，它是**放弃兜底**：告诉引擎"不要再为未索引的行
跑一遍暴力扫描"。计划里会出现一个 `FastSearch` 节点，语义是
"只搜索引覆盖到的部分"。它省掉的是未索引行那一轮的完整扫描，
代价是**静默少结果**——表上还有没进索引的新数据时，
那些数据在这个查询里等于不存在（附录 D 第 16 条）。

把两个旋钮放在一起看，能看出一条规律：**查询侧的"优化开关"大多不是
纯性能旋钮，而是用正确性换性能。**`nprobes` 调小只是漏召回，
`distance_range` 是改变结果集的定义，`fast_search` 是直接放弃一部分数据。
规划器把它们都表达成计划节点，正是为了让"我牺牲了什么"在
`explain()` 里看得见。本实现两个都有实现，所以这一条不是"没做"，
而是"没在本章的画面里"。

## 19.10 小结

**规划器要回答四个问题**：读哪些列、读哪些片段、过滤和向量检索谁先谁后、
行怎么回表。

**投影下推永远有收益，且要注意"过滤引用的列也必须读"。**

**分区裁剪是零 I/O 的**，因为统计在 manifest 里。
三态判断里只有 False 安全，"列在这个片段里没有数据"可以放心剪。

**prefilter 和 postfilter 是语义差异，不只是性能差异。**
postfilter 会返回少于 k 行。

**延迟物化把"读全部"变成"读 1%"，但前提是行范围下推真的生效**，
而且"偏移连续"的判断必须用片段内偏移。

**永远检查 `exact_scan`**——`_distance` 有四个档位：真实距离、
索引表示上的近似距离、对候选集重算的距离、以及扩大候选集后重算的距离。

**四层之外还有一批"没进计划"的决策**：`limit` 下推成 TopK（`offset` 不下推，
深分页要用键集分页）；排序加 limit 是一个 TopK；谓词重排在向量化执行器里
收益有限；片段级并行需要保证合并顺序稳定；计划的输入随时在变，
所以该缓存的是清单和索引文件而不是计划；join 和子查询属于格式层，
不进检索规划器。

**这一章讲的全是"应该怎么做"，"实际是怎么跑起来的"在附录 I。**
本章标题里的"执行"两个字不是顺带的：真实引擎是一棵 DataFusion
物理计划，每个算子自带 `elapsed_compute` / `output_batches` /
`task_wait_time` 这样的账本，并行度写在 `output_batches` 上、
合并点写在 `preserve_partitioning` 上。**本章的 plan 是"意图"，
附录 I 的 `analyze_plan()` 是"实况"——两者分开看才能发现
"计划说下推了、实际却读了全表"这类问题。** 数据怎么出去（零拷贝）
在附录 J。

规划器还要多回答一个问题——**两路分数怎么合。**
