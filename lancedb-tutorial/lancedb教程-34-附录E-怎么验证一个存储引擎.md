# 附录 E　怎么验证一个存储引擎

这份附录讲一件教程正文里反复出现、却从没集中讲过的事：
**你怎么知道一个存储引擎是对的？**

这不是方法论漫谈。整套教程的每一个数字、每一条"反直觉的结论"，
背后都有一套具体的验证手段；而 `mini_lancedb/` 里抓出来的那批真 bug，
恰好把"什么手段有效、什么手段看着有效其实无效"演示了一遍。
这份附录就是那套手段的清单。

它的用法是：**当你要自己写一个存储层、或者要评估别人的存储层时，
拿这份清单去对。** 对不上的地方就是风险所在。

---

## E.1 为什么"测试通过"在这个领域几乎不值钱

先说清楚问题有多难。

一般的应用代码，错了通常会**炸**：抛异常、崩溃、返回 500。
这类错误很好抓——错误会自己跑到你面前。

存储引擎不一样。它的大多数错误是**静默的**：
不抛异常、不写日志、监控指标正常，只是**结果不对**。
而且往往不是"完全不对"，是"少了一行""多算了一个""排序在第 8 位之后开始偏"。
这类错误在人工抽查里几乎不可能被发现，在生产上可以潜伏几个月。

本教程的实现抓出来的 bug，按后果分类大概是这样，
每一类都有用例钉住——多数在 `tests/test_regressions.py`
（它按失败模式分成九组），LIKE 那条在 `tests/test_expr.py`：

**返回错误的行数**，而且不报错。`BETWEEN` 在开启统计剪枝时静默返回 0 行
（`test_between_filter_returns_rows_with_zone_map_pruning_enabled`）；
LIKE 的前缀+后缀快速路径在短字符串上误命中
（`test_like_fastpath_agrees_with_independent_matcher`，
拿一个手写的通配匹配器当独立参照，而不是拿正则路径自己比自己）。
前者是"该有的没有"，后者是"不该有的有了"，两者都不会让任何断言变红——
因为写测试的时候，人默认的是"实现是对的"。

**结果在某个规模之上才开始偏。** FSST 解码把"每个符号"当成"每一行"，
手工构造的短字符串（一行一个符号）完全正确，真实文档文本（一行几十个符号）
解出错误的行数和内容（`test_fsst_roundtrip_on_realistic_long_strings`）。
这个 bug 在一个用短字符串做测试的套件里可以永久存活。

**监控指标静默归零。** 从前缀 store 拿到的表，I/O 计数恒为 0
（`test_prefixed_table_forwards_io_stats`）；`explain(analyze=True)`
把每个片段打印两遍、计数翻倍（`test_explain_does_not_double_count_pruned_fragments`）。
指标错了比结果错了更隐蔽——结果错了用户会报，指标错了没人会报，
而所有容量规划和调优决策都建立在指标上。

**元数据和数据不一致。** 改列类型只改 manifest 不改数据，
于是 schema 说这列是 `fixed_size_list<float32>[8]`、数据文件里还是 float64 的老编码。
读出来的东西**能用**，只是不对（`test_alter_columns_type_change_rewrites_data`）。

这四类在正文里都有展开：剪枝和指标那几条集中在第 10 章 §10.12，
LIKE 快速路径在第 11 章 §11.9，改列类型在第 5 章 §5.5.1，
FSST 在第 4 章 §4.5；附录 C 的 §C.4 又按类型把它们重讲了一遍。

这四类错误的共同点是：**它们都能通过一套"写得挺认真的测试套件"。**
本教程的实现有 1144 个测试，跑起来是 **1143 通过 + 1 跳过**；
而附录 D 那份坑清单有 55 条。
两个数字都真实，不矛盾——**测试通过和实现正确是两个不同的命题。**
弄明白它们差在哪，就是这份附录的全部内容。

## E.2 三种"假绿"

"假绿"指的是测试通过了，但它通过的原因是错的。有三种，危害递增。

### 第一种：用被测代码验证被测代码

这是最隐蔽的一种。测试拿被测代码的**另一次输出**当参照，
于是两边同时错的时候，测试是绿的。

具体形态很多。用索引 A 的结果去验证索引 B 的结果；用"我们自己写的编码器"
压、再用"我们自己写的解码器"解、比对原文——这叫**自洽往返测试**，
它对"两个组件有没有互相约定好"是有效的，
但对"这个格式对不对"**什么也没证明**。

本教程的 LZ4 实现就是栽在这里。当时的 bug 是编码器写出了一个
`offset=0` 的序列（字面意思是"匹配到自己"）。这个文件谁也读不了，
但我们自己的解码器能读出大部分内容，直到几百字节之后才因为
"字面量超界"报错——**报错位置和真正的起因完全无关**。
往返测试全程是绿的：自己压、自己解，两边犯同一个错，正好抵消。

抓住它的是**对拍**：拿 Python 的 `lz4` 包（背后是 C 实现）去解我们生成的字节流。
`mini_lancedb/encoding/compress.py` 里的 `crosscheck_lz4()` 就是干这件事的，
它返回的是**每种样本上双方能不能互相解开**，
而 `tests/test_regressions.py::test_lz4_is_byte_compatible_with_the_c_implementation`
把它变成了一条断言。环境里没有 `lz4` 包就 `skip`——
注意这个 `skip` 本身就是设计的一部分，后面 E.6 会讲为什么。

（顺带说清那**一条** skip 是什么：本机的 1144 条里有 1143 条通过、
1 条跳过，跳过的是 `tests/test_table_api.py` 里一条**需要 pandas** 的用例——
这个环境没装 pandas。它和上面那条 lz4 的 `skip` 不是一回事：
lz4 在本机是装着的，所以那条对拍**真的跑了**。
**报告测试结果时把 skip 的原因说出来**，因为"1 条跳过"在别人眼里
既可能是"环境缺个可选依赖"，也可能是"某个关键对拍被静默关掉了"。）

### 第二种：断言恰好编码了 bug 的行为

比第一种更糟。测试不是"没抓到"，而是**把错误行为写进了断言**，
从此以后这个 bug 变成了"符合规范"。

这种错误几乎总是这样发生的：先写实现，发现某些输入下行为很奇怪，
观察了一会儿，觉得"大概就是这样吧"，然后照着当前输出写下断言。
**观察变成了定义。**

本教程里有一个很清楚的例子。第 14 章讲到 4-bit PQ 的压缩比时，
文档里的数字和迷你实现算出来的差一倍；追下去发现是 4-bit 的记账口径不同——
Lance 把两个子向量的码合装进一个字节（每向量 `M/2` 字节），
迷你实现为了代码清晰，一个子向量照样占一个字节（每向量 `M` 字节）。
如果当时照着迷你实现的输出写下断言"4-bit 的压缩比 = 16"，
这条测试就会永久地把一个记账错误固化成"正确行为"（Lance 的真值是 32）。

防御手段只有一条，而且它不是技术手段：**断言必须能说清"为什么是这个值"**。
如果一条断言的理由是"因为我跑出来是这个"，它就不该存在。
本教程里所有断言的理由都指向三种东西之一——
**数学推导**（PQ 的压缩比可以手算）、**外部参照**（C 实现、Arrow 的行为）、
或者**不变量**（行号必须守恒）。凡是指向"当前输出"的断言，都要重新审。

### 第三种：覆盖不到关键分支

测试全绿，但**根本没走到出问题的那条路径**。

这一类最好抓，也最容易漏，因为它需要你知道"实现里有哪几条路"。
本教程的测试夹具里有两条规则就是专门为此设的：

主测试表固定 **120 行**，而不是 10 行。原因写在 `tests/conftest.py` 里：
10 行的页走不到压缩路径，而"字符串列的压缩/解码"恰恰是最容易出错的地方。
**测试数据的规模必须跨过实现的内部阈值**，否则测的是一个不存在的简化版。

向量维度固定 **8 维**，目的是让 `num_sub_vectors` 有整除的余地。
`mini_lancedb/index/ivf_pq.py` 的 `_default_sub_vectors()` 按 8、4、2 依次试，
取第一个能整除维度的值，一个都除不尽就 `return 1`；7 维正好落在这条退化路径上，
整个向量只切成一个子空间、PQ 退化成单个码本，正常路径反而测不到。

**这两条规则的共同形态是：把测试数据选在"能触发分支边界"的位置上。**
随机选数据通常做不到这一点——随机数据会均匀地落在中间，
恰好避开所有边界。

## E.3 验证手段的四个层次

上面讲了"什么是假绿"，现在讲"什么真的有效"。
有效的手段有四层，越往后越贵，也越能抓到深层错误。

### 第一层：单元测试（往返、边界、报错）

就是常规意义上的测试：编码器压完解回来等于原文，解析器解析一个表达式等于预期的树，
越界输入抛预期的异常。本教程的 1144 个用例里绝大多数属于这一层。

它的价值是**快、定位准**——失败信息直接指向出错的函数。
但它的能力边界也很明确：**只能证明"你想到的输入"是对的**。
上面 LZ4 和 FSST 两个 bug 都在这一层活着。

所以这一层必须写，但**绝不能只写这一层**。

### 第二层：不变量测试

不写"输入 X 得到输出 Y"，而写"无论输入是什么，下面这条关系必须成立"。
不变量比具体断言强，因为它覆盖的是**输入空间**而不是输入点。

本教程实际依赖的不变量，几条最值钱的：

**行号守恒。** 删除 N 行之后，`count_rows()` 必须正好少 N 行；
索引里剩下的行号必须全部指向活着的行。
`test_index_row_ids_are_remapped_not_stale` 测的就是这条——
删掉一半之后去查索引，任何一个指向已删行的行号都是 bug。

**排序的正确性由外部参照定义，不是由内部一致性定义。**
`tests/conftest.py` 里的 `brute_force_order()` 用 numpy 独立算一遍最近邻，
所有"排序对不对"的断言都拿它当参照。
它的 docstring 写着这套测试最重要的一句话：
**用被测代码验证被测代码，是这类测试最容易掉进去的陷阱——
两边同时错的时候，测试是绿的。**

**版本单调。** 每次提交版本号 +1，且旧版本的 manifest 永远还在。
时间旅行读到的行数必须等于那个版本提交时的行数。

**元数据不撒谎。** manifest 里声明的 schema 必须和实际数据文件里的列类型一致。
`test_alter_columns_type_change_rewrites_data` 就是这条不变量的守卫。

**改写必须保语义。** 表达式引擎的 `to_index_expr()` 把一个谓词改写成
"喂给索引的形式"之后，结果集必须和没改写时**一模一样**。
这是唯一能安全改写的前提，也是最容易被打破的一条。

### 第三层：差分测试（对拍）

**同一个问题，用两条完全独立的路径算，然后比对结果。**
这是这份教程里最有效的单一手段，没有之一。

它的威力在于：它不需要你知道正确答案是什么。两条路径同时犯同一个错误的
概率远低于一条路径犯错，前提是**两条路径的独立性是真的**。

本教程实际在对拍的东西：

我们自己的 **LZ4 编解码器** 对着 Python `lz4` 包（C 实现）对拍——
抓到了 offset 算错的 bug。

我们自己的 **varint / delta 编解码** 对着"朴素但绝对正确"的实现对拍
（比如直接 `int.to_bytes` 平铺）——`delta` 解码漏加基值那个 bug 就是这样抓到的，
它只在**首值非零**的列上暴露。

我们的**索引检索**对着 **numpy 暴力检索**对拍。
这条对拍在 `measurements/vector_index_measurements.py` 里真的跑着：
第 13 到 16 章的召回率数字都出自它自己的 `recall_of()`——
先 `index.search()`，再用 `pairwise_distances` + `top_k` 独立算一遍标准答案，求交集。
`mini_lancedb/index/base.py` 里的 `recall_against_bruteforce()` 是同一件事
被抽成公共 API 的那份实现，公式一样（`recall@k = |ANN_k ∩ BF_k| / k`），
留给外部调用者；随文脚本走的是自己那份，正文的数字不经过它。

我们的**过滤器**对着 **Python 循环逐行判定**对拍——
向量化求值器和朴素循环同时错的概率很低。

**差分的选点比差分本身更重要。** 对拍要有意义，两条路径必须在
"哪一边可能错"上是异质的：两个自己写的 numpy 向量化实现互相对拍，
价值接近于零；自己写的向量化实现对着一个显式的 Python 循环对拍，才有价值。

### 第四层：回归测试（每个坑一条，并且写清"不修会怎样"）

前三层是"主动出击"，这一层是"不再犯第二次"。

`tests/test_regressions.py` 的组织方式值得单独说，因为它的形态比内容更有价值。
它现在有 **23 个用例，分成九组**，每组对应一类失败模式：

编码器的往返测试"自洽但不能证明正确"；
重载了比较运算符的 AST 节点（拿它去比较永远不会报错）；
索引与行号（一个会崩、一个会算错）；
剪枝决策的粒度；监控指标静默归零；
schema 演进（元数据撒谎）；upsert 的静默错误；
**`cleanup_old_versions` 把标签指向的版本的数据文件删掉**；
**全 null 列改类型写出读不回来的表**。

最后两组（第八、第九）值得单独点出来：**它们是唯一两组"会丢数据"的**，
也都是后来那一轮独立审计才查出来的，不是写实现时自己发现的。
前面七组的失败形状是"结果不对"，这两组的形状是"写成功了、
当时不报错、事后才炸"。**一份回归清单如果不把这两类分开标，
读者会以为所有 bug 都是同一种严重程度。**

这份文件的开头写明了一条维护规则，它是整份测试套件里最值得抄的一句话：
**修了 bug 就在这里加一条，而且注释里要写清楚"不修会怎样"，
因为它比断言本身更有价值。**

为什么"不修会怎样"比断言更有价值？因为断言只说明"当前实现满足这个条件"，
而"不修会怎样"说明**这个条件为什么值得存在**。
下一个人重构这段代码时，断言可能被顺手改掉，而那段注释会拦住他。

这些用例的 docstring 大多写了"当初是怎么发现的"——症状长什么样、根因在哪。
这不是文学修饰：**bug 的发现路径是可复用的知识**——
"这个 bug 是靠对拍发现的"和"这个 bug 是靠用户报错发现的"，
对下一个人来说是两种完全不同价值的信号。

## E.4 对拍的配对清单

把 E.3 第三层具体化成一张可执行的清单。要给一个存储引擎做差分测试，
下面每一对都值得建立，从便宜到贵排列：

**编码层**：自己的编解码器 ↔ 参考实现（C 库、zlib、系统工具）。
不需要覆盖所有输入，只需要覆盖**形状差异大**的几类：空输入、单元素、
高重复、纯随机、以及恰好跨过内部块边界的长度。

**计算层**：向量化实现 ↔ 显式循环实现。前者快、后者显然正确。

**检索层**：近似索引 ↔ 暴力检索。这一对是唯一能量化"近似"代价的地方，
所以它同时是正确性测试和性能评测工具。

**查询层**：谓词改写后的计划 ↔ 未改写的朴素执行。结果集必须完全相同。

**存储层**：真实 store ↔ 内存 store ↔ 仪器化 store。
同一段逻辑在三种 store 上跑，结果必须一致——这能抓到
"只在某个 store 上才出现"的假设泄漏。

**跨版本**：当前版本读旧版本写的数据。这一对的成本最高，
但对一个宣称"文件格式可演进"的系统来说，没有它等于没有承诺。

## E.5 夹具与确定性的四条硬规则

测试的基础设施决定了它的上限。本教程的夹具（`tests/conftest.py`）
里有四条规则，每条都是踩过坑之后加的。

**第一条：默认跑在内存 store 上（`memory://`），不是临时目录。**
理由不是图快，是**隔离**。临时目录方案里，某条用例中途失败、没删干净目录，
下一条用例的 `table_names()` 就会多出一张表——
失败开始互相污染，最后你分不清哪条是真的坏了。
内存 store 让每条用例从绝对干净的状态开始，失败信息永远只反映它自己。
需要真落盘行为的用例，夹具里留了 pytest 的 `tmp_path` 这个口子。
不过按仓库现状看，真正落到它上面的只有 `tests/test_connection.py`
里那几条"连到一个本地目录"的用例——`cleanup_old_versions` 的那几条
和权限表的那几条其实都跑在内存 store 上。留口子是对的，
但别把"留了口子"读成"这些路径被测过"。

**第二条：所有测试数据必须确定性生成。**
`make_vectors()` 用固定 seed 的 `default_rng`。原因写在它的 docstring 里：
任何"顺序对不对"的断言，只要数据是随机的，就会变成间歇性失败，
**而间歇性失败没人会去查**。一条 3% 概率失败的测试，
在 CI 上的实际效果等于不存在。

**第三条：测试数据的规模要跨过内部阈值。** 就是 E.2 第三种假绿讲的那两条
（120 行而不是 10 行、8 维而不是 7 维）。

**第四条：噪声要压掉，让真失败显眼。**
`pytest_configure` 里过滤掉 `DeprecationWarning`——
弃用警告会把真正的失败淹没在输出里。

**这四条规则的共同点：它们都在为"失败信息可读"服务。**
一套测试套件的价值不取决于它有多少条用例，
取决于**失败的时候你能不能在三十秒内知道出了什么事**。
一条失败信息含糊的测试，实际是负资产：它消耗注意力，却不提供信息。

## E.6 什么数字可以当断言，什么数字不能

这是全书方法论的核心，和 00-preface 第 0.5 节的"关于实测的约定"是同一件事，
只是这里要把它落成**可执行的判定规则**。

`measurements/vector_index_measurements.py` 的开头把这条规则写得很清楚，
它是这份教程里判据最明确的一段：

**可以当断言的（同数据、同参数，重跑逐位相同）：**
召回率、分区大小分布、候选集大小、距离计算次数、编码后的字节数、
数据文件的大小、行数、I/O 请求次数、只算数据文件的读取字节数、
剪枝掉的片段数。这些量是**确定的**——它们只取决于算法和数据，
不取决于机器。

**看着同样确定、其实不是的：任何把 manifest 算进去的字节数。**
"字节数嘛，当然是确定的"——这句对只算数据文件的那些成立，
对"整次提交"就不成立：每次提交都会整体重写一份 manifest，
而 manifest 里存着 `time.time()` 时间戳，同一份数据重跑，
这一项会有几个字节到几百字节的浮动。本机把
`examples/06_versioning_and_maintenance.py` 连跑两遍，
"删一半"那次的整次提交写入一次是 102,657 字节、另一次是 102,656 字节；
同一份脚本末尾 `cleanup_old_versions` 的可回收字节数从 8,763,746
变成 8,763,466。对照第 23 章 §23.3 那两个数（读 5,344 字节、
142,008 字节）——它们只算数据文件，两遍逐位相同。
所以判据要再切一层：**只算数据文件或编码结果的字节数可以写死，
凡把 manifest、"整次提交"算进去的字节数，要写 `≈` 或者给一个区间。**
这一类比挂钟时间更阴，因为它长得像确定性的量：写的人很容易把它
写成精确值，下一个人重跑发现对不上，就会开始怀疑整份数据。

**不能当断言的（挂钟时间）：**
查询延迟、建图耗时、训练耗时。同一台机器上、同一份数据、同一组参数，
连跑两遍耗时列就能差出四成（本机实测的量级），取决于机器负载。
所以这类数字只能当**量级和比值**读，绝不能写进 `assert`。

这个区分可以做一次实验直接验证：把 `measurements/vector_index_measurements.py`
的同一节连跑两遍、逐行 diff，会看到**召回率、inertia、候选比例、分区大小逐位相同**，
而**每一个耗时列都变了**。本机这次跑第 13 章那一节，两遍相差最大的一档
是 k-means 的耗时（41.6 毫秒对 25.4 毫秒，约四成），第 13.10 节里那些更小的延迟
也在百分之十上下反复跳。所以"这套数字可复现"这句话必须拆成三句说：
**只算数据文件的量可复现到逐位，含 manifest 的字节数要带 `≈` 或区间，
挂钟时间只能复现到量级。**
（上面这个幅度是本机这一次的量级；换一台机器、或者机器上还跑着别的任务，
波动只会更大。）把这几类混在一张表里而不加区分的报告，
读者会误以为延迟也是稳定的、提交大小也是个精确值。

这条区分直接解释了本教程里的几个"难看"的数字为什么是那样写的：

第 13 章说"在 3000 行的规模上，延迟数字全是噪声"——
因为 3000 行的检索快到接近测量误差，挂钟时间的抖动大于真实差异。
第 24 章用"2 万行 64 维下暴力检索 0.74 毫秒，而召回只有 0.47 的 IVF_PQ
反倒要 0.82 毫秒"推出"小数据别急着建索引"时，
比的是**同一台机器上同一批查询的相对关系**，不是绝对速度——
那个 0.74 毫秒每次跑都不一样（第 12 章对同一份基线记下的两次运行是 0.502 / 0.680 毫秒），
换成另一台机器更会变，但"在这个规模上暴力检索够用"这个结论不变。
第 15 章说"HNSW 建图时间是 `O(n·m·ef_construction)` 量级，
50000 个点上 Python 实现要 128 秒"——**"128 秒"是这一次跑出来的实例值，
真正能被引用的是那个复杂度**：换台机器、换个实现，秒数会变，
但"建图成本随 `n`、`m`、`ef_construction` 三者相乘增长"这个关系不变。

**还有一类数字介于确定和噪声之间，要特别小心：内存占用。**
在同一个进程里测量内存，会受到分配器行为、GC 时机、
以及"上一个用例留下的对象还没有释放"的影响。
本教程的应对是尽量算**理论占用**（每向量字节数 × 向量条数）
而不是测实际 RSS，并在测实际值时标明测量口径。

**还有一类：外部系统的数字。**
厂商公布的性能数据、GitHub star 数、文档里的默认值——
这些必须标明**来源 + 日期 + 口径**，并且**永远不要和本机实测混在一句话里**。
本教程里的写法是"官方口径，2026-04-07"或者"厂商口径，us-east-1 on-demand"，
查不到出处的标"未经确认"，推算的标"推算"。
这不是学术洁癖：**混在一起之后，读者没有任何办法区分
哪一部分可以信、可以信到什么程度。**

## E.7 并发怎么测

并发是存储引擎测试里最容易被"假装测过"的部分。

本教程的做法是**不测"并发"这个整体，而是把它拆成三个能单独验证的命题**。
拆法值得抄，但覆盖到哪一步也要如实说：
**这三条里真正落地的是"把决策逻辑做成纯函数"这件事本身，测试并没有跟上。**

**命题一：乐观提交协议在冲突时真的会重试，且重试之后结果正确。**
这可以单进程测——手工构造两条互相冲突的事务，
让第二条走 rebase 路径，然后检查最终状态。
`mini_lancedb/format/transaction.py` 里的 `can_rebase()` / `rebase_plan()`
就是为这个可测性把逻辑从 I/O 里拆出来的：
**把决策逻辑做成纯函数，它才可测。**
冲突矩阵（`CONFLICT_MATRIX`，由一组规则在导入时填好）和 rebase 建议
都是不碰 I/O 的纯函数，这一半做到了——但要说清楚，
**仓库里现在没有任何测试调用这两个函数**，可测性就位了，用例还没补上。

**命题二：多进程写不会丢数据。** 这个必须用真进程测，
因为要覆盖的真正变量是"提交之间没有共享内存"。
用 `multiprocessing` 起 N 个进程各写一批，最后检查总数。
**本仓库没有这样的测试。** 这一条在迷你实现上也只在本地 store 上有意义
（真实系统的这一层在对象存储上，第 8 章讲了 S3 的原生原子写），
覆盖**刻意有限**可以，但"有限"不等于"把该怎么做写一遍就算做过了"——
**测试覆盖的边界要写出来，不要让人以为测过了。**

**命题三：读到的版本要么是旧的、要么是新的，不会是中间态。**
这是快照隔离的定义，可以靠"写者不停改、读者不停读、每读一次校验内部一致性"来测。
**本仓库同样没有这样的测试**——没有起过线程，也没有起过进程。
所以这一节给出的是三条**可测性设计**，不是三份测试结果。

**并发测试的禁忌：用 `sleep` 控制时序。**
任何"睡 100 毫秒等另一个线程做完"的测试都是 flaky 的种子。
正确的做法是用事件/屏障同步，或者干脆把并发收敛成"多进程 + 最终一致性断言"。

## E.8 格式兼容怎么测

一个宣称"文件格式可演进"的系统，如果没有格式兼容测试，
它的承诺就只是文档里的一句话。

**最低要求：golden file（黄金样本）。**
把各种格式版本的**真实文件**签入仓库（或者用脚本生成后校验哈希），
测试直接读这些文件，断言解析结果正确。
**这些文件永远不重新生成**——它们是历史版本的化石，重新生成就等于删掉了测试。

本教程的迷你实现用了一个成本更低的替代方案：`examples/02_file_format_tour.py`
把文件逐字节拆开打印，而那些输出被引用在正文里。
它能抓到"格式变了"（输出会变），但抓不到"读旧文件读错了"。
**这个限度值得说明**：真正的格式兼容测试需要跨版本的样本文件，
本教程没有做到，因为迷你实现只有一个格式版本。
第 28 章 §28.4 记了一次真实的兼容性事故（Lance 11.1.0 之前，
内层全 null 的 FixedSizeList 会写出任何版本的 reader 都拒收的页），
那个事故恰恰说明**这类测试在真实系统里是必需品而不是奢侈品**。

**向上兼容与向下兼容要分开承诺。**
"新版本能读旧文件"和"旧版本能读新文件"是两个完全不同的命题，
成本也完全不同。真实 Lance 的文档里对这两者分别有说法，
第 28 章把那些说法和它们的日期都列了出来。

## E.9 教程里的每个数字是怎么变成可复现脚本的

这份教程的一个硬承诺是"每个数字都能自己复现"。落实它的是三层脚本：

**`examples/`（7 个脚本）** —— 面向读者的、可以直接跑的教学脚本，
每个对应若干章节，输出是人读的（带标题、带解释）。
比如 `03_encoding_report.py` 打印每种编码的实际字节数，
`06_versioning_and_maintenance.py` 演示压实反而变慢。

**`examples/verify/`（8 个脚本）** —— 正文里直接引用的**原始测量脚本**，
对应第 9、10、11、12、18、20、22 章（第 10 章有两个：一个量下推收益，
一个量索引缓存）。它们和 `examples/` 分开的原因很实际：
正文引用的是"当时跑出那个数字的东西"，需要保持原样可复现；
而 `examples/` 里的教学脚本会随着叙述需要调整输出格式。
**混在一起的结果是：正文引用的数字和脚本输出慢慢对不上，而没人会发现。**

**这条规矩是被打脸打出来的，不是因为洁癖。** 这一层里
`ch12_refine_factor.py`、`ch10_index_cache.py`、`ch22_embedding_functions.py`
是**补写的**：它们各自对应的那一节原先都是手抄的数字，而复核时
三节里有三节都抄错了（`refine_factor(1)` 那行显示的是一次并不发生的
重排、索引缓存被说成不存在、相似度范围抄成了一个子集）。
三个错误有一个共同形状——**手抄的输出不会报错，只会安静地错下去**，
而且错得越自然越难发现。所以判据不是"这一节看起来挺确定"，
而是"这一节的数字有没有一个能跑出它的脚本"。
**没有脚本的数字，默认当作未验证。**

**`measurements/vector_index_measurements.py`** —— 第 13 到 16 章
全部索引实测数字的唯一来源，一章一节，可以按章号单独跑。
它把这些数字集中在一处的原因同样很实际：
**索引参数是互相影响的**，把测量散在四个脚本里，
就无法保证四章引用的是同一份数据、同一组参数、同一台机器。

这三层的分工本身，就是这套"实测"约定的工程形态：
**引用即脚本，脚本可单独跑，跑出来的数字和正文对得上。**

一个配套的机械手段是 `check_docs.py`：它把正文里写下的硬数字
（测试用例数、代码行数）和仓库里的事实对一遍，
把"第 N.M 节"这类交叉引用和真实的小节号对一遍。
**这类工具的价值在于：它们抓的是人眼审不出来的错误。**
章节改写会让小节号漂移、让"1144 个测试"这种硬数字过期，
而人在读了一遍自己刚改完的文件之后，是发现不了这些的。

## E.10 一份可操作的检查清单

把上面所有内容压成一份流程。**发现一个"结果不对"的时候，按顺序走：**

**第一步，把它变成一个确定性的复现。** 固定的数据、固定的 seed、
固定的调用顺序。不能稳定复现的 bug 不算被找到——它只是"出现过"。

**第二步，判断它是"炸"还是"静默"。** 如果它抛异常，先读异常信息，
但**不要相信异常位置**：LZ4 那个 bug 报的是"字面量超界"，
真正的原因是几百字节之前的 offset。异常位置往往离起因很远，
这一点在分层清晰的系统里尤其明显。

**第三步，构造第二条独立路径。** 这是最关键的一步。
如果 bug 出现在编码器上，就找一个参考实现来对拍；
如果出现在检索上，就用暴力检索对拍；如果出现在改写上，就用未改写的朴素执行对拍。
**没有第二条路径，你只能靠读代码猜；有了第二条路径，你能直接把范围切成一半。**

**第四步，二分定位。** 用第二条路径的输出差异去切分输入空间：
哪个规模开始偏？哪一类值开始偏？差值有没有规律（差 1？差一倍？错位？）？
"差一倍"指向记账口径，"错位一行"指向边界条件，
"只在首值非零时出现"指向初始化逻辑——**差异的形态比差异的大小信息量更大。**

**第五步，写回归测试，并且把"不修会怎样"写进注释。**
修完不回填测试的 bug 一定会回来。而注释里只写"修了 X"的回归测试，
在下一次重构时会被当成过时的东西删掉。

**第六步，问一句"还有谁犯了同样的错"。**
同一个错误模式往往在多个模块里重复出现：delta 解码漏加基值，
那么所有"差分编码"的地方都可能有同样的错；
某个索引忘了跳过片段，那么所有索引都要检查。
**这一类连带修复的价值，往往大于原始 bug 本身。**

## E.11 小结

把这份附录压成五句话：

存储引擎的失败模式是**静默的错误结果**，不是崩溃，
所以"测试通过"和"实现正确"是两个不同命题，而 1144 个测试与 55 条坑清单可以并存。

假绿有三种：**自己验自己**、**断言编码了 bug 的行为**、
**测试数据走不到出问题的分支**。三种都要靠"断言必须能说清为什么"来防。

有效的验证有四个层次：**单元测试**（快但只能覆盖你想到的输入）、
**不变量测试**（覆盖输入空间而不是输入点）、
**差分对拍**（不需要知道正确答案，只需要两条独立路径）、
**回归测试**（修了 bug 就加一条，写清"不修会怎样"）。

只算数据文件的量（召回率、字节数、行号、I/O 计数）可以当断言；
含 manifest 的字节数要带 `≈`；挂钟时间只能当量级和比值；
外部数字永远标明来源、日期与口径——
而且**永远不和自己的实测混在一句话里**。

最后一条，也是最容易被跳过的一条：
**把测试覆盖的边界写出来。** 本教程明确写了哪些东西没测
（跨版本格式兼容、真对象存储上的并发、真实 RSS 内存），
并且写明了为什么。**一份不说明自己限度的测试报告，
比没有测试报告更容易让人误判风险。**
