# 第 3 章　Lance 文件格式

LanceDB 的性能、成本、能力边界，八成都能追溯到它底下的那层文件格式。
上一章把整套流程跑通了，但每一步背后"磁盘上到底写成了什么"还没打开看过。
这一章就做这件事：把一个 `.lance` 文件拆到字节，看清它怎么摆。
后面所有章节——索引怎么存、删除为什么不改数据、为什么加一列几乎不花时间——
都是这一章的直接推论。

## 3.1 为什么不能直接用 Parquet

第 1 章 §1.3 已经讲了四条理由，以及一组官方基准（随机点查最多 1000 倍、
取 blob 约 75 倍、加列回填约 61 倍）。这里不重复那套账，
只补一句它们**共同指向的那个结论**——因为正是这个结论决定了本章后面
每一个字节的摆法。

向量数据库常见的做法是"底下一个通用列存格式 + 上层一堆索引"。
Lance 没有这么做，它自研了一个列式格式。最能说明原因的是随机访问。
Parquet 的组织单位是 row group（典型 128 MB）：读一行要定位 row group、
解压整块、再在块内定位。分析型扫描不在乎这个，但向量检索是点查——
ANN 返回 100 个行号，你要把这 100 行的原始列取回来，
100 个行号散落在 100 个 row group 里，就是几百 MB 的读放大。

要让"取 100 行"变成"读几百 KB"，格式必须满足一个条件：
**最小可读单位要足够小，而且要能在不解析整块的前提下定位到它。**
本章剩下的部分讲的就是 Lance 怎么做到这件事——答案是
"页 + 页表 + 64 字节对齐的缓冲区"（§3.2 到 §3.3）。

另外三条理由落到字节上是同一句话的三种形态：嵌套的每一层要能被
**单独取一个子列**（所以嵌套被结构化解开成平列）、blob 要能**绕开行读取**
直接拿到（所以 blob 外置成独立 buffer）、统计信息要能**和数据分离**
（所以列统计被抄进 manifest，让剪枝零 I/O）。
四个要求各不相同，但都是"让读什么独立于文件里有什么"。
**Parquet 为"扫全表"优化，Lance 为"点查 + 多模态 + 频繁演进"优化**——
这句总结第 1 章也说过，区别是这一章要把它兑现成具体的字节。

## 3.2 一个 Lance 文件的逐字节布局

Lance v2 容器（当前主力格式）的布局是固定的五段：

```
┌──────────────────────────────────────────────────────────┐
│ Data Pages        各列的数据页，每个缓冲区按绝对偏移引用    │
├──────────────────────────────────────────────────────────┤
│ Column Metadatas  每列的页列表、每页编码、每页 buffer 偏移   │
├──────────────────────────────────────────────────────────┤
│ Column Metadata Offset Table   每列元数据的 (偏移, 长度)    │
├──────────────────────────────────────────────────────────┤
│ Global Buffers Offset Table    跨列共享的辅助数据（本实现恒为空）│
├──────────────────────────────────────────────────────────┤
│ Footer            u64 u64 u64 u32 u32 u16 u16 "LANC"     │
└──────────────────────────────────────────────────────────┘
```

footer 定长 40 字节，是整份文件的"目录"——读它就知道元数据从哪开始、
有几列、是哪个版本。**全部小端**，字段按顺序是：三个 `u64` 偏移量
（字段 A 是第 0 列元数据的起始偏移，字段 B 是列元数据偏移表的起始偏移，
字段 C 是全局缓冲区偏移表的起始偏移）；一个 `u32` 全局缓冲区个数
（跨列共享的辅助数据条数，本实现恒为 0）；一个 `u32` 列数
（列元数据条数，**含结构化解开出的子列**）；一个 `u16` 主版本号
（当前为 2）；一个 `u16` 次版本号（0 / 1 / 2 / 3）；
最后 4 字节魔数 `LANC`。

**为什么写成"字段 A / B / C"而不是有名字的字段**，因为这正是它
和 manifest 的区别：footer 的三个偏移量是**位置约定**，
靠"第几个 u64"来读，不是靠名字；而 manifest 里的东西是自描述的。
连起来看，总长 `3×8 + 4 + 4 + 2 + 2 + 4 = 40` 字节，
**这个和是可以手算对上的**——格式的可验证性就是从这种地方来的。

**为什么魔数在尾部而不是头部？**

因为读取者只能"从尾巴上切 40 字节"。如果魔数在头部，你就得先读头部、
再想办法定位 footer——而 footer 的位置只有在知道"元数据在哪"之后才知道，
这是个循环。把魔数放尾部，读取流程就变成单向的：

1. 读末尾 40 字节，校验 `LANC`；
2. 从 footer 拿到列元数据位置与列数；
3. 读列元数据（一次范围读）；
4. 需要哪些列、哪些行，就只读那些页。

**整个"打开文件"的过程只需要 2 到 3 次 I/O**，和你表有多大无关。
这一点在对象存储上是决定性的：S3 上一次 GET 的延迟在几十毫秒量级，
如果打开一个文件要发 20 次请求，任何查询都别想做到 100 ms 以内。

**打开时会校验什么，损坏又怎么被发现。** 读取端的检查只有三道，全是结构性的、
没有校验和：末尾 4 字节必须是 `LANC`；主版本号必须是 2；缓冲区位置、页表和
位打包数据在解引用时不许越界（越界抛 `CorruptedFileError`，而不是返回一段
错位的数据）。**这个容器里没有 CRC、也没有页级校验和**——真实 Lance v2 的页
描述里同样没有这一项（本教程未在规范中找到，标注为未完整确认），完整性靠的是
"结构性自洽"加底层存储自己的校验。代价要说清楚：**一个字节被静默翻转、
翻转后仍然结构合法，是检测不出来的**——比如数据页里某一位被改，读取端会照常
解出一批"看起来对"的值。要防这一类，只能靠对象存储的完整性保护（如 S3 的
附加校验和）或应用层自己加摘要。

**容器有两个硬上限，都是 32 位。** footer 里的"列数"和每列的页数都是无符号
32 位，官方 v2 规范的 proto 注释把范围写成 0–4Gi，也就是**单个文件最多 2^32 列、
每列最多 2^32 页**；而所有偏移都是 u64，所以单文件的理论上限是 2^64 字节
（实际总被存储后端卡住）。真实场景里先撞到的不是"文件太大"而是"一个文件装不下"，
Lance 的答案是**一张表由很多个数据文件组成**（table format 里的 fragment 指向
它们），文件只是"一批行"、不是"整张表"。本教程把"一个文件"和"一张片段"当成
一回事，分片这一层留到讲版本与存储的章节。

## 3.3 缓冲区：绝对偏移 + 64 字节对齐

Lance 里所有实际数据都装在 **buffer** 里。缓冲区的位置记录在列元数据里，
而且是**文件内的绝对偏移**，不是一个可变的基址加相对偏移。

两个后果：

**好处是零成本定位。** 读取者拿到元数据就能直接发范围读，
不需要先解析前一个缓冲区才能算出后一个在哪。同一页的多个缓冲区
（值、字典、下标、有效性）可以并行发请求。

**代价是元数据体积。** 每个缓冲区要在元数据里留 16 字节（偏移 + 长度）。
一个页 2 个缓冲区、一个文件 10 万个页，就是 3.2 MB 的元数据——
而元数据每次查询都要读。这也是真实 Lance 用 FlatBuffers 而不是
文本格式存元数据的原因之一。

**对齐是硬要求，不是优化。** Lance 规定缓冲区总是对齐到 64 字节边界
（需要直通 I/O 时按 4096 字节）:

- 64 字节是 AVX-512 一条指令的宽度，对齐内存上的 SIMD 解码没有跨 cache line 的惩罚；
- 本地盘上 4 KiB 是典型预读粒度，对齐能让一次 `pread` 落在尽量少的物理块里；
- 用了 `O_DIRECT`（绕过页缓存）时，不对齐的内核请求会被直接拒绝。

对齐的代价是填充字节。写入端每个缓冲区平均浪费 32 字节，
这在几 KB 的小页上很可观，在 MB 级的大页上可以忽略——
这又是"为什么真实 Lance 推荐 8 MiB 的页"的一个理由。

## 3.4 列元数据：页、编码、统计

列元数据是这一层最核心的结构。**它回答五个问题。**

**这一列是什么？** 每条列元数据都带 `field_id` 和逻辑 `type`，
所以读取端光凭它就能重建出这张表的 schema——本实现的
`LanceFileReader.schema()` 就是拿列元数据里的 `type` 反序列化出来的，
不需要外部 manifest 配合。这一点值得单独点出：**容器是有类型的**，
只是类型挂在每列的元数据上，而不是集中在某个文件头里。

**这一列分成几页？** 每页记录 `num_values`（这一页有多少个值）
和 `priority`（页内首行的顶层行号）。有了 `priority`，
"找第 12345 行在哪一页"**设计上**可以是一次二分查找，不需要逐页累加。

不过这里要说清本实现的实际做法：**它没有用二分查找**。
读取路径（`LanceFileReader._read_pages_as_numeric` /
`_read_pages_as_bytes`）是线性扫过页列表，靠 `_page_row_bounds()`
把 `num_values` 累加成区间再求交；`priority` 只在写入时被保存下来，
**从不参与定位**。所以 `priority` 在本实现里目前是一个"为将来留的字段"，
它省下的那次累加还没有发生。

本实现的 `priority` 直接写成 JSON 整数、不限位宽；真实 Lance 把它作为
定宽字段存在平铺的元数据里（它的具体位宽本教程未逐字节核对）。

**每一页用什么编码？** 记录编码名（`plain` / `bitpack` / `dictionary` /
`byte_stream_split` / `fsst`……）。**编码是逐页决定的**，同一列的不同页
可以用不同编码——因为局部数据分布可能完全不同。比如按时间排序的日志表，
早期页全是重复值（走 `rle`），后期页是随机 uuid（走 `plain`）。

**值在哪几个缓冲区里？** 每页带一组 `(buffer_offset, buffer_size)`，
可能有一对（纯值），也可能有四对（字典编码：offsets + 字典 + 下标 + 有效性）。

**这一列的统计是什么？** 一条 zone map：数字列存 `min` / `max`（落盘时写成
浮点）和 `null_count`；字符串列的 `min` / `max` **截断到前 64 个字符**再存。
统计是**列级**的、不是页级的，这一点决定了它的粒度——一个片段的某一列只
给出一对边界值，页内不做二次统计。

统计信息这一点值得单独强调，因为它决定了**查询规划阶段的剪枝能不能零 I/O**。
Lance 的做法是把列统计**抄一份进 dataset 的 manifest**，
于是"这个片段里有没有可能包含 `id > 900000` 的行"这个问题，
在打开任何数据文件之前就能回答。如果统计只存在数据文件里，
那就要么每次查询都打开文件读元数据，要么就放弃这类优化。

## 3.5 嵌套列是"结构化解开"的

这是 Lance 文件格式里最反直觉、也最重要的一个设计。

假设表里有一列 `tags: list<utf8>` 和一列 `vector: fixed_size_list<float64>[64]`。
在文件里它们**不是**两个"嵌套结构"，而是被摊平成：

```
tags           （父列：不存值，只记子列的编号）
tags.offsets   int64     长度 = 行数 + 1
tags.item      utf8      长度 = 所有 list 元素总数
vector         （父列）
vector.item    float64   长度 = 行数 × 64
```

于是：

- 向量列的 128 万个 float64 在文件里就是一列**平铺的浮点数**，
  可以套用任何数值编码——第 4 章讲的 FOR、位打包、delta 在这一列上都成立
  （我们实测这一列自动选了 `byte_stream_split`）；
- `tags.item` 可以走字典编码和 FSST 压缩，而 offsets 列可以走 bitpack；
- 读取时按 `children` 数组跳转，父列本身不占数据页。

实测一个 2 万行、64 维向量的表，列结构是这样的（`inspect_lance_file` 的输出）：

```
index  name          type        rows      pages  encoding
0      id            int64       20000     5      delta
1      vector        fixed_size_list<float64>[64]  20000  0     -
2      vector.item   float64     1280000   313    byte_stream_split
3      title         utf8        20000     5      fsst
4      cat           utf8        20000     5      dictionary
5      score         float64     20000     5      dictionary
```

注意 `vector` 自己没有任何页，它的 313 个页全挂在 `vector.item` 上。
这个结构解释了后面很多事：

- 为什么"只读 `id` 列"几乎不花钱——因为物理上真的只读了 `id` 那一列的页；
- 为什么向量索引必须额外存一份压缩副本——因为原始向量占了文件 96% 的空间；
- 为什么加一列向量列不会让老数据变慢——老文件里根本没有这一列。

**超大对象是同一个思路的另一个方向：把列从主文件里拆出去。** 一张 4K 图、
一段音频、一个 PDF——行里塞一个 20 MB 的值，列里所有行的读取都会被它拖累。
Lance 2.2 的 Blob V2 按大小自动挑落盘形态：**小于 64 KB 走 Inline**，直接
放在主数据文件里，和普通定长列没有区别；**64 KB 到 4 MB 走 Packed**，
若干 blob 打包进共享的 `.blob` 边车文件，每个最多 1 GiB；**大于 4 MB 走
Dedicated**，一个 blob 一个 `.blob` 文件；第四种是 **External**，URI 由你指定，
Lance 只存引用。四档共用同一套磁盘描述（kind / position / size / blob_id /
blob_uri），读取代码因此不用分支。这一层的完整版本在第 21 章——那里还有
"同样的字节，Inline 和 Dedicated 在随机 blob 读取上差多少"的实测数字。

## 3.6 一次读取的真实成本

上表那个 2 万行、64 维的表，文件总共 10.7 MB。我们实测了几种读法。
下面这张表是同一个文件上四次读的 I/O 账：**读法**是这次做了什么，
**读取字节 / 范围读次数**是它实际发出的请求，**读页 / 跳过页**说明投影与
行范围下推到底省掉了多少页：

| 读法 | 读取字节 | 范围读次数 | 读页数 | 跳过页数 |
|---|---|---|---|---|
| 打开文件（只读元数据） | 138,555 | 3 | 0 | 0 |
| 读 `id` 整列 | 158,870 | 8 | 5 | 0 |
| 读 `vector` 整列 | 10,378,555 | 316 | 313 | 0 |
| 读 `id` 列的前 100 行 | 142,714 | 4 | 1 | 4 |

三件事值得停下来看：

**第一，打开文件的 138 KB 全是元数据。** 而同一个 2 万行的表只有 6 列、
333 个页——`vector.item` 一个子列就占了 313 个。真实 Lance 的元数据用
FlatBuffers 编码，体积会小一个数量级；但**元数据成本随页数线性增长**这个
规律是一样的。这也是为什么"页不能太小"——同一个 5 万行的表，只把页从
8192 个值改成 512 个值，**打开成本就从 92,610 字节（文件的 0.67%）涨到
1,409,339 字节（文件的 9.05%），差 15 倍**，而文件本身只大了 12%。

**第二，读 `id` 列的 158 KB 里有 138 KB 是元数据。** 也就是说，
对于"读一个小列"这种查询，瓶颈根本不是数据，而是元数据。
真实系统里对应的优化手段是：把元数据做紧凑、按列只读该列的元数据块、
或者在 dataset manifest 里缓存一部分。这些都是"小列查询"能不能做快的胜负手。

**第三，行范围下推真的省了页。** 读前 100 行只读了 1 页、跳过 4 页。
这不是"读完再切"，是真的少读了 4 个页的字节。列存的价值就在这里。

## 3.7 迷你实现：`format/lance_file.py`

`mini_lancedb/format/lance_file.py` 把上面这套东西完整实现了一遍。
它不是"演示用的玩具"——它是这份教程里其他所有模块的地基，
dataset、索引、删除文件全都建立在它之上。核心 API 只有两组：

写入端：

```python
writer = LanceFileWriter(target_values_per_page=4096, compression="lz4")
writer.write_batch(batch)
data = writer.finish()          # 一趟顺序写，不需要回填
```

（`target_values_per_page` 这里显式写了 4096 是为了让参数露个脸，
**它不是默认值**：默认是 8192，见 `mini_lancedb/format/lance_file.py`。
这个数是"每页目标值个数"，直接决定页表长度和 §3.6 那次读取的
请求数——调小它页变多、随机读的放大倍数就变，第 6.5 节量过这件事。）

读取端：

```python
reader = LanceFileReader(store, "data/xxx.lance")
reader.num_rows                  # 只读了 footer，还没碰数据
reader.read(columns=["vector"], row_range=(0, 1000))
reader.explain()                 # 把物理结构摊开，不读数据页
reader.stats.range_reads         # 这次读到底发了几次范围读
```

写入端有一个必须强调的顺序约束：**先写数据页，再写列元数据，最后写 footer**。
因为元数据要记录每页的偏移和大小，只有写完数据才知道；
而对象存储不支持随机改写，所以必须"边写边记、最后一次性收尾"，
不能回头 seek 回填。`finish()` 里的注释把这个顺序点明了。

读取端有两个值得单独看的实现。

**缓冲区合并读**（`_read_buffers_coalesced`）。一页可能有 1 到 4 个缓冲区，
它们由写入端顺序摆放，彼此邻近。如果每个缓冲区发一次范围读，读一页就是 4 次往返；
合并成一次读，多读几 KB，少发三次请求。对象存储上"一次请求"的固定开销
（RTT + 鉴权 + HTTP 头）远大于多读几 KB 的代价。这个取舍和
Lance 在 S3 上的策略一致。

**页级行范围下推**（`_page_row_bounds`）。这是最容易写错的地方之一。
对定长列表列，一页的值数是"行数 × 列表长度"，计算页覆盖的行区间时
必须除回去；忘了除回去，行范围下推就会把行数算错——而这类错误
在小数据上往往测不出来，因为整表只有一页，永远是"全读"。

## 3.8 与真实 Lance 格式的差异（诚实声明）

这份迷你实现的目标是"结构一致、语义一致"，不是"二进制兼容"。
六处刻意的差异，都值得知道：

**元数据用 JSON 而不是 FlatBuffers。** 选 JSON 是为了教程能直接把
元数据打印出来看——下一章的所有观察都依赖这个。代价前面已经量化了：
同样是 6 列 333 个页，元数据比真实格式大一个量级。
FlatBuffers 的真正价值是"零拷贝 + 无需解析"：读一个字段不用反序列化整个结构。
对一个"每次查询都要读、还要读很多次"的数据结构，这个属性值很多钱。

**类型写在列元数据里，global buffer 表恒为空。** 本实现把每一列的
`field_id` 与逻辑 `type` 直接写进该列的元数据项，于是文件是自描述的、
`schema()` 不依赖外部 manifest（见 §3.4）。代价是类型信息在文件里被重复了
N 次——对一个"每列都要读一次元数据"的格式，这点冗余换来的读取路径简化很划算。
真实 Lance v2 另有一张 global buffer 偏移表，用来挂跨列共享的辅助数据；
本实现保留了这张表的位置，但恒写 0 项。

**有效性位图放在列级而不是页里。** 真实 Lance 把 null 位图编进页的编码里，
我们放在列元数据里指向一个额外的缓冲区。语义相同（哪些行是 null），
实现更简单。代价是"只读某一页的 null 位图"做不到，必须整列读——
对 1 bit/行的位图来说这个代价可以接受。

**页表内联在列元数据里，而不是独立的页表段。** 真实 v2 把每页的
`buffer_offsets` / `buffer_sizes` 直接写在 `ColumnMetadata.Page` 里，
我们照做了，但为了简化的读取路径额外维护了一个可选的页表视图。
效果一样：读一个缓冲区只需要元数据，不需要额外往返。

**只有 major version 2。** 真实 Lance 的版本矩阵是
`0.1`（只能读不能写）、`2.0`、`2.1`、`2.2`、`2.3`（不稳定），
外加 `legacy` / `stable` / `next` 三个别名。我们的 `finish()` 永远写
major=2、minor=0，读取端只校验 major 是 2。

**没有 `_rowid` 这类隐藏列。** 真实 Lance 的 dataset 给每一行一个 64 位的
行地址 `(fragment_id << 32) | offset_in_fragment`，它作为保留字段 id（`-3`）
的隐藏列 `_rowid` 存在，`_row_created_at_version` /
`_row_last_updated_at_version`（`-4` / `-5`）同理；删除文件、索引、回表
全都建在这个地址上。本教程把行地址当算式现算，不把它物化成一列，所以文件里
看不到这些字段——这一层差异会在第 5 章和第 9 章显出来。

## 3.9 版本号是个雷区

**"Lance 版本"至少有三种互不相同的含义**，中文技术资料里最常搞混的就是它们：
**文件格式版本**（磁盘上的字节布局）、**Rust crate 版本**（crates.io 上的
`lance`）、**LanceDB 包版本**（Python/JS 的 `lancedb`）。三者没有对应关系。
2026-10 这个时间点上是：格式稳定版 2.2、在研 2.3；`lance` crate 13.0.0，
另有 v14.0.0-beta.x 预发布；`lancedb` 0.40.0。`lance` 与 `lancedb` 甚至是
两个包——`lancedb` 里打包了 Rust 编译出的原生模块 `_lancedb`，而 `lance`
（导入名 `pylance`）是更底层的 dataset 库。本机上 `import lance` 会失败，
原因是 pip 指向了一个内容滞后的镜像站，**不是**"Python 3.14 没有 wheel"——
第 28 章 §28.1.2 用 `pip index versions` 实测纠正过这个归因。三个版本号的
完整对照、别名（`legacy` / `stable` / `next`）和选型建议都在第 28 章，
这里只留下最要紧的一句：**不存在"Lance V3 文件格式"**——文章里说的
"Lance V3" 指的是索引格式 V3 或 FTS 的 posting 布局，不是容器版本。

文件格式这一层，2.0 到 2.3 各加了什么也值得记住，因为它解释了"为什么升
次版本号通常只是同样的数据写得更小"。2.0（2024-04）是一次重构：去掉
row group 这个概念，并为 list、fixed size list、primitive 引入 null 支持——
本章讲的"页 + 优先偏移"布局就是它定的。2.1（2025-03）增强整数与字符串压缩、
给 struct 字段补上 null 支持、改进嵌套字段的随机访问。2.2（2026-03）加
Blob V2 与原生 map 支持，外加一次大范围的压缩改进。2.3 仍在 unstable，
新增 sparse structural pages 和若干实验性编码，**官方明确要求不要用于生产**，
因为它没有兼容性保证。

还有一个实际的坑：**格式版本之间不保证向前兼容**。官方记录过一个真实的
破坏性变更——早期写入器在处理"整个固定长度列表列的 inner value 全是 null"时，
会把 `bits_per_value=0` 写进 `FullZip` 编码，导致任何读取器都读不了这个文件。
修复在 Lance 11.1.0，但**修复后写出的文件会让老读取器直接 panic**，
而不是报一个可处理的错误。所以跨版本读写 Lance 文件时，版本对齐不是可选项。

## 3.10 小结

把这一章的结论压成五句话：

数据文件是不可变的，所有变更通过写新文件加改 manifest 完成；
Lance 文件 = 数据页 + 列元数据 + offset 表 + 全局缓冲区表 + 40 字节 footer；
缓冲区按绝对偏移引用、64 字节对齐，这是"只读需要的页"能成立的前提；
嵌套列被结构化解开成平列，向量列因此能享受专门的编码和压缩；
列统计会被抄进 manifest，让查询剪枝做到零 I/O。

下一章讲"数据页里到底是什么"——编码和压缩，也就是列存真正省下空间的地方。
