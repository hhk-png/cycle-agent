# 第 23 章　压实与维护

前几章反复出现一个主题：**不可变带来了一切好处，也带来了一切麻烦。**
数据文件不能改，所以删除只能靠删除文件、更新只能靠删加追加、
schema 演进只能靠加新文件。代价会累积，而且累积的方式很不直观。

这一章讲那些"累积出来的债"——小片段、幽灵行、失效索引、膨胀的元数据——
以及 `optimize()` 把它们还清的方式。最后会给一个反直觉的实测结果：
**压实并不总是让查询变快。**

## 23.1 债是怎么欠下的

**债一：小片段。** 每次 `add` 都会产生至少一个片段（一个数据文件）。
一个 RAG 管道每 5 分钟增量写入 200 行，一天就是 57600 行、288 个文件。
一个月之后，一个几百万行的表可能有上万个片段。后果有三个：
每次查询要打开上万个文件（每个至少一次元数据读）；
manifest 里要记住上万个片段的路径和统计，文件本身膨胀到几 MB；
向量索引覆盖不全（新片段里的行不在索引里）。

**债二：幽灵行。** 删除是软删除。删掉一半行之后，数据文件里那一半还在，
只是被删除文件标记为不可见。后果是：读的时候要多一层过滤；
向量索引里那些行还在参与距离计算（占用了 nprobes 的候选名额）；
磁盘空间没有释放。

**债三：索引失效。** 压实会改行号，索引里的行号就指错了。
要么重建，要么跟着重映射（需要行血脉）。

**债四：版本膨胀。** 每次提交都写一份完整 manifest。100 个版本就是
100 份元数据。老版本的数据文件也全都在（因为 `overwrite` 不删文件）。
这个债只有 GC 能还。

## 23.2 压实做什么

`compact()` 做的事很朴素：把一批小片段整个读出来、丢掉已删除的行、
重新写成一个（或几个）大片段，然后在 manifest 里把旧片段换掉。

`compact()` 的签名上有三个参数（另有一个 `max_fragments` 用来把一次
大压实切小，见下文）。片段进不进合并集合的判定**是"或"起来的两个条件**，
任何一个成立就进：

```python
mergeable = [
    f for f in fragments
    if f.num_rows < target_rows_per_fragment
    or (materialize_deletions and f.num_deleted_rows > 0)
]
```

**第一个条件是"太小"**。`target_rows_per_fragment` 决定合并后的目标大小，
默认 100 万行——这是真实 Lance 的默认量级。太小达不到目的，
太大会让后续的增量写入再次把它切成小块。它同时就是"多小算小"
那个阈值：`f.num_rows < target_rows_per_fragment`。

**第二个条件是"删过"**。`materialize_deletions` 决定"删过的片段
要不要参与合并"。设成 `True`（默认）时，只要片段有删除就合并它——
**哪怕这个片段很大、一点不"小"**，因为合并是唯一能把删除真正落地
（把删除文件变成物理上不存在的行）的办法。

这两个条件为什么必须是"或"、不能合成一个，值得停一下：它们的**触发理由
完全不同**。"太小"是为了减少片段数、降低元数据与规划开销；
"删过"是为了回收空间、让统计量重新变准。一个 100 万行的片段
两条都不占优（不小、但删了 30% 的行），如果判定写成
"小 **且** 删过"，它永远不会被处理，删除就会一直悬在删除文件里，
而 `stats()` 报的 `deletion_ratio` 只涨不落。
**把两个不同动机的条件写成一个合取，是这类启发式最经典的一种写错。**

`min_rows_per_fragment` 在本实现里是**无操作**参数：`compact()` 声明了
它，函数体却从未引用，调它不会改变任何行为。真实 Lance 的压实把它当作
"低于这个值就无条件合并"的下限，和 `target_rows_per_fragment` 一起构成
两级阈值；这里只剩了一级。

我们的 `compact()` 返回一个字典，把合并前后的状态都报出来——
真实 LanceDB 的 `optimize()` 返回 `None`（文档里写的 `OptimizeStats`
和实测不符），想知道细节得自己调 `compact_files()`。

实测一次真实压实：5 万行、每次写 500 行，攒出 100 个片段，然后压实。

```
压实前: num_fragments=100  num_small_fragments=100  data_bytes=6,725,894
压实后: num_fragments=1    num_small_fragments=0    data_bytes=6,546,320
rows_rewritten=50000  fragments_merged=100  fragments_created=1
```

**这是同一批数字的汇总视图，不是某个脚本的逐字输出。**
`examples/06_versioning_and_maintenance.py` 打印的格式不一样
（"写入后: 片段 100 个，50,000 行，6,725,894 字节"、
"compact -> 合并 100 个片段成 1 个，重写 50,000 行"），
而且 `Dataset.compact()` 的返回值里**没有** `num_small_fragments`
和 `data_bytes` 这两个键——它们来自 `ds.stats()`。
上面这三行是把两处输出合起来排版的结果。
**六个数字本身我逐一对过，都是真的**（100/100/6,725,894 →
1/0/6,546,320，缩小 2.67%）；只有"它看起来像一段终端输出"这件事是假的。
把小节里的数字和它的**版式**分开看，是这份教程里反复出现的一条纪律——
数字可以逐位复核，而"它长得像某段输出"什么都不能证明。

数据体积小了 2.7%。原因不是"合并本身省空间"，而是**大页让编码器有机会
选到更好的编码**——同样的列，500 行一页和 5 万行一页，
字典表的摊销、位打包的位宽选择、RLE 的游程长度都不一样。
这个收益经常被忽略：压实不只是"合并文件"，它还重新做了一次编码决策。

### 真实的 API 面

迷你实现的 `compact()` 签名上有四个旋钮：`target_rows_per_fragment`、
`materialize_deletions`、`min_rows_per_fragment`，外加一个
`max_fragments`（只压前 N 个，用来把一次大压实切成几步）——但真正
接上线的只有三个，`min_rows_per_fragment` 是个没接线的空旋钮。

真实 LanceDB 的公开 Python 面差不多但更窄：`compact_files(...)` 接受
同名的三个参数，**但它在 0.21.0 就被标成弃用**，官方让你改用
`optimize()`；而 `optimize()` 自己的签名是
`optimize(cleanup_older_than=..., delete_unverified=..., retrain=...)`
——**它不暴露任何压实旋钮**。也就是说在这条路上"调压实策略"基本
等于"调不了"，你只能选"压不压"。Lance（Rust）侧有一个更细的
`CompactOptions`，但 `lancedb` 0.40.0 的 Python 层没有对应的类。

### 压实的成本模型

一次压实 = 把被选中的片段**整读一遍** + **整写一遍**，
所以成本近似是 O(被压实的数据量)，与片段个数关系不大。
在对象存储上这条代价被放大两层：读取要按页发 GET、写入要把每个
新缓冲区 PUT 上去，而每个缓冲区还要满足 64 字节对齐
（`mini_lancedb/encoding/buffer.py`），对齐填充本身也是上传量。

于是压实的优化方向和查询**相反**：查询要"少读字节"，
压实要"少发请求"。把 `target_rows_per_fragment` 设大、一次压完，
比"分很多次小规模压实"在请求数上划算得多——后者每次都要重新读
一遍没变的片段。

### 压实会把整张表慢慢升级到新编码

压实写出来的新片段用的是**当前 SDK 的默认编码**，而不是老片段当年的
编码。反复压实于是会把整张表逐渐"洗"到新写法。这既是好处
（老编码的坑被带过去），也是风险：如果新 SDK 引入了编码 bug，
压实会把它铺满全表——第 28 章 §28.4 那起 "FixedSizeList 内层全 null"
的事故就是这一类。所以跨 SDK 版本升级时，先在小表上压一遍验证，
再对生产表动手。

### Blob 边车要单独看

多模态表里的 blob 按大小分档（第 21 章 §21.4：小走 Inline、
中走 Packed 共享 `.blob` 边车、大走 Dedicated）。压实重写主数据文件时，
那些边车文件**不会自动变小或消失**——它们是被主文件引用的独立文件。
官方文档里没有把"边车文件的压实/回收"写成 `optimize()` 的承诺
（这一点本教程**未找到明确说法，标为未经确认**），所以多模态表上线前
要自己量一次"压实之后边车目录有没有变小"，别默认它会跟着收。

## 23.3 反直觉的实测：压实可能让查询变慢

这是本章最重要的一节，因为它会给"定期压实"这条经验法则加上一个前提。

同样的表，同一个查询 `WHERE n > 49900`，压实前后各跑一次
（脚本 `examples/06_versioning_and_maintenance.py`）。压实前是
100 个小片段：统计剪枝跳掉 99 个，只扫 500 行、读 **5,344 字节**。
压实后只剩 1 个大片段：一个也剪不掉，扫满 50,000 行、读 **142,008 字节**。

**压实之后，同一个查询读了约 27 倍的字节。**

耗时当然也变长了，但这里只把字节数当结论：**它是确定的**，
同一份数据重跑逐位相同；而毫秒数每次都不一样（同一台机器上压实前
1.7 到 3.8 毫秒、压实后 8 到 11 毫秒都出现过）。
凡是拿"快了/慢了几倍"当论据的地方，先分清它是靠哪个量算出来的——
这本书里的判据是附录 E 讲的那条：确定性的量可以当结论，挂钟时间只能当量级。

原因很直接：**细粒度的统计信息本身就是一种索引。** 100 个片段意味着
100 组 min/max 统计，查询能精确地跳过 99 个。合并成 1 个片段之后，
统计只剩一组（min=1, max=49999），`n > 49900` 在这组统计面前
完全无法剪枝，只能读整列。

这个现象推广开就是一条重要的设计原则：
**片段大小的选择是在"元数据开销"和"剪枝粒度"之间的权衡。**

片段太大 → manifest 小、打开快、但剪枝粒度粗、点查要扫很多行；
片段太小 → 剪枝粒度细、点查快、但元数据爆炸、查询要打开很多文件。

真实系统的应对是**两级切分**：片段本身保持在百万行量级
（控制元数据），片段内部再按"行组"切分并保存行组级统计
（提供剪枝粒度）。Lance v2 里"页"就承担了这个角色——
一页 8 MiB，页元数据里带一个 **`priority` 字段**，记的就是
**这一页第一行在片段里的行号**，读取端据此二分定位到页。
这个字段名不直观，但在本教程的实现里也能看到：写入侧
`mini_lancedb/format/lance_file.py` 的 `_emit_page` 里写着
`"priority": root_offset`，`root_offset` 就是"页内首行的顶层行号"。
（诚实补一句：**本实现的读取端并没有真的用它二分**——它用
`_page_row_bounds` 按 `num_values` 累加算出每页的行区间。
`priority` 在这里只是把真实格式的元数据形状补齐。）

所以正确的表述不是"定期压实"，而是：
**压实的目标是让片段大小落在一个区间里，而不是越小越好或越大越好。**
我们的 `compact()` 有 `target_rows_per_fragment` 参数，
`stats()` 里有 `num_small_fragments` 指标，这两个东西配合起来
才能判断"现在该不该压实"。`num_small_fragments` 的口径是
**行数小于 1024 的片段个数**（`MIN_ROWS_PER_FRAGMENT = 1024`，
见 `mini_lancedb/dataset.py`）——它和 `target_rows_per_fragment`
是两个独立的阈值，别混起来用：前者是"多小算小"的下限，
后者是"压完想多大"的目标。

## 23.4 到底什么时候该压实

官方文档给了一个触发启发式：**累计 10 万行变更，或者 20 次修改操作，
以先到者为准。** 官方还把 `optimize()` 明确比作数据库的 `VACUUM`——
也就是说它是个**维护任务**，应该由调度器定期跑，而不是由应用在写入路径上顺手跑。

判断要不要压实的四个具体信号如下。这四个量在生产里**怎么采、怎么设
报警线**，见第 25 章 §25.7.2 的表健康指标；这一节只说它们各自的机制。

**在往下读之前，先分清这里的 `stats()` 是哪一层的 —— 这是个真实的坑。**
本实现有两个同名的方法，返回的东西不一样：

```
Dataset.stats()  -> dict
   num_small_fragments / deletion_ratio / avg_fragment_rows / data_bytes / ...
Table.stats()    -> TableStatistics 对象
   fragments.num_small_fragments（嵌在 fragments 里）
   deleted_rows_ratio（是属性，不叫 deletion_ratio）
   bytes_per_column_sampled（名字里带 sampled）
```

所以下面提到的 `num_small_fragments` 和 `deletion_ratio` **在两个
方法上的写法不一样**：`Dataset.stats()` 里两个都是顶层键；
`Table.stats()` 返回的对象上，`num_small_fragments` 嵌在
`fragments` 子对象里（`s.fragments.num_small_fragments`），
`deletion_ratio` 则改名叫 `deleted_rows_ratio`。
**但它是有一个逃生口的：`Table.stats().to_dict()` 会把
`num_small_fragments` 拍平回顶层**，所以监控脚本走 `to_dict()`
就能拿到和正文一致的名字；直接按属性取则会 `AttributeError`。
两条路都在，选哪条决定了你要不要改名字——**这正是"同名方法不同层"
最容易咬人的地方**。

还有一层更重要的差别：**用户面的统计是抽样的。**
`TableStatistics` 里那个 `bytes_per_column_sampled` 字段名的存在
就说明列字节数是按片段抽样外推的（`collect_table_statistics` 的
`sample_fragments` 默认 8）。所以"表有多大"这类读数在小表上是准的、
在几千个片段的大表上是个**估计值**。而下面这四个信号里，
片段数和删除行数是**数出来的**（准），删除比例的分母是数出来的，
所以**四个信号本身不受抽样影响**——但如果你顺手看了
`bytes_per_column` 去算容量，那个数是推算出来的，别当精确值用。

**片段数的绝对值。** 几千个以上就该处理了，因为"打开表"的成本
随片段数线性增长。

**小片段占比。** `stats()` 里的 `num_small_fragments`（行数小于
1024 的片段个数）除以总片段数。如果超过一半的片段都小于这个下限，
说明写入模式是"小批量频繁追加"，压实收益很大。

**删除比例。** `deletion_ratio` 超过 10% 就值得合并。
一个有 50% 删除的片段，读它一半的 I/O 是白花的。

**索引覆盖度。** 未索引的行数（`num_indexed_rows` 和 `num_rows` 的差）
如果已经不可忽略，说明要么该重建索引、要么该压实。

反过来，**不该压实**的信号也很明确：表已经是一两个大片段、
删除比例很低、查询以全表扫描为主。这时候压实只会让存储暂时翻倍
（因为新旧片段要共存一段时间），换来几乎为零的收益。

## 23.5 清理旧版本：为什么要留窗口

`cleanup_old_versions()` 是 GC。它的核心难点不是"删什么"，而是"什么时候删"。

**可能有读者正在读老版本。** 一个跑了 20 分钟的分析查询可能正握着
v3 的 manifest 在读。这时把 v3 引用的数据文件删掉，
它读到一半就会炸。这不是理论风险——任何"长查询 + 定期维护"
的组合都会撞上。

所以策略是"**保留最近 N 个版本 + 只删早于 X 分钟的版本**"，
两个条件都是为了给在途读者留出安全窗口。窗口长度的选取是
一个纯粹的成本权衡：窗口越长越安全，但空间回收越慢。

还有一个必须注意的保护：**标签引用的版本不能被删。**
我们实测过——打了 `v1.0` 指向 v3 之后，v3 就从可删列表里消失了。
这也是"发布前打标签"这个操作的实际价值：它不只是个名字，
它是一把锁。标签在运维上的用法（发布锚点、GC 护栏，以及"忘删标签
会让空间一直涨"这个反向坑）见第 25 章 §25.6.3。

实测一次完整的清理（脚本 `examples/06_versioning_and_maintenance.py`）：

```
dry:  bytes_reclaimable ≈ 8,763,400
real: removed_versions = [101, 100, ..., 2, 1]   （101 个版本）
      removed_files = 201
      bytes_freed ≈ 8,763,400
      kept_versions = [102]
```

注意这里释放了约 8.8 MB，而表本身只有约 6.7 MB——**因为 100 个版本的
数据文件全都还在。** 每一次"每次写 500 行"都留下一份约 66 KB 的片段
文件，它们全都没被删过。这就是债的规模。（这个数里也含每份 manifest
的字节，而 manifest 带着写入时间戳，所以逐次运行会浮动几百字节；
23.3 节那两个读取字节只算数据文件，不受影响。）

真实 Lance 的 `cleanup_old_versions` **没有 `dry_run` 参数**
（传了会 TypeError）。我们的实现提供它，纯粹是为了教学：
"先看看会删多少"在实践中几乎总是值得的。

### 孤儿文件：删不掉的半提交产物

有一类文件**不被任何存活版本引用**，却也不会被普通的清理删掉：
半提交留下的产物。一次写事务可能在"数据文件已经 PUT 上去、
manifest 还没提交"这中间失败，于是数据文件成了孤儿
（第 25 章 §25.4.1 讲乐观提交时讲过这个中间态）。

**真实 LanceDB** 分不清"孤儿"和"在途事务的一环"，所以默认策略是
**保守**：年龄小于 7 天的这类文件不删。`cleanup_old_versions(delete_unverified=True)`
（或 `optimize(delete_unverified=True)`）的意思是"我保证没有别的进程
在写这张表，可以连未验证的文件一起删"。这是一个**很强的假设**——
在生产里对它唯一的正确态度是"除非我把表停写了，否则别开"
（第 25 章 §25.6.4 展开这个时间窗口为什么存在）。

**本实现把这个参数借去当了别的开关。** 迷你实现的 dataset 层**没有
"未验证文件"这个概念**，清理路径里也**没有 7 天年龄护栏**；
`delete_unverified` 在这里的语义是"真的删还是只报告"，映射为
`真的删 = (not dry_run) or delete_unverified`（`mini_lancedb/optimize.py`
的 docstring 专门标注了这条差异）。所以在本实现里它就是个"就算 dry run
也照删"的开关，既没有真实系统那套保守窗口，也不能理解成同一件事——
上面那两条"真实 LanceDB"的规矩，本实现并不执行。

所以"清理"这件事其实是两条独立的线：**已提交旧版本**的回收（按保留
窗口走，安全）和**未提交孤儿**的回收（`delete_unverified`，危险）。
把它们当成一件事，是"跑完清理发现磁盘没降"或者"跑完清理把表弄坏"的
两种典型来源。

## 23.6 `optimize()`：把维护收成一个动作

`optimize()` 名义上做三件事：压实小文件、把新数据纳入索引、清理旧版本。
官方说它模仿 `VACUUM`，默认保留期 7 天。

**第二件事在真实 LanceDB 和本实现之间差了一个档次。**真实 LanceDB 做的是
**增量索引合并**——把新数据并进已有索引，不需要重建。
本实现没有这个能力，它做的是 `retrain=True` 时的"**整体重建失效索引**"，
代价高一个量级。这不是措辞差别，是能力缺口：
"索引没覆盖新数据"在本实现里只能靠重建解决。

另外注意默认值：`table.optimize()` 三个选项
（`cleanup_older_than` / `delete_unverified` / `retrain`）默认全关，
**默认只做第一件事**。

§23.4 开头那条启发式（"累计 10 万行变更，或者 20 次修改操作，
以先到者为准"）在本实现里落成了 `should_optimize()`：它把两个计数器
分开算——`dirty_rows`（累计被删/被重写的行数）对应读放大，
`operations`（版本数）对应"打开表有多慢"——然后取两者的 `or`。
这也是本教程里 `optimize()` 触发规则的**唯一权威出处**，
第 25 章 §25.1.7 只讲"什么时候在调度器里排它"，规则本身指回这里。

有一个容易被忽略的副作用：**压实会暂时增加磁盘占用。**
新旧片段在提交前后有一段共存期，峰值占用可能接近两倍。
对容量吃紧的系统，这需要在调度上打个提前量。

还有一个现实：**`optimize()` 是这里的重操作，不要在写入路径上调用。**
它要读+重写大量数据，还可能触发索引重建，代价是分钟级的。
正确的用法是"由调度器每小时/每天跑一次"，
并在跑之前检查上文的四个信号。

**这里有个容易踩的坑：本实现有两个同名的 `optimize()`，返回值不一样。**

`table.optimize()`（面向用户的那个，`mini_lancedb/table.py`）返回
**`OptimizeStats` 对象**；`Dataset.optimize()`（更底层那个）返回的是
**字典**。对着 `table` 调却按字典取值的两种写法，报的错还**不一样**：

```
>>> r = table.optimize()          # OptimizeStats
>>> r["compact"]                  # 按键取值
TypeError: 'OptimizeStats' object is not subscriptable
>>> r.compact                     # 按属性取值
AttributeError: 'OptimizeStats' object has no attribute 'compact'
```

`TypeError: not subscriptable` 和 `AttributeError` 是两种不同的错，
指向的也是两种不同的误用（"以为它是 dict" vs "猜错了字段名"）——
**认得出这两句，比记住一个笼统的"会报错"有用**。
顺带一提，`OptimizeStats` 里压实那一段的字段名是 `compaction`
而不是 `compact`，所以 `r.compaction` 才是对的。

**但别把这个 `OptimizeStats` 当成"真实 LanceDB 的行为"**——
附录 A §A.3 和附录 D 第 6 条都记着真实库的 `optimize()` 返回 `None`
（本机 0.40.0 实测：

```
>>> r = t.optimize()
>>> type(r)
<class 'NoneType'>
```

真实库的类型标注写的是 `OptimizeStats`，但实测返回 `None`，
这是那条"文档偏离"的来源）。所以同一个方法名在三处有三种返回值：
真实库 `None`、本实现的 `table` 层 `OptimizeStats`、本实现的
`Dataset` 层字典。**这一节里凡是出现 `optimize()` 的地方，
先看它的主语是谁。**

两个函数的参数和默认值也不同，这是真正会造成误用的地方：

`table.optimize(*, cleanup_older_than=None, delete_unverified=False, retrain=False)`
——三个都是**显式选项**，默认只压实。
`Dataset.optimize(target_rows_per_fragment, cleanup=False, older_than=24*3600)`
——**没有 `retrain` 参数**，而且 `cleanup=False` 时返回的字典里
只有 `compact` 和 `stats` 两个键。

所以"`optimize()` 返回一个带三件事结果的字典"这句话，
只对 `Dataset` 那一层成立：

```python
{
  "compact": {"compacted": True, "before": {...}, "after": {...},
              "rows_rewritten": 50000, "fragments_merged": 100,
              "fragments_created": 1},
  "cleanup": {"cleaned": False, "dry_run": True, "bytes_reclaimable": 8763400},
  "stats":   {...}
}
```

用 `table.optimize()` 时，`【压实】` 那段报告是 `OptimizeStats` 格式化出来的，
形状和上面不同。**写代码前先确认自己调的是哪一层**——
这两个函数同名、同章、返回值不同，是最容易在复制粘贴里出错的一处。

## 23.7 索引与压实的相互作用

这是维护里最麻烦的一块，值得单独讲。

压实改了行号和片段组织，索引就失效了。三条出路：

**重建索引。** 最简单也最贵。一个亿级向量的 IVF_PQ 重建要**几十分钟**
——这个数是**推算，不是本机实测**：本教程在 2 万行 64 维上实测
IVF_PQ 建索引是十几秒量级（第 24 章 §24.3 那张表记的是 16.2 秒，
同一个脚本另一次跑是 9.3 秒——挂钟时间本来就是这个波动范围），
按行数线性外推到 1 亿行是十几个小时；真实实现比纯 Python 快几个数量级，
所以"几十分钟"说的是**真实 Lance 的数量级参考**，不是承诺。

**重映射行号。** 需要"行血脉"：记录"旧片段 X 的第 i 行现在在片段 Y 的第 j 行"。
能链式传递，所以多次压实之后仍能一路映射。真实 Lance 有这套东西
（`RowIdLineage`），但要求表满足若干前置条件——比如必须有主键、
必须显式开启 stable row ids。**不满足条件的表在压实后同样只能重建。**
stable row id 的前置条件（要停写、要删掉全部二级索引、迁移不重试）
和"索引侧还是实验特性"这个现状，见第 29 章 §29.1.4——这一节只说
压实这一侧的后果。

**把索引重排也纳入压实。** 真实 Lance 的压实有一个
`defer_index_remap` 选项：把"索引重排"延迟到后台任务里做，
这样压实本身可以快速返回。代价是中间态下索引不可用。

我们的实现选了第一条路：压实之后把索引标记为失效。

```python
clone.valid = False
clone.details["invalidated_by_compaction"] = True
```

这是诚实但保守的选择。它的直接后果是：**在这个实现里，
压实和向量索引不能"都要"**——要么定期重建索引，要么接受压实后索引失效。
真实现代的系统必须把这件事做对，因为"索引重建"的代价
在生产环境里是不可忽略的。

**把重建自动化。** 既然"压实 → 索引失效 → 重建"是一条固定链条，
就别指望人记得在压实之后手动重建。本实现在 `optimize(retrain=True)`
里内置了这一步：它只重建被标记为失效（`valid=False`）的索引，
并复用索引元数据里存着的原始参数（索引类型、度量、量化参数），
所以重建出来的是同一套配置，不是"随手拿默认值新建一个"。

真实 LanceDB 这条路要自己走：OSS 的 `optimize()` **不重建索引**，
它的 `retrain` 参数已经弃用且不再起作用（附录 A 的弃用清单里有它），
"自动增量重建索引"是企业版能力。所以 OSS 上的自动化是：把
`optimize()` 和一次显式的 `create_index(..., replace=True)` 排进同一个
定时任务，**并在两者之间不放写操作**——写会让刚建好的索引立刻又落后。

## 23.8 维护清单

把它落成一张可以贴在墙上的清单：

**每次写入之后**：什么都不用做。Lance 的写入路径不含任何维护。

**每小时/每天**：检查四个信号（片段数、小片段占比、删除比例、索引覆盖度）。
任一超标就跑 `optimize()`。

**每次发布前**：给版本打标签。标签会保护它不被 GC 删掉。

**每周**：跑 `cleanup_old_versions`，保留最近若干版本 + 一个时间窗口。
先 dry run 看数字再决定。

**压实之后**：确认索引状态。如果索引失效了，安排重建。

**任何时候**：不要在多进程里同时压实同一个表。压实之间的冲突
不应该靠重试解决，而应该靠"只让一个进程做维护"。
（为什么压实属于"会互相冲突"的那一类操作、以及为什么清理和压实
必须由单一所有者来做，第 25 章 §25.4.2 的冲突矩阵讲清楚了。）

## 23.9 小结

**四种债**：小片段、幽灵行、失效索引、版本膨胀。它们都是"不可变"
这个选择的利息。

**压实不是"合并文件"，它还重新做了一次编码决策**，所以数据通常会小一点。

**压实可能让查询变慢。** 实测 `WHERE n > 49900` 在压实后多读了约 27 倍的字节
（5,344 对 142,008）——因为 100 组 min/max 统计被合并成了一组。
片段大小是在元数据开销和剪枝粒度之间的权衡，不是越小越好。

**清理必须留窗口**，因为可能有读者正握着老 manifest。

**清理其实是两条线。** 已提交旧版本的回收按保留窗口走（安全）；
未提交孤儿文件的回收要 `delete_unverified=True`（危险，它等于承诺
"没有别的进程在写这张表"）。把两者当成一件事，是"清理完磁盘没降"
或"清理完把表弄坏"的两种典型来源。

**压实的成本是 O(被压实的数据量)**，与片段个数关系不大；
在对象存储上要优化的是**请求数**，所以"少次、大规模"压实
比"多次、小规模"划算。

**标签是保护，不只是命名。** 被标签引用的版本不会被 GC 删掉。

**压实会让索引失效**，三条出路里"重建"最贵、"行血脉重映射"最强，
而后者有前置条件。
