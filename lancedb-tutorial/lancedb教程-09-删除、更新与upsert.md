# 第 9 章　删除、更新与 upsert

前八章一直在说一件事：**数据文件写完就不再改。** 这一章要面对它的直接后果。

一个用户删了三行，他期待什么？磁盘上少三个记录、索引少三个条目、
下次查询少扫三行。而 Lance 给他的实际是：**一个几十字节的删除文件，
外加 manifest 里一个指针。**

这个落差不是省事，是设计。它买到的东西很具体——删除从
"重写整个片段"变成"写一个集合"，代价与删除量成正比而不是与表大小成正比。
但它也带来了三个必须讲清楚的后果：行号分裂成两套、读取多一层过滤、
空间不释放。这一章把这三件事都量化。

## 9.1 删除是一次纯元数据操作

先看实测。对一个有 `n` 行的片段，分别删 3 行和删掉一半，
写下去的删除文件各是多大：

```
n=        3  删3行:        33 B   删一半:        34 B   bitmap 固定:         1 B
n=    1,000  删3行:        37 B   删一半:       532 B   bitmap 固定:       125 B
n=  100,000  删3行:        39 B   删一半:    50,032 B   bitmap 固定:    12,500 B
n=3,000,000  删3行:        41 B   删一半: 1,500,032 B   bitmap 固定:   375,000 B
```

第一列是"删 3 行"的大小。**300 万行的片段删 3 行只花 41 字节**——
比 1000 行的片段删 3 行（37 字节）只多了 4 个字节。
第二列是同一个片段"删掉一半"的大小，1.5 MB。
同一个 300 万行的片段，两种删法的删除文件差 **3.6 万倍**。

这 3.6 万倍的差距说明删除文件不是"一个掩码"，而是"一串行号"。
文件大小正比于**你删了多少行**，而不是表有多大。

删除本身只做两件事：

1. 写一个删除文件，里面记下"片段 X 里这些物理行没了"；
2. 提交一个新 manifest，把该片段的 `deletion_file` 指向它。

数据文件一个字节都没动。这就是为什么"在一张 300 万行的表上删 3 行"
和"在一张 3 行的表上删 3 行"的**提交**代价几乎一样——
两者都只是"写一个小文件 + 条件写一份 manifest"，
和表有多大、删掉的占多少比例都无关。

## 9.2 删除文件里到底是什么

真实的 Lance 有两种编码，用扩展名区分（`_deletions/{fragment_id}-{read_version}-{id}.{extension}`）：

`.arrow` 是 Arrow IPC，内容是一个单独的 `Int32Array`，装排好序的行号。
名字里的 `ARROW_ARRAY = 0` 是它的类型标记。**稀疏删除**用它。

`.bin` 是 Roaring bitmap。`BITMAP = 1`。**密集删除**用它。

一个片段在一个版本里**至多有一个删除文件**。文件名里为什么非要带
`fragment_id` 和 `read_version`，值得说清楚，因为很容易想歪。

它解决的是**"怎么算出路径"**，不是"怎么判断死活"。manifest 里记的
`DeletionFile` 结构本身就是 `(fragment_id, read_version, id, file_type)`，
所以只要手上有 manifest，就能把完整路径**拼**出来——不需要去
`_deletions/` 目录下列一遍文件、也不需要解析文件名来反推它属于谁。
前者是一次 O(1) 的字符串拼接，后者是"先 list 再逐个 parse"，
在对象存储上这两者的代价差一整个数量级。

**但"哪些删除文件还活着"这件事，仍然只能从 manifest 里得到。**
本实现的 `cleanup_old_versions` 就是老老实实把每个保留下来的 manifest
读一遍、收集 `f.deletion_file.path`（见第 7 章 §7.7 那段
`live_files` 的构造）——从来没有、也不可能从文件名反推存活关系。
一个文件叫 `5325787448008566032-2-621f1f35e99b48ae.bin`，
它自己完全不知道自己有没有被引用；文件名里的两个数字只是"我是谁"，
不是"我还算不算数"。

（以上是 Lance 格式规范里的定义（`protos/fragment_metadata.proto`）。
**这段规范原文没有拿真实 LanceDB 的落盘文件逐字节对过**——本机虽然装了
`lancedb 0.40.0`，但这一节引的是规范里的字段定义，没有反向核对它写出来的
`_deletions/` 文件；下面提到的字节数、头部结构、行号对照则全部来自本实现的实测。）

我们的迷你实现用一种自描述的紧凑二进制：排序行号做**差分**再上 **varint**。
头部是 32 字节的定长结构：

```
struct<magic:4s, version:u32, fragment_id:u64, num_rows:u64, num_deleted:u64>
magic = b'LDEL'
```

实测一个头部，`serialize_deletions(7, 1000, [1, 500, 998])[:32]`：

```
4c44454c 01000000 0700000000000000 e803000000000000 0300000000000000
```

`4c44454c` 就是 `LDEL`，接着是版本 1、片段号 7、总行数 1000、删除行数 3。
头部之后是 varint 编码的差分序列：`1, 499, 498`（原始行号是 1、500、998）。
解回来是 `[1, 500, 998]`，逐位正确。

为什么是差分 + varint 而不是 bitmap，这张表已经回答了，但值得把推理写全：

**删除通常是零星的。** 用户删掉某几条记录、清理几个违规项、
删掉昨天的测试数据。这类操作的共同点是"行号稀疏"——300 万行里删 3 行，
差分的三个数都很小（第一个是行号本身，后面两个是间隔），
每个只要 1~2 字节，总共 41 字节。

**bitmap 是定长的。** 无论删 3 行还是删一半，都是 `num_rows/8` 字节。
300 万行的片段是 375 KB。删 3 行用 375 KB 存 3 个数，
这是把"最坏情况"当成了"基本情况"。

**但反过来，删一半的时候 bitmap 赢。** 1.5 MB 对 375 KB，
bitmap 小 4 倍；而且 bitmap 是定长数组，可以直接随机访问第 i 位，
不需要 O(n) 地把 varint 全部解出来。真实 Lance 让两种编码并存、
按删除密度选，正是因为这个交叉点是真实的。

这个取舍在其他地方也会反复出现：**编码的选择取决于数据的分布，
而不是数据的量级。** 一个"永远按最坏情况设计"的格式在真实负载上会浪费一个数量级。

## 9.3 物理行号与逻辑行号

这是这一章的核心难点，也是所有"删完之后查不对"的问题的根源。

**物理行号**（偏移）是行在数据文件里的位置。它由写入时决定，
**删除不会改变它**。片段写了 10 行，删掉第 1、3、5 行之后，
第 6 行在文件里仍然是第 6 行。

**逻辑行号**是用户看到的序号。删掉的行不占号。所以删完之后，
原来的第 6 行现在叫第 3 行。

删除文件里记的是**物理偏移**（它必须如此——如果记逻辑行号，
下一次删除就没法解释同一个文件了），而用户和 API 说的是**逻辑行号**。
两者之间隔着一张映射表。

我们的实现真的建了这张表（`Dataset._row_map()`），返回两个数组：
逻辑行号 → (片段下标, 物理偏移)。实测：

```
片段 id = 7395367629158612680
  逻辑 0 -> 物理 0 -> 地址 0x66a19fad276bfec800000000
  逻辑 1 -> 物理 1 -> 地址 0x66a19fad276bfec800000001
  ...
  逻辑 9 -> 物理 9 -> 地址 0x66a19fad276bfec800000009

删掉 n IN (1, 3, 5) 之后：
  逻辑行数 = 7  物理行数 = 10  已删 = 3
  逻辑 0 -> 物理 0 -> 地址 0x66a19fad276bfec800000000
  逻辑 1 -> 物理 2 -> 地址 0x66a19fad276bfec800000002
  逻辑 2 -> 物理 4 -> 地址 0x66a19fad276bfec800000004
  逻辑 3 -> 物理 6 -> 地址 0x66a19fad276bfec800000006
  逻辑 4 -> 物理 7 -> 地址 0x66a19fad276bfec800000007
  逻辑 5 -> 物理 8 -> 地址 0x66a19fad276bfec800000008
  逻辑 6 -> 物理 9 -> 地址 0x66a19fad276bfec800000009
```

物理偏移 1、3、5 消失了（被删了），但 6 还是 6，没有变成 3。
删除文件里的 `num_rows` 记的是**物理**行数 10，不是逻辑行数 7——
因为文件本身确实还有 10 行，删除文件描述的是"文件"，不是"表"。

**地址那一列是这一节真正要讲的东西。** 它把
`(fragment_id << 32) | offset` 这样一个 64 位整数打印成十六进制。
看最后两行：地址的低 32 位就是偏移（`...00000004` 对应偏移 4），
高 32 位是片段 id。这个编码是真实 Lance 的做法，它的价值是
**"行地址 → 位置"变成纯算术**：

```python
fragment_id = address >> 32
offset      = address & 0xFFFFFFFF
```

不需要查表，不需要读任何元数据。所以真实 Lance **根本不建行映射表**——
而我们建了，代价是 O(行数) 的内存。我们的 `_row_map()` 注释里
自己点明了这一点：教程里这样写可读，生产里不可接受。

地址之上还有一层 **stable row id**：默认情况下 `_rowid` 就等于行地址
（所以压实之后它会变），显式开启 stable row ids 之后 `_rowid` 才是独立分配、
跨压实稳定的标识。这一层属于版本与压实的题目——定义和前置条件在第 7 章 §7.8，
它和压实的相互作用在第 23 章 §23.7——这里只留下一个和删除有关的衔接点：
**删除文件记的是行地址，不是 `_rowid`**，所以行地址变、`_rowid` 可以不变，
两者要分开记。

**一句话记住这个区分：删除文件说物理偏移，用户说逻辑行号，
行地址是两者之间的换算工具。**

## 9.4 软删除的代价

删除不改数据，代价就转移到读取侧。实测一张 20,000 行的表，
删掉不同比例之后读同一列：

```
无删除      逻辑行=20,000 物理行=20,000 删除比=0.000 读字节=  44,504
删 50%      逻辑行=10,000 物理行=20,000 删除比=0.500 读字节=  37,128
删 99%      逻辑行=   200 物理行=20,000 删除比=0.990 读字节=  29,520
```

**删掉 99% 的行，读取量只降了 34%。** 这很反直觉：剩下的数据只有 1%，
凭什么是 66% 的读取？

答案是第 10 章会细讲的"行范围下推"失效了。当存活的行在片段里
**偏移连续**时，读取可以直接让 reader 跳到那一段；一旦删除把偏移打碎
（这里存活的是 0、100、200、…，步长 100），就退化成"整个片段读进来再 take"。
**删除破坏的是偏移的连续性，而这个连续性正是行范围下推的前提。**
所以删除比例越高、删得越零散，读放大的倍数就越大。

第二笔代价是**幽灵行**：如果索引不跟着删除走，被删掉的行就还留在索引里。
向量索引的候选集是从分区里 gather 出来的，而删除掩码是在 gather **之后**才应用的
——那样的话被删的行仍然占掉 `nprobes` 给出的候选名额。这个现象在早期版本里
能直接量出来：500 行、`num_partitions=8` 的 IVF_FLAT 索引，删到只剩 100 行时，
`nprobes=4` 会 gather 出约 250 行、其中只有约 50 行是活的，
**80% 的距离计算花在幽灵上**。

现在不会了：删除会把索引里的行号一起搬（`_remap_indices_after_delete`），
被删的行直接从索引里消失。同一条实测现在长这样——索引覆盖的行数变成 100
（不再是 500），`nprobes=4` 的候选池是 53 行，**每一行都是活的**：

```
删到只剩 100 行之后，num_indexed_rows = 100
nprobes=1: 候选池 16 行
nprobes=2: 候选池 33 行
nprobes=4: 候选池 53 行
nprobes=8: 候选池 100 行（= 全部存活行）
```

代价并没有消失，只是**挪到了写入侧**：搬行号的索引要重写一遍再落盘，
搬不动的直接失效。所以 9.1 节那句"删除是纯元数据操作"有边界——
**它说的是数据文件，不包括索引。**

真实 Lance 走的是另一条路：**索引保持不可变**，用删除文件里的行地址过滤索引结果，
二级索引再用 fragment bitmap 追踪覆盖率（第 7 章 §7.8 讲过索引条目的陈旧问题）。
两条路各有代价：重映射要写索引、还会让索引文件和存储版本脱钩；
位图过滤则要每次查一遍删除文件。**先过滤还是先搜**这个问题本身
在第 18 章 §18.8 展开——那里的 prefilter / postfilter 讨论的正是
"谓词作用在候选集的哪一步"。

### 这里有个实测撞到过的真 bug

迷你实现在这条路上曾经少做一步，而少做的后果是**崩**，不是慢。
当时的复现（500 行表，建 IVF_FLAT 索引，然后删掉前 400 行）：

```
建索引后检索: [0, 426, 213]
删掉前 400 行后，存活 100 行
纯向量检索 -> IndexError 行号越界: 196（共 100 行）
带 where（默认 prefilter）-> QueryError 掩码长度与索引行数不一致 (mask_len=100, rows=500)
索引记录的索引行数: 500  当前存活: 100
（delete 之后索引没有被标记失效；只有 compact 会）
```

两个报错是同一个原因：**索引里存的是"建索引那一刻的逻辑行号"**。
删掉 400 行之后，索引里的 196 号在当前的逻辑行空间里已经不存在了
（只剩 100 行），于是 `take_rows` 越界；带 `where` 时更早一步崩在长度校验上——
谓词掩码是按当前 100 行算的，索引却还报 500 行。

修法在 `_delete_append` 里：删完行之后调 `_remap_indices_after_delete`，
把索引里的行号从旧编号搬到新编号，搬不动的就标记失效。现在同一条路径跑出来是
`索引记录的索引行数: 100 当前存活: 100`，带 `where` 和不带 `where` 两种写法都正常。
回归测试是 `tests/test_regressions.py` 里的
`test_vector_search_still_works_after_delete_with_index` 和
`test_index_row_ids_are_remapped_not_stale`。

**但"搬行号"只对一部分索引成立。** 向量索引的行号就是一个下标，
搬一下就对；标量索引存的是**键**、倒排索引存的是**文档号**，行号散在索引结构里，
搬不动。所以 `_remap_indices_after_delete` 的另一半语义是"搬不动就置失效"——
谁落进哪一档，9.10 节逐个说。

**设计课：** 一个"行号"在系统的不同层里含义不同。
写入用的是物理偏移，用户看到的是逻辑行号，索引存的是
"建立时刻的逻辑行号"——第三种的失效条件最隐蔽，
因为它只在"删除发生过"时才不成立，而测试里
"建索引 → 查询"这个最常见的顺序恰好绕开了它。

## 9.5 update 是删除加追加

有了删除，更新就顺理成章了：**改一行 = 删掉旧行 + 追加新行。**

为什么不就地改？因为数据文件不可变。就地改一个字节意味着重写整个
片段文件——为了改一行而重写几百万行，这个代价与改动量完全不成比例。
删加追加的代价与**被改的行数**成正比，而且天然保留了历史版本。

副作用是行序会变。实测 6 行表更新 id=2：

```
更新前: [{'id': 0, 'tag': 'a'}, {'id': 1, 'tag': 'b'}, {'id': 2, 'tag': 'c'},
         {'id': 3, 'tag': 'd'}, {'id': 4, 'tag': 'e'}, {'id': 5, 'tag': 'f'}]
更新后: [{'id': 0, 'tag': 'a'}, {'id': 1, 'tag': 'b'}, {'id': 3, 'tag': 'd'},
         {'id': 4, 'tag': 'e'}, {'id': 5, 'tag': 'f'}, {'id': 2, 'tag': 'Z'}]
```

id=2 那一行跑到了表末尾，id=3、4、5 全部前移一位。

**这个副作用会静默地吃掉分页的行。** 真实场景是这样的：
客户端读第一页，服务端在两次翻页之间更新了一行，客户端再读第二页：

```
第 1 页 (offset 0): [0, 1, 2]
更新 id=1 之后全表: [0, 2, 3, 4, 5, 6, 7, 8, 9, 1]
第 2 页 (offset 3): [4, 5, 6]
两页拼起来: [0, 1, 2, 4, 5, 6]   <- id=3 被跳过了
```

没有报错、没有警告，就是少了一行。官方文档专门警告过这个
"reorder" 行为（`update` 和 `merge_insert` 都会打乱行序）。

**正确的分页姿势是按稳定键排序加游标**（`WHERE key > 上一页最后一个 key ORDER BY key LIMIT n`），
而不是 `offset`。前者在任何行序变化下都是对的，后者只在
"数据在两次翻页之间完全不变"时才对——而一张会被更新的表，
这个前提随时会破。

## 9.6 `values_sql`：引用现有列

`update` 的 `values` 参数给的是常量，但真实需求经常是"基于旧值算新值"：
给每个 ID 加偏移、把价格翻倍、把计数器加一。这时用 `values_sql`：

```python
table.update(where="id >= 3", values_sql={"id": "id + 100", "n": "n * 2"})
```

实测：

```
前: [{'id': 0, 'n': 0}, {'id': 1, 'n': 10}, {'id': 2, 'n': 20}, {'id': 3, 'n': 30}, {'id': 4, 'n': 40}]
后: [{'id': 0, 'n': 0}, {'id': 1, 'n': 10}, {'id': 2, 'n': 20}, {'id': 103, 'n': 60}, {'id': 104, 'n': 80}]
```

实现上，这些表达式走的是**和 `WHERE` 完全相同的表达式引擎**
（第 11 章）：先把匹配的行取出来成一批，再用 `parse` + `evaluate`
整列求值，最后把结果当作新行追加。所以 `id + 100` 在这里和它在
`WHERE id + 100 < 500` 里用的是同一套类型推导、同一套三值逻辑。
这是"一个引擎两处复用"的直接好处——`values_sql` 不需要第二套
求值语义，也就不会出现"更新时的除法规则和过滤时的除法规则不一样"
这类问题。

注意 `n * 2` 里的 `n` 是**旧值**：求值发生在 `take_rows` 出来的那批旧行上。
但如果同时更新 `id` 和依赖 `id` 的列，结果用的是旧 `id`——
所有表达式都在同一批旧数据上求值，不存在"后面的表达式看到前面改过的值"。
这和 SQL 的 `UPDATE ... SET a = b, b = a` 语义一致（同时求值）。

## 9.7 `merge_insert`：upsert 的语义，以及它的四个缺口

`update` 只能改已存在的行。upsert 需要"在就更新、不在就插入"，
这是 `merge_insert` 的活。它的形状是一个构建器：

```python
(table.merge_insert("id")                     # on=join 键，可以是多个列
      .when_matched_update_all()              # 匹配上的行：用源数据整行覆盖
      .when_not_matched_insert_all()          # 没匹配上的行：整行插入
      .execute(new_rows))
```

四个动作的语义，逐条说清。**先说一条贯穿全节的差异**：
真实 LanceDB 的 `where` 谓词用 `target.` / `source.` 前缀区分两侧的列
（例如 `where="target.color = 'red'"`），**本实现不认这两个前缀**——
它用的是裸列名（指目标表的列）。抄真实库的谓词过来要先去掉前缀：

```
when_matched_delete(where="target.color = 'z'")
# PlanError: 没有名为 'target' 的列 (available=['id', 'c'])
```

`when_matched_update_all(where=...)` 对每个"源里和目标里都有这个 key"的行，
用源行覆盖目标行。实现上就是"删掉目标旧行 + 追加源行"。
可选的 `where` 只更新满足条件的那些。

**这里有一个本实现的静默缺陷：`when_matched_update_all` 的 `where` 参数会被丢掉。**
`MergeInsertBuilder.when_matched_update_all` 接受并保存了它，
但执行路径从不读——所以传了 `where` 和不传是**完全一样的效果**，
既不报错也不警告。真正用了 `where` 的只有 `when_matched_delete`
和 `when_not_matched_by_source_delete` 两个动作。
要在本实现里表达"按条件更新"，得绕道 `update(where=...)`。

`when_not_matched_insert_all()` 对源里独有、目标里没有的 key 直接插入。

`when_matched_delete(where=...)` 只删不更新。实测：

```
初始: [{'id': 0, 'color': 'blue'}, {'id': 1, 'color': 'red'}, ...]
when_matched_delete(color='blue'): MergeResult(version=3, updated=0, inserted=0, deleted=3)
结果: [{'id': 1, 'color': 'red'}, {'id': 3, 'color': 'red'}, {'id': 5, 'color': 'red'}]
```

注意这里 `deleted=3` 且 `inserted=0`。**`inserted=0` 的原因不是"源行没插进去"，
而是这条 builder 链上根本没有声明任何插入动作**——只有 `when_matched_delete`。
源行的作用仅仅是确定"哪些 key 匹配上了"。

`when_not_matched_by_source_delete(where=...)` 是反方向：
删掉**目标表里源数据没有的**行。真实 LanceDB 里它是
"用源快照替换目标某个子集"的做法
（官方文档给的例子是"替换 `month='january'` 这一段数据"）。

**这个动作在本实现里是空操作。**实测两条：

```
# 单独调用
PlanError: merge_insert 至少需要指定一个动作

# 和 when_matched_update_all 连用
初始: [{'id': 0, 'c': 'x'}, {'id': 1, 'c': 'x'}]
源:   [{'id': 0, 'c': 'z'}]
-> MergeResult(version=3, updated=1, inserted=0, deleted=0)
结果: [{'id': 1, 'c': 'x'}, {'id': 0, 'c': 'z'}]     # id=1 该删的，还在
```

`when_not_matched_by_source_delete()` 只是把 `delete_not_matched_by_source`
这个标志位置上了，`_execute_merge` 从不读它。所以：

- **单独调用会报错**（因为"一个动作都没指定"这条检查看的是另一组标志位，
  它不认这个动作）；
- **和其他动作连用则静默无效**——`deleted=0`，目标表里那些
  "源里没有的 key"原样留着。

第二种情况是危险的那种：返回值看不出异常，表的内容也是"合法的"，
只是少了你以为删掉的那些行。要在本实现里做这件事，
只能自己先算出"源里没有的 key"，再用 `delete(where=...)` 删。

**只写 `when_not_matched_insert_all()` 就是 insert-if-not-exists。** 实测：

```
初始: [{'id': 0}, {'id': 1}, {'id': 2}]
源:   [{'id': 1}, {'id': 2}, {'id': 7}]
结果: [{'id': 0}, {'id': 1}, {'id': 2}, {'id': 7}]   MergeResult(inserted=1)
```

### 重复键怎么办

两个方向的重复，行为不一样，都要知道。先把前提说清楚：**这里的"主键"是一个 join 键，
不是唯一性约束**——普通 `add` 不强制去重，往表里塞两行同 id 的行完全合法
（实测 `[{'id': 1, 'v': 1.0}, {'id': 1, 'v': 2.0}]` 两行都在）。
这句断言和下面两条的行为都写进了 `tests/test_table_api.py` 的用例里。
**真实 LanceDB 也是"非唯一约束"**——本机 0.40.0 实测，往表里塞两行同 id 的行
两行都在。（这条原来写的是"本机没能复跑，因为 `merge_insert` 走 `pylance`
那一层而本机没装"。**那个前提是错的**：本机确实没装 `pylance`
（`import lance` 直接 `ModuleNotFoundError`，`cleanup_old_versions`
也确实因此报 `ImportError`），但 `merge_insert` **不经过 pylance**，
它在 0.40.0 上直接就能跑。把"某一个方法需要 pylance"推广成
"整条路径需要 pylance"，是这一章最容易犯的过度概括。）

**目标表里有重复 key** 时，实现里建的是 `key → 逻辑行号` 的字典，
后面的覆盖前面的，所以**取最后一行**：

```
初始: [{'id': 1, 'v': 1.0}, {'id': 1, 'v': 2.0}]
源 [{'id': 1, 'v': 9.0}] -> MergeResult(version=3, updated=1, inserted=0, deleted=0)
结果: [{'id': 1, 'v': 1.0}, {'id': 1, 'v': 9.0}]
```

第一行原地不动，第二行被改成了 9。所以结果是两行，而不是一行。

**源数据里有重复 key** 时，本实现同样**保留最后一条**：

```
源: [{'id': 1, 'v': 10.0}, {'id': 1, 'v': 20.0}]   （目标表里已有一个 id=1）
结果: [{'id': 2, 'v': 2.0}, {'id': 1, 'v': 20.0}]   MergeResult(updated=1, inserted=0)
```

`_execute_merge` 在入口就把源按 key 去重、只保留最后出现的下标。这一步不只是"防止意外"，
它挡掉一个具体的 bug：不去重时，同一个 key 的两条源行会各自生成一条待追加记录，
**目标表凭空多出一行**——跑完不报错、不警告，几天后对账才发现。回归测试是
`test_merge_insert_duplicate_source_keys_last_wins`。

真实 LanceDB 在这个位置留了旋钮：把"源里出现重复 key 怎么办"做成参数
（`MergeInsertParams.source_dedupe_behavior`），而不是写死一种策略。
本实现写死为保留最后一条；真实侧那个参数的默认值本章没有在本机复跑，
不对它下结论——把本实现当教学参照时，记住的是"**这件事有策略可选**"。

### 一条（据说）真实的硬限制

真实 LanceDB 在 `merge_insert` 上有条硬性上限：**未索引的行数不能超过 10000**，
超过会返回 HTTP 400：

```
Bad request: Merge insert cannot be performed because the number of unindexed rows exceeds the maximum of 10000
```

**这个数字、这段报错，以及下面那句机理，整段都是引用**：来自官方文档和一份报错文本。
本机装了 `lancedb 0.40.0`、没装 `pylance`，但**这一次不是 pylance 挡住的**——
`merge_insert` 在本机能跑（见下），**它只是没有报出这个错**，
所以这条限制**未经复跑确认**。第 25 章 §25.2 记了这次尝试的完整经过：
15000 行的表、join 列无索引，跑 `merge_insert` 是**成功**的。机理本身说得通——merge 要对 join 键
做一次 join，要么扫全表、要么查标量索引；索引只覆盖到某个版本为止，
之后的增量行没被索引，"未索引行数"就是这部分的规模。所以文档的建议是
**在 join 列上建标量索引，并在 merge 之前把它更新到最新**。
当"待验证的背景知识"读，别当"这条限制一定卡在这个数字上"。

**让那条建议真正生效的开关叫 `use_index`。**
真实 LanceDB 的 `merge_insert(...).use_index(True)` 是显式告诉引擎
"去用 join 列上的索引"，默认不开。所以"建了索引就用得上"是不成立的——
索引建了但没打开这个开关，join 仍然是全量扫键列。
本实现没有这个参数（join 永远是全量读键列），
所以这一条属于"真实库有、本实现没有"的差异清单。

有一条可以本地验证、也不依赖上面那条限制的：**为什么 `merge_insert` 比 `add` 慢那么多。**
`add` 只是追加片段；merge 必须先**把 join 键列整列读出来**
（`mini_lancedb/dataset.py` 的 `_execute_merge` 里那行注释写着
"这是本实现里最贵的一次读"——注意它在**调用方**，不在
`_read_key_columns` 自己的 docstring 里，后者的 docstring 只有一句
"只把 join 键列读出来"），
再决定删什么插什么，最后在一个事务里删除并重新插入行。所以 merge 的代价随
**表的规模**长，`add` 只随**新数据**长——这是量出来的区别，和上面那条 10000 无关。

## 9.8 原子性：一次提交

`delete`、`update`、`merge_insert` 走的是**同一条提交路径**，
实现里叫 `_delete_append`。它做的是"删一批行 + 追加一批行，
在一次事务里完成"。

为什么要合并成一次？考虑 upsert 分成两次提交会怎样：

1. 先提交"删掉旧的 id=7" → 成功，v11；
2. 再提交"插入新的 id=7" → 失败了（对象存储抖动、进程被杀、冲突）。

结果是**表里没有 id=7 了**。用户以为 upsert 成功了或者失败了，
实际上数据处于"删掉了但没补上"的中间态——在 upsert 场景下
这等价于**丢数据**。

合并成一次之后，两类产物（若干删除文件、若干新片段）都是**先写、
不提交**的不可变文件，最后一次条件写 manifest 把它们**一起点亮**。
要么全生效、要么全不生效。实测一次 merge 的版本号变化：

```
提交前 v2 -> 提交后 v3（一次 merge 只 +1，num_attempts=1）
```

`num_attempts` 是真实 LanceDB 也有的字段：`MergeResult` 一共六个计数
（`version`、`num_updated_rows`、`num_inserted_rows`、`num_deleted_rows`、
`num_attempts`、`num_rows`），语义是"这次 merge 试了几轮"——
真实库里它大于 1 就说明发生过并发冲突并重试过。

**但在本实现里，这个字段恒等于 1，别拿它做信号。**
`Dataset._execute_merge` 是直接 `num_attempts=1` 写死在返回值里的
（`mini_lancedb/dataset.py`），而它的下层 `_delete_append` 根本不重试——
冲突直接抛出去。所以在这个实现上，"`num_attempts > 1` 表示重试过"
这条读法**永远不会触发**，它不是一个沉默的 0，而是一个沉默的 1，
比恒为 0 更容易骗人。真要看重试行为，得去看第 8 章讲的
`Dataset.write(max_retries=N)` 那条写路径，merge 这条没有。

注意第 8 章讲过的边界在这里仍然成立：**merge 是"先读后写"的典型**。
它先读 join 键，再决定删什么插什么。两个进程同时对同一个 key
做 upsert，其中一个的重试会让它重新读到对方写进去的行。
如果业务要求"先写的赢"，那要靠外部序列号或版本判断，
不能指望数据库给你定序。

## 9.9 删完之后该做什么

对着实测数字，把维护建议讲清楚。

**先看三个信号**（都在 `stats()` 里）：

`deletion_ratio`（我们加的一个指标，真实 LanceDB 的 `TableStatistics` 里没有）
是删除行占**物理**行数的比例。它直接就是读放大倍数：0.5 意味着扫一遍表
要读两倍的行才能凑出实际数据量。实现里 `estimate_deletion_cost` 给的经验阈值是
**超过 10% 就该合并**——因为一个有 50% 删除的片段，
读它一半的 I/O 是白花的。

`num_fragments` 和 `num_small_fragments`：删除本身不会增加片段数，
但 `update` / `merge_insert` 每次都会追加新片段。一个高频 upsert 的表
会在几小时内攒出几百个小片段。

`indices` 里的 `valid`：**这个字段现在真的会告诉你东西。** 删除发生时，
实现会尝试把每个索引里的行号搬到新编号：搬得动的（各种向量索引）保持
`valid=True`，搬不动的（标量索引、倒排索引）被置成 `valid=False` 并带上
`details.invalidated_by_delete=True`。所以"这张表删过行"不再是
"`valid` 不可信"的同义词了；谁落进哪一档、后果是什么，9.10 节逐个说。

**然后跑压实。** 实测一次删除比例 0.5 的压实：

```
删除后: 片段=2 逻辑行=5000 物理行=10000 字节=22,625 删除比=0.500
压实是否发生      是
片段 移除 / 新增  2 / 1
字节 移除 / 新增  22625 / 14322
净字节变化       -8303
重写行数        5000
删除行数 前 / 后  5000 / 0
压实后: 片段=1 逻辑行=5000 物理行=5000 字节=14,322 删除比=0.000
```

逻辑行数一行没变（5000），但物理行数从 10000 掉到 5000，
文件从 22,625 字节变成 14,322 字节。**删除在这里第一次真正落地。**
（多出来的那次压缩不全是"丢掉半张表"的功劳，也有一部分是
大页让编码器选到了更好的编码，见第 23 章。）

**压实只回收段落里的空白，不回收历史版本。** 删除文件和旧 manifest 属于"旧版本"，
它们的回收是另一件事（第 23 章 §23.5）：`cleanup_old_versions(older_than=..., keep_versions=...)`
按"保留最近 N 个版本 + 只删早于 X 秒的版本"来清，因为危险的敌人是还在跑的读者——
把 v3 的文件删掉，一个正在读 v3 的长事务就会读到半个表。这是删除的第二笔空间账：
删除本身只写几十字节，但它制造的旧版本要等 GC 窗口过去才真正释放。
（顺带一句：因为版本还在，`checkout` 回滚一次删除是零成本的——见第 7 章 §7.4。）

**最后是索引。** 压实会改行号，本实现把索引一律标记失效：

```
压实后索引 valid = False   details.invalidated_by_compaction = True
```

于是顺序必须是"压实 → 重建索引"，不能反过来。
这也是为什么 `optimize()` 要由调度器定期跑，而不是在写入路径上顺手做——
一个亿级向量的索引重建是分钟级的。

**一条不该做的事：不要用 `offset` 分页。** 机制和实测都在 9.5 节，这里只留结论——
不管是普通 `LIMIT/OFFSET` 还是向量检索的 `offset`，只要这张表会被更新或 upsert，
翻页就会漏行；正确的姿势是稳定键 + 游标。

## 9.10 删除的语义与善后

前面几节讲的是机制，这一节把"删一次"之后会发生的语义细节收在一起：
返回值怎么读、哪些行删不掉、索引各有各的结局、空间什么时候回来。

### 幂等、可计数，而且不看索引

`delete` 返回 `DeleteResult(num_deleted_rows, version)`。**删到 0 行时版本号不动**：
`_delete_append` 在"既没删行也没追加"时直接返回当前版本号。所以对同一张表
连着删两次同一个谓词，第二次得到 `DeleteResult(num_deleted_rows=0, version=3)`——
版本还是 3，不会凭空多出一个空版本。**"重跑一次删除"是安全的。**

还有一件容易被忽略的事：**删除不走索引。** `_predicate_mask` 的实现是
"逐批取出整表、对每批 `evaluate_predicate`"，它没有 `_index_mask` 那条路径。
所以 `delete("id = 3")` 和 `delete("id + 1 = 4")` 一样贵——都是全表求值一遍。
这也解释了 §10.12 那个 `BETWEEN` bug 为什么"查询错、删除对"：
两条路走的是不同的代码。

### 哪些行删不掉

**`= NULL` 删不掉任何东西。** 实测一张 `[1.0, NaN, None, 4.0]` 的表：
`delete('f IS NULL')` 删掉的是那个 `None` 行（1 行），NaN 行安然无恙；
`delete('f > 0')` 删掉 1.0 和 4.0 两行，NaN 行还是没事——因为
"NaN 参与任何比较都得 NULL"（第 11 章 §11.5），而 `WHERE` 的语义是"只有 TRUE 留下"。

结果是 NaN 行成了**任何值谓词都够不着的行**：它比不过任何东西，
`IS NULL` 也判它不是空（它的 `valid` 是 True）。要删它只有两条路——
写一个恒真的谓词（`delete('true')`），或者靠写入侧别让它进来
（`on_bad_vectors`，第 11 章 §11.5 提到的第二道闸）。这是"三值逻辑 + 全序分歧"
落到运维上的具体形状。

### 索引的两种结局

删除之后，索引**不是一律失效、也不是一律修好**，而是分成两档：

**向量索引保持有效。** `IVF_FLAT` / `IVF_HNSW` / `HNSW` / `BQ` / `FLAT`
都实现了 `remap(old_to_new)`——索引里的行号就是一个数组，按映射表筛一遍、
重编号就完事。所以删完之后 `valid` 还是 `True`，`num_indexed_rows` 跟着变小。

**标量索引与倒排索引被作废。** `BTREE` 存的是有序键、`BITMAP` 存的是
"每个取值一张位图"、`LABEL_LIST` 存的是标签到行号的映射、倒排存的是
"每个 token 的文档号列表"——行号散在索引结构里，统一搬一遍的代价和重建没差多少。
所以 `_remap_indices_after_delete` 捕获到搬不动，就把它们标成
`valid = False` 并写 `details.invalidated_by_delete = True`。实测 1,000 行表上
建 `BTREE(id)` 和 `FTS(txt)`，`delete('id % 2 = 0')` 之后两个索引都变成
`valid=False` / `invalidated_by_delete=True`。

两者的后果差别很大，值得分别记住：**标量索引失效只是慢**——`count_rows('id = 3')`
仍然返回 1，查询悄悄退化回全表扫；**倒排索引失效是直接报错**——
全文检索会抛 `IndexNotFoundError: 没有可用的全文索引，无法做全文检索`，
提示你重建。一个降级、一个罢工，运维上要区别对待。

顺带把 `_revalidate_indices` 的职责分清：它处理的是**schema 变化**——
只检查"索引引用的列还在不在 schema 里"，列没了就置失效。
它和行号无关，是另一条失效路径。

### 压实、GC 与时间旅行

三件事都在删除之后发生，顺序不能乱。**压实**（§9.9 实测）把逻辑行重排、
物理行收紧，并且一律把索引标成 `invalidated_by_compaction = True`，
所以顺序是"压实 → 重建索引"——理由和上面同一句话：行号变了。**GC**
回收的是旧版本的删除文件与数据文件，窗口的意义和做法在第 23 章 §23.5。
**时间旅行**是删除的那笔"存款"：删除不改数据文件，所以 `checkout` 回到删除之前的
版本，那次删除就整体消失——不用"反向删除"，回滚一次删除是零成本的
（第 7 章 §7.4）。

### `_rowid` 在更新之后会变

对向量列做 `update` 时，`_rowid` **不保持**。它不是 stable row id，
而是"当前逻辑行号"：实测一张 4 行表（`id` 0~3），
`update(where='id = 1', ...)` 之后行序变成 `[0, 2, 3, 1]`，
于是 `id=1` 的 `_rowid` 从 1 变成 3，`id=2` / `id=3` 各前移一位。
要跨更新稳定的标识，得开 stable row ids（第 7 章 §7.8）——
这也是"为什么 upsert 场景下别拿 `_rowid` 当业务主键"的底层原因。

## 9.11 小结

**删除是纯元数据操作。** 300 万行的片段删 3 行只写 41 字节；
代价正比于删除量，不正比于表大小。

**删除文件的两种编码对应两种分布。** 稀疏删除用排序行号的 Arrow IPC，
密集删除用 Roaring bitmap。差分 + varint 在稀疏侧最优，
bitmap 在密集侧最优——选哪个取决于**分布**，不取决于数据量级。

**物理行号与逻辑行号是两套编号。** 删除文件记物理偏移（删掉的行仍占号），
用户看逻辑行号（删掉的不占号）。真实 Lance 用
`(fragment_id << 32) | offset` 的行地址把换算变成纯算术，
不需要显式映射表；stable row ids 在此基础上再提供一层跨压实稳定的标识。

**软删除的代价在读取侧。** 删掉 99% 的行只让读取量降 34%，
因为删除打碎了偏移的连续性，行范围下推失效。幽灵行是这笔代价的另一半：
索引不跟着删除走的时候，被删的行会占掉 `nprobes` 的候选名额
（早期实测 `nprobes=4` 时 250 个候选里只有 50 个是活的，**80% 算力花在幽灵上**）；
现在删除会把索引里的行号搬掉，候选池只剩活行，代价挪到了写入侧的索引重写。

**行号在系统不同层含义不同，索引那一层最隐蔽。** 索引存的是
"建索引那一刻的逻辑行号"，删除之后它就不再成立。
现在的处理是分档的：搬得动的向量索引重映射行号、保持有效；
搬不动的标量索引与倒排索引被置成 `valid = False` 并记
`invalidated_by_delete`（前者查询降级成全表扫，后者直接报错）。
`_revalidate_indices` 管的是另一件事——schema 变化后"列还在不在"。

**`update` 是删除 + 追加，所以行序会变，`offset` 分页会漏行。**
实测两页拼起来少一行，没有任何报错。

**`values_sql` 复用同一个表达式引擎**，更新语义和过滤语义
因此天然一致，不会各自漂移。

**`merge_insert` 的全部语义压在一次提交里。** 分成两次提交，
中途失败就等于丢数据。两边重复 key 的行为都是"保留最后一条"：
目标表重复 key 时更新的是最后一行（结果仍是两行），源数据重复 key 时先在入口去重。
真实 LanceDB 把源侧策略做成可配置参数，本实现写死为保留最后一条；
它那条"未索引行超 10000 会硬报错"的限制来自文档引用，**未经本机复跑**，
所以 join 列上建标量索引是建议而不是被证实的必需。

**维护的顺序是先看 `deletion_ratio`、再压实、再重建索引。**
10% 是合并的经验阈值；压实会让索引失效，所以两者不能颠倒。
压实只回收片段里的空白，旧版本的回收是 GC（第 23 章 §23.5），
而删除之前的版本在 GC 窗口内还能 `checkout` 回去（第 7 章 §7.4）。
