# 第 16 章　标量量化与二值量化

PQ 是"把维度切段、每段查码本"，压缩比靠的是子空间分解。这一章讲两条
更极端的路线：**SQ 是"每一维独立降精度"，BQ 是"每一维只留一个符号"。**
它们一个温和、一个激进，分别对应内存预算光谱的两端。

## 16.1 SQ：最笨但最划算的量化

标量量化（Scalar Quantization）的想法简单到没有门槛：
**对每一维独立地记下 `min` 和 `max`，把浮点值线性映射到
`2^b` 个整数格点上。**

编码是（`sq.py` 的 `encode`）：

```python
raw = np.rint((m - self.min) / self.scale)
codes = np.clip(raw, 0, self.max_level).astype(np.uint8)
```

解码是：

```python
decoded = self.min + codes.astype(np.float32) * self.scale
```

其中 `scale = (max - min) / max_level`。`b = 8` 时 `max_level = 255`，
一条 `d` 维向量从 `4d` 字节压到 `d` 字节——**4 倍**。

**先说清一个贯穿本节和下一节的口径，否则数字会被误读：迷你实现的 SQ
默认是逐维 bounds**（`ScalarQuantizer(per_dimension=True)`，`mini_lancedb/index/sq.py`），
也就是每一维各算一组独立的 `min/max`。本节报的重建误差（0.0058）用的就是
这个默认口径，召回数字也一样（下面那个"整体平移"实验是唯一的例外，它
显式切到了全局 bounds，因为要复现的是 Lance 那种"一套全局区间硬 clip 新值"
的行为）。而 §16.2 会论证**真实 Lance 选的其实是全局 bounds**——两处的口径
不同，看到 SQ 的误差或召回数字时先确认它是哪一种。

编码里那个 `np.clip(raw, 0, self.max_level)` 不是保险丝，是**语义的一部分**：
**训练区间之外的值会被钉到最近的端点，而不是溢出成环。** 训练时无所谓
（所有值都在区间内），但它决定了**增量写入**的行为——索引的 bounds 是建它
那一刻算出来的，之后写进来的行如果落到旧区间外，就会被 clip 到边界。
实测（8 bit、**全局** bounds、训练区间 `[-11.14, 11.43]`；测量脚本
`chapter_16` 的 `SQ 增量` 一节）：把这批数据整体平移，中位相对误差在
**平移 +0** 时是 0.0078（同分布），**+6** 时 0.0370（部分出界，已经涨到
4.7 倍），**+12** 时 0.2165（大部分出界），**+25** 时 0.5564
（整批落在区间外，一半以上的向量信息被端点吞掉）。所以"SQ 只扫一遍、
增量无损"是错觉：**它的增量是"用旧 bounds 硬 clip 新值"**，分布一旦漂移就
持续退化，正确做法是定期重建（第 12 章 §12.6 那套 `num_unindexed_rows`
的语义在这里同样适用）。

为什么误差能小到几乎看不出来？8 bit 把一段区间切成 256 份，
每个格点宽 `(max - min)/255`，最大的舍入误差是半个格点宽，
也就是 `(max - min)/510`。而真实向量每一维的取值区间本来就不宽，
所以这个绝对误差相对向量模长（**所有维度一起贡献的**）是微不足道的。

这是 SQ 和 PQ 最本质的区别：**SQ 的误差不累积**。
PQ 丢的是"子空间内部的维度相关性"，SQ 丢的只是每一维最后那一点点精度。
所以 SQ 用 4 倍压缩换来的几乎是无损——我们实测的中位相对重建误差是 0.0058，
也就是 0.6%。

SQ 还有两个相对 PQ 的工程优势：

**第一，它不训练（或者说训练只需扫一遍）。** `train()` 只做
`sample.min(axis=0)` 和 `sample.max(axis=0)`，是 `O(n·d)` 的单遍扫描。
PQ 的 k-means 要迭代几十轮。建索引时这个差异是数量级的。

**但"单遍"不等于"免费"，规模一上来它同样是实打实的带宽问题。**
求 min/max 必须**看到每一个值**（真实 Lance 的 `update_bounds` 是对
展平后的整列做 `fold`，一个值都不落），1 亿条 × 768 维就是 7.68×10¹⁰ 个
float32、约 300 GB，得完整读一遍。它确实比 PQ 的几十轮 k-means 便宜，
但在"只读一遍、串行归约"这个意义上属于另一类成本：**min/max 是归约，
没有并行度可以掩盖延迟。** 本实现的 `train()` 留了个 `sample_size` 口子，
可以在采样子集上估 bounds——省了带宽，代价是 bounds 可能比真实值域窄，
那会直接引出下面说的 clip 损失。

**第二，它的相邻性保持得更好。** 每一维都独立保留，
所以"两个向量在某一维上接近"这件事不会像 PQ 那样被码本的粗粒度抹掉。

代价是压缩率只有 4 倍（8 bit）；**4 bit 看似能到 8 倍，但那只在"把两个
4-bit 码打包进一个字节"时才成立**——迷你实现为了代码清晰没有做这个打包，
`encode` 恒返回 `np.uint8`，所以 4 bit 仍是 1 字节/维、压缩率也只算 4.0
（实测 4 bit 和 8 bit 的每条向量字节数一模一样），而真实 Lance 干脆不
支持 4-bit SQ（§16.4）。而 PQ 可以做到 100 倍以上。**SQ 是"内存还能撑住但
想省一档"时的选择，不是"内存装不下"时的选择。**

## 16.2 全局 bounds vs 逐维 bounds：Lance 的取舍

SQ 有一个必须做对的设计决定：**`min` 和 `max` 是每一维各一组，
还是全局共用一组？**

逐维 bounds 显然更"正确"——每一维有自己的动态范围，
每个 8-bit 格点都能被充分利用。全局 bounds 则是**拿所有行、
所有维度展平后的那一个 `[min, max]`** 去覆盖全部数据。

真实的 Lance 选的是**全局**。`update_bounds`
（`rust/lance-index/src/vector/sq.rs:67-86`）的实现是：

```rust
let data = vectors.values()....as_slice();   // FixedSizeList 的展平子数组
self.metadata.bounds = data.iter().fold(self.metadata.bounds.clone(), |f, v| {
    f.start.min(v.as_())..f.end.max(v.as_())
});
```

`vectors.values()` 是 `FixedSizeList` 的**展平子数组**，
所以这个 `fold` 跨越了**所有行和所有维度**，得到的是唯一的那一组
`[min, max]`。初值是 `Range { start: f64::MAX, end: f64::MIN }`，
而且是累积的（`retrain` 会进一步放宽）。

**为什么 Lance 做了这个看起来更差的选择？三个理由：**

**第一，它让"查询也要量化"这件事变得可行。** 16.3 会讲这个。
如果 bounds 是逐维的，查询向量的每一维要按它对应的 scale 换算；
全局 bounds 的话，整个查询用一个 `scale` 和一个 `min` 就编完了，
在 SIMD 里这是一次乘加、一段连续内存。

**第二，逐维 bounds 要存 `2d` 个浮点数。** 768 维就是 6 KB 的元数据，
而且它必须和码本一起读进来、参与每次查询的解码。
全局 bounds 只有 16 字节。

**第三，也是最反直觉的一点：全局 bounds 的精度损失没有想象中大。**
我们的实测（3000 × 32 维）扫了 `num_bits ∈ {2, 4, 8}` × `{逐维, 全局}`
六组，报告**中位 / 平均相对重建误差**：

**8 bit**（码值域 0..255）——逐维 0.00575 / 0.00586，全局 0.00782 / 0.00800；
**4 bit**（0..15）——逐维 0.09772 / 0.09961，全局 0.13300 / 0.13594；
**2 bit**（0..3）——逐维 0.50271 / 0.51393，全局 0.66691 / 0.68630。

**8 bit 时，全局 bounds 只让误差从 0.575% 涨到 0.782%——差 0.2 个百分点。**
用 0.2 个百分点的精度，换掉 6 KB 的逐维元数据和整个查询侧的特殊处理，
这笔账显然划算。**但位数越低，全局 bounds 的惩罚越重**：
4 bit 时误差涨 36%，2 bit 时涨 33%。因为格点越少，
"用一个大区间去覆盖所有维度"浪费掉的有效格点就越多。

看看为什么浪费：在我们这份数据上，逐维区间宽度最小 11.914、
最大 21.220，比值只有 1.78；而全局区间宽度是 22.570。
**这份数据的各维动态范围其实很接近**，所以全局 bounds 几乎不吃亏。
这是合成数据的特征——真实 embedding 的各维尺度差别常常大得多
（比如有的维度被激活函数截断在 `[0, 1]`，有的维度是自由的正态分布），
那时候全局 bounds 的惩罚会显著大于这里的 0.2%。

**所以 Lance 的选择是"接受一个通常温和、偶尔严重的精度损失，
换取查询路径的极大简化"。** 用户在遇到精度问题时，
能做的是换索引类型（`IVF_SQ` 换 `IVF_PQ` 或 `IVF_FLAT`），
而不是调 bounds——因为它不可配。

## 16.3 SQ 的查询也被量化成 u8

这是 SQ 最反直觉、也最值得单独讲的一点：**Lance 的 SQ 把查询向量
也用同一套 bounds 编码成 u8。**

`SQDistCalculator`（`rust/lance-index/src/vector/sq/storage.rs:446-724`）
持有 `query_sq_code: SQQueryCode`。对 L2/cosine
（`:664-687`）的处理是：查询向量**先编码成 u8**（用同一套 bounds，
`sq/storage.rs:554-573`），然后

```
distance = l2_u8_u64(code_x, code_q) as f32 * sq_distance_scale
```

其中 `l2_u8_u64(a,b) = Σ (a_i - b_i)²`（`lance-linalg/src/distance/l2_u8.rs`），
`sq_distance_scale = value_scale²`（`sq/storage.rs:440-444`）。
Dot 度量走代数展开（`:627-656`），同样不回头碰 f32。

**所以 SQ 是"对称距离"（SDC），不是 PQ 那种"非对称"（ADC）。**
两侧都被量化，误差来源是两个而不是一个。这和 PQ 的哲学正好相反——
PQ 拼了命保住查询侧的浮点精度（第 14 章 §14.3 的 ADC 就是为此存在的），
SQ 干脆两边都量化。**分工记清楚：本章这一节回答"SQ 为什么能走整数核"，
ADC 的查表机制归第 14 章 §14.3**，两处互指，别指望在一章里把两条路线都讲全。

为什么敢两边都量化？**因为 8 bit 够用。** 我们实测了这一步的代价
（3000 行 × 32 维，40 条查询，recall@10）：逐维 bounds 下，对称
（查询也编成 u8）是 0.9850、非对称（查询保持浮点）是 0.9825；
全局 bounds 下，对称 0.9625、非对称 0.9675。

**分开看这两组：同一种 bounds 下，"查询也量化"的代价只有 0.0025（逐维）
到 0.0050（全局）——也就是一条查询结果的抖动范围，8-bit 的查询量化在这个
规模上几乎测不出损失。四种组合合起来极差 0.0225，主要来自 bounds 粒度
（逐维 0.9825~0.9850 对全局 0.9625~0.9675），而不是来自查询量化。**
（真实数据上强过滤、小 k 的场景会更敏感，但量级上依然很小。）

而收益是巨大的：整个距离计算变成**纯整数 kernel**——
u8 之间的平方差之和，没有浮点、没有解码、没有分支。
这正是 Lance 敢用全局 bounds 的原因（16.2 第一条）：
**一个全局 scale 就能把整条查询编成 u8，然后距离就是一段
可以 SIMD 化的整数循环。** 如果用逐维 bounds，
查询的每一维要按不同的 scale 换算，那个 kernel 就写不整齐了。

这背后是一个值得记住的设计原则：**在量化系统里，
"让热路径变成同构的整数运算"往往比"每处都用最精确的表示"更值钱。**
代价是 0.2 个百分点的误差，收益是一个数量级的 kernel 复杂度。

## 16.4 SQ 的布局和 4-bit 的现状

和 PQ 相反，**SQ 的码是行主序、不转置的。**
`ScalarQuantizationStorage`（`sq/storage.rs:136-140`）取一条向量的码是

```rust
sq_code_slice(id) = &sq_codes.values()[id*dim .. (id+1)*dim]
```

标准的连续一段。而 `ScalarQuantizationMetadata` **没有重写
`is_transposed()`**，所以默认是 `false`。为什么 SQ 不需要转置？
因为它的计算模式是"一条向量对一条查询逐维相减"——
**它是按行遍历的，和 PQ 按子空间遍历正好相反。** 布局跟着计算模式走，
这条规则 PQ 和 SQ 各验证了一半。

**关于 4-bit SQ，有一个必须说清楚的现状：Lance 只支持 8-bit。**
`ScalarQuantizationMetadata` 里有 `num_bits: u16` 这个字段，
但它**只被持久化、不被使用**。`ScalarQuantizer::transform`
（`rust/lance-index/src/vector/sq.rs:88-113`）里有一行注释
`// TODO: support SQ4`，然后无条件地调 `scale_to_u8`。
所以"4-bit SQ 把两维打包进一个字节"这件事
**在当前实现里不存在**，`SQ_CODE_COLUMN` 的 Arrow 类型恒为
`FixedSizeList<UInt8, dim>`——每维一字节。

`SQBuildParams` 的默认值是 `num_bits = 8`、`sample_rate = 256`
（`sq/builder.rs:6-30`），和 IVF 的 `sample_rate` 是一套。
元数据键是 `"lance:sq"`，`storage_metadata` 里存
`dim`、`num_bits`、`bounds`。

本教程的迷你实现**支持 1/2/4/8 位**，纯粹是为了让
"位数 vs 误差"这条曲线能画出来（16.2 那张表）。**它不代表 Lance 的能力。**
写代码时如果依赖 4-bit SQ，在真实 LanceDB 上会直接跑不起来。

## 16.5 BQ：每一维只留一个符号

二值量化（Binary Quantization）是量化谱系最极端的一档：
**每一维只留符号（正/负），不留幅度。**

编码就是 `x >= 0` 的结果按位打包：

```python
# encode() 里就是一行
return pack_signs(m >= 0)

# pack_signs() 里
packed = np.packbits(s, axis=1, bitorder="little")
```

**32 倍的省法从哪来？** float32 的一个维度占 32 位，BQ 只占 1 位——
但**前提是这些位能被整齐地打包进 64 位字里，也就是维度是 64 的倍数**。
打包成 64 位字之后，一次 `popcount(xor)` 能同时比较 64 个维度。
在这个前提下，768 维的 embedding 恰好是 64 的 12 倍，于是：

```
10 亿条 768 维：float32 = 3072 GB → BQ = 96 GB
```

单机内存能装下了。而且汉明距离是 CPU 的单个指令（`POPCNT`），
比浮点点积快 5~10 倍，没有乘法。

**维度不是 64 的倍数时，压缩比要打折，折扣是明码标价的。** 实测
32 维的向量只占 1 个 uint64 字（64 位里浪费了 32 位），压缩比从 32 倍
掉到 16.0；128 维占 2 个字、刚好填满，才是完整的 32.0 倍。
**用 32 维向量做 BQ 就是在浪费一半的位。** 所以选 BQ 之前先看维度，
`dim % 64` 越接近 0 越划算。

**维度不是 64 的倍数时，标准做法是补零（padding）到 64 的倍数。**
补出来的那些位符号恒为 0，对汉明距离的贡献恒为 0、也不改变任何内积，
所以对排序没有影响；它只是让"每个向量占几个字"凑成整数。768 / 1024 /
1536 这些维度天然是 64 的倍数，不用补；而 100 维要补到 128 位——浪费 28 位，
压缩比从 32 掉到约 25（100×32 / 128 = 25）。**补零比"打包成非整数字长"
简单得多，是所有实现的默认做法。** 顺带区分一条相邻的约束：
第 12 章 §12.3 说的"`IVF_RQ` 要求维度能被 8 整除"是 RaBitQ 的 LUT
分段粒度要求（4 维一段、两段一字），和这里的 64 位对齐不是同一件事。

**代价是召回率，而且它不能靠"多探几个分区"补回来。**
符号丢掉的是幅度信息：两个分量大小差 100 倍的向量，
只要符号相同就"看起来一样"。所以 BQ 的**候选集**可能是对的，
但**排序**几乎不可信。实测 `refine_factor` 取 1（纯汉明）/ 2 / 5 / 10 /
20 / 50 时，recall@10 依次是 0.1600 / 0.2650 / 0.5800 / 0.8475 /
1.0000 / 1.0000。

**纯汉明的召回率是 0.16——基本等于随机。** 但 refine_factor 涨到 20
就回到 1.00。这个巨大反差揭示了 BQ 的真正性质：
**1 bit 留下的"大致方向"是对的（所以真正的最近邻在候选集里），
丢的是排序能力（所以纯汉明排不出来）。**

这解释了为什么 `refine_factor` 对 BQ 是**必需品而不是可选项**
（这个旋钮本身在第 12 章 §12.7 讲过，这里只看它对 BQ 的极端依赖——
BQ 把"放大候选"从加分项变成了生命线）。`BqIndex.search` 里的逻辑是两段：

```python
ham = self.quantizer.hamming(self.codes, packed_q)   # 全量汉明屏幕
sel = np.argpartition(ham, take - 1)[:take]          # 取 k*refine 个候选
scores = pairwise_distances(self.vectors[sel], ...)  # 浮点精排
```

这就是**重排策略（rescoring）**：用便宜的距离取一个宽松的候选集，
再用精确距离重排。它是所有高压缩比量化器的通用套路——
BQ 只是把它推到了极致（候选集要放宽 20 倍）。

有一个容易踩的坑：**汉明距离不能用 `pairwise_distances` 算。**
后者会把输入先转成 float32，把打包好的位串毁掉。
必须走专门的 `hamming_distance`（位异或 + popcount）。这在代码里
是一条隐式的类型契约，看代码时要留意。

**度量类型不是随便挑的：BQ 天然只配汉明距离，RaBitQ 只配 LUT 内积。**
两者都**不支持任意的 `distance_type`**——BQ 的编码只留了符号，能算的只有
"有多少位不同"（汉明，见 `DistanceType::Hamming`）；RaBitQ 用 4 维一段的
查表做整数内积，算的是"编码与查询的（近似）内积"。要拿它们做 L2，只能靠
"内积 = (‖q‖²+‖x‖²-‖q-x‖²)/2" 这类恒等变换绕一圈。**cosine 还要多一步
前提：查询和库向量都必须先归一化成单位长度**——cosine 只关心方向，而
归一化之后 `‖q-x‖² = 2 - 2·q·x`，内积度量才和 cosine 排序一致。
不归一化就直接上 BQ/RQ，等于让**模长**（而不是方向）参与打分，
而这恰好是符号量化丢得最狠的那个信息。

## 16.6 RaBitQ：为什么纯汉明不够，以及它加了什么

朴素 BQ 的问题是 16.5 那个 0.16。问题出在两处，RaBitQ 各修一处。
**和第 12 章的分工先划清：第 12 章 §12.7 负责回答"什么时候该选 RQ"
（官方 5-bit RaBitQ 的三档实测延迟与热态内存都在那里），
本章这一节负责回答"RQ 内部到底怎么工作"。** 两边不重复。

**修复一：随机旋转。** 符号量化的精度强烈依赖数据的分布方向。
如果数据集中在某个方向上（真实 embedding 常常如此），
那么"符号"这个操作会把所有点都投到相似的模式上，区分度极低。
RaBitQ 在量化之前先乘一个**随机正交矩阵**，把数据旋转成各向同性
（isotropic）的分布——每个方向上的方差大致相同，
这样"符号"才携带最大信息量。

Lance 的实现有两种旋转（`RQRotationType`，`bq.rs:92-113`），
默认是 **Fast**：不显式构造矩阵，而是做一个"随机对角符号翻转
（Rademacher）→ 快速 Walsh-Hadamard 变换 → 缩放 `1/sqrt(dim)`"的
组合（`rotation.rs:9-17`），重复 `FAST_ROTATION_ROUNDS = 4` 轮。
FWHT 是 `O(d log d)` 的，比一次 `O(d²)` 的矩阵乘法便宜得多——
**这是"随机旋转"能进入热路径的前提。** 另一种 Matrix 模式会真的
生成随机正交矩阵（随机正态 + Householder QR 取 Q，
`bq/builder.rs:1206-1260`），存在 global buffer 里，但默认不用。

**修复二：不只是符号，还有幅度。** RaBitQ 支持
`num_bits ∈ 1..=9`——位不是 1、而是 1 到 9。
常量定义在 `bq.rs:29-33`：

```rust
pub const RABIT_MIN_NUM_BITS: u8 = 1;
pub const RABIT_MAX_NUM_BITS: u8 = 9;
pub const RABIT_BINARY_NUM_BITS: u8 = 1;
pub(crate) const RABIT_DEFAULT_NUM_BITS: u8 = 5;
```

`1` 就是纯符号位。**这里有一个"两层默认值"的坑，本章是它唯一的完整
出处**：Rust 层的常量 `RABIT_DEFAULT_NUM_BITS` 确实是 **5**（上面第 4 行），
但 **Python SDK 的 `IvfRq()` 默认把它覆盖成 `num_bits=1`**——实测
`inspect.signature(IvfRq)` 拿到的注解就是 `num_bits: int = 1`
（本机 `lancedb 0.40.0`）。也就是说**用户不显式传参时拿到的是 1 bit/维、
纯符号位，不是这里 Rust 层那个 5**。第 12 章 §12.4（只钉结论）和 §12.7
（三档 `approx_mode` 那组数字的口径）都指回这一处，别在两处各记一半；
想复现官方博文里那组 5-bit 的数字，得显式传 `num_bits=5`。超出的那些位
`rabit_ex_bits(num_bits) = num_bits - 1` 是"ex-code"——
额外的幅度信息，存成单独的列。再加上
`__add_factors`（量化值与残差的内积）和 `__scale_factors`
（量化值与质心的内积），查询时用它们把整数距离还原回浮点尺度。
**RQ 的残差是无条件启用的**（`use_residual() == true`，`bq/builder.rs:1114-1116`），
不像 PQ 只在 L2/cosine 上。

**修复三，也是最容易被搞错的一点：距离不是 popcount。**
真实 Lance 里存在两条完全无关的"二进制距离"路径：

- **旧 BQ/汉明**：`DistanceType::Hamming` + 对 `UInt8` 做 popcount。
  这条路径在当前代码里是**死代码**——`BinaryQuantization` /
  `binary_quantization` 没有任何调用方；
- **RQ（活跃路径）**：用的是一个 **4 维一段、每段 16 项查表（LUT）
  的整数内积**，不是 popcount。

`build_dist_table_direct`（`bq/storage.rs:1601-1649`）把向量按
`SEGMENT_LENGTH = 4` 维切成一段，段内 `2^4 = 16` 种码，
所以整张表的大小是 `dim/4 × 16`。表是这样递推出来的：

```rust
dist_table[0] = 0.0;
for j in 1..16 {
    dist_table[j] = dist_table[j - lowbit(j)] + sub_vec[LOWBIT_IDX[j]].as_();
}
```

也就是 `dist_table[i*16 + j] = Σ (j 的第 b 位为 1 的) q[4i + b]`——
**这张表是"查询向量那一段"和"二进制码那种取值的整数内积"**。
算完整数内积之后，再乘 `__scale_factors`、加 `__add_factors`
和 `query_factor` 还原成浮点距离（`DistCalculator::distance`，
`bq/storage.rs:1849-1889`）：

```
dist_vq_qr = (2*dist - sum_q) / sqrt_d
最终距离 = dist_vq_qr * scale_factors[id] + add_factors[id] + query_factor
```

**为什么不用 popcount？** popcount 只能算"有多少位不同"，
那是**汉明距离**，它把每一维等同看待，不携带任何幅度信息。
而 RaBitQ 要算的是"二进制码和查询向量的内积"，
每一项要乘上查询那一维的实际数值——那个值只能是 0..255 的整数
（经过旋转和缩放之后），所以用"4 维一段的 16 项查表"来算：
每一段 4 个 bit 有 16 种可能取值，预先算好这 16 种取值对应的
内积和，查一次表就得到一段的贡献。这是 **LUT 内积**，不是 popcount。

存储布局也是为这个 kernel 量身定做的（`pack_codes`，
`bq/storage.rs:2320-2385`）：`BATCH_SIZE = 32`，配合一个固定的
`PERM0 = [0,8,1,9,2,10,...,7,15]` 置换，每 32 个向量一个块，
低 16 字节存低半字节、高 16 字节存高半字节。
这个布局是给 `_mm256_shuffle_epi8` 用的——
**它就是为"一次洗牌 16 个查表项"这个指令准备的。**

以上关于 RQ 的机制（旋转轮数、`SEGMENT_LENGTH`、`PERM0`、
`add_factors`/`scale_factors`）全部来自对上游 Lance Rust 源码的整理
（`bq.rs` / `bq/storage.rs`），我**没有**独立运行过 Lance 的 Rust 实现来
复现这些数字，因此这一段的机制描述标注为**转引**。第 4 章讲的是列式编码
这一层，RQ 的存储布局和它是同一个"为 kernel 定制字节排布"的思路。
本节里的召回率、模长比等数值则来自本教程迷你实现
（朴素 BQ + scale 精排）的实跑，可复现。

## 16.7 符号量化到底丢了多少：一个精确的数学事实

朴素 BQ 有一个漂亮的、可以精确算出来的性质，值得实测一遍。

符号量化把 `x` 变成 `sign(x)·s`，其中 `s = mean(|x|)` 是每行的平均绝对值
（迷你实现里的 `scales`，对应 RaBitQ 的 scale 因子）。
对于高斯（或任何零均值对称分布）数据，重建向量的模长和原始模长之比是：

```
E|x| / sqrt(E[x²])
```

对标准正态分布，`E|x| = sqrt(2/π)`，`E[x²] = 1`，
所以比值精确等于 `sqrt(2/π) ≈ 0.7979`。

实测（2000 × 256 维，高斯数据乘以 4）：

```
重建/原始 模长比: 均值 0.7992   （理论值 sqrt(2/pi) = 0.7979）
"绝对值的逐行均值精确等于 scale" 验算: True
```

**0.7992 对 0.7979——理论和实测吻合到小数点后两位。**
这个数字的含义是：**符号量化"方向对、长度打 0.8 折"。**
所有重建向量都短了 20%，而且是**均匀地**短，
所以排序时这个缩放是共同的、不影响谁更近——**直到它和别的向量比较**。

这就是 RaBitQ 那套 `add/scale` 因子在做的事：把丢掉的那 20% 幅度
用一个标量补回来。而"每行的平均绝对值"这个 scale 之所以有意义，
是因为它恰好是"这个向量该有多长"的最佳单参数估计。

顺带说一个实现细节：迷你实现里 `reconstruct()` 在
`scales` 和 `signs` 长度不一致时**直接返回符号（不乘 scale）**
（`bq.py`），这是为了在一个不支持 scale 的路径上优雅降级。
`fit_scales` 必须在 `encode` 之后、`reconstruct` 之前调用，
否则重建出来的东西会系统性偏小。

## 16.8 什么时候该用 BQ

把前面所有信息合起来，BQ 的适用条件相当清楚：

**维度要高。** 因为随机旋转和各向同性假设在高维才成立，
而且维度是 64 的倍数时才能吃满 32 倍压缩。768、1024、1536 维的
embedding 是最典型的场景。

**N 要大。** BQ 是"用算力换内存"的方案：汉明屏幕是全量扫的
（`BqIndex` 没有 IVF 分区也没有图，因为汉明已经足够便宜，
而"多探分区救不了符号损失"），所以它只有在
"内存红线卡死、且必须全量数据常驻"时才划算。
1 亿到 10 亿条这个量级是它的主场。

**召回率容忍度高。** 纯汉明的 0.16 是不能接受的，
必须要 refine。所以 BQ 的真实工作模式是
"汉明取 `20k` 个候选 + 浮点精排"，此时的精度接近精确检索，
但每查询要多读 `20k` 条原始向量（如果向量不在内存里，
这就是 20 倍的磁盘 I/O）。

**可以接受重排的开销。** 如果 k 很小（比如 10）、refine_factor 是 20，
那要回表读 200 条向量。这个数字看着不大，但如果原始向量在对象存储上，
就是 200 次随机读——那可能比整个查询还慢。**所以 BQ 真正适合的，
是"原始向量有便宜的来源（本地磁盘 / 已有的缓存）"的场景。**

**把四条路线放在一起看，内存差了两个数量级。** 以 10 亿条 × 768 维为例，
FLAT（存原始 float32）是 3072 GB，SQ（8 bit/维）是 768 GB，BQ（1 bit/维、
768 恰好是 64 的倍数）是 96 GB，PQ（m=8、8 bit）只要 8 GB。这是第 12 章
那条"压缩比谱"的算术底稿：**FLAT → SQ → BQ → PQ 是一路下探的内存阶梯，
代价是召回率从"精确"一路退化到"必须重排"**。选型时先看内存红线落在哪一档，
再在那一档里挑，而不是反过来。

一个值得记住的组合是 **IVF + BQ**：IVF 先把候选集缩到
`nprobes/P`，再在候选上做汉明屏幕。这样汉明扫的量小了，
回表重排的量也小了。LanceDB 里对应的类型是 `IVF_RQ`
（`IndexType::IvfRq`，`lib.rs:53-92`），也就是
"IVF 分区 + RaBitQ 量化"。

**最后，BQ 有一个别的量化器没有的优势：它不需要训练。**
符号规则对任何数据都一样，所以增量写入没有任何精度退化——
`BqIndex.append` 只是"同一条规则再编一批符号"。
对比之下，PQ 的追加是"挂到旧码本上"（会退化），
SQ 的追加是"用旧 bounds clip 新值"（超出训练区间的会被截断，
16.1 量过：数据整体平移 +12 时中位相对误差从 0.0078 跳到 0.22，
搬到区间外就丢掉一半以上的向量信息）。
**在持续写入的场景里，BQ 的增量是唯一真正无损的。**

## 16.9 小结

**SQ = 每一维独立降精度。** 8 bit 把一条向量从 `4d` 压到 `d` 字节（4 倍），
实测中位相对重建误差只有 0.58%——因为它的误差不跨维累积。

**Lance 的 SQ 用一组全局 `[min, max]`**（所有行 × 所有维展平，
`sq.rs:67-86`），不是逐维。实测 8 bit 时这只让误差从 0.575% 涨到 0.782%，
却省掉了 6 KB 逐维元数据和整个查询侧的特殊处理。**但位数越低惩罚越重**
（4 bit 时误差涨 36%）。

**Lance 的 SQ 把查询也编成 u8**，所以是**对称**距离，不是 PQ 那种非对称。
实测四种 bounds/对称组合的 recall 差别都在 0.0025 以内——
8-bit 查询量化基本无损，换来的是纯整数的距离 kernel。

**SQ 的码不转置，PQ 的码转置**——布局跟着计算模式走。

**Lance 只支持 8-bit SQ**，4-bit 是源码里的一行 `// TODO: support SQ4`。
本教程迷你实现支持 1/2/4/8 位只是为了让误差曲线能画出来。

**BQ 是 1 bit/维、32 倍压缩**——但只在维度是 64 的倍数时才取到
（32 维实测只有 16 倍）。纯汉明的 recall@10 是 0.16，
`refine_factor=20` 时回到 1.00：**1 bit 保住了方向，丢的是排序。**

**RaBitQ = 随机旋转 + 1~9 位（符号 + 幅度）+ 4 维一段 16 项 LUT 的
整数内积（不是 popcount），再用 add/scale 因子还原浮点尺度。**
Rust 层默认 `num_bits = 5`（常量 `RABIT_DEFAULT_NUM_BITS: u8 = 5`，
`bq.rs:29-33`；但 Python SDK 把它覆盖成 1，见 §16.6），旋转默认走
`O(d log d)` 的 FWHT。

**符号量化"方向对、长度打 0.8 折"**——实测模长比 0.7992，
理论值 `sqrt(2/pi) = 0.7979`。

**BQ 适合：高维、超大 N、内存红线卡死、能容忍重排。**
它不需要训练，所以是唯一增量无损的量化器。

到这里，向量索引的四种量化路线——FLAT、SQ、PQ、BQ（RaBitQ）——
和它们的组合（`IVF_SQ` / `IVF_PQ` / `IVF_HNSW_SQ` / `IVF_HNSW_PQ` / `IVF_RQ`）
都讲完了。其中 `IVF_HNSW_PQ` / `IVF_HNSW_FLAT` 这两型的结构与实测
（前者给了完整网格、后者标注了没有实测）见 §15.11。选型的本质是一次四方博弈：**内存、建索引时间、查询延迟、召回率**。
没有哪个索引在所有四个维度上都赢，所以真正的工作流永远是
"先用 `IVF_FLAT` 量出粗量化的天花板，再一层层加上量化和图，
每加一层就量一次召回率掉了多少"。

最后，"**先隔离误差源，再调参数**"这套方法论在第 12、13、14 章已经反复用过，
本章只补一句结论：`IVF_SQ` 的召回平台来自 SQ 的量化误差（调 `nprobes`
没用），`BQ` 那个 0.16 来自排序能力丢失（调 `refine` 以后能回到 1.00）。
看清楚是哪一种平台，才知道该动哪个旋钮。（提醒一句口径：`IVF_SQ` 那组
"调 `nprobes` 也上不去"的召回数字，用的是迷你实现**逐维 bounds** 的默认
设置，而真实 Lance 走的是全局 bounds，见 §16.1 与 §16.2。）

**如果查询是"一段文字"而不是"一个向量"呢**——那就是全文检索和 BM25。
