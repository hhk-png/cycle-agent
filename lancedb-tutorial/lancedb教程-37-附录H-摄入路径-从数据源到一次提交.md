# 附录 H　摄入路径：从数据源到一次提交

前面的正文把表建好之后的事讲得很细——查询怎么规划、索引怎么选、
版本怎么提交。但**数据是怎么进来的**那条路，散在好几章里各说了一段：
第 2 章讲了快速上手的三行代码，第 6 章讲了对象存储的读写放大，
第 24 章讲了写入路径的四个旋钮，第 25 章讲了批量大小和 upsert。
这一篇是把它们串成一条链，并且补上三个正文里没有位置放的东西：

一个**被拒绝的输入类型**，以及它为什么被拒绝——这条线索能一直通到
本实现的一个结构性取舍；真实 LanceDB 用来解决同一个问题的
`Scannable` 契约；以及一个很容易被低估的**内存问题**：
宽行数据在摄入时会先把客户端撑爆，而且爆得很突然。

## H.1 这一篇补的是哪一层

一条摄入链是六段：

数据源 → 读成批次 → 推断/校验 schema → 编码成页 → 写数据文件 → 提交 manifest

第 3、4 章讲第四段，第 7、8 章讲第五、六段，第 24 章讲第二段的旋钮。
**第一段和第三段基本是空的**，而它们恰好是"用户第一次跑不通"
最常卡住的地方——因为这里的失败大多不是崩溃，是**输入形状不对**或者
**内存不够**，而这两种失败的报错都离根因很远。

所以这一篇的读法建议是：如果你正准备往 LanceDB 灌一批真实数据，
先读 H.5 和 H.8（内存），再看 H.3（数据源的契约）；
如果你在写自己的存储引擎，H.2 和 H.7 是两份对照实现。

## H.2 一个被拒的输入，和它背后的两遍写入

先看一个具体的报错。往真实 LanceDB 里传一个**生成器**：

```python
db.create_table("t", ({"a": i} for i in range(5)))
# ValueError: Cannot create or add rows from a single dictionary.
#             Use a list of dictionaries instead.
```

报错说的是"不能从单个字典建表"——但传进去的分明是一个生成器，
不是字典。**这句话是错的，而且错得很有意思**：它泄漏了实现的一个细节。
`create_table` 内部把输入转成 Arrow 读流时会先
`next(data)` 取第一个元素（`lance` 侧 `_iterator_to_reader`），
拿到的是 `{"a": 0}`，而紧接着那个检查写的是
`isinstance(data, dict)`——现在 `data` 已经是**第一个元素**了，
于是命中了给"忘了套一层 `[...]`"准备的那条消息。
两个完全不同的用户错误（漏了方括号 / 传了生成器）共用一句报错。

**为什么生成器必须被拒？** 因为写入需要**两遍数据**：

第一遍要**看**数据，才能知道 schema——有哪些列、每列什么类型、
向量列多少维。第二遍要**写**数据，把它编码成页、落盘。
`list`、`tuple`、Arrow 表、DataFrame 都能被读两遍；生成器只能被消费一次。
如果允许传生成器，你会在第二遍才发现数据已经空了，
而那时第一遍的 schema 已经写进了 manifest。

这个"两遍"的约束不是实现偷懒。它来自一条更根本的要求：
**schema 必须在写入之前定下来**，因为 manifest 里存的是 schema，
而数据文件是按 schema 编码的。想只走一遍，就得让数据源自己声明
schema——那就回到了 Arrow 的设计，也就是下面这个契约。

## H.3 Scannable：把"两遍"变成一次契约

真实 LanceDB 用一个很轻的协议解决这件事：`lancedb.scannable.Scannable`。
它是一个 dataclass，只有四个字段：

```
schema       : pa.Schema                     数据长什么样
num_rows     : Optional[int]                 有多少行（可以不知道）
reader       : Callable[[], pa.RecordBatchReader]   工厂：每次调用给出一个新的读流
rescannable  : bool                          这个工厂能不能被反复调用
```

关键在第三个字段的措辞：**它是个工厂，不是读流**。
`reader()` 每调一次就产出一次完整的数据，这正是"两遍"需要的形状。
`to_scannable()` 用 `functools.singledispatch` 把常见类型映射到它，
本机 0.40.0 实测这套分派是这样的：

| 输入类型 | 产出的 Scannable | `num_rows` | `rescannable` |
|---|---|---|---|
| `pa.Table` | 包住 `to_reader` | 真实行数 | **True** |
| `pa.RecordBatch` | 包住这一批 | 真实行数 | **True** |
| `list[dict]` | 先转 Arrow 表 | 真实行数 | **True** |
| `ds.Dataset`（parquet 目录） | 每次新建 scanner | `count_rows()` | **True** |
| `pa.RecordBatchReader` | 原样返回 | **None** | **False** |
| `ds.Scanner` | 原样返回 | **None** | **False** |
| `dict` | —— | 抛 `ValueError` | —— |
| 单个 `LanceModel` | —— | 抛 `ValueError` | —— |
| 生成器 / 迭代器 | 先取第一个元素推 schema，再惰性拼接 | **None** | **False** |

用 `ds.Dataset` 建表在本机实测是通的：

```python
ds.write_dataset(arrow_table, "parquet_dir", format="parquet")
db.create_table("t", ds.dataset("parquet_dir", format="parquet"))   # 1000 行，通过
```

**这张表里最值得看的是最后一行**——生成器并不是简单地被拒。
`to_scannable` 的回退分支会先 `next(data)` 取第一个元素、
用它推断 schema，再把剩下的元素惰性地拼成一个
`RecordBatchReader`。所以生成器**能**走通这条路，
只是要付两个代价：`num_rows=None`（不知道总量），
以及 `rescannable=False`（读流是一次性的）。
（本机实测有个额外的坑：如果生成器里 yield 的是**字典**，
会在 `to_arrow()` 那一层炸掉，报
`NotImplementedError: to_arrow not implemented for type <class 'dict'>`——
即这条回退路径只对"元素本身是 Arrow 能懂的东西"成立。
用 `create_table` 传字典生成器仍然得到 H.2 里的那句
`Cannot create or add rows from a single dictionary.`）

## H.4 rescannable 到底买了什么

`rescannable` 这个布尔值看起来像个元数据标注，其实它直接决定
**引擎能对数据源做多少事**。区别只有一条，但影响不小：

**可重扫的源可以被"偷看一眼"。** 宽行数据的扫描参数要按
"每行多少字节"来算（下一节详述），而 schema 只能给出定长类型的宽度。
如果向量列是 `list<float32>` 而**不带**固定长度
（`list<float32, 768>` 才是定长的），schema 本身推不出每行多宽。
这时候引擎会去源里取**最多 10 行**（`_SAMPLE_ROWS = 10`）样本来量一下
平均宽度——而"取 10 行"这件事只对可重扫的源成立：
它得能读一次样本、然后再从头读一遍完整数据。

一次性的源（`RecordBatchReader` / `Scanner` / 生成器）做不到这一点，
所以它们只能退回**纯 schema 估算**，对变长列表列用一个固定的
保守值 `_VARIABLE_WIDTH_ESTIMATE = 128` 字节。
保守估宽了，只会让批次变小（吞吐略降）；估窄了，才会 OOM。
**这个方向的取舍是刻意的：估算宁可偏大。** 采样失败（比如空数据集）
也走同一条回退，`_sample_head` 把所有异常吞掉返回 `None`——
宁可退化，不能因为"量不出宽度"就拒绝摄入。

所以如果你的摄入管道是自己写的、数据源能重扫，
**把它做成 `ds.Dataset` 而不是一次性 reader**，能白拿一档更准的估算。
反过来，如果数据源真的只能读一次（比如从 Kafka 或一个 HTTP 流灌进来），
那就得自己在外面缓冲成 `pa.Table`——两遍写入这个约束是绕不过去的，
要么让源可重扫，要么在客户端把它物化成可重扫的东西。

## H.5 宽行的内存炸弹：15 GiB 是怎么算出来的

现在讲这一篇里最有用的一件事：**为什么往 LanceDB 灌嵌入向量
会把客户端 OOM，而灌普通表格不会。**

pyarrow 的 scanner 有一组默认值，它们是**按窄行调的**：

```
batch_size          = 131072 行
batch_readahead     = 16     批
fragment_readahead  = 4      批
```

关键在"readahead"这两个参数：pyarrow 读 parquet 时是**按 row group**
读的，而它会把 `batch_readahead` 个批次和 `fragment_readahead` 个片段
**同时驻留在内存里**。所以飞行中的内存量大致是：

```
在飞字节 ≈ bytes_per_row × batch_size × (batch_readahead + fragment_readahead)
```

对窄行数据这完全没问题。真正的问题出在 `bytes_per_row` 上。
用 0.40.0 里那个估算函数在本机跑一遍（`bytes_per_row` 由 schema 算出）：

| 数据形状 | bytes/row | 按默认值算出的在飞内存 |
|---|---|---|
| `int64` + `list<float32, 4>` | 24 | 0.06 GiB |
| `int64` + `list<float32, 1536>` | 6,152 | **15.02 GiB** |
| `int64` + `list<float32, 3072>` | 12,296 | **30.02 GiB** |

**这就是那个炸弹。** 一行 1536 维的 `float32` 向量是 6 KB，
乘上 131072 行的批、再乘 20 的预读深度，就是 15 GiB——
注意这还只是**一个扫描批次链**的在飞量，而客户端通常还要
再留一份给要写入的批次。1536 维是 OpenAI `text-embedding-3-small`
的维度，3072 是 `text-embedding-3-large` 的——也就是说，
**这个坑正好落在最主流的两个嵌入模型上**。

而且它爆得很突然：数据量从 10 万行涨到 100 万行，在飞内存**不变**
（batch_size 和预读深度都是常数，和总行数无关）。
所以它不会"慢慢变紧"，而是在某个维度上直接越线——
小规模测试永远测不出来，上线才炸。

（口径说明：上表三行是用 0.40.0 里的 `_estimate_bytes_per_row`
和 `_bounded_scanner_kwargs` **实际调用**得到的，不是照公式手算；
但它是**估算**，不是进程实际驻留内存的测量。真实峰值还受
parquet 压缩率、Arrow 缓冲区的分配粒度、以及 Python 侧对象的影响。）

## H.6 有界扫描器：怎么在有上限的前提下不牺牲窄表

看出问题之后，修法是显然的：把批次和预读都调小。但**不能无条件调小**——
窄行数据用 pyarrow 的默认值是能跑满带宽的，一刀切地把
batch_size 压到几千行会让所有普通表格的吞吐掉下来。

0.40.0 的做法是先算一笔账，只在**真的会超**的时候才动手：

```
默认在飞量 = bytes_per_row × 131072 × (16 + 4)
如果 默认在飞量 <= 1 GiB:   什么都不改（返回 {}）
否则:                       batch_size = clamp(16 MiB / bytes_per_row, 512, 131072)
                            batch_readahead = 2
                            fragment_readahead = 1
```

三个常量分别是 `_SCAN_MEMORY_BUDGET_BYTES = 1 GiB`、
`_TARGET_BATCH_BYTES = 16 MiB`、`_MIN_BATCH_ROWS = 512`。
用上一节那两个形状跑一遍，实际返回的是：

```
1536 维 -> {'batch_size': 2727,  'batch_readahead': 2, 'fragment_readahead': 1}
3072 维 -> {'batch_size': 1364,  'batch_readahead': 2, 'fragment_readahead': 1}
窄行     -> {}          ← 默认值原样保留
```

**三个设计决定值得单独拎出来，因为它们都不是唯一解：**

**第一，预读深度必须跟着降，不能只降 batch_size。**
源码注释把理由写得很直白：pyarrow 一次读一整个 parquet row group，
并保留 `batch_readahead` 个在内存里，所以**对宽行数据，
预读深度（而不是批次大小）主导峰值内存**。
只把 batch_size 调小、留着 16 的预读，每批是小了，
但一次驻留 16 个 row-group 大小的缓冲，峰值照样下不来。
这是"改了一个参数以为解决了，其实没碰到主要矛盾"的典型。

**第二，阈值是"要不要动手"的判据，不是"目标值"。**
判据用的是 `默认在飞量 <= 1 GiB` 这条线，而不是
`bytes_per_row <= 某个值`。区别在于前者把 pyarrow 的默认值
（131072 / 16 / 4）写进了判据里——如果哪天 pyarrow 改了默认值，
这条判据会跟着变，而不会变成一个悄悄过期的魔法数。

**第三，`_MIN_BATCH_ROWS = 512` 是个兜底。**
16 MiB ÷ bytes_per_row 对极宽的行会算出很小的数（比如
每行 1 MB 时算出 16 行），512 保证批次不会小到每次
调度开销都盖过有效工作。所以这个 clamp 是**双向**的。

## H.7 本实现的摄入：为什么它选择"全部物化"

讲完真实库的做法，该说本实现了——因为这里的取舍正好相反，
而且**是个刻意的反面教材**。

`mini_lancedb/table.py` 里有一个函数 `_rows_from_data()`，
它把所有输入统一成 `list[dict]`，而且**明确拒绝生成器**。
它的文档串把理由写得很清楚，和 H.2 那两遍写入是同一条：

```
LanceDB 要求 list/tuple/Arrow 表/DataFrame，因为写入需要两遍数据
（一遍推断 schema，一遍落盘），而生成器只能消费一次。
```

和真实库的两个差别，值得并排看：

**差别一：真实库接受一次性源（标成 `rescannable=False`），
本实现直接拒绝。** 真实库的取舍是"能跑，但功能打折"；
本实现是"跑不了，但报错清楚"。哪一个更好取决于场景：
如果你在写一个长期跑的摄入服务，**拒绝**更好（问题在开发期暴露）；
如果你在写一个从流里读数据的管道，**接受**更好（否则你得自己缓冲）。

**差别二：真实库在摄入时**流式**处理批次，本实现把整份数据物化。**
`_rows_from_data` 对 Arrow 表调 `to_pylist()`、对 DataFrame 调
`to_dict("records")`——都是"整份转成 Python 对象"。
这不是免费的，实测膨胀很明显：

```
1000 行 × 1536 维 float32
  Arrow 表                nbytes =     6,152,000      6,152 字节/行
  展开成 list[dict]：
      外层 list                     8,856
      dict × 1000                 184,000
      list 对象（含指针数组）     12,728,000
      float 对象                 36,864,000
      合计                       49,784,856     49,785 字节/行
  膨胀倍数                                 8.09x
```

**8 倍。** 原因很朴素：Arrow 里 1536 个 `float32` 是连续的 6144 字节；
展开成 Python 之后，每个浮点变成一个 24 字节的对象
（`float` 是完整的对象，不是 4 字节），再加列表里一个 8 字节的指针，
**一个 float32 变成 32 字节**——光是这两项就是 1536 × 32 = 49,152 字节，
再加上每行的 dict 和列表对象本身。这和第 5 章那条
"向量列不是特殊类型，就是 `fixed_size_list<float32>[N]`"
连起来看，结论就很硬：**物化的代价正比于向量维度**。
同样 100 万行，Arrow 里是 6 GB，展开成 Python 是 49 GB。

**这个数字我改过一次，改的原因比数字本身有用。** 原来写的是
**6.02x / 37,048 字节/行**，算法是
`Σ getsizeof(dict) + Σ getsizeof(float)`——**漏掉了每行那个 list
对象本身**（也就是装着指针的数组，1000 行共 12.7 MB）。
写的时候自己完全没觉得漏：`sys.getsizeof` 一项一项都调了，
看起来"逐层累加"了。但这正是 `getsizeof` 这类逐项求和最容易漏的一层——
**容器和它装的东西是两个对象，只数了后者就少了一整份指针数组**。
所以上面这张表把每一层单独列出来（外层 list / dict / list 对象 / float），
让"漏了哪一层"变成肉眼可见的事，而不是藏在一个合计里。

（口径：`sys.getsizeof` 逐层累加，是估算。dict 的键是共享的字符串对象、
没有重复计入，所以这个数偏保守；`id` 列那个 int 对象也没算进去。
它回答的是"小几个百分点"的问题，不影响"8 倍还是 6 倍"这个量级结论。）

所以本实现不能用来灌真正大的嵌入表，这是设计取舍，不是 bug。

**这一节和第 24 章 §24.5 是同一件事的两个位置。** §24.5 从"调参"进去，
已经给出了正确的经验做法（"按一行数据多大反推批量"）；
这一节从"内存"进去，补的是它**之前**的那一步——
那句经验做法里的"一行数据多大"，在本实现里并不只是数据文件里的大小，
还要乘上这个 8 倍。**同一个建议在两处的数值会差 8 倍**，
因为一边算的是落盘成本，一边算的是过程中必须先扛住的那份内存。

## H.8 一次摄入的内存预算怎么算

把前面几节合起来，可以得到一个可以直接抄的估算式。
摄入过程中同时在内存里的东西有三份：

```
① 读侧在飞量   = bytes_per_row × batch_size × (batch_readahead + fragment_readahead)
② 物化后的批次 = bytes_per_row × batch_size × 膨胀倍数（本实现约 8x，真实库不物化）
③ 编码缓冲区   = 每列一个，量级是 ② 里那一列的宽度
```

三个可以直接用的结论：

**先算 `bytes_per_row`，再决定批次大小。** 它是 `4 × 向量维度`
加上标量列的宽度。768 维的模型每行 3 KB，1536 维 6 KB，3072 维 12 KB——
**差一个数量级就在选模型上**。同一个批次大小在 384 维上很舒服，
在 3072 维上就是 8 倍的内存。

**批次大小要按字节定，不要按行数定。** "每批 10 万行"这个说法
在窄表和宽表上的内存差几百倍。真实库的做法就是按字节反推行数
（`_TARGET_BATCH_BYTES = 16 MiB`），这是可以直接借的：
`batch_rows = 16 MiB / bytes_per_row`。

**别在小数据上验证内存行为。** H.5 说过，在飞内存和总行数无关，
所以"我拿 1 万行跑通了"完全不能说明 100 万行能跑通。
要验证就得**用真实维度**跑——行数可以少，维度不能假。

## H.9 一次提交的边界

最后收一下口：从数据源到"数据可见"，中间有几步是**分界点**，
搞清它们才知道失败之后该从哪重来。

**第一步是 schema 定下来。** 这一步之后就进入"两遍写入"的约束了——
源不能再变，否则第二遍读到的和第一遍推断的对不上。
本实现把这一步做得更早更严：`_rows_from_data` 直接物化，
所以"源变了"这类问题在它这里不可能发生，代价是内存。

**第二步是批次写下去。** 这一步产出的是**孤儿文件**——
数据文件已经写到对象存储上了，但还没有任何 manifest 引用它。
第 23 章 §23.5 讲的孤儿文件、以及第 8 章 §8.7 讲的半提交产物，
都是这一步的产物。**失败在这里是可以安全重来的**：
重来一次会写出新的文件，旧的那些等着被 GC。

**第三步是提交 manifest。** 这才是"可见"的那一刻，前面 H.2 到 H.8
讲的所有东西，都是为了把数据**准备好**交到这一步手上。
它是一次条件写（第 8 章），失败就整个回滚——
**没有"提交了一半"这种状态**，这是整个设计里最值得记住的一条不变量。

所以"摄入失败了该怎么办"的答案是可以分层的：
schema 阶段失败 → 改输入重来，什么也没留下；
写批次阶段失败 → 直接重来，代价是几个孤儿文件；
提交阶段失败 → 重试提交，数据文件可以复用。
第 25 章 §25.8.9 那份"损坏与半提交的处置手册"就是这个分层
在生产语境下的版本。

## H.10 小结

**这条链上最容易被忽略的不是算法，是契约。** 两遍写入、
`Scannable` 的四个字段、`rescannable` 那个布尔值——
它们决定了"什么样的数据源能用"，而这一类失败在开发期
往往表现为一句离根因很远的报错（H.2 那句
`Cannot create or add rows from a single dictionary` 就是标本）。

**内存问题在宽行数据上是结构性的，而且不会随数据量慢慢恶化。**
1536 维向量在 pyarrow 默认参数下的在飞内存是 15 GiB，
这个数字和总行数无关——所以它只能靠**算**发现，不能靠小规模测试发现。
真实库的应对是一个"先算账再动手"的有界扫描器：
默认值够用就什么都不改，不够用才按 16 MiB 一批、
预读降到 2/1 重新定价。

**本实现在这一层是刻意简化的。** 它拒绝生成器、把一切物化成
`list[dict]`、膨胀约 8 倍。这是对的取舍——它换来的是
"输入形状的规则只有一条，而且报错和真实库逐字一致"。
但**不能拿它去灌真正大的嵌入表**，这是设计边界，不是待修的 bug。

**最后一层认识是：摄入的所有准备，都是为了一次条件写。**
在那之前失败都可以安全重来；那一次成功之后，数据就永久可见了。
中间的边界干净，是这套存储设计最被低估的优点。
