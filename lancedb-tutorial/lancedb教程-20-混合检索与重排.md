# 第 20 章　混合检索与重排

到这里为止，我们手上有两条独立的检索路径。

向量检索把文本压成一个稠密向量，用 ANN 找"语义相近"的行。全文检索
把文本切成词项，用 BM25 找"字面命中"的行。两条路的失败方式**几乎不重叠**，
这就是混合检索存在的全部理由。

这一章讲三件事：为什么两路一起用更好、把两路拼起来的时候最容易错在
哪里、以及四种融合/重排手段各自适合什么场景。

## 20.1 两条路的盲区是互补的

先说一个具体的失败。

假设库里有一篇文档的正文是 `GPT-4o-mini 的价格是每百万 token 0.15 美元`。
用户搜 `GPT-4o-mini`。向量模型在训练时见过的语料里，`GPT-4o-mini` 出现的
次数远少于 `GPT-4`；很多 tokenizer 会把它切成 `GPT`、`-`、`4`、`o`、
`-`、`mini` 这一段子词序列，而 `mini` 这个片段在语料里大量出现在
"迷你"、"小"这类无关语境中。结果是：**这个查询词的向量方向被"mini
里的通用语义"和"GPT-4 系列"两个方向同时拉扯**，模型很可能把它当成一个
普通的短词，召回一堆泛泛谈论大模型的文档，而真正那篇写着价格的文档
排在第 8 位。

反过来看全文检索。用户搜 `为什么向量检索在长文档上效果会变差`，
其中真正承载意图的词是"长文档"和"变差"，但 BM25 一视同仁地要求所有
词项都出现。库里那篇标题是 `长文本下的召回率下降原因分析` 的文档，
一个字都没命中查询里的"长文档""变差"，BM25 给它 0 分。**BM25 完全
不认识"长文本"和"长文档"是同一个意思。**

把这两段话放在一起，规律就很清楚了：

向量检索擅长的是"意图相近但用词完全不同"，不擅长的是"专有名词、
编号、代码符号、人名地名、型号"。后者的共同点是**它们几乎不携带
语义，它们的身份就是它的字面**。BM25 恰好相反：它只认字面，
对同义词、改写、跨语言一概无感。

真实系统里这个互补性非常重要，因为"专有名词"这类查询在 RAG 里
占比很高——用户搜的经常是产品名、错误码、函数名、配置项名。

## 20.2 方向问题必须先解决

在动手融合之前，有一件事必须先说清楚，因为它是这个领域里最容易写错、
而且**写错了不会报错**的地方。

两路返回的分数列，名字和方向都不一样：

向量路返回 `_distance`，**越小越好**。cosine 距离落在 `[0, 2]`；
l2 是平方距离、上不封顶；内积是取负的内积、可以是任意实数。
全文路返回 `_score`，**越大越好**。BM25 是无界的正数，典型值 0~30。

把这两列数字直接加权相加，等于在一个坐标系里把"米"和"摄氏度"相加。
我们实测过这种写法有多离谱：

```python
# 把 _distance 和 _score 直接相加
naive = sorted(merged.items(), key=lambda kv: -(kv[1]["_score"] - kv[1]["_distance"]))
# [(3, 6.87), (1, 4.99), (4, 0.14), (2, -0.01)]
```

`rowid=4` 在向量路排第 4（`_distance=0.88`，很难看）、在 FTS 路排第 3
（`_score=1.02`，也很低），但它靠"距离小"这个被误当成"分数高"的东西
被抬到了第三位。整个排序是静默错的：不报错、不报警，只是把最不相关的
结果排到前面去。

所以融合的**第一步永远是统一方向**，第二步才是排序或加权。
这在 `mini_lancedb/rerank/base.py` 里被写成了一个常量表
`SCORE_SCALES`，三种分数列的方向都钉在代码里：

```python
SCORE_SCALES = {
    DISTANCE_COL:  {"higher_is_better": False, ...},   # _distance
    SCORE_COL:     {"higher_is_better": True,  ...},   # _score
    RELEVANCE_COL: {"higher_is_better": True,  ...},   # _relevance_score
}
```

### `_relevance_score` 是输出列，不是 `return_score` 的取值

这里有一个很常见的混淆，必须掰开说。

`_relevance_score` 是**重排器写出来的那一列**——融合之后的统一分数，
方向永远是"越大越相关"。不同重排器给它的量纲完全不同：

**RRF 落在 `(0, m/(1+k)]`**，`m` 是参与融合的路数。两路、默认权重各 1
时上限是 `2/61 ≈ 0.0328`。这也是本节的实测输出里出现过 `0.032787`
的原因——它超过了 `1/60`，所以"上限是 `1/k`"这个常见说法是错的：
每多一路就多一项，上限跟着路数走。

cross encoder 落在 `(0, 1)`，线性加权落在 `[0, 1]`。
**它们的唯一共同契约就是方向一致。**

它**不是** `return_score` 参数的取值。真实 LanceDB 里 `return_score`
只接受两个字符串：`"relevance"` 和 `"all"`。传别的会报错，
**但两边的报错长得不一样**——这是个典型的"同一件事、两套错误文本"：

```python
# 真实 lancedb 0.40.0
>>> RRFReranker(return_score="score")
ValueError: score must be either 'relevance' or 'all'

# 本教程的迷你实现
>>> RRFReranker(return_score="score")
QueryError: return_score 只能是 'relevance' 或 'all'
  (hint="'relevance' 只留 _relevance_score；'all' 还保留 _distance / _score 便于调试",
   value='score')
```

异常类型不同（`ValueError` vs `QueryError`），文案也不同。
**所以想写"捕获这个错误"的代码时，别按类型捕**——
按类型捕的代码在换实现之后会静默失效。

`"relevance"` 是默认值，输出里只有 `_relevance_score`（原始分数被丢掉）。
`"all"` 会把两路的原始分数也保留下来，方便调试。它长这样：

```
rowid=1 _relevance_score=0.032522  _distance=... _score=...
rowid=3 _relevance_score=0.032266  _distance=... _score=...
rowid=2 _relevance_score=0.031754  _distance=... _score=...
```

注意 `rowid=1` 和 `rowid=3` 的最终分数几乎相等，但它们在两路里的名次
完全相反（一个向量路第 1、FTS 路第 2；另一个反过来）。这正是融合器
该做的事：**把两路互相矛盾的证据折中**，而不是让任何一路单独说了算。

关于 `_distance` 和 `_score` 的具体数值，这里特意留了省略号：
它们取决于你用哪份数据和哪个查询向量，而 `_relevance_score` 只取决于
名次——**前者不可复现、后者可复现**，把两者并排写成一组具体数字，
会让人误以为前者也是固定的。

真实 LanceDB 走混合检索时，不指定重排器也能跑，它默认用 RRF：

```python
t = db.create_table("h", data=data)
t.create_index("text", config=FTS(), replace=True)

r = (t.search(query_type="hybrid")
      .vector(query_vec)
      .text("GPT-4o-mini 价格")
      .rerank(RRFReranker())          # 不写这一行也走 RRF
      .limit(3)
      .to_list())
# [(3, 0.03252247), (5, 0.03226646), (1, 0.01612903)]
# 返回列: ['_relevance_score', 'id', 'text', 'vector']
```

两个细节值得记住。第一，`_relevance_score` 的列名和真实 API 一致，
所以调试时看到它就知道"这一步是重排器给的"。第二，返回列里**没有**
`_distance` 也没有 `_score`——因为 `return_score` 默认是 `"relevance"`。
想看原始分数就显式传 `return_score="all"`。

## 20.3 RRF：只用名次，对分数尺度免疫

RRF（Reciprocal Rank Fusion，倒数名次融合）的公式只有一行：

```
score(d) = Σ_i  weight_i / (rank_i(d) + k)
```

`rank_i(d)` 是文档 d 在第 i 路结果里的**名次，从 1 开始**。某一路没有
召回 d，则这一项整体不出现。`k` 是平滑常数。

`k=60` 这个默认值来自原始论文（Cormack、Clarke、Büttcher，SIGIR 2009
的 *Reciprocal Rank Fusion outperforms Condorcet and individual Rank
Learning Methods*），论文里是通过实验选出的值。真实 LanceDB 的默认值
也是 60，签名是 `RRFReranker(K=60, return_score='relevance')`——
注意参数名是大写 `K`。我们的实现主参数叫 `k`，同时保留 `K` 作为
构造别名，所以官方文档里的写法可以原样搬过来。

### 为什么它对分数尺度免疫

RRF 只读**名次**，不读分数本身。所以：向量路返回的是 `_distance`
还是 `_score`、量纲是 `[0,2]` 还是 `[0, 30000]`、方向是越大越好还是
越小越好——统统无所谓。只要每路各自按自己的标准排好序就行。

这在工程上非常值钱。混合检索最难维护的部分就是"两路分数的相对尺度"：
换一批语料之后 BM25 的整体分布会平移，向量模型的余弦相似度分布
也会随模型换代而改变。RRF 直接把这个自由度删掉了——**它是这个领域里
唯一不需要调参就能上线的融合方法**。

### 手算对照

拿 5 篇文档、两路召回做例子。向量路顺序是 `[1,2,3,4,5]`（`_distance`
升序），FTS 路顺序是 `[3,1,4,2,5]`（`_score` 降序）。k=60、两路权重
都是 1 时，手算：

```
d1: vec 第 1 名, fts 第 2 名 → 1/61 + 1/62 = 0.0163934426 + 0.0161290323 = 0.0325224749
d3: vec 第 3 名, fts 第 1 名 → 1/63 + 1/61 = 0.0158730159 + 0.0163934426 = 0.0322664585
d2: vec 第 2 名, fts 第 4 名 → 1/62 + 1/64 = 0.0161290323 + 0.0156250000 = 0.0317540323
```

用 `mini_lancedb/rerank/rrf.py` 跑出来：

```python
>>> RRFReranker(k=60).rerank_hybrid(None, vec, fts)
rowid=1  rel=0.03252247488101534
rowid=3  rel=0.03226645849596670
rowid=2  rel=0.03175403225806452
rowid=4  rel=0.03149801587301587
rowid=5  rel=0.03076923076923077
```

五篇文档、五行输出，手算的五个值**逐位对上**（`tests/test_rerank.py`
里的 `RRF_EXPECTED_ORDER = [1, 3, 2, 4, 5]` 钉的就是这个顺序）。

**这一节的每一个数字都能一条命令跑出来**：

```
python -X utf8 examples/verify/ch20_hybrid_rerank.py
```

这个脚本是后补的，原因值得记一句：本章原先没有任何可运行脚本，
上面那张表是手写在正文里的，其中一处顺序印错、还多出一行不存在的
`rowid=6`，和同一页的手算直接打架——**没有脚本钉着的"实测输出"
会漂，而漂了没人发现**。脚本里同时断言了顺序和五个分数，
以后再改公式，它会先报警。

**"被两路同时召回"在 RRF 里是一个很强的信号**，这是它比"只看一路"
更鲁棒的原因：`d1` 在向量路第 1、FTS 路第 2，两项加起来最高；
而如果某篇文档只在单路出现（比如 FTS 第 1 但向量路没进前列），
它就只能拿到一项，很难挤进 top。

### k 到底影响什么

`k` 越小越"独裁"（前几名通吃），`k` 越大越"平均"（名次间的差距被抹平）。
我们的测试语料里把 k 从 1 调到 10000，顺序居然完全没变：

```
k=1      order=[1, 3, 2, 4, 5]  top=0.83333333
k=60     order=[1, 3, 2, 4, 5]  top=0.03252247
k=10000  order=[1, 3, 2, 4, 5]  top=0.00019997
```

这容易让人误以为 k 不重要。**k 只在两路分歧很大时才起作用。**
构造一个这样的例子：文档 A 在向量路第 1 名、在 FTS 路第 50 名；
文档 B 在两路都是第 10 名。

```
k=1     A=0.519608 B=0.181818  -> A 胜
k=10    A=0.107576 B=0.100000  -> A 胜
k=60    A=0.025484 B=0.028571  -> B 胜
k=1000  A=0.001951 B=0.001980  -> B 胜
```

k=10 和 k=60 之间发生了一次反转。原因是：A 的分数被 `1/(50+k)` 这个
很靠后的名次拖着，k 一大，这个"深名次"的惩罚就相对变轻，而 B 那种
"两路都中游"的稳健性就占了上风。**所以 k 的物理含义是"名次深度有多
值钱"，不是"名次之间差多少"。** 经验上 60 附近不敏感，但把它调到 1
或调到 10000 的结果会明显不同。

### 失败模式

代价也很实在，有三条。

第一，**丢掉幅度信息**。名次第 1 和第 2 之间的差距**永远**是
`1/(1+k) - 1/(2+k)`，和"第 1 名遥遥领先"还是"第 1、2 名几乎
一样好"完全无关。一个查询只有一个明显正解时，RRF 会把一大堆平庸结果
拉到接近的分数。

第二，**两路质量差很多时它默认给同等权重**。如果向量路是从 1 亿条里
召回的，FTS 路只是在一张 500 行的附属表上查的，把它们当"民主投票"
显然不对。这正是 `weights` 参数的用处：

```python
>>> RRFReranker(k=60, weights=[1.0, 2.0]).rerank_hybrid("q", vec, fts)
[3, 1, 2, 4, 5]      # 对比等权重的 [1, 3, 2, 4, 5]
```

FTS 路权重翻倍之后，`rowid=3`（FTS 第 1 名）升到了第一位。
`weights` 的长度必须等于结果列表的个数，而且**空列表也占位**——
否则临时加一路召回就会让后面所有路的权重错位。

第三，**一个 0.99 和一个 0.51 的相似度被当成一样**。这是 RRF 最本质的
信息损失。什么时候这不可接受？当你的向量模型分数分布是"有明确头部"的
时候——比如一个经过精调的重排模型，0.99 意味着几乎确定而 0.51 意味着
只是碰巧，把两者等同会显著降质。这时候该用线性加权。

## 20.4 线性加权融合：保留幅度，代价是三个坑

线性加权的配方是三句话，顺序不能错：

```
rel(d) = weight * norm_vector(d) + (1 - weight) * norm_fts(d)
```

先**统一方向**（向量路的 `_distance` 取负翻成"越大越好"），再**归一化**
（两路原始分数没有可比性，归到同一个区间），最后**加权求和**。
`weight` 的含义是**给向量路的权重**：`weight=0` 等于只用 FTS，
`weight=1` 等于只用向量。真实 LanceDB 的默认值也是 0.7——
经验上向量召回负责"语义"、FTS 负责"精确词匹配"，前者通常更值得
信任一点。

### 三种归一化，各自踩什么坑

`minmax` 是 `(x - min) / (max - min)`。**它对异常值极其敏感。** 实测：

```
raw    : [0.1, 0.2, 0.3, 100.0]
minmax : [0.0, 0.001001, 0.002002, 1.0]
rank   : [0.0, 0.333333, 0.666667, 1.0]
```

前三个本来是有意义的 `[0.1, 0.2, 0.3]`，被一个 100 压成了
`[0.000, 0.001, 0.002]`——**它们的差距被压缩到几乎看不见**。
去掉那个离群值再看同一批数据：

```
raw: [0.1, 0.2, 0.3] -> minmax: [0.0, 0.5, 1.0]
```

完全是两个世界。反方向的问题同样严重：如果某一路召回**质量很差**、
分数分布很扁，min-max 又会把这点微小的差异**放大**成 0~1 的完整区间：

```
flat raw : [0.7001, 0.7002, 0.7003] -> minmax: [0.0, 0.5, 1.0]
```

三个几乎一样的分数被拉开了 100%。于是这一路在加权时拿到了远超它
应得的发言权。真实系统里 min-max 必须配合"取前 N 条"使用——
前 N 条里通常没有太离谱的离群点，而且分数分布也更接近。

`rank` 是名次归一化：第 1 名 1.0，第 N 名 0.0，中间线性。它**丢幅度
信息**（和 RRF 一样的病），但免疫离群值。它还有一个必须显式处理的细节：
**并列分数**。实测一批有并列的分数：

```
values   : [5.0, 5.0, 3.0, 3.0, 1.0]
平均名次 : [1.5, 1.5, 3.5, 3.5, 5.0]
rank 归一: [0.875, 0.875, 0.375, 0.375, 0.0]
```

两个 5.0 拿到完全相同的 0.875。如果不做平均名次处理，并列的两个值
会因为"谁先出现"被拆成名次 1 和 2、分数 1.0 和 0.75——那么排序结果的
差异完全由输入顺序决定，换个召回的返回顺序结果就变了。这在因果上
说不通，也让测试无法稳定复现。

`none` 是不归一化，直接拿统一方向之后的原始分数。

## 20.5 缺失分数怎么填

一篇文档经常只被一路召回。"另一路没有分数"这件事必须有个约定，
否则它就该被当成 0 分、还是被丢弃？实测各种 `fill` 策略的差别：

```
vec = [{1, _distance=0.1}, {2, _distance=0.5}]     # 只有 1、2
fts = [{2, _score=9.0},   {3, _score=1.0}]         # 只有 2、3
weight=0.5, normalize="minmax"

fill=0.0    {1: 0.5, 2: 0.5, 3: 0.0}
fill=0.5    {1: 0.75, 2: 0.5, 3: 0.25}
fill=1.0    {1: 1.0, 2: 0.5, 3: 0.5}
fill=mean   {1: 0.75, 2: 0.5, 3: 0.25}
fill=min    {1: 0.5, 2: 0.5, 3: 0.0}
fill=max    {1: 1.0, 2: 0.5, 3: 0.5}
```

注意 `rowid=2` 在**所有** `fill` 下都是 0.5——它两路都有分数，不受
填充策略影响。而只被向量路召回的 `rowid=1` 和只被 FTS 路召回的
`rowid=3` 分数随 `fill` 剧烈变化：`fill=0.0` 时它们是 0.5 和 0.0，
`fill=1.0` 时变成 1.0 和 0.5。

还有一个更隐蔽的地方：**缺失项不参与 min/max 统计量的估计**。
如果先把缺失项当成 0 塞进去再算 min-max，那么"这一路一条都没召回"
就会变成"召回了一堆 0 分"，两种情况的行为就一样了——而它们本该
不一样。我们的实现里 `_normalize_with_fill` 是先把有值的挑出来算
归一化、再回填缺失槽位的。

真实 LanceDB 的 `fill` 语义和我们这里**方向是反的**，这一点必须提醒。
它的签名是：

```python
LinearCombinationReranker(weight=0.7, fill=1.0, return_score='relevance')
```

`fill=1.0` 是在**距离空间**里填的惩罚值——距离越大越差，所以
"填 1.0"其实是"给一个很差的分数"。它自己的 docstring 里就写着：

```
fill : float, default 1.0
    The score to give to results that are only in one of the two result sets.
    This is treated as penalty, so a higher value means a lower score.
    TODO: We should just hardcode this--
    its pretty confusing as we invert scores to calculate final score
```

`TODO: ... its pretty confusing` 这句是官方源码里的原话。我们刻意
换成了"归一化之后的相关性空间"（`0.0` = 当作最不相关、`1.0` =
当作最相关），方向统一，不用每次心算。

顺带说明一个版本差异：真实 0.40.0 的 `LinearCombinationReranker`
**没有** `normalize` 参数（它内部把分数按 `1 - d` 之类的固定方式翻转）。
我们的实现多了 `normalize="minmax"|"rank"|"none"` 这个旋钮，是为了
把这三种归一化的失败模式都做成可实测的。用真实 API 时不要传它。

## 20.6 Cross-encoder 重排：必须放在最后一步

双塔（bi-encoder）检索的架构决定了 query 和 doc **从来没有见过面**：
两边各自编码成一个向量，相似度靠点积算。这带来一个不可修复的损失——
编码器必须把"这个 doc 可能被问到的所有问题"都压进一个固定长度的
向量里。

cross encoder 把 `[query, doc]` 拼成一个序列送进 Transformer，
**每一层都能做 query token 和 doc token 之间的注意力**。所以它对
"否定、比较、数量关系、长问句"这类需要细粒度对齐的查询明显更好。

代价是复杂度。双塔的文档向量**离线算一次**，查询时只编码查询再做
ANN——1 亿篇文档的在线成本是一次编码加一次 ANN 搜索。cross encoder
的分数**不能预先算**（它依赖 query），每次查询要对每个候选做**一次
完整的 Transformer 前向**，N 个候选就是 O(N) 次前向。

所以工程上的标准做法是**两阶段**。真实的检索系统一般有四层：

```
召回（recall）   →  粗排（coarse）  →  精排（fine）  →  业务规则
10^7 → 10^4          10^4 → 10^3        10^3 → 10^2       最终 10
ANN + FTS            RRF / 线性加权     cross encoder     去重/打散/置顶
```

cross encoder 只能在第三层。**永远不要对整个库跑 cross encoder**——
那不是"更准"，那是把检索系统降级成在线推理服务。100 条 × 20ms ≈ 2s
在 CPU 上已经很勉强，所以真实部署要么把候选卡在 20~50 条，
要么上 GPU 批处理。

真实 LanceDB 的签名和默认模型：

```python
CrossEncoderReranker(
    model_name='cross-encoder/ms-marco-TinyBERT-L-6',
    column='text', device=None, return_score='relevance',
    trust_remote_code=True, batch_size=32, **kwargs)
```

默认的 `cross-encoder/ms-marco-TinyBERT-L-6` 只有 6 层，是最快也最
一般的那个。生产上更常用 `cross-encoder/ms-marco-MiniLM-L-6-v2`
（质量/速度最平衡）或 `BAAI/bge-reranker-base`（中英文）。

### 离线可测的做法

真模型要下载权重、要 GPU，测试里跑不了。所以我们的实现里有一个
`HashCrossEncoder`：一个确定性的、可解释的玩具打分器，用 7 个显式
特征（token 重叠、IDF 加权重叠、查询覆盖率、首个命中位置、bigram
重叠、长度比、精确子串）加一个固定随机投影，凑出一个"像个真模型"
的分数分布。它**绝对不能当质量基准**，只用来验证管道。

跑真实候选（**下面用的 `CrossEncoderReranker` 是本教程实现的用法，
不是真实库的**：它的第一个位置参数是 `model=`，一个带 `predict(pairs)`
的对象；真实库里第一个参数是 `model_name=`，一个 HF 模型名字符串，
见上面的签名。本实现额外接受 `model_name=` 作为别名，但**给模型对象时
只能走位置参数或 `model=`**，所以这一行不能原样搬进真实库）：

```python
ce = CrossEncoderReranker(HashCrossEncoder(), top_k=3)
ce.rerank_vector("GPT-4o-mini 价格", cands)
# rowid=1 rel=0.7223695516586304   「GPT-4o-mini 的价格是每百万 token 0.15 美元」
# rowid=3 rel=0.42648500204086304  「GPT-4o 与 GPT-4o-mini 在上下文长度上的区别」
# rowid=2 rel=0.18147429823875427  「大模型 API 定价对比：各家价格一览」
# rowid=4 rel=None                 「今天天气不错」
```

有一个行为要特别注意：**被 `top_k` 截断掉的行不丢，它们的分数是
`None`，排在所有有分数的行之后。**

```
行数: 7  分数: [0.6865053772926331, 0.6467972993850708, 0.6404398679733276, None, None, None, None]
```

这样设计是为了让"重排没有把任何一条候选弄丢"这件事在结果里**可验证**。
如果截断了就默默扔掉，你就无法区分"模型认为它不相关"和"它根本没被
送进模型"。

### query 和 doc 的顺序在截断之前

还有一个容易错的工程细节：`rerank_hybrid` 里是"先合并两路（向量在前、
去重），再走单列表重排"。cross encoder **不看召回分数**，所以合并的
方式对结果没有影响——但"谁进得了前 `top_k`"有影响。这就是为什么
top-k 截断要在合并之后做，而不是在两路各自做一遍。

## 20.7 ColBERT 式晚交互：从"两路分数怎么合"到"一行多个向量"

混合检索解决了"用哪种方式打分"的问题，但没有解决"给什么打分"的问题。
前面所有方法——RRF、线性加权、cross encoder——面对的都是**同一批候选、
同一段文本**：一路召回返回的每一行是一整篇文档，重排器给这一整篇文档
打一个分。

把任何一路往前推一步，都会撞上同一个天花板：**候选的粒度是"一条记录"，
而这个粒度可能是错的。** 2000 字的文档里真正回答问题的也许只是其中一段，
剩下 1900 字在打分时不是"没有贡献"，而是在**稀释**——cross encoder
虽然能看到 `[query, doc]` 的全部 token，它的输出仍然被压成一个分数。
把候选切成段落能解决一半（切分策略见第 25.1.2 节），代价是段落脱离
了上下文，而且文档级和段落级往往要维护两套索引。

ColBERT（Khattab & Zaharia, 2020）给的是另一条路：**别压**。
文档不再用一个向量表示，而是**每个 token 各留一个向量**；
查询也切成一串 token 向量；两者用 late interaction 打分，
也就是"每个查询 token 在文档的所有 token 里找到最像它的那一个，
把这些最大值加起来"。这个打分方式的好处是可以证明的：
它同时给出了**局部对齐**（哪个查询词落在文档的哪一段）和
**漏词惩罚**（查询里的词找不到归宿就不贡献分数），
而这正是单向量表示丢掉的两种信息。

它最值钱的性质在于"**先算相似度、后求和**"——交互发生在双方编码之后，
所以文档侧的 token 向量可以离线算、可以建索引，查询时只需要编码查询。
cross encoder 没有这个性质（20.6 节讲过：它的分数依赖 query，
每次查询都要对每个候选做一次完整前向），多向量有。

代价是存储：**一行不再是一个向量，而是一个矩阵**。这一个事实带来三个
连锁后果，每一个都会改变系统的形状——类型系统要多一层嵌套定长列表、
存储代价按段落的 token 数成倍增长、索引目前只支持 cosine。
所以晚交互不是一个更好的重排器，它是**一条新的检索路径**：
从 schema、索引、查询入口到磁盘布局都和单向量那条不一样。

第 21 章接着讲这一层：MaxSim 的手算、它到底贵多少倍、
"一行多个向量"在 Lance 里怎么存、以及把这个思路推到图像和音频上
会发生什么。

## 20.8 一个完整的混合检索例子

把前面的零件全部串起来。用一个真实的 `mini_lancedb` 数据集：
6 篇文档、64 维哈希向量、真建一个 FTS 倒排索引（BM25）和一个 FLAT
向量索引（cosine），分别查、再融合。

```python
from mini_lancedb.index.base import IndexMetadata
from mini_lancedb.index.inverted import InvertedIndex
from mini_lancedb.index.flat import FlatIndex
from mini_lancedb.rerank import RRFReranker, LinearCombinationReranker

fsi = InvertedIndex.build(batch.column("text"), row_ids,
        metadata=IndexMetadata(name="text_idx", index_type="FTS", columns=["text"]))
vidx = FlatIndex.build(batch.to_numpy("vector"), row_ids,
        metadata=IndexMetadata(name="vector_idx", index_type="FLAT", columns=["vector"],
                               params={"distance_type": "cosine"}))

q_text = "GPT-4o-mini 价格"
q_vec = emb.query_vector(q_text)

hits, scores = fsi.search_ranked(q_text, k=6)      # (行号, _score)，_score 降序
res = vidx.search(q_vec[None, :], 6)               # (distances, row_ids)，_distance 升序
```

两路的原始输出：

```
FTS 路 (BM25 _score 越大越好):
  rowid=0  _score= 4.1011  GPT-4o-mini 的价格是每百万 token 0.15 美元
  rowid=2  _score= 3.4055  GPT-4o 与 GPT-4o-mini 的上下文长度区别

向量路 (_distance 越小越好):
  rowid=0  _distance= 0.4226  GPT-4o-mini 的价格是每百万 token 0.15 美元
  rowid=2  _distance= 0.5292  GPT-4o 与 GPT-4o-mini 的上下文长度区别
  rowid=4  _distance= 0.8753  用 mini 模型做本地推理的成本测算
  rowid=1  _distance= 1.0000  大语言模型 API 定价横向对比
  rowid=3  _distance= 1.0000  向量数据库的索引结构入门
  rowid=5  _distance= 1.0000  如何选择合适的嵌入模型
```

FTS 只有 2 行召回（BM25 要求词项命中，只有含"价格"或"GPT-4o-mini"
的文档有分），而向量路有 6 行——注意后四行的 `_distance` 全是 1.0000，
这是哈希向量对"没有共享词"的文档给出的**完全无区分度**的距离。
这就是 20.1 节说的"向量检索在专有名词上失效"的具体形态。

融合结果：

```
=== RRF(k=60) 融合 ===
  1. rowid=0 rel=0.032787  GPT-4o-mini 的价格是每百万 token 0.15 美元
  2. rowid=2 rel=0.032258  GPT-4o 与 GPT-4o-mini 的上下文长度区别
  3. rowid=4 rel=0.015873  用 mini 模型做本地推理的成本测算
  4. rowid=1 rel=0.015625  大语言模型 API 定价横向对比
  5. rowid=3 rel=0.015385  向量数据库的索引结构入门
  6. rowid=5 rel=0.015152  如何选择合适的嵌入模型

=== 线性(minmax, weight=0.7) 融合 ===
  1. rowid=0 rel=1.000000  GPT-4o-mini 的价格是每百万 token 0.15 美元
  2. rowid=2 rel=0.570804  GPT-4o 与 GPT-4o-mini 的上下文长度区别
  3. rowid=4 rel=0.151161  用 mini 模型做本地推理的成本测算
  4. rowid=1 rel=0.000000  大语言模型 API 定价横向对比
  5. rowid=3 rel=0.000000  向量数据库的索引结构入门
  6. rowid=5 rel=0.000000  如何选择合适的嵌入模型
```

两种融合给出的**顺序完全一样**，但分数的形态很不一样。RRF 的分数
挤在 `[0.015, 0.033]` 这个很窄的区间里（第 3 名到第 6 名只差
0.0007），线性加权的分数铺满 `[0, 1]`。这个差别在"要不要再卡一个
阈值"的时候就很关键：RRF 的绝对分数没有阈值语义，线性加权的有。

还有一处值得注意：`rowid=0` 在线性融合里拿到 1.000000。
这是 min-max 归一化把"两路各自的第一名"都归到 1.0 的结果——
它出现在两路的头部，于是 `0.7 × 1.0 + 0.3 × 1.0 = 1.0`。
反过来说，`rowid=1/3/5` 拿到 0.000000 是因为它们只在向量路有分
（`_distance=1.0000` 被 min-max 归到 0.0），FTS 路又没召回它们
（按 `fill=0.0` 补 0），于是总分是 0。**这三个 0 分是"数据里确实
没有区分度"，不是"相关度为零"。**

## 20.9 四种方法怎么选，以及融合前后的参数

前面把 RRF、线性加权、cross encoder 分别讲了一遍，但"该选哪个"这件事
一直散在各节里。这一节把它收拢，顺便补上三个只在 API 里出现、
正文从没定义过的名字。

### 四种方法横向比较

**RRF（名次倒数融合）。** 全部输入是"每一路的名次"。`1/(k+rank)` 求和，
默认 `K=60`。它不需要任何前提条件——两路分数不可比、量纲差几个数量级、
方向相反，都无所谓（20.3 节）。代价是丢掉幅度信息。

**线性加权。** 把两路统一方向、归一化之后按 `weight` 加权求和。
它需要两个前提：你**相信**两路的分数幅度有含义，而且能接受归一化
引入的两种失真（min-max 会被离群值压扁或放大、rank 会丢幅度）。
好处是输出的分数**有阈值语义**——`[0, 1]` 铺满整个区间，
可以直接拿来卡一刀（20.4 节）。

**相对分数融合。** 它是前两者的中间地带：不做全局归一化，
只把每一路**除以该路自己的最高分**。这样既保留了"这一路内部第一名
比第二名强多少"（这是 RRF 丢掉的），又免疫了绝对量纲（这是
`normalize="none"` 做不到的）。它同时避开了 min-max 的两个坑——
除数只是一个点（最大值），不依赖整条分布，所以既不怕离群值把它压扁，
也不会把一堆几乎一样的分数拉开。本教程的重排器没有单独开这一档：
`normalize="none"` 再事先把两路缩放到同一量级，得到的就是它。

**MRR。** 真实 LanceDB 把它做成一个融合器：`MRRReranker(weight_vector=0.5,
weight_fts=0.5)`。它和 RRF 的结构性差别只有一条——**没有 k 这个平滑
常数**，每一项是 `1/rank` 而不是 `1/(k+rank)`（等价于 `k=0`）。
按 20.3 节对 k 的分析，k 越小越独裁，所以 MRR 的名次衰减更快、
头部更占主导，再叠加两个显式权重，它更像"带权重、且不给深名次留余地"
的 RRF。**注意名字有歧义**：检索评测里的 MRR 指的是"平均倒数排名"
这个指标，而这里是 LanceDB 给融合器起的名字，两个含义要分开读
（附录 B 的词条按指标那层含义收录）。

**该选哪个。** 默认选 RRF：路数在三路以上、分数尺度不可比、
不想调参——这三个条件里中任意一个，RRF 就是安全答案。当"分数的绝对值
有语义"（比如一个精调过的重排器的 0.99 和 0.51 意义完全不同）、
或者需要一个能卡阈值的最终分数时，换线性加权或相对分数融合。
当两路召回质量悬殊（一路从一亿条里召回、另一路只在几百行的附表上查）时，
用 MRR 或者给 RRF 传 `weights`，别让它们"民主投票"。
追求质量上限、且能接受 O(N) 次前向，就在所有方法之后再加一层
cross encoder——**它是加法，不是替代**。

**还有一档上面四种都没覆盖：托管重排 API。**
如果你的 cross encoder 想用现成的商业服务而不是自己跑模型，
LanceDB 的 `lancedb.rerankers` 里已经包好了一批：
`OpenaiReranker`、`CohereReranker`、`JinaReranker`、`VoyageAIReranker`、
`WatsonxReranker`、`AnswerdotaiRerankers`、`TypeSafeReranker`。
它们和上面四种的关系是**同一个位置的不同实现**——都是"拿到候选、
重新打分"这一步，区别只在于模型在谁的机器上跑。

用它们要付的代价和自建 cross encoder 不一样：**多一次网络往返、
一个外部依赖、一份要保管的凭证**。最后一条正好接上附录 G 讲密钥那一节——
云端重排器要的是 API key，而那个 key 不该写在代码里。

**注意类名的大小写**：`AnswerdotaiRerankers` 末尾**带 s**（因为那个库
本身叫 rerankers），而其余都叫 `...Reranker`。用小写 `s` 之外的写法
都会 `ImportError`。附录 A 的 A.6 有完整清单和核对命令。

### 融合前每路取多少候选

融合器只能对它拿到的候选排序。这句话有一个不显眼的后果：
**如果每一路只取 k 条，融合的输入池就只有 k 条（去重后更少）。**
一条在某一路排第 11 名、在另一路排第 1 名的候选，根本不会出现在
融合器面前——而"被两路同时认可"恰恰是融合最想要的那类结果。

所以工程上融合前每一路都要多取，这个倍数就是 `oversample_factor`：
每路取 `k × oversample_factor` 条，融合之后再截到 k（这是这一类参数
的标准形状——向量路的 `refine_factor` 也是这么算的）。

**但要说清楚两件事：这个参数在哪条路径上，以及本实现有没有它。**

它属于 **SQL 路径**（DuckDB 集成那边的 `hybrid_search`），
不在 Python 的 `LanceTable.search()` 这条链上——本机在
`lancedb 0.40.0` 的 Python 包里搜不到任何 `oversample` 相关的字段或常量。
所以如果你用的是 Python API，别指望能找到这个旋钮；
多取候选这件事在 Python 侧要自己写在调用层。

**本实现的 `_run_hybrid` 不做过度采样**：它给每一路都设成
`_limit = k`（`mini_lancedb/query.py`），两路各取 k 条就直接交给融合器。
也就是说，**上面那段"每一路只取 k 条会怎样"的警告，
正好描述的是本实现现在会发生的事**——一个在向量路排第 11、
在全文路排第 1 的候选，在这个实现里进不了融合池。
这不是一个"参数没调好"，是这条路径**缺了这一步**。
（代码里那行注释写的是"真实 LanceDB 也是各取 limit 个"，
这个说法我只在 SQL 路径的文档里见到过对应的倍数参数，
Python 侧没有证据支持，所以它至少是**未经确认**的。）
它的直觉分两层。**第一，它买的是跨路互补的召回率**：
一条只被某一路认可的结果，只有在那一路的候选池里才捞得出来；
池子太小，融合退化回"只用更强的那一路"。**第二，它的收益递减很快**：
两路各自多取的候选有大量重叠，多取到某个点之后新增的都是长尾噪音，
只会让融合器变慢并让最终名次更不稳定。经验上两路质量接近时取
2~4 就够；如果有一路明显较弱、但你希望它的头部结果也能进入融合池，
把它调大，或者直接给那一路更小的权重。

这里要区分一个容易混淆的相邻参数：`refine_factor`（第 12 章）
扩的是**向量路自己**的重排候选，`oversample_factor` 扩的是
**融合之前**每路的候选。两者都能提升最终召回，但作用点不同——
一个是"把这一路的距离算准"，另一个是"让这一路的候选有机会参与融合"。

### DuckDB 侧的三个名字

第 26.6 节的 DuckDB 集成里出现了三个参数，正文从没定义过，
在这里补齐（它们的默认值和语义来自官方 SQL 参考）：

**`_hybrid_score`。** 融合之后的分数列，越大越相关。它和 Python 侧的
`_relevance_score` 语义一致，**但列名不同**——这是两条路径之间最容易
接错的一根线：一份按 `_relevance_score` 写的下游代码，换成 SQL 路径
之后会安静地拿到一个不存在的列名。

**`alpha`。** 向量与全文的混合权重，默认 **0.5**，越大越偏向向量路。
注意它和 Python 侧 `LinearCombinationReranker(weight=0.7)` 的默认值不一样：
同样是"线性混合权重"，SQL 侧默认均等（0.5）、Python 侧默认偏向量（0.7）。
把两个路径的配置对齐时，**这是最容易被忽略的一处不一致**。

**`oversample_factor`。** 就是上面那个候选池倍数，默认 **4**。

还有一个参数值得单独点出来：**`use_index`**。它决定向量路这一路
是否允许走 ANN 索引，`use_index=false` 就是强制向量路做精确 KNN。
这就是"融合时两路各自要不要过索引"这个问题的落点——**融合器不关心
两路各自是怎么算出来的**，它只拿到两路已经排好序的结果；
但两路的**召回语义必须一致地声明**。一路走了索引（近似召回）、
另一路做了精确扫描，融合出的名次就没有统一解释，因为"这一路少召回"
可能来自 ANN 近似，也可能来自谓词的掩码（这就是
"一条因为近似、一条因为过滤"的两种不同缺失）。

至于谓词的掩码在距离计算之前还是之后生效（prefilter / postfilter），
那是 19.5 节的问题，本章不重复：**这里只需要记住，
两路用的是同一种过滤语义**，否则融出来的分数是两种分布拼起来的。

### 怎么判断该不该上 cross encoder

上 cross encoder 的代价是明确的（O(N) 次前向、一个模型的服务延迟、
一次性的 GPU 投入或一个远端 API 账单），收益却经常只是"感觉更准了"。
判断方法只有一条：**在一个有标注的查询集上，把"融合后直接返回"
和"融合后过 cross encoder"的 nDCG@10 比出来。**

最小可用的准备工作是三件事。**一批真实查询**，50~200 条就够看出趋势
（统计上不严格，但足以判断"有没有收益"），最好从线上日志里抽，
而不是从文档里编。**每条查询的相关标注**，二值（相关/不相关）就够用，
它退化成 Recall@k / MRR 也能算。**一套固定口径**：候选池多大、
固定看 @几、是否惩罚"命中不相关"。

然后做三次消融。**第一，基线**：只用一路。如果两路融合没有比单路好，
问题在召回层而不是重排层，这时候上 cross encoder 是白花钱。
**第二，融合 vs 融合加精排**——这一步是核心，看 nDCG@10 有没有稳定提升。
提升很小（比如 0.01）而延迟涨了一个数量级，结论就是不上。
统计时要看"**多少条查询变好、多少条变坏**"：只看平均值会把
"一半变好、一半变坏、平均不变"这种最危险的情况藏起来。
**第三，只有在第二步确认有收益之后**，才值得去调候选数和换模型。
候选数（`top_k`）是最大的杠杆：20 条和 100 条的延迟差 5 倍，
而收益常常在 20~50 之间就饱和了——这正好对应 20.6 节那句
"把候选卡在 20~50 条"。

最后一条关于**离线结论能不能上线**：这类评测的乐观程度由候选池决定。
离线时喂给 cross encoder 的就是融合后的 top 100，线上也照做，
结论就能迁移；如果线上为了省延迟把候选砍到 20，就必须在 20 的口径下
重算一遍。**评测口径和线上口径不一致，是这类优化最常见的失败方式。**

## 20.10 小结

**向量检索和全文检索的盲区几乎不重叠**，这是混合检索存在的全部理由。
向量不擅长专有名词、编号、代码符号；BM25 不擅长同义词和改写。

**融合的第一步永远是统一方向。** `_distance` 越小越好、`_score`
越大越好，直接相加是静默错的。`_relevance_score` 是重排器的**输出列**，
不是 `return_score` 的取值——`return_score` 只接受 `"relevance"` 和
`"all"`。

**RRF 只用名次，对分数尺度免疫**，是这个领域里唯一不需要调参就能
上线的方法。它默认 `K=60`（来自 SIGIR 2009 那篇论文）。代价是丢掉
幅度信息、以及两路质量悬殊时需要手动给 `weights`。

**线性加权保留幅度**，代价是把"离群值怎么办、缺失值怎么填"这两个
坑暴露给使用者。min-max 对离群值极度敏感（`[0.1, 0.2, 0.3, 100]`
归一化后前三个变成 `[0, 0.001, 0.002]`），rank 会丢幅度但免疫离群值，
`none` 要求两路尺度本来就自洽。

**cross encoder 只能放在最后一步**。它是 O(N) 次完整前向，
标准形态是"ANN 召回 10^4 → 融合粗排 10^3 → cross encoder 精排 10^2"。
真实默认模型是 `cross-encoder/ms-marco-TinyBERT-L-6`。

**四种方法要按前提条件选，不是按"哪个更准"选。** RRF 只看名次、
对尺度免疫，是默认答案；线性加权保留幅度、输出有阈值语义，
代价是归一化的两个坑；相对分数融合（每路除以自己的最高分）
取两者中间；MRR 是无平滑、带显式权重的名次融合。cross encoder
是加法而不是替代，它只能放在最后一步：O(N) 次完整前向，
标准形态是"ANN 召回 10^4 → 融合粗排 10^3 → cross encoder 精排 10^2"，
真实默认模型是 `cross-encoder/ms-marco-TinyBERT-L-6`。
该不该上，要用一个有标注的查询集比 nDCG@10，并且看
"多少条变好、多少条变坏"，不能只看平均值。

**融合前每路要多取候选（`oversample_factor`）**，否则"在某一路排
第 11 名、在另一路排第 1 名"的候选根本进不了融合器。DuckDB 侧的
三个名字是 `_hybrid_score`（对应 `_relevance_score`，列名不同）、
`alpha`（混合权重，默认 0.5，比 Python 侧的 0.7 更均等）、
以及 `oversample_factor`（默认 4）。

**ColBERT 式晚交互是把"一个向量"换成"一堆向量"**：token 级 MaxSim、
先算相似度后求和，所以文档侧向量可以离线算、可以建索引——
这是它比 cross encoder 便宜的全部原因。代价是存储**贵 n 倍，
n 就是段落 token 数**（中文短段落 13.0 倍、256 token 的段落 256 倍），
以及整套 schema / 索引 / 查询入口都要换一条路。

怎么存，以及图像、音频、视频这些非文本模态怎么进同一张表。
