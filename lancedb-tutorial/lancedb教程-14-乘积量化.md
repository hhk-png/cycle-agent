# 第 14 章　乘积量化

上一章解决的是"要算多少距离"。这一章解决的是另一个正交的问题：
**每条向量占多大地方。**

## 14.1 内存问题比算力问题更难绕

IVF 把距离计算量降下来了，但**它一条字节都没省**。倒排链表里存的
还是完整的 float32 向量，只是被分到不同桶里而已。所以 IVF_FLAT
的内存和暴力检索完全一样——这就是 `IVF_FLAT` 在 `stats()` 里
`compression_ratio` 恒为 1.0 的原因。

在很多真实场景里，内存比算力更早撞墙。10 亿 × 128 维的 float32 是
**512 GB**，单机完全装不下；10 亿 × 768 维是 **3072 GB**，得靠一整套
分布式集群；就算降到 1 亿 × 768 维，也有 **307 GB**，要一台大内存
服务器才放得下。而 10 亿 × 128 维恰好是很常见的规模——推荐系统、
图片检索、电商去重都容易到这个量级。512 GB 装不进一台机器的内存，
意味着**每次查询都要从磁盘读**，延迟直接掉两个数量级；而且就算内存够，
跨越内存总线的那个带宽瓶颈（§13.1 量的那个）还在。

乘积量化（PQ，Jégou et al. 2011）的目标是**把每条向量压成几十个字节，
并且让压缩后的表示能直接算距离**。后半句是关键：如果能压缩但不能直接算距离，
那么查询时还得解码，把内存省下来的又还回去了。

## 14.2 子空间分解

PQ 的想法是把 `d` 维空间**切成 `M` 段**，每段宽 `d/M` 维，
然后**在每一段内部独立地跑一次 k-means**，得到 `K = 2^b` 个质心。
于是每条向量被表示成 `M` 个下标（每个下标 0..K-1），一共 `M × b` 位。

以 `d = 128, M = 8, b = 8` 为例：

```
原始:  128 维 × 4 字节 = 512 字节/向量
编码:  8 个下标 × 1 字节 = 8 字节/向量
压缩比: 64 倍
```

每个子空间里的 k-means 得到一张“码本”（codebook），形状是
`M × K × (d/M)`。`M=8, K=256, d=128` 时码本是 `8 × 256 × 16 = 32768`
个 float32，**128 KB**——这就是"学习出来的参数"的全部大小，
和 n 无关，所以可以常驻内存。

这个设计之所以有效，靠的是一个朴素但重要的假设：
**向量的不同维度段之间大致独立。** 如果第 1-16 维的分布和第 17-32 维
强相关，把它们分开量化就会丢失相关性信息。幸运的是，
embedding 向量经过的高维结构里，大部分相关性已经被前面的模型"摊开"了，
而且降低子空间的宽度（增大 M）本身就减轻了这个问题——
这就是为什么 `num_sub_vectors` 是个旋钮。

**`num_sub_vectors` 是精度和压缩率之间的旋钮，不是码本大小的旋钮。**
因为无论 M 取多少，每个子向量都占 1 个字节（当 b=8），
所以**每条向量的编码长度恒等于 M 字节**。M 从 8 涨到 16，
每条的字节数从 8 涨到 16（压缩比从 64 掉到 32），换来的好处是
每个子空间从 16 维缩到 8 维，码本描述得更精细。

真实 LanceDB 的默认 `num_sub_vectors` 是 `dimension // 16`
（不能整除时退到 `dimension // 8`，见 §12.4）——768 维默认 48 个子向量、
每条向量 48 字节。这是一条"两害相权"的经验值：M 太小码本描述不细，
M 太大压缩比又掉。

**训练成本的量级。** 码本本身很小：`M=8, K=256, d=768` 时是
`K × d × 4 = 786 KB`，和行数无关、可以常驻内存。贵的是训练——
每个子空间一次 k-means，成本是 `样本数 × K × 子空间宽 × 迭代数` 的量级。
真实 Lance 和 IVF 一样靠采样把样本数钉在 `k × 常数` 附近（§13.7），
所以训练时间不随行数线性涨；随行数涨的是编码落盘那一步（每条向量写
`M/2` 到 `M` 个字节）。放到索引层看，同样 2 万行 × 64 维，
建 `IVF_PQ` 索引要 **10 秒上下**（本机两遍运行 9.93 / 10.14 s，挂钟时间），
而 `IVF_FLAT`、`IVF_SQ` 都只要 **1.5 秒左右**
（`IVF_FLAT` 1.52 / 1.61 s、`IVF_SQ` 1.48 / 1.56 s，和 §13.3 是同一组
两遍运行）——多出来的近十秒基本上全是 PQ 训练。
**这两处的括号里都是"两遍运行的两个值"**，所以同一个索引会出现两个数；
第 13 章那里写全了，这里只挑第一遍是为省版面，**不是两组不同的实验**。这也是"数据量到了一定量、
`IVF_SQ` 还没撞墙时别急着上 PQ"的一个实际理由。

我们的实测把这条权衡量化得很清楚（3000 × 32 维数据，8 bit，压缩比按
迷你实现的口径）。M=2（子空间宽 16）时压缩比 64 倍、中位相对重建误差
0.2536；M=4（宽 8）时 32 倍、0.2214；M=8（宽 4）时 16 倍、0.1596；
M=16（宽 2）时 8 倍、0.0583；M=32（宽 1）时 4 倍、0.0046。
另一条独立的权衡是把位宽往下压：同一个 M=8，`num_bits` 从 8 降到 4，
中位相对重建误差从 0.1596 涨到 0.3432，代价换来的是码本小 16 倍
（32768 → 2048 字节）——这条留到 §14.5 再算。

注意**码本字节数一直是 32768**——因为 K 固定是 256、总维度固定是 32，
`M × K × (d/M) = K × d` 与 M 无关。M 改变的是**编码长度**和**精度**，
不是码本大小。这是教科书里最容易被说错的一点。

而且这条曲线的形状很值得看：从 M=2 到 M=8，误差从 0.254 降到 0.160，
降了三分之一；从 M=8 到 M=32，误差从 0.160 掉到 0.0046，降了 **97%**。
**收益在 M 大的时候反而更陡**——因为子空间越窄，
"维度间独立"的假设越容易成立，k-means 的任务也越简单。
M=32 时每个子空间只有 1 维，码本退化成"这一维的 256 个量化格点"，
这时候 PQ 其实就是 SQ，而 256 级一维量化确实几乎无损。

**`num_bits` 是第三个旋钮，而且它在 Lance 里只有两个合法值。**
它决定 K：`num_bits = 4` 时 `K = 16`，**总**码本是 `K × d × 4` 字节、
也就是 2048 字节；`num_bits = 8` 时 `K = 256`、总码本 32768 字节。
注意 2048 / 32768 是**整个码本**的大小（`K × d × 4`），不是"每个子空间"
的——K 变了总码本才跟着变，与 M 无关。

每条向量的字节数按 Lance 的 `M * num_bits / 8` 算：8 bit 时是 `M` 字节，
4 bit 时是 `M/2` 字节，因为 4 bit 会把两个子向量的码各占半字节、合装进
一个 `uint8`（低半字节是偶数号子向量、高半字节是奇数号，`pq.rs:243-249`）。
训练成本则随 num_bits 明显上升：同样 M=8、3000 行、`max_iters=25`，
本机实测 4 bit 约 105 ms、8 bit 约 800 ms，差了近一个数量级。
**本教程的迷你实现为了代码清晰，4 bit 也一个子向量占一个字节，
所以它报的压缩比在 4 bit 时只是 Lance 的一半。**

所以 4 bit 相对 8 bit 的收益是双重的：**码本小 16 倍、每条向量再小一半**。
两项乘起来是 32 倍的空间节省，代价是重建精度差很多——同一组 `M=8` 的
编码，`num_bits` 从 8 降到 4，`recall@10` 从 0.6900 掉到 0.3450、
重建中位相对误差从 0.1596 涨到 0.3432（§14.2 与 §14.5 实测）。
**这就是 4 bit 存在的理由**：
当你需要把压缩比再往上顶一档、又不太在乎那点排序精度（有 refine 兜底）时。**Lance 只支持 4 和 8**（`transform()` 在
`rust/lance-index/src/vector/pq.rs:145-158` 里 `match num_bits { 4 => …, 8 => …, _ => Err(...) }`，
建距离表的 `build_distance_table_l2` 同样只处理这两个值）。
4 bit 时还有个额外的约束：**`num_sub_vectors` 必须是偶数**，
因为"一个字节塞两个子向量的码"（`pq.rs:175-180`）。

## 14.3 ADC：把乘法变成查表

量化把向量压小了，但真正漂亮的部分是**怎么用压缩表示直接算距离**。

朴素的"对称距离计算"（SDC）是两个量化码之间的距离，需要预先算好
`K × K` 的码字距离表。PQ 论文提出的是**非对称距离计算**（ADC）：
**查询向量保持浮点，只有库侧被量化。**

做法是：查询到达时先算一张 `(M, K)` 的距离表

```
LUT[s][c] = ‖ q_s - centroid[s][c] ‖²
```

其中 `q_s` 是查询向量在第 s 个子空间的那一段（浮点，未量化），
`centroid[s][c]` 是第 s 个子空间第 c 个质心。这张表只有 `M × K` 个数
（`M=8, K=256` 时是 2048 个），**一次查询只算一遍**，成本是 `O(M·K·d/M) = O(K·d)`。

之后，任何一条编码向量 `x`（编码是 `code_0, code_1, ..., code_{M-1}`）的距离就是

```
d(q, x) ≈ Σ_{s=0}^{M-1} LUT[s][code_s]
```

**一次查表加一次加法，没有乘法。**

这个变换为什么成立？因为平方欧氏距离可以按子空间**可加分解**：

```
‖q - x̂‖² = Σ_s ‖q_s - x̂_s‖² = Σ_s ‖q_s - centroid[s][code_s]‖²
```

等式右边每一项只依赖第 s 个子空间，所以可以预先算好、缓存成表。
**没有这一步分解，查表技巧就不存在**——如果有任何跨子空间的交叉项，
距离就没法拆成 M 个独立的和。这也是为什么 PQ 要求维度能被子向量数整除：
分解必须是严格的，不能有一个维度横跨两个子空间。

误差只来自"库侧被量化"这一半。查询侧是精确浮点，
所以 ADC 的误差只有 SDC 的一半左右——这就是为什么几乎所有实用的 PQ
实现都走 ADC。两条路线的空间账也不同：SDC 要预算并缓存"码字到码字"的
距离，**每个子空间一张 `K × K` 表**，`M=8, K=256` 时是
`8 × 65536 = 524288` 个 float32（**2 MB**），而且两边都量化、
误差约为 ADC 的两倍。ADC 的 LUT 只有 `M × K` 个数（2048 个、8 KB），
而且**每次查询临时算一张、不用常驻**。规模效应在这里很明显：
M 大时 LUT 才变大（高压缩档 `M=96` 时是 24576 个、96 KB），
但仍远小于 SDC 的 `M × K²`。

我们的实测确认了表查找和"先解码再算距离"给出的**距离完全相同**：
在 500 条编码、4 条查询上，两者的最大绝对差是 0.000183，
纯粹来自浮点累加顺序。

**一个必须诚实说明的测量结果。** 在迷你实现里直接对比两种路径的耗时：

```
ADC 查表（500 编码 × 40 查询）      = 约 1.9 ms
解码后走 BLAS 的 pairwise_distances = 约 0.08 ms
```

ADC 反而慢了**近一个数量级**（多次跑 ADC 落在 1.6~2.2 ms、解码后 BLAS 稳定
在 0.08~0.09 ms，比值 20 上下——但这是 Python 挂钟计时，别把那个比值当精确
倍数）。这不是算法结论，是**实现语言**的结论：
ADC 的内层是 `for s in range(M): acc += table[s][codes[:, s]]` 这样的
Python 循环加 fancy-index，而 `pairwise_distances` 底层是一次 BLAS GEMM，
NumPy 把整个循环下沉到了 C 和 SIMD 里。

在 Rust/SIMD 实现里结论反过来，因为有两件事 ADC 独占：
**第一，没有乘法**（查表和加法都是低延迟操作，可以喂满流水线）；
**第二，不需要物化解码矩阵**。第二点更根本：解码会把 `(n, M)` 的
8 字节编码膨胀回 `(n, d)` 的浮点矩阵——膨胀 16 到 64 倍，
正好把压缩省下的内存全还回去，而且在 n 大的时候会直接 OOM。
**ADC 的价值不是常数更快，而是"能在压缩表示上算"，因而不需要那个大矩阵。**

这两个数字是实测脚本直接跑出来的（`measurements/vector_index_measurements.py 14`）。
作为对照，Lance 的 `compute_pq_distance`（`rust/lance-index/src/vector/pq/distance.rs:135-178`）
在 Rust 侧对 8-bit 就是 `d(q,x) = Σ_i DT[i][code_i]`，对 4-bit 走
`sum_4bit_dist_table_f32_transposed`（`lance-linalg/src/simd/dist_table.rs:1605`），
每批处理 32 行——那两个 kernel 里没有一行 Python。

## 14.4 磁盘上的布局是转置的，而且这很重要

PQ 的编码在磁盘上**不是行主序**，是**转置的**。这是 Lance 一个
值得单独讲的实现细节。

一个朴素的直觉是：编码是 `(n, M)` 的矩阵，每行一条向量，所以
按行存（row-major）最自然。但 Lance 的 `transpose`
（`rust/lance-index/src/vector/pq/storage.rs:521-541`）明确做的是：

```rust
transposed_codes[sub_vec_idx * num_rows + vec_idx] = *code;
```

也就是**布局是 `[M, n]` 的列主序**：先把全分区所有向量的第 0 个码字节
排完，再排第 1 个字节……读一条向量的全部码，步长是 n
（`get_pq_code` 用 `iter().skip(id).step_by(num_vectors).take(num_bytes)`，
`pq/storage.rs:1453-1472`）；读一个子空间的全部码，是连续的一段。

**为什么值得这么做？因为计算模式是"按子空间"而不是"按向量"。**
回忆 ADC 的内层：`acc += table[s][codes[:, s]]`。它遍历的是
**第 s 个子空间的所有行**，而不是某一行。在行主序里，
"取第 s 列"意味着每个元素跨 `M` 字节跳一次；在转置布局里，
这是内存里连续的一段，可以整块加载进 SIMD 寄存器。

我们实测了这个差别（100 万行 × 16 个子向量，逐子空间取全部码）：

```
row-major 跨列取码  = 约 40~50 ms
transposed 连续取码 = 约 42~52 ms   → 1.0~1.2 倍（有时转置反而更慢）
```

**这个结果必须诚实报告：在 NumPy 里量不出稳定的优势。** 同一台机器连跑三遍，
比值在 0.9x 到 1.2x 之间来回摆，转置甚至可能更慢——**根本跑不出一个稳定的
1.4 倍**。原因不难理解：NumPy 的跨列 gather 本来就有针对性的优化，把"缓存
不友好"这一项抹掉了大半；而且这两个数都是挂钟时间，**只在同一台机器同一次
运行内可比**，跨环境没有意义。

**但布局的取舍仍然是对的，只是它的收益要靠 Rust + SIMD 才体现得出来：**
Lance 的 kernel 用 `_mm256_shuffle_epi8` 一次批处理 32 行，转置布局允许
"一次加载 32 行 × 16 字节"这种规整的向量化，而跨列访问在 SIMD 里
根本没法向量化。所以正确的说法是"转置是为 SIMD 批处理准备的，
在 NumPy 里测不出稳定优势（1.0–1.2x）"，**不能拿一个 NumPy 里跑不出来的
倍数当论据**。Lance 的 `ProductQuantizationStorage::new_with_remapper`
（`pq/storage.rs:234-361`）在写入时就无条件转置，
并把 `metadata.transposed` 设成 `true`（`:351`）——**行主序只在
输入批里短暂存在，落盘永远是转置的。**

顺带说一个容易踩的坑：**PQ 的码在磁盘上转置，SQ 的码不转置。**
SQ 的 `ScalarQuantizationStorage`（`rust/lance-index/src/vector/sq/storage.rs:136-140`）
按 `id*dim .. (id+1)*dim` 取一条向量的码，是标准的行主序，
并且 `ScalarQuantizationMetadata` **没有**重写 `is_transposed()`。
所以 PQ 和 SQ 的布局是相反的，看代码时别把两者弄混。

最后，真实的磁盘上的编码长度是 `num_sub_vectors * num_bits / 8` 字节
（`pq.rs:614`）：8 bit 时是 `M` 字节，4 bit 时是 `M/2` 字节——
4 bit 会把两个子向量的码各占半字节（低半字节是偶数号子向量、
高半字节是奇数号，`pq.rs:243-249`）。
**顺带纠正一个流传的说法：代码里并没有一个叫 `PQ_CODE_SIZE` 的常量**
（全仓 grep 零命中），用到这条公式时直接写 `M * num_bits / 8`。
另外，Lance 没有显式的 64B/128B 对齐要求，批量 kernel 只要求
n 是 `BATCH_SIZE = 32` 的倍数（`lance-linalg/src/simd/dist_table.rs:15`），
尾部不足 32 行的单独走标量路径。

## 14.5 重建误差：唯一能直接测的东西

评估一个 PQ 码本学得好不好，只有一条直接的硬指标：**重建误差**。
把向量编码再解码，和原向量比：

```
err(x) = ‖ x - decode(encode(x)) ‖
```

本教程的 `reconstruction_error()` 报的是**相对误差** `‖x - x̂‖ / ‖x‖`，
而且是按行算的。为什么不用绝对误差？因为不同样本的模长差别很大，
绝对误差会掩盖"短向量被压得很糟"这件事——一个模长 0.1 的向量被
压出 0.05 的误差，在绝对尺度上微不足道，在相对尺度上却是 50%。
报告里同时给 mean / median / max，因为**必须看中位数**：
向量里偶尔会出现模长极小的样本，它们的相对误差会大到 100%，
把均值整个带偏，但这类样本对检索结果几乎没有影响。

实测结果（3000 × 32 维，IVF_PQ，探满所有桶；压缩比按迷你实现的口径）：
M=4、4 bit 时压缩比 32 倍、`recall@10 = 0.2425`，加 `refine_factor=8`
后升到 0.8375；M=4、8 bit 同样 32 倍、recall 0.4275、加 refine 0.9775；
M=8、4 bit 是 16 倍、0.3450、加 refine 0.9150；M=8、8 bit 16 倍、
0.6900、加 refine 1.0000；M=16、4 bit 是 8 倍、0.5875、加 refine 1.0000；
M=16、8 bit 8 倍、0.9075、加 refine 1.0000。码本大小只有两档：
4 bit 是 2048 字节，8 bit 是 32768 字节。

（"压缩比"是按迷你实现的口径报的：它对 4 bit 也一个子向量占一字节，
所以那三行 4-bit 的压缩比只有 Lance 实际的一半。真实 Lance 的 4-bit
压缩比要把 32.0 / 16.0 / 8.0 各乘 2。召回率不受这个差异影响，
因为量化格点数和重建值是一样的。）

这份结果里有几个层次的信息。

**同样是 4 bit、码本只占 2 KB，M 从 4 涨到 8，recall 就从 0.24 涨到
0.35。** 反过来，4 bit 的 32 倍压缩比 8 bit 的 16 倍压缩"更狠"。
**如果你必须要极致的压缩率，加大 M 而不是加大 num_bits 是更划算的
方向**——因为 M 只涨编码长度、码本仍是 `K × d` 那么大，而 num_bits
会平方级地涨码本和训练时间。

**`refine_factor` 几乎是万能的。** 每一行的 "+refine=8" 要么到 1.0、
要么到 0.98 以上。这印证了 §13.5 的说法：PQ 的近似误差分散在排序上，
而精确重排能把排序修好——**前提是真正的最近邻还在候选集里**。
M=4、4 bit 时即使 refine 也只到 0.84，说明那时候候选集本身就已经错了。

**注意这份 recall 是在"探满所有桶"下测的**，所以里面**没有粗量化误差**，
全是 PQ 自己的量化误差。这是 §13.10 那条"先隔离误差源"方法论的直接应用：
要评 PQ，就得先把 IVF 的影响消掉。

## 14.6 残差 PQ：换一个量化目标

§13.6 已经讲了残差的原理，这里补上 PQ 这一侧的实现细节。

残差模式下，PQ 训练和编码的对象都不是 `x`，而是 `x - centroid[partition(x)]`：

```python
def _pq_targets(self, matrix, assign):
    if not self.residual or self.num_partitions == 0:
        return matrix
    return matrix - self.centroids[assign]
```

重建时要把质心加回去：`decode(codes) + centroid[assign]`。

这里有一个**测量上的陷阱**，值得专门说，因为很容易得出错误结论。
如果比较"PQ 学到的那个东西的重建相对误差"，残差模式看起来**更差**：

```
残差模式：PQ 学习目标的重建误差  median = 0.2816
原向量：  PQ 学习目标的重建误差  median = 0.1596
```

但这比较的是两个**不同的量**。残差模式要重建的是 `x - c`（范数 6.67），
原向量模式要重建的是 `x`（范数 18.28）。相对误差是除以各自的范数，
分母差 2.7 倍。正确的比法是**都还原回 `x` 之后**再看：残差 PQ 对 `x`
的重建中位相对误差是 **0.0925**、`recall@10 = 0.6900`（nprobes=20）；
原向量 PQ 是 **0.1596** 和 **0.4650**。残差 PQ 对 `x` 的重建误差比原向量
PQ **小了 42%**，recall@10 从 0.465 涨到 0.690。结论清楚了。

这个陷阱的一般形式是：**换了一个"学习目标"之后，
所有以目标为基准的相对指标都不可比了**，必须换算回同一个参照物。
在代码评审里看到"残差版本误差更大"这种结论，第一反应应该是
去查它比较的分母是不是同一个。

**实现代价。** 残差 PQ 在查询侧要多一点东西：因为每个分区的
查询残差不同（各自减自己的质心），所以**不能只建一张 LUT**，
得按分区分组、每组建一张 `(M, K)` 的表：

```python
for p in np.unique(parts):
    q_target = q - self.centroids[int(p)] if self.residual else q
    table = self.pq.compute_distance_table(q_target)
    ...
```

这就是残差 PQ 在查询侧多出来的全部成本：候选集跨 K 个分区，就要建 K 张
表，每张 `M × K` 个数。**把量级算一下**：`M=8, K=256` 时一张 2048 个
（8 KB），高压缩档 `M=96` 时一张 24576 个（96 KB）。非残差模式一张就够，
残差模式最多 `nprobes` 张（每个被探到的分区一张，`nprobes` 通常十几），
`nprobes=20`、`M=96` 时是 20 × 96 KB ≈ **2 MB** 的瞬时内存。相对于
"把 1 亿条向量解码出来"（几十 GB）可以忽略，但它是**每次查询都要重建**
的——所以这是延迟成本，不是常驻内存成本，`nprobes` 每涨一档就多摊一点。
它换来的精度是实打实的。

**真实 Lance 对残差有额外的处理。** `ResidualTransform`
（`rust/lance-index/src/vector/residual.rs`）在流水线里的位置是
"`PartitionTransformer` 之后、`PQTransformer` 之前"；
查询侧 `preprocess_partition_query_owned`（`lance_ivf_v2.rs:1467-1485`）
对分配到分区的查询做 `query.key = sub(&query.key, partition_centroid)`。
另外 **RQ（RaBitQ）的残差是无条件启用的**（`ivf.rs:314-318`），
而 **SQ 根本没有残差变换**（`use_residual() == false`，`sq.rs:120-122`）——
因为 SQ 是逐维线性量化，减一个质心并不减小子空间的动态范围。

**删除对 PQ 的威胁，以及它在本实现里的现状。**

机制上是这样：桶里 gather 出来的是**量化码**而不是原始向量，
删除掩码如果在 gather 之后才应用，被删行的码就会照样参与 ADC 打分、
照样占 `nprobes` 的候选名额——这就是第 9 章 §9.4 说的"幽灵行"。
PQ 版只把"幽灵的字节数"从 768 缩到几字节，**挤掉召回名额的后果一样**。

**但这条代价在本实现上已经量不到了**，和第 13 章 §13.5 是同一件事：
删除时会把索引里的行号一起搬（`_remap_indices_after_delete`），
候选池里不再有死行。所以上面那段机制描述的是**真实 Lance 的行为**
（索引保持不可变，用删除文件里的行地址在读取侧过滤），
不是本实现现在会发生的现象。**如果你从第 13 章读到这里，
不要把这一节当成"又一个幽灵行的例子"——它是同一个现象的另一面。**

那还剩什么值得担心的？`refine_factor` 阶段要把候选的**原始向量**
读回来做精确重排，候选池的规模决定了这一步要读回多少行。
在真实 Lance 上，候选池里混着已删除的行，那些行是一次白读；
在本实现上，这个白读没有，但**候选池仍然是"码"而不是"向量"**,
重排的 I/O 代价随 `k × refine_factor` 线性长——这是 PQ 的固有成本，
和删除无关。**建完 PQ 索引再批量删数据的表，
在真实库上要重新看一眼 `recall@k`；在本实现上不必，
但换了部署环境就得重新确认一次。**

## 14.7 压缩率与召回率的关系

把这些数字串起来看，PQ 的取舍有一个相当清晰的形状：

**压缩率和召回率不是线性关系，而是"过了某个点就断崖"。**
在我们的数据上（8 bit），M 从 16 降到 8（迷你实现的压缩比从 8 倍涨到
16 倍），recall 从 0.908 掉到 0.690——还能接受；从 8 降到 4（16 倍到
32 倍），recall 掉到 0.428；再把 num_bits 降到 4、M=4，recall 掉到
0.24（这一档在真实 Lance 的口径下是 **64 倍**压缩，迷你实现只报 32 倍，
差别见 §14.5 的说明）。**压缩比翻一倍，召回率的损失在后期会加速。**

原因还是"子空间独立性"那个假设。M 很小的时候每个子空间很宽，
子空间内部的维度相关性被 PQ 丢掉了；M 很小时这个损失最大。
换句话说，**PQ 的压缩上限是由"数据里有多少跨维度相关性"决定的**，
不是由算法决定的。

实践中的选择顺序大致是：先固定一个可接受的压缩比（由内存预算倒推），
然后在那个预算内**尽量加大 M、把 num_bits 降到 4**，
再看 recall 能不能靠 `refine_factor` 补回来。如果补不回来，
说明压缩比定得太激进了——这时该换索引类型（比如 IVF_HNSW_SQ），
而不是继续调 PQ 的参数。

**一个容易被忽略的失效面：离群查询（out-of-distribution query）。**
ADC 的 LUT 对查询侧是精确的，问题出在库侧——OOD 查询到所有候选的距离都
很大，而候选彼此之间的差异只有零点几，量化误差的量级一旦盖过这个差异，
排序就退化成近似随机。残差模式更容易踩：查询先减掉"最近分区的质心"
（§14.6），这一步隐含"查询落在数据分布范围内"的假设；查询离得越远，
减完质心剩下的残差越大，而 PQ 的码本只见过训练数据那点残差范围，
越描述不了它。**这个问题离线基准测不出来**——基准用的查询都来自同一批
数据。真实的自由输入查询（用户随手写的文本、跨域图片）可能根本不在
embedding 模型训练时见过的分布里，PQ 会把它们的排序悄悄搞乱，
而 `_distance` 看起来还是正常的。生产里要么对这类查询做一次"离最近质心
多远"的体检、超阈值就退回暴力，要么别对开放式输入的列用极限压缩。

还有一个更根本的替代方案值得知道：**OPQ（Optimized PQ）**。
PQ 的精度受限于"子空间独立"假设，而 OPQ 在 PQ 之前先乘一个学习出来的
正交旋转矩阵，把维度重排得"更独立"。它在 LanceDB 里的状态可以给一个
明确结论：**OPQ 不是一个可选的索引配置。** Lance 的 protobuf 里定义了
`Transform { … OPQ }` 这个 stage（`protos/index.proto`），说明格式层面
给它留了位置；但 0.40.0 的 Python API 上没有任何开关能打开它——
`IvfPq` / `IvfRq` 的 config 字段只有 `distance_type`、`num_partitions`、
`num_sub_vectors`、`num_bits` 这类参数，没有旋转矩阵或 `transform`
相关项（§12.4 那份字段清单）。所以**默认的 PQ 路径不做 OPQ**；
它是否在某个内部分支里被用到，从 Python 这一侧看不到，
只能说到"API 层面不可选"为止。要用 OPQ 就得自己在入库前做那次旋转。

**这里要说清两件事，一件是我写错了的，一件是这份教程的普遍局限。**

先说写错的那件：这一段原来写的是"要确认得读 Rust 源码，而本机没有
Lance 的 Rust 源码，这一层我们核对不了"。**那个理由站不住**——
同一章 §14.3、§14.4、§14.6 里就有七八处
`rust/lance-index/src/vector/pq/...` 的逐行引用（连行号都有）。
同一个仓库不能"有源码"和"没源码"同时成立。
真实情况是：本章的 Rust 引用是从上游源码**转引**的，
OPQ 这一处**没有去追**，于是被顺手写成了"没有源码"。
**"我没查"和"查不到"是两回事**，把前者的原因写成后者，
会让读者以为这个结论受限于客观条件，其实只是这一处偷懒了。

再说普遍局限，这条对全书的 Rust 引用都成立：
**那些引用没有绑定到一个具体 commit 或 release tag。**
行号（`pq/distance.rs:135-178` 这种）在源码变动时最容易失效——
它比文件路径脆得多。所以读这些引用时，把它们当
"上游在某个版本里是这么做的"看，别当"你可以去第 135 行核对"。
真正需要确认行为时，可靠的办法是拿对应版本的 release tarball
在本地核对，或者直接跑一次真实库看行为——**这两种我们都没做**，
所以本章的 Rust 引用统一按"转引"而非"复核"来读。

## 14.8 小结

**PQ 解决的是内存，不是算力。** 10 亿 × 128 维的 float32 是 512 GB，
装不进单机；PQ（m=8, 8bit）把它压到 8 GB。

**子空间分解 + 每个子空间独立 k-means。** 码本形状 `M × K × (d/M)`，
大小 `K × d`，**和 M 无关**；每条向量的编码长度恒为 `M` 字节。

**`num_sub_vectors` 是精度/压缩率的旋钮，`num_bits` 只影响码本大小和精度**
（Lance 里只有 4 和 8）。4 bit 时 `num_sub_vectors` 必须是偶数。

**ADC 把乘法变成查表**，靠的是平方距离按子空间可加分解。
误差只来自库侧被量化。**它的价值是"不物化解码矩阵"，不是常数更快**——
在 Python 里 ADC 甚至比 BLAS 慢一个数量级，那是语言的账。

**磁盘上的 PQ 码是转置的**（`T[sub * num_rows + vec]`），
因为计算按子空间遍历；**SQ 的码不转置**，两者相反。
代码里没有 `PQ_CODE_SIZE` 这个常量，长度公式是 `M * num_bits / 8`。

**重建误差必须看中位数，而且换学习目标之后所有相对指标都不可比。**
残差 PQ 看起来"误差更大"是个测量陷阱：还原回 `x` 之后，
它的误差反而小 42%。

**残差只在 L2/cosine 上成立**，对 dot product 是错误改写；
RQ 无条件启用残差，SQ 完全没有残差。

**压缩比和召回率的关系是"过点断崖"。** 预算内应该优先加大 M、
再把 num_bits 降到 4，最后用 `refine_factor` 补排序。
