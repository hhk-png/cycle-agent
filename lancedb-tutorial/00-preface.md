# 第 0 章　导读：这份教程怎么读

## 0.1 这份教程想解决什么问题

学一个新的数据库，最常见的困境是：官方文档告诉你"怎么用"，
但不说"为什么这样设计"；博客告诉你"它有多快"，但不说"什么时候会失效"。
两者的缺口正好落在同一个地方——**设计决策与它的代价**。

所以这份教程的组织方式不是"按 API 分类"，而是**按设计决策分类**。
每一个决策都回答三个问题：为什么这么选、代价是什么、什么时候这个选择会失效。

举几个具体例子，它们都在正文里：

LanceDB 的数据文件不可变，所有变更靠"写新文件 + 改 manifest"。
好处是时间旅行零成本、快照隔离免费、并发控制只需要一个条件写。
代价是删除留下"幽灵行"、更新要重写、压实会改行号并让索引失效。

向量列不是一种特殊类型，而是 `fixed_size_list<float32>[D]` 这个普通嵌套类型。
好处是它能参与投影、切片、join，能享受所有列级编码。
代价是维度写死在类型里，改维度必须重写数据。

LanceDB 的"无服务器"意味着它把对象存储当成唯一的持久层。
好处是计算和存储分离、成本和规模脱钩。
代价是延迟比本地盘高两个数量级，而且**优化目标从 CPU 变成了请求次数**。

## 0.2 两条并行的线索

教程有两条线索，交替推进。

**第一条是知识线**：文件格式、编码、索引算法、查询规划、运维、生态、未来。
这条线可以从任意一章开始读。

**第二条是代码线**：`mini_lancedb/` 这个从零复刻的实现。
它不是"配套示例"，而是教程的一部分——很多结论只能通过读代码或跑代码得到。
代码线建议按顺序读，因为后面的模块依赖前面的。

两条线的对应关系在 [README](README.md) 的模块表里列了。
简单说：第 3 到第 11 章对应存储层与数据操作，
第 12 到第 18 章对应索引，第 19 到第 22 章对应查询，第 23 到第 29 章对应运维与生态。

## 0.3 建议的读法

**如果你想快速判断 LanceDB 适不适合自己的场景**：
读第 1 章（定位与取舍）、第 27 章（竞品对比）、第 24 章（性能的量化结论）。
大概二十分钟。

**如果你想用它做项目**：读第 2 章（上手）、第 9 章（增删改的真实语义）、
第 19 章（查询规划，特别是 prefilter 与 postfilter 的差别）、
第 25 章（生产实践）、附录 D（坑与 FAQ）。
重点是避开那些"不报错但结果不对"的陷阱。

**如果你想理解它为什么快**：读第 3、4 章（文件格式与编码）、
第 10、19 章（下推与规划）、第 12 到 16 章（索引算法）。
这条线里的数字全部可以自己复现。

**如果你想自己写一个向量数据库**：全读，然后去读 `mini_lancedb/` 的源码。
附录 C 是代码导读，讲每个模块的关键决策和踩过的坑。

**如果你想弄清楚"怎么知道一个存储引擎是对的"**：读附录 E。
它讲的是这套教程自己用的验证手段——对拍、不变量、回归测试、
以及三种"测试全绿但实现是错的"的假绿。正文里所有"实测"的可信度
都建立在那一套做法上。

**如果你要动真实 LanceDB、而不只是理解它**：读附录 F 和附录 G。
前者讲"用户可见的派生表"（物化视图、计算列、字段元数据），
后者讲"跑起来需要什么"（异步接口、作业、LSM 写路径、克隆、预热），
并且正面列了一张"哪些能力只在 Cloud/Enterprise 有"的清单——
**在选型阶段把这张清单划清楚，比后面调性能重要得多。**
这两篇里的每个数字都标了是本机实跑还是引用文档。

## 0.4 关于代码

所有代码都在 `lancedb-tutorial/` 目录下：

```
mini_lancedb/    迷你实现，约 3.6 万行
tests/           测试，1144 个用例（1143 通过 + 1 跳过）
examples/        可以直接跑的示例
```

跑法：

```bash
cd lancedb-tutorial
python -m pytest tests/ -q
python -X utf8 examples/01_quickstart.py
```

`mini_lancedb` 只依赖 numpy 和标准库。**没有其他依赖**是刻意的：
它保证这份教程在任何装了 Python 的机器上都能跑起来，
也让"这个功能到底怎么实现的"永远有确定答案。

**在 Windows 上加 `-X utf8`。** 这不是可选项：控制台默认 GBK，
输出里的中文会让 `print` 直接抛 `UnicodeEncodeError`。
库本身没有问题，是终端的默认编码问题。

## 0.5 关于"实测"的约定

这份教程对数字很较真，因为性能话题里流传的"常识"错得离谱。
约定如下：

凡是标了具体数字的，都是在本机实际跑出来的，数据规模、参数、
硬件都在上下文里说清楚了。

凡是引用厂商公布的性能数据（比如"企业版 P50 25 ms"），
都会标注**厂商口径**和日期，不和自己的测量混在一起。

凡是查不到出处的说法，标 **未经确认**，不做推测性陈述。

凡是推算（比如从 100 万行的测量外推 10 万行），明确标 **推算**。

这套约定带来了一些不太好看但更有用的结论。
比如第 4 章实测 `byte_stream_split` 只省 7.1%，而不是流传的 20% 到 30%；
第 23 章实测压实之后的同一个查询**读了约 27 倍的字节**。
这些结论比漂亮的说法有价值得多。

（注意第 23 章那条用的是**字节数**，不是"慢了多少倍"。挂钟时间同机
两遍能差两三倍，所以它没有被写成结论——同一节里明确写了
"这里只把字节数当结论"。凡是看到"快了/慢了几倍"的地方，
都要先问一句：那个数字是确定的吗？）

## 0.6 一个提醒：版本号是雷区

开始之前先把最容易搞混的事情说清楚：**"Lance 的版本"至少有三种含义。**

**文件格式版本**指容器布局和编码集，目前是 2.0 到 2.3。
**不存在 "Lance V3 文件格式"**——有些文章里的 "Lance V3" 指的是
向量索引的落盘布局 V3，和文件格式不是一回事。

**Rust crate 版本**指 `lance` 这个 crate 的发布号。

**Python 包版本**指 `lancedb` 的发布号。注意 `lancedb` 和 `lance`
（导入名是 `pylance`）是**两个包**：`lancedb` 里打包了 Rust 编译的
原生模块，而 `pylance` 是更底层的 dataset 库。

这份教程写作时的验证环境是 `lancedb 0.40.0` + Python 3.14.6 + pyarrow 26.0.0。
**但要先说清这个环境缺什么**：`pylance`（上表里的第二个包）**没有装**，
所以所有真正走 `pylance` 那一层的功能——`compact_files`、
`cleanup_old_versions`、`to_lance()`——在本机是**跑不起来**的
（`import lance` 直接 `ModuleNotFoundError`，调用处报 `ImportError`）。
正文里凡涉及这些路径的说法都标了"引用文档、未经复跑"，
那不是谦辞，是真的没跑成。这个坑本身在附录 D 里记了一条。

**这里有一条我们写错过、后来改回来的**，值得放在导读里当范例：
最初的写法是把 `merge_insert` 也划进"需要 `pylance`"那一组，
理由是"它看起来属于同一类维护操作"。**这个前提是错的**——
`merge_insert` 不经过 `pylance`，在 0.40.0 上直接就能跑，
第 9 章 §9.7 有实测结果。把"某一个方法需要 `pylance`"推广成
"整条路径需要 `pylance`"，是这份教程最容易犯的一类过度概括；
第 9 章保留了这次纠正的原文。

第 28 章会把版本号这件事彻底讲清楚，包括几个真实的兼容性事故。
