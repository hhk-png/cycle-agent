# 第 15 章　HNSW

前面两章都在**压缩**：IVF 压缩候选集、PQ 压缩向量本身。这一章走一条
完全不同的路线——**不压缩任何东西，而是把向量组织成一张图**，
让"找最近邻"变成"在图上走几步"。

HNSW（Hierarchical Navigable Small World）2016 年提出，到今天仍是
内存图索引的事实标准。它的想法可以用一句话概括：**把跳表的思想搬到近邻图上。**

## 15.1 可导航小世界

先理解"小世界"这个词。一张**可导航**的近邻图要同时满足两个看起来
互相矛盾的要求：

**第一，要贪婪可达。** 从任意一点出发，反复跳到"邻居里离目标最近的"，
最终应该能到达真正的最近邻。这意味着图必须有足够的**局部连通性**——
每个点的邻居要覆盖它周围各个方向，否则贪心会掉进局部最优出不来。

**第二，要短。** 从任意一点到任意一点，跳数要少（对数级），
否则"走几步"就变成了"走几千步"。这意味着图必须有**长边**——
能让搜索快速跨越大距离。

这两个要求是冲突的：短边保证贪心可达，长边保证路径短，
但一张只有短边的图直径很大，一张只有长边的图贪心会迷路。

NSW（Navigable Small World）的做法是在同一张图上**同时**保留短边和长边：
建图时越早插入的点越容易连到已经形成的"骨架"上，自然形成长边。
但"越早插入的点长边越多"是个脆弱的设计——插入顺序会显著影响图的质量。

**HNSW 的解法是把长边和短边分到不同的层。** 每个点被随机分配一个
"最高层" level。第 0 层包含所有点，第 1 层只包含 level ≥ 1 的点，
以此类推。搜索从最上层（点最少、边最长）的入口点开始贪心下降，
每下降一层图就更密、边更短。**这就把"一张图要同时干两件事"
变成了"每层图只干一件事"**——跳表的思路。

## 15.2 层高分布：为什么是 `ml = 1/ln(m)`

层高是这样抽的：

```python
u = float(self.rng.random())
return int(-math.log(max(u, 1e-12)) * self.ml)
```

其中 `ml = 1 / ln(m)`，`m` 是每个点最多连的边数。
层高服从一个**几何分布**：`P(level ≥ l) = m^{-l}`，
等价地 `P(level = l) = (1 - 1/m)·m^{-l}`。
从这里能推出两个口径，而它们**不能混着比**：

**累积口径**——最高层达到 `l` 及以上的点一共有 `n · m^{-l}` 个
（把第 `l` 层及以上的点全算进来）；
**逐层口径**——恰好落在第 `l` 层的点有 `n · (m-1)/m^{l+1}` 个。
两者都由同一个几何分布决定：某点在第 `l` 层的概率是
`P(level ≥ l) - P(level ≥ l+1)`，乘 `n` 就是逐层点数。
层数越高点越少，上疏下密。

`ml = 1/ln(m)` 这个常数不是拍脑袋定的，它是被"让每层搜索代价与点数无关"
这个目标反推出来的。推导很短：

- 第 `l` 层及以上的点有 `n · m^{-l}` 个（相邻两层正好差 `m` 倍）；
- 每个点连 `m` 条边，所以一层上贪心搜索的期望步数大约是 `O(m · 常数)`
  ——**和这一层有多少点无关**；
- 层数是 `O(log_m n)`，因为层高超过 `L` 的概率是 `m^{-L}`，
  最高的非空层大约是 `log_m n`。

三件事乘起来，总查询复杂度是 `O(m · log_m n)`——对数级。
如果 `ml` 取别的值，比如 `1/ln(2m)`，那么每层的点数衰减得更慢，
最高的层会变得很高，而且每层的搜索步数不再有界；取 `1/ln(m)`
正好让"每层衰减 m 倍"和"每点连 m 条边"配上。

我们的实测验证了这个分布。3000 个点，三组参数——注意实测的每层点数
是**逐层**口径（三项之和正好是 3000），所以对照的也必须是逐层理论值
`n·(m-1)/m^{l+1}`，两边同口径才能比：

```
m=12  实测每层点数 = [2755, 226, 19]
      逐层理论     = [2750.0, 229.2, 19.1]

m=8   实测 = [2629, 328, 42, 1]
      逐层理论 = [2625.0, 328.1, 41.0, 5.1]

m=16  实测 = [2812, 176, 10, 2]
      逐层理论 = [2812.5, 175.8, 11.0, 0.7]
```

前几层吻合得相当好：m=12 的 2755 对 2750、m=16 的 2812 对 2812.5，
都只差个位数的点。**只有最顶上那一两层会明显偏**，因为它们的期望本来
就只有个位数（m=8 的第 3 层期望 5.1 个点、实测只有 1 个；m=16 的第 3 层
期望 0.7 个、实测 2 个），个位数的抽样噪声足以让数字翻倍或归零。
所以规律不在"顶层具体有几个点"，而在**顶层住不住得下人**：
最高的非空层大约是 `log_m n`（m=8 时 3.85、m=12 时 3.22、m=16 时 2.89），
`m` 越大这个值越小——**m 越大，层数越少**，而每层的边数越多，
两者其实是同一个 `ml` 的两面。

**真实 Lance 的实现和论文有一处细微差别。**
`random_level_with`（`rust/lance-index/src/vector/hnsw/builder.rs:64-71`）是

```rust
let ml = 1.0 / (params.m as f32).ln();
min((-rng.random::<f32>().ln() * ml) as u16, params.max_level - 1)
```

注意上限是 **`max_level - 1`**，不是 `max_level`。`max_level` 默认 7
（`HnswBuildParams` 默认值：`max_level: 7, m: 20, ef_construction: 150,
prefetch_distance: Some(2)`，`builder.rs:74-108`）。所以层高被硬钉在
0..6 之间——这是为了避免"某个点抽到第 20 层"这种事把内存和层偏移数组
撑爆。`ml` 的公式本身和论文一致。

**注意这里又出现了一次"两层默认值"**（和第 12 章 §12.4 讲 `num_bits` 时
是同一个坑）：上面这组是 **Rust 构造器层**的默认值，而 **Python SDK 的
`HnswPq()` 把 `ef_construction` 默认成 300**，不是 150
（实测 `inspect.signature(HnswPq)`，本机 `lancedb 0.40.0`）。
所以"默认 `ef_construction` 是多少"这个问题有两层答案，
写文档或做基准时要说清自己在哪一层——**用户不传参时拿到的是 300**。

**而本实现是第三个答案，这个也得说。** `mini_lancedb/index/ivf_hnsw.py`
的 `_graph_params()` 里写的是 `m=16`、`ef_construction=100`、`seed=0`——
和前两层都不一样（Rust 是 `m=20 / ef_construction=150`，
Python SDK 是 `ef_construction=300`）。所以同一个问题现在有三个答案：

```
Rust 构造器层      m=20   ef_construction=150
Python SDK 层      ——    ef_construction=300
本实现             m=16   ef_construction=100
```

这和第 13 章 §13.3 里 k-means 的 `max_iters`（本实现 25、Lance 50）、
以及 §12.4 里 `num_bits` 的情况是同一类：**本实现自己的默认值
经常是第三个数字，而章节只在需要时才披露。**
本节的实测用的是显式传参的四组（`m ∈ {8,16}`、
`ef_construction ∈ {30,100}`），所以上面的召回率和延迟数字
不受默认值影响；但如果你照抄一段"不传 `m`"的代码去复现，
拿到的是 16 而不是 20。**凡是"默认值"三个字出现的地方，
都要问一句"谁的默认值"。**

另外 Lance 的层高 RNG 是**固定种子**的：`SmallRng::seed_from_u64(42)`
（常量 `HNSW_LEVEL_RNG_SEED: u64 = 42`，`builder.rs:58`）。
这意味着"同样的数据 + 同样的参数 ⇒ 同样的图"，对复现和调试很友好。

## 15.3 插入：三个阶段

插入一个新点 `q`（它的层高是 `L`）分三步：

**阶段一，贪心下降到目标层。** 从当前入口点开始，在高于 `L` 的那些层上
**每层只走一步**——反复跳到"邻居里离 q 最近的"，直到没有更近的邻居为止，
然后下降一层。这个阶段不做束搜索，因为那些高层只是为了快速定位，
不需要精确。`_greedy()` 就是这么写的：一个 `while improved` 循环，
每轮算一次 `q` 到当前点所有邻居的距离。

**阶段二，从 `min(L, max_level)` 往下逐层建边。** 在每一层 `lc`：

1. 用 `ef_construction` 大小的候选堆做一次束搜索（`_search_layer`），
   得到 `W`（按距离升序的候选列表）；
2. 用启发式（下面讲）从 `W` 里挑最多 `limit` 个当邻居
   ——`lc == 0` 时 `limit = m_max0 = 2m`，否则 `limit = m_max = m`；
3. 把这些边写进 `links[lc][node]`，同时**反向**给每个选中的邻居
   加一条指向 `q` 的边（`_add_link`）；
4. 把 `W` 里的点当作下一层的入口点。

**这里有一个迷你实现和真实 Lance 的差异，必须点出来。**
本教程的 `_insert` 对新节点和反向边用了**同一个** `limit`
（第 0 层都是 `2m`），所以新点在第 0 层可以连到 `2m` 条边。
而真实 Lance 的 `reciprocal_limit` 只作用于**反向边**
（`builder.rs:810-879`）：

```rust
let reciprocal_limit = if level == 0 { self.params.m * 2 } else { self.params.m };
```

也就是说**新节点自己每层只连 `m` 条**，`2m` 是留给 level-0 **互惠边**
的上限——第 0 层承担了几乎全部的搜索工作，所以它允许更密。
代码注释直接引用了论文："Algorithm 1 selects M neighbors for the new node.
Mmax0 is reserved for reciprocal edges on existing level-0 nodes."。
所以同样参数下 Lance 的图比本实现的稀疏一些，实测平均出度也更低
（本实现 m=12 时第 0 层平均出度 11.05，接近 `2m` 的上限但没顶满）。
**引用论文的 `Mmax0 = 2M` 时要说清楚它管的是谁**——
它管的是"已有节点被反向连边"时的上限，不是新节点的出度。

**阶段三，更新入口点。** 如果新点的层高超过当前 `max_level`，
新点成为入口点，`max_level` 更新。

这里还有一个隐蔽的工程问题：**反向加边可能把已有节点的出度顶爆**。
`_add_link` 的处理是——如果加上这条边超过 `limit`，就对
`src` 的整个邻居表重新跑一次启发式剪枝：

```python
cand = np.append(cur, np.int32(dst))
if cand.size > limit:
    d = self._dist(self.vectors[src], cand)
    order = np.argsort(d, kind="stable")
    W = [(float(d[o]), int(cand[o])) for o in order]
    cand = np.asarray(self._select_neighbors(W, limit), dtype=np.int32)
```

也就是说"剪枝"不只发生在新点身上，也发生在被连的旧点身上。
这是 HNSW 图质量的关键：如果不剪，图的度数会随插入线性膨胀，
内存和搜索代价都失控。

## 15.4 邻居选择启发式：论文 Algorithm 4，以及为什么它比"最近 m 个"好得多

这是 HNSW 里最重要、也最容易被略过的一段。

朴素的想法是：从 `ef_construction` 个候选里挑最近的 `m` 个当邻居。
**这个做法在聚簇数据上会退化成一颗星。** 想象一个簇，
所有点到簇心的距离都很近，那么每个点的最近 m 个邻居很可能
都是同一批"靠近簇心"的点——图变成以簇心为中心的星形，
簇边缘的点连不出去。搜索一旦走进这个簇，就再也跳不到别的簇。

Algorithm 4 的启发式要求：**候选 c 只有在"到每个已选邻居的距离
都 ≥ c 到查询点的距离"时才被保留。** 换成代码就是
（`hnsw.py` 的 `_select_neighbors`）：

```python
for a in range(ids.shape[0]):
    if len(selected) >= limit:
        break
    ok = True
    for b in selected:
        if pair[a, b] < dists[a]:
            ok = False
            break
    if ok:
        selected.append(a)
```

直觉是：如果某个已选邻居 `w` 比查询点还靠近候选 `c`，
那么"走 c → w"就能到查询点附近，c 这条边是冗余的；
而如果 `c` 在别的方向上（它到所有已选邻居的距离都不比到查询点近），
它就是一条有价值的**长边**，能避免搜索掉进局部最优。
这一步叫 **diversity pruning**（多样性剪枝）。

**这个启发式到底值多少？我们做了一次消融。**
把 `_select_neighbors` 换成"直接取最近的 limit 个"（也就是
`extendCandidates=false` 的退化版），其他一切不变，
只扫 `m ∈ {8, 16}` 和 `ef_construction ∈ {30, 100}` 四组，每组建两张图
（一张走 Algorithm 4、一张走朴素最近 m），在 `ef=50` 下量 recall@10
和 level-0 平均出度。

**m=8 的两组里，Algorithm 4 都是 recall 1.0000、平均出度 9.00 / 9.99；
换成朴素最近 m 之后 recall 掉到 0.4650 / 0.4700，出度反而涨到 16.00。**
m=16 时差距收窄但方向不变：Algorithm 4 仍是 1.0000（出度 18.93 / 12.26），
朴素版 0.8775 / 0.8650（出度 31.79 / 32.00）。

两个 `ef_construction` 取值对同一列的影响很小（`ef_construction`
本来就不是召回旋钮，见 15.7）。真正说明问题的是那两个数字的方向：
**朴素版 recall 腰斩还多，出度却几乎翻倍。** 它连了更多边、占了更多内存，
得到的召回率却只有一半——这正是"星形退化"该有的样子：
边很多但都指向同一小撮点，图其实没连通。

这个消融值得每个人都亲手跑一遍，因为它彻底推翻了"HNSW 就是
'连最近的 m 个'"这个直觉——**HNSW 的一半价值在那条剪枝规则里**，
而不在分层结构里。

**真实 Lance 用的是同一个启发式**（`select_neighbors_heuristic_owned`，
`rust/lance-index/src/vector/hnsw.rs:61-110`），并且文档注释明确写了两件事：
**`extendCandidates = false`、`keepPrunedConnections = true`**
（`hnsw.rs:61-68`）。这两句的意思是：

- `extendCandidates = false`：不把"已选邻居的邻居"也加入候选池
  （论文里那个可选的扩展步骤，Lance 不用）；
- `keepPrunedConnections = true`：启发式剪枝掉的那些候选**不是直接丢弃**，
  而是在启发式算完之后，用来填补没填满的位置
  （`results.extend(pruned.into_iter().take(k - results.len()));`）。
  这保证了"即使启发式只选出 3 个，这一层也一定能连满 m 条边"，
  不会出现度数不足导致的图断裂。

判定条件本身在 `VectorStore::prefers_candidate`
（`lance-index/src/vector/storage.rs:532-538`）里：

```rust
selected.iter().all(|other| candidate.dist < OrderedFloat(dc.distance(other.id)))
```

就是论文里的 `d(e, q) < d(e, r) for all r ∈ R`。
有一个测试 `test_selection_retains_farther_diverse_reciprocal_candidate`
（`hnsw.rs:126-147`）专门验证了"远但方向不同的候选会被保留"：
候选 `{1..5}`、k=4 时选出来的是 `[1, 5, 2, 3]`——**序号 5 那个更远的点
被保留了**，而更近的 4 被挤掉了。这就是多样性的作用。

## 15.5 搜索：贪心下降 + 束搜索

查询分两段（`HnswGraph.search`）：

```python
ep = self.entry_point
for lc in range(self.max_level, 0, -1):
    ep = self._greedy(q, ep, lc)
W = self._search_layer(q, [ep], ef, 0, keep=keep)
```

**高层贪心下降到第 1 层**，然后在第 0 层跑一次 `ef` 大小的束搜索。
论文里也是这样：贪心停止在主层的上一层，第 0 层完全交给束搜索。

`_search_layer` 用两个堆：`candidates` 是小顶堆（越近越先扩展），
`results` 是大顶堆（存负距离，堆顶是当前最差的）。循环里的剪枝条件是

```python
if len(results) >= ef and cd > -results[0][0]:
    break
```

也就是"最近的待扩展候选都比结果堆里最差的还远"时，终止。
这是束搜索的标准终止条件，保证每个点最多被访问一次、
且不会做无用扩展。

**"访问一次"是靠 `visited` 集合保证的，它的规模也值得量一下。**
`visited` 是个 Python `set`，每扩展一个点，就把它没见过的那批邻居塞进去。
关键性质是：**它的大小由 `ef` 和平均出度决定，和 n 无关**——被扩展过的点
及其邻居最多也就 `ef × 平均出度` 个（m=12、ef=100 时约一千出头）。
这正是 HNSW 查询的辅助内存是 `O(1)`（相对 n）的原因，也是它能在十亿级
库上跑的原因。代价在常数上：Python `set` 每个元素几十字节的哈希开销，
一千多个元素就是几十 KB 的分配，在短查询里相当显眼。真实 Lance 用
定长的 visited 标记数组（而不是哈希集合）来避开这一步——**这也是
"为什么真实实现比 Python 实现快一个数量级"里那些不起眼的原因之一。**

`ef` 是查询期唯一的精度旋钮，地位和 IVF 的 `nprobes` 相同。
**它必须 ≥ k**，因为结果堆装不下 k 个候选时，图搜索根本返回不出 k 条。
迷你实现在 `search` 里强制 `ef = max(ef, k)`，Lance 也一样——
`HNSW::search` 会检查 `ef >= k`，否则报
`"ef must be greater than or equal to k"`（`builder.rs:1676-1680`）。

Lance 的默认值是 **`ef = k + k/2`**（`HnswQueryParams`，
`builder.rs:1469-1489`）：

```rust
let k = query.k * query.refine_factor.unwrap_or(1) as usize;
ef: query.ef.unwrap_or(k + k / 2)
```

注意 k 已经乘过 `refine_factor` 了——**HNSW 的 `refine_factor` 是
"先放大 k，再用浮点距离重排"**，和 IVF 的两步语义完全一致；
这个"放大候选 + 精确重排"的两步套路在第 12 章 §12.7 讲四旋钮、第 13 章
§13.6 讲残差时都出现过，这里不重复，只记它对 HNSW 的落点：
`ef` 的下限被 `refine_factor` 抬高（`ef ≥ k·refine_factor`）。

我们的实测（3000 × 32 维，m=12、ef_construction=60）：`ef` 取 10 / 20 / 50 /
100 / 200 时，**recall@10 分别是 0.9700、0.9950、1.0000、1.0000、1.0000**
（召回率是确定性的，逐位可复现）。单查询延迟只给量级：**本机一轮从约
0.2 毫秒涨到约 1 毫秒**（不同轮次落在 0.13~0.22 ms → 0.95~1.8 ms 之间，
差异全在挂钟噪声里——这一列是挂钟时间，换台机器甚至同一台机器换一轮都能
差 2~3 倍，见 §15.7，所以别拿具体毫秒当基准）。

**ef 从 10 到 20 就把召回率从 0.97 推到 0.995，再往上全是饱和。**
这是 HNSW 的典型行为：`ef` 的收益比 `nprobes` 更快饱和，
因为图搜索本身已经保证了"路径是对的"，`ef` 只是保险。
延迟随 `ef` 大致线性上涨，因为是"扩展多少点"的直接成本（量级上是
"亚毫秒 → 1~2 毫秒"这一档，精确倍数不可复现）。

**`ef` 没有硬上界，但过了饱和点就只有代价。** 把 `ef` 抬到远大于 k
不会更准——束搜索最多把整个连通分量走一遍，recall 在 `ef=50` 就到顶了，
更大的 `ef` 只是让 `results` 堆多装一批永远用不到的候选。同一个索引上把
`ef` 从 200 一路加到 1000、3000（= 全库点数，测量脚本 `chapter_15` 的
`ef 远大于 k` 一节直接跑出来），recall@10 一直钉在 1.0000 不动，
而单查询延迟继续线性上涨——**`ef` 翻几倍、延迟差不多也翻几倍**
（本机那一轮从约 1 ms 涨到约 10 ms 量级，见测量脚本 `chapter_15` 的
`ef 远大于 k` 一节；绝对值同样只当量级读）。**`ef`
越大越慢是线性的，因为每层要扩展的点数正比于 `ef`**（`candidates` 堆里每
弹出一个点就扩展它的全部邻居），而 HNSW 的"亚线性"承诺恰恰建立在"`ef`
是个与 n 无关的小常数"之上。把 `ef` 设成 n 就等于把自己降级成一次图上的
全扫描：又慢，又仍然可能漏（图并不保证强连通）。

**过滤搜索是图索引的软肋，实现里有一段专门处理它的设计。**
迷你实现的 `_search_layer` 接受一个 `keep` 谓词（删除行 / prefilter），
而关键决定是：**被过滤的点照样参与图的遍历，只是不进结果堆。**

```python
if keep is None or bool(keep[j]):
    heapq.heappush(results, (-dj, j))
```

这个 `keep` 检查只加在"进结果堆"那一步，**没有加在 `visited` 和
`candidates` 上**。为什么？因为如果连遍历都跳过被过滤的点，
图会被切断——一条经过"被删掉的点"的路径就走不通了，
而那条路径可能恰恰是通向正确答案的唯一通道（小世界图的可导航性
依赖所有点在图上）。这是**图索引上的过滤**和**倒排索引上的过滤**
最大的实现差异。

真实 Lance 在这一点上做得更复杂：它实现了 **ACORN** 风格的过滤搜索
（`beam_search_acorn`，`graph.rs:548-691`），带 `ACORN_SEED_COUNT = 16`、
`ACORN_BRIDGE_BUDGET_FACTOR = 4`（预算是 `4*ef`）。
（以下 ACORN 的常量与分支逻辑都是**转引上游 Lance 的 Rust 源码**，
本教程的迷你实现没有对应路径，也没有独立复现这些数字。）
选择逻辑分三档：prefilter 为空或全部保留 → 普通 `search_basic`；
**剩余比例小于 10% → 直接退回暴力 `flat_search`**；
否则用 ACORN。那个"小于 10% 就暴力"的阈值很有信息量——
它说明**过滤很强的时候，图搜索已经不如全量扫**，
因为要在图上找到那少数几个点，得遍历大量的死胡同。

## 15.6 内存成本

HNSW 的内存是两个部分：**向量本身**和**图的边表**。

边表的规模：每个点在第 0 层最多连 `2m` 条边，在更高层最多 `m` 条，
而层高期望是 `1/(1 - 1/m)` 层左右。所以每个点贡献的边数大约是
`2m + m·(1/(m-1))`——**主导项是 `2m`**。每条边要存一个 id，
如果 id 是 8 字节（`usize`）就是 `2m × 8 = 16m` 字节；
用 4 字节（`uint32`）就是 `8m` 字节。

我们的实测（m=12、3000 个点、32 维）：

```
图字节 = 223948      → 每节点 74.65 字节
平均出度 L0 = 11.05  （m_max0 = 2m = 24）
图 + 向量 = 607948   → 每节点 202.65 字节
其中向量本身 = 384000 字节（占 63.2%）
```

**在 32 维数据上，向量本身占了总内存的 63%——图反而不是大头。**
这是个容易搞反的直觉。图的开销是 `O(m)` 每点、和维度无关；
向量的开销是 `O(d)` 每点。所以低维时向量主导，高维时图可以忽略。
但等一下——高维时向量主导得更厉害（768 维就是 3072 字节/点，
而图还是 75 字节），所以**"HNSW 内存大"的真正原因是它必须
把原始向量常驻内存**，图只是零头。

这也解释了为什么 `IVF_HNSW_SQ` 有意义：它把向量换成 SQ 编码
（1 字节/维，省 4 倍），而图的部分不变。在我们的实测里（20 分区、
每分区一张 m=8 的图、ef_construction=40），IVF_HNSW_SQ 的
`code_bytes = 96000`（SQ 码），而 **20 张图加起来** `graph_bytes = 203160`
——**压缩之后图反而成了大头**。

顺带把两个 `graph_bytes` 对上号：**上面那个 223948 是整库一张 m=12 的图，
这里的 203160 是 20 张 m=8 小图的和**——参数不同、图的数量不同，
它们不是同一次构建，别拿来直接比。同一个量只有在参数写全的前提下才有意义。
这是第 16 章要接着讲的取舍。

本实现每条边存 `int32`（4 字节），所以是"约 4 字节/边"，
和论文常引用的 "m × 8 字节/层" 差一倍。真实 Lance 用
`List<UInt32>` 存邻居，也是 4 字节/边——**引用"HNSW 每节点 m×8 字节"
这个数字时要小心，它假设了 8 字节的 id**。

## 15.7 建图时间，以及 `ef_construction` 的另一面

建图的成本是 `O(n · m · ef_construction)` 次距离计算。
`ef_construction` 决定每个新点要找多少个候选邻居：它**主要**影响
构建时间和索引大小，但**不完全是**查询期无关的——它决定图的连通质量，
所以会对查询召回率产生间接影响（下面给实测）。

实测（3000 个点，Python 实现）扫了 `m ∈ {8, 16}` ×
`ef_construction ∈ {20, 60, 200}` 六组。**m=8** 时，`ef_construction`
取 20 / 60 / 200 对应的建图耗时是 2338 / 3914 / 23244 ms，距离计算次数
346,133 / 595,666 / 1,653,498，level-0 平均出度 8.28 / 9.70 / 10.51，
图字节 216268 / 234124 / 244144；**m=16** 时同样的三档是建图
1961 / 4240 / 22301 ms、距离计算次数 435,566 / 611,785 / 1,832,274、
平均出度 21.36 / 11.62 / 13.14、图字节 345468 / 229328 / 247692。

**建图时间和 `ef_construction` 近似线性**（8→200 是 10 倍，
距离计算次数从 34.6 万涨到 165 万，约 4.8 倍；时间涨得更多是因为
每次距离调用的邻居表也变大了）。**距离计算次数、平均出度、图字节是
确定性的**（重跑逐位相同），而**建图毫秒数不是**——同一套脚本在两遍运行里
相差 2~3 倍，取决于机器负载（上面这个 `m=8, ef_construction=200` 的 23 秒，
第二次跑出来是 11 秒）。**这一条对本章所有毫秒数都成立：只有比值和量级
可信，绝对值不可复现。** **建图时间对 n 也是超线性的**——每个点插入时
都要遍历图，所以总量是 `O(n · log n · m · ef_construction)` 量级。

**`ef_construction` 对查询期召回的影响：很小，但存在。** 固定 m=12、
查询 `ef=50`，把 `ef_construction` 从 10 提到 200 扫一遍，
`efc` 取 10 / 20 / 50 / 100 / 200 时 recall@10 分别是
**0.9200 / 1.0000 / 1.0000 / 1.0000 / 1.0000**（这一列是确定性的，
测量脚本 `chapter_15` 的 `ef_construction vs 召回` 一节直接跑出来）。
这说明 `ef_construction` 太小会让图连得不够好、召回掉到 0.92，
但只要给到 20 以上，查询表现就和 200 没差别。**它是"够用就行"的参数，
不是查询旋钮**：Lance 默认取 150 是为了在更难的数据上留余量，不是为了那
零点几个百分点的召回——真正调召回时该动的是查询期的 `ef`。

在建图这件事上，规模是残酷的。同样的参数在 50000 个点（64 维）上：

```
HNSW (m=16, ef_construction=100) 建图耗时 128.72 秒
```

Python 实现下两分钟建 5 万个点的图。真实 LanceDB 用 Rust 是
秒级到十几秒级的（取决于参数），但这个量级差异不改变结论：
**HNSW 的建图比 IVF 贵得多**，因为 IVF 的 k-means 只跑
几十轮迭代、每轮是一次 BLAS GEMM，而 HNSW 是 n 次独立的图插入、
每次都有一堆小规模的随机访存。生产环境里"重建一个亿级 HNSW"
是要排期几十分钟到几小时的后台任务。

顺带一提，Lance 还有一个用 HNSW 加速 **k-means 本身**的小设计：
当质心数超过 100 万个元素（`centroids.len() >= 1_000_000`）时，
`compute_membership_and_dist` 会用一个小 HNSW 来找"最近的质心"，
参数是 `ef_construction(15).num_edges(12)`
（`lance-index/src/vector/utils.rs:104-160`）。这时候
`balance_factor` 会被忽略。

## 15.8 删除：图索引的慢性病

**倒排索引删一行很容易**——把行号从桶里摘掉，或者干脆只打一个
`mask` 标记。IVF 系列里删除是 `O(1)` 的：查询时用布尔掩码过滤掉，
`remap()` 时按掩码裁掉编码数组。

**图索引删一个点是慢性病。** 因为图的连通性依赖每个点都还在：
如果点 `A` 被删了，它的所有邻居的邻接表里还留着一条指向 `A` 的边，
搜索走到那里就会撞空；如果只是简单地把 `A` 从邻居表里摘掉，
`A` 原本连接的两部分可能就此断开——而"断开"在小世界图上
是灾难性的，召回率会掉到接近零。

业界的几种处理方式，各有代价：

**方案一，不真删，只标记。** 查询时用 `keep` 掩码跳过被删的点
（遍历照走，如 15.5 所述）。这是最常见也最便宜的做法，
本教程的迷你实现和真实 Lance 的 `Bitset` 路径都是这个思路。
代价是：被删的点越多，图越"空转"，延迟越高、召回率越低。
**这就是为什么过滤搜索的延迟会显著上升**——图里全是
"能走过但不能返回"的点。

**方案二，重建。** 压实之后重映射行号时，干脆整张图重建。
本教程的 `HnswIndex.remap()` 就是这么做的，注释也写了原因：
"删一个点要修补它所有邻居的边……对小规模教学数据这是唯一
不会引入细微 bug 的做法"。真实 Lance 的 `IvfSubIndex::remap`
同样是重建（`builder.rs:1787-1795`，注释
"We can't simply remap the row ids in the graph because the vectors are changed"），
而 `HNSWIndex::remap` 干脆直接返回错误
`"Remapping HNSW in this way not supported"`。
代价是真实的：一个亿级向量的 HNSW 重建要几十分钟。

**方案三，修补式删除。** 删一个点时先找它的邻居，
把邻居们互相连起来（"缝合"缺口），再摘掉它。听起来优雅，
但缝合的时机很难把握——晚缝会导致搜索撞空，早缝会让图变成
一堆冗余的短边。工业实现里很少单独用。

Lance 有一个折中设计值得知道：`connect_stranded_level0`
（`builder.rs:983-1139`）在构建结束时从入口点做一次第 0 层的 BFS，
把**不可达的点**重新连回图里，每个锚点最多接一个孤立点，
所以第 0 层的度数上限是 `2m + 1`。这是"事后补连通性"的思路，
针对的是"插入顺序导致某些点被孤立"，不完全是删除，
但它是同一个问题家族的解药。

**删除的反面是增量插入，而图索引在这件事上反而是四类索引里最强的。**
倒排桶和 IVF 分区在追加时都只能"挂到旧的质心/码本上"，分布会逐渐偏离；
HNSW 的 `append()` 却是"把新点照常插进已有的图"——`HnswGraph.append`
走的还是同一套 `_insert` 三阶段，不重训、不引入近似。这是 HNSW 相对
IVF 系列最大的工程优势。但 **"图能增量插入"不等于"索引自动覆盖新行"**：
索引是在某个时刻建好的，之后写进表的行不在它里面，要等重新索引才进来。
本实现把这件事暴露在 `stats()["num_unindexed_rows"] = total_rows -
num_indexed_rows`；真实 LanceDB 同样有 `num_indexed_rows` /
`num_unindexed_rows` 这一对，而且未索引的行仍然查得到，只是走**更慢的
暴力兜底路径**（第 12 章 §12.6 把这条语义和它的坑讲透了）。所以
"append 之后要不要重建索引"是一道**延迟换覆盖率**的算术题：不重建，
新行的召回靠兜底；重建，就得再付一次 `O(n·log n·m·ef_construction)`。

**最后一个容易忽略的健壮性问题：入口点在图被重映射之后。**
`entry_point` 是图里的一个节点编号，图里所有边也都是节点编号。压实把行号
重排之后，如果只改 `row_ids` 而不重建图，`entry_point` 和每一条边都会
**指向错误的向量**——搜索照样能跑，只是结果全错，而且不报错。
本实现的 `HnswIndex.remap()` 干脆整张图重建，就是为了绕开这一类"静默错"。
这条约束不是 HNSW 独有的：第 9 章讲删除后索引重映射、第 23 章讲压实，
都是同一个问题——**只要索引里存的是"物理行号"而不是"稳定行 id"，
行号一变，索引就必须重建或重映射。**

## 15.9 LanceDB 特有的那件事：HNSW 不是顶层索引

到这里必须讲一个 LanceDB 特有的、和其他向量数据库不一样的地方：

**LanceDB 里没有"HNSW"这个顶层索引类型。HNSW 只作为 IVF 的子结构存在。**

`IndexType` 枚举（`rust/lance-index-core/src/lib.rs:53-92`）里，
向量索引的取值是 `IvfFlat`、`IvfSq`、`IvfPq`、`IvfHnswSq`、
`IvfHnswPq`、`IvfHnswFlat`、`IvfRq`——**没有任何一个叫 `Hnsw`**。
`derive_vector_index_type`（`details.rs:421`）拼出来的名字是
`"IVF_" + ("HNSW_" if hnsw else "") + FLAT|PQ|SQ|RQ` 这个形式。
甚至 `IVFIndex::search()` 本身是 `unimplemented!` 的
（`"IVFIndex not currently used as sub-index and top-level indices
do partition-aware search"`）——顶层走的是"分区感知"的搜索。

**所以 LanceDB 里你能建的最接近"纯 HNSW"的东西，是
`IVF_HNSW_FLAT`：一个分区数很小的 IVF，每个分区里一张 HNSW 图，
分区内不量化。** 本教程的迷你实现里保留了 `HNSW` 这个类型
（注册表里有 8 种类型），纯粹是为了让"整库一张图"和"分区内一张图"
可以对照着讲——那是教学方法，不是 LanceDB 的 API。

**分区内建图 vs 整库建图，实测的差别是：**

```
纯 HNSW      (ef=50)                recall@10 = 1.0000
IVF_HNSW_SQ  (nprobes=20, ef=50)    recall@10 = 0.9825
```

比分是 1.00 对 0.98。差异来自两个方向相反的效应：
分区内图的规模只有 `n/P`，层数更浅、搜索路径更短（**更快更准**）；
但**分区边界上没有边**，真正的最近邻如果落在相邻分区，
跨分区就得多探一个桶才能找到（**可能漏**）。
在小数据上后者略占上风，所以分区版差一点点。

为什么 LanceDB 还是选了分区内建图？因为整库图有一个致命的成本：
**每次查询都要在整张图里走，而"按分区过滤"会退化成
"图搜索 + 过滤"**——你要在图里走很久才能凑齐属于被探分区的点。
分区内建图把"探 nprobes 个桶"的粗量化收益完整保留下来，
同时还额外拿到了"每张图更小"的好处。

## 15.10 分区内图索引的召回率与延迟

混合索引 `IVF_HNSW_SQ` 有三个旋钮：`nprobes`（探几个分区）、
`ef`（每个分区内搜多深）、`refine_factor`（要不要精确重排）。
我们在 3000 × 32 维、20 分区、每分区一张 m=8 的图上把前两个旋钮
扫成一个二维网格（数据见下，但别把它当表读——它本来就是个二维网格，
按"固定一行、扫另一列"才看得清对比关系）。

**先固定 `ef=50`、扫 `nprobes`：** 1 / 4 / 20 分区对应的 recall@10 是
0.9675 / 0.9825 / 0.9825，延迟是 1.02 / 2.69 / 13.51 毫秒。
**再固定 `nprobes`、扫 `ef`：** `nprobes=1` 时 20 / 50 / 100 的 recall 是
0.9600 / 0.9675 / 0.9675（延迟 0.56 / 1.02 / 0.95 毫秒）；
`nprobes=4` 时是 0.9750 / 0.9825 / 0.9825（延迟 1.33 / 2.69 / 4.27 毫秒）；
`nprobes=20` 时是 0.9750 / 0.9825 / 0.9825（延迟 8.40 / 13.51 / 19.18 毫秒）。

**`nprobes` 和 `ef` 是两个正交的旋钮，而且都很快饱和。**
nprobes 从 1 涨到 4，recall 从 0.96 涨到 0.9825——已经是封顶了；
再涨到 20（探满所有分区）一点没变，延迟却涨了 6 倍。
ef 从 20 到 50 只涨了 0.0075 的 recall，再往上完全不动。

**这个饱和值是 IVF_HNSW_SQ 的天花板，它来自 SQ 的量化误差——
所以这个索引里再调 nprobes 和 ef 都没用，要动只能动量化。**
这正是"先隔离误差源"方法论的价值：看到平台就知道该换哪个旋钮。

另外注意延迟的量级：探满 20 个分区、ef=100 时是 19 毫秒，
而探 1 个分区、ef=20 时只要 0.56 毫秒。**分区内图索引的延迟几乎完全
由"探了多少个分区"决定**，因为每个分区都要跑一次独立的图搜索。
这是它和纯 HNSW 最大的延迟差异：纯 HNSW 是"一次图搜索"，
IVF_HNSW 是"nprobes 次图搜索再合并"。

## 15.11 IVF_HNSW_PQ 与 IVF_HNSW_FLAT：选型谱的另一端

§12.3 把"超过 1000 万只能用 `IVF_HNSW_PQ` 或 `IVF_RQ`"写成了一个结论，
§16.9 的收尾清单也点了名，但前面几节只拆了 `IVF_HNSW_SQ` 这一型。
这里把另外两种补上——它们其实只是把 §15.10 那张网格里的"SQ"换成别的
量化档，结构上没有任何新东西。

**`IVF_HNSW_PQ`：分区 + 分区内图 + 残差乘积量化。** 它和
`IVF_HNSW_SQ` 逐字对应，只是分区内每条向量存的不是 SQ 码、而是 PQ 码。
我们在同一份 3000 × 32 维数据上量了一遍（20 分区、
`num_sub_vectors=8`、8 bit、每分区一张 m=8 的图、`ef_construction=40`，
测量脚本 `chapter_15` 的 `IVF_HNSW_PQ` 一节）：

```
IVF_HNSW_PQ 压缩比 = 16.0（码字节 24000，原始 384000）

nprobes   ef   recall@10   recall@10(refine=8)
      1   20    0.7225      0.9775
      1   50    0.7200      0.9775
      4   20    0.7325      1.0000
      4   50    0.7300      1.0000
     20   20    0.7325      1.0000
     20   50    0.7300      1.0000
```

读法和 §15.10 的 `IVF_HNSW_SQ` 完全一样：`nprobes` / `ef` 涨上去，recall
只从 0.72 爬到 0.73 就平了——**这个平台来自 PQ 的量化误差，不是分区或图
没搜够**（对照不吃 IVF 的 `IVF_PQ`：§14.5 里 M=8、8 bit 不加 refine 时
recall 也是 0.69 这个量级）。**要突破平台只能动量化的那一层**：
`refine_factor=8` 一加，召回立刻回到 0.98~1.00。这正是 §15.10 那条
"先隔离误差源"方法论的又一次应用——看到平台先判断它来自哪一层，再决定
动哪个旋钮。它相对 `IVF_HNSW_SQ` 的取舍是**用 4 倍更大的压缩（16 倍对
4 倍）换一个更低的召回平台、再靠 refine 补回来**，所以选它只有一个理由：
内存实在装不下 SQ、只能上 PQ（这正是 §12.3 把 1000 万以上的场景指向它的
原因）。

**`IVF_HNSW_FLAT`：把这层量化再去掉。** 结构上它就是"分区数很小的 IVF +
每个分区里一张 HNSW 图、分区内不量化"，也就是 LanceDB 里最接近"纯 HNSW"
的东西（§15.9 讲的 `IVF_HNSW_FLAT` 就是这一型）。它省的是"分区裁剪"的
扫描量，**内存一点都没省**——分区内保留完整 float32 向量，比 `IVF_FLAT`
还多花一张图的边表。**这一型本教程没有实测**：迷你实现里没有
`IVF_HNSW_FLAT` 这个类（`mini_lancedb/index/__init__.py` 的注册表里只有
`IVF_HNSW_SQ` 和 `IVF_HNSW_PQ`），拿不到可复现的数字，所以这里只按结构讲清
它在选型谱上的位置（高召回、不省内存的那一端），不编数。

把这三型排在一起，规律很清楚：**`IVF_HNSW_SQ` / `IVF_HNSW_PQ` /
`IVF_HNSW_FLAT` 是同一个结构（IVF 分区 + 分区内 HNSW）配上三种量化器，
召回平台和内存都由那个量化器决定，图那部分三条都省不了。** §12.3 说
"超过 1000 万只能用 `IVF_HNSW_PQ` 或 `IVF_RQ`"，指的就是这条：边表和点数
成正比，能压的只有"每条向量存多少字节"，而 PQ / RQ 是唯二能压到 1/16
以上的档。

## 15.12 过滤搜索的延迟方差：为什么 LanceDB 推荐 IVF_PQ/IVF_RQ

文档里有一条建议：**过滤较强的工作负载，别用 HNSW 系，用 IVF_PQ 或 IVF_RQ。**
我们实测验证了这个建议背后的机制。

同一份数据、同一个 HNSW，在"保留 10% 的行"的强过滤下，`ef` 取
50 / 100 / 200 的单查询延迟是：无过滤 0.9301 / 1.4833 / 2.2131 ms，
强过滤 4.6830 / 11.1562 / 15.3121 ms，**倍数 5.0x / 7.5x / 6.9x**。
（这几组延迟和 15.5 不是同一次运行——同一台机器两遍能差 2~3 倍，
见 15.7 的说明；真正稳定的只有同一个索引在同一次运行里的比值。）

**延迟涨了 5 到 7.5 倍，而且这个倍数是随过滤强度变化的——这就是"延迟方差"。**
它的机制就是 15.5 埋下的那个伏笔：被过滤的点**照样参与图的遍历**
（否则图会断），只是不进结果堆。完整的推演在第 18 章 §18.8 讲
prefilter / postfilter 时展开，这里只记现象：过滤掉 90% 的点之后，
`ef=100` 的束搜索还是要扩展同样多的点，但**能进结果堆的候选少了 90%**，
于是终止条件 `len(results) >= ef` 迟迟不满足，搜索不得不扩展更多点。
过滤越强，空转越多，延迟越高。

而 IVF 系列的过滤是另一条路径。看迷你实现的 `IvfBase.search`：

```python
cand = self._gather(parts)
if mask_arr is not None:
    cand = cand[mask_arr[cand]]      # 被删的行连候选都当不了
    if cand.size == 0:
        continue
```

**被过滤的行被直接从候选集里删掉，一个距离都不算。**
过滤越强，候选集越小，查询越快——方向和 HNSW 相反。
同一份过滤条件下：

```
HNSW   (ef=100)          recall@10 = 1.0000   延迟 = 9.7941 ms
IVF_PQ (nprobes=20, M=8) recall@10 = 0.9225   延迟 = 2.1961 ms
```

**HNSW 在强过滤下不但慢 4.5 倍，而且这里它 recall 更高纯属偶然**
（数据小、ef 大、能凑齐 300 个存活行），真实场景里 HNSW 在
强过滤下是"又慢又不准"。这就是为什么 LanceDB 的建议是
**过滤型工作负载用 IVF_PQ / IVF_RQ**：倒排结构的过滤是"剪枝"，
图结构的过滤是"空转"。

说清楚哪些数字可信：**"HNSW 强过滤比无过滤慢 5~7.5 倍"是同一个索引
在同一次运行里的比值，稳定；而"HNSW 9.79 ms 对 IVF_PQ 2.20 ms"
是跨索引的绝对值比较，会被机器负载影响**（挂钟时间为什么不可复现，
见 15.7 的说明；13.10 里那个翻车也是同一个原因）。真正跨环境成立的是
机制，不是这两个毫秒数。

这里还有一个细节和 Lance 的 ACORN 实现呼应：它的选择逻辑里
"剩余比例小于 10% 就退回暴力 `flat_search`"。这正是在承认
"强过滤下图搜索不划算"——当候选太少时，扫一遍比走图快。

## 15.13 小结

**HNSW = 把跳表搬到近邻图上。** 每层解决一个矛盾：
上层长边保证路径短，下层短边保证贪婪可达。层高是几何分布，
`ml = 1/ln(m)` 让每层搜索代价与点数无关，总复杂度 `O(m·log_m n)`。

**Lance 的层高公式是 `min(floor(-ln(U)·ml), max_level-1)`**，
上限是 `max_level-1`（默认 `max_level=7`），层高 RNG 固定种子 42。
默认参数 `m=20, ef_construction=150`。

**插入分三阶段**：Lance 里新点每层选 `m` 条边，**`2m` 只作为 level-0
互惠边的上限**（本教程的迷你实现对新节点也用 `2m`，是个已知差异）；
反向加边顶爆出度时会重新剪枝。

**Algorithm 4 的多样性剪枝是 HNSW 一半的价值所在。** 消融实测：
m=8 时朴素"最近 m 个"把 recall 从 1.00 打到 0.465，
而且边更多、内存更大。Lance 用 `extendCandidates=false`、
`keepPrunedConnections=true`。

**`ef` 是查询期唯一旋钮，必须 ≥ k**，Lance 默认 `ef = k + k/2`（k 已乘
refine_factor）。收益比 `nprobes` 更快饱和；饱和之后继续加大 `ef`
只线性变慢、不再变准（实测加到 `n` 仍是 recall 1.0000）。与之相对，
**`ef_construction` 不是召回旋钮**——只要不小于 ~20，查询表现就和 200
没差别。

**图索引的内存大头是向量，不是图**（32 维时向量占 63%）；
但换成 SQ 编码之后图反而成了大头。

**删除是图索引的慢性病**：不能真删，只能标记（查询空转）或者重建
（几十分钟到几小时）。Lance 的 `HNSWIndex::remap` 直接报错，
`IvfSubIndex::remap` 走重建。**增加则相反——HNSW 是少数能真增量插入的
向量索引**（新点照常插进已有的图，不走重训），但插入只决定
`num_unindexed_rows`，不会让索引自动覆盖新行。**任何"只改 `row_ids`、
不重建图"的重映射都会让 `entry_point` 和边指向错误的向量**，
所以压实必须连带重建索引。

**LanceDB 里没有顶层 HNSW**，只有 `IVF_HNSW_*`。
分区内建图保住了粗量化的收益，代价是分区边界上没有边
（实测 recall 0.9825 对整库图的 1.0000）。

**强过滤下 HNSW 的延迟涨 5~7.5 倍且随过滤强度变化**，
因为被过滤的点仍参与遍历；IVF_PQ/IVF_RQ 的过滤是剪枝，方向相反。
这就是 LanceDB 推荐过滤型负载用 IVF_PQ/IVF_RQ 的原因。

**建图时间是 `O(n·m·ef_construction)` 量级**，比 IVF 贵得多。
50000 个点上 Python 实现要 128 秒——生产环境里重建 HNSW 是要排期的。
