# 第 18 章　标量索引与 data skipping

向量索引和标量索引的目标**完全不同**，这一点决定了它们从头到尾的接口形态都不一样。

向量索引是"大概率的近似"：它允许漏掉真正的最近邻，换取亚线性的查询时间。
所以它的接口里必须显式携带"召回率旋钮"（`nprobes` / `ef` / `refine_factor`），
而且必须能回答"这个结果是不是精确的"。

标量索引是"精确的集合运算"：`WHERE a = 1 AND b > 5` **不允许有误差**。
漏一行就是错的。这个差别带来了三个直接后果：

**第一，接口的形状不同。** 向量索引返回"最近的前 k 个"（带距离）；
标量索引返回一个**行号集合的表达式**。真实 Lance 的 `ScalarIndex` trait 就是
`fn search(&self, query: &dyn AnyQuery) -> Result<Option<ScalarIndexExpr>>` ——
返回 `None` 表示"这个问题我答不了，请退化成全表扫描"。本实现的
`mini_lancedb/index/base.py` 照抄了这个签名。

**第二，索引之间可以组合。** 因为答案统一是"行号集合"，`And` / `Or` / `Not`
就能跨索引做交并补：`"hello" AND age BETWEEN 3 AND 9` 可以是 FTS 索引和
BTREE 索引各自答一半再相交。

**第三，"近似"仍然存在，但方向相反。** 标量索引可以给**超集**
（多给一些行，让上层再筛一遍），但绝不能给**子集**。真实 Lance 用三态表达
这一点（`rust/lance-select/src/result.rs` 的 `IndexExprResult`）：

```
exact(m)    -> { lower: m,        upper: m,        exact: true  }   索引保证精确
at_most(m)  -> { lower: 空,       upper: m,        exact: false }   只保证"不超过 m"（NGram / ZoneMap 的常态）
at_least(m) -> { lower: m,        upper: 全允许,   exact: false }   只保证"至少有 m"
```

`upper` 之外的**一定不在**答案里，`lower` 之内的**一定在**。凡是
`exact: false` 的叶子会给整棵树设 `skip_recheck = false`，扫描阶段必须
再过一遍原始谓词。NGRAM 就是这样：它标 `needs_recheck = true`，
结果永远是 `at_most` 的 `upper`，扫描阶段必须再跑一遍 `contains`。

本实现用一个更朴素的等价物：`search()` 要么返回一个**精确的**
`ExactMatch`，要么返回 `None`（答不了，请退化成扫描）。两种表达的落点
不同而已：**"我答不了"必须是一个能被上层看见的显式信号**，
而不是"看起来给了答案其实不精确"。ZONEMAP 永远返回 `None`（它根本不产生
行号集合）；NGRAM 在内部完成"候选 → 验证"两步之后才返回精确集合，
并把中间那个候选集单独暴露出来（`candidates()`），
好让测试能证明"假阳性真的存在、验证步骤不能省"（18.4 会给出实例）。

下面逐个讲五种标量索引。每一节都按同一个模板：数据结构、
能回答什么、不能回答什么、空间代价、什么时候用、什么时候不用。

## 18.1 BTREE：真正的 B+ 树

### 为什么是 B+ 树而不是哈希表

哈希表能做到 O(1) 的等值查找，但**范围查询**在它上面是 O(n) —— 因为哈希
把顺序彻底打碎了，`age BETWEEN 30 AND 40` 无从下手。数据库里范围谓词
（`>`、`<`、`BETWEEN`、`ORDER BY ... LIMIT`）出现得比等值谓词还频繁，
所以标量索引的主力结构必须**保序**。

在保序结构里，为什么不用平衡二叉搜索树？两个原因，都跟"扇出"有关。

B+ 树的扇出大（一个节点几百个键），**树高极低**。本实现实测：100,000 个
唯一键、每叶最多 64 个键时，`depth=3`、`nodes=3,225` —— 三次页读取就能
定位到任意一个键。红黑树要 ~17 次。在磁盘/页缓存场景下，"层数"直接等于
I/O 次数，这就是 B+ 树赢的原因。

B+ 树还把**数据全放在叶子**，内部节点只存分隔键（`keys[i]` 是
`children[i+1]` 的最小键）。于是内部节点很小、缓存友好，而且**叶子之间有
链表**，范围扫描是"定位一次 + 顺序走到底"，不需要反复回根节点做中序遍历：

```
        [ 30 | 70 ]                     <- 内部节点：只放分隔键
        /    |     \
   [1..29] [30..69] [70..99]            <- 叶子：键 + 行号列表，next 串成链表
        ->       ->        ->
```

### 为什么行号存成"一个键对应一串行号"

一列索引不是主键，`status = 'active'` 会命中几十万行。如果每个
`(键, 行号)` 都存一个条目，B+ 树会被重复键撑爆。所以叶子里的条目是
`(键, 值, 行号数组)` —— **键唯一，行号是列表**。这也是为什么 B+ 树天然
适合做"列索引"而不是"主键索引"。

这里有个很容易踩的坑，本实现的注释里专门标了：内部节点的 `keys[0]` 是
"**第 2 个**孩子的最小键"，**不是**这棵子树的最小键。父节点维护分隔键时
**不能**读 `child.keys[0]` —— 那会在"往最左边插入更小的键"时给出偏大的
边界，表现为范围扫描莫名漏掉或带进来一些行。正确做法是显式带上
`minkey`（子树真正的最小键），沿递归路径逐层往上传。

### null 不进索引

这是刻意对齐 SQL 的三值逻辑：`col = 1` 对 NULL 行求值是 UNKNOWN 而不是
TRUE，所以 NULL 行永远不该被"等于/大于"这类谓词命中。本实现的
`BTreeIndex.build()` 把 null 行数记在 `stats()["null_rows"]` 里，
并且 `row_ids` 只包含**真的进了索引**的行 —— 这一点很要紧：`And`/`Or`/`Not`
的求值以 `row_ids` 为"全集"，于是 `NOT(col = 1)` 不会把 null 行算进去。
测试 `test_btree_null_rows_are_not_pulled_in_by_not` 钉的就是这条。

### 能回答什么，不能回答什么

`RangeQuery` 是它的本命（保序结构的强项）；`IsIn` 单值就是等值查找；
`IsIn` 多值每个值查一次再合并 —— **值很多时不如 BITMAP**，这就是 LanceDB
的查询规划器要按"基数列 + 谓词形态"挑索引的原因。`IsIn` 在很多值时
真实的 Lance 会转而用 BITMAP。

FTS 的 `MatchQuery`、向量检索的谓词这类它一律**承认自己答不了**，
返回 `None`。这一条比"能跑但很慢"更诚实。

### 实测

20 万行唯一 id 列：

```
build 438.0 ms | range(15 万..15 万+100) 0.016 ms | depth=3 nodes=6451 keys=200,000 cardinality=1.0000
等值(RangeQuery 单点) 0.057 ms -> [123456]
大区间(0..5 万，25% 命中) 13.63 ms -> 50,001 行
```

小范围查询 16 微秒 —— 这就是"三次页读取"的威力。但大区间扫描是 13.63 ms，
因为 25% 的行都要返回；**索引能省的只是"定位"，不能省"输出"**。
`cardinality` = 不同值 / 总行数 = 1.0，说明这一列**每个值都不同**，
是 BTREE 的理想输入。

### 与真实 Lance 的差别

真实 Lance 的 BTREE 是**磁盘上分页**的（`page_data.lance` +
`page_lookup.lance`），规范里的规模论证是：10 亿个值时，索引可存 256K 个
各 4K 的叶子，**B-tree 元数据只需几 MiB 内存**，并把任何搜索收窄到 4K 个值
（规模论证引自 Lance 格式规范；文件与页布局的通用讨论见第 3 章）。
`page_lookup.lance` 的列是
`min` / `max` / `null_count` / `page_idx` —— 注意**页内 min/max 也在页表里**，
所以范围查询可以在页级别先剪一遍。每页行数 `batch_size` 默认 `"4096"`。
`page_data.lance` 只有 `values`（有序值）和 `ids`（每值对应的物理行地址
`fragment_id << 32 | offset`）。

本机用真实 `lancedb` 0.40.0 建了一个 BTREE 索引验证文件名：

```
page_data.lance   2945 B
page_lookup.lance  701 B
```

和规范一致。本实现把所有节点放在内存里做**真正的分裂**，形状更像教科书
B+ 树（教学上更容易看清"分裂"和"分隔键维护"这两件事），落盘时拍平成
"有序的 `(值, 行号列表)` 两张表"重建 —— 真实 Lance 也是这样，
索引文件里存的是"按序遍历能顺序读到的页"，而不是指针结构。

## 18.2 BITMAP：每个取值一张位图

### 结构

```
"active"  -> 1010 0110 0100 1000 ...   (每个 bit 对应一行)
"pending" -> 0101 0000 0000 0001 ...
"closed"  -> 0000 1001 1011 0011 ...
```

一张位图 = 每个被索引行占 1 bit。于是：

```
col = 'x'                -> 取那张位图
col IN (a, b, c)         -> 三张位图按字求 OR
col = 'a' AND col2 = 'b' -> 两张位图按字求 AND
NOT ...                  -> 按字取反再和有效位掩码相与
```

关键在第三步：一次布尔运算处理 **64 行**（一个 `uint64` 字），而按行号集合
做交并是"一次一行"。这就是位图索引在低基数列上能把过滤速度拉起来一个量级的
全部原因 —— **不是算法更聪明，是批处理粒度更大。**

### 空间代价：位图会爆炸

位图的总位数 = `不同值个数 × 行数`。20 万行的实测（`bits_per_row` =
每行摊到多少**比特**）：`status`（4 个不同值）位图总共 100,000 字节、
每行 4.0 bit、平均每值命中 50,000 行；`region`（3,000 个值）位图
75,000,000 字节、每行 3,000.0 bit、平均每值命中 66.7 行；`user_id`
（200,000 个值，每个值都不同）位图 5,000,000,000 字节、每行 200,000.0 bit、
平均每值命中 1.0 行。

`user_id` 那一列是 5 GB —— 对一列本来就只占 1.6 MB（20 万 × 8 字节）的数据。
**位图总量是 O(值个数 × 行数)**，高基数列上它的增长率是 n² 而不是 n。
换一个口径看同一件事，固定 20 万行、只改不同值个数：

```
基数      2 : bits_per_row =      2.0
基数     16 : bits_per_row =     16.0
基数    256 : bits_per_row =    256.0
基数  4,096 : bits_per_row =   4096.0
基数 65,536 : bits_per_row =  65536.0
基数 200,000: bits_per_row = 200,000.0
```

为什么是"≈"而不是"精确等于"：`bits_per_row = (值个数 × nwords × 64) / n`，
其中 `nwords = ⌈n / 64⌉` 是每张位图占几个 `uint64` 字。只有 `n` 恰好是 64
的整数倍时 `nwords × 64 = n`、比值才是 1；一般情形比值略大于 1，所以
`bits_per_row` 会**略大于**基数。上面那张表用的是 20 万行（`200,000 ÷ 64 =
3,125`，整除），所以看着"精确等于"；换成 100,000 行就不整了（`nwords = 1,563`、
`⌈100000/64⌉ × 64 = 100,032`），后面 §18.3 的 LABEL_LIST 例子会因此算出
50.016 而不是 50。

`bits_per_row` **≈ 基数**，判据就在这个数字里：**远小于 8 说明很划算**
（`status` 是 4，每行摊 4 bit = 半字节），**超过几十就该换索引**。
真实 LanceDB 官方文档给的门槛是"**少于 1,000 个不同值**的布尔/数字/字符串"
用 BITMAP，另一处写"**几千个以内**不同值"（两处口径都来自 LanceDB 官方
文档；"低基数列用字典编码而不是按值存"的代价，第 4 章 §4.4 从编码的角度
讲过一遍）。我们的 `region` 列刚好卡在 3,000 个值 —— 3,000 bits/row 就是
**每行 375 字节**，是"一行一个 int64"（8 字节）的 47 倍。
这一列已经在"能跑但荒谬"的区域了。

### 两个"行号集会变成空集"的坑

**第一，null 行不在任何一张位图里**，所以 `NOT` 的补集必须限制在"非 null 行"
上（否则 null 行会被 `NOT (col = 'a')` 捞出来，而 SQL 三值逻辑要求它不匹配）。
本实现的 `valid_words()` 就是那个掩码：最后一个字里超出行数的 bit 必须清掉。
不清掉的话 `NOT` 会凭空多出一批"行号越界"的命中 —— 这是位图实现里最常见的
off-by-64 错误。

**第二，位图的长度是"被索引行数"，不是 row_id 的最大值。** 如果拿 row_id
直接当 bit 下标，一个 `id=10^9` 的行会要一张 125 MB 的位图。所以本实现一律在
"局部行号"（0..n-1）上建位图，返回时再经 `self.row_ids` 映射回真实行号。
真实的 Lance 位图按 fragment 建，本质上也是这个思路
（fragment 内的行偏移 + fragment id）。

### RangeQuery 明确返回 None

位图把顺序打碎了，`col BETWEEN 3 AND 9` 在位图上只能"把值表里落入区间的值
逐个取位图再 OR"，值多的时候比全表扫还慢。本实现的 `BitmapIndex.search()`
对 `RangeQuery` **明确返回 `None`** —— 承认答不了、交给规划器换 BTREE
或退化成扫描，比"能跑但很慢"更诚实。真实 Lance 的 BITMAP 其实也支持
Range（Lance 格式规范写着"Range：范围内所有值的 bitmap 求并"；索引文件的
组织见第 3 章），但那正是"值少才划算"的操作 —— 值多的时候返回 `None`
才是对的。

### 实测与落盘

```
BITMAP / cat (4 个值, 100,000 行): build 116.3 ms | IN(1 值) 0.599 ms | 850,294 B | bits/row 4.0
```

850 KB 对一列 800 KB 的原始数据（100,000 × 8 字节的字符串引用）—— 1.06 倍，
很划算。

真实 Lance 的 BITMAP 是单文件 `bitmap_page_lookup.lance`，schema 是
`keys`（唯一值）+ `bitmaps`（序列化的 `RowAddrTreeMap`）（Lance 格式规范；
单文件索引的布局见第 3 章）。本机实测确认了这个文件名。

## 18.3 LABEL_LIST：列的值本身是个列表

`tags = ["python", "db", "sql"]` 这种列，BITMAP 处理不了 —— 它的前提是
"一行 ↦ 一个值"。差别在三个地方，都很具体：

**一行会出现在多张位图里。** BITMAP 的位图是一份**行集合的划分**
（每行恰好出现在一张位图里，所有位图 OR 起来就是全集）；LABEL_LIST 不划分，
OR 起来会重复计数。

**`SUM(位图的 popcount)` 得到的是"标签实例数"而不是行数。** 实测 100,000 行、
50 种标签、平均每行 1.48 个标签 —— 这个"1.48"就是两个数字的比值。

**没有标签的行（`[]` 或 null）不在任何位图里。** 实测 100,000 行里有
24,984 行是空的（25.0% —— 生成时每行取 `randint(0,3)` 个标签，
4 种取值，取到 0 的概率正好 1/4）。这一点和 BITMAP 的 null 行一样，
但原因不同：BITMAP 是"这一行的值未知"，LABEL_LIST 是"这一行没有值"。

**位图运算是完全一样的** —— 还是按 64 位字做 AND/OR/NOT。所以本实现
直接让 `LabelListIndex` 继承 `BitmapIndex`，只重写"构建"（一行要写进多个
位图）和"谓词翻译"（`array_contains` 是"集合成员"而不是"标量相等"）
两部分。这不是偷懒，是"两者的数据结构和算法本来就该是同一套"的诚实表达。
真实 Lance 也是这样：`LabelListIndex` 内部就是 `Arc<BitmapIndex>` 加一个
list-null 位图（转引上游 Lance 源码 `scalar/label_list.rs:95`；这种"复用
底层位图"的思路和第 4 章里"编码层复用同一套列结构"是同一个设计习惯），
落盘用的是**和 bitmap 相同的** `bitmap_page_lookup.lance`。本机实测三种索引
的落盘文件名，BITMAP 和 LABEL_LIST 确实是同一个：

```
BTREE       -> page_data.lance + page_lookup.lance
BITMAP      -> bitmap_page_lookup.lance
LABEL_LIST  -> bitmap_page_lookup.lance
```

### 查询语义

`array_contains(col, 'x')` 是最直白的：取 `x` 的位图。真实 Lance 支持的三个是
`array_has` / `array_contains`（单 label）、`array_has_all`（所有 label 位图
求交）、`array_has_any`（求并），**全部 Exact**（Lance 格式规范）。

本实现里 `col IN ('a', 'b')` 定义为"**含 a 或含 b**"（任意命中）。
SQL 里 `IN` 对列表列没有标准定义（各家方言不同），所以我们挑了一个最容易
解释的：把列表列的 `IN` 读成"和给定标签集合有交集"。想表达"同时含 a 和 b"
要用 `AND([ArrayContains('a'), ArrayContains('b')])`。

**它答不了的：** `count(tags) > 2`。位图表达不了"出现两次"，
所以本实现在构建时把同一行里重复的标签**只记一次** —— 这正是位图索引
答不了计数的原因。要答计数得换列存/倒排。

**它也不该用在标签种类爆炸的列上。** 标签种类数就是位图张数。按 10,000 个
标签 × 1 亿行算，就是 10,000 × 12.5 MB = 125 GB，直接爆掉。真实 LanceDB
因此对 LABEL_LIST 有基数上限检查。本实现把这件事写在 `stats()["bits_per_row"]`
里：实测 50 种标签 × 100,000 行 **≈ 50 bits/row** —— 严格算是 **50.016**，
因为 100,000 不是 64 的整数倍（`⌈100000/64⌉ × 64 / 100000 = 1.00032`，
再乘基数 50 就是这个数），正是上面 §18.3 说的"略大于基数"。

### 实测

```
LABEL_LIST / tags: build 266.6 ms | array_contains('t7') 0.177 ms | 2,226,224 B
                   labels=50  labels/row=1.48  bits/row=50.0
```

0.177 ms 对一个 100,000 行的表 —— 因为位图运算是字级的，一次 AND 处理 64 行。

## 18.4 NGRAM：加速 `LIKE '%abc%'`，但只给候选集

### 为什么需要它

`LIKE '%abc%'` 用不上 BTREE（保序结构只能答前缀），也用不上倒排
（倒排按**词**切，而子串可能横跨词边界，`"data base"` 里搜 `"abase"` 是搜不到的）。
于是这类查询在数据库里天然只能全表扫 —— 直到你给列建**字符级 n 元组索引**：

```
"database"  的 3-gram = {dat, ata, tab, aba, bas, ase}
"abacus"    的 3-gram = {aba, bac, acu, cus}
```

查 `'%aba%'` 时，先算 `aba` 的 3-gram = `{aba}`，取它的 postings，
只对这批候选做**真正的子串判断**。

### 假阳性不可避免 —— 一个具体的例子

查询 `'%abacus%'`（5 个字符）的 3-gram 是 `{aba, bac, acu, cus}`。
一行只要有这四个**碎片**，就同时命中全部四个 gram —— 但它并不含 `abacus`。
**gram 命中只证明了"碎片都在"，不证明"顺序和距离对"。**

我暴力搜了一个最短的反例：`abacacus`。它的 3-gram 是
`{aba, aca, acu, bac, cac, cus}`，包含 `abacus` 的全部四个 gram，
却不含子串 `abacus`。实测：

```
语料: ["abacacus", "abacus", "the abacus rolls"]
contains('abacus'): {'raw_candidates': 3, 'matches': 2, 'false_positives': 1}
被验证掉的: ['abacacus']
```

所以流程永远是两步：

```
候选 = ⋂(每个 gram 的 postings)              ← 用索引，便宜
结果 = [d for d in 候选 if needle in value[d]]  ← 必须精确验证，贵但候选很少
```

这就是搜索引擎里 **"index → candidate → verify"** 的标准模式
（Lance 的 NGRAM、Lucene 的 `NGramTokenFilter` + 后置验证、PostgreSQL 的
`pg_trgm` 都是这个套路）。**假阳性不可避免**，唯一能消除它的是"把整个字符串
也放进索引"——那就是把索引变成数据表了。

本实现把 `candidates()` 单独暴露出来，就是为了让测试能断言
"候选数 > 真实命中数"（`test_ngram_candidate_superset_and_verification_matters`），
亲手证明验证步骤不可省。

### 参数选择和它的代价

`n=3` 是通用默认（`pg_trgm`、Lucene、Lance 都是）。n 太小（2）→ 每个 gram 的
postings 太长、候选太多，验证反而成了瓶颈；n 太大（5）→ gram 种类爆炸、
索引变大，而且短查询（少于 n 个字符）**根本用不了索引**（本实现直接返回
`None` 让上游走全扫 —— 这是诚实的退化，不是 bug）。

实测这句"n 太小会让 postings 太长"的量级（100,000 行、内容都是
`item-NNNNNN-abcdef` 模板）：

```
'abcdef'         candidates=100,000   ← 子串到处都是，索引毫无剪枝力
'item-000042-'   candidates=1
'42-abcdef'      candidates=1,000
'ab'             candidates=None      ← 2 字符 < n=3，gram 索引用不上
'abcdefg'        candidates=0
```

`'abcdef'` 这一行是关键：**当子串出现在几乎每一行里时，n-gram 索引
帮不上任何忙**，候选集就是全集（`max_rows_per_gram=100,000`，
即最热的那个 gram 覆盖了整张表）。真实 Lance 的 `stats()` 里专门有
`max_rows_per_gram` 这个字段，就是为了让人一眼看出"索引没区分度"。
实测这次 `contains("item-000042-")` 花了 40.9 ms，而候选只有 1 行 ——
时间全花在**求交集时展开那几个热 gram 的巨大 postings**上，
不是花在验证上。这是 n-gram 索引的真实成本结构。

### 真实 Lance 的 NGRAM 和本实现的差别

真实 lance-index 里 `const NGRAM_N: usize = 3;` —— **只做 trigram，不可配**，
而且 `tokenizer` 字段是**固定的** `NGRAM_TOKENIZER`，"不可配（stemming 会
破坏子串语义）"（转引上游 Lance 源码；"tokenizer 不可配"这件事和第 17 章
§17.4 的分词器管线正好对照着看）。`contains(col, pattern)`
在 pattern **字符数 < 3** 时直接 `return None`，否则产出
`TextQuery::StringContains` 且 `needs_recheck = true` —— 这就是"索引只给
候选集"在真实实现里的落点，和本实现的 `_CannotAnswer` 完全对应。
真实 Lance 的 NGRAM 索引里**只有 gram → 行号**，验证时回表取值；
本实现把原值也留了一份（`self.values`），因为教学实现没有"表"可回。
多出来的这一份代价，在 `stats()["stored_value_bytes"]` 里明明白白地列着，
不做掩饰：实测 100,000 行时是 **1,800,000 字节**（每行的 `item-NNNNNN-abcdef`
正好 18 字节，100,000 × 18），占索引总落盘 16,612,560 字节的 **10.8%**
（这两个数都能对上脚本 `examples/verify/ch18_scalar_index_table.py`：
`NGRAM` 那一行的 `disk B` 就是 16,612,560）。

顺带记一个容易混的口径：同样这份数据里还有个 **2,200,000** 的数字，
它**不是** `stored_value_bytes`，而是落盘的 `values.json` 文件大小 ——
JSON 给每个串各加了一对引号和一个逗号，18 字节的串编码后占 22 字节，
100,000 × 22 = 2,200,000。**"逻辑原值"（1.8 MB）和"JSON 落盘"（2.2 MB）
差在这一层编码上，别把两个数当成一回事。**

还有一个 API 层面的实际情况（本机 `lancedb` 0.40.0 实测）：**Python API 里
没有可创建的 `NGram` 索引类型**。`create_scalar_index(col, index_type="NGRAM")`
报 `ValueError: Unknown index type NGRAM`，`lancedb.index` 里也没有 `Ngram`
配置类。要字节串索引得用 `Fm()`（FM-Index，落盘 `part_0_fm.lance`），
要子串"分词"索引得用 `FTS(base_tokenizer="ngram")`——它走的是 FTS 的那四个文件。
上游源码里 `IndexType::NGram = 5` 确实存在（转引上游 Lance 源码；`IndexType`
的取值表见第 12 章 §12.3），但 0.40 的 Python 入口没有把它暴露出来。
**文档说的索引类型和当前 SDK 能建的索引类型不是一回事，以实测为准。**

### 答不了的形态

本实现的 `Like` 只支持 **"没有其它通配符的包含式"**（`'%abc%'`）和
**"完全无通配符的等值"**（`'abc'`）两种形态；`'abc%'`（前缀）、
`'%abc'`（后缀）、`'a%c'` 一律返回 `None`。理由是前缀/后缀确实能用 gram
取候选，但"用前 n 个字符的 gram"取到的候选集几乎等于全集，加速比可以忽略，
不如把"我不会"说清楚。

`_` 也是通配符（匹配任意单字符），所以 `'%a_c%'` 里的 `a_c` **不能**当作
字面量去搜，否则会静默漏掉 `"abc"`。这类模式一律返回 `None` —— 测试
`test_ngram_like_underscore_is_not_treated_as_literal` 钉住了它。

大小写不敏感的子串查询也答不了：gram 是按原始大小写建的。真实实现要么
再建一份 `lower(列)` 的索引，要么就全扫。本实现选了后者并显式返回 `None`。

## 18.5 ZONEMAP：严格说它不是索引

### 它是"按块统计 + 跳过整块"

```
块 0（第 0 ~ 1023 行  ）: min=3   max=57   nulls=0
块 1（第 1024~2047 行）: min=61  max=118  nulls=2
块 2（第 2048~3071 行）: min=120 max=204  nulls=0
```

查询 `WHERE x BETWEEN 0 AND 50` 时，块 1、块 2 的 `min` 都大于 50 ——
**这两块里不可能有满足条件的行**，连读都不用读。

为什么这招威力这么大？因为**数据通常是有相关性的**：按时间写进去的日志、
按 id 排序写入的主键、按类别聚在一起的订单。相关性越强，每个块的值域越窄，
块与块之间越不重叠，能跳掉的块就越多。这就是 Lance 在文件格式里把"列按块
组织 + 每块带统计"做成**默认行为**（而不是可选优化）的原因：它不是
"给某些查询用的索引"，它让**所有**查询都受益。

**这一章讲的是"块级" zone map，第 10 章 §10.3 讲的是"片段级" zone map——
同一个机制的两个粒度。** 层级关系是：一张表切成若干**片段**（第 10 章），
每个片段里的列再切成若干**块**（本章）。片段级统计抄在 manifest 里，
所以第 10 章那一层是零 I/O；块级统计随数据页走，粒度更细、能跳得更准，
但要先把片段打开。两层是叠加生效的：**先用片段级统计甩掉整片，
再在留下的片段里用块级统计甩掉整块。** 本章的 `ZoneMapIndex` 是把块级
这一层单独拎出来做成了可显式构建的对象。

### 零索引成本——但要分清"谁的成本"

**真实 Lance 的 zone map 是白拿的。** 每块的统计（min / max / null_count）
在**写数据页的时候顺手**算出来、和数据一起落盘，不存在"建索引"这个独立
操作，也就不存在它的构建时间。所以在真实 Lance 里，zone map 的正确描述是
"**连索引都不用建就能用的数据跳过手段**"。

**但本章的实测里 zone map 的构建要 256.6 毫秒——这不是矛盾，是两回事。**
本实现的 `ZoneMapIndex` 为了教学，额外留了一份**原值副本**（好让"剪枝 +
求值"的对照实验能在索引内部闭环完成；真实实现不留，它会去读那一页），
还额外算了一张 null 掩码，所以它有真实的构建耗时和落盘体积：

```
ZONEMAP / id: build 256.6 ms | 1,599,843 B | blocks=98 pruned=96 (98.0%)
```

对照同一份数据（**N = 100,000**）上的 BTREE：build 245.6 ms、落盘
3,089,132 字节。**两者建索引的耗时同量级——前提是承认"本实现多存了一份值"
这个口径差**：真实系统里 zone map 这一侧根本不会出现在成本表里。
能这么比，恰恰暴露了本实现和真实实现在这一项上的定位差别——**在本教程里
它是一个"索引"，在真实 Lance 里它是文件格式的一部分。** 别拿这里的
256.6 ms 去推断真实 Lance 有 zone map 的构建成本。

（顺带对齐两个 BTREE 数字：§18.1 那个 438.0 ms 是 **20 万行**的构建，
这里是 **10 万行**的 245.6 ms——不同 N，不能直接比快慢。）

### 剪枝能力的上限：完全取决于数据排布

同一份 id 列、两种排布、同一个谓词 `id BETWEEN 0 AND 2000`：**已排序**时
98 个块里剪掉 96 个（98.0%），跳过 97,952 行、估算少读 783,616 字节；
**随机**排布时 98 个块一个都剪不掉（0.0%），跳过 0 行、0 字节。

**对均匀分布的数据，zone map 完全失效** —— 每个块的 min/max 都覆盖全域，
一个块也剪不掉。这不是实现的问题，是 zone map 的数学上界：它知道的信息只有
每块的 `(min, max, null_count)`，能剪的条件是"谓词区间和块值域不相交"。
块值域宽到覆盖全域时，没有任何谓词能满足这个条件。

第二块数据是 20 万行版本的同一个实验，结论一样：已排序 193/196 块剪掉
（98.5%），随机 0/196。注意**已排序时块内跨度很小** —— 20 万行切 196 块
（`page_size=1024`）、每块约 1020 行，实测 `avg_block_span = 1019.3`，
基本等于"块内行数减一"（数据里有一些重复值，所以**略小于每块的行数，
约 1020**——注意参照系是"块内行数"，不是 `page_size - 1 = 1023`）。
随机排布下同一个统计量是 `199595.1` —— **几乎就是整个值域**。
这一对数字是 zone map 有效性最直白的度量：跨度小 → 能剪；跨度是全域 → 剪不掉。
这也解释了 Lance 为什么要在 compaction 里做"按排序列重写"：
**重写的直接收益就是让 zone map 重新变锋利。**

### 它永远不返回行号集合

本实现的 `ZoneMapIndex.search()` **永远返回 `None`**。这不是偷懒，是不撒谎：
zone map 从来不产生"命中行号集合"，它只产生"哪些块可以跳过"。
把它硬塞进 `ScalarIndexExpr` 的返回类型里，等于让上层以为拿到了精确答案。
真正的接口是 `prune()` / `prune_expr()`（返回"哪些块要跳过"+ 一份
`PruningStats`），以及 `filter_by_expr()` 这个"下推 + 求值"的完整示范。

### PruningStats：真实的剪枝统计

本实现的 `PruningStats.as_dict()` 实测输出：

```
{'blocks_total': 98, 'blocks_pruned': 96, 'blocks_kept': 2,
 'rows_total': 100000, 'rows_skipped': 97952,
 'bytes_skipped_estimate': 783616,
 'prune_ratio': 0.9795918367346939, 'row_skip_ratio': 0.97952,
 'matcher': 'range[0, 2000]'}
```

`blocks_total` / `blocks_pruned` / `blocks_kept` 是块级账；
`rows_skipped` / `row_skip_ratio` 是行级账；`bytes_skipped_estimate` 是
"省了多少读盘"的估算（用每行平均字节数乘跳过的行数）；
`matcher` 是谓词的描述，便于日志里对照。**注意 `bytes_skipped_estimate`
是估算不是测量** —— 它假设"跳过的行如果真要读就得读整行"，而实际查询可能
只读少数几列，所以真实省下的 I/O 通常**小于**这个数。

### 它绝不能误剪

zone map 唯一的正确性要求是：**只能保守地不动手。** 谓词区间和块值域
**有交集**时，就必须保留这个块，哪怕实际一行都不命中。本实现
`BlockMatcher.could_match()` 的契约就是"必须永不误判为'不可能'"。

实测对拍暴力法（20 万行随机数据，四个谓词）：

```
[0,0]           剪枝后求值=0     暴力=0     一致=True   剪了 196/196 块
[1000,2000]     剪枝后求值=1,006 暴力=1,006 一致=True   剪了 0/196 块
[199000,300000] 剪枝后求值=979   暴力=979   一致=True   剪了 0/196 块
[-5,5]          剪枝后求值=4     暴力=4     一致=True   剪了 192/196 块
```

这两行看着矛盾，其实都对，而且原因正好相反。`[1000,2000]` 剪了 0 块：
20 万行随机 id 摊到 196 个块里，每块约 1020 行，块内 min/max 基本覆盖全域，
所以每块都"有可能命中"，zone map 只能老实地一块都不剪。
`[0,0]` 反而剪了 196/196 块：每块约 1020 个样本，**块内最小值期望在
20 万 / 1020 ≈ 196 附近**，也就是说**没有任何一块的值域包含 0**——
这不是误剪，是这份数据里真的没有 0。
`[-5,5]` 剪了 192/196 块也同一个道理：只有开头那几块的 min 落在 5 以内。

**这说明 zone map 的剪枝能力完全由数据排布决定**，和谓词写得多窄无关：
同一列换一种排布，这几行的结果会完全不同（下一节有对照）。

`NOT` 本实现刻意不支持。zone map 只知道"某一块里**有没有可能**"，
**不知道**"某一块里是不是**全部**满足"，而 `NOT p` 的剪枝恰恰需要后者
（`NOT (x > 5)` 只有在"整块都 > 5"时才能剪掉）。强行按 De Morgan 展开
反而是错的。

**"永不误剪"这条契约有一个真实的反面教材，就在 `BETWEEN` 上。**
第 10 章 §10.12 记过一个静默返回错误的 bug：片段级剪枝在 `Between` 分支里
**拿 AST 节点当 Python 值去比大小**（`expr.high < lo` 返回的是比较节点、
在布尔上下文里恒为真），于是每一片都被判定为"不可能命中"，`BETWEEN`
全都返回 0 行——而等价的 `>= AND <=` 毫发无损。两块代码走的是同一条
"区间 vs 块值域"的判定路径，所以本章的 `RangeMatcher.could_match()`
也要面对同一个陷阱：**引擎看到的是 AST，不是值；凡是要把区间端点拿去和
块的 min/max 比较的地方，都必须先把字面量取出来。** 正确性优先于性能，
在这一条上体现得最狠——剪错了不报错，只是悄悄少给行。

### 真实 Lance 的 zone map

单文件 `zonemap.lance`，列是 `min` / `max` / `null_count` / `nan_count` /
`fragment_id` / `zone_start` / `zone_length`（Lance 格式规范；单文件索引的
布局见第 3 章）。
`rows_per_zone` 默认 **`"8192"`**（本实现默认 1024 行，是为了教学数据量小
时也能看到多块）。语义上它被官方明确标成 **"inexact" 过滤器**：
"可以确定性地排除 zone，但可能包含需要复检的假阳性"。

一个值得学的细节：**因为"找 NULL"很常见，zone map 还额外维护一张 null 行的
bitmap，使 `IS NULL` 可以返回精确结果**（`IsNull` 是 Exact，
其他谓词都是 AtMost）。本实现也留了 `null_mask`，`NullMatcher` 是唯一
真正用到 `null_count` 的谓词。

真实实现里还有一个很讲究的保守性处理：跨多个 zone 折叠全局 `[min, max]` 时，
**只要任一 zone 的 `max` 是 NaN 就返回 `None`** —— 因为 `ScalarValue` 的全序
把 NaN 排在所有有限值之上，只折叠有限 max 会得到一个**真子集**，
从而剪掉真正命中的行（转引上游 Lance 源码；NaN 在排序里的位置，第 4 章
§4.6 讲浮点编码时也提过）。这类"NaN 把极值冲掉就放弃剪枝"的处理，是标量
索引里"正确性优先于性能"的典型。

## 18.6 索引的代价是双面的

到目前为止讲的都是收益。代价有三份，都真实。

**第一，写变慢。** 每次写入都要维护索引。本实现的实测（同一份数据、
单线程、取 3 次最快，**N = 100,000**）合成一处，方便横向对照。**建索引
耗时 / 一次查询耗时 / 落盘字节（相对原列倍数）/ 查询形态**分别是：
BTREE（`id` 列）245.6 ms / 0.016 ms / 3,089,132 字节（3.86 倍）/ range
100 值；BITMAP（`cat` 列）116.3 ms / 0.599 ms / 850,294 字节（1.06 倍）/
IN 1 值；LABEL_LIST（`tags` 列）266.6 ms / 0.177 ms / 2,226,224 字节
（2.78 倍）/ array_contains；NGRAM（`text` 列）667.8 ms / 40.914 ms /
16,612,560 字节（7.55 倍）/ contains 12 字符；FTS（`text` 列）4,302.6 ms /
6.013 ms / 8,500,747 字节（3.86 倍）/ term、k=10；ZONEMAP（`id` 列）
256.6 ms / 0.480 ms / 1,599,843 字节（2.00 倍）/ prune 谓词。（前五节已经
逐项量过，这里只是并排放在一起看；它们是同一份数据、同一次测量。）

读这组数字有三个要点。

**查询时间的差异是三个数量级**（BTREE 0.016 ms vs NGRAM 40.9 ms），
因为它们的成本结构完全不同：BTREE 是三次页读取、BITMAP 是字级位运算、
NGRAM 是"展开热 gram 的巨大 postings 再做集合交"。

**FTS 和 NGRAM 的"查询"里包含了后处理。** FTS 的 6.013 ms 里绝大部分是
**对整个 100,000 行的稠密分数数组**排序（真实的 WAND 剪枝就是为了避开这一步，
见第 17 章）；NGRAM 的 40.9 ms 里绝大部分是候选集求交。这两个数字**不代表**
"查一次要 40 毫秒"，只代表"这个查询形态在小语料上有多贵"。

**落盘的倍数必须谨慎解读。** 本实现的索引文件是 JSON + 原始 numpy 数组
（`keys.json` 存 100,000 个整数要 688,890 字节，即 ~6.9 字节/键 ——
JSON 把每个数字写成了十进制文本）。真实 Lance 对行号做 delta + RLE 编码、
对键做类型化列存，压缩比高一个量级。所以**这张表里的倍数只在本实现内部
可比**，不要拿去推断真实 LanceDB 的索引体积。

**第二，空间变大——而且不止落盘。** 上面量的是**落盘字节**，但索引在查询
时还要**驻留内存**。第 10 章 §10.7 记过一个很有教育意义的翻车：给 20 万行的
表建 BTREE，索引文件 11.6 MB、是整张表（1.85 MB）的 6.3 倍，一次点查要读
6.3 MB、花近一秒，比不加索引还慢几十倍——根子就是"每查一次就把整个索引
重新加载一遍"。所以正确的口径是"索引的**热态内存** × 它能不能被缓存"，
本实现的 `stats()["memory_bytes"]` 走的是同一个思路。`bits_per_row` 那个
数量级更要命：高基数列上的 BITMAP 会到 n² 级别（§18.2 那个 5 GB 就在这一档）。
**"建了索引查询一定快"是错的**——索引是拿"固定的索引读取/驻留成本"换
"随表增长的扫描成本"，交叉点取决于索引相对表的大小、以及它有没有被缓存。

**第三，索引会过期。** 表在持续写入，索引只能覆盖建它那一刻的数据。
本实现只支持全量重建，压实之后一律把索引标记失效：

```python
clone.valid = False
clone.details["invalidated_by_compaction"] = True
```

### 主索引 + delta：真实 Lance 的增量办法

**真实 Lance 走的是"主索引 + delta（增量索引）"：** 主索引保持不变，
新写入的行进一个小的 **delta 索引**；查询时两个一起搜、再合并（同一个键
取新的那一份，因为 delta 里是更新的行）。delta 小的时候查询代价可以忽略，
大到一定程度（或写入暂停时）再把主索引和 delta **合并**成一份。这就是
为什么真实 LanceDB 里 `num_unindexed_rows` 能长期是一个正数，也是第 12 章
§12.6 讲"未索引行走暴力兜底"背后的结构。

三种维护策略各有代价：

**全量重建（本实现）。** 最简单、最不容易错；代价是每次写入之后要么索引
失效、要么付一次完整重建。适合"一次建好、只读"或"写少读多"。

**主索引 + delta。** 写入路径最便宜（只往 delta 追加）、查询路径最复杂
（两次搜索 + 合并 + 去重）。**delta 的合并时机是关键调参点**：合太勤等于
频繁重建，合太懒则 delta 长成第二个主索引、每次查询要扫两遍。

**先删后插（倒排/位图类索引的做法）。** 更新就是"墓碑 + 追加"，物理
postings 永不原地改（第 17 章 §17.2 讲 FTS 时展开过）。它和 delta 的区别是：
delta 是"另起一份索引再合并"，墓碑是"在原来那份索引上打洞再压缩"。

**建索引之前先问自己三个问题：** 这一列会不会被查？被查的谓词是什么形态
（等值/范围/`IN`/子串/短语）？写入频率有多高（每次写入的维护成本能不能忍）？
三个问题里任何一个答案是"不会/不知道/很高"，就先别建。

## 18.7 索引选择的决策树

文档里的表只给了四种，而实际可选的更多。用文字把决策过程走一遍。

**第一步，先看列的值域形态。**

列是一行一个值（`status`、`age`、`created_at`），还是**一行一串值**
（`tags`、`categories`）？后者直接跳到 LABEL_LIST —— 其他的都答不了。

**第二步，看查询谓词的形态。**

谓词是范围/不等值（`>`、`<`、`BETWEEN`、`ORDER BY ... LIMIT`）？
选 BTREE。这是保序结构的本命，别的都答不了或者很慢。

谓词是等值或 `IN` 一个不大的集合？这时才是**按基数分岔**的地方：
不同值在几百以内、而且这一列会反复被过滤 → BITMAP（位运算一次 64 行，
还能白送任意布尔组合）；不同值接近行数（主键、UUID、时间戳）→ BTREE
（此时 BTREE 的等值查找就是三分树高，而 BITMAP 会爆到 n² 量级）。

谓词是子串（`contains`、`LIKE '%..%'`）？→ 字节串用 FM-Index，
词级子串用 NGRAM。**注意这两条路都不给精确答案**：FM-Index 是精确的
（BWT 上的子串搜索）、NGRAM 只给候选集必须再验证。官方给的判据是：
"过滤用 `contains(col, 'needle')`（子串）而不是等值或词搜索、
列是 `Utf8`/`Binary`、想要不付分词/语言分析/BM25 打分的代价 → 用 FM；
需要**词级相关性排序、短语查询、或语言感知的分词** → 用 FTS"
（LanceDB 官方文档；FTS 那一侧的代价第 17 章 §17.2 量过）。

谓词是词级的关键词检索、要相关性排序？→ FTS（第 17 章那一整套）。
其中短语查询要多开 `with_position`。

**第三步，如果这一列没有任何索引也不打紧，但数据有相关性 —— 别忘了
zone map 是免费的。** 它不需要建（真实系统里写在页头），
不需要额外的查询路径，对**所有**查询都生效。代价为零，
唯一的条件是数据排布要有局部性。**先看数据是不是按某列有序写入的：
是，就把这一列当成天然的 zone map 受益者。**

**第四步，多种谓词混用时，让规划器挑，而不是自己挑。**
真实 Lance 的 `apply_scalar_indices` 会把表达式树上的每个叶子交给
"能答它的索引"，然后再组合。本实现的每个 `search()` 返回 `None` 就是
在参与这个协商 —— **索引自己最清楚自己答不了什么**，
把这个信息显式传上去，比让规划器猜可靠得多。

最后一条实践经验：**一列上不要建多个同类型索引**，也不要"先建着以后可能用"。
每个索引都在写路径上有成本，而 SQL 的谓词形态往往集中在少数几列上。

### 决策树之外，还有几件常被问到的事

**复合 / 多列索引。** 本实现和上面五种索引都是**单列**的：一列一个索引，
多列谓词靠 `And` 在行号集合上求交。真实 Lance 也不提供通用的复合标量索引，
`WHERE a = 1 AND b > 5` 是"两个单列索引各答一半再相交"。**这恰恰是"返回
行号集合表达式"这个接口设计的红利**（见本章开头的三个后果）：复合谓词
不需要复合索引，靠 `And` / `Or` 就能组合，规划器再按选择率决定先算哪个。
唯一要注意的是**选择率**——把最有区分度的谓词先求交，中间结果最小。

**字符串的排序规则（collation）。** BTREE 的保序性是按**字节序**（或某种
确定的 collation）建的。一旦查询要求"大小写不敏感"或"按语言排序"
（`ORDER BY name COLLATE ...`），而索引是按原始字节序建的，**这个索引就
答不了那个范围查询**——它的顺序和查询要的顺序不是同一个。正确做法要么给
`lower(col)` 建索引、要么接受退化。**"索引的序"和"查询的序"必须一致**，
这是 BTREE 这类保序结构的第一前提。

**Bloom 过滤器是另一种"跳过"。** 它和 zone map 解决的是同一个问题
（"这一块里不可能有"），但用的是**集合成员**而不是**区间**：一个 Bloom
过滤器对"`col = 'x'` 在不在这一块里"给出"肯定不在 / 可能在"。它专门服务
**等值**谓词、且对高基数列也有效（zone map 恰恰在高基数列上失效）。
代价是假阳性（"可能在"里有误报，需要回表验证）和"过滤器本身也要读"。
本实现没有实现 Bloom，第 10 章 §10.13 提过它和 zone map 的分工。

**嵌套 / 结构体列。** `struct` 的一层层字段在 Lance 里是被**解平**成一列列
存的（第 3 章 §3.5），所以 `address.city = 'SH'` 本质上是对
`address.city` 这个**叶子列**做等值——可以给它单独建 BTREE。
`list` 列的成员查询就是 LABEL_LIST（§18.3）。**规则是：索引建在叶子列上，
路径只是命名。** 这也解释了为什么 `tags` 这种 list 列要用专门的索引类型，
而不是"对列表建个 BTREE"。

**`IS NULL` 与布尔列。** zone map 的那张 null 位图让 `IS NULL` 能返回
**精确**结果（§18.5），不需要另外建索引。布尔列本质是基数 2 的低基数
列，BITMAP 是最自然的选择（两行位图），但它同样可以先靠 zone map 的
等值剪枝白拿一部分收益。**`IS NULL` 是 zone map 唯一"精确"的谓词**，
其余都是 inexact——这一点值得记住。

**标量索引和稳定行 id / 时间旅行。** 标量索引里存的是**物理行号**
（`fragment_id << 32 | offset`，§18.1），时间旅行读的是**旧版本**。
这两件事在"索引跟着哪个版本走"上必须对齐：本实现压实后把索引标记失效
（`invalidated_by_compaction`），删除后走重映射（第 9 章）。**只要索引
里存的是物理行号，任何改变行号的版本操作都必须让索引重建或重映射**——
这条在第 15 章 §15.8（HNSW 的入口点）、第 23 章（压实）反复出现，
是标量索引和向量索引共享的约束。

**当前 SDK 建标量索引的正确入口。** 本章前面（比如 §18.4）举的都是
`create_scalar_index(..., index_type="NGRAM")` 这类**旧**接口 —— 它在
本机装的 0.40.0 上**已经弃用**，跑一下就能拿到警告原文：

```
DeprecatedWarning: create_scalar_index is deprecated as of 0.25.0.
Use create_index() with config=BTree()/Bitmap()/LabelList() instead.
```

所以"可用路径"不是那个老方法，而是把**索引配置对象**传给统一的
`create_index(col, config=...)`（本机实测四种都能建、且不再有弃用警告）：

```
table.create_index("col",  config=BTree())      # 范围 / 排序
table.create_index("col",  config=Bitmap())     # 低基数等值
table.create_index("tags", config=LabelList())  # list 成员
table.create_index("col",  config=Fm())         # FM-Index（§18.9）
table.create_index("col",  config=FTS(...))     # 全文检索（第 17 章）
```

注意 `config=` 是 **keyword-only**，且和向量索引那套位置参数（`metric` /
`num_partitions` / `index_type="IVF_PQ"`）**不要混着写**：不传 `config` 时
`create_index` 建的是向量索引，标量索引必须显式给 `config`。

这也解释了 §18.4 那个 `ValueError: Unknown index type NGRAM` 该怎么读：
报错的那个字符串入口，**同时也是官方让你别再用的入口**。本章反复讲的
"以 SDK 能建什么为准"，落点就在这儿 —— 0.40 的世界是"传一个配置类"，不是
"传一个类型字符串"。

## 18.8 prefilter 和 postfilter：过滤 + 向量检索唯一正确的做法

这是"标量索引和向量索引怎么配合"的问题，也是实践中最容易出错的地方。
**下推本身怎么工作，第 10 章 §10.2 / §10.7 已经从"列投影 / 索引下推"的
角度讲过一遍；本节讲的是它对向量检索的影响**——同一个 `FilterExec` 摆在
ANN 前面还是后面，语义完全不同。

先看两条路的区别。

**postfilter（先搜向量再过滤）** 的流程是：ANN 返回 k 个候选，再筛掉不满足
谓词的行。问题是**筛完之后可能远少于 k 行** —— 因为那 k 个候选是按距离选的，
它们和谓词无关，谓词越挑剔丢得越多。

**prefilter（先过滤再搜向量）** 的流程是：先用标量索引算出满足谓词的行集合，
把它当掩码下推给 ANN，ANN 只在掩码为真的行里找最近邻。**这才能保证
"返回 min(k, 满足谓词的行数) 行"。**

本实现端到端实测（20,000 行、32 维、IVF_FLAT 16 分区、k=10）。下面前三行
是**定性结论**，不是某一次实测的具体值 —— 因为 postfilter 的确切返回行数
**取决于查询向量**，换个查询向量结果就变（理由见下）：

```
prefilter=True  -> 恒返回 10 行（= k）
prefilter=False -> 少于 k 行，具体几行随查询向量浮动，甚至可能是 0
```

**为什么 postfilter 会少于 k：** 向量索引返回的 top-10 是按**距离**选的，
和谓词无关；谓词越挑剔，这 10 行里满足它的就越少。**为什么具体行数不固定：**
"哪 10 行"由查询向量决定，所以"这 10 行里有几行满足谓词"也跟着变。拿同一份
数据实测一遍（`id`/`grp` 两列、`id = 行号`、`grp = id % 10`，以表中每一行的
向量轮流当查询向量，共 600 次）：prefilter 每次都稳稳返回 10 行，而
`grp < 5` 的 postfilter 返回值在 **1 到 9** 之间浮动（均值约 5）、
`id < 1000` 在 **1 到 4** 之间（均值约 1.4）；再换几个这 600 个之外的查询
向量，还会掉到 **0**。**固定的是"少于 k"这个定性结论，不固定的是那个具体
数字。**

（这也是为什么本节刻意不给"某次实测的某几行结果"——那种数字换个查询向量
就对不上，读者复现不出来只会以为是实现错了。真要看具体值，得连查询向量
一起写进脚本。）

真实的 LanceDB 文档明确写过这一点（`prefilter=False` 时**可能返回少于
k 行**），本实现的 `query.py` 里也照抄了这个语义并加了醒目注释。

### 一个细节：postfilter 有它自己的解药

后过滤掉行数是因为候选池太小。如果**多取一些候选**，筛完剩下的就多了 ——
这就是 `refine_factor` 的作用。同一个查询向量下（`id < 1000`、postfilter）：

```
refine_factor=  1: 1 行
refine_factor= 10: 5 行
refine_factor= 50: 10 行
```

**这里能钉住的是一条单调趋势，不是这三个具体数字。** 候选池放大
`refine_factor` 倍，筛完剩下的行数**不减**（单调上升），到 `refine_factor=50`
时基本都能凑满 10 行——这一点在同一批 600 个查询向量上每次都成立；而
`refine_factor=10` 那一档，换查询向量会在 1 到 10 之间浮动。所以：

`refine_factor=50` 让 ANN 取 50 倍候选，筛完终于凑够 10 行。所以真实的
取舍不是"prefilter 永远对、postfilter 永远错"，而是：

**谓词很挑剔（命中 1%）时用 prefilter** —— 它能把 ANN 的工作量降两个数量级，
候选池小、搜索快。**谓词很宽松（命中 90%）时 postfilter 更划算** ——
prefilter 会让索引"在很小的候选池里挑"，反而丢召回；
postfilter 拿大候选池过一遍反而更准。

### 真实 Lance 的两条硬规则

**规则一：有 KNN 且没开 prefilter 时，标量索引根本不会被用。**
`rust/lance/src/dataset/scanner.rs:3754`：

```rust
use_scalar_index = self.use_scalar_index && (self.prefilter || self.nearest.is_none())
```

注释解释了原因："否则要先索引再向量搜索，语义/性能都不对"。
换句话说，**`prefilter=False` 不只是"过滤得晚一点"，它会让标量索引这条路
完全不被走** —— 过滤退化成扫描阶段的 `FilterExec`。

**规则二：prefilter 会把标量索引查询**下推进 ANN 子树**。
执行计划里能直接看出来。真实 Lance 的两张计划对照（本机实测
`explain_plan()`；查询计划的完整讨论见第 19 章）：

```
prefilter=True : 计划里出现 ScalarIndexQuery: query=[id > 100]@btree_idx(BTree)
postfilter=False: 外层 FilterExec + 两次 LanceRead（晚物化）
```

**上面这两行对应两种不同的配置，别混着读。** `prefilter=True` 那一行里，
标量谓词 `id > 100` 被翻译成 `ScalarIndexQuery` 并**下推进 ANN 子树**——
向量检索直接在索引给出的行集合里找；`postfilter=False`（即不预过滤）那一行里，
标量索引**根本不出现**，过滤退化成一个**外层**的 `FilterExec`，
晚于向量检索执行。

本实现的 `explain_plan()` 输出的是同一种结构，下面这个片段是
**postfilter 那一档**的计划：

```
LANCERead
  ANNSubIndex: vector_idx (IVF_FLAT)
  ANNIvfPartition: vector_idx (IVF_FLAT)
  FilterExec: id < 1000   # postfilter
  KNNVectorDistance
  TopK: limit=10
  LateMaterialization: 先定行号，再回表取投影列
```

`FilterExec` 排在 `ANNSubIndex` 之后、`KNNVectorDistance` 旁边，就是
"先搜向量、再过滤"的直接证据——那个 `# postfilter` 注释点明的正是这件事。

注意"晚物化"那一行：过滤在行号域完成，只有最后才回表取投影列 ——
这正是 postfilter 的第二个代价：它得先读一遍向量做距离计算，
筛完可能只剩 10%，那一遍距离计算基本白做了。prefilter 不读向量，
直接用标量索引的行号集合把候选收缩掉。

## 18.9 FM-Index：字节串的精确子串索引

§18.7 的决策树给"字节串的 `contains`"推荐了 FM-Index，但前面从没解释过
它是什么。它和 NGRAM 解决**同一类问题**（`LIKE '%abc%'`），走的是完全
不同的路子，所以值得单独讲。**先声明一句：mini_lancedb 没有实现 FM-Index，
这一节讲的是真实 Lance 的路线，本实现里没有能跑的对应物。**

### 它和 NGRAM 的根本区别：精确 vs 候选

**NGRAM 给的是候选集，必须再验证；FM-Index 给的是精确答案。**
这是两者最本质的分野：

- **NGRAM** 把字符串切成固定长度的字符 n 元组（trigram），查 `%abacus%`
  就去找同时含 `{aba, bac, acu, cus}` 四个碎片的行——**碎片都在不证明
  顺序对**（§18.4 的 `abacacus` 就是反例）。所以要"候选 → 回表精确验证"
  两步。
- **FM-Index** 建在**整个字节串**上，能在**不展开原串**的前提下，精确回答
  "模式 `abacus` 出现在哪些位置"。它不需要"回表验证"这一步，因为它查的
  就是完整的串本身。

代价是 **FM-Index 大得多、建得慢得多**（它要把整列的每个字节都放进索引），
而 NGRAM 只存 gram → 行号。所以判据很清楚：**能容忍"候选 + 回表"就用
NGRAM（省空间）；要求精确、且查询模式长且少见，才上 FM-Index。**

### 它是怎么做到"不展开原串也能查"的：BWT

FM-Index 的核心是 **Burrows-Wheeler 变换（BWT）**。BWT 把原串
`T` 重排成一个新串 `L`，**使相同的字符聚在一起**，而且**这个变换是可逆的**
（能从 `L` 恢复 `T`）。围绕 `L` 再建几张表：

- **采样后的后缀数组（SA）**：只记下"按字典序排好序的后缀"里**每隔若干
  个**的那些起始位置。**完整 SA 是 `O(n log n)` bit，本身就比原串还大**，
  采到只剩下几个点，它才当得起"小表"这个名号；
- **`C` 表 / `Occ` 计数表**（配 `rank` / `select` 数据结构），这才是每次
  查询都要读、且能被压得很小的那一部分。

有了这些，就能**从后往前**逐个字符地匹配模式：每读一个模式字符，就
在 `L` 上通过两次 `rank` 把"可能匹配的区间"收窄一次。查到模式耗尽，
拿到的还只是一个**序号区间**，不是位置——要变成真实位置，得对区间里的每个
序号做 **LF-mapping**：反复往前跳，直到跳到一个当初被采样下来的位置，
再按跳过的步数把原始下标一路拼回去。采样越稀、要跳的步数越多，`locate`
就越慢——这也是"小表"省下来的空间换到时间上的那一头。**整个过程只在
`L` 和这几张表上做加减法，从头到尾没有碰过原串。**

两个关键性质让它在数据库里可落地：

**它不用存原串了吗？不完全——但可以高度压缩。** BWT 的"相同字符聚在一起"
让它特别适合 `RLE` 和熵编码：真实实现里 `L`（BWT 串）本身可比原串小很多，
而 `Occ` 表的每个计数器只要 O(1) 位。**"用一份压缩后的自索引替代原串"**
是 FM-Index 最吸引人的地方——它同时是索引和数据。

**它天然支持"计数"而不是"枚举"。** "`abacus` 出现多少次"是 O(|模式|)
的区间计算，不需要列出所有位置。这在 `EXISTS` 语义下又快又省。

### 建造成本，以及为什么它很少被选

FM-Index 的建造成本和索引大小**都正比于被索引列的字节总数**，而且要
构造后缀数组——这一步最坏是 `O(n log n)`、空间上还要额外好几倍。
对比 NGRAM：它只存"去重后的 gram 集合 + 每个 gram 的行号列表"，
**和列的字节数不成正比，和"多少个不同的 gram"成正比**。

所以真实场景里的选择是：

- **列的字节串总长不大、查询模式长而精确** → FM-Index 合适；
- **列很大、查询模式短** → NGRAM 的空间优势压倒一切；
- **要词级相关性排序** → 都不用，上 FTS（第 17 章）。

还有一个"能不能建"的现实约束：本机实测 **`lancedb` 0.40.0 的 Python API
里没有可创建的 `NGram` 类型，但 `Fm()` 是可以建的**（落盘
`part_0_fm.lance`，§18.4 提过）。也就是说，官方在当前 SDK 里**把"精确
子串"这条路线留给了 FM-Index**，NGRAM 只在 Rust 侧存在。**选型时以
"SDK 能建什么"为准，而不是"格式规范里有什么"。**

### 怎么建、能回答什么

前面讲的都是原理，落地只差一张"接线表"。本机 0.40.0 实测：

**`Fm()` 是个"标签类"，没有任何配置字段。** `inspect.signature(lancedb.index.Fm)`
是 `() -> None`，`dataclasses.fields(Fm)` 是空列表 —— 也就是说采样率、
块大小这些在真实实现里必然存在的旋钮，**当前 SDK 一个都不暴露**，建出来
就是默认形态。建它只是把它当 `config` 传进去：

```
table.create_index("url", config=Fm())     # 落盘 part_0_fm.lance
```

**它能回答什么：** `contains(col, 'needle')` / `LIKE '%needle%'` 这一族
**字节串子串**查询，而且给的是**精确**答案——不用回表验证（这正是它和
NGRAM 的分野，上半节讲过）。它**不提供相关性排序**（那是 FTS 的活），
也不做词级分词、不认停用词和词干。所以"我想按相关度排序地查子串"这件事
FM-Index 答不了。

**和 `FTS(base_tokenizer="ngram")` 怎么选：** 这两条路**都能建**（本机
实测两者都成功），都能碰子串，但语义层级不同：

- **`Fm()`** 建在**原始字节**上，不切词、不展开，给精确子串 ——
  适合"模式长、少见、要精确"（URL、路径、哈希片段）。索引大小正比于列的
  字节总数（上半节的账）。它没有 `prefix_only`、停用词这些概念。
- **`FTS(base_tokenizer="ngram")`** 走的是 FTS 那四个文件（`tokens` /
  `docs` / `invert` / `metadata`，第 17 章 §17.2），把文本切成 n-gram
  **词项**再进倒排。它换来的是 FTS 那一整套能力：`MatchQuery` /
  `BooleanQuery` 做布尔组合、相关性排序、以及 `FTS(prefix_only=True)`
  这种"只索引前缀 n-gram"。代价是它继承了 §18.4 那条性质 ——
  **碎片都在不证明顺序对**（`abacacus` 的反例），所以它给的是候选、
  仍需验证，不像 `Fm()` 那样直接精确。

一句话的分岔：**只要能回答"这个串在不在"、要精确 → `Fm()`；
还要能排序 / 布尔组合 / 控前缀 → `FTS(base_tokenizer="ngram")`。**

出处：FM-Index 出自 Ferragina & Manzini, FOCS 2000（*Opportunistic Data
Structures with Applications*）。

## 18.10 小结

**标量索引不允许有误差，向量索引允许。** 这个差别决定了接口形态：
标量索引返回的是**行号集合的表达式**（可组合、可交并补），
不是"最近的前 k 个"。真实的实现用 `exact` / `at_most` / `at_least` 三态
表达"我知道多少"，本实现用"精确集合或 `None`"表达同一个意思 ——
**返回 `None` 比返回错答案诚实得多。**

**五种索引的分工是清晰的，没有一种能替代另一种。** BTREE 管范围、
BITMAP 管低基数等值、LABEL_LIST 管列表成员、NGRAM 管子串（只给候选集）、
ZONEMAP 管"跳过整块"。子串还有第二条路：**FM-Index 给精确答案**（建在
BWT 上、不用回表验证），代价是索引正比于列的字节数，比 NGRAM 大得多。**

**索引的维护有三种策略**：全量重建（本实现）、主索引 + delta、
先删后插打墓碑。删/改/压实这些改行号的操作，只要索引里存的是物理行号，
就必须连带重建或重映射——这条约束标量索引和向量索引共享。

**BITMAP 的爆炸是 n² 的。** `bits_per_row` ≈ 基数（行数是 64 的整数倍时精确）；
4 个值时是 4 bit/行（半字节），20 万个值时是 20 万 bit/行（25 KB/行）。
官方门槛是"少于 1,000 个不同值"。

**NGRAM 的假阳性不可避免。** `abacacus` 包含 `abacus` 的全部四个 trigram
却不含 `abacus`。**"index → candidate → verify"是标准模式，
验证步骤永远不能省。**

**ZONEMAP 是免费的，但它的效果完全取决于数据排布。**
实测同一份 id 列，已排序剪 98.0% 的块，随机剪 0.0%。它不需要建、
不需要额外查询路径、对所有查询生效 —— 这是 Lance 把它做成文件格式默认行为
的原因。反过来，`NOT` 它答不了，因为它的信息只有"块里有没有可能"。

**索引的代价是双面的。** 读变快、写变慢、空间变大。建之前先问
"这一列会不会被查、被怎么查、写得多不多"。

**prefilter 是"过滤 + 向量检索"唯一正确的做法**（当谓词足够挑剔时）：
postfilter 会返回少于 k 行（实测 k=10 只给 1 行），
而且真实 Lance 在 `prefilter=False` 时**根本不会用标量索引**。
宽松谓词上 postfilter + `refine_factor` 才对，实测
`refine_factor` 从 1 加到 50 能把 1 行恢复到 10 行。

至此"读"这条路上的零件就齐了：向量索引负责相似、标量索引负责精确筛选、
FTS 负责字面、zone map 在任何索引之外静静地跳块。
下一章把这些零件装成一个查询规划器。
