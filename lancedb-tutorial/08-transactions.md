# 第 8 章　事务与并发

上一章说"提交就是写一个新的 manifest 文件"。这一章回答一个更硬的问题：
**两个进程同时提交会发生什么？**

答案的能力边界直接决定了 LanceDB 能用在什么场景：单机多线程没问题、
多个无状态服务实例同时写也没问题，但你**不能**指望它像 PostgreSQL 那样
给你串行化隔离和行级锁。这一章讲清它给的是什么、为什么不给更多、
以及调用方要做什么配合。

## 8.1 对象存储只给了你一个原子操作

先把物理现实摆在桌面上。对象存储上你能做的事只有：

读一个对象；写一个对象（覆盖）；**"这个 key 不存在才写"**；删一个对象；
按前缀列举；查元信息。没有 append（部分产品有，语义各异）、
没有原子重命名、没有目录锁、没有多对象事务。

其中唯一能用来做并发控制的，是**条件写**：

```
S3        PutObject + If-None-Match: "*"
GCS       ifGenerationMatch=0
Azure     If-None-Match: "*"
本地磁盘   open(path, O_CREAT | O_EXCL)
```

"不存在才写"是一个**原子的**判断加写入——这是整个 Lance 事务协议的支点。
没有它，就只能退回"先查再写"，而那是有竞态的。

这个原语解释了很多设计。为什么 manifest 里要带版本号？
因为 key 里带版本号，才能把"我要提交版本 v+1"翻译成"创建这个 key"。
为什么数据文件不需要条件写？因为它们是不可变的新文件，
文件名里带 uuid，天然不会冲突——**随便写，不用协调**。

## 8.2 提交协议

一次写入的完整流程是五步：

1. 读最新 manifest，记下 `read_version = v`；
2. 干正事：写数据文件、删除文件、索引文件。它们都是**新的、不可变的**，
   名字带 uuid，多个写者各写各的，不需要任何协调；
3. 写事务文件 `_transactions/{v}-{uuid}.txn`，记录"我基于 v 做了什么"；
4. 条件写 `_versions/{v+1}.manifest`。**这是唯一的原子点**；
5. 成功就更新 `latest_version_hint.json`；失败说明别人已经提交了 v+1，
   进入冲突处理。

第 2 步的性质值得强调。**所有重的活都在并发写、所有轻的活在串行化。**
一个进程写 500 MB 数据文件的过程和另一个进程完全并行，
只有在最后提交那几百字节的 manifest 时才可能撞车。
这是这套协议能扛住高写入吞吐的根本原因——
换成"写的时候加表锁"，500 MB 的写入就会把整个表锁住几秒。

第 3 步的事务文件也值得单独说。**它是日志，不是状态。**
manifest 只保存"结果"，事务文件保存"过程"。`Transaction` 这个 dataclass
的字段就是它的全部内容：`read_version`（我基于哪个版本）、`operation`
（操作类型）、`payload`（操作的细节 —— append 了哪些片段、删了哪些行、
建了什么索引都装在这里）、`id`（uuid）、`timestamp`、`writer`（谁）、
`blobs`（附属二进制，见第 8.5 节）。一句话概括就是
"**谁、在什么时候、基于哪个版本、做了什么**"，和第 7.1 节对它的描述是同一件事。
它的用途有三个：

出了问题可以重放事务来重建 manifest；
多写者冲突时可以据此判断"我的操作和他的操作能不能共存"；
审计时能回答"这个版本是谁、什么时候、改了什么"。

因为它不权威，就可以用更便宜的方式写——普通 `put` 而不是条件写。
文件名带 uuid 天然不冲突，即使被覆盖也不影响正确性。
**"日志可以丢、状态不能丢"**这个取舍，让它在低持久性存储上也能低成本写入。

代价是**事务文件只增不减**：一次提交留一个 `.txn`，提交 N 次就是 N 个文件。
本实现的 `cleanup_old_versions()` 不清理 `_transactions/`（它只清 manifest、
数据文件和删除文件），所以这张目录会一直长（第 7.1 节）。真实 Lance 同样
把事务文件排除在 manifest 的引用图之外，靠保留窗口成批清理；
如果你的表写得很频繁，这是监控清单上要加的一项。

## 8.3 冲突：什么时候重试，什么时候失败

提交失败之后怎么办？这需要一个判断：**我的操作和别人的操作能不能共存？**

不能简单地"一律重试"。考虑这个场景：我基于 v5 读到了片段列表，然后
删除了片段 7 里的 100 行。现在发现别人已经提交了 v6，而 v6 也修改了片段 7。
如果我就这么重试，我的删除文件会**覆盖**掉别人的删除文件——
刚才被我"重新读到"的片段 7 里，对方删掉的行又回来了。这类 bug
不会报错，只会静默丢数据。

所以设计上需要一个**冲突矩阵**：给两种操作类型，回答"能不能 rebase"。
判定原则只有一条——**我的操作是否依赖于"我对别人改了哪些片段"的完整了解？**
把这条原则展开，就得到下面这张 4×4 的表（行是"我的操作"、
列是"并发发生的那个操作"，格子里是能否安全 rebase）：

| 我的操作 \ 别人的操作 | append | delete | create_index | overwrite |
|---|---|---|---|---|
| append | 可 | 可 | 可 | 不可 |
| delete | 可 | **不可** | 可 | 不可 |
| create_index | 可 | 可 | 可 | 不可 |
| overwrite | 不可 | 不可 | 不可 | 不可 |

**但在读这张表之前，必须先说清楚一件事：它是设计意图，不是当前的行为。**

本实现把这张矩阵实现成了 `CONFLICT_MATRIX` 和 `can_rebase()`
（在 `mini_lancedb/format/transaction.py` 里），
**但没有任何一条写路径调用过它们**——它们被定义、被导出，
然后就没有下文了。这不是"用得少"，是彻底的死代码。

真正决定"重试还是报错"的，**是调哪个 API，不是操作类型**：

- `Dataset.write()`——**append 和 overwrite 都一样**——无条件重试，
  一直试到 `max_retries` 次才抛 `CommitConflict`；
- `Dataset._delete_append()`（也就是 `delete` / `update` /
  `merge_insert` 走的那条路）**从不重试**，`_commit` 一失败立刻抛。

这个落差有两个具体后果，都得记住。

**第一，表里那条"overwrite 与任何人冲突"是不成立的。**
实测：两个写者都基于 v2，第一个 append 出 v3，
第二个拿着已经过期的 v2 做 overwrite——**它照样成功**，出 v4。
也就是说 overwrite 会静默 rebase 到你没读过的那份片段列表上。
矩阵说它"不可"，实现让它"可"。

**第二，"delete 和 delete 会失败"这个结论是对的，但原因是错的。**
实测两个并发 delete 确实抛 `CommitConflict: 提交时发生并发写`，
但拦住它的是 `_delete_append` 那条**不重试**的路径，
不是矩阵里那个"不可"格子。因果搞反了，就会在调参时找错旋钮。

所以这一节正确的读法是：**矩阵描述的是"为什么这样设计"，
而实际行为是"按 API 分档"。**把矩阵当成行为说明书，
会得到与实测相反的结论——这正是附录 E 反复说的那种
"文档写得越清楚，越容易盖住实现真实的样子"。

表里剩下的三条读法仍然成立，也仍然值得理解：

**append 是永远安全的。** 它只往片段列表末尾加片段，不碰别人写的任何东西。

**create_index 也是安全的。** 它不修改任何片段，只往 manifest 的索引列表里加一条。

**delete 与 delete 保守地判为冲突。** 两边都想改同一个片段的删除文件，
如果不重新计算就会互相覆盖。真实 Lance 的解法是在 rebase 时
**基于最新片段列表重新算一次删除集合**——它能做到，是因为它的删除文件
记的是"行地址"而不是"行号"，重新合并是纯集合运算。
我们保留这个保守版本，并在文档里点明代价：**并发删除会失败而不是静默出错**，
对教学实现来说这是更安全的默认。这条是本实现里**真实生效**的，
只不过生效的位置在 API 那一层。

**重试次数要点明"是谁的默认值"。** 本实现的 `Dataset.write(max_retries=3)`
默认重试 3 次，超了就抛 `CommitConflict("写入时反复发生提交冲突")`，
错误里带上 `attempts` 和一个"降低并发写入者数量"的提示；
`rebase_plan()` 还会给出 `can_rebase` / `blocked_by` / `advice` 三样东西，
让错误信息自己说清下一步该怎么办。**真实 Lance 的提交重试默认是
20 次、总时限约 60 秒，退避带抖动**，代价是撞车时线程被占住更久。
3 和 20 差了一个数量级，别把这里的 3 当成 Lance 的默认值 ——
它们是两个实现各自的选择，想对齐真实行为就显式传 `max_retries=20`。

我们实测过一次真实的并发写：

```
w1 sees v 2   w2 sees v 2
after w1 commit: v 3
w2 写入成功并自动 rebase 到 v 4
最终 rows 30
```

两个进程都从 v2 出发，各自写了 10 行。w1 先提交成功变成 v3；
w2 的条件写失败，但因为是"append vs append"，自动 rebase 到最新
manifest 后重新提交成 v4。最终 10 + 10 + 10 = 30 行，**一行都没丢**。

## 8.4 这个协议不比数据库事务弱在哪、弱在哪

**它给了什么。**

**原子性。** 一次提交要么全部生效、要么完全不生效。因为"生效"的定义
就是"那个 manifest 文件出现了"，而创建文件是原子的。

**快照隔离。** 一个读者拿到 manifest 之后，无论写者怎么折腾，
它看到的世界都不会变。这不是"实现了快照隔离"，而是
"不可变 + 全量快照"直接推出的结果——**根本没有别的可能**。

**丢更新不会发生。** 两个并发的 append 都会保留下来（实测的 30 行就是证据）。
这在"先读后写"的朴素实现里是做不到的。

**读己之写（read-your-writes）成立。** 提交成功后 `Dataset.write` 会把新
manifest 赋回自己的句柄（`self.manifest = manifest`），所以**同一个
`Dataset` 对象**紧接着读，读到的一定是自己刚写的那一版。换一个句柄
（另一个进程，或者另一个 `Dataset.open`）就不保证了 —— 本实现没有任何
自动刷新机制，要看新版本只能重新打开表（真实 LanceDB 把这件事做成配置项
`read_consistency_interval`，见第 6.6 节；这里的形态相当于"永远不自动刷新"）。

**它没给什么。**

**没有跨表事务。** 一次提交只作用于一个数据集。
要在两个表上做原子操作，得靠上层自己写补偿逻辑。

**没有可串行化。** 两个事务如果都读了一部分数据再写，
中间可能被第三方插入。对"批量导入 + 索引重建"这类简单模式没问题，
对"读余额再扣款"这类模式就不行。

**没有等待锁。** 冲突就是失败，不是阻塞。这是**乐观并发**的定义，
也是它在对象存储上唯一可行的形态（对象存储给不了长事务的锁）。

**没有交互式事务。** 没有 `BEGIN`，没有跨多次调用的会话状态。
每一次写操作自成一个事务。

**没有跨分支事务。** 第 7.5 节的 branch 是"可写的引用"，但分支上的提交
各算各的：在两个分支上分别提交、想保证两边一起成功或一起失败，
本实现和真实 Lance 都不提供 —— 分支只是隔离了历史，没有跨分支的原子性。

理解了这些边界，就知道该在哪里加补偿：**凡是"先读后写、且写的内容依赖读的结果"
的业务操作，都要准备好整个重做一遍。** `merge_insert` 是这个模式的典型——
它先读 join 键，再决定删什么、插什么（第 9 章讲它的完整语义）。如果两个进程
同时对同一个 key 做 upsert，其中一个的重试会让它重新读到对方写进去的行，
从而得到正确的结果（后写的赢）；但如果业务上要求"先写的赢"，
那就要靠外部的序列号或版本判断，不能指望数据库。

**跨表补偿长什么样。** 要在两张表上做一个"业务上原子"的操作，
标准写法不是"回滚"，而是"**把中间状态写进数据、让重跑幂等**"。
以"结算订单并在流水表追加一条记录"为例：先给订单打一个 `settling` 标志、
再往流水表追加、最后把订单改成 `settled`。这段逻辑在崩溃或冲突之后重跑时，
前两步要自己检查"是不是已经做过了"（同一个订单号、同一个标志位），
跳过已完成的那一步。**这个模型里没有回滚，只有"再提交一次正确的结果"**——
这也是为什么 `merge_insert` 那种"先读后写"的原语必须自带幂等性。

## 8.5 事务类型与它们的语义

真实 Lance 的事务 protobuf 里，`oneof operation` **把字段号 100–199 整段
预留给了操作类型**，当前用到的是 100–115（Append=100、Delete=101、
Overwrite=102、CreateIndex=103、Rewrite=104、Merge=105、Restore=106、
ReserveFragments=107、Update=108、Project=109、UpdateConfig=110、
DataReplacement=111、……）。规范对这段预留的用意有明确说明：
**读到范围内一个不认识的号，要当成"来自更新写者的未知操作"，而不是报错**——
这正是新操作类型能向前兼容地加进格式的机制。注意真实 Lance 里
**没有单独的 `Create` 操作**：建表走的是 `read_version = 0` 的 `Overwrite`。

我们的 `Operation` 类定义了十三种类型，覆盖最常用的一批：
`Create` 建表；`Append` 追加片段；`Overwrite` 用新片段替换整个片段列表；
`Delete` 通过删除文件删行；`Update` 是删除 + 追加；`MergeInsert` 合并插入；
`CreateIndex` / `DropIndex` 索引增删；`AlterSchema` 改 schema；
`Restore` 恢复到历史版本；`Compact` 压实；`Rewrite` 重写数据文件；
以及一个只在冲突矩阵里出现的 `TAG`。这里要说明一点：本实现的建表
（`Dataset.create`）其实**不写事务文件** —— v1 是直接写出的 manifest，
`Create` 这个常量并不产生事务，它只是照真实 Lance 的类型清单补了个位。

这些类型不只是标签，它们本来是**冲突判定和审计的输入**——
矩阵就是按它们分类的。但正如 8.3 节说的，
那个矩阵在本实现里是死代码，所以这些类型目前**只有审计价值**：
它们写进事务文件，事后能回答"这一版是谁、做了什么操作改出来的"。

分类本身仍然是合理的：压实（`Compact`）属于"修改行"那一类，
因为它改写了片段的组织和行号，和并发删除在语义上必然冲突。
**分类是对的，只是没有代码去消费这个分类。**

还有一个容易被忽略的点：**提交里有"blobs"这个概念。**
真实 Lance 的 `Transaction` 除了操作语义，还能附带二进制数据。
用途之一是把新 schema 塞进提交里，这样"从旧版本重放事务"时
不需要额外去读别的文件。我们的实现用 base64 存在 JSON 里表达同一件事。

## 8.6 压实与并发的互动

压实是唯一一个"又重又必须串行"的操作。它的本体是三步：
**读一批片段 → 合并写成一个新片段 → 提交一个指向新片段的新 manifest**。
三步全部是"写新对象、最后改一次指针"，中间任何一步失败都能重做，
不会留下半成品。

**删旧文件不在压实的定义里，这是一个容易被讲混的地方。**
如果把"删掉被替换的旧文件"也算进压实，它就会凭空多出一个阶段：
提交之前不能删（否则失败就没数据了），提交之后又不能立刻删
（否则正握着旧 manifest 的读者会读到半个表），还得管"这个 500 MB 文件
还有几个版本引用它"。真实系统的做法是把这一刀切干净：
**压实只负责让新 manifest 不再引用旧片段；真正的删除交给专门的 GC
（`cleanup_old_versions`）**，由它去等"所有引用这些文件的版本都过期"。
我们的实现走的是同一条路 —— `compact()` 从头到尾只写新对象、
最后提交一次，不删任何文件。

这也是为什么我们实现的 `compact()` 和 `cleanup_old_versions()`
是两个独立的方法，而不是一个大方法。它们的安全窗口完全不同：
压实可以频繁跑，GC 必须保守。（GC 的保留窗口怎么定见第 7.7 节；
压实之后索引为什么失效、什么时候重建见第 23 章。）

另一个互动是**多个进程同时压实**。两个进程可能都决定"把片段 A、B、C 合并"，
各自写出一份合并结果，然后一个提交成功、另一个条件写失败。
失败的进程如果重试，会发现片段已经被换掉了，于是重新规划——
这一次可能就不需要压实了。所以压实的 rebase 策略应该是
"放弃并重新判断"，而不是"重放同一个操作"。
**这一点在我们的实现里体现为"不重试"**：`compact()` 失败就抛
`CommitConflict`，而调用方 `Dataset.optimize()` 的整个函数体是

```python
result["compact"] = self.compact(target_rows_per_fragment=target_rows_per_fragment)
```

——没有 `try`、没有 `except`、没有重试循环，异常直接往上冒到调用者。
（`Table.optimize()` 那一层也一样，它只是转发。）所以在这个实现里，
"两个进程同时压实"的结果是**其中一个直接失败**，而不是自动重新规划。
这不是缺陷，是上面那条"放弃并重新判断"策略的**最激进形式**：
把重新判断的责任完全交给调度器。代价是**你的维护脚本必须自己包
`try` 并重试**——否则一个每天的定时压实任务会因为在那一秒撞上
另一个写者而整个失败，而且失败得很安静（如果没人看日志的话）。

## 8.7 对象存储不支持原子写怎么办

有一个现实问题：并非所有存储都支持 `If-None-Match`。某些 S3 兼容实现、
某些 WebDAV、某些 NFS 挂载都做不到。这时条件写会静默退化成"先查再写"，
竞态就回来了。

**一个必须知道的坑：默认配置可能就是"不安全"的。** S3 上历史默认的
commit handler 是 `UnsafeCommitHandler` —— 它把 manifest **直接写到正式路径、
不做任何存在性检查**（第 6.3 节提过）。它的"启用场景"不是"你想用"，
而是"默认就在那儿"：早期 Lance 认为 S3 上没有可用的原子 rename，
于是干脆放弃了检查。后果是**并发写者会静默丢更新**：两个写者都要写
`{v+1}.manifest`，后写的覆盖先写的，先写者的数据文件就此成为没人引用的
孤儿，而且没有任何报错。要它安全，唯一办法是**保证同一张表同时只有一个写者**
（外部加锁，或者干脆串行）。要并发安全就得换 `ConditionalPutCommitHandler`
（走条件 PUT）；在连条件写都没有的存储上，才是下面这套 External Manifest Store。

真实 Lance 有一个 **External Manifest Store** 的设计来处理这种情况：
把"谁是最新版本"这件事委托给一个支持事务的外部服务
（数据库表、etcd、DynamoDB），本地只写不可变的数据文件。
这样即使对象存储不支持条件写，也能保证只有一个人能"宣布自己是新版本"。

这是一个通用的模式，值得记住：**当底层存储给不了你需要的原子性时，
去找一个能给的组件，把"哪一份是当前状态"这件事外包出去，
而把大块的数据留在便宜的存储上。** 元数据需要强一致，
数据不需要——这个不对称性是可以被利用的。

## 8.8 多进程写的实操建议

把它落成几条能直接用的建议。

**用 `spawn` 而不是 `fork`。** Lance/LanceDB 内部是多线程的，
fork 出来的子进程会继承一个状态可疑的运行时——真实文档明确写了
`fork` 与 LanceDB 不兼容。Python 的 `multiprocessing` 默认在 Linux 上是
`fork`，必须显式改成 `spawn`。

**按"分区不重叠"设计写入。** 如果多个写者写的是不同的租户、不同的时间片，
那么冲突自然很少；如果所有写者都在追加同一个表，
append-vs-append 也是安全的。真正需要避免的是"多个进程同时做全表压实或
全表 upsert"。

**准备好重试整个业务操作。** 不是重试 `write()` 这一句，
而是重试"读→算→写"这一整段。我们的 `write()` 内部已经会重试
（参数就是 `max_retries`，默认 3），但那只能处理"我这次写入本身
重放一次还成立"的情况 —— 一旦业务逻辑依赖读到的值，就必须由上层重做整段。

**重试次数在哪调。** 本实现是 `Dataset.write(max_retries=N)` 这一个参数。
真实 Lance 侧的对应旋钮是 `CommitConfig.num_retries`（Rust API），
默认 20 次、约 60 秒（第 8.3 节）。**Python/OSS 的 LanceDB 连接接口里
并没有暴露一个"提交重试次数"参数** —— 这一点未经确认，用之前先查
你所装版本的 API；真正能调的往往不是重试次数，而是写入模式本身。

**用标签给关键版本上保险 —— 但要先确认它真的保得住。**
标签**应该**阻止 GC 删掉它指向的版本。本实现里这条曾经是**坏的**：
标签保住了 manifest，却没保住数据文件和删除文件，
于是 `cleanup_old_versions` 成功返回、几天后 `checkout(标签)` 报
`StoreError`。完整的成因、修法和回归用例在第 7.5 节。

把这条放在"多进程写的实操建议"里的理由是：**这类错误只在
"打了标签 + 跑了清理 + 想回到那个标签"三步都发生时才暴露**，
而这三步通常由不同的人、在不同时间做。所以哪怕你的实现已经修好了，
发布快照也值得**另做一次物理备份**——标签是元数据层面的引用，
备份是字节层面的副本，两者抗的故障不同。

**别忘了监控提交冲突率。** 如果冲突率高到影响吞吐，
说明写入模式有问题（比如所有进程都在做全表操作），
而不是需要把重试次数调大。

## 8.9 小结

**整个并发控制压在一个原子操作上：条件写（key 不存在才写）。**

**重活并发干、轻活串行做：** 数据文件随便写，只有几百字节的 manifest 需要协调。

**事务文件是日志不是状态：** 记意图（`read_version` / `operation` /
`payload` / `writer` / `timestamp`），可以丢，用来重放、判定冲突和审计；
它只增不减，没有 GC。

**冲突矩阵的判定原则**是"我的操作是否依赖对别人改动的完整了解"。
append 和 create_index 永远安全，修改行的操作之间保守判冲突。
重试次数要分清是谁的默认值：本实现 `max_retries=3`，
真实 Lance 默认 20 次、约 60 秒。

**给的是原子性、快照隔离和读己之写，没给跨表事务、跨分支事务和可串行化。**
先读后写的业务操作必须准备好整体重做，跨表要靠"把中间状态写进数据、
让重跑幂等"的补偿模式。

**压实和 GC 必须分开：** 压实只改引用，删除要等安全窗口。

**对象存储不支持条件写时，把"谁是最新"外包给一个支持事务的组件。**
但要注意 S3 历史默认的 `UnsafeCommitHandler` 根本不做检查，
并发写会静默丢更新 —— 并发安全要显式用上条件写的 commit handler。
