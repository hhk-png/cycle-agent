# 第 42 章 Embedding、Rerank 与检索推理

本章导读：生成式推理输出 token，表示式推理输出向量。两者都跑在 GPU 上，但瓶颈、批处理方式、缓存对象和成本模型完全不同。Embedding 服务要在高 QPS 下把短文本压成向量，Rerank 服务要在候选集上做 pairwise 打分，向量索引要在召回率、延迟和内存之间取舍。本章把这条“检索推理”链路拆成五段：编码、批处理、索引、重排、评测，并用 `mini_deepinfer/embedding.py` 把每一段跑成可测试的代码。DeepInfer 不覆盖这条路径，但任何推理平台最终都会遇到它。

## 42.1 生成与表示：两种计算特征

生成式推理的核心是自回归 decode：每步读一遍权重和 KV，受显存带宽限制，KV cache 是最大的资源。表示式推理没有 decode，也没有 KV：一次前向把整段文本编码成一个向量，计算量随 token 数线性增长，输出只有一个向量。它更像 prefill，但序列通常更短，batch 更大，QPS 更高。

这个差异决定了优化方向不同。生成式推理关心 KV 容量、前缀缓存、连续批处理和推测解码；embedding 推理关心 batch 大小、序列长度分布、padding 浪费和向量维度。生成式推理的尾延迟由长输出决定；embedding 的尾延迟由长输入和排队决定。生成式推理的缓存是 KV；embedding 的缓存是“文本或文档到向量”的映射，key 是内容哈希加模型版本。

Rerank 又不一样。Cross-encoder 把 query 和 document 拼在一起做一次前向，输出一个相关性分数；它的计算量随 pair 数线性增长，单个 pair 的 attention 成本随拼接长度平方增长。它通常只对检索出的前几十个候选做重排，而不是对全库打分。Embedding 是“召回”，rerank 是“精排”，两者解决的不是同一个问题。

## 42.2 双塔、pooling 与归一化

一个 bi-encoder 由三部分组成：token embedding、编码器（Transformer 或轻量网络）、pooling。编码器输出每个 token 的 hidden state，pooling 把它们压成一个向量。常见的 pooling 有 CLS token、mean pooling、last-token pooling；不同模型用不同策略，切换模型时必须沿用训练时的 pooling，否则向量空间会错位。

得到向量后通常要做 L2 归一化。归一化把点积变成余弦相似度，让不同长度的文本可比，也让索引可以用内积加速。`HashEmbedder` 默认归一化；测试 `test_embedder_is_deterministic_and_normalized` 检查同一文本的向量模长为 1，`similarity(a, a) = 1`。如果关闭归一化，余弦搜索仍然可以工作，但内积搜索会偏向长向量，索引行为会变。

真实的 embedding 模型还有几个工程细节。第一，**指令前缀**。有些模型要求 query 和 document 加不同的前缀（例如“query: ”、“passage: ”），前缀错了，召回率会明显下降。第二，**最大长度截断**。超过模型最大长度的部分会被截断，长文档可能丢掉关键信息；生产系统通常先分块，再对块做 embedding。第三，**维度与量化**。向量维度越高，表达力越强，但索引内存和带宽越大；Matryoshka embedding 允许截断维度，int8 或二值量化可以进一步压缩，代价是召回率。第四，**多语言与领域**。通用模型在垂直领域可能不如领域微调模型，评测必须用业务数据。

`mini_deepinfer/embedding.py` 的 `HashEmbedder` 是一个确定性的 bag-of-token 模型：查表、mean pooling、可选归一化。它不是训练好的语义模型，但保留了“token 序列到定长向量”的形状，足以验证批处理、索引和缓存的逻辑。

## 42.3 批处理与长度分桶

Embedding 服务的吞吐很大程度上取决于 batch 的形状。一个 batch 里的序列要 padding 到同一长度，padding 部分仍然参与计算；如果把一条 8 token 的 query 和一条 512 token 的文档放在一起，整批都按 512 算，浪费超过 90%。

解决办法是长度分桶加 first-fit。先把请求按长度排序，再把相近长度的请求装进同一个 batch，并限制每个 batch 的最大 token 数。`plan_embedding_batches()` 做的就是这件事：按有效长度排序，逐个尝试放进已有 batch，放不下就新开一个。`bucket_width` 把长度向上取整到固定桶，牺牲一点 padding，换取更稳定的形状和更好的 kernel 复用。

用示例里的长度 `[6, 3, 4, 5, 64, 63, 62, 120]`、`max_batch_size=4`、`max_batch_tokens=256`、`bucket_width=16`，规划结果是三批：前四个短序列一批（有效长度都补到 16），中间三个约 64 token 的序列一批，最后一个 120 token 的序列单独一批。总 padding 浪费约 17.4%。如果不排序、按到达顺序装批，短序列会和 120 token 的序列混在一起，浪费会高得多。

批处理还要和延迟目标一起看。Embedding 请求通常要求几十毫秒内返回；batch 越大，吞吐越高，但排队和单批时间也越长。生产系统会给 batch 设置一个时间窗口（例如 5 到 10 毫秒），窗口内的请求凑批，窗口结束就发车。这个策略和连续批处理的思想一致，只是没有 decode 阶段。

## 42.4 向量索引：召回率、延迟与内存

有了向量，就要能“找相近的”。最基础的是 flat 索引：把全库向量存成一个矩阵，查询时算一遍内积，取 top-k。它的召回率是 100%，但复杂度是 `O(N × d)`，库大了就慢。`VectorIndex(n_buckets=1)` 就是 flat 索引。

近似索引用空间换时间。IVF 先把向量聚成若干簇，查询时只扫最可能的几个簇；HNSW 用多层图做贪心搜索；PQ 把向量切成子空间做量化，减少内存。它们都引入一个可调参数：扫多少簇、搜多少邻居、用多少子量化。参数越激进，延迟越低，召回率越差。

`VectorIndex(n_buckets>1)` 用随机投影做桶划分：每个向量分到投影得分最高的桶，查询时只扫得分最高的 `probe_buckets` 个桶。`probe_buckets=n_buckets` 时结果和 flat 完全一致；`probe_buckets=1` 时只扫一个桶，可能漏掉真正最近的向量。示例里查询 `[10, 11, 12, 13]`，flat 和两桶搜索都返回 `kv-cache` 和 `lora`，只扫一个桶时只剩 `kv-cache`；这不是索引坏了，而是召回率和延迟的取舍。

索引还有三个容易忽略的问题。第一，**度量必须一致**。训练和检索用的相似度（cosine、dot、L2）要一致；归一化后的向量，cosine 和 dot 等价，但 L2 排序会不同。第二，**删除和更新**。很多近似索引不支持高效删除，只能标记删除再重建；文档更新后，旧向量必须失效，否则会召回过期内容。第三，**过滤**。业务经常要求“只在某租户、某语言、某时间段内检索”；先过滤再检索会损失召回，先检索再过滤可能返回不足 k 条。生产索引通常支持带过滤的 ANN，或者用分区索引。

## 42.5 Rerank：把预算花在短名单上

Rerank 的目标不是“再算一遍相似度”，而是用更贵的模型纠正 embedding 的排序。典型流程是：embedding 召回 50 到 200 条，cross-encoder 对每条打分，取前 5 到 10 条给下游。`RerankPipeline` 用 `retrieve_k` 控制召回数、`rerank_k` 控制最终返回数。

Cross-encoder 的成本是 `候选数 × 单对成本`。单对成本又随 query 和 document 的拼接长度增长，长文档要先截断或分块。生产系统会按延迟预算反推候选数：如果一次 rerank 只能花 20 毫秒，单对 1 毫秒，就只能重排 20 条；想重排更多，要么加 GPU，要么用小模型，要么先做粗筛。

Rerank 的分数是相对的，不是概率。不同模型、不同 query 的分数分布不一样，不能直接用一个全局阈值判断“相关”。常见的做法是：按分数排序取 top-k，或者用同一 query 内的分数做归一化，再用一个校准过的阈值。校准需要标注数据，不能拍脑袋。

Rerank 还会改变多样性。一个全是相似段落的候选集，重排后可能仍然是同一段内容的多个副本；生产系统会在重排后做去重或多样性约束，避免把上下文塞满重复信息。

## 42.6 缓存、版本与一致性

Embedding 和 rerank 都有缓存空间，但缓存的对象不同。

**文档向量缓存**的 key 至少包含：文档内容哈希、embedding 模型 fingerprint、预处理版本（分块、截断、归一化）、语言或指令前缀。任何一个变化都必须 miss。文档更新时，要删除旧向量或让旧版本自然过期；如果索引是双写（旧索引和新索引并存），查询要按别名切换，确认新索引召回正常后再删旧索引。

**Query 向量缓存**的 key 是 query 文本加模型版本。它的命中率取决于 query 的重复度；客服、搜索建议这类场景可能有较高重复，开放域问答则很低。缓存要设置容量和 TTL，避免被长尾 query 撑爆。

**Rerank 结果缓存**更敏感，因为同一个 query 对不同文档集合的排序不同。key 必须包含候选集或候选集指纹；只按 query 缓存会返回过期或错误的排序。

缓存还要考虑租户隔离。两个租户的文档内容可能相同，但访问权限不同；如果按内容哈希共享缓存，B 租户可能通过命中时间或结果推断 A 租户的文档存在。生产系统通常按租户命名空间隔离，或者只共享明确标记为公共的素材。

## 42.7 质量评测

Embedding 和 rerank 的评测不能只看 loss。检索系统关心的是“相关文档有没有被召回、排在第几”。常用指标有四个。

**Recall@k**：前 k 条里是否包含相关文档。它衡量召回能力，不关心排序。**MRR**：第一个相关文档的倒数排名，衡量“第一个正确答案有多靠前”。**nDCG@k**：考虑相关性等级和位置折扣，适合多级相关性。**MAP**：平均精度，综合排序质量。

评测集要包含真实 query、hard negative 和长尾。只用随机负样本，模型会显得很好；hard negative 才能区分“真的理解语义”和“只是匹配关键词”。还要按语言、长度、领域分层看，平均分不变可能意味着两类样本一升一降。

Rerank 的评测要单独做：先固定召回集，再比较 rerank 前后的 nDCG 或 MRR。如果召回集里根本没有相关文档，rerank 再好也没用；这时应该先优化 embedding 或分块，而不是换 reranker。

## 42.8 部署与成本

Embedding 和 rerank 可以独立部署，也可以和生成式模型混部。独立部署的好处是资源隔离、扩缩容简单；混部的好处是共享 GPU 和运维。混部时要防止 embedding 的长 batch 把生成式请求的 TTFT 拖慢，通常用优先级、MIG 切分或独立进程隔离。

成本模型和生成式不同。Embedding 的成本主要是输入 token 的编码，没有输出 token；每百万 token 的成本约等于 GPU 小时成本除以输入吞吐。Rerank 的成本是 pair 数乘以单对成本，长文档还要算截断后的 token。向量索引的成本包括内存（或 SSD）、查询 QPS 和重建时间；HNSW 的内存可能是原始向量的几倍，PQ 可以压缩但会损失召回。

一个常见的容量错误是“只算 GPU，不算索引”。当文档量从百万涨到十亿，索引的内存和重建时间会成为主要成本；这时可能需要分片、量化或磁盘索引。另一个错误是“按平均长度买 GPU”，长文档的尾部长尾会显著拉高单批时间，容量规划要按 P95/P99 长度留余量。

## 42.9 mini-deepinfer 的实现

`mini_deepinfer/embedding.py` 提供 `EmbeddingConfig`、`HashEmbedder`、`CrossEncoder`、`VectorIndex`、`plan_embedding_batches` 和 `RerankPipeline`。它们不依赖引擎，也不依赖训练框架。

运行：

```bash
python examples/embedding.py
```

一次运行的输出包括：4 篇文档的向量矩阵形状 `(4, 16)`，第一个向量的模长为 1；长度 `[6, 3, 4, 5, 64, 63, 62, 120]` 被分成三批，总 padding 浪费约 17.4%；flat 搜索返回 `kv-cache`（0.7574）和 `lora`（0.5857）；两桶搜索与 flat 一致；只扫一个桶时只返回 `kv-cache`；retrieve-then-rerank 返回 `kv-cache`（0.5591）和 `lora`（0.5142）。这些数字是确定性的，用来对照公式和接口，不代表真实模型的语义质量。

mini 没有训练 embedding 模型，也没有实现 HNSW、PQ、带过滤的 ANN、分布式索引和真实 cross-encoder。它证明的是“编码、分桶、索引、重排、缓存 key”这些服务机制的逻辑，不是“检索质量”。第 20 章的保真度矩阵同样适用于这里。

## 42.10 故障模式

**维度或模型不匹配**。查询用新模型编码，文档库还是旧模型的向量，相似度会完全错乱。防护是把模型 fingerprint 写进索引元数据，查询时校验，不匹配就拒绝或重建。

**归一化不一致**。索引写入时归一化，查询时忘记归一化，内积会偏向长向量。防护是把归一化写进编码器接口，不让调用方自己决定。

**分块策略变化**。文档分块大小变了，旧向量对应的是旧块，召回结果无法拼回原文。防护是把分块版本写进 key，并在索引切换时双写。

**索引删除不彻底**。文档被删除但向量还在，检索会返回已删除内容。防护是软删除加定期重建，或在 ANN 外维护一层权限/存在性校验。

**长文档截断**。超过最大长度的部分被静默截断，答案藏在尾部时召回失败。防护是分块、截断告警和按长度分层评测。

**批处理饥饿**。高 QPS 下 batch 窗口一直凑不满或一直满，导致延迟抖动。防护是自适应窗口和有界队列。

**租户串数据**。缓存或索引没有租户命名空间，A 租户的文档被 B 租户召回。防护是命名空间、哈希盐和访问控制。

## 42.11 ANN 参数、召回率与成本

近似最近邻索引的参数不是“默认值”，而是“召回率-延迟-内存”的旋钮。不同索引的旋钮不同，但调优方法是一样的：固定业务 query 集，画召回率随参数变化的曲线，选满足召回目标的最低成本点。

**HNSW** 有三个关键参数。`M` 是每个节点的邻居数，越大召回越高、内存越大；`efConstruction` 是建图时的候选数，越大图质量越好、构建越慢；`efSearch` 是查询时的候选数，越大召回越高、延迟越大。HNSW 的内存开销约为 `N × M × 2 × 4` 字节（双向边），一百万条 768 维向量，原始 FP32 约 3 GB，HNSW 图可能再加几百 MB。

**IVF** 有两个关键参数。`nlist` 是簇数，通常取 `sqrt(N)` 到 `4×sqrt(N)`；`nprobe` 是查询时扫的簇数，越大召回越高、延迟越大。IVF 的训练阶段要做 k-means，数据分布变化后需要重建或重新训练。

**PQ** 把向量切成 `m` 个子空间，每个子空间用 `nbits` 位编码。压缩率是 `m × nbits / (维度 × 32)`；例如 768 维 FP32、`m=96`、`nbits=8`，每条向量 96 字节，压缩约 32 倍。PQ 的召回损失来自子空间独立量化，通常要配合 rerank 或 OPQ 使用。

调优的顺序是：先用 flat 索引建立“真值”召回，再调 ANN 参数逼近它；不要用 ANN 的结果当 ground truth。评测要按业务 query 分布、语言、长度和过滤条件分层；一个在随机 query 上召回 95% 的索引，在长尾 query 上可能只有 70%。

成本不只在查询。索引构建、增量更新、删除、重建和副本都要算。HNSW 的插入是增量的，但删除通常只能标记；IVF/PQ 的重新训练可能需要全量重建。文档更新频繁的场景，要把“重建窗口”和“双写切换”设计进 pipeline，否则用户会检索到过期内容。

最后，过滤（tenant、语言、时间）会改变 ANN 的行为。先过滤再检索可能让候选集太小，召回下降；先检索再过滤可能返回不足 k 条。生产索引通常支持带过滤的 ANN，或者按租户/语言建分区索引；分区会降低跨分区检索的灵活性，但能保证隔离和召回。

## 42.12 带过滤的 ANN 与 hard negative

真实检索很少是“在全库里找最近邻”。租户、语言、时间、权限、文档类型都会带过滤条件；过滤和 ANN 的组合方式会显著影响召回和延迟。

**先过滤再检索**：先按条件缩小候选集，再在子集上做 ANN。召回上限是子集本身，优点是延迟低、不会返回越权结果；缺点是如果子集很小或分布偏，ANN 的索引结构可能失效（例如 HNSW 在小子图上连通性差）。**先检索再过滤**：先取 top-k，再丢掉不满足条件的；实现简单，但可能返回不足 k 条，尤其是过滤条件很严时。**过滤感知索引**：在索引结构里内置过滤，例如按租户分区、按时间分片、在图上做过滤遍历；召回和延迟更平衡，但实现复杂。

一个实用的做法是“分区 + 局部检索”：按租户或语言建独立索引，查询只进对应分区；分区内部再做 ANN。这样既保证隔离，又避免全局索引被小租户的过滤条件拖慢。分区会降低跨分区检索的灵活性，但对多租户 SaaS 通常是值得的。分区键要稳定，不能频繁变化；如果租户需要跨分区搜索，要在应用层合并结果。

Hard negative 是 embedding/Rerank 质量的关键。随机负样本太容易，模型只要学会“主题不同”就能拿高分；hard negative 是“看起来相关但答案不对”的文档，例如同一产品的新旧版本、相似问题的不同答案、同一文档的不同段落。挖掘方法有三种：用当前模型召回 top-k，把不相关的作为 negative；用人工标注的困难样本；用生成模型构造“近似但不正确”的文本。训练时要混合 easy/hard negative，比例太偏会让模型过拟合到困难样本。

评测也要用 hard negative。只用随机负样本，Recall@k 会虚高；用真实 query 和困难负样本，才能看出模型是否真的理解语义。评测集要按语言、长度、领域分层，并保留一个“私有集”防止过拟合。第 42.7 节的 Recall/MRR/nDCG 仍然适用，但数据构造比指标选择更重要。

## 小结

Embedding 与 rerank 是另一类推理负载：没有 KV，没有 decode，核心是编码吞吐、batch 形状、索引召回和重排延迟。Bi-encoder 把文本压成归一化向量，长度分桶和 first-fit 控制 padding；向量索引在召回率、延迟和内存之间取舍；cross-encoder 只对短名单做精排；缓存 key 必须绑定模型、预处理和租户；评测要看 Recall@k、MRR、nDCG 和 hard negative。mini 用确定性哈希向量和随机投影索引验证了这些机制，但没有复制真实语义模型和 ANN 库。下一章进入这些负载背后的执行层：推理编译器如何把模型图变成融合、复用内存的执行计划。
