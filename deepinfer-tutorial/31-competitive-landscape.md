# 第 31 章 竞争格局与开源战略

本章导读：推理框架不是只有 DeepInfer。vLLM、SGLang、TensorRT-LLM、TGI、LMDeploy、llama.cpp 各有定位。本章按模型覆盖、硬件、功能、生态和商业模式比较它们，解释 DeepInfer 为什么选择“只开源计算引擎”的边界，以及这个选择对用户和竞争者的含义。

## 31.1 主要玩家

**vLLM**：最广泛使用的开源推理引擎之一，PagedAttention 和 continuous batching 的代表。模型覆盖广，社区大，支持 NVIDIA/AMD/CPU 等多种硬件，OpenAI 兼容服务成熟。DeepInfer 的代码骨架大量继承自 vLLM。

**SGLang**：以 RadixAttention、前缀缓存和结构化生成（SGLang language）著称，调度和前端 DSL 有特色。DeepInfer 在调度和前缀缓存上受其启发。

**TensorRT-LLM**：NVIDIA 的官方推理栈，深度绑定 TensorRT 和 CUDA，kernel 融合、CUDA Graph、FP8/FP4 优化强，但模型适配和自定义不如 vLLM 灵活。DeepInfer 在 kernel 融合和低精度上参考了它。

**TGI**（Text Generation Inference）：Hugging Face 的服务框架，和 HF 生态结合紧密，适合快速部署 HF 模型；通用性更强，但专项优化不如专用引擎深。

**LMDeploy**：上海 AI Lab 的推理工具箱，强调 TurboMind 引擎、量化和多模态，在国内社区有一定使用。

**llama.cpp**：CPU/边缘推理的代表，GGUF 量化、跨平台、单机友好；不适合大规模 GPU 服务，但在本地/端侧很强。

**DeepInfer**：DeepSeek 的生产引擎切片，只支持 V4.1-Flash，绑定 SM100/Ascend 950，强调 kernel、Wide-EP、DSpark、SWA 重放、ZOS 和正确性。开源边界是“计算引擎”，不含 KV 存储、PD 分离部署和全局负载均衡。

还可以加上托管服务（云厂商的推理 API）和专用芯片厂商的 SDK。它们不一定是“框架”，但在选型时是替代方案：如果团队不想运维，托管 API 可能比自建任何框架都合适。

## 31.2 比较维度

不要用“谁更快”一句话比较。至少分六个维度。

**模型覆盖**：vLLM/SGLang 支持大量 Hugging Face 模型；TensorRT-LLM 需要为每个模型做适配；DeepInfer 只支持一个模型，但针对它做了深度优化。

**硬件覆盖**：vLLM 支持 NVIDIA/AMD/CPU/TPU 等；TensorRT-LLM 主要 NVIDIA；DeepInfer 支持 SM100 和 Ascend 950；llama.cpp 覆盖 CPU/Apple/边缘。

**功能**：continuous batching、prefix caching、speculative decoding、structured output、PD 分离、多模态。vLLM/SGLang 功能全；DeepInfer 在它支持的模型上功能深；TensorRT-LLM 性能强但灵活度低。

**性能**：取决于模型、硬件、batch、SLO。厂商 benchmark 往往在有利配置下测，不能直接横向比较。要看相同模型、相同精度、相同负载下的吞吐-延迟曲线。

**生态**：vLLM 社区最大，插件、教程、云厂商支持多；SGLang 有活跃的研究社区；TensorRT-LLM 有 NVIDIA 支持；DeepInfer 刚开源，生态还在建立。

**许可与支持**：vLLM/SGLang/DeepInfer/TensorRT-LLM 的仓库代码都是 Apache 2.0；但 TensorRT-LLM 依赖的 TensorRT 运行时另有 NVIDIA 许可，不能只看仓库许可证。llama.cpp 是 MIT。商业支持、SLA、安全补丁也是选型因素。

还可以加两个维度：**可运维性**（部署、监控、升级、故障恢复的成熟度）和**可扩展性**（加模型、加硬件、加自定义 kernel 的成本）。一个框架 benchmark 很好，但升级会破坏 API，长期成本可能更高。

## 31.3 DeepInfer 的差异化

DeepInfer 的差异化不在“通用性”，而在“垂直深度”：

- 只服务一个模型，可以针对 CED/CSA2/Engram/mHC 做专用 kernel；
- 只服务两种硬件，可以充分利用 SM100/Ascend 的特性；
- 有厂商自报的生产口径：155T token/天、96% 缓存命中、约 400 ms 平均 TTFT，说明它在内部生产中使用过，而不是只在实验室跑过 benchmark；这些数字没有第三方验证，不能当作独立性能证据，38 美元/GPU 小时更是收入口径而非负载证据；
- 开源了 DSpark、SWA 重放、ZOS、batch-invariant 等生产机制，这些在通用框架里往往只是部分实现；
- 明确标注了开源边界，不假装提供完整服务。

代价是：

- 换模型要改代码；
- 小规模部署不划算（推荐 64+64 GPU）；
- 缺少在线服务层和 KV 存储；
- 社区和文档还不如 vLLM 成熟。

DeepInfer 的另一个价值是“参考架构”。即使你不用它，也可以看它怎么把 CED/CSA2/DeepEP/ZOS 组织成一个系统，然后把这些设计借到自己的引擎里。第 2 章的“能力清单”就是这个用途。

## 31.4 为什么只开源计算引擎

这是一个典型的“开源核心、保留基础设施”的策略。

**开源的好处**：建立生态、吸引开发者、证明技术实力、降低客户信任门槛、获得外部反馈、形成事实标准。DeepSeek 开源 DeepInfer 和 deepseek-recipe，可以让第三方部署的 API 行为与官方一致，减少集成摩擦。

**保留的好处**：KV 存储、PD 分离部署、全局负载均衡和内部基础设施耦合太深，开源需要大量脱敏和抽象；这些也是生产服务的核心竞争力。保留它们可以避免竞争对手直接复制完整服务，同时仍然展示引擎能力。

这个策略的风险是“开源部分不够用”：用户拿到引擎，却发现缺 KV 存储和 PD 分离，无法直接生产。DeepInfer 的 README 明确说明了这一点，避免过度承诺。长期看，如果社区贡献了缺失的组件，开源边界可能会移动。

还有一个风险是“社区贡献意愿”。一个只支持单一模型的框架，外部开发者的改动很难复用；如果模型更新快，社区可能跟不上。DeepSeek 需要用文档、示例、CI 和 issue 响应来维持社区，否则开源会变成“代码展示”而不是“生态”。

## 31.5 对用户的选择建议

**选 vLLM**：需要多模型、多硬件、成熟 OpenAI 服务、社区支持；愿意自己调性能。

**选 SGLang**：需要强前缀缓存、结构化生成、研究友好；团队能跟前沿。

**选 TensorRT-LLM**：全 NVIDIA 栈、追求更低的 kernel 开销、能接受模型适配成本。

**选 DeepInfer**：模型就是 V4.1-Flash、硬件是 SM100/Ascend 950、有集群和 3FS、需要生产级 kernel 和调度；或者你想研究生产级推理系统的实现。

**选 llama.cpp**：本地/边缘/CPU、单机、量化、隐私。

**选托管 API**：不想运维、按 token 付费、需要弹性。

没有“最好”的框架，只有“最适合当前约束”的框架。选型前先写清楚模型、硬件、QPS、上下文长度、SLO、预算和团队能力。

一个实用的选型方法是“加权评分”：把模型覆盖、硬件、功能、性能、生态、许可、可运维性、成本列成维度，按业务权重打分。不要给“性能”一个过高的权重，除非你的业务真的受推理性能约束；很多团队的瓶颈其实是服务层、数据、产品体验。

## 31.6 性能比较的陷阱

厂商 benchmark 常见的偏差：

- 用有利的 batch/长度分布；
- 不报告 P99 延迟；
- 不说明是否开启推测解码/量化/前缀缓存；
- 用峰值吞吐而不是 goodput；
- 不同精度/模型版本；
- 不同 GPU 数量/互联；
- 不报告失败率/降级。

公平比较要固定模型、精度、硬件、batch 分布、SLO，报告吞吐-延迟曲线和尾延迟。最好用你自己的流量 trace 回放，而不是厂商的合成负载。

还有一个陷阱是“用不同版本的模型”。模型更新后，同样的框架可能快很多；把“模型进步”归因于“框架进步”，会得出错误结论。比较时要固定模型 checkpoint，或者明确说明模型版本差异。

## 31.7 开源生态的长期博弈

推理框架的竞争不只是性能，还有生态：

- 模型厂商希望自己的模型被框架优先支持；
- 硬件厂商希望框架用自己的 kernel/库；
- 云厂商希望框架能跑在自己的实例上；
- 企业希望框架稳定、可支持、许可清晰。

DeepInfer 的开源是 DeepSeek 生态战略的一部分：通过开源引擎和 Recipe，降低第三方部署 DeepSeek 模型的门槛，扩大模型的使用面；同时保留基础设施，维持服务质量的差异。这个策略能否成功，取决于社区是否愿意围绕一个“只支持一个模型”的框架贡献，以及 DeepSeek 后续是否开放更多组件。

从竞争角度看，DeepInfer 的对手不是 vLLM 的“通用性”，而是“其他模型厂商的专用引擎”。如果每个模型厂商都提供自己的高性能引擎，用户会按模型选引擎，而不是按引擎选模型。这会改变推理框架的市场结构：从“一个通用框架服务所有模型”变成“模型 + 引擎 + 云服务”的垂直整合。

评估一个开源推理框架的生态健康度，不能只看 star 数。更有用的指标包括：外部贡献者占比和留存、issue/PR 的首响应和合并时延、release cadence、bus factor（核心维护者数量）、安全披露流程、许可证和治理模式、以及在目标模型/硬件上的回归覆盖。一个“只有一个公司内部团队在提交”的框架，即使性能很好，也可能因为路线图不透明或供应中断而带来长期风险；反过来，一个治理开放但性能一般的框架，至少有可替换性。选型时把这些指标和性能、成本放在一起看，才不会把“今天最快”当成“三年后还能用”。

## 31.8 选型评分卡

“哪个框架最好”没有答案，但“哪个框架最适合当前约束”可以打分。一个实用的评分卡有八个维度，每个维度按 1 到 5 分打分，再按业务权重加权。

**模型覆盖**：是否支持你要服务的模型？换模型要改多少代码？DeepInfer 只支持 V4.1-Flash，这一项对多模型团队几乎是最低分；对只服务一个模型的团队是满分。

**硬件覆盖**：是否支持你的 GPU/NPU？是否有公开的性能数据？DeepInfer 支持 SM100 和 Ascend 950，但公开 benchmark 只有 NVIDIA；Ascend 的支持存在，性能要自己测。

**功能完整度**：连续批处理、前缀缓存、chunked prefill、推测解码、结构化输出、PD 分离、多模态。功能越多，覆盖场景越广，但复杂度也越高。

**性能**：在相同模型、精度、硬件、batch 和 SLO 下的吞吐-延迟曲线。不要用厂商的单点 benchmark；用自己的流量 trace 回放。

**可运维性**：部署、监控、升级、故障恢复、文档、社区响应。一个 benchmark 很好但升级会破坏 API 的框架，长期成本可能更高。

**许可与支持**：许可证是否允许商业使用？是否有商业支持、SLA、安全补丁？Apache 2.0 和 MIT 的义务不同，权重许可又是另一回事。

**生态**：插件、教程、云厂商支持、招聘容易度。生态大的框架，出问题更容易找到答案；生态小的框架，可能更贴近你的特定需求。

**成本**：GPU 利用率、KV 存储、网络、人力。框架本身的许可成本通常不是大头，运维和人力才是。

权重取决于业务。一个只服务 V4.1-Flash、有 3FS 和 SM100 集群的团队，会给模型覆盖和性能很高权重；一个多模型 SaaS 团队，会给模型覆盖和可运维性很高权重。不要照搬别人的权重，也不要把“性能”默认设成最高；很多团队的瓶颈其实是服务层、数据或产品体验。

评分卡的价值不是给出一个总分，而是逼你把“我为什么选它”写下来。半年后回头看，如果假设变了，你能知道当时的选择是否还成立。

## 31.9 可复现的横向 benchmark 协议

公平比较两个框架，最难的往往不是跑分，而是让两次运行“除了框架以外都一样”。一个可复现的协议至少包含八项。

**固定模型和精度。** 同一个 checkpoint、同一个量化格式、同一套 tokenizer 和 chat template。模型版本不同，性能差异会被误归因于框架。**固定硬件和拓扑。** 同一型号、同一数量、同一互联、同一驱动/CUDA/CANN 版本；跨机比较要写清楚 NVLink 域和 RDMA 配置。**固定负载。** prompt/output 长度分布、到达率、并发、batch 上限、缓存命中率、是否开推测解码，都要写成配置文件，而不是“默认设置”。**固定 SLO。** TTFT/TPOT 的上限、P99 还是 P50、错误率怎么算；不同 SLO 下的“最优 batch”不同。**固定测量方法。** warmup 步数、测量窗口、是否排除 profiler、是否用 trace replay；单次测量不可信，至少重复 5 次取中位数和分位数。**固定输出。** 吞吐（输出 token/s、总 token/s）、延迟分位数、goodput、显存、功耗、错误率；只报一个 tokens/s 不够。**固定失败处理。** OOM、超时、降级、重试是否计入；一个框架在失败时自动降级，另一个直接报错，吞吐数字不可比。**固定复现材料。** 配置文件、镜像 digest、脚本 commit、原始结果，能让第三方重跑。

协议写好后，先做“自比较”：同一个框架跑两次，差异应该在噪声范围内；如果自比较都不稳定，跨框架比较没有意义。再做“配对实验”：A/B 交替运行，用差值均值和置信区间判断，而不是看两个平均值谁大。第 26.12 节和第 29.12 节的统计方法可以直接用。

还要区分“框架差异”和“调优差异”。一个框架可能默认配置很差，但调参后很强；另一个默认很好，但上限低。公平比较要么都用默认配置（比“开箱即用”），要么都调到各自最优（比“工程上限”），不能一个默认一个调优。报告里要写清楚是哪一种，否则结论会被误读。

## 31.10 托管 API 与自建的 TCO 对比

选型不只是“哪个框架快”，还要回答“自己运维值不值”。托管 API 的成本是单价 × 用量，自建的成本是 GPU、电力、机房、网络、存储、人力和研发摊销。把两者放在同一时间窗口里比，才能看出临界点。

一个简化的自建年成本是：

```text
self_host = GPU 年化 + 电力 + 机房 + 网络/存储 + 运维人力 + 研发摊销
```

托管成本是 `tokens × 单价`，但要加上出网费、重试、缓存未命中的额外用量和迁移成本。自建的“单价”不是 `self_host / tokens` 这么简单，因为利用率、峰谷和冗余都会影响分母；低利用率时，自建单价可能远高于托管。

用第 32.3 节的自建 vs 云盈亏平衡公式：`u* = (自建 3 年 TCO / 3) / (GPU 数 × 8760 × 云上每 GPU 小时价格)`。如果实际利用率长期高于 `u*`，自建更便宜；低于 `u*`，托管更划算。注意不要把它和第 47.6 节“覆盖固定成本”的公式 `u* = 年固定成本 / (GPU 数 × 8760 × 每 GPU 小时贡献)` 混用：后者只说明自建能不能覆盖固定成本，不说明它比云便宜。这个判断对“模型固定、流量稳定、团队有 GPU 运维能力”的场景最可靠；对“模型频繁更新、流量波动大、合规要求高”的场景，托管的隐性价值（弹性、合规、模型更新）可能超过单价差异。

还要算“退出成本”。自建买了 GPU，如果模型路线变了、流量下降，设备残值和合同违约是损失；托管可以随时降量，但可能被单价锁定或数据迁移卡住。一个实用的决策方法是做三情景 TCO：保守（利用率 40%）、基准（60%）、乐观（80%），看自建在哪一档开始优于托管，以及这个档位是否现实。不要用单一利用率下结论。

## 小结

推理框架的竞争是多维度的：模型覆盖、硬件、功能、性能、生态、许可。DeepInfer 选择垂直深度而非通用性，只开源计算引擎，保留 KV 存储、PD 分离和全局负载均衡。用户应该按自己的模型、硬件、SLO 和团队能力选型，不要被单点 benchmark 误导。开源生态的长期博弈，比一次性能对比更值得关注。

## 练习

1. 用六个维度给你熟悉的两个框架做一张对比，不要只看吞吐。
2. 解释“开源核心、保留基础设施”策略的好处和风险。
3. 设计一个公平的 benchmark，比较 vLLM 和 DeepInfer 在同一个模型上的表现。你需要控制哪些变量？
4. 用 31.8 节的加权评分卡，为你的业务做一次选型，写出权重和理由。
