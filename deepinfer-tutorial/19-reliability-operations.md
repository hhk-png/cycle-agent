# 第 19 章 可靠性、运维与容量规划

本章导读：推理服务不是“跑起来就完了”。本章讨论自动扩缩容、故障切换、冗余配额、SLO、可观测性和容量规划，解释 DeepInfer 生产系统如何用 grace period、请求转发和 EP size 重定来吸收故障。最后给出一个可操作的容量规划清单和事故排查顺序。

## 19.1 失效模式

推理系统的故障可以分成几类：

- **硬件故障**：GPU 掉卡、NVLink 抖动、SSD 坏盘、网卡丢包。大 EP 部署里，一张 GPU 故障会让整个实例不可用。
- **软件故障**：kernel 崩溃、OOM、调度器死锁、KV 元数据损坏。
- **流量故障**：突发流量、长尾请求、恶意超长 prompt、热点专家。
- **依赖故障**：3FS 不可用、模型仓库不可达、DNS/网关故障。
- **人为故障**：错误配置、错误的模型版本、错误的扩缩容策略。

一个生产系统要针对每类故障设计检测、隔离、恢复和降级。推理框架能做的部分主要是：请求级重试/转发、KV 重建、graceful shutdown、健康检查、指标暴露；集群层面的故障转移要靠平台。

失效模式还可以按“影响范围”分层：单请求（超长 prompt、结构化输出失败）、单实例（OOM、kernel 崩溃）、单通信组（EP 组一张卡故障）、单集群（3FS 故障、网络分区）。不同层需要不同的恢复策略：单请求重试或降级；单实例重启或摘除；单通信组重定 EP size；单集群切流量或降级模型。把所有故障都当成“重启实例”，会放大故障。

## 19.2 自动扩缩容

DeepInfer 的官方 Q&A 说：prefill 根据非缓存 token 数决定需要多少机器；decode 根据 running 请求数调整；扩缩容有速率限制和上下界。

这个策略背后的逻辑是：prefill 的负载是“要算多少新 token”，缓存命中越多，需要的新 token 越少；decode 的负载是“同时有多少序列在生成”，每个序列每步都要算。两者不能用同一个指标扩缩容。

扩缩容还要考虑冷启动。加载 552B 权重、初始化 CUDA Graph、warmup 需要时间；如果流量涨得快，扩容跟不上。生产系统会保留“ready but unoccupied”的机器作为 scale-out inventory，并保持实际在线实例数高于计算需求；配额利用率高于 0.8 时禁止缩容。

一个更细的扩缩容策略是“分层”：prefill 按非缓存 token 的滑动窗口扩，decode 按 running 序列数和 KV 占用扩，VE 按图像 patch 数扩。三者的扩容速度不同：prefill 可以快速加机器，decode 受 KV 迁移影响，VE 受图像预处理影响。把它们绑在一起扩，会造成资源浪费或瓶颈。

## 19.3 Grace period 与请求转发

Decode 引擎收到关机通知后，不是立刻退出，而是进入 1 分钟 grace period。未完成的请求连同 KV cache 一次性转发到其他 CE 继续 decode。这个设计的目的是避免“缩容杀死正在生成的请求”。

请求转发要求：

- 目标 CE 有足够的 KV 空间；
- KV 传输的格式和源 CE 兼容；
- 请求的采样状态、grammar matcher、MTP 状态能一起迁移；
- 源 CE 在传输完成后才能释放资源。

DeepInfer 开源了 `send_processed_prompts`、`finalize_seq` 等虚函数和 `PROMPT`/`COMPLETION` 引擎类型，但跨实例的 KV 传输和请求转发主要在内部基础设施里。mini 的 `export_sequence_kv`/`import_sequence_kv` 演示了最小交接，但不处理采样状态和 grammar。

请求转发的失败模式要提前设计：目标 CE 没有空间、传输超时、格式不兼容、源 CE 在传输完成前崩溃。一个实用的策略是“先预留目标资源，再传 KV，最后切换请求所有权”；任何一步失败，源 CE 仍然持有请求，可以重试或返回错误。不要先释放源资源再传，否则失败就丢请求。

## 19.4 故障切换与 EP size 重定

大 EP 部署里，所有 GPU 形成一个通信域，一张卡故障会让整个实例不可用。重启时，平台重新确定 EP size：从当前健康的 GPU 里选一个能整除专家数的规模，实例按实际拿到的 GPU 数运行。这样剩下的健康 GPU 不会因为一张坏卡全部报废。

这个策略牺牲了“实例规格固定”的假设，换取了可用性。它要求模型加载、并行组初始化、EPLB 都能接受动态的 EP size；也要求调度器知道实例的容量变了，重新分配请求。

EP size 重定不是“随便选一个能整除的数”。专家数、每 rank 的容量、显存、互联拓扑都会约束可选值。例如 384 个专家、每 rank 4 个专家，可选 EP 是 96；如果坏了 3 张卡，93 不能整除 384，可能要退到 64 或 48，容量会大幅下降。平台要提前准备“降级档位”，并在扩容时优先恢复到标准档位。

## 19.5 SLO 与指标

一个推理服务至少应该暴露：

- 请求数、成功/失败/超时；
- TTFT、TPOT、E2E 的均值/P50/P95/P99；
- 输入/输出 token 数；
- batch size 分布、running/waiting 队列长度；
- GPU 利用率、HBM 带宽、显存占用；
- KV 命中率、block 使用率、COW/换出次数；
- MoE `moe_lb`、all-to-all 延迟；
- 推测解码接受率、验证长度；
- 结构化输出编译失败率、mask 拒绝率。

SLO 要写成可测量的形式，例如“P95 TTFT < 800 ms，P99 TPOT < 80 ms，错误率 < 0.1%”。不要写“响应要快”。

SLO 还要定义“什么算成功”。一个请求返回了 200 但内容被截断，算成功还是失败？一个结构化输出返回了合法 JSON 但字段缺失，算成功吗？这些定义会影响错误率和 goodput，必须在服务等级文档里写清楚。

错误预算（error budget）是一个有用的管理工具：它把 SLO 允许的不达标时间/请求比例变成一个可分配的预算。预算充足时可以多发布、多试验；预算耗尽时冻结发布、优先修可靠性。具体的 43 分钟和按请求比例拆分的算法见 19.11 节，这里只强调它必须写进发布流程，而不是停在口号上。

## 19.6 容量规划

容量规划的输入是：流量模型（QPS、prompt/output 长度分布、并发）、SLO、硬件规格、模型配置、缓存命中率。输出是：需要多少 P 实例、多少 D 实例、多少 KV 存储、多少网络带宽。

一个简化的步骤：

1. 用 P50/P95 的 prompt 长度和输出长度估算每请求的 prefill token 和 decode token。
2. 用第 4 章的公式估算单卡/单实例的 prefill 吞吐和 decode 吞吐。
3. 用 Little 定律估算并发：`并发 = QPS × 平均停留时间`。
4. 用 KV 字节数 × 并发 × 平均上下文长度估算显存需求。
5. 加上冗余：N+1 或 N+20%，并检查配额利用率不超过 0.8。
6. 用压测验证，而不是只信公式。
7. 留出扩容时间：冷启动、权重加载、CUDA Graph capture。

对长上下文 Agent 负载，KV 存储和网络往往是瓶颈，不是 GPU 算力。对短聊天负载，decode 的 batch 和 TPOT 更关键。

容量规划要区分“稳态”和“峰值”。稳态决定基线机器数，峰值决定冗余和 burst 策略。一个常见的错误是“按峰值买机器”，导致利用率低、成本高；另一个错误是“按稳态买机器”，遇到突发流量就排队。混合策略是“基线自建 + 峰值云 burst”，第 32 章会展开。容量规划还需要排队模型：同样的 GPU 数，利用率从 0.7 升到 0.9，平均吞吐只涨一点，P99 却可能翻几倍；第 46 章给出 M/M/1、M/M/c、准入控制和容量缓冲的算法。

## 19.7 事故排查顺序

线上 TTFT 飙升时，按下面的顺序查：

1. waiting 队列是否变长？是，prefill 容量不足或调度被长请求占满。
2. prefill 的缓存命中率是否下降？是，3FS/网络/元数据问题。
3. GPU 利用率是否下降？是，CPU 调度、同步、KV 换入换出。
4. `moe_lb` 是否变差？是，专家热点或 EPLB 未及时重平衡。
5. all-to-all 延迟是否上升？是，网络或 EP 规模问题。
6. 是否有大量结构化输出请求？grammar 编译/匹配可能成为 CPU 瓶颈。
7. 是否有大量长 prompt？chunked prefill 的 chunk 预算可能被挤占。

TPOT 飙升时，先看 decode batch 是否过大、KV 长度是否增长、是否有抢占、是否触发换出、是否降频。

排查时要“先看趋势，再看单点”。一个指标突然从 20 ms 涨到 200 ms，通常不是慢启动，而是某个资源饱和或某个依赖故障。看时间序列、看分位数、看同一时刻的其他指标，比盯着一个平均值有用。

## 19.8 安全与多租户

推理服务的安全边界包括：

- 输入长度限制，防止超长 prompt 耗尽 KV；
- 输出长度限制和超时，防止无限生成；
- 特殊 token 注入防护，防止用户伪造角色；
- 结构化输出编译缓存的上限，防止 DoS；
- 多租户的配额、鉴权、审计；
- 模型权重和 KV 的访问控制；
- 日志脱敏，避免记录用户 prompt。

DeepInfer 的 `XGrammarCompiler` 注释里提到 CVE-2025-32381，说明结构化输出缓存也可能是攻击面。生产部署要把这些边界写进网关和引擎，而不是只靠模型“自觉”。第 28 章会展开完整的威胁模型和控制项。

## 19.9 mini-deepinfer 的运维接口

mini 的 `EngineMetrics` 暴露请求数、token 数、TTFT/TPOT、推测接受率、抢占次数；`/metrics` 端点输出 Prometheus 文本；`/health` 做健康检查；`stats()` 返回 metrics、scheduler、block manager 的快照，以及 KV cache 的容量（`kv_cache_bytes`）和驻留块占用（`kv_cache_used_bytes`、`kv_cache_occupancy`）。前者是预分配的上限，运行中基本不变；排障时要看后者，否则会把“容量很大”误当成“还有空闲”。

这里有一个容易误读的口径：`kv_cache_used_bytes` 统计的是**物理驻留**的块，包括 `ref_count == 0` 但仍被前缀缓存持有的块；`block_manager.stats()` 里的 `free_blocks` 则是**可分配**的块，包含这些可以被淘汰的缓存块。两个数字都正确，但回答的问题不同：前者回答“HBM 里现在有多少 KV”，后者回答“还能不能再分配”。如果实现只按 `ref_count > 0` 统计 used，请求结束后占用会瞬间掉到 0，而 HBM 其实还被前缀缓存占着，排障时会完全看反。mini 现在同时暴露 `resident_blocks`、`allocatable_blocks` 和 `cached_blocks`，就是为了把这两本账分开。`stats()` 仍然不返回完整的 KV 页表快照。

它没有自动扩缩容、grace period、跨实例转发，但这些接口可以作为练习的起点：例如给 `EngineServer` 加一个 `/admin/drain` 端点，收到后停止接收新请求，把 running 请求跑完再退出。这需要修改 server 的请求接纳逻辑，并给 engine 加一个 `draining` 状态。

## 19.10 混沌演练

可靠性不能只靠“设计时想到”，还要靠演练验证。可以从小规模开始：

1. 在测试环境杀掉一个 worker，观察请求是否重试、KV 是否重建。
2. 模拟 3FS 超时，观察前缀缓存 miss 时是否回退到重算。
3. 注入超长 prompt，观察准入控制是否拒绝、队列是否被占满。
4. 模拟 GPU 掉卡，观察 EP size 重定和流量转移。
5. 模拟突发流量，观察自动扩缩容是否跟得上、SLO 是否守住。

每次演练都要记录“预期行为、实际行为、恢复时间、发现的缺口”。没有演练的故障转移方案，往往在真实故障时才发现少了一个状态、少了一个超时、少了一个告警。

## 19.11 SLO 与错误预算的算例

SLO 不是一句“要快”，而是一个可计算的预算。

假设月可用性 SLO 是 99.9%，每月按 30 天算，允许的不达标时间是 `30 × 24 × 60 × 0.001 = 43.2` 分钟。如果本月已经因为一次 3FS 故障停了 20 分钟，剩下的发布窗口只有 23.2 分钟；任何新的高风险变更都应该推迟，直到预算恢复。

如果 SLO 是“P95 TTFT < 800 毫秒”，预算不是按时间算，而是按请求比例算。一个月 1 亿请求，允许 500 万个请求超过 800 毫秒。这个预算要按租户、模型、区域拆分；一个大租户把预算用完，不应该让其他租户一起受罚。

错误预算的价值是让“可靠性”和“发布速度”变成可管理的 trade-off。预算充足时，可以多发布、多试验；预算耗尽时，冻结发布、优先修可靠性。它比“大家觉得稳定”更可执行。

推理服务还要定义“什么算成功”。一个请求返回 200 但被截断，算成功吗？一个结构化输出返回合法 JSON 但字段缺失，算成功吗？一个流式请求在第一个 token 后断开，算成功吗？这些定义会影响错误率和 goodput，必须写进服务等级文档，并在指标里实现。

一个实用的做法是把 SLO 拆成三层：基础设施层（GPU 可用、节点健康、3FS 可达）、引擎层（TTFT/TPOT、错误率、抢占率）、业务层（任务成功率、工具调用成功率、用户反馈）。三层指标一起看，才能区分“机房故障”“引擎回归”“模型质量下降”。

## 19.12 静默数据损坏与硬件退化

不是所有故障都会让进程崩溃。GPU 的 HBM 位翻转、NVLink 重传后的静默丢包、SSD 的静默损坏、kernel 的越界写，都可能让结果“看起来正常，其实已经错了”。这类故障叫静默数据损坏（silent data corruption，SDC），它比宕机更难发现，因为监控上的错误率、延迟和吞吐都可能完全正常。

检测 SDC 要靠“独立于计算的校验”。常见手段有三类。第一，端到端校验和：KV block、模型分片、传输消息带 CRC 或哈希，读取时校验；这会增加带宽和 CPU 开销，所以通常只对冷数据、跨机传输和关键权重开启。第二，数值基线：固定输入、固定 seed 的 logits 或 PPL 基线，定期在灰度实例上重跑，偏离阈值就摘除；第 26 章的 PPL baseline 就是这种思路。第三，业务金丝雀：一组固定的 prompt 和期望输出（或评分），持续打到每个实例，发现质量漂移。

硬件退化有前兆。GPU 的 ECC 可纠正错误计数、XID 错误、NVLink 重传率、SSD 的介质错误和延迟长尾，都应该进入监控；这些指标比“进程是否活着”更早反映问题。策略上，ECC 不可纠正错误通常意味着换卡；可纠正错误持续增长要降权或隔离；NVLink 重传率高要先查拓扑和光模块，而不是直接重启。

SDC 的经济学是“检测成本 vs 错误成本”。给所有 KV 加 CRC 可能让带宽翻倍，不划算；但给跨机 KV 传输、模型权重加载和评测基线加校验，成本可控，收益很大。对不能容忍错误的业务（金融、医疗、合规审计），还要考虑冗余计算或结果投票；对普通聊天，重试和灰度通常就够了。关键是把“检测什么、多久检测一次、发现后怎么处理”写成明确的策略，而不是等用户投诉。

## 小结

可靠性是推理系统的一部分，不是运维团队的附加工作。自动扩缩容要区分 prefill 和 decode 的负载指标；grace period 和请求转发避免缩容杀请求；EP size 重定让故障实例的剩余 GPU 继续服务；SLO 要可测量；容量规划要用公式加压测。mini 提供了指标和健康检查的骨架，但没有生产级的故障转移。
