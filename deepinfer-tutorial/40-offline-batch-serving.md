# 第 40 章 离线批处理：吞吐型推理服务

本章导读：DeepInfer 开源的入口是离线推理，但“离线”不等于“把请求一次性丢给模型”。离线服务有自己的目标函数：在截止时间前完成尽可能多的请求，把 GPU 利用率拉高，把单位 token 成本压低。它关心的不是单个用户的 TTFT，而是整个批次的 makespan、尾延迟、失败重试和可恢复性。本章讲批量规划、调度策略、检查点、计费口径和成本模型，并用 mini-deepinfer 的 `offline_batch.py` 把这些概念跑成一份可审计的报告。

## 40.1 离线与在线是两种目标函数

在线服务的核心约束是 SLO：TTFT 要低、TPOT 要稳、尾延迟不能炸。离线服务的核心约束是截止时间和成本：一批请求必须在某个时间点之前跑完，GPU 不能空转，失败要能重试，结果要能对账。

这个差异会改变很多默认选择。在线服务倾向小 batch、快速抢占、保留冗余；离线服务倾向大 batch、尽量填满、接受更长的单请求延迟。在线服务按请求或 token 计费，离线服务可能按任务、按 GPU 小时或按批次计费。在线服务怕尾延迟，离线服务怕长尾任务拖垮整个批次。

离线服务也不是“没有延迟要求”。它通常有批次截止时间，例如“每天凌晨 6 点前跑完”“这份评测报告 2 小时内出来”。截止时间把离线问题变成了一个调度问题：哪些请求先跑、哪些可以等、哪些要降级、哪些要放弃。没有截止时间的离线批处理，很容易变成“先把简单的跑完，难的一直排队”。

## 40.2 批的组成：长度、预算与 padding

离线批处理的第一层是“把哪些请求放进同一批”。最朴素的做法是按到达顺序攒够 N 个请求，但这会遇到和在线静态 batch 一样的问题：短请求等长请求，长请求拖慢整批。更好的做法是按长度分桶，把相近长度的请求放在一起，减少 padding 和单步时间的方差。

LLM 的 batch 通常用 varlen 表示，不需要把每条序列 padding 到同一长度；但视觉编码器、某些 kernel 和某些推理后端仍然要求形状一致。即使 LLM 不需要 padding，batch 太大也会让单步时间变长、KV 峰值变高、尾延迟变差。离线调度要同时限制 batch size 和 token budget，而不是只限制请求数。

`plan_waves` 用“预估 token 数”做预算：每个请求的成本是 prompt token 加 max_tokens，按优先级、截止时间和成本排序，然后按顺序 next-fit 装进 wave（放不下就开下一个 wave，不回溯）。一个 wave 是一个准入单元，wave 内部的请求仍然由引擎做连续批处理。这样既保留了引擎的动态调度，又让离线层能控制批次大小和截止时间。

排序键值得解释。优先级高的请求先排，保证重要任务不被普通任务挤掉；同优先级按截止时间升序，接近截止的请求先走；再按成本升序，让小请求先填满 wave 的空隙。这个排序不是全局最优，但它可解释、可复现，适合作为起点。生产调度器可能会用更复杂的背填（backfill）策略：先放大任务，再用小任务填它留下的空隙，前提是不推迟大任务的截止时间。

## 40.3 调度策略：FIFO、优先级、EDF 与背填

FIFO 最简单，按到达顺序执行。它的优点是公平、可预测；缺点是大请求会堵住后面的小请求，截止时间利用率低。

优先级调度给每个请求一个权重，高优先级先跑。它适合多租户或重要任务，但可能导致低优先级请求饥饿。缓解手段是 aging：等待越久，优先级越高；或者给每个租户保留配额。

EDF（Earliest Deadline First）按截止时间排序，理论上在单处理器、可抢占的场景下是最优的。但在推理服务里，请求的执行时间不确定，GPU 也不是单处理器；EDF 会导致“临近截止的请求”频繁抢占，增加上下文切换和 KV 重算。生产系统通常用 EDF 做粗排，再用背填和配额做修正。

背填是先调度一个“大”请求，然后在不影响它截止时间的前提下，把小请求塞进它等待的窗口。它对离线批处理很有效，因为大请求往往要跑很久，而小请求可以填满 GPU 的空隙。背填的关键是准确估计大请求的剩余时间；估计错了，要么空转，要么错过截止。

无论用哪种策略，都要处理“不可调度”的请求：prompt 太长、超过模型上下文、schema 非法、预算不够。这些请求应该在准入时被拒绝或标记，而不是在 GPU 上跑一半才失败。离线服务的失败重试也要有上限，否则一个永远失败的请求会无限占用队列。

## 40.4 检查点与可恢复性

离线批次可能跑几个小时，中间会遇到 GPU 故障、节点重启、模型热更新、存储抖动。一个没有检查点的批处理，失败一次就要从头开始；一个有检查点的批处理，可以从最后一个完成的 shard 继续。

检查点的粒度通常是“请求”或“shard”。请求级检查点记录每个请求的状态：未开始、运行中、完成、失败、跳过；完成的结果写到持久存储，带 request id、模型 manifest、输入哈希和输出哈希。恢复时先读结果清单，跳过已完成的请求，再重跑未完成和失败的请求。

幂等性是检查点的基础。同一个 request id 重跑多次，结果应该一致，或者至少能识别“这是同一次请求的重复输出”。如果采样是随机的，重跑会得到不同文本；离线场景通常用固定 seed 或贪心，保证可复现。如果业务需要随机性，结果清单要记录 seed 和采样参数，重跑时复用同一组参数。

分片（shard）是另一种粒度。把输入按文件或行号切成 shard，每个 shard 独立处理、独立写结果。shard 失败只重跑该 shard，不需要重跑整个批次。shard 的大小要平衡：太小，调度和检查点开销高；太大，失败重跑成本高。一个实用的起点是每 shard 几百到几千个请求，按平均输出长度调整。

检查点还要记录“为什么失败”。是输入非法、模型 OOM、超时、还是被用户取消？不同失败的重试策略不同：输入非法不应该重试，OOM 可以降 batch 重试，超时可以拆分请求或延长预算。把所有失败都当成“再跑一次”，会浪费大量 GPU。

## 40.5 输出、计费与对账

离线批处理的输出不只是一段文本，还包括一份可对账的记录：request id、模型版本、tokenizer 版本、输入 token 数、输出 token 数、缓存命中数、开始时间、结束时间、finish_reason、错误码。没有这些字段，出了问题无法定位，计费也无法核对。

`usage` 字段要由引擎的实际计数产生，而不是重新编码文本估算。离线场景尤其如此，因为一个批次可能包含几百万条请求，估算误差会累积成很大的账单差异。缓存命中的 token 要和未命中的 token 分开计费；如果输入命中了 90% 的前缀，实际 prefill 只有 10%，但输入 token 数仍然是全部，定价要能反映这个差异。

失败请求的计费规则要提前定义。一个请求跑到一半 OOM，算不算消耗了 GPU？一个请求因为输入非法被拒绝，是否收费？一个请求被用户取消，已经生成的 token 是否计费？这些规则要写进合同和 API 文档，而不是在账单出来后再解释。

对账还要覆盖“结果完整性”。一个批次声称完成了 100 万条请求，但结果文件只有 99 万条，差额在哪里？是失败了、跳过了、还是写丢了？结果清单要有总数、成功数、失败数、跳过数和每种失败的原因分布。没有这份清单，离线服务无法证明自己完成了任务。

## 40.6 成本：利用率、批大小与峰谷

离线批处理的单位成本主要由三个变量决定：GPU 利用率、batch 大小和电价。利用率越高，固定成本摊得越薄；batch 越大，权重读取被摊得越薄；电价越低，每小时成本越低。三者不是独立的：batch 太大会让单步时间变长，降低吞吐；电价低的时段可能 GPU 供应紧张；利用率太高会让故障恢复变慢。

一个实用的成本模型是：每百万输出 token 成本等于 GPU 小时成本除以利用率，再除以每小时输出 token 数。第 30 章已经给出公式。离线场景可以把利用率推到比在线更高，因为没有 TTFT 和 TPOT 的硬约束；但也不能推到 100%，要留出故障恢复、重试和峰值的余量。

spot 实例和 off-peak 折扣是离线服务的常用手段。spot 便宜，但会被随时回收；如果批次有检查点、能快速迁移，spot 很适合离线。off-peak 电价低，但需要把延迟不敏感的任务排到低谷；这要求调度器能识别“可延迟”的请求，并把它们和在线流量隔离。

batch 大小的选择要看“吞吐-延迟曲线”的拐点。小 batch 时固定开销主导，增大 batch 几乎线性提升吞吐；大 batch 时计算和 KV 读取主导，吞吐饱和，单步时间快速增长。离线服务可以选在饱和点附近，但要用截止时间约束尾延迟。一个批次里如果有几个超长请求，它们可能决定整个批次的 makespan；把超长请求单独分桶，往往比把它们混在普通批次里更划算。

## 40.7 质量：批不变性与可复现

离线批处理的质量保证和在线一样重要，但侧重点不同。在线服务怕“同一个请求在不同 batch 下输出不同”，离线服务怕“同一批请求重跑后结果不同”。两者都指向 batch invariance 和 deterministic sampling。

如果离线任务用贪心解码，batch 组成不应该改变输出；如果用了随机采样，固定 seed 后重跑应该得到相同结果。第 10 章讲过，GPU 的归约顺序、split-K、低精度 kernel 都可能让 logits 产生微小差异，进而在 argmax 处翻转。离线服务如果要求逐字节可复现，要开启 batch-invariant 路径，并固定模型、tokenizer、模板、硬件和驱动版本。

长上下文在离线场景里更常见，因为离线任务可以承受更长的输入。KV 压缩、稀疏注意力、SWA 重放对长上下文召回的影响，要在离线评测集上单独测。不要用在线聊天的短样本评测离线文档任务；长度分布不同，瓶颈和误差来源都不同。

结构化输出在离线场景里也常用，例如批量抽取 JSON、批量生成评测报告。离线服务可以承受更高的编译成本，因为同一个 schema 会被大量请求复用；编译缓存一次，后面都是命中。但要注意 schema 的版本和缓存 key，不能因为“都是 JSON”就复用错误的文法。

## 40.8 mini-deepinfer 的实现

`mini_deepinfer/offline_batch.py` 提供四个东西。`BatchItem` 描述一个离线请求：prompt、max_tokens、temperature、seed、优先级、截止时间、租户和预估 prompt token 数。`plan_waves` 按优先级、截止时间和成本排序，把请求装进受 batch size 和 token budget 约束的 wave。`run_offline_batch` 逐个 wave 调用常规引擎，收集结果、延迟、token 数和截止时间达成情况。`BatchReport` 计算吞吐、P50/P95 延迟、截止时间错过率和 goodput。

运行：

```bash
python examples/offline_batch.py --max-tokens 6
```

一次运行的 wave 划分是：第一批 `doc-6, doc-3, doc-2, doc-5`，预估 172 token；第二批 `doc-0, doc-1, doc-7, doc-4`，预估 141 token。8 个请求全部完成，输出 48 个 token，墙钟约 0.03 秒，输出吞吐约 1,420 token/s，P95 延迟约 23 毫秒，截止时间错过率为 0。这些时间数字依赖机器负载，不同机器上会差 20% 以上，只用于说明报告的字段；wave 划分和 token 数是确定性的，可以逐项对照。

mini 的 wave 调度是“优先级 + 截止时间 + next-fit”，没有实现背填、抢占、检查点和跨进程恢复。它的价值是让你看到离线服务的报告应该包含什么，以及一个简单的调度策略如何影响批次组成。生产系统要把 wave 规划、重试、检查点和结果清单做成独立的控制面，而不是塞进引擎。

## 40.9 生产化清单

上线离线批处理前，确认这些点。输入要能分片，分片大小和失败重跑成本要平衡。每个请求要有唯一 id、输入哈希、模型 manifest 和结果哈希，支持幂等重跑。结果清单要记录成功、失败、跳过和失败原因，能和账单对账。调度器要支持优先级、截止时间、背填和配额，能隔离超长请求。检查点要覆盖请求级和 shard 级，恢复时跳过已完成的结果。失败重试要有上限和退避，区分可重试和不可重试。成本模型要把利用率、batch、spot 和 off-peak 算进去，并留出故障恢复余量。质量评测要覆盖长上下文、结构化输出和 batch invariance。日志和追踪要能按批次、shard、请求三级定位。

## 40.10 EDF、背填与可运行伪代码

优先级和截止时间排序可以写成一段很小的伪代码：

```text
ready = sort(items, key=lambda x: (priority desc, deadline asc, cost asc))
running = []
while ready or running:
    t = now()
    # 1. 认领新工作：先放大任务，再用小任务填空隙
    for item in ready:
        if can_start(item, t) and deadline_ok(item, t):
            start(item)
    # 2. 背填：不推迟任何已启动任务的前提下，塞入小任务
    for item in ready_by_size_asc:
        if fits_gap(item, running) and not delays_any_deadline(item, running):
            start(item)
    # 3. 等待最早完成的任务
    advance_to(min(finish_time(running)))
```

这段伪代码有三个关键点。

**EDF 只做粗排。** 真正的最优调度需要知道每个请求的执行时间，而 LLM 的执行时间取决于输出长度、batch 组成和 KV 状态，事先只能估。生产系统通常用 EDF 做顺序，再用背填和配额修正；不要指望 EDF 在非抢占、执行时间不确定的 GPU 上达到理论最优。

**背填的前提是“不推迟大任务”。** 先启动一个大任务，它占住 GPU 到 `t+Δ`；在这段时间里，如果小任务能在 `t+Δ` 前完成，就可以塞进去。判断条件是 `small.finish <= big.start_of_next_phase`，不是“GPU 有空就塞”。估计错了，要么空转，要么错过截止时间。

**超长请求要单独分桶。** 一个 128K prompt 的 prefill 可能比整个批次的其他请求都长；把它混在普通批次里，会让 makespan 由它决定。生产系统会给超长请求单独的队列、更大的 chunk 或更宽松的截止时间，避免它拖垮短请求。

离线调度还要处理“不可调度”的请求：prompt 超过模型上下文、schema 非法、token 预算不够。这些请求应该在准入时被标记，而不是在 GPU 上跑一半才失败。失败重试要有上限和退避；一个永远失败的请求不应该无限占用队列。

## 40.11 离线与在线的混合部署

很多团队会把离线和在线放在同一个集群，利用低谷填谷。混部能提高利用率，但会引入新的尾延迟风险。

**优先级隔离**：在线请求高优先级，离线请求低优先级；离线任务只能使用“在线预留之外”的容量。Kubernetes 的 PriorityClass、队列权重和抢占策略可以做粗粒度隔离。

**资源隔离**：在线和离线共享 GPU 时，离线的大 batch 会争 HBM 带宽和 L2，让在线 TPOT 抖动。更安全的做法是按 GPU 或 MIG 切分，而不是在同一张卡上混跑。

**时间隔离**：把离线任务排到低谷，或者用“可中断”的 spot 实例；在线高峰时自动暂停离线任务。暂停要能保存检查点，否则重跑成本很高。

**SLO 保护**：混部时监控在线 P99，而不是总吞吐；离线任务把 GPU 利用率拉高，但如果在线的 P99 越过 SLO，混部就是亏的。第 46 章的排队模型可以用来估算“离线占多少容量时，在线还能守住 SLO”。

混部的经济性要用“增量成本”算：如果离线任务使用的是本来会闲置的容量，边际成本很低；如果它挤占了在线容量，导致在线扩容，成本可能比单独建离线集群更高。不要只看平均利用率。

## 小结

离线批处理的目标不是低 TTFT，而是在截止时间前以最低成本完成尽可能多的请求。它把问题拆成四层：批的组成、调度策略、检查点与恢复、结果与计费。长度分桶和 token budget 控制 batch 的形状；优先级、EDF 和背填控制顺序；请求级和 shard 级检查点控制失败成本；结果清单和 usage 控制对账。mini-deepinfer 用 wave 规划和报告把这些概念跑通，但没有实现生产级的背填、抢占和跨进程恢复。下一章转向平台能力：一个引擎如何同时服务多个模型和适配器，以及请求如何在它们之间路由。

离线批处理和 RL rollout 有一个共同的调度问题：一批工作必须在预算内完成，失败要能重试，结果要能对账。区别是 rollout 的“批”是一个 prompt 组，组内共享前缀，输出要带 logprob 和策略版本；第 44 章会展开这些差异。如果你的离线任务其实是“给训练器生成样本”，应该先读第 44 章，再回来看本章的 wave 和检查点设计。

## 练习

1. 一个离线批次有 10 万条请求，每条平均输入 2K token、输出 500 token，QPS 目标不重要，截止时间是 6 小时。估算需要的 GPU 数和 KV 容量；说明哪些假设最敏感。
2. 设计一个分片策略：按文件、按行号、按 token 数还是按租户？写出每种策略的优缺点和失败重跑成本。
3. 解释为什么离线调度可以用比在线更大的 batch，但不能无限大。给出一个反例，说明 batch 过大如何让 makespan 变长。
