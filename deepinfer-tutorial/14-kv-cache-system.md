# 第 14 章 KV cache 系统

本章导读：KV cache 是推理系统里最贵的资源。本章从分页、前缀哈希、copy-on-write 讲到 DeepInfer 的 block KV、SWA state、3FS 存储、TTL 和跨机传输。读完之后，你应该能算出“一条 128K 请求要多少页、能和其他请求共享多少、什么时候该换出”。

## 14.1 三种缓存

DeepInfer 的部署 Q&A 把 KV 分成三类，理解这三类的区别很重要。

**In-flight block KV + state KV**：正在推理的请求在 GPU HBM 里的缓存。block KV 是主注意力和 indexer 的 K/V，按 128 token 的 block 分页；state KV 是 SWA/压缩边界状态，每个序列占一个固定大小的 slot。

**SWA KV cache**：滑动窗口的 K/V，只保留最近 128 个 token。它不进入 paged block，而是放在 state cache 的固定 slot 里；跨请求命中时，如果本机没有，就从 400G VLAN 拉取。

**Paged block KV cache**：主 KV + indexer K，放在专用 3FS 存储集群上。它不是本地主机内存，而是所有 prefill 机器都能访问的共享存储。这样任何 prefill 机器都能命中任何前缀，不必为了缓存亲和性牺牲负载均衡。

这个分层不是随便设计的。把 block KV 放在共享 3FS，解决了“前缀亲和性 vs 负载均衡”的矛盾：如果缓存只在本地，路由器必须把相同前缀的请求送到同一台机器，负载会倾斜；放在共享存储，任何机器都能取，路由可以按负载走。代价是网络和存储延迟，需要用异步预取、GDR swap-in 来掩盖。

三者的生命周期也不同。in-flight KV 随请求结束而释放；SWA state 随序列结束而释放，但可以在请求之间复制；3FS block KV 有 TTL，按 LRU 回收。把它们混在一起管理，容易出现“请求结束了但 3FS 还在写”“SWA 被淘汰但 block KV 还在”之类的状态错位。

## 14.2 分页与 block manager

DeepInfer 的 block size 是 128 token。`BlockManager` 管理固定数量的物理 block，每个 block 有引用计数、哈希、token ids、last_used。分配时从 `ref_count == 0` 的 block 里挑 `last_used` 最小的（本质上是 LRU，而不是维护一个独立的空闲链表）；释放时引用计数减一；引用计数为 0 的 block 可以留在缓存里等待复用，也可以被下一次分配淘汰。mini 的实现就是这个扫描式 LRU，生产实现会用更高效的数据结构，但语义相同。

前缀哈希是链式的：`hash(block_i) = H(hash(block_{i-1}), tokens_i)`。这样两个序列只有在前缀完全相同时才会共享 block，不会出现“后半段相同但前半段不同”的误命中。

前缀匹配从第一个 block 开始，逐个查哈希表；命中就 `share`（引用计数加一），挂到新序列的 block table；遇到第一个 miss 就停止。命中的 token 数一定是 block size 的倍数。为了保证序列还能产生 logits，至少要留一个 token 不命中；DeepInfer 在调度时会让最后一块退回重算。

`PagedKVCache` 在逻辑上是一个 `[num_layers, num_blocks, block_size, n_kv_heads, head_dim]` 的数组：层数在最外层，因为每一层都有自己的 K 和 V。写 KV 时，根据 token 位置算 block index 和 offset；读 KV 时，按 block table 把多个 block 拼成连续序列。真实 kernel 不会真的拼接，而是用页表在 attention 内间接寻址；mini 用 NumPy 拼接，逻辑等价但慢。

容量规划要区分“理论下限”和“可调度容量”。`max_model_len × 每 token 字节` 只是单序列的 KV 下限；decode 还要为下一个 token 预留空间，speculative decoding 还要为 `k` 个 draft 预留，block 分配又有内部碎片。如果 `num_blocks × block_size` 刚好等于 `max_model_len`，普通的 decode 在达到上限时会被 `FINISHED_LENGTH_CAPPED` 正常结束，不会因为“没有下一个 block”被抢占；真正需要额外余量的是三种情况：推测解码一次要验证 `k` 个 draft，需要 `k` 个额外槽位；COW/fork 可能复制整页；state slot、block 内部碎片和分配器余量会占掉一部分容量。安全的做法是让总容量至少覆盖 `max_model_len` 再加一个 block（推测解码再加 `k` 个 token），并在启动时校验这个余量；第 19 章的容量规划会把这个余量算进并发。

用数字算一遍。128K 上下文、block size 128，需要 1024 页。如果前缀命中了 96K，就命中 768 页，只需要再分配 256 页。先算**每层**每页的字节数：`block_size × n_kv_heads × head_dim × 2 × bytes`。对 1 个 KV 头、128 维、FP8，每层每页约 `128 × 1 × 128 × 2 × 1 = 32 KiB`。再乘层数：40 层时一个物理页约 1.25 MiB；1024 页约 1.25 GiB，一条 128K 请求的稠密 FP8 KV 就有这么大，1000 条并发约 1.25 TiB。这个数字说明为什么长上下文必须依赖压缩、稀疏和共享存储：如果直接按稠密 KV 算，单机根本放不下多少并发。

公开资料中 V4.1 的 890 字节/token 是压缩、低精度、SWA 和跨层共享之后的**全局 footprint**，不能和上面的稠密公式直接相加。用 890 字节/token 重算，128K 请求约 111.25 MiB（约 116.7 MB），1000 条约 108.6 GiB（约 116.7 GB），这才是第 6 章和第 4 章使用的口径。注意不要把单条的 MiB 数直接当成 1000 条的 GiB 数：`1000 × 111.25 MiB = 111,250 MiB`，再除以 1024 才是 GiB。两个数字差一个数量级，正是压缩和共享带来的收益；读容量数字时先确认它说的是“稠密 KV”还是“压缩后 footprint”。

## 14.3 Copy-on-write

前缀共享的 block 是只读的。如果两个序列共享一个 block，其中一个要往这个 block 的尾部追加 token，直接写会破坏另一个序列的 KV。解决办法是 copy-on-write：检测到 block 引用计数大于 1 且要被修改时，分配一个新 block，把旧内容复制过去，替换页表，再写新 token。

DeepInfer 的 C++ scheduler 在 fork 序列时会显式克隆 state 和最后一个可能写了一半的 block；`clone_blocks` 列表记录了 `(src, dst)` 对，`clone_and_zero_states_and_blocks_on_default_stream` 在 GPU 上异步复制。mini 的 `PagedKVCache._cow_if_shared` 做同样的事，只是用 NumPy 的切片赋值。

COW 的代价是复制一个 block 的 KV。对 128 token、1 个 KV 头、128 维、FP8、40 层的模型，每层每页 32 KiB，整块约 1.25 MiB；复制一次不算大，但如果大量序列在同一 block 上分叉，会频繁触发，累积带宽很可观。前缀缓存的设计要尽量避免“共享块被频繁追加”，例如只共享完整 block，最后一个不完整的 block 不共享。

COW 还有一个正确性细节：复制的是“整块”，不是“到当前长度”。如果只复制有效 token 的部分，块尾部可能是未初始化数据；后续写入虽然会覆盖，但如果 kernel 读到尾部（例如 mask 写错），就会读到垃圾。mini 的实现复制整块 K/V，牺牲一点带宽换确定性。

## 14.4 State cache 与 SWA

SWA 的 KV 不是按 token 分页，而是每个序列一个固定 slot。DeepInfer 的 `state_manager` 是一个独立的 `BlockManager`，管理 `num_state_seqs` 个 slot；每个 slot 的大小由 `bytes_of_state_per_seqs` 决定。

官方 Q&A 给出的数字是：每序列存入磁盘的 SWA 只有 20 层 × 134 token × 528 B = 1,415,040 B，约 1.35 MiB（约 1.42 MB）。这里的 528 B 是**每层每 token** 的 MXFP8 格式开销；134 = 128 窗口 + 6 个回溯余量。存储位置按 128 token 对齐；decode 时每跨过一个 128 边界，就把当前窗口复制到 replica region；请求结束时从最近一次完整副本取。

这三个数要分清：128 是 attention 窗口，决定 query 能看多远，属于模型语义；134 是落盘 state 的长度，等于窗口加 6 个回溯余量，属于存储策略；第 6 章还会出现 140，那是重放时的 `keep_tokens`，等于 134 再加 6 个边界余量，属于计算策略。把 128 当成“存储量”会低估落盘大小，把 134 当成“窗口”会误判模型能看多远，把 140 当成“窗口”则会在调参时改错对象。

SWA 的命中策略和 block KV 不同。block KV 决定“能复用多少前缀”，SWA 决定“最后一个 block 要不要重算”。如果 block KV 命中 L1，但 `L1-128` 到 `L1` 没有 SWA，就要退回 128 个 token 重放。重放的成本是常数，不随上下文增长。

State cache 的容量规划容易被忽略。假设 20 层、每序列 1.35 MiB、1000 并发，就是 1.35 GiB；这还不包括 replica region 和临时副本。如果 state cache 满了，新的序列无法 prefill，即使 block KV 还有空间。调度器的 `_can_allocate_with_state` 必须同时检查两者，不能只看主 KV。

## 14.5 3FS 存储

DeepInfer 的 KV store 建在 3FS 上。官方给出的标准存储服务器配置是 20 × 30.73 TB SSD，每台至少 40 GB/s 读、5 GB/s 写，容量按 24 小时数据规划；整个集群约 100 PiB，按每 GPU 14.4 TB 逻辑容量规划。这两个数不要直接相除来反推 GPU 数：14.4 TB 是单 GPU 的 KV 预算，100 PiB 是某一层/某一集群的容量，除出来约 7,800 张卡，和 155T/天所需的 18 万到 60 万张卡不是同一个口径。公开报道提到集群峰值读约 10 TiB/s、写约 850 GiB/s，这两个数字是集群口径，不是单节点口径。关于冗余方式，公开资料存在两种口径：3FS 开源实现以 CRAQ 链式复制为主，而部分部署描述提到在 KV store 层使用 10+2 erasure coding。本书不把两者混为一谈；如果你在自己的集群上规划容量，先确认用的是复制还是 EC，因为两者的存储开销和尾延迟完全不同。下面关于 EC 的段落只描述“如果采用 10+2”的代价，不代表 3FS 的唯一实现。

TTL 按业务设置：Agent 流量 3 天，Chatbot 流量 7 天。官方说 3 天 TTL 会让 Chatbot 的缓存命中率损失 0.5% 到 1%，因为 Chatbot 有很重的长尾命中，少量 KV 被反复读取。回收由 3FS 的 GC Worker 做 LRU，不靠应用层过期。

这个设计的关键是“存储与计算解耦”。存储节点可以独立扩容，计算节点故障不会丢缓存；代价是每次命中要跨网络取 KV，需要异步 fetch 和 GDR swap-in 来掩盖延迟。

EC 的代价也要算。10+2 意味着 12 个分片存 10 份数据，存储开销 20%；读的时候要等 10 个响应，尾延迟由最慢的 10 个节点决定。它适合“大容量、可容忍少量节点故障”的场景，不适合“极低延迟、单点读”的场景。这也是为什么 KV store 要用异步预取，而不是同步读。

## 14.6 匹配、取回与换入

一次前缀命中要经过三步：

1. **匹配**：Entrypoint 在 CHECK 角色下查询本地 metadata 索引，对哈希链做前缀匹配，只查 metadata，不取数据；真正的 KV 数据在 3FS。命中长度必须在路由前算出来，所以这一步的延迟无法完全隐藏。
2. **取回**：异步进程把 KV 从 3FS 搬到主机共享内存。这一步和路由、排队可以重叠。
3. **换入**：引擎进程内的线程把共享内存的 KV 搬到 HBM。目标是让 per-layer H2D 和前向计算重叠。官方说 CUDA copy engine 对细粒度 KV block 的拷贝性能不好，所以用 GDR：RDMA NIC 在不占用 SM 的情况下打满 PCIe。

这三步的任何一步变慢，都会让“缓存命中”从收益变成尾延迟。生产系统会用异步、批量、预取和优先级来管理。

匹配阶段只查 metadata，这意味着命中长度可以在请求路由之前算出来；但 metadata 也可能过期（block 被 GC），所以取回阶段还要校验一次。取回和换入要分两级，因为主机内存和 HBM 的带宽/容量不同；把 3FS 直接读到 HBM 会占用宝贵的 PCIe 带宽，也会阻塞正在跑的 forward。

## 14.7 前缀命中的经济学

假设一条 32K prompt 的 prefill 成本是 `C`，命中 90% 后只需算 3.2K，成本降到 `0.1C` 左右（忽略重放和传输）。如果缓存命中率从 50% 提到 80%，非缓存 token 的比例从 50% 降到 20%，prefill 计算量相对原来下降 `(0.5 - 0.2) / 0.5 = 60%`。注意这和“命中率提高 30 个百分点”不是一回事：计算量看的是未命中比例的变化。对长上下文 Agent 负载，这个收益非常可观。

但缓存不是免费的。存储成本、网络带宽、GC、元数据查询、跨机拉取都要钱。一个实用的判断是：如果一条 KV 的平均复用次数大于 `(存储+传输成本)/(重算成本)`，缓存就划算。TTL 的选择也是这个公式：TTL 越长，命中率越高，但存储占用越大。

用 `examples/roofline.py` 的 `ttl_storage_bytes` 可以估算：如果集群每秒新增 5 万 token 的 KV，TTL 3 天，每 token 890 字节，稳态存储约 `50000 × 259200 × 890 ≈ 11.5 TB`。这只是一个简化模型，实际还要叠加副本或 EC 开销，并考虑未命中率；副本和 EC 是两种冗余方案，不是同时相乘。它说明“缓存 3 天”不是一个小数字，必须有容量规划。

## 14.8 mini-deepinfer 的实现

mini 的 `BlockManager` 和 `PagedKVCache` 实现了：

- 固定 block size、引用计数、LRU 淘汰；
- 链式哈希、前缀匹配、share；
- COW；
- `KVBlockStore`：本地目录、content-addressed 风格的 key、TTL、LRU、hit/miss 统计；
- `export_sequence_kv` / `import_sequence_kv`：PD 交接。

它没有实现 3FS、GDR、跨机目录、SWA state 的固定 slot，但接口和思路是对应的。运行 `python examples/kv_store.py` 可以看到 TTL 和 LRU；`tests/test_block_manager.py` 覆盖了前缀匹配、COW 和淘汰。

mini 的 `KVBlockStore` 用 `.npy` 文件存 block，key 是 `hash-layer`。它采用 content-addressed 风格的接口，但 key 实际由调用方拼接，所以不是完整的 content-addressed 实现。TTL、LRU、容量淘汰的行为和 3FS 的 GC 类似，你可以把它当成“单机版 KV store”来理解接口。

## 14.9 常见错误

**把前缀缓存当成“永不失效”。** 缓存是优化，block 可以被淘汰；命中率下降只影响性能，不影响正确性。实现要保证 miss 时能重算。

**共享了不完整的 block。** 只应共享完整 block；最后一块如果共享，追加时会 COW，增加复制成本。

**抢占时重新 pin 前缀。** 这样显存没有真正释放，调度器会空转。正确做法是先释放，下次 prefill 再匹配。

**忽略 SWA 的一致性。** block KV 命中不代表 SWA 命中；SWA 缺失时要退回重放，否则 decode 的窗口不完整。

**把 KV 当成“只读缓存”。** decode 会不断追加新 token，写入路径必须处理 COW、页表扩展和并发；只读缓存的设计不能直接套用。

**忽略租户隔离。** 如果不同租户共享前缀哈希和 block，可能通过缓存命中时间或内容推断出对方的数据。第 28 章会讨论隔离方案。

## 14.10 KV 分层预算算例

把本章的数字放进一个完整的预算，可以看到“KV 是一级存储系统”到底意味着什么。

假设一个 Agent 服务每秒新增 5 万 token 的 KV，TTL 3 天，每 token 890 字节。稳态存储是 `50,000 × 259,200 × 890 ≈ 11.5 TB`。如果采用 10+2 EC 的 20% 开销，物理占用约 13.8 TB；如果采用两副本，约 23 TB。两种方案选一种，不能把 1.2 和 2 同时乘上去。这个数字还没有算 metadata、索引和未命中重算的临时 KV。

如果 TTL 改成 7 天，裸容量约 `11.5 × 7/3 ≈ 26.9 TB`；按 10+2 EC 约 32.3 TB，按两副本约 53.8 TB。这里不是简单翻倍，因为 3 天到 7 天是 2.33 倍。公开资料说 3 天 TTL 会让 Chatbot 的缓存命中率损失 0.5% 到 1%，7 天 TTL 用更多存储换更高命中率；这个取舍必须用真实流量分布算，不能拍脑袋。

再看带宽。如果每个请求平均 77K token（这里按 77,000 计；第 16.2 节用 77×1024=78,848，两个口径会让结果差约 2.4%），命中 96%，每次命中需要从 3FS 取约 74K token 的 KV，即约 66 MB。按 10 万 QPS 的命中请求算，读取带宽是 `100,000 × 66 MB ≈ 6.6 TB/s`，约合 6.0 TiB/s，是公开 10 TiB/s 峰值的 60% 左右。这个比例已经很高：生产系统不能按“峰值还有 40% 余量”来规划，因为峰值是集群口径，单次请求还要和写入、GC、其他租户竞争。它说明 KV 存储的瓶颈不只是容量，还有网络和 SSD 带宽；缓存命中率越高，读带宽压力越大。

最后看本地 state。SWA 每序列约 1.35 MiB，1000 并发约 1.35 GiB；公开资料说本地 SWA 缓存约 180 秒、命中率超过 98%。它比主 KV 小，但生命周期短、访问频繁，适合放在本地内存而不是 3FS。把 SWA 也放到共享存储，会增加延迟和带宽，通常不划算。

这个算例的结论是：KV 预算要同时算容量、带宽、延迟和生命周期。只算“每 token 多少字节”会低估系统复杂度；只算“3FS 有多大”会忽略网络和 GC。一个成熟的容量规划会把这些项分开，并给每一项留冗余。

## 14.11 淘汰策略的比较

KV 缓存的淘汰策略决定了“同样的容量能换来多少命中率”。常见的策略有五种。

**LRU（Least Recently Used）**：淘汰最久未使用的条目。实现简单，对“最近用过的前缀还会再用”的负载有效；缺点是扫描式负载会把有用条目冲掉，长共享前缀也可能因为一次冷请求被淘汰。

**LFU（Least Frequently Used）**：淘汰访问次数最少的条目。适合热点前缀稳定的负载；缺点是历史计数会“固化”，新出现的常用前缀很难积累到足够次数。通常要用 aging 或 windowed LFU 缓解。

**TTL**：按时间过期。适合“前缀有时间局部性”的负载，例如同一个会话在几小时内反复使用；TTL 太长会占存储，太短会降低命中率。DeepInfer 的 Agent 3 天、Chatbot 7 天就是按业务局部性定的。

**成本感知淘汰**：优先淘汰“重新计算便宜”的条目。例如短前缀、低层 KV、容易重放的前缀可以优先淘汰；长前缀、decoder 全局 KV、重放代价高的条目保留更久。这需要给每个条目估算 `recompute_cost`，并按“单位容量节省的重算成本”排序。

**租户/优先级感知**：高优先级租户或高价值请求的 KV 保留更久；低优先级租户的缓存可以被淘汰。这能保证关键业务的命中率，但会增加实现复杂度和公平性争议。

没有一种策略在所有负载上都最好。LRU 是默认值，TTL 是业务局部性的表达，成本感知是推理系统特有的优化。评估淘汰策略时，不能只看命中率，还要看“命中带来的 prefill 节省”和“淘汰/取回的带宽成本”。一个命中率更高但每次命中都要跨机取回的策略，可能比命中率低但本地命中的策略更慢。

## 14.12 COW 放大：分叉率、block 大小与带宽

COW 的成本不是“复制一个 block”这么简单，它会被分叉率和 block 大小放大。设每秒发生 `f` 次分叉，每次分叉要复制 `c` 个共享 block，每个 block 的 KV 字节是 `B_block`，则：

```text
COW 带宽 = f × c × B_block
```

用第 14.2 节的数字：128 token、1 个 KV 头、128 维、FP8、40 层，一个 block 约 1.25 MiB。如果每秒 100 次分叉、每次复制 1 个 block，带宽是 125 MiB/s，约 0.13 GB/s；相对 3 TB/s 的 HBM 带宽可以忽略。如果每秒 10,000 次分叉、每次复制 4 个 block，带宽是 50 GB/s，约占 HBM 的 1.7%；仍然不大，但它会和 attention 的 KV 读取、权重读取抢带宽，在 decode 的几毫秒里可能造成抖动。

真正危险的不是平均带宽，而是**同步点**。COW 通常发生在写入路径上，如果实现是“复制完再写”，这次写就要等整块复制完成；一个 1.25 MiB 的复制在 3 TB/s 下约 0.4 微秒，看起来很小，但如果 kernel 没有把它和后续计算重叠，或者复制触发了分配器的锁，尾延迟会被放大。生产实现会把 COW 放在独立的 stream 上，用 event 和写入同步，而不是在 host 上阻塞等待。

block 大小的选择也在放大这个成本。block 从 128 token 降到 16 token，单块复制量变成 1/8，但页表项数量变成 8 倍，间接寻址和元数据开销上升；从 128 升到 256，单块复制量翻倍，但共享的粒度更粗，尾块浪费更多。没有一个对所有负载都最优的值；DeepInfer 固定 128，是因为它和 SWA 窗口、kernel 对齐、TMA 访问匹配，不是因为 128 在所有模型上都最好。

还有一个常被忽略的放大源：**共享不完整的尾块**。如果前缀缓存把最后一个半满 block 也共享出去，任何追加都会触发 COW，而复制的是整块 128 个槽位，实际只新增几个 token。解决办法是只注册完整 block，让尾块保持私有；mini 的 `register_prefix_blocks` 就是这么做的。这个策略会让命中长度少一个 block，但避免了高频 COW，净收益通常为正。

评估 COW 时，不要只看“复制了多少字节”，还要看“复制发生在哪个关键路径上”。一个在后台 GC 里复制 1 GB 的实现，可能比一个在 decode 写入路径上复制 1 MB 的实现更不影响 SLO。第 22 章会在 mini 里用引用计数和页表复现这两种路径。

## 小结

KV cache 系统是“分页 + 前缀哈希 + COW + state cache + 共享存储 + 传输”的组合。DeepInfer 把 block KV 放到 3FS，把 SWA 放在本地 state slot，用 TTL 和 LRU 管理生命周期，用异步 fetch 和 GDR 掩盖传输。mini-deepinfer 用 NumPy 实现了分页、前缀匹配、COW 和 block store，足以验证这些机制的逻辑。
