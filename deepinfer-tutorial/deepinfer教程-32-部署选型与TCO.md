# 第 32 章 部署选型与 TCO

本章导读：把第 30 章的单位经济和第 15 章的并行设计落到部署上。本章讨论硬件选型、集群拓扑、P/D 配比、存储与网络、云 vs 自建、TCO 模型、容量规划和合规检查。最后给出一张可以直接改的部署清单和一个可复算的案例。

## 32.1 硬件选型

DeepInfer 官方支持 NVIDIA SM100 和华为 Ascend 950。选型时要看：

- **显存**：能否放下模型分片 + KV cache + 激活。V4.1 的 552B 参数即使 FP4 也需要大量显存，必须 EP/多卡。
- **互联**：NVLink 域的大小决定 EP/TP 能开多大；跨机 RDMA 的带宽决定 PD 分离和 all-to-all 的成本。
- **算力/带宽比**：decode 受带宽限制，HBM 带宽比峰值 FLOPS 更重要；prefill 受算力限制，Tensor Core/矩阵单元更重要。
- **低精度支持**：FP8/FP4、MXFP4、TMA、异步拷贝。不同代的 GPU 对这些的支持不同。
- **供应与价格**：SM100 供应紧张，Ascend 950 在国内有政策/供应优势；云上按需 vs 自建要看利用率。供应链要把 lead time、整机价格、备件比例、出口管制和替代型号一起算：一张卡的交付延迟可能让整个 EP 组无法上线，备件不足会让单卡故障变成长期容量损失。采购时至少问清交付周期、最小起订量、维保年限、故障换新时间和是否有同代替代型号。
- **软件生态**：CUDA 13/CANN 9.2、驱动、编译器、kernel 库的成熟度。

不要只看峰值 FLOPS。一个带宽不足的 GPU 在 decode 上可能不如上一代；一个互联不足的集群在 Wide-EP 上会被 all-to-all 拖死。

选型时还要看“整机”而不是“单卡”。CPU、内存、NVLink switch、网卡、SSD 的配置会影响实际吞吐；一台“8 卡但只有 1 张网卡”的机器，在 PD 分离或 KV 传输时会成为瓶颈。

## 32.2 集群拓扑

DeepInfer 的推荐形态是：

- **Prefill**：普通 8 卡机器，EP2 到 EP8 / DP2 到 DP8；最小 1P 可部署。
- **Decode**：64 到 128 卡的 supernode，EP64 到 EP128；Wide-EP。
- **VE**：单卡实例，便宜 GPU。
- **KV 存储**：专用 3FS 集群，20 × 30.73 TB SSD/节点，40 GB/s 读、5 GB/s 写。
- **网络**：每 8 GPU 约 400 Gbps 跨数据中心互联；同域 NVLink。

P/D 的比例：官方说实践中 P 和 D 的 GPU 比例大约 1:1，但推荐 decode EP64 以上，所以最小高效单元是 64 卡 P + 64 卡 D。这个比例取决于 prompt/output 长度比、缓存命中率和 SLO；长 prompt 短输出需要更多 P，短 prompt 长输出需要更多 D。

拓扑设计要避免“跨域 all-to-all”。EP 的 all-to-all 应该尽量在 NVLink/supernode 内；如果跨机，延迟会吃掉收益。PD 的 KV 传输可以跨机，但要尽量在相邻机架/数据中心，并用 RDMA 和异步预取。

## 32.3 云 vs 自建

**云**：

- 优点：弹性、按需、无 capex、快速启动、全球区域。
- 缺点：单价高、GPU 供应不稳定、网络/存储可能受限、数据出云成本。
- 适合：流量波动大、初期验证、短期项目、没有机房团队。

**自建**：

- 优点：单位成本低（高利用率时）、可控、可定制网络/存储、数据驻留。
- 缺点：capex 高、采购周期长、运维复杂、利用率低时浪费。
- 适合：稳定大流量、长期、有基础设施团队、合规要求。

**混合**：基线自建 + 峰值云 burst；KV 缓存放在自建存储，云上实例按需拉取。这需要统一的调度和镜像。

一个简单的判断：如果 GPU 年利用率低于 40%，云通常更便宜；高于 60%，自建可能更划算；40% 到 60% 之间要看电价、机房和运维成本。这个阈值可以用盈亏平衡公式算，而不是拍脑袋：

```text
u* = (自建 3 年 TCO / 3) / (GPU 数 × 8760 × 云上每 GPU 小时价格)
```

当实际利用率 `u > u*` 时，自建更便宜；`u < u*` 时，云更便宜。用 32.4 的 8 卡、82.0 万美元/3 年算例：每年摊销约 27.3 万美元；云价 2 美元/小时时 `u* ≈ 1.95`，自建永远不划算；云价 4 美元/小时时 `u* ≈ 0.98`；云价 6 美元/小时时 `u* ≈ 0.65`。所以“40% 到 60%”的自建门槛对应云价约 6.5 到 9.8 美元/小时的区间，而不是 5 到 6 美元。云价越低，自建的门槛越高。这个阈值不是绝对的，预留实例、竞价实例和出网费会改变结论。

## 32.4 TCO 模型

总拥有成本（3 年）：

```text
TCO = GPU 采购 + 服务器/CPU/内存 + 网络 + 存储
    + 电力 × 3 年 + 机房/冷却 + 运维人力 + 软件/支持
    + 备件/故障 + 迁移/培训
```

按每有效 GPU 小时摊：

```text
cost_per_effective_gpu_hour = TCO / (GPU 数 × 3 年 × 8760 × 利用率)
```

举例：一张 GPU 3 万美元（8 张共 24 万），服务器/CPU/内存 12 万，网络/存储 10 万；电力按 1.5 kW/GPU、0.10 美元/kWh、3 年计算，是 `1.5 × 8 × 3 × 8760 × 0.10 ≈ 3.15 万美元`；机房托管按 1200 美元/GPU/年，是 `1200 × 8 × 3 = 2.88 万美元`；运维 10 万美元/年，3 年 30 万美元。总 TCO 约 82.0 万美元/8 卡，即 10.25 万美元/卡/3 年。按 70% 利用率，名义成本约 `820000 / (8 × 3 × 8760) ≈ 3.90 美元/GPU 小时`，每有效 GPU 小时约 `3.90 / 0.7 ≈ 5.57 美元`。这和 `examples/tco.py` 的输出一致；如果只报 65 万美元，通常是漏算了 3 年运维中的一部分（82 万减去 30 万运维约为 52 万，65 万对应的是只省掉部分运维或把电力/机房按更低口径估算），或者把电价、利用率按更乐观的假设算。把电力按 7 kW/GPU 估算会得到更高的 TCO，而不是更低；两种口径不能混用。

这个模型可以改成表格，把每个假设写清楚。TCO 的准确性取决于假设，尤其是利用率、电价、故障率和人力。

TCO 还要算“闲置成本”。如果为了峰值买了机器，低峰闲置，实际利用率可能只有 30%；这时的每有效 GPU 小时成本是 70% 利用率的两倍多。混合云/竞价实例可以把闲置成本转嫁给云，但会牺牲稳定性和数据驻留。

## 32.5 容量规划

容量规划的步骤：

1. 采集流量：QPS、prompt/output 长度分布、并发、峰谷比。
2. 估算每请求的 prefill/decode token 和 KV 字节。
3. 用 benchmark 得到单 GPU/单实例的吞吐-延迟曲线。
4. 按 SLO 选工作点（batch、EP、P/D 配比）。
5. 计算所需 GPU 数，加 20% 到 30% 冗余。
6. 计算 KV 存储和网络带宽。
7. 用压测验证，留出扩容时间。
8. 每季度复盘，按流量变化调整。

对长上下文 Agent，KV 存储和网络可能是瓶颈；对短聊天，decode batch 和 TPOT 更关键；对多模态，VE 的 GPU 和图像传输要单独算。

容量规划要区分“在线”和“离线”。离线批处理可以容忍更高延迟、更大 batch，单位成本更低；在线服务要守 SLO，不能把两者混在一个池里。混部可以用优先级和抢占，但会增加尾延迟风险。

## 32.6 合规与数据

部署选型还要考虑：

- **数据驻留**：prompt/KV 是否可以出境？KV 缓存里可能包含用户数据。
- **日志**：是否记录 prompt？保留多久？是否脱敏？
- **模型许可**：DeepSeek-V4.1-Flash 的许可、商业使用条款。
- **出口管制**：GPU/加速器的采购和出口限制。
- **审计**：谁在什么时候调用了什么模型，是否有审计日志。
- **多租户隔离**：KV 缓存是否可能串租户？前缀哈希是否泄露信息？

这些问题会影响架构：例如，如果 KV 不能跨地域，就不能做全球共享缓存；如果日志不能存 prompt，就要在网关脱敏。第 28 章已经展开安全控制。

## 32.7 部署清单

上线前逐项确认：

- [ ] 模型版本、tokenizer、chat template、grammar 版本绑定。
- [ ] 硬件型号、驱动、CUDA/CANN 版本匹配。
- [ ] 单机/多机 benchmark 达到 SLO。
- [ ] P/D 配比、EP 规模、batch 上限经过压测。
- [ ] KV 存储容量、TTL、GC、故障恢复验证。
- [ ] 网络带宽、延迟、丢包在峰值下可接受。
- [ ] 自动扩缩容、grace period、故障转移演练。
- [ ] 指标、日志、trace、告警接入。
- [ ] 鉴权、限流、输入长度限制、schema 复杂度限制。
- [ ] 数据驻留、日志脱敏、审计合规。
- [ ] 回滚方案、模型热切换、容量应急预案。

这张清单比任何 benchmark 都重要。一个性能很好但故障转移没演练过的服务，上线后可能一次机房抖动就全挂。

## 32.8 一个部署案例

假设你要服务一个 128K 上下文的 Agent 产品，QPS 20，平均输入 32K、输出 2K，SLO 是 P95 TTFT < 2s、P99 TPOT < 80ms，缓存命中率 60%。

1. 每请求 prefill 非缓存 token 约 12.8K，decode 2K。
2. 用 benchmark 得到单 P 实例（8 卡）在 12.8K prefill 下的 TTFT 和吞吐。
3. 用 decode 曲线得到单 D 实例（64 卡）在并发下的 TPOT。
4. 用 Little 定律估算并发：20 QPS × 平均停留 30s ≈ 600 并发。这里 30 秒对应平均 TPOT 约 15ms（`30s / 2000 token`），P99 TPOT < 80ms 是尾延迟上限，不是平均值；如果把 80ms 当成平均值，停留时间会变成约 160 秒，并发和 KV 都会高估约 5 倍。
5. 计算 KV：600 × 32,768 × 890 B ≈ 17.5 GB（约 16.3 GiB，仅主 KV，实际还要算输出 token、SWA/index 和副本）。
6. 按 20% 冗余和 60% 缓存命中，选 P/D 数量和存储容量。
7. 压测验证 P95/P99，调整 batch 和 P/D 比例。

这个案例的数字是示意，实际要用你的模型和硬件重算。注意第 5 步只算了主 KV；如果加上 SWA state、indexer、副本和 EC，实际容量可能是 2 到 3 倍。

## 32.9 模型更新与热切换

生产系统会频繁更新模型。热切换要考虑：

- 新旧版本的 tokenizer/chat template 是否兼容；
- KV 格式是否兼容，旧请求能否在新实例上继续；
- 权重加载是否需要停机，能否双缓冲；
- 路由能否按租户/流量灰度；
- 回滚是否能在分钟级完成。

一个安全的做法是“双版本并存”：新版本先接小流量，旧版本继续服务；等新版本稳定后，再逐步迁移。KV 不跨版本共享，避免格式/语义不兼容。

## 32.10 成本优化的顺序

部署后的成本优化，建议按下面的顺序：

1. **利用率**：先看 GPU 是否空转，batch 是否太小，缓存命中是否低。
2. **精度**：FP8/FP4 是否开启，kernel 是否融合。
3. **并行**：EP/DP/P-D 比例是否匹配负载。
4. **存储**：KV TTL、EC、副本是否合理。
5. **采购**：云/自建、预留/竞价、电价。
6. **架构**：PD 分离、多区域、专用芯片。

不要一上来就换硬件。大多数成本问题来自利用率和缓存，而不是硬件不够快。部署之后的下一层问题是流量：同样的 GPU 数，排队膝点、路由策略、重试预算和故障域会决定实际 goodput。第 46 章给出了这些模型；第 47 章则把 TCO 和现金流、NPV、LTV/CAC 接起来，回答“这笔部署投资多久回本”。

## 32.11 P/D 配比算例

P/D 配比不是固定的 1:1，它取决于 prompt/output 长度比、缓存命中率和每卡吞吐。

假设一个服务每秒需要处理 12 万非缓存 prefill token 和 4 万输出 token。公开 benchmark 给出的每卡吞吐是 prefill 约 6 万非缓存 token/s、decode 约 14,000 输出 token/s（在线口径）。不考虑冗余时：

```text
P = 120,000 / 60,000 = 2
D = 40,000 / 14,000 ≈ 2.86
P:D ≈ 1:1.43
```

如果加 20% 冗余，P 约 2.4 卡，D 约 3.4 卡，按 8 卡节点取整就是 8 卡 P + 8 卡 D；如果要满足“最小高效单元 64+64”，则要按 64 的倍数部署。这个算例说明：长 prompt、短输出的负载需要更多 P；短 prompt、长输出的负载需要更多 D；缓存命中率越高，P 的需求越低。

但实际配比还要看三个修正项。第一，**缓存命中率**：96% 命中意味着 P 只需要处理 4% 的输入 token，P 的需求会大幅下降；如果命中率只有 50%，P 的需求翻倍。第二，**SLO**：TTFT 卡得紧，P 要留更多冗余；TPOT 卡得紧，D 要留更多冗余。第三，**故障域**：EP64 的 D 实例一张卡故障可能让整组不可用，需要额外副本或 EP size 重定。

`economics.py` 的 `p_d_gpu_split` 可以复算这个例子。把 prefill/decode 每卡吞吐换成你实测的数字，把 headroom 换成你的冗余策略，就能得到自己的配比。不要直接套用公开的 1:1 或 64+64；那是 DeepSeek 的负载和硬件下的结果，不是通用常数。

## 小结

部署选型是性能、成本、合规和运维的综合。硬件要看显存、互联、带宽和低精度支持；拓扑要按 P/D/VE 分离设计；云 vs 自建取决于利用率和团队；TCO 要算 3 年全成本；容量规划要用流量、benchmark、Little 定律和冗余；合规会影响 KV 和日志架构。上线前用清单逐项确认，比事后救火便宜。
