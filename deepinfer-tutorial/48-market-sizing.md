# 第 48 章 商业分析：市场测算与进入策略

本章导读：前几章已经算过单位成本、TCO、产品定价和现金流，但那些模型都默认“有人会买”。本章补上更前面的一步：市场到底有多大，哪些客户是真正可服务的，凭什么从竞争对手或“自己搭”手里赢过来，以及一个销售团队要多久才能把收入计划变成现金流。读完本章，你应该能把“这个市场很大”拆成可代入的客户数、用量、单价和转化率，并判断一个进入计划是激进、保守，还是根本算不通。

## 48.1 为什么市场测算容易错

推理市场的测算有三个高频错误，它们都不是算术错误，而是口径错误。

第一，**把 token 总量当成收入**。公开报道喜欢说“某模型每天处理多少万亿 token”，这个数字描述的是算力消耗，不是市场规模。token 要乘以单价才是收入，而单价又分成输入、输出、缓存命中、批处理、专属实例等不同档位。用总 token 乘一个平均单价，会把长上下文、低价格、高缓存命中的流量算成高收入，误差可能有一个数量级。

第二，**把 TAM 当成第一年的收入**。TAM 是“如果所有潜在客户都用你的产品、并且按你的价格付费”的收入池，不是“你今年能拿到的订单”。从 TAM 到 SOM 要经过“产品能服务”“客户愿意买”“你能触达”“你能交付”四道漏斗，每一道都会砍掉大部分。

第三，**用自上而下的报告数代替自下而上的账**。行业报告给出的是“某年某市场多少亿美元”，它通常包含硬件、软件、服务、不同地区和不同定义。把它直接当成自己的 TAM，既无法验证，也无法指导“先打哪个客户”。更可靠的做法是从客户数、单客户用量、单价开始，自下而上加总，再用报告数做交叉校验。

本章用 `mini_deepinfer/market.py` 里的纯函数把这些口径写成可执行代码。它们不预测未来，只保证“假设变了，结果怎么变”是可复算的。

## 48.2 自下而上：TAM、SAM、SOM

先定义三个数。**TAM**（Total Addressable Market）是所有潜在客户按你的价格付费形成的收入池；**SAM**（Serviceable Addressable Market）是你的产品、区域、语言、合规和渠道真正能覆盖的那一部分；**SOM**（Serviceable Obtainable Market）是在一定时间内，考虑竞争和执行能力后你能拿到的份额。

自下而上的 TAM 可以写成：

```text
TAM = Σ_segment 客户数 × 每客户年用量 × 单价
```

`mini_deepinfer/market.py` 的 `Segment` 把这三个字段显式化：`accounts` 是客户数，`annual_tokens` 是每客户每年消耗的 token（不是百万），`price_per_mtok` 是每百万 token 的实现价格。`tam_bottom_up` 对每个 segment 做 `accounts × annual_tokens / 1e6 × price`，再加总。单位写在字段名和除法里，是为了避免“百万 token 乘百万客户”这类错误。

用一个示意例子：企业客户 20,000 家，每家每年 100 亿 token，价格 0.5 美元/百万 token；自助客户 200,000 个，每个每年 2 亿 token，价格 0.3 美元/百万 token。企业段是 `20,000 × 10,000 × 0.5 = 100,000,000` 美元，自助段是 `200,000 × 200 × 0.3 = 12,000,000` 美元，TAM 是 1.12 亿美元。这个数字是“收入池”，不是“利润池”，也不是“今年能卖到的收入”。

SAM 用 `serviceable_market(tam, share)` 计算。假设产品只覆盖中文企业市场、只支持文本和文档、只做公有云，服务份额取 30%，SAM 是 3,360 万美元。这个 30% 不是“市场份额”，而是“产品能力覆盖的比例”；它应该由产品功能、区域、合规和渠道逐项估出来，而不是拍一个“我们能做到前三”的目标。

SOM 用 `obtainable_market(sam, target_share, year, ramp_years)` 计算。假设三年后目标份额 10%，线性爬坡三年，第三年的 SOM 是 336 万美元。线性爬坡是一个刻意的简化：它强迫你写出“哪一年达到目标份额”，而不是假设第一天就拿到 10%。如果把 `ramp_years` 改成 5，第三年只能拿到 60% 的目标份额，SOM 降到约 202 万美元。同一个目标，爬坡速度不同，第一年的收入计划会差很多。

## 48.3 计量单位：token、任务、席位、结果

推理服务的计价单位不止一种。选错单位，市场测算会和成本模型对不上。

**按 token**：最接近成本结构，输入和输出分开，缓存命中可以单独定价。它适合 API 和平台型产品，客户能理解“用多少付多少”。缺点是客户很难预估账单，长上下文和 Agent 负载的 token 数波动很大。

**按任务**：一次 Agent 任务、一份文档摘要、一次代码审查算一个单位。它适合结果明确、流程固定的场景，客户不需要理解 token。缺点是任务内部的 token 数差异很大，定价要覆盖长尾，否则复杂任务会亏。

**按席位**：每个用户每月固定价格。它适合 C 端和知识工作者工具，收入可预测。缺点是重度用户的成本可能远超单价，需要限流、分层或 fair use 条款。

**按结果**：按解决的工单数、通过的审核数、节省的人力付费。它最接近客户价值，但需要可验证的结果定义和归因机制，销售和交付成本也更高。

这四种单位可以组合。一个常见结构是“平台订阅（席位）+ 用量包（token）+ 超额按任务计价”。组合的关键是让每一层对应一种成本：席位覆盖固定的人力和支持，token 覆盖 GPU 和 KV，任务覆盖峰值和长尾。不要用席位价覆盖无限 token，也不要用 token 价承诺无限支持。

单位之间还要能换算。一个 Agent 任务平均 8 轮、每轮 20K 输入 token、2K 输出 token、缓存命中 70%，那么它的有效 token 成本不是 `8 × 22K`，而是 `8 × (20K × 0.3 + 2K)` 的加权。市场测算如果按“任务数 × 单价”算收入，成本模型却按“总 token × 单位成本”算，两边必须用同一套轮数、长度和命中率假设，否则毛利会凭空多出来。

## 48.4 客户分层与待办任务

“客户”不是一个同质群体。推理服务的客户至少可以按四个约束分层：延迟敏感度、合规要求、集成复杂度、成本敏感度。每一层对应不同的产品形态和销售方式。

**延迟敏感、低合规**：代码补全、实时问答、游戏 NPC。要求几百毫秒首 token，接受公有云，按 token 或席位付费。产品重点是 TTFT、TPOT 和便宜的小模型。

**延迟敏感、高合规**：金融风控、医疗问答、政务热线。要求数据不出域、审计、私有化或专属实例。产品重点是隔离、日志、SLA 和合规证据，单价高但销售周期长。

**延迟不敏感、高集成**：离线批处理、文档处理、合成数据。要求吞吐和成本，能接受几小时甚至一天的周转。产品重点是大 batch、抢占式实例和结果对账。

**延迟不敏感、高价值**：科研推理、法律检索、复杂 Agent。愿意为准确率付费，但任务时长和 token 消耗都高。产品重点是长上下文、工具调用、可恢复执行和思考预算。

分层之后要问“客户雇这个产品来完成什么任务”（jobs to be done）。客服团队买的不是“每百万 token 0.5 美元”，而是“每个工单少花 3 分钟”；代码团队买的不是“230 token/s”，而是“补全不打断思路”；企业 IT 买的不是“支持 1M 上下文”，而是“文档不用切碎也能答对”。任务定义决定了评测指标、定价锚点和销售话术。如果产品团队只会说“我们便宜 20%”，那这个市场迟早会被更便宜的下一个模型商品化。

还要区分三种角色：使用者（写 prompt 的工程师、客服）、购买者（采购、法务、IT）、预算拥有者（CFO、业务负责人）。三者的关切口不同：使用者关心延迟和易用，购买者关心合规和集成，预算拥有者关心总成本和 ROI。一个 POC 只说服使用者，通常走不到签约；一个方案只讲 ROI，通常过不了安全评审。

## 48.5 采用曲线与渗透率

市场不会在第一年全部采用。`adoption_curve(month, ceiling, rate, midpoint)` 用 logistic 曲线描述“慢启动、快扩散、饱和”的形状：

```text
adopted(t) = ceiling / (1 + exp(-rate × (t - midpoint)))
```

`ceiling` 是可采用的总量，`midpoint` 是达到一半 ceiling 的时间，`rate` 是扩散速度。这个曲线的价值不是预测，而是逼你回答三个问题：上限是多少、拐点在哪、爬坡多陡。把 `midpoint` 从 12 个月推到 24 个月，第一年的收入会差一倍以上；把 `ceiling` 从 SAM 的 30% 降到 10%，长期收入会差三倍。

推理产品的采用还有三个额外约束。第一，**集成周期**。企业客户从 POC 到生产通常要 3 到 9 个月，涉及安全评审、数据接入、提示词调优和灰度。SOM 的 ramp 不能按“签约即满量”算。第二，**预算周期**。企业预算按年度批，错过窗口就要等下一年；这会制造季节性的签单高峰和交付高峰。第三，**信任积累**。推理输出有不确定性，客户需要时间观察错误率、延迟和成本；一个模型版本升级可能让信任归零，采用曲线会出现回退。

渗透率还有上限。即使产品免费，也只有一部分客户有技术能力集成、有数据可用、有场景愿意承担模型风险。把 SAM 的 100% 当成可渗透上限，是最常见的乐观假设。一个实用的做法是给每个分层设“可渗透比例”，再用采用曲线分配时间；两者相乘才是可达到的客户数。

## 48.6 竞争、替代与自建

推理市场的竞争者不只是其他推理 API。客户的选择至少包括五类：托管 API、专属实例、自建开源引擎、云厂商的模型服务、以及“不做”。最后一项经常被忽略：如果任务不够痛、ROI 不明显，客户会选择继续用人工或旧系统。

**托管 API** 的优势是零运维、弹性、按量付费；劣势是数据出域、单价随规模下降空间有限、模型和参数受供应商限制。**专属实例**解决隔离和容量确定性，但客户要承担闲置成本。**自建**用 vLLM、SGLang 或 DeepInfer 这类引擎，单位成本可能更低，但需要 GPU 采购、集群运维、模型接入和 on-call；只有规模足够大、利用率足够高时才划算。**云厂商服务**有渠道和区域优势，但可能有锁定和加价。**不做**则意味着市场教育成本高，销售周期长。

竞争分析要回答三个问题。第一，客户现在的替代方案是什么，切换成本有多高？第二，你的差异化能持续多久：是模型能力、成本、延迟、合规、工具生态，还是渠道？第三，如果对手降价 30%，你的单位经济还能不能活？如果答案是否定的，说明你的优势是价格，而价格通常不是护城河。

自建 vs 托管的临界点可以用第 32 章的 TCO 和第 47 章的盈亏平衡利用率算，但不能给一个固定的“50% 到 60%”。用 32.4 的 8 卡、82 万美元/3 年算例，云价 6.5 到 9.8 美元/小时时，盈亏平衡利用率才落在 50% 到 60%；云价 4 美元/小时时门槛约 98%，云价 2 美元/小时时约 195%，自建永远不划算。所以报价前先算 `u* = (自建 3 年 TCO / 3) / (GPU 数 × 8760 × 云上每 GPU 小时价格)`，再把客户的实际利用率（按峰值和增长算，不是当前平均值）代进去。很多团队按当前用量算出自建更便宜，扩容后发现利用率只有 20%，成本反而更高。

## 48.7 GTM 模式与漏斗

进入市场的模式主要有四种，选择取决于客单价、部署复杂度和合规门槛。

**产品驱动增长（PLG）**：自助注册、免费额度、按量付费。适合低客单价、低集成复杂度、开发者主导的场景。关键是激活率和留存，而不是注册数。一个开发者注册后 7 天内没有发出第一个成功请求，通常就不会再回来。

**销售驱动**：售前、POC、合同、交付。适合高客单价、高合规、长周期的企业客户。关键是销售产能、POC 转化率和回款周期。一个企业订单的销售成本可能是几万到几十万美元，不能用 PLG 的 CAC 去套。

**渠道/云市场**：通过云厂商、系统集成商、GPU 厂商卖。适合需要区域覆盖、合规背书或硬件捆绑的场景。关键是分成比例、渠道冲突和交付责任。

**开源 + 商业支持**：开源核心，卖托管、支持、企业插件。适合建立生态和开发者信任。关键是开源边界、许可和社区治理，不能把“开源”当成“免费试用”。

漏斗可以写成一串转化率：

```text
线索 -> 合格线索（MQL/SQL）-> POC -> 生产上线 -> 扩容
```

`funnel_conversion` 把每一级的转化率相乘。10 万访客、20% 注册、30% 激活、25% 付费，最终是 1,500 个付费客户，复合转化率 1.5%。这个数字看起来低，但对自助产品是正常的；企业销售的漏斗不是按访客算，而是按目标客户名单、触达、会议、POC、合同算，每一级的周期以周或月计。

漏斗的每一级都要有定义和负责人。MQL 是“有预算、有场景、有决策权”还是“下载了白皮书”？POC 的成功标准是“能跑通”还是“在真实流量下达到 SLO”？定义不清，销售和产品会为“线索质量”吵架，数据也无法指导投入。一个实用的做法是给每一级写三个字段：进入条件、退出条件、平均停留时间。这样既能看到转化率，也能看到瓶颈在销售、产品还是交付。

## 48.8 定价、包装与折扣治理

定价不是“成本加毛利”一个公式。推理服务通常要同时处理四个维度：用量、承诺、缓存、交付形态。

**包装**可以做成三档：入门版按 token、无承诺；专业版有月度承诺和折扣；企业版有专属实例、SLA、私有化和合规支持。三档的区别不只是价格，还包括并发上限、上下文长度、支持响应和数据驻留。客户按自己的约束选档，而不是按“哪个便宜”选。

**承诺折扣**用第 47 章的 `committed_contract_value` 算。一个月承诺 1 万美元、12 个月、8 折，合同收入是 9.6 万美元；如果客户实际用量超过承诺，超量部分按阶梯价。承诺的价值是收入确定性，代价是折扣和容量预留。给承诺客户留的 GPU 如果闲置，这部分成本要算进折扣，否则合同越签越亏。

**缓存折扣**要把成本差异传一部分给客户。前缀命中 90% 的请求，实际 prefill 只有 10%，但输入 token 数还是全部；如果按统一输入价收费，缓存收益全归 provider，客户没有动力复用系统提示词。把输入分成“缓存命中”和“未命中”两档，或者给命中部分 5 到 7 折，既能反映成本，也能引导客户优化用法。折扣比例要基于真实缓存成本和命中率，不能照搬。

**折扣治理**比定价表更重要。销售为了签单会给额外折扣，如果没有审批线和底线，实际价格会偏离定价表，毛利模型失效。一个最小治理结构是：标准折扣由销售自主决定，超过阈值要产品/财务审批，超过更大阈值要 CEO/CFO 审批；每季度复盘折扣分布、赢单率和毛利，找出“折扣换来的收入是否值得”。第 47 章的 NPV 和 LTV 模型可以用来评估“这个折扣下，客户还值不值得获取”。

## 48.9 销售产能与规模化门槛

收入计划要落到“多少人、多少时间、多少单”。`sales_capacity(reps, quota_per_rep, ramp_months, month)` 计算爬坡后的产能：10 个销售、每人年配额 100 万美元、爬坡 6 个月，第 3 个月的总产能是 500 万美元（按年化口径），第 6 个月才是 1,000 万美元。用满配额算第一年收入，是最常见的乐观错误。

销售产能要和漏斗匹配。如果目标是一年 100 个新客户、POC 转化率 25%，就需要 400 个 POC；如果每个销售每月能做 4 个 POC，一年 48 个，满产需要约 8.3 个销售。但第一年有 6 个月 ramp，平均有效产能只有约 24 个/人，实际需要 `400 / 24 ≈ 17` 个销售；再加管理幅度和流失，实际要招 18 到 20 个。只用“满产配额”反推，会把第一年的销售人数和成本低估一半。

规模化还有三个门槛。第一，**交付门槛**：每个客户都要定制集成、提示词和数据接入，收入增长会被交付人力卡住。第二，**支持门槛**：SLA 从 99.9% 提到 99.99%，需要额外的冗余、on-call 和故障转移，成本可能指数上升。第三，**合规门槛**：进入金融、医疗、政务需要认证、审计和数据驻留，提前期以月甚至年计。这些门槛不写在单位经济模型里，但会决定“收入能不能按时确认”。

`magic_number(new_arr, sales_marketing_spend)` 是一个快速体检：净新增 ARR 除以销售市场投入。大于 1 通常说明增长引擎有效率；小于 0.5 说明投入没有转化为收入。这个指标对窗口敏感，要看 12 个月滚动值，不要用一个季度的高低点下结论。

## 48.10 一个可复算的进入案例

假设一个团队要做面向中型企业的 Agent API，目标客户是 2,000 家，每家每年 50 亿 token，定价 0.5 美元/百万 token。TAM 是 `2,000 × 5,000 × 0.5 = 5,000,000` 美元。产品只覆盖其中 40%，SAM 是 200 万美元；三年目标份额 10%，线性爬坡，SOM 是 20 万美元。这个市场对一个小团队来说不大，但足够验证产品。

换一个更大的假设：20,000 家、每家 100 亿 token，综合单价 3.6 美元/百万 token（企业 Agent 的输出占比较高，不能直接用 0.5 美元的输入价）。每家年收入是 `10,000 × 3.6 = 3.6 万美元`，TAM 是 `20,000 × 3.6 万 = 7.2 亿美元`；SAM 30% 是 2.16 亿美元；SOM 10% 是 2,160 万美元。要拿到 300 万美元 ARR，按每客户 3.6 万美元/年算，需要约 83 个客户，占 SOM 的约 14%，是一个可以验证的目标。

这里必须做一次单位对拍：如果坚持 0.5 美元/百万，每家 100 亿 token 只有 5,000 美元/年，300 万美元 ARR 需要 600 个客户，而不是 83 个；83 个客户只能带来约 41.5 万美元 ARR。TAM、ARPU、客户数三个数必须一起改，不能只改其中一个。

按 83 个客户、POC 转化率 25%，需要 332 个 POC。每个销售满产一年 48 个，看似 7 个销售就够；但 6 个月 ramp 下第一年平均有效产能约 24 个/人，实际需要约 14 个销售。按每个销售 20 万美元的完全成本，销售团队年成本 280 万美元；加上售前、客户成功和营销，获客投入可能接近 350 万美元，而新增毛利只有 `300 万 × 55% = 165 万`。第一年这个计划是亏的，而且用 7 个销售根本交付不了 332 个 POC，需要靠续费、扩容和自助化在第二、三年回本。

这个案例的结论不是“不要做”，而是“要算清楚”。如果单价能提到 5,000 美元/月，83 个客户变成 50 个，POC 和销售人数下降，第一年可能打平；如果走自助获客，CAC 从 2 万美元降到 3,000 美元，回收期会大幅缩短；如果只做 10 个大客户，客单价高但销售周期长、集中度风险大。三条路都能到 300 万美元 ARR，但现金流、风险和团队配置完全不同。

用 `examples/finance.py` 可以复算这些数字：它打印 TAM/SAM/SOM、漏斗、magic number、DCF、倍数估值和 MOIC。把里面的客户数、用量、单价、转化率换成你的假设，就能得到自己的进入模型。第 49 章会把这个收入计划接到估值和融资上。

## 48.11 常见错误与检查清单

市场测算最常见的错误有八个。第一，用 token 总量乘单价，忽略输入/输出/缓存/批处理的价格差异。第二，把 TAM 当第一年收入，跳过 SAM、SOM 和爬坡。第三，用行业报告的“市场规模”直接当 TAM，不拆客户和用量。第四，假设所有潜在客户都能集成，忽略技术能力和预算周期。第五，用 PLG 的 CAC 估算企业销售，或反过来。第六，定价表很细，折扣治理很松，实际价格失控。第七，销售人数按“目标收入除以配额”算，忽略 ramp 和流失。第八，只算收入，不算交付、支持和合规的边际成本。

上线前可以用下面这张清单自查。市场定义是否自下而上、每一层假设是否有来源？TAM、SAM、SOM 的口径是否分开、是否写了时间？计价单位和成本单位是否一致、缓存和长尾是否算进去？客户分层是否对应不同的产品、价格和销售方式？漏斗每一级是否有进入/退出条件和停留时间？定价表是否有包装、承诺、缓存和折扣治理？销售产能是否按 ramp 算、是否和 POC 产能匹配？第一年的毛利能否覆盖获客和支持成本？如果这些问题答不上来，收入计划只是一个愿望。

## 小结

市场测算不是“找一个很大的数字”，而是把客户数、用量、单价、转化率和时间拆开，让每个假设可以被验证。TAM 是收入池，SAM 是产品能覆盖的部分，SOM 是竞争和执行后能拿到的份额；三者之间隔着产品、渠道、信任和交付四道漏斗。计价单位要和成本结构对齐，客户分层要对应不同的产品和销售方式，GTM 模式要匹配客单价和合规门槛，定价要有包装和折扣治理，销售产能要按 ramp 算。`mini_deepinfer/market.py` 把这些关系写成纯函数，`examples/finance.py` 给出可复算的算例。下一章把这些收入假设接到估值、融资和资本回报上。
