# 第 38 章 多模态推理工程：从像素到 token

本章导读：DeepSeek-V4.1-Flash 是多模态模型，但“支持图片”不等于“图片免费”。一张图要经过解码、缩放、patch 切分、视觉编码、aligner 投影，最后变成 LLM 上下文里的若干 token；这些 token 会占用 prefill 算力、KV 显存和缓存带宽。本章把这条链路拆成可计算的部分：图像如何变成 token、token 预算怎么估、视觉编码器如何批处理、图像 embedding 如何缓存、EPD 如何分离，以及质量评测为什么不能只看“能不能识别”。读完本章，你应该能在看到一张图片和一套预处理配置时，算出它要花多少 token、多少 KV、多少视觉编码算力，并知道哪些优化是真收益、哪些只是把成本挪到了别处。

## 38.1 多模态不是“多传一张图”

文本请求的成本主要由 token 数决定；多模态请求在 token 数之前还有一段“像素到 token”的转换。一个 1024×1024 的图片，如果按 16×16 的 patch 切分，有 4096 个 patch；经过 3×3 pixel-unshuffle 和 2×2 pooling 之后，可能只剩 121 个 LLM token。4096 和 121 是两个完全不同的成本口径：前者决定视觉编码器要做多少 patch 级计算，后者决定 LLM 的 prefill、KV 和上下文占用。

这条链路上每一段都有自己的瓶颈。图像解码和缩放通常在 CPU 上，可能受单核性能和内存带宽限制；patch embedding 和视觉注意力在 GPU/NPU 上，受算力和显存限制；aligner 把视觉 hidden 投影到 LLM 的 hidden 维度，产生跨模态 token；LLM 的 prefill 把这些 token 和文本 token 一起处理；KV cache 按 token 数增长；如果图片被多个请求复用，embedding 缓存可以省掉整个视觉编码阶段。

所以多模态推理的第一个原则是：**把“图像成本”拆成视觉编码成本和 LLM token 成本，分别规划**。只按文本 token 做容量规划，会低估 VE 的 GPU 需求；只按 patch 数估算 LLM 成本，会高估上下文占用。第 5.10 节已经从模型结构角度讲过这件事，本章把它落到可执行的公式和代码。

## 38.2 图像如何变成 token

DeepSeek-ViT 公开资料提到的关键设计包括 2D-RoPE、3×3 pixel-unshuffle 和约 32 层视觉塔。pixel-unshuffle 的作用不是“压缩图片”，而是把空间分辨率换成通道数：一个 3×3 的邻域被重排成一个像素的 9 个通道，空间尺寸缩小 3 倍，通道数增加 9 倍。这样后续的 patch embedding 可以在更粗的网格上工作，减少 token 数，同时保留局部细节。

可以用一个简化的三步模型来估算。第一步，原始 patch 数等于 `ceil(H/p) × ceil(W/p)`，其中 `p` 是 patch size。第二步，pixel-unshuffle 因子为 `u` 时，有效步长变成 `p × u`，token 数变成 `ceil(H/(p×u)) × ceil(W/(p×u))`。第三步，如果还有一个 `q×q` 的池化或下采样，token 数再除以 `q²`，向上取整。

以 1024×1024、`p=16`、`u=3`、`q=2` 为例：原始 patch 是 `64×64=4096`；unshuffle 后的步长是 48，网格是 `ceil(1024/48)=22`，所以是 `22×22=484`；池化 2×2 后是 `ceil(484/4)=121`。这三个数字分别对应三种成本：4096 是视觉塔要处理的 patch 数，484 是 unshuffle 后的视觉 token 数，121 是送进 LLM 的 token 数。很多容量估算的错误，来自把这三个数字混着用。

`mini_deepinfer/multimodal.py` 的 `ImageTokenPlan` 就是这套计算的可执行版本。它把 `raw_patches`、`unshuffled_tokens`、`llm_tokens`、`kv_bytes` 和 `ve_flops` 分开暴露，避免一个“token 数”掩盖三种不同的量。`ve_flops` 是一个刻意粗糙的估算，只用来判断视觉塔和 LLM 谁更贵，不是 benchmark。

## 38.3 token 预算与 KV 预算

LLM 侧的 token 预算可以直接套第 4 章的公式。121 个图像 token 加上文本 token，一起进入 prefill；KV 按每 token 890 字节计算，121 个 token 约 107,690 字节，也就是约 105 KiB。单看不大，但如果一个请求带 20 张图，就是 2420 个 token、约 2.1 MiB 的 KV；1000 个并发就是 2.1 GiB。图片数量比图片分辨率更容易被低估，因为它不改变单张图的成本，却线性放大总成本。

视觉编码器的成本则要看 patch 数。4096 个 patch 的视觉塔，计算量随 patch 数的平方增长（注意力部分），所以高分辨率图片的 VE 成本可能远高于 LLM 的增量成本。把一张 4K 截图缩到 1024×1024，可能损失 OCR 细节；不缩，则 VE 的算力和延迟会显著上升。生产系统通常按任务设置分辨率上限：聊天图片可以压到 768 或 1024，文档 OCR 需要更高分辨率，图表需要保留细线，截图需要保留小字。这个选择是质量与成本的交易，不是单纯的工程参数。

一个实用的预算表按“每请求”填：图片张数、每张图的 LLM token 数、文本 token 数、总上下文、KV 字节、VE patch 数、VE 延迟。然后把每请求的数字乘以并发，得到集群预算。不要只算平均值；图片尺寸的长尾往往比文本长度更长，一张超大图可能占掉几十张普通图的预算。

## 38.4 视觉编码器的批处理与预处理

视觉编码器也需要批处理，但它的批处理逻辑和 LLM 不同。LLM 的 batch 可以按 token 拼成 varlen 序列；视觉塔通常要求同一批图片有相同的空间形状，或者把不同形状的图片 padding 到同一个最大形状。padding 的部分仍然要参与计算，所以把一张 4K 截图和一张缩略图放在同一批，会让整批都按 4K 的形状计算，浪费大量算力。

`pack_vision_batches` 用一个简单的分桶策略处理这件事：先按 token 数除以桶宽分桶，再在桶内按大小排序，最后按 `max_batch_tokens` 做单批 next-fit（装满当前批就开下一批，不回溯之前的批）。这样相似尺寸的图片会落在同一批，padding 浪费被控制在较小范围。示例里 6 张图的 token 数是 121、100、121、480、484、960，分成三批，padding 浪费约 1.1%。如果把 960 和 100 放在一批，浪费会接近 90%。

预处理是另一个容易被忽略的瓶颈。图像解码、缩放、颜色空间转换、归一化、patch 切分通常在 CPU 上做；如果它们和 LLM 的 tokenizer 抢同一个进程，视觉请求会把文本请求的 TTFT 拖慢。生产系统通常把预处理放在独立的进程池或 VE 实例里，并限制解码后的像素数、格式白名单和解码超时。一个压缩炸弹可以在几 MB 的输入上解出几十 GB 的位图，足够把预处理池打爆。

视觉塔的延迟也要单独算。VE 通常是单卡就够，但它的延迟会加到 TTFT 上；如果 VE 和 P 实例共享 GPU，两者会互相干扰。EPD 分离把 VE 独立出来，就是为了让 P/D 不必为视觉编码预留资源，也让 VE 可以用更便宜的 GPU。

## 38.5 图像 embedding 缓存

文本前缀缓存按 token 哈希；图像缓存按“图像内容 + 预处理配置 + 编码器身份”哈希。`ImageEmbeddingCache.content_key` 把图像字节、encoder 名称和配置字符串一起做 SHA-256，任何一个变化都会导致 miss。这是正确的默认值：同一张图片在不同分辨率、不同裁剪、不同归一化下，embedding 不同，不能混用。

图像缓存和文本前缀缓存有三点不同。第一，缓存的粒度是整张图，不是 token 前缀；一张图要么全命中，要么全不命中。第二，缓存的 value 是 embedding，不是 KV；命中后省掉的是 VE 的前向和 aligner，不是 LLM 的 prefill。第三，缓存的 key 必须绑定模型版本和预处理版本；换了视觉塔或改了 patch 布局，旧 embedding 不能再用。

缓存的收益取决于复用率。商品图、文档模板、聊天里反复出现的头像和截图，复用率可能很高；用户随手拍的照片，复用率很低。TTL 和容量要按业务设置，并且要按租户隔离：A 租户的图片 embedding 不能因为内容哈希相同就被 B 租户命中，否则会泄露“这张图是否出现过”。如果业务需要跨租户共享，只能共享明确标记为公共的素材，并且要在缓存 key 里加入租户命名空间或访问策略。

`ImageEmbeddingCache` 实现了 TTL、LRU、命中率和字节统计。它不实现跨机共享、加密或租户隔离，这些是生产系统要补的。它的价值是让你看到“图片缓存不是文本缓存的附属品”，它有自己的 key、生命周期和隔离要求。

## 38.6 EPD 分离与路由

EPD 把 Vision Encoder、Prefill、Decode 三个阶段拆成独立的池子。VE 池按图片 patch 数路由，选当前处理 patch 最少的 GPU；P 池按文本和图像 token 的总长度路由；D 池按请求数和 KV 长度路由。三者的扩缩容指标不同：VE 看图片到达率和 patch 吞吐，P 看非缓存 token 数，D 看 running 序列数和 KV 占用。

`plan_epd_split` 给出了一个一阶估算。假设每秒 5 个请求、每请求 1 张图、每张图 121 个 LLM token、VE 每卡每秒 1 万 token、P 每卡每秒 6 万非缓存 token、D 每卡每秒 1.4 万输出 token、每请求 4096 个非缓存 token 和 512 个输出 token，再留 30% 余量，得到的比例大致是 VE 0.08 卡、P 0.44 卡、D 0.24 卡。这个例子里 VE 不是瓶颈，因为图片 token 少；如果每请求 20 张图，VE 的占比会迅速上升。这个模型只适合判断量级和比例，不能替代压测。

路由还要考虑“图片是否已经编码过”。如果请求带的是同一张公共图片，且 embedding 缓存命中，路由器可以把请求直接送到 P，跳过 VE；如果没命中，要先经过 VE。这个判断需要网关或路由器能访问 embedding 缓存的元数据，而不是等请求进了 VE 才发现。生产系统通常把“图片哈希 + 预处理配置”放在请求头或路由 key 里，先查缓存再决定路径。

## 38.7 视频、音频与文档

视频可以看成“按时间采样的图片序列”。一帧 1024×1024 的图片是 121 个 LLM token；如果每秒采样 2 帧、视频 60 秒，就是 120 帧、14,520 个 token，KV 约 12.9 MB（约 12.3 MiB）。帧率、分辨率、关键帧选择和时序建模都会改变成本。生产系统通常不会把每一帧都送进 LLM，而是先用视觉塔抽特征，再用时间维的池化或采样把帧数降下来。

音频通常经过编码器变成离散 token 或连续特征，再投影到 LLM 的 hidden 空间。音频的 token 率取决于编码器：一秒音频可能是几十个 token，也可能被压缩到几个 token。音频的 KV 成本同样按 token 数计算，但它的时间局部性很强，前缀缓存和流式处理的策略与文本不同。

文档是图片和文本的混合。扫描版 PDF 需要 OCR 或视觉编码；原生 PDF 可以抽取文本；表格和图表需要保留结构。文档场景的 token 预算往往由版面决定：一页 A4 在 150 DPI 下是 1240×1754 像素，按 16×16 patch 切分是 78×110≈8580 个 patch；经过 unshuffle 和池化后可能降到几百个 LLM token。页码越多，成本线性增长；如果每页都独立编码，缓存可以按页复用。

多模态的类型越多，路由和缓存的 key 就越复杂。一个实用的做法是给每种模态定义统一的“资产描述符”：类型、内容哈希、预处理配置、编码器版本、token 数。网关、VE、P 和缓存都用同一套描述符，避免每个组件自己解释“这张图是什么”。

## 38.8 质量与评测

多模态的质量问题不会在“能识别”测试里暴露。模型可能识别出图片里有一只猫，但读不出收据上的金额；可能看懂图表趋势，但把坐标轴单位搞错；可能在简单问题上很准，在需要细粒度定位的任务上崩溃。评测要覆盖五个维度。

第一是识别：物体、场景、人物、文字。第二是 OCR：小字、旋转、低对比度、表格线。第三是空间理解：位置、计数、相对关系、图表读数。第四是推理：结合图片和文本做多跳判断。第五是抗干扰：相似图片、模糊图片、对抗贴纸、截图中的无关文字。

分辨率会直接影响这些维度。把图片压得太小，OCR 和小字识别会先崩；把图片放得太大，VE 成本和延迟会上升，而且模型可能被过多细节干扰。评测要按任务类型设置不同的分辨率档位，并记录每档的 token 成本和准确率。只报一个平均分，会掩盖“聊天图很好、文档图很差”这种结构性差异。

图像 token 还会和长上下文质量叠加。图片 token 放在上下文的开头、中间、结尾，模型的召回可能不同；多图任务的图片顺序、图片之间的指代、图文交错的位置，都会影响答案。评测要覆盖真实的图文布局，而不是只把图片放在最前面。

## 38.9 mini-deepinfer 的实现

`mini_deepinfer/vision.py` 是一个迷你 ViT：16×16 的图片、4×4 的 patch、16 个 patch token、一层非 causal attention、SwiGLU 和 aligner。它把图片编码成 16 个向量，再投影到 LLM 的 hidden 维度。它不是 DeepSeek-ViT，没有 2D-RoPE、pixel-unshuffle 和真实权重，但它保留了“patch -> token -> embedding”的形状，足以验证多模态链路的接口。

`mini_deepinfer/multimodal.py` 提供本章的四个工具：`ImageTokenPlan` 算 token 和 KV，`ImageEmbeddingCache` 做内容哈希缓存，`pack_vision_batches` 做分辨率分桶，`plan_epd_split` 做 E/P/D 比例估算。运行：

```bash
python examples/multimodal.py
```

一次运行的输出包括：1024×1024 图片的原始 patch 4096、unshuffle 后 484、LLM token 121、KV 107,690 字节；迷你 ViT 的 embedding 形状是 `(16, 64)`；图片缓存命中率 1.0；6 张图分成三批，padding 浪费约 1.1%；10 张图/秒、每张 121 token 时 VE 约 0.157 卡。这些数字是确定性的，可以用来对照公式；它们不代表 DeepSeek-ViT 的真实性能。

mini 没有实现真实的图像预处理、跨机 embedding 传输、租户隔离和多模态 LLM 前向。它证明的是“成本模型、缓存 key、批处理策略和 EPD 比例”的逻辑，不是“多模态服务能跑”。第 20 章的保真度矩阵同样适用于这里。

## 38.10 常见故障

**图片 OOM。** 一张超大图在解码或 patch 化时可能占用几十 GB 内存。防护是限制像素数、格式白名单、解码超时，并在独立进程里做预处理。

**patch 爆炸。** 高分辨率图片的 patch 数按平方增长，VE 的延迟和显存会突然失控。防护是按任务设置分辨率上限，并在准入时估算 patch 数。

**缓存污染。** 不同预处理配置或模型版本共用同一个缓存 key，导致命中错误的 embedding。防护是把预处理配置和编码器版本写进 key，并在模型热更新时切换命名空间。

**缓存串租户。** 内容哈希相同不代表可以跨租户共享。防护是租户命名空间、哈希盐和访问控制。

**预处理阻塞。** 图像解码和文本 tokenization 抢同一个进程，导致文本请求 TTFT 抖动。防护是独立预处理池、有界队列和超时。

**位置和顺序错误。** 多图请求的图片顺序、图文交错位置、图像 token 的边界标记如果没有和训练格式对齐，模型会答非所问。防护是把模板和特殊 token 的版本写进 manifest，并在评测里覆盖多图布局。

**embedding 与 LLM 维度不匹配。** aligner 的输出维度、dtype 和 LLM 的 hidden 不一致，表现为形状错误或数值异常。防护是启动时校验形状和 dtype，warmup 覆盖多模态输入。

## 38.11 高分辨率切块与 OCR 路由

38.2 节的公式假设整张图缩放到一个固定网格。真实文档和截图往往不能整体缩放：一张 A4 扫描件缩到 1024×1024，小字会糊；一张 4K 截图缩到 768，代码和表格线会消失。生产系统通常采用“切块 + 路由”：把高分辨率图切成若干 tile，每个 tile 单独编码，再拼回上下文。

切块有三种策略。**固定网格**：按 512×512 或 768×768 切，重叠 10% 到 20% 防止文字被切断；实现简单，但边缘重复和拼接成本高。**版面感知**：先做 OCR/版面分析，按段落、表格、图块切；token 利用率高，但依赖预处理模型，延迟和错误率上升。**自适应**：先缩略图判断是否需要高分辨率，再对关键区域切块；成本最低，但需要两次编码或一个轻量分类器。

切块会改变 token 预算。一张 2480×3508 的 A4 在 150 DPI 下，按 512×512、20% 重叠切，大约需要 `ceil(2480/410)×ceil(3508/410)≈7×9=63` 个 tile；每个 tile 经过 patch/unshuffle/pool 后可能是几十到上百个 LLM token，总 token 数会远高于整图缩放的几百个。切块不是免费的，它把“分辨率”换成了“token 数”和“VE 计算量”。路由要根据任务决定：聊天图用整图缩放，OCR 用切块，图表用中等分辨率 + 局部放大。

OCR 路由还要考虑“先检测后识别”。整图先过一个小模型判断有没有文字、文字在哪个区域，再对区域切块；这比盲目切全图省很多 token。检测模型可以很轻，甚至用传统 CV；关键是不要把“高分辨率”当成默认，而是按任务和内容动态选择。评测要分别看“整图缩放”“固定切块”“版面感知切块”的准确率、token 成本和 P95 延迟，不能只报一个平均分。

## 38.12 EPD 的 embedding/KV 传输与背压

EPD 分离后，VE 产出的 embedding 要传给 P，P 产出的 KV 要传给 D。两条传输链路的特性不同：embedding 是一次性的、相对小（几 MB 到几十 MB），但必须在 prefill 前到达；KV 是持续的、按层和块传输，必须在 decode 前到达，且要预留容量。

embedding 传输的关键是“先算后传”还是“边算边传”。VE 可以按 tile 或按层流式输出 embedding，P 收到一部分就开始 prefill 对应位置；这样能重叠，但要求 P 的输入布局支持分段。更简单的做法是等整张图编码完再传，延迟高但实现简单。生产系统通常按图片大小选择：小图整传，大图分块流式传。

KV 传输的关键是背压。P 算得比 D 收得快，KV 会在网络上堆积；D 的 KV 页不够，P 必须减速或暂停。一个可用的协议是：D 先预留页和 state slot，返回可用容量；P 按容量发送，收到 ACK 后释放源 KV；D 在写入后更新可用容量。没有背压时，P 会一直算，D 会 OOM 或丢 KV；有背压但太粗，P 会频繁停顿，吞吐下降。

故障恢复要区分“可重试”和“不可重试”。embedding 传输失败可以重算 VE；KV 传输失败要看 P 是否还持有源 KV，如果持有可以重传，如果已经释放就只能回退到 P 重算。传输协议要带 transfer id、分块校验和幂等语义，避免重复写入。第 15.5 节的五步交接和附录 J 的 PD 排查可以对照使用。

最后，EPD 的容量规划要按阶段分开：VE 看 patch 吞吐，P 看非缓存 token 吞吐，D 看输出 token 和 KV 容量；三者用不同的扩缩容指标。把 EPD 当成一个整体做平均利用率，会掩盖某一阶段的瓶颈。

## 小结

多模态推理的成本要分三层看：patch 数决定视觉编码器的工作量，LLM token 数决定 prefill 和 KV，图片张数决定总预算。pixel-unshuffle 和池化把空间分辨率换成更少的 token，但会损失细节；分辨率、帧率和页面数是质量与成本的旋钮。视觉编码器需要按尺寸分桶批处理，预处理要独立，embedding 缓存要按内容、配置和编码器版本做 key，并且要隔离租户。EPD 分离让 VE、P、D 各自扩缩容，路由要先判断 embedding 是否命中。mini-deepinfer 用迷你 ViT 和成本模型验证了这些逻辑，但没有复制生产级的视觉塔和多模态前向。下一章把镜头转向另一类正在改变推理负载的请求：长思维链推理。
