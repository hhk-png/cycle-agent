# 第 29 章 评测体系与质量保证

本章导读：推理系统的“正确”有两层：引擎机制正确，模型输出质量可接受。前者靠单元/集成测试，后者靠评测。本章给出一个三层评测体系、benchmark 设计方法、统计显著性、长上下文/结构化输出/工具调用的专项评测、线上质量监控和发布门禁。读完本章，你应该能设计一套既能抓回归、又不会被噪声误导的评测。

## 29.1 为什么评测是系统的一部分

一个推理引擎可以“测试全绿”但业务效果很差：量化让模型偶尔答错、推测解码改变了采样分布、前缀缓存让长上下文召回下降、结构化输出让模型生成低质量但合法的 JSON。这些问题不会在单元测试里暴露，只能靠端到端评测。

评测还决定了优化能不能上线。一个 kernel 快了 10%，但如果它让 PPL 漂移 0.5%，团队要不要接受？一个量化方案省了 30% 显存，但让长上下文任务掉了 2 分，值不值？这些决策需要可复现的评测，而不是“看起来差不多”。

评测的成本很高：跑一次大模型的全量评测可能需要几百 GPU 小时。所以评测要分层：便宜的测试每次提交跑，贵的评测按版本/改动跑，业务评测按发布跑。

## 29.2 三层评测体系

三层体系的细节已经在 26.9 节展开：机制测试抓实现 bug，数值 baseline 抓数值漂移，任务评测抓质量下降。本章不重复这三层的定义，而是把重点放在“怎么设计一个可信的 benchmark、怎么解释分数、怎么把评测接进发布门禁”。如果你只想记住一句话：三层是漏斗，任何一层缺失，都会有一类问题漏到线上。

## 29.3 Benchmark 设计

一个可信的 benchmark 要回答五个问题：测什么、用什么数据、怎么判分、怎么统计、怎么复现。

**测什么**：是吞吐、延迟、质量，还是成本？吞吐要区分输入/输出 token、prefill/decode；延迟要区分 TTFT/TPOT/E2E、均值/分位数；质量要区分知识、推理、代码、长上下文、工具调用。

**数据**：数据集要和业务分布匹配。一个在 AIME 上很强的模型，不一定适合客服；一个在短问答上很好的模型，可能在长文档上崩溃。数据要覆盖长度分布、语言、领域、难度，避免只测“平均情况”。

**判分**：客观题用 exact match/accuracy；主观题用 judge 或人工；代码用单元测试/pass@k；结构化输出用 schema 校验；工具调用用执行结果。Judge 本身也有偏差，要校准（人工标注一批，比较 judge 和人的一致性）。

**统计**：报告均值、置信区间、样本量。一个小数据集上的 1% 提升可能没有统计显著性；一个 100 条样本的评测，置信区间可能宽达几个百分点。用 bootstrap 或配对检验，不要只看两个数字的大小。

**复现**：固定模型版本、tokenizer、chat template、采样参数、seed、硬件、推理配置。缺少任何一项，别人都无法复现。评测脚本要版本化，数据集要固定，judge 的 prompt 也要固定。

## 29.4 常用指标与陷阱

**Accuracy / Exact Match**：适合有标准答案的任务。陷阱是“格式不同但语义相同”被判错；要做归一化（大小写、空格、标点）。

**Pass@k**：代码任务常用，生成 k 个样本，只要有一个通过测试就算成功。陷阱是 k 越大越容易“碰对”，要同时报告 pass@1 和 pass@k。

**PPL**：语言建模的困惑度，适合检测数值漂移，不适合衡量任务质量。PPL 低不代表回答有用，PPL 高也不一定错。

**LLM-as-a-judge**：用另一个模型打分，成本低、可扩展。陷阱是 judge 偏好长答案、格式漂亮的答案、和自己风格相似的答案；要做位置随机化、人工校准、多 judge 投票。

**人工评测**：最可靠，但贵、慢、有标注者偏差。适合校准自动指标，不适合全量回归。

**业务指标**：留存、转化、投诉率、工具调用成功率。它们最接近价值，但受产品、流量、季节影响，不能直接归因于推理改动。

一个常见的陷阱是“用训练集/公开榜的数据做评测”。如果数据在训练集里，分数会虚高；如果公开榜被过度优化，分数不代表真实能力。评测数据要尽量私有、贴近业务、定期刷新。

## 29.5 长上下文评测

长上下文是推理系统最容易“看起来支持、实际不好用”的能力。评测要覆盖：

- **检索**：在长文档里找一句话/一个数字，测“大海捞针”。
- **多跳推理**：答案需要组合文档中多个位置的信息。
- **顺序/结构**：需要理解文档结构、表格、代码仓库的层次。
- **抗干扰**：文档里有相似但不相关的段落，模型是否被带偏。
- **位置偏差**：答案在开头、中间、结尾时，模型表现是否一致。很多模型对中间位置的信息召回更差。

评测时要用真实的长度分布，不要只测 1M 的极端 case；也要测“短问题 + 长上下文”，因为很多业务是这种形态。KV 压缩、稀疏注意力、SWA 重放都可能让长上下文召回下降，必须专项对比。

## 29.6 结构化输出与工具调用评测

结构化输出不能只测“合法率”。一个模型可以 100% 输出合法 JSON，但字段全错。评测要同时看：

- **合法率**：能否通过 schema 校验。
- **字段准确率**：关键字段是否和期望一致。
- **完成率**：是否在 max_tokens 内完成，是否被截断。
- **内容质量**：字段值是否合理，是否重复、空泛、编造。

工具调用要测：工具选择是否正确、参数是否合法、参数值是否正确、调用顺序是否合理、失败后是否重试/降级。最好的评测是“在沙箱里真的执行工具”，而不是只看文本。

## 29.7 线上质量监控

离线评测不能覆盖所有流量。线上要监控：

- 输出长度分布、拒答率、重复率、截断率；
- 结构化输出合法率、schema 失败率；
- 工具调用成功率、参数错误率；
- 用户反馈（点赞/点踩/重试/复制）；
- 延迟和错误率；
- 缓存命中率、量化/推测的开关状态。

线上监控的难点是“没有标签”。可以用弱信号（用户重试、会话长度、复制行为）和抽样人工评审。异常检测要看分布漂移，而不是只看均值；一个模型可能平均分不变，但某一类请求的质量大幅下降。

## 29.8 发布门禁与灰度

一个实用的发布流程是：

1. 机制测试全绿；
2. 数值 baseline 在容差内；
3. 任务评测不低于基线（或下降在可接受范围）；
4. 小流量灰度，观察延迟、错误率、业务指标；
5. 逐步放量，保留回滚开关；
6. 记录模型/配置/评测版本。

门禁要写成可执行的检查，而不是“大家觉得没问题”。例如“P95 TTFT 不超过基线 10%”“结构化输出合法率不低于 99.5%”“长上下文检索不低于基线 1 分”。阈值要按业务定，不能拍脑袋；还要大于评测本身的置信区间。如果评测只有 100 条样本、95% 置信区间有 ±4 个百分点，把门禁设成“下降不超过 1 分”只会制造噪声。样本量和置信区间的算法见 29.11 节。

灰度要按租户/流量/地域分层，避免一次全量。回滚要能在分钟级完成，且不丢请求；这要求模型版本、配置、KV 格式都兼容。

## 29.9 成本-质量-延迟的帕累托

推理优化很少是“三赢”。量化省显存但可能降质量；推测解码提吞吐但增加尾延迟；更大的 batch 提吞吐但降 TPOT；更长的缓存 TTL 提命中率但增存储成本。评测要给出帕累托前沿，而不是一个单点。

一个实用的做法是画三张图：成本 vs 质量、延迟 vs 质量、成本 vs 延迟。每个点是一个配置（精度、batch、EP、推测开关、缓存 TTL）。团队根据业务约束选点：客服可能选低延迟，离线批处理可能选低成本，高价值任务可能选高质量。

帕累托前沿上的点没有“绝对最好”，只有“在当前约束下最合适”。评测的价值是让选择有数据支撑，而不是让某个指标最大化。

## 29.10 mini-deepinfer 的评测练习

mini 没有真实任务评测，但你可以做三件事：

1. 用固定 prompt 集，比较 `temperature=0` 下不同 block size、chunk size、前缀缓存开关的输出是否一致；这是机制评测。
2. 用 `roofline.py` 算不同配置的理论成本，和 `benchmark.py` 的实测吞吐对比；这是模型 vs 实测的校准。
3. 用 `structured_output.py` 的示例，统计不同 schema 的合法率、完成率、平均长度；这是结构化输出的最小评测。

这些练习不能替代真实模型评测，但能让你熟悉“固定变量、报告分布、对比 baseline”的方法。

## 29.11 置信区间与样本量

评测最常见的错误是“看了两个数字就下结论”。100 条样本上的 1 个百分点差异，可能完全在噪声范围内。

假设准确率 80%，样本 100 条，标准误约 `sqrt(0.8 × 0.2 / 100) ≈ 0.04`，95% 置信区间约 72% 到 88%。如果新方案是 82%，旧方案是 80%，两个区间大幅重叠，不能说明新方案更好。

这里要区分两个常被混用的样本量问题。第一个是**估计精度**：希望 95% 置信区间的半宽不超过 2 个百分点，需要 `0.8 × 0.2 × (1.96 / 0.02)^2 ≈ 1537` 条。第二个是**检验功效**：希望以 80% 的概率检测出 2 个百分点的真实差异，在双侧 5% 显著性下，每组约需 `2 × (1.96 + 0.84)^2 × 0.8 × 0.2 / 0.02^2 ≈ 6270` 条；两组独立样本就是约 1.25 万条。1537 条只能保证“估得比较准”，不能保证“看得出 2 个点的差异”。如果是同一批样本上的配对检验，所需样本量取决于配对结果的相关性，通常小于独立设计，但不会小一个数量级；要用配对差的方差重新算，而不是直接套比例公式。

对于同一批样本上的新旧对比，应该用配对检验，而不是两个独立比例检验。配对检验看的是“新方案对、旧方案错”和“旧方案对、新方案错”的差值，方差更小，更容易检测出真实差异。代码任务可以用 pass@1 的配对比较，或者用 bootstrap 重采样估计置信区间。

多指标比较要做多重检验校正。如果你同时看准确率、延迟、成本、长上下文、结构化输出五个指标，每个都用 95% 置信度，至少一个假阳性的概率会显著上升。可以用 Bonferroni 或 FDR 校正，或者预先指定一个主指标，其他作为辅助。

样本量还受数据分布影响。平均准确率相同，但一个方案在短样本上更好、另一个在长样本上更好，合并后的数字会掩盖差异。评测要按长度、语言、任务类型分层，每层单独看置信区间；否则“平均分不变”可能意味着“两类样本一升一降”。

最后，统计显著不等于业务显著。一个 0.5 分的提升可能统计显著，但用户感知不到；一个 2 分的下降可能样本量不够，但业务影响很大。评测报告要同时给“效应大小”和“置信区间”，让决策者判断是否值得上线。

## 29.12 性能 benchmark 的方法学

质量评测回答“模型答得对不对”，性能 benchmark 回答“服务在什么工作点跑得多快”。两者不能混在一起，但方法上有共同点：固定变量、报告分布、能复现。

**负载生成**有两种基本模式。开环（open-loop）按固定到达率发请求，不管服务是否跟得上；闭环（closed-loop）等上一个请求完成再发下一个，更接近真实用户，但会把服务变慢反馈成到达率下降。测吞吐和尾延迟时优先用开环，否则服务一慢，负载也跟着变慢，测不出排队。生产回放则直接用 trace 的到达时间戳，保留真实的突发和长尾。

**warmup 与缓存状态**必须写清楚。第一次请求会触发 kernel 编译、CUDA Graph 捕获、页缓存冷启动；前缀缓存是空的还是热的，会让 TTFT 差几倍。一个可复现的 benchmark 至少记录：warmup 步数、缓存命中率、请求长度分布、batch/并发、是否开启推测解码和结构化输出。

**固定工作量还是固定时间**要选一个。固定工作量（例如 1000 条请求）测总时间，适合比较吞吐；固定时间（例如跑 5 分钟）测稳态，适合观察尾延迟和资源漂移。两者不能混着比。

**报告什么**：吞吐要分输入/输出 token、prefill/decode；延迟要分 TTFT/TPOT/E2E 的 P50/P95/P99；还要报 goodput（SLO 内完成的请求数）和 SLO 达标率。只报平均值或峰值吞吐，会掩盖长尾和排队。

**统计**：同一配置重复至少 3 到 5 次，报告均值和置信区间；跨配置比较用配对或 bootstrap，不要只看两个单点。性能噪声比质量评测更大，1% 到 3% 的差异通常不显著。

**厂商 benchmark 的陷阱**：有利的 batch/长度分布、预热过的缓存、只报峰值吞吐、不报 P99、混合输入/输出 token 口径、不同精度/并行配置。读任何 benchmark 先问“它测的是什么工作点、缓存是什么状态、延迟分布在哪里”。

## 29.13 Judge 校准与评测数据治理

用模型当 judge 很常见：让一个强模型给答案打分、判断是否满足要求、比较两个版本。它便宜、可扩展，但也最容易产生“看起来有数字、其实不可信”的结论。Judge 的问题不是“会不会错”，而是“错得有没有规律、有没有被校准”。

**校准**要回答三件事。第一，judge 和人工评分的一致性有多高？用同一批样本，让人工和 judge 各打一次，计算 Cohen's kappa 或 Spearman 相关；kappa 低于 0.6 通常说明评分标准不一致，不能直接用于发布门禁。第二，judge 是否有位置偏好？比较 A/B 两个答案时，把顺序对调再跑一次，如果结论翻转，说明它偏爱第一个或第二个。第三，judge 是否被长度、格式、模型风格带偏？把同样内容的短答案和长答案放在一起，看它是否系统性偏好更长或更“像”某个模型的输出。

校准之后还要做**持续监控**。Judge 本身是一个模型，供应商更新、prompt 改动、温度变化都会改变它的评分分布。每次换 judge 版本，要用一组固定的“锚点样本”重跑，确认分数没有整体漂移；如果漂移，历史评测结果不能直接和新结果比较。Judge 的 prompt 也要版本化，不能今天改一句“请严格打分”，明天还拿旧分数做趋势。

**评测数据治理**包括四件事。第一，**污染**：评测集是否出现在训练数据里？公开 benchmark 尤其容易污染。要做 n-gram 重叠检查、时间切分和私有保留集；不能只用公开榜单证明模型能力。第二，**授权**：评测数据是否有权使用？人工标注是否知情同意？涉及个人信息的数据要脱敏或删除。第三，**新鲜度**：模型和流量分布会变，评测集也要更新；一个两年前设计的集子可能已经饱和，无法区分新版本。第四，**可复现**：固定数据版本、prompt、judge 版本、解码参数和随机种子；报告里写清楚，否则别人无法复现你的分数。

一个实用的发布门禁是“三层证据”：机制测试（单元/集成）证明系统没坏；固定 baseline 证明数值没漂；业务评测证明质量没退。三层都通过才放行，任何一层缺失都要说明原因。Judge 只能作为业务评测的一部分，不能替代机制测试和人工抽检。第 26 章的测试分层和第 29.11 节的统计方法可以一起用：先用样本量公式确定需要多少题，再用配对检验判断差异是否显著，最后用 judge 校准确认评分可信。

## 小结

评测是推理系统的一部分，不是发布前的一次性检查。机制测试、数值 baseline、任务评测三层各抓不同的问题；benchmark 要固定数据、判分、统计和复现；长上下文、结构化输出、工具调用要专项评测；线上要监控分布漂移；发布要有门禁和灰度。成本、质量、延迟之间是帕累托关系，评测要帮助团队在约束下选点。

## 练习

1. 为一个客服机器人设计三层评测：每层用什么数据、什么指标、多久跑一次？
2. 解释为什么“结构化输出合法率 100%”不能说明输出质量好。设计两个补充指标。
3. 一个评测显示新量化方案平均分不变，但长上下文检索掉了 3 分。你会怎么决策？需要哪些额外信息？
4. 设计一个发布门禁：列出至少五条可执行检查，并说明阈值怎么定。
