# 第 1 章 为什么需要推理框架

本章导读：从一个朴素的 `generate()` 循环出发，解释它为什么无法直接支撑在线服务，进而建立 prefill/decode、KV cache、批处理、TTFT/TPOT 和 roofline 这几个贯穿全书的坐标系。读完本章，你应该能把“推理慢”拆成计算、显存带宽、调度和通信四类原因，并且能用一组简单公式估算瓶颈。

## 1.1 模型只做一件事

一个自回归语言模型的核心计算可以写得很简单：给定 token 序列 `x_1 ... x_t`，输出下一个 token 的概率分布 `p(x_{t+1} | x_1 ... x_t)`。生成就是不断从分布里取一个 token，把它接回序列，再算下一次。

最朴素的实现是这样的：

```python
def generate(model, prompt, max_tokens):
    tokens = prompt
    for _ in range(max_tokens):
        logits = model(tokens)
        next_token = sample(logits[-1])
        tokens.append(next_token)
    return tokens
```

这段代码在笔记本上跑一个小模型没问题，但一旦要服务很多用户，就会暴露四个问题。

第一，每一步都把整个前缀重新算一遍。第 `t` 步的注意力需要前面所有 token 的 Key 和 Value，如果每步都重算，复杂度是 `O(T^2)`，生成 1000 个 token 会把同样的前缀算 1000 次。

第二，请求是一个一个处理的。GPU 的矩阵乘法擅长同时处理很多行，batch=1 时大量算力被浪费；但直接把不同用户的请求拼在一起，又会遇到长度不同、结束时间不同、显存不足的问题。

第三，显存不够。KV cache 的大小随“层数 × 序列长度 × KV 头数 × head 维度”线性增长，长上下文和多并发会迅速吃满显存。显存不足时，是丢弃请求、降级，还是把缓存换出到主机内存，需要一套策略。

第四，指标不只是“每秒多少 token”。聊天产品关心首 token 延迟 TTFT，流式输出关心相邻 token 间隔 TPOT，批处理任务关心总吞吐，API 服务关心尾延迟和成本。不同指标会导向不同的调度决策。

推理框架就是把这些问题工程化：它不改变模型数学，但决定模型在什么 batch 下、以什么顺序、用什么精度、把哪些中间结果留在哪里。

如果这是你第一次接触 Transformer，建议先读附录 F。它用一页纸的篇幅解释 token、Q/K/V、causal mask、KV cache 和采样；本节的公式在附录 F 里都有更基础的版本。已经熟悉的读者可以跳过。

## 1.2 prefill 与 decode 是两种负载

一次请求通常分两个阶段。

**prefill** 处理用户输入的 prompt。所有 prompt token 可以并行计算，注意力矩阵是 `T_prompt × T_prompt` 的下三角。这个阶段矩阵乘法的规模大、并行度高，通常受算力限制。它决定了首 token 什么时候能出来，也就是 TTFT 的主要部分。

**decode** 每次只生成一个 token。此时 query 只有一行，但需要读取整个 KV cache 和模型权重。矩阵乘法的规模变小，显存带宽成为瓶颈。decode 的每一步时间决定了 TPOT，也就是流式输出的“打字速度”。

用 roofline 的语言说，一个算子的实际耗时取决于它更接近计算上限还是带宽上限。设算力为 `P`（FLOP/s），带宽为 `B`（Byte/s），一个算子做了 `F` 次浮点运算、搬了 `M` 字节，则：

```text
计算时间 >= F / P
带宽时间 >= M / B
实际时间 >= max(F / P, M / B)
算术强度 = F / M
```

当算术强度高于机器的 `P / B` 时，算子受算力限制；低于时，受带宽限制。prefill 的大矩阵乘法算术强度高，decode 的单行矩阵向量乘算术强度低。这就是为什么同一个模型、同一块 GPU，prefill 和 decode 的最优并行策略往往不同。

举一个可以直接心算的例子。假设某 GPU 的 FP16 算力是 1000 TFLOPS，HBM 带宽是 3 TB/s，ridge point 是 `1000e12 / 3e12 ≈ 333 FLOP/byte`。一个 16B 激活参数的模型做 decode，每步约 `2 × 16e9 = 32 GFLOP`，但要把约 16 GB 的 FP8 权重读一遍。算力时间约 `0.032 ms`，带宽时间约 `5.3 ms`，相差两个数量级。把所有请求拼成 batch，可以让同一份权重服务多行 query，这就是 decode 阶段最核心的杠杆。

DeepInfer 的部署方式正是围绕这个差异设计的：prefill 用较少的 GPU 做 EP2 到 EP8，decode 用 64 到 128 张 GPU 做 Wide-EP。这里的“64 到 128 张”是通信域的规模，不是把 EP 和 DP 相乘得到的卡数。第 15 章会解释 EP64DP64 为什么通常指 64 张卡上的两种并行视图，而不是 4096 张卡。

## 1.3 KV cache 把“重算”变成“读取”

Transformer 的每一层注意力都需要当前 token 的 Query 与所有历史 token 的 Key 做点积，再用结果对 Value 加权。历史 token 的 Key 和 Value 一旦算过就不会变，因此可以缓存。

对一层、一个 KV 头、head 维度为 `d` 的模型，每个 token 的 KV 占用是 `2 × d × bytes_per_element`。乘以层数 `L` 和 KV 头数 `H_kv`，得到每 token 的 KV 字节数：

```text
KV_bytes_per_token = 2 × L × H_kv × d × bytes
```

以 DeepSeek-V4.1-Flash 公开资料中的 890 字节/token 为例，128K token 的单条序列大约占 117 MB（约 111 MiB）。1000 条并发就是 117 GB 左右。这个数字直接决定了单卡能放多少并发、是否需要把 KV 换出、以及前缀缓存能省下多少。

KV cache 带来两个新的系统问题。

一是**分配**。序列长度事先未知，生成过程中不断增长。如果按最大长度预留，显存会被大量浪费；如果按需分配，又会产生碎片。分页 KV cache 把缓存切成固定大小的 block，用页表把逻辑 token 映射到物理 block，按需分配、按块共享。

二是**复用**。很多请求共享相同的前缀，例如同一个系统提示词、同一段文档、同一轮多轮对话的历史。如果每来一个请求都重新算前缀，既浪费算力又增加 TTFT。前缀缓存用内容哈希找到已经算过的 block，直接挂到新序列的页表上。DeepInfer 的生产系统把这类 block 放到 3FS 上，TTL 按业务设为 3 天或 7 天。

这里有一个经常被忽略的细节：缓存命中不等于“可以直接 decode”。前缀命中的 token 数通常被 block 对齐，真正需要额外处理的是**没有一起命中的状态**：滑动窗口的 KV 可能只覆盖了最后一个窗口，decoder 侧的全局表示可能来自被截断的 hidden。命中块决定“哪些 token 不用重算”，状态缓存决定“最后一个窗口要不要重放”，两者不能互相替代。第 6 章会解释为什么 SWA 命中要退回固定长度的重放，第 14 章会把这两本账分开算。

## 1.4 批处理不是“把请求排成队”

最直觉的批处理是静态 batch：攒够 N 个请求，一起跑完，再处理下一批。它有两个致命问题。

第一，短请求要等长请求。一个 10 token 的请求和一个 4000 token 的请求拼在一起，短请求的 GPU 时间被长请求拖住，尾延迟很差。

第二，batch 组成固定。生成过程中有的请求结束、有的请求新到，静态 batch 不能在中途换人，GPU 会在“等人”和“空转”之间浪费。

连续批处理（continuous batching）把调度粒度从“一个 batch”改成“一个 step”。每个 decode step 结束后，框架可以立刻把完成的请求移出、把等待的请求加入，而不必等整批结束。这样 GPU 的每一行都在做有用功，代价是调度器必须维护每个请求的状态、页表、采样参数和停止条件。

更进一步的 chunked prefill 把长 prompt 切成若干块，和 decode 请求混在同一个 step 里。它牺牲一点 prefill 的矩阵效率，换取更平滑的 TTFT 和更高的混合吞吐。DeepInfer 的调度器支持 chunked prefill，并在 DP rank 之间用投票决定这一步做 prefill 还是 decode，避免不同 rank 步型不一致。

批处理也有上限。batch 越大，单步时间越长，尾延迟越差；KV 占用也越大，可能触发抢占。一个成熟的调度器不是“尽量把 batch 塞满”，而是在 SLO 约束下寻找 goodput 最大的工作点。

## 1.5 指标：吞吐、延迟与好吞吐

推理系统常用的指标有：

- **TTFT**（Time To First Token）：从请求到达到第一个输出 token 的时间，主要由排队和 prefill 决定。
- **TPOT**（Time Per Output Token）：第一个 token 之后，平均每个输出 token 的时间，主要由 decode 决定。
- **端到端延迟**：TTFT 加上 `(输出 token 数 - 1) × TPOT`，再叠加排队和网络。
- **吞吐**：单位时间处理的输入 token 数、输出 token 数或请求数。
- **goodput**：在满足 SLO 的前提下，单位时间完成的有用请求数。它比裸吞吐更接近业务价值。

这几个指标经常互相冲突。增大 batch 能提高吞吐，但会让单请求的 TPOT 变差；把更多 GPU 分给 prefill 能降低 TTFT，但会减少 decode 的并发；更激进的量化能降低带宽，但可能影响质量。框架的调参本质上是沿着一条帕累托前沿选择工作点。

举一个计算例子。一条 8K prompt、生成 512 token 的请求，TTFT 为 300 ms，TPOT 为 20 ms，则端到端延迟约为 `0.3 + 511 × 0.02 ≈ 10.5 s`。如果 TPOT 降到 12 ms，端到端延迟变成 `0.3 + 511 × 0.012 ≈ 6.4 s`，下降了约 39%。注意首 token 的 0.3 秒在这里只占很小一部分；长输出场景下，decode 的每一步才是成本主体。

**Little 定律**把并发、到达率和停留时间联系起来：`并发数 = 到达率 × 平均停留时间`。如果服务每秒到达 20 个请求，平均每个请求停留 30 秒，系统里平均有 600 个请求在跑。这个数字决定了需要多少 KV cache 和多少 decode 容量。

DeepInfer 官方 Q&A 给出的生产数字是一个很好的量级参照：公开口径的单个服务集群每天服务 155 万亿 token，平均 TTFT 约 400 毫秒（P99 约 1 秒），decode 约 230 token/s（编码场景可达 300 token/s），输入缓存命中率约 96%，按谷时电价计算的每 GPU 小时收入为 38 美元。这组数字要一起看：每天 155 万亿 token 说明规模；400 毫秒 TTFT 说明交互可用；96% 命中率说明绝大多数输入 token 没有重新做 prefill；230 token/s 说明 decode 的吞吐足以支撑多人共享。它们背后不是某个单点优化，而是 kernel、并行、调度、缓存和运维共同作用的结果。第 30 章会把它拆成成本模型，第 36 章会把它翻译成产品和毛利。

这些是厂商公开的自报数字，没有第三方独立验证，也不代表你的硬件和流量能复现。书中引用它们是为了建立量级直觉，而不是给出 benchmark 承诺。

## 1.6 一个框架至少要做什么

把上面的问题收拢，一个推理框架至少需要以下能力。

1. **模型执行**：加载权重、组织层、调用 attention/GEMM/通信 kernel，支持多种精度和硬件。
2. **请求调度**：维护 waiting/running 队列，决定每个 step 做 prefill 还是 decode，处理抢占、取消和超时。
3. **KV 管理**：分页分配、前缀复用、换出换入、跨请求/跨节点传输。
4. **采样**：温度、top-k、top-p、停止条件、结构化约束、确定性随机数。
5. **并行与通信**：DP、EP、CP、PD 分离，集合通信与负载均衡。
6. **服务边界**：tokenizer、Chat 模板、流式输出、API 协议、限流与鉴权。
7. **可观测性与运维**：指标、日志、trace、故障恢复、扩缩容。

DeepInfer 的开源版本覆盖了其中大部分“计算路径”，但明确不包含完整的 KV cache 系统、VE/Prefill/Decode 分离部署和跨 DP 副本的负载均衡。第 2 章会说明这条开源边界，第 14、15 章会讲被省略的部分为什么难。

## 1.7 用 mini-deepinfer 观察这些现象

本仓库的迷你引擎把上面每一件事都缩小实现了一遍。你可以用一条命令看到批处理的效果：

```bash
python examples/benchmark.py --batch-sizes 1 2 4 8 --max-tokens 16
```

在普通 CPU 上，batch 从 1 增到 2 或 4 时，总吞吐通常会上升，因为一次前向传播摊薄了 Python 和 NumPy 的固定开销；继续增大时，收益会被内存带宽和缓存竞争吃掉。TTFT 和 TPOT 也会随 batch 变化。具体数值因机器而异，但这种“先升后平”的形状是连续批处理要寻找的工作区。

你也可以用 `examples/chunked_prefill.py` 观察分块 prefill 与完整 prefill 的输出一致性，用 `examples/speculative_decoding.py` 观察推测解码的接受率，用 `examples/roofline.py` 把本章的公式算一遍。第 4 章会给出把这些现象量化成公式的方法，第 18 章会解释这些公式在 GPU 上如何对应到 kernel。

## 1.8 一次十步的连续批处理追踪

抽象地讲“每步换人”很容易，真正理解它需要看一次状态变化。下面用一个极小的例子走十步：block size 为 4，单步 token 预算为 8，最多同时跑 3 条序列。请求 A 的 prompt 是 5 个 token、最多生成 3 个；请求 B 的 prompt 是 2 个 token、最多生成 2 个；请求 C 在 A 快结束时到达，prompt 是 4 个 token、最多生成 2 个。

第 1 步是 prefill 步。调度器把 A 和 B 一起放进这一步：A 贡献 5 个 token，B 贡献 2 个，合计 7，没有超过预算 8。A 需要 `ceil(5/4)=2` 个 block，B 需要 1 个 block，三条空槽位用了两个。prefill 结束后，A、B 各采样出第一个 token，序列长度变成 6 和 3，状态从 WAITING 变成 RUNNING。注意这一步的 `prefill_tokens` 是 7，但输出 token 是 2；首 token 是在 prefill 步产生的，统计口径要和 decode 分开。

第 2 步是 decode 步。running 队列里有 A、B，每条只需要 1 个 query token，`q_len=2`。A 的第二个 block 还有 2 个空位，B 的第一个 block 还有 1 个空位，所以不需要新分配 block。A 和 B 各生成一个 token。B 的输出达到 2 个，满足 `max_tokens`，在这一步结束后释放它的 1 个 block，并从 running 队列移除。

第 3 步仍然有 A，`q_len=1`。A 再生成一个 token，输出达到 3 个，也结束，释放 2 个 block。此时 running 队列为空。如果这是静态 batch，GPU 会在这里停下来等下一批；连续批处理不会，它会在第 4 步直接进入下一次 prefill。

第 4 步，C 到达，做 prefill。C 的 4 个 token 正好占 1 个 block，采样出第一个 token，进入 running。第 5 步，C 再生成一个 token，达到 `max_tokens=2`，结束并释放 block。十步的例子里实际只用了五步，但状态变化已经包含了连续批处理的全部关键动作：prefill 合批、decode 合批、短请求先结束、结束后立刻回收、新请求在下一步插入。

把这条 trace 和静态 batch 对比，可以看到两种浪费。静态 batch 的第 3 步之后，A 已经结束而 B 早已结束，GPU 仍然要等整批的“最长请求”跑完；连续批处理在第 4 步就把 C 放进来了。另一种浪费是 block 预留：如果按最大长度给 A、B、C 各预留 8 个 block，三条序列会占 24 个 block；按需分配只用了 2、1、1 个，峰值 3 个。前者在长上下文服务里会直接把并发压到十分之一。

这个例子也暴露了连续批处理的代价。每一步都要重新决定“谁进来、谁出去、谁被抢占”，调度器必须持有每条序列的页表、采样参数、停止条件和 RNG；一旦某条序列被抢占，它的 KV 要么释放后重算，要么换出到存储。静态 batch 没有这些状态，所以它简单；连续批处理用状态换利用率，这个交换是否划算，取决于请求长度分布和 SLO。第 13 章会把这条 trace 扩展成真实的调度器策略，第 22 章会在 mini 引擎里逐步打印同样的字段。

## 小结

推理框架的价值不在于“让模型更聪明”，而在于把模型的计算组织成可预测、可复用、可扩展的服务。prefill 和 decode 的计算特征不同，KV cache 把重算变成读取，连续批处理把 GPU 从“等人”中解放出来，而 TTFT、TPOT、吞吐和 goodput 共同定义了什么叫“快”。后面的章节会沿着这条主线，先看 DeepInfer 如何组织这些机制，再看我们如何在一个小实现里验证它们。
