# 第 36 章 推理产品化与商业路径

本章导读：技术指标不等于产品价值。一个推理服务可以把每百万 token 成本压到很低，却仍然没有客户；也可以技术一般，但靠场景、渠道和服务赚到钱。本章把第 30 章的单位经济向前延伸：从用户感知、客户分层、定价、毛利、销售与支持成本，到开源与闭源的商业边界，最后用一个可复算的案例把 `economics.py` 的数字串起来。读完本章，你应该能回答“这个推理产品靠什么赚钱、护城河在哪里、什么时候会亏”。

## 36.1 从技术指标到产品指标

推理工程师习惯看 TTFT、TPOT、吞吐、goodput。客户看的是另一组东西：打开聊天框后多久出现第一个字、写代码时补全是否跟手、Agent 跑一个任务要几分钟、账单月底是多少、出错时能不能重试。

这两组指标之间有映射，但不是一一对应。

**TTFT 对应“等待感”。** 聊天场景里，TTFT 超过 1 秒，用户会明显觉得卡；代码补全要求更低，通常几百毫秒；离线批处理可以容忍几十秒。DeepInfer 公开的生产数字是平均 TTFT 约 400 毫秒、P99 约 1 秒（厂商自报，未经第三方独立验证），这个量级对应的是“对话可用”。

**TPOT 对应“阅读速度”。** 人类阅读速度大约是每秒 5 到 10 个汉字；按中文 1 到 3 token/字（取决于 tokenizer），大约是 5 到 30 token/s。生成速度超过阅读速度后，用户感知的瓶颈就从模型转到阅读。代码场景对速度更敏感，因为用户在看补全结果决定是否接受。公开资料提到 decode 约 230 token/s，编码场景可达 300 token/s，这是单用户的 decode 体验（在共享集群的生产负载下测得），不是集群聚合吞吐，也不是单请求独占一张卡的峰值。

**吞吐对应“单位成本”。** 同样的 GPU，服务更多 token，单位成本更低。但吞吐和延迟是权衡：batch 越大，吞吐越高，单请求 TPOT 越差。产品要选一个工作点，而不是同时最大化两个指标。

**goodput 对应“有效收入”。** 超过 SLO 的请求即使生成了 token，也可能被用户放弃、被重试、被投诉。把 goodput 作为容量规划指标，比裸吞吐更接近业务。

**成本对应“毛利”。** 每百万 token 的成本决定定价空间；每 GPU 小时的收入决定规模下的绝对值。两者要一起看。

一个常见的误区是“把 benchmark 峰值当产品指标”。厂商 benchmark 通常在有利的 batch、长度分布和硬件配置下测，真实流量有长尾、有突发、有失败重试。产品决策要用自己的流量 trace 回放，而不是别人的单点数字。

## 36.2 客户与场景分层

推理服务不是一个大市场，而是很多个场景的组合。不同场景对延迟、质量、成本、合规的要求差别很大。

**对话/客服**：中等上下文，短输出，强延迟敏感，需要流式、多轮、工具调用、内容审核。单位 token 价格低，但调用量大；毛利靠规模和缓存命中。

**代码补全/生成**：低延迟、短输出、高并发、对正确性敏感。补全场景要求几百毫秒内返回，通常用更小的模型或蒸馏模型；生成场景可以用大模型，但要有流式。

**Agent/工作流**：长上下文、多轮工具调用、长尾延迟不敏感但总时长敏感。前缀复用率高，KV 缓存价值大；需要结构化输出、工具调用协议、可恢复的执行状态。

**离线批处理**：吞吐优先，延迟不敏感，可以用大 batch、低精度、抢占式实例。单位成本最低，但价格竞争也最激烈。

**私有化/专属实例**：客户要求数据不出域、模型独占、SLA 和审计。单价高，但销售、交付、运维成本也高；适合金融、医疗、政务、大型企业。

**边缘/端侧**：延迟极低、隐私最好、算力有限。通常用蒸馏/量化后的小模型，和云端不是同一个市场。

**推理型产品**：面向数学、代码、科研、审计等需要多步推理的场景。用户愿意为准确率付费，但思考 token 会显著拉长延迟和成本；产品要提供预算档位、折叠思考、答案保留和“预算耗尽”的明确状态。第 39 章给出了预算、流式协议和成本乘数。

**多模态产品**：面向文档 OCR、图表理解、截图问答、视频摘要。成本由图片张数、分辨率和视觉编码器决定，而不是只由文本 token 决定；产品要按“每张图 + 每个 token”定价，并提供分辨率档位。第 38 章给出了 token 预算和 EPD 比例。

分层的目的不是贴标签，而是决定“优化什么”。对话场景优化 TTFT 和缓存；代码场景优化 TPOT 和首 token；Agent 优化长上下文和工具调用；批处理优化吞吐和成本；私有化优化隔离和合规。用一套配置服务所有场景，通常在每个场景都做不到最好。

## 36.3 定价模型

推理服务的定价方式主要有五种，每种对应不同的风险分担。

**按 token 计费**：输入和输出分别定价，最常见。优点是和使用量线性相关，客户容易理解；缺点是无法覆盖固定成本，低用量客户可能不赚钱。输入和输出的成本差异很大：prefill 受算力限制，decode 受带宽限制，输出 token 通常更贵。很多 API 的输出单价比输入高几倍，就是这个原因。

**按请求计费**：适合短请求、固定价格的产品。优点是简单；缺点是长请求会亏，短请求会显得贵。通常要配合最大 token 限制。

**按订阅计费**：适合 C 端产品，成本由平均用量决定。优点是收入可预测；缺点是重度用户可能亏，需要限流或分层。

**按 GPU 小时/专属实例**：适合私有化部署和专属容量。优点是收入稳定，客户承担利用率风险；缺点是需要容量规划，闲置也要收费。

**混合计费**：基础订阅加超量按 token，或者预留容量加 burst。适合企业客户，既保证基线收入，又允许弹性。

定价还要考虑**缓存折扣**。如果前缀命中率达到 96%，同样的输入 token 的实际计算成本远低于未命中；可以把缓存命中部分打折，把节省传给客户，同时鼓励客户复用系统提示词和文档。DeepInfer 公开的数字里，缓存命中把 prefill 吞吐从每卡 6 万 token/s 提升到 150 万 token/s，这个差距就是缓存折扣的空间。

**峰谷定价**：电力、GPU 供应和流量都有峰谷。谷时电价低、GPU 空闲，可以做 off-peak 折扣，把批处理负载引导到低谷。这要求调度器能区分延迟敏感和延迟容忍的请求。

## 36.4 单位经济与毛利

第 30 章给出了单位成本公式：

```text
cost_per_mtok = C_gpu / u × 1e6 / (T × 3600)
```

其中 `C_gpu` 是 GPU 完全成本（美元/小时），`u` 是利用率，`T` 是输出 token/s。这个公式的每一个变量都可以被工程和商业手段影响。

**降低 `C_gpu`**：采购更便宜的硬件、提高折旧年限、降低电价、用竞价实例、提高机架密度。这些是采购和基础设施决策，通常空间有限。

**提高 `u`**：连续批处理、前缀缓存、自动扩缩容、多租户混部、PD 分离。利用率从 40% 提到 70%，单位成本几乎减半；这是工程能带来的最大杠杆之一。

**提高 `T`**：更好的 kernel、低精度、Wide-EP、推测解码、更大的 batch。吞吐提升直接降低单位成本，但会被 SLO 和尾延迟约束。

**提高收入**：更好的模型质量、更低的延迟、更强的工具生态、更好的客户支持。这些不直接降低成本，但能提高定价权。

`economics.py` 把这些关系写成了可执行的函数：

```python
tco = tco_breakdown(gpu_count=8, utilization=0.70)
cost = cost_per_million_tokens(tco.cost_per_effective_gpu_hour, 3000)
revenue = revenue_per_million_tokens(38.0, 3000)
margin = gross_margin(revenue, cost)
```

在一个示意场景里，8 卡、3 年 TCO 约 82 万美元，按 70% 利用率折合每有效 GPU 小时约 5.57 美元；吞吐 3000 token/s 时，每百万 token 成本约 0.52 美元。若每 GPU 小时收入 38 美元，每百万 token 收入约 3.52 美元，毛利率约 85%。这个毛利率看起来很高，但它没有扣除销售、支持、研发、带宽、存储和坏账；真实业务的毛利率通常低得多。

公开资料里的“每 GPU 小时 38 美元”是收入，不是利润。把它当成利润会严重高估商业质量。收入要减去 GPU 折旧、电力、机房、网络、存储、人力、销售、支持和研发摊销，才是毛利；再减去税费和资本成本，才是净利。

## 36.5 需求弹性与竞争

推理 API 的价格战非常激烈。模型能力接近时，客户会按价格、延迟、稳定性和生态选择；价格下降会刺激用量，但用量增长不一定能补偿单价下降。

**需求弹性**取决于场景。对话和代码补全的用量对价格敏感，价格下降会带来更多调用；企业私有化的需求对价格不那么敏感，但对合规、SLA、支持更敏感。

**竞争格局**有三类玩家。模型厂商（如 DeepSeek）可以用自己的模型和引擎做垂直整合，单位成本低；云厂商有渠道、区域和企业客户；独立推理服务商靠灵活性、专用优化和客户服务。开源框架（vLLM、SGLang）降低了进入门槛，让“自己部署”成为替代方案。

**开源的影响**是双面的。开源扩大模型的使用面，降低客户锁定；但也让推理服务更容易被商品化。DeepInfer 选择“开源计算引擎、保留 KV 存储/PD 分离/负载均衡”，就是在“扩大生态”和“保留服务差异”之间找平衡。

**护城河**通常来自四个地方：模型能力（不可替代的质量）、成本（规模、kernel、缓存）、分发（云区域、企业销售）、数据与工作流（Agent 的记忆、工具、评测）。单纯的“推理快 20%”很难成为长期护城河，因为它会被追上；但“快 20% + 稳定 + 便宜 + 合规 + 工具生态”可以。

## 36.6 产品化路线图

一个推理产品通常经历四个阶段。

**第一阶段：API 可用。** 提供 OpenAI 兼容的补全和对话接口，支持流式、停止条件、基本采样参数。目标是“能被现有客户端接入”，而不是“性能最好”。

**第二阶段：SLA 与可观测。** 定义 TTFT/TPOT/错误率目标，提供状态页、指标、告警、配额和计费。目标是“客户敢把生产流量放进来”。

**第三阶段：企业能力。** 私有化/专属实例、VPC、审计、SSO、数据驻留、内容审核、工具调用、结构化输出。目标是“能通过企业采购和安全评审”。

**第四阶段：平台化。** 多模型、多区域、微调、评测、Agent 运行时、缓存和工作流。目标是“客户不只是买 token，而是买一整套能力”。

每个阶段的门槛不同。第一阶段靠工程；第二阶段靠运维和 SLO；第三阶段靠合规、销售和支持；第四阶段靠生态和产品设计。很多团队在第一阶段就卡住，因为“能跑 demo”和“能接生产”之间隔着可观测性、配额、故障恢复和计费。

## 36.7 商业模式

**托管 API**：按 token 或订阅收费，客户不运维。适合中小客户和开发者；需要规模效应和全球/区域覆盖。

**专属实例**：给客户独占的 GPU 或实例池，按月/年收费。适合对隔离、性能、合规有要求的企业；需要容量规划和 SLA。

**私有化部署**：把软件和模型部署到客户机房，收许可费、实施费、维保费。适合金融、医疗、政务；交付成本高，但客户粘性强。

**混合云**：基线在客户机房，峰值 burst 到云；KV 缓存和模型权重跨环境同步。适合流量波动大的企业；技术复杂度高。

**开源 + 商业支持**：开源核心，卖支持、托管、企业插件。适合建立生态；需要社区运营和清晰的许可边界。

**硬件捆绑**：和 GPU/NPU 厂商合作，卖“硬件 + 推理栈”的一体化方案。适合国产算力和专用芯片；需要深度适配和渠道。

没有一种模式适合所有团队。选择取决于客户类型、团队能力、资本和竞争。一个常见的错误是“用托管 API 的价格卖私有化”，或者“用私有化的成本做 API”，两者都会亏。

## 36.8 销售、支持与隐性成本

推理服务的成本不只在 GPU。还有几项容易被低估。

**销售成本**：企业客户的采购周期长，需要售前、方案、POC、合同、合规审查。一个企业订单的销售成本可能是几万到几十万美元。

**支持成本**：7×24 on-call、故障响应、容量咨询、模型调优。SLA 越高，支持成本越高；99.9% 和 99.99% 的成本差可能是指数级的。

**合规成本**：等保、ISO、SOC 2、数据驻留、审计、渗透测试。这些是一次性和持续性的投入，不能用“技术很好”替代。

**坏账与欺诈**：按量计费会遇到盗刷、恶意调用、欠费。需要配额、风控、预付或信用额度。

**研发摊销**：自研推理引擎的研发成本通常是几百万美元级，摊到每 token 上取决于规模。小规模自研很难回本。

把这些成本加进去，很多“毛利率 80%”的模型会变成“毛利率 30%”甚至更低。产品化决策要用完全成本，而不是只算 GPU。

## 36.9 市场与生态

推理市场的增长来自三个方向：模型能力提升带来的新场景、推理成本下降带来的用量增长、Agent/多模态带来的长上下文和多轮调用。

**模型厂商**希望自己的模型被更多框架支持，扩大使用面；**硬件厂商**希望框架用自己的 kernel 和库；**云厂商**希望推理跑在自己的实例上；**企业**希望稳定、合规、可支持。这四方的利益不完全一致，开源框架是博弈的焦点。

DeepInfer 的开源策略可以看成“用引擎开源换模型生态”：第三方部署 DeepSeek 模型时，行为更接近官方 API，集成成本更低；DeepSeek 保留 KV 存储、PD 分离和负载均衡，维持服务质量的差异。这个策略能否成功，取决于社区是否愿意围绕一个“只支持一个模型”的框架贡献，以及 DeepSeek 是否持续开放更多组件。

从长期看，推理会像数据库一样分层：底层是硬件和 kernel，中间是引擎和调度，上层是协议、工具和行业解决方案。单纯卖“更快的 kernel”会越来越难，卖“场景 + 工作流 + 合规 + 服务”会更持久。

## 36.10 一个可复算的商业案例

假设一个团队要做一个面向企业的 Agent API，目标客户是 100 家中型企业，每家每月 10 亿输入 token、2 亿输出 token。这个量级下，先算容量，再算收入和获客成本，三者必须能对上。

先算 GPU。2 亿输出 token/月，按 30 天算，平均输出速率是 `200e6 / (30 × 86400) ≈ 77 token/s`；100 家就是 7,716 token/s。第 30 章的 3000 输出 token/s 是 100% 利用率口径，按 70% 实际利用率，平均需要 `7,716 / (3000 × 0.7) ≈ 3.7` 张 GPU；考虑峰值是均值的 3 倍、再留 30% 余量，约 14.3 张物理 GPU。成本用 nominal 口径：`14.3 × 730 × 3.90 ≈ 4.07 万美元/月`；或者用有效单价 5.57 美元乘“有效 GPU 小时”，结果一样。不要用 5.57 再乘 10 张物理卡，也不要用 3.90 乘 3.7 张有效卡：把“有效单价”和“物理卡数”混在一起，会把利用率算两遍。

再算并发和 KV。假设峰值 QPS 是 20、平均停留 30 秒，并发约 600；按 34K 上下文、890 字节/token 算，主 KV 约 `600 × 34,000 × 890 ≈ 18.2 GB`（约 16.9 GiB），加 25% 冗余约 21 GiB。这个数字只算主 KV，实际还要加 SWA、indexer 和副本；如果 14 张卡每张只有 40 GiB 可用，KV 不是瓶颈，GPU 算力才是。

再算收入。假设输入 0.5 美元/百万 token、输出 3 美元/百万 token，每家每月收入 `1000 × 0.5 + 200 × 3 = 1,100` 美元；100 家约 11 万美元/月。GPU 成本 4.07 万美元；按 GPU 成本的 20% 到 30% 计存储、网络、人力和支持，总成本约 4.9 到 5.3 万美元，毛利率约 52% 到 55%（取 54%）。如果把销售、市场和研发摊销也算进去，毛利率会低不少。这个毛利率看起来可以，但还没算获客成本：如果每个企业客户的 CAC 是 2 万美元，而每客户每月毛利约 590 美元，回收期约 34 个月，仍然远长于 12 到 18 个月的常见阈值，生意并不轻松。要么把单价提高到 3000 美元/月以上，要么走自助获客把 CAC 降到几千美元，要么靠规模摊薄支持成本。

这里有一个和第 47.3 节的口径差异，需要主动对齐。36.10 的 54% 是“收入减去 GPU、存储、网络后的产品毛利”，还没有扣客户成功、支持和一部分运维；47.3 用的 55% 是再扣这些半可变成本后的**贡献毛利**，两者在这个案例里接近，但含义不同。做获客决策时应该用更保守的贡献毛利：如果支持成本把贡献毛利压到 50%，每客户每月贡献约 550 美元，CAC 回收期约 36 个月。把产品毛利当成最终毛利，会系统性高估 LTV、低估回收期，进而高估增长的健康度。

这个案例说明：低价 Agent API 的毛利很薄，必须靠规模、缓存和自动化支持；企业市场则要用更高的单价覆盖 CAC、SLA 和合规成本。两个市场不能用同一套定价和成本模型。

`examples/tco.py` 可以复算这些数字：

```bash
python examples/tco.py
```

它输出 TCO 分解、每百万 token 成本、收入、毛利率、敏感性分析、容量规划和 P/D 配比。把里面的假设换成你的价格、电价、利用率和吞吐，就能得到自己的模型。敏感性分析通常显示：吞吐和利用率对成本的影响远大于电价；这就是为什么工程优化比“谈电价”更值得投入。

## 36.11 风险与反脆弱

推理产品的风险来自五个方向。

**商品化**：开源框架和模型能力扩散，让“推理”本身越来越像水电，单价持续下降。应对是向上走：工具、工作流、数据、合规、行业解决方案。

**价格战**：大厂可以用模型或云的收入补贴推理，独立服务商很难跟。应对是聚焦细分场景，做差异化，而不是拼单价。

**监管**：数据驻留、内容审核、模型备案、出口管制会增加成本和进入门槛。应对是提前做合规，把合规变成卖点。

**供应链**：GPU 供应、云区域、网络、电力都可能中断。应对是多供应商、多区域、预留容量和降级方案。

**技术路线变化**：线性注意力、新记忆结构、端侧推理可能改变成本结构。应对是保持架构可替换，不要把全部赌注压在一个模型或一种硬件上。

反脆弱的做法不是“预测唯一未来”，而是“在多种情景下都能活”。第 50 章会给出三种情景：渐进优化、架构重构、端侧/专用芯片崛起。产品架构应该让这三种情景下的迁移成本都可控。财务上的反脆弱同样重要：第 47 章会给出 NPV、LTV/CAC、承诺合同和情景分析，用来说明“在需求下降或价格战时，什么结构还能活下来”。

## 小结

推理产品化是把技术指标翻译成用户价值、把单位成本翻译成价格和毛利、把工程能力翻译成 SLA 和合规。客户分层决定优化目标；定价模型决定风险分担；单位经济决定生死；销售、支持、合规和研发摊销决定真实毛利；开源与闭源决定生态和护城河。DeepInfer 的“开源引擎、保留基础设施”是一个典型的垂直整合策略，但它不是唯一答案。最终，推理会像数据库一样分层，单纯卖算力会商品化，卖场景、工作流和服务才有长期空间。
