# 附录 J 生产故障排查手册

本附录按“症状”组织，而不是按“模块”组织。线上出问题时，你通常先看到一个现象：TTFT 变慢、TPOT 抖动、吞吐下降、OOM、输出不一致、缓存命中率掉了。下面每个症状给出可能原因、快速检查、深入定位和修复方向。它不是万能手册，但能让你在压力下按顺序排除，而不是一上来就怀疑模型或 kernel。

## J.1 先做三件事

第一，确认影响面：是所有请求、某个模型、某个租户、某个区域，还是某类长度？影响面决定你是先回滚、先扩容，还是先修一个局部 bug。

第二，确认时间线：最后一次变更是什么时候？模型、权重、配置、镜像、驱动、网络策略、流量结构，任何一项变化都可能和故障同时发生。没有变更记录时，先看部署系统和 feature flag 的审计日志。

第三，确认指标口径：TTFT 是均值还是 P99？吞吐是输出 token 还是总 token？KV 占用是“驻留块”还是“可分配块”？很多“故障”其实是两个面板用了不同口径。

## J.2 TTFT 高

**先看排队。** waiting 队列是否变长、队头等待时间是否上升？如果是，问题在 prefill 容量或调度，不在 decode。检查 prefill 实例数、`max_num_batched_tokens`、chunked prefill 的 chunk 大小、长请求占比。

**再看缓存。** 前缀缓存命中率是否下降？3FS/对象存储的读延迟、元数据查询、GC 是否异常？缓存命中率下降会让非缓存 token 数突然上升，TTFT 可能翻几倍。检查 `cache_hits`、`cache_misses`、取回 P99、3FS 带宽。

**再看 prefill 本身。** 单步 prefill 时间是否上升？看 chunk 的 `seqlen_q × seqlen_k` 是否变大、是否有超长 prompt 混入短请求池、CP all-gather 是否变慢、kernel 是否退化（驱动/编译缓存变化）。

**最后看首 token 的采样和协议。** 结构化输出的 mask 是否变慢？tokenizer/chat template 是否在处理超长输入？SSE 的第一个 chunk 是否被网关缓冲？有时 TTFT 的“慢”发生在模型之外。

修复方向：按长度分池、限制单请求最大 token、提高 prefill 配额、预热缓存、把长 prompt 路由到专用池、给网关关闭响应缓冲。

## J.3 TPOT 抖动或变慢

**先看 batch 组成。** decode batch 是否突然变大？是否有长输出请求占住 running 槽位？LCFS 会优先长输出，短请求的 TPOT 可能被拖慢。检查 running 数、输出长度分布、抢占次数。

**再看 KV。** 平均上下文是否增长？KV 读取量随上下文线性增长，TPOT 会跟着上升。检查每请求 KV 长度、KV 占用、是否有换入换出、是否有 COW 峰值。

**再看通信。** EP 的 all-to-all 是否变慢？`moe_lb` 是否变差？网络是否拥塞？decode 一步只有几毫秒，all-to-all 的尾延迟会直接反映到 TPOT。

**最后看 CPU。** 调度、结构化 mask、采样是否成为瓶颈？如果 CPU 时间超过 GPU 时间，ZOS 也藏不住；看 CPU 利用率、Python GIL、grammar 编译缓存命中率。

修复方向：限制单 batch 的 KV 总量、按输出长度分池、调整 LCFS/抢占策略、优化 all-to-all 拓扑、把 mask 移到 GPU、减少每步的 Python 对象分配。

## J.4 吞吐下降、goodput 低

**区分“忙”和“有用”。** GPU 利用率高但 goodput 低，说明系统在跑无效或超时请求。检查错误率、重试率、超时率、SLO 达标率，而不是只看 tokens/s。

**看请求组成。** 是否有大量短请求被长请求阻塞？是否有大量重试放大流量？是否有客户端超时后重试，导致同一请求被算多次？

**看资源。** KV 是否接近上限、是否频繁抢占、是否触发换出？抢占和重算会消耗额外 prefill，降低有效吞吐。检查 `preemptions`、重算 token 数、前缀命中率。

**看并行。** EP/CP 是否负载不均？是否有 rank 在等最慢的 rank？检查 `moe_lb`、all-to-all P99、每 rank 的 token 数。

修复方向：准入控制、按优先级排队、限制重试预算、扩容 prefill 或 decode、调整 EP/EPLB、减少长请求对短请求的阻塞。

## J.5 OOM 与抢占

**先确认是哪种 OOM。** 权重加载 OOM、KV 分配 OOM、激活峰值 OOM、CUDA Graph/workspace OOM、主机内存 OOM，处理方式不同。看错误栈和分配位置，不要只看“CUDA out of memory”。

**KV OOM 的常见原因。** 并发或上下文超过预算、block 碎片、缓存块没有及时淘汰、state slot 不足、推测解码预留不够。检查 `num_free_blocks`（可分配）和 `num_resident_blocks`（驻留），两者可能差很多。

**激活 OOM 的常见原因。** chunk 太大、attention 分数矩阵被 materialize、batch 太大、多模态 patch 太多。检查 prefill chunk、是否用了 FlashAttention、图像分辨率。

**抢占是不是策略问题。** 如果 `stop_preempted_request=true`，被抢占的请求会直接失败；如果是 false，会重算，可能引发重算风暴。检查抢占原因、重算次数、前缀命中率。

修复方向：降低 `max_num_seqs` 或 chunk、增加 block 数、缩短 TTL、限制单请求上下文、把缓存换出到主机/3FS、调整抢占策略。

## J.6 输出不一致、重复或乱码

**先确认是不是非确定性。** 同一 seed、同一 batch 组成、同一硬件，输出是否一致？如果只在换 batch 后不一致，查 batch invariance；如果换 seed 后不一致，是正常随机性。

**查 tokenizer 和模板。** 词表、特殊 token、BOS/EOS、chat template 版本是否和模型匹配？模板变化会让同一段文本编码成不同 token，输出自然不同。检查 manifest fingerprint 和模板哈希。

**查 KV 和缓存。** 前缀缓存是否复用了错误的块？哈希碰撞、COW 复制错误、块淘汰后仍被引用，都会让 attention 读到脏数据。检查缓存命中日志、块内容校验、COW 路径。

**查流式解码。** 输出乱码或替换字符，通常是 UTF-8 边界处理错误；输出重复，可能是 delta 和累计文本混用、重试重复发送、stop holdback 释放过早。检查流式解析器和网关的缓冲。

**查采样。** 温度、top-k/top-p、重复惩罚、logit bias 是否按请求应用？是否把 batch 的统计混在一起？检查采样参数的生命周期和 RNG 流。

修复方向：固定 seed 和 batch 组成复现、校验 manifest、关闭前缀缓存对比、修 UTF-8 缓冲、统一 delta 语义、按序列隔离采样参数。

## J.7 缓存命中率下降

**先看流量。** 是否有大量新前缀（新系统提示词、新文档、新租户）？命中率是流量结构的函数，不完全是缓存系统的指标。

**再看 TTL 和容量。** 缓存是否被提前淘汰？TTL 是否被调短？存储是否满了、GC 是否过于激进？检查 `evictions`、`cached_blocks`、存储使用率。

**再看 key。** 模型、tokenizer、模板、预处理配置、租户命名空间是否变了？任何一项变化都会让旧缓存全部 miss。检查 manifest fingerprint 和缓存命名空间。

**再看路由。** 请求是否被送到没有缓存的实例？共享 3FS 可以缓解，但本地缓存和跨机取回的命中口径不同。检查前缀亲和路由和 3FS 读延迟。

修复方向：预热高频前缀、延长 TTL、扩大缓存、统一 key 命名空间、按前缀亲和路由、把热点前缀复制到多个实例。

## J.8 结构化输出失败或卡死

**失败还是慢？** `finish_reason=structured_output` 表示文法无法继续，通常是 schema 与模型输出冲突、mask 全空、trigger 未出现。慢则是 mask 计算或编译缓存的问题。

**查 schema。** 是否有 `$ref`、递归、复杂 `oneOf`、不支持的关键字？编译是否报错？缓存是否命中？检查 schema 大小、嵌套深度、编译时间。

**查 tokenizer。** mask 是按 token 字节串算的，tokenizer 版本变化会让 mask 错位。检查词表 fingerprint 和特殊 token。

**查推测解码。** 拒绝 draft 后 grammar 状态是否回滚？stop token 是否让提交长度短于验证长度？检查 matcher 的 snapshot/restore 和提交顺序。

**查缓存 DoS。** 大量不同 schema 是否把编译缓存打满？是否设置了字节上限？检查缓存大小、编译排队、CPU 利用率。

修复方向：限制 schema 复杂度、预热编译缓存、关闭推测解码对比、修回滚逻辑、设置缓存上限。

## J.9 SSE 卡住、断连或重复

**看终止顺序。** 最后一个 chunk 是否带 `finish_reason` 和 usage，再发 `[DONE]`？如果先发 `[DONE]`，客户端可能提前关闭。

**看缓冲。** 网关、反向代理、CDN 是否缓冲了 `text/event-stream`？是否设置了 `X-Accel-Buffering: no` 或等价配置？

**看背压。** 客户端读得慢，服务端队列是否无界增长？是否阻塞了生成线程？检查队列长度、写超时、连接数。

**看连接生命周期。** HTTP/1.0 还是 1.1？是否设置了 `Content-Length`？流结束后是否关闭连接？客户端是否能感知 EOF？

修复方向：固定终止协议、关闭代理缓冲、用有界队列和写超时、正确处理客户端断开、给流式请求单独的超时。

## J.10 PD 交接失败

**看预留。** D 实例是否在传输前预留了足够的 KV 页和 state slot？如果先传后等，失败会浪费带宽并阻塞 P。

**看描述符。** 模型 fingerprint、KV 格式、block table、token 数、dtype/layout 是否匹配？不匹配时应该拒绝，而不是“尽力解码”。

**看传输。** RDMA/GDR 是否超时？是否有分块、校验、重试？同一个 transfer id 重传是否幂等？

**看所有权。** D 是否在收到并校验后才 ACK？P 是否在 ACK 后才释放源 KV？如果顺序反了，失败时两边都没有完整 KV。

**看故障恢复。** P 挂、D 挂、网络分区时，请求能否回退或重试？是否有超时和幂等键？

修复方向：先预留再传输、校验后再切换所有权、幂等 transfer id、超时回退、监控交接成功率与 P99。

## J.11 EPLB 与 EP 负载不均

**看 `moe_lb` 的时间序列。** 是持续偏高，还是周期性尖峰？持续偏高说明放置或副本不足；尖峰说明路由分布突变或重平衡太慢。

**看热点专家。** 是某几个专家持续热，还是随机波动？持续热可能需要更多副本或调整路由；随机波动可能是 batch 太小、统计窗口太短。

**看重平衡。** 重平衡是否在流量高峰触发？是否会搬运大量权重、影响推理？是否有双缓冲？

**看拓扑。** EP 越大，all-to-all 的尾延迟越明显；`moe_lb` 好看不代表端到端快。检查 all-to-all P99 和每 rank 的 token 数。

修复方向：增加冗余专家、调整统计窗口和重平衡间隔、在低峰搬运、优化 all-to-all 拓扑、限制单 rank 的专家数。

## J.12 指标口径错误

**KV 占用。** `kv_cache_bytes` 是预分配上限；`kv_cache_used_bytes` 是物理驻留（含未引用的缓存块）；`free_blocks` 是可分配（缓存块可被淘汰）。三个数回答不同问题，不能互相替代。

**吞吐。** 输出 token/s、总 token/s、请求/s 是三个口径；缓存命中的输入 token 算不算“处理量”要看业务定义。报告时要写清楚。

**延迟。** 均值会被短请求拉低，P99 才能反映尾延迟；TTFT 含不含排队、含不含网关，两个面板可能不同。

**错误率。** 客户端取消、超时、限流是否算错误？不同口径会让“可用性”差几个 9。

修复方向：统一指标字典、在仪表盘标注口径、用同一套采集和聚合、对关键指标做对账。

## J.13 一组可直接执行的检查

在 mini-deepinfer 里，可以先跑这三条确认基础状态：

```bash
python -m pytest -q
python examples/lifecycle.py
python check_docs.py
```

生产环境没有这套脚本时，按下面的顺序采集：`/health`、`/metrics`、waiting/running 队列长度、TTFT/TPOT 分位数、KV 驻留与可分配块、前缀命中率、抢占次数、`moe_lb`、all-to-all P99、3FS 读带宽、GPU/NPU 利用率和显存、CPU 利用率和 GIL 竞争、最近变更记录。

采集时尽量用同一时间窗口和同一口径。不要用“平均值 + 峰值 + 上周的截图”拼一张图；排障需要的是同一时刻的横截面和一段时间的变化趋势。

## J.14 事故记录模板

一次事故结束后，至少记录：时间线和影响面；直接原因和根本原因；为什么监控没有更早发现；为什么现有测试/演练没有覆盖；临时修复和长期修复；回滚/降级是否有效；需要补的监控、测试、文档和 runbook；负责人和截止时间。不要把“根因是某个 bug”当成结论；要问“为什么这个 bug 能进入生产、为什么没有被测试抓住、为什么发现得这么晚”。

## 小结

排障的顺序是“影响面 → 时间线 → 口径 → 分层定位”。TTFT 先看排队和缓存，TPOT 先看 batch 和 KV，吞吐先看 goodput 和重试，OOM 先分权重/KV/激活，输出问题先分确定性/tokenizer/缓存/流式，缓存命中率先看流量和 key，结构化输出先分失败/慢/回滚，SSE 先看终止和缓冲，PD 先看预留/描述符/所有权，EPLB 先看时间序列和拓扑。大多数“推理故障”不是数学错误，而是资源生命周期、口径和协议边界的问题。
