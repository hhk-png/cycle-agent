# 第 4 章 推理系统的性能模型

本章导读：用一组可手算的公式，把“模型多大、上下文多长、batch 多大、硬件多快”连起来。本书统一按 1K=1024 个 token、1M=1024K 计上下文长度；容量同时给出十进制 MB/GB 和二进制 MiB/GiB，避免把“117 MB”和“111 MiB”当成两个不同的数。你会得到 prefill/decode 的 FLOPs、KV 字节数、算术强度、TTFT/TPOT、推测解码加速比和成本下界。这些公式不追求精确到百分点，但足以判断瓶颈在哪，以及一个优化值不值得做。

## 4.1 参数、FLOPs 与显存

先定义一个简化的 Transformer：`L` 层，隐藏维度 `d`，FFN 中间维度 `f`，词表 `V`，注意力头数 `H`，KV 头数 `H_kv`，head 维度 `d_h`，其中 `d = H × d_h`。

**参数量的粗略分解**：

- token embedding：`V × d`；
- 每层 attention 的 Q/K/V/O 投影：约 `4 × d^2`（GQA 时 K/V 更小）；
- 每层 FFN：约 `3 × d × f`（SwiGLU 有三个矩阵）；
- MoE 层：路由专家参数量是 `n_experts × 3 × d × f`，但每个 token 只激活 top-k 个；共享专家始终激活。

**prefill 的 FLOPs**：处理 `T` 个 prompt token，线性层约 `2 × N_active × T`（一次乘加算 2 FLOPs）。注意力部分，完整 causal attention 如果不利用下三角稀疏，是每层约 `4 × T^2 × d`；只算下三角时约一半，即 `2 × T^2 × d`。本书统一用 causal 的实际计算量，所以：

```text
FLOPs_prefill ≈ 2 × N_active × T + 2 × L × T^2 × d
```

第一项随 T 线性增长，第二项随 T 平方增长。短 prompt 时线性层主导，长上下文时注意力主导。MLA/CSA2/SWA 会显著降低第二项的系数，这也是长上下文优化的核心。

**decode 的 FLOPs**：每步只处理 1 个 query，线性层约 `2 × N_active`。注意力部分，QK 点积要对 T 个 key 各做一次长度为 d 的乘加，得到 `2 × T × d` FLOPs；PV 加权求和再要 `2 × T × d`，所以每层是 `4 × T × d`。注意这里没有 causal 的对折：decode 的单个 query 能看到全部历史 key。因此：

```text
FLOPs_decode_per_token ≈ 2 × N_active + 4 × L × T × d
```

**KV cache 字节数**：每层每个 token 存 K 和 V，各 `H_kv × d_h` 个元素：

```text
KV_bytes_per_token = 2 × L × H_kv × d_h × bytes_per_element
```

如果使用 MLA/压缩 KV，公式要换成压缩后的维度；DeepSeek-V4.1-Flash 公开的 890 字节/token 是压缩、低精度和 SWA 共同作用后的结果，不能直接用上面的稠密公式算。

**激活与临时张量**：除了权重和 KV，prefill 还要为 `T × d` 的激活、attention 的 `T × T` 分数、FFN 的中间张量留空间。chunked prefill 的一个副作用就是把 `T` 变小，从而降低峰值激活。第 18 章会解释为什么 FlashAttention 的 tiling 能把这部分从显存移到 SRAM。

## 4.2 算术强度与 roofline

算术强度是 FLOPs 除以搬运字节数。对 decode 的线性层，每个权重元素被读一次、参与一次乘加（2 FLOPs），所以 FP16 权重（2 字节）的强度约 1 FLOP/byte，FP8 权重（1 字节）约 2 FLOP/byte。而现代 GPU 的算力/带宽比通常在几百 FLOP/byte 量级。这意味着 decode 的线性层几乎必然受带宽限制。

举一个数量级例子。假设某 GPU 的 FP16 算力为 1000 TFLOPS，HBM 带宽为 3 TB/s，ridge point 是 `1000e12 / 3e12 ≈ 333 FLOP/byte`。一个 7B 模型 decode 一个 token，线性层约 14 GFLOP，FP16 权重的强度约 1 FLOP/byte，远低于 333，所以时间是 `14 GB / 3 TB/s ≈ 4.7 ms` 量级，而不是 `14 GFLOP / 1000 TFLOPS ≈ 0.014 ms`。这就是为什么 decode 的优化重点是减少权重量、提高 batch、把多个请求的矩阵乘拼在一起。

prefill 则相反。换一个 7B 稠密模型（32 层、`d=4096`）做例子：一个 32K token 的 prompt，线性层 FLOPs 是 `2 × 7e9 × 32768 ≈ 4.6e14`，causal 注意力部分约 `2 × 32 × 32768^2 × 4096 ≈ 2.8e14`，总算力约 7.4e14 FLOP，算术强度高，受算力限制。这里换成 32 层、4096 维，是为了让两项都好算；它和前面 16B 激活参数的例子不是同一个模型，不要把参数混在一起。把 prefill 和 decode 分开部署，就是为了让两种负载各自跑到自己的 roofline 附近。

`examples/roofline.py` 把这三个例子算成了可执行的数字。在一个 1000 TFLOPS、3 TB/s 的示意设备上，它的输出是：8192³ 的 FP8 GEMM 算术强度 4096，受算力限制；16B 激活参数的 decode 算术强度 2，受带宽限制，光读权重就要 5.33 ms；32K 注意力的 Flash 版本受算力限制（约 17.6 ms），而把分数矩阵写回 HBM 的朴素版本变成受带宽限制，访存时间约 46.5 ms，端到端由 17.6 ms 变成 46.5 ms，差约 28.9 ms。这个对比就是“融合”为什么能改变瓶颈的直接证据。

## 4.3 TTFT、TPOT 与排队

设请求到达后排队时间为 `W`，prefill 时间为 `T_p`，decode 每步时间为 `T_d`，输出 `N` 个 token，则：

```text
TTFT ≈ W + T_p + T_d
E2E ≈ W + T_p + N × T_d = TTFT + (N - 1) × T_d
TPOT ≈ T_d
```

这里的 `T_d` 是第一步 decode 的耗时，已经包含在 TTFT 里。所以 `E2E` 要把首 token 的 `T_d` 补回来：`TTFT + (N-1) × T_d`，等价于 `W + T_p + N × T_d`。当 `N=1` 时，`E2E = TTFT`，不会出现“端到端比首 token 还短”的矛盾。

实际上 decode 每步时间会随上下文长度增长（注意力部分），也会随 batch 变化（batch 越大，单步越慢，但总吞吐越高）。所以 TPOT 是一个平均值，尾延迟要看 P95/P99。

**排队**是 TTFT 里最容易被低估的部分。设到达率为 `λ`，服务率为 `μ`，系统利用率 `ρ = λ / μ`。在简单的 M/M/1 近似下，平均排队时间约为 `ρ / (μ (1 - ρ))`。当 `ρ` 从 0.7 升到 0.9 时，排队时间会从约 `2.3 / μ` 升到 `9 / μ`，接近 4 倍。这就是为什么“把 GPU 利用率拉到 100%”通常会毁掉尾延迟；容量规划要留出冗余。

**Little 定律**把并发、到达率和停留时间联系起来：`并发数 = 到达率 × 平均停留时间`。如果服务每秒到达 100 个请求，平均每个请求停留 2 秒，系统里平均有 200 个请求在跑。这个数字决定了需要多少 KV cache 和多少 decode 容量。

**goodput** 是在 SLO 内完成的请求吞吐。假设 SLO 是 TTFT ≤ 500 ms、TPOT ≤ 50 ms，那么超过这个窗口的请求即使算出了 token，也不算 goodput。容量规划应该用 goodput，而不是峰值 tokens/s。

## 4.4 batch 的双刃剑

设单请求 decode 一步耗时 `t(1)`，batch 为 `B` 时一步耗时 `t(B)`。总吞吐是 `B / t(B)`。如果 `t(B)` 增长得比 `B` 慢，吞吐上升；当 `t(B)` 线性增长时，吞吐饱和；如果显存或带宽竞争导致 `t(B)` 超线性增长，吞吐反而下降。

一个常用的近似是：

```text
t(B) ≈ max(t_mem(B), t_compute(B))
t_mem(B) ≈ (W + B × KV_read) / BW
t_compute(B) ≈ 2 × N_active × B / P
```

其中 `W` 是权重字节数，`KV_read` 是每请求每步读的 KV 字节。小 batch 时 `W` 主导，增大 B 几乎不增加时间，吞吐近似线性上升；大 batch 时 KV 和计算项主导，吞吐趋于饱和。最优 batch 是这两条曲线的交点附近，再叠加 SLO 约束。

把公式改写一下，可以得到“权重摊销”的收益：

```text
t(1) ≈ (W + KV_read) / BW
t(B) ≈ (W + B × KV_read) / BW

speedup(B) = B × t(1) / t(B)
           = B × (W + KV_read) / (W + B × KV_read)
           = B × (1 + KV_read / W) / (1 + B × KV_read / W)
```

这个形式在 `B=1` 时正好等于 1，不会出现“batch 为 1 反而变慢”的假象。当 `B × KV_read << W` 时，加速比接近 B；当 `B × KV_read >> W` 时，加速比饱和到 `1 + W / KV_read`。这解释了为什么短上下文、小模型的 batching 收益高，而长上下文、大 KV 的 batching 很快碰到天花板。

DeepInfer 的 decode 选择 Wide-EP，是为了把 MoE 专家的权重分散到更多 GPU，降低单卡每步要读的权重字节数，从而把 `t_mem` 压下来。代价是 all-to-all 通信和负载不均衡。

## 4.5 推测解码的加速比

设 draft 模型一次提议 `k` 个 token，第 `i` 个 draft 的累计接受概率为 `c_i`（即前 `i` 个都被接受的概率）。目标模型一次验证的期望接受 token 数是：

```text
E = 1 + c_1 + c_2 + ... + c_k
```

这里的 `1` 是目标模型自己采样的那个 token。设目标模型一步成本为 1，draft 模型每 token 的相对成本为 `r`，则一次推测 step 的成本约 `1 + k × r`，相对“每步 1 个 token”的加速比是：

```text
speedup ≈ E / (1 + k × r)
```

如果 `c_i` 快速衰减，增大 `k` 只会增加验证成本，不会增加接受长度。DSpark 的 confidence-scheduled verification 就是在每个请求、每个位置上估计 `c_i`，只验证边际收益最高的前缀。官方数据中，动态验证把每步验证的 draft 数从固定 5 降到 3.2 到 4.4，平均接受长度基本不变（3.29 对 3.20），在生产工作点带来 4% 到 7% 的吞吐提升。

这个公式也解释了为什么推测解码在低并发时收益小：`r` 相对固定，但目标模型一步的 batch 很小，draft 的固定开销占比高；高并发时目标模型一步已经很满，多验证几个 token 的边际成本低，收益才明显。

用 `examples/roofline.py` 里的例子：每个位置的独立接受概率是 `a = [0.9, 0.8, 0.7, 0.6, 0.5]`，对应的累计接受概率 `c_i` 依次是 0.9、0.72、0.504、0.3024、0.1512；`r = 0.1` 时，期望接受长度是 3.578，加速比约 2.385。如果只看“接受率 50%”就以为收益只有 1.5 倍，会低估累计接受的贡献；反过来，如果接受概率衰减到 0.2 以下，继续加长 draft 只会浪费验证算力。

## 4.6 量化与 KV 压缩的收益

把权重从 FP16 降到 FP8，权重字节数减半，decode 的带宽时间近似减半；降到 FP4，再减半。但量化会引入 scale、反量化和精度损失，实际收益取决于 kernel 是否能融合反量化、是否有足够的 batch 掩盖开销。

KV cache 的收益更直接：每 token 字节数减半，同样显存能放两倍并发，或者同样并发能支持两倍上下文。DeepSeek-V4.1-Flash 的 890 字节/token 相比稠密 FP16 KV 小了一个数量级以上，这是它能把 1M 上下文和长 TTL 缓存做成生产服务的关键。

但 KV 压缩不是免费的。压缩/解压需要 kernel，索引器需要额外的计算和存储，低精度可能影响长上下文召回。评估时要同时看质量、吞吐和显存，不能只看字节数。

一个常见的误区是“权重越小，端到端一定越快”。decode 的总时间里，attention、KV 读取、all-to-all、采样和调度都占时间；权重只占其中一部分。如果权重从 16 GB 降到 8 GB，但 attention 的 KV 读取仍是 10 GB，总流量从 26 GB 降到 18 GB，端到端最多快约 31%（`1 - 18/26`），不会翻倍。优化要看 Amdahl 定律，而不是只看单项。

## 4.7 一个可手算的例子

假设一个 40 层、`d=5120`、`H_kv=1`、`d_h=128`、FP8 KV 的模型，每 token 的稠密 KV 约 `2 × 40 × 1 × 128 × 1 = 10240` 字节，即 10 KB。若用 4-bit 压缩、每 16 个值一个 scale，再叠加 SWA 和 indexer 的取舍，公开资料给出的全局 footprint 约为 890 字节/token，约为稠密 FP8 的 8.7%。128K 上下文单序列约 117 MB（约 111 MiB）；1000 条并发约 117 GB。这个数字决定了 decode 集群的显存下限和 KV 存储的容量。

再看算力：如果 active 参数 16B，decode 每 token 线性层约 32 GFLOP；在 1000 TFLOPS 的 GPU 上，算力时间 0.032 ms，但读 16B 参数的 FP8 权重需要 16 GB / 3 TB/s ≈ 5.3 ms。差距两个数量级，说明 decode 的瓶颈在带宽，不在峰值算力。所有的 batching、EP、量化，都是围绕这个差距做文章。

如果把 batch 提到 64，权重读取被 64 行摊薄，带宽时间仍是 5.3 ms，但总算力时间变成 `64 × 0.032 = 2.05 ms`，仍然小于带宽时间；再提到 256，算力时间 8.2 ms，超过带宽时间，瓶颈开始转向计算。这个交点就是该模型在该硬件上的“自然 batch”。实际系统还会被 KV 读取和 SLO 拉低。

## 4.8 一张可复用的估算表

做容量规划时，可以按下面的顺序填表。每一项都写下假设，不要只写结果。

1. 模型：层数、hidden、KV 头数、head 维度、激活参数量、精度。
2. 单 token KV 字节：用 4.1 的公式，或公开的压缩后数字。
3. 单请求平均上下文：prompt + 输出的一半。
4. 并发：Little 定律，`QPS × 平均停留时间`。
5. KV 总量：单 token 字节 × 单请求上下文 × 并发。
6. 单步权重流量：激活参数 × 权重字节。
7. 单步 KV 流量：并发 × 单请求上下文 × 单 token KV 字节。
8. 单步时间：`max((权重 + KV 流量) / 带宽, (2 × 激活参数 × batch + 4 × 层数 × 上下文 × hidden × batch) / 算力)`。第二项里的 attention 部分在长上下文、大 batch 时不能忽略。
9. 输出吞吐：`batch / 单步时间`。
10. 单位成本：GPU 小时成本 / 输出吞吐。

这套表不要求精确，但能让你在写代码之前就知道“瓶颈是权重、KV 还是算力”，从而决定先做哪项优化。第 18 章会把每一项对应到具体的 kernel 和硬件资源。

## 4.9 把公开数字代入手算

用公开的生产数字做一次反向验算，可以检验前面的公式是否讲得通。已知平均输入约 77K token、TTFT 约 400 毫秒、缓存命中率约 96%、decode 约 230 token/s、公开口径的单个服务集群每天 155 万亿 token（可能包含多个数据中心）。

先看单请求。如果 77K 输入里有 96% 命中缓存，实际需要 prefill 的非缓存 token 约 3.1K。按每卡 6 万非缓存 token/s 的 prefill 吞吐，3.1K token 约需 52 毫秒；加上排队、KV 取回和第一步 decode，400 毫秒的 TTFT 是合理的量级。如果没有缓存，77K token 需要约 1.28 秒，已经超过 P99 目标；这就是缓存对长上下文服务的决定性作用。

再看 decode。230 token/s 是**单用户**的 decode 体验，对应每 token 约 4.35 毫秒；如果输出 2K token，纯 decode 时间约 8.7 秒。这个数字对聊天偏长，但对 Agent 和代码生成是正常的。用户感知的“快”主要来自首 token 和流式输出，而不是总时长。

再看规模。155 万亿 token/天约等于每秒 17.9 亿 token。这里不能用 230 token/s 去折算 GPU 数：230 是单用户速度，一张 GPU 通常同时服务多个用户。用第 30 章的聚合口径 3000 输出 token/s/GPU 来算，需要约 `1.79e9 / 3000 ≈ 60 万` 张 GPU 的等效吞吐；如果聚合吞吐是 10000 token/s/GPU，则约 18 万张。这个估算有两个必须写明的口径问题。第一，155 万亿如果包含输入 token，而 3000 是输出 token/s，两者不能直接相除：输入 token 主要消耗 prefill 算力，输出 token 消耗 decode 带宽，严格做法是分别用 prefill 和 decode 的吞吐算，再相加。第二，3000 是本书用于容量规划的保守在线输出口径，不是 15.3 节 benchmark 里 25,000 以上的峰值；把峰值代进日总量会系统性地低估 GPU 数。因此这里的 18 万到 60 万只能当数量级，不能当采购数字。具体数字取决于并发、上下文、缓存命中率和 SLO，不能从单用户速度直接反推。

最后看成本。如果每 GPU 小时收入 38 美元，聚合输出吞吐 3000 token/s，则每百万输出 token 收入约 `38 × 1e6 / (3000 × 3600) ≈ 3.5` 美元；如果误用单用户 230 token/s，会得到 45.9 美元，那是“一个用户占满一张卡”的极端口径，不是集群的每 GPU 收入。两个数字差一个数量级，说明“每 GPU 小时收入”必须和“这个小时产出多少 token”一起看，不能单独引用。第 30 章会把这个关系写成单位经济模型。

这个验算也提醒一件事：公开数字是“结果”，不是“原因”。400 毫秒 TTFT 背后是 96% 缓存命中、有界重放、Wide-EP、异步调度和 kernel 优化的共同作用；单独拿其中一个数字做容量规划，很容易得出错误结论。

## 4.10 通信与显存账本

前面的公式只算了单卡的计算和带宽。多卡部署还要加两本账：通信账和显存账。它们经常是“算力明明够，端到端却慢”的原因。

**通信账**。以 MoE 的 all-to-all 为例，每个 token 要发给 top-k 个专家，dispatch 和 combine 各一次，所以每步的通信量约：

```text
bytes_all_to_all ≈ 2 × tokens × top_k × hidden × dtype_bytes
通信时间 ≈ bytes_all_to_all / 有效互联带宽
```

`tokens` 是这一步参与路由的 token 数（decode 时约等于 batch，prefill 时等于 chunk 的 token 数），`hidden` 是 hidden 维度，系数 2 对应 dispatch 和 combine。有效带宽不是标称带宽：要扣掉协议头、拥塞、跳数和 all-to-all 的不均衡。一个 8 卡 NVLink 域的有效带宽可能是标称的 60% 到 80%，跨机 RDMA 更低。把通信时间和 4.4 的 `t(B)` 比较：如果通信时间超过计算时间，EP 越大反而越慢；只有通信被计算重叠，Wide-EP 的权重流量收益才能兑现。

**显存账**。一张卡的 HBM 要同时放权重、KV、激活、通信 buffer、CUDA Graph 预留和框架开销。一个实用的预算式是：

```text
HBM ≈ 权重 + KV + 激活峰值 + 通信 buffer + graph/workspace + 安全余量
```

权重是 `激活参数 × 权重字节`；KV 是 `并发 × 平均上下文 × 每 token 字节`；激活峰值在 prefill 时随 chunk 的 `T` 增长，在 decode 时很小；通信 buffer 取决于 EP/TP 的 in-flight 消息数；CUDA Graph 要为每种捕获形状预留内存池。很多“KV 明明够却 OOM”的案例，是把激活峰值或 graph 预留漏掉了。chunked prefill 的一个副作用就是把激活峰值从“整个 prompt”降到“一个 chunk”，从而给 KV 腾出空间。

把两本账和 4.4 的 batch 模型放在一起，才能回答“该加卡、加 batch、加 EP，还是减上下文”。如果权重流量主导且通信可重叠，加 EP；如果 KV 主导，量化或前缀缓存；如果激活峰值主导，减小 chunk；如果通信暴露，先优化拓扑或重叠，而不是继续加卡。

## 4.11 求 batch 膝点

4.4 节说 batch 增大到某个点后吞吐会饱和，这个点可以解出来。把单步时间写成两项的较大值：

```text
t_mem(B)     = (W + B × KV_read) / BW
t_compute(B) = 2 × N_active × B / P
```

膝点出现在两项相等的位置：

```text
(W + B × KV_read) / BW = 2 × N_active × B / P
B* = (W / BW) / (2 × N_active / P - KV_read / BW)
```

分母必须为正，否则无论 batch 多大都是带宽受限，增加 batch 只会线性增加 KV 流量。代入 4.7 节的数字：`W=16 GB`、`BW=3 TB/s`、`N_active=16B`、`P=1000 TFLOPS`，单请求 8K 上下文的 KV 是 `8192 × 890 ≈ 7.3 MB`。权重时间是 `16/3000 ≈ 5.33 ms`；每请求的算力时间是 `32 GFLOP / 1000 TFLOPS ≈ 0.032 ms`；每请求的 KV 带宽时间是 `7.3 MB / 3 TB/s ≈ 2.4 微秒`。于是：

```text
B* ≈ 5.33 ms / (0.032 ms - 0.0024 ms) ≈ 180
```

也就是说，在这个简化模型里，batch 到 180 左右时算力时间追上权重读取时间，之后吞吐增长变慢。4.7 节用“batch=256 时算力时间超过带宽时间”做粗略判断，得到的量级一致。真实系统还会叠加 attention 的 `4 × L × T × d` 项、all-to-all、采样和调度开销，膝点通常更低；如果 KV 更长或模型更大，KV 项会把分母压小，膝点提前。

这个公式的用途不是精确预测，而是判断“现在该优化哪一侧”。如果当前 batch 远小于 `B*`，增加 batch 或减少权重字节（量化、EP）最有效；如果已经超过 `B*`，继续加 batch 只会让 TPOT 变差，应该优化算力（更好的 kernel、更低精度）或减少每请求的 KV。把 `B*` 和 SLO 允许的最大 TPOT 一起看，才能选出既不过早饱和、又不违反尾延迟的工作点。

## 小结

性能模型的价值是让你在写代码之前就知道瓶颈在哪里。prefill 看算力和注意力平方项，decode 看权重带宽和 KV 读取，batch 在固定开销和竞争之间找工作点，推测解码看接受长度与验证成本之比，量化看字节数减少是否能被 kernel 兑现。下一章开始，我们把这些模型放回 DeepSeek-V4.1-Flash 的具体结构里。
