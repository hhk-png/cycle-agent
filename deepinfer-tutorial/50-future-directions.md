# 第 50 章 未来方向

本章导读：推理系统的下一站在哪里？本章从模型结构、系统调度、硬件、协议、Agent 和评测六个方向给出判断，并区分“已经在发生”“值得关注”“还不确定”三类趋势。最后列出适合继续研究的问题和一条学习路线。

## 50.1 模型结构

**稀疏注意力会继续演进。** V4.1 的 CSA2 用压缩 + 层次稀疏索引把长上下文成本压下来。下一步可能是更动态的稀疏模式、学习到的检索/路由、以及和 KV 压缩更紧的耦合。目标是让 1M 甚至 10M 上下文的 attention 成本接近线性。

**MoE 会更大、更稀疏。** 总参数继续增长，激活参数保持或缓慢增长；专家数量增加，EP 规模扩大，EPLB 和 all-to-all 成为核心瓶颈。可能出现“专家路由 + 检索”的混合结构，把条件计算从专家扩展到记忆/工具。

**条件记忆（Engram）会更常见。** 把事实性知识放在可检索的表里，而不是稠密参数里，可以降低计算、提高可更新性。挑战是哈希分布、存储层次、跨 rank 拉取和隐私。

**多模态会成为默认。** 视觉、音频、视频 token 和文本 token 共享上下文，VE/P/D 分离会更复杂。推理框架要处理图像预处理、patch 编码、跨模态对齐和流式输入。

**线性/混合注意力仍在探索。** Mamba、RWKV、混合层在长上下文上有优势，但和 KV cache、前缀缓存、推测解码的交互还不成熟。短期内更可能是“局部 + 稀疏 + 线性”的混合，而不是完全替换 attention。

这些趋势对推理系统的影响不一样。稀疏注意力改变的是 attention kernel 和 KV 布局；MoE 改变的是通信和负载均衡；Engram 改变的是存储层次；多模态改变的是阶段划分。框架要为每一种结构留出扩展点，而不是把当前模型的结构写死。

## 50.2 系统调度

**PD/EPD 分离会更普遍。** 阶段独立扩缩容、独立并行配置、独立 SLO，是大规模服务的自然选择。挑战是 KV 传输、全局路由、故障转移和成本。

**调度会更“经济感知”。** 现在的调度主要看延迟和吞吐；未来会把电价、SLA 罚金、缓存命中收益、GPU 折旧纳入目标函数。一个请求去哪个实例、用多少 batch、是否值得推测，都会变成在线优化问题。

**KV cache 会成为一级存储系统。** 3FS 这样的共享存储 + TTL + EC + GC，会让 KV 像数据库一样管理。可能出现“KV 查询计划”：先查元数据、估算命中收益、决定是否值得取回。

**推测解码会更自适应。** Confidence Head、硬件成本曲线、batch 分布一起决定验证长度；未来可能和调度器联合优化，把“多验证一个 token”与“多接一个请求”放在同一个预算里比较。

**异步/流水线会继续加深。** ZOS 把 CPU 调度藏到 GPU 后面；下一步是把 KV 传输、存储 I/O、专家 all-to-all 也纳入统一的流水线，减少所有阶段的 bubble。

这些方向有一个共同点：从“单点优化”走向“全局优化”。现在的调度器大多只看当前 step；未来的调度器要看整个请求生命周期、整个集群的成本和 SLO，甚至要预测未来的流量。这需要更好的在线测量、更准的成本模型和更强的优化算法。

## 50.3 硬件

**FP4 会成为推理的主流格式之一。** SM100、Ascend 950 都支持低精度；关键是 scale 布局、kernel 融合和精度保证。FP4 的收益在 decode 的带宽，不在 prefill 的算力。

**互联会成为瓶颈。** Wide-EP、PD 分离、KV 共享都依赖高带宽低延迟互联。NVLink 域、supernode、RDMA、光互联的进展会直接决定推理系统的形态。

**专用推理芯片会增多。** 除了 GPU/NPU，可能出现针对 attention/MoE 的专用加速器。框架需要更抽象的平台层，才能支持多硬件。

**内存层次会更复杂。** HBM、LPDDR、CXL、SSD 的分层，要求 KV cache 和权重放置策略更动态。Engram 的 host/INT8 存储就是一个例子。

硬件的变化会反过来改变算法。例如，如果 HBM 带宽增长慢于算力，decode 会更受带宽限制，量化和 KV 压缩会更重要；如果互联带宽增长快，Wide-EP 可以开得更大，EPLB 的收益会更明显；如果专用芯片普及，框架的 kernel 层需要更强的抽象。

## 50.4 协议与 Agent

**多协议会成为标配。** Chat Completions、Responses、Messages、MCP、工具调用、结构化输出，要求推理框架在 token 流之上有一个协议层。DeepSeek Recipe 就是这方面的尝试。

**Agent 负载会改变缓存和调度。** Agent 会反复调用工具、读文档、维护长期记忆；相同前缀的复用率很高，KV 缓存和工具结果缓存的价值很大。同时，Agent 的请求长度和并发模式与聊天不同，调度器要适应。

**流式解析会更复杂。** reasoning、正文、工具参数、多模态事件交织在一个 token 流里，需要增量状态机、UTF-8 边界处理、特殊 token 识别。DeepInfer 的 Recipe 已经处理了这些。

**评测会更难。** Agent 的成功率、工具调用的正确性、长上下文的召回，不能只靠 perplexity。推理系统要提供可复现的评测和 trace。

Agent 负载的一个特殊点是“多轮、长会话、工具调用”。它会让 KV 缓存的 TTL 变长、前缀复用率变高、请求的到达模式更突发。调度器要能识别“同一会话的连续请求”，给它们缓存亲和性或优先级；存储系统要能按会话组织 KV，而不是按单请求。

## 50.5 开源与商业

**开源边界会继续博弈。** 模型厂商希望开源引擎扩大生态，但保留基础设施和服务质量差异；云厂商希望支持多模型；企业希望稳定和合规。未来可能出现更多“开源核心 + 商业控制面”的组合。

**推理成本会继续下降。** 量化、稀疏、MoE、推测、缓存、批处理、硬件升级，每一条曲线都在降成本。但需求增长可能更快，总算力消耗不一定下降。

**差异化会从“模型”转向“系统 + 数据 + 体验”。** 当模型能力接近时，延迟、可靠性、成本、工具生态、隐私会成为竞争点。

开源与商业的边界不是固定的。一个今天保留的组件，可能因为社区压力或竞争而开源；一个今天开源的组件，可能因为安全/合规而收回。选型时不要把“开源”当成永久的承诺，要看许可证、治理模式和社区的独立性。

## 50.6 值得研究的问题

1. **KV cache 的全局最优淘汰**：在多层存储、跨地域、多租户下，怎样决定哪些 KV 保留、复制、淘汰？
2. **调度与经济目标的联合优化**：怎样把 SLO、电价、缓存收益、GPU 折旧放进一个在线决策？
3. **推测解码的理论边界**：在给定 draft 质量和硬件成本下，最优验证长度和 batch 分配是什么？
4. **低精度的可证明误差**：FP4/FP8 对长上下文召回和结构化输出的影响能否给出界？
5. **Agent 负载的缓存**：工具结果、文档、对话历史、KV 如何统一缓存和失效？
6. **多硬件编译**：怎样用一套高层 IR 生成 SM100/Ascend/CPU 的高效 kernel？
7. **可观测性**：怎样在不记录用户数据的前提下，定位推理错误和性能回归？
8. **公平性与隔离**：多租户下，怎样保证尾延迟和 KV 不串？

这些问题有的偏理论，有的偏工程，但都有一个共同点：它们不能靠单一指标回答，需要同时考虑质量、延迟、成本和可靠性。

## 50.7 三种情景

**情景 A：渐进优化。** 模型结构继续演进，但推理框架的形态变化不大；优化主要来自 kernel、量化、缓存和调度。这是最可能的情景，也是本书大部分内容仍然适用的情景。

**情景 B：架构重构。** 线性/混合注意力或新的记忆结构取代 Transformer 的一部分，KV cache 的形态改变，调度和存储需要重写。这会发生，但需要几年。

**情景 C：端侧/专用芯片崛起。** 大量推理下沉到端侧或专用加速器，云端推理的形态改变；框架需要支持更多硬件和更小的模型。

三种情景不是互斥的。一个团队应该同时关注“渐进优化”的短期收益和“架构重构”的长期风险，不要把全部赌注压在一个结构上。

## 50.8 训练侧、端侧与流量

还有三条趋势不在“模型结构”里，但会改变推理系统的边界。

**推理引擎会更多地服务训练**。RL 后训练、合成数据、拒绝采样和验证器都需要大规模生成。rollout 引擎的目标函数是“单位时间产出多少可训练样本”，它要求组采样、logprob、权重同步、部分 rollout 和 staleness 管理。未来的推理框架可能同时提供 serving 和 rollout 两种模式，共享 kernel、KV 和并行层，但在调度和正确性上分开。

**端侧会成为默认入口之一**。手机 NPU、PC NPU、统一内存和浏览器 WebGPU 让 1B 到 10B 模型可以在本地跑。端侧的约束是带宽、功耗、热和碎片化，优化方向和数据中心不同：量化、mmap、前缀复用、推测解码和云边路由比 Wide-EP 更重要。未来会出现更多“端侧小模型 + 云端大模型”的混合架构，路由要同时考虑隐私、延迟、网络和成本。

**流量工程会从“运维”变成“产品能力”**。当推理服务从单集群变成多区域、多租户、多模型，排队、准入、路由、重试预算、熔断和故障转移直接决定 SLO 和成本。未来的引擎可能会把“全局调度”作为一等接口，而不是把负载均衡留给外部网关。

这三条趋势的共同点是：推理系统的边界在变宽。只懂 kernel 不够，还要懂训练循环、端侧设备、排队论和财务报表；只懂单机不够，还要懂集群、合规和商业。第 44 到 47 章就是为这个“变宽”准备的。

## 50.9 对学习者的建议

如果你想进入这个领域，建议：

- 先把一个开源引擎跑通、改一个调度策略、测一个指标；
- 读一篇论文，复现一个机制（paged attention、speculative decoding、EPLB）；
- 学一点 CUDA/TileLang，知道 kernel 的瓶颈在哪；
- 学一点分布式系统，知道 all-reduce/all-to-all 的代价；
- 学一点经济学，知道性能优化最终要落到成本。

不要只追新框架。底层的 roofline、KV、调度、通信、正确性，换一个模型或硬件仍然适用。

一个更具体的学习路径是：第 1 到 4 章建立坐标系；第 12 到 19 章理解引擎；第 20 到 27 章动手实现；第 28 到 32 章理解安全、评测、成本和部署；第 33 到 37 章补齐工程化、模型接入、云原生、产品化和合规；第 38 到 43 章理解专项负载、多模型平台、检索推理和编译优化；第 44 到 47 章把边界扩展到训练侧、端侧、流量和财务。每读一章，写一段“如果我要在自己的项目里用这个机制，第一步是什么”。这比被动阅读更能留下东西。

## 50.10 用领先指标跟踪趋势

趋势判断最容易变成“讲故事”。一个更可靠的方法是选一组**领先指标**，按季度记录，看它们是否真的在动。领先指标不是“今年又发布了什么模型”，而是那些会先于成本和架构变化而变化的量。

第一组是负载形状。平均上下文长度、超过 128K 的请求占比、每请求的图像 token 数、思考 token 与答案 token 的比例、Agent 的平均工具轮数。这些数字决定 KV、prefill 和 decode 的相对权重。如果平均上下文一年翻倍，而 KV 字节/token 没有下降，decode 的显存压力会先于价格战出现；如果思考 token 占比从 20% 涨到 60%，输出侧的算力成本会先于模型能力饱和。

第二组是系统效率。KV 字节/token、前缀缓存命中率、非缓存 prefill 吞吐（token/s/GPU）、单用户 decode 速度、Wide-EP 的规模、all-to-all 的 P99 延迟、TTFT P99、goodput。这些指标比“峰值吞吐”更能说明架构是否在进步。一个框架把峰值吞吐提高 20%，但 P99  TTFT 恶化 50%，在在线业务里不是进步。

第三组是经济性。每百万 token 的完全成本、毛利率、有效利用率、每 GB KV 存储的小时成本、缓存命中带来的单位成本下降。成本是滞后指标，但它的分项是领先的：KV 字节/token 下降会先出现在存储和带宽账单上，利用率上升会先出现在排队和尾延迟上。

有了指标，还要有**可证伪的判据**。对 50.7 的三种情景，可以预先写下信号：如果 1M 上下文请求占比超过 30% 且 KV 字节/token 没有继续下降，情景 A 的“渐进优化”就遇到瓶颈；如果线性/混合注意力在主流模型中占到相当比例，且 KV 不再是主要显存项，情景 B 开始；如果端侧 NPU 的每瓦 token 数在两年内翻倍，且 10B 级模型能在手机上以可接受速度运行，情景 C 的拐点出现。这些阈值不是预言，而是让你在数据到来时能承认“我错了”。

记录的方式比指标本身更重要。每季度写一页：哪些指标动了、为什么动、哪个假设被证伪、下一个要验证的问题是什么。不要只收集支持自己观点的数据；主动找“如果我是错的，应该看到什么”。一年后回看，这页纸比任何一次技术预测都更有价值，因为它迫使你把叙事变成可检验的观察。

## 50.11 2026 到 2028 的路线图与退出判据

趋势只有落到“什么时候做什么、什么情况下停”才有用。下面给出一条以 2026 年底为起点的三年路线图，它不是预测，而是一个可调整的计划骨架。每个阶段都写“目标、验证指标、退出判据”，方便团队在季度复盘时判断是继续、加速还是转向。

**2026 下半年到 2027 上半年：把 FP4 和长上下文做成默认。** 目标是让 FP4 权重和 KV 在主流工作负载上达到与 BF16 可比的评测质量，同时把 128K 上下文的单位成本降到可接受区间。验证指标是 FP4 验收矩阵（第 10 章）全部通过、长上下文召回下降不超过预设阈值、TTFT P99 不退化。退出判据是：如果 FP4 在长上下文或结构化输出上的质量损失无法用校准和混合精度弥补，就退回 FP8，不为了“先进”牺牲质量。

**2027：把 KV 分层和 Agent 记忆做成基础设施。** 目标是 KV 从“请求结束就释放”变成“按会话和前缀分层保留”，支持 3 天到 7 天的 TTL、跨机取回、租户隔离和成本归因。验证指标是缓存命中率、3FS 读带宽、取回 P99、单位 token 存储成本。退出判据是：如果存储和网络成本超过重算节省，就缩短 TTL 或只保留高复用前缀；不要为了“缓存命中率”这个数字本身买单。

**2027 到 2028：把 Wide-EP、PD 分离和全局调度做成可运营的产品。** 目标是 EP 规模从 64 扩到 128 甚至更大，PD 分离支持独立扩缩容和故障转移，全局路由器能按长度、缓存和租户分配容量。验证指标是 `moe_lb`、all-to-all P99、PD 交接成功率、跨区域 failover 时间、goodput。退出判据是：如果 all-to-all 的尾延迟或 EPLB 的不均衡吃掉了 Wide-EP 的权重收益，就停在当前 EP，不继续加卡；如果 PD 分离的 KV 传输成本高于它带来的扩缩容收益，就回到混合部署。

**2028：把协议、评测和合规做成平台能力。** 目标是支持多协议（Chat Completions、Responses、Messages、MCP）、可复现评测、审计和地域合规。验证指标是协议兼容性测试通过率、评测回归稳定性、审计证据完整度、合规提前期。退出判据是：如果某个市场的合规成本高于该市场的收入潜力，就明确不进入，而不是“先上线再补”。路线图不是越多越好，砍掉不做的市场也是战略。

这张路线图有三个特点。第一，每个阶段都有可验证的指标，不是“提升性能”“优化体验”这种口号。第二，每个阶段都有退出判据，允许团队承认“这条路线不划算”。第三，阶段之间有依赖：FP4 和长上下文影响 KV 成本，KV 成本影响 PD 分离的收益，PD 分离影响全局调度。跳过前一阶段直接做后一阶段，通常会在成本或质量上出问题。

## 50.12 情景触发阈值与架构投资

第 50.7 节给了三种情景，但没有给“什么时候该切换”的阈值。下面把每种情景写成一张记分卡：触发信号、12 个月内的架构投资、成本影响、继续/退出判据。

**情景 A：渐进优化。** 触发信号是平均上下文继续增长但 KV 字节/token 缓慢下降、MoE 仍是主流、GPU 仍是主要算力。架构投资是 FP4、KV 分层、Wide-EP、异步调度和协议层；这些都可以在现有引擎上增量做。成本影响是单位 token 成本每年下降 20% 到 40%，但下降速度会放缓。继续判据是：如果连续四个季度单位成本下降低于 10%，说明渐进优化的边际收益耗尽，要开始评估情景 B 的技术路线。

**情景 B：架构重构。** 触发信号是线性/混合注意力在主流模型中占到可观比例、KV 不再是主要显存项、长上下文成本接近线性。架构投资是新的 attention kernel、状态缓存、调度器重写和评测体系；这些不是增量优化，可能需要 12 到 24 个月。成本影响是短期上升（重写和迁移），长期可能下降一个数量级。退出判据是：如果新架构在真实负载上的质量或稳定性不达标，或者生态工具（kernel、编译器、模型权重）不成熟，就保持双栈并行，不把全部流量切过去。

**情景 C：端侧/专用芯片崛起。** 触发信号是端侧 NPU 的每瓦 token 数在两年内翻倍、10B 级模型能在手机上以可接受速度运行、云边路由的成本优势显现。架构投资是端侧运行时、量化、mmap、云边会话迁移和隐私路由；数据中心引擎要支持更小的模型和更碎的请求。成本影响是云端推理的增量需求可能被端侧分流，API 单价下降。退出判据是：如果端侧只能服务低价值场景，或者云边迁移的复杂度高于收益，就保持“端侧预处理 + 云端推理”的分工，不强行把大模型塞进端侧。

三种情景不是互斥的。一个团队可以同时做 A 的增量优化和 B 的技术预研，但不要把 C 的产能押在一个还没成熟的硬件上。情景记分卡的价值是让“技术路线”变成“可观测的信号 + 可执行的投资 + 可承认的退出”，而不是每年追一个热点。

## 50.13 领先指标基线、测量与复盘模板

第 50.10 节列了领先指标，但只有指标没有基线，就无法判断“动了没有”。下面给出一张可以按季度填写的基线表。表中的数字是示意，不是行业标准；团队应该用自己的历史数据替换，并保持口径不变。

**负载形状**：平均上下文（示意 32K）、超过 128K 的请求占比（5%）、每请求图像 token 数（0）、思考 token/答案 token（0.5）、Agent 平均工具轮数（2）。这些指标决定 KV、prefill 和 decode 的相对权重。

**系统效率**：KV 字节/token（示意 890）、前缀缓存命中率（60%）、非缓存 prefill 吞吐（6 万 token/s/GPU）、单用户 decode（100 token/s）、Wide-EP 规模（64）、all-to-all P99（1 毫秒）、TTFT P99（1 秒）、goodput（按 SLO 定义）。这些指标比峰值吞吐更能说明架构是否在进步。

**经济性**：每百万 token 完全成本（示意 0.5 美元）、毛利率（55%）、有效利用率（65%）、每 GB KV 存储小时成本、缓存命中带来的单位成本下降。成本是滞后指标，但它的分项是领先的：KV 字节/token 下降会先出现在存储和带宽账单上，利用率上升会先出现在排队和尾延迟上。

填表时要注意三件事。第一，口径不变：同一个指标在不同季度必须用同样的定义、同样的测量窗口、同样的硬件；换口径要在备注里写清楚。第二，分位数优先：平均值会掩盖长尾，TTFT 和 TPOT 至少记录 P50/P95/P99。第三，记录“为什么动”：指标变化要和版本、流量、硬件、价格事件对应，否则只是数字。

复盘模板可以只有一页：本季度哪些指标动了、为什么动、哪个假设被证伪、下季度要验证什么、需要什么投资或退出。不要只收集支持自己观点的数据；主动找“如果我是错的，应该看到什么”。一年后回看，这页纸比任何一次技术预测都更有价值，因为它迫使你把叙事变成可检验的观察。

## 小结

未来的推理系统会在模型结构、调度、硬件、协议和商业五个方向同时演进。稀疏注意力、MoE、Engram、多模态会改变计算和存储；PD/EPD、经济感知调度、KV 存储、推测解码会改变系统；FP4、互联、专用芯片会改变硬件；多协议和 Agent 会改变服务边界。开源与商业的博弈会继续，但底层原理不会过时。
