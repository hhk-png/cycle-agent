# 第 46 章 流量工程、多区域与容量运营

本章导读：一个引擎可以在单机上跑得很快，但线上故障往往不在 kernel 里。一个热点前缀把 least-loaded 路由打穿，一次重试风暴让已经过载的服务雪上加霜，一个队列越过膝点后 P99 从 200 毫秒涨到 5 秒，一个区域故障暴露了 KV 没有副本。本章把这些问题放在一起讲：排队论、准入控制、路由策略、重试预算、熔断、容量缓冲、多区域故障转移和负载削减。最后用 `mini_deepinfer/traffic.py` 把这些规则跑成可测试的代码。

## 46.1 单机指标看不到的故障

单机指标回答“这台机器忙不忙”：GPU 利用率、HBM 带宽、batch、KV 使用率。线上故障往往发生在机器之间：

**热点前缀**：所有请求共享同一段系统提示词，前缀缓存让它们都命中同一台 worker。least-loaded 如果只看 inflight，会把新请求继续送到这台已经缓存热的机器，直到它过载。缓存亲和和负载均衡在这里是矛盾的。

**重试风暴**：一个下游依赖超时，网关重试；重试增加负载，让更多请求超时；更多重试。系统从“有点慢”进入“完全不可用”，而单机指标可能显示 GPU 利用率不高，因为请求都卡在重试和排队上。

**队列膝点**：利用率从 70% 升到 90%，平均延迟只涨一点，P99 却可能翻几倍。容量规划如果只看平均值，会在膝点附近做出错误的扩容决策。

**区域故障**：一个区域的 KV store 或网络故障，流量切到另一个区域；如果另一个区域没有预留容量，或者数据驻留不允许跨境，切换会把局部故障放大成全局故障。

**惊群和同步**：大量实例同时扩容、同时拉取模型、同时打满存储带宽；或者大量客户端在同一秒重连。系统不是被请求量打垮的，而是被“同时性”打垮的。

这些问题需要流量层的模型，而不是 kernel 层的优化。本章的公式假设泊松到达和指数服务，真实流量更突发、更重尾；公式的用途是定位膝点和数量级，然后用生产 trace 回放验证。

## 46.2 排队论与膝点

最简单的模型是 M/M/1：到达率 `λ`，单服务台服务率 `μ`，利用率 `ρ=λ/μ`。平均排队时间：

```text
W_q = ρ / (μ × (1 - ρ))
```

当 `ρ` 从 0.5 升到 0.9，`W_q` 从 `1/μ` 升到 `9/μ`，涨 9 倍。`examples/traffic.py` 里 `μ=10`：到达 5 时等待 100 毫秒，到达 9 时等待 900 毫秒；到达 10 时系统不稳定，等待趋于无穷。

多台服务器用 M/M/c。`erlang_c(c, a)` 给出“到达时需要等待”的概率，`mmc` 再算平均等待：

```text
a = λ / μ
ρ = a / c
W_q = C(c, a) / (c μ - λ)
```

示例里 `λ=9`、`μ=10`、`c=4`：利用率只有 0.225，等待约 0.5 毫秒；而单台服务器在同样到达率下等待 900 毫秒。多一台服务器不只是“多一份算力”，它把排队从“接近饱和”拉到“轻载”，延迟下降三个数量级。这就是为什么容量规划要留冗余，而不是把利用率拉到 100%。

LLM 服务不完全符合 M/M/c：请求的服务时间差异很大（输出长度不同），GPU 的 batch 让多个请求共享一个 step，prefill 和 decode 的服务率不同。但膝点的形状是一样的：利用率接近 1 时，尾延迟急剧上升。实际系统会用 `P95/P99` 而不是平均值来判断是否越过膝点。

一个实用的经验是：在线服务把目标利用率放在 0.6 到 0.75，给突发和长请求留余量；离线批处理可以推到 0.85 到 0.95，因为它可以容忍更长的排队。这个区间不是常数，取决于流量方差、SLO 和扩容速度。

## 46.3 准入控制：admit、queue、reject

队列不是越长越好。一个无限队列会把内存吃光，让所有请求都超时；一个过短的队列会让突发流量直接失败。准入控制要在“等一等”和“快速失败”之间做选择。

`admit` 接收五个关键输入：当前 inflight、并发上限、队列长度、队列上限、预估等待和 SLO 等待预算。规则是：

1. 有容量且队列为空，直接 admit；
2. 预估等待在预算内且队列未满，queue；
3. 高优先级请求可以在有容量时绕过队列；
4. 否则 reject，并给出 `retry_after_s` 提示。

优先级绕过有一个硬边界：不能超过并发上限。否则高优先级流量会把显存打爆，低优先级请求反而不重要了。优先级应该改变“排队顺序”，不应该改变“资源上限”。

准入控制还要和 token 预算结合。一个请求的并发槽位相同，但 128K 上下文的请求占的 KV 是 1K 请求的 128 倍；只按请求数限流，会让少数长请求吃光显存。生产系统通常同时限制：并发请求数、并发 token 数、单请求最大上下文、租户配额。四个限制中任何一个触发，都要走明确的拒绝或排队路径。

`admit` 是单机/单副本的规则。全局准入还要看集群容量、区域配额和租户公平性；这些在 46.6 和 46.7 展开。

## 46.4 路由策略：least-loaded、P2C、前缀亲和

一个请求应该去哪个 worker？常见策略有四种。

**轮询（round robin）**：按顺序分配。实现简单，适合请求同质、worker 同构的场景；缺点是它完全忽略当前负载，长请求会把某个 worker 拖住。

**最少连接（least loaded）**：选 `inflight/capacity` 最小的 worker。它比轮询更能适应长请求，但有一个盲点：它不知道 KV 压力和前缀缓存。一个 inflight 低但 KV 使用率 95% 的 worker，接新请求会立刻触发抢占。

**Power of Two Choices（P2C）**：随机选两个 worker，取负载较低的那个。它用很小的采样成本接近 least-loaded 的效果，并且天然避免“所有请求同时涌向同一个最空 worker”的惊群。大规模服务常用 P2C。

**前缀亲和（prefix affinity）**：如果某个 worker 已经缓存了请求的前缀，优先送到那里。它能提高缓存命中率，降低 prefill；代价是负载倾斜。`route` 的实现是“有亲和且未饱和才走亲和，否则退回 least-loaded”，这是一个实用的折中。

`Worker` 的负载分数是 `inflight/capacity + 0.5 × kv_utilization`。这个权重是示意：inflight 反映队列，KV 反映显存；不同模型和工作点的权重不同。生产系统会用实测的“接一个请求的边际成本”来校准，而不是拍一个常数。

路由还要考虑**区域和租户**。`route` 先过滤掉 KV 超过上限的 worker，再优先同区域；如果同区域没有可用 worker，才跨区域。跨区域会增加延迟和出网成本，也可能违反数据驻留。路由不是纯粹的负载问题，它是负载、缓存、成本和合规的联合决策。

## 46.5 重试预算、熔断与 hedging

重试是可用性的工具，也是故障的放大器。一个固定重试次数（例如 3 次）在正常情况下没问题；在依赖故障时，它会把流量放大 4 倍，让本来还能喘口气的服务彻底崩溃。

**重试预算**把重试限制为成功流量的一部分：

```text
retries_allowed = successes × retry_ratio
```

`retry_budget` 在错误率 20%、1000 请求/秒、比例 0.1 时，只允许 80 次重试。错误率越高，成功越少，重试预算越小；这形成一个负反馈，而不是正反馈。生产系统通常按服务、按依赖、按租户分别设预算，并区分“可重试错误”（超时、连接重置）和“不可重试错误”（400、schema 非法）。

**熔断器**有三态：closed（正常）、open（拒绝）、half-open（探测）。`circuit_breaker` 用失败率、窗口和冷却时间判断。失败率超过阈值就 open，冷却后进入 half-open，放少量请求探测；探测成功则 closed，失败则继续 open。熔断器要按依赖实例而不是全局，否则一个坏节点会让整个服务停止重试。

**Hedging** 是在原请求可能超时时，提前发一份副本，取先返回的结果。它能降低尾延迟，但会增加负载。`hedge_delay_ms` 建议在 P99 的 95% 左右触发：太早会浪费一倍算力，太晚就失去意义。Hedging 只适合幂等请求；生成请求重发会产生两份计费和两个不同结果，通常不适合。

这三者要一起用：重试预算防止风暴，熔断器隔离坏依赖，hedging 处理偶发长尾。单独用任何一个都可能在另一种故障下失效。

## 46.6 容量缓冲与故障域

容量规划不能只按平均 QPS。`capacity_buffer` 把三个因素放在一起：

```text
peak = mean × peak_factor
usable = peak / target_utilization
with_failure = usable × failure_domains / (failure_domains - 1)
```

示例里平均 100 QPS、峰值系数 3、8 个故障域、目标利用率 0.7：峰值 300，可用容量 428.6，考虑一个故障域后 489.8。也就是说，为了在峰值时不超过 70% 利用率，并且能承受一个域故障，需要接近 490 QPS 的容量，而不是 100。

这个公式是粗粒度的：它假设故障域等大、流量可以均匀迁移、迁移不损失容量。真实系统里，故障域可能大小不一，迁移有冷启动和 KV 传输成本，跨域还可能违反数据驻留。容量规划要把这些修正项写出来，而不是只乘一个 1.2。

故障域的设计比数字更重要。一个 EP64 的 decode 实例是一整个通信域，一张 GPU 故障可能让 64 卡都不可用；一个 DP 副本的故障域小，但模型副本多、成本高。选型时要把“故障域大小”和“恢复时间”放在吞吐旁边一起看。

## 46.7 多区域与数据驻留

多区域部署有三种常见形态。

**主备（active-passive）**：一个区域服务，另一个区域待命。切换简单，但 standby 容量闲置；RTO 取决于 DNS/TTL、权重加载和 KV 恢复，可能是分钟级。

**双活（active-active）**：两个区域同时服务，流量按地理或权重分配。利用率高，但 KV 不共享，前缀命中率下降；跨区域写入和一致性更复杂。

**单元化（cell-based）**：每个区域/租户单元独立，故障被限制在单元内。它适合多租户和大规模服务，但需要全局路由和租户到单元的映射。

数据驻留会直接限制故障转移。如果欧盟用户的 prompt 和 KV 不能出境，欧盟区域故障时不能把流量切到美国区域；只能切到同驻留标签的其他区域，或者降级/拒绝。`region_failover` 给每个幸存区域标记 `accepts_failover`，只有同 `residency` 的区域才计入可承接容量。示例里 EU 故障后，健康容量是 160 QPS，但合法承接故障区域的只有 80 QPS；US 区域虽然健康，却不能接收 EU 流量。

这个区分很重要：**健康容量不等于可承接容量**。容量规划如果只看总算力，会在合规约束下高估故障转移能力。

多区域还要考虑模型版本和 KV 格式。一个区域升级了模型，另一个区域还在旧版本；故障转移时，旧区域的 KV 不能被新区域读取。生产系统会把 manifest fingerprint 写进 KV 命名空间，跨区域只迁移“同版本、同格式、同驻留”的状态。

## 46.8 负载削减与降级

当系统已经过载，等待只会让所有请求都超时。此时需要主动削减负载：

**拒绝**：返回 429/503，让客户端退避。它保护了已经接受的请求，但会损失新请求。

**降级**：用更小的模型、更短的输出、更低的精度、关闭推测解码或结构化输出。降级能保住可用性，但会改变质量和语义；必须在响应里明确标记，不能让用户以为拿到的是完整服务。

**排队**：把请求放进有界队列，按优先级和截止时间排序。排队适合短时突发，不适合持续过载；队列满了就必须拒绝。

**隔离**：把恶意或异常流量放到单独的池子，避免它影响正常租户。隔离可以是按租户、按 IP、按请求大小或按 schema 复杂度。

`load_shedding` 用利用率和队列等待做三档判断：利用率低于阈值且等待在 SLO 内，accept；利用率高但等待还可控，degrade；等待超过 SLO，reject。这个规则要和业务优先级结合：高价值租户可以多等一会儿，低价值租户可以更早被拒绝。

降级策略要提前演练。线上临时决定“关掉哪个功能”通常会出错：关掉结构化输出会让客户端解析失败，关掉推测解码会降低吞吐但保持语义，关掉缓存会让延迟和成本同时上升。降级顺序应该写进 runbook，并在测试环境验证。

## 46.10 事故排查顺序

线上延迟飙升时，按下面的顺序查，避免一上来就怀疑模型：

1. **先看请求是否堆积**：`requests_added` 和 `requests_finished` 是否匹配，waiting/queue 是否持续增长。堆积说明容量或依赖有问题。
2. **看排队还是执行**：TTFT 涨但 TPOT 正常，问题在排队/prefill；TPOT 也涨，问题在 decode/KV/通信。
3. **看错误率和重试**：错误率上升会触发重试预算；如果重试量在涨，先限制重试，避免风暴。
4. **看依赖**：KV store、模型仓库、DNS、网关、下游工具；熔断器是否 open，超时是否集中。
5. **看热点**：某个前缀、租户、区域、模型的流量是否异常集中；路由是否把请求送到同一批 worker。
6. **看资源**：GPU/HBM、CPU、网络、存储、连接数；区分“资源饱和”和“资源空闲但排队”。
7. **看变更**：最近的模型、配置、路由、扩缩容、证书变更；大多数突发故障和变更相关。

排查时要看分位数和时间序列，不要只看平均值。一个 P99 从 200 毫秒涨到 5 秒的系统，平均值可能只涨了 30%，因为大多数请求仍然很快。

## 46.11 全局负载均衡、DNS 与区域故障转移

第 46 章前面的模型大多假设“有一个路由器可以选 worker”。在跨区域部署里，这个路由器本身是分层的：DNS/Anycast 把用户带到最近或最健康的入口，区域网关再做租户/模型路由，集群内的负载均衡器再选实例。任何一层出问题，用户看到的是“服务不可用”，而不是“某个 worker 慢”。

**DNS 层**适合做粗粒度、低频率的故障转移。TTL 不能太短（解析压力大），也不能太长（故障切换慢）；常见是 30 到 120 秒。健康检查要区分“区域入口可达”和“区域容量可用”：入口活着但 GPU 全满，DNS 不应该继续把新流量送进去。DNS 切换有缓存和传播延迟，不能作为秒级故障转移的唯一手段。

**Anycast** 把同一 IP 宣告到多个区域，BGP 会把用户带到最近的路由点；区域故障时撤销宣告，流量自动改道。它的切换快，但粒度粗、调试难，而且“最近”不等于“容量最合适”。金融、政务等需要数据驻留的场景，还要在路由层加“合法承接区域”的约束，不能只按延迟选。

**区域网关**做细粒度路由：按租户、模型、优先级、缓存亲和和配额选区域。它知道每个区域的健康容量、排队长度和 KV 命中率；故障时可以把流量切到备用区域，但要先确认备用区域有容量、模型版本一致、数据可以跨境。没有这些确认，切过去只是把故障扩散。

**集群内负载均衡**再做实例级选择：前缀亲和、KV 长度、running 数、租户配额。它和区域网关的职责不同：网关决定“去哪个区域”，集群 LB 决定“去哪个实例”。两层都要有熔断和重试预算，否则一次区域故障会触发全局限流和重试风暴。

故障转移要练，不要只写预案。至少演练四种场景：区域入口不可达、区域 GPU 全满、区域网络分区、模型版本不一致。每次演练记录切换时间、失败请求数、数据合规检查、回滚时间；把结果写进 runbook，而不是留在某个人的记忆里。第 19.10 节的混沌演练和第 35.5 节的 drain 可以配合使用。

## 小结

流量工程处理的是“机器之间”的问题：排队膝点、准入、路由、重试、熔断、容量缓冲、多区域和数据驻留。M/M/c 告诉你为什么利用率接近 1 时尾延迟会爆炸；准入控制把无限队列变成有界等待；路由在前缀亲和与负载之间取舍；重试预算和熔断器阻止故障放大；容量缓冲同时考虑峰值和故障域；多区域要区分健康容量和合法承接容量。mini-deepinfer 用排队模型、路由策略、重试预算、熔断器和故障转移规则验证了这些逻辑。下一章把技术指标翻译成财务报表：现金流、NPV、LTV/CAC、定价和合同结构。

## 练习

1. 服务率 20 请求/秒，到达率从 10 增到 18，用 M/M/1 计算等待时间；再算 4 台服务器时的 M/M/c 等待。两者差多少倍？
2. 一个服务有 4 个 worker，inflight 分别是 6/8、2/8、4/8、7/8，KV 使用率是 0.7、0.3、0.5、0.8。用 `route` 的负载分数选一个 worker；如果请求的前缀只命中第一个 worker，前缀亲和会选谁？
3. 错误率 30%、1000 请求/秒、重试比例 0.1，允许多少次重试？如果错误率涨到 60%，重试预算怎么变？
4. 平均 200 QPS、峰值系数 2.5、6 个故障域、目标利用率 0.7，计算容量缓冲。如果只能承受一个故障域，结果是多少？
5. 一个欧盟区域的流量不能出境。该区域故障后，哪些区域可以承接？容量规划应该看健康容量还是可承接容量？
6. 设计一个降级顺序：当 GPU 利用率超过 90% 且队列等待超过 SLO 时，先关什么、后关什么？说明每一步对质量、延迟和成本的影响。
