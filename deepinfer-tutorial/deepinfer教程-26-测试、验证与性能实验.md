# 第 26 章 测试、验证与性能实验

本章导读：一个推理实现“能跑”不等于“正确”。本章给出 mini-deepinfer 的测试分层、关键断言、验证命令和性能实验方法，并讨论“测试全绿但实现有 bug”的常见原因。读完本章，你应该能为自己的推理项目设计一套最小但有效的验证集。

## 26.1 三条验证命令

本仓库的验证只有三条命令：

```bash
python -m pytest -q
python examples/offline_inference.py
python check_docs.py
```

第一条跑 268 个测试，覆盖 tokenizer、采样与停止条件、分页 KV、调度器、引擎、推测解码、结构化输出、EPLB、并行（CP/EP/PD/TP）、pipeline、V4 机制实验室、量化/稀疏/视觉、多模态成本模型、推理预算与流解析、离线批处理、LoRA/适配器驻留、模型路由与级联、embedding/索引/rerank、图编译与内存规划、RL rollout、端侧规划、流量工程、财务模型、市场测算与销售产能、Recipe、HTTP server、roofline 模型，以及 manifest、gateway、tracing 和 economics 四个工程化模块。第二条跑一个端到端生成，确认权重、tokenizer、引擎、采样能串起来。第三条检查文档结构、链接、代码路径和自报数量。

这三条命令不能证明生产性能，也不能证明模型质量；它们证明的是“教学仓库内部一致、机制可运行、文档没有指错”。

如果你要更严格，可以把 28 个示例全部跑一遍并检查退出码。示例覆盖离线批量、benchmark、chunked prefill、推测解码、结构化输出、EPLB、并行、KV store、HTTP、Chat、采样、长上下文与 Agent 前缀复用、roofline、manifest、gateway、tracing、TCO、多模态、推理预算、离线批处理、多模型/适配器、embedding/rerank、编译优化、RL rollout、端侧规划、流量工程和财务模型；它们比单元测试更接近真实使用。

**开发期检查**：

- `check_docs.py` 的结构检查。
- 示例脚本的退出码和输出检查。

分层的意义是“不同层抓不同的 bug”。单元测试抓公式和边界；集成测试抓状态转移和资源生命周期；示例抓端到端路径；文档检查抓“文档和代码脱节”。任何一层缺失，都会有一类 bug 漏掉。

## 26.3 关键断言

**batch invariance**：用同一组 prompt、同一组 seed，比较批量生成和逐条生成。断言逐字符相等。这个测试能抓到“RNG 依赖 batch 顺序”“attention 归约依赖 batch”之类的问题。

**chunked prefill**：完整 prefill 和分块 prefill 的输出相等。这个测试能抓到 chunk 边界、KV 写入位置、mask 位置错误。

**前缀缓存**：同一 prompt 第二次生成，`prefix_cache_hit > 0`，输出和第一次相等。这个测试能抓到哈希链、share、COW 的问题。

**抢占**：小 KV 容量下三个长请求，断言全部完成、`preemptions >= 1`。这个测试能抓到“抢占不释放块”“重新 pin 前缀”“调度器空转”的问题。

**推测贪心**：推测输出和纯目标贪心逐 token 相等。这个测试能抓到接受规则、bonus token 和逻辑长度回退的错误。

**结构化输出**：正则输出能 fullmatch，JSON 能 `json.loads`，EBNF 输出在有限集合里。这个测试能抓到 NFA 转移、mask、EOS、trigger 的问题。

**EPLB**：不均衡指标低于基线且小于 1.2。这个测试能抓到副本分配、放置、负载计算的错误。

**CP/EP 等价**：和单卡参考实现比较，误差在 1e-6。这个测试能抓到分片、repeat、combine 的错误。

**roofline 公式**：GEMM 大矩阵必须是 compute bound，decode 必须是 memory bound，Flash 必须比朴素 attention 搬更少字节。这个测试能抓到公式里的系数、单位、方向错误。

这些断言的共同点是“和独立参考比较”，而不是“重复实现的逻辑”。例如 CP 测试用单卡 attention 做参考，推测测试用纯目标贪心做参考，EPLB 测试用基线做参考。没有参考的测试，很容易变成“实现怎么写，断言就怎么编”。

## 26.4 测试抓不到什么

测试全绿不等于实现正确。常见盲区：

- **断言编码了错误行为**：如果测试期望的输出本身就是 bug 的结果，它会“假绿”。例如 COW 测试如果只检查新块 id 不同，不检查 K/V 内容，就抓不到复制错误。
- **数值容差过松**：`atol=1e-2` 可能掩盖 attention mask 或 RoPE 的错误。
- **只测正常路径**：不测空 prompt、全 mask、OOM、超长序列、特殊 token。
- **只测单步**：不测多步状态转移、抢占后重算、前缀缓存 + 推测组合。
- **只测单实现**：不和参考实现/公式对照，测试可能只是在重复实现的逻辑。

mini 尽量用“和独立参考实现比较”“和公式比较”“和纯目标路径比较”来避免假绿。例如 CP/EP 测试用单卡参考，推测测试用纯目标贪心，EPLB 用基线对比。

还有一种假绿是“测试被跳过”。如果测试依赖某个可选包或平台，`pytest -q` 可能显示“skipped”，而文档把它算成“通过”。`check_docs.py` 只统计收集数，不统计跳过数；读测试报告时要看 `passed/skipped/failed`，不能只看“收集了多少”。

## 26.5 梯度检查

手写反向传播最容易错。开发时用一个小配置（`d_model=8`、2 层、4 个 head、seq 4）做有限差分：

```text
numeric = (loss(w + eps) - loss(w - eps)) / (2 * eps)
analytic = grad[w]
ratio = numeric / analytic
```

对每个参数抽样几个索引，ratio 应该在 0.99 到 1.01 之间。第一次检查发现 RMSNorm 的反向少了 `1/rms` 因子，所有下游梯度都偏；修复后 60 个抽样点全部通过。

这个检查没有放进 pytest，因为 60 次前向在 CI 里太慢；但它是训练能收敛的前提，建议修改 `training.py` 后手动跑一次。

## 26.6 性能实验

性能实验的原则：

1. **固定负载**：prompt 长度、输出长度、batch、并发、seed 都要固定。
2. **warmup**：至少跑几轮，让 Python/NumPy 的缓存和 BLAS 线程池稳定。
3. **多次测量**：取中位数或去掉最大最小的均值，不要只跑一次。
4. **报告分布**：均值、P50、P95、P99，不只是一个总数。
5. **区分算法指标和墙钟**：接受率、验证长度是算法指标；TTFT/TPOT 是系统指标。
6. **说明硬件**：CPU 型号、核数、NumPy/BLAS 版本、Python 版本。

`examples/benchmark.py` 扫 batch size，输出吞吐、TTFT、TPOT；它支持 `--warmup 3 --repeat 5`，默认是 1 轮 warmup、3 轮取中位数。`output_tokens` 直接取 `RequestOutput.output_tokens`，不是把返回文本重新 `encode` 一遍（后者遇到 stop 截断、EOS 或特殊 token 会低估）。CPU 上的数字噪声很大，书中只把它当趋势示意，不写死具体值。`examples/speculative_decoding.py` 同时打印墙钟和算法指标，并明确说明 CPU 上 draft 不免费。`examples/roofline.py` 不算墙钟，只算理论下界，适合和实测对比。

一个常见的实验错误是“用平均值掩盖长尾”。例如 batch=8 的吞吐比 batch=1 高，但 P99 TPOT 可能差 3 倍；如果 SLO 卡的是 P99，batch=8 可能不可用。报告结果时要把分布一起给出，而不是只给一个峰值。

## 26.7 文档自检

`check_docs.py` 检查：

- 52 章 + 10 附录是否存在，是否有标题、`## 小结`、`## 练习`；
- 每章中文正文是否达到最小长度，防止空壳；
- README 的章节链接是否指向存在的文件；
- 正文中提到的 `mini_deepinfer/...`、`examples/...`、`tests/...` 路径是否存在；
- 是否出现 `>` 块引用（本书风格不允许）；
- 是否有待办/修复标记；
- README 的 `docs-meta` 中 tests/examples/chapters/appendices 是否和实际一致；
- pytest 实际收集数是否和 meta 一致。

这个检查本身也有盲区：它不检查内容是否正确、链接文字是否匹配、数字是否在正文中一致。它只能防止“结构性错误”，不能替代阅读。

章节引用的编号曾经是一个盲区：旧版 `check_docs.py` 只检查 `README` 的链接，不检查正文里的“第 13 章”或“17.8 节”是否存在。现在它会把所有章号、节号和附录字母引用和实际的章节/小节集合对一遍，能抓住“引用了不存在的编号”。它仍然抓不住“引用存在但语义指错”的情况，例如把 51.5 的清单写成 41.5；那需要人工读上下文。重编号或插入章节时，先跑检查器，再全局搜索“第 [0-9]+ 章”，逐条对照目录。

## 26.8 一次性能实验的假信号

资源生命周期的 bug 在 22.10 节已经记录过，这里换一个“测试全绿但结论错”的例子：性能实验的 warmup。

最初跑 `examples/benchmark.py --batch-sizes 1 2 4 8`，batch=4 的吞吐比 batch=2 低，看起来像“批处理越大越慢”。原因是前几轮包含了 NumPy/BLAS 线程池初始化、页缓存冷启动和 Python 解释器的首次分支预测，batch=1、2 的测量恰好排在更冷的阶段；单次测量把固定开销算进了稳态。改成先 warmup 3 轮、再重复 5 次取中位数（`--warmup 3 --repeat 5`）后，曲线恢复成“1→2 上升、2→4 饱和、8 受内存带宽影响下降”，和连续批处理的预期一致。

这个例子说明，性能实验的“假信号”通常不是代码错，而是测量方法错。至少要固定负载、做 warmup、重复测量、报告分位数，并记录硬件和软件版本；否则同一个脚本在不同时间跑出的趋势可能相反。17.5 节和 29.12 节会把这些要求展开成 benchmark 检查清单。

## 26.9 评测体系：从单元测试到模型质量

单元测试保证机制正确，评测保证模型质量。DeepInfer 仓库的 `eval/` 目录包含 AIME、GPQA、HLE 的评测脚本，以及 `common/` 下的 judge、pass@k、数据加载和编码工具。它们和引擎测试是两条线：引擎测试用固定输入检查调度、KV、采样；评测用真实题目检查模型的答案质量。

引擎侧的回归还有一层：DeepInfer 仓库的 tests/models/offline_decode_ppl.json 保存了按平台/负载索引的 PPL baseline。离线推理测试会逐样本比较 PPL，任何数值变化都必须显式刷新 baseline。这个机制能抓到 kernel、低精度、KV 布局或并行改动带来的数值漂移，比“输出看起来差不多”可靠得多。

做自己的推理服务时，建议至少有三套评测：

1. **单元/集成测试**：调度、KV、采样、结构化输出、并行正确性。
2. **固定 PPL/任务 baseline**：同一模型、同一精度、同一负载，数值变化必须解释。
3. **端到端业务评测**：用真实 prompt 集和评分标准，检查答案质量、工具调用、长上下文召回。

评测的频率：单元测试每次提交；PPL baseline 每次 kernel/精度/并行改动；业务评测每个模型版本和重大推理改动。不要把三者混成一个“跑通就行”的脚本。

## 26.10 测试设计模式

写推理测试时，有四个好用的模式。

**参考实现对照**：用一份更慢但更直观的实现做参考，例如用 `forward_full` 对照 `forward_paged`，用单卡 attention 对照 CP，用纯目标贪心对照推测解码。参考实现不需要快，只需要可信。

**不变量断言**：除了“输出等于某个值”，还断言“页表长度 >= 需要页数”“引用计数之和等于引用数”“总负载守恒”。不变量能在随机输入下抓到状态错误。

**属性测试**：对一组随机 prompt/长度/seed，断言“chunked 和 full 输出一致”“有缓存和无缓存输出一致”。属性测试比固定用例覆盖更广，但要有确定的随机种子和失败复现。

**故障注入**：人为把 KV 容量调小、把 `max_num_seqs` 调小、把 block size 调大，观察系统是否能前进、是否报错、是否泄漏。故障注入是发现资源生命周期 bug 的最有效方法。

## 26.11 CI 与性能回归

测试只有进入 CI 才有持续价值。一个推理项目的 CI 至少分四段。

**静态检查**：格式、类型、lint、依赖漏洞扫描。类型检查能抓住张量形状、dtype、设备参数的很多错误；漏洞扫描能抓住依赖里的已知 CVE。静态检查应该最快，失败最早。

**单元与属性测试**：`pytest -q` 几秒内跑完，覆盖公式、边界和状态机。属性测试用固定 seed 生成随机输入，验证“chunked 与 full 一致”“有缓存与无缓存一致”“CP/EP 与单卡一致”。失败时要打印 seed 和输入，方便复现。

**集成与端到端**：启动真实引擎，跑固定 prompt 集，检查输出、指标和资源释放。`examples/offline_inference.py` 是最小版本；更严格的做法是回放一段生产 trace，检查 P95 TTFT、错误率和缓存命中率没有退化。

**文档与打包**：`check_docs.py` 检查章节、链接、代码路径和计数；`python -m build` 检查 wheel；在干净环境 `pip install` 检查依赖完整。文档检查不是“形式主义”，它能抓住“代码改了但文档还引用旧路径”这类常见问题。

性能回归要有阈值。单元测试用“绝对上限”（例如 `pytest` 不超过 10 秒）；端到端用“相对基线”（例如 P95 TTFT 退化不超过 10%，吞吐下降不超过 5%）。基线要固定硬件、Python/NumPy 版本、线程数和负载；否则同一个测试在不同机器上会抖动，最后没人看结果。

CI 还要处理 flaky 测试。推理测试的 flaky 来源通常是：时间测量、并发顺序、随机种子、文件系统缓存、GPU 非确定性。对策是固定 seed、用逻辑指标代替墙钟、隔离临时目录、在 GPU 测试里开启确定性模式。不要用“重跑直到通过”掩盖 flaky；那会让真正的回归被忽略。

最后，CI 要保留产物：测试报告、覆盖率、性能曲线、wheel 哈希、文档检查输出。出现回归时，能对比“这次和上次到底差在哪”，比只看一个红叉有用得多。

## 26.12 两个配置的差异是否真实

性能实验最常犯的错误，是把两次单点测量当成“A 比 B 快 3%”。CPU 频率、BLAS 线程数、页缓存、后台进程和 Python 的 GC 都会让同一条命令的耗时上下浮动几个百分点；如果不做重复和配对，这个“3%”很可能只是噪声。

一个可靠的做法是**配对实验**：准备两组配置 A 和 B，用同一批输入、同一组 seed、同一台机器，交替运行 A 和 B，得到 N 对观测。交替而不是“先跑完 A 再跑完 B”，是为了让机器状态的漂移同时作用在两边，而不是只污染其中一边。每一对先算差值 `d_i = t_B,i - t_A,i`，再算差值的均值和标准误：

```text
d_bar = mean(d_i)
s     = std(d_i, ddof=1)
se    = s / sqrt(N)
CI95  = d_bar ± t(0.975, N-1) × se
```

如果置信区间跨过 0，就不能说 B 比 A 快；如果整个区间都在 0 的同一侧，差异在统计上是显著的。还要看**实际显著性**：区间可能是 [-0.4%, -0.2%]，统计上显著，但对 SLO 和成本没有意义；也可能区间是 [-8%, +2%]，看起来很大，但样本太少，结论不成立。

举一个具体的例子。A 的五次耗时是 100.0、101.2、99.5、100.8、100.1 毫秒，B 是 97.0、98.1、96.8、97.5、97.2 毫秒。配对差值是 -3.0、-3.1、-2.7、-3.3、-2.9，均值 -3.0，样本标准差约 0.224，标准误约 0.1。`N=5` 时 t 临界值约 2.776，95% 置信区间是 [-3.28, -2.72] 毫秒，不跨 0；相对 A 的均值 100.32 毫秒，B 快约 2.99%。这个结论可以说“在这台机器、这组输入上，B 稳定快约 3%”，但不能外推到别的硬件或负载。

还有四个容易踩的坑。

第一，**吞吐是比值，不是均值**。不要先算每个请求的 token/s 再取平均；正确做法是每次运行用“总输出 token / 总耗时”，再对每次运行的吞吐做配对。否则短请求会主导平均值，得到一个有偏的结论。

第二，**尾延迟需要更多样本**。P99 在 100 个样本里就是“第二慢”的那个点，噪声极大；要稳定估计 P99，通常需要几百到上千个请求，并且要报告样本量。P50 可以在几十个样本上稳定，P99 不行。

第三，**多重比较**。如果你测了 10 个配置，只挑“看起来最快”的那个，95% 置信度下出现一个假阳性并不奇怪。应该先定主指标和假设，再做比较；或者对显著性水平做 Bonferroni 之类的校正。工程上更实用的做法是：先看效应大小是否超过最小可接受差异，再看置信区间，而不是追逐 p 值。

第四，**不要用“误差棒重叠”判断显著性**。两个均值的置信区间重叠，不等于差异不显著，因为配对差值的方差可能远小于两组各自的方差；反过来，区间不重叠也不保证在你的负载上有实际意义。直接对差值做区间估计，比目测误差棒可靠。

最后，把实验设计写进报告：配对还是独立、N 是多少、是否交替、随机化顺序、主指标是什么、最小可接受效应是多少。没有这些信息，别人无法判断“快了 3%”是结论还是巧合。第 29 章的评测统计和第 47 章的情景分析也依赖同样的纪律：先问“这个差异能不能复现”，再问“它值多少钱”。

## 26.13 变异测试：用故意改坏的实现检验测试

26.4 说“测试可能编码了错误行为”，但怎么发现？一个直接的办法是**变异测试**：故意把实现改坏一小处，再跑测试；如果测试仍然全绿，说明这组测试没有覆盖到那个行为。它检验的不是代码，而是测试本身。

推理引擎里值得手动变异的地方很集中。第一，**前缀哈希**：把链式哈希改成只哈希当前 block，如果测试还过，说明没有构造“前缀不同但后缀相同”的反例。第二，**COW**：让 `_cow_if_shared` 在引用计数大于 1 时直接写，如果测试还过，说明只检查了 block id，没有检查另一个序列的 K/V 是否被污染。第三，**推测接受规则**：把 `min(1, p/q)` 改成“总是接受”，如果贪心一致性测试还过，说明测试只用了 draft 和目标完全相同的分布。第四，**top-p 边界**：把“累计首次达到 p 的 token 也保留”改成“只保留累计小于 p 的”，如果测试还过，说明候选集断言不够细。第五，**调度器释放**：把 `free` 改成空操作，如果测试还过，说明没有断言块守恒或长时间运行的占用。

一个最小的工作流是：先列出 10 到 20 个关键不变量，每个不变量对应一个“单行变异”；用脚本或手工改一处、跑 `pytest -q`、记录是否失败、再还原。失败叫“杀死”，仍然通过叫“存活”。存活不是一定错：有些变异是等价变异（改法不改变语义），有些行为本来就不在测试范围内。但对核心不变量，存活应该被当作补测信号，而不是“测试很稳”。

变异测试的覆盖率指标是 `mutation_score = killed / (killed + survived)`。不要追求 100%：推理代码里大量形状变换和日志分支的变异没有意义，追分会把测试写成“复制实现”。把预算花在调度、KV、采样、推测和结构化输出这五个正确性核心上，收益远高于给每个工具函数加断言。等价变异也要人工判断，不能看到存活就补一个脆弱的断言。

工程上不必引入第三方变异框架。一个几十行的脚本就能做“文本替换 + 跑测试 + 还原”，关键是每次只改一处、记录 diff、确保工作区干净。变异测试适合放在夜间任务，不适合每次提交：一次完整跑要几分钟到几十分钟，而普通单测应该在秒级反馈。把变异结果和覆盖率一起看，但不要用覆盖率替代变异分数；覆盖了一行不等于断言了它的行为。

## 小结

验证分为单元、集成、开发期检查和文档自检四层。关键断言是 batch invariance、chunked 一致性、前缀缓存、抢占、推测贪心、结构化输出、EPLB、CP/EP 等价和 roofline 公式。测试全绿不等于正确，要警惕假绿、容差过松、只测正常路径。性能实验要固定负载、warmup、多次测量、报告分布。`check_docs.py` 防止结构性错误，但不能替代内容审阅。
