# 第 16 章 长上下文与 Agent 负载工程

本章导读：1M 上下文是模型能力，不是服务默认值。长上下文把 attention 的二次项、KV 的线性增长、prefill 的首 token 延迟和缓存的存储带宽同时放大；Agent 又把这些成本乘以多轮工具调用。本章把“能放进去”和“能服务好”分开，讲清长上下文的成本结构、前缀缓存、上下文并行、长度分桶、Agent 状态机和容量规划。读完本章，你应该能为一个 77K 平均输入、1M 尾部的服务算出 KV、TTFT、缓存收益和 GPU 配比，并知道哪些优化是真收益、哪些只是把成本挪到了别处。

## 16.1 能力上限与工作点

模型规格里的 `max_model_len = 1M` 是一个 schema 约束：超过这个长度，RoPE、位置编码或 attention 的索引会失效。它不等于“每个请求都应该用 1M”，也不等于“服务能同时承受很多 1M 请求”。生产系统关心的是工作点：大多数请求有多长、尾部有多长、并发多少、SLO 是什么。

公开资料给出的 DeepSeek-V4.1-Flash 生产负载可以作为量级参照：平均输入约 77K token，缓存命中率约 96%，平均 TTFT 约 400 毫秒，P99 约 1 秒。77K 不是一个小数字，它说明长上下文已经是常态，而不是边缘场景；但 1M 仍然是尾部，不是中位数。把 1M 当成默认值做容量规划，会得到一个完全不经济的系统。

长上下文受四个约束同时作用。第一是模型质量：上下文越长，模型对中间位置的信息召回越差，这就是常说的“lost in the middle”；能放进去不等于能用好。第二是计算：prefill 的注意力部分随长度平方增长，1M 的注意力计算量是 128K 的 64 倍。第三是显存：KV 随长度线性增长，1M 请求的 KV 可能是几百 MB 到接近 1 GB。第四是延迟和经济性：prefill 时间、KV 传输、存储带宽都会随长度上升，最终反映为 TTFT 和每 token 成本。

所以长上下文工程的第一原则是“分层”：用长度分桶、缓存、稀疏注意力、上下文并行和路由，把不同长度的请求送到不同的工作点，而不是用一套配置服务所有请求。第 15 章讲并行的通用机制，本章讲这些机制在长上下文和 Agent 负载下怎么组合。

## 16.2 成本结构：二次项、KV 与带宽

先看 prefill。第 4 章给出过一个简化公式：

```text
FLOPs_prefill ≈ 2 × N_active × T + 2 × L × T^2 × d
```

第一项是线性层，随 token 数线性增长；第二项是注意力，随 `T^2` 增长。短 prompt 时线性层主导；长上下文时注意力主导。CSA2 的稀疏索引、SWA 的窗口、YoCo 的有界重放，都是在压低第二项的系数。理解这一点很重要：长上下文的 prefill 不是“把短 prompt 的公式乘以长度”，而是换了一个瓶颈。

再看 decode。每生成一个 token，decode 要读一遍 KV。KV 读取量随上下文长度线性增长，所以长上下文的 decode 比短上下文慢；但 decode 的注意力只是一行 query 对整段 KV，计算量远小于 prefill。长上下文服务的尾延迟往往由 prefill 和 KV 传输决定，而不是 decode 的矩阵乘。

用数字感受一下。按公开的 890 字节/token：

```text
77K 输入   × 890 B ≈ 70.2 MB（66.9 MiB）
128K 上下文 × 890 B ≈ 116.7 MB（111.3 MiB）
1M 上下文  × 890 B ≈ 933.2 MB（890.0 MiB）
```

这里按 1K=1024 个 token、1M=1024K 计算；MB 是十进制，MiB 是二进制。一条 1M 请求的 KV 约 933.2 MB（890 MiB）。如果一张 GPU 扣掉权重、激活、通信 buffer 和 CUDA Graph 预留后只剩 40 GB 给 KV，按十进制算是 `40 / 0.9332 ≈ 43` 条 1M 并发；如果这 40 是 40 GiB，按二进制算是 `40 / 0.8691 ≈ 46` 条。两种口径都能用，但必须写清楚是 GB 还是 GiB，不能把 43 和 46 混成“约 45”。实际还要算 SWA state、indexer KV、副本和碎片，能放的数量更少。这就是为什么生产系统不会把 1M 请求和 8K 请求混在同一个池子里。

TTFT 也可以手算。假设非缓存 prefill 吞吐是每卡 6 万 token/s，一条 1M（按 10^6 计）prompt 需要约 16.7 秒；如果缓存命中 96%，只剩 4 万 token 要算，约 0.67 秒。这个对比说明：长上下文的 TTFT 主要不是由 kernel 决定，而是由“有多少 token 需要重新算”决定。缓存命中率从 90% 提到 96%，看起来只差 6 个百分点，但非缓存 token 从 10% 降到 4%，prefill 计算量下降了 60%。

带宽是第三个约束。一条 128K 请求的 KV 约 116.7 MB（131,072 × 890）；如果每秒有 10 万个请求命中缓存，需要从 3FS 读取约 11.7 TB/s，已经超过公开的 10 TiB/s 峰值。缓存命中率越高，读带宽压力越大；这不是悖论，而是“把计算换成了存储和网络”。容量规划要同时算容量、带宽和延迟，不能只看“缓存命中率”。

## 16.3 前缀缓存是长上下文的第一性优化

长上下文服务最重要的优化不是更快的 attention，而是“不要重复算已经算过的前缀”。系统提示词、工具定义、文档、多轮对话历史，在大量请求之间高度重复；前缀缓存把这些前缀的 KV 保存下来，新请求命中后直接挂到页表，只算没命中的后缀。

前缀缓存的经济性可以用一个简单模型判断。设一条 prompt 的完整 prefill 成本是 `C`，命中率是 `h`，命中部分的取回和传输成本是 `C_t`，则每次请求的 prefill 成本约 `(1-h) × C + h × C_t`。当 `C_t << C` 时，命中率每提高一点，成本都近似线性下降。对 77K 的输入，`C` 很大，`C_t` 主要是 KV 传输，通常远小于重算，所以缓存非常划算。

但缓存不是免费的。它需要存储容量、元数据查询、跨机传输和淘汰策略。第 14 章讲过 DeepInfer 的分层：in-flight block KV 在 HBM，SWA state 在本地 slot，paged block KV 在 3FS，TTL 按业务设为 3 天或 7 天。3FS 约 100 PiB，按每 GPU 14.4 TB 逻辑容量规划；这个规模说明 KV 已经是一级存储系统，而不是“显存不够时的 swap”。

缓存的 key 是前缀的链式哈希。它必须绑定模型、tokenizer、chat template、位置编码和 KV 格式；任何一项变化，旧 KV 都不能复用。生产系统会把 manifest fingerprint 写进缓存命名空间，模型热更新时切换到新命名空间，避免“新模型读到旧 KV”导致输出错乱。第 34 章会讲 manifest 和版本治理。

Agent 负载让前缀缓存的收益更大，也让缓存管理更难。一个 Agent 的系统提示词、工具 schema、few-shot 示例通常固定；每一轮只追加用户输入、模型输出和工具结果。前缀是“只追加”的，缓存命中率可以很高。但工具结果可能很长、可能包含图片、可能被截断；多轮会话可能分叉（编辑、重试、重新生成）；不同租户的 prompt 可能共享相同的系统提示词，但绝不能共享 KV。缓存设计要同时考虑“复用”和“隔离”。

一个实用的 Agent 缓存策略是“三层命名空间”：全局层缓存模型厂商提供的系统提示词和工具模板；租户层缓存租户自己的文档和配置；会话层缓存当前对话的历史。全局层可以跨租户共享，但必须是只读、无用户数据；租户层和会话层按租户隔离，TTL 按业务设置。这样既能提高命中率，又不会把 A 租户的数据泄露给 B 租户。

## 16.4 分块、调度与长请求的公平性

长请求对调度器的第一个冲击是“队头阻塞”。一个 200K token 的 prefill 如果一次性做完，会占用整个 step 几百毫秒，后面的短请求只能等。chunked prefill 把长 prompt 切成固定预算的块，每个 step 只算一块，让短请求有机会插入。代价是长请求的 TTFT 变长，因为它的 prefill 被拆成多个 step；收益是整体队列的尾延迟更平滑。

chunk 大小是一个权衡。chunk 太小，prefill 的矩阵乘效率低，kernel launch 和调度开销占比高；chunk 太大，短请求被阻塞，TTFT 尾延迟变差。生产系统通常按 token 预算（例如 `max_num_batched_tokens`）和 SLO 动态调整，而不是固定一个值。第 13 章讲过，DeepInfer 还会用 `prefill_sum_seqlen_k` 限制单步所有序列的 K 总长度，防止 attention 的 `sum(seqlen_q × seqlen_k)` 爆炸；这是一个容易被忽略的约束。

长度分桶是长上下文路由的基础。一个常见的分法是小于 16K、16K 到 64K、64K 到 256K、大于 256K。短桶用普通的 P/D 实例，追求低 TTFT；长桶用更大的 chunk、更多的 CP、更激进的缓存；超长桶可能需要单独的实例池，避免它把短请求的队列拖死。DeepInfer 的 Prefill Load Balancer 就是按上下文长度分桶，再按桶分配计算配额。

公平性是另一个问题。LCFS（最长完成优先）会优先调度输出最长的请求，避免它们在快结束时被抢占；但长请求也会占住 running 槽位，让短请求饿死。缓解手段包括 `max_num_seqs`、饥饿保护间隔、按租户配额和上层负载均衡。对 Agent 负载，还要考虑“会话公平”：一个长会话不应该占满所有并发，否则新会话的 TTFT 会不可接受。

取消和超时对长请求尤其重要。一个 1M prompt 的 prefill 可能跑十几秒，如果用户已经断开，继续算就是纯浪费。调度器要能感知 abort，释放已经分配的 block，停止后续 chunk；如果请求进入 running 后取消，还要释放 KV 和 state。mini 的 `abort` 测试覆盖了“取消后 `has_unfinished` 为假”，但没有覆盖“prefill 中途取消”的所有边界；生产实现要把取消做成状态机的一部分，而不是一个布尔标志。

## 16.5 上下文并行与稀疏/窗口注意力

当单卡放不下一条长序列的 KV，或者单卡 prefill 太慢时，就要把序列切开。上下文并行（CP）把序列维度分到多张卡，每张卡处理一段 Q，但 attention 需要完整的 K/V，所以要在计算前 all-gather K/V。这样每张卡只算自己那段的 Q，输出再拼回去。

CP 的收益和代价都很直接。收益是单卡显存和 prefill 计算被摊薄；代价是 all-gather 的通信量随序列长度增长，而且每层都要做。CP 适合“唯一的长文档”——一条 1M 的请求，没有前缀可复用，单卡算不动；不适合“大量重复前缀”——那种场景前缀缓存更便宜。CP 和缓存不是互斥的：可以先命中缓存，再对未命中的长后缀做 CP。

CP 的实现有几个细节。第一，causal mask 要按全局位置生成，不能每张卡用自己的局部 mask，否则跨卡的因果性会错。第二，Q 的分片边界要和 attention 的 tile 对齐，否则负载不均。第三，all-gather 的 K/V 要按层流水，不能等所有层都算完再通信，否则通信无法和计算重叠。第四，CP 的 rank 数通常要能整除序列长度或 tile 大小，否则会有 padding 和空转。

mini 的 `context_parallel_attention` 用逻辑分片模拟了这三步：切 Q/K/V、all-gather K/V、每个 rank 算自己的 Q、拼接输出。它不启动多进程，也不模拟网络，但保留了“每个 rank 只算自己的 Q、需要完整 K/V”的语义。测试与单卡 attention 的误差在 1e-7 量级，说明分片和 mask 的逻辑是对的。第 24 章会把这个模拟映射到真实的 NCCL/HCCL 实现。

稀疏注意力和滑动窗口是另一条路线。CSA2 用 indexer 选 top-k 个历史 block，主 attention 只在这些 block 上计算；SWA 只保留最近 128 个 token；YoCo 用有界重放重建窗口。它们把注意力的成本从 `O(T^2)` 降到接近 `O(T × k)` 或 `O(T × window)`，代价是可能漏掉远距离信息，且需要额外的索引器和重放逻辑。第 6 章讲过这些机制的数学，这里强调系统含义：稀疏注意力的收益取决于 `k << T`；如果 `k` 接近 `T`，索引器的开销会让它比稠密 attention 更慢。

## 16.6 Agent 循环：状态、工具与前缀复用

Agent 不是“一次 prompt 一次回答”，而是一个循环：模型读入系统提示词、用户目标、工具列表和历史；输出一个工具调用；执行工具，把结果追加到上下文；再让模型继续。这个循环可能跑几步，也可能跑几十步；上下文只增不减，除非做压缩或截断。

Agent 对推理系统提出四个新要求。

第一，**长会话的状态管理**。一个会话在等待工具返回时，模型不计算，但 KV 不能立刻丢掉，否则下一轮要重新 prefill。系统要把会话状态分成 running、waiting_tool、paused、finished；paused 的会话保留 KV 或至少保留前缀缓存，设置 TTL 和优先级。如果 paused 会话太多，KV 会被占满，新会话无法进入；需要按租户配额、会话年龄和重算成本做淘汰。

第二，**工具调用的结构化输出**。工具名和参数必须符合 schema；流式输出要能增量解析参数；工具执行失败要能回滚或重试。第 9 章讲过 grammar 编译和 trigger/bound，第 11 章讲过采样 mask；Agent 把这些能力用在“工具调用”上，而不是“JSON 回复”上。MCP 把工具、资源和提示模板标准化，推理服务要把 MCP 的工具 schema 编译成文法或校验器，并处理工具列表变化、权限和审计。

第三，**前缀复用**。Agent 的系统提示词和工具定义通常很大且固定；每一轮追加的历史也是只增的。如果缓存命中率高，Agent 的输入成本可以大幅下降。但工具结果可能插入到上下文中部，导致前缀不再连续；这时缓存只能命中工具调用之前的部分。设计 prompt 时，把稳定的内容放在前面、易变的内容放在后面，可以最大化前缀命中。

第四，**公平性和预算**。一个 Agent 会话可能占用几分钟、几十轮、几十万 token；如果调度器按请求数公平，长会话会挤占短请求；如果按 token 数公平，短请求又会被长会话的缓存命中“搭便车”。生产系统通常用“租户配额 + 会话优先级 + 最大步数/最大 token 预算”组合控制。超过预算的会话要能优雅终止，返回已完成的部分，而不是直接杀掉。

Agent 的安全边界也比聊天复杂。工具输出是不可信输入，可能包含 prompt injection；模型可能被诱导调用危险工具、泄露系统提示词或跨租户数据。推理引擎本身不执行工具，但它要保证输出符合协议、工具名来自允许的枚举、参数经过 schema 校验；执行层要做沙箱、超时、权限和审计。第 28 章会把 Agent 纳入威胁模型。多模态 Agent 还要处理图片和文档输入，第 38 章会讲图像 token 和 EPD；长思维链 Agent 的思考预算和双通道流见第 39 章。

## 16.7 多轮会话与 KV 生命周期

多轮会话的 KV 生命周期比单轮请求复杂。单轮请求结束就释放；多轮会话在两次模型调用之间可能空闲几秒到几分钟，KV 是保留还是释放，取决于“重算成本”和“占用成本”的比较。

如果保留 KV，下一轮可以直接命中前缀，TTFT 低；代价是空闲期间占着显存，降低并发。如果释放 KV，显存可以服务其他请求；代价是下一轮要重新 prefill，TTFT 高。一个实用的策略是“分层保留”：热会话保留在 HBM，温会话换到主机内存，冷会话落到 3FS；TTL 按业务设置，淘汰时优先选择“重算成本低、空闲时间长、租户优先级低”的会话。

会话分叉是另一个细节。用户可能编辑上一条消息、重新生成、或从某个历史点分支；这些操作会产生共享前缀的多个序列。分页 KV 的 COW 和前缀共享正好支持这种模式：分叉时共享已命中的 block，写入时 COW。mini 的 `BlockManager` 和 `PagedKVCache` 实现了引用计数和 COW，`test_block_manager.py` 覆盖了共享后写入的场景。生产系统还要处理“分叉后的 grammar 状态、采样状态、工具调用历史”，不能只复制 KV。

租户隔离在长上下文场景下更重要。如果两个租户共享前缀哈希，攻击者可能通过缓存命中时间、缓存大小或 KV 内容推断对方的数据。生产实现通常按租户命名空间隔离缓存，或者只共享“模型厂商提供的、无用户数据的”全局前缀。第 28 章会展开缓存侧信道和隔离方案。

## 16.8 质量：lost in the middle 与长上下文评测

长上下文的质量问题不会在“能不能放进去”的测试里暴露。模型可能对开头和结尾的信息召回很好，对中间的信息召回很差；可能被相似但不相关的段落带偏；可能在多跳推理里漏掉一个中间实体。这些问题和 KV 压缩、稀疏注意力、SWA 重放叠加，会让“1M 上下文”变成“1M 但不好用”。

评测要覆盖五个维度。第一，检索：在长文档里找一句话或一个数字，答案在开头、中间、结尾分别测。第二，多跳：答案需要组合多个位置的信息。第三，抗干扰：文档里有相似但不相关的段落，模型是否被带偏。第四，结构：表格、代码、层级标题，模型是否能理解。第五，长度：不要只测 1M 极端 case，要测真实的长度分布，尤其是“短问题 + 长上下文”。

KV 量化、稀疏注意力和 SWA 都会影响长上下文召回。量化可能让远距离的 key 失真；稀疏索引可能漏掉需要的 block；SWA 重放可能让窗口外的信息不可见。评测时要做消融：同一组长上下文任务，分别关闭量化、稀疏、SWA，看分数变化。第 29 章会给出评测方法和统计显著性。

Prompt 结构也会影响质量。把关键指令放在开头和结尾，把长文档放在中间；用明确的分隔符和标题；对超长文档先做摘要或检索，再放入上下文。RAG 和长上下文不是对立的：RAG 降低 token 数和成本，长上下文保留更多上下文；生产系统通常按任务选择，或者两者结合。

## 16.9 容量规划与路由

长上下文的容量规划要用 Little 定律和 KV 预算一起算。设 QPS 为 `λ`，平均停留时间为 `S`，平均上下文为 `T`，每 token KV 为 `b`，则并发 `C = λ × S`，KV 总量 `C × T × b`。这个公式看起来简单，但每一项都要按分布而不是平均值算：长尾请求的 `T` 可能是平均值的几倍，`S` 也可能因为 Agent 工具调用而拉长。

举一个算例。假设服务 100 QPS、平均停留 30 秒、平均上下文 77K（按 77×1024=78,848 token 计）、每 token 890 字节，则并发约 3000，KV 约 `3000 × 78,848 × 890 ≈ 210.5 GB`；加 25% 冗余约 263 GB。如果每条 1M 请求占 933.2 MB，3000 条里有 1% 是 1M，就是 30 条、约 28.0 GB；看起来不多，但它们会占用长上下文池的并发，不能和 77K 请求混在一起算。按长度分桶后，每个桶单独做容量规划，才能避免“平均值算得下、尾部放不下”。

P/D 配比也要按长度调整。长上下文 prefill 的算力需求高，decode 的 KV 读取高；prefill 和 decode 的 GPU 配比不是固定的 1:1，而是随平均长度、缓存命中率和 SLO 变化。第 32 章会给出 `p_d_gpu_split` 的算例。对 Agent 负载，还要考虑工具调用的空闲时间：paused 会话占着 KV 但不占算力，P/D 配比要按“活跃会话”而不是“总会话”算。

路由策略要把长度、缓存命中和租户一起考虑。一个请求如果命中了一个很长的前缀，应该优先送到缓存所在的实例或能访问同一 3FS 命名空间的实例；如果没有命中，按长度桶送到对应的池子。前缀亲和路由能提高命中率，但会造成负载倾斜；共享 3FS 可以缓解这个矛盾，代价是网络延迟。第 15 章讲过 PD 分离和负载均衡器，这里的原则是“先按长度分池，再按前缀亲和，最后按负载”。

## 16.10 故障模式与运维

长上下文和 Agent 负载的故障模式有几类典型。

**OOM / KV 不足**：一条 1M 请求可能瞬间占掉几十 GB；如果准入没有按长度检查，调度器会在分配 block 时失败。防护是准入时估算 KV、按长度桶限流、对超长请求单独排队。

**缓存抖动**：大量长请求同时命中/淘汰，导致 3FS 带宽打满、HBM 频繁换入换出。防护是 TTL 分层、按租户配额、缓存预热、限制单请求的 KV 取回量。

**chunk 边界错误**：chunked prefill 在图片、特殊 token、CP 对齐或 SWA 窗口中间切断，导致 mask 或位置编码错误。防护是把 chunk 边界对齐到 block、图片边界和 CP 的 `cp_size × 2`。

**CP 长尾**：CP 的 all-gather 由最慢的 rank 决定；一个 rank 的网络抖动会让整个 step 变慢。防护是分层 all-gather、通信/计算重叠、超时和降级。

**工具超时 / 会话挂起**：Agent 等待工具返回时，会话占着 KV 但不计算；如果工具永远不返回，会话会一直占资源。防护是工具超时、会话 TTL、最大步数、取消传播。

**上下文溢出 / 静默截断**：prompt 加输出超过 `max_model_len` 时，如果没有显式错误，系统可能截断 prompt 或输出，导致模型答非所问。防护是准入时检查、显式返回错误、在响应里标注 `finish_reason`。

**缓存污染 / 跨租户泄露**：不同租户共享了不该共享的前缀，或者缓存 key 没有绑定模型版本。防护是命名空间隔离、manifest fingerprint、审计。

运维指标要按长度分桶看：每个桶的 waiting 长度、TTFT P95/P99、KV 使用率、缓存命中率、3FS 读带宽、CP all-gather 延迟、Agent 会话数/暂停数。把所有长度混在一个平均值里，会掩盖长尾问题。

## 16.11 mini 实验与与 DeepInfer 的对照

mini 没有 1M 模型，但可以把长上下文的机制拆成可运行的实验。

`examples/chunked_prefill.py` 演示完整 prefill 和分块 prefill 的输出一致，以及前缀缓存命中后 `cache_hits` 增加；`examples/kv_store.py` 演示 TTL/LRU；`examples/parallelism.py` 演示 CP 的 all-gather 和 PD 的 KV 交接；`mini_deepinfer/yoco.py` 演示 SWA 命中判定和有界重放；`examples/tco.py` 演示容量规划和 P/D 配比。新增的 `examples/long_context.py` 把这些串起来：构造一个长共享前缀、多个 Agent 轮次，比较有缓存和无缓存的 prefill token 数、缓存命中块数，并打印 77K/128K/1M 的 KV 容量估算、Agent 并发规划和 SWA 重放计划。它不算单次运行的端到端 TTFT，也不报告实际 KV 占用；那些是 `benchmark.py` 和引擎 `stats()` 的职责。

运行：

```bash
python examples/long_context.py
python examples/chunked_prefill.py
python examples/kv_store.py
python examples/parallelism.py
```

`long_context.py` 的一次运行可以复现这个对比：4 个会话共享 320 token 前缀，每个会话 352 token；开前缀缓存时 4 个会话总共只 prefill 448 token，关缓存时 1408 token，节省 960 token（68%）。这个比例不是生产命中率，而是“前缀越长、会话越多，缓存收益越大”的机制演示。

这些实验能证明“机制的逻辑是对的”，但不能证明“1M 在生产上能跑”。mini 的模型只有 512 最大长度、16 token block、单进程 NumPy；它没有 3FS、GDR、CP 多进程、真实 kernel。保真度矩阵在第 20 章，读者不要把 mini 的时间数字当成生产数字。

与 DeepInfer 的对照可以列成五条。第一，DeepInfer 有 1M 上下文、77K 平均输入、96% 缓存命中；mini 用 512 token 和合成前缀模拟同样的逻辑。第二，DeepInfer 用 3FS 做跨机 KV 存储、TTL 3/7 天；mini 用本地 `.npy` 的 `KVBlockStore`。第三，DeepInfer 用 CP、稀疏索引、SWA/YoCo 压低长上下文成本；mini 用逻辑分片、块稀疏和重放判定验证数学。第四，DeepInfer 有长度分桶、PD 分离、全局负载均衡；mini 有分桶和双路径均衡器的教学版。第五，DeepInfer 有 Agent 协议、工具调用、MCP；mini 有 `recipe.py` 的消息归一化和流式事件，但没有完整工具执行。

## 16.12 位置编码、长度外推与注意力稳定性

16.1 说 `max_model_len` 是一个 schema 约束，超过它“RoPE、位置编码或 attention 的索引会失效”。这句话值得展开，因为很多团队把“支持 1M”理解成“把配置调大”，结果是在训练长度之外强行推理，输出质量突然塌方。

现代 decoder 普遍用旋转位置编码（RoPE）。它把 query 和 key 的每一对维度看成二维向量，按位置 `p` 旋转一个角度 `p × θ_i`，其中第 `i` 对的频率是 `θ_i = base^(-2i/d)`。旋转后的点积只依赖相对位置 `m - n`，这是 RoPE 能表达相对关系的原因。频率是一组从快到慢的波：以 `d=128`、`base=10000` 为例，`θ_0=1` 是**最高频**，波长约 `2π≈6.28` 个 token；`θ_63≈1.15e-4` 是**最低频**，波长约 5.46 万 token。低维（`i` 小）是高频，负责局部；高维（`i` 大）是低频，负责长程。长上下文能力主要压在高维那几对上，但这也意味着它们的相位在训练时只覆盖了很窄的范围。

外推失败有两个不同来源。第一是“低频相位没见过”：模型在训练长度内只见过某个范围的 `p × θ_i`；把 `p` 推到 1M，高维低频分量的相位进入训练分布之外，attention logits 的尺度会漂移，softmax 可能变得过尖或过平，模型对远距离 token 的权重就不再是训练时的样子。第二是“高频精度不够”：`p=1e6` 时，`θ_0=1` 的高频分量相位数值达到 1e6 弧度，而 float32 在这个量级上的 ulp 约 0.0625，绝对误差可达约 0.06 弧度；对快速旋转的分量来说，这足以改变 cos/sin 的取值。两类问题要分开处理：前者靠位置方案或微调，后者靠 fp32/fp64 生成 cos/sin 表、范围归约，以及不要把位置表缓存成 fp16。不要把“高维负责长程”和“高维相位数值大”混为一谈：高维是低频，相位增长慢；数值大的是低维高频分量。

围绕这两个问题，业界有四类做法。第一类是**位置插值（PI）**：把推理位置缩放到训练范围内，`p' = p × L_train / L_target`。它保证相位不越界，但把局部频率也一起压缩了，模型对邻近 token 的分辨率下降，通常需要少量微调。第二类是 **NTK-aware 缩放**：不改位置，改 base，`base' = base × (L_target/L_train)^(d/(d-2))`。它让高频几乎不变、低频被拉长，相当于“局部保持、长程扩展”，但缩放系数需要按模型校准。第三类是 **YaRN**：把 NTK-by-parts、频率 ramp 和 attention temperature 组合起来，对不同频率做不同处理，并用校准数据估计缩放；它能在少量微调甚至不微调的情况下扩展数倍长度，但不是无限外推。第四类是**注意力稳定性**路线：保留开头几个 token 的 KV 作为 attention sink，再加一个滑动窗口，例如 StreamingLLM 的“4 个 sink + 最近窗口”。它能让流式生成在很长序列上保持稳定，但窗口之外的信息仍然看不见；它解决的是“不崩”，不是“记得住”。

这四类方法解决的是不同问题，不能混为一谈。PI、NTK、YaRN 改的是位置函数，目标是让模型在更长位置上仍然“读懂”；attention sink 和滑动窗口改的是可见范围，目标是让 softmax 和 KV 管理稳定；稀疏注意力、检索和 RAG 改的是信息入口，目标是让远处的内容重新进入上下文。一个 1M 服务通常要组合使用：模型侧用训练好的位置方案，系统侧用 sink/窗口控制常驻 KV，应用侧用检索把真正相关的内容放到近处。

对推理系统来说，最重要的结论是：**位置方案是 checkpoint 的一部分，不是服务参数**。服务可以决定 `max_model_len` 暴露到多少、是否拒绝更长请求、是否为长请求单独路由，但不能靠改一个配置把 128K 模型变成 1M 模型。前缀缓存的 key 也必须包含位置方案、`max_model_len`、RoPE base 和缩放系数；否则模型热更新或长度策略变化后，旧 KV 会被错误复用。CP 分片时，每个 rank 必须拿到全局位置而不是局部位置；chunked prefill 的每个 chunk 也必须带绝对偏移，否则第二块的 RoPE 会从 0 重新开始，输出会悄悄错掉。CUDA Graph 捕获的是固定形状，位置表长度变化会触发重新捕获；这也是长上下文服务启动慢的一个原因。

DeepSeek-V4.1-Flash 的 1M 能力来自训练阶段的长上下文方案和位置设计，公开资料没有把全部细节展开。本书把它当作“模型能力”使用，不假设服务侧可以任意外推。做容量规划时，先确认模型卡上的训练长度和外推方案，再决定是否接受更长的请求；不要把“API 允许 1M”当成“质量在 1M 仍然可用”。评测要按 16.8 节的方法，分别测开头、中间、结尾的召回，并做“关闭外推/缩短窗口”的消融。

mini-deepinfer 的 RoPE 在 `model/ops.py`：`rope_tables(max_seq_len, head_dim, theta)` 生成 cos/sin 表，`apply_rope` 旋转相邻维度，训练和推理共用同一张表。它的 `max_seq_len` 是 512，没有 PI、NTK 或 YaRN；如果你把配置调大，位置表会越界报错，而不是悄悄外推。这个“宁可报错”的选择，正是生产系统应该有的边界：长度能力要显式声明，不能让一个越界的位置 id 变成不可解释的质量问题。

## 小结

长上下文不是“把 max_model_len 调大”，而是在质量、计算、显存、延迟和成本之间选工作点。前缀缓存是最重要的杠杆，它把重复 prefill 换成 KV 读取；chunked prefill、长度分桶和 CP 处理单条长请求；稀疏注意力和 SWA 压低二次项；Agent 又把这些机制放进一个多轮、工具调用、状态可暂停的循环里。容量规划要按长度分布、缓存命中率和 KV 带宽算，不能只用平均值。下一章回到引擎的异步执行，看 CPU 调度和 GPU 计算如何重叠。
