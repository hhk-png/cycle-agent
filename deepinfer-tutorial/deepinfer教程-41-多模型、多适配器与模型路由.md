# 第 41 章 多模型、多适配器与模型路由

本章导读：DeepInfer 只服务一个模型，但真实平台很少只有一个 checkpoint。团队会保留一个基座模型，再挂上若干微调变体、领域适配器和不同尺寸的模型；请求进来后，先要决定“用哪个模型回答”。本章把这件事拆成三层：参数层（LoRA 如何改变权重）、服务层（一个引擎如何同时驻留和批处理多个适配器）、决策层（路由器如何在质量、延迟、成本和上下文约束下选模型）。最后用 `mini_deepinfer/lora.py` 和 `mini_deepinfer/router.py` 把三层都跑成可测试的代码。

## 41.1 多模型的三种形态

“多模型”不是一个单一功能，而是三种不同的服务形态，成本和复杂度依次上升。

第一种是**独立实例**。每个模型有自己的进程、权重、KV cache 和调度器。隔离最好，故障域最小，但每个模型都要占一份显存和一份常驻 GPU；当模型数量很多、每个模型的流量很小时，利用率会非常低。它适合模型少、流量大、SLA 要求高的场景。

第二种是**共享基座加适配器**。基座模型的权重只存一份，每个微调变体只存一组低秩矩阵。请求带上适配器 id，引擎在运行时把低秩更新加到指定层上。显存从“每个模型一份完整权重”降到“一份基座加每个适配器几 MB 到几百 MB”，适合大量领域变体、租户定制和快速迭代。代价是引擎要支持按请求切换适配器、按行批处理不同适配器，并且不能随意复用跨适配器的 KV。

第三种是**模型路由与级联**。不同请求走不同模型：短问题走小模型，难问题走大模型，长上下文走长上下文模型；或者先用便宜模型试答，置信度不够再升级。它不改变单个模型的执行方式，而是在请求进入引擎之前做决策。路由能显著降低成本，但会引入质量风险、尾延迟和路由抖动。

这三种形态可以组合。一个平台可能用独立实例服务几个大模型，用共享基座加适配器服务几百个租户定制，用路由器把简单请求分流到小模型。理解它们的边界，比记住某个框架支持多少种适配器更重要。

## 41.2 LoRA 的数学与显存账

LoRA 的核心假设是：微调带来的权重变化是低秩的。对一个形状为 `d_in × d_out` 的基座权重 `W`，不直接学习 `ΔW`，而是学习两个小矩阵 `A`（`d_in × r`）和 `B`（`r × d_out`），令：

```text
W' = W + (alpha / r) × A × B
```

其中 `r` 远小于 `d_in` 和 `d_out`，`alpha / r` 是缩放因子。前向时，输入 `x` 经过基座线性层得到 `x @ W`，再加上低秩分支 `(alpha / r) × (x @ A) @ B`。两个分支可以并行计算，也可以在上线前合并成一个稠密权重。

参数量从 `d_in × d_out` 降到 `r × (d_in + d_out)`。以一个 `4096 × 4096` 的投影为例，全量微调要更新 1677 万个参数；`r=16` 的 LoRA 只存 `16 × 8192 = 131072` 个参数，约为原来的 0.78%。如果只适配注意力的 Q/V 投影，一个 40 层模型的适配器可能只有几十 MB；这就是为什么一张 GPU 能同时驻留几十甚至上百个适配器。

但“适配器小”不等于“服务免费”。第一，低秩分支要参与前向，增加了额外的矩阵乘；小 batch 时这部分开销占比高，大 batch 时可以被摊薄。第二，适配器要常驻显存或在使用时换入，换入有传输和同步成本。第三，不同 rank 的适配器不能直接拼成一个批量矩阵，需要 padding 到共同 rank，或者用分组 GEMM。第四，适配器改变了每一层的输出，因此用基座模型算出的 KV 不能直接给适配器复用；KV 缓存必须按“基座 + 适配器版本 + 前缀”做命名空间。

`mini_deepinfer/lora.py` 采用 `A: (in, r)`、`B: (r, out)` 的布局，`project()` 返回 `(alpha/r) × (x @ A) @ B`，`apply()` 把它加到基座线性层的输出上。`merged_weight()` 返回 `W + (alpha/r) A B`，用于上线前合并。合并后前向不再有低秩分支，延迟最低，但失去了“一个基座服务多个适配器”的灵活性；合并和未合并是部署策略，不是数学差异。

## 41.3 多适配器批处理

一个 batch 里的请求可能带不同的适配器 id。最朴素的做法是逐个请求跑一次前向，但这会把 GPU 的 batch 维度浪费掉。生产实现通常按适配器分组：同一个适配器 id 的行拼成一个子 batch，分别做低秩 GEMM，再按原始行序拼回输出。`apply_batched()` 就是这套逻辑的最小版本：它按 id 分组、逐组调用 `project()`、保留 `None` 行的基座输出。

分组带来三个工程问题。

第一是 **rank 异质性**。一个 `r=8` 的适配器和一个 `r=64` 的适配器不能直接拼成同一个矩阵乘。常见做法是 padding 到最大 rank：给 `A` 补零列、给 `B` 补零行，乘积不变。补零会浪费算力，但比逐适配器启动 kernel 便宜。`rank_padded()` 实现了这一点，并且按比例调整 `alpha`，保证 `alpha/r` 不变；如果只补矩阵不改 `alpha`，适配器的实际强度会随 rank 变化，这是一个很容易漏掉的正确性 bug。

第二是 **kernel 形态**。逐适配器的低秩 GEMM 很小，启动开销占比高；生产系统会把多个适配器的 `A`、`B` 拼成大矩阵，用 grouped GEMM 或专门的 LoRA kernel 一次算完。S-LoRA、Punica 一类系统做的就是这件事：把“按请求切换权重”变成“按行选择权重”，让 batch 维度继续有效。mini 没有真实 kernel，但它保留了“按 id 分组、按行还原”的语义，测试可以验证批处理结果和逐行循环完全一致。

第三是 **CUDA Graph 约束**。decode 的 CUDA Graph 要求形状和地址固定；如果每一步的适配器 id 集合不同，图的输入会变，不能直接 replay。生产实现通常把“最大 rank、最大适配器数”固定下来，用 mask 或间接索引处理动态部分，或者为常见的适配器组合单独捕获图。适配器越多，图的组合越难穷举，这也是多适配器服务比单模型服务更难做低延迟的原因。

还有一个容易被忽略的正确性问题：**适配器切换与 KV cache**。如果一条序列在生成中途换了适配器，之前算出的 KV 是用旧权重得到的，不能继续使用。引擎要么禁止中途切换，要么把适配器 id 写进序列状态和 KV 命名空间，切换时重新 prefill。多轮会话里，“同一会话换适配器”应该被当成一次新请求，而不是简单的参数更新。

## 41.4 适配器的生命周期

适配器不是“加载一次就永远在显存里”。一个平台可能有几百个适配器，但一张 GPU 只能同时驻留几十个；引擎需要一套类似 KV block 的管理策略。

**注册与校验**。每个适配器至少要记录：适配器 id、基座模型 fingerprint、rank、alpha、目标模块、dtype、权重哈希、租户、版本。加载时校验形状、数值有限性和基座兼容性；一个 `r=16` 的适配器配一个按 `r=8` 编译的 kernel，应该在启动时失败，而不是在第一次请求时输出错误结果。

**驻留与淘汰**。常用适配器常驻，冷适配器按 LRU 淘汰；正在被请求使用的适配器要 pin 住，不能在他 batch 还在 GPU 上时被换出。`AdapterRegistry` 用 `OrderedDict` 实现 LRU，用 `pin` 模拟引用计数，用 `max_adapters` 和 `max_bytes` 双重约束。真实系统还要处理“换入时的传输延迟”和“换出时的同步点”，这两项会直接影响尾延迟。

**预加载与预热**。一个适配器第一次使用时，如果要从主机内存或对象存储换入，首 token 延迟会明显变差。生产系统会在空闲时预取热门适配器，或者在扩容时把“基座 + 常用适配器”一起预热。预热还要覆盖不同的 batch 形状和 rank 组合，否则 CUDA Graph 或 kernel 仍会在首个请求时编译。

**版本与回滚**。适配器更新和模型更新一样，要绑定 manifest，使用独立的命名空间。回滚时不能只换回旧适配器而保留新适配器的 KV；KV 的 key 里必须包含适配器 fingerprint，否则会读到语义不匹配的缓存。

## 41.5 模型路由：约束下的最便宜选择

路由器要回答的问题不是“哪个模型最好”，而是“在满足约束的前提下，哪个模型最便宜”。约束至少有四个：上下文长度、质量下限、延迟上限、成本预算。除此之外还有租户等级、地域、数据驻留、缓存亲和等软约束。

`ModelSpec` 把模型抽象成路由需要的字段：质量分、输入/输出价格、固定延迟、每 token 延迟、最大上下文。`estimate()` 给出一次请求的成本和延迟；`ModelRouter.route()` 先过滤掉上下文放不下的模型，再过滤掉质量或延迟不达标的模型，最后在可行集合里选成本最低的。如果所有候选模型的上下文都放不下，它直接抛出 `ValueError`，因为这不是“选哪个”的问题，而是请求本身超出了路由空间；如果是质量或延迟约束无解，它返回 `feasible=False` 和 `no_feasible_model_fallback`，让上层决定是拒绝、降级还是排队。两种失败语义要分开：前者应在网关层被拦下并返回 400 类错误，后者是可运营的容量/策略问题。

这个“显式失败”很重要。路由器的默认行为如果是“实在不行就用最贵的模型”，调用方会以为 SLO 被满足了，实际上延迟已经超标；如果是“实在不行就拒绝”，至少错误是可观测的。生产系统通常把 fallback 策略做成配置：高价值租户可以越界使用大模型，低价值租户直接拒绝或排队。

路由还要避免抖动。如果两个模型的成本非常接近，请求会在它们之间来回切换，导致缓存命中率下降、负载不均。常见的稳定化手段是：给每个模型设置权重和最小分流比例；按租户或会话做粘性路由；对路由决策做时间窗口平滑；把“模型选择”和“副本选择”分开，先选模型族，再由负载均衡器选副本。

路由和前缀缓存也会互相影响。一个长前缀如果已经在模型 A 的缓存里，路由到模型 B 会重新 prefill；反过来，为了缓存命中而总是路由到 A，会让 A 过载。生产系统会把“缓存亲和”作为软约束，在成本模型里给命中率一个折扣，而不是把它当成硬规则。

## 41.6 级联：用置信度换成本

级联是路由的特例：先让便宜模型回答，用一个置信度或校验器判断答案是否可接受；不可接受再升级到更强的模型。它的成本模型很清晰。设第 `i` 个模型的单次成本为 `c_i`，接受概率为 `a_i`，则期望成本是：

```text
E[cost] = c_0 + (1-a_0) c_1 + (1-a_0)(1-a_1) c_2 + ...
```

期望质量是每个模型“被使用且被接受”的概率乘以它的质量，再加上最后一个模型兜底的质量。`cascade_estimate()` 实现了这个公式，`break_even_acceptance()` 给出“两级级联与直接调用强模型成本相同”的接受率：`a* = c_cheap / c_strong`。低于这个接受率，级联比直接调用强模型更贵；高于它，级联在成本上划算，但平均质量会下降，因为更多答案来自弱模型。

这看起来反直觉：接受率越高，级联越便宜，但平均质量越低。原因是“接受”意味着你认可了弱模型的答案。级联的质量保证来自接受判据，而不是来自模型本身。如果接受判据很松，成本会下降，但错误率会上升；如果判据很严，质量会上升，但级联退化成“总是调用强模型”。级联的核心不是数学模型，而是**校准**：置信度必须能预测“这个答案会不会被人工或下游判为正确”。

级联还会增加尾延迟。一个请求可能先跑一次弱模型，再跑一次强模型，最坏情况的延迟是两者之和；如果弱模型的输出已经开始流式返回，用户会看到“答案被撤回”或“重新生成”，体验很差。生产系统通常只在非流式、可重试、对延迟不敏感的场景用级联，或者把弱模型的输出作为“草稿”而不是最终答案。

## 41.7 多租户、隔离与计费

多适配器天然适合多租户：每个租户一个适配器，共享同一份基座。但共享也带来隔离问题。适配器权重可能包含租户的领域数据，不能跨租户加载；KV cache 更不能跨适配器共享；适配器的编译缓存、grammar、日志也要按租户命名空间隔离。`LoRAAdapter` 带 `tenant` 字段，`AdapterRegistry` 可以按租户做配额，但真正上线还要在网关和存储层做访问控制。

计费也要区分“基座”和“适配器”。常见做法是：基座按 token 计费，适配器按月或按请求收固定费用；或者把适配器加载、常驻显存和换入成本折算成“适配器小时”。如果只按 token 计费，一个租户的适配器长期常驻但流量很低，平台会亏；如果只按常驻计费，突发流量又会不公平。混合计费更常见：基础常驻费加超量 token 费。

## 41.8 mini-deepinfer 的实现

`mini_deepinfer/lora.py` 提供 `LoRAConfig`、`LoRAAdapter`、`apply_batched`、`AdapterRegistry` 和 `make_adapter`。`mini_deepinfer/router.py` 提供 `ModelSpec`、`ModelRouter`、`cascade_estimate` 和 `break_even_acceptance`。它们不依赖引擎，可以单独测试。

运行：

```bash
python examples/multi_model.py
```

一次运行的输出包括：`sql` 适配器占 224 字节；`rank_padded(4)` 与原适配器的输出完全一致；四行 batch 的分组结果与逐行循环一致；registry 在容量 2 时淘汰了最久未使用的适配器，统计为 `resident=2, evictions=1`；短对话被路由到 `medium`，成本约 0.0013 美元、延迟约 1950 毫秒；长 Agent 请求同样走 `medium`，成本约 0.048 美元、延迟约 7200 毫秒；把质量下限提到 0.95、延迟上限压到 300 毫秒后，没有可行模型，路由器返回 `large` 并标记 `feasible=False`；两级级联在 0.9 接受率下的期望成本约 0.00195 美元、期望质量约 0.715、期望调用次数 1.1。

这些数字是确定性的，但只用于说明机制。真实的适配器大小、路由成本和延迟要用你的模型、硬件和流量重算。

## 41.9 生产清单与故障模式

上线多模型/多适配器服务前，逐项确认：

- 适配器 manifest 绑定基座 fingerprint、rank、alpha、目标模块、dtype 和权重哈希；
- 引擎支持按行分组和 rank padding，且测试覆盖“批处理 = 逐行循环”；
- 适配器驻留策略有容量上限、LRU、pin/refcount 和预加载；
- KV cache 的 key 包含适配器 fingerprint，跨适配器不复用；
- CUDA Graph 对动态适配器集合有明确策略，不能捕获后静默读错权重；
- 路由器的约束、fallback 和稳定性策略写进配置，而不是藏在代码里；
- 级联的接受判据经过校准，且有最坏延迟预算；
- 租户隔离覆盖权重、KV、grammar 编译缓存和日志；
- 计费能区分基座 token、适配器常驻和换入成本；
- 监控能按适配器、模型、租户看命中率、延迟、错误率和淘汰次数。

常见故障有六类。第一，rank padding 时忘记调整 `alpha`，适配器强度随 rank 漂移。第二，适配器被换出时仍有 in-flight batch 在使用，导致读到错误权重或崩溃。第三，KV 缓存没有绑定适配器版本，切换后输出错乱。第四，路由抖动导致缓存命中率下降和负载倾斜。第五，级联的弱模型输出已经流式返回，升级时用户看到重复或矛盾的内容。第六，适配器加载失败被静默降级成基座模型，用户以为用了定制模型，实际上没有。

## 41.10 适配器感知的 KV 与路由校准

LoRA 适配器只改一部分权重，但 KV cache 是基座模型在前向中产生的。两个请求用同一个基座、不同适配器，它们的 KV 能不能共享？答案取决于适配器作用在哪一层、KV 是否受该层影响。如果适配器只改最后一层或输出头，前几层的 K/V 完全相同，可以共享；如果适配器改了 attention 的 Q/K/V 投影，或者改了 MoE 路由，KV 就会不同，不能共享。

判断条件可以写成：对每一层，比较“有适配器”和“无适配器”的 K/V 投影权重是否相同；只有所有产生 K/V 的层都相同，才能按前缀共享。实现上不要把“同一个基座”当成“KV 兼容”，要在缓存 key 里加入适配器 fingerprint 和“影响 KV 的层集合”。如果两个适配器只在最后一层不同，可以共享前面所有层的 KV，但最后一层要分开存；这能把缓存收益保留大部分，又不会读错。

适配器的生命周期也会影响 KV。适配器换入换出时，旧 KV 不能直接给新适配器用；如果适配器是“按请求加载、请求结束卸载”，KV 的生命周期和适配器绑定，缓存命中率会下降。生产系统通常把热门适配器常驻，冷门适配器按 LRU 换入；换入时预热一个短前缀，避免第一个请求承担加载延迟。

路由校准是另一个容易被忽略的问题。`ModelRouter` 用成本、延迟、质量约束选模型，但“质量”通常来自离线评测或一个置信度分数，和线上真实质量有偏差。一个模型在评测集上准确率高，可能在长尾或特定领域很差；一个级联的“弱模型先答、强模型兜底”策略，如果弱模型的置信度校准不好，会在该兜底时不兜底。校准要用线上反馈：记录每个模型的接受率、回退率、用户反馈和人工抽检，按场景、长度、语言分组，定期更新阈值。不要用一个全局阈值服务所有流量。

级联的盈亏点也要按真实接受率算。弱模型成本是强模型的 `c`，接受率是 `a`，则平均成本是 `c + (1-a) × 1`（忽略重试和额外延迟）；只有 `c + 1 - a < 1`，即 `a > c`，级联才比直接强模型便宜。如果弱模型成本 15%、接受率 60%，平均成本是 `0.15 + 0.4 = 0.55`，便宜 45%；但如果接受率掉到 10%，平均成本是 1.05，反而更贵。路由的收益完全取决于接受率，而接受率会随流量分布漂移，所以要持续监控，不能上线时算一次就完。

## 小结

多模型服务有三层：参数层的 LoRA 用低秩矩阵把“每个模型一份权重”变成“一份基座加许多小适配器”；服务层要解决按行分组、rank padding、驻留淘汰和 KV 命名空间；决策层的路由器在上下文、质量、延迟和成本约束下选最便宜的可行模型，级联则用接受概率换成本。DeepInfer 本身不包含这条路径，但它的调度、KV 和 manifest 思想可以直接迁移。mini 用两个独立模块把数学、批处理、LRU 和路由约束都变成了可测试的代码。下一章把镜头转向另一类推理负载：embedding 与 rerank。
