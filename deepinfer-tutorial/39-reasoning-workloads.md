# 第 39 章 推理模型与长思维链服务

本章导读：推理模型把“回答问题”变成“先想很久，再回答”。对用户来说，这只是多了一段可以折叠的思考过程；对推理系统来说，它改变了输出长度分布、decode 的持续时间、KV 的增长曲线、缓存的复用方式、流式协议和计费口径。本章讨论长思维链负载的工程问题：思考预算怎么定、双通道流式怎么做、KV 和调度会怎样退化、成本怎么算、质量怎么评，以及 mini-deepinfer 如何用一个模型无关的预算器和流解析器把这些问题变成可运行的代码。

## 39.1 推理负载和聊天负载的区别

聊天请求的输出通常是几十到几百个 token，推理请求的输出可能是几千到几万个 token，其中大部分是用户看不到的思考。这个差异会沿着整条服务链路放大。

第一，decode 的时间变长。decode 每步只出一个 token，输出 8000 个 token 就是 8000 个 step；即使每步只要几毫秒，端到端也会到几十秒。TTFT 可能仍然很短，因为第一个思考 token 很快就出来了，但用户感知的“完成时间”被拉长。

第二，KV 随总输出增长。KV 不只存用户看到的答案，也存思考过程的 K/V。一个 1000 token 输入、8000 token 思考、500 token 答案的请求，KV 按 9500 个 token 计算；按 890 字节/token，约 8.5 MB。100 个并发就是 850 MB。思考 token 不是“免费的内部状态”，它和答案 token 一样占显存。

第三，batch 的组成会变化。推理请求的输出长度差异很大，有的想 200 个 token 就结束，有的想 8000 个。LCFS 会优先调度长输出，短请求可能等待；decode 的 batch 里如果混着很多长思考请求，单步时间会被 KV 读取拉长，短请求的 TPOT 变差。

第四，缓存的价值和复杂度都上升。多轮推理、分支重试、自我检查会产生共享前缀；同一道题的不同解法可能共享题目和部分思考。前缀缓存可以复用这些前缀，但思考过程的分叉会让缓存树变得很宽，淘汰策略要能识别“哪些分支还可能被复用”。

第五，计费和产品语义变复杂。用户可能只想为答案付费，但服务商要为思考 token 付 GPU 成本；如果按输出 token 计价，思考 token 算不算？如果隐藏思考，用户看不到质量依据；如果展示思考，又要防止泄露系统提示、工具凭据或他人数据。这些问题不是模型能力问题，而是服务设计问题。

## 39.2 思考预算：token、时间与答案保留

推理模型通常支持“思考预算”：最多想多少 token、最多想多久、至少留多少 token 给答案。预算可以是请求级参数，也可以是服务级默认值。一个合理的预算对象至少包含三个字段：`max_reasoning_tokens`、`max_answer_tokens`、`min_answer_tokens`。前两个是硬上限，第三个是答案保留，防止模型把预算全部花在思考上，最后返回一个空答案。

`ReasoningBudget` 和 `ReasoningTracker` 实现了这套记账。tracker 分别累计 reasoning 和 answer 的 token 数，超出预算时置位 `budget_exceeded` 或 `answer_exhausted`；`should_force_answer` 在思考预算耗尽或答案保留受到威胁时返回真。生产引擎可以在这个信号上做三件事：强制插入结束思考的标记、提高答案阶段的采样优先级、或者在达到硬上限时终止请求并返回已完成的部分。

预算不是越大越好。思考 8000 个 token 的准确率可能比思考 2000 个高，但成本是 4 倍；对简单问题，过度思考会增加延迟，甚至让模型在错误的思路上越走越远。一个实用的上线方法是画“预算-准确率-成本”曲线：在固定评测集上扫 512、1024、2048、4096、8192 几个档位，记录准确率、平均思考长度、P95 延迟和单位成本，然后按业务选择工作点。不要用一个全局预算服务所有请求；简单问题用短预算，复杂问题用长预算，路由器可以按问题类型或历史难度分配。

时间预算和 token 预算是两回事。一个请求可能在 2000 个 token 内想完，也可能因为生成速度慢而超时；时间预算要覆盖排队、prefill、decode 和工具调用，不能只限制 decode。对 Agent 来说，思考可能和多轮工具调用交织，预算要按“整个任务”而不是“单次模型调用”设置。

## 39.3 双通道流式：reasoning 与 content

推理模型的输出流里通常有两类内容：思考过程和最终答案。API 会把它们放在不同字段里，例如 `reasoning_content` 和 `content`；UI 把思考折叠起来，只显示答案，或者让用户展开。推理引擎不需要理解思考的语义，但它要能把一条 token 流正确切分，并且处理标记跨 chunk 的情况。

`ThinkingStreamParser` 用一对可配置的标记（默认 `<thinking>` 和 `</thinking>`）做切分。它维护一个小 tail buffer：如果当前 chunk 的末尾可能是标记的前半段，就先不输出，等下一个 chunk 到达再判断。这样即使 `<thinking>` 被拆成 `<thin` 和 `king>`，解析器也不会把半截标记发给客户端。`feed` 返回 `(channel, text)` 事件，channel 是 `reasoning` 或 `content`；`finish` 在流结束时把缓冲区剩余内容按当前通道输出。

示例里四个 chunk 被拆成七个事件：内容 `I should compare the two optio`、`ns. `，思考 `The first is cheaper, the second `、`is faster. Therefore pick the seco`、`nd.`，内容 `The second option is the better t`、`rade-off.`。事件边界不一定和语义边界对齐，因为解析器只保证“标记不跨事件”，不保证“句子完整”。如果产品需要按句流式，应该在解析器之上再加一层句子缓冲。

双通道流式有几个工程细节。第一，标记本身不能出现在最终文本里；解析器要消费标记，而不是把它当内容。第二，如果模型没有输出结束标记就结束了，`finish` 要把剩余内容按当前通道输出，并标记“思考未闭合”，而不是静默丢弃。第三，思考通道可能很长，客户端如果不想接收，服务端应该支持“只发 content”的订阅模式，避免浪费带宽。第四，思考内容可能包含敏感信息，日志和追踪默认不应该记录完整思考，至少要脱敏和采样。

协议层要把两个通道的语义写清楚：`reasoning_content` 是增量还是累计，`content` 是否在思考结束后才开始，`finish_reason` 是否区分“答案完成”和“思考被预算截断”。这些字段一旦确定，客户端和评测都依赖它们，不能随版本悄悄改变。

## 39.4 KV、调度与推测解码

长思考对 KV 的影响是线性的，但对调度的影响是非线性的。一个输出 8000 token 的请求，在 decode 期间会一直占着 running 槽位和 KV；如果它的前缀很长，还会挤占其他请求的空间。LCFS 会优先让它完成，因为它的沉没成本最高；但这也意味着短请求可能被饿死。生产系统通常给推理请求单独的队列或配额，避免它们和聊天请求混在一起。

chunked prefill 对推理请求的帮助有限，因为瓶颈在 decode 而不是 prefill；但如果输入很长（例如带大量文档），chunked prefill 仍然能控制首 token 延迟。真正需要关注的是 decode 的 batch 组成：把输出长度差异很大的请求放在同一个 batch，会让短请求的 TPOT 被长请求拖慢。一个实用的策略是按“预计输出长度”分桶，短思考请求走低延迟池，长思考请求走吞吐池。

推测解码在推理负载上的收益不确定。draft 模型对思考 token 的接受率可能低于普通文本，因为思考过程更发散、更依赖长距离上下文；如果接受率低，验证成本会吃掉收益。另一方面，思考 token 的生成速度直接影响端到端时间，即使接受率中等，减少 decode step 也可能有价值。判断方法是按“思考阶段”和“答案阶段”分别测接受率：如果答案阶段的接受率高、思考阶段低，可以对答案阶段启用推测，对思考阶段关闭，或者用更保守的验证长度。第 8 章的公式仍然适用，只是 `c_i` 要按阶段估计。

KV 回滚在推理请求里更复杂。思考过程可能分叉：模型先写一个思路，发现不对，再回到前面的某一点重试。如果引擎支持“分支”，KV 要能共享分叉点之前的前缀，并在写入时 COW；如果引擎只支持线性序列，分叉只能靠重新 prefill。生产系统通常把“重新生成”当成新请求，复用前缀缓存，而不是在同一个序列里做树搜索。

## 39.5 缓存、压缩与上下文管理

推理请求的前缀复用机会比聊天更多。同一道题的多轮追问、同一份文档的多次分析、同一个 Agent 任务的多个步骤，都会共享很长的前缀。前缀缓存可以省掉重复 prefill，但思考过程本身也会增长 KV；如果每个分支都保留完整思考，缓存会被大量低复用率的分支占满。

一个实用的缓存策略是“分层保留”：题目、文档、系统提示等稳定前缀放长期缓存；思考过程按会话或任务保留较短 TTL；答案和最终状态保留更久。淘汰时优先淘汰“重算便宜、复用率低、占用大”的思考分支。这个策略需要缓存 key 能区分“稳定前缀”和“临时思考”，而不是把所有 token 一视同仁。

上下文压缩是另一条路线。当思考过程太长时，可以把它摘要成一段短文本，再用摘要替换原始思考，释放 KV。这个操作会改变后续生成的上下文，所以必须显式、可观测，不能悄悄做。压缩的时机、摘要的质量、压缩后是否还能回答原问题，都要评测。对合规场景，压缩还可能影响审计：原始思考被删掉后，无法复现模型的决策过程。

分支和重试会产生“共享前缀 + 不同后缀”的树。分页 KV 的 COW 正好支持这种结构：分叉点之前的 block 共享，写入时复制。mini 的 `BlockManager` 和 `PagedKVCache` 实现了引用计数和 COW，但 mini 的引擎是线性序列，没有实现树搜索。生产系统如果要做推理树的并行采样，需要在调度器里支持“一个父序列多个子序列”，并为每个子序列维护独立的采样状态和 grammar 状态。

## 39.6 成本：思考 token 的乘数

思考 token 的成本可以用一个简单的乘数模型估算。设答案 token 为 `A`，思考 token 为 `R`，decode 的单位成本与输出 token 成正比，KV 成本与总上下文成正比，则相对“只生成答案”的成本大约是：

```text
decode_ratio = (R + A) / A
kv_ratio = 1 + w × R / A
cost_multiplier = decode_ratio × kv_ratio
```

其中 `w` 是 KV 在总成本中的权重，通常在 0.1 到 0.4 之间，取决于上下文长度、batch 和硬件。`reasoning_cost_multiplier` 实现了这个公式。`R/A=9`、`w=0.25` 时，乘数是 `10 × 3.25 = 32.5`；也就是说，同样一个答案，思考 9 倍 token 可能让成本变成 30 倍以上。这个数字看起来很夸张，但它解释了为什么推理服务的定价通常远高于普通聊天。

第 39.9 节的示例还会打印一个 `10.0` 的乘数，那是**只算 decode token、不含 KV 权重**的口径：`(R+A)/A=10`。`32.5` 是含 KV 的总成本口径。两个数字都对，但回答的问题不同：前者说明“多生成多少 token”，后者说明“总算力/显存成本变成多少”。在定价和容量规划里用 32.5 这种总成本口径；在解释“为什么思考 9 倍不是 9 倍时间”时用 10.0 的 decode 口径。正文和示例必须同时标注是哪一个，否则读者会以为两个数字互相矛盾。

`plan_reasoning_capacity` 给出了更完整的容量算例。假设 QPS 10、输入 1000 token、思考 900 token、答案 100 token、单用户 decode 100 token/s、TTFT 0.4 秒、每卡聚合 decode 3000 token/s、GPU 小时成本 5.57 美元。总输出是 1000 token，单请求延迟约 10.4 秒，并发约 104，KV 约 185 MB，decode 需要约 3.33 张 GPU（加 30% 余量约 4.33 张）。单请求的 GPU 成本约 0.000516 美元，而只生成 100 个答案 token 的基线约 0.0000516 美元，正好是 10 倍。这个模型没有算 prefill、网络和存储，但足以说明“思考 token 是成本主体”。

成本优化要针对思考阶段，而不是答案阶段。减少无效思考、按难度分配预算、缓存稳定前缀、对简单问题路由到小模型，都是比“把答案生成加速 10%”更大的杠杆。反过来，如果业务按答案 token 收费，而思考 token 不计费，那么思考越长，毛利越薄；定价必须把思考 token 算进去，或者设置硬预算。

## 39.7 质量：过度思考与欠思考

推理模型的准确性不是“思考越长越好”。在简单问题上，长思考可能引入不必要的假设，甚至让模型怀疑一个正确的直觉；在难题上，思考太短又可能漏掉关键步骤。评测要画“预算-准确率”曲线，而不是只测一个预算点。

评测还要区分“答案正确”和“推理过程合理”。一个模型可能给出正确答案但推理是错的，也可能推理正确但最后抄错数字。对需要审计的场景，过程质量很重要；对只关心结果的场景，答案正确更重要。评测集要覆盖这两类需求，并分别报告。

思考过程的可读性也是产品指标。用户展开思考时，如果看到重复、循环、自我矛盾，会降低信任；如果思考太长，用户可能直接跳过。产品可以设置“折叠阈值”：短思考直接展示，长思考默认折叠；也可以提供“只看关键步骤”的摘要。这些功能不影响模型，但影响用户体验和 token 展示策略。

评测还要覆盖预算截断。一个请求在思考预算用完时被强制结束，答案可能不完整；`finish_reason` 要能区分“正常完成”“答案长度上限”“思考预算耗尽”“用户取消”。如果把这些都记成成功，质量指标会虚高，计费也会错。

## 39.8 安全与隐私

思考过程可能泄露三类信息。第一是系统提示和工具凭据：模型可能在思考里复述系统指令、API key、内部 URL。第二是用户数据：思考可能包含从上下文里读到的隐私信息，甚至是被其他租户污染的内容。第三是安全策略：如果攻击者能看到模型的完整思考，就能更容易地找到越狱路径。

防御要分层。默认不把完整思考返回给不可信客户端，只返回答案或摘要；如果产品要展示思考，要在服务端做敏感信息检测和脱敏。日志和追踪默认不记录完整思考，或者只记录哈希、长度和采样片段。思考内容在传输和存储时要加密，并设置保留期限。对多租户，思考缓存要按租户隔离，不能因为前缀相同就共享。

提示注入在推理负载里更危险，因为模型会把注入内容当成“思考的素材”。一个网页或工具结果里如果藏着“忽略之前的指令”，模型可能在思考里接受它，并在答案里执行。推理引擎不能替代内容审核，但它可以在工具结果进入上下文前做标记、隔离和长度限制，并在输出侧做策略检查。第 28 章的威胁模型同样适用，只是攻击面多了“思考通道”。

## 39.9 mini-deepinfer 的实现

`mini_deepinfer/reasoning.py` 提供三个组件。`ReasoningBudget` 定义思考、答案和答案保留的上限；`ReasoningTracker` 分别记账，给出剩余预算和“是否应该强制进入答案阶段”的信号；`ThinkingStreamParser` 把一条流切成 reasoning 和 content 两个通道，并处理标记跨 chunk。`plan_reasoning_capacity` 和 `reasoning_cost_multiplier` 把 token 混合翻译成延迟、KV、GPU 数和成本乘数。

运行：

```bash
python examples/reasoning.py
```

一次运行的输出包括：思考 4096 token 后 `force answer` 为真，答案保留 128；流式解析把四个 chunk 切成 content 和 reasoning 交替的事件；容量算例的输出 token 1000、延迟 10.4 秒、并发 104、KV 185,120,000 字节、decode 3.33 张 GPU、token 乘数 10、成本乘数 10；简化成本乘数是 32.5。这些数字是确定性的，可以用来对照公式。

mini 没有把预算接进引擎的采样循环，也没有实现“强制插入结束思考标记”的模型特定逻辑。原因是不同模型的思考标记、结束方式和训练格式不同，把这些写死在教学引擎里会制造一个虚假的通用性。mini 提供的是模型无关的记账和解析层；生产引擎要在模型适配层里把 `should_force_answer` 翻译成具体的 token 或 logits 操作。

## 39.10 工程清单

上线推理服务前，至少确认这些点。预算是请求级可配置的，且有服务级默认值和硬上限。流式协议区分 reasoning 和 content，标记跨 chunk 不会泄露或截断。`finish_reason` 能区分答案完成、答案长度上限、思考预算耗尽和用户取消。KV 容量按“输入 + 思考 + 答案”计算，而不是只按答案。调度器能把长思考请求和短聊天请求分开，避免尾延迟互相污染。前缀缓存能识别稳定前缀和临时思考，并有租户隔离。日志默认不记录完整思考，展示思考时有脱敏和访问控制。成本模型把思考 token 算进去，定价覆盖思考成本。评测覆盖预算-准确率曲线、截断率和过程质量。

## 小结

推理模型把输出 token 的结构从“答案”变成“思考 + 答案”，从而改变了延迟、KV、调度、缓存、流式协议、计费和安全的每一个环节。思考预算要在 token、时间和答案保留之间做取舍；双通道流式要处理标记跨 chunk 和敏感信息；KV 和调度要按总输出而不是答案长度规划；成本要用乘数模型把思考 token 算进去；质量要画预算-准确率曲线，而不是只看单点。mini-deepinfer 用预算器、流解析器和容量模型验证了这些逻辑，但没有绑定具体模型的思考格式。下一章转向另一类被低估的负载：离线批处理。

## 练习

1. 一个请求输入 2000 token、思考 6000 token、答案 500 token，按 890 字节/token 计算 KV；如果 QPS 是 5、平均延迟 65 秒，并发和 KV 总量是多少？
