# 第 30 章 推理经济学

本章导读：推理服务的成本由 GPU 小时、利用率、吞吐、存储和网络共同决定。本章给出一套可代入的单位经济模型，解释 DeepInfer 官方 Q&A 中“每天 155 万亿 token、每 GPU 小时 38 美元收入”的量级含义，并讨论批处理、缓存、量化和推测解码对毛利的影响。最后给出一个可以改成你团队表格的敏感性分析。

## 30.1 成本的六个部分

一个推理服务的总成本可以拆成六块。

**GPU 折旧/租赁**：最大的固定成本。按 3 年折旧，一张 3 万美元的 GPU 每年约 1 万美元，每小时约 1.14 美元（不含电和机房）。如果算上整机（CPU、内存、网卡、SSD），每张 GPU 的摊销可能到 1.5 到 2 美元/小时。

**电力与散热**：GPU 功耗 700W 到 1200W，8 卡整机加上 CPU、网络、风扇通常是 8kW 到 14kW，高密度液冷机柜可以到 15kW 以上；只有 2 到 4 卡的工作站才会落在 2kW 到 5kW。按 0.08 到 0.15 美元/kWh，一台 8 卡机每小时 0.64 到 2.1 美元。电价低的地区（例如 0.03 到 0.05 美元/kWh）会显著改变成本结构。第 32.4 节的 TCO 算例用 1.5 kW/GPU，对应 8 卡 12kW，和这里的范围一致；如果看到“8 卡整机 2kW”的数字，先确认它是不是只算了 GPU 的 TDP，漏了 CPU、内存和风扇。

**网络**：NVLink 是机器内成本，跨机 RDMA/以太网是集群成本；按每 GPU 每小时的摊销，可能 0.1 到 0.5 美元。PD 分离和 KV 共享会放大网络成本。

**存储**：模型权重、KV cache、日志。3FS 的 SSD 和 EC 成本按每 GB 每月摊销；KV 的容量可能比模型权重大一个数量级。

**机房与运维**：机位、冷却、人力、监控、备件。这部分容易被低估，尤其是小规模部署；一个 7×24 的 on-call 团队成本可能超过 GPU 折旧。

**软件与研发**：框架、调度、kernel、平台团队的摊销。自研推理引擎的研发成本通常是几百万美元级，摊到每 token 上取决于规模。

电力这一项还有两个容易被漏掉的乘数。第一是 PUE（电能使用效率）：IT 设备耗 1 kWh，机房实际可能耗 1.1 到 1.4 kWh，液冷或高密度机柜会更高；算电费时要把 PUE 乘进去。第二是碳强度：同样 1 kWh，不同电网的排放可能从每 kWh 几十克到几百克 CO2e，采购绿电或选择低碳区域会改变“每 token 的碳足迹”，但不改变电费。对外的 ESG 报告通常要区分范围 2（外购电力）和范围 3（供应链）；对内的成本模型只需要电费，但两者不要混在一张表里。单位 token 的能耗可以用 `J/token = 功率 / token 速率` 估算，它比“每 GPU 小时耗电”更适合跨硬件比较。

把 1 到 5 加起来，一张 GPU 的**名义**完全成本（nominal）可能在 2 到 5 美元/小时，取决于硬件价格、电价和规模；再除以利用率，才是**有效**成本（effective）。30.11 的算例是：8 卡 3 年 TCO 82.0 万美元，名义成本约 3.90 美元/GPU 小时，按 70% 利用率折合 5.57 美元/有效 GPU 小时。读任何“每 GPU 小时成本”时，先确认它说的是 nominal 还是 effective。官方说的“每 GPU 小时 38 美元收入”是收入，不是成本；两者之间的差额是毛利，但要扣除上述所有成本。

## 30.2 每百万 token 的成本

设一张 GPU 的完全成本为 `C_gpu` 美元/小时，输出吞吐为 `T` token/s，利用率为 `u`，则每百万输出 token 的成本是：

```text
cost_per_mtok = C_gpu / u × 1e6 / (T × 3600)
```

如果 `C_gpu = 3` 美元/小时，`T = 3000` token/s，`u = 1.0`，则：

```text
cost_per_mtok = 3 × 1e6 / (3000 × 3600) ≈ 0.28 美元
```

如果利用率降到 0.7，成本变成约 0.40 美元；如果吞吐降到 300 token/s，成本变成 2.8 美元/百万 token。吞吐差 10 倍，成本差 10 倍。这就是为什么推理优化直接等于毛利。

注意这里的 `T` 是**输出 token 吞吐**。Prefill 的输入 token 也要算成本，但通常按输入/输出分别定价；如果输入很长，prefill 的算力成本不能忽略。可以用加权 token 数：

```text
weighted_tokens = input_tokens × α + output_tokens × β
```

`α` 和 `β` 由硬件和模型决定，通常输出 token 更贵，因为 decode 受带宽限制。一个粗略的起点是 `α = 0.1`、`β = 1`，但要用实际 benchmark 校准。

## 30.3 官方数字的量级

官方 Q&A 说，单个集群每天服务 155 万亿 token，按谷时电价计算的每 GPU 小时收入为 38 美元。这个数字可以反推“每百万 token 收入”：

```text
revenue_per_mtok = 38 / (T × 3600 / 1e6)
```

如果 `T = 3000` token/s，收入约 3.52 美元/百万 token；如果 `T = 10000` token/s，收入约 1.06 美元/百万 token。这里的 3000 是 100% 利用率下的输出能力，38 美元是**每有效 GPU 小时**的收入（把空闲时间排除后的口径）；两者同一口径，所以不再乘一次利用率。30.2 的公式里 `T` 是 100% 利用率吞吐、`u` 单独出现；当你用有效 GPU 小时做分母时，`u` 已经被吸收进分母，不能再除一次。如果官方说的 38 美元其实是自然小时收入（包含空闲），那么收入/百万 token 要乘 `u`；读公开数字时先确认它说的是自然小时还是有效小时。第 32 章的 14,000 token/s/GPU 是短输出、在线 SLO 下的另一种口径，附录 B 提到的 25,000 以上是特定 benchmark 工作点的峰值。三者不能直接比较，做成本模型时必须和对应的 SLO、长度分布、batch 一起引用。具体吞吐取决于集群规模、模型、batch 和 SLO，官方没有给出对应的 GPU 数，所以不能直接用 155T/天除以 38 美元/GPU 小时来算总收入。

这个数字的真正含义是：在 DeepSeek 的负载和定价下，一张 GPU 一小时能产生 38 美元的收入。它不是一个通用的市场价格，也不是成本。它说明推理服务在合适的规模、利用率和定价下，可以有正的毛利空间；但毛利率取决于成本结构，不能只看收入。

还可以做一个“规模感”换算：155 万亿 token/天约等于每秒 17.9 亿 token。如果一张 GPU 每秒 3000 token，需要约 60 万张 GPU 等效吞吐；如果每秒 10000 token，需要约 18 万张。这是“服务总量”的口径，可能包含多集群、多模型、多地域；即使官方称其为单集群，也可能跨多个数据中心。不要把它当成一个机房的物理卡数。

## 30.4 利用率是隐藏的杠杆

GPU 不是 100% 时间都在算 token。排队、冷启动、故障、维护、低峰都会降低利用率。设名义成本为 `C_nominal`，利用率为 `u`，实际每有效 GPU 小时的成本是 `C_nominal / u`。

如果利用率从 70% 降到 40%，有效成本几乎翻倍。提高利用率的方法：

- 连续批处理，减少 GPU 空转；
- 前缀缓存，减少重复 prefill；
- 自动扩缩容，低峰释放机器；
- 多租户混部，填谷；
- 预填充/解码分离，按阶段扩缩容；
- 推测解码，提高每步产出。

但利用率不是越高越好。把 GPU 跑到 100% 会让尾延迟变差，违反 SLO。容量规划要留 20% 到 30% 的冗余，尤其是面对突发流量。

利用率的“质量”也很重要。一个集群 70% 的时间在跑有效 token，和 70% 的时间在跑重试/失败请求，成本完全不同。监控要区分“有效利用率”和“占用率”。

## 30.5 缓存的经济性

前缀缓存把“重算 prefill”换成“读 KV”。假设一条 32K prompt 的 prefill 成本是 `C_p`，缓存命中 90% 后成本是 `0.1 C_p`，但需要存储和传输成本 `C_s`。缓存划算的条件是：

```text
saved   = C_p × 命中请求数
cost    = C_s_per_token_hour × 平均缓存 token 数 × 保留小时数 + C_transfer
缓存划算  ⇔  saved > cost
```

所有项要在同一个时间窗口内计价，例如“一天”：`C_p` 是单次重算的 GPU 成本（美元/次），`命中请求数` 是这一天内命中该前缀的请求数，`C_s_per_token_hour` 是 KV 存储的每小时每 token 成本，`保留小时数` 是 TTL。不要把“命中率”和“命中请求数”再乘一次：命中请求数已经包含了命中率；如果手里只有总请求数和命中率，就写成 `C_p × 总请求数 × 命中率`。混用“每次”“每月”“每 GB”是这类估算最常见的错误。对 Agent 负载，同一段系统提示词/工具定义会被反复使用，命中请求数高，缓存非常划算；对一次性问答，命中请求数低，存储成本可能超过节省的 prefill。TTL 的选择也是这个公式：TTL 越长，`保留小时数` 和存储成本越大，命中率也越高，要找到净收益最大的点。

官方给出的基准 TTL 是 Agent 流量 3 天、Chatbot 流量 7 天。如果把 Chatbot 的 TTL 从 7 天缩短到 3 天，缓存命中率会损失 0.5% 到 1%，说明长尾命中很重要；7 天 TTL 用更多存储换更高的命中率。这个取舍要用实际流量分布算，不能拍脑袋。

用第 14 章的 `ttl_storage_bytes` 可以估算存储：每秒新增 5 万 token、TTL 3 天、每 token 890 字节，裸容量约 11.5 TB。如果采用 10+2 EC，物理容量约 `11.5 × 1.2 ≈ 13.8 TB`；如果采用两副本，约 23 TB。EC 和副本是两种冗余方案，不能相乘；只有“单副本、无 EC”才是 11.5 TB。14.10 节有同样的算例。这个数字要和 3FS 的成本、命中带来的 prefill 节省一起算，不能把不同冗余口径混着用。

## 30.6 量化、MoE、推测解码的收益

**量化**：权重从 FP16 降到 FP8，decode 的带宽时间近似减半，单位 token 成本可能下降 30% 到 50%；降到 FP4 再减半，但精度和 kernel 支持是约束。收益不是线性的，因为 attention、通信、调度也有成本。

**MoE**：总参数大、激活参数小，单位 token 的计算成本低；但 EP 的 all-to-all 和负载不均衡会增加系统成本。MoE 的经济性取决于专家并行效率和 batch 分布。

**推测解码**：用 draft 的计算换目标模型的步数。如果 draft 成本是目标的 10%，期望接受长度是 3（即平均接受 2 个 draft，加上目标模型自己的 1 个 token），验证 `k=2` 个 draft 的成本是 `1 + 2 × 0.1 = 1.2`，单位 token 成本是 `1.2 / 3 = 0.4`，下降 60%。这里容易把“接受长度 3”误当成“验证 3 个 draft”，从而算出 1.3 和 57%；`k` 是验证的 draft 数，`E` 是产出 token 数，两者差 1。实际收益还取决于接受率和并发。

**批处理**：增大 batch 能摊薄权重读取，但会增加 TPOT。对按 token 计费的服务，吞吐提升直接降低单位成本；对按请求计费的服务，延迟会影响用户体验和留存。

这些优化可以叠加，但不是简单相乘。量化降低带宽，推测解码增加每步 token，batch 摊薄权重；三者的收益会互相影响。做决策时要用同一套 benchmark，逐项开关，测组合效果。

**多模态**是另一个成本项。一张 1024×1024、patch size 16 的图片有 4096 个 patch；经过 pixel-unshuffle 或池化后可能减少，但仍然会变成几千个 LLM token。成本包括 VE 的 GPU 时间、embedding 传输、这些 token 的 prefill，以及图片解码/缩放的 CPU。相同图片被多次使用时，可以缓存图片哈希对应的 embedding，省掉整个 VE 阶段；这和文本前缀缓存是两套 key，不能混用。做多模态定价时，要按“每张图 + 每个 token”分别算，不能只按文本 token 报价。

**推理模型**是另一个成本项。思考 token 和答案 token 一样消耗 decode 和 KV，但用户可能看不到；一个 `R/A=9` 的请求，按 token 计的成本可能变成 10 倍，按 KV 加权后可能到 30 倍以上。第 39.6 节给出乘数模型和容量算例；定价时要么把思考 token 计入，要么设置硬预算。

**Agent** 的成本要按任务而不是按单次请求算。一个任务可能包含多轮模型调用、工具执行和观察结果；输入 token 大部分是重复的前缀，命中缓存时便宜，未命中时要重新 prefill；输出 token 可能很少，但工具调用的等待时间和失败重试也要计入。按任务定价时，先估每个任务的平均轮数、每轮输入/输出 token、缓存命中率和工具失败率，再乘单位成本。按 token 定价时，要把缓存命中和未命中分成两档，否则长会话会把成本藏进平均值里。

## 30.7 定价策略

常见的定价方式：

- **按 token**：输入/输出分别定价，适合 API 服务。
- **按请求**：适合短请求、固定价格的产品。
- **按订阅**：适合 C 端产品，成本由平均用量决定。
- **按 GPU 小时**：适合专属实例/私有化部署。
- **混合**：基础订阅 + 超量按 token。

定价要覆盖“平均成本 + 冗余 + 毛利”，还要考虑竞争、用户价格敏感度和峰谷差异。谷时电价低，可以做 off-peak 折扣；长上下文成本高，可以分层定价。

按 token 定价的一个细节是“输入和输出的比例”。长上下文 RAG 的输入可能是输出的 50 倍，如果输入定价太低，会亏；短聊天则相反。定价模型要基于真实流量分布，而不是一个平均 token 数。

一个最小可用的“价格书”要写清五件事：输入未命中、输入命中、输出、批处理、专属实例。每一项都要有计量单位（每百万 token、每千 token、每 GPU 小时）、最低计费粒度（例如按 1K token 向上取整）、以及折扣上限。价格书之外还要有“折扣瀑布”：标价 → 承诺折扣 → 量级折扣 → 战略折扣，每往下一层都需要更高权限，财务按季度看“净价实现率”（实际收入 / 标价收入）。没有这一层治理，销售为了签单会把折扣叠满，单位经济模型和实际毛利会对不上。

## 30.8 一个可代入的算例

把下面的变量填进你的场景：

- GPU 完全成本 `C_gpu`：____ 美元/小时
- 输出吞吐 `T`：____ token/s/GPU
- 平均输入/输出比：____
- 缓存命中率：____
- 利用率 `u`：____
- 目标毛利率：____

然后计算：

```text
cost_per_mtok = C_gpu / u × 1e6 / (T × 3600)
price_per_mtok = cost_per_mtok / (1 - 目标毛利率)
```

代入一组示意数字：`C_gpu=5.57` 美元/有效 GPU 小时、`T=3000` 输出 token/s、`u` 已经包含在 5.57 里（不要再除一次），成本约 `5.57 × 1e6 / (3000 × 3600) ≈ 0.516` 美元/百万 token。目标毛利率 60% 时，标价约 `0.516 / 0.4 ≈ 1.29` 美元/百万 token。再把输入/输出按 4:1 拆：输出 3.0 美元/百万、输入未命中 0.75 美元/百万、输入命中 0.3 美元/百万；批处理再打 8 折。

价格定出来只是第一步，真正到手的是“毛利桥”：收入 1.29，减去 GPU 0.52、电力 0.06、存储/网络 0.08、支持 0.10、获客摊销 0.15，贡献毛利约 0.38，贡献毛利率约 29%。这和第 30.1 节说的“名义成本 2 到 5 美元、有效成本 5.57 美元”是同一套账，只是把“标价毛利 60%”拆成了“GPU 之外的每一项”。如果算出来的价格高于市场价，你需要提高吞吐、利用率或缓存命中率，或者接受更低的毛利；如果低于市场价，你有定价空间，但要注意竞争和需求弹性。不要把“毛利率 60%”当成“每百万 token 能留下 0.77 美元”，中间还有电力、存储、支持和获客。

## 30.9 敏感性分析

单位经济模型的最大价值不是给出一个数字，而是告诉你“哪个假设最敏感”。可以做三组敏感性分析。

第一，吞吐 ±30%：如果吞吐从 3000 降到 2100，成本从 0.28 涨到 0.40，涨幅 43%。第二，利用率从 0.7 降到 0.5：成本涨 40%。第三，电价从 0.08 涨到 0.15：如果电力占总成本 15%，总成本涨约 13%。

把这三个变量画成一张 tornado 图（横向条形图），你就能看出“优化吞吐”比“谈电价”更有效。不同业务的最敏感变量不同：长上下文 Agent 可能对 KV 存储成本更敏感，短聊天可能对 GPU 利用率更敏感。

## 30.10 不要只看单位成本

单位成本低不代表业务成功。还要看：

- **需求**：有没有人愿意为这个价格付费？
- **延迟**：用户能不能接受 TPOT/TTFT？
- **质量**：量化/推测/小模型是否降低了答案质量？
- **可靠性**：故障和限流会不会赶走用户？
- **合规**：数据保留、地域、审计会不会增加成本？

推理经济学不是“把 token 成本压到最低”，而是“在质量、延迟、可靠性的约束下，找到可持续的毛利”。本章的单位成本是第 47 章现金流模型的输入：一个项目可能单位成本很低，但 capex、ramp 速度和客户流失会让 NPV 为负；反过来，单位成本一般的项目可能因为回款快、利用率稳定而更值得投。把本章的 `cost_per_mtok` 代进第 47 章的 `npv` 和 `scenario_table`，才能看到“成本优势”在财务上的真实价值。

```text
  utilization  $0.645 .. $0.430
  electricity  $0.526 .. $0.506
```

这个算例的假设是：8 卡、3 年、70% 利用率、输出 3000 token/s、每 GPU 小时收入 38 美元。结果有两个值得注意的地方。

第一，capex 占总 TCO 的 43.9%，电力只占 3.8%。所以“谈电价”对总成本的影响远小于“提高利用率”或“提高吞吐”。敏感性分析也显示，吞吐 ±30% 带来的成本变化最大，电价 ±50% 反而最小。这和很多人的直觉相反，但对高 capex 的 GPU 集群是正常的。

第二，85% 的毛利率没有扣除销售、支持、研发、带宽、存储和坏账。真实业务的毛利率会低很多；如果一个团队按 85% 做财务模型，很容易高估利润。第 36 章会把完全成本加进去。

`economics.py` 还提供 `capacity_plan` 和 `p_d_gpu_split`。前者用 Little 定律算并发和 KV，后者按 prefill/decode 每卡吞吐算 GPU 配比。它们不能替代压测，但能在写代码之前判断“瓶颈是 GPU、KV 还是网络”。

这个模块的设计原则是“纯函数 + 数据类”：每个函数只依赖输入，不读全局状态，不写文件，返回可断言的结构。这样它既可以在示例里打印，也可以在测试里断言，还可以在 notebook 里做敏感性分析。第 36 章会用它做产品化案例。

## 小结

推理成本由 GPU、电力、网络、存储、机房和研发共同决定，单位 token 成本与吞吐成反比、与利用率成反比。官方 38 美元/GPU 小时的数字是收入量级，不是成本；155T token/天说明规模，但不能直接反推利润。缓存、量化、MoE、推测解码和批处理都能降低成本，但各有约束。定价要覆盖平均成本、冗余和毛利，同时考虑竞争和需求。
