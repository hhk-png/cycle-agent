# 第 44 章 商业分析 III：产品形态、平台与选型

## 44.1 四种产品形态

### 库/框架

- 代表：verl、TRL、OpenRLHF；
- 用户：算法/平台工程师；
- 收费：开源免费 + 支持/培训/企业版；
- 关键：生态、文档、模型支持、性能。

### 托管 API

- 代表：Tinker 等；
- 用户：不想管基础设施的团队；
- 收费：按 token/训练任务；
- 关键：易用、稳定、数据隔离。

### 平台

- 代表：云厂商的 RL 微调/训练平台；
- 用户：企业；
- 收费：GPU 小时/订阅/项目；
- 关键：算力、合规、SLA、生态。

### 垂直解决方案

- 代表：法律/医疗/代码/机器人的 RL 方案；
- 用户：行业客户；
- 收费：项目/结果/席位；
- 关键：场景数据、评测、交付。

## 44.2 用户画像

| 用户 | 需求 | 痛点 |
|---|---|---|
| 研究者 | 算法灵活、可改 | 框架限制、调试难 |
| 算法工程师 | 快速实验、可复现 | 配置复杂、坑多 |
| 平台工程师 | 多租户、稳定、可观测 | 故障、成本、权限 |
| 企业 CTO | ROI、合规、交付 | 数据安全、供应商锁定 |
| 创业者 | 快速验证、低成本 | 算力、数据、人才 |

产品设计要明确服务哪一类用户；试图服务所有人通常导致体验平庸。

## 44.3 功能矩阵

| 能力 | 库 | 托管 API | 平台 | 垂直方案 |
|---|---|---|---|---|
| 自定义算法 | 强 | 弱 | 中 | 弱 |
| 自定义环境/工具 | 强 | 中 | 中 | 强 |
| 多租户/配额 | 弱 | 强 | 强 | 中 |
| 可观测/审计 | 中 | 中 | 强 | 强 |
| 开箱即用 | 弱 | 强 | 中 | 强 |
| 成本可控 | 中 | 强 | 中 | 中 |
| 数据隔离 | 强 | 中 | 强 | 强 |

## 44.4 选型矩阵

企业选型时按权重打分：

| 维度 | 权重 | 说明 |
|---|---|---|
| 模型支持 | 20% | 是否支持你的模型/多模态 |
| 规模 | 15% | 单卡/多机/千卡 |
| 算法 | 15% | PPO/GRPO/DAPO/Agent/蒸馏 |
| 稳定/容错 | 15% | 断点续训、监控、SLA |
| 成本 | 15% | GPU 小时/单位 token |
| 易用 | 10% | 安装/配置/文档 |
| 生态 | 10% | 社区/插件/招聘 |

权重因团队而异；关键是**先写权重再打分**，避免被 demo 带偏。

## 44.5 总拥有成本（TCO）

TCO 不只是 GPU：

```text
TCO = 算力 + 存储 + 网络 + 人力 + 数据/评测 + 支持/培训 + 失败重跑
```

自建常常低估：

- 平台/运维人力；
- 故障处理；
- 安全/合规；
- 版本升级；
- 闲置算力。

托管常常低估：

- 数据迁移/锁定；
- 按量费用的峰值；
- 定制限制；
- 网络延迟。

## 44.6 开源产品的商业化

可行路径：

1. **Open Core**：核心开源，企业功能收费；
2. **托管服务**：开源 + 云托管；
3. **支持/培训**：SLA、咨询、认证；
4. **生态合作**：云/芯片厂商分成；
5. **垂直方案**：基于开源做行业交付。

风险：

- 云厂商“白嫖”托管；
- 社区分叉；
- 企业版与开源版功能冲突；
- 维护成本。

## 44.8 产品化陷阱

- 只做 demo，不做数据/评测闭环；
- 追求“支持所有模型”，每个都不深；
- 忽略长尾/故障，生产不可用；
- 把开源当免费劳动力；
- 定价过低，无法覆盖支持成本；
- 低估企业销售周期。

## 44.9 对 verl 生态的含义

verl 作为开源框架，产品化机会在：

- 托管 RL 服务；
- 企业支持/培训；
- 垂直 recipe/环境；
- 可观测/评测；
- 与云/芯片的合作。

直接“卖 verl”很难；价值在“用 verl 解决具体问题”。

## 44.10 选型评分卡：一个算例

把 44.4 的权重变成可操作的表。评分 1～5，权重合计 100%：

| 维度 | 权重 | 自建 verl | 托管平台 | 垂直方案 |
|---|---:|---:|---:|---:|
| 模型支持 | 20% | 5 | 3 | 2 |
| 规模 | 15% | 5 | 3 | 3 |
| 算法 | 15% | 5 | 2 | 2 |
| 稳定/容错 | 15% | 3 | 5 | 4 |
| 成本 | 15% | 3 | 3 | 2 |
| 易用 | 10% | 2 | 5 | 5 |
| 生态 | 10% | 5 | 3 | 3 |
| **加权总分** | 100% | **4.10** | **3.35** | **2.85** |

计算方式：每列 $\sum w_i s_i$。例如自建 = 0.2×5 + 0.15×5 + 0.15×5 + 0.15×3 + 0.15×3 + 0.1×2 + 0.1×5 = 4.10。

但总分不能直接做决定。先设**红线**：

- 数据不能出域 → 托管平台直接出局；
- 必须有 SLA/审计 → 自建要额外补平台能力；
- 团队没有 GPU 运维 → 自建的“稳定/易用”分数还要下调。

红线之外，再做权重敏感性：如果把“易用”从 10% 提到 25%、“成本”从 15% 降到 5%，权重和变成 105%，归一化后大约自建 3.90、托管 3.62、垂直 3.24——托管缩小了差距，但**没有反超**。要让托管反超，需要把“稳定/易用”的合计权重再提高，或把自建的规模/算法优势打下来；这正说明结论对权重敏感，应该先补信息（试用、访谈、POC），而不是硬选。

敏感性表要写清“归一化”与“未归一化”两种口径；否则权重和不是 100% 时，分数不可比。

最后，评分卡的价值不是“算出唯一答案”，而是**把争论变成可讨论的假设**：为什么给这一项 3 分？有没有证据？把证据附在分数后面，评审才有意义。

## 本章小结

- 产品形态：库、托管 API、平台、垂直方案；服务对象不同。
- 选型要先定权重再打分；TCO 包含人力/数据/失败重跑。
- 开源商业化路径：Open Core、托管、支持、生态、垂直。
- 采购清单覆盖模型、规模、异步、容错、合规、价格、迁移。
- verl 生态的机会在托管/支持/垂直，而不是卖框架本身。
