# 第 45 章 商业分析 IV：投资、创业与职业

## 45.1 投资论点

RL 后训练的长期价值来自：

- 模型能力从“预训练 scaling”转向“后训练/推理时计算”；
- 企业需要私有化、可验证、可审计的后训练；
- Agent 需要环境、工具、过程奖励；
- 在可验证任务上，小模型 + RL 可能接近大模型效果，从而降低推理成本；这不是普遍规律，必须按任务验证。

但要注意：

- 框架层开源、毛利低；
- 云厂商/芯片厂商有分发优势；
- 技术路线可能被 SFT/蒸馏/合成数据部分替代；
- 客户预算集中在头部。

## 45.2 市场时机

判断信号：

- 云厂商推出托管 RL 产品；
- 企业从 POC 转向生产；
- 推理成本下降；
- 开源项目进入“平台化”；
- 监管/合规要求出现。

如果这些信号同时出现，说明市场从“早期采用者”进入“早期多数”。

## 45.3 尽职调查清单

- 技术：架构、规模、故障率、模型支持、性能数据；
- 数据：数据来源、授权、隐私、评测；
- 客户：付费意愿、续约、案例；
- 团队：工程/研究/销售能力；
- 竞争：云厂商/开源/其他创业公司；
- 成本：GPU/人力/支持；
- 法律：开源许可证、专利、合规。

## 45.4 风险

- 技术风险：异步/多模态/长序列的工程难度；
- 市场风险：需求集中在头部，长尾付费弱；
- 竞争风险：云厂商捆绑、开源商品化；
- 成本风险：算力价格/利用率；
- 监管风险：Agent/工具/数据；
- 团队风险：RL 系统工程人才稀缺。

## 45.5 创业方向

- 垂直 RL 方案（法律/医疗/代码/机器人）；
- 数据/验证器/沙箱；
- 评测/可观测性；
- 托管 RL 平台；
- 面向 Agent 的环境/工具。

不建议：

- 又一个通用 PPO 框架；
- 只做 demo 的应用；
- 依赖单一云/单一模型的方案。

## 45.6 职业角色

| 角色 | 核心能力 | 产出 |
|---|---|---|
| RL 算法工程师 | PPO/GRPO/DAPO、reward、评测 | 算法与实验 |
| RL 基础设施工程师 | 分布式、FSDP/Megatron、vLLM、Ray | 训练系统 |
| 平台工程师 | Kubernetes、调度、多租户、可观测 | 平台 |
| 应用/解决方案 | 行业、数据、交付 | 客户价值 |
| 研究者 | 新算法、论文、benchmark | 影响力 |

## 45.7 技能树

**算法**：

- 策略梯度/PPO/GAE/GRPO/DAPO/GSPO；
- KL/entropy/loss aggregation；
- reward modeling/verification；
- 评测/pass@k/统计。

**系统**：

- PyTorch/FSDP/Megatron；
- vLLM/SGLang；
- Ray/placement group；
- NCCL/IB；
- checkpoint/merge；
- 异步/队列/容错。

**工程**：

- Python/C++；
- 分布式调试；
- profiler；
- 数据管道；
- 云/容器。

## 45.8 作品集建议

- 一个可运行的 MiniVerl（本教程）；
- 一个真实 verl 的小规模实验（0.5B/7B）；
- 一篇技术分析（性能/算法/对比）；
- 一个垂直场景的 reward/评测；
- 一份可复现的实验报告。

面试时能讲清：

- 一次 PPO 更新的数据流；
- 权重同步的字节账；
- 为什么 GRPO 不需要 critic；
- 如何定位“reward 涨但验证不涨”；
- 如何把吞吐提升 2 倍。

## 45.9 面试题示例（商业/系统设计向）

技术自测题见附录 F；这里更偏“把技术放进业务”的能力：

1. 为一个新领域设计 RLVR 的奖励与验证集，你会先做什么、如何验收？
2. 给定 8×H100 与 7B 模型，估算一次 GRPO 实验的成本、瓶颈与失败预算。
3. “训练 reward 涨、验证不涨”，给出 30 分钟内的排查计划与证据清单。
4. 设计一个多租户 RL 平台的资源隔离、配额与计费口径。
5. 向 CTO 论证 build vs buy：需要哪些数据、如何做敏感性分析？
6. 设计 Agent RL 的工具协议、沙箱池与幂等/回放机制。
7. 比较两个 RL 框架并给出选型建议：权重、红线、验证方式。
8. 把训练吞吐提升 2 倍：如何测量、归因、验证不是“假提升”？
9. 设计数据飞轮：合成、过滤、难度分层、污染控制、版本化。
10. 上线后模型回退：如何保证 checkpoint、配置、tokenizer 与评测都可复现？

## 45.11 从学习到落地：90 天计划

8 周学习计划解决“知道”，90 天计划解决“做出来”。一个可执行的节奏：

### 第 1～30 天：建立基线

- 读完第 1～5、9～14 章；
- 跑通 MiniVerl 全部示例，改一个 reward/算法并补测试；
- 在真实 verl 上跑 0.5B 的 PPO 与 GRPO，记录耗时、显存、指标；
- 产出：一份“一次 PPO 更新的数据流”笔记 + 一个可复现实验。

### 第 31～60 天：做一个完整实验

- 选一个可验证任务（数学/代码/结构化抽取）；
- 建 200～500 条验证集，写独立 reward 与评测；
- 跑 GRPO → DAPO 的对照，至少 2 个 seed；
- 记录 manifest、成本、失败案例；
- 产出：一份带消融的实验报告（不是“loss 曲线截图”）。

### 第 61～90 天：加一个“生产维度”

四选一：

1. **规模**：7B/32B、FSDP2/Megatron、多机；
2. **Agent**：多轮工具、observation mask、沙箱；
3. **性能**：profile → 优化 rollout/同步，报告端到端提升；
4. **平台**：断点续训、监控、灰度、成本模型。

产出：一个能讲 30 分钟的项目复盘，包含目标、基线、方案、数据、结果、失败与下一步。

### 每周节奏

```text
周一：定一个可验证的问题
周二～周四：实现 + 小规模实验
周五：复盘（指标、失败、下周假设）
周末：读一篇论文/一个 recipe，写 300 字摘要
```

不要用“跑了多少 step”衡量进度，用“回答了什么可验证的问题”衡量。

### 作品集矩阵

| 作品 | 证明什么 | 最低要求 |
|---|---|---|
| MiniVerl 扩展 | 系统理解 | 新 reward/算法 + 测试 |
| 真实 verl 实验 | 工程能力 | 可复现 manifest + 消融 |
| 性能报告 | 调优能力 | profile + 端到端数据 |
| Agent/多模态项目 | 场景能力 | 环境/工具/评测闭环 |
| 技术文章 | 表达能力 | 有数据、有失败、有结论 |

## 45.12 最后的建议

- 先把同步文本 RL 做对，再谈异步/多模态/Agent。
- 数据、奖励、评测是长期资产；框架会换。
- 能跑通不等于正确；用测试、对照、审计验证。
- 性能优化先 profile，再动手。
- 商业上，解决具体问题比“支持所有功能”更有价值。

## 45.13 一页纸备忘录：把前四章压缩成一个决策

商业分析最容易犯的错，是写成一堆“RL 很重要”的论述，却没有一个可被否决的决策。一页纸备忘录（one-page memo）强迫你回答：**为谁、解决什么、凭什么、花多少、什么时候验证、如果错了怎么办**。

### 模板

```text
标题：一句话说明要做的决策
1. 问题：谁在什么场景下，因什么损失而痛
2. 方案：产品形态（库/API/平台/垂直）+ 训练/推理技术栈
3. 证据：已有数据、POC、客户访谈、竞品缺口
4. 单位经济：价格、算力/人力成本、毛利、回收期
5. 壁垒：数据、环境、评测、工作流、生态（按可持续性排序）
6. 风险：技术、需求、合规、供应商、现金
7. 里程碑：30/90/180 天各自验证什么假设
8. 资源与 ask：人、卡、钱；如果只给一半，砍什么
9. 反事实：什么信号出现就停止/转向
```

### 一个算例（全部为假设）

假设做“面向中型软件团队的代码 Agent RL 平台”：

| 项 | 假设值 | 说明 |
|---|---:|---|
| 目标客户 | 5,000 家 | 有 50+ 研发、已用 Copilot 类工具 |
| 年费 | $120k | 按 100 席位 × $100/月 |
| SAM | $600M | 5,000 × $120k，未打折 |
| 单客户月算力 | $6k | 64×H100、60% 利用率、$2.5/GPU-h |
| 单客户月支持 | $2k | 1/5 个解决方案工程师 |
| 毛利率 | ~33% | ($10k - $8k)/$10k，未计研发 |
| 单次改进周期 | $20k | 数据/训练/评测/回归 |
| 客户年节省 | $300k | 返工、评审、缺陷逃逸，需 POC 验证 |

单位经济的关键不是毛利率，而是**客户节省是否可归因**。如果客户无法把“缺陷率下降”归因到你的模型，续费就会变成“预算削减的第一项”。

### 里程碑与停止条件

| 时间 | 要验证的假设 | 通过标准 | 不通过就 |
|---|---|---|---|
| 30 天 | 任务可验证、reward 与人工判断一致 | 验证集与人工一致率 ≥ 85% | 换任务/换 reward |
| 90 天 | RL 相对 SFT 有可测提升 | 同模型 pass@1 +5pt，2 seed 可复现 | 回到数据/评测 |
| 180 天 | 客户愿意为提升付费 | ≥3 个付费 POC，ACV ≥ $80k | 转工具/服务 |
| 12 个月 | 毛利与续费可持续 | 毛利 ≥ 50%，续费 ≥ 80% | 缩窄场景 |

停止条件要写进备忘录，而不是等董事会问。例如：

- 两个季度内拿不到 3 个付费 POC；
- RL 提升在 2 个 seed 下都小于 2pt；
- 单客户算力成本超过价格的 60%；
- 关键数据/环境无法合法获取。

### 五个常见谬误

1. **把 TAM 当收入**：TAM 是“理论上限”，不是“今年能卖多少”。备忘录里必须同时写 SAM/SOM 与获客路径。
2. **用训练 loss 证明价值**：客户买的是通过率、缺陷率、人工节省；loss 只是内部指标。
3. **忽略失败成本**：RL 实验的失败率很高；预算要包含重跑、数据返工与评测建设（第 43 章）。
4. **把开源当护城河**：verl 是 Apache-2.0；壁垒在数据、环境、评测与工作流，不在“我们用了 verl”。
5. **没有停止条件**：只写“乐观/基准”，不写“什么情况下不做”，备忘录就不可执行。

### 一页纸检查清单

- [ ] 一句话能说清决策与目标客户。
- [ ] 有一个可验证的任务与独立评测，不依赖训练 reward。
- [ ] 单位经济写清算力、人力、失败重跑与毛利。
- [ ] 至少一个竞品/替代方案对比（build vs buy）。
- [ ] 30/90/180 天里程碑各自对应一个可证伪的假设。
- [ ] 写了停止条件与“只给一半资源时砍什么”。
- [ ] 所有数字标注“假设/实测”，并给出敏感性区间。

写不出这一页，通常不是“商业分析还不够”，而是**技术方案还没有收敛到一个可验证的价值主张**。先回到第 17 章（奖励）、第 24 章（评测）与第 43 章（成本），把可验证性补齐。

## 本章小结

- RL 后训练的投资价值在“后训练/Agent/私有化/成本”，但框架层竞争激烈。
- 创业应做垂直/数据/评测/平台，而不是又一个通用框架。
- 职业角色分算法、基础设施、平台、应用、研究；技能树跨算法/系统/工程。
- 作品集与面试要能讲清数据流、同步、算法、调优与商业。
- 8 周学习计划把教程、MiniVerl、真实 verl 与商业分析串起来。
- 一页纸备忘录把技术方案收敛为可证伪的决策：目标客户、证据、单位经济、里程碑、停止条件。
