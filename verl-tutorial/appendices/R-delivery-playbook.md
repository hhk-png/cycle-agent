# 附录 R 项目交付与实验复盘手册

> 本附录把前面 45 章的技术内容收束成一个可执行的项目流程：**如何把一个“想用 RL 提升模型能力”的想法，变成可验收、可复现、可上线的交付物。**
>
> 它不是项目管理模板的堆砌，而是针对 RL 项目特有的失败模式：奖励写错、数据泄漏、基线不公平、实验不可复现、成本失控、上线后回退不了。

## R.1 先定义交付物

一个 RL 项目至少有六类交付物。只交“一个 checkpoint”通常不算完成。

| 交付物 | 内容 | 验收人 |
|---|---|---|
| 问题定义 | 目标能力、基线、成功指标、失败边界 | 业务/产品 |
| 数据资产 | 训练/验证/测试集、去重与污染报告 | 数据/评测 |
| 奖励与评测 | reward 函数、验证器、人工抽查协议 | 算法/评测 |
| 训练配方 | 配置、代码版本、资源、成本 | 平台/算法 |
| 模型产物 | checkpoint、合并后的 HF 模型、推理配置 | 工程/部署 |
| 复盘报告 | 曲线、消融、失败案例、下一步 | 全体 |

一个常见的“伪交付”是：训练 reward 涨了，但没有独立验证集、没有基线、没有回滚方案。这样的结果无法判断是模型变好，还是奖励被 hack。

## R.2 30 / 60 / 90 天节奏

### 第 0～30 天：可行性与基线

- 选一个**可验证**的任务（数学、代码、结构化抽取、工具调用），不要一上来做开放域对话；
- 建 200～1000 条高质量验证集，人工确认答案；
- 跑通 SFT/提示词/更大模型三个基线；
- 用 MiniVerl 验证 reward、mask、advantage 的语义；
- 在真实 verl 上跑 0.5B～1.5B 的 PPO/GRPO smoke test；
- 产出：基线报告、数据 v0、reward v0、第一版成本估算。

**Go/No-Go 标准**：如果提示词/更大模型/蒸馏已经能达到目标，RL 可能不是最优解。先证明“RL 有增量”，再投入大规模。

### 第 31～60 天：小规模 RL

- 固定数据 v1、reward v1、评测协议；
- 7B～8B、8 卡、sync 模式，跑 GRPO/DAPO；
- 做至少三组消融：无 RL、RL + 不同 n、RL + 不同 KL/clip；
- 记录每条曲线的配置、seed、代码 commit；
- 产出：第一版 RL 模型、消融报告、失败案例集。

**Go/No-Go 标准**：验证集提升是否超过噪声？是否在多个 seed 上成立？是否以长度爆炸/reward hacking 为代价？

### 第 61～90 天：规模化与上线准备

- 加规模（32B/Megatron/多机）或加任务复杂度（多轮/Agent/多模态）；
- 异步/PD/TransferQueue 只在有明确吞吐瓶颈时引入；
- 做容错、断点续训、监控、成本上限；
- 做灰度/回滚方案与推理服务压测；
- 产出：可上线 checkpoint、部署手册、RTO/RPO、成本模型。

## R.3 项目章程：一页纸

在写任何训练脚本前，先填完这一页：

```text
目标能力：
当前基线（模型/提示词/SFT）：
成功指标（主指标 + 护栏指标）：
失败边界（哪些行为不可接受）：
数据来源与授权：
验证集构造与污染控制：
奖励函数与版本：
训练资源与预算上限：
上线形态与回滚方案：
```

“护栏指标”常被忽略：正确率提升但长度翻倍、延迟翻倍、拒绝率上升，都是失败。至少同时监控：

- 正确率/通过率；
- 平均/尾部长响应长度；
- 推理延迟与成本；
- 安全/拒答/格式合规；
- 人工抽查通过率。

## R.4 数据：先做减法

RL 数据不在多，而在“有区分度”。启动前做四件事：

1. **去重**：精确去重 + 近似去重（MinHash/SimHash）；同一道题的不同表述会放大训练信号。
2. **难度分层**：用基线模型采样，把样本分成“全对/全错/有区分度”三组；全对/全错组对 GRPO 没有梯度。
3. **污染检查**：训练集与验证集、公开 benchmark 的去重；时间切分；canary 字符串。
4. **版本化**：数据 manifest 记录来源、过滤规则、哈希、生成脚本与日期。

一个实用的数据配比：

```text
60% 有区分度的主任务
20% 稍难/课程样本（当前模型偶尔能做对）
10% 简单样本（防止遗忘/稳定格式）
10% 多样性/通用样本（防止过拟合）
```

比例不是教条；关键是**监控每组的 reward 均值与方差**，全 0/全 1 的组要及时替换。

## R.5 奖励与评测：两套独立的东西

奖励是训练目标，评测是验收标准。二者必须**独立实现**，否则奖励的 bug 会同时污染训练和验收。

最低要求：

- reward 函数有单元测试与 golden 样本；
- 验证集 reward 与训练 reward 使用同一 parser，但验证指标由独立脚本计算；
- 人工抽查 50～100 条验证输出，记录错误类型；
- 对 reward hacking 有专门检查：长度、格式、重复、抄 prompt、测试泄漏；
- 评测报告写清采样参数（temperature/top-p/n）与 parser 版本。

一个常见的自欺：训练 reward 从 0.3 涨到 0.7，但验证集用的是同一个有 bug 的 parser，真实正确率没变。独立的评测脚本能在第一天就抓到这个问题。

## R.6 训练配方：从简单到复杂

推荐顺序：

1. **SFT 冷启动**（如果需要格式/工具协议）；
2. **GRPO + 规则奖励**（n=8，sync，FSDP2）；
3. **DAPO 改进**（clip-higher、动态过滤、token-level loss、overlong penalty）；
4. **规模/异步**（只有在吞吐成为瓶颈时）；
5. **蒸馏/拒绝采样**（把大模型或成功轨迹迁移到小模型）。

不要一开始就上：

- fully async + 大 staleness；
- 多 teacher 蒸馏 + PPO + MTP；
- 多模态 + 多轮 Agent + PD 分离。

每加一个复杂度，都要能回答：它解决了哪个已测量的瓶颈？如果没有测量，就是猜测。

## R.7 实验记录：让三个月后的你能复现

每次实验至少记录一个 manifest：

```yaml
experiment_id: grpo-qwen3-8b-dapo-v3
code:
  repo: verl
  commit: <sha>
  dirty: false
config:
  file: configs/dapo_8b.yaml
  hash: <sha256>
data:
  train: s3://.../train-v3.parquet
  train_hash: <sha256>
  val: s3://.../val-v2.parquet
  val_hash: <sha256>
model:
  base: Qwen/Qwen3-8B
  tokenizer_hash: <sha256>
reward:
  version: reward-v4
  hash: <sha256>
runtime:
  gpu: 8xH100
  cuda: "13.0"          # v0.9.1 的 torch 2.11/vLLM 0.24 是 cu130 轮子；自定义 cu128 构建需另注
  torch: "2.11.0"
  vllm: "0.24.0"
  verl: "0.9.1"
seed: 1234
deterministic: false
metrics:
  val_accuracy: 0.71
  val_pass@8: 0.89
  response_length_mean: 812
  cost_usd: 420
```

没有 manifest 的实验，三个月后就是“某个 wandb run”。记录成本与硬件同样重要：同样的指标，成本翻倍就是退步。

## R.8 失败复盘模板

RL 项目的失败通常不是“代码报错”，而是“曲线不对”。复盘时按固定顺序写：

```text
现象：训练 reward 涨，验证不涨；response length 从 600 涨到 1400。
时间线：第 120 步开始分叉；之前改过 reward v3 → v4。
数据：训练/验证分布差异？验证集是否泄漏？
奖励：v4 是否给长度加分？人工抽查 30 条。
算法：advantage 方差、clipfrac、KL、entropy 是否异常？
系统：rollout/actor log-prob 是否一致？权重同步版本？
结论：reward v4 的格式奖励权重过高，模型学会写长格式。
动作：回退 reward，加入长度惩罚，重跑 3 个 seed。
```

复盘的价值在于**把“感觉”变成可检验的假设**。每条结论都要指向一个指标或一组样本；不要写“可能是超参问题”就结束。

## R.9 成本与资源计划

用第 43 章的成本公式做预算，但不要只算 GPU：

```text
GPU 小时 = steps × 每步秒数 × GPU 数 / 3600
直接算力 = GPU 小时 × 单价
总成本 ≈ 直接算力 × (2～5)     # 数据、评测、工程、失败重跑（与第 43 章一致）
```

预算要设三道闸：

1. **单次实验上限**：超过即停止，避免坏配置烧钱；
2. **项目总上限**：按阶段分配（可行性/小规模/规模化）；
3. **回滚预算**：上线后出问题，回滚与重训也要钱。

成本优化的顺序：先提高利用率（长尾/异步/prefix cache），再换更小模型/LoRA，最后才考虑降精度/减数据。

## R.10 上线与回滚

上线前至少确认：

- 推理服务能加载合并后的 checkpoint；
- 同一 prompt 在训练引擎与推理引擎上的输出分布一致；
- 有 A/B 或灰度流量；
- 有回滚到上一版模型的开关；
- 有在线指标（成功率、延迟、成本、安全）；
- 有数据回流与再训练路径。

回滚不是“再训练一次”。回滚要求：

- 旧 checkpoint 与推理配置可复现；
- 数据/配置有版本；
- 线上流量能快速切回；
- 回滚后的指标与之前基线一致。

一个常见事故是“只保存了 actor，没保存 tokenizer/chat template/推理参数”，回滚后输出格式全变。checkpoint 要包含模型、tokenizer、配置与版本元数据。

## R.11 交付检查清单

- [ ] 问题定义、基线、成功指标、护栏指标写清楚。
- [ ] 数据去重、难度分层、污染检查、manifest 完成。
- [ ] reward 与评测独立实现；golden 样本与人工抽查通过。
- [ ] 至少三个 seed/消融，结论不是单点噪声。
- [ ] 训练配置、代码 commit、环境版本可复现。
- [ ] 成本在预算内；有单次实验与项目总上限。
- [ ] checkpoint 含模型、优化器、tokenizer、配置、版本。
- [ ] 推理服务加载/压测/灰度/回滚演练完成。
- [ ] 监控覆盖质量、延迟、成本、安全。
- [ ] 复盘报告包含失败案例与下一步。

## R.12 两个缩略案例

### 数学 RLVR

- 数据：GSM8K/MATH 风格，答案可验证；按基线通过率分三组。
- 奖励：精确匹配 + 格式；格式权重低，避免只学格式。
- 算法：GRPO n=8 → DAPO（clip-higher + 动态过滤 + overlong）。
- 关键指标：验证 pass@1、pass@8、response length、reward hacking 抽查。
- 常见失败：答案抽取与训练模板不一致；长度爆炸；全对组无梯度。

### 代码 Agent

- 数据：仓库级任务 + 单元测试；工具是 shell/编辑器/测试运行器。
- 奖励：测试通过率 + 编译/格式；沙箱超时记 0。
- 算法：多轮 GRPO，observation mask=0；奖励穿过工具 span。
- 关键指标：任务通过率、工具调用成功率、轮次、沙箱失败率、成本/任务。
- 常见失败：测试泄漏；工具输出 token 被算进损失；多轮 tokenizer 错位；沙箱不稳定。
