# 第 32 章 商业分析（三）：TCO、ROI 与决策

> 本章的数字是**模型示例**，不是报价或市场事实。实际值取决于 GPU 价格、利用率基线、团队成本、电价/机房、合同条款。

## 32.1 一个 512 卡集群的账

假设：

- 512 张 GPU；
- 按需价格 $2/GPU-hour（示例，A100/H100 的实际价格随合同/地区波动很大）；
- 年运行 8,760 小时；
- 当前平均利用率 55%；
- 忽略存储/网络/电力/人力，只看 GPU 算力成本。

年 GPU 成本：

```text
512 × $2 × 8,760 = $8,970,240 ≈ $8.97M
```

有效算力（被使用的 GPU-hour）：

```text
512 × 8,760 × 0.55 = 2,466,816 GPU-hour
```

每有效 GPU-hour 的成本：

```text
$8.97M / 2.4668M ≈ $3.64
```

如果调度/配额把利用率从 55% 提到 65%：

```text
有效算力 = 512 × 8,760 × 0.65 = 2,915,328 GPU-hour
每有效 GPU-hour = $8.97M / 2.9153M ≈ $3.08
成本下降 = 1 - 3.08/3.64 ≈ 15.4%
```

两种解读：

- **需求固定、可以缩容**：同样的工作量只需更少 GPU，年省约 $1.38M。
- **集群固定、需求增长**：同样的钱多做约 18.2% 的工作（0.65/0.55 - 1），等价算力价值约 448,512 GPU-hour × $2 ≈ $0.90M（按边际价格计）。

不要把两种口径混在一起宣称“省了 15% 又多了 18%”。

## 32.2 调度器的成本

| 成本项 | 示例范围 | 说明 |
|---|---|---|
| 软件许可 | $0 | Volcano Apache-2.0 |
| 集成/迁移 | $50k–$300k 一次性 | 队列设计、迁移、测试 |
| 运维人力 | 0.5–2 FTE | 调度器/控制面/监控 |
| 支持订阅 | $0–$500k/年 | 第三方支持/SLA |
| 培训 | $10k–$50k | 平台团队/用户 |
| 可观测性 | $20k–$100k/年 | Prometheus/Grafana/日志 |
| 迁移风险 | 难以量化 | 停机/回滚/机会成本 |

假设年化总成本 $500k（2 FTE + 支持 + 工具）。则：

```text
盈亏平衡所需的成本下降 = 500k / 8.97M ≈ 5.6%
在 55% 基线下，所需的利用率提升 ≈ 0.55 × 0.056 / (1 - 0.056) ≈ 3.3 个百分点
```

也就是说，**在 512 卡、$2/卡时、55% 利用率的假设下，利用率提升约 3.3pp 就能覆盖 $500k/年的调度器成本**。如果提升 10pp，ROI 很高。

### 32.2.1 如何测量基线利用率

ROI 模型最容易被质疑的地方不是公式，而是“55% 是怎么来的”。如果基线不可复现，节省金额就没有说服力。建议把利用率拆成三个口径，分别测量：

| 口径 | 定义 | 数据源 | 用途 |
|---|---|---|---|
| 分配率 | 已分配 GPU / 总 GPU | `volcano_queue_allocated`、Pod requests | 容量与配额 |
| 实际利用率 | GPU 忙时间 / 可用时间 | DCGM `DCGM_FI_DEV_GPU_UTIL`、`nvidia-smi` | 真实效率 |
| 有效作业率 | 有作业在跑的卡时 / 总卡时 | 作业提交/完成记录 | 业务视角 |

三者关系：

```text
分配率 ≥ 实际利用率
有效作业率 ≤ 分配率
```

一个常见的“利用率很高”的假象：队列分配率 90%，但 GPU 实际利用率只有 40%——作业占着卡在等数据、等 checkpoint、等别的 worker。只看分配率会高估调度器的价值。

一个可复现的测量步骤：

1. **固定窗口**：至少 4 周，覆盖发薪日/月末等业务高峰。
2. **按队列/型号分组**：A100 与 H100、训练与推理分开算；混在一起会掩盖结构问题。
3. **同时记录等待时间**：P50/P95 从提交到 Running，按优先级分组。
4. **记录碎片**：每个 tick 的“最大可调度 gang”与总空闲 GPU 的比值。
5. **记录抢占/回收**：次数、受影响作业数、平均恢复时间。
6. **保留原始数据**：Prometheus 快照 + 作业表，便于复算。

PromQL 示意（指标名以你的环境为准）：

```promql
# 集群 GPU 分配率（按队列）
sum by (queue_name) (volcano_queue_allocated_scalar_resources{resource="nvidia.com/gpu"})
  / sum by (queue_name) (volcano_queue_deserved_scalar_resources{resource="nvidia.com/gpu"})

# 节点 GPU 实际利用率（DCGM）
avg by (node) (DCGM_FI_DEV_GPU_UTIL)

# 等待时间 P95（Volcano 没有内置作业等待直方图；需自建 exporter 或离线表，
# 下面的指标名只是示意）
histogram_quantile(0.95, sum by (le, queue) (rate(volcano_job_wait_seconds_bucket[1h])))
```

如果没有作业级直方图，用离线表更可靠：

```sql
SELECT queue,
       percentile_cont(0.95) WITHIN GROUP (ORDER BY started_at - submitted_at) AS p95_wait
FROM jobs
WHERE submitted_at >= now() - interval '28 days'
GROUP BY queue;
```

测量时的五个坑：

1. **平均的平均**：先算每个节点的日均值再平均，与全局加权平均不同；报告时写清楚口径。
2. **MIG/vGPU 的逻辑卡**：1 张物理卡切成 4 份，分配率可能按逻辑卡算到 400%，不能与物理卡直接比。
3. **空闲但已分配**：Pod 占着卡不干活，分配率高、实际利用率低；这是“调度问题”还是“作业问题”要分开。
4. **样本缺失**：节点刚加入、DCGM exporter 挂掉，都会让分母偏小；先补数据再算。
5. **窗口偏差**：只选业务低谷的 4 周，会低估等待时间、高估利用率。

一个诚实的 ROI 报告应该同时给出：

```text
基线：分配率 78%，实际利用率 55%，P95 等待 42 分钟
改进：分配率 85%，实际利用率 65%，P95 等待 18 分钟
口径：4 周，A100 384 卡，训练队列，排除故障窗口
```

只写“利用率提升 10pp”而不写口径，采购评审时一定会被追问。

### 32.2.2 用计算器复算，而不是手算

本教程附带一个只依赖标准库的计算器，把本章的 GPU 成本、队列份额、训练时间、KV cache 和推理副本放进同一份报告：

```bash
cd Volcano-tutorial
python scripts/capacity_model.py --selftest
python scripts/capacity_model.py \
  --gpus 512 --price 2 --hours 8760 \
  --baseline 0.55 --improved 0.65 --annual-cost 500000 \
  --queue train:3:120:400 --queue infer:1:60:160
```

它不会替你判断“55% 基线是否可信”，但会保证：

- 年成本、每有效 GPU-hour、两种节省口径的算法一致；
- `Σ guarantee` 是否超过可用容量；
- 训练时间是否用了实测 MFU，而不是峰值；
- 推理副本是否按目标利用率向上取整并加了冗余。

## 32.3 敏感性分析

“需求固定、可缩容”口径下，年省金额 = GPU 年成本 × (1 - base/(base+improvement))。

以 $8.97M/年为例：

| 基线利用率 | +2pp | +5pp | +10pp |
|---|---:|---:|---:|
| 40% | $0.43M | $1.00M | $1.79M |
| 55% | $0.31M | $0.75M | $1.38M |
| 70% | $0.25M | $0.60M | $1.12M |

结论：

- 基线越低，提升空间越大；
- 同样的 pp 提升，在低基线下的相对收益更高；
- 高基线（70%+）下，调度器的边际收益下降，重点转向碎片/拓扑/公平。

## 32.4 除了利用率，还有什么价值

- **等待时间下降**：高优先级作业更快开始，业务价值难以直接折算，但影响用户满意度/收入。
- **运维效率**：统一队列/配额/观测，减少人工协调。
- **碎片减少**：大 gang 可调度，减少“有卡但跑不了”。
- **公平/合规**：多租户配额、审计。
- **故障恢复**：更快的重启/重调度。
- **成本可视化**：Showback/Chargeback。

这些价值往往比“省几台 GPU”更难量化，但在企业采购中同样重要。

## 32.5 定价模式

以下是**示意性**的商业模式，不是市场报价：

| 模式 | 定价锚点 | 优点 | 缺点 |
|---|---|---|---|
| 支持订阅 | 每集群/每年 $50k–$250k | 可预测、轻交付 | 需要 SLA/团队 |
| 按 GPU 订阅 | 每 GPU/年 $50–$300 | 与价值挂钩 | 客户可能觉得贵 |
| 托管服务 | 基础设施支出的 5%–15% | 高粘性 | 需要云/运维能力 |
| 平台许可 | $200k–$1M/年 | 适合大客户 | 销售周期长 |
| 培训/认证 | 每人 $2k–$5k | 低门槛 | 规模有限 |
| 垂直方案 | 项目制 | 高客单 | 交付重 |

开源项目的挑战：软件本身免费，客户会问“为什么付费”。答案必须是：

- SLA/兜底；
- 补丁/升级；
- 调优/最佳实践；
- 合规/审计；
- 培训；
- 定制开发。

## 32.6 Build vs Buy vs Managed

| 方案 | 年成本（示意） | 时间 | 风险 |
|---|---|---|---|
| 自研调度器 | 4–8 工程师 × $150k–$250k = $0.6M–$2M | 12–24 个月 | 高（招聘/维护/正确性） |
| 开源自运维 | 0 许可 + 1–2 FTE | 1–3 个月 | 中（排障/升级） |
| 商业支持 | $100k–$500k | 2–6 周 | 低 |
| 托管平台 | 基础设施的 5%–15% | 1–4 周 | 低（锁定） |

决策要点：

- 如果调度是核心竞争力 → 自研/深度定制；
- 如果调度是支撑能力 → 开源 + 支持/托管；
- 如果团队 < 3 人且无 K8s 专家 → 托管。

## 32.7 采购 RFP 问题清单

1. 支持哪些作业类型/框架？gang 的最小单位？
2. 队列模型：层级、权重、guarantee、capability、borrow/lend？
3. 抢占/回收：同队列/跨队列？gang 粒度？PDB？
4. 拓扑：HyperNode/机架/ NUMA？自动发现？
5. 设备：MIG/vGPU/vNPU/DRA？队列配额？
6. 规模：最大节点/Pod/作业数？吞吐/延迟？
7. HA：leader election、多副本、故障切换时间？
8. 安全：RBAC、webhook、CVE 响应、审计？
9. 可观测性：指标/事件/explain/what-if？
10. 升级：CRD 兼容、回滚、支持窗口？
11. 支持：SLA、响应时间、补丁、培训？
12. 参考客户：同规模/同行业？
13. 退出：数据/配置可迁移？是否锁定？
14. 路线图：推理/Agent/DRA/多集群？

### 32.7.1 采购谈判的五个杠杆

RFP 问完，真正影响价格的通常是这五个杠杆：

| 杠杆 | 怎么用 | 注意 |
|---|---|---|
| 合同期限 | 1 年 vs 3 年，年单价差 10%–25% | 不要用过长合同锁定未成熟功能 |
| 计价单位 | 按集群、按 GPU、按利用率 | 按 GPU 计价要把闲置/故障卡的口径写清楚 |
| 支持范围 | 7×24 vs 5×8、响应时间、是否含调优 | “支持”不等于“驻场”，写进 SLA |
| 退出条款 | 配置/数据可导出、源码/镜像可保留 | 开源底座是最大议价筹码 |
| 参考案例 | 同规模/同行业 | 让对方提供可联系的客户，不只是 logo |

谈判前先算清自己的 BATNA（最佳替代方案）：开源自运维的成本、托管平台的报价、继续用默认调度器的损失。没有 BATNA 的谈判只会变成压价。

## 32.8 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| 利用率提升不达预期 | ROI 为负 | 先 pilot，测基线，分阶段 |
| 运维复杂度被低估 | 故障/人力 | 培训、支持、runbook、HA |
| 与默认调度器冲突 | 资源重复分配 | 节点池隔离/统一调度 |
| 版本升级破坏 | 停机 | 灰度、回滚、CRD diff |
| 供应商锁定 | 议价权下降 | 开源底座、可迁移配置 |
| 安全漏洞 | 合规/事故 | patch 线、审计、最小权限 |
| 团队流失 | 知识断层 | 文档、培训、外部支持 |

## 32.11 采购评分卡

把“感觉哪个好”变成可讨论的分数。权重按你的约束调整，下面是示例：

| 维度 | 权重 | 评分要点 | 1 分 | 5 分 |
|---|---:|---|---|---|
| 功能匹配 | 25% | gang/队列/拓扑/设备 | 缺关键能力 | 全部覆盖且 GA |
| 运维成本 | 20% | 部署/升级/排障/人力 | 需专人 | 托管/自动化 |
| 性能规模 | 15% | 节点/Pod/吞吐/尾延迟 | 不达规模 | 有 benchmark 证据 |
| 生态集成 | 15% | Kueue/Ray/Kubeflow/LWS | 无集成 | 原生/社区活跃 |
| 支持与 SLA | 10% | 响应/补丁/培训 | 社区 only | 7×24 + 赔付 |
| 安全合规 | 10% | RBAC/CVE/审计 | 缺项 | 通过审计 |
| 退出成本 | 5% | 配置/数据可迁移 | 锁定 | 开源底座可迁移 |

用法：

1. 先定“一票否决项”（例如不支持 gang、无 PDB、无法回滚），不满足直接淘汰；
2. 再按权重算总分，但**不要只看总分**：把差距最大的两项拿出来讨论；
3. 对每个分数要求证据（benchmark、POC、参考客户），不接受“销售说可以”；
4. 把评分卡和 TCO 模型放在一起看：功能强但运维成本高，可能不如简单方案。

一个常见错误是把权重设成“功能 60%”。调度器的失败往往不是功能不够，而是运维/规模/退出成本被低估。

## 32.12 本章小结

- 512 卡、$2/卡时、55% 利用率下，年 GPU 成本约 $8.97M；提升 10pp 可省约 $1.38M（缩容口径）或多做 18.2% 的工作（增量口径）。
- $500k/年的调度器成本，在 55% 基线下约需 3.3pp 利用率提升即可打平。
- 利用率之外，等待时间、运维效率、公平/合规同样有价值。
- 定价模式：支持订阅、托管、平台许可、培训；开源软件本身不收费。
- 采购要问规模、gang、拓扑、设备、HA、安全、升级、支持、退出。
- 自研/开源/托管的选择取决于调度是否核心竞争力与团队能力。
