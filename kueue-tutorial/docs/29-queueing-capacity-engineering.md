# 第 29 章 · 排队论与容量工程：把"配额够不够"算清楚

前 28 章讲语义、算法和落地。本章换一种语言：**用排队论和离散事件模拟回答"配额应该配多少、等待时间会多长、什么时候会雪崩"。**

配额讨论里最常见的两句话是：

- "集群利用率只有 60%，为什么我的 8 卡作业还要等？"
- "把 nominal 总和压到物理容量的 80%，利用率不就上去了吗？"

这两句话都忽略了一个事实：**GPU 作业不是可以任意切分的流量，而是需要多个资源同时到位的"批量到达、批量服务"系统。** 本章给出可计算的模型，并提供一个可以跑的模拟器 `scripts/capacity_model.py`。

> 本章的数字用于建立直觉，不是生产承诺。真实容量规划要用你自己的到达过程、作业大小分布、运行时长分布和调度策略校准。

## 29.1 三个必须分开的问题

容量规划经常把三个问题混在一起：

| 问题 | 需要的模型 | 典型指标 |
|---|---|---|
| 平均需要多少资源？ | 到达率 × 平均占用 | offered load、利用率 |
| 高峰时等多久？ | 排队模型/模拟 | P50/P95/P99 等待时间 |
| 会不会雪崩？ | 稳定性/过载分析 | 队列是否发散、拒绝率 |

只回答第一个问题，就会得到"平均利用率 70%，很健康"的结论；但 P99 可能已经是几十小时。

## 29.2 基础量：λ、S、c、a、ρ

记：

```text
λ   作业到达率（个/小时）
S   单个作业的平均占用时间（小时）
c   并行服务能力（GPU 数，或节点数，取决于模型）
a   offered load = λ × E[S]（Erlang）
ρ   利用率 = a / c
```

例如：

```text
λ = 1.8 作业/小时
E[S] = 6 小时
每作业 8 GPU
c = 96 GPU

a = 1.8 × 6 × 8 = 86.4 GPU·小时/小时
ρ = 86.4 / 96 = 90%
```

### 29.2.1 Little 定律

对任何稳定系统：

```text
L = λ × W
```

- `L`：系统中平均作业数（排队 + 运行）；
- `λ`：到达率；
- `W`：平均逗留时间（排队 + 运行）。

它不依赖分布，只要求系统稳定。用途：

- 已知平均队列长度和到达率，反推平均等待；
- 检查监控数据是否自洽：如果 `L` 和 `λ×W` 差很多，说明统计口径或采样有问题。

### 29.2.2 利用率的非线性

排队时间不是随利用率线性增长的。经典 M/M/1 的等待时间：

```text
Wq = ρ × E[S] / (1 - ρ)
```

当 ρ 从 0.8 到 0.9，等待时间翻倍；从 0.9 到 0.95，再翻倍；从 0.95 到 0.98，再翻几倍。这就是"利用率 90% 看起来很健康，实际上已经很危险"的原因。

## 29.3 理想模型：M/M/c 与 Erlang C

如果把每个 GPU 看成一个独立服务台，作业可以任意拆分到 GPU 上，那么可以用 M/M/c：

```text
到达：Poisson(λ)
服务：指数分布，均值 E[S]
服务台：c 个（GPU）
队列：无限，FIFO
```

排队概率由 Erlang C 给出：

```text
P(wait) = (a^c / c!) / [ (a^c / c!) + (1 - ρ) × Σ_{k=0}^{c-1} a^k / k! ]

Wq = P(wait) × E[S] / (c × (1 - ρ))
W  = Wq + E[S]
```

对 `c = 96`、`E[S] = 6h`：

| ρ | P(等待) | 平均排队 Wq | 平均逗留 W |
|---:|---:|---:|---:|
| 0.50 | 0.0000 | 0.00h | 6.00h |
| 0.70 | 0.0006 | 0.00h | 6.00h |
| 0.80 | 0.0220 | 0.01h | 6.01h |
| 0.90 | 0.2252 | 0.14h | 6.14h |
| 0.95 | 0.5143 | 0.64h | 6.64h |
| 0.98 | 0.7793 | 2.44h | 8.44h |

这个模型说：96 卡、90% 利用率，平均只等 8 分钟。**但它和真实 GPU 集群的体验经常相差一个数量级**，原因有三：

1. **作业是多服务台批量服务**：一个 8 卡作业需要 8 个 GPU 同时空闲，不能先占 1 个再等 7 个。
2. **放置有物理约束**：8 卡通常要在同一节点（或同一 NVLink 域/rack），不能把 96 个 GPU 当成一个连续池。
3. **作业大小异构**：大作业会排在队头，阻塞后面的小作业（StrictFIFO），或者小作业不断插队让大作业饥饿（BestEffortFIFO）。

所以 Erlang C 只能作为**下界/理想参考**，不能直接拿来定配额。

## 29.4 碎片：为什么 60% 利用率也可能放不下 8 卡

假设 12 台节点，每台 8 GPU，总 96 GPU。节点上的空闲 GPU 是随机的，整体利用率为 50%，即每台节点平均空闲 4 GPU。

一个 8 卡作业要求同一节点有 8 个空闲 GPU。单台节点"恰好全空"的概率：

```text
P(8 个 GPU 全空) = 0.5^8 = 0.00390625
```

12 台节点的期望全空节点数：

```text
12 × 0.0039 = 0.047
```

也就是说，**整体一半 GPU 空闲，但平均只有 0.047 台节点能放下一个 8 卡作业。** 这就是碎片。

更一般地，若单台节点空闲概率为 `p`，节点有 `G` 个 GPU，则：

```text
P(节点可放 k 卡作业) = C(G, k) × p^k × (1-p)^(G-k)
```

对 8 卡作业、G=8，只有 k=8 一项，即 `p^8`。

### 29.4.1 碎片不是"浪费"，是"不可合并"

碎片来自三个因素：

- 作业需要连续/同节点的多卡；
- 不同作业的时长不同，空闲时间错开；
- 调度器不能随意迁移正在运行的 Pod。

缓解手段：

- 让作业尽量小，或支持多节点/弹性；
- TAS 把同 rack/同节点的容量显式建模；
- 预留整节点/整 rack 给大作业；
- 用 `WaitForPodsReady` + 抢占/回收清理长期占坑的小作业；
- 在容量模型里按"可放下的最大连续块"评估，而不是只看总空闲。

## 29.5 异构作业与队头阻塞

假设作业大小混合：

```text
45% 1 卡
20% 2 卡
20% 4 卡
15% 8 卡
平均 2.85 卡
```

12 台 × 8 卡 = 96 卡，平均时长 4 小时，到达率 8 作业/小时：

```text
offered load = 8 × 4 × 2.85 = 91.2 GPU·小时/小时
ρ ≈ 95%
```

用 `scripts/capacity_model.py` 跑 90 天，StrictFIFO 与 BestEffortFIFO 的差别非常明显：

| 策略 | 完成数 | 利用率 | 等待 P50 | 等待 P95 | 等待 P99 | 最大队列 |
|---|---:|---:|---:|---:|---:|---:|
| StrictFIFO | 16832 | 89.47% | 0.00h | 94.79h | 102.88h | 242 |
| BestEffortFIFO | 17029 | 91.73% | 0.00h | 12.73h | 20.64h | 79 |

StrictFIFO 的队头一旦是一个 8 卡作业，后面所有 1 卡作业都不能插队；BestEffortFIFO 跳过放不下的队头，把小作业填进碎片里。代价是：

- 大作业可能长期饥饿；
- 等待时间的分布更偏；
- 需要配合公平分享/预留保护大作业。

这不是"哪种策略更好"的问题，而是"你的业务更需要可预测的顺序，还是更高的吞吐"。第 6 章讲过语义，这里给出量化后果。

## 29.6 借用/出借的流体模型

Cohort 借用可以看成一个两队列的流体模型。记两个 CQ 的 nominal 为 `N1`、`N2`，当前需求为 `D1`、`D2`，总容量 `C = N1 + N2`。

在没有借用的理想情况下：

```text
queue1 需求 = max(0, D1 - N1)
queue2 需求 = max(0, D2 - N2)
```

有借用时，空闲的 nominal 可以在 Cohort 内流动，但受：

```text
borrow1 <= N2 - D2   （peer 的空闲）
borrow2 <= N1 - D1
lendingLimit 进一步收紧可借量
Cohort 总量：D1 + D2 <= C
```

几个结论：

1. **借用提高的是"峰谷互补"的利用率，不是总容量。** 如果两个队列同时满载，借用没有空间。
2. **lendingLimit 会把空闲"锁住"。** A 空闲 10 卡但 `lendingLimit: 2`，B 最多只能借 2，Cohort 里剩下的 8 卡对 B 不可见。
3. **borrowingLimit 限制的是单个队列的借入上限**，不是 Cohort 的总借出量。Cohort 级 borrowingLimit 才是子树上限。
4. **回收会改变等待时间分布。** 借用者被驱逐后重新排队，可能形成"抢占—重排队—再抢占"的抖动；退避时间和优先级决定抖动幅度。

### 29.6.1 一个流体例子

```text
A: nominal 60, 需求 30  → 空闲 30
B: nominal 40, 需求 70  → 缺口 30
总容量 100
```

B 可以借 30，达到 70；A 仍是 30；总用 100，Cohort 满。

如果 B 的 `borrowingLimit: 20`：

- B 最多用到 60（nominal 40 + 借 20）；
- A 仍用 30；
- 总用 90，剩余 10 卡闲置，但 B 不能再借；
- 这不是"容量不够"，是"借用上限不够"。

排障时要把"物理容量"、"nominal 总量"、"borrowingLimit"、"lendingLimit"四个数分开看。第 5 章给了判定公式，本节给的是容量视角。

## 29.7 一个可运行的容量模拟器

`scripts/capacity_model.py` 用纯标准库实现了一个离散事件模拟器：

- Poisson 到达；
- 固定或混合的作业大小；
- 指数/对数正态运行时长；
- 整作业单节点放置，或 `--allow-multi-node`；
- StrictFIFO / BestEffortFIFO；
- 输出完成数、利用率、P50/P95/P99 等待、队列长度、结束时空闲节点。

### 29.7.1 基本用法

```bash
cd kueue-tutorial

python scripts/capacity_model.py \
  --nodes 12 --gpus-per-node 8 \
  --arrival-rate 1.8 --mean-duration 6 \
  --job-size 8 --policy strict --hours 2160
```

输出：

```text
capacity model
  cluster:        12 nodes x 8 GPUs = 96 GPUs
  arrivals:       1.8/h, mean duration 6.0h, cv=1.0
  job size:       8 GPUs
  placement:      whole job on one node
  policy:         strict

  arrivals:       3911
  completed:      3898
  still queued:   1
  running at end: 12
  GPU utilization: 89.96%
  wait p50:       1.43 h
  wait p95:       10.79 h
  wait p99:       19.70 h
  wait mean:      2.98 h
  max queue:      44
  avg queue:      5.40
  fully free nodes at end: 0
  free GPUs/node at end:   0.00
```

### 29.7.2 对比两种 FIFO

```bash
for pol in strict best-effort; do
  python scripts/capacity_model.py \
    --nodes 12 --gpus-per-node 8 \
    --arrival-rate 8 --mean-duration 4 \
    --job-size-mix "1:0.45,2:0.2,4:0.2,8:0.15" \
    --policy "$pol" --hours 2160
done
```

结果就是 29.5 的表。把 `--json` 加进去可以做自动化回归：

```bash
python scripts/capacity_model.py ... --json | jq '.wait_p95'
```

### 29.7.3 观察碎片

```bash
# 整作业单节点：8 卡作业需要一台全空节点
python scripts/capacity_model.py \
  --nodes 12 --gpus-per-node 8 \
  --arrival-rate 8 --mean-duration 4 \
  --job-size-mix "1:0.45,2:0.2,4:0.2,8:0.15" \
  --policy best-effort --hours 2160

# 允许多节点：同样总量下，大作业更容易开始
python scripts/capacity_model.py \
  --nodes 12 --gpus-per-node 8 \
  --arrival-rate 8 --mean-duration 4 \
  --job-size-mix "1:0.45,2:0.2,4:0.2,8:0.15" \
  --policy best-effort --allow-multi-node --hours 2160
```

### 29.7.4 一个反例：32 卡作业不能跨节点

```bash
python scripts/capacity_model.py \
  --nodes 12 --gpus-per-node 8 \
  --arrival-rate 0.6 --mean-duration 8 \
  --job-size 32 --policy best-effort --hours 2160
```

输出会提示：

```text
warning: job-size 32 exceeds gpus-per-node 8 and --allow-multi-node is off;
these jobs can never start
```

结果：完成 0，队列 1273。这对应真实世界的"配额够、节点放不下"：如果作业必须整节点放置，而单节点只有 8 卡，32 卡作业永远无法开始。解决方式是多节点训练框架 + 调度器支持，或把作业拆小，而不是继续加 nominal。

## 29.8 容量规划工作流

把容量规划做成一个可重复的流程，而不是一年一次的 Excel：

```text
1. 观测
   ├── 到达率 λ（按小时/天/周）
   ├── 作业大小分布（1/2/4/8/16/32/64 卡）
   ├── 运行时长分布（P50/P95/P99、长尾）
   └── 优先级/抢占/重试比例

2. 建模
   ├── 物理容量 C（可调度 GPU/节点）
   ├── 逻辑配额 N（nominal 总和）
   ├── 安全余量 C - N
   └── 碎片/拓扑约束（每节点卡数、rack 结构）

3. 模拟
   ├── 基线：当前配额/策略
   ├── 变体：调整 nominal、borrowingLimit、FIFO、TAS
   └── 记录 P95/P99、利用率、抢占率、队列长度

4. 决策
   ├── 保底配额给足
   ├── 借用/公平处理峰谷
   └── 安全余量覆盖碎片和故障

5. 上线与回顾
   ├── 监控实际 P95/P99 vs 模型
   ├── 每季度重估分布
   └── 变更走 GitOps + review
```

### 29.8.1 安全余量怎么定

安全余量至少覆盖：

- 系统组件/DaemonSet/驱动；
- 节点故障/维护；
- 碎片（尤其是大作业）；
- 突发到达的短时峰值；
- 扩容/缩容的滞后。

一个实用起点：

```text
N_total <= C_schedulable × 0.85   （碎片/故障余量 15%）
```

但这不是万能公式。如果大作业占比高、拓扑约束强，余量要更大；如果作业小且可抢占，余量可以更小。

### 29.8.2 用模拟器做配额评审

评审"把 team-a 的 nominal 从 24 提到 32"时，不要只看平均值。至少跑四组：

| 场景 | 关注 |
|---|---|
| 当前基线 | P95/P99、利用率 |
| 变更后 | 等待时间是否改善、是否挤占别人 |
| 峰值 +20% | 队列是否发散 |
| 大作业比例翻倍 | 碎片是否导致 P99 爆炸 |

如果模拟显示 P99 从 10h 变成 80h，即使平均利用率更高，也未必是可接受的变更。

## 29.9 模型不覆盖什么

`capacity_model.py` 是教学/评审工具，不是生产容量规划系统。它不覆盖：

- 多资源维度（CPU/内存/GPU 同时约束）；
- 多 Flavor/Cohort 的借用/回收动态（只模拟单一池）；
- TAS 的 rack/block 层级和跨 Workload 打散；
- 抢占和重排队；
- 作业依赖、gang 启动时间、checkpoint/重启；
- 云上扩容延迟和 spot 中断；
- 真实调度器的打分、亲和性、卷/网络约束。

这些要用真实集群的 shadow workload、Kueue 指标和更细的模拟器验证。模拟器的价值是**在改配额前排除明显错误的方案**，不是替代生产观测。

## 29.10 常见容量误区

1. **"平均利用率 70%，所以还有 30% 余量。"** 余量可能是碎片，大作业用不上。
2. **"nominal 总和 = 物理容量，利用率最高。"** 没有安全余量，任何节点故障/碎片都会导致排队。
3. **"borrowingLimit 越大越好。"** 借用者可能抽干 Cohort，原主回收时引发抢占风暴。
4. **"StrictFIFO 更公平。"** 它保证顺序，但会牺牲吞吐；大作业队头会阻塞小作业。
5. **"BestEffortFIFO 利用率高，所以更好。"** 大作业可能长期饥饿，P99 更差。
6. **"Erlang C 算出来等 8 分钟，为什么实际等 8 小时？"** 因为 GPU 作业不是可任意拆分的独立服务台。
7. **"多加卡就能解决等待。"** 如果瓶颈是单节点卡数/rack 拓扑，加卡但不改放置约束可能没用。
8. **"历史平均时长代表未来。"** 模型/数据/框架变化会改变作业大小和时长分布。

## 29.11 本章小结

- 容量规划要分开回答"平均需要多少"、"高峰等多久"、"会不会雪崩"。
- λ、E[S]、c、a、ρ 是基础量；Little 定律用于校验监控口径。
- M/M/c 和 Erlang C 给出理想下界，但 GPU 作业是多服务台批量服务，实际等待通常更高。
- 碎片让"总空闲"不等于"可放置"；8 卡作业需要同节点 8 卡，概率是 `p^8`。
- 异构作业 + StrictFIFO 会产生严重的队头阻塞；BestEffortFIFO 提高吞吐但可能饿死大作业。
- 借用提高峰谷互补的利用率，不增加总容量；lendingLimit 会把空闲"锁住"。
- `scripts/capacity_model.py` 提供了一个可运行的离散事件模拟器，用于配额评审和策略对比。
- 容量模型要持续校准：观测 → 建模 → 模拟 → 决策 → 监控 → 回顾。
