# 第 55 章 选型、迁移与退出策略

## 55.1 先写需求，不看产品

选型前明确：

- 规模：活跃序列/样本摄入/日志量/span 量；
- 保留：本地/长期/合规；
- 查询：并发/延迟/历史深度；
- 多租户/权限；
- 部署：SaaS/自托管/混合/气隙；
- 合规：数据驻留/加密/审计；
- 预算/人力；
- 现有工具链（Grafana/OTel/K8s）；
- 退出要求（数据导出/API 兼容）。

## 55.2 评分矩阵

```text
维度            权重   候选 A   候选 B   候选 C
功能覆盖         20%
规模/性能        20%
成本/TCO         20%
运维/人力        10%
生态/兼容        10%
安全/合规        10%
锁定/退出        10%
```

评分要基于 POC/数据，不是销售材料。

## 55.3 候选方案

| 方案 | 适合 | 风险 |
|---|---|---|
| 自托管 Prometheus + 本地 TSDB | 小规模/边缘/实验 | 扩展/长期存储有限 |
| Prometheus + Thanos | 已有对象存储、要全局查询 | 组件多/运维复杂 |
| Prometheus + Mimir | 多租户/大规模/云原生 | 资源/成本/复杂度 |
| VictoriaMetrics | 高压缩/成本敏感/单机或集群 | 生态/兼容差异 |
| 云托管 Prometheus | 低运维/云内集成 | 成本/锁定/功能限制 |
| 全栈 SaaS（Datadog/Dynatrace 等） | 全栈/托管/快速上线 | 成本/锁定/数据主权 |

## 55.4 POC 设计

- 用真实数据规模（至少 10%～30%）；
- 真实查询/面板/告警；
- 测摄入/查询/规则/故障恢复；
- 测迁移/导出；
- 测成本（按量计费模拟）；
- 记录运维步骤/人力。

POC 输出：

```text
功能差距清单
性能/成本数据
迁移工作量
风险/缓解
建议/不选理由
```

## 55.5 迁移策略

- 双跑：旧系统 + 新系统并行；
- 双写：关键指标同时写两边；
- 切读：Grafana 数据源切换；
- 切告警：测试渠道对比后切换；
- 停旧：保留只读/归档。

回滚：

- 数据源可切回；
- 告警路由可切回；
- 历史数据可访问；
- 合同/退出条款支持。

## 55.6 退出策略

- 数据导出格式（OpenMetrics/remote write/Parquet/CSV）；
- API 兼容（PromQL/remote read）；
- 仪表盘/告警可迁移；
- 合同终止/数据删除条款；
- 过渡期支持；
- 定期演练（每年至少一次）。

## 55.7 决策示例

### 场景 A：50 人公司，10 个服务

- 自托管 Prometheus + Grafana + Alertmanager；
- 本地 15 天，快照备份；
- 成本低，运维 0.2 FTE。

### 场景 B：500 人，1000 服务，多集群

- 每集群 Prometheus + Thanos/Mimir；
- 多租户/长期存储；
- 平台团队 2～5 人；
- 需要 SLO/告警治理。

### 场景 C：受监管行业，数据不能出域

- 自托管/私有云；
- 开源后端 + 企业支持；
- 审计/加密/气隙；
- 供应商锁定风险高，需退出条款。

## 55.8 常见选型错误

- 只看功能列表，不看规模/成本；
- 用 POC 的小数据得出结论；
- 忽略迁移/运维人力；
- 被"全栈"捆绑，失去议价；
- 没有退出计划；
- 忽略合规/数据驻留。

## 55.9 RFI/RFP 与 POC 验收标准

RFI（信息征询）用来缩小候选；RFP（方案征询）用来比较报价/承诺。问题清单：

```text
1. 支持哪些数据模型/查询语言？PromQL 兼容度？
2. 摄入/查询/保留的计价单位与上限？
3. 多租户/隔离/权限模型？
4. 高基数/高吞吐的实测数据（同规模）？
5. 数据驻留/加密/审计/合规认证？
6. 迁移工具/历史数据导入/导出格式？
7. SLA/支持/on-call 责任？
8. 许可/合同终止/数据删除？
9. 路线图/版本节奏/社区治理？
10. 参考客户/同规模案例？
```

POC 验收要可量化：

- 用你的数据分布/查询语料，不是厂商 demo；
- 固定硬件/版本/并发；
- 测摄入、查询 P99、规则、恢复、故障注入；
- 对比总成本（含人力/迁移/退出）；
- 记录失败/限制，不只看演示成功。

## 55.10 退出策略与数据可移植性

退出策略要在**签约前**设计：

- **数据导出**：remote write/OpenMetrics/Parquet/快照；是否收费/限速？
- **格式兼容**：目标系统能否直接读 Prometheus TSDB/remote write？
- **查询迁移**：PromQL 兼容度；仪表盘/告警迁移工具；
- **身份/权限**：SSO/SCIM/API token；
- **并行期**：双写/双读/切流/回滚；
- **合同**：过渡期支持、数据删除证明、最低承诺；
- **演练**：至少做一次小规模导出/导入。

可移植性等级：

```text
高：开放格式 + 标准协议 + 无导出费
中：厂商导出工具 + 一次性费用
低：私有格式/不可导出/合同限制
```

选型时把"退出成本"折算进 TCO；锁定越深，未来议价能力越弱。

## 55.12 并购与整合期的选型风险

2025–2026 年可观测性市场出现多起大型并购（第 52 章）：安全平台收购指标平台、数据平台收购可观测性平台。对买方，这意味着"选型"不只是选产品，也是选**未来 3 年的公司归属与路线图**。

并购后常见变化：

- 价格/打包方式调整，原有折扣或免费层被收回；
- 产品路线图向收购方的主业务倾斜（安全、数据平台、云）；
- 支持团队/合同主体/数据驻留区域变化；
- 部分功能停止维护或合并到新平台；
- 许可/服务条款更新，导出/API 兼容性可能变化。

尽调清单：

- 收购方的主业务是什么？可观测性在其叙事中是核心还是附庸？
- 交易是否已关闭？监管是否可能附加条件？
- 现有合同是否有 change-of-control、价格保护、数据导出、过渡期条款？
- 关键功能是否依赖被收购方的专有 agent/查询语言？
- 数据驻留/子处理者是否会变化？
- 社区/开源项目的治理是否受影响？

技术上的保护措施与第 54 章一致：用 PromQL/OTLP/OpenMetrics/remote write 做边界，保留原始数据导出，避免把核心采集绑到闭源 agent，定期演练迁移。合同上把"并购/重组"纳入退出触发条件，而不是假设供应商永远不变。

## 本章小结

- 选型从需求/规模/合规/预算出发，用评分矩阵和 POC。
- 候选方案按规模/多租户/成本/运维权衡。
- 迁移用双跑/双写/切读/切告警/回滚。
- 退出策略要写进合同并演练；并购/重组应作为退出触发条件。
- 不要用小规模 POC 推断大规模成本。
