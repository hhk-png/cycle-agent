# 第 56 章 团队、组织与职业路线

## 56.1 可观测性团队的角色

- **平台工程师**：Prometheus/Operator/存储/多租户/升级。
- **SRE**：SLO/告警/容量/故障响应。
- **应用工程师**：instrumentation/指标规范/仪表盘。
- **数据/分析**：成本/容量/趋势。
- **安全/合规**：数据驻留/访问控制/审计。

小团队可以一人多角色；大团队需要明确边界。

## 56.2 组织模式

### 集中式平台团队

- 统一 Prometheus/存储/告警；
- 提供自助服务（ServiceMonitor/规则评审）；
- 优点：标准化/成本；
- 缺点：瓶颈/离业务远。

### 嵌入式 SRE

- SRE 嵌入业务团队；
- 平台团队提供基础设施；
- 优点：贴近业务；
- 缺点：重复建设/标准不一。

### 混合

- 平台管基础设施/多租户/存储；
- 业务管指标/告警/仪表盘；
- 最常见。

## 56.3 技能栈

- Prometheus/PromQL/Alertmanager；
- Kubernetes/Operator/云；
- Linux/网络/存储；
- Go/Python（工具/控制器）；
- OpenTelemetry/OTLP；
- SLO/容量/成本；
- 故障排查/沟通。

## 56.4 On-call

- 轮值/升级策略；
- 告警归属；
- runbook；
- 复盘（blameless）；
- 疲劳管理；
- 交接/上下文。

## 56.5 面试题（示例）

1. `rate()` 为什么要外推？窗口边界怎么处理？
2. counter 重置时 `increase()` 如何计算？
3. `histogram_quantile` 的输入为什么要 `sum by (le)`？
4. 默认向量匹配忽略什么标签？多对多怎么办？
5. stale marker 与 lookback 的区别？
6. WAL/checkpoint/block 的关系？
7. 如何定位高基数？如何治理？
8. Prometheus HA 如何去重？external labels 怎么配？
9. remote write 队列积压怎么排查？
10. SLO burn rate 多窗口为什么需要短窗口？
11. Kubernetes ServiceMonitor 不生效怎么查？
12. 如何设计一个不会告警疲劳的告警体系？

## 56.6 职业路线

- 初级：exporter/仪表盘/基础 PromQL；
- 中级：规则/告警/容量/故障排查；
- 高级：架构/多集群/多租户/成本/SLO；
- 专家/架构：平台战略/存储/大规模/组织。

学习建议：

- 读官方文档 + 源码；
- 跑真实集群；
- 写 exporter/operator；
- 参与社区；
- 做故障复盘；
- 学 OTel/云原生。

## 56.7 30/60/90 天计划

### 30 天

- 盘点现有监控/告警/成本；
- 跑通 Prometheus/Grafana/Alertmanager；
- 建立关键 SLO/仪表盘；
- 识别高基数/告警噪音。

### 60 天

- 治理基数/告警；
- 建立 recording rules/告警规范；
- 容量/成本报告；
- 备份/升级/演练。

### 90 天

- 多集群/长期存储；
- 自助服务平台；
- SLO 评审/预算；
- 路线图/培训。

## 56.8 软技能

- 写清晰的 runbook/复盘；
- 与业务/开发/安全协作；
- 用数据说话（成本/可靠性）；
- 管理告警疲劳/期望；
- 教学/分享。

## 56.9 常见组织问题

- 平台团队成为瓶颈；
- 业务团队重复造轮子；
- 没有指标规范；
- 告警无主；
- 成本无人负责；
- 迁移/升级无计划。

## 56.10 能力矩阵

按"知道/会做/能设计/能带人"四级评估：

| 领域 | 知道 | 会做 | 能设计 | 能带人 |
|---|---|---|---|---|
| 指标模型 | 类型/标签/基数 | 设计指标 | 制定规范 | 评审/培训 |
| PromQL | 选择器/函数 | 写告警 | 查询优化 | 建立规则库 |
| 存储 | TSDB 概念 | 调 retention/压缩 | 容量/长期存储 | 架构选型 |
| 抓取 | SD/relabel | 接新目标 | 分片/HA | 平台化 |
| 告警 | 规则/Alertmanager | 路由/抑制 | SLO/告警体系 | on-call 体系 |
| K8s | Operator/CRD | ServiceMonitor | 多集群/多租户 | 平台治理 |
| OTel | 模型/协议 | Collector 配置 | 语义映射 | 标准化 |
| 成本 | 计费维度 | 看报表 | 预算/单位经济 | 成本文化 |
| 软技能 | 文档 | runbook | 复盘/评审 | 跨团队领导 |

评估用途：

- 个人发展计划；
- 团队招聘/培训；
- 平台能力缺口；
- on-call 授权（不是所有级别都能独立值班）。

## 56.11 面试评分表

面试题不要只考"背命令"，用场景题评估思维：

| 维度 | 问题示例 | 看什么 |
|---|---|---|
| 语义 | `rate()` 为什么要外推？counter 重置怎么处理？ | 是否理解原理，而不是背公式 |
| 排障 | 目标 up=1 但曲线有缺口，怎么查？ | 分层排查、append 错误、stale |
| 基数 | 一个指标序列暴涨，如何定位/治理？ | TSDB stats、relabel、源头修复 |
| 设计 | 设计一个多集群指标平台 | 拓扑、长期存储、HA、成本、合规 |
| SLO | 给定 SLO，设计 burn-rate 告警 | 窗口、多燃烧率、无流量 |
| 告警 | 这个告警为什么会被忽略？ | 可执行性、路由、噪音、runbook |
| 成本 | 100 万序列的 TCO 怎么估？ | 口径、假设、优化杠杆 |
| 安全 | 如何保护 admin/remote write？ | 威胁模型、网络/认证、最小权限 |
| 协作 | 业务团队不愿改指标，怎么办？ | 影响力、平台 paved road、数据说话 |

评分：

```text
1 = 不知道
2 = 知道概念
3 = 能独立做
4 = 能设计/权衡
5 = 能带人/建立体系
```

不要用"是否用过某厂商产品"作为核心信号；语义/排障/设计能力更可迁移。

## 56.13 认证、作品集与面试准备

### 56.13.1 Prometheus Certified Associate（PCA）

CNCF 的 PCA 是面向 Prometheus/可观测性基础的入门级认证。2026 年的公开考纲大致为：

| 领域 | 权重 | 对应本教程 |
|---|---|---|
| Observability Concepts | 18% | 第 1、25、26 章 |
| Prometheus Fundamentals | 20% | 第 2～5、11～13 章 |
| PromQL | 28% | 第 6～8、17 章 + 附录 A/O |
| Instrumentation and Exporters | 16% | 第 5、12 章 + 附录 AA/AD/W |
| Alerting and Dashboarding | 18% | 第 9、10、26 章 + 附录 C/M/N |

考试形式通常为 90 分钟选择题，75% 通过（以 CNCF/Linux Foundation 官方页面为准）。PCA 适合作为知识地图，不是能力证明；真正的区分度来自排障、设计和落地经验。

其他相关认证/课程：

- CKA/CKAD：Kubernetes 基础，对 Operator/K8s 监控有帮助；
- 云厂商可观测性认证：与具体平台绑定，迁移性较弱；
- OpenTelemetry 相关课程：采集/语义约定，适合与 Prometheus 互补。

### 56.13.2 作品集

面试时，一个可复现的作品集比"用过某工具"更有说服力：

1. **一个最小平台**：Prometheus + Alertmanager + Grafana + 长期存储（Thanos/Mimir 二选一），用 Docker Compose/Kind 可一键启动；
2. **一套 SLO**：至少一个服务的 SLI/SLO/错误预算/burn-rate 告警，附压测或故障注入结果；
3. **一套规则库**：recording/alerting rules + `promtool test rules` 单元测试；
4. **一份压测报告**：序列/样本/查询/规则四类负载，说明瓶颈和优化前后对比；
5. **一份事故复盘**：真实或模拟事故的时间线、监控缺口、改进项和验证。

作品集的重点不是"组件多"，而是**每个决策有数据、有取舍、有验证**。这比背命令更能体现工程能力。

### 56.13.3 面试准备

建议按"语义 → 排障 → 设计 → 组织"四层准备：

- **语义**：能解释 `rate` 外推、counter reset、stale、lookback、向量匹配、直方图分位数；
- **排障**：给一个"`up=1` 但曲线有缺口"或"remote write 积压"的场景，能分层定位；
- **设计**：白板设计一个多集群、多租户、长期存储、成本可控的指标平台；
- **组织**：如何推动指标规范、告警治理、SLO 落地，如何处理业务团队不配合。

回答时用"假设 → 取证 → 决策 → 验证"的结构，比罗列工具更有说服力。准备 2～3 个自己主导的案例，能说清背景、约束、取舍、结果和复盘。

## 本章小结

- 可观测性需要平台/SRE/应用/安全协作。
- 组织模式有集中/嵌入/混合，按规模选择。
- 技能栈覆盖 Prometheus/K8s/存储/OTel/SLO/成本。
- PCA 可作为知识地图（5 个领域，PromQL 权重最高），但不能替代实战能力。
- 作品集应包含可复现平台、SLO、规则测试、压测报告和事故复盘。
- 面试题聚焦语义/故障/治理，不是背命令。
- 30/60/90 天计划从盘点/跑通到治理/平台化。
