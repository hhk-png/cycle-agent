# 第 54 章 开源治理、许可与商业模式

## 54.1 Prometheus 的治理

- 许可证：Apache License 2.0；
- 基金会：CNCF（2016 加入，2018 毕业）；
- 治理：维护者/评审者制度，社区驱动；
- 没有单一公司拥有 Prometheus 商标/代码；
- 路线图由维护者/社区讨论决定。

意义：

- 用户可以自托管、修改、分发；
- 厂商不能单方面闭源；
- 商业公司通过托管/支持/周边盈利；
- 生态碎片化风险较低（但有兼容性差异）。

## 54.2 开源商业模式

围绕 Prometheus 的常见模式：

1. **托管服务**：Grafana Cloud、云厂商 Managed Prometheus。
2. **长期存储/全局查询**：Thanos/Mimir/VictoriaMetrics 的开源 + 企业版。
3. **支持/咨询**：SLA、迁移、培训。
4. **Operator/管理平台**：简化部署/多租户/治理。
5. **可观测性平台**：指标+日志+追踪捆绑。
6. **安全/合规增值**：审计、RBAC、数据驻留。

## 54.3 Open Core 与许可

- **Open Core**：核心开源，企业功能（SSO/RBAC/多租户/长期支持）闭源。
- **Apache 2.0**：宽松，允许商业分发/修改。
- **AGPL**：网络使用也触发开源义务。Grafana、Mimir、Loki、Tempo 等 Grafana 生态核心项目采用 AGPLv3，托管服务要评估义务；Prometheus/Thanos/VictoriaMetrics 仍是 Apache-2.0。
- **SSPL/BSL**：限制云厂商托管，争议大（Elasticsearch/MongoDB/Redis 等历史）。
- **Confluent Community License** 等：特定限制。

Prometheus 生态大多保持 Apache 2.0；后端项目（Mimir/Thanos/VictoriaMetrics）许可各异，选型时要确认：

- 是否允许自托管/托管服务；
- 是否要求贡献回馈；
- 是否有商标/品牌限制；
- 企业功能是否锁定。

### 54.3.1 常见项目的许可证矩阵

| 项目 | 许可证 | 托管/分发注意 |
|---|---|---|
| Prometheus / Alertmanager | Apache 2.0 | 可自由修改、分发、托管 |
| Thanos | Apache 2.0 | 同上 |
| VictoriaMetrics | Apache 2.0 | 同上；企业版功能另看商业条款 |
| Cortex | Apache 2.0 | 同上 |
| Grafana Mimir / Loki / Tempo | AGPLv3 | 网络服务/托管需评估 AGPL 义务；企业版功能另看合同 |
| Grafana | AGPLv3 | 同上；插件/企业版许可另看 |
| OpenTelemetry Collector | Apache 2.0 | 可自由分发/托管 |
| Kubernetes / etcd | Apache 2.0 | 同上 |

许可证会变化，上表只反映 2026-11 的常见状态；选型时以项目仓库的 `LICENSE`、`NOTICE` 和官方公告为准，必要时请法务审阅。AGPL 不等于"不能商用"，但**修改后通过网络提供服务**的边界需要按你的部署形态具体判断。

### 54.3.2 许可变更的风险管理

历史上多个基础设施项目从 Apache/BSD 转向 SSPL/BSL/AGPL，触发分叉或托管商调整。对买方/平台团队：

- 在架构上保留可替换的采集/存储/查询层，避免单一项目许可变化导致整体不可用；
- 优先使用开放协议（PromQL、remote write、OTLP、OpenMetrics）做边界；
- 合同写入许可变更通知、过渡期和数据导出条款；
- 对关键依赖做许可证扫描（SBOM/CI）；
- 不要把"开源"当成"永久免费且无风险"。

## 54.4 厂商锁定与退出

锁定来源：

- 专有查询语言/API；
- 数据导出格式；
- Agent/采集器绑定；
- 告警/仪表盘生态；
- 合同/最低消费；
- 数据驻留/合规。

降低锁定：

- 用 PromQL/OpenMetrics/OTLP 等开放标准；
- 保留原始数据导出能力；
- 避免专有 agent 的独有功能；
- 合同写入退出/数据导出条款；
- 定期演练迁移。

## 54.5 社区参与

- 提交 issue/PR；
- 参与 SIG/工作组；
- 维护 exporter/operator；
- 贡献文档/测试；
- 赞助/会议。

对企业的价值：

- 影响路线图；
- 提前获知变更；
- 招聘/品牌；
- 降低支持成本。

## 54.6 商业分析中的常见偏差

- **把 star 数当市场份额**：GitHub star 不等于生产使用。
- **把下载量当收入**：开源下载与商业收入不直接相关。
- **忽略迁移成本**：低价方案可能迁移昂贵。
- **忽略人力成本**：自托管"免费"但需要运维。
- **把开源当无风险**：项目可能停滞/改变许可/被收购。

## 54.7 对买方的建议

- 明确"必须自托管/可用开源"的边界；
- 要求数据导出/API 兼容；
- 评估供应商的社区参与/治理；
- 合同包含许可变更/退出条款；
- 不要把核心可观测性绑定到单一闭源 agent。

## 54.8 对卖方的建议

- 用开放标准降低采用门槛；
- 在规模/多租户/治理/支持上差异化；
- 避免"开源版故意残缺"激怒社区；
- 提供清晰的迁移/退出路径；
- 关注单位经济性/毛利。

## 54.9 许可证与治理风险

开源项目的"许可证"和"治理"是两件事：

- **许可证**决定你能不能修改/分发/托管；
- **治理**决定谁有权改路线图/商标/版本。

常见风险：

- **许可变更**：项目从 Apache/BSD 转向 SSPL/BSL/AGPL，托管商/用户受影响；
- **商标/品牌**：分叉不能用原商标；
- **CLA/DCO**：贡献者的版权/专利授权；
- **单一厂商控制**：路线图/发布节奏受商业利益影响；
- **基金会治理**：CNCF 项目有 TOC/沙箱/毕业流程，但不等于"永久中立"；
- **依赖链**：Prometheus 生态依赖 Go/etcd/Thanos 等项目，各自的治理/许可也要看。

买方尽调：

- 许可证是否允许你的部署形态（SaaS/私有化/分发）？
- 是否有 CLD/CLA/专利条款？
- 项目是否在基金会/中立治理下？
- 关键组件是否由单一厂商主导？
- 有无许可变更历史/分叉？
- 商业支持方的路线图与社区是否一致？

## 54.10 买方的开源策略

开源不是"免费"，而是一种采购/建设策略：

- **自建**：控制力强、成本可预测，但需要人力/运维/升级；
- **托管开源**：用云厂商/Grafana Cloud 等托管 Prometheus/Mimir，降低运维；
- **开源发行版**：厂商打包的 Prometheus + 长期存储 + 支持；
- **商业 SaaS**：全栈/工作流/支持，但锁定/成本更高；
- **混合**：本地 Prometheus + 远端长期存储/全局查询。

决策维度：

- 数据主权/合规；
- 团队能力/人力；
- 规模/增长；
- 成本结构；
- 锁定/退出；
- 支持/SLA；
- 路线图影响力。

建议：

- 保留 PromQL/remote write/OpenMetrics 的兼容性；
- 数据可导出（至少 remote write/快照）；
- 不把核心采集绑到闭源 agent；
- 合同写清许可变更/退出；
- 定期评估自建 vs 托管。

## 54.11 卖方的 GTM 与单位经济性

开源商业化的常见 GTM：

- **Open Core**：核心开源，企业功能（多租户/SSO/审计/长期存储）收费；
- **托管服务**：开源 + 运维/ SLA/计费；
- **支持/咨询**：面向自托管大客户；
- **平台捆绑**：指标+日志+追踪+安全；
- **云市场**：按云厂商计费/承诺消费。

单位经济性要算：

```text
ARPA（每客户收入）
- 基础设施/存储/查询成本
- 支持/人力成本
- 获客成本（CAC）
= 毛利/客户
```

可观测性的成本结构特殊：

- 存储/查询成本随客户用量增长，可能侵蚀毛利；
- 高基数/长保留客户可能"越用越亏"；
- 支持/on-call 成本随规模上升；
- 开源版用户可能永远不会付费。

定价策略：

- 按用量（序列/样本/GB/查询）还是按席位/主机？
- 是否设置最低消费/承诺？
- 超额/突发怎么计费？
- 是否提供成本可视/预算工具？
- 免费层是否足够吸引开发者但不侵蚀收入？

### 54.11.1 开源商业化的三条曲线

```text
采用曲线：下载/部署/活跃实例 → 免费用户
转化曲线：免费用户 → 付费托管/企业版
扩张曲线：单团队 → 多团队 → 全公司；指标 → 日志/追踪/安全
```

三条曲线的时间尺度不同：

- **采用**可以很快，但下载不等于生产使用，更不等于付费；
- **转化**通常滞后 6～18 个月，取决于团队规模、合规和运维痛点；
- **扩张**决定净留存（NRR），也是订阅制估值的关键。

只盯"star 数/下载量"会高估商业前景；只看"付费客户数"会忽略未来的扩张空间。健康的结构通常是：采用面广、转化率可控、扩张有明确路径。

### 54.11.2 Open Core 的边界与毛利

Open Core 的关键不是"开源多少行"，而是**边界是否稳定、是否可信**：

- 边界稳定：社区能预期哪些能力永远开源，避免"先开源再收回"；
- 边界可信：企业功能不能靠"故意让开源版不可用"来制造；
- 边界可扩展：托管/多租户/合规/支持是天然的企业价值点；
- 边界可防守：云厂商能托管开源核心，差异化必须来自运维、规模、治理和工作流。

毛利结构：

```text
托管毛利 = 收入 - (存储 + 计算 + 网络 + 支持人力 + 账单/计费)
```

可观测性的特殊之处是**边际成本不为零**：客户用得越多，存储/查询成本越高。高基数、长保留、重查询的客户可能"越用越亏"。因此定价必须与成本驱动因素对齐（序列/样本/扫描字节/保留），并配合配额、降采样和分层存储；否则增长会稀释毛利。

### 54.11.3 定价与价值度量

定价单位最好满足三个条件：

1. **与客户价值相关**：主机/服务/租户/查询量，而不是纯技术内部指标；
2. **与成本相关**：能覆盖存储/计算/支持；
3. **可预测**：客户能做预算，不会因为一次标签爆炸账单翻倍。

常见组合：

- 平台费 + 用量（active series、ingest、retention）；
- 按主机/容器 + 自定义指标包；
- 按租户/席位 + 查询配额；
- 企业版按合同（多租户、SSO、审计、支持）。

无论哪种，都要提供**成本可见性**（按团队/服务/指标的用量）和**护栏**（配额、告警、超额策略）。否则客户会在第一次账单冲击后迁移，获客成本白白浪费。

## 本章小结

- Prometheus 是 Apache 2.0/CNCF 项目，无单一厂商控制。
- 商业模式以托管/长期存储/支持/平台为主。
- 许可（Apache/AGPL/SSPL/BSL）影响托管/分发权利，选型要确认；常见项目许可证矩阵见 54.3.1。
- 开源商业化要同时看采用、转化、扩张三条曲线，以及"用量增长侵蚀毛利"的特殊性。
- 锁定来自查询语言/数据导出/agent/合同；开放标准降低锁定。
- 社区参与影响路线图与风险。
