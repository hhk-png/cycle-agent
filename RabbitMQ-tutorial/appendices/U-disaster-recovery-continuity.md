# 附录 U 灾备、多地域与业务连续性

> 本附录定位：把“高可用”与“灾备”分开。高可用解决节点/可用区内的故障，灾备解决区域、账号、数据损坏和人为误操作。RabbitMQ 的复制能力有明确边界；跨集群没有银弹，必须用 RPO/RTO、备份、复制拓扑和演练把业务连续性做成可验证的工程。

## 先定义 RPO 与 RTO

灾备讨论最容易变成“我们也要多活”。先把两个数字写清楚：

- **RPO（Recovery Point Objective）**：最多能接受丢多少数据，通常用时间表示，例如“最多丢 5 分钟消息”。
- **RTO（Recovery Time Objective）**：最多能接受停多久，例如“区域故障后 30 分钟内恢复下单”。
- **MTTR**：实际平均恢复时间；**MTBF**：平均故障间隔。
- **RCO（Recovery Consistency Objective）**：恢复后数据一致性目标，例如“订单与库存差异不超过 N 条”。

不同业务等级要有不同目标：

| 业务 | 示例 RPO | 示例 RTO | 说明 |
|---|---|---|---|
| 支付/扣款 | 0～秒级 | 分钟级 | 不能丢，重复要幂等 |
| 订单创建 | 秒级 | 分钟级 | 可重放/对账 |
| 通知/短信 | 分钟级 | 小时级 | 可丢可补 |
| 审计日志 | 0 | 小时级 | 合规要求 |
| 指标/遥测 | 分钟级 | 天级 | 可聚合/可丢 |

RPO/RTO 不是运维指标，是业务指标。没有业务 owner 签字的 RPO/RTO，演练时就没有验收标准。

## 故障域模型

灾备设计先画故障域：

```text
进程 -> Pod/节点 -> 机架 -> 可用区 -> 区域 -> 云账号 -> 供应商
```

每一层能承受的故障不同：

- **进程崩溃**：连接断开、未确认消息重投；客户端重连即可。
- **节点故障**：Quorum 队列失去一个副本，多数派仍在；Classic 队列若只在该节点则不可用。
- **机架/可用区故障**：跨 AZ 副本仍有多数派；单 AZ 部署直接不可用。
- **区域故障**：同区域集群整体不可用，需要另一个区域的集群和数据。
- **云账号/供应商故障**：需要跨账号/跨云备份或至少可重建的代码与数据。

RabbitMQ 集群解决的是前两层到第三层的一部分；它不解决区域故障、误删、勒索软件和逻辑数据损坏。后者必须靠备份、不可变存储、权限和演练。

## 备份的对象与边界

备份 RabbitMQ 要分五类对象：

| 对象 | 内容 | 常用方法 | 注意 |
|---|---|---|---|
| 拓扑 | vhost、用户、权限、交换机、队列、绑定、策略、参数 | `export_definitions`、CR YAML、IaC | 不含消息 |
| 配置 | `rabbitmq.conf`、`advanced.config`、环境变量、插件列表 | Git、Secret、ConfigMap | 与版本绑定 |
| 密钥/证书 | CA、服务端/客户端证书、私钥、Erlang cookie | Secret/密钥管理 | 泄露等于接管 |
| 节点数据 | Classic/Quorum/Stream 的段文件、索引、元数据 | PVC 快照、停机拷贝 | 一致性难保证 |
| 消息 | 队列中的消息、Stream 内容 | 上游日志、对象存储、Shovel、消费者归档 | 没有一键备份 |

### 拓扑备份

```bash
# 在任意节点导出 definitions（包含用户密码哈希）
rabbitmqctl export_definitions /backup/definitions-$(date +%F).json

# 恢复
rabbitmqctl import_definitions /backup/definitions-2026-11-26.json
```

管理 API 等价：

```bash
curl -u user:pass http://broker:15672/api/definitions > definitions.json
curl -u user:pass -X POST -H 'content-type: application/json' \
  --data @definitions.json http://broker:15672/api/definitions
```

definitions 的边界：

- 包含 vhost、用户（密码哈希）、权限、topic 权限、参数、策略、队列、交换机、绑定；
- 不包含队列中的消息；
- 不包含插件二进制、TLS 证书、`rabbitmq.conf`；
- 版本差异可能导致导入失败（例如已移除的队列类型/参数）；
- 导入前要确认目标集群没有同名但配置不同的资源。

### 消息备份

RabbitMQ 没有“导出所有队列消息”的通用命令。常见方案：

1. **上游事件日志/对象存储归档**：生产者在写 broker 前/同时写一份不可变日志；需要时重放。
2. **消费者归档**：关键消费者把原始消息落到对象存储/数据湖，按业务键可重放。
3. **Shovel 到备份集群**：把源队列消息转发到目标集群；注意它是消费转发，不是无损复制，配置错误会丢/重复。
4. **文件系统/PVC 快照**：停机或按存储一致性快照；恢复时要验证日志、索引和消息计数。
5. **Stream retention**：Stream 本身保留历史，可作为重放源；但 retention 不是备份，删除/过期后不可恢复。

Quorum 队列的文件备份尤其要小心：

- 每个副本各自持有 Raft 日志；单个 follower 可能落后；
- 只快照一个节点，恢复后可能缺少已提交但未复制到该节点的消息；
- 对运行中的集群做跨节点非原子快照，可能得到不一致的成员/日志状态；
- 更稳妥的是“逻辑导出 + 应用归档”，或停机后按官方恢复流程处理。

不要把“PVC 快照成功”当成“消息可恢复”。恢复演练要实际启动集群、导入拓扑、校验消息计数和抽样内容。

### Stream 备份

Stream 的保留策略决定可恢复窗口：

- `max-age`/`max-length-bytes` 到期后数据被删除；
- 消费 offset 不是备份，消费者可以重读但前提是数据还在；
- 跨集群没有内置同步复制；需要应用层双写、外部镜像工具或上游日志；
- 文件快照要停机/保证一致性，恢复后校验 leader/coordinator 状态。

## 跨集群复制的三种现实方案

### 方案 A：Federation（异步转发）

Federation 把上游 exchange/queue 的消息转发到下游：

- 适合“事件扩散/多区域订阅”；
- 异步、至少一次、可能重复；
- 不是同步复制，不保证 RPO=0；
- 上游队列积压不会自动完整复制（取决于 federation 类型和 backlog 设置）；
- 需要处理循环、重复、顺序。

### 方案 B：Shovel（队列搬运）

Shovel 从一个队列消费并转发到另一个队列/broker：

- 适合迁移、灾备转发、跨版本搬运；
- 源消息在目标确认后 ack（取决于 ack 模式）；
- 配置错误、目标不可用、prefetch 不当会导致重复/积压；
- 不是 fan-out；多个 Shovel 会竞争同一队列。

### 方案 C：应用层双写/事件日志

应用在写主集群的同时写备份区域/对象存储/日志：

- 最灵活，能按业务键做幂等/冲突处理；
- 成本最高，复杂度在应用；
- 适合 RPO 极低的关键业务；
- 必须处理“双写部分成功”的不一致，配合 outbox/对账。

没有一种方案能同时给你“零丢失、零重复、零运维”。选型要先写清楚业务能接受哪种失败。

## Active-Passive 拓扑

### Pilot Light（最小备份）

- 备份区域只保留网络、密钥、IaC、definitions 和少量节点；
- 平时不承载流量；
- 故障时扩容、恢复数据、切流；
- RTO 较长（小时级），成本低。

### Warm Standby（温备）

- 备份区域有完整集群和复制链路，但容量较小；
- 关键队列通过 Federation/Shovel 或应用双写保持热数据；
- 故障时扩容、校验、切流；
- RTO 分钟级，成本中等。

### Hot Standby（热备）

- 两个区域都全量运行，流量按权重切换；
- 需要解决双向复制、重复、冲突和顺序；
- 成本最高，运维最复杂；
- 只有明确业务收益时才做。

Active-Passive 的关键不是“备集群存在”，而是：

1. 备份数据是否持续更新？
2. 备份集群是否定期启动/验证？
3. 切换后客户端如何发现新地址？
4. 回切时如何避免丢消息/重复？
5. 切换过程谁有权决策？

## Active-Active 拓扑

Active-Active 常见三种切法：

1. **按地域分区**：华东用户写华东，华南用户写华南；同一实体不跨区写。
2. **按业务域分区**：订单在主区，库存/物流在备区；跨域用事件同步。
3. **按租户分区**：大客户固定区域；中小客户共享。

真正危险的是“同一队列/同一实体在两个区域同时写”。这会产生：

- 消息重复；
- 顺序冲突；
- 库存/余额双花；
- 状态机分叉。

解决冲突不能只靠“最后写入获胜”：

- 用业务版本号/状态机；
- 用幂等键；
- 用 CRDT/可合并结构（适合计数/集合，不适合金额）；
- 用单写者/分区所有权；
- 用对账和人工兜底。

## 切流与客户端配合

灾备切换不只是 broker 的事。客户端要配合：

- **DNS/GSLB**：TTL 不要太长，但也不要指望秒级生效；客户端和 JVM 可能缓存 DNS。
- **连接重连**：指数退避 + 抖动，避免切换瞬间重连风暴。
- **拓扑恢复**：重连后重新声明 exchange/queue/binding，处理已存在/参数冲突。
- **confirm/return**：重连后重新开启 confirm，处理未确认消息。
- **消费者重启**：重新注册 consumer，处理重复投递。
- **幂等**：切换窗口内重复/乱序是常态。
- **健康检查**：不要把“TCP 可连”当成“可发布/可消费”。

一个切换 runbook 的骨架：

```text
T-30：确认故障范围、RPO/RTO、业务影响
T-20：冻结变更，通知业务/客服/on-call
T-10：校验备集群健康、拓扑、权限、证书、磁盘
T-5： 停止主区入口（或切只读），等待在途消息/confirm
T-0： DNS/GSLB 切流；客户端重连；监控确认
T+5： 校验发布/消费/积压/DLQ；对账
T+30：业务确认；记录时间线；决定是否回切
```

回切更难：要确认主区数据已追平、备区积压已清、重复/冲突已处理，否则会把问题带回去。

## 数据一致性与对账

跨区域复制通常是至少一次，必须假设重复和乱序：

- 每条消息带全局唯一 `message_id`/业务键；
- 消费者用唯一约束/去重表/状态机；
- 关键金额用对账，不依赖消息顺序；
- 记录复制位点/批次，便于定位差异；
- 定期抽样比较主备消息计数和业务状态；
- 差异要有自动修复和人工审核入口。

对账维度：

```text
生产数 vs 消费数
主区订单状态 vs 备区订单状态
库存扣减 vs 订单支付
DLQ 数量 vs 失败业务记录
消息时间戳 vs 业务发生时间
```

## 灾难恢复演练

没有演练的灾备等于没有灾备。演练层次：

| 层次 | 内容 | 频率 |
|---|---|---|
| 桌面推演 | 角色、决策、通知、runbook | 每季度 |
| 组件故障 | 杀进程/节点、断网、磁盘满 | 每月/每季度 |
| AZ 故障 | 关一个 AZ 的节点 | 每半年 |
| 区域切换 | 实际切到备区 | 每半年/每年 |
| 数据恢复 | 从备份恢复拓扑/消息 | 每季度 |
| 误删/勒索 | 删除队列/加密文件后的恢复 | 每年 |

演练验收：

- 实际 RTO/RPO 是否达标；
- 消息是否重复/丢失；
- 客户端是否自动重连；
- 监控/告警是否及时；
- 对账是否发现差异；
- runbook 是否有过期步骤；
- 谁在什么时候做了什么（时间线）。

演练后要更新：拓扑、备份、告警阈值、客户端配置、联系人、权限。

## 合规与数据驻留

受监管行业要额外考虑：

- **数据驻留**：消息/备份是否跨境；vhost/集群是否按区域隔离。
- **加密**：传输 TLS、静态加密、备份加密、密钥轮换。
- **审计**：谁发布/消费/修改拓扑；管理面操作日志；备份访问日志。
- **保留/删除**：消息保留期、备份保留期、右到删除（GDPR 等）。
- **供应商**：托管服务的子处理者、SLA、审计报告。
- **不可变备份**：防勒索/内部滥用；WORM/对象锁。

备份里通常含 PII/交易数据，必须按生产数据标准保护。不要用“反正是备份”降低权限。

## 成本模型

灾备成本不只是备集群机器：

```text
灾备成本 = 备区资源 + 跨区流量 + 备份存储 + 复制链路
         + 演练人力 + 运维复杂度 + 机会成本
```

常见误区：

- 备集群按生产 100% 容量常开，但从不验证；
- 只备份 PVC，不备份 definitions/证书；
- 跨区复制全量消息，流量费超过机器费；
- 演练只做桌面推演，不实际切流；
- 备区版本/插件/配置与主区不一致，切换即失败。

按业务分级：核心交易热备/双活，普通业务温备，内部系统可重建。

## 常见错误

1. **把 Quorum 当跨区域复制**：Quorum 是集群内多数派复制，不是跨区域灾备。
2. **把 Federation 当同步复制**：Federation 异步、至少一次、可能重复。
3. **只备份 definitions**：恢复后队列是空的。
4. **只备份 PVC**：恢复后拓扑/用户/策略缺失。
5. **备集群从不启动**：证书过期、版本不兼容、磁盘不足，切换时才发现。
6. **没有回切方案**：切过去容易，切回来丢数据。
7. **DNS TTL 过长/客户端缓存**：切流后部分客户端仍连旧地址。
8. **切换时全量重连**：没有退避/抖动，压垮新集群。
9. **忽略重复/乱序**：跨区切换后重复扣款。
10. **没有业务 owner**：RPO/RTO 无人签字，演练无法验收。

## 检查清单

- [ ] 每个业务等级有明确 RPO/RTO/RCO 和 owner；
- [ ] 故障域画清楚，单 AZ/单区域故障有预案；
- [ ] definitions、配置、证书、节点数据、消息分别有备份；
- [ ] 备份加密、访问受控、不可变（关键业务）；
- [ ] 备份保留期覆盖恢复/合规窗口；
- [ ] 跨集群复制方案明确（Federation/Shovel/应用双写）；
- [ ] Active-Active 的实体所有权/冲突策略明确；
- [ ] 客户端支持重连、拓扑恢复、confirm/return、幂等；
- [ ] DNS/GSLB 切换和回切演练过；
- [ ] 每季度至少一次恢复演练，记录实际 RTO/RPO；
- [ ] 监控覆盖复制延迟、积压、DLQ、证书、磁盘；
- [ ] 合规/数据驻留要求映射到集群和备份位置。

## 小结

灾备不是“再建一个集群”，而是把 RPO/RTO、故障域、备份对象、复制方案、切流和演练连成闭环。RabbitMQ 的 Quorum 解决集群内复制，Federation/Shovel 解决异步跨集群转发，应用层双写/事件日志解决更低 RPO 的需求；三者都不能消除重复、乱序和冲突。真正可靠的是：明确业务目标、分层备份、可回切、持续演练，以及消费端幂等和对账。
