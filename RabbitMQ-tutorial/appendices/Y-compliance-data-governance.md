# 附录 Y 消息系统合规与数据治理

> 本附录定位：把 RabbitMQ 的技术控制映射到常见合规框架（GDPR、PCI DSS、HIPAA、SOC 2、等保 2.0）的工程语言。它不是法律意见，也不替代法务、审计师或认证机构的判断。不同司法辖区、行业和客户合同的要求不同；落地前必须由合规/法务确认适用范围。

## 为什么消息系统是合规重灾区

消息系统同时具备四个“合规放大器”：

1. **数据停留时间长**：队列积压、DLQ、Stream retention、备份都可能保留消息数天到数月；
2. **数据副本多**：Quorum 副本、Federation/Shovel 下游、备份、日志、客户端缓冲；
3. **访问路径多**：生产者、消费者、管理 API、运维脚本、监控/追踪、插件；
4. **元数据也会泄露**：routing key、队列名、header、message_id、trace、租户 ID 都可能包含业务/个人信息。

很多团队只盯着“消息正文有没有加密”，却忽略了 DLQ 里的失败消息、备份里的旧数据、日志里的 header、跨区域复制的数据驻留。合规审计问的往往不是“你有没有 TLS”，而是“你能否证明数据从产生到删除的全生命周期受控”。

## 数据分类：先知道有什么

| 数据对象 | 位置 | 示例 | 风险 | 控制重点 |
|---|---|---|---|---|
| 消息正文 | 队列/Stream/磁盘/副本 | 订单、支付、病历、文档 | 高（PII/PCI/PHI） | 加密、访问、保留、脱敏 |
| 消息属性/header | broker 元数据、消息 | routing key、tenant、trace、message_id | 中高（可能含 PII） | 最小化、脱敏、访问审计 |
| 拓扑元数据 | vhost/queue/exchange/binding | 队列名暴露业务结构 | 中 | ACL、审计、命名规范 |
| 管理/审计日志 | broker 日志、SIEM | 登录、权限变更、管理操作 | 中高 | 保留、篡改防护、脱敏 |
| 消费/投递日志 | 客户端/服务端 | message_id、失败原因 | 中 | 不记录正文/密码 |
| DLQ/parking lot | 队列 | 失败消息原文 | 高 | 访问审批、保留期、加密 |
| 备份/快照 | 对象存储/磁盘 | 全量消息/元数据 | 高 | 加密、保留、驻留、删除 |
| 指标/追踪 | Prometheus/APM | 租户标签、延迟、ID | 中 | 高基数控制、脱敏 |
| 客户端缓冲 | 内存/本地磁盘 | 未确认消息、重试队列 | 中高 | 加密、清理、最小化 |

分类之后，才能回答：哪些数据必须加密、谁能读、保留多久、删除请求如何传播、备份是否覆盖。

## 控制面模型

把合规要求拆成九个控制面，每个面都要有“手段 + 证据”：

| 控制面 | 目标 | RabbitMQ 手段 | 证据 |
|---|---|---|---|
| 身份 | 谁能连 | 内部用户、OAuth 2.0/OIDC、LDAP、mTLS | 用户列表、IdP 配置、证书 |
| 授权 | 能做什么 | vhost ACL、topic authorization、管理面角色 | 权限导出、评审记录 |
| 传输加密 | 防窃听/篡改 | TLS/AMQPS、mTLS、管理 HTTPS | 配置、证书链、扫描报告 |
| 静态加密 | 防磁盘/备份泄露 | 云盘/KMS、备份加密、PVC 加密 | 加密配置、密钥策略 |
| 审计 | 谁做了什么 | 管理事件、日志、SIEM、Firehose（短期） | 日志样本、保留策略 |
| 保留/删除 | 数据不超期 | TTL、max-length、Stream retention、DLQ 保留 | policy 导出、清理记录 |
| 数据驻留 | 数据不乱跑 | 集群 placement、Federation 方向、备份位置 | 拓扑图、区域清单 |
| 可用性/完整性 | 不丢不改 | Quorum、备份、DR、校验 | 演练报告、RPO/RTO |
| 供应商 | 外包可控 | 合同、SLA、安全公告、退出条款 | DPA、SOC 2 报告、支持合同 |

这张表的价值是逼你把“合规”从一句口号变成可检查的对象。没有证据的控制，审计时等于没有。

## GDPR：个人数据与跨境

GDPR 的核心不是“加密”，而是**处理个人数据的合法性、最小化、限期、可问责**。消息系统常见映射：

| GDPR 要求 | 工程问题 | RabbitMQ 落地 |
|---|---|---|
| 合法性/目的限制 | 消息里为什么有个人数据 | 事件契约标注 purpose；避免把全量用户对象塞进事件 |
| 数据最小化 | 是否只需要 ID | 用业务 ID/令牌替代姓名/手机号；正文只放必要字段 |
| 存储限制 | 队列/DLQ/Stream 保留多久 | TTL、max-length、Stream retention、DLQ 清理 |
| 完整性与保密性 | 传输/静态/访问 | TLS、磁盘/备份加密、vhost ACL、OAuth/mTLS |
| 可问责 | 能否证明 | 审计日志、权限评审、处理记录、DPIA |
| 数据主体权利 | 查询/删除/更正 | 业务表为准；消息/ DLQ/备份/下游副本要有删除流程 |
| 跨境传输 | 数据是否出境 | 集群/备份/复制区域；Federation 方向；供应商驻地 |

难点是**删除权**：删掉业务库一行，不等于删掉消息。消息可能还在：

- 队列 ready/unacked；
- Quorum 副本/Stream segment；
- DLQ/parking lot；
- 备份/快照；
- 日志/追踪/指标标签；
- 下游消费者/数据仓库；
- Federation/Shovel 的对端；
- 客户端本地缓冲。

可操作的流程：

1. 以业务库为真相源，标记删除/匿名化；
2. 发布“删除/更正”事件，消费者幂等处理；
3. 队列消息靠 TTL/消费自然消化；必要时按业务键清理（需要可查询的索引/工具）；
4. DLQ/parking lot 纳入同一保留策略；
5. 备份按保留策略过期；法律保留（legal hold）例外要记录；
6. 下游副本/数据仓库各自执行删除；
7. 记录删除请求、执行范围、未覆盖项。

“删除队列”不是删除数据：副本、备份、日志、下游仍可能保留。审计要的是**可证明的删除范围**，不是一次 `queue.delete`。

## PCI DSS：卡数据不在消息里

PCI DSS 的核心原则之一是：**授权后不得保留敏感认证数据**（SAD，如 CVV、完整磁道），即使加密也不应作为常规存储。消息系统常见的错误是把支付请求/响应原文（含 PAN、CVV）塞进队列、DLQ 和日志。

工程建议：

1. **令牌化**：消息只传 payment token/订单 ID，不传 PAN/CVV；
2. **不记录敏感字段**：日志、追踪、DLQ 检查工具都要脱敏；
3. **分段**：承载卡数据的 broker 独立集群/vhost/网络，限制访问；
4. **加密**：传输 TLS、静态磁盘/备份加密、密钥管理；
5. **访问控制**：最小权限、MFA（管理面）、审计；
6. **保留**：消息/DLQ/备份的保留期与 PCI 要求一致；
7. **供应商**：托管服务的 PCI 范围、共享责任、合规证明。

如果业务确实必须在消息中处理卡数据，先问“能否改架构”。不能改时，把 broker、备份、日志、监控、运维访问全部纳入 PCI 范围，并让 QSA 确认边界。不要把“TLS 开了”当成 PCI 合规。

## HIPAA：PHI 与 BAA

HIPAA 关注受保护健康信息（PHI）的机密性、完整性和可用性。消息系统常见控制：

- 与托管商签 BAA（Business Associate Agreement）；
- 传输/静态加密；
- 唯一用户标识、最小权限、紧急访问流程；
- 审计日志与完整性保护；
- 保留/销毁策略；
- 事件响应与 breach notification；
- 备份/DR。

PHI 可能出现在消息正文、header、DLQ、日志、追踪标签。工程上要做的不是“给队列改名”，而是**数据流映射 + 访问审计 + 加密 + 保留**。如果使用云托管，确认共享责任模型和 BAA 覆盖范围。

## SOC 2：证据与持续控制

SOC 2 不是“一个证书”，而是对信任服务标准（安全性、可用性、处理完整性、保密性、隐私）的控制审计。消息系统相关的证据通常包括：

- 访问控制矩阵与定期评审；
- 变更管理（拓扑/配置/升级评审）；
- 监控/告警/事件响应；
- 备份/恢复演练；
- 容量/可用性报告；
- 加密/密钥管理；
- 供应商管理；
- 日志保留与篡改防护。

RabbitMQ 侧可提供的证据：

```text
- definitions 导出（拓扑/用户/权限/策略）
- vhost/用户/权限清单与评审记录
- TLS 配置、证书链、过期监控
- 管理面访问日志/审计事件
- 备份策略与恢复演练报告
- 升级/变更 runbook 与审批记录
- 告警规则/runbook/on-call 记录
```

SOC 2 审计关心“控制是否持续运行”，不是“某天配置过”。把证据纳入日常运维，而不是审计前临时补。

## 等保 2.0：控制项映射

等保 2.0 的控制项因级别/行业而异。下面是常见工程映射，具体条款以测评机构要求为准：

| 控制域 | 常见要求 | RabbitMQ 手段 |
|---|---|---|
| 身份鉴别 | 唯一身份、复杂度、定期更换 | 独立用户、OAuth/LDAP、强密码、禁用 guest |
| 访问控制 | 最小权限、职责分离 | vhost ACL、管理/数据面分离、只读账号 |
| 安全审计 | 记录关键操作、保护日志 | 管理事件、日志集中、保留/防篡改 |
| 入侵防范 | 最小服务、漏洞管理 | 关闭不需要的插件/端口、补丁、镜像扫描 |
| 数据完整性 | 防篡改 | TLS、磁盘校验、Quorum、备份校验 |
| 数据保密性 | 加密/访问控制 | TLS、静态加密、ACL、脱敏 |
| 备份恢复 | 定期备份、演练 | definitions/消息备份、RPO/RTO、恢复演练 |
| 剩余信息保护 | 删除后不可恢复 | 磁盘/备份销毁、密钥销毁、DLQ 清理 |
| 个人信息保护 | 最小化、授权、删除 | 数据分类、TTL、删除流程、审计 |

等保测评会看“制度 + 技术 + 证据”。只有技术配置，没有制度/记录，通常不算达标。

## RabbitMQ 的具体落地清单

### 身份与访问

- 禁用/限制 `guest`，生产不用默认账号；
- 每服务独立用户，configure/write/read 正则最小化；
- 管理面与数据面账号分离；管理面不暴露公网；
- OAuth/OIDC 短令牌、正确 audience/issuer/scope；
- mTLS 证书 SAN/CN 与身份映射，证书轮换/吊销；
- 定期权限评审，删除离职/下线服务用户。

### 加密

- 客户端到 broker：TLS/AMQPS，校验证书与主机名；
- broker 到 broker：Erlang distribution 走可信网络/TLS（按版本支持）；
- 静态：云盘/KMS、PVC 加密、备份加密；
- 密钥：独立管理、轮换、访问审计；
- 不要用“关闭证书校验”解决连接问题。

### 审计与日志

- 管理操作（建删队列/策略/用户）进 SIEM；
- 认证失败/权限拒绝告警；
- 日志不记录消息正文、密码、完整 token；
- 追踪只记录 message_id/correlation_id，敏感字段脱敏；
- 日志保留满足合规，且有防篡改/访问控制。

### 保留与删除

- 队列 TTL/max-length、Stream retention、DLQ 保留期；
- 业务删除事件 + 下游幂等删除；
- 备份过期与 legal hold 流程；
- 删除范围记录（队列/副本/DLQ/备份/日志/下游）；
- 定期演练“删除请求 → 证据”。

### 数据驻留

- 集群/备份/复制区域清单；
- Federation/Shovel 方向与数据分类；
- 管理面/运维访问是否跨境；
- 云厂商的 region/zone 与数据驻留承诺；
- 跨境传输的合同/机制（按适用法律）。

### 供应商与供应链

- 固定 RabbitMQ/Erlang/插件版本；
- 官方镜像/签名包、CVE 扫描；
- 托管商版本、插件限制、共享责任；
- 支持合同/SLA/退出条款；
- 插件来源可信，避免依赖已归档插件。

## 审计证据清单

| 证据 | 证明什么 | 常见缺口 |
|---|---|---|
| definitions 导出 | 拓扑/用户/权限/策略 | 过期、未版本化 |
| 权限矩阵 + 评审记录 | 最小权限 | 只有清单，没有评审 |
| TLS 配置/证书链 | 传输加密 | 自签名、未校验、过期 |
| 管理面访问日志 | 谁改了什么 | 未集中、未保留、可篡改 |
| 备份策略 + 恢复报告 | 可恢复 | 只备份未演练 |
| DLQ/保留策略 | 数据不超期 | DLQ 无 owner/无清理 |
| 数据流图 | 数据去哪 | 缺下游/备份/跨境 |
| 事件响应 runbook | 出事能处理 | 没有演练记录 |
| 供应商 DPA/SOC 2 | 外包可控 | 未覆盖实际服务 |
| 删除请求记录 | 数据主体权利 | 只删业务库，未覆盖消息 |

审计访谈常问：

1. 消息里有哪些个人/敏感数据？谁定义的？
2. 数据保留多久？DLQ/备份/日志呢？
3. 谁能读队列？权限多久评审一次？
4. 删除请求如何传播到消息/副本/备份/下游？
5. 跨境复制/备份在哪里？
6. 最近一次恢复演练是什么时候？RPO/RTO 多少？
7. 管理面暴露在哪里？谁有管理员权限？
8. 插件/镜像来源？漏洞如何响应？

答不上来的问题，就是合规缺口。

## 常见误区

| 误区 | 现实 |
|---|---|
| “开了 TLS 就合规” | TLS 只是传输加密；访问、审计、保留、删除、驻留都要覆盖。 |
| “删除队列就删了数据” | 副本、备份、DLQ、日志、下游可能仍保留。 |
| “日志不含正文就没有 PII” | header/routing key/message_id/租户 ID 也可能含个人信息。 |
| “DLQ 是内部队列，不受保留策略约束” | DLQ 往往保留最久、敏感度最高，必须纳入治理。 |
| “vhost 等于强隔离” | vhost 不隔离网络/资源；强隔离要独立集群/账号/网络。 |
| “云托管自动合规” | 共享责任；版本/插件/备份/驻留仍要确认。 |
| “加密等于访问控制” | 有密钥的人仍能读；ACL/审计/最小权限不可省。 |
| “备份不受删除权影响” | 备份通常有保留期例外，但要有策略、记录和到期删除。 |

## 合规检查清单

- [ ] 完成消息数据分类（正文/header/元数据/日志/DLQ/备份/追踪）；
- [ ] 画出数据流：生产、队列、副本、DLQ、下游、备份、跨境；
- [ ] 每个数据对象有 owner、保留期、访问矩阵；
- [ ] 禁用 guest，服务独立用户，最小权限；
- [ ] TLS/mTLS、静态加密、备份加密、密钥轮换；
- [ ] 管理面隔离、HTTPS、强认证、审计；
- [ ] 日志/追踪脱敏，不记录正文/密码/token；
- [ ] DLQ/parking lot 有保留期、访问审批、清理记录；
- [ ] 删除请求覆盖消息/副本/DLQ/备份/日志/下游；
- [ ] 数据驻留与跨境复制有清单和合同依据；
- [ ] 备份/恢复演练有报告，RPO/RTO 明确；
- [ ] 供应商 DPA/SOC 2/版本矩阵/退出条款；
- [ ] 插件/镜像来源可信，CVE 响应流程；
- [ ] 审计证据可随时导出，而不是审计前补；
- [ ] 合规/法务/安全/平台团队职责清晰。

## 小结

消息系统合规不是“加密 + 日志”两个开关，而是数据分类、访问控制、加密、审计、保留/删除、驻留、备份、供应商和事件响应的组合。GDPR/PCI/HIPAA/SOC 2/等保的条款不同，但工程落点高度重叠：知道数据在哪、谁能读、保留多久、如何删除、如何证明。RabbitMQ 提供了 vhost/ACL、TLS/OAuth、Quorum、TTL/retention、definitions、管理 API 等积木；合规性来自你如何组合并留下证据。技术安全见第 15 章，事件契约与数据最小化见[附录 O](O-event-contracts-governance.md)，灾备与数据驻留见[附录 U](U-disaster-recovery-continuity.md)。
