# 附录 S 消息架构模式与反模式目录

第 05 章给了六种拓扑模式，第 19 章讲了 outbox、Saga 和幂等。本附录把这些散落的模式收拢成一份可检索的目录：每个模式回答“它解决什么问题、RabbitMQ 怎么表达、失败时会发生什么、该测什么”。它不是模式大全的抄写，而是把企业集成模式（EIP）放回 RabbitMQ 的交换机、队列、确认和运维约束里。

使用方式：

- 设计新拓扑时，从“问题”查模式，不要从“我想用 topic exchange”倒推需求；
- 评审旧拓扑时，先查反模式目录，再查模式是否被误用；
- 写测试时，用“模式 -> 必须覆盖的失败”表补齐重复、乱序、崩溃和积压场景。

## 模式不是配方

同一个业务问题可以有多种实现。选择时先问三个问题：

1. **语义**：这条消息是命令还是事件？需要每消息一次、每消费者一次，还是广播？
2. **失败**：重复、乱序、丢失、积压、毒消息，哪些可以接受，哪些必须处理？
3. **所有权**：谁声明拓扑、谁负责清理、谁在故障时被叫醒？

模式的价值是提供共同语言，不是替代判断。下面每个模式都给出“最小拓扑”和“失败方式”，因为**模式的价值往往在失败路径上才体现**。

## 基础投递模式

### 点对点 / 工作队列（Work Queue）

```text
producer -> exchange (direct) -> queue -> worker 1..N
```

- 语义：一条消息由一个消费者处理；
- RabbitMQ：多个 consumer 竞争同一个队列；手动 ack + prefetch；
- 适用：任务分发、后台作业、图片处理、账单生成；
- 失败：消费者崩溃导致重投；处理慢导致积压；毒消息反复 requeue；多队列绑定同一 key 变成广播。

关键测试：重复投递、ack 前崩溃、prefetch 饱和、毒消息进入 DLX。

### 发布/订阅（Pub/Sub）

```text
producer -> exchange (fanout/topic) -> queue A, queue B, queue C
```

- 语义：每个订阅者收到一份；
- RabbitMQ：每个订阅者独立队列 + 绑定；不是“多个 consumer 共享一个队列”；
- 适用：事件通知、审计、缓存失效、多下游投影；
- 失败：订阅者队列积压互不影响，但会各自占磁盘；新增订阅者需要补历史时，普通队列没有重放能力。

关键测试：新增/删除绑定、订阅者离线、队列独立积压、消息重复。

### 请求/响应（Request/Reply）

```text
client -> rpc.exchange -> rpc.queue -> server
server -> reply queue (reply-to) -> client
```

- 语义：一问一答，通常带 `correlation-id`；
- RabbitMQ：`reply-to` + `correlation-id`；临时回复队列用 exclusive/auto-delete；4.2+ 支持 AMQP 1.0 Direct Reply-To；
- 适用：同步 RPC、查询、命令确认；
- 失败：回复队列泄漏、超时无响应、correlation-id 冲突、服务端重复处理。

关键测试：超时、回复丢失、重复回复、客户端取消、服务端崩溃。

### 竞争消费者（Competing Consumers）

- 语义：多个消费者共享一个队列，提升吞吐；
- RabbitMQ：同一队列多个 consumer；prefetch 控制每个消费者的未 ack 上限；
- 失败：消费者处理能力不同导致倾斜；prefetch 过大导致消息堆在慢消费者；消费者优先级/单活消费者改变竞争关系。

关键测试：消费者增减、慢消费者、prefetch 调整、公平分发。

### 单活消费者（Single Active Consumer）

- 语义：同一队列同一时刻只有一个消费者活跃，其他待命；
- RabbitMQ：`x-single-active-consumer`；故障时自动切换；
- 适用：需要顺序或单写者的场景；
- 失败：切换期间消息堆积；待命消费者健康但未接管；与多队列分区混用导致顺序错觉。

关键测试：活跃消费者崩溃、切换时间、积压恢复、重复投递。

### 独占消费者（Exclusive Consumer）

- 语义：队列只允许一个消费者；
- RabbitMQ：`exclusive` consume；连接关闭后释放；
- 适用：严格单写者、临时排他任务；
- 失败：消费者崩溃后队列无人消费；与自动删除/排他队列混淆；多实例部署时第二个实例直接失败。

关键测试：第二个消费者被拒、连接断开释放、重启恢复。

## 路由与消息形态模式

### 内容路由器（Content-Based Router）

```text
exchange (topic/headers) -> queue per route
```

- 语义：按消息内容/属性路由到不同下游；
- RabbitMQ：topic routing key、headers exchange、绑定参数；
- 失败：路由键设计成“万能前缀”导致绑定爆炸；headers 过大；路由规则散落在生产者和绑定两处。

关键测试：每条路由的命中/不命中、未知路由的 AE/DLX、绑定变更。

### 消息过滤器（Message Filter）

- 语义：消费者只处理满足条件的消息；
- RabbitMQ：尽量在 exchange/binding 层过滤；不要在消费者里拉全量再丢弃；
- 失败：过滤条件变化需要重建绑定；消费者侧过滤造成无效流量和积压。

关键测试：过滤边界、绑定更新、过滤后空队列。

### 拆分器（Splitter）

- 语义：一条大消息拆成多条子消息；
- RabbitMQ：生产端拆分，或 Stream + 消费端拆分；
- 失败：部分子消息失败导致半完成；重放时重复拆分；顺序丢失。

关键测试：部分失败、重放、子消息幂等、聚合对账。

### 聚合器（Aggregator）

- 语义：多条相关消息聚合成一条；
- RabbitMQ：按 correlation-id/业务键分区到同一队列，单消费者聚合；状态存数据库/缓存；
- 失败：部分消息永远不到，聚合窗口超时；重启丢状态；重复消息导致重复聚合。

关键测试：超时、乱序、重复、重启恢复。

### 重排序器（Resequencer）

- 语义：把乱序消息恢复为业务顺序；
- RabbitMQ：按 key 分区 + 单活消费者，或应用层缓冲/排序；
- 失败：缺号导致永久等待；缓冲无界；多分区全局顺序幻觉。

关键测试：缺号、重复、超时、缓冲区上限。

### 索赔检查（Claim Check）

- 语义：大消息放对象存储，消息只传引用；
- RabbitMQ：消息体传 URI + 校验和 + 版本；消费者按需拉取；
- 失败：对象存储权限/生命周期与消息不一致；引用失效；消息小但对象大导致下游超时。

关键测试：对象缺失、权限拒绝、校验和不匹配、清理策略。

### 路由单（Routing Slip）

- 语义：消息携带“下一步去哪”的步骤列表；
- RabbitMQ：headers 里的步骤列表 + 动态路由/网关；
- 失败：步骤变更导致在途消息走旧路径；步骤失败无补偿；路由单被篡改。

关键测试：步骤失败、重试、版本变更、审计。

### 接收者列表（Recipient List）

- 语义：一条消息发给动态计算的多个接收者；
- RabbitMQ：fanout + 动态绑定，或应用层逐条转发；
- 失败：接收者列表爆炸；部分接收者失败；重复投递。

关键测试：空列表、部分失败、重复、权限。

### 线夹（Wire Tap）

- 语义：旁路复制一份消息用于审计/调试；
- RabbitMQ：额外队列绑定到同一 exchange；或 Firehose/追踪插件；
- 失败：旁路队列积压拖垮磁盘；敏感数据进入审计；旁路消费者 ack 影响主流程（不应影响）。

关键测试：旁路独立积压、敏感字段脱敏、主流程不受影响。

### 消息历史（Message History）

- 语义：记录消息经过的步骤/时间；
- RabbitMQ：headers/annotations 追加历史；或外部审计存储；
- 失败：headers 无限增长；敏感信息泄露；历史与实际处理不一致。

关键测试：历史截断、脱敏、并发追加。

## 可靠性与一致性模式

### 幂等接收者（Idempotent Receiver）

- 语义：同一消息处理多次，业务结果只发生一次；
- RabbitMQ：消息带 `message-id`/业务键；消费端唯一约束/去重表；
- 失败：去重表无限增长；键选择错误；并发重复插入冲突；ack 前崩溃。

关键测试：重复投递、并发重复、ack 前崩溃、去重表清理。

### 事务性 Outbox

- 语义：业务数据和“待发布事件”在同一数据库事务提交；
- RabbitMQ：outbox 表 + 发布器 + confirm；发布成功后标记 sent；
- 失败：发布器崩溃在“发布成功、标记 sent 之前”导致重复；多发布器乱序；outbox 表膨胀。

关键测试：发布前崩溃、发布后崩溃、重复发布、并发发布器、清理。

### Inbox

- 语义：消费端先把消息写入 inbox，再处理；
- RabbitMQ：inbox 表 + 唯一键 + 状态机；处理成功后 ack；
- 失败：inbox 与业务表不在同一事务；重复消费；inbox 清理与重放窗口冲突。

关键测试：重复、崩溃、事务边界、重放。

### Saga / 流程管理器（Process Manager）

- 语义：长流程用本地事务 + 补偿，而不是分布式事务；
- RabbitMQ：命令/事件 exchange + 状态机持久化 + 超时；
- 失败：补偿失败；状态机版本冲突；消息乱序；人工介入缺失。

关键测试：每一步失败、补偿幂等、超时、重复、乱序。

### 死信通道（Dead Letter Channel）

- 语义：处理失败/过期/超限的消息进入可观测的失败通道；
- RabbitMQ：DLX + DLQ；`x-death` 记录原因；
- 失败：DLX 不可路由；DLQ 自身积压；死信循环；`x-death` 被覆盖。

关键测试：拒绝、过期、超长、delivery-limit、DLQ 告警。

### 毒消息（Poison Message）

- 语义：一条消息反复失败，必须隔离而不是无限重试；
- RabbitMQ：`delivery-limit` + DLX；或应用层重试计数；
- 失败：requeue 风暴；重试计数丢失；毒消息阻塞顺序队列。

关键测试：达到上限、进入 parking lot、人工重放。

### 停尸房（Parking Lot）

- 语义：把无法处理的消息集中存放，等待人工/异步修复；
- RabbitMQ：独立队列 + 管理工具 + 审计；
- 失败：只进不出；缺少 owner；重放时再次失败。

关键测试：入库、查询、重放、权限、保留期。

### 退避重试（Retry with Backoff）

- 语义：失败后延迟重试，避免打爆下游；
- RabbitMQ：TTL + DLX、多级延迟桶、Quorum 原生延迟重试（4.3+）、`x-opt-delivery-time`（4.4+）；
- 失败：队头阻塞；延迟桶容量；重试风暴；重试改变优先级/顺序。

关键测试：退避曲线、最大次数、延迟精度、重启恢复。

### 断路器（Circuit Breaker）

- 语义：下游连续失败时快速失败，恢复后放量；
- RabbitMQ：消费端状态 + 暂停消费/降低 prefetch；或网关层；
- 失败：断路器状态不持久；半开探测打爆下游；与重试叠加。

关键测试：打开/半开/关闭、恢复、并发。

### 关联标识（Correlation Identifier）

- 语义：把请求、响应、事件、日志串起来；
- RabbitMQ：`correlation-id` + message-id + trace headers；
- 失败：ID 冲突；跨协议丢失；日志未采集。

关键测试：端到端追踪、重复 ID、跨协议映射。

### 返回地址（Return Address）

- 语义：异步响应发到请求方指定地址；
- RabbitMQ：`reply-to` + 临时队列；
- 失败：回复队列泄漏；地址不可达；权限不足。

关键测试：队列生命周期、不可达、超时。

### 保证投递（Guaranteed Delivery）

- 语义：在给定故障模型下不丢消息；
- RabbitMQ：持久消息 + durable queue + confirm + Quorum/Stream + 消费端幂等；
- 失败：只开 confirm 不开持久化；只持久化不复制；磁盘故障；备份缺失。

关键测试：节点崩溃、磁盘满、重启恢复、备份恢复。

### 消息存储（Message Store）

- 语义：需要重放/审计时保留消息；
- RabbitMQ：Stream retention、外部对象存储、归档队列；
- 失败：无限保留导致磁盘爆炸；保留期与合规冲突；重放污染生产。

关键测试：保留策略、重放隔离、清理、权限。

## 顺序与并发模式

顺序的队列语义、分区键设计、重试冲突和可运行实验见[第 31 章](../chapters/31-ordering-partitions.md)；下面只保留模式卡片。

### 分区顺序（Partitioned Ordering）

```text
exchange (x-consistent-hash / x-modulus-hash)
  -> partition queue 0..N
  -> 每个分区单消费者
```

- 语义：同一业务键的消息有序，不同键可并行；
- RabbitMQ：一致性哈希/模数哈希交换机；按订单 ID/用户 ID 分区；
- 失败：扩容重排 key；分区热点；消费者并发破坏顺序。

关键测试：同键顺序、跨键并行、扩缩容、重投。

### 单写者（Single Writer）

- 语义：同一聚合根只有一个写者；
- RabbitMQ：单活消费者/独占消费者 + 分区；
- 失败：切换窗口重复；旧写者未释放；多实例配置错误。

关键测试：切换、 fencing、重复写。

### 版本号 / 序列号

- 语义：检测乱序/重复/旧版本；
- RabbitMQ：消息带 `aggregate_version`/`sequence`；消费端拒绝旧版本；
- 失败：版本回退；并发写覆盖；序列号不连续。

关键测试：乱序、重复、回退、并发。

### 优先级通道（Priority Lanes）

- 语义：高优先级消息先处理；
- RabbitMQ：classic 优先级队列、Quorum 两档/32 级（版本相关）、独立队列；
- 失败：低优先级饥饿；优先级不跨队列；重投丢优先级。

关键测试：高低优先级、饥饿、重投。

## 多租户与多活模式

### 每租户 vhost

- 语义：强隔离；
- RabbitMQ：vhost + 独立权限；
- 失败：vhost 数量爆炸；跨 vhost 无法原子操作；运维成本。

关键测试：权限隔离、配额、备份、删除。

### 共享交换机 + 租户前缀

- 语义：资源复用，逻辑隔离；
- RabbitMQ：topic routing key 前缀 + 权限正则；
- 失败：正则过宽；routing key 泄露；一个租户绑定影响他人。

关键测试：越权绑定、前缀冲突、配额。

### Federation / Shovel

- 语义：跨集群/跨地域复制或转发；
- RabbitMQ：Federation（exchange/queue）或 Shovel（源到目标）；
- 失败：环路；重复；顺序；延迟；上游不可用。

关键测试：断链恢复、重复、环路、顺序。

### 双活（Active-Active）

- 语义：两个地域都能写；
- RabbitMQ：Federation/Shovel + 冲突解决 + 幂等；
- 失败：双写冲突；重复；顺序；分区；对账缺失。

关键测试：分区、冲突、重复、切流。

### 蓝绿 / 影子流量

- 语义：新旧版本并行验证；
- RabbitMQ：独立队列 + 复制/双写；影子消费者只读；
- 失败：影子消费者 ack 影响主队列；重复副作用；比对口径不一致。

关键测试：双写一致性、影子隔离、切换、回滚。

## 反模式目录

| 反模式 | 症状 | 为什么坏 | 修复 |
|---|---|---|---|
| 把队列当数据库 | 查询历史、按 ID 取消息、无限保留 | 队列不是索引/查询引擎，积压会拖垮 broker | 用数据库/Stream/对象存储 |
| 无界队列 | 磁盘涨满、内存告警、恢复极慢 | 没有背压和清理策略 | 长度/字节上限、DLX、消费者扩容 |
| 关键业务 auto-ack | 崩溃丢消息、重复无感知 | 消息在业务处理前被删除 | 手动 ack + 幂等 |
| requeue 风暴 | CPU 打满、日志刷屏、队列不动 | 毒消息无限重投 | delivery-limit + DLX + 退避 |
| 没有 DLX | 失败消息消失或卡住 | 无法观测/重放 | DLX + parking lot |
| 每个用户一个队列 | 队列/绑定爆炸、元数据慢 | 拓扑随用户增长 | 分区/共享队列 + 路由 |
| 把 RPC 当消息总线 | 同步阻塞、超时雪崩 | 耦合调用方与被调方 | 异步事件 + 补偿 |
| 大消息直传 | 内存/磁盘/复制放大 | broker 不是文件传输 | Claim Check + 对象存储 |
| 共享高权限账号 | 越权、审计缺失 | 无法定位责任 | 每应用独立账号 + 最小权限 |
| global QoS | 版本升级被拒、性能差 | 跨队列协调成本高 | per-consumer prefetch |
| 轮询管理 API 取消息 | 延迟、负载、非数据面 | 管理面不是消息通道 | 用 consume/客户端 SDK |
| 忽略 confirm | 发布丢失无感知 | 不知道 broker 是否接受 | confirm + return + 重试 |
| 宣称 exactly-once | 重复副作用、对账不平 | 协议不提供业务幂等 | 至少一次 + 幂等 + 对账 |
| 无背压 | 消费者 OOM、延迟飙升 | 生产速度长期大于消费 | prefetch/限流/扩容 |
| 拓扑频繁变更 | 声明冲突、406、连接抖动 | 拓扑是契约，不是临时变量 | 拓扑即代码 + 版本管理 |
| 无限重试 | 下游被打爆、队列堆积 | 没有上限/退避 | 最大次数 + 退避 + 死信 |
| DLQ 无监控 | 失败静默、事后才发现 | 死信不是回收站 | 告警 + owner + 重放工具 |
| 每请求一个队列 | 元数据/连接爆炸 | 队列创建成本被低估 | 共享回复队列 + correlation-id |
| 用 management API 发消息 | 性能差、权限过大 | 控制面不是数据面 | AMQP/1.0/Stream 客户端 |
| 把 Mini 当生产 broker | 无持久化/复制/安全 | 教学实现有明确边界 | 用官方 RabbitMQ + 运维 |

## 模式选择矩阵

| 需求 | 首选模式 | RabbitMQ 原语 | 主要代价 |
|---|---|---|---|
| 每任务一次 | 工作队列 | direct exchange + 多 consumer | 重投/毒消息 |
| 每订阅者一份 | Pub/Sub | fanout/topic + 每订阅者队列 | 队列/磁盘增长 |
| 一问一答 | Request/Reply | reply-to + correlation-id | 超时/回复队列 |
| 按内容路由 | Content Router | topic/headers | 绑定复杂度 |
| 大消息 | Claim Check | 小消息 + 对象存储 | 对象生命周期 |
| 顺序 | 分区顺序 | hash exchange + 单消费者 | 扩缩容重排 |
| 不丢 | 保证投递 | 持久化 + confirm + Quorum | 延迟/成本 |
| 不重复副作用 | 幂等接收者 | 去重表/唯一键 | 存储/清理 |
| 跨地域 | Federation/Shovel | upstream/shovel | 环路/重复 |
| 长流程 | Saga | 命令/事件 + 状态机 | 补偿/人工 |
| 失败隔离 | DLX + parking lot | DLX/delivery-limit | 运维工具 |
| 多租户 | vhost 或前缀 | vhost/权限/topic | 隔离 vs 成本 |

## 模式到测试的映射

每个模式至少要覆盖四类失败：

| 模式 | 重复 | 乱序 | 崩溃 | 积压/毒消息 |
|---|---|---|---|---|
| 工作队列 | 重投后业务只执行一次 | 多消费者不保证顺序 | ack 前崩溃 | prefetch 饱和、DLX |
| Pub/Sub | 每订阅者重复 | 各队列独立 | 订阅者离线 | 单队列积压 |
| Request/Reply | 重复回复 | 响应错配 | 服务端崩溃 | 超时、回复队列泄漏 |
| 分区顺序 | 同键重复 | 跨键并行 | 分区消费者崩溃 | 热点分区 |
| Outbox | 重复发布 | 多发布器乱序 | 发布前后崩溃 | outbox 膨胀 |
| Saga | 重复命令/事件 | 步骤乱序 | 协调器崩溃 | 补偿失败 |
| DLX | 死信重复 | 重试顺序 | DLQ 崩溃 | 死信循环 |
| 多活 | 双写重复 | 地域间乱序 | 链路中断 | 冲突/对账 |

具体测试手法见[附录 P](P-application-testing-chaos.md)：单元测试钉业务逻辑，Mini 组件测试验证编排，真实 RabbitMQ 集成测试验证协议，Toxiproxy/混沌实验验证故障恢复。

## 一个组合案例：订单履约

把多个模式组合起来，形成一个可运维的订单链路：

```text
订单服务
  ├── 本地事务：orders + outbox
  ├── outbox 发布器 -> orders exchange (topic)
  │     ├── order.created -> inventory.queue
  │     ├── order.created -> billing.queue
  │     └── order.#       -> audit.queue
  ├── inventory 消费 -> 预留库存 -> inventory.reserved
  ├── billing 消费   -> 扣款     -> payment.captured
  └── saga coordinator 监听事件，推进/补偿
```

关键设计：

- **Outbox** 保证订单与事件同事务；
- **幂等接收者** 用 `order_id + event_type` 唯一键吸收重复；
- **Saga** 在扣款失败时释放库存，补偿命令也幂等；
- **DLX + parking lot** 接住无法处理的消息；
- **Claim Check** 把发票/合同等大文件放对象存储；
- **对账** 每日比对订单、库存、支付和消息计数；
- **可观测性** 用 correlation-id 串起日志/追踪/指标。

这个组合不是“标准答案”，而是一个检查清单：每个模式都要有 owner、失败路径和测试。缺少任何一项，链路在故障时就会退化成“消息发了，但没人知道结果”。

## 小结

消息架构模式的价值不在拓扑图，而在失败语义：工作队列要处理重投和毒消息，Pub/Sub 要处理独立积压，Request/Reply 要处理超时和回复队列，Outbox 要处理发布前后崩溃，Saga 要处理补偿失败，多活要处理冲突和对账。反模式往往不是“用了错的交换机”，而是忽略了背压、幂等、清理和所有权。

设计时先用“语义/失败/所有权”三问选模式，再用模式到测试的映射补齐重复、乱序、崩溃和积压用例。模式是词汇表，不是免思考的配方；真正决定系统质量的，是失败路径上的工程细节。
