# 附录 K 生产故障案例库与复盘模板

本附录用十二个“典型到几乎每个团队都会遇到”的故障案例，把前面的协议、确认、队列、集群、运维知识串成排障直觉。案例是复合/匿名化的教学场景，不对应任何具体公司；时间线和数字用于说明方法，不是行业基准。

## 案例 1：队列积压，消费者“在线但不动”

### 现象

- `messages_ready` 从几千涨到几百万；
- `consumers` 显示 8，连接也在；
- `messages_unacknowledged` 很高且不下降；
- 发布端 confirm 延迟上升，最后出现 blocked。

### 时间线

```text
09:00 下游库存服务发布新版本，单次调用延迟从 20ms 升到 2s
09:10 队列 ready 开始上涨，未触发告警（阈值只设了 100 万）
09:25 unacked 达到 prefetch × 消费者数，消费者不再取新消息
09:40 队列触发内存告警，发布者被 blocked
09:45 on-call 重启消费者，未确认消息全部重投，重复处理
10:10 回滚下游版本，积压开始下降
12:30 积压清空，但产生了大量重复扣减
```

### 根因

不是“消费者挂了”，而是**下游变慢 + prefetch 过大 + 没有积压速率告警**。每个消费者预取 200 条，8 个消费者共 1600 条卡在未确认状态；重启把 1600 条全部重投，放大了重复。

### 检测

- 应监控 `ready` 的**增长速率**和 `unacked` 的**持续时间**，而不只是绝对值；
- `consumer utilisation`（消费者忙碌比例）下降是早期信号；
- 端到端延迟 p99 比队列深度更早报警。

### 处理

1. 先限流/降级，避免积压继续放大；
2. 查下游延迟、线程栈、连接池、数据库锁；
3. 不要盲目重启消费者；先确认在途消息和幂等；
4. 修复下游后逐步放量，观察积压恢复时间。

### 预防

- prefetch 与下游容量匹配，慢处理用小预取；
- 积压按“持续时间 + 增长速率”告警；
- 消费者优雅关闭，等待在途任务；
- 业务幂等，重投不产生重复副作用；
- 压测“下游变慢 10 倍”时的行为。

## 案例 2：毒消息无限 requeue

### 现象

- 单条消息的 `redelivered=true` 反复出现；
- CPU 和日志量暴涨；
- 队列深度不涨，但消费速率异常高；
- 下游日志出现同一条 message_id 的重复报错。

### 时间线

```text
14:00 上游发布一条缺字段的订单事件
14:01 消费者反序列化失败，捕获异常后 basic_nack(requeue=True)
14:01 broker 立即重投，消费者再次失败
14:02 该消费者占满 prefetch，其他消息无法被处理
14:05 日志量触发磁盘告警
14:20 人工 purge 队列，丢失了同队列的正常消息
```

### 根因

`requeue=True` 用于“暂时性失败”，却被用于“数据格式错误”这种永久失败。broker 不认识业务异常，只会立即重投。

### 处理

1. 立即停止该消费者的自动重投（改代码/下线消费者）；
2. 把毒消息转入 DLQ/parking lot；
3. 修复数据或跳过并记录；
4. 恢复其他消息消费。

### 预防

- 区分可重试异常（网络、限流、下游 5xx）和不可重试异常（反序列化、校验失败）；
- 不可重试异常 `requeue=false` 进 DLX；
- 可重试异常走延迟/退避，不立即 requeue；
- 设置 `x-delivery-limit`（Quorum 4.0 默认 20）；
- DLQ 有 owner、告警、重放工具。

## 案例 3：磁盘满导致发布全部阻塞

### 现象

- 所有发布者收到 `connection.blocked` 或超时；
- 消费仍在继续，但队列下降很慢；
- 磁盘使用率 100%，系统日志写入失败；
- 管理 UI 打不开或极慢。

### 根因

队列积压 + 持久化消息 + 没有 `max-length`/TTL，磁盘被写满；磁盘告警触发 blocked，但业务没有暂停发布，反而重试放大。

### 处理

1. 暂停非关键生产者；
2. 清理可丢弃数据（确认过的 DLQ、过期日志、无用队列）；
3. 扩容磁盘或迁移数据；
4. 恢复后缓慢放量，避免瞬间打满；
5. 检查是否有队列无限增长。

### 预防

- `disk_free_limit` 显式配置并留足余量；
- 关键队列设 `x-max-length` / `x-max-length-bytes` / TTL；
- 监控磁盘增长速率，不只使用率；
- 生产者监听 blocked，暂停并退避；
- 定期清理未使用队列和 DLQ；
- 大消息放对象存储，消息只传引用。

## 案例 4：网络分区后的“双主”幻觉

### 现象

- 两个机房的应用都认为自己连着“同一个集群”；
- 部分队列在两个分区都能发布，但消费者看到的消息不一致；
- 管理 UI 显示 partitions；
- 恢复网络后出现大量重复/丢失告警。

### 根因

跨机房组集群，网络抖动导致 Erlang 分区；`cluster_partition_handling` 配置不当（例如 `ignore`），两侧都继续接受写入。

### 处理

1. 确认分区边界和两侧状态；
2. 按既定策略恢复（`pause_minority` 下少数派应已暂停）；
3. 不要盲目重启所有节点；
4. 对账两侧消息，处理重复/丢失；
5. 复盘拓扑是否应该跨机房组集群。

### 预防

- 跨地域不要组一个大集群，用 Federation/Shovel；
- 显式选择并演练分区策略；
- 监控 `partitions` 指标和节点间网络；
- Quorum 队列只在多数派一侧可写，但 classic 队列仍可能脑裂；
- 关键业务用业务幂等 + 对账兜底。

## 案例 5：Quorum leader 选举风暴

### 现象

- Quorum 队列频繁换 leader；
- 发布 confirm p99 飙升，出现超时；
- `rabbitmq-queues quorum_status` 显示成员反复 offline；
- 节点 CPU/磁盘/网络某一项接近饱和。

### 根因

leader 所在节点资源不足（磁盘 IO 抖动、CPU 被其他进程抢占、网络丢包），Raft 心跳超时，反复触发选举。也可能是 3 节点集群里一个节点长期不稳定。

### 处理

1. 找出不稳定节点：磁盘、网络、GC、CPU steal；
2. 把该节点移出集群或修复；
3. 观察 leader 是否稳定；
4. 检查 Quorum 队列的副本数和 leader locator 策略；
5. 必要时重建队列/迁移。

### 预防

- Quorum 节点同规格、低延迟网络、独立磁盘；
- 不要让节点资源长期打满；
- 监控选举次数、leader 变化、Raft 日志/快照大小；
- 3 节点是常见基线，5 节点提高容错但增加写延迟；
- 定期做 leader 故障演练。

## 案例 6：TLS 证书过期

### 现象

- 某天凌晨大量客户端连接失败；
- 日志出现 `certificate has expired` / `handshake failure`；
- 管理 UI 通过 HTTPS 也打不开；
- 部分老客户端仍能连接（未启用 TLS 的旁路）。

### 根因

服务端/客户端证书或 CA 过期，没有到期告警和轮换流程；或者证书轮换后客户端未更新信任链。

### 处理

1. 确认是服务端证书、客户端证书还是 CA；
2. 用新证书滚动替换节点；
3. 更新客户端信任链/证书；
4. 验证主机名/SAN、协议版本、加密套件；
5. 恢复后检查是否有连接风暴。

### 预防

- 证书到期前 30/14/7 天告警；
- 证书轮换纳入变更流程并演练；
- 客户端支持双证书/热加载；
- 监控 TLS 握手失败率；
- 不要把“关闭证书校验”当修复。

## 案例 7：升级后队列声明 406

### 现象

- 升级到 4.x 后，部分服务启动失败；
- 日志显示 `PRECONDITION_FAILED - inequivalent arg`；
- 管理 UI 里同名队列参数与代码声明不一致；
- 回滚后问题消失。

### 根因

4.x 改变了默认值/弃用项：`x-queue-mode` 被忽略、transient 非排他队列被拒、Quorum 默认 `delivery-limit` 变化、某些参数不再允许。客户端仍按旧参数声明，broker 认为不等价。

### 处理

1. 对比代码声明参数与管理 UI 中实际参数；
2. 删除并重建不符合新语义的队列（先备份/排空）；
3. 更新客户端声明，移除弃用参数；
4. 对无法重建的队列，用 policy/新队列迁移；
5. 在预发环境复现并补充测试。

### 预防

- 升级前扫描 `ha-mode`、`x-queue-mode`、transient、global QoS；
- 拓扑声明作为代码纳入版本控制；
- 预发环境用真实客户端跑启动流程；
- 升级 runbook 包含“声明冲突”处置步骤。

## 案例 8：误删队列/交换机

### 现象

- 某个业务突然无消息；
- 管理 UI 中队列消失；
- 生产者仍在发布，但 mandatory 返回 NO_ROUTE；
- 消费者连接报 404。

### 根因

管理员/脚本执行了删除，或 auto-delete/exclusive 队列生命周期设计错误；也可能是 definitions 导入覆盖。

### 处理

1. 立即停止相关生产者，避免继续丢消息；
2. 从 definitions 备份恢复拓扑；
3. 检查是否有消息归档/上游事件日志可重放；
4. 重建消费者并验证；
5. 对账丢失窗口内的业务数据。

### 预防

- 删除操作需要审批/二次确认；
- 生产禁用管理 UI 的高危写操作或加审计；
- auto-delete/exclusive 只用于临时队列；
- definitions 定期导出并版本化；
- 关键事件保留上游日志/对象存储归档；
- 权限最小化，禁止通配删除。

## 案例 9：重复扣款——至少一次 + 没有幂等

### 现象

- 用户投诉重复扣款；
- 支付服务日志显示同一订单的支付事件被处理两次；
- 消息 `redelivered=true`；
- 发布时间附近有网络抖动/消费者重启。

### 根因

RabbitMQ 提供 at-least-once；消费者 ack 前崩溃或连接断开，broker 重投。业务代码只做了“读订单-扣款-写状态”，没有唯一约束/幂等键，第二次执行再次扣款。

### 处理

1. 立即冻结相关订单，人工核对/退款；
2. 用 message_id/业务键找出重复处理记录；
3. 补幂等表/唯一约束；
4. 对历史数据对账；
5. 重放前确认幂等。

### 预防

- 消费端用业务唯一键 + 数据库唯一约束/状态机；
- 去重表保留期覆盖最大重试/重放窗口；
- 支付等副作用接口使用 idempotency key；
- 监控 redelivered/重复 message_id；
- 故障演练包含“ack 前 kill 进程”。

## 案例 10：Federation/Shovel 环路放大

### 现象

- 两个集群之间的消息量突然翻倍；
- 同一条 message_id 在两边反复出现；
- 队列深度持续上涨，消费追不上；
- CPU/网络打满。

### 根因

A → B 和 B → A 同时配置了 Federation/Shovel，且没有正确使用 origin header/拓扑隔离；重试又放大了重复。

### 处理

1. 立即停掉一条复制链路；
2. 清理重复消息/队列；
3. 检查 origin 链、max-hops、绑定范围；
4. 恢复单向后观察；
5. 重新设计多活拓扑。

### 预防

- 明确单向/双向复制，画出拓扑图；
- 使用 Federation 内建 origin 机制，Shovel 自定义 origin header；
- 设置最大跳数；
- 监控重复 message_id 和跨集群流量；
- 多活必须业务幂等 + 冲突解决。

## 案例 11：升级 4.3 后延迟消息“提前”到达

### 现象

升级到 RabbitMQ 4.3 后，原本 60 秒后重试的失败消息几乎立刻回到消费者；没有报错，没有堆积，监控也看不出异常。业务侧出现重复扣款/重复通知。

### 时间线

```text
T0     升级 4.3 完成，拓扑声明正常
T+5m   失败消息开始“立即重试”，重试次数暴涨
T+15m  下游被打爆，才发现延迟没有生效
T+30m  回滚到 4.2，延迟恢复，但期间已产生重复副作用
```

### 根因

系统仍在使用 `rabbitmq_delayed_message_exchange` 的 `x-delayed-message` 交换机和 `x-delay` header。插件依赖 Mnesia，4.3 移除 Mnesia 后插件不可用；升级后消息没有延迟路径，`x-delay` 被忽略，消息立即投递。**这是一个静默行为变化：没有 406，没有 channel error。**

### 检测

- 对比消息的 `x-delay` 与“实际投递时间 - 发布时间”；
- 检查交换机类型是否仍为 `x-delayed-message`；
- 检查插件列表和 4.3 的 Mnesia 依赖告警；
- 观察重试速率是否在升级后突增。

### 处理

1. 立即回滚到 4.2（如果还在回滚窗口）；
2. 或紧急切换到 TTL+DLX/外部调度，暂停延迟生产者；
3. 对已提前重试的消息做幂等/对账，修复重复副作用；
4. 迁移到 4.3 原生 `x-delayed-retry-*` 或 4.4 `x-opt-delivery-time` 后再升级。

### 预防

- 升级检查清单里把“延迟插件/x-delay”标为阻塞项；
- 预发环境用真实延迟消息验证“到点才投递”；
- 业务侧保留幂等键和重试计数，不依赖 broker 的延迟语义做唯一防线。

## 案例 12：Khepri 少数派导致“节点活着但不能声明拓扑”

### 现象

4.3 集群两个节点故障，剩余一个节点仍能连接、能消费已有队列，但新消费者启动时声明队列失败；管理 UI 部分页面报错。团队误以为是权限/网络问题。

### 根因

4.3 起 Khepri 是唯一元数据存储，元数据写入要求集群多数派在线。3 节点集群只剩 1 个节点时，读可能还能工作，但声明交换机/队列、修改 policy 等写操作无法完成。`cluster_partition_handling` 不再生效，旧的分区处理预期不成立。

### 处理

- 恢复多数派节点（优先恢复原节点，避免重建导致数据丢失）；
- 不要在生产用 `forget_cluster_node` 强行“修复”少数派；
- 如果无法恢复多数派，按灾难恢复流程从备份/蓝绿集群恢复；
- 恢复后检查 Khepri/Raft 日志、队列 leader、副本。

### 预防

- 3 节点是元数据可用性的最低基线，关键业务用 5 节点；
- 监控“在线节点数/多数派状态”，而不只是“节点 ping 通”；
- 升级/维护窗口避免同时下线多个节点；
- 在 runbook 中明确“少数派不能改拓扑”的新语义。

## 故障排查的通用顺序

```text
1. 影响面：哪些业务/队列/区域？是否还在扩大？
2. 消息在哪：ready / unacked / DLQ / 被拒绝 / 未路由？
3. 消费者：数量、连接、channel、prefetch、下游延迟、线程栈
4. broker：内存/磁盘告警、blocked、分区、Quorum leader
5. 拓扑：绑定/路由键/policy 是否变化
6. 最近变更：发布、升级、配置、证书、权限
7. 再决定：限流、降级、扩容、回滚、重启
```

重启永远排在最后。重启会清掉未确认消息、触发重投、丢失现场，常常把“可诊断的故障”变成“不可复现的故障”。

## 复盘评审问题

1. 我们能否在 5 分钟内回答“消息现在在哪”？
2. 告警是基于症状、趋势还是业务影响？有没有误报/漏报？
3. 为什么消费者没有优雅关闭？在途消息如何处理？
4. 重复消息是否造成了业务副作用？幂等键是否覆盖所有入口？
5. DLQ 是否有 owner、保留期、重放工具？
6. 容量规划是否考虑了“下游变慢 10 倍”和“节点故障”？
7. 升级/变更是否在预发演练过？回滚是否真的可用？
8. 权限是否过大？删除/重置操作是否有审批和审计？
9. 备份是否包含拓扑和消息？恢复演练多久没做？
10. 这次故障能否被自动化测试/故障注入提前发现？

## 小结

生产故障很少是“RabbitMQ 挂了”，更多是积压、毒消息、磁盘、分区、升级、权限和幂等的组合。排查顺序是“影响面 → 消息在哪 → 消费者 → broker → 拓扑 → 最近变更”，重启放最后。每个案例的预防措施最终都落到同一组能力：可观测、容量规划、幂等、DLQ/重放、优雅关闭、变更演练和最小权限。
