# 第 30 章 变更工程：拓扑、消费者与数据的无损演进

> 本章定位：生产系统里最危险的不是第一次上线，而是第 N 次变更。改一个 routing key、换一个队列类型、升级消费者，看似只是配置差异，实际会同时影响在途消息、旧版本消费者、回滚路径和对账口径。本章把“变更”当成一等工程问题：先量化爆炸半径，再用 expand-contract 分阶段推进，最后用可运行示例验证零停机迁移。

## 为什么消息系统变更特别危险

无状态服务可以“全部重启换新版本”，消息系统不行。原因有四条：

1. **拓扑是隐式契约**：交换机名、routing key、队列参数散落在生产者、消费者、运维脚本和监控里，代码仓库往往不是唯一事实源；
2. **消息会穿过版本边界**：队列里可能同时躺着旧版本生产者写的消息和新版本生产者写的消息，消费者必须同时理解两种格式；
3. **消费者不是原子的**：滚动发布期间，新旧消费者会同时从一个队列取消息；任何一方解析失败都可能把消息打进 DLQ；
4. **回滚不是“回滚代码”**：新消费者可能已经写了业务数据、发了下游事件，旧代码回滚后无法撤销这些副作用。

一个真实的事故链通常长这样：团队把 `order.created` 改成 `orders.created`，只改了生产者和新队列绑定；旧消费者还在监听旧队列，新消息全部不可路由；mandatory 没开，消息静默丢弃；两天后对账发现少单，但消息已经不在队列里。

所以变更工程的第一原则不是“怎么改得快”，而是“怎么让错误可发现、可回滚、可对账”。

## 先画变更的爆炸半径

在动手前，把变更拆成“改了什么”和“谁会受影响”两张表。

| 变更对象 | 典型动作 | 爆炸半径 | 主要检测手段 | 可逆性 |
|---|---|---|---|---|
| routing key / binding | 改名、改通配、加绑定 | 生产者到队列的路径 | 不可路由计数、队列深度 | 高（双绑定） |
| 交换机 | 改名、改类型、加 AE | 所有绑定与路由 | 绑定列表 diff、发布返回 | 中（别名/双写） |
| 队列名 | 重命名、拆分、合并 | 消费者、权限、监控、DLX | 消费者数、队列深度 | 中（双队列） |
| 队列类型 | classic ↔ quorum ↔ stream | 持久化、复制、优先级、性能 | 声明 406、复制状态 | 低（需迁移） |
| 消息 schema | 加字段、删字段、改类型 | 所有消费者与下游 | 解析错误、DLQ、契约测试 | 中（兼容窗口） |
| 消费者代码 | 升级、拆分、合并 | 处理语义、顺序、幂等 | 业务对账、影子 diff | 高（代码回滚） |
| policy / 参数 | TTL、max-length、delivery-limit | 在途与新建队列 | 406、队列行为变化 | 中（策略可回退） |
| 集群 / 版本 | 升级、扩缩容、迁移 | 全集群 | 节点健康、Quorum、告警 | 低（单向门） |
| 凭据 / 权限 | 用户、vhost、TLS | 连接与发布/消费 | 认证失败、403 | 高（并存期） |

每一行都要回答三个问题：

- **在途消息怎么办？** 队列里已有的旧格式消息，新消费者能不能读？
- **旧消费者怎么办？** 新生产者发出的消息，旧消费者能不能读？读不了会不会死循环？
- **回滚时怎么办？** 新消费者已经写入的数据/已发出的下游事件，旧版本能否共存或补偿？

如果三个问题有一个答不上来，这个变更还不具备上线条件。

### 变更的四种语义

| 类型 | 例子 | 默认策略 |
|---|---|---|
| 兼容扩展 | 新增可选字段、新增绑定 | 消费者先升级，生产者后升级 |
| 行为变更 | 改重试次数、改 DLQ 目标 | 双跑观察，灰度切换 |
| 破坏变更 | 删字段、改类型、改队列类型 | expand-contract，绝不原地改 |
| 语义变更 | 同一字段含义变化 | 视为新事件类型/新版本 |

“兼容”不是由生产者单方面宣布的，而是由**最旧的在役消费者**决定的。只要还有一个旧消费者在线，新消息就必须对它可解析，或者把它隔离到独立队列。

## Expand-Contract：通用四阶段

把任何破坏性变更拆成四步：

```text
1. Expand   新旧并存：新增交换机/队列/绑定/字段，旧路径不动
2. Dual     双写/双读：生产者同时写新旧，消费者影子消费或双读
3. Migrate  回填与切换：历史数据补齐，流量逐步切到新路径
4. Contract 收缩：确认无流量后删除旧路径，关闭兼容代码
```

每个阶段都有明确的“出口条件”，不是靠感觉推进：

| 阶段 | 出口条件 | 证据 |
|---|---|---|
| Expand | 新拓扑声明成功、绑定正确、权限就绪 | definitions diff、绑定列表、声明幂等 |
| Dual | 新旧路径计数一致、影子 diff 在阈值内 | 发布/消费计数、抽样对账、错误率 |
| Migrate | 历史数据回填完成、积压清零、延迟达标 | 水位线、积压曲线、对账报告 |
| Contract | 旧路径零流量持续一个回滚窗口 | 队列深度 0、消费者 0、无发布 |

**兼容窗口**要覆盖四段时间的最大值：

```text
兼容窗口 ≥ max(最长消息生命周期,
                最长消费者发布周期,
                回滚观察窗口,
                历史回填耗时)
```

队列里可能还有 TTL 很长的消息；移动端/边缘消费者可能几周才升级；回滚窗口通常按天计；回填可能按小时到天计。兼容代码删早了，等于把回滚能力提前扔掉。

## 拓扑变更：交换机、队列与 routing key

### 不要原地重命名

RabbitMQ 没有“重命名交换机/队列”的原子操作。原地删除再创建，会丢失绑定、权限、策略和在途消息。正确做法是**新增一个名字，双写/双读，再删除旧名字**。

交换机改名可以用别名思路：

```text
旧生产者 -> exchange: orders.legacy -> queue: orders.worker
新生产者 -> exchange: orders.v2     -> queue: orders.worker
```

让新旧交换机绑定到同一个队列，消费者完全不用改。等所有生产者切到 `orders.v2` 后，再解绑并删除 `orders.legacy`。

队列改名则更麻烦，因为队列是消息的存储位置：

```text
阶段 1：声明 orders.v2.worker，绑定到同一交换机（或新交换机）
阶段 2：消费者同时消费两个队列；或让新消费者只消费新队列，旧消费者继续消费旧队列
阶段 3：生产者双写/切换，确认新队列积压与延迟正常
阶段 4：旧队列 drain 到 0，删除
```

如果两个队列都需要完整历史，可以用 Shovel 把旧队列的消息搬到新队列（见[第 13 章](13-federation-shovel.md)）；如果只需要“未来的消息”，双写就够了。

### routing key 变更：双绑定过渡

把 `order.created` 改成 `orders.created` 时，最稳的做法是让交换机同时接受两种 key：

```text
exchange: orders (topic)
  binding: order.created  -> queue: billing
  binding: orders.created -> queue: billing
```

生产者先双发（或先发旧 key），消费者保持双绑定；确认新 key 的消费正常后，再停旧 key。topic 交换机的通配能力可以进一步降低耦合：

```text
binding: order.*   -> queue: billing     # 兼容 order.created / order.paid
binding: orders.*  -> queue: billing     # 兼容 orders.created / orders.paid
```

注意两种“双”要分清：

- **双绑定**：同一个队列同时绑 `order.*` 和 `orders.*`。一条消息即使匹配两条绑定，AMQP 也保证同一队列只收到一份；它适合“生产者发一种 key，消费者兼容两种”。
- **双发**：生产者对同一业务事件发两条消息（旧 key + 新 key）。如果消费者同时双绑定，这两条是两条不同的消息，队列会收到两份。双发只适合“两个独立队列/影子消费者”，不适合“同一队列双绑定”。
- 同一条消息绑定到**两个不同队列**时，每个队列各收到一份，这是 fanout/影子消费的基础。

把策略写进变更记录，别把“双发”和“双绑定”混成一句话。

### 声明等价性与 406

RabbitMQ 声明交换机/队列时，参数必须与已存在的对象**等价**，否则返回 `PRECONDITION_FAILED`（406）。常见不等价项：

- `durable`、`auto_delete`、`exclusive`；
- `x-queue-type`（classic/quorum/stream）；
- `x-max-priority`、`x-message-ttl`、`x-dead-letter-exchange`；
- `x-max-length`、`x-overflow`；
- 交换机类型（direct/topic/fanout/headers）。

变更时最危险的不是 406 本身，而是**客户端把 406 当成临时错误重试**，导致拓扑永远建不起来，或者运维手工建了一个参数不同的对象，后续声明全部失败。处理原则：

1. 声明失败要打印完整的 `PRECONDITION_FAILED` 文本，包含“现有值 vs 请求值”；
2. 不要用 `passive=True` 绕过检查，它只能确认存在，不能确认等价；
3. 拓扑变更前先导出 definitions，做 diff；
4. 用管理 API 或 `rabbitmqctl list_queues name arguments` 核对现有参数。

```bash
# 导出拓扑，作为变更前后的基线
rabbitmqctl export_definitions /tmp/before.json

# 查看队列参数与消费者
rabbitmqctl list_queues name type durable arguments consumers messages

# 查看绑定关系
rabbitmqctl list_bindings source_name destination_name routing_key
```

### 删除对象的安全顺序

删除队列/交换机前，按依赖倒序检查：

```text
1. 生产者是否已停止发布到该交换机/队列？
2. 队列是否为空（messages=0）且无 unacked？
3. 是否有消费者仍在线？
4. 是否被 policy、Federation upstream、Shovel 引用？
5. 是否有监控/告警/审计依赖该名字？
```

管理 API 支持条件删除，能挡住“还有消息/还有消费者”的误删：

```bash
curl -u guest:guest -X DELETE \
  'http://127.0.0.1:15672/api/queues/%2F/orders.legacy?if-empty=true&if-unused=true'
```

`if-empty` 要求队列没有 ready 消息，`if-unused` 要求没有消费者。两者都满足才删除；否则返回 400/409，比“删了才发现丢消息”安全得多。

## Schema 与契约变更

### 先分清“加字段”和“改语义”

| 变更 | 兼容性 | 上线顺序 | 回滚 |
|---|---|---|---|
| 新增可选字段 | 向后兼容 | 消费者先能忽略未知字段，生产者后发 | 生产者回退即可 |
| 新增必填字段 | 破坏性 | 消费者先支持默认值/双版本，生产者后发 | 需保留旧消费者 |
| 删除字段 | 破坏性 | 消费者先停止依赖，生产者后删 | 旧消费者需能读新消息 |
| 字段改名 | 破坏性 | 消费者双读，生产者双写过渡 | 保留双写窗口 |
| 类型变化 | 破坏性 | 新字段/新版本，绝不原地改 | 版本路由回退 |
| 语义变化 | 破坏性 | 新事件类型/新版本 | 按新版本处理 |

一个常见的错误是“只加了一个必填字段”，以为向后兼容。对旧消费者来说，缺字段会导致解析失败；对新消费者来说，旧消息缺字段也会失败。**必填字段的变更永远是破坏性的**，要么给默认值，要么走新版本。

### Envelope 是变更的缓冲层

把“事件元数据”和“业务载荷”分开，能让 schema 演进不影响路由与治理：

```json
{
  "event_id": "evt-123",
  "event_type": "order.created",
  "schema_version": 2,
  "occurred_at": "2026-11-26T10:00:00Z",
  "producer": "order-service/1.8.3",
  "traceparent": "00-...-...-01",
  "data": {
    "order_id": "order-100",
    "amount": 199.0,
    "currency": "CNY"
  }
}
```

- `event_id` 用于幂等与去重；
- `event_type` 用于路由/契约目录；
- `schema_version` 让消费者知道该用哪个解析器；
- `traceparent` 让跨服务追踪不断链；
- `data` 才是业务载荷。

完整的命名规范、CloudEvents 映射、兼容性规则与契约测试见[附录 O](../appendices/O-event-contracts-governance.md)。

### 消费者必须能读“上一个版本”

迁移期间最容易被忽略的是**回填**：新消费者不仅要读新生产者写的消息，还要读历史归档/旧队列里的旧格式消息。示例 21 里的 v2 消费者同时接受两种 payload：

```python
def _decode_v2(self, body: bytes):
    payload = json.loads(body)
    order_id = payload.get("order_id") or payload["id"]
    currency = payload.get("currency", "CNY")
    return order_id, float(payload["amount"]), currency
```

这不是“防御性编程”，而是迁移期的硬要求。等旧格式消息的生命周期结束、回填完成、回滚窗口关闭后，才能删掉兼容分支。

## 消费者发布：混合版本共存

### 队列的消费者就是一个“组”

AMQP 0-9-1 没有 Kafka 那样的 consumer group/offset 概念。一个队列上的多个消费者是**竞争关系**，RabbitMQ 轮询投递；每条消息只给其中一个消费者（除非有多个队列/绑定）。这意味着滚动发布期间，新旧消费者会同时处理同一队列的消息：

```text
queue: billing
  consumer: billing-v1 (旧)
  consumer: billing-v2 (新)
```

因此：

- 新消费者必须能处理旧生产者写的消息；
- 旧消费者必须能处理新生产者写的消息，或者生产者在旧消费者全部下线后才切换格式；
- 任何一方解析失败都可能把消息打进 DLQ，造成“发布期间错误率上升”的假象。

### 上线顺序由兼容性决定

| 变更 | 推荐顺序 | 原因 |
|---|---|---|
| 新增可选字段 | 消费者 → 生产者 | 旧消费者忽略未知字段也能跑 |
| 新增必填字段 | 消费者（带默认值）→ 生产者 | 旧消息缺字段不能崩 |
| 删除字段 | 消费者停止依赖 → 生产者删除 | 旧消费者不能突然读到缺字段 |
| 改路由键 | 双绑定/双发 → 消费者兼容 → 生产者切换 | 避免不可路由 |
| 改队列类型 | 双队列 → 回填 → 切流 → 删旧 | 不能原地改 |

一个实用原则：**先让读方兼容，再让写方改变**。写方一旦改变，读方就没有退路；读方先兼容，写方可以慢慢切。

### 优雅关闭与在途消息

滚动发布时，旧消费者不能“收到 SIGTERM 就立刻退出”，否则 unacked 消息会被 requeue，造成重复处理。正确顺序：

```text
1. 停止接受新消息（basic.cancel 或关闭 channel）
2. 等待在途回调完成（设置超时，避免无限等待）
3. ack/nack 已处理的消息
4. 关闭连接
5. 进程退出
```

RabbitMQ 的 `consumer_timeout` 会保护“消费者拿了消息但长期不 ack”的情况；默认值因版本而异，生产要显式配置并监控。超时后 channel 会被关闭，消息重新入队——这既是保护，也是发布期间需要观察的信号。

### 灰度与流量权重

RabbitMQ 没有“给某个消费者 10% 流量”的原生开关。常见灰度方式：

1. **独立队列 + 影子消费**：新消费者订阅一个新队列，只观察不写业务；
2. **按业务键分流**：生产者按 `tenant_id`/`order_id` 哈希，把一小部分流量发到新交换机/队列；
3. **消费者优先级**：同一队列上给新消费者更高优先级，先处理一部分消息（但仍是竞争，不精确）；
4. **单活消费者（SAC）**：同一时刻只有一个消费者活跃，适合“主备切换”而不是按比例灰度。

按比例灰度最可靠的是第 2 种：在生产者侧做确定性分流，监控两边的错误率/延迟，再逐步扩大比例。

### 顺序在发布期间的风险

如果业务要求同一订单的事件有序，滚动发布期间不要让两个消费者同时处理同一订单：

- 按 `order_id` 分区到不同队列，每个队列单消费者；
- 或用 `x-single-active-consumer`，同一队列只有一个消费者活跃；
- 发布时先停旧消费者，再启新消费者（有短暂停机），或用分区级 handoff。

“先扩容再缩容”的常规无状态发布策略，在有序消息场景下可能造成乱序；顺序要求必须写进发布 runbook。

## 队列类型与集群变更

### classic → quorum 不能原地改

`x-queue-type` 是声明参数，不能通过 policy 修改；对已存在的 classic 队列声明 quorum 会 406。迁移步骤：

```text
1. 声明 orders.quorum（quorum, durable），绑定到同一交换机
2. 消费者同时消费两个队列，或新消费者只消费 quorum 队列
3. 确认 quorum 的 confirm 延迟、磁盘、复制状态正常
4. 生产者切换/双写，旧 classic 队列 drain
5. 删除 classic 队列；保留回滚窗口
```

注意：

- quorum 队列必须 durable，不能 exclusive；
- quorum 不支持 classic 的 `x-max-priority` 参数；4.0–4.2 只有 normal/high 两档，4.3+ 是 32 级严格优先级（总是启用），详见[第 06 章](06-queues-ttl-priority.md)和[附录 W](../appendices/W-4x-feature-labs.md)；
- quorum 的写放大和磁盘占用更高，容量要重算；
- 迁移期间两个队列都会收到消息，消费者要幂等，否则双消费会重复写业务。

### 队列拆分与合并

拆分（一个队列拆成多个）通常是为了并行/隔离：

```text
orders -> orders.high / orders.normal / orders.low
```

用 headers 或 routing key 分流，消费者分别消费。拆分后要重新评估：

- 顺序：同一订单是否还在同一队列？
- 容量：小队列是否更容易堆积？
- 监控：告警是否按新队列重新配置？
- DLQ：每个队列的失败路径是否独立？

合并则相反：减少队列数量、降低元数据开销，但会牺牲隔离和并行度。合并前确认消费者能处理混合流量，且顺序要求允许。

### policy 变更

policy 可以动态改变 TTL、max-length、delivery-limit、DLX 等，但：

- 对已存在消息的生效时机取决于参数（TTL 可能立即扫描，max-length 可能立即裁剪）；
- 不是所有参数都能热改（`x-queue-type`、`x-max-priority` 等声明参数不行）；
- 策略冲突/优先级要理清，避免“以为设了 DLX，实际被更高优先级策略覆盖”；
- 变更后要观察队列深度、丢弃计数、DLX 流量。

### 版本升级与集群迁移

版本升级、Khepri 迁移、CQv2 `.sqs`、feature flags 属于“单向门”变更，不能按普通拓扑变更处理。升级路径、回滚边界和验证清单见[附录 I](../appendices/I-version-migration.md)；Kubernetes 上的滚动升级见[附录 T](../appendices/T-kubernetes-operator-production.md)；跨集群切换与灾备见[附录 U](../appendices/U-disaster-recovery-continuity.md)。

蓝绿集群迁移的通用顺序：

```text
1. 新集群按同一 definitions 建拓扑（先不接流量）
2. 生产者双写/Shovel 复制，消费者影子消费
3. 对账确认无丢失/重复
4. DNS/连接串切流，旧集群保留只读/回滚窗口
5. 观察一个业务周期，再下线旧集群
```

不要用“改 DNS 就算切流”——长连接不会立刻重连，客户端需要重连策略、连接 draining 和超时。切换方案要包含客户端行为，而不只是基础设施。

## 数据回填与对账

回填是变更工程里最容易被低估的部分。它不是一个脚本，而是一条有水位线、限速、幂等和对账的数据管道。

### 回填的四个输入

| 来源 | 适用 | 注意 |
|---|---|---|
| 业务库/outbox | 事件可重放 | 要按时间/主键分页，避免长事务 |
| 消息归档/对象存储 | 历史事件 | 要校验完整性、顺序、重复 |
| 旧队列/Stream | 未消费积压 | 先 drain 再回填，避免边写边读 |
| 下游快照 | 只补状态 | 可能丢失中间事件 |

### 水位线与切流

回填期间线上仍在产生新消息，必须定义“回填到哪个点”：

```text
T0：开始回填历史 [start, watermark]
T1：回填完成，进入增量追平
T2：增量追平（新消息同时写新旧）
T3：暂停写入/短暂 quiesce，确认新旧计数一致
T4：切流到新路径
```

水位线可以是时间戳、自增 ID、Stream offset 或 outbox 主键。关键是**可比较、可重放、可验证**。

### 对账查询

至少要对四类数字：

```text
生产数（按 event_type/时间窗）
新路径消费数
旧路径消费数
业务表行数/金额汇总
```

差异要能解释：重复、丢失、延迟、过滤、死信。不能解释的差异一律按事故处理。

## 可观测性与变更门禁

变更期间，常规监控不够，要能按“版本/路径”切片：

| 指标 | 用途 | 变更期阈值示例 |
|---|---|---|
| 发布成功/失败数 | 发现不可路由、406、confirm 超时 | 失败率 < 0.1% |
| 新旧路径消费数 | 判断双写/双读是否一致 | 差异 < 0.5% 且可解释 |
| 队列深度/年龄 | 发现消费者跟不上 | 积压年龄 < 5 分钟 |
| redelivered/DLX | 发现解析失败、毒消息 | 无突增 |
| 消费者数 | 发现发布期间消费者掉线 | 不低于预期 |
| confirm p99 | 发现 Quorum/磁盘问题 | 不超过基线 2 倍 |
| 影子 diff | 发现语义差异 | 抽样差异为 0 或有解释 |

变更门禁建议写成“自动检查 + 人工签字”：

```text
自动：拓扑声明成功、关键队列有消费者、DLQ 无突增、积压年龄达标
人工：owner 确认业务对账、回滚方案、观察窗口
```

## 一次零停机迁移的完整剧本

`examples/21_zero_downtime_migration.py` 把上面的原则压缩成一个可运行闭环。场景：

- v1：`orders.v1` 交换机、`orders.v1.worker` 队列、schema `{id, amount}`；
- v2：`orders.v2` 交换机、`orders.v2.worker` 队列、schema `{order_id, amount, currency, schema_version}`；
- 业务表按 `order_id` 主键幂等，影子表只观察不写业务；
- 迁移期间 v2 消费者必须同时读 v1/v2 两种 payload。

运行：

```bash
python examples/21_zero_downtime_migration.py
```

输出：

```text
phase 0  v1 live: business=5 shadow=0 v1=on v2=shadow/off
phase 1  expand + shadow: business=8 shadow=3 v1=on v2=shadow/on
phase 2  backfill: business=8 shadow=8 v1=on v2=shadow/on
phase 3  cutover: business=10 shadow=8 v1=off v2=primary/on
phase 4  rollback drill: business=11 shadow=9 v1=on v2=shadow/on
phase 5  re-cutover: business=12 shadow=9 v1=off v2=primary/on
phase 6  duplicate publish: business=12 shadow=9 v1=off v2=primary/on
phase 7  decommission v1: business=12 shadow=9 v1=off v2=primary/on
business rows=12 duplicates=1
shadow rows=9 duplicates=0
serving gaps=0
business ids: order-1 order-10 order-11 order-12 order-2 order-3 order-4 order-5 order-6 order-7 order-8 order-9
queues: v1=0 v2=0
OK 21_zero_downtime_migration
```

逐阶段对照：

| 阶段 | 动作 | 证明什么 |
|---|---|---|
| phase 0 | v1 独立运行 | 基线：5 单进入业务表 |
| phase 1 | 声明 v2、双写、影子消费 | 新旧并存，v2 不产生业务副作用 |
| phase 2 | 回填 5 条历史事件到 v2 | v2 消费者能读 v1 payload |
| phase 3 | v2 转正、v1 停服 | 切流后业务继续增长 |
| phase 4 | v1 重新接一条消息 | 回滚路径可用，v2 仍能影子处理 |
| phase 5 | 再次切回 v2 | 回滚后可恢复 |
| phase 6 | 重复发布同一 `order_id` | 业务主键/幂等键吸收重复，不重复记账（示例按 `order_id` 去重，不以 `message_id` 为键） |
| phase 7 | drain 并删除 v1 | 收缩阶段可安全下线旧拓扑 |

这个示例能证明：

- expand-contract 的每个阶段都有可观察状态；
- 双写期间新旧消费者可以共存；
- 回填消息与实时消息走同一套幂等逻辑；
- 回滚不是“回滚代码”，而是“把流量切回仍然可用的旧路径”；
- 收缩前必须 drain 到 0。

它不能证明真实 RabbitMQ 的网络分区、Quorum 复制、跨集群延迟和客户端重连；这些要用[附录 P](../appendices/P-application-testing-chaos.md)的集成/混沌测试补。它还用同一张业务表模拟共享存储，因此没有覆盖“旧消费者使用独立数据库、回滚前必须先补齐切换期间事件”的场景；真实系统的回滚方案要把这段回填写进 runbook。`serving_gap` 也只是一个阶段级模型，不等于对每一次请求的零停机证明。示例的价值是把“零停机迁移”从 PPT 变成可断言的计数。

## 回滚设计

回滚要分三种情况讨论：

1. **代码回滚**：新消费者有 bug，旧版本仍能读新消息 → 直接回滚部署；
2. **路径回滚**：新拓扑有问题，旧拓扑仍在 → 切回旧交换机/队列，生产者双写继续；
3. **数据回滚**：新版本已经写了业务数据/发了下游事件 → 不能“撤销”，只能补偿/对账。

因此：

- 破坏性变更必须保留旧路径至少一个回滚窗口；
- 生产者在回滚窗口内保持双写，或至少保留可重放的事件源；
- 新消费者写入的业务数据要带版本/来源标记，方便识别和补偿；
- 回滚演练要定期做，不能只在事故时第一次执行。

**Roll-forward vs rollback**：如果新版本已经产生大量正确数据，回滚可能造成更大不一致，此时更稳的是修 bug 后继续向前。决策权要提前定义（谁可以拍板、依据哪些指标），不要事故现场临时争论。

## 变更评审清单

### 变更前

- [ ] 变更类型（兼容/行为/破坏/语义）已分类；
- [ ] 爆炸半径、在途消息、旧消费者、回滚路径已写清；
- [ ] 新旧拓扑/ schema 的兼容窗口已定义；
- [ ] definitions 已导出并 diff；
- [ ] 回填来源、水位线、限速、幂等方案已确认；
- [ ] 监控/告警已按新旧路径切片；
- [ ] 回滚触发条件、决策人、观察窗口已确定；
- [ ] 预发环境已演练，生产变更窗口已审批。

### 变更中

- [ ] 先 expand，确认声明成功、绑定正确、消费者在线；
- [ ] 双写/影子消费期间持续对比计数与错误率；
- [ ] 回填按水位线推进，积压年龄可控；
- [ ] 切流前确认新旧计数一致或差异可解释；
- [ ] 观察 confirm 延迟、DLQ、redelivered、消费者数；
- [ ] 任何异常先停切流，不要“再观察一下”。

### 变更后

- [ ] 旧路径零流量持续一个回滚窗口；
- [ ] 业务对账通过（计数/金额/状态）；
- [ ] 删除旧拓扑/兼容代码/临时策略；
- [ ] 更新事件目录、runbook、监控面板；
- [ ] 记录变更复盘：耗时、问题、改进项；
- [ ] 关闭变更单，保留证据。

## 本章小结

消息系统的变更不是“改配置”，而是同时改变拓扑、契约、消费者和在途数据。安全变更的核心是 expand-contract：先让新旧并存，再双写/影子验证，回填后切流，最后在确认零流量后收缩。兼容窗口要覆盖消息生命周期、消费者发布周期、回填耗时和回滚窗口；回滚要区分代码、路径和数据三种情况。`examples/21_zero_downtime_migration.py` 用可断言的阶段输出证明了这条路径，但真实集群的复制、分区和客户端重连仍需混沌演练。

变更工程做得好，系统才能持续演进；做得不好，每一次“小改动”都可能变成一次数据事故。下一章把顺序、并发与分区作为横切专题收束：变更期间最容易被打乱的，正是业务赖以成立的顺序。
