# 第 01 章 消息中间件与 RabbitMQ 全景

> 本章定位：建立“为什么需要消息中间件、RabbitMQ 在系统中到底承担什么角色”的整体心智模型。后续所有协议细节和可靠性技巧，都要挂在这张图上。

## 从一次下单说起

一个电商下单请求看似只有一步，实际至少涉及：创建订单、扣减库存、生成支付单、发优惠券、写审计日志、通知仓库、给用户发短信。若全部同步调用，用户要等所有下游完成；任何一个下游变慢，整条链路都会抖动；下游临时不可用，订单直接失败。更麻烦的是，业务代码会逐渐长成一张网：订单服务知道库存服务、积分服务、风控服务的地址和重试规则，每新增一个消费者就要改一次订单服务。

消息中间件把“发生了一件事”与“谁需要处理它”拆开。订单服务只负责把 `order.created` 事件可靠地交给 broker；库存、积分、审计各自订阅自己关心的路由。生产者不需要知道消费者是谁、有几个、是否在线。消费者可以按自己的节奏扩容、重启、补数据。系统从“同步调用图”变成“事件流 + 独立消费者”。

这个变化带来四个直接收益：

1. **时间解耦**：生产者不必等待消费者完成。
2. **空间解耦**：双方不需要互相发现地址，只依赖交换机、队列和路由键。
3. **流量缓冲**：突发流量先进入队列，消费者按能力消费。
4. **故障隔离**：某个消费者宕机，不会拖垮生产者；消息可以保留到它恢复。

代价也同样真实：系统最终一致、消息可能重复、顺序不再天然保证、排障需要新的工具、运维多了一个有状态组件。消息队列不是“解耦银弹”，而是把同步调用的复杂度换成了异步系统的复杂度。

## RabbitMQ 是什么

RabbitMQ 是一个开源消息 broker，核心协议是 AMQP 0-9-1，使用 Erlang/OTP 构建。它把消息的接收、路由、存储、投递、确认和管理做成一个独立服务。生产者通过 TCP 连接把消息发布到交换机（exchange），交换机根据绑定（binding）把消息路由到队列（queue），消费者从队列订阅或拉取消息。

它最鲜明的能力不是“吞吐量最大”，而是**灵活路由 + 成熟协议 + 可运维性**：

- direct、fanout、topic、headers 四类内置交换机，加上一致性哈希等插件；
- 交换机到交换机绑定、备用交换机、死信交换机；
- publisher confirms、消费者确认、预取、事务；
- classic、quorum、stream 三种队列形态；
- 管理 UI/HTTP API、Prometheus、Firehose、Shovel、Federation；
- 多语言客户端，以及 AMQP 1.0（4.0 起是核心协议，不再是插件）、MQTT、STOMP 等协议接入。

RabbitMQ 诞生于 2007 年，最初由 Rabbit Technologies 开发，后来经历 VMware、Pivotal，如今处于 Broadcom 的 VMware Tanzu 生态。项目本身以 MPL 2.0 许可证开源。理解这段历史很重要：它解释了为什么 RabbitMQ 既有深厚的企业集成基因，又在云原生时代不断补齐 Kubernetes、Streams 和 Quorum Queue 能力。

## 一张图看懂核心模型

```text
publisher ──TCP/AMQP──> connection ── channel ──> exchange
                                                    │
                                      binding: key / pattern / headers
                                                    │
                              ┌─────────────────────┼─────────────────────┐
                              ▼                     ▼                     ▼
                           queue A               queue B               queue C
                              │                     │                     │
                           consumer 1            consumer 2            consumer 3
```

几个名词必须一开始就分清：

- **Connection**：一条 TCP 连接，认证、vhost、心跳、关闭都在这个层级。
- **Channel**：连接上的逻辑多路复用通道。绝大多数 AMQP 操作在 channel 上执行；确认、事务、QoS 都是信道级状态。
- **Exchange**：只负责路由，不存储消息。没有绑定匹配时消息可能被丢弃或被退回。
- **Queue**：消息真正停留的地方，负责存储、顺序、容量、消费者分发和确认状态。
- **Binding**：交换机到队列（或交换机）的路由规则，可带参数。
- **Routing key**：生产者提供的路由字符串，由交换机类型解释。
- **Virtual host**：类似命名空间，隔离交换机、队列、绑定和权限。
- **Consumer tag**：消费者在信道内的标识；**delivery tag** 是投递确认的编号。

最常见的误解是“消息发到队列”。实际上，AMQP 0-9-1 的发布动作是“消息发到交换机”；即使是默认交换机，也是由 broker 隐式按队列名路由。把这个模型建立起来，后面看死信、备用交换机、联邦拓扑时就不会混乱。

## RabbitMQ 在技术栈中的位置

消息系统大致可以分为三类：

| 类型 | 代表 | 强项 | 典型场景 |
|---|---|---|---|
| 传统消息队列 | RabbitMQ、ActiveMQ Artemis、IBM MQ | 灵活路由、事务/确认、请求响应 | 业务解耦、任务分发、RPC、企业集成 |
| 分布式日志 | Kafka、Pulsar、Redpanda | 高吞吐、可重放、分区顺序 | 日志、事件溯源、流处理、数据管道 |
| 云托管队列 | SQS、Azure Service Bus、Google Pub/Sub | 免运维、弹性计费 | 云原生任务队列、简单事件通知 |

RabbitMQ 的甜点区是“**需要复杂路由、可靠投递、低到中等延迟、团队希望快速上手**”的业务消息。它也能承受相当高的吞吐，但在“保留海量历史事件、按 offset 重放、顺序写盘”这类日志型负载上，Kafka/Pulsar 更自然。反过来，Kafka 做每消息优先级、复杂 headers 路由、单条消息确认和请求响应，会比 RabbitMQ 别扭得多。

选择时不要只比较 TPS。要问：

- 消息需要保留多久？消费者是否需要重放历史？
- 路由是简单队列名，还是多条件、多租户、多区域？
- 是否需要单条确认、优先级、延迟、死信？
- 团队是否愿意维护 Erlang 集群和状态存储？
- 是否已有云厂商绑定、合规或成本约束？

## RabbitMQ 的三条“平面”

学习 RabbitMQ 时，把系统拆成三个平面会清晰很多。

### 数据平面

消息从 publish 到 deliver 的路径：连接、信道、交换机、绑定、队列、消费者、确认。数据平面的关键是**不丢、不重、不过载**。它涉及持久化、Quorum 复制、流控、预取、确认和死信。

### 控制平面

声明拓扑、配置策略、创建用户、设置权限、启停插件、集群加入/移除、升级。控制平面变化频率低，但一旦出错影响全局。RabbitMQ 用 definitions 导出/导入拓扑，用 policy 动态覆盖队列参数，用 feature flags 管理版本兼容。

### 管理平面

监控、告警、审计、追踪、容量分析、故障演练。很多团队只在上线后补监控，结果队列积压到磁盘告警才发现。正确顺序是：先定义指标与 SLO，再决定队列和集群的部署形态。

Mini-RabbitMQ 也按这三个平面组织：数据面在 broker/vhost/queue，控制面在 management API 与 policy，管理面在 metrics/health。第 20 章会展开代码结构。

## 一个完整的业务例子

假设订单系统要发布 `order.created`，库存和审计都要消费。一个可工作的拓扑可以这样设计：

```text
exchange: orders (topic, durable)
  binding: order.created -> queue inventory.order-created
  binding: order.#       -> queue audit.all-orders

queue inventory.order-created
  x-dead-letter-exchange: orders.dlx
  x-message-ttl: 86400000

exchange: orders.dlx (fanout, durable)
  binding -> queue orders.failed
```

生产者的可靠性链条是：声明 durable exchange/queue、消息 `delivery_mode=2`、开启 publisher confirm、处理 basic.return、记录业务唯一键。消费者的可靠性链条是：手动 ack、合理 prefetch、幂等处理、失败进入 DLX、带退避重试、有最大重试次数和人工兜底队列。

这条链路听起来不复杂，但每一环都可以出错：交换机拼错、队列不存在、消息未持久化、confirm 超时、消费者重复、死信循环、重试风暴。教程后面的章节会逐环拆解，并用 Mini-RabbitMQ 的真实代码和测试证明这些语义。

## 命令、事件与流：先分清三种语义

很多“消息队列选型”争论，其实是在用同一个词描述三种不同的东西。先把语义分清，后面的路由、确认、保留策略才有共同语言。

| 语义 | 典型问题 | 例子 | 合适的抽象 |
|---|---|---|---|
| 命令（command） | “请做这件事” | 扣库存、发短信、生成报表 | 队列 + 竞争消费者 + ack |
| 事件（event） | “这件事已经发生” | 订单已创建、支付已捕获 | 交换机广播/主题订阅 + 多队列 |
| 流（stream） | “发生过什么，按顺序保留” | 审计日志、遥测、事件溯源 | 追加日志 + offset + retention |

三者的差别不只是性能：

- **命令**通常要求“每条只被一个 worker 处理”，失败要重试，成功要 ack，强调任务状态和幂等。
- **事件**通常要求“所有关心的订阅者都收到”，强调路由、解耦和最终一致；重复和乱序是常态。
- **流**通常要求“保留历史、可重放、按 offset 读取”，强调顺序、保留和消费进度，而不是“处理完删除”。

把命令塞进流，会导致多个消费者重复执行同一个任务；把流塞进队列，会导致无法重放历史；把事件当命令，会让“广播”变成“只有一个服务收到”。RabbitMQ 的核心是前两类，Streams 补充第三类；Kafka 更偏第三类。选型时先写清楚“这是命令、事件还是流”，比比较 TPS 更有用。

## 什么时候不该用消息队列

消息队列不是默认正确的架构。以下场景应优先考虑别的方案：

1. **强同步、强一致的请求/响应**：用户要立即看到结果，且下游必须同步成功；直接 RPC/HTTP 更简单。
2. **需要跨资源原子性的短事务**：数据库事务能解决的事情，不要用消息队列模拟 XA。
3. **数据量很小、调用链很短**：引入 broker 带来的运维、监控、重复处理成本可能高于收益。
4. **需要复杂查询/聚合**：消息是流动的，不是查询引擎；用数据库/OLAP。
5. **团队没有运维能力且业务不可降级**：托管队列或同步调用可能更现实。
6. **只是“解耦代码”而非“解耦运行时”**：模块化/依赖注入可能就够了。

消息队列真正擅长的是：异步、削峰、跨团队/跨系统集成、失败重试、事件广播、任务分发。判断标准不是“是否时髦”，而是“同步调用图是否已经成为变更瓶颈”。

## 一张选型决策树

```text
需要保留历史并按 offset 重放吗？
├── 是 → 事件流/日志（Kafka/Pulsar/RabbitMQ Streams）
└── 否
    ├── 需要复杂路由（多条件、多租户、topic/headers）？
    │   ├── 是 → RabbitMQ
    │   └── 否
    │       ├── 只需要简单任务队列，且已在云上？
    │       │   ├── 是 → SQS/云队列
    │       │   └── 否 → RabbitMQ / NATS（看协议与生态）
    │       └── 需要请求/响应、优先级、死信、延迟？
    │           ├── 是 → RabbitMQ
    │           └── 否 → 轻量队列/数据库轮询
    └── 团队是否愿意维护有状态 broker？
        ├── 否 → 托管服务
        └── 是 → 自建 RabbitMQ 集群
```

这张树不是标准答案，而是逼你把“保留/重放、路由、运维、云绑定”四个问题显式回答。真正的选型还要加权重：成本、合规、团队经验、迁移代价。

## 本章小结

RabbitMQ 是一个以 AMQP 0-9-1 为核心、以灵活路由和可靠投递见长的消息 broker。它把同步调用图变成事件流，用交换机、绑定、队列把生产者和消费者解耦。它的优势在复杂路由、成熟协议和可运维性；它的代价是最终一致、重复消息、顺序约束和额外的有状态运维。

后续章节会从安装和第一条消息开始，逐步深入到协议帧、可靠性状态机、集群和商业分析。Mini-RabbitMQ 不是玩具演示，而是一条可测试的实现主线：你会看到每个概念如何落到数据结构、锁、确认和错误码上。
