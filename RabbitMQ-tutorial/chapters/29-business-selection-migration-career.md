# 第 29 章 商业分析 III：选型、迁移与职业建议

> 本章定位：把前两章的市场/商业框架落到决策。给出选型矩阵、迁移 playbook、成本示例、风险清单和职业路径。所有评分/成本都是示范，不是标准答案。

## 选型不是“选最强”

先写需求，再选产品。至少明确：

1. 消息语义：任务、事件、日志、RPC、流处理；
2. 吞吐/延迟/消息大小；
3. 持久化/复制/顺序/重放；
4. 路由复杂度；
5. 多租户/安全/合规；
6. 运维能力/云环境；
7. 预算/支持/SLA；
8. 迁移/锁定/生态。

一个团队没有 Kafka 运维能力，却因为“吞吐高”选 Kafka，可能比选 RabbitMQ 更贵。反过来，需要长期日志重放却硬用 RabbitMQ 队列，也会痛苦。

## 加权决策矩阵（示范）

假设一个订单/任务平台，权重如下：

| 维度 | 权重 | RabbitMQ | Kafka | SQS | NATS |
|---|---:|---:|---:|---:|---:|
| 任务/路由 | 25% | 5 | 3 | 3 | 3 |
| 持久化/复制 | 20% | 5 | 5 | 4 | 3 |
| 吞吐/重放 | 15% | 3 | 5 | 2 | 3 |
| 运维简单 | 15% | 3 | 2 | 5 | 4 |
| 生态/集成 | 15% | 5 | 5 | 3 | 3 |
| 成本/托管 | 10% | 4 | 3 | 5 | 4 |
| 加权 | 100% | 4.30 | 3.85 | 3.55 | 3.25 |

评分是主观的；换一个场景（日志/数据管道）Kafka 会领先，换纯云任务 SQS 可能领先。矩阵的价值是逼团队显式讨论权重，而不是“拍脑袋”。

### 场景化建议

| 场景 | 首选 | 备选 | 理由 |
|---|---|---|---|
| 订单/支付任务 | RabbitMQ Quorum | Kafka + 幂等 | 路由/确认/死信/重试成熟 |
| 日志/遥测 | Kafka/Pulsar | RabbitMQ Streams | 高吞吐/保留/重放 |
| 简单云任务 | SQS | RabbitMQ 托管 | 免运维/按量 |
| 企业集成 | RabbitMQ | ActiveMQ/IBM MQ | AMQP/JMS/插件/管理 |
| IoT | MQTT 平台/EMQX | RabbitMQ MQTT | 设备/协议/规模 |
| 微服务控制面 | NATS | RabbitMQ | 低延迟/轻量 |
| AI 推理队列 | RabbitMQ/SQS | Kafka | 任务/重试/优先级 |

## 迁移：RabbitMQ 与其他系统

### ActiveMQ/IBM MQ → RabbitMQ

常见动因：成本、云迁移、协议现代化、社区。

步骤：

1. 盘点队列、主题、连接、事务、选择器、消息属性；
2. 映射 JMS 概念到 AMQP（Queue/Topic、ack、事务、DLQ）；
3. 处理 JMS 特有语义（XA、消息组、选择器）；
4. 双写/双读过渡；
5. 客户端改造（JMS/AMQP 库）；
6. 对账/回滚。

风险：

- XA 事务在 RabbitMQ 中没有直接等价；
- JMS 选择器 vs AMQP routing/headers；
- 顺序/消息组；
- 管理工具/监控差异；
- 历史积压迁移。

### RabbitMQ → Kafka

不要“lift and shift”。差异：

- 队列/交换机 → topic/partition；
- per-message ack → offset；
- 死信/重试 → 消费者逻辑/重试 topic；
- 路由 → key/partition + 消费端过滤；
- 请求响应 → 不自然；
- 优先级 → 不支持（需多 topic/分区设计）。

适合迁移的场景：日志/事件流/重放/高吞吐。不适合：任务队列/RPC/复杂路由。迁移前重新设计事件契约和消费模型，而不是复制拓扑。

### Kafka → RabbitMQ

适合：任务分发、RPC、复杂路由、低延迟业务消息。需要：

- 把 topic/partition 映射为 exchange/queue/routing key；
- 处理 offset/重放缺失（用 Streams 或外部归档）；
- 消费者组 → 竞争消费者/单活；
- 顺序 → 分区键 + 单消费者；
- 保留策略 → TTL/DLX。

### 云队列 → RabbitMQ

SQS 的 visibility timeout/长轮询/死信与 RabbitMQ 的 ack/prefetch/DLX 不同。迁移时：

- 重新设计确认/重试；
- FIFO 队列 → 单队列/单消费者或分区；
- 延迟队列 → TTL/DLX/原生延迟（4.3+）；
- 权限/IAM → vhost/用户/TLS；
- 监控/告警重建。

### RabbitMQ → 云托管

动因：减少运维、弹性、合规。代价：

- 插件/参数限制；
- 网络/延迟；
- 成本随规模；
- 迁移/锁定；
- 管理 API 差异。

混合策略：核心自建/托管，边缘/突发用云队列，通过 Shovel/Federation 连接。

## 迁移 playbook

### 阶段 0：发现

- 拓扑、队列、交换机、绑定、策略；
- 消息大小/速率/积压；
- 客户端/协议/版本；
- 事务/顺序/重试/DLQ；
- 权限/证书/网络；
- SLO/故障历史。

### 阶段 1：目标设计

- 队列类型（classic/quorum/stream）；
- 路由/命名规范；
- 可靠性语义（confirm/ack/outbox）；
- 安全/多租户；
- 监控/告警；
- 容量/成本。

### 阶段 2：双跑

- 新集群部署；
- 拓扑导入；
- 生产者双写/影子流量；
- 消费者双读/比对；
- 限速/回滚开关。

### 阶段 3：切换

- 低峰窗口；
- 停止旧生产者；
- 排空旧队列；
- 切换 DNS/配置；
- 验证生产/消费/延迟；
- 保留回滚路径。

### 阶段 4：退役

- 观察期；
- 对账；
- 删除旧拓扑/用户；
- 归档配置/数据；
- 复盘。

## 风险清单

| 风险 | 影响 | 缓解 |
|---|---|---|
| 拓扑不一致 | 消息丢失/路由错 | definitions 校验/双跑 |
| 客户端不兼容 | 连接失败/语义差异 | 版本矩阵/试点 |
| 顺序变化 | 业务错乱 | 分区键/单消费者/版本号 |
| 重复消息 | 重复扣款 | 幂等/去重/对账 |
| 迁移积压 | 切换时间长 | 限速/分批/影子 |
| 权限/证书 | 上线失败 | 预发演练 |
| 监控缺口 | 故障发现晚 | SLO/告警/仪表盘 |
| 回滚失败 | 停机扩大 | 回滚演练/双写 |

## 成本：TCO 与迁移投入

### 自建 vs 托管

```text
自建：
  3 × 8vCPU/32GB/500GB SSD ≈ $1,500/月
  支持合同 ≈ $500/月
  0.5 FTE 运维 ≈ $5,000/月
  监控/备份 ≈ $300/月
  合计 ≈ $7,300/月

托管：
  3 节点托管 ≈ $3,500/月
  支持/高级功能 ≈ $1,000/月
  0.1 FTE ≈ $1,000/月
  合计 ≈ $5,500/月
```

托管可能更便宜，但取决于规模/折扣/人力成本/合规。自建的优势是控制/插件/数据驻留；托管优势是 SLA/运维。不要用单一报价比较。

### 迁移投入

迁移不只是“换个 broker”：

```text
一次性成本：
  - 盘点/设计（人天）
  - 客户端改造（人天 × 服务数）
  - 拓扑重建/测试
  - 数据/积压迁移
  - 双跑/对账
  - 培训/文档
  - 回滚方案

持续成本：
  - 新平台运维
  - 监控/告警
  - 支持/许可
  - 人力/on-call
  - 机会成本
```

一个粗略估算：

```text
10 个服务 × 5 人天 = 50 人天
2 个平台工程师 × 20 人天 = 40 人天
双跑 1 个月资源 = 1.5 倍月成本
培训/文档 = 10 人天
合计 ≈ 100 人天 + 1 个月双倍资源
```

如果迁移后每年节省的运维/许可成本小于这个投入，迁移可能不划算。反之，如果故障/合规风险很高，迁移是必要的。

## 组织能力

消息系统需要跨团队能力：

| 角色 | 职责 |
|---|---|
| 平台团队 | broker 部署/升级/监控/备份 |
| 应用团队 | 生产者/消费者/幂等/重试 |
| SRE | on-call/故障演练/容量 |
| 安全 | TLS/认证/审计 |
| 架构 | 事件契约/拓扑治理 |

没有平台团队时，托管服务 + 应用侧规范是更现实的选择。自建不等于“买几台服务器”，而是建立一套运维产品。

## 职业路径与能力矩阵

消息系统相关角色：

| 路径 | 核心能力 | 产出 |
|---|---|---|
| 后端工程师 | 可靠生产/消费、幂等、outbox | 业务可靠性 |
| 平台/SRE | 集群/Quorum/升级/监控/容量 | 平台 SLA |
| 架构师 | 事件驱动/选型/治理/多活 | 架构决策 |
| 解决方案/顾问 | 迁移/行业方案/客户沟通 | 项目交付 |
| 开发者关系 | 内容/社区/培训 | 生态增长 |
| 产品经理 | 托管服务/开发者体验/定价 | 产品方向 |

共同基础：

1. AMQP/消息语义；
2. 分布式系统（复制/共识/分区）；
3. 可靠性工程（幂等/对账/故障演练）；
4. 运维（K8s/Linux/网络/存储）；
5. 安全（TLS/OAuth/ACL）；
6. 性能/容量；
7. 业务建模/事件契约；
8. 写作/沟通。

区别在于侧重点：后端更偏业务可靠性，平台/SRE 更偏复制/容量/升级，架构师更偏事件契约与多活取舍，顾问/布道/产品更偏沟通与商业化。不要把“会用 RabbitMQ”当成职业能力；能解释失败场景、做出取舍并验证，才是。

学习路径：

- 第 1～10 章打基础；
- 第 11～19 章做分布式/可靠性；
- 第 20～25 章读/改 Mini；
- 用真实 RabbitMQ 做故障演练/压测；
- 写一篇迁移/故障复盘；
- 参与开源/社区。

证书/培训不是能力证明。是否存在官方认证、课程覆盖什么，以厂商当前的产品与培训页面为准；面试更看重你能否解释确认/幂等/分区/容量取舍，以及是否有真实的故障复盘。

## 90 天计划与验收

第 1～2 周：

- 读第 1～8 章；
- 跑 22 个示例；
- 搭 3 节点 RabbitMQ；
- 画出现有系统消息拓扑。

第 3～4 周：

- 实现 outbox + 幂等消费；
- 建 DLQ/重试/对账；
- 压测 confirm/消费；
- 做一次节点故障演练。

第 5～8 周：

- 选一个非关键业务迁移到 RabbitMQ Quorum；
- 建监控/告警/SLO；
- 写 runbook；
- 复盘。

第 9～12 周：

- 评估 Kafka/云队列边界；
- 做成本/TCO 分析；
- 制定 12 个月路线图；
- 培训团队。

验收标准：

- 第 1～2 周：能画出当前系统消息拓扑，指出 3 个风险；
- 第 3～4 周：实现 outbox + 幂等消费，通过重复/乱序测试；
- 第 5～8 周：完成一次节点故障演练，记录 RTO/RPO；
- 第 9～12 周：完成一次迁移/选型报告，包含 TCO/风险/回滚。

产出比“读完多少章”更能证明能力。

## 面试与能力评估

消息系统岗位常问：

1. 如何保证消息不丢？分发布/存储/消费三层回答。
2. confirm 和 ack 的区别？各自证明什么？
3. 如何保证顺序？全局 vs 实体分区，见[第 31 章](31-ordering-partitions.md)。
4. 重复消息怎么处理？幂等表/唯一约束/状态机。
5. 队列积压怎么排查？ready/unacked/consumer/下游。
6. Quorum 和 classic 的区别？Raft/副本/优先级/成本。
7. 网络分区怎么办？4.2 及以前看 `pause_minority`/`autoheal`；4.3+ Khepri 下这些 Mnesia 时代的配置不再生效，按 Quorum 多数派、leader 选举和业务对账回答。
8. 如何做零停机迁移？双写/双读/切换/回滚。
9. DLQ 怎么设计？owner/告警/重放/保留。
10. 如何压测？矩阵/尾延迟/故障/恢复。

好的回答不是背概念，而是能说出“失败场景 + 取舍 + 验证方法”。

## 本章小结

选型要基于场景/权重，不是“最强产品”。迁移是重新设计语义，不是复制拓扑；双跑、对账、回滚是核心。成本要算人力/故障/迁移，不只云资源。职业上，消息系统能力横跨后端、SRE、架构、安全和商业；项目经验/故障复盘比证书更有说服力。
