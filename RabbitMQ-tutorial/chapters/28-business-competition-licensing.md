# 第 28 章 商业分析 II：竞争、许可与商业模式

> 本章定位：理解 RabbitMQ 的竞争位置、MPL 2.0 许可的含义、Broadcom 生态的影响，以及开源基础设施常见的商业模式。数字和公司行为会变化，分析框架不会。

## MPL 2.0 许可

RabbitMQ 使用 Mozilla Public License 2.0（MPL 2.0）。核心要点（非法律意见）：

- 允许使用、修改、分发；
- 修改 MPL 覆盖的文件需要以 MPL 共享源代码；
- 可以与专有代码组合成更大作品，只要 MPL 文件的修改保持开源；
- 没有 copyleft 传染到整个应用（与 GPL 不同）；
- 专利授权/终止条款；
- 商标不属于许可范围。

商业含义：

- 云厂商/托管商可以在 MPL 基础上提供服务；
- 企业可以修改插件/内部代码而不必开源整个业务系统；
- 但“RabbitMQ”商标、官方支持、认证不能随意使用；
- 发行版可以加入专有管理/支持组件（取决于具体许可证）。

### 与替代品的许可对比

| 项目 | 许可证 | 商业影响 |
|---|---|---|
| RabbitMQ | MPL 2.0 | 允许托管/修改，文件级开源义务 |
| Kafka | Apache 2.0 | 更宽松，云厂商可自由托管 |
| Pulsar | Apache 2.0 | 同上 |
| NATS | Apache 2.0 | 同上 |
| ActiveMQ Artemis | Apache 2.0 | 同上 |
| IBM MQ | 商业 | 许可/支持付费 |
| SQS/SNS | 云服务 | 按用量付费，无源码 |

许可证影响“谁能提供托管”“谁能修改”“是否需要回馈”。它不直接决定技术优劣，但会影响厂商投入和生态。

### 合规检查清单

如果企业要修改 RabbitMQ 源码或插件并对外分发：

- [ ] 记录哪些文件被修改、修改是否包含第三方代码；
- [ ] 分发时提供对应 MPL 文件的源代码；
- [ ] 保留版权/许可声明；
- [ ] 确认商标使用（产品名、域名、宣传语）；
- [ ] 确认插件/依赖的许可证（可能不是 MPL）；
- [ ] 内部使用与对外分发的义务不同，让法务确认；
- [ ] 商业发行中的专有组件与 MPL 文件的边界清晰。

## Broadcom/VMware Tanzu 生态

RabbitMQ 项目处于 Broadcom 的 VMware Tanzu 生态。对客户的影响：

- 商业支持/发行渠道可能调整；
- 打包/定价/销售策略可能变化；
- 开源项目本身仍在 MPL 下，代码不会被“收回”；
- 社区/独立托管商仍有空间；
- 企业采购需要评估供应商路线图和支持条款。

不要把“被收购”直接等同于“项目死亡”。开源项目的存续取决于社区/维护者/用户；商业支持的变化会影响采购，但不改变代码许可。另一方面，企业不能假设“开源=永远免费支持”，SLA/安全补丁/认证通常需要商业合同。

工程上的对冲手段：

- 保留自建/镜像能力，不把全部环境绑死在单一托管商；
- 使用标准 AMQP/管理 API，减少专有扩展；
- 定期导出 definitions、拓扑和配置；
- 关注 release notes、安全公告和版本支持窗口；
- 在合同中写清退出/迁移支持。

## 竞争格局

### Kafka

- 分布式日志、分区、offset、高吞吐；
- 生态：Connect、Streams、KSQL、Schema Registry；
- 强项：日志/流处理/数据管道/事件溯源；
- 弱项：复杂路由、每消息确认、优先级、RPC；
- 商业：Confluent、云厂商托管。

RabbitMQ vs Kafka 不是“谁更好”，而是“队列/路由” vs “日志/流”。很多企业两者并用：RabbitMQ 做业务任务，Kafka 做数据管道。

### Pulsar

- 计算/存储分离、多租户、分区日志；
- 生态不如 Kafka 成熟，但云原生/多租户强；
- 运维复杂；
- 适合大规模流/队列统一平台。

### NATS

- 轻量、低延迟、云原生；
- JetStream 提供持久化/流；
- 路由/协议简单；
- 生态/企业集成不如 RabbitMQ；
- 适合微服务/边缘/控制面。

### ActiveMQ Artemis

- JMS/AMQP 兼容，企业集成；
- 社区/商业支持；
- 与 RabbitMQ 在传统 MQ 场景竞争；
- 生态/云托管选择较少。

### 云队列

- SQS/SNS、Azure Service Bus、Google Pub/Sub、EventBridge；
- 免运维、弹性、按量计费；
- 限制：协议/路由/插件/可移植性；
- 默认选择效应强；
- 跨云/混合云需要抽象层。

### Redpanda / WarpStream 等

- Kafka 兼容、低运维/对象存储；
- 竞争 Kafka 而非 RabbitMQ；
- 但会挤压“日志型”RabbitMQ Streams 场景。

## 差异化矩阵

| 维度 | RabbitMQ | Kafka | NATS | SQS |
|---|---|---|---|---|
| 复杂路由 | 强 | 中 | 中 | 弱 |
| 任务队列 | 强 | 中 | 中 | 强 |
| 日志/重放 | 中（Streams） | 强 | 中 | 弱 |
| 协议生态 | 强 | 中 | 中 | 云 API |
| 运维简单 | 中 | 中/复杂 | 强 | 强（托管） |
| 吞吐 | 中高 | 很高 | 高 | 高（托管） |
| 企业集成 | 强 | 中 | 中 | 中 |
| 云可移植性 | 强 | 强 | 强 | 弱 |

“强/中/弱”是相对判断，具体取决于规模/配置/团队。

## 商业模式

开源基础设施常见模式：

### 1. 支持订阅

- SLA、24×7、补丁、升级指导；
- 按节点/CPU/集群/年计费；
- 适合自建/私有云/受监管行业。

### 2. 托管服务（DBaaS/PaaS）

- 按 vCPU/内存/存储/吞吐/连接计费；
- 多租户、自动备份、监控、升级；
- 毛利受云资源/人力/支持影响；
- 适合中小团队/云原生。

### 3. 商业发行版

- 开源核心 + 专有管理/安全/连接器；
- 需要小心许可证/社区关系；
- 客户为“省心/合规”付费。

### 4. 市场/插件

- 云市场、监控/安全集成；
- 收入分成/联合销售；
- 依赖生态。

### 5. 培训/认证/咨询

- 课程、认证、架构评审；
- 适合建立品牌/渠道；
- 规模有限但毛利高。

### 6. 行业解决方案

- 金融/电商/IoT 的参考架构 + 支持；
- 更高客单价，但交付重；
- 需要行业知识。

MPL 2.0 允许“open core”模式，但社区可能对“把关键功能锁进商业版”有反弹。平衡点是：核心可靠性/协议保持开放，商业价值放在运维/合规/规模/支持。

## 单位经济与定价

### 一个示范模型

假设一个托管 RabbitMQ 服务：

```text
客单价：$1,000/月
云资源成本：$300/月
支持/人力分摊：$300/月
毛利：$400/月（40%）
获客成本：$6,000
回本周期：15 个月
年流失率：15%
LTV ≈ 毛利 × 12 / 流失率 = 400×12/0.15 = $32,000
LTV/CAC ≈ 5.3
```

这些数字是假设，不是行业基准。真实模型要考虑：

- 多租户密度；
- 存储/网络成本；
- 支持工单；
- SLA 赔偿；
- 客户规模分布；
- 获客渠道；
- 价格战。

### 敏感性

```text
LTV = ARPA × 毛利率 / 流失率
CAC = 销售/市场投入 / 新客户数
```

如果流失率从 15% 涨到 30%，LTV 减半；如果支持成本翻倍，毛利率下降；如果获客成本上升，回本周期拉长。

托管消息服务的难点：

- 可靠性成本随规模非线性上升；
- 大客户议价能力强；
- 云厂商可以用整体云收入补贴；
- 故障/赔偿可能一次性吃掉多年利润。

不要用“SaaS 平均毛利率”套消息服务；基础设施的 on-call/合规/安全成本更高。

### 定价维度与风险

| 维度 | 优点 | 风险 |
|---|---|---|
| 按节点/资源 | 可预测 | 客户压缩资源/超卖 |
| 按消息量 | 贴合价值 | 突发/重试导致账单惊吓 |
| 按存储/保留 | 鼓励清理 | 大积压客户成本高 |
| 按连接数 | 适合 IoT | 连接复用/代理绕过 |
| 按支持等级 | 高毛利 | 响应时间/人力成本 |
| 按功能 | 差异化 | 客户反感“功能税” |

建议：

- 至少两个维度（资源 + 支持/功能），避免单一维度被套利；
- 明确重试/死信/复制是否计费；
- 提供预算告警/配额；
- 大客户定制合同，不公开“隐藏折扣”；
- 把“可靠性成本”（跨 AZ/备份/on-call）计入价格。

不要只按“CPU 小时”定价，否则客户会把 RabbitMQ 当无状态服务，忽略运维价值。

## 锁定与可移植性

开源 broker 的一个卖点是可移植性：

- AMQP 标准客户端；
- 自建/托管/多云；
- 拓扑/消息格式可迁移；
- 避免云厂商专有 API 锁定。

但现实锁定来自：

- 插件/参数差异；
- 管理 API/工具；
- 认证/网络安全；
- 运维知识；
- 商业支持合同。

选型时评估“迁移成本”，而不只是“源码是否开放”。

## 供应商风险与缓解

| 风险 | 缓解 |
|---|---|
| Broadcom 战略调整 | 保留自建能力/镜像、标准协议、退出条款 |
| 云厂商限制插件 | 确认所需插件/参数、预留迁移方案 |
| 开源维护者流失 | 关注 release/社区、内部 fork 能力 |
| 安全漏洞 | 订阅公告、固定版本、快速升级流程 |
| 许可变更 | 法务评审、代码/配置可迁移 |
| 支持合同 | SLA/响应/赔偿/退出支持写清楚 |

供应商风险的评估不应只看“公司是否被收购”，还要看：版本支持窗口、补丁节奏、插件兼容、托管商锁定、合同退出条款。

## MPL 2.0 的常见误解

| 误解 | 实际情况 |
|---|---|
| “MPL 是 GPL，必须开源整个系统” | MPL 是文件级 copyleft；修改的 MPL 文件要开源，不传染整个应用 |
| “可以随便用 RabbitMQ 商标做托管” | 商标不在许可证范围；商业使用要遵守商标/品牌政策 |
| “开源就不能收费” | 可以卖支持/托管/培训/商业发行 |
| “改了代码必须回馈上游” | 分发修改后的 MPL 文件时需要提供源代码；内部使用/不分发有不同义务 |
| “云厂商必须开源托管服务” | MPL 不要求；这与 AGPL/SSPL 不同 |

这不是法律意见。企业使用前应让法务确认“分发/修改/托管/商标”的具体边界。

## Open Core 的边界

RabbitMQ 本身是开源核心，商业价值在上层（支持、托管、合规、运维）。Open core 的常见边界：

- 核心协议/可靠性/队列保持开源；
- 商业版提供管理/监控/安全/多集群/支持；
- 云厂商提供托管，但不一定回馈全部功能；
- 插件/连接器可能由第三方提供。

风险：

- 社区对“关键功能锁进商业版”的反弹；
- 云厂商“白嫖”开源但不贡献；
- 商业版与开源版分叉；
- 许可变更（历史上有公司从 Apache 改 SSPL/BSL）。

缓解：

- 明确开源承诺/治理；
- 核心功能不阉割；
- 商业价值放在“规模/合规/支持”而非“基础可用性”；
- 与社区/客户透明沟通。

## 本章小结

RabbitMQ 的竞争位置是“复杂路由 + 任务队列 + 企业集成”，不是“所有消息”。MPL 2.0 允许托管/修改，但商标/支持/商业发行仍有边界。Broadcom 生态带来不确定性，但不改变开源代码许可。商业模式包括支持、托管、商业发行、市场、培训和行业方案；单位经济取决于可靠性成本、获客和流失。
