# 第 31 章 消息顺序、并发与分区：把 FIFO 错觉拆开

> 本章定位：把散落在队列、消费、重试、Streams 和变更工程里的“顺序”集中讲清楚。你会看到 RabbitMQ 在哪些窄条件下真的 FIFO、哪些常见操作会打破它，以及工程上如何用分区键、版本号、单活消费者和重排序缓冲把“每实体有序”做成可验证的约束。

## 从一次“乱序发货”说起

一个订单服务按顺序发布三条事件：

```text
order-1001: created
order-1001: paid
order-1001: shipped
```

消费者收到后却先处理了 `shipped`，再处理 `paid`，于是发货系统看到“未支付已发货”，库存服务看到“已发货未扣减”。团队第一反应是“RabbitMQ 不是 FIFO 吗”，于是加机器、换队列类型、把 prefetch 调到 1，问题仍然偶发。

根因通常不在 broker 的“队列是不是 FIFO”，而在整条链路上有五个不同的顺序：

1. **生产顺序**：业务代码在哪个线程/事务里、以什么顺序调用 publish；
2. **入队顺序**：broker 接受消息并写入队列的顺序；
3. **投递顺序**：队列把消息交给消费者的顺序；
4. **处理完成顺序**：消费者并发处理时，哪条先处理完；
5. **副作用顺序**：数据库写入、外部 API 调用真正生效的顺序。

RabbitMQ 只能对第 2、3 层的一部分做出承诺。第 1、4、5 层由应用决定。把这三层混为一谈，就会得到“队列是 FIFO，所以业务有序”的错误结论。

## 顺序的五个层次

| 层次 | 由谁决定 | 常见破坏因素 |
|---|---|---|
| 生产顺序 | 应用线程/事务/重试 | 多线程并发 publish、失败重发、outbox 多发布器 |
| 入队顺序 | broker | 多交换机路由到同一队列、优先级、TTL 过期、溢出丢弃 |
| 投递顺序 | broker + 消费者模型 | 多消费者竞争、requeue、redelivery、single active consumer 切换 |
| 处理完成顺序 | 应用并发模型 | 线程池、异步回调、批量处理、下游延迟差异 |
| 副作用顺序 | 数据库/下游 | 事务提交顺序、唯一键冲突、补偿动作、跨服务调用 |

一个可用的顺序设计，必须明确“哪一层需要顺序、由谁保证、失败时如何恢复”。只说“用 RabbitMQ 保证顺序”，等于没有设计。

## RabbitMQ 到底保证什么

先把结论放前面：**RabbitMQ 不提供端到端的全局顺序**。它提供的是“单队列、单消费者、无重投、无优先级”条件下的 FIFO 近似，以及 Streams 的分区内顺序。任何超出这个条件的场景，都需要应用层补语义。

### 单队列 + 单消费者

在同一个队列上，只有一个消费者，消息没有因为 requeue、优先级、TTL 或溢出被重新排列时，消费者看到的顺序与入队顺序一致。这是最接近“FIFO”的场景，也是很多教程默认的隐含前提。

但它仍然不是“生产顺序”的证明：

- 生产者可能用多个线程/多个 channel 并发 publish，broker 看到的到达顺序不等于业务发生顺序；
- publisher confirm 只确认“被接受”，不确认“业务顺序”；
- 如果生产者在 confirm 超时后重发，同一条业务事件可能出现两次，且第二次排在后面。

### 多消费者竞争

同一个队列挂多个消费者时，队列会把消息分发给不同消费者。每条消息仍然只给一个消费者，但**全局处理顺序是交错的**。每个消费者看到的子序列通常有序，合并起来不再有序。

这就是 work queue 模式的正常行为：它优化的是吞吐和公平，不是顺序。若业务要求“同一订单的三条事件按序处理”，就不能让三个消费者无序地抢同一个队列。

### requeue、nack 与 redelivery

消费失败后 `nack(requeue=true)` 或连接断开导致未确认消息重投，会打破“处理顺序”：

```text
入队:   m-1  m-2  m-3
消费:   m-1  m-2
失败:   m-1 被 requeue
之后:   m-1(redelivered)  m-3
```

从业务处理历史看，顺序变成了 `m-1, m-2, m-1, m-3`：既有重复，也有“后一条先完成”的错觉。RabbitMQ 会把重投消息放回队列（经典队列尽量靠近原位置，Quorum 队列的位置与实现/版本有关），但不承诺“重投后仍然严格 FIFO”。Mini 为了测试可重复，保留了消息原始的 `queued_seq`，所以示例里 `m-1` 会排在 `m-3` 前；生产系统不应依赖这个细节。

更稳妥的规则是：**只要发生重投，就把这段流视为“至少一次 + 可能乱序”**，由消费端的幂等和版本号兜底。

### 优先级

优先级队列会主动重排 ready 消息：高优先级先投递。即使只有一个消费者，FIFO 也不成立。Quorum 队列的优先级模型还分版本：4.0–4.2 是 normal/high 两档并按约 2:1 调度，4.3+ 是 32 级严格优先级；重投消息在 Quorum 中不保留原优先级。细节见[第 06 章](06-queues-ttl-priority.md)。

如果业务同时要求“优先级”和“同一实体严格有序”，通常要拆队列：高优先级走独立队列，或者同一实体的消息带序号，由消费端重排序。

### 死信、延迟与重试

消息进入 DLX、延迟队列或重试队列后，已经离开了原来的队列。重试消息再次回到主队列时，可能排在大量新消息后面。于是：

```text
原始: order-1.created -> order-1.paid -> order-1.shipped
重试: order-1.paid 失败 -> 进入 retry -> 5 分钟后重新入队
结果: order-1.shipped 可能先被处理
```

这不是 broker 的 bug，而是“重试 = 新的一次投递”的必然结果。第 09 章给了重试拓扑；本章补上顺序维度：**重试队列也必须按实体分区，或者消费端必须能处理乱序。**

### Quorum Queue

Quorum Queue 用 Raft 复制日志，leader 按日志顺序提交，消费者看到的是已提交消息的顺序。它在“单队列、单消费者、无重投”条件下同样近似 FIFO，但：

- 写入需要多数派确认，leader 切换期间可能短暂不可写；
- 重投/requeue 的顺序不保证与原始一致；
- 优先级模型与 classic 不同；
- 多消费者仍然是竞争消费，不提供全局顺序。

Quorum 解决的是“节点故障时不丢已确认消息”，不是“业务事件按序处理”。两者不要混为一谈。Raft 日志、leader 切换、成员变更和故障演练见[第 11 章](11-cluster-quorum.md)。

### Stream 与 Super Stream

Stream 是追加日志：每条消息有单调 offset，消费者按 offset 读取，读取不删除。单个 Stream 内严格按 append 顺序；Super Stream 把消息按分区键哈希到多个分区，**只保证分区内有序，不保证跨分区全局有序**。

这和 Kafka 的模型一致：顺序的边界是分区，不是主题。要让同一订单的事件有序，必须让它们进入同一个分区；要让所有订单全局有序，只能退化成单分区，吞吐会受限。Stream retention、Super Stream 分区发现、消费者组与 offset 提交的细节见[第 12 章](12-streams-super-streams.md)。

### 交换机与多队列

交换机只负责路由，不负责排序。一条消息被 fanout 到三个队列，每个队列各自维护自己的顺序；三个队列的消费者之间没有共同的时间线。交换机到交换机的绑定、alternate exchange、dead-letter exchange 都可能让同一条业务事件走不同路径，进一步削弱“全局顺序”的直觉。交换机类型、绑定等价性和路由成本见[第 05 章](05-exchanges-routing.md)。

### 一张表

| 场景 | 顺序保证 | 工程含义 |
|---|---|---|
| 单队列 + 单消费者 + 无重投/优先级 | 近似 FIFO | 最简单，也最容易被并发/重试打破 |
| 单队列 + 多消费者 | 每消费者子序列有序，全局交错 | 适合无状态任务，不适合同实体状态迁移 |
| 有 requeue/redelivery | 可能重复、可能乱序 | 必须幂等 + 版本号/状态机 |
| 有优先级 | 按优先级重排 | 顺序让位于紧迫性 |
| Quorum Queue | 提交日志有序，重投不保证原序 | 高可用不等于业务顺序 |
| Stream | 单 Stream 内按 offset 有序 | 可重放，适合事件溯源/审计 |
| Super Stream | 分区内有序，跨分区无序 | 分区键决定顺序边界 |
| 跨 broker Federation/Shovel | 异步、至少一次 | 顺序更弱，需业务对账 |

## 全序、每键序与因果序

工程上不要把“顺序”当成一个布尔值。至少要区分三种：

### 全序（total order）

所有消息共享一个顺序。实现方式通常是单队列 + 单消费者，或者单分区 + 单消费者。代价是吞吐上限和可用性耦合：消费者一慢，全局都慢；消费者一挂，全局都停。

全序适合：配置变更、全局序列号、单账户账本（如果账户就是全局唯一实体）、审计链。

### 每键序（per-key order）

同一实体（订单、账户、设备、租户）内的消息有序，不同实体之间可以并行。实现方式是“按 key 分区”：

- 每个 key 一个队列；
- 或 consistent hash exchange 把 key 路由到固定队列；
- 或 Super Stream 按 key 哈希到固定分区；
- 或单队列 + 消费端按 key 做串行化/重排序。

这是大多数业务真正需要的模型。它把顺序范围缩小到业务聚合根，换来了水平扩展。

### 因果序（causal order）

消息之间的“因为所以”关系有序，而不是所有消息全序。例如“支付成功”必须发生在“库存预留”之后，但两个不同订单之间没有关系。因果序通常需要版本向量、因果依赖标记或业务状态机，不能只靠队列。

| 模型 | 顺序范围 | 典型实现 | 代价 |
|---|---|---|---|
| 全序 | 所有消息 | 单队列/单分区 + 单消费者 | 吞吐低、单点 |
| 每键序 | 同一 key | 分区键 + 固定消费者/分区 | 热点、倾斜 |
| 因果序 | 有依赖的消息 | 版本向量/状态机/ Saga | 应用复杂度高 |
| 无序 | 无 | 竞争消费者 | 最简单，业务需容忍 |

## 分区键设计

“按订单 ID 分区”听起来简单，实际要回答四个问题。

### 1. key 的基数够不够

key 太少会导致分区倾斜。例如用“租户 ID”做 key，一个大租户可能占满一个分区；用“订单 ID”通常基数足够，但同一订单的所有事件必须带同一个 key。

### 2. 会不会产生热点

电商大促时，少数爆款商品的订单可能集中在同一 key（如果按商品 ID 分区）。热点分区的消费者会成为瓶颈，其他分区空闲。解决方式：

- 换更高基数的 key（订单 ID 而不是商品 ID）；
- 热点 key 加随机后缀再聚合（会牺牲该 key 的严格顺序）；
- 独立热点通道 + 限流；
- 业务上拆分热点实体。

### 3. 分区数怎么定

分区数决定最大并行度，也决定未来扩容的成本。Super Stream 的分区数通常不能原地增加；增加分区会改变 key 到分区的映射，破坏“同一 key 一直在同一分区”的假设。常见做法是：

- 按未来 2～3 年的峰值吞吐预留分区；
- 分区数取 2 的幂，便于哈希分布；
- 扩容时新建 Super Stream，做双写/迁移，而不是直接改分区数；
- 监控每个分区的速率/积压，发现倾斜再调整 key。

### 4. 分区键和路由键是不是一回事

不是。路由键（routing key）是交换机匹配用的字符串；分区键（partition key）是 Super Stream/一致性哈希用来选分区的值。它们可以相同，也可以不同。设计时要明确：

- 交换机按 routing key 路由到哪些队列；
- 队列内部/Stream 按哪个 key 分区；
- 消费端按哪个 key 串行化。

三者不一致，是“明明按订单分区了，还是乱序”的常见原因。

### 一致性哈希交换机

RabbitMQ 的 `x-consistent-hash` 插件可以把 routing key 哈希到多个队列，适合“每个 key 固定到一个队列”的场景。4.3+ 还提供内置的 `x-modulus-hash`。它们解决的是“消息进哪个队列”，不解决“队列内多消费者”的顺序；要保证顺序，每个分区仍然只能有一个消费者（或消费端按 key 串行化）。

## 消费者并发模型

即使消息按 key 进了同一分区，消费端的并发模型仍可能打破顺序。

### prefetch 与 in-flight

`basic.qos(prefetch_count=N)` 允许消费者同时持有 N 条未确认消息。消息按顺序投递，但处理完成顺序取决于业务代码：

```text
投递: m-1  m-2  m-3
处理: m-2 先完成并 ack
      m-1 后完成并 ack
```

broker 看到的 ack 顺序是 `m-2, m-1`。如果 ack 之后还有副作用（写库、发下游事件），副作用顺序就可能与投递顺序不同。把 prefetch 设为 1 可以让“投递-处理-ack”串行，但吞吐会下降；更好的做法是让同一 key 的消息在应用内串行处理（按 key 分片线程/actor），不同 key 并行。

`basic.qos` 的 `global` 标志也要分清：`global=false` 是每消费者窗口，`global=true` 是整条 channel 共享窗口。RabbitMQ 4.0 起弃用 global，4.3+ 对 Quorum/Stream 默认拒绝；顺序敏感的系统应使用 per-consumer prefetch，并按 key 串行化，而不是依赖 channel 级窗口。

### 批量 ack

批量 ack 只减少确认开销，不改变处理顺序。`multiple=true` 表示“确认到此 tag 为止的所有消息”，如果中间有消息处理失败，批量 ack 可能把失败消息也确认掉。顺序敏感的业务应避免跨实体批量 ack，或按分区批量。

### 单活消费者（Single Active Consumer）

`x-single-active-consumer=true` 让同一队列的多个消费者中只有一个处于 active 状态，其余待命。active 消费者挂掉后，队列自动切换。它适合“同一队列需要多个消费者做高可用，但同一时刻只能有一个处理”的场景。

注意：

- 单活是队列级，不是 key 级；它保证同一队列同时只有一个消费者，不保证消息在多个队列之间的顺序；
- 切换瞬间可能有短暂空窗；
- 待命消费者不消费，资源利用率低；
- 它不能替代分区；全局单活仍然受单消费者吞吐限制。

Mini 的 `x-single-active-consumer` 在 `mini_rabbitmq/queue.py` 中实现，`tests/test_ordering.py::test_single_active_consumer_serializes_delivery` 验证了 active 切换。

### 消费者优先级

消费者优先级（`x-priority`）让高优先级消费者先拿到消息，低优先级消费者在高优先级空闲时补位。它会改变“哪个消费者处理哪条消息”，但不会改变同一消费者看到的子序列顺序。不要用它来实现业务顺序。

### 线程池与异步回调

最常见的“消费端乱序”不是 broker 造成的，而是应用把消息丢进线程池后立即 ack：

```python
def on_message(message, delivery):
    executor.submit(process, message)   # 异步处理
    broker.ack(delivery.delivery_tag)   # 立刻 ack
```

这样 ack 顺序与处理顺序完全脱钩，进程崩溃还会丢消息。正确做法是“处理完成后再 ack”，并让同一 key 的任务进入同一个串行队列。

## 重试与顺序的冲突

重试是顺序的头号敌人，因为“失败的消息晚点再来”天然会插到新消息后面。

### 方案 A：阻塞重试

同一 key 的消息处理失败时，不 ack，原地重试或阻塞该 key 的后续消息，直到成功/进入死信。优点是顺序严格；缺点是毒消息会卡住整个 key，吞吐下降。

适合：同一实体状态机、账本、必须严格串行的场景。必须配合最大重试次数、超时和人工兜底。

### 方案 B：重试队列

失败消息进入 retry 队列，延迟后回到主队列。优点是主队列不被阻塞；缺点是后续消息可能先处理。缓解方式：

- retry 队列也按 key 分区，保证同一 key 的重试消息仍在该 key 的分区；
- 消费端按 key 维护“等待重试”状态，后续消息先缓冲；
- 使用版本号/状态机，让“旧事件”被拒绝而不是被误处理；
- 对顺序敏感的业务改用阻塞重试。

### 方案 C：延迟桶 + 顺序键

把重试消息按“实体 key + 重试时间”放入延迟桶，消费端先按 key 聚合，再按原始序号处理。实现复杂度高，但能在不阻塞主队列的情况下保持每键序。

### 方案 D：parking lot

超过最大重试次数的消息进入 parking lot（人工/自动修复队列），不再回到主流程。它不解决顺序，但能防止毒消息无限循环。parking lot 的消息必须带原始 key、序号、失败原因和重试历史，修复后可以按 key 重放。

### 一张决策表

| 业务要求 | 推荐 | 不推荐 |
|---|---|---|
| 同一订单严格有序，失败可阻塞 | 单 key 单消费者 + 阻塞重试 + 最大次数 | 多消费者竞争 + 无限重试 |
| 同一订单有序，但可短暂延迟 | 按 key 分区 + retry 分区 + 消费端缓冲 | 全局 retry 队列 |
| 不同订单可并行 | 按订单 ID 分区 | 全局单队列 |
| 允许乱序，只要最终一致 | 竞争消费者 + 幂等 + 版本号 | 依赖 FIFO |
| 需要重放历史 | Stream/Super Stream + 分区键 | 普通队列 + DLX |

## 版本号、状态机与水位线

当无法保证物理顺序时，用逻辑顺序兜底。

### 每实体版本号

每条事件带 `aggregate_id` 和 `version`（单调递增）。消费端维护每个实体的已处理版本：

```text
if event.version <= current_version:
    ignore as duplicate/stale
elif event.version == current_version + 1:
    apply; current_version += 1
else:
    buffer or reject as gap
```

这能处理重复、旧事件和部分乱序。缺口（gap）需要缓冲、等待或告警；不能静默跳过，否则会丢业务状态。

### 状态机

订单状态机只允许合法迁移：

```text
CREATED -> PAID -> SHIPPED -> COMPLETED
```

收到 `SHIPPED` 时如果当前状态是 `CREATED`，说明 `PAID` 还没到：可以拒绝、缓冲或进入异常队列。状态机把“顺序问题”转化为“状态迁移合法性问题”，更容易测试和审计。

### 水位线与缺口检测

对每个 key 维护“已连续处理到的最大序号”。如果收到更大的序号但中间有缺口，记录缺口并等待；超过超时时间后告警或人工修复。水位线也是监控指标：缺口数量、等待时长、乱序率。

### 因果依赖

跨实体的事件可能需要因果序。例如“支付成功”依赖“库存预留”，但两者属于不同聚合。可以在事件里带 `causation_id`/`correlation_id`，消费端检查依赖是否已满足；不满足则缓冲。版本向量适合检测并发修改，但对业务团队的理解成本高，通常只在多活/离线合并场景使用。

## 跨服务与跨区域

### Outbox 的顺序

Outbox 表按 `id` 排序、单发布器或按 aggregate 分区发布，可以保证同一聚合的事件按插入顺序发出。多发布器用 `FOR UPDATE SKIP LOCKED` 提高吞吐时，必须保证同一 aggregate 不会被两个发布器同时处理，否则会乱序。第 19 章给了表结构和 SQL；这里补上顺序约束：

- `ORDER BY id` 只保证扫描顺序，不保证多发布器的提交顺序；
- 按 `aggregate_id` 哈希到固定发布器，或加 `aggregate_id` 级锁；
- 发布成功后再标记 sent；失败重试可能重复，消费端要幂等；
- outbox 清理不能删除尚未发布的行。

### CDC 的顺序

CDC 从数据库日志派生事件，通常按 WAL/LSN 顺序。但下游消费可能并行，且不同表的变更可能被拆分到不同 topic/partition。要保证同一聚合的顺序，CDC 连接器必须按主键分区，消费端按主键串行化。

### 跨区域

Active-Active 多区域写入时，两个区域可能同时修改同一实体。Federation/Shovel 是异步复制，不提供全局顺序；冲突解决必须靠业务（最后写入获胜、版本向量、按区域分区、冲突队列）。第 13 章给了拓扑和冲突策略，[附录 U](../appendices/U-disaster-recovery-continuity.md)给了 RPO/RTO 与切换演练。

## 如何测试顺序

顺序 bug 很难靠“跑一遍 happy path”发现。需要刻意制造并发、重投和延迟。

### 1. 序号断言

给每条消息带 `(key, seq)`，消费端记录实际处理序列，断言：

- 每个 key 的序号连续；
- 没有重复（或重复被幂等吸收）；
- 没有缺口；
- 跨 key 的交错不影响每 key 顺序。

`tests/test_ordering.py` 和 `examples/22_ordering_partitions.py` 就是这种断言的可运行版本。

### 2. 故障注入

- 消费后、ack 前 kill 进程；
- 处理到一半抛异常，触发 requeue；
- 网络断开导致未确认消息重投；
- 消费者扩容/缩容，触发 rebalance；
- 单活消费者切换；
- 延迟/超时导致重试。

每次注入后检查：重复率、乱序率、缺口、业务状态是否合法。

### 3. 并发模型测试

用线程池/异步任务模拟“先投递、后完成”：

```python
# 伪代码：两个 key 并行，同一 key 串行
executor_by_key = {key: ThreadPoolExecutor(max_workers=1) for key in keys}
```

断言同一 key 的任务不会并发执行；不同 key 可以并行。不要只测单线程。

### 4. 属性测试

对“重排序缓冲”这类纯逻辑，可以用随机序列测试：任意乱序输入，输出必须按 key 连续、无重复、无丢失。Python 的 `hypothesis` 或自写随机循环都可以。重点不是覆盖所有输入，而是覆盖“缺口、重复、迟到、跨 key 交错”四类边界。

### 5. 监控与告警

顺序问题在生产上通常表现为：

- 消费端版本冲突/旧事件被拒绝的比例上升；
- 缺口等待超时；
- 重试率上升；
- DLQ 中出现“前置事件未到”；
- 业务对账出现状态不一致。

把这些指标纳入第 16 章的监控体系，而不是等业务告警。

## Mini-RabbitMQ 的实现走读

Mini 的顺序实现集中在三处：

### 队列：堆 + 序号

`mini_rabbitmq/queue.py` 的 ready 队列是一个堆：

```python
heapq.heappush(
    self._heap,
    (-self._priority_of(message), seq, expires_at, message),
)
```

- `-priority` 让高优先级成为堆顶；
- `seq` 是入队序号，保证同优先级 FIFO；由于 seq 唯一，比较不会走到后面的 `expires_at`；
- `expires_at` 只是随堆元素携带、供过期扫描使用，不参与消息排序，也不应被当成业务顺序的一部分。

`_requeue_locked` 保留原始的 `queued_seq`，所以重投消息会回到原序号位置。这是教学实现为了可重复测试做的选择；真实 RabbitMQ 的位置语义更复杂，不能照搬。

### 消费者：单活与分发

`Queue.add_consumer` 在 `x-single-active-consumer` 下只让第一个消费者 active；`remove_consumer` 会把 active 状态交给下一个。`Queue.dispatch` 按消费者优先级和创建时间选择目标，prefetch 限制未确认数量。测试覆盖在 `tests/test_queue.py` 和 `tests/test_ordering.py`。

### Streams：offset 与分区

`mini_rabbitmq/streams.py` 的 `Stream.append` 分配单调 offset，`Stream.read` 按 offset 读取且不删除；`SuperStream.partition_for` 用 SHA-256 对 routing key 取模选分区。它演示了“分区内有序、跨分区无序”，但没有真实段文件、复制和 Stream 协议。

### 能证明什么，不能证明什么

`examples/22_ordering_partitions.py` 能证明：

- 单队列单消费者 FIFO；
- 竞争消费者的子序列有序；
- requeue 会带 redelivered 并改变处理序列；
- 优先级会重排；
- Super Stream 的每 key 顺序；
- 应用层 Resequencer 能把乱序恢复成每键有序。

它不能证明真实 RabbitMQ 在 Quorum 重投、网络分区、跨区域复制下的顺序行为；这些需要[附录 W](../appendices/W-4x-feature-labs.md)的集群实验和[附录 P](../appendices/P-application-testing-chaos.md)的故障注入。

## 一个可运行的最小闭环

运行：

```bash
python examples/22_ordering_partitions.py
python -m pytest -q tests/test_ordering.py
```

示例输出类似：

```text
single queue FIFO: ['m-0', 'm-1', 'm-2', 'm-3', 'm-4']
competing consumers: {'worker-a': [0, 2, 4], 'worker-b': [1, 3, 5]}
after requeue: [('m-1', True), ('m-3', False)]
priority order: ['urgent', 'normal', 'low']
per-key partition order: {'order-1': [0, 1, 2, 3], ...}
resequenced: {'order-1': ['order-1:0', ...], 'order-2': ['order-2:0']}
OK 22_ordering_partitions
```

这六行输出对应六个事实。把“队列是 FIFO”拆成这六个事实后，设计时就不会再问“RabbitMQ 保不保证顺序”，而是问“我需要哪一层、哪个范围的顺序，谁来保证，失败时怎么恢复”。

## 顺序设计检查清单

### 业务层

- 哪些实体需要顺序？是订单、账户、设备还是租户？
- 需要全序、每键序还是因果序？
- 乱序的业务代价是什么（重复扣款、状态回退、审计缺口）？
- 能否用状态机/版本号把乱序变成可拒绝的旧事件？
- 失败时是阻塞、重试、跳过还是人工修复？

### 拓扑层

- 分区键是什么？基数、热点、倾斜是否评估过？
- 同一实体是否始终进入同一队列/分区？
- 分区数是否按未来容量预留？扩容方案是否演练？
- 是否使用了优先级/延迟/重试队列？它们如何影响顺序？
- 是否有多条路径（fanout、E2E、AE、DLX）汇聚到同一业务流？

### 消费层

- 每个分区是否只有一个消费者，或消费端按 key 串行化？
- prefetch 与并发模型是否会让同一 key 的消息并发处理？
- ack 是在处理完成后还是提交任务后？
- 重试是否按 key 分区？是否有最大次数和 parking lot？
- 消费者扩缩容/rebalance 时，在途消息如何处理？

### 验证层

- 是否有 `(key, seq)` 断言和缺口检测？
- 是否注入了重复、乱序、延迟、kill、rebalance？
- 是否有乱序率/缺口/重试率监控？
- 对账能否发现顺序导致的业务不一致？
- 回滚/重放时，顺序是否仍然成立？

## 本章小结

RabbitMQ 的顺序保证是窄条件的：单队列、单消费者、无重投、无优先级时近似 FIFO；多消费者、requeue、优先级、DLX、Quorum 重投和跨 broker 复制都会削弱它。真正可扩展的模型是“每键序”：按业务聚合根分区，分区内单消费者或按 key 串行化，跨分区并行。无法保证物理顺序时，用版本号、状态机、缺口检测和重排序缓冲把逻辑顺序补回来。

顺序不是 broker 的一个开关，而是生产、入队、投递、处理、副作用五层共同的结果。把每一层的责任写清楚，用 `(key, seq)` 做可执行断言，用故障注入验证失败路径，才能把“FIFO”从口号变成可运维的约束。分区顺序、单活消费者、重排序器和停尸房等模式的组合与失败路径，见[附录 S](../appendices/S-messaging-patterns-antipatterns.md)；应用侧的并发/混沌测试方法见[附录 P](../appendices/P-application-testing-chaos.md)。
