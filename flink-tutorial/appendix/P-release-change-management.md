# 附录 P 作业交付与变更管理手册

第 24 章讲工程化开发、测试与 CI/CD，第 25 章讲 Kubernetes 与 Operator，附录 M 讲 REST API 与运维自动化。它们分别回答“代码怎么写得可维护”“作业怎么部署到集群”“平台怎么调用控制面”。

## P.1 交付单元与版本坐标

一次 Flink 变更从来不是“一个 jar”。交付物至少包含六个坐标：

| 坐标 | 例子 | 不固定会发生什么 |
|---|---|---|
| Flink 版本 | 2.3.0 | API/状态/配置行为漂移 |
| 连接器版本 | Kafka connector 4.x | 类冲突、offset/事务语义变化 |
| 作业制品 | `orders-job-1.4.0.jar` / 镜像 digest | 回滚到错误代码 |
| 配置 | `config.yaml`、`-D` 参数、CRD spec | 默认值变化、参数被忽略 |
| 状态格式 | savepoint/checkpoint 的算子 UID、序列化器 | 恢复失败或状态错位 |
| 外部契约 | topic/schema、维表主键、sink 事务超时 | 端到端重复/丢失 |

发布记录里必须能回答：

```text
这次变更的六个坐标分别是什么？
哪个坐标变了？变了之后哪条兼容性假设不再成立？
出问题时，六个坐标能否一起回到上一个已知良好组合？
```

只记录镜像 tag 不够。`latest`、可变 tag、集群里手工改过的配置，都会让“回滚”变成一次新的变更。

## P.2 环境分层与配置

### 三层环境

```text
dev        单机/本地 MiniCluster，快速验证逻辑
staging    与生产同构的小集群，验证状态、连接器、发布流程
prod       生产，只接受经过 staging 验证的制品
```

staging 不必和生产的容量一样，但**拓扑形状、Flink 版本、连接器版本、状态后端、checkpoint 存储类型**要一致。只在 dev 跑过单元测试的作业，不能直接进生产。

### 配置分层

```text
base.yaml                所有环境共享的默认值
env/staging.yaml         端点、并行度、资源
env/prod.yaml            生产端点、资源、HA、监控
secret/                  Secret 管理，不进 Git
```

原则：

- **配置进 Git**，Secret 用外部密钥管理；
- **镜像不可变**，用 digest 而不是 tag；
- **环境差异显式化**，不要靠“生产手工改一个参数”；
- **配置键有版本**，2.x 改名的键要逐项核对，不能假设旧键仍然生效。

```yaml
# 反例：同一个镜像，生产手工改并行度
job:
  parallelism: 8   # 生产被手工改成 32，Git 里看不出来
```

## P.3 变更分类与风险矩阵

不是所有变更都需要 savepoint。先分类，再决定发布方式。

| 变更 | 状态影响 | 默认策略 | 额外验证 |
|---|---|---|---|
| 纯 Stateless 逻辑 | 无 | 滚动/直接重启 | 输出抽样 |
| 有状态算子内部逻辑 | 状态 schema 不变 | savepoint 升级 | 恢复后输出对账 |
| 新增/删除有状态算子 | UID/拓扑变化 | savepoint + 兼容性检查 | 作业图 diff |
| 修改 key | 分区布局变化 | 新 UID / State Processor API | 重分配后结果对账 |
| 修改并行度 | key group 重分配 | savepoint + rescale | 状态大小/恢复时间 |
| 修改 `maxParallelism` | key group 数变化 | State Processor API 重写 | 兼容性演练 |
| 修改状态序列化器 | 二进制格式变化 | 序列化兼容性测试 | 旧快照恢复 |
| 升级 Flink 大版本 | 运行时/状态格式 | 双跑 + 迁移演练 | 状态、连接器、配置 |
| 升级连接器 | offset/事务状态 | 连接器兼容矩阵 | offset 连续/无悬挂事务 |
| 修改 SQL 查询 | 计划/状态布局 | 计划 diff + savepoint 演练 | changelog/sink 语义 |
| 修改 source/sink 语义 | 端到端一致性 | 双写/影子链路 | 对账、重复/丢失 |

### 风险分级

```text
低：无状态、可重放、下游幂等
中：有状态但 schema/UID/key 不变，可 savepoint 恢复
高：状态 schema/key/并行度/序列化变化
极高：跨大版本、跨连接器、跨 sink 语义、无法重放
```

高风险变更必须满足三个条件才允许进生产：

1. 在 staging 用**生产规模的快照**做过恢复演练；
2. 有**可执行的回滚路径**，不只是“再发一版”；
3. 有**对账/观测指标**证明新版本没有改变业务结果。

## P.4 兼容性门禁

### 4.1 UID 与拓扑

所有有状态算子必须有稳定 `uid`。CI 里应该做作业图 diff：

```text
新增 uid、删除 uid、uid 重复、uid 对应算子类型变化
→ 阻止合并或要求显式审批
```

`name` 只影响 UI，`uid` 才决定 savepoint 里的状态归属。改 `name` 通常安全，改 `uid` 等于换了一个算子。

### 4.2 状态 schema

检查：

- 状态名是否变化；
- 状态类型/序列化器是否兼容；
- POJO 字段增删、类名/包名是否变化；
- `ListState`/`MapState` 的元素类型是否变化；
- 序列化器是否注册了 `TypeSerializerSnapshot`；
- 是否从 Kryo 切到 POJO/AVRO，或反向切换。

```text
允许：新增带默认值的字段、兼容的类型提升
高风险：删除字段、改字段类型、改类名、换序列化器
```

### 4.3 key 与 key group

- 改 `keyBy` 的 key → 同一业务 key 可能落到不同 subtask，旧状态找不到；
- 改并行度 → key group 重新分配，需要 rescale；
- 改 `maxParallelism` → key group 数变化，通常必须用 State Processor API 重写 savepoint；
- 改 key 的哈希语义（例如把 `String` 改成 `hashCode()` 包装）→ 分区变化。

### 4.4 连接器与外部契约

| 检查项 | 问题 |
|---|---|
| Source offset 状态 | 新连接器能否读旧 offset |
| Sink 事务状态 | 是否有悬挂事务、transaction id 是否冲突 |
| 分区发现 | 新分区从 earliest/latest 开始，是否重复/缺失 |
| Schema 演进 | 源端 DDL 是否会让下游失败 |
| 事务超时 | 新默认值是否小于 checkpoint 间隔 |
| 指标名 | 看板/告警是否还能匹配 |

### 4.5 配置门禁

2.x 改了配置文件名和一批键名。发布前逐项检查：

```text
flink-conf.yaml → config.yaml
state.backend.* → state.backend.type
execution.checkpointing.* 的默认值
taskmanager.memory.* 的分配
high-availability.*
```

配置键写错通常不会让作业起不来，而是**静默使用默认值**。这类问题只能靠“发布后对比运行时配置”发现。

### 4.6 SQL 计划门禁

SQL 作业要 diff 执行计划，而不是只看 SQL 文本：

```sql
EXPLAIN SELECT ...;
```

重点看：

- join 是否从 interval 退化成 regular；
- 是否新增/删除了有状态算子；
- changelog 模式是否变化；
- 是否引入 `SinkUpsertMaterializer`；
- 并行度/算子链是否变化；
- 是否出现全表扫描/无界状态。

## P.5 发布策略

### 5.1 滚动重启

适用于无状态或可快速重建的作业。K8s 里是替换 Pod；Flink 里是 cancel 后用相同配置重启。

风险：有状态作业会丢失状态或从旧 checkpoint 恢复，必须确认语义。

### 5.2 Savepoint 升级

有状态作业的默认策略：

```text
触发 savepoint → 停止旧作业 → 部署新版本 → 从 savepoint 恢复 → 验证 → 观察
```

适合大多数“状态 schema 不变”的变更。

### 5.3 蓝绿

两套完整环境（蓝/绿），同一份输入：

```text
上游双写 / 同一 topic 两个 consumer group
蓝集群：旧版本，写 sink A
绿集群：新版本，写 sink B
对账通过后，把下游切到 B
```

优点：回滚只需切回 A；缺点：双倍资源、双写一致性、下游切换成本。

### 5.4 金丝雀

只让一小部分流量走新版本：

```text
按分区/用户/租户拆分输入
1% → 10% → 50% → 100%
```

流作业的金丝雀比 Web 服务难：不能简单按请求比例路由，通常要按 Kafka 分区、业务 key 或上游双写实现。要确保同一业务 key 不被两个版本同时处理，否则状态会分叉。

### 5.5 影子链路

新版本消费同一份输入，但写到影子 sink（不对外可见），与生产结果对账：

```text
生产作业 → sink_prod
影子作业 → sink_shadow
对账：行数、主键集合、金额汇总、抽样明细
```

影子链路不改变生产结果，适合验证逻辑/状态迁移；代价是双倍计算和存储。

### 5.6 双跑

两个版本各自完整运行，输出到不同位置，按时间窗口对比。双跑最适合跨版本/跨引擎迁移，但必须定义“允许的差异”（时间边界、乱序、浮点误差）。

## P.6 标准升级 Runbook

下面是一份可以直接落地的有状态作业升级流程。命令是形状，具体参数以环境和版本为准。

### 阶段 0：变更记录

```text
变更单：CR-2026-1117-01
作业：orders-realtime
变更：升级 Flink 2.2 → 2.3，修改窗口聚合逻辑
风险：高（运行时 + 状态逻辑）
回滚：旧镜像 + 升级前 savepoint
负责人 / 观察人 / 变更窗口
```

### 阶段 1：Pre-flight

- [ ] staging 已用生产快照恢复成功；
- [ ] savepoint 目录可写、容量足够；
- [ ] 目标版本/连接器在兼容矩阵内；
- [ ] 作业图 diff 已审阅（uid/状态算子/并行度）；
- [ ] 配置键已逐项核对；
- [ ] 下游 sink 能处理重复/回退；
- [ ] 监控看板已切到新指标名；
- [ ] 回滚镜像和旧 savepoint 可用；
- [ ] 变更窗口内没有其他高风险变更。

记录基线：

```text
P99 延迟、吞吐、Kafka lag、checkpoint 时长/大小、状态大小、重启次数
```

### 阶段 2：触发 savepoint（与 stop-with-savepoint 二选一）

```bash
flink savepoint <job-id> s3://bucket/savepoints/orders
```

或 REST：

```bash
curl -X POST http://jm:8081/jobs/<job-id>/savepoints \
  -H 'Content-Type: application/json' \
  -d '{"target-directory":"s3://bucket/savepoints/orders","cancel-job":false}'
```

savepoint 是异步的。必须轮询到 `COMPLETED` 并拿到 `location`，不能把 202 当成功。

验证：

- savepoint 路径存在、大小合理；
- 包含所有有状态算子；
- 没有缺失 uid/状态句柄；
- 记录 savepoint id 和路径到变更单。

如果计划直接用 `flink stop --savepointPath` 完成“savepoint + 停止”，可以跳过本阶段的独立 savepoint，避免两次快照之间产生一段需要重放的数据。

### 阶段 3：停止旧作业

```bash
flink stop --savepointPath s3://bucket/savepoints/orders <job-id>
```

或（阶段 2 已经 savepoint 时）直接 cancel：

```bash
flink cancel <job-id>
```

注意：

- `stop` 会先做一次 savepoint 再停止；如果阶段 2 已经做过 savepoint，**只恢复其中一个**，不要恢复阶段 2 的快照又重放 stop 产生的快照之后的区间；
- `drain=true` 会发出 `MAX_WATERMARK` 做收尾；savepoint 之后的新数据在恢复后仍会被消费，但可能因为事件时间状态已被 MAX_WATERMARK 清理而被当作迟到数据丢弃，**发布暂停通常用 `drain=false`**；
- 停止后确认没有残留 TaskManager 在写 sink；
- 如果 sink 是事务性的，确认没有悬挂事务。

### 阶段 4：部署新版本

- 镜像 digest 与变更单一致；
- 配置/CRD 与 Git 一致；
- 资源规格满足新版本要求；
- ServiceAccount/RBAC/网络策略已更新；
- 如果是 Operator，确认 `upgradeMode` 和 `state`。

### 阶段 5：从 savepoint 恢复

```bash
flink run -s s3://bucket/savepoints/orders/savepoint-... \
  -d /opt/flink/usrlib/orders-job-1.5.0.jar
```

或 Operator：把 `job.state` 设为 `running`，`upgradeMode: savepoint`，让 Operator 处理。

检查：

- 作业进入 RUNNING；
- 所有 subtask 部署成功；
- 没有 `ClassNotFoundException`/`NoSuchMethodError`；
- 状态大小与 savepoint 一致（允许合理差异）；
- watermark 开始推进；
- checkpoint 开始成功。

### 阶段 6：发布后验证

前 10 分钟：

- [ ] checkpoint 成功次数 ≥ 2；
- [ ] Kafka lag 没有持续增长；
- [ ] 反压没有持续 HIGH；
- [ ] P99 延迟在预算内；
- [ ] 输出行数/金额与基线对账；
- [ ] 没有重复主键/丢失主键；
- [ ] 日志无异常刷屏；
- [ ] 状态大小没有异常膨胀。

前 1 小时：

- [ ] 与上游/下游做一次事件级对账；
- [ ] 检查迟到/死信比例；
- [ ] 检查恢复时间（如果发生重启）；
- [ ] 检查成本/资源利用率。

### 阶段 7：观察与关闭

观察窗口（例如 24 小时）结束后：

- 记录实际指标与基线差异；
- 更新 runbook/看板/告警；
- 清理旧镜像/旧 savepoint（按保留策略）；
- 关闭变更单；
- 把“实验特性/已知限制”记入技术债。

## P.7 回滚手册

### 先分清三种回滚

| 回滚 | 回滚什么 | 不能回滚什么 |
|---|---|---|
| 代码回滚 | 镜像/jar/配置 | 已经写入 sink 的数据 |
| 状态回滚 | 从旧 savepoint 恢复 | savepoint 之后处理过的数据 |
| 数据回滚 | 下游补偿/重放/删除 | 外部副作用（已发通知、已扣款） |

**代码回滚不等于状态回滚。** 旧代码 + 新状态可能无法恢复；旧状态 + 新数据会产生空洞。回滚方案必须写清楚“数据从哪里补”。

### 回滚决策树

```text
新版本有问题？
├─ 只是延迟/资源问题 → 先扩容/降载，未必回滚
├─ 结果错误但状态兼容 → 回滚代码 + 从旧 savepoint 恢复 + 重放
├─ 状态不兼容/恢复失败 → 回滚代码 + 旧 savepoint + 重放
├─ 已写入错误数据 → 先止损（停写/切流），再补偿/回滚
└─ 外部副作用已发生 → 业务补偿，不能只靠技术回滚
```

### 回滚步骤

1. 停止新版本（不要让它继续写 sink）；
2. 确认旧版本镜像/配置可用；
3. 确认旧 savepoint 可读；
4. 从旧 savepoint 恢复旧版本，确认 source 已从快照里保存的 offset/位点续读；
5. 只有在 source offset 由外部系统管理、或你刻意跳过了 source 状态时，才按时间/offset 手工重放；对已经由 savepoint 管理的 source，手工重放同一区间会造成重复消费；
6. 对账：主键集合、金额、计数；
7. 清理新版本产生的错误数据（幂等 sink/补偿作业）；
8. 记录回滚原因、时间线、数据影响。

### 回滚的最坏情况

- 旧 savepoint 损坏/丢失；
- source 保留期不够，无法重放；
- sink 不支持删除/更新，错误数据无法修复；
- 外部副作用无法撤销。

这些情况必须在变更前评估。**没有回滚路径的高风险变更，不应该在业务高峰执行。**

## P.8 灰度与切流

### 按 Kafka 分区灰度

```text
新版本只消费部分分区
旧版本消费其余分区
```

要求：

- 同一业务 key 只落在一个版本；
- 分区分配稳定；
- 两个版本的输出不会互相覆盖；
- 下游能合并两个版本的结果。

### 按业务 key 灰度

```text
user_id % 100 < 1 → 新版本
```

适合按用户/租户隔离的业务，但要求 source 能按 key 过滤，且两个版本的状态互不干扰。

### 上游双写

```text
业务 → topic_new / topic_old
新版本消费 topic_new，旧版本消费 topic_old
```

双写要保持同一事件 id，下游按 id 去重；否则切流时会出现重复/丢失。

### 切流检查

- [ ] 新版本处理了足够长时间，指标稳定；
- [ ] 新旧结果对账通过；
- [ ] 下游已准备好接收新格式/新主键；
- [ ] 回切路径可用；
- [ ] 切流窗口内没有其他变更；
- [ ] 切流后旧版本停止消费，避免双写。

## P.9 变更窗口、冻结与审批

### 变更窗口

- 避开业务高峰、财务结算、大促、月末；
- 高风险变更留足观察时间；
- 跨团队依赖（上游/下游/平台）同步窗口；
- 时区/夏令时切换期间避免时间相关变更。

### 冻结期

以下时期通常冻结非紧急变更：

```text
大促/重要活动
财务结账
重大节假日
安全事件/故障处理期间
```

紧急变更要有“break-glass”流程：审批、记录、事后复盘，不能成为常态。

### 审批

| 风险 | 审批人 |
|---|---|
| 低 | 作业 owner |
| 中 | owner + 平台 on-call |
| 高 | owner + 平台负责人 + 业务负责人 |
| 极高 | 变更委员会/架构评审 |

审批不是形式。审批人要看的是：**兼容性证据、回滚路径、观测指标、数据影响**。

## P.10 发布后验证

### 四类验证

| 类别 | 指标 | 判定 |
|---|---|---|
| 正确性 | 主键集合、行数、金额汇总、抽样明细 | 与基线/上游对账 |
| 延迟 | 端到端 P99、watermark lag、Kafka lag | 在 SLO 内 |
| 稳定性 | checkpoint 成功率/时长、重启次数、反压 | 不劣于基线 |
| 成本 | CPU/内存/状态大小/存储请求 | 在预算内 |

### 对账的最小集合

```text
1. 源端与 sink 的行数（按时间窗）
2. 主键集合差（missing/extra）
3. 金额/计数等可加指标的汇总差
4. 抽样明细逐字段对比
5. 重复主键计数
6. 迟到/死信比例
```

对账窗口要覆盖：

- 变更前已处理的数据（状态恢复是否正确）；
- 变更后新到达的数据（新逻辑是否正确）；
- 迟到/乱序数据（watermark 是否变化）。

### 观测窗口

```text
0～10 分钟：是否能起来、checkpoint 是否成功
10～60 分钟：延迟/lag/反压/错误率
1～24 小时：状态增长、内存、成本、对账
```

不要在新版本刚 RUNNING 时就宣布成功。很多状态/资源问题要几个小时才显现。

## P.11 多作业平台发布

当一个业务域有多个作业（标准化、聚合、风控、输出）时，发布顺序很重要：

```text
上游 schema/语义变更
  → 先发下游兼容版本（能读新旧两种）
  → 再发上游新版本
  → 观察
  → 清理兼容代码
```

原则：

- **先兼容，再切换**：下游先支持新旧 schema，上游再切换；
- **避免同时改两端**：同时改上下游会让故障定位失去基线；
- **共享 source 的作业一起评估**：一个作业的反压会影响其他作业；
- **发布编排**：用 DAG 表达作业依赖，按拓扑顺序发布；
- **统一版本坐标**：同一批作业尽量使用相同的 Flink/连接器版本，减少矩阵复杂度。

## P.12 事故响应与复盘

### 分级

| 级别 | 影响 | 响应 |
|---|---|---|
| P0 | 核心业务中断/资损 | 立即止血，全员响应 |
| P1 | 重要指标延迟/错误 | 15 分钟内响应 |
| P2 | 非核心作业异常 | 工作时间处理 |
| P3 | 潜在风险/告警 | 排期处理 |

### 止血顺序

```text
1. 停止错误扩散（停写/切流/降级）
2. 保留现场（日志/指标/快照/线程 dump）
3. 恢复服务（回滚/重启/扩容）
4. 验证正确性（对账）
5. 补偿数据（重放/修正）
6. 复盘与改进
```

不要一上来就重启。重启会破坏现场，也可能让重复/丢失更难定位。

### 复盘模板

```text
标题：
时间线（T0 发现、T1 止血、T2 恢复、T3 关闭）：
影响范围（业务/数据/时间窗）：
根因（技术/流程/组织）：
为什么没提前发现（测试/监控/演练缺口）：
做得好的：
做得不好的：
行动项（负责人/截止时间/验收标准）：
```

复盘的目标不是追责，而是让同类问题不再发生。行动项必须可验证，不能写“加强监控”这种无法验收的话。

## P.13 RACI 与职责

| 活动 | 作业 Owner | 平台团队 | 业务方 | On-call |
|---|---|---|---|---|
| 变更分类/风险评估 | A/R | C | C | I |
| 兼容性演练 | R | A/C | I | I |
| 发布执行 | R | A | I | C |

## P.15 常见失败案例

### 案例一：savepoint 成功，恢复失败

现象：savepoint 完成，新作业启动时报“状态找不到对应算子”。

根因：升级时改了有状态算子的 `uid`，或删除了一个算子导致后续 uid 偏移。

防范：CI 做作业图 diff；所有有状态算子显式 uid；升级前在 staging 用同一 savepoint 恢复。

### 案例二：checkpoint 成功，下游重复

现象：作业恢复后，sink 出现重复订单。

根因：sink 非幂等，source offset 已回拨到 checkpoint，重复消费。

防范：sink 幂等键/事务；恢复后对账；不要假设“checkpoint 成功 = 端到端 exactly-once”。

### 案例三：改并行度后状态错位

现象：扩容后结果异常，部分 key 的历史丢失。

根因：只改了并行度，没有验证 key group/rescale；或 `maxParallelism` 不兼容。

防范：savepoint 恢复演练；确认状态可 rescale；高风险变更用 State Processor API。

### 案例四：配置键被静默忽略

现象：升级后 checkpoint 间隔/内存配置没有生效。

根因：2.x 配置键改名，旧键被忽略，运行时用了默认值。

防范：发布后对比运行时配置；维护配置迁移清单；不要只依赖启动成功。

### 案例五：蓝绿双写同时生效

现象：切流后下游收到两份数据。

根因：蓝绿两个作业同时消费/写入，切换时没有停旧版本。

防范：切流脚本幂等；同一业务 key 只允许一个版本处理；切流后确认旧版本停止。

### 案例六：回滚状态但 source 已前移

现象：回滚到旧 savepoint 后，下游出现缺口或重复。

根因：source offset 由外部系统/手工提交管理，恢复时没有回到 savepoint 位点；或者回滚后又手工重放了 savepoint 已经覆盖的区间。

防范：先确认 source offset 与 savepoint 的绑定关系；不要把“重放”当成回滚的默认步骤；外部 offset 场景单独设计补偿，并用对账验证。

## P.16 检查清单

### 变更前

- [ ] 变更已分类，风险等级明确；
- [ ] 兼容性门禁全部通过；
- [ ] staging 用生产快照恢复成功；
- [ ] 回滚路径可执行，数据补偿方案明确；
- [ ] 监控/告警/看板已更新；
- [ ] 变更窗口和审批完成；
- [ ] 上下游已通知。

### 变更中

- [ ] savepoint 完成且可读；
- [ ] 旧作业已停止，无残留写入；
- [ ] 新版本从正确 savepoint 恢复；
- [ ] 没有类冲突/配置错误；
- [ ] checkpoint 开始成功；
- [ ] watermark 开始推进。

### 变更后

- [ ] 正确性对账通过；
- [ ] 延迟/吞吐/lag 在 SLO 内；
- [ ] checkpoint 成功率/时长不劣于基线；
- [ ] 状态大小/成本可控；
- [ ] 无异常日志/重启；
- [ ] 观察窗口结束，变更单关闭；
- [ ] 经验进入 runbook/技术债清单。

发布不是“把作业跑起来”，而是**证明新版本在正确性、延迟、稳定性和成本四个维度都不劣于旧版本，并且失败时能退回来**。附录 M 给的是控制面接口，本附录给的是围绕这些接口的决策与流程；两者结合，才构成可重复的交付能力。
