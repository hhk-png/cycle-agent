# 第37章 流处理生态、选型与未来方向

前置知识：第 10、13 章（连接器、CDC/湖仓）、第 26 章（容量与成本）。即使没读前 33 章，也可以把本章当作选型框架。

第 34～36 章讲的是 Flink 自身的技术演进。这一章把镜头拉远：**Flink 在流处理版图里到底处于什么位置，什么时候该选它，什么时候不该选，未来几年哪些判断值得下注**。

先给结论：

- Flink 仍然是“通用、有状态、事件时间、强一致”流计算的主力，但“流处理”不再等于“Flink”；
- 选型的分水岭不是吞吐 benchmark，而是**语义、状态规模、生态、运维、成本和团队**；
- 流式湖仓、流数据库、Serverless、AI Agent 正在改变边界，但不会在一夜之间替代 Flink；
- 最危险的不是选错引擎，而是**用引擎的能力去掩盖架构/数据/组织问题**。

## 37.1 生态全景

流处理不是孤立产品，而是一条栈：

```text
消息/CDC：Kafka、Pulsar、Fluss、Debezium、Flink CDC
计算：Flink、Spark Structured Streaming、Kafka Streams、ksqlDB、
      RisingWave、Materialize、Pulsar Functions
存储：Paimon、Iceberg、Hudi、ClickHouse、Doris、StarRocks、Fluss
平台：Kubernetes Operator、云托管 Flink、实时计算平台
上层：BI、告警、特征、风控、推荐、AI Agent
```

可以用四个问题切分：

```text
消息层：数据怎么流？
计算层：数据怎么算？
存储层：结果怎么存/查？
平台层：谁运维/谁治理？
```

Flink 的位置是**计算层**：它不负责长期消息存储，也不是 OLAP 数据库。很多“Flink 性能问题”其实是把消息/存储/查询的职责塞给了它。

### 三个市场口径

“流处理市场”没有统一口径。常见三种：

| 口径 | 包含 | 规模 | 买家 |
|---|---|---|---|
| 流计算引擎 | Flink/Spark/Kafka Streams | 较小 | 数据平台团队 |
| 实时数据平台 | 计算 + 消息 + 存储 + 集成 | 中 | 平台/架构 |
| 实时业务方案 | 风控/推荐/IoT/客服 | 大 | 业务负责人 |

口径越大，越接近业务预算，也越难用单一产品覆盖。这解释了为什么“卖引擎”很难，“卖平台/方案/省心”更容易。

## 37.2 竞品对比

### 一张表

| 系统 | 定位 | 优势 | 局限 | 典型场景 |
|---|---|---|---|---|
| Flink | 通用流计算 | 事件时间、状态、EOS、SQL、生态 | 运维复杂、资源开销大 | 实时数仓、风控、CDC、复杂 join |
| Spark Structured Streaming | 微批/持续流 | 与 Spark 批生态一体 | 低延迟/状态语义弱于 Flink | 已有 Spark 批、分钟级 |
| Kafka Streams | 库形态流处理 | 轻量、与 Kafka 紧耦合 | 只适合 Kafka、运维自建 | Kafka 内的简单 ETL/聚合 |
| ksqlDB | Kafka 上的 SQL | 上手快 | 复杂状态/连接器有限 | 简单实时 SQL |
| RisingWave | 流数据库 | SQL 友好、存算分离 | 生态较新 | 实时物化视图/分析 |
| Materialize | 增量物化视图 | 实时 SQL、强一致 | 场景/生态聚焦 | 实时看板/增量计算 |
| Pulsar Functions | 轻量函数 | 与 Pulsar 一体 | 复杂状态弱 | 简单事件处理 |
| Flink Agents | 事件驱动 Agent | 与 Flink 状态/容错一体 | 新项目、API 演进中 | 实时 Agent/工具编排 |
| Fluss | 流式存储 | 面向流读流写、与 Flink 深度集成 | 2026 毕业为 TLP，1.0 已发布，生态仍在成长 | 流式湖仓/实时存储 |

### 决策树

```text
已经在 Kafka 生态，逻辑简单？
  ├── 是 → Kafka Streams / ksqlDB
  └── 否 → 继续

已有 Spark 批，延迟要求分钟级？
  ├── 是 → Structured Streaming
  └── 否 → 继续

需要事件时间、复杂状态、CEP、多源 join、端到端 EOS？
  ├── 是 → Flink
  └── 否 → 继续

想要“SQL 数据库体验”的实时物化视图？
  ├── 是 → RisingWave / Materialize
  └── 否 → 继续

需要事件驱动 Agent/工具调用？
  ├── 是 → Flink Agents（评估）
  └── 否 → 重新审视需求
```

### 对比维度

```text
延迟：Flink ≈ Kafka Streams < Spark 微批
状态：Flink 最强，Spark 次之，Kafka Streams 受限
SQL：Flink/RisingWave/Materialize 强，Kafka Streams 弱
生态：Flink 连接器最全
运维：托管 > 自建；库形态最轻
锁定：开源/可迁移 > 专有平台
```

**不要只看 benchmark。** 公开 benchmark 通常：

- 数据分布均匀、无倾斜；
- 无故障注入；
- 状态/连接器配置理想化；
- 不包含运维和人力成本。

真实业务的瓶颈往往是数据质量、schema、状态倾斜、运维和成本。

## 37.3 选型框架

### 七个维度

| 维度 | 权重 | 关键问题 |
|---|---|---|
| 语义正确性 | 25% | 事件时间、EOS、状态、恢复是否满足？ |
| 生态 | 20% | 连接器、SQL、湖仓、Catalog 是否齐全？ |
| 运维 | 15% | 部署、升级、监控、扩缩容、故障恢复？ |
| 成本 | 15% | 3 年 TCO？状态/流量如何计费？ |
| 团队 | 10% | 能否招到/培养人？现有技能栈？ |
| 风险 | 10% | 社区、供应商、锁定、合规？ |
| 合规 | 5% | 认证、审计、数据驻留？ |

权重不是固定的。金融可能把合规/正确性调到 40%，互联网可能把成本/弹性调高。

### 必须项 vs 加分项

先列“必须项”（一票否决）：

- 支持事件时间/watermark；
- 支持所需 source/sink；
- 状态规模可支撑；
- 端到端语义满足；
- 部署环境支持；
- 合规/安全满足。

再列“加分项”：

- SQL 覆盖率高；
- 物化表/湖仓集成；
- 自动扩缩容；
- 可观测性；
- 多租户；
- 社区活跃。

不要用加分项掩盖必须项的缺失。

### POC 检查清单

- 用真实 schema 和倾斜数据；
- 峰值 2 倍压测；
- kill TM/JM 恢复；
- 大状态 checkpoint/restore；
- 规则/维表热更新；
- 端到端 EOS（source → sink → 下游）；
- 权限/审计；
- 成本账单模拟；
- 迁移/导出；
- 故障演练和回滚。

POC 的目标不是“跑通”，而是**证明失败时也能正确恢复**。

### TCO

```text
TCO = 计算 + 存储 + 网络 + 软件/托管 + 人力 + 迁移 + 故障损失
```

常见误判：

- 只算 CPU，不算状态存储和 checkpoint；
- 只算资源单价，不算人力；
- 只算正常路径，不算故障/对账/补数；
- 只算当前规模，不算 3 年增长。

第 40 章会给出更细的成本/ROI 算例。

### 锁定与退出

- 数据能否导出？
- 作业/SQL 能否迁移？
- 连接器是否标准？
- 元数据/Catalog 是否可移植？
- 专有功能用了多少？
- 退出成本是否可接受？

“迁移成本”不是选型的唯一因素，但必须提前量化。

## 37.4 流式湖仓与 OLAP

### 三种常见架构

```text
A. 实时数仓（OLAP 服务看板）
Kafka/CDC → Flink → Doris/ClickHouse/StarRocks → BI

B. 流式湖仓（一份存储，流批共用）
Kafka/CDC → Flink → Paimon/Iceberg/Hudi → 查询引擎/训练

C. 混合（湖仓存明细 + OLAP 存指标）
Kafka/CDC → Flink ─┬→ 湖仓（明细/审计）
                   └→ OLAP（看板/点查）
```

### 湖仓 vs OLAP

| 维度 | 湖仓 | OLAP |
|---|---|---|
| 存储成本 | 低 | 高 |
| 查询延迟 | 秒级/分钟级 | 亚秒级/秒级 |
| 更新 | 支持（表格式） | 支持（主键模型） |
| 流读 | 支持（增量） | 有限 |
| 适用 | 明细/历史/对账/训练 | 看板/点查/高并发 |

湖仓不是“更快的 OLAP”，OLAP 也不是“更便宜的湖仓”。很多团队最后落成混合架构。

### Paimon / Iceberg / Hudi

| 维度 | Paimon | Iceberg | Hudi |
|---|---|---|---|
| 流式写入 | 强（Flink 原生） | 中 | 中 |
| 更新/删除 | 主键 upsert | 支持 | 支持 |
| 流读 | 增量/变更日志 | 增量 | 增量 |
| 生态 | Flink 社区强 | 跨引擎广 | Spark 社区强 |
| 小文件/compaction | 内建 | 依赖引擎/服务 | 内建 |
| 适用 | 实时湖仓 | 开放湖仓 | 近实时入湖 |

选型要看：

- 主写引擎（Flink/Spark）；
- 查询引擎（Trino/StarRocks/Spark）；
- 更新频率；
- 小文件治理；
- 元数据服务；
- 多引擎并发写。

### 小文件与 compaction

流式写入会产生大量小文件。治理手段：

- 按分区/桶聚簇；
- 定期 compaction；
- 控制 checkpoint 间隔与文件大小；
- 写入端攒批；
- 监控文件数/平均大小；
- 查询端避免全量扫描。

小文件不治理，最后会同时拖慢写入、查询和恢复。

## 37.5 云原生、托管与 Serverless

### 部署光谱

```text
自建 Standalone/YARN
  → 自建 Kubernetes + Operator
  → 云托管 Flink
  → Serverless / 按量 SQL
```

越往右：

- 运维越少；
- 单价越高；
- 定制/调试空间越小；
- 锁定风险越高。

### 托管 vs 自建

判断只需四个问题：流处理是不是核心能力？规模是否足够大？团队能否承担 7×24 运维与合规？三年 TCO 谁更低？

- 核心能力 + 规模大 + 团队强 → 自建/混合；
- 业务支撑 + 团队小 + 要快 → 托管；
- 金融/政务有数据驻留要求 → 私有化/专有云；
- 多业务共享 → 平台化 + 内部计费。

完整的成本表、供应商记分卡与建 vs 买财务模型见[第 40 章 40.4～40.5](40-business-roi.md#404-建-vs-买)，这里不再重复。

### Serverless 的边界

Serverless 适合：

- 长尾/实验作业；
- 峰谷明显、按需弹性；
- SQL 为主、少自定义状态；
- 小团队、无专职平台。

不适合：

- 超大状态/复杂 DataStream；
- 需要精细调优/自定义连接器；
- 严格数据驻留/专有云；
- 成本可预测性要求高（按量可能失控）。

## 37.6 开源、商业与自建

Flink 是 Apache 2.0 开源项目，云厂商可以自由托管。这决定了“卖引擎许可证”很难成立，商业化必须往托管、平台、行业方案、支持与合规走。具体的商业模式、Open Core 边界和开源/商业张力见[第 39 章 39.7](39-business-model.md#397-开源与商业化的张力)，这里只保留选型问题：

- 你是否愿意/能够承担 7×24 运维？
- 出故障时谁负责？
- 安全合规谁签字？
- 3 年 TCO 谁更低？
- 退出成本多少？

## 37.7 未来五年的判断

以下是判断，不是预言。每条都给出“下注”和“对冲”。

### 判断一：流批边界继续模糊，但批不会消失

- 流批一体降低开发成本；
- 批处理在回填、对账、训练、低成本历史计算上仍有优势；
- 未来是“同一套语义，多种执行模式”，不是“所有任务都流式”。

**下注**：SQL/湖仓/流批一体。
**对冲**：保留批处理/离线链路，不要把所有回填都塞进流作业。

### 判断二：湖仓成为实时存储默认选项之一

- Paimon/Iceberg/Hudi 支持更新、增量读、流批共用；
- 成本低于常驻 OLAP；
- 但查询延迟/小文件/元数据仍是挑战。

**下注**：湖仓 + Flink 的实时入湖。
**对冲**：保留 OLAP 做高并发看板/点查。

### 判断三：SQL 覆盖更多场景，但复杂状态仍需要 DataStream/PTF

- 窗口 TVF、join、去重、TopN、物化表越来越成熟；
- 复杂事件、外部调用、自定义状态仍需要底层 API；
- PTF 把两者拉近，但调试/状态设计仍难。

**下注**：SQL 优先，复杂逻辑用 PTF/DataStream。
**对冲**：不要让 SQL 变成“不可维护的巨型嵌套查询”。

### 判断四：Data + AI 带来新增量，但不会取代传统 ETL

- 实时特征、向量检索、模型推理、Agent 编排；
- 成本/延迟/不确定性需要工程化；
- 传统 ETL/数仓仍是大多数业务的基础。

**下注**：实时特征 + 检索 + 规则/小模型过滤。
**对冲**：不要把全量事件都送进大模型。

### 判断五：云托管/Serverless 占比上升，自建集中在大平台

- 中小团队优先托管；
- 大厂/金融自建或专有云；
- 平台化/多租户/成本治理成为竞争力。

**下注**：Kubernetes + Operator + 平台化。
**对冲**：保持可迁移，避免深度绑定专有 API。

### 判断六：可观测性、治理、成本成为竞争重点

- 引擎性能差距缩小；
- 运维体验/状态治理/成本可视化决定长期口碑；
- 安全合规是行业门槛。

**下注**：指标/追踪/成本/权限/审计。
**对冲**：不要等出事才补监控。

### 判断七：流数据库/湖仓/引擎边界继续移动

- RisingWave/Materialize/ClickHouse/Doris 都在向“实时”扩展；
- Fluss 等流式存储探索新架构；
- Flink 的护城河是生态/状态/连接器，不是单一 benchmark。

**下注**：保持架构可迁移，核心逻辑与引擎解耦。
**对冲**：避免把业务逻辑写死在某个专有 SQL 方言里。

## 37.8 选型反模式

- **benchmark 驱动**：只看吞吐，不看状态/恢复/运维；
- **功能清单驱动**：功能都有，但都不成熟；
- **忽略状态规模**：POC 用小状态，生产状态爆炸；
- **忽略故障恢复**：正常路径跑通就上线；
- **一个巨大作业**：升级/扩缩容/故障爆炸半径失控；
- **过度平台化**：小团队维护不了多租户平台；
- **深度锁定**：专有 API/格式/连接器，退出成本极高；
- **把实时当万能**：分钟级够用的场景硬上秒级；
- **忽略数据质量**：引擎再强，脏数据也算不对；
- **忽略人力**：买得起平台，养不起团队。

## 本章小结

Flink 是流处理生态的核心计算引擎，但不是全部。选型要看**语义、生态、运维、成本、团队、风险、合规**，而不是单一 benchmark。

未来属于“流批湖一体 + 云原生 + SQL/API 双轨 + Data/AI 融合”的平台，但每条路线都有边界。最稳妥的策略是：**核心逻辑与引擎解耦，保持可迁移；用 POC 证明失败恢复；用 TCO 而不是单价做决策**。
