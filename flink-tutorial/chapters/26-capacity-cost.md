# 第26章 容量规划、SLO 与成本

## 26.1 先定义 SLO

容量不是“能跑就行”，而是满足明确目标：

- 端到端 P99 延迟 < 5 秒；
- 数据新鲜度 < 1 分钟；
- 可用性 99.9%；
- 故障恢复 < 10 分钟；
- 每天可处理 10 亿条事件，峰值 5 万条/秒。

没有 SLO，就无法判断该加多少资源、花多少钱。

```text
SLO 示例：
- 99% 的订单在 5 秒内进入结果表
- 99.9% 的时间作业处于 RUNNING
- checkpoint 成功率 >= 99%
- 故障后 10 分钟内恢复
```

SLO 要可测量、可告警、可取舍。不要写“尽量快”这种无法验证的目标。

## 26.2 吞吐估算

基础公式：

```text
峰值吞吐 = 平均吞吐 × 峰值系数
所需 subtask 数 ≈ 峰值吞吐 / 单 subtask 处理能力
```

单 subtask 处理能力必须用真实作业压测，不能拍脑袋。影响因素：

- 序列化/反序列化；
- 状态读写；
- 外部查询；
- 网络 shuffle；
- checkpoint；
- 数据倾斜。

经验：先按 2～3 倍余量设计，再用压测校准。

### 一个算例

```text
平均 2 万条/秒，峰值系数 3 → 峰值 6 万条/秒
单 subtask 压测 5 千条/秒
所需并行度 ≈ 60000 / 5000 = 12
留 30% 余量 → 16
```

如果 join/窗口放大 2 倍，下游并行度要按 12 万条/秒估算。

## 26.3 并行度与 slot

```text
作业 slot 需求 ≈ max(各算子并行度)   # 默认 slot sharing
TaskManager 数 ≈ ceil(slot 需求 / 每 TM slot 数)
```

但还要考虑：

- source 并行度受分区数限制；
- sink 并行度受目标系统限制；
- 单个 TM 的 CPU/内存/磁盘；
- 故障时能否在剩余节点上重新调度。

```text
最大算子并行度 16，每 TM 4 slot → 至少 4 台 TM
留故障余量 25% → 5 台 TM
```

不要把所有 slot 占满，留出故障转移和滚动升级的余量。

### 资源形状

- CPU 密集（序列化/正则/加密）：多核、少内存；
- 状态密集（RocksDB）：多内存/本地 SSD；
- 网络密集（shuffle/join）：高带宽；
- sink 密集（数据库）：连接池/批量。

一个作业里不同算子可能需要不同形状，可以用 slot sharing group 隔离。

## 26.4 状态容量

```text
状态大小 ≈ key 数量 × 每 key 状态大小 × 副本/索引开销
```

RocksDB 还有写放大、压缩、LSM 多层存储开销。实际磁盘可能是逻辑状态的 1.5～3 倍，取决于配置和数据。

必须估算：

- 活跃 key 数；
- 每 key 保留多久（TTL）；
- 窗口/会话/join 缓存；
- checkpoint 全量/增量；
- 恢复时间。

```text
1000 万用户 × 每用户 2 KB × 1.5 放大 ≈ 30 GB
加上窗口/join 缓存，可能到 100 GB
```

状态是流作业最容易失控的成本。

### 状态增长的驱动因素

- key 基数增长；
- TTL 太长/没有；
- 窗口重叠（滑动窗口）；
- regular join 无界；
- CEP 部分匹配；
- 广播状态过大；
- 脏数据导致 key 爆炸。

## 26.5 Checkpoint 存储与网络

```text
每次 checkpoint 上传量 ≈ 状态大小（全量）或增量大小
带宽需求 ≈ 上传量 / checkpoint 间隔
```

例如 100 GB 状态、每 10 分钟全量、2 小时保留 12 份，存储约 1.2 TB，峰值上传约 170 MB/s。增量 checkpoint 可以显著降低，但恢复仍需读取大量文件。

```text
100 GB / 600 s ≈ 170 MB/s
```

这还不包括并发 checkpoint、其他作业、正常业务流量。对象存储带宽要留余量。

## 26.6 网络与 Kafka

- shuffle 数据量 ≈ 输入量 × 放大系数；
- 双流 join/窗口可能放大数倍；
- Kafka 分区数决定消费并行度；
- 跨可用区流量有成本；
- checkpoint 上传走对象存储网络。

```text
输入 100 MB/s → keyBy shuffle 100 MB/s → join 输出 200 MB/s
```

网络不是免费的：跨 AZ、跨区域、NAT 网关都可能产生费用和延迟。

## 26.7 成本模型

总拥有成本（TCO）：

```text
TCO = 计算 + 内存 + 存储 + 网络 + 托管/许可 + 人力 + 故障损失
```

云上常见计费：

- 按 vCPU/内存/小时；
- 按 slot 或 CU；
- 对象存储容量 + 请求；
- 跨区/出口流量；
- 托管服务溢价。

自建还要算：

- 运维人力；
- 硬件折旧；
- 机房/电力；
- 监控/安全；
- 升级/故障成本。

### 成本拆解示例

```text
计算：8 台 × 16 vCPU × $0.1/h × 730h ≈ $9,344/月
内存：包含在计算
存储：checkpoint 1.2 TB × $0.023/GB ≈ $28/月
网络：跨 AZ 10 TB × $0.01/GB ≈ $100/月
托管：30% 溢价
人力：1.5 FTE
```

数字是示意，实际以云厂商报价为准。重点是把“隐性成本”列出来。本章、第 38 章和第 40 章的算例刻意使用不同规模与单价，目的是展示方法而不是拼成一个总账；做真实决策时请用同一套基线和报价重算。

## 26.8 成本优化

- 用增量 checkpoint；
- 设置状态 TTL；
- 减少不必要的窗口重叠；
- 避免 regular join 无限状态；
- 合理并行度，避免大量空闲 slot；
- 使用弹性伸缩；
- 冷数据归档；
- 选择合适存储层级；
- 压缩网络数据；
- 批量写入下游；
- 把低频作业放到批模式/调度。

不要为了省资源把并行度压到极限，故障恢复和延迟会反噬。

### 成本优化的优先级

1. 减少状态（TTL/窗口/join 设计）——收益最大；
2. 减少 shuffle（预聚合/广播）——次之；
3. 提高资源利用率（弹性/混部）——第三；
4. 降低存储/网络单价——最后。

## 26.9 容量演练

上线前做：

1. 峰值流量压测；
2. 故障注入（kill TM、Kafka 抖动、sink 限流）；
3. checkpoint 大状态测试；
4. 恢复时间测试；
5. 扩缩容测试；
6. 成本回归。

记录基线，后续每次大变更对比。可复现的负载模型、指标口径和实验报告模板见[附录 J](../appendix/J-performance-engineering.md)。

```text
基线：峰值 6 万条/秒，P99 3.2s，checkpoint 45s，状态 80GB
变更后：P99 4.8s，checkpoint 70s → 需要回滚/优化
```

## 26.10 容量工作表

把估算落成一张可复算的表：

```text
输入：
- 平均/峰值 events/s
- 每条记录字节数
- source 分区数
- 状态 key 数 / 每 key 字节
- 窗口/join 放大系数
- checkpoint 间隔/保留份数

计算：
- 网络入口 = 峰值 × 记录字节
- shuffle = 入口 × 放大系数
- 状态 = key 数 × 每 key 字节 × 1.5~3
- checkpoint 上传 = 状态 × 变化率 / 间隔
- slot = max(算子并行度)
- TM = ceil(slot / 每 TM slot) + 故障余量
```

示例：

```text
峰值 6 万/s × 1 KB = 60 MB/s
shuffle ×2 = 120 MB/s
状态 100 GB → checkpoint 增量 5 GB / 5 min = 17 MB/s
slot 16 → 4 TM（每 TM 4 slot）+ 1 台余量
```

## 26.11 扩容还是优化

```text
延迟高：
├─ 反压在某算子 → 先看倾斜/同步调用/状态
├─ sink 慢 → 批量/并发/限流
└─ 全链路忙 → 扩容
状态大：
├─ TTL/窗口/join 设计 → 先优化
└─ 业务必须保留 → 扩容/分层存储
checkpoint 慢：
├─ 状态大 → 增量/减少状态
├─ 存储慢 → 换存储/带宽
└─ 反压 → 先解决反压
```

扩容不是第一步。很多“容量不足”其实是状态设计/倾斜/同步调用导致的。

## 26.12 端到端 P99 延迟预算

“P99 延迟 < 5 秒”是一个结果指标，不能直接指导扩容。必须把它拆成每一跳的预算，否则团队只会反复加资源，却不知道哪一段吃掉了时间。

### 26.12.1 先定义起点和终点

同一条链路至少有四种“延迟”，口径不同，数值可能差一个数量级：

| 口径 | 起点 | 终点 | 适用 |
|---|---|---|---|
| 事件延迟 | 事件在业务系统产生（`event_time`） | sink 写出/下游可见 | 业务 SLO、对账 |
| 摄取延迟 | source 读到记录 | 算子处理完 | 连接器/反序列化排障 |
| 处理延迟 | 记录进入算子 | 记录离开算子 | 算子/状态/外部调用调优 |
| 可见延迟 | sink 提交完成 | 查询/下游消费者可见 | 数仓新鲜度、报表 |

业务说“5 秒内看到结果”，通常指**事件延迟**；Flink 内置 `latency` 指标测的是“source → 算子”的传输/排队时间（见[第 22 章 22.2 节](22-monitoring.md#222-核心指标)），既不是事件延迟，也不是可见延迟。先统一口径，再谈预算。

### 26.12.2 一条 5 秒预算的拆法

```text
P99 事件延迟
  = 业务产生到进入 Kafka        (上游)
  + Kafka 消费/反序列化          (source)
  + 事件时间等待（watermark/窗口） (正确性成本)
  + 算子处理/状态/网络           (计算)
  + sink 批量/事务提交           (输出)
  + 下游可见（索引/缓存/查询）    (下游)
```

一个示意预算（P99，单位 ms）：

| 阶段 | 预算 | 主要影响因素 | 观测手段 |
|---|---:|---|---|
| 业务 → Kafka | 300 | 客户端批量、重试、分区 | 上游埋点、Kafka 时间戳 |
| Kafka → source | 200 | 分区数、反序列化、消费限流 | consumer lag、source busy |
| watermark/窗口等待 | 1500 | 乱序容忍、窗口大小、空闲分区 | watermark lag、窗口触发间隔 |
| 处理与状态 | 800 | 状态大小、RocksDB、GC、UDF | busy、latency、GC |
| 网络/反压排队 | 500 | 并行度、倾斜、buffer | 反压、队列长度 |
| sink 提交 | 1200 | 批量大小、事务超时、外部限流 | sink latency、commit 时长 |
| 下游可见 | 500 | 索引刷新、缓存 TTL | 业务探针 |

这张表的作用不是“加总一定等于 5 秒”，而是暴露**谁占了大头**。如果 watermark 等待 3 秒，优化算子没有意义；如果 sink 提交 2 秒，应该先调批量/事务，而不是加 CPU。

### 26.12.3 用排队论判断“加资源有没有用”

把每个算子看作一个排队系统：

```text
利用率 ρ = 到达率 λ / 服务率 μ
平均排队时间 Wq ≈ (ρ / (1 - ρ)) × 平均服务时间
```

- ρ < 0.7：排队时间大致稳定，扩容收益有限；
- ρ 接近 0.9：同样 10% 的流量增长，排队时间可能翻倍；
- ρ ≥ 1：队列发散，反压成为常态，必须降载或扩容。

P99 比平均值更敏感：平均值可能只涨 20%，P99 已经涨 3 倍。容量规划要按**峰值 + 长尾**设计，而不是按日平均。

Little 定律给出在途数据量：

```text
L = λ × W
```

例如峰值 5 万条/秒、目标端到端 2 秒，系统内平均在途 10 万条。每条 1 KB，就是 100 MB 的“在途数据”，会分布在 source 缓冲、网络 buffer、状态和 sink 批次里。网络内存/队列容量要和这个量匹配（21.10）。

### 26.12.4 哪些时间不该算进“处理延迟”

- **等待数据到齐**：事件时间窗口等 watermark 是正确性成本，不是算得慢。它应该单独记为“完整性等待”，否则会被误判为性能问题；
- **checkpoint 暂停**：同步阶段/对齐会短暂停止处理，P99 会周期性抖动；非对齐 checkpoint 可以缓解，但会增加状态上传量；
- **sink 事务提交**：Kafka 事务提交、湖表 commit、JDBC 批量提交都是批量的，延迟随批量/间隔变化；
- **下游可见**：写入成功不等于可查询，索引刷新、缓存失效、物化视图刷新都可能额外几秒；
- **冷启动/恢复**：恢复期间从 checkpoint 重建状态、回放 source，不是稳态延迟，应单独设 RTO。

### 26.12.5 度量方法与常见错误

推荐同时埋三个点：

1. source 记录 `event_time` 和 `ingest_time`；
2. sink 记录 `emit_time`（写出前）和 `commit_time`（提交后）；
3. 下游/查询侧记录 `visible_time`。

```text
事件延迟   = visible_time - event_time
处理延迟   = emit_time - ingest_time
完整性等待 = 窗口触发时间 - 窗口结束时间
```

常见错误：

- 用平均值代替 P99；
- 用 Flink `latency` 指标冒充端到端延迟；
- 把 watermark 等待算进算子处理时间；
- 忽略时钟漂移（跨节点比较 `currentTimeMillis`）；
- 只测稳态，不测流量突增、checkpoint、恢复和倾斜；
- 采样率太低，P99 实际只有几十个样本；
- 只优化中位数，长尾仍由少数热点 key 决定。

### 26.12.6 优化顺序

1. **先砍完整性等待**：能否缩小乱序容忍/窗口，或用 CUMULATE/增量输出？注意窗口 TVF 不支持 legacy group window 的 early-fire，别把不生效的配置当优化手段。
2. **再砍 sink 提交**：批量、并发、事务超时、下游限流；
3. **处理倾斜**：热点 key 会把 P99 拉长，平均看不出来；
4. **降利用率**：扩容或减少 shuffle/状态访问；
5. **调 buffer/网络**：只有在确认是缓冲不足时才调；
6. **最后调 JVM/GC**：先看火焰图和 GC 日志，不要盲调参数。

延迟预算要写进 SLO 文档，并在每次架构变更后重新测量。没有分阶段预算的“5 秒 SLO”，最终只会变成“加机器”的同义词。

## 26.13 商业视角

从商业看，流平台的成本不只是云账单，还包括：

- 数据延迟带来的业务损失；
- 故障导致的收入损失；
- 工程师维护时间；
- 合规/审计成本；
- 迁移/锁定成本。

一个“便宜”的方案如果经常故障、难以扩展，总成本可能更高。第 39～41 章会从市场、ROI、行业与组织角度继续讨论。

## 本章小结

容量规划 = SLO + 吞吐 + 状态 + 网络 + 故障余量。成本优化要在不破坏 SLO 的前提下进行。流作业的最大隐形成本是状态和恢复时间，早期设计就要控制。
