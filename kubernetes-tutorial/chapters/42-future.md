# 第 42 章 云原生未来方向

## 42.1 如何判断“未来”

云原生领域每年都有新项目。判断一个方向是否值得投入，可以问：

1. 它解决的是真实痛点，还是“技术很酷”？
2. 是否进入 CNCF 毕业/孵化，或有主要云厂商支持？
3. 是否有生产案例和清晰的运维模型？
4. 是否增加不可逆的锁定？
5. 团队是否有能力维护？

本章不是“预测名单”，而是一张技术地图。它**不重复**前面章节的机制细节：Gateway API 的资源模型见第 14 章，eBPF 数据面见第 15 章，DRA/GPU 见第 22 章，多集群见第 33 章。这里只回答“是否采用、何时采用、用什么证据判断”。

## 42.2 Gateway API

Ingress 的局限催生 Gateway API：

- 角色分离：GatewayClass/Gateway/Route。
- 类型化路由（HTTPRoute/GRPCRoute/TLSRoute/TCPRoute）。
- 跨 namespace 授权（ReferenceGrant）。
- 可扩展 Policy Attachment。

未来：

- 更多 Ingress 功能迁移到 Gateway API。
- 服务网格与 Gateway API 融合（GAMMA）。
- 云厂商 LB 控制器原生支持。

实施建议：

- 新项目优先评估 Gateway API。
- 保留 Ingress 兼容路径。
- 关注控制器实现差异，不要假设完全可移植。

## 42.3 eBPF

eBPF 已经从“观测工具”进入数据面：

- Cilium 的 Service/NetworkPolicy/可观测性。
- Tetragon 的运行时安全。
- Pixie 的自动追踪。
- 负载均衡、DDoS 防护。

趋势：

- 更多 CNI 用 eBPF 替代 iptables。
- 内核版本要求逐步降低。
- 与 Wasm 结合（eBPF + Wasm 插件）。

风险：

- 内核兼容性。
- 调试门槛。
- 云环境限制。
- 团队能力。

## 42.4 Wasm

机制与运行形态见第 41.4 节，这里只给采用判断。Wasm 有两类完全不同的用法：作为**工作负载运行时**（runwasi/SpinKube/wasmCloud）和作为**插件沙箱**（Envoy/Istio、Cilium、OPA）。后者的生产成熟度明显更高，前者仍集中在边缘/轻量函数。

| 采用信号 | 最低证据 | 建议阶段 | 退出成本 |
|---|---|---|---|
| 插件/过滤器 | 宿主已支持 Wasm，插件接口稳定 | 生产可用（按宿主项目） | 低：回退到原生插件 |
| 边缘轻量函数 | 冷启动/内存是硬约束；有可观测与调试方案 | 试点 | 中：函数需可移植 |
| 通用工作负载替代容器 | 系统调用/网络/存储能力满足；工具链与排障成熟 | 实验室 | 高：重写与运行时绑定 |

采用前问：你的问题真的是“启动太慢/体积太大”，还是“镜像/依赖/发布流程没治理好”？后者用容器优化更便宜。

## 42.5 动态资源分配（DRA）

GPU/FPGA/NIC 等设备管理：

- Device Plugin 的扩展资源模型不够灵活。
- DRA 支持设备属性、选择器、共享、拓扑。
- 与调度器集成，支持细粒度分配。
- **1.34 达到 GA**（`resource.k8s.io/v1`），1.35 起默认启用；1.37 把设备污点/容忍带到 GA，并推进可分区设备、可消费容量和组请求共享。

趋势：

- AI 工作负载推动 DRA 成熟。
- GPU Operator/厂商驱动支持。
- 与 Kueue/Volcano/gang scheduling 集成。
- Device Plugin 与 DRA 会长期并存，迁移要按驱动和运行时矩阵推进。

机制、对象模型和升级验收见[附录 R](../appendices/R-version-evolution-1.32-1.37.md) R.4.3。

## 42.6 AI/ML 工作负载

Kubernetes 已成为 AI 基础设施的事实平台：

- 训练：PyTorchJob、RayJob、JobSet、Kubeflow。
- 推理：KServe、Ray Serve、vLLM、Triton。
- 调度：GPU 拓扑、gang scheduling、队列（Kueue/Volcano）。
- 存储：高性能并行文件系统、对象存储、本地 NVMe。
- 网络：RDMA/InfiniBand、GPUDirect。
- 可观测：GPU 利用率/显存/温度/ECC。

趋势：

- DRA + 拓扑感知调度。
- 推理的弹性/冷启动优化。
- 多集群/多云 GPU 池化。
- 模型/数据供应链安全。

挑战：

- GPU 昂贵，利用率低。
- 训练故障恢复（checkpoint）。
- 推理 SLA/成本。
- 多租户隔离。

本章只给方向；GPU 调度、DRA、推理服务的工程细节见第 22 章。

## 42.7 边缘计算

边缘的机制、发行版与 KubeEdge/OpenYurt/Akri 的差异见第 41.5 节。采用判断的核心不是“选哪个发行版”，而是四个约束：

| 约束 | 要验证什么 | 不满足的后果 |
|---|---|---|
| 断网自治 | 中心不可达时本地控制面/工作负载能否继续 | 站点停摆 |
| OTA 与回滚 | 分批升级、A/B 分区、失败自动回退 | 变砖，需要现场维修 |
| 镜像/模型分发 | 区域缓存、P2P、增量传输、带宽预算 | 升级窗口不可控 |
| 设备身份与远程运维 | 证书轮换、最小权限、远程取证 | 大规模安全事件 |

边缘项目最常见的失败不是 Kubernetes 本身，而是“把云端配置原样搬过去”：资源请求、探针、日志采集、升级策略都不适配窄带/小内存。先做 2–3 个站点的离线演练，再规模化。

## 42.8 多集群与集群 API

- Cluster API：声明式管理集群生命周期。
- Karmada：多集群调度/联邦。
- Argo CD/Flux：多集群 GitOps。
- vCluster/Kamaji：虚拟集群。

趋势：

- 多集群成为默认，而不是例外。
- 跨集群服务发现/策略/可观测。
- 数据主权/合规驱动区域集群。

多集群的架构与落地见第 33 章。

## 42.9 Serverless 与虚拟集群

Knative/KEDA/vCluster/Fargate 的机制见第 41.6 节。采用判断看“谁承担冷启动和隔离成本”：

| 形态 | 省掉什么 | 新增什么 | 适用 |
|---|---|---|---|
| Knative/KEDA | 闲置副本与节点 | 冷启动、并发模型、事件源运维 | 突发/事件驱动、可容忍冷启动 |
| 虚拟节点/Serverless K8s | 节点运维与容量规划 | 单价、运行时限制、网络/存储差异 | 低运维、弹性优先 |
| vCluster/Kamaji | 每租户一个真实控制面的成本 | 虚拟控制面运维、网络/策略穿透 | 多租户、强隔离但共享数据面 |

“开发者不想管节点”不是采用 Serverless 的充分理由；先算清单价、冷启动 SLO 和锁定成本。需要 GPU、特权、特殊内核或稳定低延迟时，Serverless 往往不是答案。成本模型会从“节点”转向“请求/资源”，但平台仍要承担冷启动、隔离和可观测的固定成本。

KubeVirt、Knative、Wasm 与边缘的完整讨论见第 41 章。

## 42.10 安全与供应链

- Sigstore/cosign：签名/透明日志。
- SLSA：构建完整性。
- SBOM：依赖可见性。
- eBPF 运行时安全。
- 机密计算（Confidential Containers）。
- 沙箱运行时（gVisor/Kata）。
- 零信任/服务网格。

趋势：

- 默认安全（secure by default）。
- 策略即代码。
- 供应链攻击防御成为准入标准。

## 42.11 平台工程

平台工程是“把 Kubernetes 的复杂性封装成内部开发者平台”：

- Golden Path：脚手架、CI/CD、可观测、安全默认值。
- Backstage/Port：开发者门户。
- Crossplane：用 K8s API 管理云资源。
- Argo CD/Flux：GitOps。
- 成本/合规/多租户。

趋势：

- 从“给团队一个集群”到“给团队一个平台”。
- 平台即产品（Platform as a Product）。
- 度量开发者体验（DORA/SPACE）。

## 42.12 可持续性与成本

- FinOps：成本可见性、预算、优化。
- Carbon-aware scheduling：按电网碳强度调度。
- 资源利用率：bin-packing、自动伸缩、混部。
- GPU 共享/分时。

趋势：

- 成本成为架构的一等公民。
- 能效/碳排放指标进入平台。

## 42.13 API 与控制器演进

- Server-Side Apply 被更多 GitOps/Operator 工具采用；但 `kubectl apply` 在 v1.31 仍默认客户端 apply，SSA 需显式 `--server-side` 或工具选择。不要把它写成“已经是默认”。
- ValidatingAdmissionPolicy（CEL）替代部分 webhook。
- 结构化 schema/CRD 成熟。
- 控制器运行时（controller-runtime）标准化。
- API Priority and Fairness 普及。

## 42.14 哪些不会变

- 声明式 API + 控制循环。
- etcd/一致性存储的核心地位（或等价物）。
- 容器/镜像生态。
- 网络/存储/安全的物理约束。
- 组织/流程/成本问题。

技术会变，但这些基础问题不会消失。

## 42.15 学习建议

- 先把核心（API/调度/控制器/网络/存储/安全）学扎实。
- 每季度选一个方向做小实验，不要追每个新项目。
- 读 CNCF 毕业项目的设计文档，而不是只看博客。
- 关注生产案例和失败复盘。
- 对“银弹”保持怀疑。

## 42.16 采用路线图：从试验到生产

前沿技术的失败往往不是“方向错了”，而是“跳过了验证阶段”。一个可复用的采用路线：

### 门槛 0：问题是否真实

- 现有方案的具体痛点是什么？能量化吗（延迟、成本、人力、故障率）？
- 不用新技术，能否通过配置/流程解决？
- 谁受益、谁承担运维、谁批准预算？

### 门槛 1：实验室验证

- 在 kind/隔离集群复现目标场景。
- 验证 API 阶段（alpha/beta/stable）、版本要求、feature gate。
- 记录失败模式与回滚路径。

### 门槛 2：预发验证

- 用真实镜像、网络、存储、身份跑一遍。
- 做故障注入：组件重启、节点故障、证书过期、配额耗尽。
- 验证可观测性：指标/日志/追踪能否定位问题。
- 验证升级/降级：版本偏斜、CRD 兼容、数据迁移。

### 门槛 3：受限生产

- 选低风险业务/小流量，定义成功指标与回滚条件。
- 保留旧路径，双跑一段时间。
- 每周复盘：性能、成本、告警、工单、事故。

### 门槛 4：规模化

- 自动化安装/升级/备份/巡检。
- 建立 SLO、on-call、容量模型、成本分摊。
- 写清楚“不适用场景”，避免被当成万能方案。

### 采用评分卡

| 维度 | 要问的问题 | 不合格信号 |
|---|---|---|
| API 稳定性 | 是否 stable/beta？弃用策略？ | 只有 alpha，字段频繁变 |
| 生态 | 是否有多个独立实现/采用者？ | 只有一家供应商 |
| 可运维 | 升级/备份/排障文档？ | 只能重装 |
| 安全 | 威胁模型、CVE 响应、权限模型？ | 默认全权限 |
| 性能 | 在我们的规模下有基准？ | 只有玩具 demo |
| 退出成本 | 数据和配置能否迁移？ | 深度私有 API 锁定 |
| 团队 | 是否有人能值班/贡献？ | 没人看得懂 |

### 常见跳级错误

- 从“看过 demo”直接到“生产全量”。
- 只验证成功路径，不验证失败/回滚。
- 把 beta API 当 stable 用，升级时被迫重写。
- 没有退出方案，锁定后才发现迁移成本。
- 只看技术指标，不算人力/培训/值班成本。

前沿章节的价值不是“预测哪个项目会赢”，而是给你一套判断框架：**在什么条件下、用什么证据、承担多大风险，才把一个新能力放进生产**。

## 42.17 版本演进阅读法：1.31 之后怎么跟

本书以 v1.31 稳定 API 为基线，但生产集群不会停在 1.31。截至 2026-11，受支持的 minor 是 1.35/1.36/1.37，1.34 已于 2026-10-27 EOL。与其背“哪个版本加了什么”，不如建立一套可持续的跟踪方法：

1. **按 API 阶段判断**：alpha 不用于生产；beta 看默认开启与弃用窗口；GA 才作为稳定依赖。
2. **按 KEP 读动机**：每个特性都有 Motivation/Alternatives/Risks；读懂“为什么不是另一种设计”，比记字段更有用。
3. **按 release notes 做升级清单**：每个 minor 的“Deprecations and Removals”先扫一遍。
4. **按自己的对象/控制器做回归**：新版本可能改变默认值、准入行为、调度打分、指标名。
5. **按托管服务支持矩阵裁剪**：云厂商可能禁用某些 feature gate 或 API。

一个实用的季度流程：

```text
第 1 周：读目标版本 release notes + 弃用公告
第 2 周：扫描 Git/集群的弃用 API（pluto/kubent）
第 3 周：在预发升级，跑 conformance + 业务 E2E
第 4 周：更新 runbook/版本台账，安排生产窗口
```

对“新特性是否采用”，用第 42.16 的评分卡；对“旧版本是否还能用”，看支持窗口与 CVE。版本治理不是一次升级，而是持续节奏。详细检查表见附录 I，1.32–1.37 的逐版本特性见附录 R。

## 本章小结

- Gateway API、eBPF、Wasm、DRA、AI 工作负载、边缘、多集群、平台工程是主要方向。
- 每个方向都有真实价值和采用成本，不要盲目追新。
- 核心抽象（声明式/控制循环/一致性）仍然稳定。
- 学习方法是小实验 + 生产案例 + 设计文档。
