# 第 47 章 综合架构案例：六种平台的取舍

前面 46 章分别讲了机制、实现、运维和商业。真实架构从来不是“把所有最佳实践都装上”，而是在约束下做取舍：团队规模、预算、合规、延迟、数据、增长预期。本章用六个案例把技术选择放回上下文。案例中的组织、数字和价格均为示例，用于演示推理，不代表真实客户。

## 47.1 案例一：五人团队的 SaaS

**背景**：一个 B2B SaaS，5 名工程师，3 个服务 + 1 个 Postgres，客户 200 家，流量有明显的日内峰谷。

**约束**：

- 没有专职 SRE/平台团队。
- 预算敏感，但不能接受频繁宕机。
- 团队会写应用，不熟悉控制面运维。
- 未来 12 个月可能增长 5–10 倍。

**架构**：

```text
托管 Kubernetes（单集群，2–3 可用区节点池）
├── ingress controller + cert-manager
├── 3 个无状态服务（HPA 2–10 副本）
├── 托管 Postgres（不放进集群）
├── 对象存储（备份/静态资源）
├── 托管可观测（指标/日志/告警）
└── GitOps（单仓库，Argo CD 或 Flux）
```

**关键决策**：

1. **托管控制面**：省掉 etcd/证书/升级的运维，团队把时间花在业务。
2. **数据库托管**：不自建 Operator；五人团队没有能力承担备份/故障切换。
3. **单集群**：多集群带来的网络/身份/成本复杂度，在这个阶段不值得。
4. **HPA 只用于无状态服务**：基于 CPU/请求数，保留最小副本避免冷启动。
5. **GitOps 从第一天开始**：不是为了“先进”，而是让变更可审计/可回滚。
6. **可观测用托管**：自建 Prometheus/Grafana 的维护成本高于订阅费。

**失效模式**：

- 托管控制面故障：等待厂商，应用多 AZ 部署降低影响。
- 节点池耗尽：Cluster Autoscaler/Karpenter + 配额告警。
- 数据库连接耗尽：PgBouncer/连接池 + 最大连接告警。
- 误删 namespace：RBAC 限制 + GitOps 恢复 + 备份。

**这个阶段不该做的**：

- 自建多集群/服务网格/自研 Operator。
- 为了“云原生”把数据库塞进 StatefulSet。
- 过早上 vCluster/多租户平台。
- 用 10 个工具做可观测，没人看告警。

**成功指标**：部署频率、变更失败率、MTTR、月度云账单/每客户成本。

## 47.2 案例二：企业多租户平台

**背景**：一家 2000 人的企业，20 个业务团队，100+ 服务，3 个云/区域，合规要求中等。

**约束**：

- 团队自治 vs 中央治理的冲突。
- 需要隔离（网络/配额/权限），但不能给每个团队一个集群。
- 需要统一审计、成本分摊、镜像/策略。
- 已有 VMware/VM 体系，迁移是渐进的。

**架构**：

```text
管理集群（Cluster API + GitOps + 策略）
├── 业务集群 A/B/C（按区域/环境）
│   ├── namespace-as-a-tenant（RBAC/Quota/NetworkPolicy/PSA）
│   ├── 共享 Ingress/Gateway（ReferenceGrant 隔离）
│   ├── 节点池（general / memory / GPU / spot）
│   └── 平台组件（DNS/CSI/CNI/可观测/策略）
├── 镜像仓库 + 签名/扫描
├── 中央可观测/日志/审计
└── 成本分摊（labels/namespaces/showback）
```

**关键决策**：

1. **集群边界按故障域/合规域划分**，不是按团队划分；团队用 namespace。
2. **默认拒绝**：NetworkPolicy、PSA `restricted`（有例外审批）、RBAC 最小权限。
3. **Gateway API + ReferenceGrant**：应用团队管 Route，平台管 Gateway。
4. **策略即代码**：VAP/Kyverno 做准入，OPA 做更复杂策略；策略有测试与灰度。
5. **成本标签强制**：没有 cost-center/owner 标签的工作负载拒绝或告警。
6. **平台团队做“产品”**：Golden Path、模板、文档、SLO，而不是工单队列。

**失效模式**：

- 租户通过 hostPath/privileged 逃逸：PSA + 准入 + 节点池隔离。
- 共享 Ingress 路由冲突：ReferenceGrant + allowedRoutes + 命名规范。
- 配额被单个团队占满：ResourceQuota + PriorityClass + 队列。
- 策略误杀生产：先在 audit 模式跑，再 enforce。
- 成本不可见：标签治理 + showback 从第一天做。

**这个阶段不该做的**：

- 给每个团队一个集群（控制面/网络/升级成本爆炸）。
- 只靠 namespace 做“硬隔离”。
- 让应用团队直接改集群级 RBAC/CRD/webhook。
- 没有退出/迁移方案就绑定某个平台产品。

**成功指标**：租户上线时间、越权测试通过率、策略拒绝率、单位服务成本、平台团队工单量。

## 47.3 案例三：AI 训练与推理平台

**背景**：一家 AI 公司，80 张 GPU（A100/H100 混合），训练任务从小规模微调到多机多卡，推理服务对 TTFT/ITL 敏感。

**约束**：

- GPU 昂贵，利用率是生命线。
- 训练任务 gang scheduling、拓扑、RDMA、checkpoint。
- 推理需要低延迟、弹性、按 token 成本核算。
- 研究团队与工程团队共享集群。

**架构**：

```text
GPU 集群
├── 节点池：A100 / H100 / 推理卡（taint + label）
├── GPU Operator（驱动/device plugin/DCGM）
├── Kueue（队列/配额/借用/抢占）+ Volcano/JobSet（gang）
├── 训练：PyTorchJob/RayJob + 本地 NVMe + 并行文件系统
├── 推理：vLLM/KServe + Gateway + 队列/延迟 HPA
├── 存储：对象存储（数据/checkpoint）+ 高速缓存
└── 可观测：GPU 利用率/显存/Xid/IB/NCCL/队列等待
```

**关键决策**：

1. **训练与推理分池**：避免长训练阻塞在线推理；用 taint/label 隔离。
2. **队列先于调度器**：Kueue 管配额/借用，Volcano/JobSet 管 gang；不要让几千个 Pending Pod 压垮调度器。
3. **拓扑感知**：同机 NVLink、同机架/同交换机；DRA/device plugin 表达设备属性。
4. **checkpoint 到持久存储**：训练中断可恢复；本地盘只做缓存。
5. **推理按队列/延迟扩缩**：CPU HPA 无效；用 KEDA/自定义指标。
6. **成本按团队/作业分摊**：GPU 小时、利用率、排队时间、每 token 成本。

**失效模式**：

- GPU 碎片：大作业永远等不到整机；预留/碎片整理/队列策略。
- 训练任务占满 GPU 但不工作：gang 未满足、数据加载瓶颈、NCCL 配置。
- 推理 OOM：KV cache 打满；限并发/加副本/PD 分离。
- 节点 GPU 掉卡：Xid/ECC；自动隔离/替换。
- 队列饥饿：配额/优先级/借用策略不合理。

**这个阶段不该做的**：

- 用普通 HPA 扩 GPU 推理。
- 把训练和在线服务混在同一节点池。
- 没有 checkpoint/重试就跑长作业。
- 只看 GPU 利用率，不看有效吞吐/排队时间。

**成功指标**：GPU 利用率、作业等待时间、训练中断恢复时间、推理 TTFT/ITL、每百万 token 成本。

## 47.4 案例四：金融/合规平台

**背景**：一家金融机构，核心交易系统上云，受强监管，要求审计、隔离、灾备、变更审批。

**约束**：

- 多 AZ/同城双活/异地灾备。
- 审计日志长期保留、防篡改。
- 生产变更需要审批/双人复核。
- 不能使用共享控制面/多租户混部核心系统。

**架构**：

```text
生产集群（专用控制面，多 AZ）
├── 控制面 3/5 节点，etcd 专用 SSD，跨 AZ
├── 节点池：核心交易/一般业务/批处理（taint 隔离）
├── 网络：VPC-native CNI，NetworkPolicy 默认拒绝，出口网关
├── 安全：OIDC+MFA、RBAC、PSA restricted、镜像签名、VAP
├── 审计：API 审计 + 容器日志 + 云审计 → SIEM（WORM）
├── 备份：etcd 快照 + Velero + 应用级备份，异地副本
└── 灾备：同城双活 + 异地冷备，定期切换演练
```

**关键决策**：

1. **专用集群/节点池**：核心系统不与一般业务混部。
2. **变更管控**：GitOps + PR 审批 + 策略检查 + 灰度；紧急变更走 break-glass 并审计。
3. **审计不可抵赖**：API 审计覆盖写操作/Secret/exec/RBAC；日志集中、只追加、长期保留。
4. **加密**：etcd 静态加密 + KMS、传输 TLS、备份加密。
5. **灾备以演练为准**：RTO/RPO 用实际切换验证，不靠文档。
6. **供应链**：镜像签名/SBOM/漏洞扫描/准入，构建环境隔离。

**失效模式**：

- 审计日志只存本地：节点故障/攻击者删除后无法取证。
- 灾备集群配置漂移：切换时才发现缺 Secret/CRD/策略。
- 证书/密钥过期：大面积不可用；监控到期时间。
- 变更绕过 GitOps：紧急操作没有记录；用 break-glass 流程补审计。
- 多 AZ 存储拓扑不匹配：Pod 调度到无卷的 AZ。

**这个阶段不该做的**：

- 用共享多租户集群跑核心交易。
- 只做备份不做恢复演练。
- 把合规当“审计前突击”。
- 为了省成本关闭审计/多 AZ。

**成功指标**：RTO/RPO 实测、审计覆盖率、变更失败率、越权测试、灾备切换成功率。

## 47.5 案例五：边缘/IoT 平台

**背景**：一家制造企业，500 个工厂/门店节点，网络不稳定，需要本地推理/数据采集，中央统一管理。

**约束**：

- 边缘节点资源小（2–8 核）、网络间歇、无人值守。
- 需要离线运行、断点续传、OTA 升级、回滚。
- 中央需要看到边缘状态，但不能依赖实时连接。

**架构**：

```text
中心集群
├── GitOps/配置分发（按站点/设备组）
├── 镜像/模型仓库（区域缓存）
├── 设备管理/证书/身份
└── 可观测（边缘聚合上报）
边缘节点
├── K3s/MicroK8s（单节点/小集群）
├── 本地存储（SQLite/本地 PV）
├── 本地推理/采集工作负载
├── 离线队列/缓存
└── 自动更新/回滚（systemd/OTA）
```

**关键决策**：

1. **轻量发行版**：K3s 单二进制、SQLite/嵌入式 etcd，资源占用低。
2. **离线优先**：应用能本地缓存/排队；不要假设中心 API 永远可达。
3. **声明式配置 + 最终一致**：边缘恢复连接后收敛，不要求实时。
4. **OTA 分批/可回滚**：按站点灰度，失败自动回退；保留旧版本。
5. **安全**：设备身份/证书、磁盘加密、最小权限；边缘节点物理安全弱。
6. **可观测**：本地缓冲 + 聚合上报，避免网络抖动丢数据。

**失效模式**：

- 中心不可达导致边缘无法启动：本地缓存/离线模式。
- 升级失败变砖：A/B 分区/回滚。
- 证书过期：批量离线；提前轮换/长有效期策略。
- 存储写满：本地数据保留策略/清理。
- 设备被物理攻破：磁盘加密/安全启动/远程擦除。

**这个阶段不该做的**：

- 在边缘跑完整多控制面 HA。
- 依赖中心实时 API 做关键决策。
- 一次性全量升级所有站点。
- 忽略边缘的资源/网络约束，直接搬云端配置。

**成功指标**：边缘在线率、离线恢复时间、升级成功率、站点故障自愈率、带宽成本。

## 47.6 案例六：成本受限的迁移

**背景**：一家传统企业，VM 上有 200 个应用，计划迁到 Kubernetes，预算有限，团队刚开始学。

**约束**：

- 应用多为单体/有状态，改造能力有限。
- 不能一次性停机迁移。
- 需要证明成本/稳定性不比 VM 差。

**架构**：

```text
阶段 1：小规模托管集群 + 无状态应用
阶段 2：批处理/定时任务 + 内部工具
阶段 3：有状态服务（Operator/托管数据库）
阶段 4：核心应用（最后）
```

**关键决策**：

1. **先迁“可回滚”的应用**：无状态、流量可切、失败影响小。
2. **不强迫全部容器化**：VM 与 K8s 并存，按价值迁移。
3. **托管数据库**：不要为了“统一”把核心数据库塞进集群。
4. **成本对照**：VM 账单 vs 集群账单 + 人力 + 工具；用实际利用率，不用理论值。
5. **平台最小化**：先 DNS/Ingress/日志/监控/备份，不要一上来装 20 个组件。
6. **培训/值班**：团队要能处理 Pod Pending、镜像拉取、DNS、存储挂载。

**失效模式**：

- 迁移后成本更高：节点利用率低、过度预留、工具订阅叠加。
- 应用未改造：本地盘/固定 IP/会话粘滞导致频繁故障。
- 团队不会排障：一有问题就回滚，迁移停滞。
- 平台组件太多：每个都是故障点/升级负担。

**这个阶段不该做的**：

- 为了“云原生”重写所有应用。
- 没有基线就承诺 ROI。
- 一次性迁移核心交易。
- 把 VM 的运维习惯直接搬到 K8s（例如长期不升级）。

**成功指标**：迁移应用数、回滚率、单位应用成本、故障恢复时间、团队独立排障率。

## 47.7 六种案例的对照

| 维度 | 五人 SaaS | 企业多租户 | AI 平台 | 金融合规 | 边缘 | 成本迁移 |
|---|---|---|---|---|---|---|
| 集群数 | 1 | 3–10 | 1–3 | 2+（生产/灾备） | 数百边缘 | 1–2 |
| 控制面 | 托管 | 托管/CAPI | 托管/自建 | 专用/自建 | K3s | 托管 |
| 多租户 | 弱 | 强 | 中（队列） | 强（专用） | 弱 | 弱 |
| 网络 | 简单 Ingress | Gateway + 策略 | 高速 RDMA | 分段/出口网关 | 离线/窄带 | 简单 |
| 存储 | 托管 DB/对象 | CSI + 备份 | 并行文件系统/本地 NVMe | 多 AZ + 灾备 | 本地盘 | 托管/CSI |
| 安全 | 基础 RBAC/PSA | 策略即代码 | 供应链/租户隔离 | 审计/加密/合规 | 设备身份 | 基础 |
| 成本重点 | 人力/托管费 | 分摊/利用率 | GPU 利用率 | 合规/灾备 | 带宽/运维 | VM 对照 |
| 主要风险 | 无人运维 | 隔离/治理 | 碎片/排队 | 审计/切换 | 离线/变砖 | 改造成本 |

## 47.8 架构评审清单

无论哪种案例，评审时问同样的问题：

1. **故障域**：控制面/节点/区域/依赖故障时，业务如何降级？
2. **数据**：RPO/RTO 是多少？备份/恢复演练过吗？
3. **隔离**：谁能看/改/删什么？越权测试做过吗？
4. **变更**：如何发布/回滚？谁批准？有审计吗？
5. **容量**：瓶颈在哪？扩容需要多久？有缓冲吗？
6. **成本**：单位成本是什么？谁负责？有优化杠杆吗？
7. **可观测**：出故障时，5 分钟内能定位到哪一层？
8. **退出**：如果平台/厂商不可用，如何迁移/降级？
9. **团队**：谁值班？谁有能力改平台？培训/文档够吗？
10. **演进**：6/12/24 个月后，这个架构的下一步是什么？

## 47.9 跨案例反模式

- **抄大厂架构**：没有对应的团队/规模/预算，复杂度只会压垮自己。
- **一次到位**：试图第一天就多集群/多租户/服务网格/零信任。
- **只建平台不做产品**：开发者不用，平台就没有价值。
- **只算资源单价**：忽略人力、工具、迁移、事故成本。
- **没有退出方案**：锁定后才发现迁移成本。
- **把合规/安全当项目**：做完就忘，没有持续证据。
- **用技术指标代替业务指标**：Pod 数量/集群数不等于交付能力。

## 47.10 从案例到你的架构

一个可执行的推导顺序：

```text
业务目标/SLO
  → 团队能力/预算/合规约束
  → 故障域与数据 RPO/RTO
  → 集群/租户/网络/存储形态
  → 平台组件最小集
  → 运维/安全/成本治理
  → 演进路线与退出方案
```

不要从“装什么”开始，从“约束是什么”开始。Kubernetes 的组件很多，但真正决定架构的是少数几个问题：隔离边界、故障域、数据一致性、团队能力、成本模型。

用法：先读案例建立取舍，再按表进入附录；不要从头到尾背附录。

## 本章小结

- 架构是约束下的取舍，不是最佳实践清单的堆叠。
- 五人团队、企业平台、AI、金融、边缘、成本迁移的答案完全不同。
- 共同底线：故障域、数据恢复、隔离、变更、容量、成本、可观测、退出。
- 先用业务/SLO/约束推导，再选组件；不要从工具反推架构。
- 每个阶段都要有“不该做什么”，否则复杂度会失控。
