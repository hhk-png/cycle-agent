# 第 46 章 商业分析 IV：企业 TCO、选型与落地路线图

> 前三章分别讨论市场格局、托管经济学和平台/开源/创业。本章把商业分析落到一个企业决策上：**自建还是托管？选哪家？怎么算总成本？怎么落地？** 文中的价格与人力数字均为示例假设，用于演示方法，不代表任何厂商报价；实际决策应以合同、账单和实测为准。

## 46.1 从技术选型到商业案例

技术选型常见失败不是“选错了产品”，而是**没有定义要解决的问题**：

- 是要降低运维人力，还是提高发布速度？
- 是要满足合规，还是支持 AI 训练？
- 是要从单集群走向多集群，还是从 VM 迁移到容器？
- 是要降低云成本，还是避免厂商锁定？

一个可执行的商业案例至少包含：

```text
现状基线 → 目标状态 → 方案选项 → 成本/收益 → 风险 → 决策与验收
```

没有基线的 ROI 都是故事。基线要量化：

- 当前集群数、节点数、CPU/内存/GPU 利用率。
- 当前运维人力、工单量、发布频率、变更失败率。
- 当前云账单：计算、存储、网络、可观测、安全。
- 当前事故：次数、MTTR、业务损失。
- 当前合规缺口与审计发现。

## 46.2 TCO 的构成

TCO 不是“节点单价 × 数量”。完整口径：

```text
TCO = 基础设施
    + 软件许可/订阅
    + 人力
    + 迁移/培训
    + 工具与集成
    + 网络/出口
    + 灾备/备份
    + 安全/合规
    + 事故/停机
    + 机会成本
```

逐项说明：

### 基础设施

- 计算：节点、控制面、GPU、Spot/预留/按需。
- 存储：块、对象、文件、快照、备份。
- 网络：LB、NAT、跨 AZ/跨地域、出口。
- 空闲/冗余：HA、N+1、灾备集群。

### 软件与支持

- 托管控制面费用。
- 企业版订阅、支持合同。
- 可观测/安全/策略/GitOps 的商业版。
- 镜像仓库、制品库、CI/CD。

### 人力

- 平台工程师、SRE、安全工程师。
- 值班/on-call。
- 培训与认证。
- 招聘/外包成本。

人力通常是被低估的最大项，但“需要多少人”必须和集群规模、自动化程度、合规要求一起估。用一个按 estate 分档的表（假设值，用于演示数量级）代替单一数字：

| Estate | 集群/节点 | 平台团队规模 | 说明 |
|---|---|---|---|
| 小型 | 1–3 集群 / 30 节点 | 3–5 FTE | 托管控制面、少量自建组件、无 7×24 专职 |
| 中型 | 5–10 集群 / 300 节点 | 10–15 FTE | 多租户、GitOps、可观测、安全、值班 |
| 大型 | 多区域 / 1,000+ 节点 | 25–40 FTE | 自建/混合控制面、合规、灾备、平台产品化 |

按 $15k/人/月计算，小型 4 FTE ≈ $60k/月（$720k/年），中型 12 FTE ≈ $180k/月（$2.16M/年）。**人力不是按节点线性增长**：自动化、托管服务、团队成熟度会显著改变曲线；反过来，合规/多集群/自建控制面会让同样节点数需要更多人。实际数字取决于地区、资历和外包比例，但方向性结论成立：先按 estate 定义团队，再算节点；不要用“30 人团队”去套 30 个节点。

### 迁移与组织

- 应用改造、容器化、CI/CD 重建。
- 双轨运行（旧新系统并行）。
- 文档、培训、变更管理。
- 生产力下降（学习曲线、迁移窗口）。

### 隐性成本

- 多集群的重复建设。
- 版本升级/兼容性测试。
- 安全事件响应。
- 供应商锁定后的议价能力下降。
- 自建组件的维护（Operator、CRD、监控栈）。

## 46.3 一个 worked example（假设）

> 本节算的是**稳态月度运行成本（run-rate）**，不含迁移、培训、双轨运行、事故损失和机会成本。3 年 TCO 应把 46.2 中的一次性与隐性成本摊销进来，不能直接把本节数字乘以 36。

假设一家公司有 3 个环境（dev/staging/prod），共 30 个等效工作节点，每节点 16 vCPU/64GiB，平均利用率 45%。当前在 VM 上自建 Kubernetes。这属于 46.2 表中的“小型 estate”，因此下面用 4 FTE 作为基线；如果规模换成 300 节点/10 集群，人力要按 10–15 FTE 重算，节点成本也要同步放大。

示例单价（仅为演示）：

| 项目 | 假设单价 |
|---|---|
| 工作节点（按需） | $0.40/小时 ≈ $292/月 |
| 控制面节点（较小） | $0.27/小时 ≈ $197/月 |
| 托管控制面 | $0.10/小时 ≈ $73/月/集群 |
| 块存储 | $0.08/GB/月 |
| 对象存储 | $0.023/GB/月 |
| 出口流量 | $0.09/GB |
| 平台工程师（全成本） | $15,000/人/月 |
| 可观测 SaaS | $30/节点/月 |
| 安全 SaaS | $25/节点/月 |

### 方案 A：自建

- 工作节点：30 × $292 = **$8,760/月**
- 控制面：3 集群 × 3 节点 × $197 = **$1,773/月**
- etcd 磁盘/快照：**$300/月**
- 存储：20TB × $0.08 × 1024 ≈ **$1,638/月**
- 出口：10TB × $0.09 × 1024 ≈ **$922/月**
- 可观测：自建基础设施 + 人力，假设 **$1,200/月**
- 安全：$25 × 30 = **$750/月**
- 平台人力：4 FTE × $15,000 = **$60,000/月**

合计 ≈ **$75,343/月**（约 $904k/年）。

### 方案 B：托管控制面

- 工作节点：**$8,760/月**
- 托管控制面：3 × $73 = **$219/月**
- 存储/出口：同上 **$2,560/月**
- 可观测 SaaS：$30 × 30 = **$900/月**
- 安全：**$750/月**
- 平台人力：3 FTE × $15,000 = **$45,000/月**（少一台控制面运维，但仍需平台团队）

合计 ≈ **$58,189/月**（约 $698k/年）。

差额约 **$17k/月**，主要来自控制面节点和 1 个 FTE。若自建需要 5 个 FTE，差额会扩大到 $32k/月；若自建只需 3 个 FTE，差额缩小到约 **$2.2k/月**。

按本节假设做盈亏平衡：非人力成本自建约 $15.3k/月、托管约 $13.2k/月，人力 $15k/FTE/月，则

```text
15,343 + 15,000 × F = 58,189  →  F ≈ 2.86
```

即自建团队低于约 **2.9 个 FTE** 时自建更便宜；高于这个数，托管在示例假设下更经济。这个数字对 FTE 单价、控制面费用和出口费极其敏感，务必用真实报价替换。

### 敏感性

| 变量 | 变化 | 对结论的影响 |
|---|---|---|
| 平台人力 | ±1 FTE（$15k/月） | 最大敏感项 |
| 节点数 | 30 → 100 | 托管控制面费用占比下降，节点成本主导 |
| 利用率 | 45% → 70% | 自建/托管都受益，但自建闲置浪费更大 |
| 出口流量 | 10TB → 50TB | 托管可能更贵，需看厂商定价 |
| GPU | 加入 8 卡节点 | GPU 成本压倒控制面差异 |
| 事故 | 每年 2 次 4 小时故障 | 业务损失可能超过全年差价 |

结论不是“托管一定更便宜”，而是：**在示例假设下，托管省下的控制面运维人力超过了控制面费用；但若规模很大、利用率很高、团队能力强，自建可能更经济。**

## 46.4 多集群与 GPU 的 TCO

### 多集群

成本不只是“多几个控制面”：

- 每个集群的监控/日志/安全 agent。
- 跨集群网络/出口。
- 重复的镜像/备份/灾备。
- 运维人力按集群数增长（除非高度自动化）。
- 闲置容量：每个集群都要留 HA 余量。

一个粗略模型：

```text
多集群 TCO ≈ Σ(每集群固定成本 + 节点成本 × 利用率冗余)
            + 跨集群网络
            + 平台人力 × f(集群数)
```

`f(集群数)` 如果接近线性，说明自动化不足；目标是次线性（一套平台管 N 个集群）。

### GPU

GPU 的 TCO 与 CPU 不同：

- 卡贵、节点贵、网络贵（RDMA）。
- 闲置成本极高，利用率比单价更重要。
- 共享（MIG/time-slicing）能提高利用率，但增加隔离/干扰风险。
- 训练任务的存储/网络成本可能超过 GPU 本身。
- 推理的冷启动/副本冗余会拉低有效利用率。

GPU TCO 要看**有效吞吐/成本**，而不是“每卡小时价格”：

```text
每 token 成本 = (GPU 成本 + 节点 + 网络 + 存储 + 人力) / 有效 token 数
```

如果模型利用率只有 20%，再便宜的卡也不便宜。

## 46.5 选型评分卡

不要用“功能清单”选型。用加权评分卡，把假设摆到桌面上：

| 维度 | 权重 | 评估问题 |
|---|---|---|
| 安全与合规 | 20% | 认证、隔离、审计、密钥、数据驻留 |
| 总成本 | 20% | 3 年 TCO、出口费、支持费、隐藏成本 |
| 运维负担 | 15% | 升级、监控、备份、故障恢复 |
| 生态与兼容 | 15% | CNI/CSI、Operator、GitOps、可观测 |
| 锁定与可移植 | 10% | API 兼容、数据导出、迁移成本 |
| 支持与服务 | 10% | SLA、响应、专业服务、社区 |
| 路线图 | 5% | 版本节奏、GPU/AI、多集群 |
| 组织匹配 | 5% | 团队技能、采购流程、供应商关系 |

评分 1–5，加权求和。关键不是分数，而是：

- 权重是否反映真实优先级。
- 低分项是否有缓解措施。
- 供应商的答案是否有证据（POC、案例、合同条款）。

## 46.6 迁移成本与组织变革

迁移到 Kubernetes/新平台不是“把 YAML 搬过去”。成本包括：

- **应用改造**：无状态化、配置外置、健康检查、优雅终止、日志/指标。
- **CI/CD 重建**：镜像构建、签名、制品库、GitOps。
- **网络/存储**：Ingress/Gateway、证书、DNS、CSI、备份。
- **安全**：RBAC、准入、镜像扫描、运行时检测。
- **组织**：平台团队、on-call、培训、职责边界。
- **双轨运行**：旧新系统并行期间的重复成本。

迁移策略：

1. **先易后难**：无状态、低风险服务先行。
2. **Strangler**：逐步替换，不一次性大爆炸。
3. **Wave 规划**：按依赖/风险分批。
4. **回滚预案**：每批都可回退。
5. **度量**：迁移速度、事故率、成本变化。

组织变革往往比技术更难：平台团队要从“运维执行者”变成“产品团队”，应用团队要承担更多运行时责任（You build it, you run it）。

## 46.7 合同与议价

托管/企业软件的合同条款会显著影响 TCO：

- **SLA**：控制面可用性、数据面、赔偿方式；注意 exclusions。
- **支持**：响应时间、渠道、是否含架构评审/故障复盘。
- **价格调整**：续约涨幅、汇率、通胀条款。
- **承诺消费**：预留/承诺折扣与灵活性。
- **出口费**：跨 AZ/跨地域/公网流量。
- **数据可移植**：导出格式、迁移协助、退出条款。
- **锁定**：专有 API、托管服务、IAM、网络。
- **合规**：审计报告、数据处理协议、区域选项。

议价杠杆：

- 多供应商竞标/POC。
- 承诺消费换折扣。
- 长期合同换价格保护。
- 混合云/多云架构降低单一依赖。
- 开源替代方案作为“可信的退出选项”。

## 46.8 落地路线图

### 0–90 天：基线与试点

- 盘点应用/依赖/流量/合规要求。
- 建立成本基线（按团队/服务/环境）。
- 选定 1–2 个试点服务（无状态、低风险、有明确收益）。
- 搭建 landing zone：网络、身份、日志、监控、镜像仓库、GitOps。
- 定义 Golden Path：脚手架、CI、部署、回滚、可观测。
- 设定验收指标：发布频率、Lead time、事故率、成本。

### 3–6 个月：平台化

- 多团队接入，自助服务。
- 策略即代码：PSS、RBAC、配额、镜像签名。
- 可观测/告警/SLO 标准化。
- 成本分摊/配额/预算。
- 灾备/备份演练。
- 培训与社区（内部文档、office hours）。

### 6–12 个月：规模化

- 多集群/多区域。
- GPU/AI 工作负载。
- 渐进式交付/自动化回滚。
- FinOps 持续优化。
- 平台 ROI 复盘：人力、成本、交付、可靠性。
- 决定下一步：自建/托管/混合。

## 46.9 常见失败模式

- **Lift-and-shift**：把 VM 上的单体原样搬进容器，收益低、复杂度高。
- **平台团队成为瓶颈**：所有变更都要平台团队审批/操作。
- **成本不可见**：没有标签/分摊，月底才发现账单爆炸。
- **过度定制**：为每个团队做一套平台，维护成本失控。
- **没有 SLO**：不知道“好”是什么，无法衡量平台价值。
- **安全事后补**：上线后才加准入/隔离，迁移成本高。
- **供应商锁定**：用了大量专有服务，退出成本极高。
- **组织不匹配**：平台团队没有产品/支持能力，应用团队不承担责任。

## 46.10 度量与持续优化

平台/云原生的度量分四层：

1. **交付**：发布频率、Lead time、变更失败率、MTTR（DORA）。
2. **可靠性**：SLO 达成率、事故数、MTTR、容量余量。
3. **成本**：每服务/团队/环境成本、利用率、闲置率、单位成本（每请求/每 token）。
4. **采用**：平台使用率、自助率、工单量、开发者满意度。

优化顺序：

```text
可见性 → 归因 → 配额/预算 → 架构优化 → 采购优化
```

没有可见性就开始砍成本，通常会砍错地方。

## 本章小结

- TCO 要覆盖基础设施、软件、人力、迁移、工具、网络、灾备、安全、事故和机会成本。
- 人力通常是被低估的最大项；托管与自建的差异往往在人力而非控制面单价。
- 多集群和 GPU 的成本结构不同，要看单位有效产出，而不是单价。
- 选型用加权评分卡，权重反映真实优先级，低分项要有缓解措施。
- 落地从基线和试点开始，平台化、规模化分阶段推进；组织变革与技术同样重要。
