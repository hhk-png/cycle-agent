# 第 1 章 为什么需要 Kubernetes

## 1.1 从“把进程跑起来”到“让系统保持形状”

单机时代，部署一个服务大致是：

```bash
scp app.tar.gz server:/opt/app/
ssh server "systemctl restart app"
```

机器少、进程少、故障靠人盯，这套方法可以工作。容器把“进程 + 依赖 + 文件系统”打包成镜像后，交付单位变小了，但新的问题立刻出现：

- 镜像放到哪台机器？机器挂了谁重新拉起？
- 服务要 10 个副本，如何保证任何时刻都不多不少？
- 新版本发布时，如何在不中断流量的情况下替换实例？
- 一个实例怎么找到另一个实例？IP 变了怎么办？
- 100 台机器上分别跑什么？资源如何分配？
- 谁有权限删除生产命名空间？
- 出故障时，如何知道是调度失败、镜像拉取失败，还是应用没通过健康检查？

这些问题的共同点是：**它们不是“启动一个进程”的问题，而是“让一组进程持续满足某个形状”的问题**。Kubernetes 的价值不是“容器编排”四个字，而是把运维意图编码成 API 对象，再用控制循环不断把现实拉回意图。

## 1.2 声明式：从命令到期望状态

命令式运维描述“怎么做”：

```text
创建 3 个容器
如果挂了，重启第 1 个
把第 2 个从负载均衡摘掉
```

声明式运维描述“要什么”：

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3
  selector:
    matchLabels: {app: web}
  template:
    metadata:
      labels: {app: web}
    spec:
      containers:
        - name: web
          image: nginx:1.27
```

用户只提交 `spec.replicas: 3`。至于是创建、删除还是替换 Pod，由控制器决定。这种模式带来三个关键性质：

1. **幂等**：同一份 YAML 提交一百次，结果一致。
2. **自愈**：控制器持续观察实际状态，偏差出现就修正。
3. **可审计**：集群状态是对象集合，可以 diff、版本化、做策略检查。

声明式不是“没有命令”，而是把命令藏进控制器。`kubectl apply` 只是提交意图，真正干活的是 DeploymentController、ReplicaSetController、Scheduler 和 Kubelet。

## 1.3 Kubernetes 的本质：一个带控制器的分布式数据库

可以用一句话概括：

> Kubernetes 是一个保存“期望状态”的分布式对象数据库，外加一组把现实推向期望状态的控制器。

这个抽象解释了几乎所有设计：

- 为什么所有组件都通过 API Server 读写对象，而不是互相 RPC？
- 为什么 watch 是核心机制，而不是轮询？
- 为什么控制器可以独立重启、水平扩展？
- 为什么 `resourceVersion`、乐观并发和 finalizer 如此重要？
- 为什么 etcd 是控制面最关键的依赖？

下图是本书反复使用的闭环：

```text
用户 / 系统 ──写 spec──▶ API Server ──持久化──▶ etcd / Store
                              │
                              │ watch
              ┌───────────────┼────────────────┐
              ▼               ▼                ▼
         Scheduler       Controllers        Kubelet
         选节点          建 Pod/RS/...      跑容器/报状态
              │               │                │
              └───────────────┴──────写 status──┘
                              │
                        观测到偏差，再调谐
```

注意“写 status”这条线：控制器不是直接修改现实，而是先推动现实，再把观测结果写回对象。调度器写 `spec.nodeName`，kubelet 写 `status.phase`，Deployment 控制器写 `status.availableReplicas`。下一次调谐读取这些 status，形成反馈。

## 1.4 一个 Pod 的旅程

把上面的抽象落到一次 `kubectl apply`：

1. **API Server** 认证用户、RBAC 鉴权、准入控制（默认值、配额、Pod Security），把 Deployment 写入存储，分配 `resourceVersion`。
2. **DeploymentController** watch 到新对象，创建 ReplicaSet；ReplicaSetController 创建 Pod。
3. **Scheduler** watch 到 `spec.nodeName` 为空的 Pod，过滤掉资源不足、污点不匹配、亲和性不满足的节点，打分选出节点，写回 `spec.nodeName`。
4. **Kubelet** watch 到绑定到本节点的 Pod，调用容器运行时拉镜像、建沙箱、启动容器；执行探针；把容器状态和 Pod 条件写回 status。
5. **EndpointsController** 看到 Pod Ready，把 Pod IP 写进 Endpoints/EndpointSlice。
6. **kube-proxy / eBPF / ServiceProxy** 让 Service 的虚拟 IP 流量落到这些后端。
7. 如果 Pod 挂了，Kubelet 按 `restartPolicy` 重启容器；如果 Pod 被删除，ReplicaSetController 补一个新 Pod；如果节点失联，NodeLifecycleController 标记 NotReady，调度器不再往上面放新 Pod。

这七步里，没有任何一个组件“命令”另一个组件。它们只通过 API 对象交流。这种松耦合是 Kubernetes 能容纳不同厂商、不同运行时、不同网络实现的原因，也是它复杂度的来源。

## 1.5 为什么不是“一个超级调度器”？

初学者常问：为什么不写一个程序，收到请求后直接找机器、起容器、配负载均衡？

可以，但会很快遇到耦合：

- 调度策略和运行时强绑定，换运行时就要改调度器。
- 发布逻辑和扩缩容逻辑互相调用，形成循环依赖。
- 任何组件重启都丢失内存中的“正在做什么”。
- 无法单独升级网络插件或存储插件。
- 第三方无法在不 fork 核心代码的情况下扩展。

Kubernetes 的选择是把“状态”放进 API，把“行为”拆成独立控制器。代价是：

- 组件多，链路长，排障需要理解 watch 和缓存。
- 最终一致，存在短暂的中间状态（例如 Deployment 刚更新时新旧 RS 并存）。
- API 成为瓶颈和故障域，必须认真设计规模与高可用。

理解这些代价，比背 `kubectl` 参数更重要。

## 1.6 什么时候不该用 Kubernetes

Kubernetes 不是默认答案。以下场景要谨慎：

- **只有一两个长期服务、单机足够**：systemd + 反向代理更简单。
- **团队没有平台运维能力**：托管 K8s 能降低控制面负担，但网络、权限、成本、发布流程仍要人负责。
- **强实时、超低延迟、特殊内核**：需要认真评估 CNI、调度抖动和容器隔离开销。
- **批处理量很小**：一台机器 + 队列可能更便宜。
- **无法接受最终一致**：Kubernetes 的控制循环是异步的，不适合把“毫秒级强一致编排”当目标。

但如果你需要多团队共享资源、声明式发布、弹性伸缩、生态工具和可移植性，Kubernetes 仍然是事实标准。关键不是“用不用”，而是“用到什么程度、哪些部分自己写、哪些买托管”。

## 1.7 本教程的学习方法

本书同时提供两条线：

- **概念线**：每章先讲真实 Kubernetes 的问题、机制和取舍。
- **实现线**：MiniK8s 用可读的 Python 复现核心机制，并用测试固定行为。

建议的读法：

1. 先读第 2～5 章建立对象模型和 API 思维。
2. 按工作负载、网络、调度、安全的主线读。
3. 读到第 34 章以后，对照 `mini_k8s/` 源码看实现。
4. 每章至少跑一次对应示例；`examples/run_all.py` 会验证 18 个场景。
5. 商业章节放在最后读，避免把“技术能做什么”与“市场愿意付钱”混为一谈。

## 1.8 Kubernetes 的历史、治理与版本节奏

理解 Kubernetes 的很多设计，需要知道它从哪里来：

- **Borg/Omega 的血统**：Google 内部用 Borg 管理大规模容器，Omega 引入了更通用的调度与声明式状态模型。Kubernetes 把 Borg 的经验产品化，但放弃了“单一调度器控制一切”的紧耦合。
- **2014 年开源，2015 年发布 1.0**：最初由 Google 主导，随后捐赠给新成立的 CNCF。CNCF 的中立治理是它击败 Mesos、Swarm 等竞品的重要原因之一。
- **API 优先的社区模式**：每个重要能力都要经过 KEP（Kubernetes Enhancement Proposal）讨论，SIG（Special Interest Group）按领域维护，例如 SIG-Node、SIG-Network、SIG-Scheduling、SIG-Security。
- **发布节奏**：稳定期大约每年 3 个 minor 版本（约 4 个月一个）。每个版本会引入 alpha/beta/stable API，并按弃用策略移除旧 API。
- **一致性认证**：CNCF 的 Kubernetes Conformance 认证要求发行版通过官方一致性测试，这也是“Kubernetes”这个名字可以被不同厂商使用的前提。

这些背景解释了几个常见现象：

1. **为什么 API 版本如此重要**：社区用版本和弃用窗口换兼容性，升级集群前必须扫描 beta API。
2. **为什么扩展点这么多**：CRD、admission webhook、CNI、CSI、CRI、Scheduler Framework 都是为了在不 fork 核心的情况下让厂商和用户扩展。
3. **为什么“发行版”差异很大**：核心只规定 API 与行为，网络、存储、运行时、负载均衡由实现决定。
4. **为什么不要追每个新项目**：大量能力仍在 alpha/beta，生产采用要看 KEP 阶段、实现成熟度和社区支持。

对学习者的实际建议：

- 读概念时同时看对应 KEP 的 “Motivation/Alternatives”，能理解为什么不是另一种设计。
- 选择发行版/托管服务时，确认它通过的 conformance 版本和支持窗口。
- 升级前用 `pluto`、`kubent` 等工具检查弃用 API；这不是可选项，而是变更管理的一部分。

### 版本锚点

本书的稳定 API 语义以 Kubernetes v1.31 的稳定接口为基线。这个基线的作用是“保证示例使用的 API 在较新集群上仍然成立”，不是“v1.31 才引入这些能力”。**v1.31 已于 2025-10-28 结束社区维护**：示例冻结在该版本是为了可复现，新建生产集群必须使用当前受支持的 minor，并按 minor 逐个升级。

阅读时注意区分两类事实：

- **在 v1.31 之前已经稳定**：`ReadWriteOncePod`、`PodDisruptionBudget`、`EndpointSlice`、`ValidatingAdmissionPolicy`（1.30 稳定）等。它们可以放心作为稳定 API 使用。
- **在 v1.31 之后才稳定**：原生 sidecar 容器在 1.33 GA；DRA 在 1.34 GA（`resource.k8s.io/v1`）；原地扩缩容在 1.35 GA；Pod 证书在 1.37 GA。本书正文仍用 v1.31 可用的写法，但会标注这些演进方向；逐版本细节见[附录 R](../appendices/R-version-evolution-1.32-1.37.md)。

截至 2026-11，受支持的 minor 是 1.35/1.36/1.37，1.34 已于 2026-10-27 EOL。本书不会追逐每个版本号；遇到“这个字段是否还存在/是否默认开启”的问题，以目标集群的 `kubectl explain`、release notes 和 KEP 阶段为准。版本号不是重点，**API 阶段和弃用窗口**才是升级风险的来源。

## 1.9 替代方案：Kubernetes 不是唯一答案

在决定采用之前，先看它在哪些维度上胜出、在哪些维度上更贵：

| 方案 | 适合 | 优势 | 代价 |
|---|---|---|---|
| Kubernetes | 多团队、多服务、需要生态与可移植性 | 声明式、扩展性、生态、事实标准 | 复杂度、控制面运维、学习曲线 |
| Nomad | 混合容器/批处理/VM、中小规模 | 单二进制、简单、调度灵活 | 生态小、K8s 兼容工具少 |
| Amazon ECS/Fargate | AWS 深度用户、不想管节点 | 托管、与 IAM/ALB 集成 | 云锁定、可移植性差 |
| Docker Swarm | 小规模、简单编排 | 上手快、内置 | 社区/生态萎缩、功能有限 |
| 纯 Serverless（Lambda/Cloud Run） | 事件驱动、突发、低运维 | 免运维、按需计费 | 冷启动、运行时限制、状态/长任务不友好 |
| systemd + 脚本/Ansible | 少量长期服务、单机/少量机器 | 透明、无额外层 | 无自愈/调度/滚动发布，规模上限低 |
| Mesos/Marathon | 历史遗留、大数据混部 | 资源池化 | 社区衰退，迁移成本高 |

选择不是“先进 vs 落后”，而是“问题形状 vs 工具形状”：

- 如果你只有 3 个服务、2 台机器，Kubernetes 的控制面可能比业务还复杂。
- 如果你需要 GPU 队列、多租户、GitOps、服务网格、Operator 生态，Kubernetes 的“复杂度”是买入生态的门票。
- 如果你在 AWS 且团队没有平台能力，ECS/Fargate 可能比自建 EKS 更省人。
- 如果你要跨云/混合云/边缘统一控制面，Kubernetes 的 API 抽象仍然是最通用的选择。

## 1.10 采用与迁移的经济学

Kubernetes 的成本不只在集群账单。一个完整的采用决策至少算四笔账：

1. **平台成本**：控制面、节点、网络、存储、可观测、安全、备份。
2. **人力成本**：平台团队、SRE、培训、on-call。
3. **迁移成本**：应用改造、CI/CD 改造、数据迁移、双跑期。
4. **机会成本**：延迟交付、组织摩擦、锁定。

迁移前先做“应用就绪度”评估：

- 是否无状态/可水平扩展？有状态服务是否需要 Operator？
- 是否把本地磁盘、主机路径、固定 IP 当依赖？
- 是否有健康检查、优雅终止、配置外置？
- 构建产物是否不可变（镜像 digest）？
- 是否有可观测性和资源 requests？
- 团队是否理解“最终一致”和“控制器会重试”？

一个常见的迁移顺序：

```text
无状态 Web/API → 批处理/定时任务 → 内部工具 → 有状态服务（Operator）
→ 数据平台/GPU → 核心交易（最后）
```

不要一开始就迁数据库。先迁“失败可回滚、无状态、流量可切”的服务，建立平台可信度，再处理有状态系统。

## 1.11 失效模型：Kubernetes 不保证什么

Kubernetes 常被误解为“高可用银弹”。它提供的是**控制循环和调度**，不是：

- 应用正确性：代码 bug、死锁、数据损坏它不管。
- 数据持久性：PV 不是备份，节点/区域故障仍可能丢数据。
- 强一致：控制面是最终一致的，状态有中间态。
- 零停机：滚动更新仍可能因探针/容量/依赖失败而中断。
- 安全隔离：容器不是强沙箱，默认配置可能很宽松。
- 成本优化：调度器不按价格/碳排优化，需要额外工具。
- 网络质量：CNI/云网络决定延迟/丢包，K8s 只提供抽象。

一个有用的故障分类：

| 层 | 典型故障 | K8s 能否自愈 |
|---|---|---|
| 应用 | 崩溃、死锁、内存泄漏 | 部分（重启/驱逐），根因需修代码 |
| 容器/运行时 | 镜像拉取失败、运行时挂起 | 有限（重试/重建），需节点运维 |
| 节点 | 宕机、磁盘满、内核故障 | 部分（重新调度），有状态数据可能丢 |
| 网络 | DNS 故障、CNI 异常、策略误配 | 有限（重试），需网络排障 |
| 存储 | 卷不可用、快照损坏 | 有限（重挂载），依赖 CSI/备份 |
| 控制面 | API Server/etcd 故障 | 多副本可缓解，需 HA/备份 |
| 人为 | 误删、错误策略、错误升级 | 不自动，需审计/审批/回滚 |

理解这张表，才能在事故中快速判断“该等控制器自愈，还是人立刻介入”。

## 本章小结

- Kubernetes 解决的是“持续维持系统形状”，不是“启动容器”。
- 声明式 API + 控制循环是其核心抽象；所有组件通过 API 对象解耦。
- 最终一致性带来扩展性，也带来中间状态和排障复杂度。
- 它不是所有场景的默认答案；托管服务、团队能力和成本模型决定采用方式。
