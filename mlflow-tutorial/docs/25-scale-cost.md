# 第 25 章 规模、性能与成本：从 SQLite 到平台

## 学习目标

- 估算元数据、指标、artifact、trace 的容量与增长。
- 识别 SQLite、单进程服务器和同步 trace 的瓶颈。
- 设计分页、归档、聚合、缓存与 TTL 策略。
- 用成本模型做“自建 vs 托管”的判断。

## 25.1 容量估算

先建立单位：

```text
R = 每天新增 run 数
M = 每个 run 的 metric 点数
A = 每个 run 的 artifact 平均大小
T = 每天 trace 数
S = 每条 trace 平均 span 数与负载大小
```

元数据：

```text
metric 行数/天 ≈ R * M
参数/标签行数/天 ≈ R * (P + G)
trace 行数/天 ≈ T
span 行数/天 ≈ T * S
```

示例（假设，不是基准）：

```text
R=2,000, M=5,000, P=20, G=10
metric 行/天 = 10,000,000
每行含索引 ~100 B → ~1 GB/天（仅指标）
```

这说明指标历史是增长最快的元数据表。必须考虑：

- 降采样（保留每 N 步/每小时聚合）；
- TTL；
- 冷热分层；
- 只保留关键 key 的完整历史。

artifact：

```text
A=2 GB, R=200/天 → 400 GB/天
```

模型/检查点会迅速超过数据库几个数量级。需要对象存储 + 生命周期 + 去重。

## 25.2 SQLite 的边界

适合：

- 单机开发；
- 测试；
- 单团队低并发（读多写少）；
- 小于几十 GB 的元数据。

不适合：

- 多台应用服务器共享；
- 高并发写；
- 在线 schema 迁移；
- 大表复杂查询；
- 高可用。

迁移到 Postgres 时要注意：

- 自增/序列；
- 事务隔离；
- JSONB；
- 索引策略；
- 连接池；
- 迁移脚本。

Mini 的 SQL 尽量标准，但 `AUTOINCREMENT`、`PRAGMA`、窗口函数和 `ON CONFLICT` 仍需适配。

## 25.3 指标表的优化

### 最新值表

维护 `latest_metrics(run_id,key,value,timestamp,step)`：

- 写入时 upsert；
- 搜索/详情直接读小表；
- 历史表只用于曲线/审计。

代价：双写一致性、额外存储。

### 分区

按时间/实验分区：

```text
metrics_2026_11
```

查询最近数据更快，归档/删除按分区。代价：跨分区查询复杂。

### 降采样

保留：

- 原始点 7 天；
- 每小时聚合 90 天；
- 每天聚合永久。

注意图表/审计需求，不要丢掉关键转折点。

### 索引

- `(run_id, key, timestamp, id)` 支持单 run 曲线；
- `(key, value)` 支持搜索，但低选择性；
- 搜索多条件时，相关子查询仍可能慢。

### 系统指标是“隐形的大表”

真实 MLflow 支持自动采样系统指标：

```python
import mlflow

mlflow.enable_system_metrics_logging()
# 可选：调整采样间隔、GPU 指标等；以版本文档为准
```

常见指标键包括 CPU、内存、磁盘、网络，以及 GPU 利用率/显存等，通常带 `system/` 前缀。它们看起来“不要钱”，实际会显著放大行数：

```text
run 数 × 采样频率 × 指标数 × 训练时长
```

一个 8 卡训练 24 小时的 run，如果每分钟每个指标一个点，很容易产生数十万行。容量规划时要把系统指标单独估算，并考虑：

- 降低采样频率；
- 只对长训练开启；
- 单独表/分区；
- 与业务指标不同的保留期；
- 图表降采样；
- 关闭不需要的设备/网络指标。

Mini 没有实现系统指标采集；它的价值是提醒你：**监控数据本身也是需要治理的数据**。

## 25.4 搜索性能

Mini 的查询：

- 每个 metric 条件一个 `EXISTS` + 相关子查询；
- 多条件叠加；
- `ORDER BY` 动态子查询；
- `OFFSET` 深分页。

优化顺序：

1. 限制时间/实验范围（缩小候选集）；
2. 物化最新指标；
3. 索引 `(experiment_id, start_time)`；
4. keyset 分页；
5. 缓存常用查询；
6. 导出到 OLAP/搜索引擎做复杂分析。

不要在没有测量的情况下加索引：每个索引都会拖慢写入。

## 25.5 Trace 成本

Trace 负载可能远大于训练指标：

```text
T=1,000,000/天, 平均 20 KB → 20 GB/天
```

控制：

- 采样（头部/尾部）；
- 截断（Mini 默认 256 KiB/字段）；
- 只存必要字段；
- 异步批写；
- 列式存储/压缩；
- TTL（例如 30 天）；
- 冷热分层。

成本不只在存储，还在写入/索引/查询 CPU。

### 25.5.1 Webhook 投递成本

Webhook 的成本不是“一条 POST”，而是：

```text
事件数 = 写操作数 × 订阅该事件的 webhook 数
投递数 = 事件数 × (1 + 重试次数)
```

如果每个 tag 变更都触发事件，一个高频训练流水线很容易产生百万级投递。需要：

- 只订阅真正需要的 entity.action；
- 对高频事件做合并/采样；
- 限制单 webhook 的并发与速率；
- `DELIVERED` 投递记录按保留期清理；
- 监控 `pending` 数，避免 outbox 无限增长；
- 对失败 endpoint 做熔断，而不是无限重试。

## 25.6 Artifact 成本

- 对象存储单价低，但请求/流量/跨区复制可能更贵；
- 模型下载到推理节点的流量成本；
- 重复存储（每个 run 一份）浪费；
- 生命周期策略可把旧版本转冷层；
- 删除前检查 Registry 引用。

去重收益取决于：

- 文件重复率；
- 分块大小；
- 元数据开销；
- 加密/租户隔离限制。

## 25.7 成本模型（可替换假设）

设：

```text
C_db   = 数据库实例/存储/备份成本
C_obj  = 对象存储容量 + 请求 + 出口流量
C_srv  = 应用服务器/网关
C_obs  = 日志/监控/trace 存储
C_ops  = 运维人力（按 FTE 折算）
```

自建年成本：

```text
C_self = C_db + C_obj + C_srv + C_obs + C_ops + 迁移/停机风险
```

托管年成本：

```text
C_managed = 许可/订阅 + 用量费 + 迁移成本 + 锁定风险
```

决策不应只看单价，要看：

- 团队规模；
- 合规/数据驻留；
- 需要的集成；
- 运维能力；
- 增长速度；
- 议价能力。

## 25.8 容量规划步骤

1. 采集当前 R/M/A/T；
2. 预测 12 个月增长；
3. 设定保留策略；
4. 估算存储/请求/带宽；
5. 压测关键路径；
6. 设定告警阈值；
7. 每季度复盘。

不要用“平均值”做容量规划；用 p95/p99 和峰值。第 45 章给出监控窗口（模型 × 特征 × 粒度 × 保留期）的单独成本模型，别把它混进训练指标预算。

## 25.9 性能测试清单

- 创建 run 的 QPS；
- 批量日志吞吐；
- 搜索 p50/p95/p99；
- 深分页；
- artifact 上传/下载吞吐；
- 并发读写锁等待；
- Trace 写入对在线延迟的影响；
- 数据库/对象存储故障时的降级。

## 25.10 与真实 MLflow 的差距

- 真实 MLflow 可水平扩展服务器、使用 Postgres/对象存储；
- 真实实现有更成熟的批量/缓存/异步；
- Mini 的性能结论不能外推；
- 成本数字必须按你的云合同/用量重算，本文不提供“标准报价”。

## 小结

- 指标历史和 trace 是增长最快的元数据；artifact 是容量大头。
- SQLite 只适合单机/低并发；生产要换数据库并做迁移。
- 优化顺序是“缩小候选集 → 物化/索引 → 分页 → 缓存 → OLAP”。
- 成本模型要包含运维、迁移、锁定和故障风险，而不只是存储单价。

## 练习

1. 用你自己的 R/M/A/T 估算 12 个月容量。
2. 设计一个指标降采样策略，保证关键转折不丢。
3. 比较“自建 Postgres + S3”与托管平台的 3 年 TCO，列出假设。
