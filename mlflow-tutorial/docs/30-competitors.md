# 第 30 章 竞品对比：W&B、Kubeflow、LangSmith 与云平台（含 Neptune 复盘）

> 产品能力/定价变化很快，本章只做架构与定位层面的比较，不引用具体报价。选型请以官方文档和试用为准。

## 学习目标

- 用同一组维度比较实验追踪/模型平台/LLM 可观测性工具。
- 理解“开源核心 + 托管服务”“平台套件”“专用工具”的取舍。
- 识别功能矩阵之外的迁移、治理和总成本因素。
- 为你的场景给出有条件的推荐，而不是绝对排名。

## 30.1 比较维度

| 维度 | 关键问题 |
|---|---|
| 核心定位 | 实验追踪？端到端 MLOps？LLM 可观测？ |
| 数据模型 | run/metric/artifact？span/trace？prompt/eval？ |
| 部署 | SaaS / 自托管 / 混合 |
| 扩展性 | 多后端、对象存储、分布式 |
| 生态 | 框架 flavor/autolog、云集成 |
| 治理 | RBAC、审计、合规、数据驻留 |
| 成本 | 许可 + 用量 + 运维 + 迁移 |
| 锁定 | 数据/模型/prompt 是否可导出 |
| LLM 能力 | tracing、eval、prompt；独立 gateway 在 3.0 移除，改由平台/应用侧承担 |
| 成熟度 | 社区、发布节奏、支持 |

## 30.2 MLflow

定位：开源 AI/ML 生命周期平台，Databricks 主导/深度集成。

优势：

- 开放、可自托管；
- Tracking/Models/Registry/Projects 概念清晰；
- 生态广、集成多；
- 可导出，迁移成本相对可控；
- GenAI tracing/eval 方向明确。

不足：

- 开源版已有工作区、RBAC/子资源 DENY、预算与 MCP（部分实验），但 SSO/SCIM、审计导出、合规认证、跨区域与 SLA 通常要商业/自建方案；
- 自托管要自己运维数据库/对象存储/升级；
- UI/协作能力不如商业套件；
- 大规模 tracing/查询需要额外架构。

适合：

- 想掌握数据/模型元数据、避免锁定；
- 有平台工程能力；
- 需要与现有数据栈集成；
- 从传统 ML 逐步扩展到 GenAI。

## 30.3 Weights & Biases（W&B）

**状态（截至 2026-11）**：2025-05 被 CoreWeave 完成收购，作为 CoreWeave 的 AI 开发者平台产品运营；官方承诺保持多云/框架互操作。选型时要把“产品路线受母公司影响”纳入评估。

定位：实验追踪/模型管理/可视化，强于研究者体验与可视化。

优势：

- 实验对比、图表、报告体验好；
- 与深度学习框架集成成熟；
- 团队协作/分享；
- 托管服务省运维。

不足：

- SaaS 为主（企业版有自托管选项，依合同）；
- 成本随席位/用量上升；
- 数据驻留/合规需评估；
- 深度治理/部署仍需其他系统。

适合：

- 研究/算法团队，重视可视化和快速迭代；
- 能接受 SaaS；
- 不需要完全自建。

## 30.4 Neptune（已停止独立服务）

**状态（截至 2026-11）**：OpenAI 于 2025-12 宣布收购 Neptune；托管服务于 2026-03 关闭并删除数据，Helm/容器镜像仓库随后下线。它不再是现役竞品。

历史定位：实验追踪/模型管理，面向大规模实验与团队协作。其迁移工具提供到 MLflow/W&B 的导出路径；这也说明“追踪数据可导出”是选型时的硬指标。新项目不应再把 Neptune 作为候选，除非你只需要迁移历史数据。

## 30.5 Comet

定位：实验管理/模型监控/LLM 实验。

优势：

- 实验对比/可视化；
- 模型监控；
- 托管体验。

不足：

- SaaS/合同约束；
- 与现有数据平台集成深度需验证；
- 治理能力依版本。

适合：

- 需要快速上手、可视化强的团队。

## 30.6 Kubeflow

定位：Kubernetes 上的 ML 平台套件（Pipelines、Katib、KServe 等）。

优势：

- 云原生、可自托管；
- 流水线/超参/服务生态；
- 与 K8s 权限/网络集成。

不足：

- 运维复杂；
- 组件多、版本兼容难；
- 实验追踪体验不如专用工具；
- 小团队成本高。

适合：

- 已有成熟 K8s 平台团队；
- 需要端到端流水线/服务；
- 愿意承担运维。

## 30.7 云厂商平台（SageMaker / Vertex AI / Azure ML）

定位：托管端到端 ML 平台。

优势：

- 训练/调参/部署/监控一体化；
- 与云 IAM/存储/网络深度集成；
- 合规/支持合同；
- 省运维。

不足：

- 供应商锁定；
- 成本不透明/随用量上升；
- 跨云/本地困难；
- 实验追踪可能不如专用工具灵活。

适合：

- 已在某云深度使用；
- 合规/支持优先；
- 团队不想自建平台。

## 30.8 LLM 可观测性专用工具

代表：LangSmith、Langfuse、Arize Phoenix、Helicone 等（定位各异）。这个赛道的所有权/状态变化很快，选型前必须核对当前状态：

| 产品 | 状态（截至 2026-11，需以官方为准） |
|---|---|
| LangSmith | LangChain 旗下，仍作为独立产品运营 |
| Langfuse | 2026-01 被 ClickHouse 收购；保持开源/可自托管，Cloud 产品继续 |
| Arize Phoenix | Arize 旗下；有报道称 Arize 被 Dynatrace 收购，**需核实** |
| Helicone | 据报道 2026-03 由 Mintlify 接手并进入维护模式，**需核实** |

优势：

- LLM trace/prompt/eval 体验专精；
- 快速接入 SDK；
- 针对 token/成本/反馈优化；
- 部分开源可自托管。

不足：

- 与经典 ML 追踪/Registry 可能割裂；
- 数据驻留/锁定；
- 评测方法/标准不一；
- 规模/治理依产品。

适合：

- LLM 应用为主、经典 ML 较少；
- 需要快速调试/评测；
- 能接受专用栈。

选型提醒：这个赛道 2025–2026 的并购/停服频繁，**所有权稳定性、导出能力与开源许可证**应与功能同等权重；不要只比较 demo 体验。

## 30.9 功能矩阵（定性）

| 能力 | MLflow | W&B | Kubeflow | 云平台 | LLM 专用 |
|---|---|---|---|---|---|
| 实验追踪 | 强 | 很强 | 中 | 强 | 中 |
| 模型 Registry | 强 | 强 | 中 | 强 | 弱 |
| 可视化 | 中 | 很强 | 中 | 强 | 强（LLM） |
| 自托管 | 强 | 依版本 | 很强 | 弱 | 依产品 |
| 企业治理 | 强（OSS 基础；SSO/审计另配） | 强（商业） | 强（需自建） | 很强 | 依产品 |
| GenAI trace/eval | 强（演进中） | 中/强 | 弱 | 强 | 很强 |
| 生态开放 | 很强 | 中 | 强 | 中 | 中 |
| 运维负担 | 中 | 低（SaaS） | 高 | 低 | 低 |

“强/中/弱”是定性判断，不是基准测试。

## 30.10 选型方法

1. 列出必须能力（例如“自托管 + 对象存储 + RBAC + trace”）。
2. 做 2 周 PoC：真实数据、真实模型、真实权限。
3. 测迁移：导出 run/模型/prompt，换一个环境加载。
4. 测故障：数据库/对象存储/网络断开。
5. 算 3 年 TCO：许可 + 用量 + 运维 + 迁移 + 机会成本。
6. 检查锁定：数据/模型/评测集能否导出。
7. 评估社区/支持/路线。

不要用功能清单做决定；用“故障时能否恢复、换供应商时能否迁移”。

## 30.11 组合策略

常见组合：

- MLflow（追踪/Registry）+ KServe（服务）+ OTel 后端（trace）；
- W&B（研究追踪）+ 云平台（部署/治理）；
- LLM 专用工具（trace/eval）+ MLflow（经典 ML/Registry）；
- 自建元数据 + 托管训练/推理。

组合的代价是集成/双轨；收益是各取所长。关键是明确“系统 of record”，避免同一事实存两份且不一致。

## 小结

- MLflow 的优势是开放、可自托管、生态广；不足是企业治理/运维。
- 商业工具强在体验/托管；代价是成本/锁定。
- Kubeflow/云平台是平台套件，范围更大但更重。
- LLM 专用工具在 trace/eval 上更专精，但可能与经典 ML 割裂。
- 选型要看迁移、故障、TCO，而不是功能列表。
