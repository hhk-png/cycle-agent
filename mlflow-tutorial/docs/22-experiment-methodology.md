# 第 22 章 实验管理方法论：命名、指标、对比与复现

## 学习目标

- 把“做实验”从随手尝试变成可审计的假设检验。
- 设计命名、标签、指标和基线的团队约定。
- 识别 Notebook 驱动实验的常见反模式。
- 建立实验评审和结果归档流程。

## 22.1 实验不是“多跑几次”

一个有效实验至少包含：

```text
假设：把特征窗口从 7 天改到 30 天，能提升召回而不显著降低精确率
变量：window_days ∈ {7, 14, 30}
控制：数据快照、模型族、随机种子、评测集、阈值
指标：recall@threshold=0.5（主）、precision、延迟、成本
决策规则：recall +0.03 且 precision 不低于 -0.01，否则回退
```

没有假设和决策规则的“调参”，只是在消耗算力。

## 22.2 命名与标签

推荐模板：

```text
Experiment: <domain>-<task>-v<major>
Run:        <model>-<variant>-<yyyymmdd>-<shortsha>
```

标签：

```text
team, owner, git_commit, data_snapshot, feature_set,
model_family, hardware, review_status, ticket
```

参数：

```text
model.*, data.*, train.*, eval.*
```

指标：

```text
train_*, val_*, test_* 前缀区分数据切分
latency_p50/p95, cost_usd, tokens_in/out（LLM）
```

规则要可检查：

- CI 校验必需标签；
- 参数 key 白名单；
- 指标单位/定义写进文档；
- 禁止在 key 中编码高基数 ID。

## 22.3 基线

没有基线的实验无法判断好坏。至少准备：

1. **业务基线**：现有规则/人工流程；
2. **简单模型基线**：逻辑回归/均值/频率；
3. **当前生产模型**；
4. **消融基线**：去掉新特征/新模块。

实验报告应展示相对基线的差异，而不是孤立指标。

## 22.4 随机性与可复现

固定：

- Python/NumPy/框架随机种子；
- 数据划分种子；
- 初始化；
- 数据加载顺序；
- 并行度（可能影响浮点求和顺序）；
- CUDA 确定性（性能代价）。

记录：

- 种子；
- 框架/驱动版本；
- 硬件；
- 数据 digest；
- 代码 commit；
- 环境锁文件。

注意：即使固定种子，不同 GPU/库版本也可能有微小差异。可复现的目标是“统计等价”，不是逐位相同。

## 22.5 Notebook 反模式

| 反模式 | 风险 | 替代 |
|---|---|---|
| 隐式全局状态 | 结果依赖执行顺序 | 脚本/函数化 + 参数 |
| 手动改 CSV | 数据不可追溯 | 数据快照 + digest |
| 只保留最后一个 cell 输出 | 无法审计 | 每次 run 记录 |
| 用测试集调参 | 过拟合 | 验证集/holdout |
| 图和指标只存在 notebook | 无法比较 | 日志 + artifact |
| `!pip install` 漂移 | 环境不可复现 | lock 文件/镜像 |
| 打印代替指标 | 无法聚合 | structured metrics |

Notebook 可以用于探索，但进入评审的实验应从可执行脚本/项目产生。

## 22.6 对比方法

单指标排序不够。建议：

1. 固定评测集和阈值；
2. 报告均值 + 置信区间/多 seed 方差；
3. 看切片（长尾/群体）；
4. 看成本/延迟；
5. 看失败案例；
6. 做配对显著性检验；
7. 记录决策与理由。

MLflow 的搜索只能帮你找 run，不能替你判断因果。相关性不是因果：学习率 0.001 的 run 可能恰好用了更好的数据。

## 22.7 实验评审

一个轻量评审模板：

```text
- 问题与假设
- 数据来源/窗口/排除规则
- 评测集与指标（主/次）
- 基线
- 结果（含切片/置信区间）
- 失败模式与风险
- 成本/延迟
- 是否进入 Registry
- 后续实验
```

评审输出应写回 run tags/description 或关联文档，而不是只留在会议记录。

## 22.8 归档与清理

- 保留所有“影响过决策”的 run；
- 定期归档无用的探索 run（软删除/对象存储冷层）；
- 保持评测集版本；
- 清理大 artifact 前检查 Registry 引用；
- 记录清理审计。

“全保留”会导致成本和噪声；“只留最好”会丢失失败经验。按决策价值分层。

## 22.9 一个完整案例

目标：提升客服工单分类的 macro-F1。

```text
实验 1：TF-IDF + 逻辑回归（基线）
实验 2：+ 主题特征
实验 3：+ 历史交互特征（检查时间泄漏）
实验 4：替换为轻量 Transformer
```

每个 run 记录：

- 数据快照 `tickets-2026-11-01`；
- 切分：按时间，训练 < 2026-09-01，测试 >= 2026-10-01；
- 指标：macro-F1、每类 F1、p95 延迟、成本；
- 标签：`leakage_review=passed`。

决策：实验 3 提升但延迟翻倍，实验 4 提升 0.02 但成本 5 倍，最终选择实验 3 + 缓存。

这个案例说明：**最佳指标不等于最佳上线选择**。

## 22.10 与真实 MLflow 的差距

- 真实 MLflow 提供 run 对比 UI、图表、数据集输入；
- 但方法论（假设、基线、切片、评审）不能由工具替代；
- Mini 只能用搜索/标签/指标支持同样的流程。

## 小结

- 实验要有假设、变量、控制、指标和决策规则。
- 命名/标签/指标口径是团队资产，必须自动化检查。
- 基线、随机性、切片和置信区间决定结论可信度。
- Notebook 适合探索，评审级实验应可脚本化复现。

## 练习

1. 为你的项目写一个“实验卡片”模板。
2. 设计 3 个基线，并说明各自能排除什么原因。
3. 如何向非技术评审解释“提升 0.01 但不显著”？
