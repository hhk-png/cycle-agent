# 附录 H 练习与参考答案

> 先自己做，再对照。答案不是唯一解，重点是论证。

## H.1 第 1 章

**题：列出模型项目缺失的 5 项元数据，哪项最可能导致线上事故？**

参考：

1. 数据快照/切分逻辑；
2. 代码 commit；
3. 依赖锁；
4. 随机种子；
5. 特征列顺序/预处理版本。

最危险通常是“特征列顺序/预处理版本”，因为模型仍能输出，错误静默且难以发现。数据/代码问题通常更早暴露。

## H.2 第 3 章

**题：`val_auc` 与 `val_auc@threshold=0.5` 哪种 key 更好？**

参考：优先 `val_auc`（固定阈值作为参数/标签记录），因为指标 key 应稳定可枚举；把阈值编码进 key 会导致基数爆炸、搜索困难。若必须并存多个阈值，用 `val_auc_at_50` 这类有限枚举，并记录阈值定义。

## H.3 第 7 章

**题：两个进程同时创建同一模型的下一个版本，如何避免冲突？**

参考：

- 单独 `sequences` 表：`UPDATE ... SET value=value+1 WHERE name=? RETURNING value`；
- 或在事务中 `INSERT ... SELECT COALESCE(MAX(version),0)+1` 并捕获唯一冲突重试；
- Postgres 可用 advisory lock/serializable；
- 客户端幂等键避免重复。

## H.4 第 9 章

**题：为 DSL 增加 BETWEEN。**

参考 AST：

```python
@dataclass(frozen=True)
class Between:
    field: Field
    low: Any
    high: Any
    negated: bool = False
```

SQL：

```sql
field BETWEEN ? AND ?
```

注意：`BETWEEN` 对字符串/数值的语义、边界包含、索引使用。测试需覆盖 `NOT BETWEEN`、类型错误、空范围。

## H.5 第 10 章

**题：增加 sha256 manifest。**

参考：

```json
{"files": {"model/model.json": {"sha256": "...", "size": 123}}}
```

读取时校验；写入时先算 digest 再原子替换 manifest；GC 按 manifest 找孤儿。注意大文件流式计算、并发写、manifest 自身原子性。

## H.6 第 12 章

**题：检测“版本被删除但 alias 仍指向它”。**

参考 SQL：

```sql
SELECT a.name, a.alias, a.version
FROM model_version_aliases a
LEFT JOIN model_versions v
  ON v.name=a.name AND v.version=a.version
WHERE v.name IS NULL;
```

外键应阻止这种情况；若历史数据存在，需对账任务。删除版本时应先检查 alias/部署引用。

## H.7 第 14 章

**题：`log_batch` 批次 ID 去重。**

参考表：

```sql
CREATE TABLE batch_ids (
  run_id TEXT NOT NULL,
  batch_id TEXT NOT NULL,
  created_at INTEGER NOT NULL,
  PRIMARY KEY (run_id, batch_id)
```

写入前插入；冲突则直接返回成功（幂等）。定期删除旧批次（超过重试窗口）。注意“先插批次再写数据”同事务。

## H.9 第 19 章

**题：不记录原文的可调试性。**

## H.12 第 31 章

**题：开源核心 + 企业治理定价。**

参考：

- 免费：单工作区、基础追踪、有限保留；

## H.13 第 33 章

**题：Prompt 版本与别名的最小发布流程。**

参考：

1. 实验中使用固定版本 `prompts:/name/3`；
2. 评测报告记录 name + version + 数据集 digest；
3. 通过后 `set_alias(name, "production", 3)`；
4. 回滚把 alias 指回旧版本；
5. trace tag 记录 prompt name 与解析后的 version；
6. 删除版本仅在无引用且过保留期后，且保留审计。

**题：为什么 Assessment 不能只用 tag？**

参考：缺类型、缺来源、缺时间语义、不能多维度、不能范围查询/聚合。

## H.14 第 34 章

**题：将 2.x stage 迁移为 alias 的脚本要点。**

参考：

- 读取所有模型版本与当前 stage；
- 为每个 stage 映射 alias（Production→champion、Staging→candidate）；
- 处理多个版本同 stage 的情况（取最大版本并记录告警）；
- 部署配置改为 `models:/name@alias`；
- 保留旧 stage 字段一段时间，双读单写；
- 回滚时恢复 alias 指针，而不是依赖 stage。

## H.17 第 37 章

**题：工作区加 RBAC 之后，为什么仍可能越权？列出三条路径。**

参考：

1. 鉴权前解析资源：先按 ID 查出对象，再检查 workspace，期间已经返回了存在性/内容；
2. artifact/缓存 key 不带 workspace，跨租户命中同一文件或缓存；
3. 子资源权限只校验父资源：能读 experiment 就顺带读到 trace/assessment，未对 trace 单独 DENY。

**题：Gateway 预算在多副本下为什么容易超支？**

参考：预算计数在进程内存，每个副本各自认为“还剩 1 美元”；必须用 Redis/数据库原子扣减，并在扣减失败时拒绝请求；告警 webhook 不能替代原子性。

## H.18 第 38 章

**题：为什么 Webhook 投递是“至少一次”，接收方需要做什么？**

参考：HTTP 响应可能丢失（请求已成功但调用方超时），因此发送方会重试；接收方必须按 `X-Mlflow-Delivery-ID` 做幂等，先验签/校验时间窗，再处理业务并记录 delivery id。不能假设事件只来一次，也不能假设到达顺序。

**题：事务性 outbox 要解决什么问题？**

参考：如果业务写入先提交、事件入队在提交之后，进程在两者之间崩溃会丢事件。事务性 outbox 把业务变更和 delivery 插入放在同一个数据库事务里；提交后 dispatcher 才可见。需要改 store 方法/事务边界，并测试“事务回滚时 outbox 也不留行”。

## H.19 第 39 章

**题：什么时候用确定性 scorer，什么时候用 judge？**

参考：能用规则/结构/精确匹配判断的先用确定性 scorer（便宜、可复现、可解释）；语义正确性、语气、政策合规等无法规则化的维度再用 judge，并固定 judge 模型/温度/prompt、做人工校准与一致性检查。

**题：为什么 trace 里要记录 prompt 的解析后版本，而不只是 alias？**

参考：alias 会移动，只记 `production` 无法回答“这次请求到底用了哪一版模板”；应记录 prompt name + resolved version（以及数据集 digest、模型版本），否则评测/事故回溯不可复现。

## H.20 第 40 章

**题：为什么 LoggedModel 的 `source_run_id` 用 `ON DELETE SET NULL`，而 `experiment_id` 用 `ON DELETE CASCADE`？**

参考：实验是模型的所有者，实验被物理删除时模型元数据失去归属，应一起清理；run 只是“出生记录”，模型的生命周期可以长于 run，删除 run 不应带走模型。反过来会导致“删 run 丢模型”或“删实验留下孤儿模型”。

**题：为什么模型指标最新值要按 `step DESC, timestamp DESC`，而不是只按 timestamp？**

参考：训练脚本可能补写低 step 的历史点；只按 timestamp 会让补写的历史点覆盖最新进度。先按 step 再按 timestamp 符合“进度优先”的语义，也是 3.18 的行为变化。查询必须用窗口函数或等价的相关子查询，不能简单 `MAX(timestamp)`。

**题：搜索方言为什么拒绝 `tags.*`、`OR` 和一元 `NOT`？**

参考：官方搜索指南写“No Tag Support”，但实现/docstring 又有 `tags.*` 示例（已知文档矛盾 mlflow#17920）；Mini 选择按指南不支持，并在第 40.10 节标注差异。`OR`/`NOT` 同样只保证 AND 组合。窄方言的目的是避免“本地能跑、目标版本报错”，不是声称真实平台一定不支持；上线前要在锁定版本上实测。

## H.21 第 41 章

**题：`--serve-artifacts` 解决了什么问题，代价是什么？**

参考：客户端不再需要对象存储凭证，artifact 通过 MLflow 的 `/mlflow-artifacts/` 端点代理；代价是字节穿过 server 进程，占用 worker 的内存/带宽，超大模型应考虑直连对象存储或独立 artifact 服务。

**题：为什么升级顺序是“备份 -> 副本 db upgrade -> 服务端 -> 客户端”？**

参考：schema 迁移不可逆时，备份是唯一回退路径；先在副本验证迁移能发现锁表/耗时/数据问题；服务端先升级才能读新格式；客户端最后升级并遵循“先读后写”，避免新写入让旧版本读不了。

## H.22 第 42 章

**题：为什么 `/ping` 与 `/health` 要分开？**

参考：`/ping` 只证明 HTTP 进程能响应，适合 liveness；`/health` 应证明模型已加载、依赖可用，适合 readiness。混用会让模型还在加载时流量就被打进来，或者在依赖故障时把本可服务的副本重启掉。

**题：为什么 `instances` 的 `list[list]` 必须能从签名/特征名推断列顺序？**

参考：位置数组本身没有列名；如果服务端随便猜顺序，训练/服务列顺序漂移会给出稳定但错误的预测，而且不会报错。没有签名或特征名时应该拒绝，而不是猜。

**题：动态批处理的最大批次与最大等待时间如何影响 p50/p99？**

参考：增大批次提高吞吐/GPU 利用率，但请求要在队列里等更久，p99 变差；减小等待降低延迟但批次变小、吞吐下降。要用压测画吞吐-延迟曲线，并按业务 p99 目标选参数。

## H.23 第 43 章

**题：为什么流失预警要用排序/概率而不是硬分类？**

参考：干预容量有限（例如每天 50 人），业务需要按风险排序并选择阈值；硬分类丢掉排序信息，也无法按成本调整阈值。概率还便于校准和按业务成本做决策。

**题：为什么部署清单要固化版本 + digest，而不是只记录 alias？**

参考：alias 会移动；只记录 `champion` 无法回答“当时到底加载了哪个版本”。固化 version + digest 才能复现、归因和回滚，也能发现“重启后悄悄换了模型”。

**题：线上反馈为什么不能直接当成训练标签？**

参考：反馈有选择偏差（只有被干预的客户才有结果）、标签延迟、干预本身影响结果；直接回流会把偏差和因果混淆。应把预测、标签、反馈分开存储，经过实验设计/偏差校正后再进入训练或评测。

## H.24 第 44 章

**题：为什么数据集 digest 不包含 name 与 tags？**

参考：name/tags 是检索与治理标签，不是内容。把名称算进 digest 会让“同一批样本换名”被误判为内容变化；反过来，内容相同、标签不同应当能被识别为同一数据。需要区分“逻辑数据集”时，用 dataset_id + version，而不是改 digest 定义。

**题：并发 merge 为什么不能只靠数据库事务？**

参考：事务保证写入原子，但 digest/schema/profile 是在事务外基于旧快照计算的。两个写者都读到 v1、各自算出“v1+新增”的 digest，后提交者会写回不包含先提交者记录的摘要。Mini 用 version CAS 让后提交者发现快照过期并重算；生产还要考虑多进程/多数据库的行锁与重试预算。

**题：真实 MLflow 的 `merge_records` 按 inputs 哈希去重，Mini 为什么选择追加？**

参考：追加实现简单、顺序明确、不会静默覆盖人工 expectation；代价是重复样本会放大权重、重试可能重复写入。迁移到真实 MLflow 前必须对账，因为去重后记录数与 digest 都会变化。练习 1 要求在 Mini 上补去重语义。

## H.25 第 45 章

**题：为什么 PSI 高不等于模型性能下降？**

参考：PSI 只说明输入分布变了。如果新样本仍落在模型学得好的区域，性能可能不变甚至更好；反过来，输入没变但标签定义变了，性能也可能下降。监控应把数据漂移、预测漂移、延迟标签性能和业务指标分开记录，再用决策矩阵判断动作。

**题：为什么 Mini 的基线要保留最多 2000 个样本值，而不是只存直方图？**

参考：直方图只能在分箱边界比较 CDF；当特征取值很少或并列值很多时，用边界重建会得到虚假的 KS 距离。保留一个有界样本可以做真实两样本 KS，同时控制 baseline JSON 的大小。代价是 KS 仍是抽样估计，生产可用 reservoir/sketch。

**题：小样本窗口为什么不能直接 ALERT？**

参考：2 条记录的 PSI/KS 波动极大，可能是抽样噪声。Mini 用 `min_samples_warn` 把结论降级为 WARN，并保留原因；生产还应计算置信区间、设置最小样本门槛，或把窗口合并到足够大再判断。

**题：设计一条“新类别 enterprise 激增”的处置链。**

参考：先确认上游套餐/字段变更，再决定是否回退到规则策略；同时检查模型对新类别是否有默认行为。修数据（映射/回填）后，重新评估基线并走灰度；不要直接自动重训。详见 45.7 的事故复盘示例。

## H.26 第 46 章

**题：为什么会话级 assessment 通常挂在第一条 trace，而不是最后一条？**

参考：首条 trace 是会话的稳定锚点，会话开始时就能确定；挂最后一条要等会话结束，且最后一条可能被单独删除/归档。挂首条使 `search_traces(assessments.*)` 能一次命中整个会话，UI 也能从会话入口直接看到总评。代价是首条被删除会丢锚点，生产要禁止单独删除或另建 session 资产。

**题：模拟用户通过、线上仍失败，可能是什么原因？**

参考：模拟器的目标/人格/停止条件与真实用户不同；训练/评测集选择偏差；模拟器与目标检查器同源导致“自洽但不真实”；线上工具/环境/权限与测试环境不同；采样只覆盖了正常路径。模拟只证明“在写下的假设下稳定”，不能替代真实反馈与线上分诊。

**题：在线评分为什么必须按会话采样，而不是按 trace？**

参考：多轮结论依赖完整上下文；只抽中一条 trace 会得到不完整输入。按 trace 采样还会让同一会话的不同轮次一半评分、一半不评分，无法比较。按 session 采样并让同一会话共享采样结果，才能保证结论一致与幂等。

**题：`assert_improved` 为什么要求至少 6 对样本？**

参考：样本太少时，bootstrap 区间与 p 值都不稳定，容易把噪声当成改进。真实 MLflow 将不足 6 对标记为 `insufficient_pairs` 并让门禁失败（fail closed）；Mini 对齐这一语义。6 只是下限，生产建议 ≥30 并预注册主指标。

**题：Issues 的规则检测与 LLM 聚类各自适合什么？**

参考：规则检测可解释、零模型成本、适合工具失败/超时/错误签名；LLM 聚类能合并语义相似但字面不同的失败，但成本高、有误报、需要模型访问与人工反馈校准。生产常用“规则打底 + 模型增强 + 人工分诊”，而不是二选一。

**题：Skill Registry 与 MCP Registry 的治理差异是什么？**

参考：MCP 管“Agent 能调用什么工具/上下文”，风险在远程服务、权限与工具 schema 漂移；Skill 管“Agent 知道怎么做的指令/脚本包”，风险在任意代码执行、提示注入与来源不可信。两者都需要版本固定、来源白名单、diff 审查、权限最小化与撤销机制。

## H.27 第 47 章

**题：为什么 RAG 评测要先量检索，再看答案？**

参考：答案错误可能来自检索没召回、排序太靠后/上下文截断、或模型没按上下文回答。只看最终答案无法区分这三层，也就无法决定换 embedding、调分块、改 Prompt 还是换模型。`recall@k`/`precision@k`/`MRR`/`nDCG` 把检索层单独量出来，再与 `must_include`、citation F1、groundedness 对照，才能定位问题。

**题：v2 的 `must_include` 从 0.375 升到 1.0，grounding 却从 1.0 降到 0.809，应该发布吗？**

参考：不能只看一个指标。先看下降来自哪里（示例中“下一步”引入了上下文外词项）、是否影响高风险切片、citation 是否提升、成本/延迟是否可接受。若 grounding 下降只是“建议性文本”造成，且人工抽检通过，可以发布但要在评审记录中说明；若下降来自编造事实，则必须修复。发布门禁应按风险给指标分配权重，而不是追求单一总分。

**题：为什么在线评分要按 session 采样并用确定性 hash？**

参考：会话级结论依赖完整上下文，按 trace 采样会得到不完整输入；按 session 采样能保证同一会话共享采样结果。确定性 hash（source_id + scorer + session_id）让重跑不会把会话从样本里翻进翻出，配合 assessment 幂等写入，避免重复计费与结论跳变。错误/慢/负反馈流量应强制全采。

**题：Prompt、模型路由、索引、judge 四类变更，回滚方式有什么不同？**

参考：Prompt 回滚是 alias 指回 previous；模型路由回滚是 Gateway 配置回滚并失效缓存；索引回滚是切回旧索引快照（可能需要重建/双写）；judge 回滚是停用新 scorer 并恢复旧版本。四者证据与影响面不同，不能混成一次“发布”；同时变更会让因果归因失效。

**题：BM25 的 `recall@2=1.0` 能说明检索很强吗？**

参考：不能。示例只有 8 个单文档、可回答的问题，黄金集太容易；真实项目要加入多文档综合、同义改写、拼写错误、中英混合、无答案应拒答、权限过滤与时效冲突。`k` 越大越容易高，报告必须绑定 `k`、数据版本与切片。
