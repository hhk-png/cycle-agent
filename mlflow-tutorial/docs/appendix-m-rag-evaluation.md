# 附录 M 检索与 RAG 评测手册：从 recall@k 到 groundedness

> 第 47 章把知识助手的交付链跑通了；本附录把其中最容易被“感觉”带偏的部分——检索与 RAG 评测——拆成可计算、可复核、可写进 CI 的指标。所有公式都能在 `mini_mlflow/rag.py` 找到实现，`tests/test_rag.py` 给出边界用例。这里讨论的是度量方法，不是某个模型的排行榜。

## M.1 为什么检索评测先于回答评测

RAG 的答案错误至少有三类来源：

```text
① 检索没召回（retrieval miss）
② 检索召回了，但排序太靠后/上下文被截断（ranking/context miss）
③ 上下文对了，模型没按上下文回答（generation miss）
```

如果只看最终答案，这三类会混成一个“准确率下降”，你无法决定是该换 embedding、调分块、改 Prompt，还是换模型。先量检索，能把问题切小：

| 现象 | 检索指标 | 回答指标 | 优先排查 |
|---|---|---|---|
| 答案缺关键事实 | `recall@k` 低 | `must_include` 低 | 分块/索引/同义词/ACL |
| 答案引用了无关文档 | `precision@k` 低 | `citation_f1` 低 | 排序/rerank/噪声文档 |
| 正确文档排在第 8 位 | `MRR@k`/`nDCG@k` 低 | 取决于 k | rerank/上下文预算 |
| 检索对，答案仍错 | 检索指标正常 | groundedness 低 | Prompt/模型/上下文顺序 |
| 答案对但没引用 | 检索正常 | `citation_f1=0` | 输出格式/Prompt/校验 |

这张表是排查顺序，不是因果证明。最终仍要看 trace 与人工抽检。

## M.2 四个检索指标：定义、手算与陷阱

设一个 query 的相关文档集合为 \(R\)，检索返回的有序列表为 \(L\)，截断长度为 \(k\)。

### M.2.1 Recall@k

\[
\mathrm{Recall@}k = \frac{|L_{1:k} \cap R|}{|R|}
\]

例子：\(R=\{b,d\}\)，\(L=[a,b,c]\)，\(k=3\) → 命中 \(b\) → \(1/2=0.5\)。

陷阱：

- \(k\) 越大越容易高，但上下文成本也越高；报告必须写 \(k\)。
- 一个 query 有多个相关文档时，召回一个不等于召回全部。
- 如果知识库里没有答案，\(R=\emptyset\)，recall 无定义；这类问题应单独统计“正确拒答率”，不要塞进 recall。

### M.2.2 Precision@k

\[
\mathrm{Precision@}k = \frac{|L_{1:k} \cap R|}{k}
\]

例子：\(L=[a,x]\)，\(R=\{a\}\)，\(k=2\) → \(1/2=0.5\)。

陷阱：

- 分母是 \(k\)，不是 `len(L)`。检索只返回 2 条却要求 top-5 时，不能假装上下文已填满。
- 相关文档很多时，precision 会低估“只要有一条正确就够”的场景；要和业务目标对齐。

### M.2.3 MRR@k

\[
\mathrm{MRR@}k = \frac{1}{\mathrm{rank}_{\text{first relevant}}}
\]

例子：\(L=[x,b]\)，\(R=\{b\}\)，\(k=2\) → 第一个相关在第 2 位 → \(1/2=0.5\)。

陷阱：

- 只奖励“第一个相关”，忽略其余相关文档；适合“只需要一条证据”的问答，不适合多文档综合。
- 没有相关文档在 top-k 时记为 0，不是“不计算”。

### M.2.4 nDCG@k（二值相关性）

\[
\mathrm{DCG@}k = \sum_{i=1}^{k} \frac{\mathrm{rel}_i}{\log_2(i+1)},\quad
\mathrm{nDCG@}k = \frac{\mathrm{DCG@}k}{\mathrm{IDCG@}k}
\]

其中 \(\mathrm{rel}_i \in \{0,1\}\)，IDCG 是把所有相关文档排在最前面时的 DCG。

例子：\(L=[x,a]\)，\(R=\{a\}\)，\(k=2\) → DCG \(=1/\log_2(3)\approx0.6309\)，IDCG \(=1\)，nDCG \(\approx0.6309\)。

陷阱：

- 二值 nDCG 无法表达“部分正确”；要分级相关性，必须先有标注 rubric。
- IDCG 的分母取决于 \(|R|\) 与 \(k\)，实现不一致会让跨团队数字不可比。
- 排序位置越靠后，折损越强；这对“上下文窗口有限”的 RAG 是合理的。

### M.2.5 聚合与切片

不要只报总体均值。至少同时报：

- 总体均值；
- 按 `slice`（政策/账户/物流/数据）的均值与样本量；
- 最差切片的均值；
- 失败 case 的原始 query、检索结果、期望文档。

Mini 的 `retrieval_report()` 返回总体四个指标 + 每 query 行，方便按切片二次聚合。

## M.3 BM25 的实现细节与边界

Mini 的 `BM25Index` 是教学实现，但保留了生产检索的几个关键决策：

```text
score(q,d) = Σ_t idf(t) · tf(t,d)·(k1+1)
             / (tf(t,d) + k1·(1-b+b·|d|/avgdl))
idf(t) = ln(1 + (N-df(t)+0.5)/(df(t)+0.5))
```

### M.3.1 分词

- 英文按 `[a-z0-9]+` 切分，做轻量复数折叠（`refunds → refund`）；
- 中文按连续汉字切 bigram（`退款政策 → 退款/款政/政策`）；
- 不做词干化/停用词删除，避免把 `not` 删掉导致语义反转。

生产要点：

- 离线索引与在线查询必须用**同一个**分词器版本；换分词器等于换索引，要重建并重跑黄金集；
- 同义词/缩写要显式扩展，不要指望 BM25 自己懂；
- 多语言要按语言路由或分字段索引，混在一起会被高频语言淹没。

### M.3.2 参数

| 参数 | 作用 | 调参风险 |
|---|---|---|
| `k1` | 词频饱和速度 | 太大让长文档/重复词占优 |
| `b` | 文档长度归一化 | 0 不归一化，1 完全归一化 |
| `k` | 返回条数 | 与上下文预算、延迟、成本耦合 |

Mini 默认 \(k1=1.5, b=0.75\)，并对参数做有限性/范围校验。生产要用黄金集调参，不要用“感觉”。

### M.3.3 为什么 BM25 仍然值得保留

- **可解释**：能说清为什么这篇文档被召回；
- **确定性**：CI 可重复，适合做回归基线；
- **便宜**：每次提交跑全量黄金集也不心疼；
- **互补**：hybrid 检索里 BM25 补向量模型对稀有词/编号/缩写的短板。

把 BM25 当“必须被替换的旧技术”是误解；它更像“检索的单元测试”。

## M.4 分块、元数据与 ACL

### M.4.1 分块

| 决策 | 太小 | 太大 |
|---|---|---|
| 召回 | 语义碎片，答案缺上下文 | 主题被稀释，排序变差 |
| 生成 | 模型看不到完整条件 | 浪费 token，引入噪声 |
| 引用 | 引用到半句话 | 引用整篇，无法定位 |

实践起点：200–500 tokens，10–20% overlap；用黄金集测 `recall@k` 与答案质量，再调。表格、代码、政策条款要按结构切，不要按固定字符数硬切。

### M.4.2 元数据

每块至少带：

```text
doc_id, parent_id, chunk_index, source_uri, version,
effective_at, tenant, acl, lang, checksum, owner
```

元数据不是“存着好看”，它决定：

- 能不能在检索前过滤（ACL/租户/时效）；
- 能不能在答案里生成可核对的引用；
- 能不能在文档更新后判断旧引用是否还有效；
- 能不能做切片评测（按来源/语言/业务域）。

### M.4.3 ACL 的顺序

正确顺序：

```text
query → 解析用户/租户 → 检索（带 ACL 过滤）→ rerank → 上下文 → 生成 → 输出校验
```

错误顺序：

```text
检索全库 → 生成 → 在输出里删掉无权内容
```

后者不仅泄露风险高，还会让模型在无权内容上“推理”，即使最终不显示，也可能通过引用/措辞泄露。ACL 要下推到索引层，并在服务端复核。

## M.5 回答指标：must_include、token F1、ROUGE-L

### M.5.1 must_include

最实用的下限指标：答案必须包含某些事实/数字/拒绝词。

优点：可解释、便宜、适合政策/金额/日期。

缺点：同义表达会漏判（“30 天” vs “一个月”），也可能被“提到但否定”骗过（“不是 30 天”包含“30 天”）。

改进：

- 用多条 must_include / must_not_include；
- 对数字做归一化（30 days / 30-day / 三十天）；
- 对否定做规则或 judge 复核；
- 高风险场景不要只用字符串包含。

### M.5.2 token F1 与 ROUGE-L

token F1：

\[
F_1 = \frac{2PR}{P+R}
\]

其中 \(P\) 是预测 token 中与参考重合的比例，\(R\) 是参考 token 被覆盖的比例。ROUGE-L 用最长公共子序列，能容忍一定语序变化。

适用：短答案、抽取式问答、模板化输出。

不适用：长答案、同义改写、需要推理的结论、引用/格式很重要的答案。示例中 v2 的 token F1 只比 v1 略高，但 `must_include` 和 `citation_f1` 天差地别——这说明单一字面指标会误导。

## M.6 引用与 groundedness

### M.6.1 引用指标

设期望证据集合为 \(E\)，答案引用集合为 \(C\)：

\[
P = \frac{|C \cap E|}{|C|},\quad
R = \frac{|C \cap E|}{|E|},\quad
F_1 = \frac{2PR}{P+R}
\]

- 引用无关文档算假阳性；
- 少引一个必要文档算假阴性；
- 没有引用时 \(P=R=F_1=0\)，不是“无定义”。

Mini 的 `citation_metrics()` 采用这个严格定义。它适合做“引用完整性”门禁，但**不能证明引用支持结论**：引用了正确文档、答案却与文档矛盾，citation F1 仍然是 1。

### M.6.2 词项 groundedness 的下限

Mini 的 `grounding_report()` 计算答案内容词项在上下文中出现的比例：

\[
\mathrm{grounding} = \frac{\text{answer tokens present in context}}{\text{answer tokens}}
\]

它会忽略引用标记与常见停用词，保留否定词。用途：

- 抓“上下文里根本没有的数字/实体/URL”；
- 作为廉价 CI tripwire；
- 给人工复核排序。

它不能：

- 判断语义蕴含；
- 发现“用上下文词拼出的错误结论”；
- 处理同义词/跨语言；
- 替代 judge 或人工。

示例中 v2 的 grounding 从 1.0 降到 0.809，因为“下一步”引入了上下文外词项。这不是缺陷，而是提醒：**grounding 是维度，不是总分**。

### M.6.3 更强的 groundedness

生产可组合：

1. **NLI/蕴含模型**：判断 context 是否蕴含 answer；
2. **LLM judge**：给“每个结论是否有引用支持”打分；
3. **人工抽检**：高风险/低分样本；
4. **引用对齐**：把答案句子映射到引用段落，检查支持关系。

每种都有成本与偏差；不要用一个分数代替全部证据。

## M.7 LLM judge：校准、偏差与成本

judge 的工程化清单：

```text
[ ] 固定模型、版本、Prompt、温度、最大 token
[ ] 用 100–300 条人工标注校准
[ ] 报告准确率、混淆矩阵、Cohen's kappa
[ ] 检查位置偏差（A/B 顺序）
[ ] 检查长度/风格偏差
[ ] 记录 judge 的输入、输出、理由、成本
[ ] 失败/超时 fail closed 或转人工
[ ] 定期重校准（模型/数据/业务变化后）
```

常见错误：

- 用 judge 调 Prompt，再用同一个 judge 评测 → 过拟合 judge；
- 只报平均分，不看 judge 与人工的分歧样本；
- judge 的 Prompt 里泄露了“期望答案”；
- 把 judge 当确定性指标，忽略其随机性与版本漂移；
- 不记录 judge 成本，导致评测预算失控。

## M.8 样本量、置信区间与配对比较

### M.8.1 为什么需要区间

8 个 case 上 0.375 → 1.0 看起来很大，但样本少时不确定性也大。配对 bootstrap 的做法：

1. 对每个 case 计算差值 \(d_i = \text{candidate}_i - \text{baseline}_i\)；
2. 有放回重采样 \(n\) 次，计算每次的均值；
3. 取 2.5%/97.5% 分位数作为 95% CI；
4. 用 bootstrap 分布估计 p 值。

Mini 的 `compare_paired()` 使用 percentile bootstrap；真实 MLflow 3.18 的 `compare_evaluations` 使用 BCa 区间与 t 检验，并把少于 6 对标记为 `insufficient_pairs`。两者都是近似，结论要看 CI 与业务代价，不要只看 p 值。

### M.8.2 配对的意义

配对要求两个版本在**同一批 case、同一份数据、同一套判定**上比较。否则：

- 数据不同 → 差异可能来自样本；
- 判定不同 → 差异可能来自标尺；
- 顺序不同 → 缓存/状态可能影响结果。

### M.8.3 多重比较

同时看 10 个指标/切片，至少有一个“显著”的概率会上升。做法：

- 预注册主指标，其余为诊断指标；
- 用 Bonferroni/Holm 或 FDR 校正；
- 对切片结论标注样本量；
- 不把“某个切片 p<0.05”直接当成发布依据。

### M.8.4 实际显著性

统计显著不等于业务显著。发布门禁要同时看：

- 效应量（提升多少）；
- 成本（token/延迟/人工）；
- 风险（最差切片、安全集）；
- 可逆性（回滚成本）。

## M.9 黄金集治理：切片、泄漏、刷新

### M.9.1 切片

至少按以下维度切片：

- 业务意图（政策/账户/物流/数据）；
- 难度（单文档/多文档/需要推理）；
- 语言/表达（标准/口语/中英混合/拼写错误）；
- 风险（安全/合规/高金额）；
- 来源（真实/模拟/对抗）。

每个切片至少 20–50 条，才能谈“这个切片变好了”。总体 0.9 可能掩盖某个切片 0.4。

### M.9.2 泄漏

检查：

- 黄金问题是否出现在 Prompt few-shot / 微调数据 / 文档示例里；
- 参考答案是否直接来自当前 Prompt 的输出；
- 评测集是否被用于调参（如果是，它就不再是 holdout）；
- 训练/索引/评测的时间切分是否未来数据泄漏。

### M.9.3 刷新

黄金集会过期：

- 政策/价格/产品变化；
- 用户表达变化；
- 模型/检索能力变化；
- 新风险出现。

治理：

- 数据集版本 + digest；
- 变更记录与 owner；
- 定期抽样复核；
- 旧版本保留，支持历史报告复现；
- 删除/更正走审批，不直接改历史。

## M.10 Mini 的实现与限制

| 能力 | Mini | 生产 |
|---|---|---|
| 检索 | BM25，内存索引 | hybrid/向量、增量索引、分布式 |
| 分词 | 英文+复数折叠、中文 bigram | 模型分词器、多语言、同义词 |
| 指标 | recall/precision/MRR/nDCG、citation、词项 grounding | 分级相关性、NLI、judge、人工 |
| 比较 | percentile bootstrap | BCa、t 检验、多重比较校正 |
| 数据 | SQLite 数据集 + digest | 湖仓/对象存储、血缘、权限 |
| 规模 | 单机、小样本 | 分布式评测、采样、成本控制 |

`tests/test_rag.py` 覆盖：

- BM25 排序、tie-break、无重叠、元数据过滤、参数校验；
- recall/precision/MRR/nDCG 的边界；
- `retrieval_report` 的长度/空集校验；
- 引用提取、precision/recall/F1；
- grounding 的支持/不支持词项、引用忽略、Document 输入。

这些测试证明“公式实现正确”，不证明“指标适合你的业务”。后者只能靠真实数据与人工校准。

## M.11 检查清单

```text
[ ] 每个 query 的 k 固定并写进报告
[ ] 检索/回答/运营三层指标都有
[ ] 至少一个“无答案应拒答”切片
[ ] 至少一个“多文档综合”切片
[ ] citation 的期望证据集合有明确来源
[ ] groundedness 的上下文就是模型实际看到的上下文
[ ] judge 已校准并记录版本/成本
[ ] 配对比较使用同一批 case 与同一判定
[ ] 多重比较有校正或预注册主指标
[ ] 黄金集 digest 进入评测运行与发布证据
[ ] 失败 case 可回放到 trace
[ ] 指标下降时能定位到检索/排序/生成哪一层
```
