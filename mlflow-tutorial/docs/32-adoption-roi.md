# 第 32 章 采用策略、ROI 与组织落地：从试点到平台化

## 学习目标

- 用成熟度模型判断组织当前阶段，避免“一刀切上平台”。
- 设计 90 天试点，以可量化收益换取继续投入。
- 计算实验追踪/模型治理的 ROI，并识别隐藏成本。
- 处理利益相关者、流程与反模式，让工具真正被使用。

## 32.1 成熟度模型

| 阶段 | 特征 | 主要痛点 | 优先动作 |
|---|---|---|---|
| L0 手工 | 文件/Excel/Notebook | 找不到结果 | Git + 命名 + 最小 run 记录 |
| L1 可追踪 | 有 Tracking | 指标口径不一、无发布治理 | 模板/标签/评测基线 |
| L2 可复现 | 数据/环境/代码可追溯 | 模型上线靠人 | Registry + 审批 + CI |
| L3 可治理 | 版本/别名/审计 | 规模化/多团队/成本 | 多租户/配额/平台化 |
| L4 平台化 | 自助、SLO、生态 | 平台团队瓶颈 | 产品化/内部计费/联邦 |

不要从 L0 直接买 L4 平台；先把命名、数据和评测基线补齐。

## 32.2 利益相关者

| 角色 | 关心 | 阻力 |
|---|---|---|
| 数据科学家 | 不打断工作流、易用 | 额外记录负担 |
| ML 工程师 | 可部署、可回滚 | 迁移/集成成本 |
| 平台团队 | 运维/SLA/成本 | 需求分散 |
| 安全/合规 | 权限/审计/数据驻留 | 开源治理不足 |
| 财务 | 成本/ROI | 难以量化收益 |
| 管理层 | 上线速度/风险 | 看不到短期回报 |

策略：

- 用“减少找结果/回滚时间”打动一线；
- 用“审计/回滚证据”打动合规/管理；
- 用“减少重复平台建设”打动架构；
- 用试点数据打动财务。

## 32.3 90 天试点

### 第 1–2 周：基线与范围

- 选 1–2 个真实项目（不要选最复杂的）；
- 记录当前痛点指标：找结果时间、复现失败率、上线周期、回滚时间；
- 定义成功标准（例如“找结果从 30 分钟降到 3 分钟”）。

### 第 3–6 周：最小闭环

- 统一 Experiment/Run 命名；
- 模板：参数/指标/artifact/模型签名；
- 接入 CI：评测门槛；
- 注册 1 个模型，设置 alias；
- 部署到 staging。

### 第 7–10 周：治理

- 审批/证据；
- 回滚演练；
- 权限/审计（至少最小）；
- 成本/容量估算；
- 文档/培训。

### 第 11–12 周：评估

- 对比基线指标；
- 收集用户反馈；
- 决定扩展/停止；
- 写复盘。

## 32.4 ROI 计算

### 可量化收益

```text
时间节省 = 人数 × 每周节省小时 × 周数 × 人力成本
事故减少 = 事故数下降 × 平均事故成本
上线加速 = 提前上线天数 × 每日业务价值
重复建设避免 = 自建平台人力/云成本
```

### 成本

```text
平台成本 = 软件/托管 + 云资源 + 运维人力 + 培训 + 迁移 + 机会成本
```

### 示例（假设，仅演示）

```text
50 名算法工程师，每周节省 1 小时 → 50×1×50×$80 = $200k/年
每年减少 2 次重大事故，每次 $150k → $300k/年
上线提前 10 天，业务价值 $20k/天 → $200k/年
总收益 ≈ $700k/年

平台成本：
  托管/云 $150k + 运维 0.5 FTE $100k + 培训/迁移 $50k = $300k/年
ROI ≈ (700-300)/300 = 133%
```

不要直接引用这些数字；替换成你的真实数据，并做敏感性分析。

### 难以量化

- 审计通过；
- 招聘/留存；
- 协作质量；
- 决策速度；
- 风险降低。

用 proxy 指标（审计准备时间、回滚 MTTR、实验复用率）。

## 32.5 成功指标

领先指标：

- 活跃用户/周；
- 记录 run 的项目比例；
- 模板使用率；
- 模型注册率；
- 评测覆盖率；
- 文档访问。

滞后指标：

- 上线周期；
- 回滚 MTTR；
- 事故率；
- 重复实验率；
- 审计发现数；
- 平台成本/模型。

避免只用“run 数量”作为成功指标：它可能鼓励刷量。

## 32.6 Build vs Buy

| 因素 | 自建 | 购买/托管 |
|---|---|---|
| 数据驻留/合规 | 可控 | 依厂商 |
| 定制/集成 | 高 | 中 |
| 运维负担 | 高 | 低 |
| 成本 | 前期低/长期人力 | 可预测/随用量 |
| 上市速度 | 慢 | 快 |
| 锁定 | 低 | 中/高 |

决策问题：

1. 这是差异化能力吗？
2. 我们是否已有平台团队/运维能力？
3. 合规是否要求自托管？
4. 3 年 TCO 谁更低？
5. 迁移是否可行？

常见错误：

- 小团队自建“全能平台”；
- 大企业盲目 SaaS 导致合规问题；
- 只算 license 不算人力；
- 不做迁移演练。

## 32.7 组织与流程

必须落地的流程：

- 实验模板/评审；
- 模型注册/审批；
- 发布/回滚；
- 数据/模型保留；
- 安全/合规审查；
- 成本/配额。

RACI 示例：

```text
实验记录：数据科学家 R，Tech Lead A
模型注册：ML Engineer R，发布负责人 A
生产发布：平台/值班 R，业务 Owner A
审计：合规 R，平台 A
```

没有明确 owner 的平台会变成“大家都在用，没人负责”。

## 32.8 反模式

- **工具先行**：没定义指标/流程就买平台。
- **记录负担**：要求每个 cell 都手动 log，导致抵触。
- **只做 UI**：没有 CI/审批/回滚。
- **过度治理**：每个实验都要审批，创新停滞。
- **平台团队瓶颈**：所有接入靠平台团队手工。
- **指标虚荣**：run 数量增长但复用/上线没改善。
- **双轨**：一部分团队用 A，一部分用 B，元数据割裂。

## 32.9 扩展阶段

从 1 个团队到多团队：

1. 模板/自助接入；
2. 命名空间/租户；
3. 配额/成本分摊；
4. 权限/审计；
5. 联邦/内部平台 API；
6. SLO/支持。

不要一次性上多租户；先验证单团队闭环。

## 32.10 案例复盘（虚构）

一家 200 人金融科技公司：

- 现状：80 个模型，Notebook 为主，审计靠人工；
- 试点：2 个风控模型，MLflow + 评测门槛 + alias 发布；
- 结果：找结果 30min→3min，回滚 2h→20min，审计准备 2 周→3 天；
- 扩展：6 个月覆盖 60% 模型，建立平台团队；
- 失败点：最初强制所有实验审批，导致绕过；后来改为“仅生产发布审批”。

教训：

- 治理要分层，探索与生产不同；
- 先解决痛点，再扩展；
- 指标要绑定业务，不是 run 数。

## 32.11 与真实 MLflow 的差距

本章是组织/商业方法，不依赖 Mini 实现；真实落地还需要企业级权限、审计、支持。

## 小结

- 采用要按成熟度分阶段，先闭环再平台化。
- 90 天试点用真实痛点指标证明价值。
- ROI 要包含时间、事故、上线速度和平台成本，并做敏感性分析。
- Build vs Buy 看差异化、合规、运维和 3 年 TCO。
- 流程/owner 与工具同样重要。

## 练习

1. 为你的组织画成熟度评估表，给出下一步 3 个动作。
2. 用真实数据做一次 ROI 计算，列出敏感性因素。
3. 设计一个“探索不审批、生产强审批”的分层治理方案。
