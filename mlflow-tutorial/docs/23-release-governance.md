# 第 23 章 模型注册与发布治理：审批、别名、回滚

## 学习目标

- 设计从“评测通过”到“生产流量”的治理流程。
- 用 alias 表达 champion/canary/shadow，而不是硬编码版本。
- 把审批、证据、回滚和审计变成可执行规则。
- 理解 Registry 的能力边界，避免把它当部署系统。

## 23.1 发布不是一次 API 调用

一个负责任的模型发布至少包含：

```text
训练完成
  → 评测报告（离线/切片/公平性/安全）
  → 制品完整性/签名
  → 审批（人工/策略）
  → 注册版本（source/run/lineage）
  → 部署到 staging
  → 冒烟/回放/影子
  → canary 小流量
  → champion 全量
  → 监控与回滚预案
```

Registry 负责：

- 版本元数据；
- 别名/阶段；
- 标签/描述；
- 来源血缘。

部署系统负责：

- 拉取/验证制品；
- 启动实例；
- 流量切换；
- 健康检查；
- 监控/回滚执行。

## 23.2 别名设计

推荐：

| 别名 | 含义 | 谁可改 |
|---|---|---|
| `champion` | 当前全量生产 | 发布负责人/自动化 |
| `challenger` | 候选 challenger | 训练团队 |
| `canary` | 小流量验证 | 发布自动化 |
| `shadow` | 影子流量（不影响用户） | 算法团队 |
| `previous` | 上一个稳定版本 | 发布自动化 |

规则：

- 生产服务只解析 `champion`，不解析 `latest`；`latest` 是 URI 关键字/保留名，不是可分配的普通 alias；
- `previous` 在每次 champion 切换时更新，用于快速回滚；
- 别名变更必须审计（谁、何时、为什么）；
- 同一别名指向唯一版本；
- 禁止与 URI 语法冲突的名字（如 `latest`、裸数字）；`v1` 这类带前缀名字在真实 MLflow 中可以存在。

Mini 实现 alias 表 `(name, alias) → version`，并拒绝裸数字别名；它没有实现 `latest` 的 URI 关键字语义，迁移时以真实客户端为准。

## 23.3 审批与证据

审批不是“点个通过”，而是检查证据：

- 评测报告（数据版本、指标、切片、置信区间）；
- 与基线的对比；
- 公平性/偏差检查；
- 安全/合规（PII、许可证、模型卡）；
- 资源/成本评估；
- 回滚计划；
- 负责人。

把这些存为：

- run tags（`review_status`、`reviewer`）；
- model version tags（`eval_report_uri`、`approved_by`）；
- artifact（报告、签名、SBOM）；
- 外部工单链接。

Mini 的 tags 足够表达；真实系统可接工单/策略引擎。

## 23.4 策略即代码

示例规则：

```text
- 必须来自 FINISHED 的 run
- 必须有签名
- 测试集 macro-F1 >= 0.80
- 切片最差组 F1 >= 0.65
- p95 延迟 <= 200ms
- 模型大小 <= 2GB
- 依赖无高危 CVE
- 审批人 != 训练者
```

实现方式：

- CI 在注册前调用评测/扫描；
- 注册 API 前置检查；
- 定时对账；
- 不通过则拒绝 alias 提升。

MLflow 本身不内置这些策略；需要周边系统。

## 23.5 发布模式

### 直接替换

- 简单，但风险最高；
- 适合内部低风险模型。

### 蓝绿

- 两套环境，切换流量；
- 回滚快；
- 成本翻倍。

### Canary

- 小比例流量；
- 观察错误率/延迟/业务指标；
- 逐步扩大；
- 需要流量路由与统计显著性。

### Shadow

- 新模型接收复制流量但不影响用户；
- 对比预测分布/延迟；
- 适合高风险场景。

### 回放

- 用历史请求回放；
- 可离线比较；
- 不能完全代表线上分布。

## 23.6 回滚

回滚不是“重新部署旧镜像”这么简单：

- 模型版本 alias 指回 previous；
- 推理服务热加载/滚动重启；
- 特征/预处理版本必须兼容；
- 缓存失效；
- 数据 schema 兼容；
- 记录回滚原因与时间。

回滚演练：

- 定期在 staging 执行；
- 测量 MTTR；
- 确认 previous 仍可加载；
- 确认 artifact 未被 GC。

## 23.7 模型卡与文档

建议每个版本包含：

- 用途/非用途；
- 训练数据来源/时间/许可证；
- 评估指标/切片；
- 已知限制/失败模式；
- 公平性/安全评估；
- 联系人与更新记录。

MLflow 的 model version description/tags 可以存摘要，完整模型卡作为 artifact。

## 23.8 审计

必须能回答：

- 这个版本是谁、何时、从哪个 run 注册的？
- 谁批准？依据是什么？
- 哪个环境在何时使用了哪个版本？
- 回滚到哪个版本？为什么？
- 制品是否被修改？

实现：

- 追加式审计日志；
- alias/version 变更事件；
- 部署系统回写部署记录；
- 制品 digest 校验；
- 访问日志。

Mini 没有审计表；生产应单独设计，不能只依赖应用日志。第 38 章的 Webhook/outbox 可以作为“审计事件外发”的起点，但投递记录本身不是不可篡改审计日志，仍要写入独立审计存储。

## 23.9 责任分离

推荐角色：

```text
训练者：产出 run/模型，提交评测
评审者：检查证据，批准/拒绝
发布者：执行 alias/部署
值班：监控/回滚
安全/合规：抽查/审计
```

同一个人可以兼任小团队角色，但要有“第二双眼睛”的规则（尤其高风险模型）。

## 23.10 与真实 MLflow 的差距

- 真实 MLflow Registry 提供版本/别名/标签/描述/UI，但不提供完整审批流；
- 真实企业通常接 Databricks/云平台/内部发布系统；
- Mini 只实现核心指针与元数据，没有部署/审批/审计。

## 小结

- Registry 是发布指针，不是发布流程。
- alias 表达 champion/canary/shadow/previous，生产不要用 latest。
- 审批要绑定证据，策略要可执行。
- 回滚必须演练，且要考虑特征/预处理/缓存兼容。
- 审计是治理的底线。

## 练习

1. 为 champion 切换设计一个两人审批 + 自动检查的流程。
2. 设计 canary 的放量/回滚判定指标。
3. 如果 previous 版本的 artifact 被 GC，回滚预案如何失效？如何预防？
