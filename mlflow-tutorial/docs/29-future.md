# 第 29 章 MLflow 3 与未来路线：机会、标准与风险

> 本章包含对趋势的判断，不是官方路线图。MLflow 的版本/功能随发布变化，请以官方文档和 release notes 为准。

## 学习目标

- 区分“已经稳定的能力”和“仍在演进的押注”。
- 理解 OpenTelemetry、评测驱动、数据目录/湖仓对 MLflow 的影响。
- 评估未来 1–3 年平台选型的风险。
- 为你的组织制定可调整的技术路线，而不是追逐单点功能。

## 29.1 从“实验追踪”到“AI 控制面”

MLflow 的演进方向大致可以概括为：

```text
Tracking（记录）
  → Models/Registry（交付）
  → Evaluate（质量）
  → Tracing/Prompt/Gateway（GenAI 运行时）
  → 统一 AI 资产/治理控制面
```

驱动力：

- LLM 应用迭代快，传统离线评估不够；
- Agent 系统需要请求级因果；
- 企业需要审计/成本/权限；
- 数据平台（湖仓/目录）希望管理模型与特征资产；
- OpenTelemetry 等标准成熟，降低可观测性接入成本。

## 29.2 已经相对稳定的能力

- Tracking 的对象模型（experiment/run/metric/param/artifact）；
- Model flavor/PyFunc 的基本契约；
- Registry 的版本/别名；
- 项目/模型服务的基本命令；
- REST/客户端的基本形态。

这些能力不会轻易消失，但字段/实现可能变化。基于它们做架构风险较低。

## 29.3 仍在演进的押注

### Tracing 标准化

OpenTelemetry 的 GenAI 语义约定仍在演进。风险：

- 字段名/结构变化；
- 自动埋点覆盖不一；
- 采样/成本语义没有统一；
- 不同厂商对 trace 存储的查询能力差异。

策略：

- 内部定义稳定的 span 类型/关键属性；
- 通过 OTel 适配层导出；
- 不把 UI/查询强绑定到某个字段名；
- 保留原始负载的受控副本。

### Prompt / Eval / Feedback 一体化

Prompt 版本、评测数据集、scorer、人工反馈可能整合为统一资产模型。风险：

- 不同团队的工作流差异大；
- 评测标准难统一；
- 数据隐私/标注成本；
- 供应商锁定。

策略：

- prompt/评测集用可导出的格式；
- scorer 作为代码/配置版本化；
- 保留原始数据与评分记录；
- 不把关键评测只存在某个 SaaS。

### AI Gateway

Gateway 可能成为平台入口。先记住版本事实：MLflow 2.9 把 AI Gateway 改名为 Deployments for LLMs，3.0 移除了独立 deployments server；**但 3.9 起 AI Gateway 以“内嵌在 tracking server”的形式回归**，并陆续加入路由/回退、预算管理、guardrail 与多 provider 支持。因此“开源 MLflow 没有网关”在 3.9+ 已不成立，准确的说法是“网关从独立进程变成了 tracking server 的内置能力”。这部分平台化演进见第 37 章。

风险：

- 单点故障/延迟；
- 密钥集中；
- 路由策略复杂；
- 开源/托管能力差异；
- 供应商锁定与配额。

策略：

- 先解决可观测/成本，再引入路由；
- 评估独立网关（LiteLLM/Envoy/云网关）；
- 明确 fallback/配额/审计；
- 用第 33 章的 Mini Gateway 理解控制面，而不是把它当生产替代。

### 数据目录/湖仓集成

Unity Catalog、Iceberg/Delta、数据目录可能接管模型/特征/血缘。风险：

- 双轨元数据；
- 权限模型冲突；
- 迁移成本；
- 开源版可用性。

策略：

- 明确“系统 of record”；
- 用稳定 ID/URI 关联；
- 定期对账。

## 29.4 评测驱动开发（Eval-driven）

趋势：

- 先写评测集/scorer，再改 prompt/模型；
- CI 中跑回归评测；
- 线上 trace 采样进入评测集；
- 发布门禁基于评测 + 成本/延迟。

影响：

- MLflow 的 Evaluate/Tracing 会成为核心，而不是附属；
- 评测数据治理与版本化变得关键；
- “模型”与“prompt/检索/工具”一起版本化；
- 需要统计显著性与人工校准。

风险：

- 过拟合评测集；
- judge 偏差；
- 评测成本；
- 评测集污染/泄漏。

## 29.5 Agent 与图结构

Span 树适合请求链，但 Agent 可能有：

- 循环/重试；
- 并行分支/汇合；
- 多 Agent 协作；
- 人类介入；
- 长期运行/断点恢复。

未来可能需要：

- 图/事件模型；
- 跨 trace 的会话；
- 状态快照；
- 工具副作用审计；
- 预算/终止条件。

MLflow 的 trace 模型可能扩展，但“树 + 事件”在多数场景已够用。不要为了图而图。

## 29.6 部署与运行时

趋势：

- 模型/prompt/工具作为版本化制品；
- 推理网关与实验追踪解耦；
- 边缘/端侧模型；
- 多模态；
- 成本感知路由；
- 评测/guardrails 在请求路径中。

风险：

- 请求路径变长，延迟/可用性下降；
- 版本组合爆炸；
- 回滚复杂；
- 供应商锁定。

## 29.7 开源治理与商业化

MLflow 由 Databricks 发起并持续投入，社区/基金会治理与商业托管并存。未来风险：

- 开源版与企业版功能差距扩大；
- 云厂商分叉/兼容层；
- 许可证/治理变化；
- 关键功能只在托管版可用。

策略：

- 核心元数据可导出；
- 不依赖单一托管商；
- 关注 release notes/治理公告；
- 对关键路径做替代方案演练。

## 29.8 标准与互操作

值得关注：

- OpenTelemetry GenAI semantic conventions；
- OpenLineage/数据血缘；
- MLCommons/模型卡；
- ONNX/开放模型格式；
- OpenAPI/JSON Schema；
- OCI 模型/制品规范。

标准成熟会降低锁定，但也可能带来“标准很多、互操作很少”的中间态。选型时看实际导出的可用性，而不是只看声明。

## 29.9 未来 1–3 年的务实建议

1. 把 run/模型/prompt/评测集的结构化元数据掌握在自己手里；
2. 用 OTel 兼容的 trace 管道，避免绑死 UI；
3. 评测集/scorer 代码化、版本化；
4. 对 Gateway/托管能力做故障与迁移演练；
5. 保持模型制品可独立加载；
6. 不追每个新功能，先解决数据/权限/成本。

## 29.10 可能失败的方向

- 把所有 GenAI 能力塞进一个“万能平台”，导致复杂度失控；
- 过度依赖自动埋点，产生海量低质量 trace；
- 用 LLM judge 替代人工/业务指标；
- 只做 UI 不做数据治理；
- 忽视成本/延迟，导致上线不可持续。

## 29.11 与真实 MLflow 的差距

本章是判断，不是实现。Mini 只覆盖核心概念和手动 trace；真实路线要以官方为准。3.9–3.18 已经落地的平台能力（工作区、RBAC、MCP Registry、Gateway 预算/guardrail、Review Queue）集中放在第 37 章，本章不再重复预测。

## 小结

- MLflow 正从实验追踪扩展到 AI 控制面，但核心对象仍然重要。
- Tracing/评测/Prompt/Gateway 是主要增量，标准与治理仍在演进。
- 选型要看可导出性、可替代性和总成本，而不是功能列表。
- 评测驱动、Agent 观测、湖仓集成是值得关注的方向。

## 练习

1. 为你的组织写一份“MLflow 3 采用风险清单”。
2. 设计一个 OTel 兼容的 trace 导出层，避免绑定单一后端。
3. 评估“自建 Gateway vs 托管 Gateway”的 3 个关键指标。
