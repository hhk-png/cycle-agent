# 第 1 章 为什么需要 MLflow：从 Notebook 到可复现的生产系统

## 学习目标

- 说清机器学习交付中“实验不可复现”和“模型不可治理”两类问题。
- 用四个问题判断一个团队是否真的需要实验追踪平台。
- 理解 MLflow 的定位：它不是训练框架，也不是推理网关，而是生命周期元数据与模型交付的控制面。
- 识别不该使用 MLflow 的场景，避免为了工具而工具。

## 1.1 一个熟悉的事故

周五下午，数据科学家小陈在 Notebook 里训练出一个欺诈检测模型，F1 从 0.71 提升到 0.78。周一他准备上线，却发现：

- 训练数据是上周从数仓手工导出的 CSV，文件名叫 `data_final_v3(1).csv`；
- 验证集划分的随机种子写在某个已删除的 cell 里；
- 能复现 0.78 的那次训练，超参数只留在 Slack 截图中；
- 线上要用的特征列顺序，和训练时相比少了 `merchant_age`；
- 合规团队问“这个模型是用哪版数据训练的”，没人能给出可核验的答案。

这不是模型能力问题，而是**元数据没有成为一等公民**。训练脚本记录了权重，却没有记录“产生权重的上下文”。

MLflow 的核心价值，是把这些上下文变成结构化、可查询、可关联的数据：

```text
Experiment ──< Run ──< Param / Metric / Tag / Artifact
                 │
                 └──< Model Version ──> Registry ──> Deployment
```

## 1.2 四个问题

判断一个团队是否需要 MLflow，先问这四个问题。

### 问题一：同一个结果能否在另一台机器上复现？

可复现至少需要：

- 代码版本（commit SHA，而不是“最新代码”）；
- 数据版本或数据快照（digest / 分区 / 时间窗口）；
- 运行环境（Python、依赖、CUDA、镜像）；
- 超参数与随机种子；
- 预处理逻辑；
- 评估脚本与指标定义。

MLflow 能记录其中大部分元数据，但它**不会自动保证**数据快照和依赖锁定。它是账本，不是时间机器。把 `mlflow.log_param("git_sha", ...)` 写上，并不意味着代码真的可重建。

### 问题二：100 次实验能不能在一分钟内找到最好的 3 次？

如果答案依赖 Excel、Notebook 文件名和人的记忆，那么实验数量一旦超过几十次，比较成本会指数上升。MLflow Tracking 提供统一的 run 列表、过滤和排序；代价是团队必须约定命名、标签和指标口径。工具解决“存”，方法论解决“可比”。

### 问题三：上线的是哪个模型版本，谁批准的，怎么回滚？

“模型文件在共享盘 `/models/best_final.pkl`”不是版本管理。你无法回答：

- 它是哪个 run 产出的？
- 它依赖哪个特征工程版本？
- 上一个稳定版本是什么？
- 回滚需要改哪一行配置？

Model Registry 用不可变版本 + 可变别名/阶段，把“制品”和“发布指针”分开。这个设计是第 12、23 章的重点。

### 问题四：线上效果变差时，能否追溯到训练与数据？

需要把线上请求/预测、模型版本、训练数据、评测集和代码连成一条链。传统监控只能告诉你“AUC 降了”，不能告诉你“降的是哪个切片、哪个版本、哪次数据刷新之后”。MLflow 的 lineage 字段（run、source、dataset input）是这条链的起点，但完整的可观测性还要接指标、日志和 Trace。

只要有两个以上问题回答“不能”，引入实验追踪就值得；四个都回答“不能”，说明问题已经不是工具能单独解决的，需要先补数据与发布流程。

## 1.3 MLflow 是什么，不是什么

MLflow 官方把自己描述为机器学习生命周期的开源平台，覆盖四类能力（不同版本表述略有差异）：

1. **Tracking**：记录实验的参数、指标、标签、制品和运行元数据。
2. **Models**：用统一的“flavor”打包模型，提供签名、依赖和加载接口。
3. **Model Registry**：管理模型版本、别名/阶段、描述与发布协作。
4. **Projects**：用 `MLproject` 描述可复现的运行入口和环境。

在 MLflow 3.x 时代，还强化了：

- **Tracing**：面向 LLM/Agent 的调用链可观测性；
- **Evaluation**：从传统模型评估扩展到 GenAI 评测；
- **Prompt / 评测数据集 / AI Gateway** 等 GenAI 工作流能力。

它不是：

- 训练框架（不替代 PyTorch、XGBoost）；
- 特征存储（不解决 point-in-time correctness）；
- 推理网关（`models serve` 是开发/验证工具，不是高可用网关）；
- 数据版本系统（不替代 Iceberg/Delta/LakeFS）；
- 权限系统（开源版的鉴权能力有限，企业级 RBAC 往往依赖周边设施）。

理解“不是什么”很重要：把 MLflow 当万能平台，会在数据一致性、权限和在线服务层留下巨大空洞。

## 1.4 一个最小但完整的生命周期

一个负责任的模型交付闭环至少包含：

```text
定义问题与指标
   ↓
准备可追溯的数据快照
   ↓
训练 + 记录 run（参数、指标、数据、代码、环境）
   ↓
固定评估集，生成评测报告与切片指标
   ↓
打包模型（签名、依赖、输入样例）
   ↓
注册版本（来源 run、审批、别名）
   ↓
部署（批量/在线/流式），记录部署版本
   ↓
监控（延迟、成本、质量、漂移）
   ↓
反馈与再训练，形成新版本
```

MLflow 覆盖中间的“记录—打包—注册—部署引用”，并向两端延伸。它不替你做数据工程、特征计算、在线扩缩容和业务监控。

## 1.5 什么时候不该上 MLflow

- **只有一个模型、一次训练、不打算迭代**：一个带哈希的模型文件加一份 README 可能更划算。
- **组织还没有基本的代码与数据版本管理**：先上 Git、数据快照和制品库。追踪平台会把混乱记录得更整齐，但不会减少混乱。
- **强监管且必须使用特定云平台**：先确认云厂商的托管实验追踪是否已满足审计要求，避免双轨。
- **把 MLflow 当模型服务平台**：如果需求是 10 万 QPS、灰度、自动扩缩容和金丝雀发布，应该用 KServe/Seldon/云推理服务；MLflow 的注册表只负责“版本指针”。
- **只需要 Prompt 调试**：轻量场景可能用专门 LLM 可观测性工具更直接；但如果已有 MLflow，统一栈的收益通常更大。

## 1.6 成本与收益的粗略框架

不要用“工具免费”来论证引入。真实成本包括：

- 学习与约定成本：命名、标签、指标口径、保留策略；
- 运维成本：数据库、对象存储、备份、升级、监控；
- 迁移成本：历史 run 和模型版本；
- 机会成本：团队本可以做模型的时间。

收益包括：

- 减少重复实验与“找不到好结果”的时间；
- 缩短审计与上线评审；
- 降低回滚时间；
- 让模型资产可复用。

第 31、32 章会给出可量化的 ROI 模型。这里先记住一个判断：**当“找到并解释一个历史结果”的耗时成为常态痛点时，追踪平台的 ROI 最高。**

## 1.7 与真实 MLflow 的差距

MiniMLflow 复现的是“控制面”的核心对象与交互，不包含真实 MLflow 的：

- 多后端存储（Postgres/MySQL）、对象存储（S3/GCS/Azure）；
- 多租户、OIDC、细粒度权限；
- 与 Databricks/云平台的深度集成；
- 完整的 flavor 生态与自动日志框架；
- 生产级 REST 兼容和数据迁移工具。

这些差距不是实现“偷懒”，而是刻意把不可简化的复杂度留给后续章节讨论。

## 小结

- MLflow 的价值在于把实验上下文与模型交付指针变成可查询的结构化数据。
- 它解决“记录、比较、打包、注册”，不自动解决数据版本、权限和在线服务。
- 先用四个问题判断需求，再决定引入范围。
- 工具必须配合命名、指标和发布流程，否则只会把混乱电子化。
