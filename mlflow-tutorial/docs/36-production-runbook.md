# 第 36 章 生产运维手册：升级、备份、监控与演练

## 学习目标

- 把“能跑”变成“可运营”：知道 MLflow 平台的日常运维对象与故障模式。
- 设计分层的部署拓扑，理解每一层的单点与扩展方式。
- 掌握升级、备份、恢复、监控、限流、密钥轮换的可执行步骤。
- 用故障演练验证假设，而不是等事故来教你。
- 区分 Mini 的边界与真实平台的运维要求。

## 36.1 部署拓扑：按规模分层

### 36.1.1 单机（个人/小团队）

```text
laptop / VM
  mlflow server
    backend: sqlite:///mlflow.db
    artifacts: ./mlartifacts
```

适用：演示、个人实验、低并发。限制：

- SQLite 单写者；
- 本地磁盘无冗余；
- 无 HA；
- 备份 = 复制文件（注意 WAL）。

### 36.1.2 团队（推荐起点）

```text
          ┌──────────────┐
Client ──>│ Load Balancer│
          └──────┬───────┘
                 │
        ┌────────┴────────┐
        │ mlflow server   │  (2+ replicas, stateless)
        │ mlflow server   │
        └────────┬────────┘
                 │
      ┌──────────┴──────────┐
      │ PostgreSQL          │
      │ (metadata)          │
      └──────────┬──────────┘
                 │
      ┌──────────┴──────────┐
      │ Object Store (S3/GCS)│
      │ (artifacts)          │
      └─────────────────────┘
```

要点：

- 跟踪服务端尽量无状态，副本可水平扩展；
- 元数据用托管 Postgres，开备份/PITR；
- artifact 用对象存储，开版本控制/生命周期；
- 客户端通过 LB 访问，不直连数据库；
- 若使用服务端代理 artifact，注意带宽与超时；否则客户端需要对象存储凭据。

### 36.1.3 平台（多团队）

在团队拓扑上增加：

- 独立数据库实例/读写分离；
- artifact 代理层或 CDN；
- SSO/OIDC、RBAC、审计；
- 每团队/每项目的配额与保留策略；
- 独立的 tracing 存储/采样；
- 监控、告警、日志集中化；
- 灾备区域与恢复演练。

## 36.2 升级与数据库迁移

### 36.2.1 升级前检查表

- [ ] 记录当前服务端、客户端、SDK、数据库 schema 版本；
- [ ] 读目标版本的 release notes / breaking changes；
- [ ] 确认客户端与服务端版本兼容矩阵；
- [ ] 备份数据库与 artifact（或确认快照可回滚）；
- [ ] 在 staging 用生产数据副本演练；
- [ ] 准备回滚包与回滚步骤；
- [ ] 通知使用方升级窗口与影响。

### 36.2.2 升级顺序

```text
1. 备份
2. 升级只读副本/报表任务（验证读兼容）
3. 升级服务端（一次一个副本，健康检查通过再下一个）
4. 升级客户端（先升读取路径，再升写入路径）
5. 跑 golden 回归（run/模型/评测/trace）
6. 全量切换
7. 观察 24-72 小时，保留回滚窗口
```

MLflow 3 的兼容规则是“新读旧可以，旧读新不一定”，所以不要反过来先升级写入方。

### 36.2.3 数据库迁移

```bash
# 先备份！
mlflow db upgrade postgresql://user:pass@host/mlflow
```

注意：

- 迁移可能加列/建索引，长时间锁表；在低峰执行；
- 大表加索引要评估锁与磁盘；
- 迁移脚本不可逆时，回滚只能靠备份；
- 多副本服务端不要同时启动迁移；先迁移再滚动升级；
- 记录迁移耗时，纳入下次容量规划。

Mini 的 schema 迁移是 `schema_meta.version` + `CREATE TABLE IF NOT EXISTS`，只适合教学；生产要 Alembic 风格的编号迁移与回滚脚本。

## 36.3 备份与恢复

### 36.3.1 备份对象

| 对象 | 方式 | 频率 | 备注 |
|---|---|---|---|
| 元数据库 | 逻辑备份/物理快照/PITR | 每日 + 持续 WAL | 含 experiments/runs/metrics/registry/prompts |
| Artifact | 对象存储版本控制/跨区复制 | 持续 | 大文件多，优先增量 |
| 配置 | Git/配置中心 | 变更即提交 | 含 gateway 路由、保留策略 |
| 密钥引用 | Secret Manager | 变更即提交 | 不备份明文密钥 |
| 模型文件 | 由 artifact 覆盖 | 随 artifact | 3.x 在 `models/<model_id>/` |

### 36.3.2 一致性

元数据与 artifact 是两套系统，备份要保证**可恢复的一致性**：

- 先备份元数据快照，再备份/确认 artifact 版本；恢复时以“元数据引用的 artifact 都存在”为准；
- 删除 run 通常是软删除，artifact 不立即删；GC 前要确认备份窗口；
- 恢复演练要验证：run 能查、artifact 能下载、模型能加载、registry alias 能解析。

### 36.3.3 恢复等级

| 等级 | 目标 | 手段 |
|---|---|---|
| RPO=0 | 不丢已确认写入 | 同步复制/托管 PITR |
| RPO=15min | 可接受少量丢失 | WAL 归档 + 定期快照 |
| RTO=1h | 一小时内恢复 | 预置实例/ IaC/ 恢复脚本 |
| RTO=1d | 一天内恢复 | 冷备 + 手动恢复 |

先定 RPO/RTO，再选技术。没有目标的“我们做了备份”没有意义。

## 36.4 监控：四个黄金信号 + 三个领域指标

### 36.4.1 服务层

- **延迟**：REST P50/P95/P99，按端点分（`runs/log-batch`、`runs/search`、artifact 上传/下载）；
- **流量**：QPS、并发连接、artifact 吞吐；
- **错误**：4xx/5xx 比例，按错误码分（`RESOURCE_DOES_NOT_EXIST` 不是故障，`INTERNAL_ERROR` 是）；
- **饱和度**：线程/worker、连接池、CPU/内存、磁盘。

### 36.4.2 数据库

- 连接数与等待；
- 慢查询（尤其 search、metric history）；
- 锁等待/死锁；
- 磁盘增长与索引膨胀；
- 复制延迟（只读副本）；
- 备份是否成功。

### 36.4.3 Artifact 与 Trace

- 上传/下载失败率与 P99；
- 对象存储 4xx/5xx、限流；
- artifact 增长速率、单文件大小分布；
- trace 写入量、payload 大小、采样率；
- trace 查询延迟与扫描行数。

### 36.4.4 指标暴露方式

MLflow 本身不保证暴露完整的 Prometheus 指标。常见做法：

- 反向代理/服务网格采集 HTTP 指标；
- 数据库/对象存储用云监控；
- 应用侧在 client 包装层打点（log_batch 延迟、失败率）；
- Gateway 这类自建组件自己暴露 counters/histograms。

不要假设“装了 MLflow 就有全套监控”。监控是部署的一部分，不是产品自带。

### 36.4.5 Webhook 投递

如果启用了 Registry/Prompt webhook，额外监控：

- `pending` 投递数是否持续增长（dispatcher 停止/接收方故障）；
- 按 webhook × event 的成功率、重试次数、最后一次错误；
- 投递延迟 p95/p99；
- `DELIVERED`/`FAILED` 表的增长速度与保留期；
- secret 轮换窗口内的双签名兼容。

Webhook 故障不应影响 Registry 写入，但“事件不丢”需要事务性 outbox；Mini 在业务提交后才入队，生产要按第 38 章改造。

## 36.5 容量与成本运营

### 36.5.1 增长来源

- metric 行数：run 数 × 指标数 × step 数；
- trace/span：请求量 × 采样率 × payload；
- artifact：模型/数据集/日志/图片；
- 元数据索引：搜索字段越多，索引越大。

### 36.5.2 保留策略

按对象分级：

| 对象 | 热保留 | 冷归档 | 删除策略 |
|---|---|---|---|
| 生产 run 元数据 | 1-3 年 | 合规要求 | 软删除 + 审批 |
| 实验 run | 90-180 天 | 对象存储 | 自动清理 |
| 高频 metric | 30-90 天 | 降采样 | 保留首末/极值 |
| trace | 7-30 天 | 采样 | 按错误/高价值保留 |
| artifact | 随模型/合规 | 生命周期 | 引用计数 + GC |

### 36.5.3 成本模型（示例框架）

```text
月成本 =
  数据库实例 + 存储 + 备份
  + 对象存储容量 + 请求 + 出口流量
  + 计算副本
  + 监控/日志
  + 人力运维
```

优化顺序：

1. 降采样高频 metric；
2. trace payload 截断/脱敏；
3. artifact 生命周期与去重；
4. 冷数据归档；
5. 只读副本按需；
6. 不要为了“全量”牺牲可用性。

## 36.6 安全运维

### 36.6.1 密钥与令牌

- 服务间用短期凭据/实例角色，不用长期 AK；
- 客户端 token 定期轮换，支持双 token 过渡；
- 密钥放 Secret Manager，配置只存变量名；
- 日志/错误信息不打印 Authorization、cookie、API key；
- Gateway 的 provider key 只在调用时读取，不序列化。

### 36.6.2 网络与 TLS

- 对外只暴露 LB 的 443；
- 服务端到数据库/对象存储走私网；
- 证书自动续期与到期告警；
- 禁止把 tracking server 直接暴露公网；
- artifact 下载设置 Content-Disposition/ nosniff，避免存储型 XSS。

### 36.6.3 权限与审计

- 最小权限：读写分离、按项目/租户隔离；
- 管理操作（删除、恢复、alias 变更、prompt 发布）留审计日志；
- 审计日志独立存储，防篡改；
- 定期审查长期未使用的 token/账号；
- 模型加载视为代码执行，限制来源与审批。

### 36.6.4 依赖与供应链

- 固定版本与哈希；
- 定期扫描 CVE；
- 模型反序列化格式优先选非 pickle；
- 第三方 flavor/plugin 审核来源；
- 升级前跑加载回归与安全测试。

## 36.7 故障演练脚本

演练的目标是验证**检测 -> 定位 -> 缓解 -> 恢复**，不是证明系统不会坏。

### 演练 1：数据库连接耗尽

```text
注入：把连接池降到 1，或开大量慢查询
观察：5xx、连接等待、日志
预期：告警触发；副本可重启；连接恢复后自愈
改进：连接池上限、超时、慢查询治理
```

### 演练 2：artifact 磁盘/桶满

```text
注入：限制写入或填满测试桶
观察：上传失败、错误码、客户端重试
预期：明确 4xx/5xx；不产生半写文件；告警
改进：配额、生命周期、预检、磁盘水位告警
```

### 演练 3：错误版本发布

```text
注入：部署一个 schema 不兼容的服务端
观察：健康检查、迁移失败、客户端错误
预期：滚动发布暂停；旧副本继续服务；回滚成功
改进：canary、迁移门禁、回滚脚本
```

### 演练 4：Registry/模型损坏

```text
注入：删除一个 artifact 或破坏一个模型文件
观察：加载失败、alias 解析、告警
预期：定位到具体版本；从备份/对象存储版本恢复
改进：完整性校验、引用检查、恢复演练
```

### 演练 5：Gateway provider 故障

```text
注入：主 provider 持续 5xx / 超时
观察：fallback 成功率、成本变化、延迟
预期：自动回退；attempts 可解释；告警
改进：熔断、预算、provider 健康检查
```

## 36.8 值班 Runbook 模板

```text
事件标题：
影响范围（用户/团队/功能）：
开始时间：
严重级别（SEV1/2/3）：
现象（指标/错误/告警）：
最近变更（部署/配置/数据）：
已尝试：
当前判断：
下一步：
需要谁：
恢复时间：
复盘负责人：
```

排查顺序（MLflow 平台）：

1. **健康检查**：`/health`、LB 后端状态；
2. **版本/配置**：最近部署、环境变量、URI；
3. **数据库**：连接、锁、慢查询、磁盘；
4. **artifact**：对象存储权限/配额/网络；
5. **客户端**：版本、token、超时、重试；
6. **模型**：LoggedModel/Registry/alias 解析；
7. **trace**：写入量、payload、采样；
8. **webhook**：pending 堆积、接收方 5xx、签名/时间窗失败；
9. **回滚**：是否触发预设回滚条件。

## 36.9 Mini 的运维缺口

Mini 明确不具备：

- 多副本/HA；
- 连接池与数据库迁移工具；
- 对象存储与 CDN；
- RBAC/OIDC/审计；
- 分布式限流/缓存；
- 指标暴露与告警；
- 备份/恢复工具；
- 灰度发布与 canary。

但 Mini 的代码结构保留了运维切入点：

- `MiniConfig` 集中配置，便于注入环境差异；
- `TrackingService` 无 HTTP 依赖，便于健康检查/批处理；
- `SqliteStore` 的事务/锁语义明确，便于理解并发故障；
- `Gateway` 的统计/回退/限流是生产网关的最小骨架；
- `scripts/verify.py` 是可重复的回归入口。

## 小结

- 运维的第一原则是分层：LB、无状态服务、数据库、对象存储各自扩展与备份。
- 升级按“备份 -> 读路径 -> 服务端 -> 写路径 -> 回归 -> 回滚窗口”执行。
- 备份要覆盖元数据、artifact、配置、密钥引用，并用恢复演练证明可用。
- 监控看四个黄金信号，加上数据库、artifact、trace 三个领域指标。
- 故障演练验证检测与恢复，不验证“不会坏”。
- Mini 是教学系统；它的价值是让你理解运维对象，而不是替代生产平台。

## 练习

1. 为你的团队画一张部署拓扑图，标出单点、备份、监控和权限边界。
2. 写一个升级 runbook：包含检查表、命令、回滚条件、通知模板。
3. 设计一个 artifact 生命周期策略：按模型/数据集/日志分类，给出保留期与删除审批。
4. 为 Gateway 设计熔断策略：错误率、窗口、半开探测、恢复条件。
5. 做一次数据库恢复演练：从备份恢复到新实例，验证 run/artifact/模型/alias 四类对象。
6. 列出你当前监控里缺失的三个指标，并说明它们能提前发现什么故障。
