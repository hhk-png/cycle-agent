# 22 附录 I:Agent 工程原则与决策速查

> 第 19 章附录 F 给出了一本「反模式目录」——50 条**不要做什么**的命名与修复。
> 本附录是它的正面镜像:**该做什么**。
>
> 它把分散在全书各章、反复出现的工程判断提炼成 **68 条可命名的原则**,
> 每条一行、可查、可引用。风格致敬《代码大全》的「软件工艺」精神——
> 好的工程书不止讲技术,还讲**判断力**。当你或你的团队在任何一个 Agent
> 决策点上犹豫时,翻到这一章,找到那条原则,再回到对应章节读细节。
>
> **用法**:这不是一篇需要从头读到尾的文章,而是一张「决策速查表」。
> 遇到决策点查分组,遇到「系统行为怪异」查第 19 章反模式(负),遇到
> 「不知道该不该这么做」查本章原则(正)。两条配起来,就是完整的判断体系。

## 1. 为什么需要原则清单

一本「能读很多年」的教程,最终沉淀下来的不是 API 参数(它们年年变),
而是**判断依据**。第 02 章给了模式语言,第 19 章给了反模式语言,
本章给出**原则语言**——三者合起来,构成 Agent 工程完整的三套共同词汇:

| 语言 | 回答 | 形态 |
|---|---|---|
| **模式语言**(第 02 章 §5) | 系统可以长成什么样 | 7 种工作流模式 |
| **反模式语言**(第 19 章) | 系统为什么会坏 | 50 条反模式(症状→根因→修复) |
| **原则语言**(本章) | 该按什么标准做决定 | 68 条原则 + 决策清单 |

**原则与反模式的关系**:反模式是「原则的违背」,原则是「反模式的解药」。
例如反模式 AP-22「把窗口当存储」对应原则 P-38「上下文是工作台,不是存储」。
读反模式时顺手查本章对应原则,修复就有了正面依据。

**三条使用纪律**:

1. **原则是权衡,不是教条**。每条原则都在某个具体约束下成立;
   场景变了,原则的权重就变。判断的标准永远是「当前语境」。
2. **原则要落到评测**。凡是原则要求的行为,都应能写成评测断言(第 10 章);
   不能断言的原则,只是空话。
3. **原则要变成团队共同语言**。像引用反模式名一样引用原则名——
   「这条改动违反了 P-27」比「这样塞上下文不太好」精确得多。

## 2. 六组原则

每条原则的结构:**编号 + 命名 + 一句话陈述 + 依据章节**。
按 Agent 工程的六个生命周期阶段分组,与第 19 章反模式目录(8 个分组)在思路上呼应——原则回答「该做什么」,反模式回答「别做什么」,两者互补但不一一对应;对照关系见 §5。

### A. 目标与边界(Purpose & Boundaries)

> 回答:**这个系统到底是什么、该管到哪、该交给谁。**

| 编号 | 原则 | 依据 |
|---|---|---|
| **P-01** | **Agent = 有目标 + 能行动 + 能迭代**。三者缺一,严格说都不是 Agent——判断系统性质的第一问 | 第 01 章 §1 |
| **P-02** | **能确定就不用模型,不能确定才交给 Agent**。确定的部分用 Workflow/代码/规则,不确定的部分才交给模型——成本、可靠性与可审计性的第一来源 | 第 01 章 §3.2、第 02 章 §5.9 |
| **P-03** | **Workflow 与 Agent 是谱系,不是对立**。同一个系统里可以「确定段用代码、不确定段用模型」,不要二选一 | 第 01 章 §3.2 |
| **P-04** | **RAG 是 Agent 的工具箱之一,不是对立面**。一个拥有 `search` 工具的 Agent 天然就是「Agent + RAG」 | 第 01 章 §3.3 |
| **P-05** | **先单后多**。任何多 Agent 方案都要用评测证明「单 Agent + 好工具」确实不够,再拆;一次只引入一个拆分 | 第 08 章 §8、第 19 章 AP-02 |
| **P-06** | **自主度越高,约束越紧**。L1–L2 覆盖绝大多数真实场景;L3+ 意味着更多不可控与更贵的成本 | 第 01 章 §5.2、第 11 章 §8 |
| **P-07** | **可预测性 > 花哨**。生产级判断永远是「行为可控、可审计」优先于「能力惊艳」 | 第 01 章 §8 |
| **P-08** | **能力 = 模型 × 工具 × 记忆 × 循环,相乘而不是相加**。短板决定整体,别只盯着模型换 | 第 01 章 §4 |

### B. 循环与推理(Loop & Reasoning)

> 回答:**循环怎么转、思考到什么深度、哪里该停。**

| 编号 | 原则 | 依据 |
|---|---|---|
| **P-09** | **所有 Agent 底层都是感知-思考-行动-观察循环**。理解任何框架,先找它的循环 | 第 02 章 §1 |
| **P-10** | **循环的历史全在 `messages` 里**。模型的「记忆」就是输入上下文,因此上下文治理(第 05 章)直接决定循环质量 | 第 02 章 §1 |
| **P-11** | **显式思考提升多步推理质量**。ReAct 让模型在行动间穿插推理,正确率与可诊断性同时提升 | 第 02 章 §2 |
| **P-12** | **停止条件要三问齐答**:正常结束(模型不再要工具)、硬上限(迭代数)、预算上限(token/耗时)——少一个就是烧钱 | 第 02 章 §6.1 |
| **P-13** | **循环是状态机,不是 `while(true)`**。显式状态(消息+计数+预算)带来可恢复、可测试、可观测、可约束 | 第 02 章 §6.4 |
| **P-14** | **规划的价值在「可对照」,不在「正确」**。计划让 Agent 和人类都能判断「走到哪了」;计划本身会过时,要能重规划 | 第 02 章 §3.5 |
| **P-15** | **规划要基于真实工具清单**。让计划里的每一步引用真实工具名,压制「计划幻觉」 | 第 02 章 §3.5、第 19 章 AP-08 |
| **P-16** | **反思是用计算换正确性,按需启用**。高价值、高失败成本的任务反思;低风险任务关闭,别一律双轮 | 第 02 章 §4 |
| **P-17** | **推理模型按任务分级使用**。简单任务用普通模型,复杂推理才用推理模型;别依赖「读思考过程」做业务逻辑 | 第 02 章 §2.3 |
| **P-18** | **工具错误是观察,不是事故**。把失败回喂给模型让它自愈,是 Agent 韧性的直接来源 | 第 02 章 §1、第 03 章 §5.6 |

### C. 接口与工具(Interface & Tools)

> 回答:**怎么跟模型打交道、怎么定义 Agent 的「手脚」。**

| 编号 | 原则 | 依据 |
|---|---|---|
| **P-19** | **定义自己的中间格式,不绑定任何厂商**。Message/ToolCall 用内部契约,格式转换只发生在 provider 边界 | 第 03 章 §4.3、第 07 章 §3 |
| **P-20** | **决策型调用用低温度(0–0.3)**。工具选择、规划、评测打分需要确定性;创意生成才用高温 | 第 03 章 §1.4 |
| **P-21** | **Prompt Caching 是成本工程最大的单一杠杆**。稳定前缀在前、动态内容在后、保持前缀字节一致 | 第 03 章 §1.3、第 05 章 §4 |
| **P-22** | **结构化输出优先于「提示 + 解析」**。程序要 `JSON.parse` 模型输出,就用约束解码(json_schema);解析失败必须有兜底 | 第 03 章 §3 |
| **P-23** | **工具参数必须 JSON Schema 校验**。模型输出是「需要校验的输入」,不是「模型的承诺」;校验失败返回 isError | 第 03 章 §6、第 11 章 §5 |
| **P-24** | **工具错误绝不穿透循环**。所有异常转成可读文本回喂,让模型看到错误并自我修正 | 第 03 章 §5.6、第 07 章 §5.2 |
| **P-25** | **工具是任务级,不是操作级**。一个 10 步的子任务最好是一个工具;粗粒度让模型好决策、省上下文 | 第 03 章 §5.5 |
| **P-26** | **工具描述是「给模型看的说明书」**。写清「何时触发 + 输入约束 + 返回值含义」,必要时附 few-shot 例子 | 第 03 章 §5.2 |
| **P-27** | **`tool_choice` 是协议层约束,比提示词可靠**。该防呆用 `required`,该路由指定工具;别把什么都设成 `required` | 第 03 章 §4.4 |
| **P-28** | **并行工具调用只用于独立工具**;有依赖必须串行,嵌套是 ReAct 循环的自然形态 | 第 03 章 §4.5 |
| **P-29** | **模型接口调用要有重试与退避**。只在瞬时错误(429/5xx/网络)上重试,确定性错误直接失败 | 第 03 章 §8、第 02 章 §6.3 |

### D. 记忆与上下文(Memory & Context)

> 回答:**记住什么、怎么取回、怎么装进窗口。**

| 编号 | 原则 | 依据 |
|---|---|---|
| **P-30** | **记忆 = 把「已发生的交互」转化为「可复用的上下文」**。记忆系统解决的不是「存得下」,而是「在有限窗口内装最相关的」 | 第 04 章 §1 |
| **P-31** | **何时写入比怎么存储更难**。用「策略触发 + 模型提取 + 重要度打分」只沉淀高价值信息,别什么都记 | 第 04 章 §5.1、第 19 章 AP-19 |
| **P-32** | **读快写慢**。写路径走「记忆线程」异步提炼,读路径多路(短期/向量/结构化)按需拼装 | 第 04 章 §5.3 |
| **P-33** | **记忆要透明、可控、可删除**。没有删除能力的记忆系统在生产是合规事故 | 第 04 章 §8.2、第 11 章 §4 |
| **P-34** | **记忆去重与一致性是质量底线**。重复/矛盾/过期的脏记忆比没有记忆更糟 | 第 04 章 §7.1 |
| **P-35** | **遗忘是记忆的一等公民**。TTL + 容量上限 + 主动清理,防止过期信息污染 | 第 04 章 §8.1 |
| **P-36** | **RAG 与 Agent 记忆共用技术栈,区别在内容来源与写入方**。生产系统常共用一个向量库的不同 collection | 第 04 章 §6.1 |
| **P-37** | **RAG 要评测**:召回率 + 答案正确率 + 引用准确率 + 无证据拒答率,别用「感觉好」代替「可量化」 | 第 04 章 §6.5 |
| **P-38** | **上下文是工作台,不是存储**。塞得越全越相关,但越贵越容易溢出——本质是权衡,不是「把窗口填满」 | 第 05 章 §1.2、第 19 章 AP-22 |
| **P-39** | **预算分配:固定开销(系统提示+工具)与可变开销(历史+记忆)分开**。输入留 60–75%,给输出与回环留空间 | 第 05 章 §2.2 |
| **P-40** | **关键信息放头尾,不埋中段**。lost-in-the-middle——关键约束放 system 或最近消息,「引用而非复制」 | 第 05 章 §3.2 |
| **P-41** | **动态工具子集:只给本轮可能用到的工具**;但「漏选比多选更贵」,子集判定要稳 | 第 05 章 §5 |
| **P-42** | **工具返回要结构化 + 可迭代 + 可修正**。带元数据(来源/时间/置信度),让模型读完即用 | 第 05 章 §3.4 |
| **P-43** | **上下文是可观察的系统**。转储、token 分布、裁剪事件、重复检测、缓存命中率——先看清再调 | 第 05 章 §8 |
| **P-44** | **上下文压缩用关键点提取优于自由摘要**,用固定模板 + 分层摘要 + 信息回收测试验证 | 第 05 章 §6 |

### E. 框架与实现(Frameworks & Implementation)

> 回答:**选什么工具、怎么写代码、怎么保证质量。**

| 编号 | 原则 | 依据 |
|---|---|---|
| **P-45** | **框架是「当时最优」的封装,不是「永远正确」的真理**。看懂时间线就看得懂「下一个主角」长什么样 | 第 06 章 §1.1 |
| **P-46** | **选框架先回答三个问题**:流程确定还是不确定?绑不绑模型?要不要审计/人工介入? | 第 06 章 §9 |
| **P-47** | **先定契约,再写实现**。统一 Message/ToolCall 契约先于一切,模块间不互相「猜」格式 | 第 07 章 §3 |
| **P-48** | **面向接口,依赖注入**。换实现不改业务逻辑;依赖通过构造参数与 Context 注入,而非全局单例 | 第 07 章 §4、§5 |
| **P-49** | **防御式编程**。捕获一切异常转 isError,错误不穿透循环;安全边界前移(拒绝 eval、路径校验) | 第 07 章 §5.2、§15.1 |
| **P-50** | **可观测内建,不事后补**。事件流 + Span 树 + 统计信息,让运行过程可见、可回放、可评测 | 第 07 章 §9.5、§12 |
| **P-51** | **行为验证而非冒烟测试**。测试断言「行为正确」(对应设计约束),而不是「能跑」 | 第 07 章 §15.1 |
| **P-52** | **先小后大,用评测驱动升级**。先单 Agent + Mock 验证核心逻辑,再换真实模型、再加复杂度 | 第 16 章 §10 |

### F. 多智能体、协议与工程治理(Multi-agent, Protocols & Governance)

> 回答:**怎么协作、怎么连接外部、怎么把系统送上生产并守住。**

| 编号 | 原则 | 依据 |
|---|---|---|
| **P-53** | **多 Agent 的评测与安全成本必须计入选型**。评测与安全做不齐,单 Agent 往往是更负责任的选择 | 第 08 章 §4.6 |

| **P-57** | **没有评测就不是改进,是碰运气**。评测是 Agent 工程的第一优先级 | 第 10 章 §1 |

| **P-59** | **评测数字要带 n / CI / 显著性**。没有置信区间的百分比只是另一种主观印象 | 第 10 章 §9.1 |
| **P-60** | **能力边界是最后防线**。别指望模型懂安全,要让系统在模型被骗时依然安全——工具白名单、审批流、最小权限 | 第 11 章 §2.3 |
| **P-61** | **身份与授权要分清 AuthN/AuthZ**。工具必须知道「这次动作代表谁」;上线前必答「用户 A 让 Agent 操作用户 B 的数据会怎样?」 | 第 11 章 §3.4 |
| **P-62** | **生产 Agent = 分布式异步工作系统**。Agent 循环只是业务逻辑,周围是标准后端工程 | 第 12 章 §1 |
| **P-63** | **可观测三支柱(日志/trace/metrics)缺一不可**;看板按「能回答什么问题」组织,重趋势不重单点 | 第 12 章 §3 |
| **P-64** | **状态在存储层,worker 无状态**。这是横向扩展、断点续跑、任务级幂等的前提 | 第 12 章 §2.3、§5 |
| **P-65** | **Agent API 契约化**:task_id 是唯一入口,状态显式化,`requires_approval` 是合法状态而非错误 | 第 12 章 §2.4 |
| **P-66** | **成本公式化** `C ≈ n×(P_in·r_in + P_out·r_out) + 工具成本`——每个优化杠杆对应一个公式变量 | 第 12 章 §6.3 |
| **P-67** | **人机协作是信任的基石**。关键动作要人确认;审批界面要展示决策依据,而不是裸的「允许/拒绝」 | 第 12 章 §7、第 11 章 §5 |
| **P-68** | **提示词/模型/工具集/护栏全部配置化 + 版本化 + 可回滚** | 第 12 章 §8.3 |

## 3. 决策速查:关键决策点一页纸

以下是全书中**最高频的八个决策点**的速查。每个决策都遵循「先列条件,再选方案,
再用评测验证」的流程。

### 3.1 Workflow 还是 Agent?

```
这一步有明确的「输入→输出」规则吗?
  ├─ 有 → Workflow / 代码 / 规则(提示链、路由)——便宜、快、可审计
  └─ 没有 → Agent(循环 + 工具)——把「不确定」交给模型
一句话:能确定就不用模型。
```

### 3.2 用不用多 Agent?

```
先跑「单 Agent + 好工具」基线
  └─ 评测(第 10 章)证明瓶颈在「单 Agent 能力不足」?
        ├─ 单 Agent 上下文过长 / 单一提示词难兼顾多职责
        ├─ 子任务天然独立且需要并行
        └─ 需要多视角降低偏见
        是 → 引入多 Agent,一次只拆一个
        否 → 保持单 Agent(协调开销常吃掉收益)
一句话:先单后多,评测驱动。
```

### 3.3 RAG 还是 Agentic RAG?

```
问题固定、知识静态 → 普通 RAG(便宜、快、稳)
问题开放、需要多步推理、证据要拼装 → Agentic RAG(灵活、准,但贵)
一句话:先普通后 Agentic,用「检索覆盖率」评测证明瓶颈再升级。
```

### 3.4 用不用推理模型?

```
瓶颈在「逻辑推理」(数学、规划、多条件判断)→ 换推理模型
瓶颈在「信息获取」(工具、检索、记忆)→ 换模型没用,先解决工具/上下文
一句话:默认普通模型,评测发现「推理类失败」占大头时再引入推理模型。
```

### 3.5 缓存 / 工具子集 / 压缩,该上哪个?

```
成本从哪里来?
  ├─ 重复前缀(多轮循环)→ Prompt Caching(稳定前缀在前)
  ├─ 工具定义太庞大 → 动态工具子集(只发本轮可能用到的)
  └─ 历史太长 → 上下文压缩(关键点提取优于自由摘要)
一句话:按「成本公式」的变量定位,别凭感觉优化。
```

### 3.6 工具设计的三问

```
[ ] 命名是动词开头、语义清晰(query_order 而非 order)?
[ ] 描述写清「何时触发 + 输入约束 + 返回值含义」?
[ ] schema 精确到类型 + required + 枚举 + additionalProperties:false?
一句话:工具决定能力边界,描述决定工具选对率。
```

### 3.7 安全:高危操作怎么管?

```
这个操作有副作用吗(转账/删除/外发/执行代码)?
  ├─ 有 → 进审批流 + 人工确认 + 最小权限凭证
  └─ 无 → 参数校验 + 白名单即可
另外:工具返回一律当不可信数据;记忆按用户隔离可删除;日志脱敏。
一句话:能力边界是最后防线,别指望提示词。
```

### 3.8 上线前的评测门禁

```
[ ] 最小回归集(几十条,分钟级)通过
[ ] 完整集(夜间)通过
[ ] 结果 + 轨迹双重断言(不止看最终输出)
[ ] 安全用例(注入 / 越权 / 工具滥用)通过
[ ] 成本预算检查(改动是否显著增本)
一句话:没有评测门禁,任何「改进」都是碰运气。
```

## 4. 把原则变成团队资产

原则清单只有被使用才有价值。三条落地建议:

1. **写进 code review 清单**。review 时除了查 bug,查「这条改动是否违反某条原则」:
   「把 30 个工具全塞给模型,违反 P-41」比「工具太多了」可执行得多。

2. **写进评测断言**。原则要求的每个行为,都应有一条断言:
   P-23(参数校验)→ `toolNotCalled` + 参数断言;
   P-42(工具返回结构化)→ 断言工具返回是 JSON;
   P-58(轨迹断言)→ `toolCalled('query_order', argCheck)`。
   原则从「说法」变成「检查」,才真正落地。

3. **写进设计文档**。每个 Agent 系统设计文档开头,列一个「本系统遵循的关键原则」清单
   (通常 8–12 条),评审时逐条过。这比「架构图 + 技术选型」更能暴露设计缺陷——
   因为原则暴露的是**判断依据**,而不是**表面结构**。

> **与反模式目录的配合**:遇到诡异行为,先查第 19 章(症状→根因);
> 找到根因后,反查本章对应原则,把修复写成「回归到某条原则」。
> 例:AP-22(把窗口当存储)→ 根因是没有预算分配 → 修复 = 回归 P-38(预算分配见 P-39)。

## 5. 本节要点

1. **原则是反模式的正面镜像**:反模式回答「系统为什么坏」,原则回答「该按什么标准做决定」;
2. 68 条原则按六个生命周期阶段分组(目标边界 / 循环推理 / 接口工具 / 记忆上下文 /
   框架实现 / 多智能体协议与治理),每条可查、可引用、带章节依据;
3. **原则是权衡,不是教条**——判断标准永远是「当前语境」;
4. 八个高频决策点(Workflow vs Agent、单 vs 多、RAG vs Agentic RAG、推理模型、
   成本优化、工具设计、高危操作、评测门禁)各有速查一页纸;
5. **原则要落到评测断言,才能从「说法」变成「检查」**;
6. 原则 + 反模式 + 模式语言三套共同词汇,构成 Agent 工程完整的判断体系——
   **模式决定结构,反模式防止堕落,原则校准方向**。
