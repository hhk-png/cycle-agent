# 10 Agent 评测

> 本章目标:回答「怎么知道我的 Agent 变好了」——评测维度、离线与在线评测、
> 基准与数据集、LLM-as-Judge、轨迹评测、以及把评测工程化的方法。

---

## 1. 为什么评测是 Agent 工程的第一优先级

没有评测,Agent 开发就是「盲人摸象」:

- 改了 system prompt,是变好了还是变差了?
- 加了新工具,成功率提升了吗?
- 换了大模型,值不值多出来的成本?
- 该不该上多 Agent?——第 08 章说要「评测驱动」,没有评测就没法驱动。

**Agent 的不确定性放大了评测的必要性**:LLM 应用(单次调用)的评测已经够难,
Agent 是**多步轨迹**,每一步都有决策点,错误会累积、会传播。一个工具调用顺序错了,
可能后面全盘皆输。所以 Agent 评测必须同时看「最终结果」和「执行轨迹」。

> 一个经常被引用的说法:**「没有评测的 Agent 工程,不是在改进,而是在碰运气。」**

## 2. 评测什么:五维框架

### 2.1 任务成功率(Task Success)

最终目标是否达成。最核心、但最「粗」的指标。

- **严格成功率**:完全正确才得分(如「返回了正确的 JSON」);
- **部分完成度**:子任务完成比例;
- **分级评分**:0–5 分(如「完全错误 / 部分正确 / 完全正确」)。

### 2.2 过程质量(Process Quality)

Agent 不仅结果要对,**过程也要对**:

- **工具选择**:该用 `query_order` 时,是否用了正确的工具?
- **参数正确性**:传给工具的参数是否有效?(甚至可以先于结果检查)
- **决策合理性**:是否在信息不足时正确追问?是否过早放弃?
- **错误恢复**:面对工具错误,是否成功自愈?

> 过程质量常被低估。一个「结果碰巧对但过程混乱」的 Agent 不可维护、不可审计。
> 很多生产团队用「过程正确率」作为第一门禁,因为过程错了,结果对也只是运气。

### 2.3 效率(Efficiency)

- **成本**:token 消耗、模型调用次数;
- **延迟**:端到端耗时、首 token 延迟;
- **迭代轮数**:同样的任务,好的 Agent 用更少轮次完成;
- **工具调用数**:是否调用冗余工具(「反复搜索同一关键词」是常见浪费)。

**关键指标:成本/成功率比**。一个成功率 95%、但成本是别人 3 倍的 Agent,
在成本敏感场景未必更好。

### 2.4 鲁棒性(Robustness)

- **输入扰动**:换措辞、加错别字、加无关信息,结果是否稳定?
- **边界输入**:空输入、超长输入、恶意输入(第 11 章);
- **状态恢复**:中断后能否恢复?
- **多语言/多格式**:不同地区用户的表现。

### 2.5 安全与对齐(第 11 章详细)

- 是否拒绝危险请求?
- 是否被提示注入攻破?
- 是否泄露敏感信息?

### 2.6 指标的计算与聚合:从「感觉」到「数字」

评测的最终输出是一组**可计算的指标**。几个最常用的定义:

| 指标 | 公式 | 说明 |
|---|---|---|
| **任务成功率(Task Success Rate)** | `通过用例数 / 总用例数` | 最简单、最核心 |
| **过程正确率(Process Correctness)** | `工具调用正确的用例数 / 总用例数` | 结果对不算,过程也要对 |
| **平均迭代轮数(Avg Iterations)** | `Σ迭代轮数 / 用例数` | 效率指标;越少越好 |
| **平均成本(Avg Cost)** | `Σtoken × 单价 / 用例数` | 成本/成功率比的关键输入 |
| **端到端延迟 P50/P95** | 分位数 | 性能指标 |
| **关键指标回收率(上下文工程)** | `答对的关键事实数 / 总关键事实数` | 第 05 章 §6.4 的信息回收测试 |

**聚合的原则**:

1. **按组切片,不要只看总分**。按任务类型 / 难度 / 失败模式分组算成功率——
   总分 80% 可能掩盖「happy path 100%、边界 20%」的严重失衡;
2. **同时看均值与方差**。Agent 是概率系统,均值可能被个别极端样本拉偏;
   P50/P90/P99 一起看;
3. **趋势比绝对值重要**。单次分数意义有限,「改了什么导致从 70%→85%」
   才是评测驱动开发的价值;
4. **成本与质量一起看**。`成本/成功率比` 是生产选型的核心指标:
   一个 95% 成功率但成本 3 倍的 Agent,在成本敏感场景未必更好。

## 3. 离线评测(Offline Eval)vs 在线评测(Online Eval)

| 维度 | 离线评测 | 在线评测 |
|---|---|---|
| 数据 | 固定数据集(golden set) | 线上真实流量 |
| 时机 | 开发/CI 阶段 | 灰度/生产 |
| 反馈 | 快(分钟级) | 慢(需要积累) |
| 控制 | 完全可控、可复现 | 不可控、有风险 |
| 用途 | 迭代开发、回归测试 | 上线验收、持续监控 |
| 风险 | 无 | 可能影响真实用户 |

**正确的组合**:离线评测做「开发时迭代」,在线评测做「上线前把关 + 生产监控」。
两者缺一不可——离线评测会过拟合数据集,在线评测反应太慢。

## 4. 评测数据集怎么来

### 4.1 构建方法

1. **人工标注**:领域专家写「任务 + 标准答案」。质量最高,成本也最高;
2. **真实流量采样**:从生产日志抽样真实用户请求,人工标注期望结果;
3. **合成生成**:用大模型生成任务与答案,人工抽检修正(注意合成偏差);
4. **社区基准**:用公开数据集起步(SWE-bench、GAIA、WebArena 等,见 §6)。

### 4.2 数据集的工程要求

- **版本管理**:数据集进 Git,任何变更可追溯;
- **最小集**:维护一个「最小回归集」(几十条),每次改代码跑一遍,
  几分钟内发现回归;完整集(几百上千条)留给 CI 或夜间跑;
- **领域分布**:覆盖主流程 + 边界 + 异常,而不是只覆盖 happy path;
- **去重与防泄漏**:避免测试数据与训练数据重复。

## 5. 打分方法:谁来当裁判

评测数据集有了,谁来判断 Agent 的输出对不对?

### 5.1 确定性匹配

- 精确匹配(JSON 完全相等);
- 子串/正则匹配;
- **结构化断言**:解析输出 JSON,断言字段值。

适用:输出是结构化数据(工具参数、分类结果)的场景。快、稳、无成本。

### 5.2 参考答案匹配

- 语义相似度(embedding 余弦);
- 关键点抽取对比(先让模型提取要点,再比对要点)。

### 5.3 LLM-as-a-Judge(模型当裁判)

用大模型给 Agent 的输出打分/对比。2024 年后成为主流方法。

```text
[系统]
你是一个公正的评测员。判断以下回答是否满足用户需求,给出 1-5 分并说明理由。
评分标准:1=完全不相关,3=基本正确但有缺漏,5=准确且完整。

[用户]
任务:查询订单 8847-223 的物流
Agent 的回答:您的耳机已发货,预计明天到达。

[助手]
评分:4
理由:正确回答了物流状态与预计时间,但未提及承运商(若任务隐含需要)。
```

**LLM Judge 的工程要点**:

1. **结构化评分**:要求输出 JSON `{"score": 4, "reason": "…"}`,方便程序解析;
2. **多次采样取均值**:LLM 打分有随机性,同一输出打 3 次取平均;
3. **盲评(blind)**:对比评测时,打乱 A/B 顺序,避免位置偏差;
4. **裁判模型选更强的**:用比被测模型更强的模型当裁判;
5. **校准校验**:定期抽一批「人工已标注」的样本,验证裁判与人工一致率;
6. **防裁判偏差**:长输出偏好、自恋偏差(裁判偏爱自己的风格)、
   顺序偏差——通过盲评与随机顺序缓解。

### 5.4 人工评测

最终极的裁判。适用:高风险任务、裁判模型不可靠时、以及给裁判模型做校准。
代价高,适合「定期抽检」而非全量。

## 6. 评测 Agent 的「过程」:轨迹评测

Agent 评测的独特之处在于:**结果可能对,但过程错;过程对,结果也可能错**。
所以要把「执行轨迹」也纳入评测。

### 6.1 轨迹评测的三层

```
第一层:最终输出是否满足用户需求?(结果评测)
第二层:工具调用是否合理?该用的用了没?参数对不对?(行为评测)
第三层:决策轨迹是否高效、可解释?(效率 + 过程评测)
```

### 6.2 轨迹如何评测

1. **人工审阅轨迹**:把「消息历史 + 工具调用」渲染成可读日志,专家标注
   「此处工具选错」「此处多余调用」;
2. **LLM 审阅轨迹**:给裁判模型完整轨迹,让它标注决策质量
   (「在第 3 步,Agent 在信息已足够时仍调用了 search,应直接回答」);
3. **规则断言**:对轨迹做断言(「工具调用次数 ≤ 5」「未调用危险工具」)。

> mini-agent 的 `AgentResult` 返回完整 `messages`(含工具往返),就是为了
> 支持轨迹评测——你在 mini-agent 上写评测,拿 `result.messages` 就能分析。

### 6.3 可观测性是评测的前提

轨迹从哪来?从可观测性来。第 07 章的 `Tracer`、事件流、`AgentRunStats`
(迭代轮数/模型调用数/工具调用数/停止原因)就是评测的原始数据。
**没有可观测性,就没有评测;没有评测,就没有改进。**

### 6.4 上下文工程也要评测

第 05 章讲了上下文工程(预算/排序/缓存/压缩)是性能与成本的核心。
它是**可评测的**,而且应该评测——否则「调上下文」就变成玄学:

| 评测项 | 度量 | 说明 |
|---|---|---|
| **信息回收率** | 给模型一段上下文,问其中关键事实能否答对 | 检验「压缩后信息是否丢失」(第 05 章 §6) |
| **上下文长度** | 每次调用进入模型的 token 数(P50/P90) | 检验预算与裁剪是否生效 |
| **缓存命中率** | provider 返回的缓存命中 token / 总输入 | 检验前缀稳定性(第 05 章 §4) |
| **工具遗漏率** | 该用的工具没被调用(因工具子集漏选) | 检验动态工具子集的判定(第 05 章 §5) |
| **每任务成本** | 单任务总 token × 单价 | 检验上下文工程对成本的实际影响 |

> **经验法则**:上下文工程的每一项改动(重排消息、加缓存、换摘要策略)
> 都应当有对应的评测指标,否则你无法判断「改对了还是改糟了」。
> 把它纳入 §8 的评测平台,和成功率、成本一起追踪。

## 7. 著名基准(2024–2026)

| 基准 | 测什么 | 形态 |
|---|---|---|
| **SWE-bench**(及其 Verified 子集) | 真实 GitHub issue → 修代码 | 代码 Agent 的事实标准 |
| **GAIA** | 需要多工具/多步推理的开放问题 | 通用 Agent 能力 |
| **WebArena / WebVoyager** | 真实网页环境完成任务 | 浏览器 Agent |
| **ToolBench** | 工具选择与调用 | 工具 Agent |
| **τ-bench (tau-bench)** | 客服类多轮工具交互(含用户模拟) | 对话 Agent |
| **BFCL(Berkeley Function Calling)** | 函数调用正确性 | 工具调用专项 |
| **AgentBench** | 多环境通用 Agent 能力 | 综合 |
| **MINT** | 多轮交互中的错误反馈恢复 | 反思/自愈能力 |
| **AgentDojo** | 在工具调用任务中测提示注入攻防 | 安全基准(第 11 章) |
| **CyberSecEval / PromptInject** | 注入、越狱、危险代码生成 | 安全基准(第 11 章) |

> 安全评测基准(AgentDojo 等)近年快速增长,标志着「安全」从选修变成
> 评测的必要维度(第 11 章)。**注意**:这些基准仍在快速演进,
> 用它们横向比较可以,生产安全评估仍要建自己的注入用例集(第 16 章附录 C)。

> 读基准时的提醒:**基准分数不等于生产表现**。SWE-bench 高分不代表你的
> 代码 Agent 在生产好使——生产的数据分布、工具、约束完全不同。
> 基准用于「横向比较模型/方法」,生产评估还是要建自己的评测集。

## 8. 评测工程化:一个生产级的评测系统

把评测从「脚本」变成「系统」,需要五个组件:

```
┌────────────────────────────────────────────┐
│ 评测平台                                      │
│  ├─ 数据集管理(版本化 / 分类 / 防泄漏)         │
│  ├─ 运行器(并行跑 Agent × 数据集,记录轨迹)     │
│  ├─ 打分器(规则 / LLM Judge / 人工抽检)        │
│  ├─ 报告(聚合指标 / 失败样本分类 / 趋势)        │
│  └─ CI 集成(PR 触发,回归阻断)                  │
└────────────────────────────────────────────┘
```

### 8.0 一个可运行的最小评测 harness(mini-agent)

在 mini-agent 上落地「运行器 + 断言 + 报告」只需几十行。下面是
`examples/eval-agent.ts` 的核心(可直接运行:`node examples/eval-agent.ts`;
业务化扩展见第 16 章附录 C):

```ts
import { Agent } from '../src/agent.ts';
import type { AgentResult } from '../src/types.ts';

// 1. 数据集:黄金集(版本化,进 Git)
interface EvalCase {
  id: string;
  input: string;
  assert: (r: AgentResult) => { ok: boolean; reason?: string };  // 结果 + 轨迹断言
}

// 2. 运行器:跑 Agent × 用例,记录轨迹与统计
async function runEval(agent: Agent, cases: EvalCase[]) {
  const results = [];
  for (const c of cases) {
    const result = await agent.run(c.input);   // 含完整 messages(轨迹)
    const verdict = c.assert(result);
    results.push({ ...c, result, verdict });
  }
  return results;
}

// 3. 报告:聚合指标 + 失败样本分类
function report(results) {
  const pass = results.filter((r) => r.verdict.ok).length;
  const avgTokens = results.reduce((s, r) => s + r.result.stats.totalTokens, 0) / results.length;
  const avgIters = results.reduce((s, r) => s + r.result.stats.iterations, 0) / results.length;
  const toolErrors = results.reduce((s, r) => s + r.result.stats.toolErrors, 0);
  console.log(`成功率:${pass}/${results.length} | 平均 token:${avgTokens} | 平均轮数:${avgIters} | 工具错误:${toolErrors}`);
  for (const r of results.filter((r) => !r.verdict.ok)) {
    console.log(`❌ ${r.id}:${r.verdict.reason ?? '(无原因)'} | stop=${r.result.stats.stopReason}`);
  }
}

// 4. 一个用例示例:断言「调用了正确工具且参数合法」(过程断言,第 10 章 §6)
const case1: EvalCase = {
  id: 'calc-1',
  input: '计算 (2+3)*4',
  assert(result) {
    const calls = result.messages
      .filter((m) => m.role === 'assistant' && m.toolCalls?.length)
      .flatMap((m) => m.toolCalls!);
    if (!calls.some((c) => c.name === 'calculator')) return { ok: false, reason: '未调用 calculator' };
    return { ok: result.output.includes('20'), reason: `输出=${result.output}` };
  },
};
```

**要点**:
- **数据、运行、打分、报告分离**——每部分可单独替换(换数据集/换打分器);
- **断言是「结果 + 轨迹」双层**(`case.assert` 里可以同时查 `output` 和 `messages`);
- **`AgentResult.messages` 是轨迹评测的数据源**,无需额外埋点;
- 接入 CI:跑最小回归集,失败即阻断合并(§8.3)。

### 8.1 指标聚合

- **总分**:任务成功率的加权平均;
- **按类细分**:按任务类型、难度、失败模式分组的成功率(发现薄弱点);
- **P50/P90 延迟与成本**;
- **趋势**:随迭代变化的折线图(每次改动都记录,回看「哪次改动提升了什么」)。

### 8.2 失败分析

评测的价值一半在「失败分析」:

- **失败样本聚类**:把失败样本按失败模式聚类(「都栽在参数错误」「都在长上下文
  丢失信息」),而不是一个个看;
- **错误归因**:轨迹里哪一步开始错?是规划、工具选择、还是信息不足?
- **回归阻断**:把「以前通过、现在失败」的样本自动标记为回归,阻断合并。

### 8.3 CI 集成

```text
PR 提交 → 跑最小回归集 → 通过? → 完整集(夜间)→ 报告
                     └→ 失败? → 阻断合并,附失败报告
```

## 9. 评测 Agent 的五个常见错误

1. **只测最终结果,不测轨迹**:过程混乱的 Agent 会漏网;
2. **数据集过小/过偏**:10 条 happy path 测不出真实水平;
3. **用被测模型当裁判**:裁判与被测同模型,自恋偏差严重;
4. **没有最小回归集**:每次小改要跑几十分钟全量,于是干脆不跑——评测就死了;
5. **不跟踪趋势**:只看单次分数,不看「改了什么导致变好」。

### 9.1 评测数字的可信度:统计严谨性

上面提到「数据集过小」,但什么叫「够大」?评测输出一堆百分比,如果不带
**可信度度量**,这些数字可能只是噪声。三个必须掌握的统计概念:

**1. 样本量与置信区间**

- 20 条用例测出 80% 成功率(16/20),95% 置信区间约为 **[59%, 92%]**(Wilson 区间,
  下界偏长、**非对称**)——意味着真实值可能低到 59%,这个「80%」几乎不说明任何问题;
- 经验法则:区分「20%→80%」这种量级差异,几十条用例够;区分「80%→85%」这种
  微小改进,需要**数百条**;
- 报告时要写「成功率 84%(n=300,95% CI [79%, 89%])」,而不是裸写「84%」。

**2. 显著性:两版之间的差异是不是随机**

- 换了 prompt 后成功率从 78% 涨到 82%,这 4 个点是真的改进还是运气?
  不做检验无法回答。两个最常用的工具:
  - **卡方检验**:两组成功率是否有显著差异;
  - **配对采样**:对同一批用例分别跑 A/B 版,看差异分布(A/B 测试的离线版)。
- 只有「差异超过噪声」的改进才值得合入——否则你是在给随机波动调参。

**3. 方差报告:别只看均值**

- 「平均轮数 3.2」掩盖了「一半任务 1 轮、一半任务 6 轮」的极端分布;
  对线上体验,长尾往往比均值更重要(第 12 章 P95 延迟同理);
- 报告 `p50 / p90 / p99` 而不是只报 `mean`;同时看失败样本的**分布**,
  而不是只数失败个数。

**4. 一致率(LLM-as-judge 的可信度)**

- 用 LLM 当裁判时,要报告它与人类(或另一个裁判)的**一致率**:
  - **简单一致率** = 裁判判分与人工判分相同的比例;
  - **Cohen's kappa**:扣掉「碰巧一致」的一致率,比简单一致率更可靠
    (κ > 0.6 通常认为可用,κ < 0.4 说明裁判不可信,换裁判);
- 一致性差的裁判,测出的分数本身就是噪声——先校准裁判,再信分数。

> **一句话总结**:评测的作用是把「变好了还是变差了」从主观印象变成可检验的
> 判断;但**没有置信区间和显著性检验的百分比,只是另一种主观印象**。
> 给评测数字带上 n、CI、显著性,它才能成为第 12 章「评测门禁」的可信依据。

## 10. 对照 mini-agent

mini-agent 的「可评测性」不是事后补的,而是内置的:

| 评测需求 | mini-agent 支持 |
|---|---|
| 结果断言 | `AgentResult.output` |
| 轨迹分析 | `AgentResult.messages`(完整含工具往返) |
| 过程指标 | `AgentRunStats`(iterations / llmCalls / toolCalls / toolErrors / stopReason) |
| 事件观测 | `agent.on('tool_call'/'tool_result'/…)` |
| 可复现 | `MockProvider` 确定性脚本 |
| 测试即评测 | `tests/agent.test.ts` 中 7 个 Agent 行为测试(全仓 10 个文件共 54 个用例) |

**把测试当评测的起点**:mini-agent 的测试文件,本质就是一个「最小回归集」。
生产实践是把它扩展成「领域评测集 + LLM Judge」。

## 11. 评测工具生态:别只自己造 harness

第 8 节的评测 harness 是「最小骨架」——透明、零依赖,但生产里迟早要面对一个
选择题:**继续自建,还是引入现成工具**?先看清主流工具生态,再决定。

### 主流评测工具一览

| 工具 | 语言 | 定位 | 最适合谁 |
|---|---|---|---|
| **Promptfoo** | 声明式 YAML + Node/Python | 离线评测 + CLI/CI 回归 | 想快速上手、把评测接进 CI 的团队 |
| **DeepEval** | Python | LLM/Agent 单元测试框架,metrics 即插件 | Python 技术栈、要细粒度指标(如 G-Eval、幻觉率) |
| **Braintrust** | Python/Node | 评测 + 追踪 + 数据集管理一体化 | 需要在线回流、多人协作的平台化团队 |
| **LangSmith** | Python/TS | 与 LangGraph 生态绑定,自带数据集与评测 | 已经在用 LangChain/LangGraph 的团队 |
| **OpenAI Evals** | Python | 研究向,YAML/JSON 用例 + 自定义 eval | 做研究、要高度自定义打分逻辑 |
| **W&B Weave** | Python/TS | 实验追踪 + 评测 | 已经在用 W&B 做实验管理的团队 |

**要点**:
- Promptfoo 的「声明式 YAML + CLI」与第 8 节的 harness 理念最接近,是平滑迁移路径;
- DeepEval / Braintrust 把「metrics 即插件」做成核心抽象,正好补第 5 节「打分方法」
  里 LLM-as-Judge 的实现细节;
- 工具的共性是「帮你少造轮子」,代价是**引入依赖 + 学习成本 + 平台锁定**。

### 自建 vs 现成工具:怎么取舍

mini-agent 的 `examples/eval-agent.ts`(第 10 章 §8)是自建的代表:

| 维度 | 自建 harness(mini-agent §8) | 现成工具(Promptfoo / Braintrust…) |
|---|---|---|
| 透明性 | 全代码可见,每步可查 | 打分逻辑部分黑盒 |
| 依赖 | 零外部依赖 | 引入 SDK / 服务 / 账号 |
| CI 嵌入 | 一个脚本即可 | 需适配其 CLI / API |
| UI | 无 | 有看板、失败样本浏览 |
| 数据集版本管理 | 自己维护(进 Git) | 内置版本化 + 在线管理 |
| 在线回流(线上失败→评测集) | 无,需自建 | 部分工具有 |
| 成本 | 人力维护 | 商业授权 / 数据出域 |

**工程启示**:不是「非此即彼」,而是按阶段升级——

1. **起步(<100 用例、单人)**:自建 harness + 黄金集(第 10 章 §8.0),零依赖、
   可嵌入 CI,足够支撑早期迭代;
2. **成长(几百用例、多人协作)**:迁移到 Promptfoo(声明式用例好审 diff)
   或 Braintrust(带数据集管理 + 在线回流);
3. **规模化(跨团队、有数据合规要求)**:平台化,评测集与追踪一体化,
   并接入第 12 章的在线反馈闭环。

**要点**:自建的好处是「每个字节都透明」,坏处是「UI、数据集版本、在线回流
都要自己写」;工具生态相反。绝大多数团队的合理起点是**自建 + 一套黄金集**,
等用例数超过几百、需要多人协作时再迁移。迁移时,第 8 节「数据 / 运行 / 打分 / 报告」
四层分离的骨架,会让替换成本大幅下降——只需要换掉「运行器 + 报告」两层。

## 12. 本节要点

1. 评测是 Agent 工程的第一优先级,因为不确定性与轨迹错误都需要度量;
2. **五维框架**:任务成功率 / 过程质量 / 效率 / 鲁棒性 / 安全;
3. **离线 + 在线组合**:离线迭代,在线把关;
4. 数据集要版本化、要最小回归集、要覆盖边界与异常;
5. **LLM-as-Judge** 是主流,但要做结构化、多次采样、盲评、校准;
6. **轨迹评测**是 Agent 评测的独特之处——结果对≠过程对;
7. 可观测性是评测的前提;
8. **指标要按组切片 + 看方差 + 跟趋势**,成本与质量一起看(`成本/成功率比`);
9. 评测工程化:数据集 + 运行器 + 打分器 + 报告 + CI;
10. 安全评测(AgentDojo 等)正在成为必要维度;
11. 常见错误:不测轨迹、数据集偏、裁判偏差、没有回归集、不跟趋势;
12. **评测 harness 的骨架**(数据集 / 运行器 / 断言 / 报告)在 mini-agent 上
    只需几十行——「结果 + 轨迹」双层断言是 Agent 评测的关键,`AgentResult.messages`
    就是轨迹数据源。

下一章,讲评测的另一面——安全。Agent 越是强大,被攻击的后果越严重。
