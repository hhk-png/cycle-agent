## 1. 为什么需要近似最近邻(ANN)

给定 N 条向量,查询时找「最相似的 k 条」。最直接的做法是**暴力扫描
(brute-force)**:把查询向量与全部 N 条向量逐一算相似度,取前 k。
复杂度 O(N × d),N 为向量数,d 为维度。

- N = 1 万、d = 256:暴力扫描毫秒级,没问题;
- N = 1 亿、d = 1024:暴力扫描需要约 10^11 次浮点运算,单机要数秒——
  无法支撑「在线检索必须几十毫秒返回」的需求。

**近似最近邻(Approximate Nearest Neighbor,ANN)**牺牲一点召回率,换取
数量级的速度提升:它不保证返回「绝对最近的 k 个」,只保证「很可能是最近的 k 个」。
RAG 对召回率的容忍度很高——检索 top-50 再重排取 top-5(第 04 章 §6.2),ANN
带来的少量漏检可以被重排阶段吸收。

> **关键认知**:ANN 是「速度 × 召回率 × 内存」的三方权衡。没有免费的午餐,
> 理解每个算法的取舍,才知道在什么场景选什么。

## 2. 距离度量:先定「什么叫相似」

算法选型之前,先定度量。同一个向量库,换一种距离,检索结果完全不同。

| 度量 | 定义 | 关注 | 适用 |
|---|---|---|---|
| **余弦相似度** | `cos(A,B) = (A·B) / (\|A\|·\|B\|)` | 方向,忽略模长 | 文本语义(最常用):同一话题「说得长/短」都相似 |
| **欧氏距离** | `\|\|A − B\|\|₂ = √Σ(Aᵢ−Bᵢ)²` | 方向 + 模长 | 图像、数值特征;模长本身有意义时 |
| **内积(MIPS)** | `A·B = ΣAᵢBᵢ` | 方向 + 模长(未归一化) | 推荐系统;内积大 = 相关且模长大 |

**工程要点**:

1. **归一化 + 余弦 = 欧氏单调等价**。当 `‖A‖ = ‖B‖ = 1` 时,
   `‖A−B‖² = 2 − 2·cos(A,B)`,排序完全一致。所以很多库建议「先 L2 归一化,
   再用内积」——性能和余弦等价,但很多索引算法对内积有优化;
2. **同一批向量统一度量**。检索与写入必须用同一个度量,换度量 = 全量重建索引;
3. **Embedding 模型决定了「语义相似」的含义**。度量只是「数学上的相似」,
   「语义上的相似」由 embedding 模型的质量决定(§5)。

> **对照 mini-agent**:`src/memory/vector.ts` 用的是余弦相似度 + n-gram 哈希
> 嵌入。骨架与真实系统一致,只是「嵌入」是启发式的。

## 3. 索引算法:暴力扫描之外的三条路线

### 3.1 倒排索引(IVF)

**思想**:先把向量空间用 K-means 聚类切成 `nlist` 个「格子(cell)」,
每条向量归入最近的格子;查询时只搜索 `nprobe` 个「与查询最近的格子」,
在格子内部暴力扫描。

```
写入:  N 条向量 → K-means 聚成 nlist 个质心 → 每条向量挂到最近质心
查询:  找查询最近的 nprobe 个质心 → 只在这些格子内暴力扫描 → 取前 k
```

| 参数 | 含义 | 调大 | 调小 |
|---|---|---|---|
| `nlist` | 格子数 | 内存小、速度快,但可能把相近向量分到不同格子(漏检) | 召回高,但格子大、慢 |
| `nprobe` | 查询扫描的格子数 | 召回高,但慢 | 快,但可能漏检 |

**取舍**:IVF 内存友好(只需存质心 + 原始向量),适合「亿级以内、追求速度」;
召回率受 `nlist`/`nprobe` 影响,是「速度换召回」的典型。

> **读表提示**:`nlist` 是「格子数」——调大 = 格子更细、每个格子里向量更少
> (扫描更快),但「本来该相近的向量」可能被分进不同格子(漏检);调小则相反。
> 直觉类比:把一个大仓库切成更多小隔间,找东西更快,但「两件相邻的东西」
> 更容易被放进不同隔间。实际中 `nlist` 常取「向量数开根号」量级(如 10⁶ 条 → 约 1000),
> `nprobe` 从几到几十逐个试,用评测的召回率(第 10 章)校准。

### 3.2 HNSW(Hierarchical Navigable Small World)

**思想**:构建多层「近邻图」。每一层是一个小世界网络——每个节点连接
若干个近邻;层越高越稀疏(节点越少),层越低越稠密。查询从顶层开始,
逐层贪心向下搜索。

```
第 2 层(稀疏):  ● ─ ● ─ ●          ← 快速定位到「大致区域」
第 1 层(中层):  ● ─ ● ─ ● ─ ● ─ ●
第 0 层(稠密):  ● ─ ● ─ ● ─ ● ─ ● ─ ● ─ ●   ← 精确搜索
```

| 参数 | 含义 | 典型值 | 影响 |
|---|---|---|---|
| `M` | 每节点最多连接数 | 16–64 | 越大图越密、召回越高,内存越大 |
| `efConstruction` | 建图时的搜索宽度 | 100–200 | 越大图质量越高,建索引越慢 |
| `efSearch` | 查询时的搜索宽度 | 50–400 | 越大召回越高,查询越慢 |

**取舍**:HNSW 是目前**召回率与查询速度平衡最好**的算法之一,尤其适合
「数据量适中(< 1 亿)、能放进内存、追求高召回」的场景。缺点是**内存占用大**
(需要全量向量与图结构驻留内存),且**删除/更新成本高**(图结构不易增量维护)。

### 3.3 乘积量化(PQ / Product Quantization)

**思想**:把高维向量**压缩存储**。把 d 维向量切成 m 个子空间(每段 d/m 维),
对每个子空间独立做 K-means 量化成 `k` 个码字;一条向量用 m 个「码字索引」
表示(每段一个整数),存储从「d 个 float」压缩到「m 个整数」。

```
原向量(256 维,256×4B = 1024B)
  → 切成 8 段(每段 32 维)
  → 每段量化成 256 个码字(8 bits 索引)
  → 存储 = 8 个字节
  (压缩约 128 倍)
```

| 变体 | 说明 |
|---|---|
| **PQ** | 标准乘积量化;查询时用「查表法」近似计算距离 |
| **OPQ** | 先对向量做旋转优化再量化,召回略高 |
| **IVF+PQ** | 先用 IVF 缩小范围,再在候选内用 PQ 近似距离——工业标准组合 |
| **HNSW+PQ** | HNSW 构图 + PQ 压缩向量,兼顾召回与内存 |

**取舍**:PQ 把内存占用降一个数量级,是「亿级以上、内存受限」场景的标配;
代价是**距离是近似的**,召回率低于原始向量暴力扫描。通常用「PQ 粗筛 +
原始向量精排」两级策略:先用 PQ 快速找候选,再对候选用原始向量精确算相似度。

### 3.4 算法选型速查

| 场景 | 推荐 | 理由 |
|---|---|---|
| 千万级、内存充裕、要高召回 | **HNSW** | 速度与召回平衡最好 |
| 亿级、内存紧张 | **IVF+PQ / HNSW+PQ** | 内存是关键约束 |
| 数据频繁增删 | **IVF**(或 IVFFlat) | HNSW 动态维护图代价高 |
| 需要确定性精确检索 | **暴力扫描(Flat)** | 数据量小(< 10 万)时最简单 |
| 关系库已有数据 | **pgvector(IVFFlat/HNSW)** | 与 SQL 共存,少一套基础设施 |

> **经验法则**:数据量 < 10 万,暴力扫描就够了(毫秒级,无召回损失);
> < 1 亿用 HNSW;再往上用 IVF+PQ 或分布式向量库。**别一上来就上最复杂
> 的——先暴力,用量与延迟数据驱动升级。**

## 4. 向量数据库与工具选型

「向量库」不是非黑即白——它可以从「一个函数」到「一个分布式系统」:

| 方案 | 形态 | 特点 | 适用 |
|---|---|---|---|
| **FAISS** | Python/C++ 库(非服务) | 最灵活,可嵌入任何系统 | 研究、自建索引、离线建库 |
| **pgvector** | PostgreSQL 扩展 | 与关系数据共存,SQL 查询 | 已有 PG 的中小系统 |
| **Chroma** | 轻量嵌入式向量库 | 零运维、本地优先 | 原型、本地应用 |
| **Qdrant** | 独立向量数据库 | 纯向量、Rust 写、功能聚焦 | 中大规模、需要独立向量服务 |
| **Milvus / Zilliz Cloud** | 分布式向量数据库 | 云原生、水平扩展、多索引 | 亿级以上、生产级 |
| **Weaviate** | 独立向量数据库 | 内置混合检索、GraphQL | 需要混合检索开箱即用 |

**选型考虑因素**(按重要性排序):

1. **数据量级**:10 万 → FAISS/pgvector;千万 → Qdrant/Milvus;亿级 → Milvus/云;
2. **与现有栈的关系**:已有 PostgreSQL → pgvector 最少基础设施;
3. **是否需要过滤**:向量 + 元数据过滤(按用户/时间过滤)是刚需
   (第 04 章按 userId 隔离)。有的库过滤性能好,有的差;
4. **混合检索**:需要 BM25 + 向量融合?Weaviate/Qdrant 原生支持,否则要自建;
5. **运维成本**:独立向量库多一套系统要维护,小团队要掂量。

> **趋势**:pgvector 在中小场景快速普及(「SQL 里顺便存向量」);独立向量库
> 在高吞吐/大规模场景仍是主流。2026 年「向量数据库」正在成为数据库的
> 标准能力,而不是独立品类。

## 5. Embedding 模型选型

### 5.1 什么是好 Embedding

Embedding 模型把文本映射成向量,「语义相近的文本向量也相近」。
**度量只是数学,embedding 决定语义**——同一个检索问题,换 embedding 模型,
结果可能完全不同。

### 5.2 选型的维度

| 维度 | 说明 | 取舍 |
|---|---|---|
| **模型来源** | API(OpenAI text-embedding-3 / 各家)vs 开源(BGE、E5、GTE、m3e) | API 省心但要联网+付费;开源可本地、可微调,但要自己部署 |
| **维度** | 如 384 / 768 / 1024 / 3072 | 维度高信息多但存储与计算贵;很多模型支持 `dimensions` 截断 |
| **语言** | 中文 / 多语言 | 中文场景选对中文优化的模型(m3e、BGE-zh、text-embedding-3 的 multi 模式) |
| **匹配粒度** | 句向量 vs 文档向量 vs 查询-文档匹配 | 有的模型专门为「query-doc 匹配」训练,检索效果更好 |
| **输入长度** | 支持多长文本 | 长文档要切块(§7),块长受 embedding 输入长度限制 |

### 5.3 三个工程经验

1. **先测后选**:用你自己的领域数据,做一个小规模「召回率对比测试」
   (第 04 章 §6.5 的指标),而不是看榜单;
2. **维度够用就好**:3072 维不一定比 768 维好——对中文短文本,很多 768 维
   模型的效果与高维 API 相当,而存储便宜 4 倍;
3. **与下游一致**:如果你用「向量 + 重排」,embedding 只要「召回够好」即可,
   精度靠重排补(§6);如果只靠向量(无重排),embedding 质量就是生命线。

> **对照 mini-agent**:`src/memory/vector.ts` 用 n-gram 哈希做「零依赖嵌入」。
> 它证明了「嵌入的骨架」(写入 → 向量 → 相似度 → top-k)与真实系统一致;
> 生产升级 = 换成真实 embedding 模型 + 向量库,Agent 代码零改动。

## 6. 混合检索与重排序

### 6.1 为什么需要混合检索

**向量检索(语义)**擅长「换个说法也找得到」;**关键词检索(BM25)**擅长
「精确匹配」——ID、型号、专有名词、代码。二者互补:

| 场景 | 向量 | 关键词(BM25) |
|---|---|---|
| 「帮我把手机调成静音」的说明书 | ✅ 能召回 | ❌ 缺关键词可能漏 |
| 「iPhone 15 序列号 SN123456789」 | ❌ 语义无意义 | ✅ 精确命中 |
| 「华为 Mate 60 的屏幕尺寸」 | ✅ | ⚠️ 部分 |

生产最佳实践:**两路检索、结果融合**。

**但不是所有查询都该走两路:查询路由(route per query)**。「恒混合」是多一路
召回(更稳),但每路检索都有成本与延迟。生产系统常按「查询更像哪种」分流:

| 查询特征 | 走哪路 | 例子 |
|---|---|---|
| 专有名词 / ID / 型号 / 精确短语 | 纯 BM25 | 「iPhone 15 序列号 SN123」 |
| 口语化、语义开放、换说法 | 纯向量 | 「怎么把手机调成静音」 |
| 混合(专有名词 + 语义) | 两路 + RRF | 「Mate 60 的屏幕是不是 OLED」 |

路由判定可以很便宜:关键词规则(含正则/型号前缀 → 走 BM25)、轻量分类模型、
或「先 BM25、结果不足再向量」的级联。**经验:先恒混合跑基线,当成本/延迟敏感
且查询类型可分时,再上路由**——用评测(第 10 章)验证路由分流没有损失召回。

### 6.2 融合算法:RRF 与加权

**RRF(Reciprocal Rank Fusion,倒数排名融合)**——不依赖打分绝对值,
只依赖排名,简单稳健(第 04 章 §4.3):

```
RRF(d) = Σ_{r ∈ R_d} 1/(k + r)      (k 通常取 60)
```

其中 `R_d` 是文档 d 在两个结果集中的排名集合。例:文档 d 在向量结果里排第 2、
在 BM25 结果里排第 5,则 `RRF(d) = 1/62 + 1/65 ≈ 0.0315`。

**加权融合**——如果两个结果集打分可归一化(都映射到 0–1):

```
score(d) = α · vector_score(d) + (1−α) · bm25_score(d)
```

- 优点:可控(调 α);缺点:两个打分尺度不同,归一化方法影响结果;
- **经验**:不确定时默认 RRF——它无参数、稳健、效果好。

### 6.3 重排序(Rerank)

向量检索的 top-k 排序「在小 k 时不稳定」,且 ANN 有近似误差。
**重排**是「粗检 + 精排」的两级策略:

```
粗检:  向量 + BM25 → top-50 候选(便宜、快)
精排:  rerank 模型 → 对 50 个候选精确打分 → top-5(贵、慢,但只对少量候选)
```

**两种排序模型的本质区别**:

| | 双编码器(Bi-encoder) | 交叉编码器(Cross-encoder) |
|---|---|---|
| 输入 | query 与 doc **分别**编码成向量 | query + doc **拼接**一起编码 |
| 交互 | 无(只比向量) | 有(模型能看到两者交互) |
| 精度 | 中 | **高**(精度显著优于双编码) |
| 速度 | 快(可预计算 doc 向量) | 慢(每对都要算) |
| 用在哪 | **召回阶段** | **重排阶段** |

**工程要点**:
- 重排只对「候选集」做(如 top-50),候选集小,交叉编码器的慢可以接受;
- 常见模式:「粗检 top-50 → cross-encoder 重排取 top-5」,比「直接向量
  top-5」的端到端效果显著更好(第 04 章 §6.2);
- 重排是 RAG 系统里「投入产出比最高」的改进之一——它不改变索引与检索,
  只加一层精排,就能显著提升「返回给模型的内容质量」。

## 7. 完整 RAG 管线工程

把第 04 章与本节内容拼起来,一条生产级 RAG 管线的每一环与调优点:

```
① 切分 ──► ② 嵌入+索引 ──► ③ 检索 ──► ④ 重排 ──► ⑤ 生成
 文档      embedding/ANN    向量+BM25  cross-encoder   prompt
                 │              │          │             │
            切分策略        索引参数     融合权重     候选数/阈值   引用溯源/无证据拒答
```

### 7.1 切分(Chunking):被低估的第一环

第 04 章 §6.2 给了四种切分策略(固定/结构/语义/递归)。工程要点补充:

- **块大小影响「信息完整性」与「检索粒度」**:块太小,一个完整要点被切碎,
  检索命中「半句话」;块太大,检索命中「一大段」,上下文被无关内容稀释;
  常用 300–800 token + 重叠 15–25%;
- **结构化优先**:Markdown 按标题、代码按函数、论文按段落切——信息边界
  天然完整;
- **切分要与 embedding 匹配**:embedding 输入长度限制决定了块长上限;
- **切分影响评测**:换切分策略 = 召回率变化,用第 04 章 §6.5 的指标验证。

**Contextual Retrieval:给每个 chunk 附「上下文」**(Anthropic 2024 年提出,
近两年性价比很高的实践)。痛点:单个 chunk 脱离文档语境时语义残缺——
比如「它支持 4K」这种句子,单独切出来不知道「它」指什么。做法:构建索引时用
一次模型调用,把「文档标题 + chunk 前后文要点」浓缩成一两句上下文前缀,
拼在每个 chunk 前面再嵌入:

```
原始 chunk:  "它支持 4K 录制"
附上下文后: "本文介绍 GoPro 12 相机功能。它支持 4K 录制。"
```

- **收益**:不换 embedding 模型、不动向量库,单靠给 chunk 补语境就能显著提升召回
  (Anthropic 报告其结合「上下文 + 混合检索」把检索失败率降低约 49%);
- **成本**:多一次离线模型调用(建索引时一次性,可接受);
- **落地**:离线建索引时批量补写,在线检索完全无感;与重排序(§6.3)叠加效果更好。

### 7.2 索引:元数据是「第二索引」

向量检索之外,元数据过滤是第一道粗筛:

```
检索 query 的同时,过滤:
  source = "客服手册" AND lang = "zh" AND updated > 2026-01-01
```

**经验**:把「可以精确过滤的维度」(来源 / 时间 / 用户 / 权限 / 语言)做成
元数据字段,用过滤先粗筛,再向量排序——既快又准,还能实现多租户隔离
(第 11 章按用户隔离)。

### 7.3 检索:多路召回 + 融合

```
路 1:向量 top-50(语义)
路 2:BM25 top-50(字面)
→ RRF 融合 → top-20 候选
→ cross-encoder 重排 → top-3~5 进上下文
```

**为什么多路召回**:不同查询性质不同(§6.1),单路必然有盲区;
**为什么融合后还要重排**:融合结果仍是「粗排序」,交叉编码器才能看
「query 与 doc 的交互」。

### 7.4 生成:把证据交给模型

检索到了,还要让模型「用对证据」:

1. **只放重排后的 top-k**,别把 50 条候选全塞进上下文(稀释注意力 + 烧 token);
2. **引用溯源**:要求模型回答标注来源文档 ID——投毒文档会暴露(第 11 章 §2.4);
3. **无证据拒答**:system 提示声明「没有检索到证据时,明确说'知识库中没有
   相关信息',不要编造」(第 04 章 §6.2);
4. **上下文布局**:检索结果属于「动态段」,放在最近消息(缓存友好,第 05 章 §4)。

### 7.5 RAG 调优的顺序(经验)

按「投入产出比」排序:

1. **重排**(cross-encoder)——收益最大、改动最小;
2. **切分策略**——结构化切分通常立竿见影;
3. **混合检索**——解决「精确匹配漏检」;
4. **embedding 换模型**——语义质量的地基,但成本高、要全量重索引;
5. **元数据过滤**——减少噪声、多租户隔离。

> **每改一步都要评测**(第 04 章 §6.5、第 10 章):「召回率 / 答案正确率 /
> 引用准确率 / 无证据拒答率」四个指标一起看,而不是「感觉好了」。

### 7.6 四个指标的「可计算定义」

正文反复说「四个指标一起看」,这里给出能直接落地计算的定义:

**① 召回率 Recall@k(检索质量)**
> 对每个评测问题,标注「应命中的相关文档集 R」,取检索返回的 top-k,统计命中比例:
> $$\text{Recall@k} = \frac{|\\{\text{返回的 top-k}\\} \cap R|}{|R|}$$
> 它回答「该检到的检到了多少」。注意:它不度量「检回来的有多少是噪音」
> (那是**精度 Precision@k**);RAG 里召回率通常比精度更重要,因为噪音可以靠重排过滤,
> 漏检无法补救。

**② MRR / 排名(检索质量)**
> 对每个问题,取第一个相关文档在返回列表里的位置:
> $$\text{MRR} = \frac{1}{|Q|}\sum_{q \in Q}\frac{1}{\text{rank}_q}$$
> 回答「相关文档排得多靠前」。当「只要第一页就够」时比 Recall@k 更贴近体验。

**③ 答案正确率(端到端质量)**
> 用黄金答案集 + 结果断言(第 10 章)判断最终回答对不对。它是**唯一能拍板的
> 指标**——检索分再高,答案不对就没用。

**④ 引用准确率 / 无证据拒答率(可信度)**
> - **引用准确率** = 「回答中每个引用真的支持该论断」的比例(人工或 LLM 裁判
>   逐条核对);
> - **无证据拒答率** = 在「知识库里确实没有答案」的用例上,模型诚实说
>   「不知道」的比例。它直接度量第 04 章「没有证据就说不知道」这条约束的遵守情况。

> **用哪个?**:调检索参数看 ①②;调提示词/生成看 ③④。**线上监控**看 ③④
> (端到端),**离线诊断**看 ①②(定位是检索问题还是生成问题)。

## 8. RAG 的失败模式与诊断

第 04 章 §6.3 给了 RAG 的四类失败模式。这里补上「怎么诊断」:

| 症状 | 可能根因 | 诊断动作 | 修复 |
|---|---|---|---|
| 答非所问 | 检索到的内容不相关 | 看「检索返回的 top-k 原文」:相关吗? | 换 embedding / 调切分 / 加重排 |
| 答案缺关键点 | 相关文档没被检索到 | 手动用 query 检索,看相关文档排第几 | 多路召回 / 调大候选数 / 调索引参数 |
| 看着对但编造 | 生成阶段没有「无证据拒答」约束 | 检查引用:回答里的每个论断有出处吗? | 加引用溯源 + 无证据拒答 |
| 上下文被无关内容稀释 | 候选太多 / 阈值太松 | 看进入上下文的片段数 | 收紧 top-k / 加阈值 / 加重排 |
| 增量更新后变差 | 索引没重建 / 脏数据 | 对比更新前后评测 | 全量重建索引 / 去重 |
| 检索慢 | 索引参数不当 / 数据量大 | 看 P95 查询延迟 | 调 `efSearch`/`nprobe`/上 HNSW |

> **诊断的核心心态**:把 RAG 当成一条**可拆开的管线**来调——先定位「是哪
> 一环坏了」(切分 / 检索 / 重排 / 生成),再对症下药。不要「整体重写」。

## 9. 从 RAG 到 Agentic RAG:把检索交给 Agent

第 04 章 §6.4 讲了 Agentic RAG——检索次数、查询改写、充分性判断交给模型。
工程上的落地点:

1. **检索工具化**:`search(query, filters)` 是 Agent 的一个工具
   (mini-agent 的 `web_search` 是 mock 版);
2. **查询改写**:模型把「用户问题」改写为「检索查询」——加入上下文、
   拆成多查询(「他们上个月说的是哪个项目?」→ 检索「项目名 + 上个月」);
3. **迭代检索**:第一次结果不足,模型判断「还缺什么」再检索一次;
4. **充分性判断**:模型判断「证据够不够」,够了就停,不够再查;
5. **设上限**:检索次数上限(如 3 次),防止 Agent 无脑循环检索烧 token。

> **与普通 RAG 的选择**:问题固定、知识静态 → 普通 RAG(便宜快稳);
> 问题开放、需要多步推理 → Agentic RAG(灵活准,但贵)。
> **先普通后 Agentic**,用评测证明「普通 RAG 的检索次数 / 覆盖率」确实
> 是瓶颈时再升级。

## 10. 对照 mini-agent

| 概念 | mini-agent 落点 | 生产升级 |
|---|---|---|
| 余弦相似度 | `src/memory/vector.ts`(cosine) | 换真实度量或归一化内积 |
| 嵌入 | n-gram 哈希(256 维) | 真实 embedding 模型(§5) |
| 向量库 | 内存数组 | pgvector / Qdrant / Milvus(§4) |
| 检索 | `search(query, k, threshold)` | ANN 索引 + 元数据过滤(§3、§7.2) |
| 混合检索 | 未实现 | BM25 + 向量 + RRF(§6.2) |
| 重排 | 未实现 | cross-encoder 精排(§6.3) |
| RAG 评测 | `examples/eval-agent.ts` | 召回率 + 引用准确率 + 无证据拒答(§8) |

骨架不动,把 `VectorMemory` 内部换成真实向量库 + 真实 embedding,再按 §6
加上混合检索与重排——就是一条生产级记忆/RAG 管线。

## 11. 本节要点

1. **ANN 是「速度 × 召回率 × 内存」的三方权衡**;数据量小直接暴力扫描;
2. **距离度量先于算法**:余弦看方向、欧氏看大小、内积看未归一化点积;
   归一化后余弦与欧氏排序等价;
3. **三条索引路线**:IVF(聚类粗筛 + 暴力细扫)、HNSW(多层近邻图,召回/速度
   平衡最好、内存大)、PQ(量化压缩,亿级内存受限场景标配);工业常用
   IVF+PQ / HNSW+PQ;
4. **向量库选型按数据量与现有栈**:<10 万暴力扫描;中小用 pgvector/FAISS;
   中大型用 Qdrant/Milvus/Weaviate;
5. **Embedding 决定「语义相似」的含义**:先测后选、维度够用就好、与重排配合;
6. **混合检索 = 向量(语义)+ BM25(字面)**,用 RRF(无参数、稳健)或加权融合;
7. **重排(交叉编码器)是 RAG 投入产出比最高的改进**——粗检 top-50 →
   精排取 top-5;
8. **RAG 是一条可拆开的管线**(切分 → 索引 → 检索 → 重排 → 生成),
   每环都有评测指标;诊断先定位「哪一环坏了」;
9. **元数据过滤是「第二索引」**:可精确过滤的维度先粗筛,再向量排序,
   顺带实现多租户隔离;
10. **生成阶段**:只放重排后 top-k、强制引用溯源、无证据拒答、动态段放
    最近消息(缓存友好);
11. **Agentic RAG 把检索次数/查询改写/充分性判断交给模型**,设检索上限
    防跑偏;先普通后 Agentic,评测驱动;
12. 与第 04 章的关系:第 04 章是「记忆的骨架」,本附录是「检索的工程
    细节」——两者合起来才是完整的记忆/RAG 工程。
