# 06 主流框架

> 本章目标:横向盘点 2026 年主流的 Agent 框架——它们各自的抽象、优劣势、适用场景,
> 以及最重要的:如何根据你的需求选框架。

---

## 1. 为什么框架这么多,而且还在变

Agent 框架的演化遵循一个经典周期:先有「胶水库」统一各家模型接口,
再出现「编排层」控制 Agent 循环,接着「状态化」「多智能体」「协议化」逐层叠加,
最后又分化为「图式状态机」与「轻量循环」两条路线。到 2026 年,生态大致分成五类:

| 类别 | 代表 | 核心抽象 | 优势 |
|---|---|---|---|
| **循环型 harness** | OpenAI Agents SDK、Claude Agent SDK | Agent 循环 + 工具 + 护栏 | 贴近模型原生能力,简单直接 |
| **图式编排** | LangGraph | 显式状态图(节点/边/状态) | 确定性、可审计、支持复杂流 |
| **多智能体框架** | CrewAI、AutoGen/AG2、Microsoft Agent Framework | 角色化团队 / 群聊 | 分工协作开箱即用 |
| **胶水库** | LangChain、LlamaIndex | 组件抽象 + RAG 管线 | 生态最全、组件最多 |
| **应用集成派** | Vercel AI SDK、Mastra | 把 Agent 嵌进 Web/移动/全栈应用 | 前后端一体、Streaming/UI 原生 |

> **应用集成派**是 2025–2026 年把 Agent 送进真实产品的主要路径:它不强调
> 「Agent 框架」本身,而是提供「在 TypeScript/React 应用里用 Agent + 流式 UI +
> 工具 + 记忆」的一体化 SDK。与「胶水库」的区别:胶水库把 LLM 当「组件」,
> 应用集成派把 Agent 当「产品功能」——如果你的目标是把 Agent 装进一个已有的
> Web 应用,这类框架往往比图式编排更快上手。选型时别忘了它。

> 读这一章时请记住:**框架是「当时最优」的封装,不是「永远正确」的真理。**
> 第 07 章你会亲手实现一个最小 Agent,届时这些框架的抽象对你都是透明的。

### 1.1 一条时间线:看懂框架为什么长这样

| 时间 | 事件 | 留下的遗产 |
|---|---|---|
| 2022 | **LangChain** 发布,「胶水库」爆发 | 「组件抽象」成为 LLM 工程的共同词汇 |
| 2023.10 | **AutoGen** 发布,对话式多智能体 | GroupChat + 人类代理模式 |
| 2023.11 | **CrewAI** 发布,角色化团队 | 「角色 / 任务 / 流程」的低门槛心智 |
| 2024.1 | **LangGraph** 重构 LangChain,状态图 | 显式状态 + 检查点成为企业级标配 |
| 2024.11 | **MCP** 发布,工具接入协议化 | 「连工具」从私有集成走向标准协议 |
| 2025.3 | **OpenAI Agents SDK** 发布(Swarm 后继) | handoff + 三层护栏 + 内置追踪 |
| 2025.6 | **A2A** 由 Google 捐赠 Linux 基金会 | 「连 Agent」也开始标准化 |
| 2025.12 | **MCP** 捐赠 Linux 基金会(旗下 AAIF) | 协议治理进入中立轨道 |
| 2025–2026 | **Claude Agent SDK**(Claude Code 开源) | 深度自主 Agent + 最全 MCP 生态 |
| 2026 | A2A 并入 **Agentic AI Foundation**(与 MCP 同归);Google ADK 三协议 | 双协议同归中立治理 |

**规律**:每 6–12 个月换一个「主角」,但每一次演进都在解决上一代的一个
具体痛点——Chain 太静态 → 状态图;集成太私有 → 协议;Agent 太弱智 →
深度自主。看懂时间线,就看得懂「下一个主角」大概会长什么样。

## 2. LangChain 与 LangGraph

### 2.1 LangChain(胶水库)

LangChain(2022)是最早出圈的 LLM 框架,核心是**组件抽象**:

- `ChatModel` / `LLM`:统一各家模型接口;
- `PromptTemplate`:提示模板;
- `Tool`:工具抽象;
- `Retriever` / `DocumentLoader`:RAG 组件;
- `Chain`:把组件串成流水线。

**问题**:Chain 是静态的,难以表达「循环」「条件分支」「状态」。
社区一度批评 LangChain「抽象过度、黑盒、难调试」。

### 2.2 LangGraph(图式状态机)

LangGraph 是 LangChain 团队针对 Chain 缺点的重构,2024 年发布后快速成为
**企业级 Agent 编排的事实标准之一**,2026 年初在 GitHub stars 上超过 CrewAI。

核心抽象是一个**显式状态图**:

```python
from langgraph.graph import StateGraph, END

graph = StateGraph(State)
graph.add_node("agent", call_agent)       # 节点 = 一步逻辑
graph.add_node("tools", call_tools)
graph.add_edge("agent", "tools")          # 边 = 控制流
graph.add_conditional_edges("tools", should_continue, {"continue": "agent", "end": END})
```

**LangGraph 的关键能力**:

1. **显式状态(state)**:所有数据(消息、工具结果、计数器)存在一个状态对象里,
   图上的每个节点读写状态。这让「执行到哪了」完全可见。
2. **检查点(checkpoint)**:每个节点执行后落盘,支持**断点续跑 / 时间旅行调试**——
   「回放任意一次运行」是企业审计的刚需。
3. **持久化**:状态可存数据库,进程重启不丢——生产可靠性的基础。
4. **人工介入(human-in-the-loop)**:节点可配置为「暂停等人工批准」。
5. **条件分支 / 循环 / 并行**:图天然表达,比 Chain 的线性流水线强一个维度。

**适配**:`interrupt()` 暂停、`Command` 跳转、流式输出、多 Agent(子图)。

**优劣势**:
- 优点:确定性、可审计、模型无关、支持复杂控制流与检查点;
- 缺点:学习曲线陡、样板代码多、对简单 Agent 是过度设计。

**适用**:企业级工作流,需要状态、重试、人工审批、合规审计的场景。

## 3. CrewAI(角色化多智能体)

CrewAI(2023)把 Agent 建模成「角色(role)+ 目标(goal)+ 背景(backstory)」,
组合成一个 **Crew(团队)**,任务按依赖关系在成员间流转。

```python
from crewai import Agent, Task, Crew, Process

researcher = Agent(role="研究员", goal="搜集资料", backstory="资深研究员")
writer = Agent(role="写手", goal="输出报告", backstory="资深编辑")

research = Task(description="调研 AI Agent 现状", agent=researcher)
write = Task(description="写成 3 句总结", agent=writer)

crew = Crew(agents=[researcher, writer], tasks=[research, write], process=Process.sequential)
crew.kickoff(inputs={"topic": "AI Agent"})
```

**特点**:
- **上手最快**:约 20 行代码出一个多 Agent demo,学习曲线全生态最低;
- **原生支持协议**:是少数同时支持 MCP 与 A2A 的框架之一;
- **进程模式**:顺序(sequential)、层级(hierarchical)等;
- 任务依赖建模、工具复用、memory 支持。

**局限**:
- 角色化的「背景故事」对模型行为的约束有限(本质是提示词调味);
- 对执行细节的控制弱于 LangGraph,复杂系统常从 CrewAI 迁到 LangGraph;
- 类型安全弱(运行时校验)。

**适用**:快速原型、内容生产、研究管线;团队想「用最小成本跑通多 Agent」。

## 4. AutoGen / AG2 / Microsoft Agent Framework

AutoGen(Microsoft, 2023)是**对话式多智能体**的开创者:
Agent 之间通过「对话」协作(GroupChat + speaker selection),支持嵌套对话与人类代理。

2026 年的 AutoGen 版图比较分裂,需要澄清:

| 项目 | 状态 | 定位 |
|---|---|---|
| **AutoGen(原版)** | 维护模式,无新特性 | 历史经典,不建议新项目 |
| **AG2** | 社区活跃分支(原创作者维护) | 延续 AutoGen 的多 Agent 对话模式 |
| **Microsoft Agent Framework** | 2025 年合并 Semantic Kernel,2026 年 1.0 | 微软企业级方向,Azure/.NET 生态 |

**特点(AutoGen 系)**:
- GroupChat:一组 Agent + 发言者选择(轮流/自动);
- Human-in-the-loop:可以随时插入「人类代理」;
- 嵌套对话、代码执行、多模态。

**优劣势**:
- 优点:多 Agent 对话模式丰富,历史贡献大(很多框架的模式源自它);
- 缺点:品牌混乱;AG2 API 偶有破坏性变更;对话模式对非聊天型任务适配差。

**适用**:研究、已有 AutoGen 系统的维护;微软技术栈选 Microsoft Agent Framework。

## 5. OpenAI Agents SDK

OpenAI 的官方 Agent SDK(2025 年 3 月发布,替代实验性的 Swarm)是
**循环型 harness** 的代表。核心抽象是 **handoff(交接)**:
Agent 通过一个特殊工具调用把控制权转给另一个 Agent,上下文随之传递。

```python
from agents import Agent, Runner

support_agent = Agent(name="客服", instructions="解决订单问题", tools=[query_order])
escalation_agent = Agent(name="升级代理", instructions="处理投诉")

# handoff:客服 Agent 判断处理不了时,把会话交接给升级代理
support_agent.handoffs = [escalation_agent]

result = Runner.run_sync(support_agent, "我要投诉!")
```

**特点**:
- **handoff 模型**:交接即「调用 transfer 工具」,无需共享状态总线,实现干净;
- **三层护栏**:input guardrails / output guardrails / tool guardrails,默认并行;
- **结构化输出**:默认按 JSON Schema / Pydantic 校验;
- **内置追踪**:dashboard 观测每次运行;
- 2026 年 4 月更新加入了沙箱执行与模型路由(按步切换模型)。

**优劣势**:
- 优点:与 OpenAI 模型配合最佳、生产级护栏、上手快;
- 缺点:OpenAI 优先(换模型体验降级);状态模型弱于 LangGraph;
- 仍处 0.x,API 在演进。

**适用**:已绑定 OpenAI 模型、需要「可预测的 Agent 循环 + 护栏」的生产系统。

## 6. Claude Agent SDK(Anthropic)

Anthropic 的官方 SDK(2026 年初由 Claude Code SDK 更名而来),
定位是「**深度自主 Agent**」:同构于 Claude Code 的 Agent 循环,
能自主规划、行动、自我修正,并深度集成 MCP。

**特点**:
- **最深的 MCP 集成**:200+ 现成 MCP 服务器,一行配置接入
  (GitHub、Slack、Postgres、Notion 等);
- **内置工具**:文件操作、Bash、编辑、搜索、computer use,
  复用 Claude Code 的战斗经验;
- **子 Agent 架构**:上下文隔离 + token 归因;
- **生命周期钩子**:PreToolUse / PostToolUse / Stop / SessionStart / SessionEnd,
  是治理与审计的关键扩展点;
- **Extended thinking**:思考与行动交错执行(think → act → refine)。

**优劣势**:
- 优点:自主 Agent 能力最强、MCP 生态最丰富、内置工具齐、钩子体系完整;
- 缺点:Anthropic/Claude 优先(换模型体验降级);Python 与 TS SDK 分开维护;
- 0.x 版本,定价与产品方向偶有调整。

**适用**:编码 Agent、系统级访问、长文档分析、需要深度 MCP 的自主任务。

## 8. 横向对比(2026 视角)

| 维度 | LangGraph | CrewAI | OpenAI SDK | Claude SDK |
|---|---|---|---|---|
| 核心抽象 | 状态图 | 角色团队 | Agent 循环 + handoff | Agent 循环 + 内置工具 |
| 学习曲线 | 陡 | 最平 | 平 | 平 |
| 控制精度 | 最高 | 中 | 中 | 中高 |
| 状态/检查点 | 强 | 弱 | 中 | 中 |
| MCP 支持 | 有 | 有 | 有 | 最全 |
| A2A 支持 | 部分 | 原生 | 部分 | 无 |
| 模型绑定 | 无 | 无 | OpenAI 优先 | Claude 优先 |
| 生产成熟度 | 高 | 中 | 中 | 中 |
| 调试可观测 | LangSmith | 一般 | 内置 tracing | 内置 |
| 最适用 | 复杂工作流 | 快速原型 | OpenAI 生产 | 自主 Agent |

> 一个「坏消息」:2026 年的共识是 **没有框架在所有维度赢**。
> LangGraph 赢生产编排、Claude SDK 赢自主深度、CrewAI 赢易用、OpenAI SDK 赢护栏。
> 「记忆」是所有框架的普遍短板——没有一个具备生产级长程记忆 + 语义检索 + 自动整理。
> 而「上下文工程」(预算 / 缓存 / 压缩,第 05 章)恰恰是**框架不帮你做的事**——
> 框架给你循环与编排,但「怎么把信息装进上下文」仍是你自己的责任。

## 9. 怎么选:一个决策框架

选择框架前,先回答五个问题:

1. **你的流程是确定还是不确定?**
   - 确定 → 用 Workflow 或 LangGraph 的显式图;
   - 不确定 → 用 Agent 循环型框架。
2. **是否绑定某家模型?**
   - 是 → 用该家官方 SDK;
   - 否 → LangGraph / CrewAI 等模型无关框架。
3. **需要人工审批 / 审计 / 断点续跑吗?**
   - 需要 → LangGraph(检查点是杀手锏)。
4. **任务的失败模式是什么?**
   - 静默失败(结果错但看起来对)→ 需要显式状态 + 追踪 → LangGraph;
   - 噪音失败(循环、报错)→ 需要 harness 的停止条件 + 沙箱 → 官方 SDK。
5. **团队规模与迭代速度?**
   - 小团队快速验证 → CrewAI / 官方 SDK;
   - 大团队复杂系统 → LangGraph + 内部封装。

**再补一条被反复验证的经验**:
> **别为「多 Agent」而多 Agent。** 很多「多 Agent 需求」用「单 Agent + 好工具」
> 就能解决,而且更便宜、更可靠。先单后多,用评测数据驱动升级。

### 9.1 三个选型案例(把决策框架用起来)

**案例一:企业内部知识库问答 + 客服。**
- 需求:确定性高(查文档、走工单)、需要审计、要人工审批退换货;
- 决策:流程大部分确定 → **LangGraph**(显式图 + 检查点 + interrupt 审批);
- 理由:可审计、可断点续跑、人工介入原生支持。

**案例二:已绑定 OpenAI 的创业公司,做一个代码审查 Agent。**
- 需求:循环 + 护栏 + 快速上线;
- 决策:**OpenAI Agents SDK**;
- 理由:与 OpenAI 模型配合最佳、三层护栏开箱即用、内置追踪。

**案例三:要接 MCP 生态的深度自主 Agent(写代码、操作文件)。**
- 需求:自主规划、系统级工具、大量 MCP 服务器;
- 决策:**Claude Agent SDK**;
- 理由:MCP 生态最全、内置工具成熟、生命周期钩子利于治理。

> 三个案例的共同点:**先列需求,再选框架,而不是先选框架再适配需求。**
> 需求清单里最关键的三个问题永远是:确定还是不确定?绑不绑模型?
> 要不要审计/人工介入?

## 10. 与 mini-agent 的关系

mini-agent 不是要替代任何框架,而是**剥掉封装让你看见本质**:

| 框架抽象 | mini-agent 对应 | 说明 |
|---|---|---|
| LangGraph 的 State | `Message[]` + `AgentRunStats` | 状态就是消息历史 + 统计 |
| LangGraph 的节点/边 | `run()` 循环 + 停止条件 | 循环是隐式图 |
| CrewAI 的角色 | `RoleAgent`(多智能体) | role 只是 system prompt + 工具集 |
| OpenAI SDK 的 handoff | `MessageBus.send`(协作) | 交接 = 传递任务上下文 |
| OpenAI SDK 的 guardrails | `ToolRegistry` 校验 + 第 11 章护栏 | 入参校验 + 输出策略 |
| Claude SDK 的内置工具 | `createBuiltinTools` | 工具是 Agent 能力边界 |
| MCP 集成 | `StdioMcpClient` | 协议化工具接入 |

> 当你读完第 07 章、亲手实现一遍循环后,再看 LangGraph 的 `StateGraph`、
> CrewAI 的 `Crew`、OpenAI 的 `Runner`,都会是「原来是这么回事」。

## 11. 本节要点

1. 框架分四类:循环型 harness / 图式编排 / 多智能体 / 胶水库;
2. **LangGraph**:状态图 + 检查点,企业级复杂工作流的当前主流;
3. **CrewAI**:角色化团队,上手最快,适合原型与内容管线;
4. **AutoGen 系**:品牌分裂,历史贡献大,新项目谨慎;
5. **OpenAI SDK**:handoff + 三层护栏,适合 OpenAI 绑定的生产;
6. **Claude SDK**:自主 Agent + 深度 MCP + 生命周期钩子;
7. 记忆是所有框架的短板;协议化(MCP/A2A)是 2026 的共同方向;
8. **框架演化有规律**:每次换代都在解决上一代的具体痛点(Chain 太静态→图;
   集成太私有→协议;Agent 太弱智→深度自主);
9. **选框架先回答「确定 vs 不确定」「绑不绑模型」「要不要审计」**,
   用案例验证决策(见 §9.1);
10. 先单 Agent 后多 Agent,用评测驱动升级。
