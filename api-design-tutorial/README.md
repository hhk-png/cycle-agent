# API 设计全景：从契约到商业

> 一本关于 API 的原理、协议、工程、领域实践、AI 演进与商业化的系统教程。

API 是软件世界最不起眼、却最昂贵的东西。

它通常只有几行 JSON、一个 URL、一次握手，看起来像“把数据暴露出去”这样简单的工作。但真正决定一个 API 成败的，往往不是代码写得多快，而是几年之后：当第一个破坏性变更到来时，你能不能安全地演进；当调用方从 3 个变成 30 万个时，你还能不能定位一次慢请求；当监管、攻击、组织调整和商业目标同时压过来时，这份契约还站不站得住。

这本教程试图把 API 设计从“接口写法”提升为一项完整的工程与商业能力。它既讨论字段名、状态码、分页游标，也讨论组织边界、协议选型、可观测性、AI Agent、定价与单位经济。原因很简单：**API 是技术决策，也是组织决策，最终还会变成商业决策。**

---

## 这本书适合谁

- **后端工程师 / 架构师**：想建立完整的 API 设计判断力，而不只是记住 REST 规范。
- **平台与基础设施团队**：正在建设 API 网关、开发者平台、服务治理或内部开发者门户。
- **技术负责人 / 产品经理**：需要理解 API 的成本、演进规律和商业价值。
- **创业者 / 商业化负责人**：正在设计 API 产品、用量计费、开发者生态或平台战略。
- **AI 工程师**：正在设计 LLM、RAG、Agent 与工具调用接口，希望避免把传统 API 的错误复制到 AI 时代。
- **安全、合规与法务协作人员**：需要把监管条款、审计要求与合同承诺翻译成可实现的 API 能力与证据。
- **准备面试或做系统设计的人**：需要一套能覆盖广度、又能落到细节的知识框架。

## 这本书不是什么

- 它不是某个框架的说明书。示例会用到 HTTP、OpenAPI、gRPC、GraphQL、AsyncAPI、MCP 等，但重点永远是**为什么这样设计**。
- 它不是“最佳实践清单”。大多数设计问题没有唯一正确答案，只有约束下的权衡。书中会明确给出立场，也会说明立场失效的条件。
- 它不追求枚举所有厂商和所有标准版本。协议与产品变化很快，书里更重视那些跨越版本仍然稳定的原理。
- 它不把“RESTful”当作道德标准。REST、RPC、GraphQL、事件、流式接口各有适用边界，风格之争通常掩盖了真正的问题：消费者是谁、契约如何演进、失败如何被处理。

## 全书结构

教程分为七部分，共 56 章，另有 38 个附录。

### 第一部分：契约与建模

从“API 是什么”出发，建立契约、边界、产品三种视角；随后进入领域建模、风格选型、命名、表示、错误、分页、写操作、版本与异步任务。这一部分是全书的地基。

### 第二部分：安全与运行

认证、授权、限流、缓存、实时通信、文件传输、多租户与安全纵深。这些能力不属于某个业务，却几乎决定每个业务 API 能否上线。

### 第三部分：协议与架构

HTTP 的深层语义、REST 与超媒体、gRPC、GraphQL、事件驱动、Webhook、网关、服务网格、BFF、契约优先。这里讨论“用什么承载契约”，以及不同协议背后的真实代价。

### 第四部分：工程质量与产品化

测试、可观测性、性能、可靠性、SDK、文档与开发者体验、治理、发布与弃用。API 不是写完就结束，它需要像产品一样被运营。

### 第五部分：领域实战

电商、支付、SaaS、IoT、数据平台、内部平台六个高价值场景。每一章都从领域约束出发，给出关键资源、状态机、失败模式与设计取舍。

### 第六部分：AI 与未来

LLM API、RAG 与向量检索、Agent 协议（MCP / A2A）、AI 原生 API，以及协议与架构的前沿。重点不是追逐名词，而是理解“当消费者从人变成 Agent”时，契约会发生什么变化。

### 第七部分：商业分析

商业模式、定价、单位经济、市场与生态、运营指标、风险与组织路线图。技术读者可以借此理解 API 为什么值钱、钱从哪里来、成本花在哪里；商业读者可以理解技术约束如何塑造商业模式。

## 阅读约定

- **契约**：这里指 API 生产者与消费者之间可验证的约定，包括语法、语义、行为、错误、性能和生命周期，而不只是 OpenAPI 文件。
- **消费者**：任何调用 API 的主体，可能是前端、移动端、合作伙伴、内部服务、脚本，也可能是 AI Agent。
- **资源**：领域中被命名、可寻址、可操作的对象或概念。资源不必然对应数据库表。
- **操作**：难以自然表达为资源状态变化的动作，例如支付、取消、重试。
- **SLO / SLI / SLA**：分别指服务等级目标、指标与协议。SLA 通常带有商业与法律承诺，不能与内部 SLO 混为一谈。
- **代码示例**：以 HTTP/JSON、TypeScript、Python、Go、Protobuf、GraphQL SDL、YAML 为主；形式化与数据章节会用到 TLA+、Alloy 与 SQL。示例为了表达设计意图，省略了部分生产环境所需的鉴权、日志和异常处理。
- **“必须 / 应该 / 可以”**：分别表示强约束、默认建议、可选做法。书中给出的“必须”只在其约束成立时成立。

## 如何使用这本书

不要把每一章当作孤立的知识点。每读完一章，尝试用它审视一个你正在维护的 API，并回答三个问题：

1. **这份契约服务谁？** 他们的任务、失败模式、演进节奏是什么？
2. **哪些决定一旦发布就会变成负债？** 标识、错误码、分页方式、认证模型、事件语义通常比字段类型更难改。
3. **如何验证？** 有没有契约测试、负载测试、故障演练、弃用演练和真实的开发者反馈？

API 设计的成熟，不是记住更多规则，而是更早看见后果。
