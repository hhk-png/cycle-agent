# 第 1 章 API 的本质：契约、边界与产品

## 1.1 一个定义，三种读法

如果只允许给 API 下一个定义，我倾向于：

> **API 是两个独立主体之间，为了完成某项任务而建立的、可被验证的长期约定。**

这个定义刻意回避了“HTTP”“JSON”“接口地址”这些实现词汇。因为 API 的真正难点从来不是“怎么把数据发出去”，而是“两个可能互不信任、独立演进的主体，如何在一段时间内稳定协作”。

定义里有四个关键词。

- **独立主体**：双方可以独立部署、独立演进，甚至属于不同公司。独立性越高，协调成本越大，契约就越重要。同一个进程里的两个函数不需要 API 契约，因为它们共享编译器、类型系统和发布节奏；两个公司之间则需要。
- **任务**：API 不是“暴露数据”，而是帮助调用方完成一件事。数据只是任务的材料。用户要的不是“订单表”，而是“查到订单、知道能不能退、把退款办成”。
- **可验证**：约定不能只存在于文档或口头理解中，必须有 schema、测试、示例或运行时校验来确认。不能被验证的承诺，在故障发生时通常也说不清是谁的责任。
- **长期**：一次性的脚本可以随意，长期契约必须考虑演进、弃用和故障。一个只活三天的内部脚本，和一个要被上千个合作伙伴集成五年的支付接口，应当用完全不同的设计标准。

由此可以展开三种读法。

### 契约：语法、语义、行为

- **语法**：URL、方法、字段名、类型、必填性、编码。语法是契约中最容易被工具捕捉的部分，也是 OpenAPI、Protobuf、GraphQL SDL 最擅长的部分。
- **语义**：字段代表什么，状态转换意味着什么，错误码在什么条件下出现。语义决定了调用方是否真的理解你。
- **行为**：超时、重试、并发、幂等、一致性、速率限制、弃用节奏。行为决定了系统在异常时是否仍然可信。

大多数团队只关注语法，因为语法最容易写进 OpenAPI 文件。但线上事故往往来自语义和行为：

- `status = "PAID"` 到底表示支付成功、支付已授权，还是渠道返回成功但尚未对账？
- 重复提交同一请求会不会扣两次款？
- 删除后立即查询是否还能看到？
- 接口在 P99 延迟 3 秒时，调用方的 1 秒超时会不会触发重试风暴？
- 新增一个枚举值，会不会让某个严格校验的客户端整页崩溃？

这些问题没有一个能靠“字段类型写对了”解决。

### 边界：谁负责什么

API 是组织边界的物化。一个接口的归属、数据所有权、失败责任和变更审批，通常比技术实现更能决定它的命运。

好的边界有三个特征：

1. **高内聚**：同一业务不变量由同一方维护。订单金额的计算规则、状态机、退款条件，应该由同一个边界负责。
2. **低耦合**：调用方不需要了解提供方的内部实现。调用方不应该知道你的订单服务用了分库分表，也不应该依赖某个内部枚举的数值。
3. **失败可隔离**：一个边界内的故障不会无限制地传播。推荐服务挂掉，不应该让下单主链路一起挂掉。

当 API 跨越边界却没有明确责任时，就会出现典型的“分布式泥球”：每个人都能改，没人能保证语义；每个服务都依赖其他服务，却没有一个服务能独立上线。

一个实用的检验方法是问三个问题：

- 这个 API 依赖的数据，是否由一个团队拥有？
- 这个 API 的不变量，是否能在边界内被维护？
- 这个 API 在凌晨三点出故障时，谁被叫醒？

如果三个答案指向不同的团队，边界大概率有问题。

### 产品：谁愿意用，为什么

公开 API、合作伙伴 API，甚至内部平台 API，都具有产品属性。产品属性意味着：

- 有明确的用户与使用场景；
- 有上手成本、留存、扩展和支持问题；
- 有版本、定价、文档和服务等级；
- 需要被运营，而不只是被发布。

一个技术上优雅但没人愿意接入的 API，是失败的产品。一个产品上成功但契约混乱的 API，则会在规模扩大后变成技术债。

产品视角还会反过来改变技术决策。例如：

- 如果目标是“开发者十分钟跑通”，那么认证流程、沙箱、示例和错误信息的重要性会超过极致的性能。
- 如果目标是“金融级可靠性”，那么幂等、对账、审计和多区域容灾会压过接入门槛。
- 如果目标是“内部平台自助化”，那么 API 的发现性、权限申请和模板化会比公网 CDN 缓存更重要。

这三种视角并不冲突，而是同一枚硬币的三面。只懂协议的人会设计出“语法正确但没人想用”的接口；只懂业务的人会承诺系统无法兑现的 SLA；只懂架构的人可能把一次简单查询做成需要三支团队排期的分布式事务。

本教程的核心主张是：

> **好的 API 设计，是在明确约束下，同时照顾契约、边界与产品三种视角的持续决策过程。**

## 1.2 API 的成本曲线

API 的成本不是线性的，而是“前期便宜、后期昂贵”。更准确地说，是**修改成本随时间指数上升，而设计成本在前期几乎不变**。

### 设计时

设计阶段多投入的一天，通常能在未来省掉数周甚至数月：

- 多花一天想清楚资源模型，可能省掉未来几个月的兼容层。
- 多定义一个稳定的错误码，可能减少大量支持工单。
- 多考虑一种重试场景，可能避免一次资金损失。
- 多花半天定义金额与时间的表示，可能避免一次跨时区对账事故。
- 多写一个 `Idempotency-Key` 参数，可能避免一次重复扣款。

这些投入的共同点是：**成本发生在只有少数人知道的时候，收益发生在所有人都依赖之后。**

### 发布后

一旦 API 对外发布，修改成本会跳变：

- 字段改名需要协调所有消费者，而你可能根本不知道消费者是谁；
- 认证模型变更可能要求所有调用方重新集成；
- 分页方式从 offset 改成 cursor，可能破坏所有深度翻页的客户端；
- 错误语义变化会让调用方的重试逻辑失效；
- 默认排序变化会让分页结果重复或遗漏，而调用方很难察觉；
- 新增必填字段会让旧客户端在升级前全部失败。

更麻烦的是“沉默的破坏”：接口仍然返回 200，但业务含义变了。例如把 `amount` 从“分”改成“元”，所有金额都小了 100 倍，监控不会报警，只有财务对账时才会发现。

### 规模化后

当调用方从 10 个变成 10 万个，任何“小问题”都会被放大：

- 1% 的错误率意味着每天数万次失败；
- 一个未限制的查询可能拖垮数据库；
- 一个缺少租户隔离的缓存键可能造成数据泄露；
- 一个不清晰的限流策略可能让大客户在关键时刻被误伤；
- 一次没有退避的重试风暴可能让故障从单点扩散为全局；
- 一个未签名的 Webhook 可能被伪造，造成虚假发货。

**API 设计的本质，是在成本还低的时候，为成本变高之后做决定。**

可以用一张简单的表来理解这种不对称：

| 决策 | 设计时成本 | 发布一年后修改成本 | 可逆性 |
|---|---|---|---|
| 资源命名 | 几分钟 | 跨团队迁移数月 | 低 |
| ID 格式 | 几分钟 | 几乎不可改 | 极低 |
| 分页方式 | 半天 | 所有客户端改造 | 低 |
| 错误结构 | 一天 | SDK、文档、告警全改 | 中 |
| 认证模型 | 数天 | 所有集成重新走流程 | 低 |
| 限流阈值 | 几分钟 | 配置调整即可 | 高 |
| 排序规则 | 几分钟 | 影响分页正确性 | 中 |

这张表解释了一个常见现象：团队愿意花两周讨论微服务拆分，却不愿意花两小时讨论 ID 格式。前者看起来更“架构”，后者看起来更“细节”；但后者往往更难改。

## 1.3 为什么“能跑”远远不够

一个 API 能返回 200，不代表它可用。至少还要问七个问题。

### 正确性

返回值在业务上是否真实、完整、及时？

- 订单显示“已支付”，资金真的到账了吗？
- 库存显示 3 件，实际仓库里还有吗？
- 报表总数和明细对得上吗？
- 时区转换后，“今天”的订单范围正确吗？

正确性不是“代码没抛异常”，而是“业务事实被准确表达”。

### 一致性

相同请求在相同状态下是否得到相同结果？

- 重试会不会产生重复订单？
- 两个并发请求会不会互相覆盖？
- 读请求会不会看到半完成的状态？
- 缓存会不会返回过期数据？

一致性需要被明确承诺，而不是让调用方猜测。

### 可理解性

调用方能否从响应和错误中知道下一步做什么？

一个 `400 Bad Request` 对开发者几乎没有帮助；一个 `422` 加上字段路径、实际值、期望值和修复建议，才能让调用方自助解决问题。对 AI Agent 而言，这一点更加关键，因为它不会打电话给支持团队。

### 可演进性

增加字段、修改行为、弃用旧版本时，能否不破坏现有消费者？

可演进性取决于三件事：

- 契约是否允许扩展（未知字段、未知枚举、可选参数）；
- 是否有使用量观测（知道谁在用旧字段）；
- 是否有弃用和迁移机制。

### 安全性

是否验证了身份、权限、输入、输出和资源消耗？

安全性不只是“有没有登录”，还包括：

- 对象级授权（用户 A 能否读取用户 B 的订单）；
- 输入边界（超长字符串、深层嵌套、负数、特殊字符）；
- 输出脱敏（日志、错误、导出文件）；
- 资源消耗（单次查询能扫描多少数据）；
- 供应链（SDK、依赖、镜像、密钥）。

### 可观测性

失败时能否定位到具体请求、租户、依赖和版本？

最低要求是：每个响应有 `Request-Id`，每条日志能关联到该 ID，每个关键依赖有延迟与错误指标，每个租户的用量和错误率可区分。

### 经济性

每次调用的计算、存储、网络和支持成本是否可接受？

一个 API 可以技术上完美，但每次调用亏损 0.01 元；也可以技术上粗糙，但单位经济健康。第 50～55 章会详细讨论这件事。

这些问题无法靠一个框架解决。它们需要在设计阶段被明确，在实现阶段被验证，在运行阶段被观测。

## 1.4 一个反例：CRUD 映射的陷阱

很多 API 是这样长出来的：

```text
GET    /api/orders
GET    /api/orders/{id}
POST   /api/orders
PUT    /api/orders/{id}
DELETE /api/orders/{id}
```

这组接口看似标准，实际上只是数据库表的 HTTP 映射。它没有回答：

- 下单时需要校验库存、价格、优惠券和风控，这些不变量由谁保证？
- 支付、发货、取消、退款是状态变化还是独立资源？
- `PUT /orders/{id}` 是否允许客户端修改金额？哪些字段可写？
- 重复 POST 会不会创建两个订单？
- 订单创建后，库存预占失败如何补偿？
- 调用方如何知道订单何时真正生效？
- 订单状态有几种？谁可以触发迁移？
- 部分取消、部分退款如何表达？

更好的设计会围绕任务与状态机展开：

```text
POST /orders                       # 创建订单，支持 Idempotency-Key
GET  /orders/{orderId}             # 读取订单聚合
POST /orders/{orderId}/cancel      # 取消，带原因与并发版本
POST /orders/{orderId}/payments    # 发起支付，独立资源
POST /orders/{orderId}/refunds     # 申请退款，独立资源
GET  /orders/{orderId}/events      # 订单事件流（可选）
```

这里的关键不是 URL 好不好看，而是每个操作都有明确的业务语义、失败模式和生命周期。

进一步看，订单资源本身也应该被拆成多个状态维度，而不是一个 `status` 字段包打天下：

```json
{
  "id": "ord_123",
  "orderStatus": "CONFIRMED",
  "paymentStatus": "AUTHORIZED",
  "fulfillmentStatus": "NOT_STARTED",
  "returnStatus": "NONE",
  "version": 42
}
```

每个状态有自己的状态机、触发权限和失败语义。支付失败不应该把订单变成“已取消”，发货延迟也不应该影响支付状态。把多个生命周期压进一个字段，最终会让所有消费者都猜错。

## 1.5 API 设计失败的六种典型方式

### 1. 把实现暴露成契约

数据库字段、内部枚举、微服务拆分直接泄漏到 API。结果是调用方与实现细节耦合，任何重构都变成破坏性变更。

典型信号：

- URL 里出现表名：`/t_order_item`
- 字段名是数据库列名：`is_del`、`gmt_create`
- 响应里出现内部服务名或主机名
- 枚举值直接使用数据库存储的数字：`status: 3`

### 2. 把灵活性当成友好

一个接口接受 30 个可选参数、5 种过滤语法、3 种分页模式。看起来什么都能做，实际上调用方不知道该怎么用，提供方也无法测试所有组合。

灵活性应该来自清晰的组合规则，而不是参数堆叠。好的设计通常提供少量正交能力，而不是一个万能端点。

### 3. 把一致性当成默认

假设网络可靠、调用方不重试、写入立即可见、依赖永远可用。这些假设在演示环境成立，在生产环境不成立。

典型后果：

- 客户端超时后重试，服务端执行了两次；
- 主从延迟导致“刚创建就查询不到”；
- 下游超时导致线程池耗尽；
- 缓存与数据库不一致，用户看到旧价格。

### 4. 把发布当成结束

没有版本策略、没有弃用流程、没有使用量观测、没有开发者支持。API 上线即失控。

API 的生命周期通常是：设计 → 发布 → 采用 → 扩展 → 弃用 → 下线。只设计“发布”这一步，等于只设计了故事的开头。

### 5. 把文档当成契约

文档写了，但 schema 没有；schema 有了，但运行时没校验；运行时校验了，但错误路径没定义。调用方以为文档是承诺，提供方以为文档是参考。

契约必须是可验证的：schema、测试、示例、运行时行为至少要对得上。

### 6. 把“内部”当成“可以随便改”

“这是内部 API，不需要版本化”是最危险的借口之一。内部消费者同样有发布节奏、缓存、重试和遗留代码；而且内部 API 往往没有正式的集成测试，破坏性变更更容易静默传播。

内部 API 可以少一些形式，但不能少语义和兼容性设计。

## 1.6 AI 时代为什么更明显

传统 API 的消费者是人写的代码。人会阅读文档、询问支持、处理边界情况。AI Agent 也会，但方式不同：

- 它依赖**机器可读的工具描述**，描述含糊就会选错工具；
- 它对**错误信息**非常敏感，`400 Bad Request` 无法帮助它恢复；
- 它会**自动重试和组合调用**，幂等与并发问题会被放大；
- 它可能拥有**广泛的权限**，授权边界必须比人类操作更细；
- 它的行为难以完全预测，需要**审计、回放和评估**；
- 它会在**上下文窗口**中携带工具描述和结果，返回过大就会挤掉关键信息；
- 它可能同时看到多个相似工具，命名和描述的重叠会导致误选。

这意味着 API 设计不仅要“对人友好”，还要“对机器可理解、可验证、可约束”。

举一个具体例子。两个工具分别叫 `get_order` 和 `fetch_order`，描述都写“查询订单”。人类工程师会看文档、问同事，最终选对；Agent 只能根据描述和参数猜测。如果两个工具的参数略有不同，Agent 很可能反复试错，消耗 token，甚至用错权限。

再比如，一个退款工具返回：

```json
{ "error": "400" }
```

人类会去查日志、问后端；Agent 只能换参数重试，可能把一次本可恢复的“订单未支付”变成多次无效调用。

这正是第 45～48 章的主题：当消费者从人变成 Agent，契约的清晰度、错误可恢复性和权限边界会从“最佳实践”变成“功能正确性”的一部分。

## 1.7 三条最不可逆的决策

如果一本书只能记住三件事，我会选这三条。它们共同的特点是：**设计时几乎不花成本，发布后几乎无法修改。**

### 1. 标识（Identity）

资源用什么 ID、ID 是否可枚举、是否带类型前缀、是否跨环境稳定。ID 会出现在调用方的数据库、日志、报表、URL、缓存键和外部系统中。一旦发布，改 ID 格式等于让所有历史数据失去关联。

### 2. 语义（Semantics）

每个字段和状态到底是什么意思。语法可以加字段兼容，语义变化却无法兼容：同一个 `status: "PAID"`，从“已授权”变成“已到账”，调用方的所有判断都会错，而且不会报错。

### 3. 信任边界（Trust Boundary）

谁可以调用、以什么身份调用、能看到哪些数据、失败时谁负责。认证模型、租户模型和授权粒度会渗透到每一个端点、每一张表、每一个缓存键。后期修改往往需要重做集成、重跑合规审计。

这三条决策应该在设计评审中被单独拿出来讨论，而不是混在“接口细节”里。

## 1.8 本章小结

- API 是契约、边界与产品的统一体。
- 契约不仅包含语法，还包含语义与行为。
- API 的成本在发布后非线性增长，设计阶段是最便宜的纠错时机。
- “能跑”是最低标准，正确性、一致性、可理解性、可演进性、安全性、可观测性和经济性才是完整标准。
- 把实现暴露成契约、把灵活性当友好、把一致性当默认、把发布当结束、把文档当契约、把内部当随便改，是六种典型失败。
- AI Agent 让契约的清晰度、错误可恢复性和权限边界变得更重要。
- 标识、语义和信任边界是最不可逆的三类决策。

## 设计练习

选一个你熟悉的 API，回答：

1. 它最重要的三个消费者分别是谁？他们的任务是什么？
2. 哪些字段或行为一旦改变，会破坏调用方？
3. 如果让你重新设计一个最痛的接口，你会改变资源边界、错误模型还是交互方式？为什么？
4. 这个 API 的 ID 格式、状态语义和信任边界，分别有多难改？
5. 如果明天要让一个 AI Agent 调用它，最需要补充的三条信息是什么？
