# 第 9 章 列表、分页、过滤与搜索

## 9.1 列表接口是最容易被低估的接口

几乎所有系统都有列表：订单、用户、日志、商品、事件、审计记录。列表接口看似简单，实际上同时涉及：

- 数据量与性能；
- 排序稳定性；
- 并发写入；
- 权限过滤；
- 缓存；
- 导出；
- 搜索体验；
- 调用方遍历成本；
- 数据库索引；
- 计数成本。

一个设计糟糕的列表接口，可能在上线一年后成为数据库最大的负担。

列表接口的特殊性在于：**它是唯一一个会被调用方“遍历”的接口**。单资源读取一次只影响一行，列表接口一次可能扫描百万行；调用方还可能用循环把整个数据集拉一遍。

## 9.2 分页的三种基本方式

### 1. Offset / Limit

```http
GET /orders?offset=100&limit=20
```

SQL：

```sql
SELECT * FROM orders
ORDER BY created_at DESC
LIMIT 20 OFFSET 100;
```

优点：

- 实现简单；
- 支持跳页；
- 调用方容易理解；
- 适合后台管理界面。

缺点：

- 深分页性能差：数据库需要扫描并丢弃前 `offset` 行；
- 并发写入会导致重复或遗漏；
- 大 offset 可能被滥用；
- 总数查询成本高；
- 不同数据库的 offset 性能差异大。

深分页的成本可以用一个例子说明：如果每页 20 条，跳到第 10,000 页，数据库需要先产生 200,000 行再丢弃。即使有索引，这也可能从毫秒级变成秒级。

### 2. 游标（Cursor）

```http
GET /orders?limit=20&cursor=eyJjcmVhdGVkQXQiOi...
```

游标是不透明的字符串，编码了“从哪里继续”的位置。

优点：

- 深分页性能稳定；
- 对并发写入更稳健；
- 不暴露内部排序键（如果签名/加密）；
- 适合无限滚动；
- 不需要 COUNT。

缺点：

- 不能跳页；
- 游标可能过期；
- 需要稳定排序键；
- 实现和调试更复杂；
- 调用方不能随机访问。

### 3. Keyset（键集）

Keyset 是游标的一种实现方式，基于排序键比较：

```sql
SELECT *
FROM orders
WHERE (created_at, id) < ('2026-11-26 10:00:00', 'ord_123')
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

优点：性能好、语义清晰。缺点：排序键必须唯一且稳定；多字段排序复杂；不适合任意跳页。

### 三种方式的性能对比

| 方式 | 第 1 页 | 第 1000 页 | 第 100 万页 | 跳页 | 并发稳定 |
|---|---|---|---|---|---|
| Offset | 快 | 慢 | 极慢 | 是 | 差 |
| Cursor/Keyset | 快 | 快 | 快 | 否 | 较好 |
| 快照游标 | 快 | 快 | 快 | 否 | 最好 |

“快照游标”指游标绑定一个快照/事务 ID，保证遍历期间看到一致视图。成本更高，但适合导出和对账。

## 9.3 如何选择

| 场景 | 推荐 |
|---|---|
| 后台管理、需要跳页 | Offset，但限制最大页深 |
| 移动端无限滚动 | Cursor |
| 大数据量、深分页 | Keyset |
| 导出全量数据 | 异步任务 + 文件 |
| 搜索结果 | Cursor + 搜索游标 |
| 审计/事件流 | Cursor 或流式 |
| 对账/报表 | 快照游标或时间窗口 |
| 小数据集（<1000） | Offset 足够 |

**务实建议**：

- 公开 API 默认 Cursor；
- 需要跳页时提供 Offset，但设置上限（如 10,000）；
- 超过上限引导用户缩小过滤范围或使用导出；
- 不要同时提供两套分页参数造成歧义；
- 在文档中明确遍历期间的并发语义。

### 混合分页

有些 API 同时支持：

```http
GET /orders?pageSize=20&pageToken=...
```

`pageToken` 可以是 offset 的编码，也可以是 cursor。对调用方来说都是不透明令牌，服务端可以逐步从 offset 迁移到 keyset，而不破坏契约。

## 9.4 游标设计

一个安全的游标应满足：

1. **不透明**：调用方不应解析或构造；
2. **防篡改**：签名或加密，防止越权/注入；
3. **可过期**：避免无限期持有旧位置；
4. **包含排序键**：保证稳定；
5. **包含过滤条件指纹**：防止换条件后复用游标；
6. **版本化**：游标格式变化时可识别；
7. **可绑定租户/用户**：防止跨租户复用；
8. **可绑定快照**：需要一致视图时。

示例结构（解码后）：

```json
{
  "v": 1,
  "sort": "createdAt:desc,id:desc",
  "filterHash": "sha256:...",
  "last": ["2026-11-26T10:00:00Z", "ord_123"],
  "tenantId": "t_123",
  "exp": 1798761599
}
```

服务端对 JSON 做 HMAC 签名，Base64URL 编码后返回。

### 游标过期

- 设置合理 TTL（如 24 小时）；
- 过期返回 `410 Gone` 或 `400 INVALID_CURSOR`；
- 文档说明调用方应从头开始或重新查询；
- 对导出任务使用更长的 TTL 或快照。

### 过滤条件变化

如果调用方改变过滤条件却复用旧游标，可能得到错误结果。应在游标中绑定过滤条件哈希，不匹配时返回 `400 CURSOR_FILTER_MISMATCH`。

### 游标与权限

游标必须绑定租户/用户。否则：

- 用户 A 拿到游标，用户 B 复用，可能越权读取；
- 租户 A 的游标在租户 B 的上下文中解析出错误位置；
- 权限变更后，旧游标可能绕过新权限。

服务端在每次使用游标时都应重新做权限检查，不能只依赖游标内的信息。

### 游标与排序键

排序键必须唯一且稳定：

```sql
ORDER BY created_at DESC, id DESC
```

如果只按 `created_at` 排序，相同时间的记录顺序不确定，分页可能重复或遗漏。加上唯一 ID 作为 tie-breaker。

## 9.5 列表响应结构

```json
{
  "data": [
    { "id": "ord_123", "status": "PAID" },
    { "id": "ord_124", "status": "SHIPPED" }
  ],
  "pagination": {
    "nextCursor": "eyJ2IjoxLC...",
    "hasMore": true,
    "limit": 20
  }
}
```

或使用链接：

```json
{
  "data": [],
  "links": {
    "next": "https://api.example.com/orders?cursor=...",
    "prev": null
  }
}
```

### 是否返回总数

`total` 很诱人，但成本高：

- 需要额外 `COUNT(*)`；
- 大表、复杂过滤时可能很慢；
- 与游标分页的“无限滚动”语义不匹配；
- 并发写入下总数会变化；
- 权限过滤会让计数更复杂。

建议：

- 默认不返回总数；
- 需要时提供 `includeTotal=true`，并限制使用场景；
- 或提供近似总数（如 `estimatedTotal`）；
- 后台报表使用异步统计；
- 对精确总数设置超时和降级。

### 总数的一致性

即使返回 `total`，它也可能与 `data` 不一致：

```json
{
  "data": [ ... 20 条 ... ],
  "total": 1000,
  "hasMore": true
}
```

在并发写入下，`total` 是查询时刻的近似值，不是快照。文档应说明。

### 空结果

空结果不应是错误：

```json
{
  "data": [],
  "pagination": { "nextCursor": null, "hasMore": false }
}
```

不要返回 404。404 表示“资源不存在”，不是“集合为空”。

## 9.6 过滤设计

### 简单等值过滤

```http
GET /orders?status=PAID&customerId=cus_123
```

### 多值

```http
GET /orders?status=PAID&status=SHIPPED
```

或：

```http
GET /orders?status=PAID,SHIPPED
```

选择一种并统一。

### 操作符

常见语法：

```text
?createdAt[gte]=2026-01-01
?createdAt=gte:2026-01-01
?createdAt.gte=2026-01-01
```

需要定义：

- 支持哪些操作符（eq, ne, gt, gte, lt, lte, in, contains）；
- 是否允许组合（AND/OR）；
- 是否限制过滤字段；
- 是否允许对未索引字段过滤；
- 未知操作符如何处理；
- 操作符大小写是否敏感。

### 过滤白名单

不要让调用方过滤任意数据库列。应维护白名单：

```text
status, createdAt, customerId, totalAmount, warehouseId
```

原因：

- 性能可控；
- 避免泄露内部字段；
- 避免 SQL 注入/NoSQL 注入；
- 便于索引设计；
- 避免调用方依赖未承诺的字段。

### 过滤与索引

每个允许的过滤组合都应有索引支持，否则：

- 查询变慢；
- 数据库 CPU 飙升；
- 影响其他租户；
- 触发慢查询告警。

对未索引字段的过滤，可以：

- 拒绝（400）；
- 降级为扫描（有上限）；
- 异步导出。

### 过滤的语义

- 多个过滤条件是 AND 还是 OR？
- 多值过滤是 IN 还是 OR？
- 空值是“忽略”还是“匹配空”？
- 否定过滤如何表达？
- 范围边界是闭区间还是开区间？

这些语义必须写进文档，并在测试中覆盖。

## 9.7 排序

```http
GET /orders?sort=-createdAt,totalAmount
```

规则：

- `-` 表示降序；
- 多字段排序按顺序；
- 必须有一个唯一键作为最后排序条件（通常是 ID），保证稳定；
- 限制可排序字段；
- 对空值排序行为做定义；
- 排序字段变化会影响游标，需绑定排序指纹。

如果没有唯一键，分页可能重复或遗漏：

```sql
ORDER BY created_at DESC, id DESC
```

### 空值排序

不同数据库对 NULL 的排序不同：

```sql
ORDER BY shipped_at DESC NULLS LAST
```

API 应明确：

- NULL 排在最前还是最后；
- 是否允许调用方指定；
- 游标如何编码 NULL。

### 排序与索引

排序字段应该有索引，否则数据库需要排序整个结果集。复合排序需要复合索引，且顺序要匹配。

## 9.8 搜索

搜索与过滤不同：

- 过滤是精确条件；
- 搜索是相关性排序；
- 搜索可能需要全文索引、同义词、拼写纠错、分词、向量检索。

API 设计：

```http
GET /products?q=无线耳机&category=audio&sort=relevance
```

需要考虑：

- 搜索词长度限制；
- 特殊字符与注入；
- 空搜索结果；
- 相关性排序与游标；
- 搜索日志与隐私；
- 多语言分词；
- 是否暴露搜索语法（如 `price:<100`）；
- 是否支持拼写纠错；
- 是否支持同义词；
- 是否支持过滤与搜索组合。

搜索通常应使用独立索引（如 OpenSearch、Elasticsearch、向量索引），而不是直接查主库。

### 相关性排序与分页

相关性分数通常是浮点数，且可能因索引更新而变化。游标分页需要：

- 绑定搜索快照；
- 或使用 `_score` + `id` 作为排序键；
- 或限制结果集大小。

不要承诺“搜索结果在分页之间完全稳定”，除非使用快照。

### 搜索的隐私

- 搜索日志可能包含个人信息；
- 搜索建议可能泄露其他用户的行为；
- 自动补全可能泄露未公开数据；
- 搜索分析需要脱敏和保留期。

### 分面搜索

分面（facet）返回每个过滤值的计数：

```json
{
  "facets": {
    "category": [
      { "value": "audio", "count": 42 },
      { "value": "wearable", "count": 18 }
    ],
    "priceRange": [
      { "value": "0-100", "count": 12 }
    ]
  }
}
```

分面计数通常近似，且受过滤条件影响。文档应说明。

## 9.9 并发的语义

列表在并发写入下不可能同时满足：

- 稳定排序；
- 无重复；
- 无遗漏；
- 实时性。

需要明确保证哪一种：

- **快照一致性**：基于某个时间点/事务 ID 的视图；
- **读己之写**：当前用户刚写入的数据可见；
- **最终一致**：允许延迟；
- **键集连续性**：只保证排序键上的连续性，不保证快照。

游标分页通常保证“在排序键上的连续性”，但不保证快照隔离。文档应说明。

### 重复与遗漏的示例

假设按 `created_at DESC` 分页：

1. 第一页读取最新 20 条，最后一条 `created_at = T`。
2. 此时有新记录插入，时间 `T+1`。
3. 第二页从 `T` 之后继续，新记录不会被看到（遗漏），但不会重复。
4. 如果记录被删除，可能出现重复或跳过。

如果业务要求“导出期间数据不变”，应使用快照或时间窗口导出。

## 9.10 性能与保护

- 强制 `limit` 上限（如 100）；
- 对深 offset 拒绝或降级；
- 对复杂过滤要求索引；
- 对搜索限流；
- 对导出使用异步任务；
- 监控慢查询；
- 返回 `X-Total-Count` 要谨慎；
- 缓存常见查询；
- 避免 N+1（列表项关联数据）；
- 对租户做查询配额；
- 对超大结果集使用流式。

### 反模式

```http
GET /orders?limit=1000000
```

如果没有上限，这是一次数据库拒绝服务攻击。

### 列表接口的缓存

列表缓存比单资源难：

- 缓存键包含所有过滤、排序、分页参数；
- 数据变更导致缓存失效范围大；
- 租户/权限影响缓存；
- 游标使缓存键不稳定。

常见策略：

- 缓存短 TTL；
- 缓存热点查询；
- 使用 ETag + 条件请求；
- 对权限敏感的数据不缓存或按用户缓存。

## 9.11 导出

导出全量数据不应通过分页 API 反复拉取：

- 调用方需要处理限流、重试、断点；
- 服务端承受持续压力；
- 大结果集可能超时；
- 分页语义在导出期间可能变化；
- 调用方可能拉取到重复或遗漏数据。

更好的设计：

```http
POST /exports
{
  "resource": "orders",
  "filter": { "createdAt": { "gte": "2026-01-01" } },
  "format": "csv"
}
```

返回：

```json
{
  "id": "exp_123",
  "status": "PROCESSING",
  "downloadUrl": null
}
```

完成后通过 Webhook 或轮询获取预签名下载 URL。

### 导出设计要点

- 导出任务有独立状态机；
- 结果文件有 TTL；
- 文件有校验和；
- 导出有配额；
- 导出内容做权限过滤；
- 导出格式稳定（CSV 列顺序、编码）；
- 大文件分片；
- 导出日志审计；
- 敏感数据脱敏；
- 支持取消。

### 导出与计费

导出可能消耗大量计算和存储，应计入配额或单独计费。否则大客户可以通过导出绕过在线 API 的限流。

## 9.12 本章小结

- 列表接口需要同时设计分页、过滤、排序、搜索和导出。
- Offset 简单但深分页昂贵；Cursor/Keyset 更适合大数据量。
- 游标应不透明、防篡改、可过期，并绑定过滤条件、租户和排序。
- 总数不是默认需求，按场景提供。
- 过滤与排序要有白名单和上限。
- 搜索与过滤是不同问题，通常需要独立索引。
- 并发下列表无法同时保证稳定、无重复、无遗漏和实时。
- 导出应异步化，避免拖垮在线 API。
- 批量写入、导入管线、导出一致性、迁移对账与数据可携带性的完整模式见[附录 S](../appendices/s-bulk-import-export.md)。
- 游标作为不透明标识的签名、过期、绑定查询与防篡改，见[附录 AH](../appendices/ah-primitive-semantics.md)。

- 支持导出；
- 限制查询跨度；
- 处理日志量极大、索引成本高的情况。
