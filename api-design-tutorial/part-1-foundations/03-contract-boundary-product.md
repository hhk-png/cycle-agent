# 第 3 章 契约的四个层次

## 3.1 “契约”不只是 OpenAPI 文件

很多团队说“我们有契约”，指的是仓库里有一份 OpenAPI 文件。但一份 YAML 只能描述语法的一部分。真正的 API 契约至少包含四个层次：

| 层次 | 回答的问题 | 典型载体 | 谁最关心 |
|---|---|---|---|
| 商业契约 | 提供什么、承诺什么、如何计费与赔偿？ | 服务协议、SLA、价格表、DPA | 客户、法务、销售、财务 |
| 语义契约 | 字段和操作在业务上意味着什么？ | 领域模型、状态机、术语表 | 产品、领域专家、调用方 |
| 技术契约 | 如何编码、传输、校验？ | OpenAPI、Protobuf、JSON Schema | 工程师、代码生成器 |
| 运行契约 | 失败、延迟、限流、演进如何处理？ | SLO、错误目录、弃用策略 | SRE、支持、架构师 |

只维护技术契约，会导致“接口能调通，但业务理解不一致”；只维护商业契约，会导致“承诺无法落地”。

四个层次之间必须一致。常见的冲突包括：

- 商业契约承诺 99.99% 可用，运行契约却没有多区域容灾；
- 语义契约说“退款即时生效”，技术契约却把退款设计成异步任务，运行契约又没有说明延迟；
- 技术契约允许任意大请求，商业契约却按请求数计费，导致大客户用一次请求传 1GB；
- 商业契约承诺“删除即彻底清除”，技术契约却只做软删除，备份保留 90 天。

契约评审应该专门花时间找这类矛盾，而不是只检查字段命名。

## 3.2 商业契约：承诺的边界

商业契约的核心不是法律文本，而是**可被兑现的承诺**。

### SLA 不是 SLO

- **SLI（Indicator）**：实际测量值，例如“过去 30 天成功请求比例”。
- **SLO（Objective）**：内部目标，例如“99.95% 的请求在 500ms 内成功”。
- **SLA（Agreement）**：对外承诺及违约后果，例如“月可用性低于 99.9% 时返还 10% 费用”。

三者的关系可以写成：

```text
SLO 是工程目标，通常比 SLA 更严格；
SLA 是对外底线，通常带有赔偿条款；
SLI 是测量方法，必须能被双方独立验证。
```

如果 SLO 是 99.95%，SLA 是 99.9%，那么工程团队有 0.05% 的缓冲。如果把 SLO 直接写成 SLA，团队每天都在违约边缘工作，任何一次发布都可能触发赔偿。

### 一个 SLA 必须回答的问题

1. **如何定义“可用”？**
   - HTTP 200 比例？
   - 业务成功比例（排除 4xx）？
   - 关键端点加权？
   - 是否包括异步任务的最终成功率？
2. **哪些请求计入分母？**
   - 鉴权失败算不算？
   - 客户端错误算不算？
   - 限流响应算不算？
   - 健康检查算不算？
3. **维护窗口是否排除？**
   - 计划内维护提前多久通知？
   - 紧急安全补丁是否豁免？
4. **赔偿如何计算？**
   - 按未达标时长阶梯返还？
   - 上限是多少（通常不超过月费）？
   - 是否需要客户主动申请？
5. **依赖第三方故障是否免责？**
   - 云厂商故障、支付渠道故障、DNS 故障如何划分责任？
6. **测量口径是否公开？**
   - 客户能否看到同样的 SLI？
   - 争议时以谁的数据为准？

一个没有明确这些问题的 SLA，在真正出事时通常无法执行。

### 可用性数字的直观含义

“99.9%”听起来很高，但换算成时间：

| 可用性 | 每月不可用时长 | 每年不可用时长 |
|---|---|---|
| 99% | 约 7.2 小时 | 约 3.65 天 |
| 99.9% | 约 43 分钟 | 约 8.8 小时 |
| 99.95% | 约 21 分钟 | 约 4.4 小时 |
| 99.99% | 约 4.3 分钟 | 约 52 分钟 |
| 99.999% | 约 26 秒 | 约 5.3 分钟 |

这些数字会直接约束架构：

- 99.9% 可能允许单区域 + 快速恢复；
- 99.99% 通常需要多可用区、自动化故障转移和严格的变更管理；
- 99.999% 需要多区域多活、端到端冗余和极高的运维成熟度。

### 商业契约还会约束技术选择

如果承诺“99.99% 可用、RPO=0、RTO<5 分钟”，那么：

- 单区域部署不够；
- 异步复制可能不满足 RPO；
- 没有自动化故障转移就无法满足 RTO；
- 限流和降级策略必须提前设计；
- 数据库、消息队列、对象存储都必须有多活方案；
- 发布流程必须支持金丝雀和快速回滚。

商业承诺不是营销文案，它会反向决定架构预算。

### 法律与合规条款

除了 SLA，商业契约还包括：

- **数据处理协议（DPA）**：数据用途、留存、跨境传输、子处理者；
- **数据驻留**：数据必须存储在哪个国家/区域；
- **审计权**：客户能否审计你的安全控制；
- **通知义务**：数据泄露后多久通知；
- **终止与数据导出**：合同结束后如何取回数据；
- **知识产权**：API 返回的数据归谁；
- **可接受使用政策**：禁止的调用方式。

这些条款会转化为技术需求：区域化部署、审计日志、导出接口、删除接口、速率限制、内容审核。合同、SLA 与采购条款的清单见[附录 N](../appendices/n-api-contracts-legal.md)；把这些义务映射为 API 能力与证据见[附录 T](../appendices/t-compliance-engineering.md)。

## 3.3 语义契约：让双方理解同一件事

语义契约是最容易被低估的一层。它包含：

- **术语表**：`order`、`payment`、`refund` 在业务上分别指什么；
- **状态机**：状态有哪些、允许哪些迁移、谁是触发者；
- **不变量**：哪些条件在任何时候都必须成立；
- **时间语义**：创建时间、生效时间、结算时间、时区；
- **金额语义**：币种、精度、是否含税、舍入规则；
- **删除语义**：软删除、硬删除、归档、保留期；
- **空值语义**：`null`、字段缺失、空数组分别代表什么；
- **幂等语义**：相同请求重复执行的效果；
- **顺序语义**：事件和操作是否保证顺序。

### 例子：`status` 的歧义

```json
{
  "id": "ord_123",
  "status": "PAID"
}
```

`PAID` 可能意味着：

1. 用户已完成支付授权；
2. 资金已到账；
3. 订单已进入可发货状态；
4. 支付渠道返回成功，但尚未对账。

如果 API 不说明，调用方只能猜测。更糟的是，不同团队会给出不同解释，最终在财务对账时爆发。

更清晰的建模是把“支付状态”和“订单状态”分开：

```json
{
  "id": "ord_123",
  "orderStatus": "CONFIRMED",
  "paymentStatus": "AUTHORIZED",
  "fulfillmentStatus": "NOT_STARTED"
}
```

每个状态都有自己的状态机与术语定义。这不是字段更多，而是语义更精确。

### 例子：金额的语义

```json
{ "amount": 129.9, "currency": "CNY" }
```

这行 JSON 至少隐藏了六个问题：

- `129.9` 是元还是分？
- 是否含税？
- 税费如何舍入？
- 是否含运费？
- 折扣前还是折扣后？
- 退款时按哪个金额计算？

更明确的写法：

```json
{
  "total": { "amount": 12990, "currency": "CNY" },
  "tax": { "amount": 1181, "currency": "CNY", "included": true },
  "rounding": "HALF_UP",
  "priceVersion": "2026-11-01"
}
```

### 例子：时间的语义

```json
{ "createdAt": "2026-11-26T10:00:00" }
```

没有时区的时间不是时刻，只是一个“墙上时间”。它可能被解释为：

- 服务器本地时间；
- UTC；
- 用户所在时区；
- 业务时区。

推荐：

```json
{
  "createdAt": "2026-11-26T10:00:00+08:00",
  "billingDate": "2026-11-26",
  "timeZone": "Asia/Shanghai"
}
```

并明确：

- `createdAt` 是时刻，带偏移；
- `billingDate` 是业务日期，不带时间；
- 服务端存储 UTC；
- 展示时按业务时区转换；
- 跨时区的“今天”以哪个时区为准。

### 语义契约的载体

- 领域术语表（Glossary）；
- 状态机图；
- 事件目录；
- 示例与反例；
- 契约测试中的业务断言；
- 文档中的“不保证”列表；
- 数据字典（字段的业务定义、单位、精度、取值范围）。

OpenAPI 的 `description` 可以承载一部分语义，但它不是强制的，也无法被机器验证。重要的语义最好同时出现在文档、测试和运行时行为中。

### 反例：没有语义契约的系统

一个支付系统可能同时存在：

- 前端认为 `PAID` 表示“支付成功”；
- 订单服务认为 `PAID` 表示“已授权”；
- 财务系统认为 `PAID` 表示“已结算”；
- 风控系统认为 `PAID` 表示“低风险”。

四套语义共享同一个字段，任何一次状态变更都会让至少一个系统做出错误判断。这类问题不会在集成测试中暴露，因为每个系统单独测试都通过。

## 3.4 技术契约：可机器验证的部分

技术契约负责“线上字节如何组织”。常见载体包括：

- **OpenAPI**：HTTP/JSON API 的描述；
- **JSON Schema**：JSON 数据结构与校验；
- **Protobuf**：gRPC 消息与服务定义；
- **GraphQL SDL**：类型系统与查询能力；
- **AsyncAPI**：事件与消息通道；
- **CloudEvents**：事件信封；
- **WSDL / XML Schema**：传统 SOAP 系统；
- **Avro / Parquet Schema**：数据管道。

技术契约应满足：

1. **可验证**：能用工具校验请求、响应和实现；
2. **可生成**：能生成 SDK、mock、文档；
3. **可比较**：能检测破坏性变更；
4. **可版本化**：能与代码、发布、环境关联；
5. **完整**：覆盖错误、认证、分页、枚举等非“快乐路径”。

### 示例：不完整的 OpenAPI

```yaml
paths:
  /orders:
    post:
      summary: 创建订单
      responses:
        "200":
          description: 成功
```

这份契约几乎没有信息：请求体是什么？哪些字段必填？失败返回什么？是否幂等？认证方式是什么？调用方无法据此安全集成。

更完整的片段：

```yaml
paths:
  /orders:
    post:
      operationId: createOrder
      summary: 创建订单
      parameters:
        - $ref: "#/components/parameters/IdempotencyKey"
      requestBody:
        required: true
        content:
          application/json:
            schema:
              $ref: "#/components/schemas/CreateOrderRequest"
      responses:
        "201":
          description: 订单已创建
          headers:
            Location:
              schema:
                type: string
                format: uri
          content:
            application/json:
              schema:
                $ref: "#/components/schemas/Order"
        "400":
          $ref: "#/components/responses/BadRequest"
        "409":
          $ref: "#/components/responses/Conflict"
        "422":
          $ref: "#/components/responses/UnprocessableEntity"
        "429":
          $ref: "#/components/responses/TooManyRequests"
```

注意，完整不仅仅意味着字段多，还意味着**错误路径和运行约束被表达出来**。

### 技术契约的常见缺口

即使 OpenAPI 写得很长，也常常缺少：

- 枚举的扩展策略（客户端遇到未知值怎么办）；
- 字段的可空性语义；
- 分页游标的不透明性与过期；
- 幂等键的作用域与 TTL；
- 错误码目录与可重试性；
- 认证方式与 scope；
- 速率限制的维度；
- 弃用时间表；
- 示例中的边界值；
- 多态类型的判别字段。

这些内容有些可以写进 OpenAPI 的 `description`，有些必须单独维护。关键是不要让它们只存在于某位工程师的脑子里。

### 契约的单一真相

同一个 API 不应同时维护多份互相矛盾的技术契约。常见冲突源：

- OpenAPI 文件与代码注解不一致；
- 文档站与 schema 不一致；
- 手写 SDK 与 schema 不一致；
- 网关配置与 schema 不一致；
- 测试用例与 schema 不一致。

解决方式不是“多写几份”，而是指定一个权威来源，其他产物从它生成或对它校验。

## 3.5 运行契约：失败时仍然可信

运行契约回答：

- 超时是多少？客户端应该等多久？
- 哪些错误可以重试？重试间隔如何？
- 限流阈值是多少？如何反馈？
- 幂等键保留多久？
- Webhook 会重试几次？顺序是否保证？
- 数据延迟的上界是多少？
- 版本支持多久？弃用提前多久通知？
- 维护窗口如何安排？
- 单次请求的最大体积、最大分页、最大并发是多少？

这些内容通常不会写进 OpenAPI，却直接决定集成成败。

### 一个运行契约示例

```text
- 请求超时：客户端应在 10 秒后放弃；服务端网关在 30 秒强制断开。
- 重试：仅对 429、502、503、504 以及网络错误进行指数退避重试；
  非幂等请求必须携带 Idempotency-Key。
- 幂等键：保留 24 小时，相同键与不同请求体返回 422。
- 限流：默认每租户 1000 req/min；响应包含 RateLimit-* 头。
- Webhook：至少一次投递，指数退避重试 24 小时；接收方需按 event_id 去重。
- 数据新鲜度：订单状态变更后 5 秒内可查询；报表数据 T+1。
- 版本：主版本至少支持 24 个月；弃用提前 12 个月通知。
- 最大请求体：10 MB；超过返回 413。
- 最大分页：100 条；超过自动截断并返回警告头。
```

这份契约比 schema 更能帮助调用方设计可靠的系统。

### 运行契约要写“不保证什么”

成熟的运行契约不仅写承诺，也写不承诺：

- 不保证跨分区事件顺序；
- 不保证列表结果在并发写入下无重复；
- 不保证 Webhook 只投递一次；
- 不保证跨区域读己之写；
- 不保证免费层有 SLA；
- 不保证弃用期内的行为不变（安全修复除外）。

明确“不保证”，比含糊的“尽力而为”更有用，因为它让调用方知道要在哪里做防御。

## 3.6 边界：契约背后的组织现实

API 边界通常与团队边界重合。一个边界是否合理，可以用三个问题检验：

1. **这个 API 的所有数据，是否由一个团队拥有？**
2. **这个 API 的不变量，是否能在边界内维护？**
3. **这个 API 的失败，是否由边界内的团队负责？**

如果答案是否定的，说明边界切错了，或者需要明确共享责任。

### 分布式单体信号

- 一个业务操作需要同步调用 6 个服务；
- 每个服务都依赖同一个数据库；
- 修改一个字段需要三个团队一起发布；
- 没有团队能独立解释端到端状态；
- 故障时所有服务一起雪崩；
- 发布窗口必须全公司协调；
- 一个服务的重试会放大成整个系统的重试风暴。

这些信号说明服务拆分了，但契约边界没有拆分。

### 契约的所有权

每个 API 应有明确的：

- **产品负责人**：决定能力与优先级；
- **技术负责人**：决定契约与架构；
- **运维负责人**：决定 SLO 与 on-call；
- **消费者代表**：反馈使用问题与演进需求；
- **数据负责人**：决定数据分类、留存与合规。

没有所有者的 API 会逐渐变成“公共垃圾场”：谁都能改，谁都不负责。

### 边界不是越细越好

过细的边界会带来：

- 分布式事务；
- 跨服务调试；
- 网络延迟；
- 版本协调；
- 运维复杂度；
- 团队沟通成本。

边界的正确粒度取决于不变量、团队规模和变更频率。一个只有三个人的团队，不需要把订单拆成七个微服务；一个有一百个团队的平台，可能需要更细的边界。

## 3.7 产品视角：契约也是一种承诺体验

当开发者使用你的 API 时，他体验到的不仅是技术，还包括：

- 能否在 10 分钟内完成第一次成功调用；
- 文档是否准确、示例是否可运行；
- 错误信息是否告诉他如何修复；
- 沙箱是否安全、数据是否可重置；
- 限流是否透明、升级是否容易；
- 出问题时能否找到人；
- 价格是否可预测；
- SDK 是否覆盖他的语言；
- 变更是否提前通知。

这些体验会形成“契约信任”。信任一旦建立，开发者更愿意扩展用量、推荐给他人、容忍偶发问题；信任一旦破裂，恢复成本极高。

契约信任的建立通常遵循一个顺序：

1. **可发现**：能找到文档、示例、价格；
2. **可试用**：能在一个下午完成第一次调用；
3. **可预测**：错误、限流、计费符合预期；
4. **可恢复**：出问题时能自助或找到人；
5. **可演进**：变更被提前告知，迁移有路径。

任何一步断裂，都会让开发者退回“自己实现”或“换一家”。

## 3.8 本章小结

- 契约有商业、语义、技术、运行四个层次，缺一不可。
- SLA 是对外承诺，SLO 是内部目标，二者不能混用。
- 可用性数字必须能换算成时间，才能指导架构。
- 语义契约要明确状态、时间、金额、空值、删除和顺序的含义。
- 技术契约要可验证、可生成、可比较、可版本化，并覆盖错误路径。
- 运行契约决定失败时的可信度，也要写明“不保证什么”。
- 边界应与数据所有权、不变量维护和故障责任一致。
- 产品体验是契约信任的外在表现。
- 序列化格式、类型精度与 schema 演进规则会直接影响契约能否被独立验证和长期兼容，见[附录 AE](../appendices/ae-serialization-schema-evolution.md)。
- 数据库表、RLS 与生成器配置也会构成事实契约；自动生成接口并没有取消契约设计，见[附录 AF](../appendices/af-database-as-api-baas.md)。

## 设计练习

为一个“退款 API”写出四个层次的契约各一页：

1. 商业层：SLA、计费、赔偿；
2. 语义层：退款状态机、金额规则、时间语义；
3. 技术层：OpenAPI 片段，包含至少 5 种错误；
4. 运行层：超时、重试、幂等、Webhook、版本策略。

然后检查四层之间是否存在矛盾。重点检查：

- 商业承诺的到账时间与异步任务的实际延迟是否一致；
- 语义层的“退款成功”与技术层的状态码是否一致；
- 技术层允许的请求大小与计费单位是否冲突；
- 运行层的重试窗口与幂等键 TTL 是否匹配。
