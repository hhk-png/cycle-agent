# 第 4 章 从用例到资源：领域建模

## 4.1 为什么 API 设计要从领域开始

一个 API 的 URL 和字段，最终会变成调用方心智中的世界模型。如果这个世界模型是数据库表的镜像，调用方就会被实现细节绑架；如果这个世界模型是业务概念的抽象，调用方就能在实现变化时保持稳定。

领域建模的目标不是画一张漂亮的类图，而是回答：

- 哪些概念有独立身份？
- 哪些概念只是值？
- 哪些不变量必须一起维护？
- 哪些状态变化需要被记录？
- 哪些边界内可以强一致，哪些只能最终一致？
- 哪些概念在不同团队眼里含义不同？

这些问题看起来抽象，但会直接决定 API 的形态。例如：

- 如果“订单”是一个聚合，那么修改订单明细必须通过订单根，不能直接 PATCH 单条明细；
- 如果“库存”与“订单”是两个聚合，那么下单只能预占库存，并通过事件补偿，不能要求一个数据库事务；
- 如果“客户”在销售、计费、支持三个上下文里含义不同，那么不应该有一个返回所有字段的 `/customers/{id}`。

### 领域模型不是数据库模型

数据库模型回答“数据怎么存”，领域模型回答“业务怎么想”。两者经常不一致：

| 数据库 | 领域 |
|---|---|
| `orders` 表 + `order_items` 表 | 订单聚合，包含明细 |
| `user_profile` + `user_settings` | 用户与偏好两个概念 |
| `status` 列 | 多个状态维度 + 状态机 |
| 外键 | 聚合间引用（通常用 ID） |
| 触发器 | 领域事件与副作用 |

如果把数据库模型直接暴露成 API，调用方就会依赖你的存储结构。任何分库分表、字段拆分、索引优化都会变成破坏性变更。

## 4.2 实体、值对象与聚合

### 实体（Entity）

有独立身份、生命周期可以跨越多次修改的对象。

```text
Order(order_id)
Customer(customer_id)
Payment(payment_id)
Device(device_id)
```

身份通常不等于属性。两个订单即使金额、商品、地址完全相同，也是两个不同的订单。实体的身份必须在整个生命周期内稳定，即使属性全部改变。

实体的 API 含义：

- 通常有独立的 URL；
- 有版本或 ETag；
- 可以被单独引用；
- 有生命周期（创建、修改、归档、删除）。

### 值对象（Value Object）

没有独立身份，只由属性定义的对象。

```text
Money(amount, currency)
Address(country, province, city, street, postal_code)
DateRange(start, end)
GeoPoint(lat, lng)
```

值对象适合内联在实体中，也适合作为 API 中不可变的复合字段。

值对象的关键特征是**相等性由属性决定**。两个 `Money(100, "CNY")` 是同一个值；两个 `Order(id=1)` 和 `Order(id=2)` 即使金额相同也是不同实体。

API 中的值对象应该：

- 内联为 JSON 对象；
- 不分配独立 ID；
- 整体替换，而不是部分修改；
- 有明确的校验规则。

### 聚合（Aggregate）

一组必须一起维护不变量的实体与值对象的边界。聚合根是外部访问的唯一入口。

例如：

```text
Order (聚合根)
├── OrderItem[]
├── ShippingAddress (值对象)
├── Money total (值对象)
└── OrderStatus (状态)
```

不变量可能是：

- 订单总金额等于所有明细金额之和（含折扣与运费）；
- 已支付订单不能直接删除；
- 订单状态只能按状态机迁移；
- 退款总额不能超过已支付金额；
- 明细数量不能为负。

聚合边界决定了事务边界。一个操作如果需要原子地修改两个聚合，通常意味着要么边界切错了，要么需要领域事件与最终一致。

### 聚合设计的五条规则

1. **聚合尽量小。** 大聚合会导致锁竞争、加载缓慢、并发冲突。订单聚合不需要包含客户的完整资料。
2. **通过聚合根访问。** 外部不能直接修改聚合内部实体，否则会绕过不变量。
3. **一个事务只修改一个聚合。** 跨聚合的一致性通过事件和补偿实现。
4. **聚合之间用 ID 引用。** 不要在一个聚合里嵌套另一个聚合的完整对象。
5. **不变量放在聚合内。** 如果一条规则需要跨聚合才能校验，它可能不是强不变量，或者边界切错了。

### API 中的体现

- 聚合根通常对应顶层资源；
- 聚合内部实体可以作为子资源，但不一定需要独立 URL；
- 值对象通常内联为 JSON 对象；
- 跨聚合引用使用 ID，而不是嵌套完整对象；
- 聚合的写操作通过聚合根完成。

例如，不应该允许：

```text
PATCH /orders/{orderId}/items/{itemId}
```

如果订单总价、库存、优惠都需要随明细变化而重算，直接修改明细会绕过聚合不变量。更好的方式是：

```text
POST /orders/{orderId}/items:add
POST /orders/{orderId}/items/{itemId}:remove
```

或者把“修改购物车”建模为独立聚合。

有人会反驳：这样 URL 不够 RESTful。但 REST 从来没有要求“每个数据库行都必须有 URL”。资源是领域概念，不是表行。聚合根才是资源边界。

## 4.3 资源不是数据库表

资源是 API 消费者理解的概念，不是存储实现的映射。

| 数据库表 | 可能的 API 资源 |
|---|---|
| `orders` | `/orders` |
| `order_items` | 嵌套在订单中，或 `/orders/{id}/items` |
| `users` + `profiles` + `settings` | `/users/{id}` 聚合返回 |
| `payments` | `/payments`，也可作为 `/orders/{id}/payments` |
| `audit_log` | `/audit-events`，只读 |
| 物化视图 | `/reports/sales-summary`，只读资源 |
| 关联表 `user_roles` | 可能是 `/users/{id}/roles`，也可能只是内嵌字段 |

关键判断：

- 调用方是否需要独立寻址它？
- 它是否有独立生命周期？
- 它是否有独立权限？
- 它是否需要被分页、过滤、缓存？
- 它是否是一个业务概念，而不是实现细节？
- 它是否会被独立引用到其他系统？

如果答案是否定的，不要急着给它顶层 URL。

### 资源粒度案例：地址

地址可以有三种建模：

```text
# 方案 A：内联值对象
"shippingAddress": { "city": "上海", "street": "..." }

# 方案 B：用户地址簿子资源
GET /customers/{id}/addresses
POST /customers/{id}/addresses

# 方案 C：独立地址资源
GET /addresses/{addressId}
```

选择取决于：

- 地址是否可复用（地址簿）？
- 地址是否有独立权限？
- 地址是否需要被其他资源引用？
- 地址是否会独立变化？

如果只是订单上的收货地址快照，方案 A 更合适；如果是用户管理的地址簿，方案 B；如果地址是跨系统共享的主数据，方案 C。

同一个“地址”，在不同上下文里可以是值对象、子资源或独立资源。没有唯一正确答案，只有与任务匹配的模型。

## 4.4 资源建模的五个步骤

### 第一步：收集名词

从需求、对话、工单、数据库、事件中收集业务名词：

```text
客户、组织、项目、订单、商品、库存、支付、退款、发票、优惠券、地址、审批、任务、通知
```

注意区分：

- 业务名词：订单、退款、结算；
- 技术名词：任务、消息、缓存；
- 实现名词：表、索引、分片。

API 应优先使用业务名词。

### 第二步：区分身份与值

对每个名词问：

- 它需要被单独引用吗？
- 两个属性相同的实例是否可互换？
- 它有自己的生命周期吗？
- 它需要独立权限吗？

有身份的是实体，没有的是值对象。

### 第三步：划聚合边界

对每个实体问：

- 哪些数据必须原子地一起修改？
- 哪些不变量不能容忍短暂不一致？
- 外部是否可以直接修改内部成员？
- 这个聚合会不会太大，导致并发冲突？

聚合应尽量小。大聚合会导致锁竞争、加载缓慢和并发冲突。

### 第四步：识别生命周期与状态机

为每个核心聚合画状态机：

```text
DRAFT ──submit──> PENDING_REVIEW ──approve──> APPROVED
  │                    │
  │                    └──reject──> REJECTED
  └──cancel──> CANCELLED
```

状态机要明确：

- 状态集合；
- 允许的迁移；
- 触发者与权限；
- 迁移的副作用（扣库存、发事件、写审计）；
- 非法迁移的返回（409？422？）；
- 是否可以回到之前的状态；
- 终态是什么；
- 超时如何处理。

### 第五步：区分命令、查询与事件

- **命令**：请求改变状态，例如 `CreateOrder`、`CancelOrder`；
- **查询**：读取状态，例如 `GetOrder`、`ListOrders`；
- **事件**：已经发生的事实，例如 `OrderCreated`、`OrderCancelled`。

API 设计中最常见的错误是把三者混在一起：用同一个端点既修改又返回复杂视图，或者把事件当命令发送。

三者在 API 中的典型形态：

| 类型 | 形态 | 幂等 | 失败语义 |
|---|---|---|---|
| 命令 | POST/PUT/PATCH/DELETE | 需要显式设计 | 拒绝或接受 |
| 查询 | GET/HEAD | 天然幂等 | 返回当前状态 |
| 事件 | 消息/Webhook/流 | 至少一次 | 消费者负责去重 |

## 4.5 有界上下文

同一个词在不同业务上下文中可能有不同含义。

例如“客户”：

- 销售上下文：潜在线索、商机、联系人；
- 计费上下文：付款方、账单地址、税率；
- 支持上下文：工单提交者、服务水平；
- 风控上下文：风险等级、黑名单状态。

如果强行做一个“全局客户模型”，它会变成所有团队字段的并集，最终无人能维护。

有界上下文（Bounded Context）意味着：

- 每个上下文有自己的领域模型和语言；
- 上下文之间通过明确的契约交互；
- 同一个 ID 可以跨上下文引用，但属性不一定共享；
- 上下文之间可以使用事件、API 或共享内核集成。

API 设计应尊重上下文边界。一个 `/customers/{id}` 返回所有上下文的全部字段，通常是边界失控的信号。

### 上下文映射的几种模式

| 模式 | 含义 | API 含义 |
|---|---|---|
| 共享内核 | 两个上下文共享一小部分模型 | 共享 schema 或库，耦合高 |
| 客户-供应商 | 下游依赖上游，上游优先 | 上游 API 需考虑下游需求 |
| 遵奉者 | 下游完全接受上游模型 | 下游失去建模自由 |
| 防腐层 | 下游用适配层隔离上游模型 | 推荐，尤其对接遗留系统 |
| 发布语言 | 上下文间用专门的事件/schema 通信 | 事件驱动常用 |
| 分离方式 | 各自独立，无集成 | 成本最低，但可能重复建设 |

对 API 设计者来说，最重要的是**防腐层**：不要让上游的内部模型直接成为你的 API 模型。上游改字段，你不一定需要跟着改；你可以用自己的语言重新表达。

### 上下文边界与 API 网关

网关不应该成为“上下文合并器”。把销售、计费、支持的客户字段拼成一个巨大响应，看起来方便，实际上让三个上下文的演进互相锁死。

更好的做法是：

- 每个上下文提供自己的 API；
- BFF 按场景组合；
- 组合层不拥有领域语义；
- 跨上下文一致性通过事件或明确的编排实现。

## 4.6 读写模型分离

复杂查询往往不适合直接复用写模型。

### 写模型

关注不变量、事务和状态迁移：

```text
POST /orders
POST /orders/{id}/cancel
POST /payments
```

写模型通常：

- 返回最小必要信息；
- 强调操作结果和状态；
- 不返回跨聚合的大视图；
- 保证不变量。

### 读模型

关注展示、过滤、聚合和性能：

```text
GET /orders/{id}
GET /orders?status=PAID&from=...&to=...
GET /reports/orders/summary?groupBy=day
```

读模型可以：

- 使用物化视图或搜索索引；
- 返回跨聚合的组合数据；
- 针对客户端裁剪字段；
- 接受最终一致的延迟；
- 使用独立的缓存策略。

这并不意味着一定要上 CQRS 框架。很多系统只是在查询侧使用不同的数据库视图或缓存。关键是**不要让读性能需求污染写模型的契约**。

### 读写分离的代价

- 数据延迟：写入后立即读可能读不到；
- 一致性：需要读己之写或版本令牌；
- 运维：多一套索引/视图要维护；
- 成本：存储和计算翻倍；
- 调试：问题可能出在读模型同步。

因此，读写分离应该由查询复杂度和性能需求驱动，而不是由架构潮流驱动。

## 4.7 领域事件

领域事件是“过去发生的事实”，命名通常是过去式：

```text
OrderCreated
OrderPaid
OrderCancelled
PaymentRefunded
InventoryReserved
```

好的事件应包含：

- 事件 ID；
- 事件类型与版本；
- 发生时间；
- 聚合 ID；
- 最小必要载荷；
- 关联 ID（trace、causation）；
- 租户/组织 ID；
- 元数据（生产者、schema 版本）。

事件不是数据库变更日志。`OrderRowUpdated` 这种事件暴露了实现细节，也无法表达业务语义。调用方需要的是“订单已支付”，而不是“某行某列变了”。

### 领域事件 vs 集成事件

- **领域事件**：发生在聚合内部，用于表达业务事实，可能只在进程内传播；
- **集成事件**：跨越上下文/服务边界，需要稳定的 schema、版本和投递保证。

很多团队把两者混为一谈，导致内部实现细节泄漏到外部契约。正确做法是：

```text
领域事件 OrderPaid（内部）
  → 转换/投影
集成事件 com.example.order.paid.v1（外部）
```

转换层负责：

- 只暴露必要的字段；
- 使用稳定的命名；
- 添加版本；
- 脱敏；
- 避免暴露内部 ID 结构。

### 事件设计检查清单

- 事件名是否是过去式？
- 是否表达了业务事实，而不是数据变更？
- 是否包含足够的关联 ID？
- 是否包含租户 ID？
- 载荷是否最小必要？
- 是否可以被重放？
- 消费者是否可以幂等处理？
- 顺序是否重要？如何保证？
- Schema 如何演进？
- 是否包含敏感数据？

## 4.8 状态机设计实例：退款

```text
REQUESTED ──approve──> APPROVED ──submit──> PROCESSING
    │                     │                    │
    │                     │                    ├──succeed──> SUCCEEDED
    │                     │                    └──fail─────> FAILED
    │                     └──cancel──> CANCELLED
    └──reject──> REJECTED
```

### 转换表

| 当前状态 | 动作 | 目标状态 | 触发者 | 副作用 |
|---|---|---|---|---|
| REQUESTED | approve | APPROVED | 客服/风控 | 冻结可退金额 |
| REQUESTED | reject | REJECTED | 客服/风控 | 释放冻结 |
| APPROVED | submit | PROCESSING | 系统 | 调用支付渠道 |
| APPROVED | cancel | CANCELLED | 用户 | 释放冻结 |
| PROCESSING | succeed | SUCCEEDED | 渠道回调 | 记账、通知 |
| PROCESSING | fail | FAILED | 渠道回调/超时 | 释放冻结、告警 |
| FAILED | retry | PROCESSING | 系统/客服 | 重新提交 |
| SUCCEEDED | — | 终态 | — | — |

设计问题：

- `REQUESTED` 是否立即扣减可退金额？
- `PROCESSING` 超时后自动重试还是转人工？
- `FAILED` 是否允许重新发起？是新退款还是同一退款重试？
- `SUCCEEDED` 后能否撤销？
- 部分退款如何表示？一个退款单对应多个明细？
- 渠道回调乱序到达如何处理？
- 重复回调如何幂等？

API 可能设计为：

```text
POST /refunds
GET  /refunds/{refundId}
POST /refunds/{refundId}/cancel
POST /refunds/{refundId}/retry
GET  /orders/{orderId}/refunds
```

每个动作都有明确的合法状态与错误语义。调用方不需要猜测“修改状态”应该 PATCH 哪个字段。

### 状态机的实现建议

- 状态转换集中在一个领域服务或状态机引擎中；
- 每次转换带 `expectedVersion`，防止并发覆盖；
- 每次转换写审计事件；
- 非法转换返回 `409` + 当前状态；
- 终态不可逆，除非有明确的“补偿”流程；
- 超时由独立的调度器处理，不依赖请求线程。

## 4.9 反模式

### 1. 数据库表直出

`/t_order_items`、`/t_user_profile` 这种命名会把内部实现永久固化。

### 2. 万能聚合

一个 `/accounts/{id}` 返回用户、订单、账单、设备、偏好、权限、日志。响应巨大、权限复杂、缓存困难、演进牵一发动全身。

### 3. 过度嵌套

```json
{
  "order": {
    "customer": {
      "orders": [
        {
          "items": [
            { "product": { "category": { "parent": {} } } }
          ]
        }
      ]
    }
  }
}
```

嵌套应服务于任务，而不是炫技。通常用 ID 引用 + 按需展开更合适。

### 4. 状态字段大杂烩

一个 `status` 同时表示支付、发货、审核、关闭。应拆分为多个维度，或使用明确的状态机。

### 5. 把事件当 RPC

用消息队列发送“请执行某事”的命令，却没有幂等、重试、死信和所有权。这是分布式系统事故的常见来源。

### 6. 用“资源”掩盖动作

把一个复杂的多步骤业务动作硬塞进 `PATCH /orders/{id}`，只改一个 `status` 字段，却隐藏了扣款、库存、通知、审计等副作用。调用方无法知道发生了什么，也无法重试。

### 7. 聚合里嵌套聚合

订单里嵌套完整客户对象、商品对象、支付对象，导致：

- 响应巨大；
- 数据过期；
- 权限混乱；
- 更新冲突；
- 缓存失效范围过大。

跨聚合用 ID 引用，按需展开。

## 4.10 建模工作坊：如何在三小时内完成一次领域建模

以下八个环节合计约 180 分钟。团队熟练后可以压缩到两小时，但第一次不要省略“去重/找身份/找冲突”。

1. **列名词（20 分钟）**：所有人写下业务名词，不讨论对错。
2. **去重与归类（20 分钟）**：合并同义词，标记歧义词。
3. **找身份（20 分钟）**：哪些需要独立 ID？哪些是值？
4. **划聚合（30 分钟）**：哪些不变量必须原子维护？
5. **画状态机（30 分钟）**：每个核心聚合的状态与迁移。
6. **找事件（20 分钟）**：哪些事实需要被记录和传播？
7. **标边界（20 分钟）**：哪些概念属于不同上下文？
8. **找冲突（20 分钟）**：不同团队对同一词的理解是否不同？

工作坊的产出不是最终模型，而是一张可以继续讨论的地图。

## 4.11 本章小结

- 领域建模决定 API 的世界观，比 URL 风格更根本。
- 实体有身份，值对象由属性定义，聚合维护不变量。
- 聚合应尽量小，一个事务只修改一个聚合。
- 资源是消费者概念，不是数据库表。
- 聚合边界决定事务边界，跨聚合通常需要事件与最终一致。
- 有界上下文允许同一词汇有不同含义，防腐层可以隔离上游模型。
- 读写模型可以分离，但不要为了模式而模式。
- 领域事件应表达业务事实，集成事件需要稳定的 schema 与版本。
- 状态机是复杂资源设计的核心工具。

## 设计练习

为“招聘平台”建模：

1. 识别至少 8 个实体和 5 个值对象；
2. 划出职位、申请、面试三个聚合；
3. 写出申请状态机；
4. 设计 3 个领域事件和 3 个集成事件；
5. 判断哪些查询需要独立读模型；
6. 找出至少两个跨上下文的歧义词。

进阶：为“面试改期”设计 API，要求保留历史、通知双方、处理时区，并保证并发改期不会覆盖。
