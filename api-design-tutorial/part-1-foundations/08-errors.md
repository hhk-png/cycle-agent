# 第 8 章 错误设计：让失败可理解、可恢复

## 8.1 错误是 API 的主要使用路径

在演示环境里，成功路径占 99%。在生产环境里，错误路径才是常态：

- 网络超时；
- 令牌过期；
- 权限不足；
- 参数校验失败；
- 资源冲突；
- 限流；
- 下游依赖故障；
- 幂等键冲突；
- 业务规则拒绝；
- 客户端版本过旧；
- 请求体过大；
- 证书过期。

如果错误信息只告诉调用方“失败了”，调用方就无法恢复，只能重试、报警或找支持。错误设计的目标是：

1. **可理解**：知道发生了什么；
2. **可操作**：知道下一步做什么；
3. **可分类**：知道是否应该重试；
4. **可追踪**：知道如何定位一次具体请求；
5. **可安全**：不泄露敏感信息；
6. **可编程**：机器可以稳定判断，不依赖自然语言。

错误设计不是“异常处理”的同义词。异常处理关心“程序如何不崩”，错误设计关心“调用方如何继续完成任务”。

## 8.2 错误分类

### 按责任方

- **客户端错误（4xx）**：请求有问题，调用方需要修改。
- **服务端错误（5xx）**：服务端无法完成，调用方通常可以重试或降级。
- **依赖错误**：下游服务失败，通常映射为 502/503/504。
- **策略错误**：限流、配额、权限、合规拒绝。

### 按可恢复性

| 类型 | 例子 | 调用方动作 |
|---|---|---|
| 可立即修复 | 参数缺失、格式错误 | 修改请求后重试 |
| 需状态变更 | 资源已存在、版本冲突 | 重新读取或换操作 |
| 可重试 | 429、503、网络错误 | 退避重试 |
| 不可重试 | 401、403、业务规则拒绝 | 修复凭证/权限/业务条件 |
| 需人工介入 | 对账异常、风控冻结 | 联系支持 |
| 需升级客户端 | 版本过旧、协议不支持 | 升级 SDK/客户端 |

### 按业务语义

- 校验失败；
- 认证失败；
- 授权失败；
- 资源不存在；
- 冲突；
- 限流；
- 依赖不可用；
- 内部错误；
- 合规拒绝；
- 内容审核拒绝。

### 错误分类树

```text
请求失败
├── 客户端能自行修复？
│   ├── 是 → 4xx + 明确字段/规则
│   └── 否
│       ├── 当前状态不允许？ → 409/412 + 当前状态
│       ├── 权限不足？ → 401/403 + 所需权限
│       ├── 资源不存在？ → 404（或 403 隐藏存在性）
│       └── 业务规则拒绝？ → 422/403 + 可操作原因
└── 服务端/依赖问题？
    ├── 临时故障？ → 503/504 + Retry-After
    ├── 限流？ → 429 + Retry-After
    └── 未知错误？ → 500 + requestId
```

这张树可以帮助团队在实现时快速选择状态码和错误码，而不是每个端点各自发明。

## 8.3 状态码：用对，但不要迷信

常见状态码：

| 状态码 | 语义 | 常见误用 |
|---|---|---|
| 400 | 请求语法/参数错误 | 用来表示所有业务错误 |
| 401 | 未认证 | 与 403 混用 |
| 403 | 已认证但无权限 | 用来隐藏资源存在性时需谨慎 |
| 404 | 资源不存在 | 用 403 代替所有越权 |
| 405 | 方法不允许 | 返回 404 |
| 406 | 无法满足 Accept | 返回 400 |
| 409 | 状态冲突 | 用于参数校验 |
| 410 | 资源已永久删除 | 与 404 混用 |
| 412 | 前置条件失败 | 与 409 混用 |
| 413 | 请求体过大 | 返回 400 |
| 415 | 媒体类型不支持 | 返回 400 |
| 422 | 语义校验失败 | 与 400 边界不清 |
| 428 | 需要前置条件 | 用于强制 If-Match |
| 429 | 限流 | 返回 503 |
| 500 | 未预期错误 | 暴露堆栈 |
| 502 | 上游返回无效响应 | 与 500 混用 |
| 503 | 服务暂不可用 | 不返回 Retry-After |
| 504 | 上游超时 | 与 503 混用 |

### 400 与 422

- `400 Bad Request`：请求格式错误，服务端无法解析或理解。
- `422 Unprocessable Content`：格式正确，但语义校验失败（如结束时间早于开始时间）。

很多 API 只用 400 也能工作，但明确区分有助于调用方决定是否重试。团队应统一约定，不要同一类错误在不同端点返回不同状态码。

### 401 与 403

- `401`：缺少凭证或凭证无效；通常应带 `WWW-Authenticate`。
- `403`：凭证有效，但无权执行。

对于敏感资源，返回 404 而不是 403 可以避免泄露资源存在性，但这会让调试更困难。需要根据威胁模型选择，并在文档中说明。

### 404 与 410

- `404`：资源不存在，可能是从未存在，也可能是被删除；
- `410`：资源曾经存在，现已永久删除，且不会恢复。

410 对客户端有明确语义：不要重试，不要创建。

### 409 与 412

- `409 Conflict`：请求与当前资源状态冲突（如重复创建、状态机不允许）；
- `412 Precondition Failed`：`If-Match` 等前置条件不满足。

如果使用 ETag 做并发控制，版本不匹配应返回 412；如果是业务状态冲突，返回 409。

### 429 与 503

- `429 Too Many Requests`：调用方超过了速率限制；
- `503 Service Unavailable`：服务端整体不可用或过载。

429 应带 `Retry-After`，并说明限制维度（租户、端点、用户）。503 也应带 `Retry-After`，但语义是“服务暂时不可用”，不是“你太快了”。

### 状态码不是错误码

HTTP 状态码表达**类别**，错误码表达**具体原因**。一个 409 可能是：

- 订单已支付；
- 库存不足；
- 版本冲突；
- 幂等键冲突；
- 资源正在被其他操作锁定。

调用方需要错误码来区分这些情况。

## 8.4 Problem Details（RFC 9457）

RFC 9457 定义了标准的错误表示：

```http
HTTP/1.1 422 Unprocessable Content
Content-Type: application/problem+json
```

```json
{
  "type": "https://errors.example.com/order/insufficient-inventory",
  "title": "库存不足",
  "status": 422,
  "detail": "商品 sku_123 在仓库 wh_shanghai 的可用库存为 2，请求数量为 5。",
  "instance": "/orders",
  "requestId": "req_01J9Z6Q8K3W7V2M4N5P6R7S8T9",
  "code": "INSUFFICIENT_INVENTORY",
  "errors": [
    {
      "field": "items[0].quantity",
      "code": "QUANTITY_EXCEEDS_AVAILABLE",
      "message": "请求数量超过可用库存",
      "meta": { "requested": 5, "available": 2 }
    }
  ]
}
```

字段说明：

- `type`：稳定的错误类型 URI，可用于文档和程序判断；
- `title`：简短的人类可读摘要；
- `status`：HTTP 状态码；
- `detail`：针对本次请求的具体说明；
- `instance`：发生错误的资源路径或请求 ID；
- 扩展字段：`code`、`requestId`、`errors` 等。

### 稳定性

调用方应基于 `code` 或 `type` 做程序判断，而不是解析 `detail` 文本。`detail` 可能本地化、调整措辞或包含动态信息。

### `type` URI 的设计

`type` 应该是：

- 稳定的；
- 可解析的；
- 指向文档的；
- 不随请求变化的。

例如：

```text
https://errors.example.com/order/insufficient-inventory
https://errors.example.com/auth/token-expired
https://errors.example.com/validation
```

不要用会变的 URL（如带请求 ID 的链接）作为 `type`。

### 扩展字段的兼容性

Problem Details 允许扩展字段，但客户端应忽略未知字段。新增扩展字段通常兼容；删除或改语义是破坏性的。

## 8.5 错误码设计

错误码是长期契约。设计原则：

1. **稳定**：发布后不轻易改名；
2. **唯一**：同一语义只有一个码；
3. **可分类**：前缀表达领域，如 `ORDER_`、`PAYMENT_`；
4. **可读**：`PAYMENT_CARD_DECLINED` 比 `E1024` 更易调试；
5. **不含敏感信息**：不要用错误码暴露内部实现；
6. **有文档**：每个码说明触发条件、可恢复性和建议动作；
7. **可枚举**：错误码集合应可被 SDK 生成常量；
8. **不重复状态码**：错误码不是 `HTTP_409`。

### 示例目录

```text
AUTH_TOKEN_EXPIRED              401  重新获取令牌
AUTH_INSUFFICIENT_SCOPE         403  申请权限
ORDER_NOT_FOUND                 404  检查 ID
ORDER_ALREADY_PAID              409  查询订单状态
ORDER_INVALID_STATE             409  按状态机操作
PAYMENT_CARD_DECLINED           402  换支付方式
PAYMENT_DUPLICATE_REQUEST       409  使用相同幂等键或查询结果
RATE_LIMITED                    429  退避重试
DEPENDENCY_UNAVAILABLE          503  稍后重试
INTERNAL_ERROR                  500  联系支持并提供 requestId
```

### 错误码与 HTTP 状态码的关系

- HTTP 状态码表达**类别**；
- 错误码表达**具体原因**；
- 两者不是一一对应。多个错误码可以共享一个状态码。

### 错误码的命名空间

大型平台应有命名空间，避免不同团队撞码：

```text
ORDER_NOT_FOUND
PAYMENT_CARD_DECLINED
INVENTORY_INSUFFICIENT
IDENTITY_TOKEN_EXPIRED
```

或者：

```text
order.not_found
payment.card_declined
inventory.insufficient
identity.token_expired
```

关键不是格式，而是**全局唯一且可检索**。

### 错误码的生命周期

- 新增错误码通常兼容；
- 删除错误码是破坏性的；
- 修改错误码含义是破坏性的；
- 错误码应进入文档、SDK、监控和告警；
- 弃用错误码需要迁移期。

## 8.6 校验错误

校验错误应尽可能指出：

- 哪个字段；
- 什么规则；
- 实际值；
- 期望值；
- 如何修复。

```json
{
  "type": "https://errors.example.com/validation",
  "title": "请求参数校验失败",
  "status": 400,
  "code": "VALIDATION_FAILED",
  "errors": [
    {
      "field": "email",
      "code": "INVALID_FORMAT",
      "message": "邮箱格式不正确",
      "meta": { "value": "not-an-email" }
    },
    {
      "field": "items[2].quantity",
      "code": "OUT_OF_RANGE",
      "message": "数量必须在 1 到 99 之间",
      "meta": { "min": 1, "max": 99, "actual": 0 }
    }
  ]
}
```

注意：

- 不要一次只返回第一个错误，除非有性能或安全理由；
- 不要回显敏感值（密码、完整卡号）；
- 字段路径要稳定，最好与请求 JSON 路径一致；
- 错误顺序应可预测；
- 对数组元素使用 `items[2].quantity` 这种路径；
- 对嵌套对象使用 `customer.address.city`；
- 对未知字段，指出字段名而不是“请求无效”。

### 校验错误的性能

一次性校验所有字段需要遍历整个请求体，可能很贵。折中方案：

- 对小于阈值（如 1MB）的请求做全量校验；
- 对大请求做快速失败；
- 在文档中说明。

但不要因为性能而只返回“第一个错误”，除非确实有攻击风险。

### 校验错误与安全

校验错误可能泄露：

- 内部字段名；
- 数据库约束；
- 业务规则；
- 用户是否存在。

对外 API 应只返回必要的字段路径和规则，不返回堆栈、SQL 或内部枚举。

## 8.7 业务错误与状态冲突

业务规则拒绝不应一律映射为 400。常见情况：

- 订单已支付，不能取消 → `409 Conflict`；
- 版本不匹配 → `409` 或 `412 Precondition Failed`；
- 余额不足 → `422` 或 `409`，取决于语义；
- 风控拒绝 → `403` 或 `422`，并给出可操作原因；
- 重复请求 → `409` 或返回原结果（幂等）。

关键是让调用方区分：

- 请求本身错了（改请求）；
- 当前状态不允许（重新读取/换操作）；
- 系统暂时不可用（重试）；
- 业务规则拒绝（换方案/联系支持）。

### 业务错误的可操作性

一个业务错误应告诉调用方：

```json
{
  "code": "ORDER_INVALID_STATE",
  "message": "订单当前状态为 SHIPPED，不能取消",
  "meta": {
    "currentStatus": "SHIPPED",
    "allowedActions": ["request_return"],
    "nextStep": "请使用退货流程"
  }
}
```

`allowedActions` 比一句“不能取消”有用得多，尤其对 AI Agent。

### 业务错误与 HTTP 语义的冲突

有些业务错误难以映射到 HTTP 状态码：

- 风控拒绝：403？422？200 + 业务错误？
- 部分成功：200？207？422？
- 异步任务已接受但最终失败：202 之后如何表达？

原则是：**HTTP 状态码表达本次请求的处理结果，业务错误码表达业务状态**。不要为了“语义纯粹”把所有业务错误都塞进 200。

## 8.8 重试语义

错误响应应明确是否可重试：

```http
HTTP/1.1 503 Service Unavailable
Retry-After: 30
```

```json
{
  "code": "DEPENDENCY_UNAVAILABLE",
  "retryable": true,
  "retryAfterSeconds": 30
}
```

但要注意：

- 只有幂等请求才能安全重试；
- 非幂等请求重试必须依赖幂等键；
- 不要在客户端无条件重试 500；
- 429 的 `Retry-After` 应准确；
- 重试应带抖动，避免惊群；
- 重试次数应有上限；
- 重试应区分“可重试错误”和“不可重试错误”。

### 哪些错误可重试

| 状态码 | 可重试 | 条件 |
|---|---|---|
| 408 | 是 | 幂等请求 |
| 425 | 是 | 幂等请求，稍后重试 |
| 429 | 是 | 遵循 Retry-After |
| 500 | 谨慎 | 仅幂等请求，且有限次数 |
| 502 | 是 | 幂等请求 |
| 503 | 是 | 遵循 Retry-After |
| 504 | 是 | 幂等请求 |
| 400/401/403/404/409/422 | 否 | 修复请求/权限/状态 |

### 重试与幂等

非幂等请求（如 POST 创建订单）重试可能导致重复。解决方案：

- 使用 `Idempotency-Key`；
- 服务端在幂等窗口内返回原结果；
- 客户端持久化幂等键，重试时复用；
- 明确幂等键的 TTL 和作用域。

### 重试风暴

当依赖故障时，所有客户端同时重试会让故障扩大。防护：

- 指数退避 + 抖动；
- 服务端返回 `Retry-After`；
- 熔断；
- 客户端重试预算；
- 服务端限流；
- 队列缓冲。

## 8.9 错误信息的安全边界

错误信息可能泄露：

- 数据库结构、SQL、堆栈；
- 内部服务名、IP、端口；
- 用户是否存在；
- 资源是否存在；
- 密钥、令牌、个人信息；
- 业务规则细节（可被滥用）；
- 依赖版本（可被用于定向攻击）。

原则：

- 对外返回最小必要信息；
- 内部日志保留完整上下文；
- 用 `requestId` 关联内外；
- 对认证/授权错误统一措辞；
- 不在生产环境返回堆栈；
- 对敏感字段做脱敏；
- 错误码不要暴露内部实现。

### 用户枚举

登录、注册、找回密码接口容易泄露用户是否存在：

```json
{ "error": "USER_NOT_FOUND" }   // 泄露
{ "error": "INVALID_CREDENTIALS" } // 更安全
```

但也要平衡可用性：如果用户确实需要知道“邮箱未注册”，可以在验证邮箱后提供。

### 资源枚举

`GET /orders/123` 返回 403 还是 404，会泄露资源是否存在。对高敏感系统，统一返回 404；对需要调试的系统，返回 403 并记录审计。

## 8.10 本地化

如果 API 面向多语言调用方：

- 错误码保持英文稳定；
- `title`/`detail` 可根据 `Accept-Language` 本地化；
- 不要要求调用方解析本地化文本；
- 文档提供错误码的多语言说明；
- 本地化文本不应改变错误码；
- 对 RTL 语言、日期格式、数字格式要测试。

```http
Accept-Language: zh-CN, en;q=0.8
```

响应：

```json
{
  "code": "ORDER_INVALID_STATE",
  "title": "订单状态不允许此操作",
  "detail": "订单当前状态为 SHIPPED，不能取消。"
}
```

调用方应基于 `code` 判断，`title`/`detail` 只用于展示。更完整的 locale 协商、复数规则、RTL 与可访问性设计见[附录 Q](../appendices/q-i18n-accessibility.md)。

## 8.11 错误可观测性

错误响应应与监控关联：

- 每个错误码有对应的指标；
- 按端点、租户、客户端版本、错误码维度统计；
- 错误率突增告警；
- 错误日志包含 `requestId`、`traceId`、`tenantId`；
- 错误响应时间分布；
- 错误恢复率（调用方是否成功重试）。

没有这些，错误设计只是“写给人看的文案”，无法运营。

## 8.12 错误设计的反模式

- 所有错误都返回 200，用 `success: false` 表示失败；
- 所有错误都返回 500；
- 错误响应结构随端点变化；
- 只返回 `message: "error"`；
- 把堆栈或 SQL 返回给客户端；
- 用错误码表示 HTTP 状态；
- 不区分可重试与不可重试；
- 429 不返回 `Retry-After`；
- 校验错误不回显字段路径；
- 错误码随发布随意改名；
- 错误信息本地化后调用方解析文本；
- 用 403 隐藏所有资源存在性，导致调试困难；
- 对幂等冲突返回 500。

## 8.13 本章小结

- 错误是主要使用路径，必须被设计。
- 用状态码表达类别，用稳定错误码表达原因。
- Problem Details 提供了可扩展的标准结构。
- 校验错误要指出字段、规则和修复方式。
- 业务错误要与协议错误区分，并提供可操作信息。
- 明确可重试性、重试间隔和幂等前提。
- 错误信息既要可操作，又不能泄露敏感信息。
- 错误要可观测、可统计、可告警。

## 设计练习

为“文件上传 API”设计错误目录，覆盖：

- 文件过大；
- 类型不支持；
- 分片缺失；
- 校验和不匹配；
- 存储配额不足；
- 病毒扫描失败；
- 预签名 URL 过期；
- 并发上传冲突。

为每个错误定义 HTTP 状态码、错误码、可重试性、用户可见信息和日志字段。然后回答：

1. 哪些错误应该返回 4xx，哪些应该返回 5xx？
2. 病毒扫描失败是否可重试？调用方应如何知道？
3. 分片缺失时，如何告诉调用方缺哪一片？
4. 如果同一个文件被并发上传，返回 409 还是合并？
