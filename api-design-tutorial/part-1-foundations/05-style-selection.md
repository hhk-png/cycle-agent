# 第 5 章 API 风格选型：REST、RPC、GraphQL、事件与流

## 5.1 风格不是信仰

API 风格之争经常变成身份政治：REST 纯粹主义者、GraphQL 布道者、gRPC 性能派、事件驱动原教旨主义者。这些争论大多没有意义，因为它们把“手段”当成了“目标”。

真正的问题是：

1. 消费者要完成什么任务？
2. 任务的交互形态是什么？
3. 消费者与提供方的耦合程度可以多低？
4. 失败、延迟、一致性要求是什么？
5. 团队有能力运维哪种协议？
6. 五年后，这种选择会不会成为迁移负担？

风格只是这些约束下的一个选择。更准确地说，风格是**一组默认约定的集合**：

- REST 默认“资源 + 统一接口 + 缓存”；
- RPC 默认“动作 + 强类型 + 代码生成”；
- GraphQL 默认“客户端声明字段 + 单一端点”；
- 事件默认“事实发布 + 异步消费”；
- 流默认“长连接 + 持续传输”。

选风格，本质上是选一组默认约定，然后接受它们的代价。

## 5.2 五种基本交互形态

### 请求—响应

调用方发起请求，提供方同步返回结果。

```http
GET /orders/ord_123
```

适合：

- 读取已知资源；
- 简单的创建、更新、删除；
- 低延迟、结果可立即确定的操作；
- 需要 HTTP 缓存、CDN、代理的场景。

不适合：

- 长时间处理；
- 需要持续推送；
- 大量跨服务组合查询；
- 结果依赖多个异步依赖且延迟不可控。

请求—响应的隐藏假设是“结果在超时窗口内可得”。如果这个假设不成立，就应该转向异步任务。

### 远程过程调用（RPC）

调用方像调用本地函数一样调用远程服务。

```proto
rpc CreateOrder(CreateOrderRequest) returns (Order);
```

适合：

- 内部服务之间；
- 强类型、高性能；
- 动作导向的接口；
- 需要流式传输；
- 多语言代码生成。

不适合：

- 需要广泛缓存；
- 消费者是浏览器或简单脚本；
- 需要低门槛的公开 API；
- 需要人类直接调试的场景。

RPC 的核心优势不是“快”，而是**契约明确、代码生成、调用语义接近本地函数**。它的核心风险是“把网络调用当本地调用”，忽略超时、重试、部分失败和版本演进。

### 图查询（GraphQL）

客户端声明需要哪些字段，服务端返回匹配的图结构。

```graphql
query {
  order(id: "ord_123") {
    id
    total { amount currency }
    customer { name }
    items { sku quantity }
  }
}
```

适合：

- 多客户端、字段需求差异大；
- 聚合多个数据源；
- 前端需要减少往返；
- 有较强治理能力。

不适合：

- 简单 CRUD；
- 缓存要求极高；
- 团队没有能力处理复杂度、N+1 和安全问题；
- 公开 API 需要最低接入门槛；
- 客户端不可信且无法限制查询复杂度。

GraphQL 把“查询规划”的一部分责任转移给了客户端。这既是它的力量，也是它的风险。

### 事件

生产者发布事实，消费者异步接收。

```json
{
  "type": "com.example.order.paid",
  "source": "/orders/ord_123",
  "data": { "orderId": "ord_123", "amount": 12900 }
}
```

适合：

- 多消费者；
- 解耦与异步；
- 状态同步、审计、分析；
- 长流程编排；
- 削峰填谷。

不适合：

- 需要立即返回结果；
- 消费者需要强一致读；
- 团队没有幂等、去重、死信处理能力；
- 需要严格全局顺序。

事件的核心价值是解耦，核心代价是**时间耦合变成状态耦合**：消费者必须处理延迟、重复、乱序和 schema 演进。

### 流

持续传输数据，可能是单向或双向。

```text
SSE: 服务器持续推送事件
WebSocket: 双向消息
WebTransport: 基于 QUIC 的多路复用流
WebRTC: 点对点音视频与数据通道
```

适合：

- 实时通知；
- 协同编辑；
- 金融行情；
- 日志/指标尾随；
- 大文件分块；
- 语音/视频。

不适合：

- 一次性查询；
- 客户端网络不稳定且无法重连；
- 简单轮询已足够；
- 团队没有连接管理和背压能力。

## 5.3 选型矩阵

| 维度 | REST/HTTP | gRPC | GraphQL | 事件 | 流 |
|---|---|---|---|---|---|
| 公开 API 门槛 | 低 | 中 | 中 | 高 | 中 |
| 浏览器支持 | 好 | 需 gRPC-Web/Connect | 好 | 需网关 | SSE 好，WebSocket 好 |
| 强类型 | 中（OpenAPI 可补） | 强 | 强 | 中（Schema 可补） | 视协议 |
| 性能 | 中 | 高 | 中 | 高（异步） | 高 |
| 缓存 | 强 | 弱 | 复杂 | 不适用 | 弱 |
| 多客户端字段裁剪 | 弱 | 弱 | 强 | 不适用 | 不适用 |
| 实时性 | 弱 | 强（流） | 订阅 | 强（异步） | 强 |
| 演进难度 | 中 | 中 | 高 | 高 | 高 |
| 运维复杂度 | 低 | 中 | 高 | 高 | 中高 |
| 调试便利性 | 高 | 中 | 中 | 低 | 中 |
| 典型场景 | 公开/合作伙伴 API | 内部微服务 | BFF/聚合层 | 集成/分析 | 实时协作/推送 |

这张表只能作为起点。真实决策还要考虑组织能力、现有基础设施和消费者约束。

### 一个更实用的决策顺序

1. **先问结果是否立即可得。** 不是 → 异步任务或事件。
2. **再问是否需要持续推送。** 是 → 流或 SSE/WebSocket。
3. **再问消费者是否是浏览器/合作伙伴。** 是 → HTTP/JSON 优先。
4. **再问字段需求是否高度动态。** 是 → GraphQL 或 BFF 聚合。
5. **再问是否内部高性能调用。** 是 → gRPC。
6. **最后问团队能否运维。** 不能 → 选更简单的方案。

这个顺序的好处是：先排除不适用的形态，再在剩下的选项里比较。

## 5.4 REST 的适用边界

REST 的核心不是“用 GET/POST”，而是：

- 资源有标识；
- 通过统一接口操作资源；
- 状态转移由表示驱动；
- 缓存与分层是架构约束；
- 无状态交互（每次请求携带足够上下文）。

REST 适合：

- 资源边界清晰；
- 读多写少；
- 需要 HTTP 缓存、CDN、代理；
- 消费者多样且希望低门槛；
- 需要长期稳定、可发现、可链接的接口；
- 需要人类可直接调试。

REST 不适合：

- 高度动作化、难以资源化的流程；
- 需要极致性能的内部调用；
- 客户端字段需求高度动态；
- 需要服务端推送；
- 需要事务性批量操作。

但“REST 不适合”不等于“HTTP 不适合”。你完全可以在 HTTP 上设计 RPC 风格接口，使用 JSON 和 POST，而不必假装每个动作都是资源。

### REST 的常见误解

- **误解一：REST 就是 JSON over HTTP。** JSON 只是表示之一，REST 的核心是架构约束。
- **误解二：URL 里不能有动词。** 动作可以建模为子资源或冒号动作，关键是有明确语义。
- **误解三：必须用 HATEOAS。** 超媒体是 REST 的一个约束，但多数所谓 REST API 并未实现；这不一定是错，只是要诚实。
- **误解四：状态码必须完美。** 状态码是工具，不是道德标准；关键是调用方能理解。

## 5.5 RPC 的适用边界

RPC 适合“动作”而非“资源”：

```text
ReserveInventory
CapturePayment
SendNotification
RecalculateRiskScore
```

gRPC 的优势：

- Protobuf 强类型、紧凑；
- HTTP/2 多路复用；
- 四种流模式（一元、服务端流、客户端流、双向流）；
- 代码生成成熟；
- 适合内部服务网格；
- 明确的 deadline 与取消传播；
- 丰富的拦截器生态。

代价：

- 浏览器支持需要额外层；
- 人类可读性差；
- 调试成本高；
- 契约演进需要严格遵守 Protobuf 规则；
- 网关、缓存、日志生态不如 HTTP/JSON 成熟；
- 负载均衡需要理解 HTTP/2 长连接；
- 错误模型与 HTTP 状态码不同。

RPC 不意味着可以忽略资源建模。即使方法叫 `CreateOrder`，请求和响应仍然需要清晰的领域对象。

### RPC 的常见错误

- 把内部数据结构直接作为请求/响应，导致每次重构都是破坏性变更；
- 没有 deadline，导致调用方无限等待；
- 重试不带退避，导致重试风暴；
- 用 `google.protobuf.Any` 逃避类型设计；
- 把所有字段设为 optional，失去契约约束；
- 忽略取消传播，导致下游继续做无用功。

## 5.6 GraphQL 的适用边界

GraphQL 解决的核心问题是：**客户端需要灵活地声明数据形状，而服务端希望避免为每个客户端维护一个端点。**

它适合：

- 多端（Web、iOS、Android、TV）字段需求差异大；
- 后端有多个数据源需要聚合；
- BFF 层需要快速迭代；
- 客户端希望减少网络往返；
- 需要强类型 schema 和自省。

它带来的新问题：

- 查询复杂度攻击；
- N+1 查询；
- 字段级授权；
- 缓存困难；
- Schema 演进与弃用；
- 可观测性更复杂；
- 客户端可能写出低效查询；
- 单个端点难以按操作限流；
- 错误是 200 + errors 数组，监控需要额外处理。

GraphQL 不是“更好的 REST”，而是“把部分查询规划责任转移给客户端”的架构选择。没有治理能力时，它是负债。

### GraphQL 的适用信号

- 你有超过 3 个客户端，字段需求明显不同；
- 你的 BFF 需要组合 5 个以上数据源；
- 你愿意投入查询复杂度限制、持久化查询、字段级授权和缓存；
- 你的团队能维护 schema 治理和弃用流程。

如果这些条件不成立，REST + 少量定制端点通常更便宜。

## 5.7 事件的适用边界

事件适合“已经发生的事实”：

```text
OrderPaid
UserRegistered
DeviceOffline
```

事件的核心价值是解耦：

- 生产者不需要知道有多少消费者；
- 消费者可以独立演进；
- 新消费者可以回放历史；
- 异步流程可以削峰；
- 故障可以隔离。

事件的核心代价是：

- 最终一致；
- 重复投递；
- 顺序问题；
- Schema 演进；
- 可观测性与调试困难；
- 消费者治理；
- 事件风暴；
- 数据所有权模糊。

事件不是“更高级的 API”。它要求团队具备分布式系统的成熟度。

### 事件 vs 消息 vs 命令

| 类型 | 语义 | 例子 | 消费者 |
|---|---|---|---|
| 事件 | 已经发生的事实 | `OrderPaid` | 零到多个 |
| 命令 | 请求执行动作 | `ChargeCard` | 一个（通常） |
| 消息 | 通用传输单元 | 任意 | 视设计 |

把命令当事件广播，会导致多个消费者重复执行；把事件当命令点对点发送，会失去解耦价值。

## 5.8 混合架构是常态

真实系统很少只用一种风格。

```text
公开 API：REST/HTTP + OpenAPI + Webhook
内部服务：gRPC
BFF：GraphQL 或 REST 聚合
分析管道：Kafka + CloudEvents
实时通知：SSE/WebSocket
大文件：预签名 URL + 对象存储
```

关键不是统一风格，而是明确每种风格的边界：

- 对外契约稳定、低门槛；
- 对内契约高效、强类型；
- 异步契约可追踪、可重放；
- 流式契约可恢复、可背压。

### 混合架构的治理

混合架构最大的风险是“语义碎片化”：同一个业务概念在 REST、gRPC、事件里有不同的字段名和状态值。治理方法：

- 统一的领域术语表；
- 统一的 ID 规范；
- 统一的错误码目录；
- 事件 schema 与 API schema 的映射关系；
- 跨协议的契约测试；
- 一个总体的 API 目录。

## 5.9 一个决策案例：在线协作白板

需求：

- 用户打开白板时加载全部元素；
- 多人实时编辑；
- 支持评论、历史版本、导出；
- 移动端网络不稳定；
- 需要与外部系统集成。

可能的组合：

| 能力 | 风格 |
|---|---|
| 加载白板 | REST/GraphQL 查询 |
| 实时编辑 | WebSocket/WebTransport |
| 评论 | REST + 事件 |
| 历史版本 | REST 分页查询 |
| 导出 | 异步任务 + 预签名下载 |
| 外部集成 | Webhook + 事件 |

没有一种风格能覆盖全部。设计的关键是让不同通道共享同一套领域语义（元素 ID、版本、权限、事件类型）。

### 实时编辑的额外问题

- 冲突解决：OT 还是 CRDT？
- 离线编辑：本地如何合并？
- 权限：每个元素是否有独立权限？
- 版本：如何表示“看到的是旧版本”？
- 重连：断线后如何补齐缺失操作？
- 背压：客户端跟不上时怎么办？

这些问题不是协议能自动解决的，必须在领域层设计。

## 5.10 选型检查清单

1. 消费者能否使用这种协议？网络、代理、防火墙是否允许？
2. 交互是同步还是异步？结果是否立即可得？
3. 是否需要浏览器原生支持？
4. 是否需要强类型和代码生成？
5. 是否需要 HTTP 缓存/CDN？
6. 是否有多个消费者需要不同的字段组合？
7. 是否需要服务端推送或双向通信？
8. 团队是否具备运维该协议的技能？
9. 失败、重试、幂等、顺序如何解决？
10. 五年后，这种选择会不会成为迁移负担？
11. 是否有行业标准强制要求？
12. 是否能与现有网关、监控、审计集成？

## 5.11 遗留协议与行业协议

现实世界不只有 REST、gRPC、GraphQL 和事件。你还会遇到：

- **SOAP/WSDL**：银行、保险、电信、政务；
- **XML-RPC / JSON-RPC**：轻量 RPC，MCP 也基于 JSON-RPC；
- **OData**：企业数据查询；
- **tRPC**：全栈 TypeScript；
- **Cap'n Proto / FlatBuffers**：零拷贝高性能；
- **MQTT / CoAP / LwM2M / AMQP**：IoT 与消息；
- **FHIR / OpenRTB / NDC / TM Forum**：行业标准；
- **OFX / ISO 20022**：金融报文；
- **HL7 v2 / DICOM**：医疗。

选型时不要只看“新不新”，而要看行业强制标准、消费者生态、团队能力和迁移成本。更多协议与领域速览见[附录 K](../appendices/k-more-domains-protocols.md)。

### 遗留协议的现代化策略

- **Strangler Fig（绞杀者模式）**：新接口并行，逐步迁移；完整方法见[附录 X](../appendices/x-legacy-modernization.md)；
- **适配层**：用防腐层隔离遗留协议；
- **协议网关**：SOAP ↔ REST、XML ↔ JSON；
- **双写/双读**：迁移期保证一致性；
- **契约映射**：明确新旧字段对应关系。

不要试图“一次性重写”。遗留协议往往承载着多年积累的业务语义，重写风险远高于表面复杂度。

## 5.12 本章小结

- 风格选择应由任务形态、消费者约束和组织能力决定，而不是潮流。
- REST 适合资源化、可缓存、低门槛的场景。
- RPC 适合内部、强类型、高性能的动作调用。
- GraphQL 适合多客户端字段裁剪与聚合，但治理成本高。
- 事件适合解耦与异步，但要求幂等、去重和 Schema 治理。
- 流适合实时交互，但需要重连、背压和状态恢复。
- 混合架构是常态，关键是边界清晰、语义一致。
- 遗留协议要现代化，不要浪漫化重写。
- 风格选定后，框架与实现架构的选型见[附录 R](../appendices/r-implementation-architecture.md)。

## 设计练习

为“在线教育平台”选择 API 风格：

- 课程目录查询；
- 视频上传与转码；
- 直播课堂；
- 作业提交；
- 学习进度同步；
- 第三方 LMS 集成。

为每个能力选择风格，并说明理由与代价。然后回答：如果要把这些能力统一到一个开发者门户里，哪些语义必须跨协议保持一致？
