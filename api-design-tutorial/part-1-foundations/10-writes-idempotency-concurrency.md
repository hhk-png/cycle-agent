# 第 10 章 写操作、幂等、并发与一致性

## 10.1 写操作是最危险的部分

读错了可以再读一次，写错了可能扣款两次、超卖库存、覆盖别人的修改，或者产生无法回滚的副作用。

写 API 设计必须回答：

- 这个操作是否安全（safe）？
- 是否幂等（idempotent）？
- 并发修改如何裁决？
- 失败后调用方能否重试？
- 跨服务的一致性如何保证？
- 部分成功如何处理？
- 超时后调用方应该查询什么？
- 重复请求如何识别？

读接口的错误通常是“看到旧数据”，写接口的错误可能是“多扣一笔钱”。两者的设计标准不同。

## 10.2 HTTP 方法的语义

| 方法 | 安全 | 幂等 | 典型用途 |
|---|---|---|---|
| GET | 是 | 是 | 读取 |
| HEAD | 是 | 是 | 读取元数据 |
| OPTIONS | 是 | 是 | 能力发现 |
| PUT | 否 | 是 | 全量替换/创建 |
| DELETE | 否 | 是 | 删除 |
| PATCH | 否 | 否（通常） | 部分修改 |
| POST | 否 | 否（通常） | 创建/动作 |

注意：

- “幂等”指多次执行的效果与一次相同，不要求响应完全相同。
- `DELETE` 第二次可能返回 404，但资源状态仍与第一次后相同。
- `POST` 可以通过幂等键变成幂等。
- `PATCH` 是否幂等取决于操作：`{"status":"PAID"}` 是幂等的，`{"$inc":{"count":1}}` 不是。
- `PUT` 是幂等的，但“全量替换”可能覆盖其他客户端的并发修改，仍需要并发控制。

### 安全与幂等的区别

- **安全**：不改变服务器状态（GET、HEAD、OPTIONS）。
- **幂等**：执行一次和执行多次的最终状态相同，但可能改变状态（PUT、DELETE）。

一个安全的接口一定幂等；一个幂等的接口不一定安全。

### 常见误解

- “POST 一定不幂等”：可以通过幂等键变成幂等。
- “PUT 一定安全”：PUT 会修改资源，不安全。
- “DELETE 第二次返回 404 就不幂等”：幂等看的是资源状态，不是响应码。
- “幂等就是去重”：幂等是语义，去重是实现手段之一。

## 10.3 幂等键

### 基本流程

```http
POST /payments
Idempotency-Key: 7d3f9c2a-4b1e-4f6a-9c8d-2e5b7a1f0c34
Content-Type: application/json
```

```json
{
  "orderId": "ord_123",
  "amount": 12900,
  "currency": "CNY"
}
```

服务端逻辑：

1. 读取 `Idempotency-Key`；
2. 计算请求指纹（方法 + 路径 + 关键头 + 规范化请求体）；
3. 在幂等存储中查找：
   - 若不存在：以原子操作写入 `PROCESSING`，执行业务，保存响应；
   - 若存在且状态为 `COMPLETED`：先校验调用主体与指纹，一致才返回保存的响应；
   - 若存在且状态为 `PROCESSING`：返回 `409` 或 `202`，让调用方稍后重试；
   - 若存在但指纹不同：返回 `422 IDEMPOTENCY_KEY_REUSED`；
4. 响应保存 TTL（如 24 小时）；
5. 并发请求通过唯一约束或分布式锁串行化。

### 关键细节

- **作用域**：幂等键通常按“租户 + 调用主体 + 端点 + key”隔离，不能全局复用。只按租户隔离会让同一租户内的不同调用方撞键；只按端点隔离会让同一调用方在不同端点之间错误复用响应。
- **主体绑定**：重放已保存响应前，必须确认当前调用主体与首次执行的主体一致。否则，同一租户内的另一个主体可能通过猜测或复用 key 拿到别人的响应。
- **指纹**：必须包含影响结果的字段；忽略无关的 header。
- **原子性**：检查与占位必须原子，否则两个并发请求会同时执行。
- **响应保存**：保存状态码、关键响应头、响应体。
- **失败处理**：业务失败是否缓存？通常缓存确定性失败，临时失败可允许重试。
- **过期**：TTL 应覆盖调用方最大重试窗口。
- **清理**：避免无限增长。
- **加密**：幂等键可能被日志记录，避免包含敏感信息。
- **大小限制**：限制键长度，防止存储攻击。

### 数据库实现

```sql
CREATE TABLE idempotency_keys (
  tenant_id     TEXT NOT NULL,
  principal_id  TEXT NOT NULL,
  endpoint      TEXT NOT NULL,
  key           TEXT NOT NULL,
  request_hash  TEXT NOT NULL,
  status        TEXT NOT NULL,
  response_code INT,
  response_body JSONB,
  created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
  expires_at    TIMESTAMPTZ NOT NULL,
  PRIMARY KEY (tenant_id, principal_id, endpoint, key)
);
```

占位：

```sql
INSERT INTO idempotency_keys
  (tenant_id, principal_id, endpoint, key, request_hash, status, expires_at)
VALUES
  ($1, $2, $3, $4, $5, 'PROCESSING', now() + interval '24 hours')
ON CONFLICT (tenant_id, principal_id, endpoint, key) DO NOTHING
RETURNING *;
```

如果插入成功，当前请求获得执行权；如果失败，读取已有记录并比较指纹。

### 状态机

```text
PROCESSING ──success──> COMPLETED
     │
     ├──deterministic failure──> FAILED (可缓存)
     └──transient failure──> 删除占位，允许重试
```

关键问题：

- `PROCESSING` 状态下进程崩溃怎么办？
- 需要超时回收机制，允许后续请求接管；
- 但接管可能导致重复执行，需要业务幂等或锁。

### 请求指纹

指纹应包含：

- HTTP 方法；
- 路径；
- 影响结果的查询参数；
- 关键请求头（如 `Content-Type`）；
- 规范化后的请求体。

规范化包括：

- 键排序；
- 去除无意义空白；
- 统一数字格式；
- 忽略不影响结果的字段。

指纹不匹配时，返回：

```http
HTTP/1.1 422 Unprocessable Content
Content-Type: application/problem+json

{
  "code": "IDEMPOTENCY_KEY_REUSED",
  "title": "幂等键已用于不同请求",
  "detail": "该 Idempotency-Key 已绑定到另一组请求参数。",
  "status": 422
}
```

### 常见错误

- 只对“创建”做幂等，不对“支付/退款”做；
- 幂等键由客户端随机生成但不持久化，重试时换了新键；
- 先查再写，存在竞态；
- 缓存了错误响应却允许重试；
- TTL 太短，调用方长时间重试时重复执行；
- 不校验请求体，同一个键被用于不同请求；
- 幂等键在网关被剥离；
- 多实例部署时使用本地缓存做幂等。

### 幂等键的边界

幂等键不能解决所有重复问题：

- 如果调用方在收到响应前崩溃，重试时换了新键，仍会重复；
- 如果幂等记录已过期，重试会重新执行；
- 如果请求经过多个服务，幂等键需要逐层传递；
- 如果业务本身不是确定性的（如随机分配），重复执行可能不同。

因此，幂等键是“降低重复概率”，不是“保证 exactly-once”。真正的 exactly-once 需要业务层的唯一约束、状态机和审计。

## 10.4 并发控制

### 乐观并发

使用版本号或 ETag：

```http
GET /orders/ord_123
ETag: "v42"
```

```http
PATCH /orders/ord_123
If-Match: "v42"
Content-Type: application/merge-patch+json

{ "shippingAddressId": "addr_456" }
```

如果版本不匹配：

```http
HTTP/1.1 412 Precondition Failed
```

优点：无锁、吞吐高。缺点：冲突时调用方需要重读重试。

### 悲观锁

在数据库或分布式锁中锁定资源。适合冲突频繁、重试成本高的场景。缺点是吞吐低、死锁风险、锁超时。

### 版本字段

```json
{
  "id": "ord_123",
  "version": 42,
  "status": "PAID"
}
```

更新时要求 `version` 匹配，成功后递增。

### 三种并发控制对比

| 方式 | 冲突处理 | 吞吐 | 适用 |
|---|---|---|---|
| 乐观锁（版本/ETag） | 冲突时失败，调用方重试 | 高 | 读多写少、冲突低 |
| 悲观锁 | 阻塞等待 | 低 | 冲突高、操作短 |
| 条件更新（CAS） | 原子比较并交换 | 高 | 单行状态机 |
| 串行化隔离 | 数据库保证 | 中 | 强一致事务 |
| 分布式锁 | 跨服务互斥 | 低 | 跨资源协调 |

### 并发控制与业务语义

并发控制不只是“防止覆盖”，还要回答：

- 冲突时哪一方赢？
- 失败方如何知道当前状态？
- 是否需要合并（如购物车）？
- 是否需要人工介入？
- 冲突是否可重试？

### 幂等 vs 并发

- 幂等解决“同一请求重复执行”；
- 并发控制解决“不同请求同时修改同一资源”；
- 两者不能互相替代。

一个支付请求可能既需要幂等（防重复扣款），又需要并发控制（防同时修改订单状态）。

## 10.5 事务边界

单库事务可以保证 ACID；跨服务事务通常需要：

- **Saga**：一系列本地事务 + 补偿；
- **Outbox**：本地事务写业务表与事件表，异步发布；
- **TCC**：Try-Confirm-Cancel；
- **两阶段提交**：强一致但成本和可用性代价高；
- **事件溯源**：以事件为真相，重放得到状态。

### Outbox 模式

```sql
BEGIN;
INSERT INTO orders (...) VALUES (...);
INSERT INTO outbox (event_id, type, payload, created_at)
VALUES ('evt_123', 'OrderCreated', '{...}', now());
COMMIT;
```

后台进程读取 outbox，发布到消息队列，成功后标记已发送。

优点：

- 业务写入与事件发布原子；
- 避免“写库成功、发消息失败”；
- 可重试、可审计。

缺点：

- 至少一次投递，消费者必须幂等；
- 需要清理与监控；
- 事件顺序需要额外设计；
- outbox 表可能成为热点。

### Outbox 的实现细节

- 使用 `SELECT ... FOR UPDATE SKIP LOCKED` 提高并发；
- 记录 `published_at`、`attempts`、`last_error`；
- 设置重试上限和死信；
- 监控积压；
- 清理已发布记录；
- 保证事件 ID 唯一。

### Saga

```text
创建订单 → 预占库存 → 扣减余额 → 确认订单
             ↓失败        ↓失败
          释放库存     退款/释放库存
```

Saga 需要：

- 每个步骤幂等；
- 补偿操作幂等；
- 超时与人工介入；
- 状态可查询；
- 避免补偿失败导致不一致；
- 补偿的顺序与重试策略。

### Saga 的两种实现

- **编排（Orchestration）**：一个协调器调用各服务，明确流程；
- **协同（Choreography）**：各服务监听事件，自行决定下一步。

编排更易理解和调试；协同更解耦，但流程分散，难以追踪。

### TCC

- **Try**：预留资源（冻结余额、预占库存）；
- **Confirm**：确认使用；
- **Cancel**：释放预留。

TCC 适合需要强预留的场景，但实现复杂，需要处理空回滚、悬挂、幂等。

### 两阶段提交

- 准备阶段：所有参与者锁定资源；
- 提交阶段：协调者决定提交或回滚。

优点：强一致；缺点：协调者单点、阻塞、性能差。多数互联网系统避免使用。

## 10.6 部分成功

批量操作可能部分成功：

```http
POST /orders/bulk
```

```json
{
  "results": [
    { "index": 0, "status": 201, "id": "ord_1" },
    { "index": 1, "status": 422, "error": { "code": "INVALID_ITEM" } },
    { "index": 2, "status": 201, "id": "ord_3" }
  ]
}
```

需要明确：

- 是全部成功或全部失败（原子），还是允许部分成功？
- 部分成功返回 200 还是 207？
- 调用方如何重试失败项而不重复成功项？
- 是否支持幂等键 per item？
- 结果顺序是否与请求顺序一致？
- 部分成功后，整体事务是否回滚？

**建议**：默认原子；需要部分成功时显式命名（如 `bulk`）并在响应中逐项返回结果。

### 批量操作的响应格式

```json
{
  "summary": {
    "total": 3,
    "succeeded": 2,
    "failed": 1
  },
  "results": [
    { "index": 0, "status": 201, "id": "ord_1" },
    {
      "index": 1,
      "status": 422,
      "error": {
        "code": "INVALID_ITEM",
        "message": "商品 sku_999 不存在"
      }
    },
    { "index": 2, "status": 201, "id": "ord_3" }
  ]
}
```

每个失败项都应包含可操作的错误码和字段路径。

### 批量操作的性能

- 批量大小上限；
- 分批处理；
- 异步任务（大批量）；
- 幂等；
- 限流；
- 部分成功时的事务边界。

## 10.7 一致性模型

API 应明确承诺：

- **强一致**：读到的一定是最新写入；
- **读己之写**：同一用户写入后立即能读到；
- **单调读**：不会读到比之前更旧的数据；
- **最终一致**：允许延迟，但给出上界；
- **因果一致**：有因果关系的操作按顺序可见。

例如：

```text
订单创建后立即可查（强一致）；
库存扣减后 5 秒内同步到查询服务（最终一致）；
搜索结果 30 秒内可见（最终一致）。
```

没有一致性承诺，调用方只能假设最坏情况，或者错误地假设最好情况。

### 一致性承诺的写法

不要写“最终一致”，要写：

```text
写入成功后，同一租户的读请求在 5 秒内可见；
跨区域读请求在 30 秒内可见；
列表搜索索引在 60 秒内更新。
```

有数字、有范围、有维度，调用方才能设计重试和降级。

### 读己之写的实现

- 写入返回版本号/令牌；
- 读请求携带令牌，路由到主库或等待复制；
- 会话粘性；
- 本地缓存写入结果；
- 读主库（成本高）。

### 一致性与缓存

缓存会破坏一致性承诺：

- 缓存 TTL 决定了最大延迟；
- 缓存失效可能导致旧数据；
- 多级缓存可能叠加延迟；
- 按用户缓存与按租户缓存语义不同。

一致性承诺必须把缓存算进去。

## 10.8 写操作的错误处理

- 幂等键冲突 → 409/422；
- 版本冲突 → 409/412；
- 资源已存在 → 409；
- 资源不存在 → 404；
- 状态非法 → 409；
- 业务规则拒绝 → 422；
- 临时失败 → 503 + Retry-After；
- 超时 → 调用方查询操作状态，而不是盲目重试。

### 超时的正确处理

写请求超时后，调用方不知道操作是否成功。正确做法：

1. 如果请求有幂等键，用相同键重试；
2. 如果没有幂等键，先查询资源状态；
3. 如果无法查询，使用对账/审计；
4. 不要直接重试非幂等写请求。

服务端应提供：

- 按幂等键查询结果；
- 按业务 ID 查询状态；
- 操作日志；
- 对账接口。

## 10.9 写操作的审计

每个写操作应记录：

- 谁（用户/服务/租户）；
- 什么（操作、资源、参数摘要）；
- 何时；
- 从哪（IP、客户端、trace）；
- 结果（成功/失败/错误码）；
- 前后的关键状态；
- 幂等键；
- 请求 ID。

审计日志本身应：

- 不可篡改；
- 可查询；
- 有保留期；
- 脱敏；
- 可导出。

## 10.10 本章小结

- 写操作需要明确安全、幂等、并发和一致性语义。
- 幂等键是解决重复提交的核心工具，但实现必须原子、可校验、可过期。
- 幂等键不等于 exactly-once。
- 乐观并发适合大多数场景，悲观锁适合高冲突场景。
- 跨服务一致性通常依赖 Saga、Outbox 和幂等消费者。
- 批量操作要明确原子性与部分成功语义。
- 一致性承诺必须写进契约，并包含数字和维度。
- 超时后的正确动作是查询状态，不是盲目重试。
- 跨区域写权威、fencing、会话保证与 RPO/RTO，见[附录 Z](../appendices/z-distributed-consistency-multi-region.md)。
- 用状态机、性质测试与 TLA+ 验证并发不变量，见[附录 AA](../appendices/aa-formal-contracts-model-checking.md)。
- 批量写入的逐条结果、导入管线与迁移对账，见[附录 S](../appendices/s-bulk-import-export.md)。
- 幂等键、请求指纹与资源 ID 的规范化、稳定性和生命周期，见[附录 AH](../appendices/ah-primitive-semantics.md)。

## 设计练习

为“转账 API”设计：

1. 幂等键流程；
2. 乐观并发控制；
3. 跨账户事务边界；
4. 失败补偿；
5. 查询操作状态的接口；
6. 对账与人工介入。

画出正常路径与至少三种失败路径。然后回答：

1. 如果转账请求超时，调用方如何知道钱是否转了？
2. 如果两个请求同时从同一账户扣款，如何防止透支？
3. 如果补偿失败，如何保证最终一致？
4. 如何证明“没有重复扣款”？
