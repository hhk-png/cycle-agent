# 第 11 章 版本化与兼容性

## 11.1 版本化的目标不是“编号”

很多团队把版本化理解为在 URL 里加 `/v1`。但版本号本身不解决任何问题。真正要解决的是：

- 如何增加字段而不破坏调用方？
- 如何修改行为而让调用方有时间迁移？
- 如何弃用旧接口而不造成事故？
- 如何知道谁在使用哪个版本？
- 如何证明新版本没有破坏旧消费者？

版本化是**兼容性管理**的一部分，而不是一个路径前缀。

版本号只是兼容性边界的一个标签。真正的工程工作是：

- 定义什么算破坏性变更；
- 让变更可被机器检测；
- 让消费者能安全迁移；
- 让旧版本能有序退出。

## 11.2 兼容性的四个维度

### 1. 语法兼容

请求和响应的结构是否仍能被解析：

- 新增可选字段通常兼容；
- 删除字段、改类型、改必填性通常破坏；
- 新增枚举值可能破坏未处理未知值的客户端；
- 字段重命名是破坏性的，除非同时保留旧字段；
- 修改数组顺序可能破坏依赖顺序的客户端。

### 2. 语义兼容

字段含义是否变化：

- `status` 从“支付状态”变成“订单状态”；
- `amount` 从“含税”变成“不含税”；
- 时间从本地时间变成 UTC；
- 错误码含义变化；
- 分页游标的排序键变化；
- 默认值变化。

语法不变但语义变化，是最隐蔽的破坏性变更。

### 3. 行为兼容

- 默认分页大小变化；
- 排序规则变化；
- 限流阈值变化；
- 重试行为变化；
- 幂等窗口变化；
- 延迟/一致性变化；
- 错误重试策略变化；
- 超时时间变化。

### 4. 运行兼容

- 认证方式变化；
- TLS 版本要求；
- 域名/证书变化；
- 弃用旧头；
- 新增必填头；
- IP 白名单变化；
- 网关行为变化；
- CORS 策略变化。

运行兼容问题往往在集成测试中不出现，却会在生产环境集中爆发。

## 11.3 什么算破坏性变更

### 通常兼容

- 新增可选请求字段；
- 新增端点；
- 新增可选请求头；
- 放宽校验（需谨慎）；
- 性能提升；
- 文档修正。

### 条件兼容

以下变更只有在消费者满足特定契约时才兼容：

- **新增响应字段**：客户端必须忽略未知字段；严格 schema 校验的客户端可能失败；
- **新增可选枚举值**：客户端必须能处理未知枚举值；使用封闭枚举的客户端可能崩溃；
- **新增错误码**：客户端必须把未知错误码当作可处理错误，而不是直接崩溃；
- **修改字段顺序**：JSON 对象无序，但依赖顺序的解析器可能失败；
- **增大分页大小**：客户端必须能处理更大的响应。

条件兼容不是“提供方说了算”。它要求在 API 契约、文档和 SDK 中明确写出消费者应遵守的宽容读取规则，并通过契约测试验证。

### 通常破坏

- 删除或重命名字段；
- 修改字段类型；
- 把可选字段改为必填；
- 修改枚举值的大小写或含义；
- 修改默认值；
- 删除端点或方法；
- 修改状态码；
- 修改错误结构；
- 修改分页/排序语义；
- 修改认证/授权模型；
- 收紧校验导致原本合法的请求失败；
- 改变幂等/重试语义；
- 改变一致性或延迟承诺；
- 修改 URL 结构；
- 修改字段的可空性；
- 修改数值精度或单位。

### 灰色地带

- **修改速率限制**：对正常调用方可能无感，对接近阈值的调用方是破坏；
- **修改默认排序**：语法兼容，但分页结果可能重复或遗漏；
- **修改错误信息的文案**：如果客户端解析文本，可能破坏；
- **修改缓存行为**：可能影响数据新鲜度与一致性；
- **修改重试语义**：可能让调用方的重试策略失效。

**原则**：兼容性由消费者决定，不由提供方定义。需要了解消费者的解析行为。

### 兼容性矩阵

| 变更 | 语法 | 语义 | 行为 | 运行 | 建议 |
|---|---|---|---|---|---|
| 新增可选字段 | 兼容 | 兼容 | 兼容 | 兼容 | 可直接发布 |
| 新增必填字段 | 破坏 | 破坏 | 破坏 | 兼容 | 不要做，除非新端点 |
| 删除字段 | 破坏 | 破坏 | 兼容 | 兼容 | 扩展—收缩 |
| 改字段类型 | 破坏 | 可能破坏 | 可能破坏 | 兼容 | 新字段并行 |
| 新增枚举值 | 灰色 | 灰色 | 兼容 | 兼容 | 文档要求宽容解析 |
| 改默认值 | 兼容 | 破坏 | 破坏 | 兼容 | 显式参数 |
| 改排序 | 兼容 | 破坏 | 破坏 | 兼容 | 新排序参数 |
| 改认证 | 兼容 | 兼容 | 破坏 | 破坏 | 长迁移期 |
| 改错误结构 | 破坏 | 破坏 | 破坏 | 兼容 | 新版本 |

## 11.4 版本策略

### URL 主版本

```text
/v1/orders
/v2/orders
```

优点：

- 清晰、易路由、易文档、易缓存；
- 适合公开 API；
- 调用方容易理解；
- 网关可以按路径分流。

缺点：

- 容易把版本当成“重写”的借口；
- 多版本并行维护成本高；
- URL 膨胀；
- 跨版本共享资源困难。

### Header 版本

```http
Accept: application/vnd.example.v2+json
```

或：

```http
X-API-Version: 2026-11-01
```

优点：URL 稳定。缺点：调试、缓存、浏览器访问更复杂；CDN 可能忽略 header；日志分析更麻烦。

### 日期版本

```http
Stripe-Version: 2026-11-26
```

适合需要频繁行为变更的 API，但要求服务端长期维护多个行为分支，工程复杂度高。

### 字段级版本

通过新字段并存实现渐进迁移：

```json
{
  "total": { "amount": 12900, "currency": "CNY" },
  "legacyTotal": "129.00"
}
```

新字段 `total` 与旧字段 `legacyTotal` 并存；旧字段标记弃用，待调用方迁移后删除。金额本身仍统一用最小单位整数，旧字段只是兼容表示。字段级版本适合小范围变更，不适合大规模重构。

### 特性开关

```http
X-Feature-Flags: new-pricing
```

适合灰度，不适合作为长期版本机制。

### 建议

- 公开 API：URL 主版本 + 兼容性扩展；
- 内部 API：优先扩展—收缩，尽量不引入新主版本；
- 高变更频率的 API：考虑日期版本或 feature flag；
- 不要把每个小功能都变成新版本；
- 版本号应少而稳定，变更应多而兼容。

## 11.5 扩展—收缩（Expand–Contract）

这是最可靠的兼容演进模式。

### 第一步：扩展

同时支持旧字段和新字段：

```json
{
  "name": "Alice",
  "fullName": "Alice Zhang"
}
```

或同时支持旧端点和新端点：

```text
GET /v1/orders/{id}
GET /v2/orders/{id}
```

扩展阶段要：

- 新字段可写可读；
- 旧字段继续工作；
- 文档标明旧字段弃用；
- 监控旧字段使用量；
- 提供迁移指南。

### 第二步：迁移

- 通知消费者；
- 提供迁移指南；
- 双写/双读；
- 监控旧字段使用量；
- 提供兼容层；
- 收集消费者反馈；
- 处理边界情况。

### 第三步：收缩

确认无人使用后，删除旧字段/端点。

```text
旧字段使用量连续 90 天为 0 → 标记弃用 → 再观察 90 天 → 删除
```

这个 90+90 的节奏只适用于内部字段、有明确迁移支持或已与消费者逐一确认的场景。公开 API 的默认通知期应更长（见 11.6 的 12 个月建议）；安全漏洞等紧急情况走例外流程，并保留审计。

扩展—收缩的关键是**可观测性**：你必须知道谁在使用旧契约。

### 扩展—收缩的变体

- **双写**：同时写新旧存储，读旧；
- **双读**：读新失败时回退旧；
- **影子流量**：把生产流量复制到新版本，比较结果；
- **并行运行**：新旧版本同时提供服务，逐步切流。

## 11.6 弃用

弃用不是“发个邮件然后删除”。一个完整的弃用流程包括：

1. **标记**：文档、响应头、开发者门户；
2. **通知**：邮件、控制台、客户经理；
3. **迁移工具**：兼容层、迁移脚本、对照表；
4. **监控**：旧版本调用量、调用方列表；
5. **渐进关闭**：灰度、按租户关闭、brownout（短暂停用）；
6. **最终删除**：保留审计与回滚能力。

### 响应头

```http
Deprecation: @1798761599
Sunset: Thu, 31 Dec 2026 23:59:59 GMT
Link: <https://docs.example.com/migrate/v2>; rel="deprecation"
```

RFC 9745 的 `Deprecation` 是结构化字段日期（`@` + Unix 秒），不是布尔值 `true`。`Sunset`（RFC 8594）使用 HTTP-date。具体头字段以团队采用的标准为准，关键是让调用方在运行时也能感知弃用。

相关标准：

- `Deprecation` 头（RFC 9745）；
- `Sunset` 头（RFC 8594）；
- `Link` 头（RFC 8288）。

### 弃用政策

文档中应明确：

- 提前多久通知（如 12 个月）；
- 旧版本支持多久；
- 是否有安全例外；
- 迁移支持范围；
- 紧急弃用的处理流程；
- 弃用期间的 SLA 是否变化。

### Brownout

Brownout 是“短暂停用旧版本”，用于：

- 提醒尚未迁移的调用方；
- 验证迁移监控；
- 降低突然删除的风险。

Brownout 应：

- 提前通知；
- 选择低峰期；
- 有明确时间窗口；
- 可立即恢复；
- 不影响关键业务。

## 11.7 消费者驱动契约

消费者驱动契约（Consumer-Driven Contracts, CDC）让消费者定义期望，提供方验证：

```text
消费者测试：我期望 GET /orders/123 返回 id、status、total
提供方验证：我的实现是否满足所有消费者的期望
```

工具如 Pact 可以：

- 在消费者端生成契约；
- 在提供方 CI 中验证；
- 检测破坏性变更；
- 减少集成测试环境依赖。

CDC 不能替代 API 设计评审，但能显著降低“提供方以为兼容、消费者实际崩溃”的风险。

### CDC 的局限

- 只能覆盖已编写契约的消费者；
- 无法覆盖未知消费者；
- 维护成本高；
- 对内部实现变化的敏感度需要调优；
- 不适合验证性能、可靠性。

### 契约测试与 schema 测试

- **Schema 测试**：验证响应符合 OpenAPI/Protobuf；
- **契约测试**：验证消费者期望的字段和行为；
- **快照测试**：验证响应结构没有意外变化；
- **模糊测试**：验证边界输入。

四者互补，不能互相替代。

## 11.8 版本化的组织问题

### 谁决定破坏性变更？

应有明确的审批流程：

- API 所有者；
- 消费者代表；
- 安全/合规；
- 支持团队；
- 商业负责人（如果涉及合同）。

### 如何知道谁在用？

- API Key / OAuth client 维度统计；
- User-Agent；
- 请求头中的客户端版本；
- 网关日志；
- 开发者门户的订阅关系；
- SDK 版本遥测（需隐私合规）；
- 计费系统；
- 支持工单。

### 多版本维护成本

每个主版本都需要：

- 代码分支或兼容层；
- 测试；
- 文档；
- 安全补丁；
- on-call；
- 数据迁移；
- 监控；
- 客户支持。

因此，**能通过兼容扩展解决的，不要开新主版本**。

### 版本与团队边界

如果每个团队都能随意发新版本，最终会出现：

- 版本爆炸；
- 消费者不知道用哪个；
- 文档碎片化；
- 支持成本上升。

需要平台团队或 API 治理委员会统一版本策略。

## 11.9 客户端版本碎片化

移动端和桌面客户端往往无法强制升级：

- 用户不更新；
- 应用商店审核；
- 企业 MDM 限制；
- 老旧设备不支持新版本。

应对策略：

- 服务端保持向后兼容；
- 客户端做宽容解析（未知字段/枚举）；
- 功能开关；
- 最低客户端版本策略；
- 强制升级提示；
- 老版本降级服务；
- 长期支持分支。

### 宽容读取原则

客户端应：

- 忽略未知字段；
- 把未知枚举当作 `UNKNOWN`；
- 不依赖字段顺序；
- 不依赖可选字段一定存在；
- 对缺失字段有默认值；
- 对新增错误码有兜底。

这条原则应写进 SDK 和文档，否则服务端再小心也会被客户端搞崩。

## 11.10 版本化反模式

- 用 `/v1.2.3` 表示每次发布；
- 同一 API 同时支持 URL、Header、Query 三种版本；
- 版本号与功能发布绑定；
- 没有弃用政策；
- 删除字段前不检查使用量；
- 用“内部 API 不需要版本”作为不做兼容性设计的借口；
- 消费者永远不升级，提供方无限维护旧版本；
- 新版本只是“重写”，没有明确迁移路径；
- 版本切换没有监控和回滚；
- 把 beta 版本当稳定版本承诺。

## 11.11 本章小结

- 版本化是兼容性管理，不是编号。
- 兼容性包括语法、语义、行为和运行四个维度。
- 破坏性变更的判定权在消费者。
- 扩展—收缩是最可靠的演进模式。
- 弃用需要标记、通知、工具、监控和渐进关闭。
- 消费者驱动契约能提前发现兼容问题。
- 组织必须知道谁在使用哪个版本。
- 客户端版本碎片化要求服务端长期兼容和宽容读取。
- 从遗留协议、旧字段到新契约的迁移与退役，见[附录 X](../appendices/x-legacy-modernization.md)。

## 设计练习

为一个“用户资料 API”设计从 v1 到 v2 的迁移：

- v1 使用 `name` 单字段；
- v2 拆分为 `givenName`、`familyName`；
- 需要支持国际化姓名；
- 旧客户端至少继续工作 18 个月。

写出扩展阶段、迁移阶段、收缩阶段的接口与监控方案。然后回答：

1. 如何处理只有 `name` 的旧客户端写入？
2. 如何判断旧字段是否可以删除？
3. 如果某个大客户拒绝迁移，怎么办？
4. 如何在响应头中表达弃用，而不破坏旧客户端？
