# 第 2 章 全景地图与设计方法

## 2.1 API 的七层地图

在动手写接口之前，先建立一张地图。任何一个 API 都可以放在七个层次上审视：

```text
┌─────────────────────────────────────────────┐
│ 7. 商业层：谁付费、如何计量、生态如何扩展      │
├─────────────────────────────────────────────┤
│ 6. 产品层：开发者如何发现、接入、使用、支持    │
├─────────────────────────────────────────────┤
│ 5. 工程层：测试、CI、可观测性、发布、SLO       │
├─────────────────────────────────────────────┤
│ 4. 运行层：认证、授权、限流、缓存、容错        │
├─────────────────────────────────────────────┤
│ 3. 协议层：HTTP、gRPC、GraphQL、事件、流       │
├─────────────────────────────────────────────┤
│ 2. 契约层：资源、操作、Schema、错误、版本      │
├─────────────────────────────────────────────┤
│ 1. 领域层：边界、概念、不变量、状态机          │
└─────────────────────────────────────────────┘
```

自上而下是价值，自下而上是约束。一个常见的失败是直接从第 3 层开始：先选框架、先写 Controller、先生成 Swagger，然后再倒推领域。这样得到的 API 通常语法正确，但边界混乱。

更可靠的做法是从第 1 层和第 7 层同时开始：

- 第 1 层回答“系统真正维护哪些不变量”；
- 第 7 层回答“谁愿意为什么价值买单”；
- 中间五层是连接两者的实现路径。

### 每一层的关键问题

| 层 | 核心问题 | 一旦做错的后果 |
|---|---|---|
| 领域 | 世界如何切分？谁拥有哪个不变量？ | 资源模型扭曲，所有上层都被拖累 |
| 契约 | 双方如何确认理解一致？ | 集成靠猜，变更靠协调 |
| 协议 | 用什么承载调用与事件？ | 性能、缓存、浏览器兼容受限 |
| 运行 | 失败时系统如何表现？ | 故障扩散，重试风暴，数据泄露 |
| 工程 | 如何保证质量与可演进？ | 测试看不出破坏，发布靠运气 |
| 产品 | 开发者如何理解并愿意使用？ | 无人接入，支持成本高 |
| 商业 | 价值如何被度量与捕获？ | 用量增长但亏损扩大 |

这张地图还有一个用途：**定位争论属于哪一层**。团队经常把不同层的争论混在一起，导致会议无法收敛。例如：

- “为什么不用 GraphQL？”是协议层问题，但真正的原因可能在产品层（多端字段差异）。
- “为什么不能改字段名？”是契约层问题，但根因可能在商业层（合作伙伴合同承诺了字段）。
- “为什么限流这么严？”是运行层问题，但根因可能在商业层（免费层成本失控）。

把争论放回正确的层，才能找到正确的决策者。

第 5 层（工程）在这些年明显变厚：它不再只是 CI 和监控，还包括可验证的沙箱与测试数据、可控的渐进发布，以及基础设施本身的声明式契约。这三件事常被归给平台团队，却会直接改变 API 的契约、发布风险和事故半径。本版用三个附录展开：[附录 AJ](../appendices/aj-sandbox-mock-test-data.md)、[附录 AK](../appendices/ak-feature-flags-experiments-progressive-delivery.md) 与 [附录 AL](../appendices/al-infrastructure-as-api-terraform-crd-gitops.md)。

### 地图不是流程

七层地图描述的是“一个 API 由哪些决策组成”，不是“必须按顺序完成七个阶段”。真实设计往往是跳跃的：

- 看到领域模型后，发现商业模式不成立，回头调整；
- 选了 gRPC 后，发现浏览器不支持，改成 Connect；
- 做了限流后，发现定价模型需要按“成功请求”而不是“总请求”计量，回头改契约。

地图的价值是让你知道“还有哪些层没被考虑”，而不是强迫你线性推进。

## 2.2 设计前的四类输入

API 设计不是凭空创造，而是对输入的压缩。输入越完整，设计越不需要猜。至少有四类输入。

### 1. 功能需求

不是“需要订单接口”，而是：

- 谁创建订单？
- 订单包含哪些商品与价格快照？
- 下单时是否需要预占库存？
- 支付失败后订单保留多久？
- 是否允许部分取消？
- 需要支持哪些查询维度？
- 是否需要草稿、审核、定时生效？
- 是否需要批量导入、批量导出？
- 有哪些外部系统需要感知订单变化？

功能需求要写到“可以据此写测试”的程度。如果一句话无法判断对错，它就还不是需求。

### 2. 质量属性

功能需求决定“做什么”，质量属性决定“做成什么样”：

- 延迟目标：P50 / P95 / P99；
- 吞吐与突发流量；
- 一致性要求：强一致、读己之写、最终一致；
- 可用性目标与可接受的降级；
- 数据保留、审计与合规；
- 多租户隔离级别；
- 成本上限；
- 可观测性要求；
- 灾难恢复目标（RPO / RTO）。

质量属性最容易在设计中缺席，因为它们不写在功能清单里。但它们往往决定架构：

- 如果 P99 要求 100ms，就不能在请求路径上做同步跨区调用；
- 如果要求 RPO=0，就不能只依赖异步复制；
- 如果要求租户级隔离，缓存键、数据库连接、日志都必须带租户维度。

### 3. 消费者约束

- 他们使用什么语言和运行时？
- 能否处理流式响应？
- 是否支持 HTTP/2 或 gRPC？
- 他们的发布节奏是否可控？
- 是否有防火墙、代理或老旧客户端？
- 他们的错误处理能力如何？
- 他们是否有严格的 schema 校验？
- 他们能否处理未知字段和未知枚举？
- 他们是否需要离线或弱网支持？

消费者约束经常被低估。一个在内部服务之间完美运行的 gRPC 接口，可能因为合作伙伴的 Java 7 环境、企业代理或浏览器限制而无法落地。

### 4. 组织约束

- 哪个团队拥有这个 API？
- 谁负责 on-call？
- 变更需要谁批准？
- 是否存在遗留系统或监管要求？
- 团队是否具备相应的运维能力？
- 预算和排期如何？
- 是否有合规审计窗口？

组织约束不是“政治”，而是真实的设计边界。一个需要三支团队协调两周才能发布的接口，和一个单团队可以每天发布的接口，应该有不同的版本策略和耦合程度。

**API 设计不是寻找“最优解”，而是在这四类输入的交集中寻找可执行解。**

## 2.3 一个可复用的设计流程

下面这套流程不是瀑布，而是一个可以在一周内跑完的循环。复杂 API 可以迭代多轮。

### 第一步：写消费者故事

用类似用户故事的方式描述调用场景：

```text
作为移动端应用，
我希望在用户下拉刷新时获取最近 20 条订单，
以便快速展示最新状态，
同时不需要一次性下载全部历史订单。
```

消费者故事应包含：

- 角色：谁在调用？
- 触发条件：什么时候调用？
- 目标：要完成什么任务？
- 数据量级：一次多少条？总共多少？
- 失败后的行为：超时、重试、降级？
- 成功标准：怎样算“好用”？

再举一个更复杂的例子：

```text
作为合作伙伴的对账系统，
我希望每天凌晨拉取前一天的已结算交易，
以便在早上 8 点前完成财务对账。
数据量约 50 万条，允许 30 分钟延迟；
如果拉取失败，我会重试 3 次，然后告警；
我不能接受重复记录，但可以接受分页。
```

这个故事的写法会直接推导出：异步导出、游标分页、幂等、稳定的结算时间语义、文件校验和。

### 第二步：画领域边界

列出核心概念、它们的关系和不变量：

- 订单有唯一的 `order_id`；
- 订单金额在创建后不可变，退款是独立记录；
- 订单状态只能按状态机迁移；
- 库存预占与订单创建必须最终一致；
- 一个订单可以有多笔支付，但只有一笔成功支付；
- 退款总额不能超过已支付金额。

领域边界不要求画 UML。一张白板、几个方框、几行不变量，通常比正式模型更有用。

### 第三步：选择交互形态

| 任务形态 | 首选形态 |
|---|---|
| 读取一个已知对象 | 请求—响应 |
| 条件查询与分页 | 请求—响应 + 游标 |
| 创建后需要时间处理 | 异步任务 + 轮询/回调 |
| 多个系统需要感知状态变化 | 事件 |
| 持续双向交互 | WebSocket / WebTransport |
| 单向实时推送 | SSE |
| 大文件上传下载 | 分块 / 预签名 URL |
| 跨服务组合查询 | BFF / GraphQL / 聚合 API |
| 高频小写入、可容忍延迟 | 消息队列 / 批量缓冲 |
| 需要严格顺序的状态复制 | 日志/流 + 分区键 |

### 第四步：先写示例，再写 Schema

不要先写 OpenAPI。先写 3～5 个真实的请求与响应示例，包括：

- 正常路径；
- 参数校验失败；
- 权限不足；
- 资源不存在；
- 冲突或并发失败；
- 依赖超时；
- 分页边界；
- 空结果；
- 部分成功；
- 重复请求。

示例会暴露 Schema 无法表达的语义问题。例如：

```json
{
  "id": "ord_123",
  "status": "PAID",
  "paidAt": null
}
```

这个示例立刻引出一个问题：状态是 `PAID`，为什么 `paidAt` 是 `null`？是支付已授权但未到账，还是数据不一致？Schema 不会告诉你，但示例会逼你回答。

### 第五步：定义错误与状态机

对每个操作问：

- 哪些失败是调用方可恢复的？
- 哪些失败应该重试？重试是否安全？
- 哪些失败需要人工介入？
- 状态如何从 A 到 B？是否存在中间态？
- 并发操作如何裁决？
- 部分成功如何表达？
- 超时后调用方应该查询什么？

### 第六步：对抗性评审

让不参与设计的人扮演“恶意的调用方”：

- 重复提交 10 次会怎样？
- 两个客户端同时修改同一资源会怎样？
- 传入负数、超长字符串、错误类型会怎样？
- 在 99 分位延迟下，客户端会怎样？
- 如果某个依赖不可用，API 返回什么？
- 如果调用方两年不升级，会发生什么？
- 如果调用方每秒轮询 1000 次，会怎样？
- 如果攻击者拿到一个合法 token，能做什么？
- 如果请求体是 100MB 的嵌套 JSON，会怎样？
- 如果时区是 UTC+14，日期边界会怎样？

对抗性评审不需要正式流程。一张清单、一个小时、三个人，通常就能找出最贵的几个问题。

### 第七步：原型与验证

- 用 mock server 验证契约；
- 用真实数据验证分页与性能；
- 用契约测试验证消费者假设；
- 用负载测试验证容量；
- 用故障注入验证降级；
- 用安全测试验证边界；
- 用真实开发者做一次“首次接入”观察。

原型的目标不是“做个 demo”，而是“用最小成本验证最贵的假设”。最贵的假设通常是：消费者能否理解、性能是否达标、失败是否可恢复。

### 第八步：记录决策

每个重要决定都应有记录：

```markdown
# ADR-014：订单列表使用游标分页

## 状态
已接受

## 背景
订单量可达每租户千万级，offset 分页在深页时性能急剧下降，
且并发写入会导致重复/遗漏。

## 决策
使用不透明游标，游标包含排序键与唯一 ID，服务端签名。

## 后果
- 客户端不能跳页；
- 需要提供稳定的排序键；
- 游标过期时间设为 24 小时；
- 导出场景改用异步任务。
```

ADR 的价值不在于形式，而在于把“当时的约束”保留下来。否则半年后所有人只会看到“为什么不用 offset”这个表面问题。

一个好的 ADR 还应记录：

- 考虑过哪些替代方案；
- 为什么排除它们；
- 这个决定在什么条件下会失效；
- 谁批准的；
- 何时复查。

## 2.4 设计画布

在评审会上，一张 A4 纸通常比 30 页文档更有效：

```text
┌──────────────────────────────────────────────┐
│ API 名称：订单服务                            │
│ 消费者：移动端、Web、合作伙伴、对账系统         │
│ 核心任务：下单、查单、取消、支付、退款          │
│ 关键不变量：金额快照、库存预占、状态机          │
│ 风格：REST + 事件 + Webhook                   │
│ 认证：OAuth 2.1 + 租户声明                     │
│ 一致性：订单强一致，库存最终一致                │
│ 延迟目标：P95 < 300ms                         │
│ 可用性：99.95%                                │
│ 版本策略：URL 主版本 + 兼容性扩展               │
│ 计量：按订单创建数计费                          │
│ 主要风险：超卖、重复支付、Webhook 丢失          │
└──────────────────────────────────────────────┘
```

这张画布不追求完整，它的作用是让评审者在五分钟内看到全局，并迅速发现矛盾。例如：

- 如果可用性目标是 99.99%，但依赖一个没有多活的消息队列，矛盾就暴露了；
- 如果按订单创建数计费，但重试会创建重复订单，收入与成本都会被扭曲；
- 如果要求 P95 < 100ms，但设计里包含同步调用三个外部服务，目标不可达。

画布还可以升级为“决策一页纸”，在右侧加上每个决定的负责人和复查日期。

## 2.5 设计评审的六个问题

1. **消费者是否能用一句话说清这个 API 的价值？**
2. **最坏情况下，调用方会看到什么？**
3. **哪些决定是不可逆的？我们是否为它们付出了足够的设计成本？**
4. **如果流量增长 100 倍，哪个环节先崩？**
5. **如果必须删除一个字段，我们怎么知道谁在用？**
6. **这个 API 的失败会不会转化为资金、信任或合规损失？**

如果团队无法回答第 3 和第 5 个问题，通常说明可演进性还没有被认真设计。

可以再加三个问题，用于 AI 时代：

7. **一个 Agent 只读工具描述，能否正确选择这个接口？**
8. **错误信息是否足以让自动化调用方自行恢复？**
9. **每个操作的最小权限是什么？是否存在“一个 token 做所有事”的情况？**

## 2.6 案例：设计一个会议室预订 API

假设需求是“员工可以预订会议室”。

**初级设计**可能直接给出：

```text
POST /bookings
GET /bookings/{id}
DELETE /bookings/{id}
```

**进一步追问**会发现问题：

- 如何查询某会议室某天的可用时段？
- 重复预订如何防止？
- 时区如何处理？
- 会议改期是修改还是新建？
- 取消是否需要理由和权限？
- 周期性会议如何表达？
- 外部访客能否预订？
- 预订与日历系统如何同步？
- 会议室设备故障时如何释放？
- 参会人冲突如何检测？

**更完整的模型**可能包含：

```text
GET  /rooms?capacity=8&equipment=video&building=shanghai
GET  /rooms/{roomId}/availability?from=...&to=...&timeZone=Asia/Shanghai
POST /bookings
GET  /bookings/{bookingId}
POST /bookings/{bookingId}/reschedule
POST /bookings/{bookingId}/cancel
GET  /bookings?userId=...&from=...&to=...
```

关键设计点：

- 可用性查询是独立资源，因为它有复杂的查询语义，且可能来自日历、门禁、设备状态多个数据源；
- 创建预订需要 `Idempotency-Key`，防止双击产生两条记录；
- 改期是显式操作，保留历史，而不是 PATCH 时间字段；
- 取消有独立权限与审计；
- 时间使用 ISO 8601 带偏移量，同时明确业务时区；
- 并发预订通过数据库约束或分布式锁保证不重叠；
- 周期性会议建模为“系列”资源，单次实例可单独取消；
- 外部访客需要单独的邀请与审批流程。

同一个需求，初级设计与完整设计的差距不在“REST 知识”，而在是否追问了领域约束、失败模式和长期演进。

### 一个容易忽略的细节：时间区间

“预订 10:00–11:00”与“预订 10:00–11:00”可能重叠，也可能不重叠，取决于区间是左闭右开还是双闭。API 必须明确：

```text
[start, end)  # 推荐：10:00–11:00 与 11:00–12:00 不重叠
```

如果用双闭区间，10:00–11:00 与 11:00–12:00 在 11:00 这一秒重叠，可能导致“看起来没冲突却订不上”的灵异问题。区间语义应写进契约，并在测试中覆盖边界。

## 2.7 设计方法的三种常见误区

### 误区一：把“设计”等同于“画 ER 图”

ER 图描述数据关系，不描述任务、权限、状态和失败。一个 ER 图完美的系统，可能没有一个好用的 API。

### 误区二：把“设计评审”等同于“格式检查”

如果评审只检查字段命名和 URL 复数，而不问消费者任务、失败模式和演进策略，它只是一次 lint，不是设计评审。

### 误区三：把“敏捷”等同于“不设计”

敏捷反对的是大 upfront 设计，不是反对设计。好的敏捷设计是“刚好足够的设计 + 快速验证 + 持续演进”。API 的不可逆决策需要提前想清楚，可逆决策可以边做边改。

## 2.8 本章小结

- API 设计应同时从领域约束和商业价值出发，中间五层是连接路径。
- 设计输入包括功能需求、质量属性、消费者约束和组织约束。
- 先写消费者故事与示例，再写 Schema 与实现。
- 对抗性评审是发现契约漏洞的最便宜方式。
- ADR 与设计画布能把隐性约束显性化。
- 好的设计流程不是瀑布，而是可重复的循环：建模、契约、验证、观测、演进。
- 设计评审要问不可逆决策、规模瓶颈、使用量观测和 AI 可理解性。
- 需要按问题查模式时，使用[附录 M](../appendices/m-patterns-antipatterns.md)。
- 并发与多区域设计用[附录 Z](../appendices/z-distributed-consistency-multi-region.md)做一致性承诺；关键状态机用[附录 AA](../appendices/aa-formal-contracts-model-checking.md)验证不变量。
- 从设计进入实现时，使用[附录 R](../appendices/r-implementation-architecture.md)；批量与迁移见[附录 S](../appendices/s-bulk-import-export.md)；合规映射见[附录 T](../appendices/t-compliance-engineering.md)；失败模式见[附录 U](../appendices/u-incident-postmortems.md)。
- 商业落地见[附录 V](../appendices/v-metering-billing.md)（计量与计费）、[附录 W](../appendices/w-api-product-management.md)（产品与增长）；遗留系统迁移见[附录 X](../appendices/x-legacy-modernization.md)。
- 密码学与后量子迁移见[附录 AD](../appendices/ad-cryptography-pqc.md)；序列化、压缩与 schema 演进见[附录 AE](../appendices/ae-serialization-schema-evolution.md)。

## 设计练习

为“企业报销审批 API”完成一张设计画布，并写出至少 8 个请求/响应示例，覆盖正常、校验失败、权限不足、并发冲突和依赖超时。然后让一位同事扮演恶意调用方，找出三个你没想到的失败场景。

进阶：为这个 API 写一份 ADR，记录“审批流是同步返回还是异步任务”的决定，并说明它在什么条件下会失效。
