# 第 53 章 市场、竞争与生态

## 53.1 市场分析的基本问题

- 谁有这个问题？
- 问题有多大？
- 他们现在怎么解决？
- 为什么你的方案更好？
- 他们愿意付多少钱？
- 谁能阻止你？

API 市场的分析不能只看“开发者数量”，还要看：

- 决策者；
- 预算；
- 集成成本；
- 合规；
- 替代方案；
- 采购周期。

### 开发者数量不等于市场

- 开发者可能没有预算；
- 决策者可能是 CTO/采购；
- 集成成本可能高于订阅费；
- 合规可能阻止采用；
- 替代方案可能是自建/Excel。

## 53.2 TAM / SAM / SOM

```text
TAM（总可寻址市场）
  └── SAM（可服务市场）
        └── SOM（可获得市场）
```

例如“企业身份验证 API”：

- TAM：所有需要身份验证的软件；
- SAM：你的区域/合规/产品形态能服务的客户；
- SOM：你未来 1～3 年能获取的份额。

常见错误：

- 把 TAM 当收入；
- 忽略采购预算；
- 忽略替代方案；
- 忽略合规/区域限制；
- 高估转化。

### 自下而上的估算

```text
SAM = 目标客户数 × 平均客单价
```

例如：

```text
目标客户 5,000 家 × 平均年费 $10,000 = $50M
```

比“全球 API 市场 $100B”更有意义。

## 53.3 市场细分

按维度细分：

- 客户规模（SMB、Mid-Market、Enterprise）；
- 行业（金融、医疗、电商、教育）；
- 地域；
- 技术栈；
- 使用场景；
- 采购方式；
- 合规要求。

不同细分需要不同：

- 产品；
- 定价；
- 文档；
- 支持；
- 销售；
- SLA；
- 合规。

### 细分的选择

- 不要一开始覆盖所有细分；
- 选一个能赢的细分；
- 建立参考客户；
- 再扩展。

### 细分矩阵

| 细分 | 需求 | 付费意愿 | 销售 | 合规 |
|---|---|---|---|---|
| SMB | 简单、便宜 | 低 | 自助 | 低 |
| Mid-Market | 功能、集成 | 中 | 销售辅助 | 中 |
| Enterprise | 安全、合规、SLA | 高 | 销售 | 高 |

## 53.4 竞争分析

分析维度：

- 能力；
- 价格；
- 可靠性；
- 文档/DX；
- 生态；
- 合规；
- 支持；
- 集成；
- 品牌；
- 切换成本。

### 竞争格局

- 直接竞品；
- 间接竞品（自建、开源、外包）；
- 平台巨头；
- 新兴 AI 原生；
- 客户内部团队。

最大的竞争对手往往是“客户自建”或“Excel/人工流程”。

### Porter 五力

| 力量 | 问题 |
|---|---|
| 现有竞争 | 有多少直接竞品？ |
| 新进入者 | 进入门槛高吗？ |
| 替代品 | 客户能用什么替代？ |
| 供应商 | 你依赖谁？ |
| 买方 | 客户议价能力如何？ |

## 53.5 壁垒与护城河

- 网络效应；
- 切换成本；
- 规模经济；
- 数据；
- 品牌；
- 合规/牌照；
- 生态；
- 技术；
- 成本。

API 的切换成本来自：

- 集成深度；
- SDK；
- 数据；
- 工作流；
- 认证；
- 审计；
- 团队习惯。

### 壁垒的检验

- 客户迁移需要多久？
- 迁移成本是多少？
- 竞品能否复制？
- 平台巨头能否免费提供？
- 监管是否保护？

## 53.8 市场/应用市场

API 产品可以通过市场分发：

- 云市场；
- SaaS 市场；
- 开发者工具市场；
- Agent 工具市场。

要点：

- 上架要求；
- 计费；
- 分成；
- 审核；
- 支持；
- 评价；
- 竞争；
- 排名。

### 市场的经济学

市场不是“多一个获客渠道”，而是一套新的成本与激励结构：

| 维度 | 自营 API | 通过市场 |
|---|---|---|
| 获客 | 自己投放、销售 | 市场发现与推荐 |
| 分成 | 无 | 通常 15%～30% |
| 计费 | 自己收单 | 市场代收、延迟结算 |
| 审核 | 自己控制 | 上架审核、持续合规 |
| 数据 | 完整客户关系 | 平台可能限制数据 |
| 风险 | 自己承担 | 平台下架、排名变化 |
| 信任 | 自建品牌 | 借用平台信任 |

市场适合“客户已经在平台上、采购流程复杂、需要统一账单”的场景。它不适合作为唯一渠道：一旦平台改变分成、排名或审核规则，收入会被动波动。健康的结构通常是“自营 + 市场 + 合作伙伴”三条腿，且客户关系与计费数据可迁移。

### Agent 工具市场

Agent 时代可能出现新的“工具市场”：模型或 Agent 在运行时发现、比较并调用第三方能力。它与传统 API 市场的区别：

- 发现由机器完成，描述与 schema 的质量比营销页更重要；
- 调用频率高、单次金额小，结算与对账要支持微支付；
- 信任来自签名、来源、评估与审计，而不是品牌 Logo；
- 竞争更透明，价格、延迟、成功率可被实时比较；
- 责任更难界定：Agent 选错工具、工具返回错误、用户受损，谁负责？

对 API 提供方的启示：

- 把能力描述、价格、SLA、限制做成机器可读；
- 提供沙箱、测试用例与可验证的输出；
- 支持按次计费、预算与退款；
- 记录完整调用轨迹，便于争议处理；
- 不要只优化“人看到的页面”，要优化“模型读到的契约”。

## 53.9 开放标准策略

- 采用标准降低集成成本；
- 参与标准制定获得影响力；
- 开源建立信任；
- 但标准可能商品化；
- 需要在“开放”和“差异化”之间平衡。

### 标准策略

| 策略 | 优点 | 缺点 |
|---|---|---|
| 采用标准 | 低门槛、互操作 | 商品化 |
| 扩展标准 | 兼容 + 差异化 | 复杂度 |
| 自建标准 | 控制 | 生态难 |
| 开源 | 信任、生态 | 竞争 |

## 53.10 平台包抄

平台巨头可能：

- 把 API 变成免费功能；
- 捆绑销售；
- 限制访问；
- 复制能力；
- 改变规则。

防御：

- 深耕细分；
- 生态锁定；
- 数据/网络效应；
- 合规；
- 客户关系；
- 速度；
- 差异化；
- 多平台策略。

### 平台依赖

- 云厂商；
- 应用市场；
- 模型供应商；
- 支付渠道；
- 身份提供商。

需要：

- 多供应商；
- 可迁移；
- 合同保护；
- 退出计划。

## 53.11 案例：支付/通信/模型 API

### 支付

- 竞争激烈；
- 差异化在开发者体验、全球覆盖、合规、增值服务；
- 网络效应弱，切换成本中等；
- 价格战常见。

### 通信

- 运营商关系；
- 全球覆盖；
- 价格透明；
- 规模效应；
- 监管。

### 模型 API

- 能力快速迭代；
- 价格下降；
- 生态/工具链；
- 安全/合规；
- 供应商锁定；
- 自托管/开源替代。

### 案例启示

- 能力会商品化；
- 集成深度和生态是壁垒；
- 合规可以是壁垒；
- 开发者体验是差异化；
- 成本领先需要规模。

## 53.12 生态指标

- 开发者数；
- 活跃集成；
- 合作伙伴数；
- 市场收入；
- 社区活跃；
- SDK 下载；
- 认证人数；
- 生态带来的收入占比；
- 伙伴满意度；
- 集成时间；
- 生态留存。

## 53.13 本章小结

- 市场分析要看客户、预算、替代方案与合规。
- TAM/SAM/SOM 要谨慎使用。
- 细分市场决定产品、定价与支持。
- 竞争包括自建、开源、平台巨头。
- 壁垒来自网络效应、切换成本、规模、数据、品牌、合规、生态。
- 生态与合作伙伴扩大分发。
- 市场渠道有分成、审核、排名与客户关系风险，不宜作为唯一渠道。
- Agent 工具市场把竞争推向机器可读契约、微支付与可验证信任。
- 开放标准与平台包抄需要战略平衡。
