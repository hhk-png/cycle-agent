# 第 55 章 风险、组织与路线图

## 55.1 风险地图

API 业务的风险至少包括：

### 安全风险

- 数据泄露；
- 越权；
- 令牌泄露；
- 供应链攻击；
- 滥用；
- DDoS；
- 提示注入（AI）。

### 合规风险

- 数据驻留；
- 隐私；
- 行业监管；
- 反洗钱；
- 消费者保护；
- AI 责任；
- 出口管制；
- DORA / NIS2 的运营韧性与事件报告；
- EU Data Act 的切换与可携带性；
- PCI DSS 4.0.1 的持续控制要求。

义务到 API 能力与证据的映射，见[附录 T](../appendices/t-compliance-engineering.md)。

### 商业风险

- 客户集中；
- 价格战；
- 平台依赖；
- 供应商锁定；
- 毛利侵蚀；
- 需求变化；
- 汇率。

### 技术风险

- 单点；
- 容量；
- 依赖；
- 版本碎片；
- 技术债；
- 团队能力；
- 协议过时。

### 组织风险

- 所有权不清；
- 治理瓶颈；
- 支持不足；
- 知识集中；
- 人才流失；
- 团队冲突。

## 55.2 风险矩阵

```text
概率 × 影响 = 风险等级
```

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| 越权泄露 | 中 | 极高 | 对象级授权、RLS、审计 |
| 供应商故障 | 中 | 高 | 多供应商、降级 |
| 大客户流失 | 低 | 高 | 多元化、合同 |
| 价格战 | 高 | 中 | 差异化、成本 |
| 合规罚款 | 低 | 极高 | 合规体系 |
| 容量不足 | 中 | 高 | 压测、弹性 |
| 版本碎片 | 高 | 中 | 弃用政策 |
| 模型供应商锁定 | 中 | 高 | 抽象层、多模型 |

### 风险的量化

```text
风险敞口 = 概率 × 损失
```

例如：

```text
数据泄露概率 5%，损失 $10M → 敞口 $500K
```

量化不精确，但能帮助排序。

### 风险登记表

| 字段 | 说明 |
|---|---|
| 风险 | 一句话描述 |
| 类别 | 安全/合规/商业/技术/组织 |
| 概率 | 低/中/高 |
| 影响 | 低/中/高/极高 |
| 敞口 | 概率 × 损失 |
| 触发信号 | 如何知道它正在发生 |
| 缓解 | 预防措施 |
| 应急 | 发生后的动作 |
| 负责人 | 谁负责 |
| 复查 | 下次复查时间 |

风险登记表应定期更新，而不是一次性文档。

## 55.3 组织模式

### 集中式 API 团队

- 统一标准；
- 平台能力；
- 可能成为瓶颈。

适合：

- 小组织；
- 强合规；
- 需要快速统一。

### 联邦式

- 各团队拥有 API；
- 中央 Guild 制定标准；
- 需要强治理。

适合：

- 中大型组织；
- 多业务线；
- 团队成熟。

### 平台团队

- 提供网关、目录、工具；
- 业务团队自助；
- 适合中大型组织。

适合：

- 平台工程；
- 自助文化；
- 规模大。

### API Guild

- 跨团队社区；
- 标准制定；
- 评审；
- 培训；
- 不直接拥有所有 API。

适合：

- 联邦式组织；
- 需要横向协调。

### 模式对比

| 模式 | 一致性 | 速度 | 瓶颈 | 适用 |
|---|---|---|---|---|
| 集中式 | 高 | 慢 | 高 | 小组织 |
| 联邦式 | 中 | 快 | 低 | 中大 |
| 平台 | 高 | 快 | 中 | 中大 |
| Guild | 中 | 中 | 低 | 补充 |

## 55.4 所有权

每个 API 应有：

- 产品负责人；
- 技术负责人；
- on-call；
- 安全联系人；
- 文档负责人；
- 客户成功。

所有权要写入目录、值班表和合同。

### 所有权的信号

- 事故时谁响应？
- 变更谁审批？
- 文档谁维护？
- 消费者找谁？
- 预算谁负责？

### RACI 示例

| 活动 | 产品 | 技术 | SRE | 安全 | 法务 |
|---|---|---|---|---|---|
| 能力规划 | A | R | C | C | I |
| 契约设计 | C | A/R | C | C | I |
| 发布 | I | A/R | C | I | I |
| 事故响应 | I | C | A/R | C | I |
| 合规 | C | C | I | A/R | C |

- R：执行；
- A：最终负责；
- C：咨询；
- I：知会。

没有 A 的活动，通常没人真正负责。

## 55.5 成熟度模型

### Level 1：临时

- 无标准；
- 无目录；
- 无契约；
- 无监控。

### Level 2：规范

- 风格指南；
- OpenAPI；
- 基础监控；
- 评审。

### Level 3：平台化

- 网关；
- 目录；
- 自助；
- 契约测试；
- SLO。

### Level 4：产品化

- 开发者门户；
- 定价；
- 生态；
- 数据驱动；
- 生命周期。

### Level 5：生态化

- 合作伙伴；
- 市场；
- 标准影响；
- 网络效应。

### 成熟度的评估

- 契约覆盖率；
- 自动化程度；
- 可观测性；
- 治理；
- 开发者体验；
- 商业化。

### 成熟度评估问题

1. 能否在一天内列出所有公开 API 及其所有者？
2. 每个 API 是否有机器可读契约？
3. 破坏性变更是否会被 CI 拦截？
4. 是否有 SLO 和错误预算？
5. 是否有统一的错误格式？
6. 是否有对象级授权测试？
7. 是否有弃用流程？
8. 开发者能否在 10 分钟内完成首次调用？
9. 是否知道每个 API 的调用方和版本？
10. 是否能按租户/端点分析成本和错误？

答案越多的“是”，成熟度越高。

## 55.9 投资优先级

用“影响 × 可行性”排序：

- 高影响、低可行性 → 规划；
- 高影响、高可行性 → 立即做；
- 低影响、高可行性 → 有空做；
- 低影响、低可行性 → 不做。

### 影响评估

- 收入；
- 成本；
- 风险；
- 体验；
- 战略。

### 可行性评估

- 技术；
- 组织；
- 预算；
- 时间；
- 依赖。

## 55.10 组织反模式

- API 团队变成审批瓶颈；
- 业务团队各自为政；
- 平台团队闭门造车；
- 没有所有权；
- 没有 on-call；
- 治理与业务脱节；
- 只考核数量；
- 安全团队最后介入；
- 平台团队没有产品经理；
- 支持团队不知情。

## 55.12 本章小结

- API 风险包括安全、合规、商业、技术、组织。
- 风险矩阵帮助排序。
- 组织模式有集中、联邦、平台、Guild。
- 所有权必须明确。
- 成熟度模型帮助定位。
- 90 天、1 年、3 年路线图分阶段推进。
- 投资优先级看影响与可行性。
