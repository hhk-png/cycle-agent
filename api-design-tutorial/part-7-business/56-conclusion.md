# 第 56 章 结语：把 API 当作长期资产

## 56.1 回到最初的问题

我们从一个简单的字段改名开始：`PAID` 变成 `paid`。看似微不足道，却可能让支付、对账、报表、移动端和合作伙伴同时失效。

这就是 API 设计的全部难点：**它把当下的实现，变成未来的约束。**

一个 API 发布之后，就不只属于它的作者。它属于调用它的代码、依赖它的团队、围绕它建立的业务流程，以及最终被它影响的用户。设计 API，本质上是在设计一种长期关系。

### 资产的视角

如果把 API 当作资产，就会问：

- 它在增值还是贬值？
- 维护成本是多少？
- 谁会依赖它？
- 它的生命周期多长？
- 如何让它持续产生价值？

API 的“资产价值”来自：

- 被依赖的程度；
- 切换成本；
- 生态；
- 数据；
- 信任。

而“负债”来自：

- 不兼容的变更；
- 未管理的版本；
- 安全债；
- 文档债；
- 治理债。

## 56.2 十条原则

如果这本书只能留下十句话，我希望是：

1. **先理解消费者与任务，再选择协议与风格。**
2. **资源模型比 URL 更重要；领域边界比框架更重要。**
3. **契约包含语法、语义、行为与运行承诺，缺一不可。**
4. **错误是主要使用路径，必须可理解、可恢复、可追踪。**
5. **幂等、并发、一致性不是高级话题，而是写操作的基本功。**
6. **兼容性由消费者决定；版本化是管理，不是编号。**
7. **安全要在对象、字段、租户、功能四个层次检查。**
8. **可观测性不是日志堆积，而是能回答“发生了什么、为什么”。**
9. **性能与可靠性要用分位数、预算、过载保护和演练来证明。**
10. **API 是产品，也是生意；技术决策最终会变成成本、价格与信任。**

### 如果再加三条

11. **AI Agent 让契约从“给人看”变成“给机器执行”，清晰度就是功能正确性。**
12. **治理的目标是让正确路径更省事，而不是增加审批。**
13. **文档、SDK、错误信息和支持，是 API 产品的一部分，不是附属品。**

## 56.3 三个常见误区

### “先跑起来，以后再优化”

有些东西可以后补：缓存、索引、监控面板。有些东西很难后补：身份模型、资源边界、错误语义、幂等、多租户隔离。**区分“可逆决策”和“不可逆决策”，把设计精力放在后者。**

可逆决策：

- 缓存策略；
- 索引；
- 日志格式；
- 内部实现；
- 部署方式。

不可逆决策：

- ID 格式；
- 资源边界；
- 认证模型；
- 多租户模型；
- 错误语义；
- 金额/时间表示。

### “我们内部用，不需要那么正式”

内部消费者可能比外部更多、更隐蔽、更难协调。内部 API 同样需要契约、所有权、版本和 SLO。区别只在于协调成本，而不是质量下限。

内部 API 的特殊风险：

- 没有正式合同；
- 消费者不可见；
- 变更靠沟通；
- 故障传播快。

### “用了最新协议就先进”

协议是载体。REST、gRPC、GraphQL、事件、MCP 都不能替代领域建模、权限设计、错误处理和运营能力。**技术选型要解决真实约束，而不是制造身份认同。**

## 56.4 从今天开始

### 如果你正在设计一个新 API

1. 写一页设计画布；
2. 写五个真实请求/响应示例，包括失败；
3. 画出状态机；
4. 找一位不参与的同事做对抗性评审；
5. 先写契约，再写实现；
6. 上线前准备监控、限流、回滚和弃用计划。

### 如果你在维护一个老 API

1. 盘点消费者与版本；
2. 找出最痛的三个契约问题；
3. 用扩展—收缩逐步修复；
4. 补上契约测试与可观测性；
5. 建立所有权与生命周期。

### 如果你在建设 API 平台

1. 建目录；
2. 定标准；
3. 做工具；
4. 选试点；
5. 度量；
6. 推广；
7. 治理。

### 如果你在做 API 商业

1. 明确客户与价值；
2. 设计计量；
3. 定价；
4. 算单位经济；
5. 建生态；
6. 管风险；
7. 持续运营。

如果你想把这些原则放进一个完整系统里演练，[附录 O](../appendices/o-end-to-end-ticketing.md) 从需求、建模、契约、库存、支付、检票、实时、限流、测试一直走到上线与单位经济；[附录 P](../appendices/p-review-rubric-and-questions.md) 可以用来评审你的答案。

如果你要把设计落到代码，[附录 R](../appendices/r-implementation-architecture.md) 讨论分层、中间件、事务、幂等与部署；[附录 S](../appendices/s-bulk-import-export.md) 处理批量、导入导出与迁移；[附录 T](../appendices/t-compliance-engineering.md) 把合规条款变成 API 能力；[附录 U](../appendices/u-incident-postmortems.md) 用失败案例检验你的假设。

## 56.5 一张最终的检查清单

```text
消费者：谁在用？任务是什么？失败会怎样？
领域：边界、资源、状态机、不变量
契约：语法、语义、行为、运行
协议：REST/gRPC/GraphQL/事件/流
安全：认证、授权、租户、字段
可靠性：超时、重试、熔断、降级
可观测性：指标、日志、追踪、SLO
演进：版本、弃用、迁移
产品：文档、SDK、沙箱、支持
商业：计量、定价、成本、生态
```

## 56.6 最后

API 设计没有终点。业务会变，消费者会变，协议会变，模型会变。唯一不变的是：

> **你必须让另一个独立的主体，在无法完全预测的未来里，仍然能够理解你、信任你、与你协作。**

这就是契约的意义。

愿你的 API 不仅“能用”，还能被长期依赖。
