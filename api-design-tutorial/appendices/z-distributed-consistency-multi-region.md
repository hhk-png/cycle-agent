# 附录 Z：分布式一致性与多区域 API 设计

> 正文第 10 章讨论了写操作、幂等与一致性承诺，第 25 章讨论了事件，第 27 章用一节介绍了多区域与边缘。本附录把散落在各章的“一致性”收拢成一套可写进契约、可测试、可运维的设计语言。它不追求分布式系统理论的完整教材，而是回答一个工程问题：**当 API 跨机房、跨区域、跨时区运行时，我们到底向调用方承诺了什么，又如何证明这个承诺成立？**

## Z.1 一致性问题最终会变成契约问题

先看一个真实而常见的故障链：

```text
10:00:00.000  用户在 Shanghai 区域创建订单，写入成功，返回 201
10:00:00.120  同一用户刷新订单列表，请求被 GeoDNS 路由到 Frankfurt
10:00:00.180  Frankfurt 副本尚未收到复制，返回“订单不存在”
10:00:00.200  客户端认为创建失败，自动重试
10:00:00.260  重试请求回到 Shanghai，因为没有幂等键，创建了第二笔订单
```

从单个服务的角度看，每一步都“成功”了；从 API 契约的角度看，这份契约从一开始就不成立：

- 它没有说明“创建成功后，哪个范围内的读能看到这条记录”；
- 它没有说明“跨区域读取可能旧到什么程度”；
- 它没有要求写操作幂等；
- 它没有告诉调用方：读到旧数据时应该等待、重试，还是换一个区域。

一致性不是数据库内部的参数，而是 **API 对调用方的时间承诺**。一旦写进契约，它就会约束路由、复制、缓存、故障转移、SDK 重试和计费口径。

### 一致性承诺必须写成可验证的句子

模糊的写法：

```text
保证数据强一致。
```

可验证的写法：

```text
同一租户内，创建订单成功后 1 秒内，任意区域的按 ID 查询都能读到该订单；
跨区域列表查询最多滞后 5 秒；
故障转移期间允许最多 30 秒的写不可用，不保证跨区域读己之写。
```

后者包含四个要素：**范围**（同租户/同区域/全局）、**操作**（按 ID 查/列表查）、**时间上界**（1 秒/5 秒/30 秒）、**例外**（故障转移期间）。缺少任何一个，测试就无法判定通过与否。

## Z.2 一致性模型的坐标系

“强一致”是一个被过度使用的词。工程上至少要区分下面几层。

### Z.2.1 单对象模型

| 模型 | 保证 | 典型实现 | 代价 |
|---|---|---|---|
| 线性一致（linearizable） | 所有操作看起来在某个实时点原子生效，且遵守实时顺序 | 单主 + 同步复制、Raft/Paxos 读 | 跨区延迟、写可用性 |
| 顺序一致（sequential） | 存在一个全序，每个客户端看到自己的程序顺序 | 单主、部分内存模型 | 不保证实时顺序 |
| 因果一致（causal） | 有因果关系的操作按因果顺序可见 | 因果广播、版本向量 | 元数据与实现复杂 |
| 最终一致（eventual） | 停止写入后，副本最终收敛 | 异步复制、CRDT | 无时间上界则不可测试 |

线性一致是单对象最强保证。它不等于“所有对象放在一个事务里”，也不等于“跨多个对象的快照一致”。很多 API 声称“强一致”，实际只做到了单对象线性一致 + 跨对象最终一致。

### Z.2.2 会话保证

对大多数面向用户的 API，比“全局强一致”更实用的是会话保证：

| 保证 | 含义 | 失败时的用户感受 |
|---|---|---|
| 读己之写（read-your-writes） | 同一会话写入后，后续读能看到自己的写 | 刚保存就消失 |
| 单调读（monotonic reads） | 同一会话不会读到比之前更旧的数据 | 刷新后数据倒退 |
| 单调写（monotonic writes） | 同一会话的写按发起顺序生效 | 后发起的修改被覆盖 |
| 写跟随读（writes-follow-reads） | 读到某版本后，后续写基于至少该版本 | 基于旧值覆盖新值 |

这四条通常可以通过“会话粘性 + 版本令牌”实现，成本远低于全局线性一致。API 契约应明确支持哪几条，而不是笼统写“强一致”。

### Z.2.3 CAP 与 PACELC 的正确用法

CAP 说的是：网络分区发生时，分布式系统只能在一致性（C）与可用性（A）之间取舍。它有三个常见误用：

1. **把 CAP 当成日常设计三选二。** 没有分区时，系统可以同时追求一致与可用；CAP 只在分区期间生效。
2. **把 C 理解成“强一致”。** CAP 里的 C 是线性一致，不是“数据不丢”或“最终一致”。
3. **忽略延迟。** 跨区域同步复制即使没有分区，也会把写延迟从毫秒抬到几十甚至上百毫秒。

PACELC 补上了“否则（Else）”分支：分区时在 A 与 C 之间取舍，无分区时在延迟（L）与一致性（C）之间取舍。对 API 设计的直接含义是：

- 跨区域同步复制不是“更安全”，而是“用写延迟买 RPO”；
- 跨区域异步复制不是“偷懒”，而是“用一致性窗口买可用性与延迟”；
- 同一份 API 可以对不同端点、不同租户、不同数据类别做不同选择。

### Z.2.4 一致性承诺的粒度

一致性承诺至少可以按四个维度切分：

```text
数据类别：余额/订单/库存/日志/推荐
操作类型：按 ID 读 / 条件查询 / 列表 / 聚合
范围：单键 / 单租户 / 单区域 / 全局
时间：同步 / ≤1s / ≤5s / 无上界（只保证最终）
```

把这张表填完，比在架构图上写“多活”有用得多。一个常见的选择是：

| 数据 | 写 | 读 | 承诺 |
|---|---|---|---|
| 支付余额 | 单主、强一致 | 强一致 | 不允许旧读 |
| 订单 | 单主、同区域强一致 | 按 ID 读己之写，列表最终一致 | 列表滞后 ≤5s |
| 商品目录 | 多区域可写、CRDT/合并 | 本地读 | 收敛，允许冲突提示 |
| 推荐结果 | 异步 | 本地缓存 | 允许分钟级陈旧 |
| 审计日志 | 追加写 | 只读、按时间 | 不丢，允许延迟 |

## Z.3 会话保证的实现

### Z.3.1 版本令牌

服务端在写响应中返回一个不透明令牌，客户端在后续读请求中带上它：

```http
POST /orders
Content-Type: application/json
Idempotency-Key: 01J9Z6K4...

{"items": [...]}
```

```http
HTTP/1.1 201 Created
Location: /orders/ord_123
X-Consistency-Token: v1:eyJzaGFyZCI6Im9yZF8xMjMiLCJ2ZXJzaW9uIjo0Mn0
```

```http
GET /orders/ord_123
X-Min-Version: v1:eyJzaGFyZCI6Im9yZF8xMjMiLCJ2ZXJzaW9uIjo0Mn0
```

服务端收到 `X-Min-Version` 后：

- 如果本地副本版本 ≥ 令牌版本，直接返回；
- 如果本地副本落后，转发到主副本、等待复制，或返回 `503` + `Retry-After`；
- 令牌要签名，防止客户端伪造版本；
- 令牌要绑定租户与资源范围，避免成为跨租户探测工具；
- 令牌要有过期时间，过期后降级为普通读。

令牌不是“读缓存键”，而是“最低可见版本”。它不要求服务端记住会话，适合无状态网关。

### Z.3.2 会话粘性

把同一会话（或同一用户）的请求固定到同一区域/同一副本：

```text
Set-Cookie: route=ap-east-1; Path=/; Secure; HttpOnly; SameSite=Lax
```

或由网关根据 `tenant_id` 做一致性哈希。

优点：实现简单，能同时满足读己之写与单调读。缺点：

- 区域故障时会话被迫迁移，会话保证中断；
- 移动端网络切换可能丢失粘性；
- 负载不均；
- 跨区域用户延迟可能变差。

因此粘性通常与版本令牌组合使用：正常情况下靠粘性，故障转移后靠令牌兜底。

### Z.3.3 写跟随读

客户端读到资源版本 7 后修改，提交时带上：

```json
{
  "baseVersion": 7,
  "data": { "title": "..." }
}
```

服务端用 CAS 检查：版本不匹配返回 `409` 与当前版本。这既是并发控制，也是“写跟随读”的实现。对于高频冲突的资源，可以返回字段级差异，让客户端做字段合并。

### Z.3.4 会话保证的边界

会话保证不能跨设备、跨用户、跨长期离线。一个用户在两台设备上操作，本质上就是两个会话；若业务要求“多设备强一致”，就必须升级为服务端线性一致或显式合并，而不是继续加令牌。

## Z.4 时间、顺序与时钟

### Z.4.1 不要相信客户端时间

客户端时间可能：

- 被用户手动修改；
- 因时区设置错误偏移数小时；
- 因设备休眠漂移；
- 被恶意伪造，用于绕过过期、排序或计费。

因此：

- `createdAt`、`updatedAt` 由服务端生成；
- 客户端时间只作为 `clientReportedAt` 提示字段，不能用于排序、过期判断或计费；
- 需要业务时间（如“用户当地 9 点”）时，传 IANA 时区 ID，由服务端计算；
- 所有时间戳用 RFC 3339 UTC，另带业务时区字段。

### Z.4.2 时钟同步的极限

NTP 能把时钟误差控制在毫秒级，但无法消除：

- 虚拟机暂停（stop-the-world）导致的时间跳变；
- 闰秒（多数系统用 smear 处理）；
- 时钟回拨；
- 跨区域网络不对称。

所以，“最后写入胜出（LWW）”依赖的 `updatedAt` 并不可靠。两个写入相差 2ms，时钟误差 5ms，胜负就可能反转。

### Z.4.3 逻辑时钟

| 机制 | 能回答的问题 | 不能回答的问题 |
|---|---|---|
| Lamport 时钟 | A 是否因果先于 B | 并发还是先后 |
| 向量时钟 | 两个事件是否并发 | 全局实时顺序 |
| 混合逻辑时钟（HLC） | 接近实时的因果顺序，可排序 | 仍受时钟误差影响 |
| 版本号/序列号 | 同一聚合内的严格顺序 | 跨聚合顺序 |

API 契约中更实用的是 **每聚合单调序列号**：

```json
{
  "id": "ord_123",
  "version": 42,
  "updatedAt": "2026-11-26T10:00:00.123Z"
}
```

客户端用 `version` 做并发控制与增量同步，用 `updatedAt` 做展示。不要让 `updatedAt` 承担并发裁决。

### Z.4.4 事件顺序

事件流只保证分区内有序。跨分区的事件顺序必须由业务定义：

- 同一订单的支付、发货、退款事件用 `order_id` 做分区键；
- 消费者用 `(aggregate_id, version)` 拒绝旧事件；
- 跨聚合的因果关系用 `causation_id` / `correlation_id` 表达，而不是假设全局顺序；
- 需要全局顺序时，明确代价：单分区吞吐上限、或引入排序服务。

## Z.5 多区域拓扑

### Z.5.1 五种常见拓扑

| 拓扑 | 写 | 读 | RPO | RTO | 适用 |
|---|---|---|---|---|---|
| 单区域 + 冷备 | 单区域 | 单区域 | 分钟级 | 小时级 | 内部系统、成本敏感 |
| 单区域 + 热备 | 单区域同步/异步复制 | 主区域，备区域只读 | 0～秒级 | 分钟级 | 大多数企业 API |
| 主区域 + 只读副本 | 单主 | 本地只读 | 秒级 | 分钟级 | 读多写少、全球内容 |
| 按租户分片多活 | 每租户单主 | 租户本地 | 0（租户内） | 分钟级 | SaaS、数据驻留 |
| 全局多主 | 多区域可写 | 本地 | 取决于冲突策略 | 秒级 | 协作、目录、CRDT |

“多活”不是一个二元属性。真正要回答的是：

1. 每个键的写权威在哪里？
2. 故障时写权威如何转移？
3. 转移期间未复制的写怎么办？
4. 读能否接受旧值？旧多久？
5. 数据驻留是否允许跨区？

### Z.5.2 按租户/按键的单写者

最实用的多区域方案通常不是“所有区域都能写同一个键”，而是：

- 每个租户有一个 home region；
- 每个聚合键有唯一写区域；
- 其他区域只读或转发；
- 故障时通过租约 + fencing token 转移写权威。

这样避免了大部分冲突，同时保留本地读的低延迟。

```text
tenant t_123 → home: ap-east-1
key ord_123  → owner: ap-east-1
读：任意区域本地副本
写：路由到 owner；owner 不可用时，经共识转移
```

### Z.5.3 Cell 架构

把用户切成独立的 cell（单元），每个 cell 包含完整服务与数据：

```text
用户 → 路由层（按 user_id 哈希）→ cell A / cell B / cell C
```

优点：

- 故障爆炸半径小；
- 可逐个 cell 升级；
- 容量扩展线性；
- 数据驻留容易满足。

代价：

- 跨 cell 查询困难；
- 全局唯一性（如用户名）需要额外服务；
- 路由层成为关键路径；
- 运维工具要支持多 cell。

Cell 架构适合大规模消费级 API；中小企业 API 通常用“主区域 + 只读副本”更划算。

## Z.6 写路径设计

### Z.6.1 分区键

分区键决定顺序、热点与跨区流量。选择原则：

- 高基数，避免单分区热点；
- 与业务聚合一致（`tenant_id` + `order_id`）；
- 稳定，不随业务状态变化；
- 不包含敏感信息（避免日志/指标泄露）；
- 考虑租户规模差异，大租户可能需要独立分区。

反例：用 `created_at` 做分区键，导致所有新写入集中到最后一个分区；用 `status` 做分区键，导致状态迁移时跨分区。

### Z.6.2 全局 ID

多区域下，自增 ID 会暴露写入位置、难以合并、容易冲突。推荐：

- UUIDv7：时间有序、全局唯一、索引友好；
- ULID：类似，Base32 可读；
- 带前缀的 ID：`ord_01J...`，便于日志与排查；
- 不要用可枚举的短 ID 作为公开标识，除非有额外授权与速率限制。

ID 的生成位置：

| 方案 | 优点 | 缺点 |
|---|---|---|
| 客户端生成 | 离线可用、减少往返 | 需要校验与冲突处理 |
| 服务端生成 | 可控 | 离线创建需要临时 ID |
| 区域前缀 + 序列 | 可读、可定位 | 迁移/合并复杂 |

ID 不应编码业务含义（如“区域+用户等级”），否则业务变化后 ID 变成谎言。

### Z.6.3 Quorum

对于需要强一致的复制组：

```text
N = 3 副本，W = 2，R = 2
W + R > N → 读写有交集，可保证读到最新已确认写
```

代价：

- 写要等两个副本确认，跨区延迟叠加；
- 一个副本故障仍可用；
- 两个副本故障则不可写；
- 读也可能需要跨区。

Quorum 不是“越多越好”。N=5、W=3、R=3 能容忍两个故障，但延迟和成本更高。选择要与 SLO 和预算一起算。

### Z.6.4 Fencing token

故障转移时，旧主可能仍在处理请求（例如 GC 暂停后恢复）。如果新主已经开始服务，旧主的写会破坏数据。

解决方案：每次成为主时获取一个单调递增的 fencing token，所有写请求携带 token，存储层拒绝比已见 token 更小的写：

```text
旧主 token=41，暂停
新主 token=42，开始服务
旧主恢复，带 token=41 的写 → 被存储层拒绝
```

API 层不一定暴露 token，但内部写路径必须支持。对调用方可见的版本号也可以承担类似作用，但 fencing token 由基础设施生成，不依赖业务逻辑。

### Z.6.5 跨区域事件

写本地数据库与发跨区域事件不能靠“先写库再发消息”：

```text
写库成功 → 进程崩溃 → 事件丢失 → 其他区域永远不知道
```

用 Outbox：

```text
同一事务：
  insert order
  insert outbox(event)
异步发布器：
  读取 outbox → 发布 → 标记已发送
```

跨区域复制 outbox 时要注意：

- 事件 ID 全局唯一；
- 消费者幂等；
- 复制延迟计入契约；
- 事件顺序按聚合键；
- 失败进入 DLQ，不能静默丢弃。

## Z.7 读路径设计

### Z.7.1 本地读与陈旧度

本地读延迟低，但可能旧。契约应给出 **陈旧度上界**：

```text
商品价格：本地读，最多陈旧 30 秒
库存数量：本地读，最多陈旧 2 秒；下单时以主区域为准
订单状态：按 ID 读己之写；列表最多陈旧 5 秒
```

没有上界的“最终一致”无法验收。上界可以通过以下方式测量：

- 复制延迟指标（p50/p95/p99/max）；
- 读请求携带的副本版本与主版本差；
- 合成探针：写入带时间戳的探针记录，定期从各区域读；
- 客户端埋点：写后读的失败率与延迟。

### Z.7.2 读修复

当读发现副本落后：

- 同步等待复制（增加延迟）；
- 从主副本读（跨区）；
- 返回旧值 + `X-Data-Age`；
- 触发异步读修复。

选择取决于契约。对价格、库存等敏感数据，返回旧值可能造成资损；对推荐、计数等，返回旧值通常可接受。

### Z.7.3 缓存与一致性

跨区域缓存的失效比单区域更难：

```text
区域 A 更新 → 失效消息发到区域 B → B 的 CDN 仍缓存旧值
```

措施：

- 缓存键带版本或租户；
- 使用短 TTL 作为兜底；
- 失效消息走可靠通道，不依赖广播；
- 对强一致读绕过缓存；
- 返回 `Age`、`ETag`，让客户端参与条件请求；
- 监控缓存命中率与陈旧命中率。

第 16 章的条件请求语义在这里同样适用，但要注意：`ETag` 只能证明“表示没变”，不能证明“底层数据最新”。

## Z.8 故障转移与脑裂

### Z.8.1 故障检测本身不可靠

超时不等于对方死亡：可能只是网络慢、GC 暂停、交换机丢包。因此：

- 不要仅凭一次超时就切换主；
- 使用租约（lease）+ quorum 确认；
- 设置合理的故障检测窗口；
- 切主后旧主必须能被 fencing；
- 记录切换原因与时间线。

### Z.8.2 脑裂的代价

两个主同时接受写，会产生：

- 同一订单两条支付记录；
- 库存超卖；
- 用户看到互相矛盾的订单状态；
- 对账差异；
- 无法自动合并的审计链。

防脑裂的手段：

| 手段 | 作用 | 局限 |
|---|---|---|
| Quorum 选主 | 只有一个主获得多数派 | 少数派区域不可写 |
| Lease | 主在租约内有效 | 依赖时钟，需容错 |
| Fencing token | 拒绝旧主写 | 存储层必须支持 |
| Witness | 打破 2:2 平票 | 增加部署复杂度 |
| STONITH | 强制隔离旧主 | 运维风险 |

### Z.8.3 故障转移的契约语义

故障转移期间，API 应向调用方表达：

```http
HTTP/1.1 503 Service Unavailable
Retry-After: 30
```

```json
{
  "type": "https://api.example.com/problems/region-failover",
  "title": "区域切换中",
  "status": 503,
  "detail": "写操作暂时不可用，读操作可能返回最多 60 秒前的数据",
  "retryable": true,
  "region": "ap-east-1",
  "failoverId": "fo_20261126_01"
}
```

要点：

- 明确“写不可用”还是“读变旧”；
- 给出重试建议；
- 不要返回 `200` + 空结果，让调用方误以为数据不存在；
- 写请求必须幂等，否则切换期间的重试会重复；
- 故障恢复后要有对账，不能假设切换无损。

### Z.8.4 RPO 与 RTO 的契约化

| 承诺 | 含义 | 实现要求 |
|---|---|---|
| RPO=0 | 故障切换不丢已确认写 | 同步复制到故障域外，或 quorum + 可恢复的剩余副本 |
| RPO≤5s | 最多丢 5 秒写 | 异步复制 + 监控 |
| RTO≤1min | 1 分钟内恢复服务 | 自动切主、DNS/路由快速收敛 |
| RTO≤1h | 1 小时内恢复 | 半自动、人工确认 |

注意：RPO 只覆盖“已确认写”。如果客户端超时但服务端实际成功，故障切换后仍可能重复或丢失，需要幂等与对账兜底。

## Z.9 冲突解决

### Z.9.1 先避免冲突

最好的冲突解决是不产生冲突：

- 按租户/聚合分片，单写者；
- 把“并发修改”建模为显式操作（`reserve`、`cancel`），而不是整对象覆盖；
- 用事件表达意图，由单一所有者裁决；
- 对共享资源使用预订/锁/配额，而不是后写覆盖。

### Z.9.2 LWW 的陷阱

```json
{
  "id": "doc_1",
  "title": "A",
  "updatedAt": "2026-11-26T10:00:00.100Z"
}
```

LWW 看似简单，但：

- 依赖时钟，时钟回拨会丢更新；
- 同一毫秒内的并发写无法排序；
- 丢失的是“整个对象”，而不是冲突字段；
- 用户无法知道自己的修改被覆盖。

LWW 只适合“最后一次设置生效”的配置类数据，不适合订单、库存、金额、权限。

### Z.9.3 业务裁决

对关键资源，服务端应作为裁决者：

```text
库存扣减：reserve(quantity) → 成功/不足
座位锁定：lock(seat, ttl) → 成功/已被占
优惠券核销：redeem(code, user) → 成功/已使用
```

API 暴露的是“意图 + 结果”，而不是“把整个对象 PUT 上去”。这样冲突在业务层被显式处理，而不是在存储层被静默覆盖。

### Z.9.4 CRDT 与 OT

| 方案 | 适合 | 代价 |
|---|---|---|
| LWW-Register | 单值配置、最后设置生效 | 丢更新 |
| G-Counter / PN-Counter | 计数、点赞 | 只能增/减，语义有限 |
| OR-Set | 标签、集合 | 元数据增长 |
| RGA / Logoot / Yjs | 文本、列表 | 实现复杂、快照/GC |
| OT | 中心化文本编辑 | 变换函数复杂、需服务器 |

CRDT 保证收敛，不保证业务正确。比如“库存不能为负”不是 CRDT 能表达的约束；这类约束必须由单一写者或业务裁决保证。

### Z.9.5 删除与墓碑

跨区域删除需要墓碑：

- 删除事件必须复制；
- 墓碑保留时间要覆盖最大离线/复制延迟；
- 墓碑清理要有确认机制；
- 防止“删除后复活”；
- 合规删除要能传播到所有副本、备份、索引、缓存。

## Z.10 数据驻留与合规路由

多区域设计不仅是性能问题，也是法律问题。GDPR、数据本地化法规、行业监管可能要求：

- 数据不跨区存储；
- 日志、备份、密钥不跨区；
- 跨区支持访问需要审批与审计；
- 故障转移不能把数据带到不允许的区域。

### Z.10.1 契约字段

```json
{
  "dataRegion": "eu-central-1",
  "processingRegion": "eu-central-1",
  "allowedFailoverRegions": ["eu-west-1"],
  "residencyPolicy": "eu-only"
}
```

注意：

- `dataRegion` 是数据存储位置，`processingRegion` 是本次处理位置；
- 不要把区域字段暴露给无关调用方，避免信息泄露；
- 跨区故障转移前检查 `allowedFailoverRegions`；
- 如果无法在合规区域内恢复，宁可降级或不可用，也不要违规转移。

### Z.10.2 驻留与可用性的冲突

```text
要求：数据只存 EU；同时要求 99.99% 可用
现实：EU 单区域故障时，无法把数据切到 US
解决：EU 内多可用区 + 多区域（如 eu-central-1 / eu-west-1）
```

数据驻留要求会把“全球多活”变成“区域内多活”。这会提高成本，也会限制容量弹性。商业合同中的可用性承诺必须与驻留策略一起评审，不能由两个团队分别承诺。

## Z.11 测试与验证

### Z.11.1 故障注入

至少覆盖：

- 区域间网络分区；
- 单区域延迟升高；
- 时钟回拨/跳变；
- 进程暂停（SIGSTOP）；
- 磁盘变慢；
- 副本落后；
- 主节点崩溃；
- DNS 故障；
- 证书过期；
- 限流/配额耗尽。

### Z.11.2 一致性检查

- **线性一致性检查**：记录并发历史，用 Knossos/Jepsen 类工具检查是否存在合法线性化；
- **会话保证检查**：写后读、单调读、单调写、写跟随读的自动化测试；
- **不变量检查**：库存不为负、退款不超过支付、订单状态不回退；
- **对账**：跨区域按 ID 集合、金额总和、状态分布比对；
- **故障转移演练**：定期真实切主，记录 RTO、丢失写、重复写、告警时间线。

### Z.11.3 指标

| 指标 | 含义 | 告警 |
|---|---|---|
| replication_lag_seconds | 跨区复制延迟 | 超过契约上界 |
| cross_region_rps | 跨区请求比例 | 突增（路由错误） |
| failover_duration | 切主耗时 | 超过 RTO |
| conflict_rate | 冲突/合并比例 | 突增 |
| stale_read_rate | 陈旧读比例 | 超过预算 |
| split_brain_events | 脑裂检测 | 大于 0 |
| reconciliation_diff | 对账差异 | 大于 0 |

## Z.12 设计检查清单

- [ ] 一致性承诺写清了范围、操作、时间上界与例外。
- [ ] 区分了单对象一致性、跨对象一致性与会话保证。
- [ ] 写操作有幂等键，故障转移期间重试不会重复。
- [ ] 关键资源有唯一写权威，冲突在业务层裁决。
- [ ] 全局 ID 不依赖自增，不暴露写入位置。
- [ ] 跨区事件用 Outbox，消费者幂等。
- [ ] 读路径给出陈旧度上界，并有测量方式。
- [ ] 故障转移有 fencing token/租约，能阻止旧主写入。
- [ ] 切换期间返回明确的 503/降级语义，不返回伪 200。
- [ ] RPO/RTO 与复制方式、成本、合同一致。
- [ ] 数据驻留与故障转移区域已评审，不违规跨区。
- [ ] 有一致性测试、故障演练与对账，而不只有监控。
- [ ] 一致性降级有产品提示与补偿流程，不只靠工程兜底。

## Z.13 小结

- 一致性是 API 的时间承诺，不是数据库参数；必须写成可验证的句子。
- “强一致”太模糊；至少区分线性一致、顺序一致、因果一致、会话保证与最终一致。
- 大多数用户 API 用“会话粘性 + 版本令牌”就能满足读己之写与单调读，成本远低于全局线性一致。
- 不要相信客户端时间；并发裁决用版本号/序列号，不用 `updatedAt`。
- 多区域的核心问题是“每个键的写权威在哪里”，而不是“有几个区域”。
- 故障转移必须配合幂等、fencing、对账；否则“高可用”会变成“高质量地重复扣款”。
- 数据驻留会把全球多活降级为区域内多活，商业承诺必须与技术约束一起评审。
- 一致性只能通过故障注入、历史检查与对账证明，不能通过架构图证明。
