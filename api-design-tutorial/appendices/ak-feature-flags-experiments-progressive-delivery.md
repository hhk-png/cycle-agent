# 附录 AK：特性开关、实验与渐进发布

部署（deploy）是把代码放进运行环境；发布（release）是让消费者看见变化；实验（experiment）是比较两种变化谁更好。这三件事经常被混为一谈，于是团队用一次全量部署同时完成三者，再用回滚承担全部风险。

特性开关、渐进发布与实验工程，把“变更暴露”从部署中拆出来，变成一个可观测、可回滚、可度量的独立过程。对 API 而言，这一层尤其重要：消费者跨越组织边界，很多客户端无法强制升级，行为变化即使语法兼容也可能造成真实损失。开关可以让一个行为变更先影响 1% 的租户；实验可以回答“新分页大小是否真的降低了延迟”；kill switch 可以在依赖故障时几秒内关闭一条昂贵路径。

但开关不是免费的。每一个长期存在的开关都是一条分叉路径、一份测试矩阵、一个可能被遗忘的默认值。本章讨论如何把开关当作契约的一部分来设计，而不是把它当作“先上线再说”的遮羞布。

## AK.1 三个时间尺度

| 动作 | 问题 | 时间尺度 | 典型工具 | 失败代价 |
|---|---|---|---|---|
| 部署 | 代码是否在运行 | 分钟 | CI/CD、容器编排 | 可回滚 |
| 发布 | 消费者是否看见 | 秒到月 | 特性开关、流量切分 | 可能不可逆 |
| 实验 | 哪个方案更好 | 天到月 | 分流、曝光、指标 | 统计错误、公平性 |
| 弃用 | 旧路径何时消失 | 月到年 | 版本、Sunset、brownout | 客户流失、违约 |

关键区分：

- **部署不等于发布**：代码可以已经在生产，但开关关闭，消费者看不到。
- **发布不等于全量**：可以按租户、地区、客户端版本、百分比逐步放量。
- **实验不等于发布**：实验结束后要选一个方案并清理，而不是永久保留两个分支。
- **开关不等于版本**：版本是公开契约的长期分界；开关是临时行为控制。不要用开关隐藏破坏性 schema 变更。

## AK.2 开关的类型学

不是所有开关都一样。类型决定了生命周期、默认值、审批和测试策略。

| 类型 | 目的 | 典型生命周期 | 默认值 | 风险 |
|---|---|---|---|---|
| Release flag | 控制新功能可见性 | 天到周 | 关 | 长期残留、分支腐烂 |
| Experiment flag | 分流并比较效果 | 周到月 | 对照 | 污染、统计错误 |
| Ops / kill switch | 故障时关闭路径 | 长期 | 开（可关闭） | 失效、误关 |
| Permission flag | 按套餐/租户开放能力 | 长期 | 按合同 | 越权、计费错误 |
| Migration flag | 新旧路径切换 | 月 | 旧 | 双写不一致、清理遗漏 |
| Pricing flag | 控制价格/计量规则 | 长期 | 按合同 | 账单争议、审计 |

### Release flag

用于把“代码已部署”和“功能已发布”分开。它应该短命：功能全量后删除开关和旧路径。长期保留的 release flag 会变成事实上的版本，却没有版本的文档、弃用和测试。

### Experiment flag

用于 A/B 实验。它必须绑定实验 ID、目标指标、开始/结束时间和负责人。实验结束后，要么全量采用，要么删除；不要让它悄悄变成 release flag。

### Ops / kill switch

用于依赖故障、流量异常、成本失控时快速关闭一条路径。它通常长期存在，但必须：

- 默认安全（依赖故障时关闭，而不是打开）；
- 生效时间以秒计，而不是等配置缓存过期；
- 有独立于常规发布的开合权限；
- 有审计和演练。

### Permission flag

按套餐、合同、地区开放能力。它更接近授权而不是发布，应该由授权/计费系统提供事实来源，而不是散落在代码里的布尔值。否则销售承诺、账单和实际能力会不一致。

### Migration flag

用于新旧实现切换，例如读路径从旧表切到新表。它需要：

- 双写/回填；
- 读路径灰度和对账；
- 明确的回滚条件；
- 切换后删除旧路径的时间表。

### Pricing flag

控制价格、折扣、计量规则。它直接影响账单和收入确认，必须与计费系统、合同和审计对齐。不要用前端开关“临时改价”，否则对账时无法解释。

## AK.3 开关的契约语义

### 开关可能是公开契约

内部开关只影响实现；一旦开关改变 API 的响应、错误码、分页大小、限流或可用功能，它就成了契约的一部分。

需要区分：

- **服务端内部开关**：消费者不可见，只影响实现路径。可以自由使用，但仍要测试两条路径。
- **消费者可见开关**：响应字段、功能可用性、错误行为随开关变化。必须有文档、稳定的评估规则和变更通知。

消费者可见的开关至少要做到：

- 评估结果可解释：为什么这个租户看到了新行为？
- 评估是确定的：同一上下文多次评估结果一致；
- 评估上下文有明确维度：租户、用户、地区、套餐、客户端版本；
- 默认值安全：配置服务不可用时，退回兼容行为；
- 变更可观测：开关翻转后，错误率、延迟、业务指标可对比。

### 评估上下文与分桶

```json
{
  "flag": "orders.new-pagination",
  "context": {
    "tenantId": "t_123",
    "userId": "u_456",
    "region": "ap-east",
    "plan": "enterprise",
    "clientVersion": "3.8.1"
  },
  "defaultValue": false
}
```

分桶应该：

- 使用稳定哈希，如 `hash(flagKey + salt + unitId)`；
- 同一实验单元（用户/租户/密钥）始终落在同一桶；
- 分桶键与实验目标一致：租户级计费实验按租户分，界面实验按用户分；
- 分桶比例变更时，尽量保持已入组单元不变（可分层/可叠加哈希）；
- 记录盐值版本，避免换盐后用户跳组。

```python
import hashlib


def bucket(flag_key: str, unit_id: str, salt: str = "v1") -> int:
    digest = hashlib.sha256(f"{flag_key}:{salt}:{unit_id}".encode()).hexdigest()
    return int(digest[:8], 16) % 10000  # 0..9999


def is_enabled(flag_key: str, unit_id: str, rollout_bp: int) -> bool:
    # rollout_bp 以基点表示，10000 = 100%
    return bucket(flag_key, unit_id) < rollout_bp
```

### 默认值与失效模式

开关系统本身会故障。必须定义：

- 配置服务不可用时，使用本地缓存的最后已知值，还是代码默认值？
- 本地缓存多久过期？
- kill switch 是否走独立通道，避免与普通开关一起失效？
- 默认值是否安全：关闭新功能、保留旧行为、拒绝高风险操作？

一个常见事故是：配置服务故障，所有开关回退到“开”，于是未完成的新路径被全量暴露。默认值应该按开关类型分别设计，而不是统一为 `false` 或 `true`。

### 开关与版本

| 变更 | 用开关 | 用版本 |
|---|---|---|
| 新增可选字段 | 可以 | 不必 |
| 改变默认排序 | 可以，但需通知 | 更安全 |
| 删除字段 | 不可以 | 必须 |
| 改字段类型 | 不可以 | 必须 |
| 改认证方式 | 不可以 | 必须 |
| 改分页协议 | 谨慎 | 更安全 |
| 临时关闭昂贵功能 | 必须 | 不适用 |

原则：**开关控制行为，版本控制语法**。不要用开关让同一个 URL 在不同租户返回不同 schema；这会让客户端、缓存、SDK 和审计全部失效。

### 响应中的能力声明

如果功能按租户/套餐变化，最好显式返回能力，而不是让客户端猜：

```json
{
  "capabilities": {
    "bulkExport": true,
    "newPagination": false,
    "maxPageSize": 100
  },
  "capabilitiesVersion": "2026-11-01"
}
```

要求：

- 能力字段有稳定语义和文档；
- 能力变化走变更日志；
- 缓存键包含能力版本或租户；
- 客户端不要缓存能力过久；
- 能力声明与实际行为一致，不能只是营销文案。

## AK.4 渐进发布模式

| 模式 | 爆炸半径 | 回滚速度 | 适用 | 关键要求 |
|---|---|---|---|---|
| 暗发布（dark launch） | 零用户可见 | 快 | 验证容量/行为 | 影子流量、差分、无副作用 |
| 金丝雀（canary） | 小比例 | 快 | 大多数发布 | 流量切分、SLI、自动回滚 |
| 环形发布（ring） | 内部→设计伙伴→全量 | 中 | 高风险功能 | 明确环定义、退出标准 |
| 蓝绿（blue-green） | 全量切换 | 快 | 基础设施变更 | 双环境、数据兼容 |
| Brownout | 部分时间/租户不可用 | 快 | 弃用演练 | 提前通知、可恢复 |
| 按租户迁移 | 单租户 | 慢 | 企业客户、数据迁移 | 对账、回滚、白名单 |

### 暗发布

暗发布把新路径的流量复制一份给新实现，但不返回给用户：

```text
客户端 → 旧实现 → 响应
              ↘ 影子请求 → 新实现 → 记录差异（丢弃响应）
```

适合：

- 验证新实现的容量和延迟；
- 对比新旧响应结构；
- 在真实流量下发现边界情况。

风险：

- 影子请求可能有副作用（写库、发消息、扣款），必须确保只读或隔离；
- 影子流量会放大下游负载；
- 差异比较要忽略非确定性字段（时间、ID、排序）；
- 隐私与审计：影子数据不能泄露给未授权方。

### 金丝雀

按百分比、租户、Header 或客户端版本切流：

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata:
  name: orders-api
spec:
  replicas: 10
  strategy:
    canary:
      steps:
        - setWeight: 5
        - pause: { duration: 10m }
        - analysis:
            templates:
              - templateName: error-rate
        - setWeight: 25
        - pause: { duration: 30m }
        - setWeight: 100
      trafficRouting:
        nginx:
          stableIngress: orders-stable
```

自动分析应基于 SLI，而不是“Pod 是否 Ready”：

- 错误率；
- P95/P99 延迟；
- 超时率；
- 业务成功率（下单、支付、回调）；
- 依赖错误；
- 每条路径的成本。

金丝雀最常见的假阳性是：只把内部租户或测试账号放进金丝雀。内部流量模式与真实客户差异很大，金丝雀通过不代表真实流量通过。金丝雀样本应包含真实租户，且按租户/地区分层。

### 环形发布

```text
Ring 0：内部员工
Ring 1：设计伙伴/白名单
Ring 2：小客户/单地区
Ring 3：全量
```

每一环要有：

- 进入条件；
- 观察窗口；
- 退出标准；
- 回滚触发条件；
- 客户沟通模板。

### Brownout

Brownout 是在弃用前，按计划短暂关闭旧路径，让仍依赖它的消费者暴露出来：

```text
每周二 10:00–10:15 关闭旧端点
```

要求：

- 提前公告；
- 可随时恢复；
- 有错误提示和迁移链接；
- 记录受影响的调用方；
- 不要在客户关键业务期做。

### 按租户迁移

企业客户、数据迁移、合同约束下，常见做法是逐个租户切换：

- 租户白名单；
- 切换前对账；
- 切换后观察；
- 保留回滚窗口；
- 记录每个租户的状态、联系人和例外。

## AK.5 实验设计

### 实验单元

| 单元 | 适用 | 风险 |
|---|---|---|
| 请求 | 无状态、短时效果 | 同一用户看到不同结果，体验不一致 |
| 用户 | 界面、推荐 | 多设备/多会话可能不一致 |
| 租户 | 计费、配额、企业功能 | 样本量小，租户内污染 |
| API Key | 开发者工具、SDK | 同一组织多 Key 可能不一致 |
| 地区 | 合规、延迟 | 地区差异混杂 |

选择单元的原则：

- 与实验目标一致：计费实验按租户，界面实验按用户；
- 同一单元在实验期间稳定入组；
- 单元之间尽量独立，避免网络效应；
- 样本量足够，尤其是租户级实验。

### 指标

每个实验至少定义：

- **主要指标**：要提升什么；
- **护栏指标**：不能变坏什么（错误率、延迟、退款率、投诉率）；
- **反向指标**：短期提升但长期有害（如强制更多调用、增加客诉）；
- **成本指标**：单位调用成本、下游成本。

API 实验常见指标：

- 成功率、错误率；
- P50/P95/P99 延迟；
- 重试率；
- 分页请求数；
- 每次任务的总调用数；
- Token/流量消耗；
- 支持工单；
- 收入/转化。

### API 特有的实验陷阱

- **缓存串味**：CDN 或网关按 URL 缓存，未把实验变体纳入缓存键，导致 A 组看到 B 组结果。
- **重试双曝光**：一次用户操作重试多次，曝光被重复计数。
- **共享租户**：同一租户内不同用户被分到不同组，协作场景体验割裂。
- **长连接**：WebSocket/SSE 建立后长期不重新评估开关，实验组与实现不一致。
- **Webhook**：事件载荷随开关变化，消费者未适配。
- **SDK 版本**：客户端 SDK 缓存了旧的能力声明。
- **异步任务**：任务创建时在 A 组，完成时开关已变，结果按 B 组处理。
- **计量与计费**：实验改变调用次数，直接影响账单和收入确认。

### 曝光与统计

- 曝光日志要记录：实验 ID、变体、单元 ID、时间、上下文、是否首次曝光；
- 分析时按“首次曝光”分组，避免重试和重复请求污染；
- 检查样本比例失衡（SRM）：实际分流比例与配置比例是否显著不同；
- 预先注册主要指标和分析方法，避免事后挑指标；
- 顺序检验或多重比较要校正；
- 实验结束要有明确的决策记录：采用、放弃、继续。

### 定价与计费实验

这类实验风险最高：

- 可能违反合同或监管；
- 不同租户看到不同价格，可能构成歧视；
- 账单必须可解释、可审计；
- 实验期间产生的账单不能“事后重算”；
- 需要法务、财务、客服提前知情；
- 护栏指标包括退款率、投诉率、流失率，而不只是收入。

建议：定价实验优先在“新客户/新套餐”上做，避免改变既有客户的已承诺价格；如果必须对既有客户做，要有合同依据和退出机制。

## AK.6 开关、缓存与一致性

### 缓存键

开关影响响应时，缓存键必须包含变体：

```text
key = path + query + tenant + variant + capabilitiesVersion + Accept-Language
```

或者在响应中使用：

```http
Vary: X-Experiment-Variant, Accept-Language, Authorization
Cache-Control: private, max-age=60
```

注意：

- `Vary: Authorization` 会让缓存几乎失效，通常应使用租户级缓存而不是共享缓存；
- CDN 边缘可能不支持复杂的变体键；
- 实验变体变化后，旧缓存要能失效；
- 不要在共享缓存中缓存按用户分桶的响应。

### 配置传播

- 开关从控制面到数据面的传播延迟要可观测；
- 关键 kill switch 应该有独立通道和更短的传播时间；
- 本地缓存要有上限和过期；
- 配置变更要有版本号和审计；
- 数据面要能报告“当前生效的配置版本”。

### 开关与数据迁移

扩展—收缩（expand-contract）比开关更适合 schema 变更：

```text
1. 扩展：新增字段/表，双写
2. 迁移：回填，读路径切换（可用开关）
3. 收缩：删除旧字段/表
```

开关只能控制“读哪条路径”，不能替代数据库迁移的顺序。先删旧字段再关开关，会导致回滚失败。

### 事件与 Webhook

如果事件载荷随开关变化：

- 事件 schema 要版本化；
- 消费者必须能处理新旧版本；
- 不要让同一订阅在实验期间收到结构不同的载荷而不标注版本；
- 事件 ID、幂等键和顺序语义不能因开关而变。

## AK.7 开关治理

### 命名

建议采用可搜索、可归属的命名：

```text
release.orders.new-pagination.2026-11
experiment.checkout.one-click.2026-10
ops.killswitch.payment-provider-a
permission.plan.enterprise.bulk-export
migration.orders.read-from-v2
pricing.invoice.rounding-mode
```

命名应包含：

- 类型；
- 领域/服务；
- 功能；
- 日期或实验 ID（便于清理）。

### 生命周期

```text
提议 → 评审 → 创建 → 灰度 → 全量/放弃 → 清理
```

每个开关要有：

- 负责人；
- 创建原因；
- 目标清理日期；
- 关联的 issue/实验；
- 当前状态；
- 依赖它的代码位置。

### 清理

长期开关是技术债。清理机制：

- 开关目录定期扫描超过 N 天的 release/experiment flag；
- 自动创建“删除开关”的 PR；
- 删除前确认全量或已放弃；
- 删除旧路径和旧测试；
- 保留历史记录，便于审计。

### 权限与审计

- 谁能创建/修改/删除开关？
- 谁能翻转 kill switch？
- 高风险开关是否需要双人审批？
- 开关变更是否进入审计日志？
- 是否记录变更前后的值、操作者、原因、工单？
- 是否有自动化回滚？

kill switch 的权限应该与常规发布分离：值班工程师应该能在事故中关闭一条路径，而不需要等完整发布流程；但关闭动作必须被记录和复盘。

### 测试

每个开关至少测试：

- 开/关两条路径；
- 默认值；
- 配置服务不可用；
- 分桶边界（0%、100%、中间值）；
- 与缓存、异步、Webhook 的组合；
- 开关切换过程中的并发请求；
- 清理后旧路径确实不可达。

测试矩阵不要爆炸：用成对组合和关键路径覆盖，而不是所有开关的笛卡尔积。

## AK.8 事故复盘

### 案例一：kill switch 没有生效

**经过**：支付渠道故障，值班工程师关闭 kill switch，但配置缓存 TTL 为 5 分钟，期间仍持续调用故障渠道，错误率继续上升。

**根因**：kill switch 与普通开关共用配置通道和缓存；没有独立的快速通道；没有验证生效时间。

**修复**：kill switch 使用独立通道和短 TTL；数据面定期上报生效配置版本；每季度演练关闭并测量生效时间。

### 案例二：金丝雀只覆盖内部租户

**经过**：新分页逻辑在金丝雀环境运行 2 小时无错误，全量后大客户出现超时。内部租户数据量小，未触发深分页。

**根因**：金丝雀样本不代表真实流量；没有按租户规模分层；没有深分页压测。

**修复**：金丝雀包含不同规模的真实租户；增加按数据量分层的分析；发布前用生产规模数据做影子测试。

### 案例三：默认值翻转

**经过**：配置服务故障，所有开关回退到代码默认值，而新功能的默认值是 `true`，导致未完成的功能被全量暴露。

**根因**：默认值没有按开关类型设计；缺少配置服务故障演练。

**修复**：release flag 默认 `false`；kill switch 默认 `true`（保持可用）；增加配置服务故障的混沌测试。

### 案例四：实验污染计费

**经过**：一个“减少分页请求”的实验改变了默认页大小，实验组调用次数下降，但按调用计费的客户账单异常，客户投诉。

**根因**：实验只看了延迟指标，没有把计费作为护栏；实验变体影响了计量口径。

**修复**：涉及计量的实验必须经过财务评审；护栏指标包含账单异常；实验期间对受影响租户出具说明。

### 案例五：清理开关删除了兼容路径

**经过**：一个两年前的 release flag 被清理，旧路径删除。一个仍在使用旧客户端的大客户开始收到 400。

**根因**：清理前只检查了“开关是否全量”，没有检查旧客户端和旧路径的实际调用；没有弃用流程。

**修复**：清理前做调用方盘点；旧路径走正式弃用；保留至少一个弃用周期的兼容层。

### 案例六：Webhook 变体未标注

**经过**：实验改变了事件载荷字段名，消费者按旧字段解析失败，重试风暴。

**根因**：事件 schema 没有版本化；实验变体直接改变了公开事件；消费者没有兼容策略。

**修复**：事件 schema 版本化；实验不改变公开事件结构；消费者必须忽略未知字段并处理版本。

## AK.9 工具与最小实现

### 工具类别

| 用途 | 工具 |
|---|---|
| 开关/实验平台 | LaunchDarkly、Unleash、Flagsmith、Split、GrowthBook |
| 标准化 SDK | OpenFeature |
| 渐进交付 | Argo Rollouts、Flagger |
| 流量切分 | 网关、服务网格、Ingress |
| 实验分析 | 自建数仓、Amplitude、Statsig |
| 审计/策略 | OPA、审计日志、工单系统 |

### 最小可行实现

如果不想引入商业平台，最小实现需要：

```sql
CREATE TABLE feature_flags (
  key            text PRIMARY KEY,
  type           text NOT NULL,          -- release/experiment/ops/permission
  enabled        boolean NOT NULL,
  rollout_bp     integer NOT NULL DEFAULT 0,  -- 0..10000
  salt           text NOT NULL,
  owner          text NOT NULL,
  expires_at     timestamptz,
  updated_at     timestamptz NOT NULL,
  updated_by     text NOT NULL,
  reason         text
);

CREATE TABLE feature_flag_audit (
  id         bigserial PRIMARY KEY,
  key        text NOT NULL,
  old_value  jsonb,
  new_value  jsonb,
  actor      text NOT NULL,
  reason     text,
  created_at timestamptz NOT NULL DEFAULT now()
);
```

加上：

- 本地缓存 + 版本号；
- 定期拉取或流式推送；
- 评估日志（采样）；
- kill switch 独立通道；
- 过期提醒；
- 管理 API 的鉴权和审计。

### 代码示例

```python
from openfeature import api
from openfeature.evaluation_context import EvaluationContext


client = api.get_client("orders-api")

ctx = EvaluationContext(
    targeting_key=tenant_id,
    attributes={
        "region": region,
        "plan": plan,
        "clientVersion": client_version,
    },
)

if client.get_boolean_value("release.orders.new-pagination", False, ctx):
    return paginate_v2(...)
return paginate_v1(...)
```

注意默认值：第三个参数是配置服务不可用时的回退值。它必须与开关类型匹配。

## AK.10 决策表

| 需求 | 选择 |
|---|---|
| 新功能逐步可见 | Release flag + 金丝雀 |
| 比较两种实现的效果 | Experiment flag + 曝光日志 |
| 依赖故障时快速关闭 | Kill switch + 独立通道 |
| 按套餐开放能力 | Permission flag + 授权/计费事实源 |
| 新旧存储切换 | Migration flag + 双写/回填/对账 |
| 修改价格/计量 | Pricing flag + 财务/法务评审 |
| 删除字段/改类型 | 新版本，不用开关 |
| 改认证方式 | 新版本 + 弃用流程 |
| 基础设施切换 | 蓝绿/金丝雀 + 数据兼容 |
| 弃用旧端点 | Sunset + brownout + 迁移看板 |

## AK.11 反模式

- 用开关隐藏破坏性变更；
- 开关长期不清理，代码里布满死分支；
- 默认值不安全，配置故障时全量暴露；
- kill switch 与普通开关共用慢通道；
- 金丝雀只覆盖内部租户；
- 实验没有护栏指标；
- 实验改变计费但不通知财务；
- 缓存键不含实验变体，A/B 串味；
- 重试导致重复曝光；
- 开关翻转没有审计；
- 任何人可以关闭 kill switch；
- 测试只覆盖默认分支；
- 把“开关全量”当作“可以删除旧路径”；
- 用实验永久保留两套产品逻辑。

## AK.12 检查清单

- [ ] 区分部署、发布、实验和弃用，不用一次全量部署完成所有事。
- [ ] 每个开关有类型、负责人、创建原因和目标清理日期。
- [ ] Release/experiment flag 默认关闭；kill switch 默认保持可用。
- [ ] 分桶稳定、可解释，记录盐值和分桶单元。
- [ ] 开关影响响应时，缓存键包含变体，且不跨租户泄露。
- [ ] Kill switch 有独立通道，生效时间可测量，定期演练。
- [ ] 渐进发布有 SLI、观察窗口、自动/手动回滚条件。
- [ ] 金丝雀包含真实租户，按规模/地区分层。
- [ ] 实验预先注册主要指标、护栏指标和分析方法。
- [ ] 曝光日志记录首次曝光，检查样本比例失衡。
- [ ] 涉及计费/定价的实验经过财务、法务评审。
- [ ] 开关变更进入审计日志，高风险操作双人审批。
- [ ] 两条分支都有测试，包括默认值和配置故障。
- [ ] 过期开关有扫描和自动清理机制。
- [ ] 清理旧路径前完成调用方盘点和弃用流程。
- [ ] 事件/Webhook 的 schema 版本化，实验不改变公开结构。

## AK.13 小结

- 部署、发布、实验、弃用是四个不同的问题，需要不同的工具和时间尺度。
- 开关有类型：release、experiment、ops、permission、migration、pricing；类型决定生命周期和风险。
- 开关一旦改变消费者可见行为，就成为契约的一部分，需要文档、确定性和可观测性。
- 开关控制行为，版本控制语法；不要用开关隐藏破坏性变更。
- 渐进发布从暗发布、金丝雀、环形到 brownout，核心是控制爆炸半径和快速回滚。
- 实验要预先定义指标、稳定分桶、记录曝光，并警惕缓存、重试、异步和计费污染。
- 开关治理的关键是命名、所有权、过期、审计和清理。
- 最好的开关是已经删除的开关；长期存在的开关就是技术债。

## 设计练习

为一个“企业 SaaS 的权限与计费 API”设计发布方案：

- 新版权限模型按租户灰度；
- 新计费单位按套餐开放；
- 一次价格调整需要 A/B 对比；
- 支付渠道故障时需要快速关闭；
- 旧权限字段需要 18 个月弃用；
- 事件载荷不能破坏消费者。

回答：

1. 哪些变更用开关，哪些必须用版本？
2. 权限开关的事实来源应该是授权系统还是开关平台？
3. 价格实验如何避免账单争议？
4. Kill switch 的生效时间如何测量和演练？
5. 旧权限字段的弃用与开关清理如何协同？
6. 如何证明实验组和对照组的缓存没有串味？
