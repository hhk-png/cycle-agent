# 附录 U：API 事故复盘集——十二个失败模式

> 下面的案例是**复合案例**：它们由公开事故复盘中反复出现的模式改写、合并与匿名化而成，不指向任何具体公司或真实系统。目的不是讲故事，而是训练一种能力：从“接口看起来正常”里看见失败链。

每个案例按同一结构展开：

```text
背景 → 触发 → 失败链 → 影响 → 监控为什么没拦住 → 设计修复 → 可迁移的教训
```

## U.1 新增枚举值，客户端整页崩溃

### 背景

订单 API 返回 `status`，文档列出 `PENDING`、`PAID`、`SHIPPED`、`CANCELLED`。移动端用严格枚举解析，未知值直接抛异常并显示错误页。

### 触发

后端为“部分退款”新增 `PARTIALLY_REFUNDED`。字段类型没变，OpenAPI 也没标 breaking，后端测试全绿。

### 失败链

1. 服务端开始返回新值；
2. 旧版移动端解析失败；
3. 首页订单列表整体渲染失败；
4. 用户看到空白页，重试无效；
5. 客服收到大量“订单消失”投诉。

### 影响

旧版客户端用户无法查看订单；回滚服务端会丢失新功能；强制升级需要应用商店审核与用户配合。

### 监控为什么没拦住

- 服务端指标只看 5xx，响应是 200；
- 没有按客户端版本统计解析错误；
- 契约测试只覆盖已知枚举，没有“未知值”用例；
- 移动端没有把解析失败上报为可观测事件。

### 设计修复

- 枚举在契约中声明“客户端必须容忍未知值”；
- 服务端提供 `status` 的稳定分类字段（如 `statusGroup: OPEN | CLOSED`），新值不改变分类；
- 客户端采用宽容读取：未知值降级展示，不整页崩溃；
- 发布前用旧版客户端做契约回放测试；
- 新枚举先灰度到内部/测试租户，观察客户端错误率。

### 可迁移的教训

**新增枚举值在语法上兼容，在行为上可能是破坏性的。** 契约要规定未知值处理，测试要覆盖未知值，监控要能按消费者版本看错误。

## U.2 超时 + 重试 + 无抖动 = 重试风暴

### 背景

订单服务调用库存服务，客户端超时 1 秒，失败重试 3 次；库存服务 P99 在高峰期达到 1.2 秒。

### 触发

一次数据库慢查询让库存服务延迟整体上升。

### 失败链

1. 客户端 1 秒超时，触发重试；
2. 重试没有退避与抖动，所有客户端同时重试；
3. 库存服务请求量瞬间放大 4 倍；
4. 连接池耗尽，延迟进一步上升；
5. 更多请求超时，形成正反馈；
6. 故障从库存扩散到订单、支付、网关。

### 影响

下单主链路不可用；重试还放大了数据库负载，恢复时间被拉长。

### 监控为什么没拦住

- 只看平均延迟，没看 P99 与超时率；
- 没有“重试放大系数”指标；
- 告警只在错误率超过阈值时触发，而超时被记为客户端错误；
- 没有依赖级的熔断。

### 设计修复

- 重试预算：重试次数 / 总请求比例设上限；
- 指数退避 + 抖动；
- 只在幂等且可重试的错误上重试；
- 熔断与舱壁，防止故障扩散；
- 超时预算从入口向下分配，下游超时小于上游剩余预算；
- 服务端返回 `Retry-After`，客户端尊重；
- 压测时注入延迟，验证重试行为。

### 可迁移的教训

**重试是放大器，不是修复。** 没有预算、退避、抖动与熔断的重试，会把单点故障变成系统性故障。

## U.3 幂等键作用域错误，重复扣款

### 背景

支付 API 要求 `Idempotency-Key`。实现把 key 存在全局 Redis，TTL 24 小时。

### 触发

两个不同租户的客户端都生成了 `order-2026-11-26-001` 作为 key，但请求内容不同。

### 失败链

1. 租户 A 用该 key 创建支付，成功；
2. 租户 B 用相同 key 创建另一笔支付；
3. 服务端发现 key 已存在，直接返回租户 A 的响应；
4. 租户 B 认为支付成功，实际未扣款；
5. 或者反向：服务端检测到内容不同，返回 409，但客户端已重试多次。

### 影响

资金状态与订单状态不一致；对账出现缺口；客户投诉。

### 监控为什么没拦住

- 幂等命中率没有按租户/操作拆分；
- 没有“同 key 不同请求指纹”的告警；
- 支付成功指标只看 API 返回，不看资金流水。

### 设计修复

- 幂等键作用域至少是 `(tenant_id, operation, key)`；
- 存储请求指纹（方法、路径、关键 body 的规范化哈希）；
- 同 key 不同指纹返回明确错误，不返回旧响应；
- 幂等记录与业务写入同事务，避免“记录了但没执行”；
- 对账任务比对 API 成功记录与资金流水。

### 可迁移的教训

**幂等键不是全局唯一字符串，而是一个带作用域与请求指纹的协议。** 任何省略作用域的“简化”都会在多方租户环境下变成资金事故。

## U.4 Offset 分页漂移，报表少算订单

### 背景

订单列表用 `offset` + `limit` 分页，默认按 `created_at DESC` 排序。对账脚本按页拉取当天订单。

### 触发

对账期间有新订单持续创建，且 `created_at` 有重复值。

### 失败链

1. 脚本拉第 1 页（offset 0）；
2. 新订单插入到前面；
3. 第 2 页（offset 100）整体后移，部分旧订单被跳过；
4. 排序键重复导致顺序不稳定，部分订单重复出现；
5. 报表少算或多算，金额对不上。

### 影响

财务对账差异；重复退款或漏退款；审计问题。

### 监控为什么没拦住

- API 返回 200，没有错误；
- 对账脚本只校验总数，没校验 ID 集合；
- 没有分页一致性测试。

### 设计修复

- 对账/导出使用游标或 keyset 分页，排序键包含唯一 tie-breaker（如 `created_at, id`）；
- 游标绑定快照时间或过滤条件；
- 导出使用一致性快照；
- 对账比对 ID 集合与金额总和，而不只是数量；
- 契约写明“分页不保证跨页一致性”或“提供快照游标”。

### 可迁移的教训

**Offset 分页在数据变化时会重复/遗漏。** 对账、导出、审计类场景必须用稳定排序 + 游标 + 快照。

## U.5 Webhook 没有防重放，攻击者伪造发货

### 背景

电商平台向商户发送 `order.paid` Webhook。签名使用 HMAC，但只签了 body，没有时间戳与事件 ID 去重。

### 触发

攻击者截获一次合法 Webhook，原样重放 100 次。

### 失败链

1. 商户验签通过（body 没变）；
2. 商户把每次投递当成新事件；
3. 重复发货 100 次；
4. 库存与物流成本损失；
5. 商户认为是平台重复推送，平台认为是商户没去重。

### 影响

直接资金与库存损失；双方信任受损。

### 监控为什么没拦住

- 平台只监控投递成功率，不监控重复率；
- 商户没有事件 ID 去重；
- 签名没有时间戳，无法判断新鲜度；
- 没有重放告警。

### 设计修复

- 签名覆盖 timestamp + event ID + body；
- 接收方校验时间窗（如 5 分钟）并拒绝过期；
- 接收方按 event ID 幂等去重，保留窗口大于最大重试周期；
- 平台提供事件 ID、投递 ID、重试次数与签名版本；
- 双方约定重放/重复的处理语义；
- 监控重复事件率与验签失败率。

### 可迁移的教训

**Webhook 的签名只证明“来源”，不证明“新鲜”与“只此一次”。** 防重放需要时间戳、事件 ID、接收方去重三者配合。

## U.6 缓存键缺少租户，跨租户数据泄露

### 背景

SaaS 的订单详情接口用 Redis 缓存，key 为 `order:{orderId}`。

### 触发

两个租户恰好使用了相同的业务订单号 `ORD-1001`。

### 失败链

1. 租户 A 查询 `ORD-1001`，结果写入缓存；
2. 租户 B 查询自己的 `ORD-1001`，命中租户 A 的缓存；
3. 返回了租户 A 的订单详情；
4. 缓存 TTL 内持续泄露；
5. 直到某次数据对不上才被发现。

### 影响

跨租户数据泄露；合规事件；客户信任损失。

### 监控为什么没拦住

- 缓存命中率是“好指标”，没有按租户校验；
- 响应 200，没有异常；
- 没有对象级授权的集成测试；
- 日志没有记录缓存 key 与租户。

### 设计修复

- 缓存 key 必须包含租户/权限域：`t:{tenantId}:order:{orderId}`；
- 读缓存前做对象级授权，或把授权结果编码进 key；
- 缓存值包含租户 ID，读取时校验；
- 集成测试覆盖“同 ID 不同租户”；
- 监控跨租户缓存命中异常。

### 可迁移的教训

**多租户系统里，任何缓存、索引、队列、搜索、限流的 key 都必须带租户维度。** 只带资源 ID 的 key 是定时炸弹。

## U.7 JWT 算法混淆，攻击者伪造管理员

### 背景

API 用 JWT 认证，支持 RS256，但校验库配置为“按 token 的 `alg` 选择验证方式”。

### 触发

攻击者拿到公钥，构造 `alg: HS256` 的 token，用公钥作为 HMAC 密钥签名。

### 失败链

1. 服务端按 token 的 `alg` 选择 HS256；
2. 用公钥验签，攻击者的签名通过；
3. 攻击者在 payload 里写 `role: admin`；
4. 服务端信任 payload，授予管理员权限；
5. 数据被导出/篡改。

### 影响

完全认证绕过；严重数据泄露。

### 监控为什么没拦住

- 认证成功日志正常；
- 没有校验 `alg` 白名单；
- 没有异常 token 签发来源告警；
- 权限变更没有二次审计。

### 设计修复

- 服务端固定允许的算法，忽略 token 的 `alg` 选择；
- 校验 `iss`、`aud`、`exp`、`kid`，并使用可信 JWKS；
- 不把角色/权限完全放在客户端可伪造的 payload 里，或使用签名+短 TTL+服务端校验；
- 关键操作二次授权；
- 监控异常签发、异常 `kid`、异常地理/频率。

### 可迁移的教训

**JWT 的安全边界在验证配置，不在 token 格式。** 算法白名单、audience、issuer、密钥轮换，一个都不能省。

## U.8 URL 导入功能变成 SSRF 跳板

### 背景

图片 API 支持 `POST /images/import { "url": "..." }`，服务端下载后转存。

### 触发

攻击者传入 `http://169.254.169.254/latest/meta-data/iam/security-credentials/`。

### 失败链

1. 服务端直接请求用户提供的 URL；
2. 命中云元数据服务，拿到临时凭证；
3. 攻击者用凭证访问对象存储/其他服务；
4. 数据泄露或资源被滥用。

### 影响

云账号凭证泄露；数据泄露；可能横向移动。

### 监控为什么没拦住

- 出网请求没有集中审计；
- 没有私网/元数据地址拦截；
- 下载失败/成功没有异常模式告警；
- 没有限制重定向与 DNS 解析。

### 设计修复

- 出网 allowlist，默认拒绝；
- 拦截私网、回环、链路本地、元数据地址；
- DNS 解析后校验 IP，防 DNS 重绑定；
- 禁止或限制重定向，每一跳都校验；
- 使用独立的出网代理/沙箱，最小权限；
- 不在元数据服务上授予过高权限（IMDSv2、最小角色）；
- 记录完整出网审计。

### 可迁移的教训

**任何“让服务器替你访问 URL”的功能都是 SSRF 入口。** 防护要在解析后、连接前、重定向每一跳都做。

## U.9 GraphQL 复杂度攻击，数据库被打满

### 背景

GraphQL 网关暴露订单、用户、商品，支持嵌套关联。没有深度/复杂度限制。

### 触发

攻击者构造一个深度嵌套、带大量别名的查询。

### 失败链

1. 查询通过语法校验；
2. 每个嵌套字段触发 N+1 查询；
3. 数据库连接池耗尽；
4. 其他接口超时；
5. 整个 API 不可用。

### 影响

全站性能故障；可能产生高额数据库账单。

### 监控为什么没拦住

- 只看 HTTP 错误率，GraphQL 返回 200；
- 没有按查询复杂度/解析字段数监控；
- 没有单查询成本上限；
- 没有识别异常客户端。

### 设计修复

- 查询深度、复杂度、别名数量、字段数量限制；
- 持久化查询/allowlist；
- DataLoader 批量加载，避免 N+1；
- 单查询超时与成本预算；
- 按客户端/租户限流；
- 监控慢查询与高成本查询。

### 可迁移的教训

**GraphQL 把“查询成本”交给了客户端，服务端必须把成本控制拿回来。** 深度、复杂度、分页、超时、限流缺一不可。

## U.10 批量导入一个大事务，锁库八小时

### 背景

导入接口把 50 万行放在一个数据库事务里，逐行校验、逐行插入。

### 触发

客户上传了一个 50 万行的 CSV。

### 失败链

1. 事务持有大量行锁；
2. 其他读写被阻塞；
3. 连接池被占满；
4. 导入越来越慢；
5. 运维不敢杀事务，怕回滚更久；
6. 业务停摆数小时。

### 影响

全租户不可用；数据可能部分回滚；支持工单爆发。

### 监控为什么没拦住

- 导入接口有自己的超时，但数据库锁等待没有告警；
- 没有“单事务行数/时长”指标；
- 没有导入并发限制；
- 没有试运行/分片机制。

### 设计修复

- 导入走异步任务，分片提交；
- 每批 500～5,000 行，短事务；
- 先校验到 staging，再批量合并；
- 单租户导入并发限制；
- 锁等待、事务时长、复制延迟告警；
- 提供取消与回滚策略；
- 大客户走离线/专用通道。

### 可迁移的教训

**批量不是“更大的事务”，而是“可恢复的管线”。** 事务越大，失败成本越高，锁的影响越广。

## U.11 弃用直接硬切断，合作伙伴集体失效

### 背景

v1 接口标记弃用 90 天，文档写了，但没有逐个通知，也没有监控旧版本调用方。

### 触发

第 91 天，网关直接拒绝 v1 请求。

### 失败链

1. 仍在使用 v1 的合作伙伴请求全部 410；
2. 对方没有收到直接通知，只有文档变更；
3. 对方的发布流程需要数周；
4. 业务中断，合同纠纷；
5. 团队紧急回滚，但回滚本身也有风险。

### 影响

合作伙伴业务中断；收入损失；信任受损。

### 监控为什么没拦住

- 没有按 API key/租户统计版本使用；
- 弃用响应头没有被调用方处理；
- 没有“仍在使用弃用版本”的运营清单；
- 弃用决策没有 owner 与升级路径。

### 设计修复

- 弃用前先盘点所有消费者；
- 直接通知（邮件、控制台、工单），不只改文档；
- 提供迁移指南、兼容层、沙箱与时间表；
- `Deprecation`/`Sunset` 响应头 + 使用量报表；
- Brownout（短时不可用演练）而非突然硬切；
- 对关键合作伙伴做联合迁移；
- 设定“无流量后才下线”的门槛。

### 可迁移的教训

**弃用是一个运营项目，不是一次代码删除。** 没有消费者清单与迁移支持的弃用，等同于单方面违约。

## U.12 金额单位从分改成元，静默少算 100 倍

### 背景

订单 API 的 `amount` 一直是整数分。新团队为了“更直观”，把字段改成 decimal 元，字段名不变。

### 触发

新版本发布，部分服务升级，部分未升级。

### 失败链

1. 新服务返回 `"amount": 12.90`；
2. 旧客户端按“分”解析，得到 12.9 分或直接截断；
3. 报表金额缩小 100 倍；
4. 监控没有业务语义校验；
5. 财务对账时才发现。

### 影响

收入少算；退款金额错误；报表与合同不一致。

### 监控为什么没拦住

- HTTP 200，schema 仍是 number；
- 没有“金额量级”异常检测；
- 契约没有单位说明；
- 没有跨版本对账。

### 设计修复

- 金额字段显式命名与文档：统一使用 `{ "amount": 1290, "currency": "CNY" }`（最小单位整数），不要混用 `amountMinor`、`scale` 或金额字符串；
- 契约写明单位、精度、舍入规则；
- 变更单位视为破坏性变更，必须新字段/新版本；
- 对账监控金额总量与量级；
- 跨版本契约测试覆盖金额解析。

### 可迁移的教训

**字段类型不变，语义变化同样致命。** 金额、时间、百分比、枚举、排序默认值，都是“语义契约”的一部分。

## U.13 复盘模板

一次好的复盘不是“谁犯了错”，而是“系统为什么允许这个错误发生，以及如何让它更难发生”。

```markdown
# 事件复盘：<标题>

## 摘要
- 时间线（UTC）
- 影响范围（租户、请求、金额、数据）
- 持续时间
- 严重级别

## 触发与根因
- 直接触发
- 促成条件（设计、监控、流程、组织）
- 为什么现有防护没有生效

## 时间线
| 时间 | 事件 | 负责人 |
|---|---|---|

## 影响
- 客户影响
- 财务影响
- 合规影响
- 信任影响

## 检测与响应
- 如何发现
- 为什么没有更早发现
- 响应中的有效/无效动作

## 修复
- 立即修复
- 短期防护
- 长期设计变更
- 负责人/截止日期

## 可迁移的教训
- 哪些其他系统有同样模式？
- 需要新增/修改的契约、测试、监控、runbook？
```

## U.14 复盘检查清单

- [ ] 时间线使用统一时区，关键决定有负责人。
- [ ] 区分直接触发、根因与促成条件。
- [ ] 影响包含客户、财务、合规与信任，而不只是请求数。
- [ ] 解释“为什么监控/测试/评审没拦住”。
- [ ] 修复分为立即、短期、长期，并有 owner 与日期。
- [ ] 找到同类系统，避免只修一个点。
- [ ] 把新发现变成契约测试、告警或 runbook。
- [ ] 复盘文档可被未来的人读懂，不依赖当事人记忆。

## U.15 小结

- 事故往往不是“某个字段写错”，而是契约、客户端、监控、流程共同失效。
- 枚举、金额、时间、分页、幂等、缓存键、Webhook、认证、SSRF、批量、弃用，是最常见的失败面。
- 监控要看业务语义与消费者行为，不能只看 HTTP 状态码。
- 修复要同时考虑契约、实现、测试、监控与运营。
- 复盘的产出不是“以后注意”，而是可验证的变更。

## 设计练习

从上面选一个案例，替换成你自己的系统：

1. 同样的失败链在你的系统里是否可能存在？
2. 哪个监控指标会最先发现？如果没有，补什么？
3. 哪个契约条款可以阻止它？如果没有，怎么加？
4. 如果明天发生，你的 30 分钟/2 小时/24 小时动作是什么？
5. 写一个能在 CI 中运行的回归测试。
