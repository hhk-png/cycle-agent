# 附录 AJ：沙箱、Mock 与测试数据工程

一个 API 的质量不只在生产环境里被检验，也在它被第一次调用之前被检验。

开发者在拿到密钥后的十分钟内，需要一个不产生真实后果的地方理解契约；CI 在每次提交时，需要一个可重复、可注入故障的对手；合作伙伴在联调时，需要一条能走通成功、失败、超时、重复和异步回调的完整路径；Agent 在获得写权限之前，需要先在安全副本上证明它能完成任务。沙箱、Mock 与测试数据，就是把“契约”从文档变成可操作事实的基础设施。

这一层经常被当作“演示环境”草草搭建，结果是：文档里的示例能跑，真实集成却处处失败；Mock 永远返回 200，CI 永远绿色；沙箱里的数据互相污染，测试只能按固定顺序执行；测试密钥能打到生产，或者生产数据被脱敏后放进沙箱却无人审计。本章把沙箱当作一个需要设计的 API 产品，而不是一个附属页面。

## AJ.1 沙箱不是演示环境

演示环境的目的是“让人看到功能”，沙箱的目的是“让人和机器验证契约”。两者的验收标准不同：

| 维度 | 演示环境 | 沙箱 |
|---|---|---|
| 目标 | 展示卖点 | 验证集成 |
| 数据 | 精心准备的样例 | 可创建、可重置、可隔离 |
| 失败路径 | 通常没有 | 必须可注入 |
| 异步与回调 | 常常省略 | 必须可观察、可重放 |
| 密钥 | 共享或写死 | 独立测试密钥、可轮换 |
| 一致性 | 与生产可能不同 | 需要持续对拍 |
| 生命周期 | 长期存在 | 按需创建、自动过期 |

沙箱要对三类消费者负责：

1. **人**：开发者、合作伙伴、支持工程师。他们需要可读的日志、清晰的错误、可复制的示例。
2. **CI**：契约测试、集成测试、SDK 生成后的冒烟测试。它们需要确定性、可并行、可清理。
3. **Agent**：工具调用、工作流编排、自动化运维。它们需要明确的能力边界、幂等、可回滚和审计。

### 沙箱的三个承诺

一个可用的沙箱至少要兑现三个承诺：

- **可预测**：同样的输入产生同样的结果，除非显式注入变化。
- **可重置**：任何测试造成的状态都能被清理，不依赖人工。
- **可注入**：成功之外的路径——校验失败、权限不足、限流、超时、部分成功、异步延迟——都能被稳定触发。

缺少任何一个，沙箱就会退化成“能跑通 happy path 的演示”。

### 同源实现还是独立实现

沙箱有两种实现方式：

- **同源实现**：沙箱跑的是同一套服务代码，只隔离数据、密钥和外部依赖。保真度高，但需要强大的环境隔离与数据清理能力。
- **独立实现**：单独写一套模拟服务。启动快、成本低，但极易与生产行为漂移。

建议：**对外承诺的沙箱优先同源实现**；内部早期可以用独立 Mock，但必须用同一套契约测试对拍，并明确标注保真度等级。

## AJ.2 模拟保真度的六级阶梯

不是所有测试都需要真实沙箱。把测试放在正确的保真度层级，比盲目追求“全真环境”更经济。

| 等级 | 形态 | 能验证什么 | 不能验证什么 | 典型工具 |
|---|---|---|---|---|
| L0 | 文档静态示例 | 请求/响应形状 | 任何运行时行为 | Markdown、OpenAPI examples |
| L1 | 契约生成的静态 Mock | 路由、字段、基本校验 | 状态、权限、并发 | Prism、Mockoon |
| L2 | 状态化 Mock | CRUD、分页、错误注入 | 真实业务规则、外部依赖 | WireMock、Microcks |
| L3 | 隔离沙箱 | 真实业务逻辑、异步、Webhook | 生产规模、真实第三方 | 同源服务 + 测试数据 |
| L4 | 影子/回放 | 生产流量下的行为差异 | 写操作的真实副作用 | 流量复制、差分测试 |
| L5 | 生产测试模式 | 真实计费/清算前的最后验证 | 无（但风险最高） | Test clock、测试卡、测试租户 |

使用原则：

- **单元与前端并行开发**用 L0/L1；
- **消费者契约测试**用 L1/L2，并在 CI 中校验 Mock 响应符合 schema；
- **集成与联调**用 L3；
- **高风险迁移或协议升级**用 L4 做差分；
- **支付、计费、清算**才需要 L5，并且必须有额度、审计和人工兜底。

一个常见错误是：只用 L1 Mock 做 CI，然后宣称“契约测试通过”。Mock 通过只证明“消费者与 Mock 一致”，不证明“提供方与契约一致”。真正的契约验证需要提供方在 L3 或真实环境执行同一组消费者期望。

## AJ.3 契约驱动 Mock

### 从 OpenAPI 生成

```bash
# 静态 Mock：按 schema 生成响应，校验请求
prism mock openapi.yaml --port 4010

# 指定示例
curl -H "Prefer: example=paid_order" http://localhost:4010/orders/ord_123

# 主动返回错误，验证客户端错误处理
curl -H "Prefer: code=422" http://localhost:4010/orders
```

Prism 的价值在于：

- 请求不符合 schema 时直接返回 422，帮消费者尽早发现错误；
- 响应可由 schema 或 `examples` 生成；
- 支持按 `Prefer` 头选择示例或状态码；
- 可以作为 CI 中的“契约门禁”。

局限也很明显：它不理解业务状态，不会因为库存不足而拒绝订单，也不会因为你重复提交同一个幂等键而返回原结果。

### 状态化 Mock

WireMock 用 scenario 表达状态迁移：

```json
[
  {
    "scenarioName": "order-lifecycle",
    "requiredScenarioState": "Started",
    "request": { "method": "POST", "url": "/orders" },
    "response": {
      "status": 201,
      "jsonBody": { "id": "ord_123", "status": "PENDING_PAYMENT" },
      "headers": { "Location": "/orders/ord_123" }
    }
  },
  {
    "scenarioName": "order-lifecycle",
    "requiredScenarioState": "Started",
    "newScenarioState": "Paid",
    "request": { "method": "POST", "url": "/orders/ord_123/pay" },
    "response": {
      "status": 200,
      "jsonBody": { "id": "ord_123", "status": "PAID" }
    }
  }
]
```

WireMock 的初始场景状态是 `Started`，状态在命中 stub 时由 `newScenarioState` 推进；没有显式状态迁移的 stub 不写该字段。

状态化 Mock 适合：

- 前端在没有后端时走完整流程；
- 消费者测试分页、状态机、幂等重放；
- 演示失败后的恢复路径。

需要明确：

- 状态存在哪里？进程内、文件还是外部存储？
- 并发请求如何串行化？
- 如何重置到初始状态？
- 状态是否按测试运行隔离？
- Mock 的状态机是否与真实状态机同源？

如果 Mock 的状态机是手写的，它就会成为第二份真相。更可靠的做法是从领域状态机或契约生成 Mock 场景，并用同一组状态迁移测试对拍。

### gRPC、GraphQL 与事件

- **gRPC**：用 `buf` 生成服务骨架，或用 `grpc-mock`/MockServer 按 proto 返回；流式 RPC 要模拟分片、半关闭和错误终止。
- **GraphQL**：用 `graphql-tools` 的 `addMocksToSchema` 生成类型正确的 Mock；对 N+1、复杂度限制和字段级授权，Mock 基本无能为力，必须在沙箱验证。
- **事件/Webhook**：用 Microcks 或自建事件回放器，按 CloudEvents/AsyncAPI 发送样例；要覆盖重复、乱序、迟到和 schema 版本差异。

### Mock 保真度测试

Mock 本身也需要测试：

```text
1. Mock 响应必须通过 OpenAPI/JSON Schema 校验；
2. Mock 的每个示例必须能被官方 SDK 反序列化；
3. 同一组消费者契约测试，至少在 Mock 与沙箱各跑一次；
4. 定期对比 Mock 与沙箱的响应结构（字段、类型、状态码）；
5. 任何 Mock 与真实行为的差异，都要记录为已知偏差。
```

一个实用的 CI 矩阵：

| 流水线 | 环境 | 目的 | 频率 |
|---|---|---|---|
| 单元 | 进程内 | 业务逻辑 | 每次提交 |
| 消费者契约 | L1/L2 Mock | 消费者期望 | 每次提交 |
| 提供方契约 | L3 沙箱 | 实现符合契约 | 每次合并 |
| 差分 | L4 影子 | 新旧行为一致 | 发布前 |
| 端到端 | L3/L5 | 关键路径 |  nightly / 发布前 |

## AJ.4 状态化 Mock 的设计要点

### 请求匹配的优先级

状态化 Mock 常见匹配维度：

```text
method + path > query > headers > body 字段 > 通配
```

必须定义优先级和“未匹配”行为。默认应该是 **404/501 并记录**，而不是返回一个看起来成功的空响应。静默兜底会让消费者把错误当成成功。

### 动态响应

模板化响应可以引用请求参数：

```json
{
  "request": { "method": "GET", "urlPathPattern": "/orders/([^/]+)" },
  "response": {
    "status": 200,
    "jsonBody": {
      "id": "{{request.pathSegments.[1]}}",
      "status": "PAID"
    },
    "transformers": ["response-template"]
  }
}
```

注意：

- 模板中的用户输入要转义，避免 Mock 自身被注入；
- 动态 ID 要稳定，便于断言；
- 时间字段要用可控时钟，不要用 `now()`；
- 分页游标要能真正翻页，而不是永远返回同一页。

### 故障注入

故障注入应该是显式、可审计、不可误触发生产的：

```http
POST /orders
X-Test-Scenario: payment_timeout
```

或使用专用测试值：

```json
{ "cardNumber": "4000000000000002" }
```

设计原则：

- 只接受测试密钥；
- 场景名有白名单；
- 注入记录进审计日志；
- 可设置概率与持续时间，但默认关闭；
- 生产密钥看到这些头时直接忽略或拒绝，绝不能触发。

## AJ.5 沙箱架构

### 隔离模型

| 模型 | 隔离强度 | 成本 | 适用 |
|---|---|---|---|
| 共享沙箱 + 数据前缀 | 低 | 低 | 早期、内部试用 |
| 按租户命名空间 | 中 | 中 | 大多数对外 API |
| 每次测试运行创建临时环境 | 高 | 高 | CI、并行集成测试 |
| 专用沙箱实例 | 最高 | 最高 | 大客户、受监管行业 |

共享沙箱必须至少做到：

- 每个测试租户有独立命名空间或数据前缀；
- 查询、缓存、队列、日志都带租户键；
- 任何跨租户读取都返回 404，而不是 403（避免泄露存在性）；
- 清理按租户执行，不依赖全局 truncate。

### 密钥模型

测试密钥应该：

- 有明显前缀，如 `sk_test_`、`pk_test_`；
- 与生产密钥使用不同的签名密钥和数据库；
- 有独立的作用域、配额和过期时间；
- 不能调用生产端点，生产密钥也不能调用沙箱；
- 支持自助轮换和吊销；
- 在日志中脱敏，但仍保留可关联的密钥 ID。

一个常见事故是：测试密钥与生产密钥共用同一套验证逻辑，只是数据库不同。一旦环境判断出错，测试流量就可能打到生产。环境绑定应该是密钥的属性，并由网关在入口强制校验，而不是靠应用层“记得检查”。

### 重置与播种

沙箱应提供明确的管理接口，但与业务 API 分离：

```http
POST /__sandbox/reset
Authorization: Bearer <sandbox-admin-token>

POST /__sandbox/seed
{ "scenario": "subscription_past_due" }

POST /__sandbox/scenarios
{ "name": "payment_timeout", "enabled": true, "ttl": "10m" }
```

要求：

- 管理接口使用独立主机名、端口或双向 TLS；
- 不接受普通测试密钥；
- 重置是异步任务时，要返回可查询的任务 ID；
- 播种是幂等的，重复执行不产生重复数据；
- 清理要覆盖数据库、缓存、对象存储、搜索索引、队列和 Webhook 投递记录。

### 确定性与测试时钟

沙箱的默认行为应该是确定的：

- ID 可以由请求中的幂等键派生，或使用固定前缀 + 递增序列；
- 随机数使用可播种的 PRNG；
- 时间使用可注入的时钟；
- 外部依赖使用固定的响应集；
- 排序在相等键上有稳定的次级排序。

参见 [附录 AH](ah-primitive-semantics.md) 关于时间、时区和账期的语义。测试时钟的具体用法见 AJ.7。

### 异步与 Webhook

沙箱必须能观察和驱动异步过程：

- 异步任务：创建后返回 `202 + Location`，状态可按可控节奏推进；
- Webhook：开发者注册测试端点，沙箱用测试签名密钥投递；
- 重试：可手动触发第 N 次重试，或注入失败；
- 事件日志：记录每次投递的请求、响应、耗时和签名；
- 重放：支持按事件 ID 重新投递；
- 死信：可查看并重新入队。

如果沙箱只能同步返回，开发者就无法验证自己最需要的部分：回调验签、重复投递、乱序、延迟和失败恢复。

## AJ.6 测试数据工程

测试数据不是“随便造几条”，而是测试可重复性的基础。

### 数据工厂与场景构造

```python
import random
from dataclasses import dataclass


@dataclass
class TestContext:
    tenant_id: str
    rng: random.Random
    clock: "TestClock"


def make_order(ctx: TestContext, **overrides):
    seq = ctx.rng.randrange(10**6)
    order = {
        "id": f"ord_test_{seq:06d}",
        "tenantId": ctx.tenant_id,
        "status": "PENDING_PAYMENT",
        "total": {"amount": 12900, "currency": "CNY"},
        "createdAt": ctx.clock.now_iso(),
    }
    order.update(overrides)
    return order
```

原则：

- **每个测试有自己的上下文**：租户、随机种子、时钟；
- **工厂只造合法对象**：非法对象由显式的“损坏”函数构造，避免误用；
- **通过 API 到达目标状态**：不要直接写数据库，否则绕过了业务规则和审计；
- **状态构造器可组合**：`paid_order()`、`shipped_order()`、`refunded_order()`；
- **清理按上下文**：测试结束删除该租户的所有数据。

### 标识策略

- 不要在测试中硬编码数据库自增 ID；
- 使用工厂返回的 ID，或使用幂等键派生稳定 ID；
- 对外 ID 使用不透明前缀，测试断言只依赖“非空、稳定、可寻址”；
- 需要断言排序时，使用可控的时间或序列，而不是依赖插入顺序。

### 数据量与引用完整性

- 分页测试至少覆盖：空、一页、恰好一页、跨页、末页、非法游标；
- 大数据量测试用批量播种，不要循环调用单条 API；
- 造数据时保持外键和聚合边界一致；
- 删除测试要覆盖级联、软删除、墓碑和索引清理；
- 对搜索/分析类 API，要造出分布不均的数据，避免“平均值正确、长尾错误”。

### PII 与合成数据

- 默认使用合成数据，不复制生产数据；
- 需要格式逼真时，使用保留格式的合成器（如符合 Luhn 的测试卡号、符合校验位的 IBAN）；
- 合成数据也要避免使用真实人的姓名、电话、地址；
- 如果必须使用脱敏生产数据，要有审批、审计、保留期限和再识别风险评估；
- 测试日志同样可能泄露 PII，脱敏要覆盖日志、Trace、错误详情和快照。

### 黄金夹具与 schema 版本

契约测试、序列化测试和迁移测试需要稳定的夹具：

```text
fixtures/
  order/
    v1_paid.json
    v2_paid_with_discount.json
  event/
    order_paid_v3.cloudevent.json
```

要求：

- 夹具带 schema 版本；
- 夹具本身通过 schema 校验；
- 变更夹具时，明确是“新增场景”还是“修改既有语义”；
- 旧版本夹具保留，用于兼容性测试；
- 夹具中的时间、ID、金额使用固定值，便于 diff。

## AJ.7 测试时钟与时间旅行

时间是 API 测试中最常见的非确定性来源。以下场景几乎无法用真实时间稳定测试：

- 订阅试用到期；
- 账期结算、月结、跨年；
- 令牌、签名、游标的过期；
- 定时任务、重试退避、熔断半开；
- 夏令时缺口与重叠；
- 按比例退款、按天计费；
- 预约、取消截止时间。

### 三种实现方式

| 方式 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| 注入时钟 | 应用内使用 `Clock` 接口，测试传入假时钟 | 精确、快 | 需要改造代码，覆盖不到数据库/第三方 |
| 冻结时间 | 测试框架冻结进程时间 | 无需改造 | 影响同进程其他测试，难并行 |
| 外部测试时钟 | 沙箱提供时钟服务，所有组件读取同一时间源 | 接近真实、可跨服务 | 实现复杂，需处理缓存与已签发令牌 |

对外沙箱建议提供“时间偏移”能力，而不是任意跳转：

```http
POST /__sandbox/clock
{ "offset": "P30D" }
```

偏移是相对真实时间的，避免时钟倒退导致单调性假设被破坏。若必须跳到过去，要明确哪些组件支持、哪些缓存/TTL 不会回退。

### 陷阱

- 数据库的 `now()`、`CURRENT_TIMESTAMP` 可能绕过应用时钟；
- JWT 的 `exp`、`iat` 由签发时的真实时间决定，冻结应用时钟无效；
- 缓存 TTL 可能基于真实时间；
- 定时任务可能使用系统 cron，而不是应用时钟；
- 跨时区测试要同时覆盖 DST 缺口（不存在的时间）和重叠（出现两次的时间）；
- 月末、闰年、闰秒要有专门用例；
- 测试时钟的偏移要记录在响应头或审计日志中，避免把测试结果误当生产证据。

## AJ.8 异步、Webhook 与流式回放

### Webhook 测试面板

一个合格的 Webhook 沙箱应提供：

```text
1. 注册/更新测试端点（含签名密钥）
2. 发送测试事件
3. 查看投递日志（请求头、体、签名、响应码、耗时）
4. 手动重放某次投递
5. 注入失败（超时、500、连接拒绝）
6. 查看重试计划与下一次重试时间
7. 暂停/恢复投递
8. 查看死信并重新入队
```

开发者最常遇到的问题不是“收不到”，而是“收到了但验签失败”“重复收到”“顺序不对”“重试把我打挂了”。沙箱要能稳定复现这些情况。

### 流式回放

对 SSE/WebSocket/NDJSON：

- 录制一段真实或合成的流；
- 支持按事件 ID 重放；
- 支持在指定事件后断开，验证 `Last-Event-ID` 恢复；
- 支持注入慢消费者、背压和心跳丢失；
- 支持在流中途返回错误事件，验证客户端错误处理。

### 事件总线

如果 API 包含事件订阅：

- 提供测试主题/队列；
- 支持按 schema 版本发布事件；
- 支持重复、乱序、迟到事件；
- 支持消费者位点重置；
- 支持死信与重放；
- 记录事件 ID、分区、偏移和投递次数。

## AJ.9 安全、隔离与滥用

沙箱不是“安全区”，它同样是攻击面。

| 威胁 | 场景 | 控制 |
|---|---|---|
| 沙箱逃逸 | 测试密钥调用生产 | 密钥环境绑定、网关强制校验 |
| SSRF | Webhook URL 指向内网/云元数据 | 出站代理、DNS 解析后校验、禁止私网地址 |
| 数据泄露 | 多租户共享沙箱，查询未带租户 | 强制租户过滤、跨租户返回 404 |
| PII 残留 | 脱敏生产数据进入沙箱 | 合成数据优先、审批、TTL、审计 |
| 资源滥用 | 免费算力、挖矿、垃圾注册 | 配额、邮箱/企业验证、异常检测 |
| Webhook 重放 | 攻击者重放旧回调 | 时间戳、签名、事件 ID 去重 |
| 测试密钥泄露 | 提交到公开仓库 | 密钥扫描、自动吊销、最小权限 |
| Agent 越权 | Agent 拿到过大作用域的测试密钥 | 细粒度 scope、人工确认、审计 |

### 出站安全

Webhook 和回调是沙箱最危险的出站通道：

- 解析 URL 后校验 IP，禁止回环、私网、链路本地和云元数据地址；
- 防止 DNS 重绑定：解析一次后固定 IP，或在连接层再次校验；
- 使用独立出口代理，限制可访问的端口和协议；
- 限制重定向次数，禁止跳转到私网；
- 对出站请求做超时、大小和速率限制；
- 记录出站目标，便于滥用排查。

### Agent 的测试权限

Agent 在沙箱中应该使用：

- 只覆盖测试资源的 scope；
- 明确的预算和调用上限；
- 对不可逆操作（删除、支付、发布）要求人工确认；
- 完整的工具调用审计；
- 可随时吊销的凭证。

不要因为“是沙箱”就给 Agent 一个万能密钥。沙箱里的错误行为会变成对生产权限模型的错误信心。

## AJ.10 运维、漂移与度量

### 漂移检测

沙箱最大的风险是“看起来能用，但和生产不一样”。至少做：

- **契约对拍**：同一组契约测试在沙箱与预发/生产金丝雀上运行，比较状态码、字段和类型；
- **行为探针**：对关键端点定期发送固定请求，比较响应结构；
- **错误码对拍**：沙箱是否返回了生产中不存在的错误码，或缺少生产中的错误码；
- **状态机对拍**：同一组状态迁移在沙箱与生产测试租户上是否一致；
- **版本对拍**：沙箱当前服务哪个 API 版本，是否与文档一致。

差异要进入缺陷列表，而不是“沙箱就这样”。

### 沙箱 SLO

沙箱的可用性目标可以低于生产，但不能没有：

- 沙箱可用性；
- 测试密钥签发成功率；
- 环境创建/重置时间；
- Webhook 投递成功率；
- 支持工单响应时间。

沙箱宕机会直接阻塞合作伙伴集成，影响收入，只是不会立刻体现在生产错误率上。

### 度量

- Time to First Call（TTFC）；
- 从注册到首次成功沙箱调用；
- 沙箱到生产的转化率；
- 沙箱中最常见的错误码；
- 沙箱请求成功率；
- 每个开发者的沙箱调用次数；
- 支持工单中“沙箱问题”的比例；
- 因沙箱与生产差异导致的联调失败数。

## AJ.11 反模式

- 沙箱是另一套手写实现，与生产长期漂移；
- 沙箱共用生产数据库或生产密钥；
- 测试密钥可以调用生产；
- 数据不能重置，测试互相污染；
- 只有 happy path，无法注入失败；
- Mock 永远返回 200，CI 永远绿色；
- 测试依赖当前时间和随机数；
- 共享测试租户，测试顺序成为隐式依赖；
- Webhook 只能手动触发，无法重放；
- 沙箱没有限流，被当成免费算力；
- 脱敏生产数据进入沙箱，但没有审计和保留期限；
- Agent 在沙箱里拿到万能密钥；
- 沙箱版本与文档版本不一致；
- 把“沙箱能跑”当作“可以上线”。

## AJ.12 检查清单

- [ ] 沙箱与生产使用同一套实现，或明确标注保真度等级。
- [ ] 测试密钥有前缀、独立作用域、环境绑定和轮换机制。
- [ ] 测试密钥无法调用生产，生产密钥无法调用沙箱。
- [ ] 每个测试运行有独立租户/命名空间，跨租户读取返回 404。
- [ ] 数据可播种、可重置、可自动过期。
- [ ] 重置覆盖数据库、缓存、对象存储、搜索、队列和 Webhook 记录。
- [ ] Mock 响应通过 schema 校验，并与沙箱定期对拍。
- [ ] 可稳定注入校验失败、权限不足、限流、超时、部分成功和异步延迟。
- [ ] 测试时钟可控制，覆盖时区、DST、月末和过期场景。
- [ ] Webhook 可注册、可验签、可重放、可注入失败、可查看投递日志。
- [ ] SSE/流式可回放、可断开、可恢复。
- [ ] 测试数据使用合成数据，工厂确定、隔离、可清理。
- [ ] 沙箱出站流量有 SSRF 防护和审计。
- [ ] 沙箱有配额、滥用检测和独立 SLO。
- [ ] 沙箱版本、文档版本和生产版本有明确对应关系。
- [ ] Agent 使用最小权限测试凭证，不可逆操作需确认。

## AJ.13 小结

- 沙箱是契约的可操作副本，不是演示页面。
- 模拟有保真度阶梯：静态示例、契约 Mock、状态化 Mock、隔离沙箱、影子回放、生产测试模式。
- Mock 通过不等于集成通过；Mock 与沙箱必须用同一组契约测试对拍。
- 沙箱的核心承诺是可预测、可重置、可注入。
- 测试数据要确定、隔离、可清理；时间要用可控时钟。
- Webhook、异步任务和流式响应是沙箱最容易被省略、也最需要验证的部分。
- 沙箱同样是攻击面：测试密钥、出站请求、PII 和 Agent 权限都要治理。
- 沙箱需要漂移检测、SLO 和度量，否则会在无人察觉中失效。

## 设计练习

为一个“订阅计费 API”设计沙箱：

- 套餐、订阅、试用、账期、发票、退款；
- 测试时钟可推进 30 天、跨月、跨年、跨 DST；
- 测试卡号触发成功、拒绝、超时、重复扣款；
- Webhook 可注册、验签、重放、注入失败；
- 每个测试运行独立租户；
- 支持一次性重置和按租户清理；
- 沙箱密钥与生产密钥严格隔离；
- 记录开发者最常失败的场景。

回答：

1. 试用到期和账期结算如何用测试时钟稳定复现？
2. 如何证明沙箱与生产的计费行为一致？
3. Webhook 重放如何防止被攻击者利用？
4. 沙箱被滥用挖矿时，如何在不影响正常开发者的前提下止血？
5. 如果只能先做三件事，优先做哪三件？
