# 附录 Y：API 成本工程与 FinOps

> 单位经济回答“这门生意是否成立”，成本工程回答“每一分钱花在哪里、谁该负责、如何下降”。
> 很多 API 产品毛利被侵蚀，不是因为定价太低，而是因为团队看不见成本：共享资源没有归因、免费层没有预算、重试没有计量、日志比业务还贵。

本附录与[第 33 章](../part-4-engineering-product/33-performance.md)（性能与容量）、[第 52 章](../part-7-business/52-unit-economics.md)（单位经济）、[附录 V](v-metering-billing.md)（计量与计费）互补：33 讲性能，52 讲财务模型，V 讲收入，本附录讲成本。

## Y.1 成本不是月底的一张账单

API 成本至少分为两类、四层：

**交付成本（COGS 的主体）**：

| 层次 | 例子 | 谁负责 |
|---|---|---|
| 基础设施 | 计算、存储、网络、数据库、缓存 | 平台 / SRE |
| 第三方 | 模型、短信、地图、支付通道 | 产品 / 采购 |
| 运营 | 支持、合规、审计、客户成功 | 业务 / 支持 |

**质量与合同成本（通常不计入 COGS）**：

| 层次 | 例子 | 财务处理 |
|---|---|---|
| 重试/浪费 | 重试、滥用、孤儿资源 | 可能已包含在交付成本中，不要重复计 |
| 合同/质量 | 退款、SLA 赔偿、拒付、事故补偿 | 通常作为收入抵减或其他费用，不是 COGS |

“云账单”只覆盖第一层的一部分。真正的交付成本还包括第三方、支持与合规；退款和赔偿要单独看，不要混进单位成本。

### Y.1.1 固定成本、可变成本与阶梯成本

- **固定成本**：控制平面、常驻数据库、合规认证、基础团队。
- **可变成本**：请求计算、token、出口流量、存储增长。
- **阶梯成本**：当用量跨过某个阈值，需要新增分片、区域、集群或支持人员。

容量规划要同时看固定与可变成本。只按“每请求成本”做决策，会忽略阶梯成本的跳变。

### Y.1.2 共享成本

多租户平台的大量成本是共享的：

- 网关、认证、日志、监控；
- 数据库连接池；
- 缓存集群；
- 消息队列；
- 支持团队；
- 合规审计。

共享成本必须被分摊，否则：

- 大客户看起来毛利很高，实际占用了最多共享资源；
- 小客户看起来亏损，实际只是被平均成本误伤；
- 平台团队无法证明自己的价值；
- 优化没有优先级。

## Y.2 成本模型

### Y.2.1 从资源到单位成本

```text
单位成本 = 总成本 / 业务量
```

但“业务量”要选对：

- 每请求；
- 每成功请求；
- 每 1K token；
- 每 GB 存储/月；
- 每 GB 出口；
- 每租户/月；
- 每活跃用户；
- 每任务；
- 每订单/支付/文档。

一个 API 可能同时有多个单位成本。不要用一个平均数掩盖差异。

### Y.2.2 成本归因公式

```text
租户交付成本 =
  直接计算成本（明确是否已包含重试）
+ 直接存储成本
+ 直接网络/出口成本
+ 直接第三方成本
+ 支付通道费
+ 分摊的共享平台成本
+ 分摊的支持/合规/客户成功成本
```

退款、SLA 赔偿、拒付与事故补偿通常作为收入抵减或其他费用，不并入上述交付成本。重试如果已经计入“直接计算成本”，就不要再单列一次。

分摊规则要写清楚：

- 按用量分摊（请求数、token、GB）；
- 按峰值/预留分摊（连接池、缓存）；
- 按人头/工时分摊（支持）；
- 按收入分摊（共享合规）；
- 固定比例分摊（平台团队）。

没有完美分摊。目标是“可解释、可复现、可改进”，而不是会计精确到分。

### Y.2.3 一个示例

```text
某租户月用量：
  1,000 万次请求
  500 GB 出口
  2,000 万 input tokens
  500 万 output tokens

直接成本：
  计算        $120
  数据库      $80
  缓存        $20
  出口        $45
  模型        $300
  存储        $15

共享分摊：
  网关/认证   $25
  日志/追踪   $30
  支持        $40

合计          $675
每请求成本    $0.0000675
```

如果该租户月收入 $1,000，毛利率约 32.5%。如果模型成本上涨 30%，毛利率降到约 23.5%。

### Y.2.4 碳成本与 GreenOps

FinOps 管钱，GreenOps 管碳。两者高度重叠：闲置资源、过度预留、重复计算、无缓存、超大日志，既烧钱也排碳。

基本口径：

```text
能耗（kWh） ≈ IT 设备功率 × 运行时长 × PUE
排放（gCO2e） = 能耗 × 区域电网碳强度（gCO2e/kWh）
每请求排放 = 排放 / 请求数
```

要区分：

- **范围 1/2/3**：自有燃烧、外购电力、供应链（云厂商、硬件、网络）；
- **location-based vs market-based**：按区域电网平均强度，还是按购买的绿电/证书；
- **PUE**：数据中心总能耗 / IT 能耗；
- **碳强度**：随区域、季节、时段变化，不能用一个全球平均值。

对 API 设计的影响：

- 区域选择同时影响延迟、成本、数据驻留与碳强度；
- 批量/可延迟任务可以调度到低碳时段或区域；
- 缓存、压缩、连接复用、右 sizing 同时降本降碳；
- 日志/Trace 采样不仅省钱，也减少存储与网络排放；
- 免费层与重试会放大排放，和成本一样需要预算；
- 不要把“购买碳抵消”当作“零排放”，抵消不改变实际能耗。

如果对外提供碳估算：

```json
{
  "requestId": "req_123",
  "energyKwh": 0.00042,
  "gCO2e": 0.18,
  "region": "eu-central-1",
  "methodology": "location-based-v2",
  "estimated": true
}
```

必须标注方法学、区域、估算性质与版本；不要把它写成合同承诺。客户要用于 CSRD/GHG Protocol 报告时，需要可审计的因子来源与边界说明。

## Y.3 计量、标签与归因

### Y.3.1 成本标签

常见维度：

- 租户、项目、环境；
- 端点、方法、状态码；
- 模型、区域、可用区；
- 客户端版本、API Key；
- 成本中心、团队、工作负载；
- 请求类型（读/写/流式/批量）。

高基数标签会让监控与成本系统爆炸。请求 ID、完整 URL、用户邮箱不要做成本标签。

### Y.3.2 成本数据管线

```text
云账单 / 供应商账单
  → 成本明细（按资源、标签、时间）
  → 用量事件（请求、token、GB）
  → 归因（租户、项目、端点）
  → 单位成本与毛利
  → 预算/告警/优化
```

两条数据要能对上：

- 财务口径的成本（优先用**摊销/应计成本**，而不是当月现金支付）；
- 工程用量（请求/token/GB）。

预付费、承诺消费、预留实例会造成“现金支付”与“当期成本”错位。单位经济用摊销/应计成本；现金流对账单独做，不要把时间差当成成本超支。

对不上时，优先查：

- 标签缺失；
- 共享资源未分摊；
- 折扣/承诺未反映；
- 汇率/税；
- 时间窗口；
- 免费层/内部调用；
- 重试与失败请求。

### Y.3.3 成本可见性

最低要求：

- 每个租户能看到自己的用量与估算成本；
- 每个团队能看到自己负责的服务的单位成本；
- 每个端点能看到成本排名；
- 每个模型/第三方能看到成本趋势；
- 成本异常能告警；
- 成本变更能追溯到发布/配置/价格。

## Y.4 Showback 与 Chargeback

### Y.4.1 两种模式

| 模式 | 含义 | 优点 | 风险 |
|---|---|---|---|
| Showback | 展示成本，不实际收费 | 低摩擦、教育团队 | 无硬约束 |
| Chargeback | 按成本向内部团队收费 | 强激励 | 争议、分摊复杂 |

建议从 showback 开始，等分摊规则稳定后再考虑 chargeback。

### Y.4.2 内部定价

内部平台可以：

- 按成本价；
- 成本 + 平台费；
- 市场价；
- 套餐/配额；
- 免费 + 预算。

内部定价的目标不是利润，而是：

- 让团队看见成本；
- 避免滥用；
- 优先高价值工作；
- 证明平台价值；
- 支持容量规划。

### Y.4.3 共享成本的分摊争议

常见争议：

- “这个缓存是大家用的，为什么算我们头上？”
- “我们的峰值是别人造成的。”
- “平台团队自己的开销为什么要业务承担？”
- “预留容量没用完，谁付钱？”

解决方法：

- 公开分摊规则；
- 提供逐项明细；
- 允许申诉；
- 定期复核；
- 对不可控成本设置上限；
- 不把分摊当作惩罚。

## Y.5 预算、预测与异常

### Y.5.1 预算

预算维度：

- 租户/项目；
- 团队/成本中心；
- 环境；
- 模型/第三方；
- 端点/工作负载。

预算控制：

- 告警（50%/80%/100%）；
- 软上限（告警）；
- 硬上限（拒绝/降级，需客户授权或合同约定；内部成本预算与客户配额要分开）；
- 自动扩容上限；
- 审批提额；
- 预算结转。

### Y.5.2 预测

```text
月末预测 = 当前累计 + 平均日速率 × 剩余天数
（平均日速率取过去 7/28 天，并按季节性调整）
```

更稳的做法：

- 按日/周季节性；
- 按 cohort；
- 按大客户；
- 按发布计划；
- 按价格/模型变化；
- 给区间，不给单点。

### Y.5.3 成本异常

异常信号：

- 单租户用量突增；
- 单端点成本突增；
- 重试率上升；
- 缓存命中率下降；
- 模型路由变化；
- 出口流量异常；
- 日志/追踪量突增；
- 免费层滥用；
- 批处理任务泄漏；
- 孤儿资源。

异常处理：

1. 确认是真实用量还是计量错误；
2. 定位租户/端点/版本；
3. 判断是恶意、缺陷还是正常增长；
4. 限流/降级/修复；
5. 通知客户/财务；
6. 记录复盘。

## Y.6 优化手段

### Y.6.1 按成本排序

```text
1. 找出成本最高的 10 个端点/租户/模型
2. 区分固定/可变/共享
3. 找可避免的浪费（重试、日志、孤儿、过度缓存）
4. 优化单位成本，而不是总账单
5. 验证性能/可靠性没有变差
```

### Y.6.2 常见优化

| 手段 | 降低成本 | 风险 |
|---|---|---|
| 缓存 | 数据库/计算 | 内存、一致性 |
| 批量 | 往返/固定开销 | 延迟、复杂度 |
| 压缩 | 出口/存储 | CPU |
| 存储分层 | 存储 | 读取延迟 |
| 模型路由 | 推理 | 质量 |
| 预留容量 | 计算 | 利用率不足 |
| 边缘计算 | 回源/延迟 | 运行时限制 |
| 日志采样 | 存储/查询 | 可观测性 |
| 生命周期 | 存储 | 合规保留 |
| 限流/配额 | 过载/滥用 | 客户体验 |

### Y.6.3 一个量化示例

沿用 Y.2.3 的租户（月成本 $675）：

| 优化 | 变化 | 月节省 |
|---|---:|---:|
| 提高缓存命中率 | 数据库 $80 → $50 | $30 |
| 出口压缩 | 网络 $45 → $35 | $10 |
| 日志采样 | 日志/追踪 $30 → $18 | $12 |
| 小模型路由 | 模型 $300 → $240 | $60 |
| **合计** | **$675 → $563** | **$112（16.6%）** |

单请求成本从 `$0.0000675` 降到 `$0.0000563`。但要同时验证：

- 缓存是否引入一致性/权限问题；
- 压缩是否增加 CPU 或改变 Range 语义；
- 日志采样是否让排障变难；
- 小模型是否降低质量/任务成功率；
- 节省是否值得实施与维护成本。

优化不是“把数字压下去”，而是在质量、可靠性、合规约束下降低单位成本。

### Y.6.4 不要优化错的东西

- 优化了只占 2% 成本的端点；
- 用更贵的实例换一点延迟；
- 为了省存储删掉审计日志；
- 缓存了不该缓存的数据；
- 把成本转嫁给客户但不告知；
- 只看云账单，忽略第三方与支持。

## Y.7 FinOps 运营

### Y.7.1 月度节奏

```text
第 1 周：账单与用量对账
第 2 周：单位成本与毛利复盘
第 3 周：异常与优化项
第 4 周：预算/预测/下月计划
```

### Y.7.2 角色

- 工程：单位成本、性能、容量；
- 产品：定价、套餐、免费层；
- 财务：账单、毛利、收入确认；
- 采购：第三方合同、承诺；
- 平台：共享成本、标签、工具；
- 支持：支持成本、工单原因。

### Y.7.3 指标

- 每请求/每 token/每 GB 成本；
- 每租户毛利；
- 共享成本占比；
- 免费层成本；
- 重试/失败成本；
- 缓存命中率；
- 存储增长率；
- 预留容量利用率；
- 预算偏差；
- 成本异常次数；
- 优化项完成率。

### Y.7.4 优化 backlog

每个优化项要写：

- 影响成本；
- 影响性能/可靠性；
- 实施成本；
- 负责人；
- 截止日期；
- 验证方式；
- 回滚方案。

没有 owner 和验证的“优化”，通常不会发生。

## Y.8 反模式

- 只看云账单，不看第三方/支持/失败成本；
- 用平均成本掩盖租户差异；
- 共享成本不分摊；
- 标签缺失/高基数；
- 免费层无预算；
- 重试不计成本；
- 日志/追踪全量保留；
- 缓存掩盖慢查询；
- 预留容量买太多；
- 优化非瓶颈；
- 成本告警没有 owner；
- 成本下降以可靠性为代价；
- 内部定价变成政治；
- 不做预测；
- 不做对账。

## Y.9 检查清单

- [ ] 成本分为基础设施、第三方、运营、失败成本。
- [ ] 固定/可变/阶梯成本分别建模。
- [ ] 共享成本有公开、可复现的分摊规则。
- [ ] 单位成本按请求/token/GB/租户/端点可计算。
- [ ] 成本标签有基数限制，不含敏感/高基数数据。
- [ ] 财务账单与工程用量能对账。
- [ ] 租户/团队/端点能看到成本与趋势。
- [ ] 预算有告警、软/硬上限与提额流程；硬上限有客户授权/合同依据，且与内部成本预算区分。
- [ ] 有月度预测与异常检测。
- [ ] 优化项有 owner、影响、验证与回滚。
- [ ] 成本优化不牺牲可靠性/合规。
- [ ] 免费层、重试、日志、孤儿资源有专门监控。
- [ ] 碳成本有口径（范围、区域、PUE、碳强度），并与成本一起优化。
- [ ] 对外碳估算标注方法学、版本与估算性质，不作为合同承诺。

## 设计练习

为一个“多模型 LLM 网关”建立成本工程方案：

- 模型 A 便宜但质量低，模型 B 贵但质量高；
- 有缓存、批处理、流式；
- 免费层每月 100 万 token；
- 企业客户有承诺消费；
- 支持团队按工时分摊；
- 云账单、供应商账单、用量事件三套数据。

请回答：

1. 单位成本按什么维度计算？
2. 共享成本如何分摊？
3. 如何检测免费层滥用？
4. 模型路由如何影响毛利？
5. 预算/告警/硬上限如何设计？
6. 如何证明优化没有损害质量？
7. 财务账单与用量事件对不上时，排查顺序是什么？

## 小结

- 成本工程不是月底看账单，而是持续归因、预测、优化。
- 固定/可变/阶梯/共享成本要分别建模。
- 单位成本要选对业务量，不能用平均数掩盖差异。
- 成本标签要可解释、可复现、低基数。
- Showback 先于 Chargeback；分摊规则要公开、可申诉。
- 预算、预测、异常检测是运营闭环。
- 优化要按成本排序，不能牺牲可靠性/合规。
- 碳成本与成本高度重叠：区域、批量、缓存、采样、右 sizing 同时影响两者；碳估算要标注口径，不当作合同承诺。
- FinOps 需要工程、产品、财务、采购、平台、支持共同参与。
