# 附录 W：API 产品管理、开发者关系与增长

> API 不是“把后端能力暴露出去”就结束了。它有自己的用户、旅程、定价、路线图、支持与增长模型。
> 本附录讨论：谁来决定 API 做什么、先做什么、如何验证、如何让开发者真正用起来，以及如何把一次发布变成可持续的产品。

本附录与[第 36 章](../part-4-engineering-product/36-docs-and-dx.md)（文档与 DX）、[第 51 章](../part-7-business/51-pricing.md)（定价）、[第 54 章](../part-7-business/54-operations-metrics.md)（运营指标）、[第 55 章](../part-7-business/55-risk-org-roadmap.md)（风险、组织与路线图）互补：那几章讲“怎么做”，这里讲“谁来做、为什么做、做完如何判断”。

## W.1 API 产品与 API 项目

### W.1.1 三个产品表面

一个 API 产品通常有三个表面，任何一个断裂都会让采用失败：

| 表面 | 用户接触点 | 核心问题 |
|---|---|---|
| 契约表面 | 端点、字段、错误码、事件、SDK | 能不能正确、稳定地完成调用？ |
| 学习表面 | 文档、教程、示例、沙箱、错误信息 | 能不能在十分钟内跑通并理解？ |
| 商业表面 | 定价、套餐、账单、合同、支持 | 能不能买、用得值、续得起？ |

很多团队只做“契约表面”，把文档当附属品，把定价当财务的事。结果是接口能跑，但没人愿意集成；或者集成后账单吓跑了客户。

### W.1.2 项目思维与产品思维

| 维度 | 项目思维 | 产品思维 |
|---|---|---|
| 成功标准 | 按时上线 | 采用、留存、扩展、毛利 |
| 用户 | 需求方 | 多类开发者与决策者 |
| 生命周期 | 交付即结束 | 持续演进与运营 |
| 反馈 | 上线后再说 | 设计前就开始 |
| 文档 | 交付物 | 产品的一部分 |
| 指标 | 完成度 | 激活、TTFC、NRR、支持成本 |
| 失败 | 延期 | 没人用、用错、用不起 |

API 项目可以靠一个团队冲刺完成；API 产品需要产品经理、工程、DX、支持、销售、财务、法务共同运营。

### W.1.3 四类“客户”

不要把“开发者”当成唯一客户：

1. **动手的开发者**：写代码、调试、集成。关心文档、SDK、错误信息、沙箱。
2. **技术决策者**：架构师、技术负责人。关心可靠性、安全、合规、迁移成本、长期维护。
3. **经济决策者**：采购、财务、业务负责人。关心价格、合同、ROI、风险。
4. **机器消费者**：脚本、自动化平台、AI Agent。关心 schema、工具描述、错误可恢复性、权限边界。

一个 API 产品要同时回答四类人的问题。只讨好开发者，可能过不了采购；只讨好采购，可能没人愿意集成。

## W.2 发现：先找任务，不要先找端点

### W.2.1 Jobs-to-be-Done

API 的价值不是“提供数据”，而是“帮助调用方完成一项任务”。用 JTBD 语言描述：

```text
当我（角色）在（场景）时，
我想要（动机/任务），
以便（预期结果）。
```

例子：

```text
当我是一个跨境电商的开发者，
在客户下单后需要扣减库存并收款时，
我想要一个能保证不超卖、不重复扣款的下单接口，
以便我可以放心地把订单承诺给客户。
```

从任务出发，才能发现：

- 需要哪些资源与动作；
- 哪些不变量必须由服务端保证；
- 失败时调用方需要什么信息；
- 哪些步骤可以异步；
- 哪些数据必须一次返回，哪些可以分页。

### W.2.2 发现的信息来源

| 来源 | 能发现什么 | 陷阱 |
|---|---|---|
| 客户访谈 | 任务、痛点、替代方案、决策链 | 客户说的方案不一定是需求 |
| 支持工单 | 文档缺口、错误信息问题、集成摩擦 | 只代表已经来求助的人 |
| API 日志 | 真实调用模式、失败率、弃用使用 | 看不到未接入的人 |
| 文档搜索 | 用户找不到什么 | 搜索日志可能不完整 |
| 销售通话 | 采购标准、竞品、价格敏感度 | 销售视角有偏差 |
| 社区/论坛 | 高频问题、误解、生态需求 | 噪音大 |
| 竞品 API | 行业惯例、差距 | 不能照抄 |
| 设计伙伴 | 深度反馈、早期验证 | 不代表大众市场 |

### W.2.3 十二个访谈问题

1. 你最近一次完成这个任务是什么时候？能逐步讲一遍吗？
2. 你现在用什么方式完成？为什么不用其他方式？
3. 这个任务最耗时间/最容易出错的是哪一步？
4. 如果这一步失败，会发生什么？谁受影响？
5. 你如何判断调用成功？你相信什么信号？
6. 你需要多快得到结果？能否异步？
7. 你会如何处理重试、重复、部分失败？
8. 你需要看到哪些数据才能做下一步？
9. 你的团队里谁决定是否采用？谁负责集成？谁付钱？
10. 你最担心安全/合规/锁定中的哪一项？
11. 如果明天要换掉这个 API，成本有多大？
12. 你愿意为“少一次人工操作/少一次故障”付多少钱？

访谈的目标不是收集功能清单，而是理解任务、约束、失败代价与决策链。

### W.2.4 机会解决方案树

```text
目标：提高订单 API 的激活率
├── 机会：开发者不知道如何创建测试订单
│   ├── 方案：沙箱一键生成测试数据
│   ├── 方案：快速开始内置订单示例
│   └── 方案：错误信息直接给出修复请求
├── 机会：首次调用因认证失败
│   ├── 方案：测试密钥自动创建
│   └── 方案：认证错误带可复制示例
└── 机会：集成后不知道是否成功
    ├── 方案：Webhook 测试工具
    └── 方案：集成检查清单
```

先列机会，再列方案。不要从“做一个新端点”开始。

## W.3 定义 API 表面

### W.3.1 最小可用表面

一个 API 的 MVP 不是“一个端点”，而是“一个任务端到端可完成”。

以“发票收款”为例，最小表面可能包括：

```text
POST /invoices                       创建发票
POST /invoices/{invoiceId}/finalize  终态化
POST /payments                       发起支付
GET  /payments/{paymentId}           查询结果
POST /webhook-subscriptions          订阅支付结果
```

缺少任何一环，开发者都无法完成真实任务。反过来，以下能力可以后置：

- 批量创建；
- 高级搜索；
- 多币种；
- 部分退款；
- 自定义报表。

### W.3.2 表面设计的产品原则

1. **一个任务一条主路径**：不要让开发者为了完成一件事组合五个端点。
2. **默认安全**：默认最小权限、默认幂等、默认超时、默认分页。
3. **默认可观测**：每个响应有请求 ID，每个错误可追踪。
4. **可组合**：资源和动作的语义一致，避免每个端点一套风格。
5. **可退出**：数据可导出，契约可迁移，不制造人为锁定。
6. **可理解**：命名、错误、文档使用同一套业务语言。

### W.3.3 命名是 UX

开发者每天读的是：

```text
GET /orders/{orderId}/fulfillments
POST /orders/{orderId}/cancel
```

不是营销页面。命名要回答：

- 这是资源还是动作？
- 单数还是复数？
- 状态字段叫什么？
- 错误码是否可搜索？
- 同一个概念在不同端点是否同名？

命名不一致会直接增加支持工单。把命名纳入设计评审，而不是留给实现者即兴发挥。

### W.3.4 错误信息是 UX

一个好的错误信息应包含：

```json
{
  "type": "https://errors.example.com/insufficient-inventory",
  "title": "库存不足",
  "status": 422,
  "code": "INSUFFICIENT_INVENTORY",
  "detail": "SKU sku_123 在仓库 wh_1 仅剩 2 件，请求 5 件。",
  "instance": "/orders/ord_123",
  "meta": {
    "sku": "sku_123",
    "warehouseId": "wh_1",
    "available": 2,
    "requested": 5
  },
  "docsUrl": "https://docs.example.com/errors/insufficient-inventory",
  "requestId": "req_abc"
}
```

错误信息的产品标准：

- 说清楚发生了什么；
- 说清楚下一步能做什么；
- 不泄露内部实现；
- 可被日志、SDK、Agent 解析；
- 有稳定错误码；
- 有文档链接；
- 有请求 ID。

### W.3.5 文档是产品界面

文档不是“写完接口后补的说明”，而是开发者接触产品的第一界面。产品经理应参与：

- 快速开始的验收；
- 示例是否覆盖真实任务；
- 错误文档是否可搜索；
- 术语是否一致；
- 迁移指南是否可执行；
- 文档指标是否进入路线图。

## W.4 路线图与优先级

### W.4.1 三种工作

API 产品的路线图通常包含三类工作：

1. **新能力**：新端点、新资源、新协议、新市场。
2. **采用与体验**：文档、SDK、沙箱、错误、入门流程。
3. **基础与债务**：契约一致性、版本迁移、可观测性、安全、合规、计费。

只做第一类，会出现“功能很多但没人用”；只做第二类，会缺少差异化；只做第三类，会被业务认为平台团队不创造价值。

### W.4.2 优先级方法

| 方法 | 公式/思路 | 适用 |
|---|---|---|
| RICE | (Reach × Impact × Confidence) / Effort | 功能优先级 |
| WSJF | Cost of Delay / Job Size | 敏捷组合 |
| Cost of Delay | 延迟带来的收入/风险损失 | 平台与合规 |
| Kano | 基本型/期望型/兴奋型 | 体验与差异化 |
| 风险矩阵 | 概率 × 影响 | 安全/合规 |
| 依赖图 | 阻塞关系 | 平台基础能力 |

API 产品要特别考虑：

- **契约不可逆性**：越难改的决策，越应该提前；
- **采用摩擦**：一个文档改进可能比一个新端点更能提升激活；
- **迁移成本**：新版本会带来长期维护成本；
- **商业价值**：不是所有调用都值得支持；
- **合规期限**：监管截止日期可能压倒其他优先级。

### W.4.3 路线图的三种视图

```text
对外路线图：主题 + 时间窗口 + 状态（探索/计划/开发/已发布）
对内路线图：具体交付物 + 负责人 + 依赖 + 风险
技术路线图：契约、协议、迁移、基础设施、债务
```

对外路线图不要承诺具体日期，除非合同要求；对内路线图要能追踪到负责人和依赖。

### W.4.4 Beta 与 GA

```text
探索（Discovery） → 设计伙伴（Design Partner） → 私有 Beta
→ 公开 Beta → GA → 扩展 → 弃用
```

每个阶段要有：

- 进入条件；
- 退出标准；
- 支持的客户类型；
- SLA；
- 反馈机制；
- 破坏性变更政策；
- 文档与 SDK 状态。

Beta 不是“功能没做完就发布”。Beta 是“契约可能变化，但已有明确支持和迁移承诺”。

### W.4.5 设计伙伴计划

设计伙伴是早期采用者，不是免费测试员。一个好的计划包括：

- 明确的目标场景；
- 共同定义的验收标准；
- 定期反馈会议；
- 优先支持；
- 早期访问；
- 价格/合同安排；
- 退出机制；
- 公开引用许可。

设计伙伴的价值是验证任务、契约与价值主张，而不是收集“再加一个字段”的请求。

## W.5 开发者旅程

### W.5.1 八个阶段

```text
发现 → 评估 → 注册 → 首次调用 → 集成 → 上线 → 扩展 → 续费
```

| 阶段 | 开发者问题 | 产品动作 | 指标 |
|---|---|---|---|
| 发现 | 有没有解决我问题的 API？ | 搜索、内容、案例、对比页 | 流量、搜索排名 |
| 评估 | 能不能信任？好不好集成？ | 文档、沙箱、定价、SLA | 文档到注册转化 |
| 注册 | 如何开始？要信用卡吗？ | 自助注册、测试密钥 | 注册完成率 |
| 首次调用 | 能不能十分钟跑通？ | 快速开始、SDK、示例 | TTFC、首次成功率 |
| 集成 | 如何处理错误、重试、分页？ | 指南、错误目录、SDK | 集成完成率 |
| 上线 | 能不能稳定运行？ | 限流、SLA、监控、支持 | 生产密钥、活跃度 |
| 扩展 | 如何用更多？ | 用量视图、套餐、客户成功 | NRR、用量增长 |
| 续费 | 值不值得继续？ | 价值回顾、支持、路线图 | 留存、流失原因 |

### W.5.2 摩擦日志

安排团队成员（包括产品经理和工程师）亲自完成一次新客户接入，记录每一步：

```text
时间  步骤  预期  实际  摩擦  严重度  证据
10:00 注册  30 秒  2 分钟  邮箱验证延迟  P2  截图
10:05 找密钥 明显  藏在三级菜单  P1  录屏
10:12 首次调用 复制即可 示例过期  P0  报错
```

摩擦日志比“满意度调查”更能指导改进。每个摩擦点要有负责人和修复期限。

### W.5.3 TTFC 与 TTFV

- **TTFC（Time to First Call）**：从注册到第一次成功调用。
- **TTFV（Time to First Value）**：从注册到完成一个真实业务任务。
- **TTFI（Time to First Integration）**：从注册到集成上线。

TTFC 短不代表成功；有些产品 TTFC 只要 2 分钟，但 TTFV 需要两周。两个指标要一起看。

### W.5.4 入门检查清单

- [ ] 不需要信用卡即可试用（或明确说明为什么需要）。
- [ ] 测试密钥自动创建，权限最小但足够跑通示例。
- [ ] 快速开始 10 分钟内可完成。
- [ ] 示例可复制、可运行、与当前版本一致。
- [ ] 第一个错误有解释和修复建议。
- [ ] 沙箱可模拟成功、失败、限流、异步。
- [ ] 有下一步：Webhook、分页、错误处理、上线检查。
- [ ] 文档搜索能搜到错误码和端点。
- [ ] 支持入口明显，响应时间有承诺。

## W.6 DevRel 与开发者生态

### W.6.1 DevRel 的四种工作

| 工作 | 目标 | 产出 |
|---|---|---|
| 内容 | 让开发者找到并理解 | 教程、博客、视频、示例 |
| 社区 | 让开发者互相帮助 | 论坛、Slack、Discord、活动 |
| 产品反馈 | 把开发者声音带回产品 | 议题、优先级、设计评审 |
| 生态 | 让第三方围绕 API 构建 | 集成、插件、市场、合作伙伴 |

DevRel 不是“市场部的外包”，也不是“技术支持”。它连接产品、工程、市场与社区。

### W.6.2 内容组合

```text
入门：5 分钟快速开始、10 分钟教程
任务：如何分页、如何处理 Webhook 重试、如何做幂等
概念：状态机、权限模型、计量与计费
案例：某客户如何用 API 完成 X
变更：新功能、弃用、迁移
故障：常见错误、排障指南、事故复盘
```

内容要围绕任务，而不是围绕端点。一个“如何创建订单并处理支付失败”的教程，比十个端点说明更有用。

### W.6.3 社区运营

- 明确社区边界与行为准则；
- 有官方回答 SLA；
- 把重复问题沉淀为文档；
- 识别并培养活跃开发者；
- 定期办公时间；
- 公开路线图与变更；
- 不把社区当免费支持队列。

### W.6.4 生态与集成

生态集成的优先级：

1. 客户最常用的技术栈；
2. 客户最常集成的上游/下游系统；
3. 能显著降低集成成本的 SDK/插件；
4. 能带来新客户的渠道；
5. 能形成标准的开放协议。

不要为了“生态数量”做大量低质量集成。一个维护良好的官方 SDK，比十个无人维护的社区插件更有价值。

## W.7 定价、包装与销售协作

产品经理不需要成为定价专家，但必须参与：

- 计量单位是否可理解；
- 套餐是否匹配任务；
- 免费层是否会被滥用；
- 升级路径是否自然；
- 账单是否可解释；
- 销售折扣是否破坏毛利；
- 企业功能是否可单独购买。

与销售协作的关键问题：

1. 客户为什么买？为什么没买？
2. 客户拿什么和自建/竞品比较？
3. 哪个功能是“必须有的”，哪个是“锦上添花”？
4. 客户能接受的价格区间？
5. 采购流程与安全审查有哪些要求？
6. 客户最担心锁定/合规/支持中的哪一项？

### W.7.1 一个折扣审批示例

```text
标价：$120,000/年，含 50,000,000 次调用
客户要求：20% 折扣 + 80,000,000 次调用
预估交付成本：$30,000/年

方案 A（同意 20% 折扣，额度不变）：
  收入 $96,000；毛利 $66,000；毛利率 68.75%

方案 B（同意 20% 折扣，额度提高到 80M）：
  收入 $96,000；成本约 $42,000；毛利 $54,000；毛利率 56.25%

方案 C（拒绝折扣，改为 3 年承诺）：
  收入 $360,000；成本按年摊销；毛利更高，但锁定周期更长
```

审批要回答：

- 毛利是否低于底线？
- 折扣是否换取承诺、案例、渠道或多年合同？
- 超额单价是否覆盖边际成本？
- 是否会被其他客户复制？
- 合同是否允许涨价/调整计量口径？

不要让销售在“标价”与“成交价”之间自由浮动而没有成本依据。

定价的工程实现见[附录 V](v-metering-billing.md)，商业模式见[第 50 章](../part-7-business/50-business-models.md)，定价模型见[第 51 章](../part-7-business/51-pricing.md)。

## W.8 发布、反馈与迭代

### W.8.1 发布不是终点

每次发布都要设计：

- 目标用户；
- 成功指标；
- 反馈渠道；
- 支持准备；
- 文档/SDK 同步；
- 迁移/弃用计划；
- 回滚条件。

### W.8.2 反馈分类

| 类型 | 例子 | 处理 |
|---|---|---|
| 缺陷 | 端点返回 500 | 修复 |
| 文档 | 示例过期 | 更新 |
| 契约 | 字段语义不清 | 设计评审 |
| 功能 | 需要批量导入 | 路线图 |
| 体验 | 错误信息难懂 | DX 改进 |
| 商业 | 价格太高 | 定价/包装 |
| 合规 | 需要数据驻留 | 法务/架构 |

不要把全部反馈都变成功能请求。很多问题是文档、错误信息、示例或定价问题。

### W.8.3 反馈闭环

```text
收集 → 分类 → 评估 → 决策 → 实现 → 通知 → 度量
```

每个公开反馈应有状态。即使不实现，也要说明原因。开发者最怕的不是“不做”，而是“没有回应”。

## W.9 指标与实验

### W.9.1 指标分层

| 层级 | 指标 | 用途 |
|---|---|---|
| 北极星 | 成功任务数 / 成功调用数 | 客户价值 |
| 采用 | 注册、激活、TTFC、集成完成 | 漏斗 |
| 使用 | 活跃 Key、调用量、端点分布 | 产品使用 |
| 留存 | 租户/收入/用量留存 | 可持续性 |
| 扩展 | NRR、套餐升级、新项目 | 增长 |
| 质量 | 错误率、延迟、工单、SLO | 体验 |
| 商业 | 毛利、CAC、LTV、回本 | 经济性 |
| Agent | 任务成功率、工具正确率、人工介入率 | AI 消费者 |

指标定义、口径、数据源、负责人要写清楚。否则不同团队会给出不同数字。

### W.9.2 实验设计

API 产品可以做：

- 快速开始流程；
- 文档布局；
- 错误信息；
- SDK 默认值；
- 沙箱行为；
- 定价与包装；
- 限流阈值；
- Beta 准入。

实验要有：

- 假设；
- 主要指标与护栏指标；
- 样本量与实验周期；
- 分流单位（租户/用户/Key）；
- 停止条件；
- 伦理与合同约束。

不要对同一客户展示不同价格而不告知；不要违反合同；不要用实验掩盖可靠性问题。开关类型、稳定分桶、曝光日志、缓存串味与计费污染，见[附录 AK](ak-feature-flags-experiments-progressive-delivery.md)；沙箱与测试数据见[附录 AJ](aj-sandbox-mock-test-data.md)。

### W.9.3 实验的常见陷阱

- 指标太多，没有主指标；
- 样本量不足；
- 实验期太短，忽略季节性与学习效应；
- 分流不独立，租户内互相污染；
- 只看短期转化，忽略留存与支持成本；
- 实验组和对照组文档/版本不同；
- 把相关性当因果。

## W.10 组织与协作

### W.10.1 角色

| 角色 | 职责 |
|---|---|
| API 产品经理 | 任务、路线图、优先级、采用、商业 |
| 工程负责人 | 契约、实现、可靠性、性能、安全 |
| DX / 技术写作 | 文档、示例、SDK、门户、反馈 |
| DevRel | 内容、社区、生态、开发者反馈 |
| 支持 | 工单、排障、知识库、升级 |
| 销售 / 客户成功 | 商机、合同、续费、扩展 |
| 财务 | 计量、计价、账单、收入确认 |
| 法务 / 合规 | 合同、隐私、监管、条款 |
| 安全 | 威胁建模、审计、事件响应 |

小团队可以一人多角色，但职责要明确。

### W.10.2 API 委员会

API 委员会不是审批机关，而是：

- 维护风格指南；
- 评审高风险契约；
- 解决跨团队冲突；
- 管理例外；
- 推动迁移；
- 分享案例。

委员会要有明确的服务水平：多久评审、什么必须评审、什么可以自助。

### W.10.3 RACI 示例

| 活动 | PM | 工程 | DX | 安全 | 法务 | 财务 |
|---|---|---|---|---|---|---|
| 新 API 设计 | A | R | C | C | I | I |
| 契约评审 | C | R | C | C | I | I |
| 文档发布 | A | C | R | I | I | I |
| 定价发布 | R | C | C | I | C | A |
| 安全事件 | I | R | I | A | C | I |
| 弃用 | A | R | R | I | I | I |

（R=负责执行，A=最终负责，C=被咨询，I=被通知。）

### W.10.4 激励

如果团队只被奖励“发布新功能”，就不会投入文档、迁移、可靠性和支持。API 产品的考核应包含：

- 采用与激活；
- 留存与扩展；
- 可靠性；
- 支持成本；
- 迁移完成率；
- 开发者满意度；
- 毛利。

## W.11 反模式

- 把 API 当项目，发布即结束；
- 只收集功能请求，不做任务研究；
- 路线图只有新功能，没有 DX 与债务；
- 文档由最后一个人补；
- 快速开始需要信用卡或人工审批；
- 错误信息只有“Bad Request”；
- 沙箱与生产行为不一致；
- Beta 没有支持与迁移承诺；
- 设计伙伴变成免费外包；
- 定价与 API 计量脱节；
- 销售承诺未实现的功能；
- 指标只看注册数；
- 实验没有护栏指标；
- DevRel 只做内容，不反馈产品；
- API 委员会变成审批瓶颈；
- 只奖励发布，不奖励采用与留存。

## W.12 检查清单

### 发现与定义

- [ ] 目标客户与任务用 JTBD 写清楚。
- [ ] 访谈覆盖开发者、技术决策者、经济决策者。
- [ ] 识别机器消费者/Agent 的工具描述、schema、错误可恢复性与权限边界。
- [ ] 识别现有替代方案与切换成本。
- [ ] MVP 能端到端完成一个真实任务。
- [ ] API 表面有明确的产品原则与命名规范。
- [ ] 错误信息、文档、示例纳入设计评审。

### 路线图

- [ ] 路线图同时包含新能力、采用体验、基础债务。
- [ ] 优先级方法公开，考虑不可逆性与合规期限。
- [ ] 对外路线图不承诺未确定日期。
- [ ] Beta/GA 有进入/退出标准。
- [ ] 设计伙伴有明确目标与退出机制。

### 开发者旅程

- [ ] 团队亲自走通一次新客户接入。
- [ ] TTFC 与 TTFV 有定义与度量。
- [ ] 快速开始 10 分钟内可完成。
- [ ] 首错有解释与修复建议。
- [ ] 沙箱覆盖成功、失败、限流、异步。
- [ ] 支持入口与 SLA 明确。

### 生态与增长

- [ ] DevRel 工作有内容、社区、反馈、生态四类。
- [ ] 内容围绕任务，不围绕端点。
- [ ] 社区有行为准则与响应 SLA。
- [ ] 集成优先级基于客户技术栈与价值。
- [ ] 定价、包装、销售折扣有产品参与。
- [ ] 反馈有分类、状态与闭环。

### 指标与组织

- [ ] 指标有定义、口径、数据源、负责人。
- [ ] 实验有主指标、护栏指标、样本量与停止条件。
- [ ] RACI 明确，跨团队协作有约定。
- [ ] 考核包含采用、留存、可靠性、支持成本。
- [ ] API 委员会有服务水平，不是审批瓶颈。

## 设计练习

为一个“面向中小企业的电子发票 API”做产品管理练习：

- 目标客户：财务人员、外包会计、SaaS 开发者；
- 核心任务：开票、红冲、查询、导出、对接税务；
- 现有替代：手工开票、Excel、传统财务软件；
- 竞争：大型财务软件、免费工具、银行接口；
- 约束：税务合规、发票号码、数据保留、区域差异。

## 小结

- API 产品有契约、学习、商业三个表面，缺一不可。
- 从任务而不是端点出发；JTBD、访谈、摩擦日志比功能清单更有用。
- MVP 是端到端完成一个任务，不是一个端点。
- 路线图要同时投资新能力、采用体验与基础债务。
- 开发者旅程的每个阶段都有流失；TTFC 与 TTFV 要一起看。
- DevRel 连接内容、社区、反馈与生态，不是市场外包。
- 定价、计量、账单是产品的一部分，不是财务的事后工作。
- 指标要有定义、口径、负责人；实验要有护栏。
- 组织激励决定 API 是否会被长期运营。
