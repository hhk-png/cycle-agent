# 附录 X：遗留 API 现代化与迁移实战

> 大多数 API 设计不是在白纸上开始的，而是在一套运行了十年、没人完全理解、每天都在产生收入的系统上开始的。
> 本附录讨论如何盘点、映射、包装、迁移、切流和退役遗留 API。目标不是“重写得更漂亮”，而是在业务不停机的前提下，把旧契约安全地换成新契约。

相关章节：[第 5 章 风格选型](../part-1-foundations/05-style-selection.md) 的遗留协议小节、[第 11 章 版本化与兼容性](../part-1-foundations/11-versioning.md)、[第 38 章 发布、弃用与迁移](../part-4-engineering-product/38-release-deprecation.md)、[附录 K 更多协议与领域速览](k-more-domains-protocols.md)。

## X.1 遗留系统的真实形态

遗留系统不一定是“老代码”。它可能是：

- SOAP / WSDL 服务；
- ESB 上的消息流；
- 单体应用里的“接口层”；
- 存储过程 + 定时任务；
- 文件交换（SFTP、CSV、XML）；
- 主机/大型机事务；
- 厂商提供的 API；
- 屏幕抓取（screen scraping）；
- 一套没人敢改的 SDK；
- 多个版本的 REST 端点并存。

### X.1.1 为什么“重写”经常失败

| 失败原因 | 表现 |
|---|---|
| 低估隐藏语义 | 旧系统里的特殊分支、补丁、人工规则没有文档 |
| 低估数据质量 | 脏数据、重复、缺失、编码不一致 |
| 低估消费者 | 不知道谁在调用、用什么字段、何时调用 |
| 低估组织约束 | 旧系统由外包/离岸团队维护，知识不在内部 |
| 大爆炸切换 | 一次性切流，出问题无法回滚 |
| 双轨失控 | 新旧系统长期并存，口径越来越远 |
| 业务中断 | 迁移窗口与业务高峰冲突 |
| 激励错位 | 迁移团队与运维团队目标不一致 |

**原则：不要重写系统，重写契约；不要一次性切换，逐步替换。**

### X.1.2 现代化的目标

现代化不是“换成 REST/JSON”或“上云”。目标应该是：

- 契约更清晰、更稳定；
- 消费者更容易集成；
- 数据所有权更明确；
- 可靠性与可观测性更好；
- 合规与安全更容易证明；
- 总拥有成本更低；
- 为未来演进留出空间。

风格只是手段。一个语义清晰、稳定、可观测的 SOAP 服务，可能比一个混乱的 REST 服务更“现代”。

## X.2 盘点与评估

### X.2.1 盘点什么

| 资产 | 需要记录 |
|---|---|
| 端点 | 方法、路径、协议、版本、认证、限流 |
| 消费者 | 内部服务、合作伙伴、脚本、移动端、Agent |
| 用量 | 调用量、时段、峰值、增长趋势 |
| 关键性 | 收入影响、合规影响、故障影响 |
| 数据 | 实体、字段、敏感级别、保留期、驻留 |
| 依赖 | 数据库、消息、第三方、批处理 |
| 契约 | 是否有 schema、文档、测试、版本 |
| 运维 | 部署方式、监控、告警、值班 |
| 知识 | 谁维护、文档在哪、是否有原始团队 |

### X.2.2 消费者发现

很多迁移失败，是因为“不知道谁在用”。发现手段：

- 网关/负载均衡访问日志；
- API Key / OAuth client 清单；
- DNS / 证书 / 主机名；
- 数据库连接与调用记录；
- 合作伙伴合同与集成清单；
- SDK 下载与版本分布；
- 代码仓库搜索；
- 网络流量分析；
- 直接询问大客户。

对每个消费者记录：

```text
消费者 ID、类型、负责人、调用端点、字段使用、调用时间、
SLA、合同、迁移联系人、迁移风险
```

### X.2.3 评估矩阵

用“业务价值 × 变更成本”分四类：

```text
高价值 / 低成本：优先迁移
高价值 / 高成本：分阶段，先包装
低价值 / 低成本：批量清理
低价值 / 高成本：维持或退役
```

再加两个维度：

- **风险**：合规、资金、安全、客户影响；
- **可逆性**：切流后能否快速回滚。

### X.2.4 基线指标

迁移前要记录：

- 端点调用量与错误率；
- P50/P95/P99 延迟；
- 每消费者用量；
- 数据量、增长率、质量；
- 运维工单与事故；
- 成本；
- 契约测试覆盖；
- 文档完整度。

没有基线，就无法证明迁移改善了系统。

## X.3 契约映射

### X.3.1 语义映射优先于字段映射

旧系统到新系统的映射，不是“字段 A 改成字段 B”，而是语义对齐：

| 维度 | 问题 | 例子 |
|---|---|---|
| 实体 | 同一个词是否指同一件事？ | “客户”在旧系统是账户，新系统是组织 |
| 标识 | ID 是否稳定、唯一、可跨系统？ | 旧自增 ID vs 新 UUID |
| 状态 | 状态机是否一致？ | 旧 `1/2/3` vs 新 `ACTIVE/SUSPENDED` |
| 金额 | 单位、精度、币种？ | 分 vs 元，单币种 vs 多币种 |
| 时间 | 时区、格式、精度？ | 本地时间 vs UTC |
| 错误 | 错误码与可恢复性？ | SOAP Fault vs Problem Details |
| 分页 | offset vs cursor？ | 深分页行为不同 |
| 空值 | 缺失、空字符串、null 是否同义？ | 旧系统用 `""` 表示未设置 |
| 枚举 | 未知值如何处理？ | 旧客户端可能崩溃 |
| 权限 | 角色/范围/对象级？ | 旧系统只有功能级权限 |

### X.3.2 映射表模板

```yaml
entity: Order
source:
  system: legacy-oms
  table: T_ORDER
target:
  system: orders-api
  resource: Order
fields:
  - source: ORDER_NO
    target: id
    transform: "prefix('ord_') + lower(ORDER_NO)"
    notes: "旧 ID 暴露给合作伙伴，必须保持可映射"
  - source: ORDER_STAT
    target: status
    transform:
      "10": "PENDING"
      "20": "CONFIRMED"
      "30": "SHIPPED"
      "40": "CANCELLED"
    unknown: "map_to_UNKNOWN_and_keep_raw"
    notes: "读接口返回 UNKNOWN + rawStatus；写接口才拒绝未知值"
  - source: TOTAL_AMT
    target: total.amount
    transform: "round_half_up(decimal(TOTAL_AMT) * 100)"
    notes: "旧系统单位为元，新系统为分；显式舍入到整数最小单位"
  - source: CREATE_TIME
    target: createdAt
    transform: "parse('yyyy-MM-dd HH:mm:ss', 'Asia/Shanghai') -> UTC"
```

映射表要版本化，并成为测试与文档的共同来源。

### X.3.3 未知值与兼容性

旧系统可能有新系统不认识的枚举值。处理策略：

1. **拒绝**：返回明确错误，要求人工处理；
2. **映射到 `UNKNOWN`**：保留原值在扩展字段；
3. **透传**：新系统不解释，只存储与返回；
4. **丢弃**：仅当确认无业务影响。

对外 API 推荐：

- 新系统定义稳定枚举；
- 对未知值返回 `UNKNOWN` + `rawStatus`；
- 文档说明未知值的处理；
- 不要因为未知值让整个响应失败。

### X.3.4 错误映射

旧系统错误可能是：

```text
SOAP Fault: code=SERVER, string="ORA-00001: unique constraint violated"
```

不要仅凭 `ORA-00001` 就断言“订单重复”：任何唯一约束都可能抛出它。只有当约束名/操作明确指向订单号时，才映射为具体业务错误；否则返回安全的通用错误，并把原始错误写入内部日志。

```json
{
  "type": "https://errors.example.com/duplicate-order",
  "title": "订单已存在",
  "status": 409,
  "code": "ORDER_ALREADY_EXISTS",
  "detail": "订单号 ord_123 已存在。",
  "meta": { "orderId": "ord_123" },
  "requestId": "req_abc"
}
```

如果无法确认约束含义：

```json
{
  "type": "https://errors.example.com/conflict",
  "title": "请求与当前资源状态冲突",
  "status": 409,
  "code": "CONFLICT",
  "detail": "请求无法完成，请重新读取资源后重试。",
  "requestId": "req_abc"
}
```

注意：`SOAP Fault code=SERVER` 本身是服务端错误，不应自动变成 409。映射要基于业务语义，而不是错误码字面。

映射要点：

- 不泄露数据库错误、堆栈、内部主机；
- 保留可操作信息；
- 区分客户端错误与服务端错误；
- 区分可重试与不可重试；
- 旧错误码与新错误码有对照表；
- 日志保留原始错误，响应只给安全信息。

### X.3.5 幂等与重试映射

旧系统可能没有幂等键。迁移时：

- 在新 API 增加 `Idempotency-Key`；
- 用旧业务键（订单号、请求号）做自然幂等；
- 对无法幂等的操作，明确“最多一次”或“至少一次”；
- 重试策略与旧系统行为对齐；
- 不要假设旧系统支持安全重试。

### X.3.6 分页与排序映射

旧系统：

```text
page=1&size=20&sort=CREATE_TIME desc
```

新系统：

```text
cursor=...&limit=20&sort=-createdAt
```

迁移时要处理：

- 默认排序变化；
- 空值排序；
- 相同排序键的稳定性；
- 深分页性能；
- 总数是否可得；
- 旧客户端是否依赖页码。

可以提供兼容层：旧参数映射到新游标，但明确限制深分页。

### X.3.7 认证与授权映射

旧系统可能是：

- 共享 API Key；
- IP 白名单；
- WS-Security；
- 会话 Cookie；
- 基本认证；
- 自定义签名。

新系统可能是：

- OAuth 2.1；
- mTLS；
- JWT；
- DPoP；
- 工作负载身份。

迁移策略：

- 先支持旧认证，逐步引入新认证；
- 双认证并存期；
- 认证失败信息可操作；
- 密钥/证书轮换；
- 权限模型映射；
- 审计与回滚。

## X.4 目标架构

### X.4.1 四种包装方式

| 方式 | 说明 | 适用 |
|---|---|---|
| Facade（门面） | 新 API 调用旧系统 | 快速提供现代契约 |
| Adapter（适配器） | 新旧协议/模型转换 | 协议差异大 |
| Proxy（代理） | 透传请求，少量改写 | 低风险、渐进迁移 |
| Strangler（绞杀者） | 新实现逐步替换旧功能 | 长期现代化 |

### X.4.2 防腐层（Anti-Corruption Layer）

防腐层隔离旧系统的模型、术语与错误，避免污染新领域：

```text
新 API → 应用服务 → 防腐层 → 旧系统客户端 → 旧系统
```

防腐层负责：

- 模型转换；
- 状态映射；
- 错误映射；
- 幂等与重试；
- 超时与熔断；
- 日志与追踪；
- 兼容旧系统的特殊行为。

不要把旧系统的字段直接透传到新 API。否则新契约会被旧模型绑架。

### X.4.3 Strangler Fig

```text
阶段 1：新 API 门面 → 旧系统
阶段 2：新实现处理部分读/写 → 旧系统处理剩余
阶段 3：新实现处理大部分流量 → 旧系统只读/兜底
阶段 4：旧系统退役
```

关键：

- 路由按端点/租户/功能切片；
- 新旧实现共享同一契约；
- 数据双写/回填/对账；
- 可随时切回；
- 旧系统冻结新功能，只修缺陷。

### X.4.4 Branch by Abstraction

在代码内部抽象出接口，新旧实现并存：

```text
OrderService (interface)
├── LegacyOrderService
└── NewOrderService
```

通过开关/配置选择实现。适合单体内部重构，不改变外部契约。

### X.4.5 事件与数据所有权

迁移过程中，数据所有权要明确：

- 哪个系统是写入权威？
- 哪个系统是读取权威？
- 事件由谁发布？
- 旧系统是否还需要数据？
- 如何回填与对账？
- 迁移完成后谁拥有数据？

不要出现“两个系统都写、没人知道谁对”的双主状态。

## X.5 迁移模式

### X.5.1 并行运行与影子流量

```text
生产流量 → 旧系统（权威）
          └→ 新系统（影子，异步复制请求）
```

比较：

- 响应结构；
- 业务结果；
- 延迟；
- 错误；
- 数据写入。

影子流量不应对生产产生副作用。对写操作要使用沙箱/测试租户/只读模式。

### X.5.2 双写

```text
写请求 → 旧系统
       └→ 新系统
```

风险：

- 一边成功、一边失败；
- 顺序不一致；
- 重复写入；
- 数据冲突；
- 回滚困难。

建议：

- 双写只作为过渡；
- 明确主写与从写；
- 从写失败可重试/补偿；
- 有对账与告警；
- 尽快收敛到单写。

### X.5.3 CDC 与回填

```text
旧数据库 → CDC（Debezium 等）→ 事件流 → 新系统
```

适合：

- 读迁移；
- 数据同步；
- 搜索索引；
- 分析库。

注意：

- schema 变化；
- 删除/更新语义；
- 事务边界；
- 重复与乱序；
- 初始快照与增量衔接；
- 数据脱敏。

回填：

```text
1. 冻结/标记迁移窗口
2. 导出旧数据
3. 转换/清洗
4. 批量导入新系统
5. 校验总量与抽样
6. 开启增量同步
7. 对账
```

### X.5.4 灰度切流

按以下维度逐步切：

- 租户；
- 地区；
- 端点；
- 百分比；
- 请求头/客户端版本；
- 内部员工 → 设计伙伴 → 普通客户。

每一阶段：

- 有明确进入/退出标准；
- 监控关键指标；
- 可一键回滚；
- 记录切流比例；
- 通知支持团队。

### X.5.5 蓝绿与金丝雀

| 模式 | 说明 | 适用 |
|---|---|---|
| 蓝绿 | 两套环境，整体切换 | 低耦合、可快速回滚 |
| 金丝雀 | 小比例流量先切 | 高风险、需要观察 |
| 按租户 | 大客户单独切 | B2B、合同约束 |
| 按端点 | 读先切、写后切 | 降低风险 |

### X.5.6 迁移模式对比

| 模式 | 风险 | 成本 | 回滚 | 适用 |
|---|---|---|---|---|
| 门面 | 低 | 低 | 容易 | 快速现代化 |
| 影子流量 | 低 | 中 | 容易 | 读写验证 |
| 双写 | 中高 | 高 | 难 | 过渡期 |
| CDC | 中 | 中 | 中 | 读迁移/同步 |
| 灰度切流 | 中 | 中 | 容易 | 生产切换 |
| 蓝绿 | 中 | 高 | 容易 | 整体替换 |
| 大爆炸 | 高 | 高 | 很难 | 不推荐 |

## X.6 数据迁移与对账

### X.6.1 数据迁移步骤

```text
1. 数据画像：量、分布、质量、敏感级别
2. Schema 映射：字段、类型、约束、默认值
3. 清洗：去重、补全、格式统一、编码
4. 转换：ID、金额、时间、枚举、关联关系
5. 导入：批量、分片、限速、可恢复
6. 校验：行数、总额、抽样、业务不变量
7. 增量：CDC/双写/事件
8. 对账：持续比较
9. 切换：读写权威
10. 清理：旧数据、临时表、开关
```

### X.6.2 对账维度

| 维度 | 检查 |
|---|---|
| 数量 | 行数、订单数、用户数 |
| 金额 | 总额、分币种、分状态 |
| 关系 | 外键完整性、孤儿记录 |
| 状态 | 状态分布、非法状态 |
| 时间 | 创建/更新时间范围 |
| 抽样 | 随机样本逐字段比较 |
| 业务不变量 | 库存不为负、账本平衡 |

对账结果要可重复、可导出、可追踪到差异记录。

### X.6.3 差异处理

差异类型：

- 缺失；
- 多余；
- 字段不一致；
- 金额/数量不一致；
- 状态不一致；
- 关联丢失；
- 编码/格式差异。

处理：

- 自动修复（明确规则）；
- 人工复核；
- 记录原因；
- 不回写污染源；
- 对账报告归档。

### X.6.4 切流后的数据一致性

切流后：

- 新系统成为写入权威；
- 旧系统只读或退役；
- 停止双写；
- 保留回滚窗口；
- 监控数据差异；
- 处理迟到/补偿；
- 更新备份与恢复流程。

## X.7 切流与退役

### X.7.1 切流前检查

- [ ] 新系统通过功能、契约、性能、安全测试。
- [ ] 消费者已知情并有迁移指南。
- [ ] 监控、告警、值班就绪。
- [ ] 回滚方案演练过。
- [ ] 数据对账通过。
- [ ] 限流、配额、计费已配置。
- [ ] 文档、SDK、示例已更新。
- [ ] 支持团队已培训。
- [ ] 合同/合规已确认。
- [ ] 切流窗口避开业务高峰。

### X.7.2 切流执行

```text
T-7  最终通知；冻结旧系统新功能
T-1  数据快照；对账；检查回滚包
T0   切流 1%（内部/设计伙伴）
T+1h 观察错误率、延迟、业务指标
T+1d 切流 10%
T+3d 切流 50%
T+7d 切流 100%
T+14d 旧系统只读
T+30d 旧系统退役
```

时间表按风险调整，不要机械照搬。

### X.7.3 回滚

回滚触发：

- 错误率超过阈值；
- 核心业务失败；
- 数据不一致；
- 性能不可接受；
- 安全事件；
- 大客户投诉。

回滚步骤：

```text
1. 停止继续切流
2. 冻结新系统写入与双写，等待在途请求结束
3. 把写入权威切回旧系统
4. 校验/对账新系统已写入的数据
5. 通知客户与支持
6. 观察指标
7. 复盘并修复后再重新切流
```

顺序不能反：如果先切回旧系统、再停止新系统写入，切换窗口内可能有请求同时写两边，造成数据分裂。

回滚不等于“什么都没发生”：新系统可能已写入部分数据，需要补偿/对账。

### X.7.4 退役

退役清单：

- [ ] 所有消费者已迁移。
- [ ] 旧端点调用量为零或已确认例外。
- [ ] 数据已归档/迁移。
- [ ] 凭证/证书已吊销。
- [ ] DNS/域名/负载均衡已清理。
- [ ] 监控/告警已下线。
- [ ] 文档标记历史。
- [ ] 合同/合规已关闭。
- [ ] 备份保留策略明确。
- [ ] 团队知识已转移。

## X.8 组织与治理

### X.8.1 迁移团队与运维团队

- 迁移团队负责设计与执行；
- 运维团队负责稳定性与值班；
- 两者要有共同目标与交接机制；
- 不要让迁移团队“扔下就跑”；
- 旧系统知识要显式转移。

### X.8.2 冻结与例外

迁移期间：

- 旧系统冻结新功能，只修缺陷与安全；
- 例外要记录、审批、限期；
- 新需求优先在新系统实现；
- 避免“旧系统又长出新分支”。

### X.8.3 沟通

- 对外：时间表、影响、迁移指南、支持渠道；
- 对内：状态、风险、依赖、决策；
- 对高管：业务影响、成本、里程碑；
- 对支持：常见问题、升级路径、话术。

### X.8.4 风险登记

| 风险 | 概率 | 影响 | 缓解 | 负责人 |
|---|---|---|---|---|
| 大客户拒绝迁移 | 中 | 高 | 专属支持、合同条款 | 客户成功 |
| 数据不一致 | 中 | 高 | 对账、回填、回滚 | 数据 |
| 切流后性能下降 | 中 | 中 | 压测、灰度、容量 | 工程 |
| 旧系统知识丢失 | 高 | 中 | 文档、访谈、结对 | 架构 |
| 合规审批延迟 | 中 | 高 | 提前沟通、证据准备 | 合规 |

### X.8.5 决策记录

每个关键决策写 ADR：

- 为什么迁移；
- 目标与非目标；
- 备选方案；
- 选择理由；
- 后果与失效条件；
- 回滚条件。

ADR 让后来者理解决策背景，而不是只看到结果。

## X.9 三个案例

### X.9.1 SOAP 保险保单 API → REST/JSON

**背景**：

- 旧系统 SOAP/WSDL，字段数百个；
- 合作伙伴使用不同子集；
- 错误以 SOAP Fault 返回；
- 认证用 WS-Security；
- 批处理通过 SFTP。

**现代化**：

1. 盘点合作伙伴与字段使用；
2. 定义保单、投保人、保障、理赔资源；
3. 防腐层映射 SOAP；
4. 新 REST API 先做门面；
5. 逐步把读迁到新服务；
6. 写操作双写 + 对账；
7. 合作伙伴按租户灰度；
8. 旧 SOAP 只读 6 个月后退役。

**关键教训**：

- 字段使用分析比 WSDL 更重要；
- 旧错误码要映射，不要直接透传；
- 保单状态机必须显式建模；
- 合作伙伴迁移需要专属支持；
- 批处理不能忘，否则迁移不完整。

### X.9.2 单体订单模块 → 领域 API

**背景**：

- 单体应用，订单、库存、支付、发货共用数据库；
- 订单表被多个模块直接读写；
- 没有明确事务边界；
- 发布一次影响全站。

**现代化**：

1. 识别订单聚合与不变量；
2. 先做订单读 API；
3. 写路径通过防腐层调用单体；
4. 逐步把库存预占、支付、发货拆为独立服务；
5. 用 Outbox/事件同步；
6. 双写 + 对账；
7. 按流量灰度；
8. 最后迁移数据所有权。

**关键教训**：

- 不要先拆数据库；
- 先明确聚合与不变量；
- 读写分离是过渡手段，不是终点；
- 分布式事务尽量用 Saga/Outbox；
- 组织边界要跟上。

### X.9.3 厂商 API 替换

**背景**：

- 使用某厂商的短信/地图/支付 API；
- 厂商涨价/服务质量下降/合规变化；
- 需要多供应商冗余。

**现代化**：

1. 定义内部统一 API（防腐层）；
2. 适配多个厂商；
3. 按国家/渠道/成本路由；
4. 统一错误与重试；
5. 对账与用量；
6. 灰度切换；
7. 保留回退。

**关键教训**：

- 不要把厂商字段透传到业务；
- 统一语义比统一协议更重要；
- 多供应商增加复杂度，要有路由与对账；
- 合同与数据驻留要提前确认；
- 退出策略要在合同中写明。

## X.10 反模式

- 大爆炸重写；
- 没有消费者清单就切流；
- 把旧字段直接透传到新 API；
- 新旧系统双主写入，没有对账；
- 只迁移读，忘记写/批处理/报表；
- 迁移期间旧系统继续加新功能；
- 没有回滚演练；
- 没有数据质量评估；
- 用“现代化”掩盖业务重构；
- 只关注协议，不关注语义；
- 迁移完成后不退役旧系统；
- 旧系统知识没有转移；
- 没有基线指标，无法证明改善；
- 合同/合规最后才介入。

## X.11 检查清单

### 盘点

- [ ] 端点、消费者、用量、关键性、数据、依赖已盘点。
- [ ] 消费者有负责人、联系人与迁移风险。
- [ ] 基线指标已记录。
- [ ] 业务价值/变更成本/风险/可逆性已评估。

### 契约

- [ ] 实体、标识、状态、金额、时间、错误、分页、空值、枚举、权限有映射。
- [ ] 未知值处理策略明确。
- [ ] 错误映射不泄露内部信息。
- [ ] 幂等与重试语义明确。
- [ ] 认证/授权迁移路径明确。
- [ ] 防腐层隔离旧模型。

### 迁移

- [ ] 门面/适配器/Strangler 方案已选择。
- [ ] 数据所有权与写入权威明确。
- [ ] 双写/CDC/回填/对账方案可行。
- [ ] 灰度维度与回滚方案明确。
- [ ] 影子流量不产生生产副作用。
- [ ] 切流前检查清单完成。

### 数据

- [ ] 迁移团队与运维团队职责明确。
- [ ] 旧系统冻结新功能。

- [ ] 风险登记与 ADR 完整。

## 小结

- 遗留系统现代化不是重写，而是逐步替换契约与实现。
- 先盘点消费者、用量、数据与依赖，再谈技术方案。
- 语义映射优先于字段映射；防腐层隔离旧模型。
- 门面/适配器/Strangler 比大爆炸更安全。
- 数据迁移的核心是对账与可回滚，不是导入速度。
- 灰度切流、影子流量、双写、CDC 各有代价，不要混用而不对账。
- 旧系统要冻结、退役、清理，否则迁移永远不会结束。
- 组织、合同、合规与知识转移，和技术方案同等重要。
