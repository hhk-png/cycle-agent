# 附录 L：移动端、离线优先与同步 API

> 移动端 API 不是“把桌面 API 缩小”。弱网、断网、后台限制、本地缓存、冲突合并，会改变契约本身。本附录补齐正文未展开的离线同步设计。

## L.1 为什么移动端需要不同的契约

移动端与服务器之间不是稳定链路，而是：

- 网络在 4G/5G/Wi-Fi/无网之间切换；
- 延迟从 20ms 到数秒；
- 连接可能被系统挂起；
- 请求可能发出但响应丢失；
- 用户可能在电梯、地铁、飞机上操作；
- 电量与流量有限；
- 应用可能几天不打开；
- 多个设备可能同时修改同一数据。

这些约束会直接影响 API 设计：

- 不能假设“写成功后立即可读”；
- 不能假设“请求只发一次”；
- 不能假设“客户端总能连上”；
- 不能假设“只有一个客户端”；
- 不能假设“时间戳可信”。

### 三种客户端模型

| 模型 | 数据所在 | 断网行为 | 复杂度 |
|---|---|---|---|
| 在线优先 | 服务器 | 不可用 | 低 |
| 缓存优先 | 本地缓存 + 服务器 | 只读 | 中 |
| 离线优先 | 本地数据库 | 可读写，稍后同步 | 高 |

离线优先不是所有产品都需要。IM、笔记、现场作业、POS、物流、医疗记录通常需要；普通内容浏览可能只需要缓存优先。

## L.2 离线优先的基本架构

```text
UI
 ↓
本地数据库（SQLite/Core Data/IndexedDB）
 ↓
同步引擎（Sync Engine）
 ↓
网络层（HTTP/WebSocket）
 ↓
服务端 API + 变更日志
```

关键组件：

- **本地数据库**：持久化业务数据；
- **变更队列（outbox）**：记录本地未同步的写操作；
- **同步游标**：记录已拉取到的位置；
- **冲突解决**：合并本地与服务端变更；
- **网络监听**：在线/离线切换；
- **后台任务**：重试、拉取、推送。

### 本地 ID 与服务器 ID

离线创建的资源在服务器分配 ID 之前就需要被引用：

```json
{
  "id": "local_01J...",
  "clientId": "client_123",
  "serverId": null,
  "syncStatus": "PENDING"
}
```

两种策略：

1. **客户端生成全局 ID**（UUIDv7/ULID）：服务器接受客户端 ID，简单；
2. **本地临时 ID + 服务器 ID 映射**：离线创建后用映射表替换。

推荐客户端生成 ID，但服务端必须：

- 校验格式；
- 防止冲突；
- 记录 `clientId`；
- 幂等处理重复提交。

## L.3 同步协议设计

### 拉取（Pull）

```http
GET /sync/changes?cursor=...
```

```json
{
  "changes": [
    { "entity": "note", "id": "note_1", "version": 5, "deleted": false, "data": {...} },
    { "entity": "note", "id": "note_2", "version": 3, "deleted": true, "data": null }
  ],
  "nextCursor": "c_123",
  "hasMore": true
}
```

要点：

- 游标不透明；
- 变更按顺序；
- 包含删除（tombstone）；
- 包含版本；
- 分页；
- 租户隔离；
- 权限过滤；
- 支持全量重置。

### 推送（Push）

```http
POST /sync/changes
```

```json
{
  "clientId": "client_123",
  "changes": [
    {
      "operationId": "op_01J...",
      "entity": "note",
      "id": "note_1",
      "baseVersion": 4,
      "data": { "title": "..." },
      "clientTimestamp": "2026-11-26T10:00:00Z"
    }
  ]
}
```

响应：

```json
{
  "results": [
    {
      "operationId": "op_01J...",
      "status": "APPLIED",
      "version": 5
    },
    {
      "operationId": "op_01K...",
      "status": "CONFLICT",
      "serverVersion": 6,
      "serverData": {...}
    }
  ],
  "nextCursor": "c_124"
}
```

### 同步状态

```text
IDLE → PULLING → PUSHING → APPLYING → IDLE
         │          │          │
         └→ FAILED  └→ FAILED  └→ FAILED
```

失败要：

- 退避重试；
- 区分网络/认证/冲突；
- 不丢本地变更；
- 可手动重试；
- 可查看状态。

## L.4 冲突解决

### 冲突的来源

- 两个设备同时修改；
- 离线修改后服务器已变；
- 删除与修改冲突；
- 权限变更；
- 版本回退。

### 策略一：最后写入胜出（LWW）

```text
选择 updatedAt 较新的版本
```

优点：简单。缺点：

- 依赖时钟；
- 可能丢失修改；
- 不适合协作编辑。

### 策略二：版本号/CAS

```json
{
  "id": "note_1",
  "baseVersion": 4,
  "data": {...}
}
```

服务端：

- 版本匹配 → 应用；
- 不匹配 → 409 + 当前版本；
- 客户端合并后重试。

适合：

- 单用户多设备；
- 冲突不频繁；
- 可提示用户。

### 策略三：字段级合并

```text
本地修改 title；
服务端修改 body；
合并两者。
```

需要：

- 字段级版本；
- 合并规则；
- 冲突字段提示。

### 策略四：CRDT

CRDT（Conflict-free Replicated Data Type）让副本最终一致：

- G-Counter；
- LWW-Register；
- OR-Set；
- RGA/Logoot 序列。

适合：

- 协同编辑；
- 离线多设备；
- 高频并发。

代价：

- 元数据大；
- 实现复杂；
- 删除/垃圾回收；
- 语义限制。

### 策略五：OT

OT（Operational Transformation）通过变换操作解决并发：

- 适合文本编辑；
- 需要中心服务器；
- 实现复杂；
- 与 CRDT 各有适用。

### 策略选择

| 场景 | 推荐 |
|---|---|
| 单用户多设备 | 版本号 + 提示 |
| 低频协作 | 字段级合并 |
| 高频协同编辑 | CRDT/OT |
| 简单设置 | LWW |
| 金融/库存 | 服务端裁决，不接受客户端合并 |

## L.5 删除与墓碑

离线客户端需要知道“某条数据被删除了”，否则会把它当成“尚未同步的新数据”重新上传。

```json
{
  "id": "note_2",
  "deleted": true,
  "deletedAt": "2026-11-26T10:00:00Z",
  "version": 7
}
```

墓碑需要：

- 保留一段时间；
- 定期清理；
- 客户端确认后才可物理删除；
- 防止“删除后复活”。

## L.6 增量同步与全量重置

### 增量

- 游标；
- 变更日志；
- 分页；
- 顺序；
- 压缩。

### 全量

当游标过期或客户端数据损坏：

```http
GET /sync/snapshot
```

```json
{
  "snapshotId": "snap_123",
  "downloadUrl": "https://...",
  "expiresAt": "...",
  "checksum": "sha256:..."
}
```

客户端：

1. 下载快照；
2. 校验；
3. 替换本地数据；
4. 从快照游标继续增量。

## L.7 后台同步与推送

### 后台限制

- iOS 后台任务有时间限制；
- Android 有 Doze/App Standby；
- 系统可能杀掉进程；
- 网络可能被限制。

设计：

- 同步可中断；
- 可恢复；
- 不依赖长时间后台；
- 使用系统调度；
- 推送唤醒。

### 推送通知

推送用于：

- 告知有新数据；
- 触发同步；
- 提醒用户；
- 不用于传输大量数据。

推送应：

- 可去重；
- 可折叠；
- 不包含敏感信息；
- 可关闭；
- 有兜底轮询。

### 网络感知

- Wi-Fi vs 蜂窝；
- 漫游；
- 计费网络；
- 低数据模式；
- 离线模式。

客户端应：

- 大文件只在 Wi-Fi；
- 尊重用户设置；
- 显示同步状态；
- 允许手动同步。

## L.8 幂等与重复提交

离线队列可能重复提交：

- 网络超时；
- 应用重启；
- 队列重放；
- 多设备。

每个变更应有：

```json
{
  "operationId": "op_01J...",
  "idempotencyKey": "op_01J..."
}
```

服务端：

- 按 `operationId` 去重；
- 返回原结果；
- 记录已处理；
- 保留足够长时间。

## L.9 安全与隐私

离线数据在设备上：

- 可能被窃取；
- 可能被备份；
- 可能被其他应用读取；
- 可能包含敏感信息。

措施：

- 本地加密；
- 安全存储（Keychain/Keystore）；
- 远程擦除；
- 会话过期；
- 生物识别；
- 最小化本地数据；
- 退出登录时清理；
- 备份策略。

同步传输：

- TLS；
- 令牌；
- 租户隔离；
- 字段级权限；
- 审计。

## L.12 小结

- 移动端 API 要面对弱网、断网、后台限制和多设备。
- 离线优先需要本地数据库、变更队列、同步游标和冲突解决。
- 客户端生成 ID 可以简化离线创建，但服务端要幂等。
- 冲突策略取决于业务：LWW、版本号、字段合并、CRDT/OT。
- 删除需要墓碑，否则会“复活”。
- 后台同步要可中断、可恢复，推送只做通知。
- 本地数据必须加密，退出要清理。
