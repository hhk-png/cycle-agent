# 附录 N：API 合同、SLA 与采购条款

> 技术契约之外，还有一层法律与采购契约。它决定“承诺是否可执行、事故谁负责、数据归谁、如何退出”。本附录面向技术负责人、商业化负责人和法务协作。

## N.1 API 合同的分层

一个企业级 API 合作通常包含：

| 文件 | 作用 | 谁关心 |
|---|---|---|
| 服务条款（ToS） | 使用规则、禁止行为、责任限制 | 法务、客户 |
| 订单表单（Order Form） | 套餐、价格、期限、数量 | 商务、财务 |
| SLA | 可用性、延迟、赔偿 | 客户、SRE |
| 数据处理协议（DPA） | 数据用途、留存、跨境、子处理者 | 法务、安全 |
| 安全附件 | 加密、访问控制、审计、事件通知 | 安全 |
| 支持附件 | 响应时间、渠道、升级路径 | 支持、客户成功 |
| 可接受使用政策（AUP） | 滥用、爬取、转售、内容限制 | 法务、风控 |

技术团队需要参与的不是全部，但必须确保：

- SLA 的 SLI 可测量；
- DPA 的数据流可实现；
- 安全附件有对应控制；
- 支持承诺有值班能力；
- 退出条款有导出接口。

## N.2 SLA 的写法

### 可用性

```text
月可用性 = 1 - 不可用分钟数 / 总分钟数
```

必须定义：

- 什么算“不可用”；
- 哪些请求计入；
- 维护窗口是否排除；
- 第三方依赖是否免责；
- 测量点在哪里（网关/服务/客户端）。

### 延迟

```text
P95 < 300ms
```

必须定义：

- 测量端点；
- 请求类型；
- 区域；
- 是否包含网络；
- 是否包含客户端错误。

### 错误率

```text
5xx 比例 < 0.1%
```

必须定义：

- 分母；
- 是否排除 4xx；
- 是否排除限流；
- 是否按端点加权。

### 赔偿

```text
可用性 < 99.9% → 返还月费 10%
可用性 < 99.0% → 返还月费 25%
可用性 < 95.0% → 返还月费 50%
```

赔偿应：

- 有上限（通常不超过月费）；
- 有申请流程；
- 有时限；
- 不与其它赔偿重复；
- 不构成唯一救济。

### 排除项

- 客户误用；
- 客户网络；
- 第三方依赖；
- 不可抗力；
- 计划维护；
- 免费层；
- 实验性功能；
- 客户未升级到受支持版本。

## N.3 DPA 与数据条款

### 数据角色

- 控制者（Controller）；
- 处理者（Processor）；
- 子处理者（Sub-processor）。

API 提供方通常是处理者，但某些场景可能是控制者（如风控数据）。

### 必须明确

- 数据用途；
- 数据类别；
- 数据主体；
- 保留期限；
- 删除时机；
- 跨境传输机制；
- 子处理者清单与变更通知；
- 审计权；
- 事件通知时限；
- 协助义务（DSAR、DPIA）。

### 数据驻留

```text
数据存储区域：中国境内
备份区域：中国境内
支持访问：仅境内人员
```

技术实现：

- 区域化部署；
- 数据不跨区复制；
- 日志不跨区；
- 密钥不跨区；
- 支持人员访问控制。

### 监管矩阵

API 合同很少只受一部法律约束。下面这张表用于识别“哪些条款不是法务偏好，而是硬约束”：

| 法规/标准 | 适用 | 对 API 合同的典型影响 |
|---|---|---|
| GDPR（欧盟） | 处理欧盟数据主体数据 | DPA、SCC、DSAR、72 小时泄露通知、DPIA、数据最小化 |
| UK GDPR | 英国数据 | 与 GDPR 类似，但传输机制与监管机构不同 |
| CCPA/CPRA（美国加州） | 加州居民数据 | 披露、删除、更正、退出“出售/共享”、服务提供商条款 |
| PIPL（中国） | 中国境内个人信息 | 单独同意、跨境评估/标准合同、境内存储、个人信息保护影响评估 |
| LGPD（巴西） | 巴西数据 | 法律基础、数据主体权利、DPO、跨境传输 |
| DPDP（印度） | 印度数字个人数据 | 同意、目的限制、数据受托人义务 |
| HIPAA（美国医疗） | PHI | BAA、最小必要、审计、泄露通知、加密 |
| PCI DSS 4.0.1 | 持卡人数据 | 范围、分段、令牌化、日志、MFA、脚本完整性 |
| SOC 2 / ISO 27001 | 企业采购 | 控制证据、审计报告、持续监控 |
| ISO 27701 | 隐私管理 | 隐私控制与 DPA 证据 |
| EU AI Act | AI 系统/通用模型 | 风险分级、透明度、评估、人类监督、事件报告；高风险时间表经 2026 年 Omnibus 调整 |
| DSA / DMA | 平台服务 | 研究者数据访问、商业用户 API、互操作、透明度 |
| DORA | 欧盟金融实体/关键 ICT 提供商 | ICT 风险、事件报告、第三方登记、韧性测试、退出策略 |
| NIS2 | 欧盟关键/重要实体 | 风险管理、供应链安全、24/72 小时/月报（按国家转化） |
| EU Data Act | 欧盟云/数据处理服务 | 开放接口、切换、导出、费用透明与逐步禁止切换费 |
| PSD2 / PSD3 / PSR | 欧盟支付 | 开放银行、SCA、TPP 牌照、同意管理；PSD3/PSR 处于立法收尾阶段 |
| MiFID II / EMIR | 金融服务 | 交易报告、记录保留、最佳执行 |
| FedRAMP / CJIS / IRAP | 公共部门 | 云安全授权、数据驻留、人员审查 |

使用方法：

1. 先画数据流：哪些数据、从哪来、到哪去、存多久；
2. 标记每个数据集的监管属性（个人数据、健康、支付、未成年人、出口管制）；
3. 找出“最严”的约束，而不是逐条满足互相冲突的条款；
4. 把约束映射到技术能力：区域化部署、字段级加密、审计日志、删除 API、同意记录；
5. 在合同中写明责任边界、协助义务、通知时限与审计权。

一个常见错误是把“合规”写成一句“供应商应遵守所有适用法律”。这句话既不可验证，也无法在事故时指导行动。可执行的条款应该说明：什么事件、多久通知、提供什么证据、谁来承担成本。

如何把这些条款映射到 API 能力、审计证据与运行流程，见[附录 T](t-compliance-engineering.md)。

## N.4 安全附件

应覆盖：

- 加密（传输/静态）；
- 身份与访问控制；
- 多因素认证；
- 漏洞管理；
- 渗透测试；
- 事件响应；
- 业务连续性；
- 供应链安全；
- 员工背景调查；
- 安全培训；
- 认证（SOC 2/ISO 27001）。

客户可能要求：

- 安全问卷；
- 渗透测试报告；
- 认证证书；
- 审计报告；
- 事件通知；
- 整改计划。

## N.5 支持与运维条款

- 支持渠道；
- 支持时间；
- 响应时间；
- 解决时间；
- 升级路径；
- 值班；
- 状态页；
- 事故沟通；
- 维护通知；
- 变更通知。

### 支持等级

| 等级 | 响应 | 解决 | 适用 |
|---|---|---|---|
| P0 | 15 分钟 | 4 小时 | 全站不可用 |
| P1 | 1 小时 | 8 小时 | 核心功能 |
| P2 | 4 小时 | 2 个工作日 | 部分功能 |
| P3 | 1 个工作日 | 5 个工作日 | 一般问题 |

## N.6 可接受使用政策

应明确禁止：

- 转售；
- 爬取；
- 滥用；
- 攻击；
- 逆向工程；
- 绕过限流；
- 违法内容；
- 侵犯隐私；
- 高风险用途（如自动武器、非法监控）。

执行：

- 监控；
- 警告；
- 限流；
- 暂停；
- 终止；
- 报告。

## N.7 知识产权与数据归属

- API 本身的知识产权归提供方；
- 客户数据归客户；
- 衍生数据/聚合数据的归属；
- 模型训练使用权；
- 反馈数据；
- 输出内容的所有权；
- 开源组件许可。

AI API 还要明确：

- 输入是否用于训练；
- 输出是否可版权；
- 模型改进使用权；
- 零数据保留选项。

### AI 专项条款

AI API 的合同需要比传统 API 多回答一些问题：

- **训练使用**：客户输入、输出、反馈是否用于训练或改进模型？如果是，能否按租户关闭？关闭后是否影响功能？
- **保留期限**：prompt、completion、工具结果、轨迹分别保留多久？是否支持零数据保留？
- **输出归属**：输出的知识产权归谁？是否保证不侵权？客户能否商用？
- **模型变更**：提供方能否在不通知的情况下改变模型行为？固定版本、弃用周期、评估报告是否承诺？
- **用途限制**：哪些高风险用途被禁止（医疗诊断、法律意见、自动决策、武器、监控）？违反后能否暂停服务？
- **安全与滥用**：内容过滤、越狱检测、速率限制、执法请求如何处理？
- **责任与赔偿**：幻觉、错误建议、数据泄露、知识产权侵权分别由谁承担？赔偿上限是否覆盖 AI 特有风险？
- **可解释与审计**：能否提供模型版本、输入输出记录、工具调用轨迹、人工确认记录？
- **监管协作**：如果客户被监管问询，提供方是否协助提供证据？
- **退出与迁移**：模型弃用后，客户能否导出评估结果、提示模板与微调数据？

这些条款会反向影响技术设计。例如，承诺“零数据保留”意味着日志、追踪和调试采样都要重新设计；承诺“固定模型版本”意味着不能使用会静默更新的 `latest` 别名；承诺“可解释”意味着工具调用与关键决策必须留下结构化轨迹。

## N.8 采购流程

企业客户通常需要：

1. 安全问卷；
2. 架构评审；
3. 法务审查；
4. 采购审批；
5. 试点；
6. 合同签署；
7. 上线；
8. 续费。

API 提供方应准备：

- 安全白皮书；
- SOC 2/ISO 证书；
- DPA 模板；
- SLA 模板；
- 架构图；
- 数据流图；
- 渗透测试摘要；
- 参考客户；
- 定价表；
- 合同条款说明。

## N.9 退出与可移植性

合同应明确：

- 终止通知期；
- 数据导出格式；
- 导出时限；
- 导出费用；
- 数据删除；
- 过渡支持；
- 知识产权；
- 尾款。

技术实现：

- 导出 API；
- 批量导出；
- 标准格式；
- 校验和；
- 删除证明；
- 迁移文档。

没有退出条款的 API 合同，会在更换供应商时变成锁定。

- [ ] SLA 的 SLI 可测量。
- [ ] 赔偿有上限和流程。
- [ ] 排除项合理。
- [ ] DPA 覆盖数据流。
- [ ] 数据驻留可实现。
- [ ] 子处理者变更通知。
- [ ] 安全控制有证据。
- [ ] 支持等级与值班匹配。
- [ ] AUP 可执行。
- [ ] 数据归属清晰。
- [ ] 导出与删除可实现。
- [ ] 终止条款可操作。
- [ ] 价格与用量可对账。
- [ ] 责任限制与保险匹配。

## N.11 技术团队的参与点

- 审查 SLA 是否可测量；
- 审查 DPA 是否可实现；
- 审查安全附件是否有控制；
- 审查支持承诺是否有值班；
- 审查导出/删除是否有接口；
- 审查计费是否能对账；
- 审查事故通知是否能做到；
- 审查合同中的“合理努力”是否可执行。

## N.12 小结

- API 合同不只是法务文件，它会约束技术架构。
- SLA、DPA、安全附件、支持条款、AUP、退出条款缺一不可。
- SLA 必须可测量、可赔偿、有排除项。
- 数据驻留、删除、导出必须有技术实现。
- 监管矩阵要先于条款起草，避免“遵守所有适用法律”这种不可执行的话。
- AI 合同要明确训练使用、保留、输出归属、模型变更、用途限制与责任。
- 采购流程需要安全证据和合同模板。
- 技术团队应参与合同评审，避免承诺无法兑现。
- 合同中的加密算法、密钥托管、后量子迁移与审计证据要能落到实现，见[附录 AD](ad-cryptography-pqc.md)。
