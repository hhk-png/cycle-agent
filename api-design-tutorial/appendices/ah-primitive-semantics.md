# 附录 AH：API 契约中的基础语义——时间、金钱、数量、标识与语言

> 本书前面反复强调“类型不等于语义”。本附录把最容易在字段层面被低估、却在生产环境里反复制造事故的五类基础语义集中起来：时间、金钱、数量与单位、标识、语言与文本。它们不是某个行业的特殊问题，而是每个 API 都要面对的地基。地基一旦含糊，上层再优雅的契约也会在集成、对账、审计和迁移中崩塌。

## AH.1 为什么基础语义是契约

一个字段写成 `string`、`number` 或 `integer`，只回答了“字节如何编码”，没有回答下面这些问题：

1. **单位是什么？** 元还是分？秒还是毫秒？米还是英尺？
2. **参照系是什么？** UTC 还是本地时间？哪个时区？哪种坐标系？
3. **精度和舍入是什么？** 保留几位？何时舍入？用哪种舍入模式？
4. **规范形式是什么？** 大小写、空白、Unicode 归一化、前后导零如何处理？
5. **生命周期是什么？** 是否可重复使用？是否会合并、拆分、重命名？
6. **失败时是什么？** 无效时区、币种不匹配、单位不一致返回什么错误？

这六个问题不写进契约，调用方就只能靠猜；而跨组织、跨语言、跨数据库的集成里，“猜”几乎必然猜错。

### 一个字段的完整契约

以“金额”为例，下面是最低限度的契约声明：

| 维度 | 必须写清的内容 | 反例 |
|---|---|---|
| 类型 | 整数最小单位，还是十进制字符串 | `12.30` 被解析成浮点 |
| 单位 | 最小货币单位，还是主单位 | `amount: 12.3` 是元还是分 |
| 币种 | ISO 4217 代码，且与金额同现 | 只返回数字，币种靠上下文 |
| 精度 | 小数位数、是否允许负值 | 日元被强行保留两位 |
| 舍入 | 何时舍入、哪种模式 | 每行四舍五入后总额对不上 |
| 不变式 | 明细之和等于总额 | 分摊后差一分钱 |

这张表适用于所有基础语义。**“字段有类型”只是起点，“字段有可验证的语义”才是契约。**

### 基础语义错误的三个特征

- **不会立刻报错。** 时区差八小时、金额差一百倍、单位差一千倍，系统往往照常返回 200。
- **会跨系统放大。** 一个 API 的歧义会被 SDK、报表、对账脚本、合作伙伴各解释一次，产生多个“真相”。
- **修复代价极高。** 字段名可以改，语义一旦被外部依赖，改语义就是破坏性变更。

因此，基础语义应该在**契约评审的第一轮**就确定，而不是等集成测试暴露问题。

## AH.2 时间的五种类型

“时间”不是一个类型，而是一组语义完全不同的概念。把它们混成一个 `timestamp` 字段，是 API 设计中最常见的错误之一。

| 类型 | 回答的问题 | 示例 | 典型字段 |
|---|---|---|---|
| 时刻（instant） | 宇宙中发生的某一个点 | `2026-11-26T02:15:30.123Z` | `createdAt`、`paidAt` |
| 本地日期时间（local date-time） | 某个地方墙上的日期和时间 | `2026-11-26T10:15:30` + `Asia/Shanghai` | `pickupAt`、`appointmentAt` |
| 日期（date） | 某个日历日，不带时刻 | `2026-11-26` | `billingDate`、`birthDate` |
| 当日时间（time-of-day） | 一天中的某个时间，不带日期 | `09:00:00` | `openingTime` |
| 时长（duration） | 两点之间的长度 | `PT30M`、`P1M` | `timeout`、`trialPeriod` |
| 区间（interval） | 起点与终点之间的范围 | `[2026-11-01, 2026-12-01)` | `billingPeriod`、`availability` |

很多系统只有一个 `timestamp` 字段，结果把“生日”存成了 UTC 时刻，把“营业时间”存成了某个时区的时刻，把“账期”存成了两个时间戳。调用方只能猜测每个字段到底属于哪一类。

### 时刻：用 RFC 3339，带偏移或 `Z`

```json
{
  "createdAt": "2026-11-26T02:15:30.123Z",
  "paidAt": "2026-11-26T10:15:30.123+08:00"
}
```

规则：

- 使用 RFC 3339（ISO 8601 的一个 profile），必须带偏移或 `Z`；
- 不要发送“没有时区的本地时间”来表示时刻；
- 小数秒的位数要固定或明确说明，避免不同客户端截断方式不同；
- 服务端存储统一用 UTC，展示时再按业务时区转换；
- 比较时刻时先解析再比较，不要按字符串比较；只有在偏移和精度都一致时，字典序才偶然等价。

### 本地日期时间：时刻 + 时区，或“浮动时间”

“明天上午 9 点开会”不是一个时刻，而是一个本地日期时间。它需要两个信息：

```json
{
  "localStart": "2026-11-27T09:00:00",
  "timeZone": "Asia/Shanghai"
}
```

如果只存 `2026-11-27T01:00:00Z`，当时区规则变化、用户搬家或跨时区展示时，语义就会漂移。

有些场景故意使用“浮动时间”（floating time），例如“每天 09:00 的提醒”，它不绑定任何时区，按用户当前时区解释。这类字段必须显式命名为 `localTime` 或 `wallTime`，并在文档中说明它不是一个时刻。

### 日期：不要用午夜时刻冒充

```json
{
  "billingDate": "2026-11-26",
  "birthDate": "1990-05-17"
}
```

日期没有时区。把日期存成 `2026-11-26T00:00:00Z`，在西半球会被显示成 11 月 25 日。日期字段应使用 `YYYY-MM-DD`，并在过滤、排序、展示时始终按日期处理。

### 时长：区分“精确时长”和“日历时长”

- 精确时长：`PT30M`、`PT3600S`，可以换算成秒；
- 日历时长：`P1M`、`P1Y`，长度取决于起止日期；
- “30 天”不等于“1 个月”；
- 超时、重试间隔、缓存 TTL 通常用秒或毫秒；
- 试用期、账期、订阅周期通常用日历单位。

```json
{
  "timeoutSeconds": 30,
  "trialPeriod": "P14D",
  "billingPeriod": "P1M"
}
```

如果一个字段同时可能表示“30 天”和“1 个月”，就应该拆成两个字段，或在契约中明确“按日历月计算”。

### 区间：默认半开

区间最容易被忽略的是边界。推荐默认使用半开区间 `[start, end)`：

```json
{
  "periodStart": "2026-11-01T00:00:00Z",
  "periodEnd": "2026-12-01T00:00:00Z"
}
```

半开区间的好处是相邻区间不重叠、不遗漏：11 月的结束就是 12 月的开始。若业务必须使用闭区间，应在字段名或文档中写清 `inclusive`，并提供一致的过滤语义。

## AH.3 时区与夏令时

### 偏移不是时区

`+08:00` 是一个偏移，不是时区。时区是一个规则集合，包含历史偏移、夏令时规则和未来变化。`Asia/Shanghai` 是时区，`GMT+8` 不是。

契约中应使用 IANA 时区数据库的名称：

```json
{
  "timeZone": "Asia/Shanghai"
}
```

不要使用：

- `GMT+8`、`UTC+8`：无法表达夏令时和历史变化；
- `CST`：可能是中国标准时间、美国中部时间或古巴标准时间；
- `Beijing Time`：不是稳定的机器标识；
- 固定偏移：在跨 DST 的场景会出错。

### 夏令时的两个陷阱

以 `America/New_York` 为例：

- **春季前跳**：2026-03-08 02:00 直接跳到 03:00，本地时间 `02:30` 不存在；
- **秋季回拨**：2026-11-01 01:00 回拨到 00:00，本地时间 `01:30` 出现两次。

类似地，`Europe/Berlin`、`Australia/Sydney`、`Pacific/Auckland` 都有 DST；`Australia/Lord_Howe` 使用 30 分钟的 DST 偏移；`Asia/Shanghai` 当前没有 DST，但历史上曾实行过。

当客户端提交一个本地日期时间时，服务端必须定义解析策略：

| 情况 | 策略 | 结果 |
|---|---|---|
| 不存在的本地时间（春季缺口） | 向后顺延到下一个有效时刻 | `02:30` → `03:30` |
| 不存在的本地时间 | 拒绝并返回明确错误 | `NONEXISTENT_LOCAL_TIME` |
| 重复的本地时间（秋季重叠） | 选择第一次出现（较早偏移） | `01:30` → 第一次 |
| 重复的本地时间 | 选择第二次出现（较晚偏移） | `01:30` → 第二次 |
| 重复的本地时间 | 拒绝并要求客户端带偏移 | `AMBIGUOUS_LOCAL_TIME` |

没有“唯一正确”的策略，但必须有唯一且稳定的契约。对高风险业务（排班、结算、航班、医疗），推荐拒绝歧义，让调用方显式提供偏移或选择策略。

### 历史时区与未来规则

时区数据库会更新：

- 某国取消或恢复夏令时；
- 某地更改标准偏移；
- 历史数据被修正；
- 出现新的时区名称。

因此：

- 存储时刻时，UTC 是稳定的；存储本地日期时间时，时区名称是稳定的，但解释规则可能变化；
- 对需要可复现的业务（账单、合同、审计），记录**解析时使用的 tzdb 版本**；
- 不要假设“未来时区规则等于当前规则”；
- 跨时区排班、航班、结算要使用带版本的时区数据，并在测试中覆盖规则变更。

### 时区错误的 API 表达

```json
{
  "type": "https://errors.example.com/time/invalid-timezone",
  "title": "无效的时区",
  "status": 422,
  "code": "INVALID_TIMEZONE",
  "detail": "时区必须是 IANA 名称，例如 Asia/Shanghai，而不是 GMT+8。",
  "parameter": "timeZone"
}
```

## AH.4 业务日历、截止时间与账期

### 日历日不等于业务日

“3 个工作日内回复”不能简单地在日期上加 3 天。业务日需要：

- 工作日规则（周一到周五，或地区性工作周）；
- 节假日日历（法定节假日、调休、行业假日）；
- 截止时间（cut-off time）；
- 时区；
- 特殊工作日（周末上班、临时停业）。

```json
{
  "calendarId": "CN-2026",
  "calendarVersion": "2026.11",
  "businessDayConvention": "FOLLOWING",
  "cutOffTime": "17:00:00",
  "timeZone": "Asia/Shanghai"
}
```

金融场景常见的业务日约定：

| 约定 | 含义 |
|---|---|
| `FOLLOWING` | 顺延到下一个业务日 |
| `MODIFIED_FOLLOWING` | 顺延，但跨月时回退到上一个业务日 |
| `PRECEDING` | 提前到上一个业务日 |
| `MODIFIED_PRECEDING` | 提前，但跨月时顺延 |
| `NONE` | 不调整，允许非业务日 |

这些约定会直接影响结算日、起息日、到期日和罚息。契约中不能只写 `settlementDate`，还要写清它按哪个日历、哪种约定计算。

### 截止时间

“当日到账”通常意味着“在截止时间之前提交”。API 应返回或要求：

```json
{
  "cutOffAt": "2026-11-26T17:00:00+08:00",
  "valueDate": "2026-11-26",
  "timeZone": "Asia/Shanghai"
}
```

如果只返回 `valueDate` 而不返回截止时间，调用方会误以为当天任何时间提交都算当天。

### 账期与月末锚点

订阅、账单、利息和租金常见两种周期：

- **日历周期**：每月 1 日到月末；
- **周年周期**：按订阅开始日（如每月 15 日）滚动。

月末锚点尤其容易出错：

- 1 月 31 日开始按月续费，2 月没有 31 日，应锚定到 2 月 28/29 日，还是 3 月 3 日？
- 之后是回到 31 日，还是永久改为 28 日？
- 闰年 2 月 29 日开始的年度订阅，平年如何续费？

契约应明确：

```json
{
  "billingAnchor": { "dayOfMonth": 31, "policy": "CLAMP_TO_MONTH_END" },
  "prorationPolicy": "ACTUAL_DAYS",
  "periodStart": "2026-01-31",
  "periodEnd": "2026-02-28"
}
```

### 按比例计算（proration）

中途升级、降级、取消时，常见算法有：

- 按剩余天数 / 周期总天数；
- 按剩余秒数 / 周期总秒数；
- 按剩余整月数；
- 按固定 30 天月；
- 不按比例，直接切换。

不同算法会产生不同金额。契约必须写明：

1. 用哪个时间基准（秒、天、月）；
2. 周期总长度如何算（含首尾、闰日、DST）；
3. 舍入发生在哪一步；
4. 升级/降级是否立即生效；
5. 退款还是抵扣未来账单。

## AH.5 精度、时钟与事件顺序

### 精度

| 场景 | 常见精度 | 注意 |
|---|---|---|
| HTTP 日期头 | 秒 | `Last-Modified` 只有秒级 |
| JavaScript `Date` | 毫秒 | 超出部分被截断 |
| Java `Instant` | 纳秒 | 数据库可能只存微秒 |
| Python `datetime` | 微秒 | 时区处理需显式 |
| PostgreSQL `timestamptz` | 微秒 | 存储 UTC，显示按会话时区 |
| 高频交易/观测 | 纳秒或更高 | 需要单调时钟与硬件时间戳 |

契约应说明：

- 小数秒保留几位；
- 多余位是截断还是四舍五入；
- 客户端是否可以依赖亚毫秒顺序；
- 两个事件在同一毫秒内如何排序。

不要把“时间戳精度”当成“事件顺序”。同一毫秒内的两个事件，时间戳可能完全相同。

### 闰秒

UTC 可能在 23:59:60 插入闰秒。不同系统的处理方式不同：

- 有的系统接受 `23:59:60`；
- 有的系统把闰秒抹平（smear）；
- 有的系统直接忽略，导致时间短暂回退或重复；
- POSIX 时间通常不表示闰秒。

API 契约应明确：

- 是否接受闰秒表示；
- 内部是否使用 POSIX 时间；
- 是否使用 smear；
- 定时任务是否避开闰秒边界。

对绝大多数业务 API，最实用的规则是：**不承诺闰秒语义，使用 POSIX 时间，并在文档中写明。** 对天文、卫星、精密测量等场景，则需要专门的时间尺度。

### 时钟偏差

客户端时间不可信：

- 设备时钟可能慢几分钟；
- 用户可能手动改时间；
- 虚拟机可能发生时钟漂移；
- 跨区域服务器的时钟有偏差。

因此：

- 不要用客户端时间做授权、过期、幂等或排序的唯一依据；
- 服务端记录 `receivedAt`（服务端收到请求的时间）；
- 客户端可提供 `occurredAt`（业务事件实际发生的时间），但要标记为不可信输入；
- 对超时、重试、租约使用**单调时钟**，不要用墙上时钟；
- 分布式事件排序可使用逻辑时钟、向量时钟或混合逻辑时钟（HLC）。

```json
{
  "occurredAt": "2026-11-26T10:15:30.123Z",
  "receivedAt": "2026-11-26T10:15:31.987Z",
  "clockSkewMillis": 1864
}
```

### 事件顺序

事件 API 常见四种排序依据：

| 依据 | 适合 | 风险 |
|---|---|---|
| 事件时间 `occurredAt` | 业务分析、回放 | 时钟偏差、乱序 |
| 接收时间 `receivedAt` | 审计、排查 | 不反映业务顺序 |
| 每聚合序列号 `sequence` | 状态变更、命令 | 需要单写者或协调 |
| 混合逻辑时钟 `HLC` | 跨节点近似因果顺序 | 实现复杂，不是全序 |

契约应说明：

- 排序键是什么；
- 是否保证同一聚合内有序；
- 跨聚合是否有序；
- 重复、迟到、乱序如何处理；
- 消费者是否可以用 `sequence` 去重；
- 水位线（watermark）或 `dataThrough` 如何表达“数据已基本到齐”。

### HTTP 日期头

HTTP 有自己的日期格式和语义：

```http
Date: Thu, 26 Nov 2026 02:15:30 GMT
Last-Modified: Thu, 26 Nov 2026 02:15:30 GMT
If-Modified-Since: Thu, 26 Nov 2026 02:15:30 GMT
Retry-After: 120
Expires: Thu, 26 Nov 2026 03:15:30 GMT
Sunset: Sat, 31 Jan 2027 00:00:00 GMT
```

要点：

- HTTP-date 使用 IMF-fixdate，GMT，秒级；
- `Last-Modified` 的秒级精度可能不足以表达快速变更，优先使用 `ETag`；
- `If-Modified-Since` 只适合粗略缓存，不适合并发控制；
- `Retry-After` 可以是秒数或 HTTP-date；
- `Expires` 是绝对时间，`Cache-Control: max-age` 是相对时间；
- `Sunset`（RFC 8594）用于声明资源下线时间；
- `Age` 表示响应在缓存中已存活的时间。

## AH.6 重复、调度与定时任务

### RRULE 与 cron 不是一回事

- **RRULE**（RFC 5545）描述日历重复：每周一、每月最后一个周五、每年 3 月第 2 个周日；
- **cron** 描述按字段匹配的时间点：`0 2 * * *`；
- RRULE 更适合“业务日历”语义，cron 更适合“运维调度”；
- 两者都必须处理时区、DST、月末和异常日期。

一个常见的 RRULE：

```text
FREQ=MONTHLY;BYDAY=-1FR;COUNT=12
```

含义是“每月最后一个周五，共 12 次”。如果用 cron 表达，需要额外的日期计算。

### 调度契约

```json
{
  "scheduleId": "sch_123",
  "rrule": "FREQ=WEEKLY;BYDAY=MO,WE,FR",
  "timeZone": "Asia/Shanghai",
  "startAt": "2026-11-26T09:00:00+08:00",
  "endAt": null,
  "catchUpPolicy": "RUN_ONCE",
  "overlapPolicy": "SKIP",
  "misfirePolicy": "FIRE_NOW"
}
```

需要写清：

- 时区与 DST 规则；
- 错过执行（服务停机、部署、故障）如何补跑；
- 上一次未结束时是否允许并发；
- 任务执行超时如何处理；
- 幂等键是否包含计划时间；
- 取消、暂停、恢复的语义；
- 单次执行与重复执行的资源上限。

### 幂等运行

定时任务最容易产生重复副作用。推荐用 `(jobId, scheduledFor)` 作为幂等键：

```text
jobId: daily-invoice
scheduledFor: 2026-11-26T00:00:00Z
```

无论任务被触发多少次，同一个计划时间只应产生一次业务效果。补跑、重试、人工触发都应携带同一个键。

## AH.7 金钱

### 金额不是数字

金额由“数值 + 币种 + 精度 + 舍入规则”组成。只返回一个数字，等于把解释权交给调用方。

```json
{
  "total": {
    "amount": 12990,
    "currency": "CNY"
  }
}
```

其中 `amount` 是最小货币单位（人民币为分）。这是本书推荐的默认表示。

### 最小单位不是固定的两位小数

ISO 4217 定义了各币种的小数位（exponent）：

| 小数位 | 示例币种 | 说明 |
|---|---|---|
| 0 | JPY、KRW、VND、CLP、ISK | 没有小数 |
| 2 | CNY、USD、EUR、GBP | 最常见 |
| 3 | KWD、BHD、OMR、JOD、TND | 三位小数 |
| 4 | CLF | 智利发展单位 |

不要硬编码“所有金额乘以 100”。如果系统支持多币种，必须按币种读取 exponent。

加密货币不属于 ISO 4217。如果 API 支持加密货币，需要单独定义精度、最小单位、网络和确认数，不能复用“分”的假设。

### 整数最小单位 vs 十进制字符串

两种常见表示：

```json
{ "amount": 12990, "currency": "CNY" }
```

```json
{ "amount": "129.90", "currency": "CNY" }
```

| 表示 | 优点 | 缺点 |
|---|---|---|
| 最小单位整数 | 精确、易比较、易存储 | 需要知道币种精度；大额可能超过 2^53 |
| 十进制字符串 | 人类可读、精度显式 | 需要解析；不同语言 decimal 行为不同 |
| 浮点数 | 方便 | **禁止用于金额** |

如果使用整数最小单位，超过 JavaScript 安全整数范围（2^53−1）时要用字符串编码，或在契约中限制金额上限。如果使用十进制字符串，要规定小数点、禁止指数形式、禁止前后空格、固定小数位或允许的位数范围。

### 舍入

常见舍入模式：

| 模式 | 含义 | 示例（保留 2 位） |
|---|---|---|
| `HALF_UP` | 四舍五入 | `2.345` → `2.35` |
| `HALF_EVEN` | 银行家舍入 | `2.345` → `2.34`，`2.355` → `2.36` |
| `HALF_DOWN` | 五舍六入 | `2.345` → `2.34` |
| `CEILING` | 向正无穷 | `-2.341` → `-2.34` |
| `FLOOR` | 向负无穷 | `-2.341` → `-2.35` |
| `UP` | 远离零 | `-2.341` → `-2.35` |
| `DOWN` | 向零 | `-2.349` → `-2.34` |

比“用哪种模式”更重要的是“在哪一步舍入”：

- 每行先舍入再加总；
- 先加总再舍入；
- 税费单独舍入；
- 折扣按行分摊后舍入；
- 汇率换算后舍入。

不同顺序会产生分差。契约应写明，并用性质测试断言“明细之和等于总额”。

### 分摊

把 100.00 元平均分成 3 份，不能得到三个 33.33 元，否则总和少一分。常见做法是“最大余数法”：

```text
100.00 / 3 = 33.333...
基础份额：33.33、33.33、33.33
余数：0.01
把余数分给最大余数（或第一个）份额：33.34、33.33、33.33
```

契约应规定：

- 分摊是否保证总和不变；
- 余数给谁（按顺序、按最大余数、按比例）；
- 负金额如何分摊；
- 多币种是否分别分摊。

### 负数、退款与符号

金额的符号约定必须统一：

- `amount` 永远为正，另用 `type: DEBIT | CREDIT` 表示方向；
- 或者 `amount` 可为负，正表示收入、负表示支出；
- 退款是独立资源，还是负金额？

推荐：**资源上的金额使用正数 + 明确的业务类型；账本分录使用借贷方向；不要在同一字段里混用“正数收入/负数支出”和“正数应付/负数退款”。**

```json
{
  "type": "REFUND",
  "amount": { "amount": 5000, "currency": "CNY" },
  "originalPaymentId": "pay_123"
}
```

### 多币种与汇率

多币种金额不能直接相加。必须区分：

- 原始币种金额；
- 结算币种金额；
- 换算汇率；
- 汇率来源与时间；
- 换汇手续费；
- 舍入规则；
- 汇率锁定时间。

```json
{
  "original": { "amount": 10000, "currency": "USD" },
  "settled": { "amount": 71930, "currency": "CNY" },
  "fx": {
    "rate": "7.1930",
    "base": "USD",
    "quote": "CNY",
    "source": "ECB",
    "quotedAt": "2026-11-26T00:00:00Z",
    "rateId": "fx_20261126_usdcny"
  }
}
```

汇率必须用十进制字符串或定点数，不能用浮点数。换算只应在明确的步骤发生一次，避免“先换汇再舍入再换回”造成漂移。

### 税

税费设计要回答：

- 金额含税还是不含税；
- 税率、税种、税收辖区；
- 是否适用反向征收、免税、零税率；
- 税额按行计算还是按发票总额计算；
- 舍入发生在税前还是税后；
- 税率变更时历史单据如何复现。

```json
{
  "net": { "amount": 10000, "currency": "CNY" },
  "tax": {
    "rate": "0.13",
    "amount": { "amount": 1300, "currency": "CNY" },
    "included": false,
    "jurisdiction": "CN",
    "code": "VAT"
  },
  "gross": { "amount": 11300, "currency": "CNY" }
}
```

税率用十进制字符串或基点表示，避免 `0.13` 浮点误差。历史发票必须保存税率和计算规则，而不是只保存总额。

### 价格版本

价格会变，订单必须保存“下单时的价格快照”：

```json
{
  "priceId": "price_123",
  "priceVersion": "2026-11-01",
  "unitAmount": { "amount": 12990, "currency": "CNY" },
  "quantity": 2,
  "lineTotal": { "amount": 25980, "currency": "CNY" }
}
```

不要在下单后重新查询“当前价格”来计算历史订单。价格表、折扣规则、税率和汇率都应该可版本化、可重放。

## AH.8 数量与单位

### 数值没有单位，等于没有意义

```json
{ "weight": 10 }
```

是 10 千克、10 磅还是 10 吨？契约必须同时给出数值和单位：

```json
{ "weight": { "value": "10.5", "unit": "kg" } }
```

### SI 与 UCUM

- **SI** 定义七个基本单位：米、千克、秒、安培、开尔文、摩尔、坎德拉；
- **UCUM**（Unified Code for Units of Measure）提供机器可读的单位代码，大小写敏感；
- 常见 UCUM 代码：`m`、`kg`、`s`、`Cel`、`[degF]`、`mg`、`mL`、`[IU]`、`mm[Hg]`；
- 医疗、实验室、药剂量强烈建议使用 UCUM，而不是自定义字符串。

```json
{
  "value": "37.0",
  "unit": "Cel",
  "ucum": "Cel"
}
```

### 单位换算

换算不是简单的乘法：

- 温度是仿射变换：`°F = °C × 9/5 + 32`；
- 压力、浓度、剂量可能涉及分子量和当量；
- 货币换算需要汇率和时间；
- 时间单位有日历月和精确秒的区别；
- 数据单位有十进制和二进制两种。

契约应说明：

- 是否允许客户端指定单位；
- 服务端是否统一转换为基准单位；
- 转换的精度和舍入；
- 未知单位如何处理；
- 单位是否参与相等性判断。

### 百分比、百分点与基点

三个概念经常被混用：

| 概念 | 含义 | 示例 |
|---|---|---|
| 百分比 | 比例乘以 100 | `12%` |
| 百分点 | 两个百分比之差 | 从 12% 到 15%，上升 3 个百分点 |
| 基点（bp） | 万分之一 | `150 bp = 1.5%` |

API 中推荐：

- 用 `rate` 表示 0～1 的比例，并说明精度；
- 用 `basisPoints` 表示整数基点；
- 不要用 `percent: 12` 又让调用方猜它是 12% 还是 0.12；
- 利率、费率、折扣、税率都应在字段名中带单位。

```json
{
  "interestRate": { "basisPoints": 350 },
  "discount": { "rate": "0.125" },
  "taxRate": { "percent": "13.0" }
}
```

### 时长与数据量

- `PT30M` 是精确的 30 分钟；`P1M` 是日历月；
- `KB` 在存储语境常指 1000 字节，`KiB` 指 1024 字节；
- 网络带宽常用 bit/s，存储常用 byte；
- `MB`、`GB`、`TB` 的十进制/二进制歧义要写清；
- 分页大小、请求体上限、文件大小限制都应带单位。

### 地理坐标

地理坐标也是基础语义：

- 坐标系要显式：WGS84（EPSG:4326）、Web Mercator（EPSG:3857）等；
- EPSG:4326 的轴顺序是纬度、经度；GeoJSON 是经度、纬度；
- 精度、海拔、基准面要说明；
- 反子午线、极点、多边形环绕方向要处理；
- 距离计算要区分平面距离、球面距离、测地距离。

```json
{
  "type": "Point",
  "coordinates": [121.4737, 31.2304],
  "crs": "EPSG:4326"
}
```

GeoJSON 默认使用 WGS84，坐标顺序是 `[longitude, latitude]`。不要在其他字段里悄悄使用 `[lat, lon]`。

## AH.9 标识

### 标识应该是不透明的

对外 API 的 ID 应满足：

- 全局唯一；
- 稳定，不随属性变化；
- 不可枚举，避免泄露规模；
- URL 安全；
- 大小写敏感且有明确规则；
- 长度有上限；
- 不包含业务语义或个人信息。

推荐使用带类型前缀的字符串：

```text
ord_01J9Z6Q8K3W7V2M4N5P6R7S8T9
cus_01J9Z6Q8K3W7V2M4N5P6R7S8T9
```

前缀让日志、错误信息和调试更容易，也让 SDK 可以做类型检查。但**调用方不能解析前缀或从中提取时间、机器、序列号**。

### 常见 ID 方案

| 方案 | 结构 | 优点 | 风险 |
|---|---|---|---|
| 自增整数 | 数据库序列 | 简单、短 | 可枚举、泄露规模、难分片 |
| UUIDv4 | 128 位随机 | 无需协调、不可枚举 | 不可排序、索引局部性差 |
| UUIDv7 | 48 位毫秒 + 随机 | 时间有序、数据库友好 | 泄露创建时间 |
| ULID | 48 位毫秒 + 80 位随机 | 时间有序、字符串紧凑 | 泄露创建时间、实现差异 |
| Snowflake | 时间 + 机器 + 序列 | 有序、可扩展 | 依赖时钟、机器 ID 管理 |
| KSUID | 32 位秒 + 128 位随机 | 有序、无需协调 | 泄露创建时间 |
| 自然键 | 邮箱、手机号、SKU | 人类可读 | 可变、可重用、含 PII |

选择时问：

- 是否需要按创建时间排序？
- 是否允许泄露创建时间？
- 是否跨区域生成？
- 是否需要数据库索引局部性？
- 是否会被用户看到？
- 是否需要迁移或合并？

### ID 的生命周期

- **永不复用**：删除后的 ID 不应再分配给新实体；
- **不要用自然键做主 ID**：邮箱、手机号、用户名会变；
- **合并/拆分**：两个账户合并后，旧 ID 应返回重定向或别名，而不是 404；
- **外部 ID**：`externalId` 应带来源系统命名空间，避免冲突；
- **幂等键**：不是资源 ID，但同样需要唯一、可过期、绑定请求指纹。

```json
{
  "id": "cus_123",
  "externalIds": [
    { "system": "salesforce", "value": "001A000001234" }
  ],
  "mergedInto": null
}
```

### 规范化与校验

标识在比较、存储、传输前可能需要规范化：

- 邮箱：域名小写；本地部分理论上大小写敏感，实践中多数系统不敏感；
- 电话：E.164，带国家码，去掉空格和分隔符；
- IBAN：大写、去空格；
- 税号：按国家规则；
- 域名：IDNA / punycode；
- Unicode 文本：NFC 归一化。

规范化必须幂等、可逆（或至少可解释），并在契约中说明。不要在一个接口里规范化，在另一个接口里保留原始形式。

### 校验位

很多行业标识带校验位：

- Luhn：银行卡号；
- mod-97：IBAN；
- mod-10：GS1 GTIN；
- ISBN、VIN、IMEI 等。

API 应尽早校验格式，但**不要仅凭校验位判断存在性或有效性**。校验位只能发现录入错误，不能证明账户存在。

### 游标也是标识

分页游标应视为不透明标识：

- Base64URL 编码；
- 包含排序键、过滤条件、快照/租户绑定；
- 用 HMAC 或加密防篡改；
- 有 TTL；
- 不泄露内部 SQL 或敏感字段；
- 不能跨租户、跨查询复用。

```text
cursor = base64url(payload) + "." + base64url(hmac)
payload = { tenantId, sortKey, lastId, filterHash, snapshotId, exp }
```

## AH.10 语言与文本

### 语言标签

使用 BCP 47：

```text
zh-Hans-CN
zh-Hant-TW
en-US
sr-Latn-RS
```

- 语言 + 书写系统 + 地区；
- 不要用 `zh_CN`（下划线是 POSIX locale，不是 BCP 47）；
- 不要用 `CN` 表示中文；
- 回退链要明确：`zh-Hans-CN` → `zh-Hans` → `zh` → 默认；
- `Accept-Language` 支持 q 值；
- `Content-Language` 声明响应内容语言；
- 语言标签大小写不敏感，但推荐规范化大小写。

```http
Accept-Language: zh-CN,zh;q=0.9,en;q=0.8
Content-Language: zh-CN
```

### 语言不等于地区

- `en-US` 和 `en-GB` 的日期格式、货币、拼写不同；
- `pt-BR` 和 `pt-PT` 的词汇和语法不同；
- `zh-Hans` 和 `zh-Hant` 是书写系统差异；
- 同一个语言在不同地区的排序规则可能不同。

API 应区分：

- `language`：内容语言；
- `locale`：格式化偏好（日期、数字、货币、排序）；
- `timeZone`：时间解释；
- `currency`：金额币种。

不要把四者塞进一个 `locale` 字段。

### Unicode 归一化

同一个字符可能有多种编码：

- `é` 可以是预组合字符 U+00E9，也可以是 `e` + U+0301；
- 韩文、泰文、阿拉伯文都有组合形式；
- 不同输入法、不同系统产生的字节可能不同。

比较、搜索、去重前应统一归一化形式（通常 NFC），并在契约中说明。不要假设“用户看到的相同”等于“字节相同”。

### 字符串长度

“长度”至少有三种：

- 字节数（UTF-8 编码后）；
- Unicode 码点数；
- 字形簇（grapheme cluster）数。

emoji、组合字符、家庭 emoji 在不同计数下差异很大。API 限制应明确：

- 数据库字段长度按字符还是字节；
- 业务限制按用户感知字符还是码点；
- 超长时是拒绝还是截断；
- 截断是否可能切断组合字符。

### 排序与搜索

- 排序规则由 locale 决定，不是码点顺序；
- 大小写、重音、变音符号可能影响排序；
- 中文需要拼音、笔画或部首排序；
- 搜索需要分词、词干、同义词、拼写容错；
- 不要假设 `ORDER BY name` 在所有语言下都符合用户预期。

### 双向文本与 RTL

阿拉伯语、希伯来语等从右到左书写。API 返回的文本可能包含双向控制字符。需要：

- 不在错误信息中拼接方向不明的片段；
- 前端使用 `dir="auto"` 或明确方向；
- 日志中保留原始文本，但注意控制字符；
- 搜索和比较时处理双向标记。

### 人名与地址

不要假设：

- 姓名一定由“名 + 姓”组成；
- 姓在前还是名在前；
- 一定有中间名；
- 婚姻状况会改变姓氏；
- 地址一定有州/省、邮编；
- 电话号码一定有区号。

推荐结构化但可扩展：

```json
{
  "name": {
    "family": "张",
    "given": "三",
    "additional": [],
    "prefix": [],
    "suffix": [],
    "script": "Hans"
  },
  "address": {
    "country": "CN",
    "region": "上海市",
    "locality": "上海市",
    "postalCode": "200000",
    "streetAddress": "南京东路 100 号",
    "careOf": null
  }
}
```

校验应宽松，展示应尊重当地格式。

## AH.11 跨语言、跨数据库的落地

### JSON 的精度陷阱

JSON 没有整数/浮点之分，只有 `number`。不同解析器行为不同：

- JavaScript 的 `number` 是 IEEE 754 双精度，超过 2^53−1 的整数会丢精度；
- Python 的 `int` 是任意精度，但 `json` 解析后可能变成 `float`；
- Java 的 `Long` 和 `BigDecimal` 需要显式选择；
- Go 的 `float64` 默认解析数字，大整数需要 `json.Number`；
- 某些库会把 `1.0` 解析成 `1`，改变表示。

因此：

- 金额、大整数、精确小数用字符串；
- 需要数值比较的字段，明确范围；
- 不要在 JSON 中传输超过 2^53 的整数而不加说明；
- 契约测试要覆盖边界值。

### 数据库类型映射

| 语义 | 推荐存储 | 注意 |
|---|---|---|
| 时刻 | `timestamptz` / UTC `timestamp` | 不要存本地时间 |
| 日期 | `date` | 不要用 `timestamp` 代替 |
| 金额 | `numeric(precision, scale)` 或整数最小单位 | 不要用 `float`/`double` |
| 比例 | `numeric` 或整数基点 | 明确精度 |
| 单位 | 数值 + 单位代码 | 不要只存数值 |
| ID | `uuid` / `text` / `bigint` | 与生成策略一致 |
| 语言 | `text` BCP 47 | 不要用数据库 locale 代替 |

### SDK 类型映射

SDK 应把基础语义封装成类型，而不是裸 `string`/`number`：

```ts
type Money = { amount: string; currency: string };
type Instant = string; // RFC 3339
type LocalDate = string; // YYYY-MM-DD
type Duration = string; // ISO 8601
type UnitValue = { value: string; unit: string };
```

TypeScript 的类型别名不能提供运行时校验，SDK 仍应在边界做解析和校验。Java 可用 `BigDecimal`、`Instant`、`LocalDate`；Python 可用 `Decimal`、`datetime`；Go 可用 `decimal.Decimal`、`time.Time`。

### 契约描述

OpenAPI 中 `format: decimal` 只是注解，不是验证。要配合 `pattern`、`multipleOf` 或自定义关键字：

```yaml
Money:
  type: object
  required: [amount, currency]
  properties:
    amount:
      type: string
      pattern: '^-?[0-9]+$'
      description: 最小货币单位整数，字符串编码以避免精度丢失
    currency:
      type: string
      pattern: '^[A-Z]{3}$'
      description: ISO 4217 币种代码
  additionalProperties: false
```

Protobuf 中金额可用 `int64 amount_minor` + `string currency`，或 `string amount_decimal`。不要用 `double`。

## AH.12 错误模型与契约模板

基础语义错误应使用稳定错误码，而不是把解析异常直接返回：

| 错误码 | HTTP | 含义 |
|---|---|---|
| `INVALID_TIMEZONE` | 422 | 时区不是有效 IANA 名称 |
| `NONEXISTENT_LOCAL_TIME` | 422 | 本地时间落在 DST 缺口 |
| `AMBIGUOUS_LOCAL_TIME` | 422 | 本地时间落在 DST 重叠 |
| `INVALID_DATE_RANGE` | 422 | 区间起点晚于终点或超出范围 |
| `CURRENCY_MISMATCH` | 422 | 金额与币种不匹配 |
| `UNSUPPORTED_CURRENCY` | 422 | 不支持的币种 |
| `INVALID_MINOR_UNIT` | 422 | 金额精度与币种 exponent 不符 |
| `ROUNDING_RESIDUAL` | 422 | 分摊/舍入后总额不一致 |
| `UNIT_MISMATCH` | 422 | 单位不一致或不可换算 |
| `UNKNOWN_UNIT` | 422 | 未知单位代码 |
| `INVALID_IDENTIFIER` | 422 | 标识格式无效 |
| `INVALID_LANGUAGE_TAG` | 422 | 语言标签不符合 BCP 47 |
| `UNSUPPORTED_LANGUAGE` | 422 | 不支持的语言 |
| `TEXT_TOO_LONG` | 422 | 文本超过字节/码点/字形簇限制 |

错误响应应包含字段路径和可操作的提示：

```json
{
  "type": "https://errors.example.com/money/invalid-minor-unit",
  "title": "金额精度与币种不匹配",
  "status": 422,
  "code": "INVALID_MINOR_UNIT",
  "detail": "JPY 没有小数位，amount 必须是整数日元。",
  "parameter": "total.amount",
  "currency": "JPY",
  "expectedExponent": 0
}
```

### 契约声明模板

每个基础语义字段至少声明：

```yaml
field: total
type: Money
semantics:
  amount: 最小货币单位整数，字符串编码
  currency: ISO 4217
  exponent: 按币种动态
  negative: 不允许；退款使用独立资源
  rounding: HALF_EVEN，在行级计算后汇总
invariants:
  - sum(lineItems.total) == total
examples:
  - { amount: "12990", currency: "CNY" }
errors:
  - CURRENCY_MISMATCH
  - INVALID_MINOR_UNIT
```

## AH.13 测试与不变量

基础语义适合用性质测试（property-based testing）验证，而不是只写几个示例。

### 时间

- 任意时刻 → 格式化为 RFC 3339 → 解析回来，语义不变；
- 任意 IANA 时区 + 本地时间 → 解析 → 再格式化，在非 DST 边界一致；
- DST 缺口/重叠的固定矩阵；
- 闰年 2 月 29 日、月末、跨年；
- 时区数据库升级后，历史时刻的 UTC 不变；
- 时钟回拨时，单调时钟仍递增；
- 事件按 `sequence` 排序后，状态机不回退。

### 金钱

- 任意金额 + 币种 → 序列化 → 反序列化，值不变；
- 任意分摊：`sum(parts) == total`；
- 任意汇率换算：`convert(convert(x, a→b), b→a)` 在容差内；
- 任意舍入：结果与指定模式一致；
- 负数、零、最大金额、最小单位；
- 多币种不混加；
- 税费：`net + tax == gross`（在舍入规则下）。

### 单位

- 任意单位换算 → 反向换算，在精度内一致；
- 温度换算的仿射性质；
- 未知单位被拒绝；
- 单位不一致被拒绝；
- 百分比/基点/比例换算一致。

### 标识

- 生成的 ID 唯一；
- ID 不因属性变化而变化；
- 删除后不复用；
- 合并后旧 ID 可解析；
- 游标不能跨租户/跨查询复用；
- 游标被篡改时被拒绝。

### 文本

- Unicode 归一化幂等；
- 大小写折叠幂等；
- 字符串长度限制按字节/码点/字形簇一致；
- 排序在不同 locale 下有预期结果；
- 双向文本不被错误拼接；
- 搜索分词覆盖目标语言。

### 时间旅行与假时钟

测试 DST、账期、试用期、令牌过期时，不要依赖真实时间。使用可注入的时钟：

```python
class Clock:
    def now(self) -> Instant: ...
    def today(self, zone: str) -> LocalDate: ...
```

测试中可以固定到 `2026-03-08T01:59:59-05:00`，然后推进一秒，观察行为。生产代码不要直接调用 `time.Now()` 或 `new Date()`。

## AH.14 检查清单

- [ ] 每个时间字段明确是时刻、本地日期时间、日期、当日时间、时长还是区间。
- [ ] 时刻使用 RFC 3339，带偏移或 `Z`；日期使用 `YYYY-MM-DD`。
- [ ] 时区使用 IANA 名称，不使用固定偏移或 `CST` 等歧义缩写。
- [ ] DST 缺口/重叠有明确解析策略和错误码。
- [ ] 业务日、截止时间、账期锚点、按比例计算规则写清。
- [ ] 时间精度、截断/舍入、闰秒策略、时钟偏差处理写清。
- [ ] 事件排序键、重复/乱序/迟到处理、水位线写清。
- [ ] 金额由数值 + ISO 4217 币种组成，不使用浮点数。
- [ ] 最小货币单位按币种 exponent，不硬编码两位小数。
- [ ] 舍入模式、舍入步骤、分摊规则、总额不变式写清。
- [ ] 多币种、汇率来源与时间、换汇手续费、结算币种写清。
- [ ] 税费含/不含、税率、辖区、舍入、历史复现写清。
- [ ] 数量字段带单位；单位代码使用 SI/UCUM 或明确的自定义体系。
- [ ] 百分比、百分点、基点不混用。
- [ ] 地理坐标声明 CRS 和轴顺序。
- [ ] ID 不透明、稳定、不可枚举、不复用、URL 安全。
- [ ] ID 方案的时间泄漏、排序需求、跨区域生成、迁移策略已评估。
- [ ] 外部 ID、合并/拆分、别名、校验位、规范化规则写清。
- [ ] 语言标签使用 BCP 47，回退链明确；语言、地区、时区、币种分开。
- [ ] Unicode 归一化、字符串长度口径、排序规则、搜索分词写清。
- [ ] 跨语言/跨数据库的类型映射和精度边界有测试。
- [ ] 基础语义错误有稳定错误码、字段路径和可操作提示。
- [ ] 性质测试覆盖时间、金额、单位、标识、文本的不变量。

## 小结

- 基础语义不是“字段类型”，而是单位、参照系、精度、规范形式、生命周期与失败语义的总和。
- 时间有五种类型；把时刻、日期、本地时间混成一个 `timestamp`，是最昂贵的简化之一。
- 时区和 DST 必须用规则而不是偏移表达；业务日历、截止时间和账期锚点要写进契约。
- 金额是“数值 + 币种 + 精度 + 舍入 + 分摊”的组合；浮点数不是金额类型。
- 数量必须带单位；百分比、百分点、基点要区分；坐标要声明 CRS。
- 标识应不透明、稳定、不可枚举、不复用；游标也是标识，必须防篡改、可过期、绑定查询。
- 语言与文本涉及 BCP 47、Unicode 归一化、字形簇、排序和双向文本；不能假设“看到的相同”就是“字节相同”。
- 这些语义一旦发布就很难改；应在契约评审第一轮确定，并用性质测试守住不变量。

## 设计练习

为一个“跨境订阅计费 API”设计基础语义：

- 订阅开始日、试用期、账期、月末锚点；
- 用户所在时区、账单时区、截止时间；
- 多币种定价、汇率锁定、换汇手续费；
- 含税/不含税、税率变更、历史账单复现；
- 按比例升级/降级、分摊、舍入；
- 发票、贷项通知单、退款；
- 客户 ID、订阅 ID、发票 ID、幂等键；
- 多语言账单、货币格式化、地址与姓名。

写出：

1. 每个字段的类型与语义表；
2. 账期和按比例计算的伪代码；
3. 金额分摊与舍入的不变量；
4. 至少 10 条性质测试；
5. 基础语义错误码目录。

然后回答：

1. 1 月 31 日开始按月订阅，2 月账期如何计算？3 月是否回到 31 日？
2. 用户在 DST 切换日 02:30 下单，系统应接受、顺延还是拒绝？
3. 美元定价、人民币结算、欧元发票，汇率和舍入在哪一步发生？
4. 如果税率在账期中途变化，已生成账单如何更正？
5. 客户合并后，旧订阅 ID 和旧发票 ID 应如何表现？
