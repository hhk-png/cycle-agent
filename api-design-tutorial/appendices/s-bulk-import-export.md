# 附录 S：批量操作、导入导出与数据可携带性

> 单个资源的 CRUD 是最容易设计的部分。真正考验契约的是“一次处理十万条”“把三年的数据带走”“从旧系统迁移过来”“失败一半怎么办”。本附录讨论批量写、导入、导出、迁移与可携带性的模式与陷阱。

## S.1 为什么批量是独立设计问题

批量不是“把单个请求循环调用 n 次”。一旦批量进入契约，就会出现单资源 API 不会遇到的问题：

| 问题 | 单资源 | 批量 |
|---|---|---|
| 原子性 | 一个资源成功或失败 | 全部成功？部分成功？如何报告？ |
| 幂等 | 一个 key | 批次 key 与条目 key 的关系 |
| 错误 | 一个错误 | 每个条目的错误、索引、原始输入 |
| 顺序 | 无关 | 条目之间是否依赖？ |
| 大小 | 受单条限制 | 受请求体、内存、数据库、下游限制 |
| 性能 | 一次查询/写入 | 批处理、分片、并发、背压 |
| 计费 | 一次调用 | 按条、按字节、按批次？重试是否重复计费？ |
| 可观测性 | 一个 trace | 批次级与条目级指标 |

如果契约没有回答这些问题，调用方会在生产环境用循环 + 重试来“自己实现批量”，最终把你的服务打垮。

## S.2 批量写的四种模式

### 模式一：批量端点，全有或全无

```http
POST /orders/batch
Content-Type: application/json
Idempotency-Key: batch_01J...

{
  "orders": [
    { "clientOrderId": "c-1", "items": [...] },
    { "clientOrderId": "c-2", "items": [...] }
  ]
}
```

语义：要么全部创建，要么全部不创建。适合强一致、条目间有业务约束的场景（如转账批次、库存预占）。

优点：调用方容易理解；缺点：一条坏数据会让整批失败；大事务带来锁与超时风险。

### 模式二：批量端点，逐条结果

```http
POST /orders/batch
Content-Type: application/json

{
  "orders": [
    { "clientOrderId": "c-1", "items": [...] },
    { "clientOrderId": "c-2", "items": [...] }
  ]
}

HTTP/1.1 207 Multi-Status
```

```json
{
  "batchId": "bat_123",
  "results": [
    { "index": 0, "status": 201, "id": "ord_1" },
    { "index": 1, "status": 422, "error": { "code": "VALIDATION_FAILED", "field": "items[0].quantity" } }
  ],
  "summary": { "succeeded": 1, "failed": 1 }
}
```

语义：每条独立成功或失败。适合导入、同步、大多数业务写入。

要点：

- `index` 必须稳定，调用方能对应回原始输入；
- 每条结果要有状态码、资源 ID 或错误对象；
- 顶层 HTTP 状态表达“批次是否被接受”，不要用 200 掩盖整体失败；
- 若整个请求格式错误，返回 400；
- 全部条目成功返回 200；部分条目失败返回 207（并在 body 中报告）；全部条目失败按主要失败原因返回 400/409/422；
- 207 源自 WebDAV Multi-Status（RFC 4918），用于普通 JSON 批量响应时属于约定用法，要在文档中说明 body 结构，并确认客户端/代理支持；
- 不要只返回失败条目，否则调用方无法知道成功的是哪些。

### 模式三：批量资源

把批次本身建模为资源：

```http
POST /import-jobs
GET  /import-jobs/{jobId}
GET  /import-jobs/{jobId}/errors
POST /import-jobs/{jobId}/cancel
```

适合大批量、长耗时、需要进度与错误报告的导入。批量资源把“同步请求”变成“异步任务”，是导入管线的标准形态。

### 模式四：流式批量

用 NDJSON 或分块上传逐条处理：

```http
POST /orders/stream
Content-Type: application/x-ndjson

{"clientOrderId":"c-1",...}
{"clientOrderId":"c-2",...}
```

适合超大文件、内存受限、需要边读边写的场景。响应也可以是流式的逐条结果。代价是错误处理与重试更复杂，通常需要配合幂等键与断点续传。

## S.3 批量大小、分片与背压

### 必须有限制

```text
单批最多 1,000 条
单批请求体最多 10 MB
单条最大 1 MB
批次处理超时 60s
每租户并发批次 5
```

限制不是“刁难调用方”，而是保护系统与给出可预测的失败。超过限制要返回明确的 413/422，并告诉调用方如何分片。

### 分片策略

- 按数量分片：每批 500～1,000 条；
- 按字节分片：避免超大单条撑爆内存；
- 按依赖分片：有顺序要求的条目放在同一批；
- 按租户/分区键分片：避免跨分区事务；
- 客户端并发受服务端限流约束，不能无限并行。

### 背压信号

- 429 + `Retry-After`；
- 503 + `Retry-After`；
- 批次排队深度与预计等待时间；
- 逐条流式响应中的 `retryAfter`；
- 明确的“请减小批次”错误码。

调用方应实现指数退避 + 抖动，并尊重 `Retry-After`。服务端应区分“限流”和“过载”：前者可以等，后者可能需要降级。

## S.4 导入管线

一个可靠的导入不是“接收文件 → 写数据库”，而是一条可恢复的管线。

```text
上传
  → 病毒/内容扫描
  → 格式与编码校验
  → schema 校验（逐行）
  → 业务校验（引用、权限、重复）
  → 暂存（staging）
  → 预览/试运行（可选）
  → 提交（事务/分片）
  → 错误报告
  → 对账与通知
```

### 关键设计

- **导入 ID 幂等**：同一文件重复上传不应重复写入。用文件哈希 + 租户 + 目标资源生成幂等键。
- **试运行（dry run）**：只校验不提交，返回错误报告。对高风险导入（财务、库存、权限）几乎是必需。
- **逐行错误报告**：行号、字段、原始值（脱敏）、错误码、建议修复。
- **部分提交**：要么明确“全有或全无”，要么明确“成功后不可回滚，失败行可重试”。不要含糊。
- **断点续传**：大文件分片上传；失败后从上次成功的分片继续。
- **schema 版本**：导入文件带版本，服务端按版本解析；旧版本至少支持一个弃用周期。
- **审计**：谁在什么时候导入了什么、多少行、成功/失败多少、是否覆盖了已有数据。
- **保留期**：原始文件、错误报告、staging 数据的保留与删除策略。

### 导入状态机

```text
uploaded → validating → validation_failed
                    └→ ready → importing → completed
                                      ├→ partially_completed
                                      ├→ failed
                                      └→ canceled
```

每个状态都要有 `updatedAt`、可查询的进度、可下载的错误报告。不要只给一个“处理中”。

## S.5 导出管线

### 同步导出 vs 异步导出

| 规模 | 方式 | 说明 |
|---|---|---|
| 小（< 1 万行 / < 10 MB） | 同步 | 直接返回文件流或 JSON |
| 中（< 100 万行） | 异步任务 + 签名 URL | 202 + 任务状态 |
| 大（> 100 万行） | 异步 + 分片/分区文件 | 清单文件 + 多个分片 |
| 持续 | 增量导出 / CDC / 数据订阅 | 按游标或事件流 |

### 导出的正确性

- **快照一致性**：导出开始时确定一个快照（事务 ID、时间点、游标），避免导出过程中数据变化导致前后不一致。
- **稳定排序**：分片导出要有稳定排序键，避免重复或遗漏。
- **格式**：CSV 适合人看与表格工具；JSONL 适合程序逐行处理；Parquet 适合分析；压缩（gzip/zstd）要声明。
- **编码**：UTF-8；CSV 在 Excel 场景可能需要 BOM；换行、引号、分隔符要正确转义。
- **CSV 注入**：以 `=`, `+`, `-`, `@` 开头的单元格要转义，防止打开表格时执行公式。
- **PII**：导出是否包含敏感字段？是否需要脱敏、审批、水印、审计？
- **访问控制**：签名 URL 短期有效、绑定租户与文件、不可枚举；下载要审计。
- **保留期**：导出文件到期删除；大文件存储成本要计入单位经济。

### 导出任务 API

```http
POST /exports
{
  "resource": "orders",
  "format": "csv",
  "filter": { "createdAt": { "gte": "2026-01-01" } },
  "columns": ["id", "status", "total", "createdAt"]
}

HTTP/1.1 202 Accepted
Location: /exports/exp_123
```

```json
{
  "id": "exp_123",
  "status": "running",
  "progress": { "rowsProcessed": 120000, "estimatedTotal": 500000 },
  "createdAt": "2026-11-26T10:00:00Z",
  "expiresAt": "2026-12-03T10:00:00Z"
}
```

完成后返回签名 URL，而不是把文件代理过 API 进程。代理大文件会占用连接、内存与带宽，且难以做断点续传。

## S.6 数据可携带性

“可携带性”不只是技术导出，它是合同、监管与信任的一部分。

### 监管背景

- **GDPR**：数据主体有权以结构化、常用、机器可读的格式获取其个人数据，并在技术可行时要求直接传输给另一个控制者。
- **EU Data Act**：自 2025 年 9 月 12 日起适用，要求云与数据处理服务提供开放、文档化的接口与切换能力；自 2027 年 1 月 12 日起，切换费用原则上禁止（有限例外以官方文本为准）。
- **CCPA/CPRA、PIPL、LGPD、DPDP** 等也有访问、删除、可携带或更正的要求。

具体适用与时限请以法务意见和官方文本为准。工程上要准备的是能力，而不是一句“支持导出”。

### 可携带性接口

```http
POST /privacy/export-requests
{
  "subjectId": "user_123",
  "format": "jsonl",
  "include": ["profile", "orders", "events"]
}

POST /privacy/delete-requests
{
  "subjectId": "user_123",
  "reason": "erasure_request"
}
```

要点：

- **身份验证**：不能让攻击者导出别人的数据；DSAR 请求要验证主体身份。
- **范围**：个人数据、派生数据、日志、备份、第三方共享数据，边界要写清。
- **格式**：机器可读、带 schema 与字段说明；不要只给 PDF。
- **时限**：监管通常有响应时限（如 GDPR 一个月，可延长），系统要能跟踪。
- **删除 vs 保留**：法律留存、财务记录、反欺诈、备份可能要求保留；要能“删除可见数据 + 保留合规副本 + 到期清除”。
- **证据**：导出与删除都要有审计记录，能证明“何时、为谁、做了什么”。

### 避免锁定

- 标识符要有稳定、可导出的业务 ID，而不只是内部自增 ID；
- 枚举、状态、金额、时间的语义要有文档；
- 导出包含 schema 版本；
- 附件与二进制对象要能批量导出；
- 事件与审计日志要能按时间范围导出；
- 合同里写明退出协助、迁移窗口与费用。

## S.7 迁移与对账

从旧系统迁移到新 API，通常不是“一次性切流”，而是一段并行运行。

```text
1. 双读：新系统读旧数据，验证一致性
2. 双写：新系统写旧系统（或反之），观察差异
3. 回填：历史数据批量导入
4. 对账：按 ID、金额、状态、数量比对
5. 灰度切流：按租户/流量比例切换
6. 回滚预案：保留旧路径与开关
7. 下线：确认无流量、无差异、无回滚需求
```

对账要回答：

- 哪些记录只在新系统存在？
- 哪些只在旧系统存在？
- 哪些字段不一致？差异是否可解释？
- 金额/库存/余额的总额是否一致？
- 差异如何修复？修复是否幂等？

没有对账的迁移，只是“看起来切成功了”。

## S.8 计费与配额

批量与导出最容易产生计费争议：

- 按请求计费：一个批次算一次，调用方会尽量合并；
- 按条计费：重试是否重复计费？失败条目是否计费？
- 按字节计费：压缩前还是压缩后？导出流量是否计费？
- 按计算资源计费：异步任务的 CPU/扫描行数如何计量？
- 免费额度：是否覆盖导入导出？滥用如何限制？

契约要写清：**计量单位、何时计量、重试与失败是否计费、争议如何申诉。** 否则财务对账会成为支持工单的主要来源。计量事件、去重、迟到事件、发票与对账的完整设计见[附录 V](v-metering-billing.md)。

## S.9 反模式

- 批量端点没有条数/字节上限；
- 部分成功却返回 200，且不告诉调用方哪些失败；
- 错误只返回第一条，调用方要反复试错；
- 导入没有试运行，直接覆盖生产数据；
- 导出用同步请求，超时后调用方重复触发；
- 导出文件 URL 永久有效、可枚举；
- CSV 不转义，导致公式注入；
- 删除请求只删主表，日志/备份/搜索索引仍保留；
- 迁移没有对账，靠“用户没投诉”判断成功；
- 重试导致重复计费或重复写入。

## S.10 检查清单

- [ ] 批量语义明确：全有或全无，还是逐条结果？
- [ ] 每条结果有稳定索引、状态、资源 ID 或错误对象。
- [ ] 有单批条数、字节、并发、超时限制，并返回可操作的错误。
- [ ] 幂等键覆盖批次与条目，重试不会重复写入。
- [ ] 大批量走异步任务，有状态、进度、取消与错误报告。
- [ ] 导入支持试运行、逐行错误、断点续传与 schema 版本。
- [ ] 导出有一致性快照、稳定排序、正确转义与签名 URL。
- [ ] 导出文件有保留期、访问控制与审计。
- [ ] 数据可携带性覆盖个人数据、附件、事件与 schema 说明。
- [ ] 删除与保留策略能同时满足隐私与合规留存。
- [ ] 迁移有双写/回填/对账/灰度/回滚，不靠运气。
- [ ] 计费单位、重试计费与失败计费写进契约。

## S.11 小结

- 批量是把“单资源契约”放大到“集合契约”，原子性、错误、幂等、顺序、成本都会被放大。
- 同步批量适合小规模与强一致；异步任务适合大规模与可恢复。
- 导入的关键不是写库，而是校验、暂存、试运行、错误报告与对账。
- 导出的关键是快照一致性、格式正确、访问控制与保留期。
- 可携带性是监管要求，也是降低锁定、建立信任的产品能力。
- 迁移的成功标准不是“切流完成”，而是“对账无差异、可回滚、可解释”。

## 设计练习

为一个 SaaS 产品设计“客户数据导出与迁移”能力：

1. 导出包含哪些资源、附件、事件与审计日志？
2. 如何保证导出期间数据变化不会造成前后不一致？
3. 10 GB 导出如何分片、压缩、加密与传输？
4. 删除请求如何处理备份、日志与法律留存？
5. 从旧系统迁移时，如何对账金额、数量与状态？
6. 如果导出被滥用为“批量爬取”，如何限流与审计？

写出一份 API 表面（端点、状态机、错误码）和一页迁移对账方案。
