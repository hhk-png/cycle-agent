# 附录 Q：国际化、本地化与可访问性

大多数 API 设计指南把“国际化”简化成一句“支持 `Accept-Language`”。但真正面向全球用户的 API，会在很多不起眼的地方出错：

- 把 `2026-12-01` 当成一个时刻；
- 用字符数限制用户名，结果把 emoji 截断；
- 用默认的 Unicode 排序，让德语和瑞典语用户找不到内容；
- 把金额存成浮点数，日元和科威特第纳尔出现小数；
- 把错误信息拼接成句子，翻译后语序完全错乱；
- 文档只有鼠标交互，键盘与屏幕阅读器用户无法完成首次调用。

本附录把国际化（i18n）、本地化（l10n）与可访问性（a11y）放在一起，因为它们的共同点是：**契约不能假设所有用户、语言和设备都与设计者相同。**

## Q.1 先区分三件事

| 概念 | 含义 | API 中的体现 |
|---|---|---|
| 国际化（i18n） | 让系统在设计上支持多语言/多区域 | 字段结构、locale 参数、时区、货币、排序 |
| 本地化（l10n） | 为特定市场提供翻译与适配 | 错误消息、文档、日期格式、地址格式 |
| 可访问性（a11y） | 让残障用户也能使用 | 文档、媒体替代文本、错误提示、认证方式 |

国际化是架构能力，本地化是内容交付，可访问性是基本质量。三者都不能靠“上线后补”。

## Q.2 locale 协商

### 语言标签

使用 BCP 47：

```text
zh-Hans-CN     简体中文（中国）
zh-Hant-TW     繁体中文（台湾）
sr-Latn-RS     塞尔维亚语（拉丁字母，塞尔维亚）
en-US          英语（美国）
pt-BR          葡萄牙语（巴西）
```

不要用 `zh_CN`、`cn` 这类非标准写法作为契约值。`en` 是合法的 BCP 47 标签，表示“任意英语”，但比 `en-US` 更宽泛；响应中应尽量返回与实际内容匹配的完整标签。

### 协商方式

`Accept-Language` 是 HTTP 标准机制：

```http
Accept-Language: zh-CN, zh;q=0.9, en;q=0.8
```

服务端按权重与自身支持的语言选择，并在响应中声明：

```http
Content-Language: zh-CN
Vary: Accept-Language
```

但 `Accept-Language` 不是唯一来源。优先级通常是：

1. 用户显式设置（账号偏好、请求参数）；
2. 会话/租户默认；
3. `Accept-Language`；
4. 服务端默认。

不要根据 IP 地理定位猜测语言。IP 只能说明网络位置，不能说明用户语言；一个在德国的英语用户不应收到德语错误。

### locale 放在哪里

| 方式 | 优点 | 缺点 |
|---|---|---|
| `Accept-Language` | 标准、透明 | 缓存要 `Vary`，URL 不体现 |
| 查询参数 `?locale=zh-CN` | 可分享、可缓存 | 污染 URL，容易被忽略 |
| 路径 `/zh-CN/...` | CDN 友好、可索引 | 路由复杂，重复内容 |
| 用户/租户配置 | 一致性好 | 不适合多语言并存 |

对公开内容站点，路径或子域名更适合 CDN；对 API，`Accept-Language` + 用户偏好更常见。无论选哪种，都要在文档中写清楚优先级与回退链。

### 回退链

```text
zh-Hant-HK → zh-Hant → zh → en → 默认
```

回退不是“随便找一个”。要保证：

- 回退后语义不改变，只改变语言；
- 回退可观测（记录实际使用的 locale）；
- 不要让 `zh-Hant` 用户收到简体而不自知；
- 对阿拉伯语、希伯来语等 RTL 语言，布局与方向也要回退。

## Q.3 Unicode 与文本

### 编码

JSON 默认 UTF-8。不要在 JSON 中假设单字节，也不要用本地编码（GBK、Shift-JIS）作为契约。文件上传、文件名、HTTP 头中的非 ASCII 内容都要明确编码。

### 规范化

同一个字符可能有多种 Unicode 表示：

```text
é  = U+00E9（预组合）
é  = U+0065 U+0301（e + 组合重音）
```

如果不去重/规范化，用户名、邮箱、搜索键会出现“看起来一样但比较不相等”。建议：

- 存储前统一 NFC（大多数场景）；
- 比较时使用 case folding + normalization；
- 不要对用户可见文本做不可逆的“清洗”；
- 密码若要做 Unicode 规范化，注册与登录必须使用完全相同的规则；不要做有损清洗或静默截断。

### 长度与截断

字符串长度至少有三种含义：

- 字节数（存储/传输）；
- Unicode 码点数（语言 API 常见）；
- 用户感知字符（grapheme cluster）。

```text
"👨‍👩‍👧‍👦" 可能是一个 grapheme，但由多个码点组成；
"é" 可能是 1 或 2 个码点；
某些 emoji 在 UTF-16 中占 2 个 code unit。
```

API 契约要明确限制的是哪一种。用户名、昵称、标题通常应按 grapheme 限制，并按字节做存储上限。截断时不要把一个 grapheme 切成两半。

### 大小写

大小写转换不是全局一致的：

- 土耳其语：`i` 的大写是 `İ`，`I` 的小写是 `ı`；
- 德语：`ß` 的大写可以是 `SS`；
- 希腊语：词尾 sigma `ς` 与 `σ`；
- 立陶宛语等有特殊规则。

不要用简单的 `toLowerCase()` 做唯一性判断。邮箱本地部分理论上区分大小写（实践中多半不区分），域名不区分；用户名是否区分大小写要在契约中写清。

### 双向文本与 RTL

阿拉伯语、希伯来语、波斯语、乌尔都语是 RTL。API 层面要注意：

- 不要把方向写死在字段里；
- 返回纯文本，让客户端按 locale 渲染；
- 混合 LTR/RTL 时使用 Unicode 隔离符（如 U+2068/U+2069）或让前端处理；
- 数字、URL、代码片段在 RTL 文本中要保持 LTR；
- 文档与错误页要测试 RTL 布局。

## Q.4 排序、搜索与大小写

### 排序规则

Unicode 码点顺序不是人类排序。不同语言对同一组词的排序不同：

```text
德语：ä 可能排在 a 后，也可能与 ae 等价；
瑞典语：å、ä、ö 排在 z 之后；
西班牙语：ñ 在 n 之后；
中文：按拼音、笔画或部首；
日文：按假名、汉字读音或笔画。
```

API 不要自己实现排序。使用 ICU/CLDR 的 collation，并允许客户端指定：

```http
GET /v1/contacts?sort=name&locale=sv-SE
```

返回时说明排序规则：

```json
{
  "sort": { "field": "name", "locale": "sv-SE", "strength": "primary" }
}
```

`strength` 决定是否区分大小写、重音、变体。搜索通常用 primary/secondary，显示排序可能用 tertiary。

### 搜索

多语言搜索要处理：

- 分词：中文、日文、泰语没有空格，需要专门分词；
- 词干：英语 `running` → `run`，德语复合词；
- 同义词：`手机` / `移动电话` / `cellphone`；
- 拼写容错：编辑距离、语音相似；
- 变音符号：`café` 与 `cafe`；
- 转写：阿拉伯语/希伯来语的拉丁转写；
- 大小写与全半角。

不要假设“空格分词”适用于所有语言。搜索索引的 analyzer 要按字段语言配置，而不是全局一个。

### 排序稳定性

分页排序必须稳定。多语言排序可能产生大量相等值，要加次级排序键（如 ID）：

```text
ORDER BY name_collation, id
```

否则翻页时会出现重复或遗漏。

## Q.5 时间、时区与日历

### 三种时间语义

| 类型 | 示例 | 用途 |
|---|---|---|
| 时刻（instant） | `2026-12-01T11:30:00Z` | 日志、创建时间、过期时间 |
| 带时区的本地时间 | `2026-12-01T19:30:00+08:00` | 会议、演出、航班 |
| 本地日期 | `2026-12-01` | 生日、账单日、节假日 |

不要用一个字段表达三种语义。特别是“本地日期”不要伪造成 `00:00:00Z`，否则跨时区会变成前一天。

### 时区

- 使用 IANA 时区 ID：`Asia/Shanghai`、`America/New_York`；
- 不要用 `GMT+8` 作为存储值，它不能表达夏令时；
- 不要假设时区偏移固定；
- 未来时区的规则可能变化，存储时保留时区 ID 与原始本地时间；
- 跨时区排序用 UTC 时刻，展示用本地时间。

### 夏令时

夏令时会产生：

- 不存在的本地时间（春季跳过的一小时）；
- 重复的本地时间（秋季重复的一小时）；
- 不同的日长。

对“每天 9 点”的任务，要明确是按当地墙钟时间还是按固定 UTC 间隔。前者在夏令时切换日仍然是 9 点，后者会偏移一小时。

### 日历与周

- 公历不是唯一日历；伊斯兰历、佛历、和历在部分场景使用；
- 一周从周几开始因地区而异；
- ISO 周（周一为第一天）与本地周不同；
- 财政年度、季度定义因公司/地区而异。

如果 API 涉及“周”“季度”“财年”，要在契约中定义，而不是让客户端猜。

### 持续时间

使用 ISO 8601 duration：

```text
PT1H30M     1 小时 30 分
P30D        30 天
P1M         1 个月（语义依赖起始日期）
```

“1 个月”不是固定秒数。到期时间、订阅周期、试用期要明确是按日历还是按秒计算。

## Q.6 数字、货币与单位

### 金额

本教程统一使用“最小货币单位整数 + ISO 4217 币种”的 wire format：

```json
{
  "amount": 12900,
  "currency": "CNY"
}
```

其中 `amount` 是最小货币单位的整数（人民币为分，日元为元，KWD/BHD 为千分之一）。`scale` 不随金额一起传，由币种定义决定；需要展示时由客户端按 ISO 4217 格式化。

要点：

- 币种用 ISO 4217；
- 不同币种小数位不同：JPY 0 位，KWD/BHD 3 位；
- 不要用浮点数，也不要在 API 中传输 `"129.00"` 这样的金额字符串；
- 不要假设所有币种都能用两位小数；
- 汇率、手续费、税额要分行；
- 四舍五入规则要写清（银行家舍入还是四舍五入）；
- 发票展示可以使用十进制字符串，但 API 资源与事件应使用上述整数格式。

### 数字格式

API 返回机器可读的数字，不要返回 `1,234.56` 这种带千分位的字符串。展示格式由客户端按 locale 处理。如果需要返回格式化文本，单独提供 `display` 字段，并明确它不稳定、不可解析。

### 单位

物理量要带单位，使用 UCUM 或明确的枚举：

```json
{
  "value": 12.5,
  "unit": "kg"
}
```

不要用 `weight: 12.5` 让调用方猜是千克还是磅。

## Q.7 姓名、地址与电话

### 姓名

不要假设“名 + 姓”：

- 有些文化姓名顺序是姓在前；
- 有些人只有一个名字；
- 有父名、教名、氏族名；
- 有敬称、代称、罗马化拼写；
- 有非拉丁脚本。

推荐：

```json
{
  "fullName": "张三",
  "givenName": "三",
  "familyName": "张",
  "displayName": "张三",
  "script": "Hans"
}
```

字段可以为空，不要强制拆分。排序时使用 `sortName` 或让客户端按 locale 处理。

### 地址

地址格式因国家而异。不要用固定的 `street/city/state/zip` 强制所有国家：

```json
{
  "country": "JP",
  "postalCode": "100-0001",
  "region": "東京都",
  "locality": "千代田区",
  "addressLines": ["千代田1-1"],
  "formatted": "東京都千代田区千代田1-1 100-0001"
}
```

`addressLines` 保留原始行，结构化字段用于查询与校验。不要假设有“州”或“邮编”。

### 电话

使用 E.164 存储：

```text
+8613800138000
```

同时保留国家代码与原始输入。不要用正则强制所有国家格式；使用 libphonenumber 之类的库按区域校验。短信验证码要考虑国际可达性与成本。

## Q.8 错误与文档本地化

### 稳定错误码 + 可本地化消息

```json
{
  "code": "ORDER_INVALID_STATE",
  "title": "订单状态不允许此操作",
  "detail": "订单当前状态为 SHIPPED，不能取消。",
  "messageKey": "order.invalid_state",
  "params": { "currentStatus": "SHIPPED" }
}
```

规则：

- `code` 永远英文、稳定、可机器判断；
- `title`/`detail` 可按 `Accept-Language` 本地化；
- `messageKey` + `params` 让客户端自己翻译；
- 不要要求客户端解析本地化文本；
- 本地化不能改变错误码或 HTTP 状态；
- RTL 语言的错误页要测试。

### 翻译工作流

- 源字符串集中管理，不散落在代码里；
- 使用 ICU MessageFormat 处理复数、性别、语序；
- 翻译有版本，与 API 版本解耦；
- 伪本地化（pseudo-localization）用于发现硬编码与布局问题；
- 翻译缺失时回退到默认语言，并记录日志；
- 不要让机器翻译直接进入生产错误消息而不审核。

### 复数与语序

```text
英文：1 item / 2 items
中文：1 件 / 2 件
阿拉伯语：零、一、二、少数、多数、其他等多种形式
```

不要拼接：

```text
"Found " + n + " results"
```

翻译后语序可能完全不同。使用 ICU MessageFormat：

```text
{count, plural, one {找到 # 个结果} other {找到 # 个结果}}
```

## Q.9 缓存与内容协商

本地化内容容易被缓存串味。要做到：

- `Vary: Accept-Language`（或 `Vary: Accept-Language, Accept-Encoding`）；
- 如果 locale 在 URL 中，缓存键自然区分；
- `ETag` 按语言版本生成，不要一个 ETag 覆盖所有语言；
- `Content-Language` 告诉缓存与客户端实际语言；
- CDN 配置要尊重 `Vary`，否则可能把中文页面发给英文用户；
- 用户私有内容用 `Cache-Control: private`。

```http
GET /v1/help/articles/refunds
Accept-Language: zh-CN
Accept-Encoding: gzip

HTTP/1.1 200 OK
Content-Language: zh-CN
Vary: Accept-Language, Accept-Encoding
ETag: "zh-CN-v3"
```

## Q.10 可访问性

API 的可访问性有两层：**文档/门户的可访问性**，以及**API 所服务产品的可访问性**。

### 文档与门户

- 遵循 WCAG 2.2 AA；
- 键盘可完成所有操作；
- 代码块可复制、可聚焦；
- 对比度足够，不只靠颜色传达状态；
- 标题层级正确，便于屏幕阅读器导航；
- 表单有 label 与错误提示；
- 支持浏览器缩放与窄屏；
- 提供文本版架构图或替代描述。

### API 返回的内容

- 图片、视频、音频提供 alt text、字幕、转录；
- 媒体资源暴露多语言音轨与字幕轨道；
- 错误信息不只是颜色或图标，要有文本；
- 验证码提供无障碍替代方案；
- 认证流程不要只依赖认知测试或视觉识别；
- 时间限制可延长或关闭。

```json
{
  "media": {
    "videoUrl": "https://cdn.example.com/lecture.mp4",
    "captions": [
      { "language": "zh-CN", "url": "https://cdn.example.com/lecture.zh-CN.vtt" },
      { "language": "en", "url": "https://cdn.example.com/lecture.en.vtt" }
    ],
    "audioDescription": "https://cdn.example.com/lecture.ad.vtt",
    "transcript": "https://cdn.example.com/lecture.txt"
  }
}
```

### 认证与安全

可访问性不是“降低安全”。但要注意：

- 短信 OTP 对某些残障用户不可用，应提供备用方式；
- 生物识别要有替代方案；
- 会话超时前要警告并允许延长；
- 不要用“识别图中扭曲文字”作为唯一验证；
- 屏幕阅读器要能读出错误与下一步。

## Q.11 测试矩阵

| 维度 | 样本 |
|---|---|
| 语言 | 中文、英文、阿拉伯语（RTL）、德语（长词）、日语（无空格）、土耳其语（i） |
| 脚本 | 拉丁、汉字、假名、阿拉伯、天城文、emoji |
| 时区 | UTC、Asia/Shanghai、America/New_York、Europe/Berlin、Australia/Lord_Howe（30 分钟偏移） |
| 夏令时 | 春季跳变、秋季重叠、南半球 |
| 货币 | CNY、USD、JPY（0 位）、KWD（3 位） |
| 数字 | 小数、负数、千分位、不同数字系统 |
| 排序 | 瑞典语、德语、西班牙语、中文拼音 |
| 复数 | 英语、中文、阿拉伯语、俄语 |
| 布局 | LTR、RTL、长文本、窄屏、200% 缩放 |
| 可访问性 | 键盘、屏幕阅读器、高对比度、减少动画 |

测试不要只验证“接口返回 200”。要验证：

- locale 回退是否符合预期；
- 排序是否与 locale 一致；
- 日期是否在 DST 边界正确；
- 金额舍入是否正确；
- 截断是否破坏 grapheme；
- 错误消息是否可翻译且不泄露内部信息。

## Q.12 检查清单

- [ ] 语言标签使用 BCP 47，并有回退链。
- [ ] locale 来源与优先级明确。
- [ ] 文本存储与比较使用一致的规范化。
- [ ] 长度限制明确是字节、码点还是 grapheme。
- [ ] 排序使用 locale 感知的 collation。
- [ ] 搜索 analyzer 按语言配置。
- [ ] 时刻、本地时间、本地日期分别建模。
- [ ] 时区使用 IANA ID，处理 DST。
- [ ] 金额使用 ISO 4217 与明确的最小单位。
- [ ] 姓名、地址、电话不强制西方格式。
- [ ] 错误码稳定，消息可本地化。
- [ ] 复数与语序使用 ICU MessageFormat。
- [ ] 缓存正确处理 `Vary` 与 `Content-Language`。

## Q.13 小结

- 国际化不是“加一个语言参数”，而是对文本、时间、数字、排序与缓存的系统性设计。
- 本地化不是翻译字符串，而是让内容在目标市场可用、可理解、可维护。
- 可访问性不是额外功能，而是契约是否对所有人成立。
- 最贵的错误往往不是“翻译错了”，而是“根本没有为另一种语言、时区或输入方式建模”。
