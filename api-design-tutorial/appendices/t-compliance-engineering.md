# 附录 T：合规工程——从监管条款到 API 能力

> 本附录讨论如何把监管条款翻译成可实现的 API 能力、运行流程与证据，而不是复述法条。它不是法律意见；具体适用、时限与豁免请以法务意见和官方文本为准。内容基准为 2026 年 11 月。

## T.1 合规不是法务附注

“供应商应遵守所有适用法律”是一句不可验证的合同语言。工程上真正有用的合规，必须能回答三个问题：

1. **哪条义务？** 不是“隐私”，而是“数据主体在法定时限内（GDPR 通常为一个月，可依法延长）获得可携带的副本”。
2. **哪个 API 能力承接？** 端点、字段、状态机、保留任务、审计日志。
3. **什么证据？** 日志、报告、测试、审计导出、删除证明。

| 义务 | API 能力 | 证据 |
|---|---|---|
| 访问个人数据 | DSAR 查询端点 / 导出任务 | 请求记录、导出清单、交付时间 |
| 更正个人数据 | PATCH / 更正请求 | 变更前后值、审计 |
| 删除个人数据 | 删除请求 + 级联/保留规则 | 删除证明、保留例外说明 |
| 可携带 | 结构化导出 + schema | 文件格式、字段映射、传输记录 |
| 同意管理 | 同意记录、撤回、目的绑定 | 同意版本、时间、来源、撤回 |
| 数据最小化 | 字段级采集与返回控制 | schema、访问日志、字段清单 |
| 数据驻留 | 区域路由、租户钉扎 | 部署清单、日志/备份区域证据 |
| 审计 | 不可篡改审计日志 | 日志完整性、保留、访问控制 |
| 事件通知 | 检测、分级、通知工作流 | 时间线、通知副本、根因报告 |
| AI 透明 | 模型卡、内容标记、人工监督 | 文档、评估、日志 |

如果一张合规表只有“是/否”，没有能力与证据，它就是一张愿望清单。

## T.2 数据映射与分类

在写任何合规代码之前，先画数据流：

```text
数据主体 → 采集点 → API → 存储 → 派生/索引 → 分析 → 第三方 → 备份 → 删除
```

每个节点记录：

- 数据类别：身份、联系、支付、健康、位置、行为、生物特征、未成年人；
- 敏感级别：公开、内部、机密、受限；
- 法律基础/目的：合同、同意、法定义务、合法利益；
- 保留期限与删除触发；
- 存储区域与跨境路径；
- 谁可以访问（人、服务、第三方）；
- 是否进入日志、缓存、搜索索引、数据仓库、模型训练。

### 分类要落到字段

```yaml
fields:
  email:
    class: personal
    sensitivity: confidential
    purpose: [account, notification]
    retention: account_lifetime_plus_30d
  card_number:
    class: pci
    sensitivity: restricted
    tokenized: true
    retention: never_store_pan
  health_note:
    class: special_category
    sensitivity: restricted
    purpose: [care]
    retention: 7y_legal
```

字段级分类是很多能力的源头：脱敏、访问控制、导出范围、保留任务、审计、AI 训练过滤。只在表级分类，最终会在“这个字段能不能返回”上反复争论。

## T.3 隐私接口

### 同意管理

同意不是一次弹窗，而是一组可验证的记录：

```http
POST /consents
{
  "subjectId": "user_123",
  "purpose": "marketing_email",
  "version": "2026-05",
  "source": "web_signup",
  "granted": true
}

DELETE /consents/{consentId}
```

要点：

- 目的要具体，不能把“营销”与“服务通知”混在一起；
- 记录同意文本版本、时间、来源、IP/设备（在合法范围内）；
- 撤回要能传播到下游系统与营销工具；
- 同意不是唯一法律基础；合同履行、法定义务等场景不要误用同意；
- 未成年人、特殊类别数据需要额外保护。

### DSAR（数据主体访问请求）

```http
POST /privacy/requests
{
  "type": "access",          // access | correct | delete | portability | restrict
  "subjectId": "user_123",
  "verificationToken": "..."
}

GET /privacy/requests/{requestId}
```

状态机：

```text
received → identity_verification → in_progress → completed
                                            ├→ partially_completed
                                            ├→ rejected (with reason)
                                            └→ expired
```

设计要点：

- **身份验证**：不能仅凭邮箱或用户 ID 就导出/删除；要防止账户接管与社交工程。
- **范围**：个人数据、派生数据、日志、备份、第三方共享、模型训练数据，逐项说明。
- **时限**：监管通常有响应窗口（如 GDPR 一个月，可延长）；系统要能计时、提醒、升级。
- **拒绝理由**：法律例外、他人权利、重复请求、明显无根据；拒绝也要有记录与申诉路径。
- **异步**：大数据量用任务 + 签名 URL，不要阻塞请求。
- **证据**：请求、验证、处理、交付、删除都要审计。

### 删除的真相

“删除”通常不是 `DELETE FROM users`。要区分：

| 数据位置 | 处理方式 |
|---|---|
| 主数据库 | 删除或匿名化 |
| 关联表 | 级联删除或置空 |
| 搜索索引 | 删除文档 |
| 缓存 | 失效/删除 |
| 对象存储 | 删除对象与版本 |
| 日志 | 按保留策略清理，或写入时脱敏 |
| 备份 | 到期自然清除；必要时可检索删除 |
| 数据仓库 | 分区删除/匿名化 |
| 第三方 | 通知 subprocessor 删除 |
| 模型训练 | 不回溯训练，但要从后续训练集排除；评估记忆风险 |

契约要写清“删除何时生效、哪些副本会保留、保留多久、为什么”。用户看到“已删除”但后台仍保留三年，是信任与合规的双重问题。

## T.4 数据驻留与跨境

数据驻留不是“选一个 region 部署”这么简单。至少包括：

- 主数据存储区域；
- 备份与灾备区域；
- 日志、指标、Trace 的存储区域；
- 缓存与搜索索引区域；
- 密钥管理区域；
- 支持人员所在区域与访问路径；
- 第三方 subprocessor 的处理区域；
- 模型推理与训练区域。

### 技术实现

- **租户钉扎**：租户创建时确定区域，路由层按租户/数据主权选择后端；
- **区域化部署**：每个区域独立数据平面，控制平面可以集中但不下发数据；
- **禁止跨区复制**：包括日志、备份、分析管道；
- **密钥本地化**：KMS/HSM 与数据同区；
- **支持访问控制**：跨区支持需要审批、临时凭证、审计；
- **数据出口**：导出、Webhook、事件流都可能跨境，不能只盯数据库。

### 跨境机制

不同司法区有不同机制：充分性认定、标准合同条款（SCC）、约束性公司规则（BCR）、单独同意、安全评估、标准合同备案等。API 设计要能支持：

- 数据分类与区域标签；
- 传输记录与目的地；
- 同意/合同依据的版本；
- 数据主体请求的跨区协调；
- 监管问询时的证据导出。

## T.5 审计与证据

审计日志是合规的“黑匣子”。它必须回答：谁、在何时、从哪里、对什么、做了什么、结果如何、为什么。

### 审计事件结构

```json
{
  "eventId": "aud_01J...",
  "occurredAt": "2026-11-26T10:15:30.123Z",
  "actor": {
    "type": "user",              // user | service | agent | support
    "id": "user_123",
    "tenantId": "t_456",
    "onBehalfOf": "user_789"
  },
  "action": "order.refund",
  "resource": { "type": "order", "id": "ord_123" },
  "outcome": "success",
  "reason": "customer_request",
  "source": { "ip": "203.0.113.10", "userAgent": "...", "requestId": "req_..." },
  "before": { "status": "PAID" },
  "after": { "status": "REFUNDED" },
  "policy": { "decision": "allow", "rule": "refund_within_30d" }
}
```

### 审计的工程要求

- **不可篡改**：追加写、WORM 存储、哈希链或外部锚定；
- **完整性**：写入失败要告警，不能“审计丢了但业务成功”；
- **保留**：按法规与合同设定，通常长于业务数据；
- **访问控制**：审计日志本身包含敏感信息，读取要授权与审计；
- **可查询**：按主体、资源、时间、动作、结果查询；
- **可导出**：监管/客户审计时能给出完整证据；
- **最小化**：不要记录完整令牌、密码、PAN、健康详情；必要时哈希或掩码；
- **时钟**：统一 UTC，记录时钟同步状态。

### 职责分离

高风险操作（退款、权限变更、数据导出、删除）应要求：

- 双人审批；
- 或强认证 + 理由 + 事后审计；
- 不能由同一个主体既发起又批准；
- 支持人员访问客户数据要有工单、时限、可见性。

## T.6 运营韧性监管：DORA 与 NIS2

### DORA

DORA（Digital Operational Resilience Act，Regulation (EU) 2022/2554）自 **2025 年 1 月 17 日**适用，覆盖欧盟金融实体及其关键 ICT 第三方提供商。对 API 平台的典型影响：

- **ICT 风险管理**：资产、依赖、变更、漏洞、容量、备份；
- **事件报告**：重大 ICT 事件分级、时限报告、根因与恢复；
- **第三方风险**：合同条款、退出策略、审计权、集中度风险、ICT 第三方登记册；
- **测试**：韧性测试、威胁导向渗透测试（TLPT）；
- **信息共享**：威胁情报共享的安排。

API 合同与运行要能提供：SLA/SLO、事件通知、审计权、退出协助、数据可携带、分包商清单、区域与依赖说明。

### NIS2

NIS2（Directive (EU) 2022/2555）于 2023 年 1 月生效，成员国转化截止日为 **2024 年 10 月 17 日**；各国落地进度不一，实际义务取决于所在国法律。它覆盖能源、交通、金融、健康、数字基础设施、ICT 服务等多个行业，强调：

- 风险管理与治理责任；
- 供应链安全；
- 事件报告：早期预警（通常 24 小时内）、事件通知（通常 72 小时内）、最终报告（通常一个月内）；
- 业务连续性与危机管理；
- 漏洞披露与补丁管理。

对 API 的映射：资产清单、依赖图、日志与检测、事件分级、通知模板、供应商安全要求、演练记录。

> 监管时限会因国家转化与实施细则变化。把“24/72 小时/一个月”写进运行手册时，必须核对适用司法区的最终文本。

## T.7 AI 合规

AI 让 API 合规多出几个维度：训练数据、模型行为、透明度、人类监督、内容来源、评估与事件。

### EU AI Act 的时间线

截至 2026 年 11 月，需要区分原始文本与后续调整：

- 法规于 **2024 年 8 月 1 日**生效；
- 禁止性实践自 **2025 年 2 月 2 日**适用；
- 通用目的 AI（GPAI）义务自 **2025 年 8 月 2 日**适用；
- 原定 2026 年 8 月的高风险义务，经 2026 年 7 月的 AI Omnibus（Digital Omnibus on AI）调整，Annex III 独立高风险系统推迟至 **2027 年 12 月 2 日**，嵌入受监管产品的高风险系统推迟至 **2028 年 8 月 2 日**；部分透明度与标记义务仍在 2026～2027 年分阶段适用。

这不是“合规可以拖到 2028”的信号。高风险系统的数据治理、风险管理、技术文档、日志、人类监督、评估与上市后监测，都需要提前建设。具体日期与适用范围以 EUR-Lex 与主管机构指引为准。

### 风险分级与 API 能力

| 风险等级 | 例子 | API 侧要准备 |
|---|---|---|
| 禁止 | 社会评分、操纵性技术 | 不做；建立禁用清单与审查 |
| 高风险 | 招聘筛选、信贷、关键基础设施、教育评估 | 风险管理、数据治理、技术文档、日志、人类监督、准确性/鲁棒性、上市后监测 |
| 有限风险 | 聊天机器人、深度伪造 | 透明度：告知用户在与 AI 交互、标记生成内容 |
| 最小风险 | 垃圾邮件过滤、游戏 | 一般产品与安全要求 |

### GPAI 与模型提供方

如果 API 提供的是通用模型能力，要考虑：

- 模型卡/系统卡：能力、限制、训练数据摘要、评估结果；
- 版权政策与训练数据摘要；
- 下游集成商所需的信息；
- 严重事件报告；
- 系统性风险模型的额外评估与缓解；
- 禁止用途与可接受使用政策。

### AI API 的合同与接口

- 输入/输出数据的使用范围：是否用于训练？保留多久？
- 输出归属与责任边界；
- 模型版本、弃用、行为变化的通知；
- 评估与红队报告的可披露范围；
- 人工监督与申诉渠道；
- 内容标记（机器可读水印/元数据）；
- 事件通知与补救；
- 子处理者与区域；
- 模型迁移与数据导出。

## T.8 行业与区域矩阵

下表用于识别“哪些要求会变成 API 能力”，不是法律适用意见。

| 法规/标准 | 触发条件 | 典型 API 能力 | 证据 |
|---|---|---|---|
| GDPR / UK GDPR | 处理欧盟/英国个人数据 | DSAR、删除、同意、DPA、跨境、72 小时通知 | 请求记录、DPIA、SCC、审计 |
| CCPA/CPRA | 加州居民数据 | 披露、删除、更正、退出出售/共享 | 请求日志、选择记录 |
| PIPL（中国） | 中国境内个人信息 | 单独同意、跨境评估/标准合同、境内存储、PIA | 同意记录、评估报告、区域部署 |
| LGPD（巴西） | 巴西数据 | 法律基础、主体权利、DPO、跨境 | 记录、DPO 联系、传输机制 |
| DPDP（印度） | 印度数字个人数据 | 同意、目的限制、数据受托人义务 | 同意、目的、删除 |
| HIPAA | 美国 PHI | BAA、最小必要、审计、泄露通知、加密 | BAA、审计、风险评估 |
| PCI DSS 4.0.1 | 持卡人数据 | 分段、令牌化、MFA、日志、脚本完整性 | ROC/SAQ、扫描、日志评审 |
| SOC 2 / ISO 27001 | 企业采购 | 访问控制、变更、监控、事件、供应商 | 审计报告、控制证据 |
| DORA | 欧盟金融实体/关键 ICT 提供商 | ICT 风险、事件报告、第三方登记、韧性测试 | 登记册、报告、测试结果 |
| NIS2 | 欧盟关键/重要实体 | 风险管理、供应链、24/72 小时/月报 | 资产清单、演练、通知 |
| EU Data Act | 欧盟云/数据处理服务 | 开放接口、切换、导出、费用透明 | 合同、接口文档、切换记录 |
| EU AI Act | 欧盟 AI 系统/GPAI | 风险分级、透明度、日志、监督、评估 | 技术文档、评估、事件报告 |
| PSD2 / PSD3 / PSR | 欧盟支付/开放银行 | SCA、同意、TPP、账户访问 | 同意、SCA 日志、牌照 |
| Open Banking（UK/CDR/FDX） | 区域开放银行 | 账户/支付 API、同意、性能、安全 | 目录注册、同意、SLA |
| FedRAMP / CJIS / IRAP | 公共部门 | 授权边界、数据驻留、人员审查 | 授权包、审计 |

### 几条使用建议

1. **先画数据流，再谈法规**。同一份数据可能同时触发隐私、支付、行业与出口管制。
2. **找最严约束，而不是逐条满足**。区域驻留 + 删除 + 审计往往能覆盖多个法规的公共要求。
3. **把义务写成可测试的用例**。例如“删除后 30 天内，主库、索引、缓存、对象存储均不可检索”。
4. **保留证据，而不是保留口号**。合规审计看的是日志、报告、工单与测试结果。
5. **监管会变**。把适用条款、版本、日期与负责人放进合规登记表，定期复核。

## T.9 合规即代码

合规能力如果只靠人工流程，规模一大就会失真。可自动化的部分包括：

- **数据分类标签**：schema/字段级标签，进入代码生成与访问控制；
- **策略即代码**：授权、保留、区域路由、导出审批；
- **保留任务**：按数据集/租户/法规自动清理，失败告警；
- **删除验证**：删除后扫描主库、索引、缓存、对象存储；
- **审计管道**：不可篡改写入、完整性校验、异常访问告警；
- **CI 检查**：新增字段必须声明分类与保留；新增第三方必须登记；新增区域必须更新数据流；
- **证据快照**：定期生成控制证据（访问评审、加密状态、备份恢复测试）；
- **事件演练**：按季度模拟泄露、区域故障、供应商退出。

### 合规登记表

```yaml
obligation_id: GDPR-ART15
description: 数据主体访问权
applies_to: [eu_personal_data]
api_capability: [privacy.access_request]
sla: 30d
owner: privacy-engineering
evidence: [request_log, export_manifest, delivery_receipt]
last_tested: 2026-10-15
next_review: 2027-01-15
```

这张表比“合规检查清单”更能抵抗组织变化：它把义务、能力、负责人、证据与复核日期绑定在一起。

## T.10 事件响应与通知

合规事件的时间线通常从“发现”开始，而不是从“确认”开始。

```text
检测 → 分级 → 遏制 → 取证 → 通知 → 修复 → 复盘 → 证据归档
```

### 通知时限（示例，需按适用法律核对）

- **GDPR**：在知悉个人数据泄露后 **72 小时**内向监管机构通知（除非不太可能造成风险）；高风险时通知数据主体。
- **NIS2**：早期预警通常在 **24 小时**内，事件通知通常在 **72 小时**内，最终报告通常在一个月内。
- **DORA**：重大 ICT 相关事件按主管机构要求报告，时限与模板以最终技术标准为准。
- **PCI DSS**：按收单行/卡组织合同通知，通常要求立即。
- **合同**：企业客户合同往往要求更短的通知时限（如 24 小时），以合同为准。

### 事件响应中的 API 能力

- 快速定位受影响的主体、租户、数据类别与区域；
- 导出访问日志与审计轨迹；
- 临时吊销令牌、禁用集成、隔离租户；
- 生成客户通知所需的事实清单；
- 保留证据，避免日志轮转覆盖；
- 记录每个决定的时间、负责人与依据。

没有这些能力，72 小时会变成“72 小时用来找数据”。

## T.11 反模式

- 把合规当成法务一个部门的事，工程不参与；
- 只有“同意弹窗”，没有同意记录与撤回传播；
- 删除只删主表，索引/缓存/备份/日志全留着；
- 数据驻留只做数据库，日志与备份跨境；
- 审计日志可被管理员修改或删除；
- 事件响应没有分级、没有模板、没有演练；
- 用“匿名化”掩盖可重识别数据；
- AI 训练数据来源与用途没有记录；
- 合规证据靠截图与人工汇总，无法持续；
- 合同承诺的 SLA/通知时限，系统根本测不出来。

## T.12 检查清单

- [ ] 有数据流图与字段级分类，覆盖存储、日志、缓存、仓库、第三方、备份。
- [ ] 每个监管义务映射到 API 能力、负责人、证据与复核日期。
- [ ] DSAR 支持访问、更正、删除、可携带，并有身份验证与时限跟踪。
- [ ] 删除覆盖主库、索引、缓存、对象存储、日志、备份与第三方。
- [ ] 同意有版本、目的、来源、撤回与下游传播。
- [ ] 数据驻留覆盖主数据、备份、日志、密钥与支持访问。
- [ ] 审计日志不可篡改、可查询、可导出、保留期明确。
- [ ] 高风险操作有双人审批或强认证 + 理由 + 审计。
- [ ] DORA/NIS2/AI Act/PCI/行业要求已识别并映射到运行流程。
- [ ] 事件响应有分级、时限、模板、联系人、演练与证据归档。
- [ ] 合规检查进入 CI 与定期评审，而不是一次性项目。
- [ ] 合同中的时限、审计权、退出协助与技术能力一致。

## T.13 小结

- 合规的工程形态是“义务 → 能力 → 证据”，不是“法务说可以”。
- 数据分类与数据流是所有隐私、驻留、删除、审计能力的基础。
- 删除、可携带、同意、审计是 API 产品能力，不是后台脚本。
- DORA、NIS2、Data Act、AI Act 把韧性、供应链、切换与 AI 治理带进了 API 合同。
- 合规即代码让证据可持续，让审计从“找截图”变成“查系统”。
- 监管会变，能力与证据不会白做；它们同时也是安全、可靠性与客户信任的基础。
- 加密义务要落到可验证的 TLS、密钥管理、消息签名与后量子迁移计划；具体工程细节见[附录 AD](ad-cryptography-pqc.md)。
- 隐私义务还要落到数据最小化、聚合阈值、隐私预算、TEE/MPC 等 PET 能力与证据；具体工程细节见[附录 AG](ag-privacy-enhancing-tech.md)。

## 设计练习

选择一个你熟悉的 API，完成一张合规映射表：

1. 它处理哪些个人/敏感/支付/健康数据？分别存在哪里？
2. 适用哪些法规与合同条款？最严的约束是什么？
3. 访问、更正、删除、导出分别由哪个端点承接？时限是多少？
4. 删除后如何验证主库、索引、缓存、对象存储与备份？
5. 如果发生泄露，24/72 小时内你能拿出哪些事实与证据？
6. 如果监管明天要求“数据不得离开某区域”，哪些组件需要改？

然后写一份“合规能力差距清单”，按风险与工作量排序。
