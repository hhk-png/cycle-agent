# 附录 R：API 实现架构与框架选型

> 契约描述“外面看到什么”，实现架构决定“里面如何可靠地兑现”。本附录补齐从 OpenAPI / Protobuf 到代码的那一段：分层、中间件、校验、事务、幂等、数据访问、部署与测试缝。它不推荐某个框架，而是给出一张按约束选型的判断表。

## R.1 契约到代码的映射

一份契约里的每个元素，最终都要落到某个实现位置。位置错了，代码会变得难改；位置缺失，契约就会在运行时失真。

| 契约元素 | 典型实现位置 | 必须有对应测试 |
|---|---|---|
| 路径、方法、媒体类型 | 路由 / 控制器 | 路由与内容协商测试 |
| 认证 scheme | 边缘 / 认证中间件 | 令牌缺失、过期、错误 audience |
| 权限规则 | 授权中间件 + 领域服务 | 对象级、字段级、租户级越权 |
| 请求 schema | 边界校验层 | 缺字段、多字段、类型错、边界值 |
| 业务不变量 | 领域层 | 状态机非法转换、金额/库存约束 |
| 幂等语义 | 幂等存储 + 事务 | 重复请求、并发请求、超时重试 |
| 错误目录 | 异常映射层 | 每个公开错误码至少一个用例 |
| 分页/过滤/排序 | 查询层 | 游标稳定性、过滤注入、成本上限 |
| 超时/重试/限流 | 中间件 + 客户端策略 | 超时预算、重试风暴、429 处理 |
| 事件/Webhook | Outbox + 投递器 | 至少一次、去重、签名、重放 |
| 可观测性 | 中间件 + 领域埋点 | Trace 贯通、错误关联 ID |

一个常见的架构错误，是把所有事情塞进控制器：解析、校验、鉴权、事务、业务、序列化、错误处理。这样写短期最快，长期最贵，因为每个契约元素都失去了独立的测试缝。

### 分层的目标不是“层数”

分层只有一个目标：**让容易变化的部分隔离，让必须一致的部分集中。**

- **接口层**：HTTP/gRPC 细节、内容协商、状态码映射。它应该很薄。
- **应用层**：用例编排、事务边界、幂等、权限检查顺序。它决定“一次调用发生什么”。
- **领域层**：不变量、状态机、金额与库存规则。它不应依赖框架。
- **基础设施层**：数据库、缓存、消息、外部 API。它实现领域定义的端口。

六边形架构、整洁架构、洋葱架构说的都是同一件事：依赖指向内层，领域不依赖 HTTP 框架或 ORM。名称不重要，依赖方向重要。

```text
HTTP / gRPC / CLI
        │
   Interface Adapters        ← 控制器、序列化、错误映射
        │
   Application Services     ← 用例、事务、幂等、授权编排
        │
      Domain                ← 聚合、不变量、领域事件
        │
   Infrastructure Ports     ← repository、消息、时钟、支付网关
```

## R.2 框架选型矩阵

框架选型最常见的错误，是拿 benchmark 的 QPS 当第一标准。真正决定长期成本的，是契约支持、团队能力、运维方式和退出成本。

| 维度 | 要问的问题 |
|---|---|
| 契约优先 | 能否从 OpenAPI / Protobuf 生成骨架，或从代码生成契约？ |
| 校验 | schema 校验、类型转换、错误定位是否一等公民？ |
| 序列化 | JSON、流式、二进制、日期/金额/枚举处理是否可控？ |
| 认证授权 | 中间件/过滤器模型是否清晰？能否做对象级授权？ |
| 异步与流 | SSE、WebSocket、gRPC streaming、后台任务是否自然？ |
| 可观测性 | OpenTelemetry、结构化日志、指标是否易接入？ |
| 运维 | 启动、优雅关闭、健康检查、配置、迁移是否成熟？ |
| 生态 | 数据库、消息、缓存、身份提供商是否有稳定客户端？ |
| 性能 | 在目标负载下是否足够？瓶颈在框架还是数据库？ |
| 团队 | 团队能否在没有原厂支持时排障与升级？ |
| 退出成本 | 业务逻辑是否被框架类型污染？能否迁移？ |

### 常见框架的定位

下表是“典型强项”，不是排名。每个框架都能做大多数事情，差别在于默认路径和代价。

| 框架 / 运行时 | 典型强项 | 主要代价 |
|---|---|---|
| Spring Boot（Java/Kotlin） | 企业生态、事务、安全、可观测性成熟 | 启动与内存成本、抽象层多、升级需治理 |
| ASP.NET Core（C#） | 性能、类型系统、认证授权、云原生集成 | 团队与生态依赖微软栈 |
| FastAPI（Python） | 类型提示 + OpenAPI 生成、开发速度快、AI 生态好 | 默认同步/异步混用易出错、重业务需自律 |
| Django REST Framework | 快速 CRUD、ORM、后台管理 | 复杂领域容易与 ORM 耦合、性能需额外设计 |
| NestJS（TypeScript） | 结构化、依赖注入、模块化、前后端同语言 | 抽象层多、运行时开销、版本升级节奏 |
| Fastify / Express（Node.js） | 轻量、生态大、流式自然 | 大型项目需自建结构；Express 默认缺少约束 |
| Go（chi / echo / gin） | 简单、可预测、部署轻、并发模型清晰 | 框架能力少，认证/校验/文档需组合 |
| Rust（axum / actix-web） | 性能、内存安全、强类型 | 学习曲线、编译时间、生态成熟度 |
| Rails（Ruby） | 约定优于配置、快速迭代 | 大规模下的抽象成本、团队供给 |
| Laravel（PHP） | 开发效率、生态、托管普及 | 类型与长期演进需纪律 |
| Ktor（Kotlin） | 协程、轻量、多平台 | 生态相对小、团队经验要求 |

### 选型的三个问题

1. **这个框架的默认路径，是否正好是我要的路径？** 如果你 80% 的代码都在绕开框架，选错了。
2. **团队能否在生产事故中读懂它？** 框架的隐藏行为在故障时最昂贵。
3. **五年后能否迁移？** 业务逻辑是否依赖框架的注解、基类、ORM 实体？能否通过端口隔离？

对于公开 API，还有一个额外标准：**契约工具链是否成熟**。OpenAPI lint、破坏性检测、mock、SDK 生成、契约测试，往往比框架本身更能决定交付效率。

## R.3 请求处理管线

一个请求从进入进程到返回，经过一串有序阶段。顺序错了，会出现安全问题或性能问题。

```text
TLS / 连接
  → 请求 ID / Trace 上下文
  → 访问日志（脱敏）
  → 请求体大小限制
  → 认证（token 校验、API Key）
  → 限流 / 配额（按主体、租户、路由）
  → 路由
  → 授权（功能级 + 对象级）
  → 内容协商与解析
  → schema 校验
  → 幂等检查
  → 应用服务 / 事务
  → 领域逻辑
  → 序列化
  → 错误映射
  → 响应头（缓存、限流、追踪）
```

### 顺序的几条硬规则

- **请求 ID 必须最早生成**，否则后续日志无法关联。
- **请求体大小限制必须在解析之前**，否则大 body 会先耗尽内存。
- **认证在限流之前还是之后？** 公共 API 通常先做低成本限流（按 IP），再做认证；内部 API 可以先认证，再按主体限流。两者都要防止“未认证流量打满认证服务”。
- **授权必须在读取业务对象之后做对象级检查**，不能只检查路由权限。BOLA（对象级授权缺失）是 API 最常见的严重漏洞之一。
- **幂等检查要在事务内或与业务写入同一原子边界**，否则并发请求仍会重复执行。
- **错误映射必须在最外层统一处理**，避免每个控制器各写一套。

### 一个中间件骨架

```ts
// 伪代码：顺序比框架更重要
app.use(requestId());
app.use(traceContext());
app.use(accessLog({ redact: ["authorization", "cookie", "set-cookie"] }));
app.use(bodyLimit({ json: "1mb", multipart: "20mb" }));
app.use(rateLimit({ by: "ip", route: "public" }));
app.use(authenticate());
app.use(rateLimit({ by: "subject", route: "api" }));
app.use(authorizeRoute());
app.use(validateSchema());
app.use(idempotency());
app.use(errorMapper());
```

## R.4 校验与错误映射

校验分三层，不能互相替代：

1. **语法校验**：类型、格式、必填、枚举、长度、范围。由 schema 在边界完成。
2. **语义校验**：字段之间的关系，例如 `endAt > startAt`、`currency` 与 `amount` 匹配。
3. **领域不变量**：状态机、库存、余额、权限。必须在领域层和持久化约束中保证。

只在数据库做校验，会让错误变成 500；只在控制器做校验，会让并发请求绕过不变量；只在领域层做校验，会让无效请求消耗大量资源。

### 错误映射表

| 内部异常 | 对外错误码 | HTTP | 是否可重试 |
|---|---|---|---|
| schema 校验失败 | `VALIDATION_FAILED` | 400 / 422 | 否 |
| 未认证 | `UNAUTHENTICATED` | 401 | 否（先刷新令牌） |
| 无权限 | `FORBIDDEN` | 403 | 否 |
| 对象不存在或不可见 | `NOT_FOUND` | 404 | 否 |
| 状态冲突 | `INVALID_STATE` | 409 | 否 |
| 并发版本冲突 | `VERSION_CONFLICT` | 409 / 412 | 可重新读取后重试 |
| 幂等键复用但参数不同 | `IDEMPOTENCY_KEY_REUSED` | 409 / 422 | 否 |
| 限流 | `RATE_LIMITED` | 429 | 是（按 `Retry-After`） |
| 依赖超时 | `DEPENDENCY_TIMEOUT` | 503 / 504 | 是（有预算） |
| 未知内部错误 | `INTERNAL` | 500 | 视情况 |

错误响应至少要有：稳定的 `code`、人类可读的 `message`、请求关联 ID、字段级 `details`。不要把堆栈、SQL、内部主机名返回给调用方。

```json
{
  "type": "https://api.example.com/problems/validation-failed",
  "title": "VALIDATION_FAILED",
  "status": 422,
  "detail": "请求包含 2 个无效字段。",
  "instance": "/orders",
  "traceId": "tr_01J...",
  "errors": [
    { "field": "items[0].quantity", "code": "MIN_VALUE", "message": "必须大于 0" },
    { "field": "currency", "code": "UNSUPPORTED", "message": "当前租户不支持 USD" }
  ]
}
```

## R.5 幂等、事务与并发

### 幂等键的正确实现

幂等不是“加一个 header”，而是一段有状态协议：

```sql
CREATE TABLE idempotency_keys (
  tenant_id      TEXT NOT NULL,
  principal_id   TEXT NOT NULL,
  operation      TEXT NOT NULL,       -- 例如 POST /orders
  key            TEXT NOT NULL,
  request_hash   TEXT NOT NULL,
  status         TEXT NOT NULL,       -- IN_PROGRESS | COMPLETED | FAILED
  response_code  INT,
  response_body  JSONB,
  created_at     TIMESTAMPTZ NOT NULL,
  expires_at     TIMESTAMPTZ NOT NULL,
  PRIMARY KEY (tenant_id, principal_id, operation, key)
);
```

处理流程：

```text
1. 以 (tenant_id, principal_id, operation, key) 尝试插入 IN_PROGRESS
2. 插入成功 → 执行业务事务
3. 插入冲突 → 读取已有记录
   - principal 或 request_hash 不同 → 409 IDEMPOTENCY_KEY_REUSED
   - COMPLETED → 返回缓存的响应
   - IN_PROGRESS → 409 或等待（取决于契约）
   - FAILED → 允许重试或返回失败（必须明确）
4. 在业务事务内把记录标为 COMPLETED，与业务写入一起提交
```

如果响应只能在业务事务提交后生成（例如需要调用外部系统），不要写“提交后再用同一事务标记”。应使用：

- 把响应写入同一事务的 outbox；
- 或使用 `IN_PROGRESS → COMPLETED` 的两阶段状态，并让重试能查询到最终结果；
- 或由后台任务完成并写入响应，调用方轮询/重试。

关键是：**幂等记录的最终状态不能依赖一个已经提交的事务内操作。**

关键点：

- **作用域**：至少包含租户、调用主体与操作；不能只按全局 key。只按 `(tenant_id, key)` 会让同租户不同主体撞键，也会让同一 key 在不同端点之间错误复用响应。
- **请求指纹**：方法、路径、关键 body 字段的规范化哈希。否则“同 key 不同请求”会被误判为重复。
- **原子性**：幂等记录与业务写入必须在同一事务，或使用可恢复的两阶段状态。
- **TTL**：太长浪费存储，太短会让迟到的重试重复执行。按业务风险设定。
- **失败语义**：业务失败是否缓存？通常 4xx 可缓存，5xx 不缓存，但要在契约中写清。

### 事务边界

一个 API 调用通常对应一个事务，但以下情况不能简单包在一个数据库事务里：

- 调用外部支付网关；
- 发送消息/事件；
- 写对象存储；
- 跨服务写入。

这时用 **Transactional Outbox**：业务数据与“待发送事件”在同一事务写入，再由独立投递器发送。不要用“先写库再发消息”的双写，除非你能接受丢失。

```text
BEGIN
  INSERT INTO orders (...)
  INSERT INTO outbox (aggregate_id, event_type, payload)
COMMIT
-- 投递器读取 outbox，至少一次发送，消费方幂等
```

跨服务的长事务用 **Saga**：每个步骤有补偿动作，状态机持久化，失败可重试或人工介入。Saga 不是“分布式事务的免费替代”，它把一致性变成了业务可见的中间状态。

### 并发控制

| 场景 | 方案 | 注意 |
|---|---|---|
| 覆盖写 | `If-Match` + 版本号 | 返回 412，不要静默覆盖 |
| 计数/库存 | 原子 SQL、行锁、条件更新 | 避免读-改-写 |
| 唯一性 | 数据库唯一约束 | 不要只靠先查后插 |
| 长事务 | 短事务 + 状态机 | 避免锁等待与超时 |
| 外部副作用 | 幂等键 + 去重表 | 外部系统也要支持幂等 |

## R.6 数据访问与查询实现

### 不要把 ORM 实体直接当 API 模型

ORM 实体包含持久化细节：懒加载、代理对象、数据库列、关联关系。直接序列化会带来：

- 意外暴露字段（Mass Assignment / 数据泄露）；
- N+1 查询；
- 循环引用；
- 数据库 schema 变更直接变成 API 破坏性变更；
- 无法表达 API 的多态与版本。

正确做法是显式的 API 模型（DTO / schema），在边界做映射。映射代码是成本，但它是契约稳定性的保险。

### 列表查询的成本护栏

列表接口必须有上限，而不是“调用方要多少给多少”：

```text
limit 默认 20，最大 100
offset 最大 10,000（或禁用深 offset）
过滤字段白名单
排序字段白名单
查询超时 2s
扫描行数上限
```

游标分页的实现要点：

```ts
// 游标应是不透明的、带签名的、包含排序键与方向的
type Cursor = {
  v: 1;
  k: (string | number | null)[]; // 排序键值
  d: "asc" | "desc";
  f: string;                     // 过滤条件指纹
  exp: number;                   // 过期时间
};

// 查询时用 (sortKey, id) 做 keyset，而不是 OFFSET
SELECT * FROM orders
WHERE tenant_id = $1
  AND (created_at, id) < ($2, $3)
ORDER BY created_at DESC, id DESC
LIMIT $4;
```

游标要绑定过滤条件与权限范围。否则调用方改一个过滤参数，就可能用旧游标读到不该读的数据，或者得到语义混乱的结果。

### N+1 与批量加载

列表返回关联数据时，常见错误是逐项查询。解决方式：

- 批量 `IN` 查询后内存组装；
- DataLoader（GraphQL 常用）；
- 预加载/join（注意笛卡尔积）；
- 冗余字段（在一致性可接受时）；
- 明确“展开”是显式参数，不是默认行为。

## R.7 认证与授权的落地

### 令牌校验

- 远程 JWKS 要缓存，并支持轮换与失败降级；
- 校验 `iss`、`aud`、`exp`、`nbf`、签名算法白名单；
- 不要信任客户端传来的 `tenant_id`、`role`、`user_id`，从令牌或服务端会话推导；
- 不透明令牌走内省，内省结果缓存要短；
- 令牌错误与权限错误要分开：401 是“你是谁不确定”，403 是“你是谁已知但不行”。

### 授权检查的位置

```text
路由级：这个主体能否访问这个功能？
对象级：这个主体能否操作这个具体对象？
字段级：这个主体能否看到/修改这个字段？
```

对象级授权必须在读取对象后、执行副作用前完成。典型错误是：

```text
GET /orders/{id}  → 只检查“有 order:read scope”
                  → 直接按 id 查询
                  → 返回了别的租户的订单
```

正确做法是把租户与主体作为查询条件的一部分，而不是查询后再过滤（后者容易在分支中遗漏）。

## R.8 流式、异步与后台作业

### SSE / WebSocket

- SSE 适合服务端单向推送，自动重连，穿透代理较好；
- WebSocket 适合双向、低延迟、频繁交互；
- 两者都要处理：认证、心跳、背压、断线重连、消息去重、顺序、慢消费者；
- 不要把“连接建立”当成“永久授权”，长时间连接要能失效与重新认证。

### 异步任务

长任务不要占用请求线程。标准模式：

```text
POST /exports → 202 + Location: /exports/{id}
GET  /exports/{id} → status: queued | running | succeeded | failed
GET  /exports/{id}/result → 302 到签名 URL（完成后）
DELETE /exports/{id} → 取消（如果支持）
```

要点：

- 任务 ID 幂等；
- 状态机明确，失败可重试；
- 进度不是必须，但“最后更新时间”必须有；
- 结果有保留期与访问控制；
- 取消是协作式的，不能假设立即停止；
- Worker 要有死信队列与人工重放工具。

## R.9 部署与运行时

### 容器、Serverless 与边缘

| 形态 | 适合 | 注意 |
|---|---|---|
| 容器 / Kubernetes | 长连接、稳定吞吐、复杂依赖 | 连接池、优雅关闭、资源限制 |
| Serverless | 突发、低运维、事件驱动 | 冷启动、连接复用、超时上限、状态外置 |
| 边缘 | 低延迟、认证、个性化、限流 | 状态、一致性、调试、供应商锁定 |

Serverless 里的数据库连接是经典陷阱：每个实例建连接会打爆数据库。要用连接池代理、HTTP 数据接口或按需连接。

### 优雅关闭

```ts
process.on("SIGTERM", async () => {
  server.stopAcceptingNewRequests();
  await inflight.drain({ timeoutMs: 25_000 });
  await db.close();
  await queue.close();
  process.exit(0);
});
```

没有优雅关闭，滚动发布时会出现一批 502/499。超时时间要小于编排系统的强杀时间。

### 发布策略

- **蓝绿**：切换快，回滚快，成本翻倍；
- **金丝雀**：按流量逐步放量，需要指标与自动回滚；
- **特性开关**：控制功能可见性，不等于代码部署；
- **影子流量**：复制请求到新版本，不返回结果，用于验证；
- **数据库迁移**：先扩展、再双写/回填、再收缩，避免应用与 schema 同时破坏。

## R.10 代码组织与测试缝

### 推荐的组织方式

```text
src/
  orders/                 # 一个业务能力
    interfaces/http/      # 路由、控制器、请求/响应模型
    application/          # 用例、事务、幂等、授权编排
    domain/               # 聚合、值对象、领域服务、领域事件
    infrastructure/       # repository、消息、缓存、外部客户端
  payments/
    interfaces/http/
    application/
    domain/
    infrastructure/
  shared/
    observability/        # trace、metric、log、redaction
    config/               # 配置与启动
```

先按业务能力分包（`orders/`、`payments/`），再在能力内按技术层分层。这样边界清晰，也避免一个全局 `interfaces/` 目录把所有业务控制器混在一起。

### 测试缝

- **契约测试**：用 OpenAPI/Protobuf 生成或校验，防止实现偏离契约；
- **集成测试**：Testcontainers 起真实数据库/消息，验证事务与 SQL；
- **端到端**：少量关键路径，验证网关、认证、序列化；
- **故障注入**：超时、断连、重复投递、磁盘满、依赖 5xx；
- **性能测试**：尾延迟、连接池、慢查询、背压；
- **安全测试**：对象级授权、注入、SSRF、Mass Assignment。

可测试性不是测试团队的事，而是架构的属性。如果领域逻辑依赖全局单例、当前时间、随机数、HTTP 上下文，它就很难被单测。

## R.11 实现反模式

- 控制器直接写 SQL、发消息、调支付；
- ORM 实体直接作为 API 响应；
- 校验只在数据库，错误变成 500；
- 幂等键只在内存或只在网关；
- 事务里调用外部服务，超时后状态不明；
- 先查后插做唯一性，绕过数据库约束；
- 所有错误都返回 200 + `success: false`；
- 日志打印完整令牌、身份证、银行卡；
- 用全局变量保存租户上下文；
- 没有优雅关闭；
- 数据库迁移与应用发布强耦合；
- 业务逻辑依赖框架注解，无法单测与迁移。

## R.12 检查清单

- [ ] 每个契约元素都有实现位置与测试。
- [ ] 请求管线顺序固定，并有集成测试覆盖。
- [ ] 请求体大小、超时、连接数、查询成本都有上限。
- [ ] 认证与授权分离，对象级授权在副作用前完成。
- [ ] 幂等键有作用域、指纹、原子写入与明确失败语义。
- [ ] 外部副作用通过 Outbox/Saga，避免双写丢失。
- [ ] API 模型与 ORM 实体分离。
- [ ] 列表接口有游标、白名单、成本护栏。
- [ ] 流式与异步有背压、重连、去重、取消。
- [ ] 优雅关闭与发布策略经过演练。
- [ ] 关键路径有契约、集成、故障注入与性能测试。
- [ ] 业务逻辑可以在没有框架的情况下被单测。

## R.13 小结

- 实现架构的价值，是让契约的每个承诺都有可验证的落点。
- 分层不是目的，依赖方向与测试缝才是。
- 框架选型应按契约支持、团队能力、运维与退出成本判断，而不是 benchmark。
- 中间件顺序、幂等原子性、对象级授权、事务边界是最容易出错的地方。
- 部署形态会改变连接、超时、状态与故障模式，必须在设计时就考虑。
- 好的实现让正确的事情容易做，让错误的请求难以生效。

## 设计练习

为你正在维护的一个 API 画出请求管线，并标注：

1. 每个阶段由谁负责（网关、中间件、控制器、领域、数据库）？
2. 哪个阶段可能成为性能瓶颈？
3. 幂等键在哪个事务边界内写入？
4. 对象级授权发生在读取对象之前还是之后？
5. 如果数据库连接池耗尽，哪些请求应该被优先拒绝？
6. 滚动发布时，如何避免 502/499？

然后选一个你熟悉的框架，写出“如果明天迁移到另一个框架，哪些代码必须重写”，并据此判断当前架构的耦合程度。
