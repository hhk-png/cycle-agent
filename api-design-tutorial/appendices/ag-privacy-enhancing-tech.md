# 附录 AG：隐私增强技术与 API——从差分隐私到机密计算

> 传统 API 安全回答“谁能调用”，隐私工程回答“调用之后能学到什么”。这两件事经常被混为一谈：一个接口可以认证正确、授权正确、传输加密，却仍然通过聚合查询、错误信息、模型输出或日志，把个人数据一点点泄露出去。
>
> 本附录把隐私增强技术（Privacy-Enhancing Technologies，PET）放回 API 设计语境：不是罗列密码学名词，而是说明**每种技术能防住什么、防不住什么、代价在哪里，以及如何写进契约、配额与错误模型**。

---

## AG.1 为什么 API 设计需要 PET

一个看似无害的分析接口：

```http
GET /analytics/revenue?group_by=postal_code&period=2026-11
```

它可能泄露：

- 某个邮编只有一户商家，营收等于该商家的营收；
- 通过多次带/不带某条件的查询做差，推断单个用户；
- 通过 `count`、`avg`、`min`、`max` 反推极端值；
- 通过错误信息判断某条记录是否存在；
- 通过缓存、日志、trace 把原始行带到另一个系统；
- 通过模型 API 的置信度或 token 概率做成员推断。

隐私风险的本质不是“字段有没有脱敏”，而是**输出是否让攻击者更有把握地推断某个个体**。PET 的目标是把这种推断优势限制在可量化、可审计的范围内。

PET 不是单一技术，而是一组取舍：

| 目标 | 可能的技术 | 主要代价 |
|---|---|---|
| 发布统计而不泄露个体 | 差分隐私、聚合阈值 | 精度下降、预算管理 |
| 多方联合计算而不共享原始数据 | MPC、PSI、联邦学习 | 通信/延迟、工程复杂 |
| 在不可信基础设施上处理明文 | TEE/机密计算 | 信任厂商、侧信道 |
| 对密文计算 | 同态加密 | 性能、表达力受限 |
| 训练模型而不集中数据 | 联邦学习 + 安全聚合 + DP | 收敛、设备管理 |
| 共享“像真数据”的替代品 | 合成数据 | 效用与隐私都需验证 |
| 隐藏网络元数据 | OHTTP、Privacy Pass | 滥用控制更难 |

**第一步永远是威胁模型**：你在防谁？是好奇的分析师、外部攻击者、云厂商、内部运维、模型提供方，还是未来的数据买家？不同答案对应完全不同的设计。

## AG.2 威胁模型：先写清楚“防谁”

| 角色 | 能看到的 | 典型攻击 | 可能的对策 |
|---|---|---|---|
| 外部匿名用户 | 公开 API 输出 | 枚举、差分、关联 | 认证、限流、聚合阈值、DP |
| 已认证分析师 | 明细/聚合结果 | 链接攻击、成员推断 | 列/行权限、目的限制、查询审计 |
| 合作伙伴 | 共享数据集/API | 重识别、二次分发 | 合同、水印、DP、最小字段 |
| 内部运维 | 日志、备份、指标 | 窥探、误用 | 最小权限、脱敏、审计、TEE |
| 云/基础设施提供商 | 内存、磁盘、网络 | 侧信道、快照 | 机密计算、加密、密钥托管 |
| 模型提供方 | Prompt/文档内容 | 训练、日志、泄露 | 不发送敏感数据、私有部署、DP |
| 网络观察者 | 流量元数据 | 关联、指纹 | TLS、OHTTP、填充 |

写威胁模型时至少明确：

1. **数据主体**是谁（用户、患者、员工、设备）；
2. **敏感属性**是什么（身份、位置、健康、财务、行为）；
3. **攻击者能力**（能否多次查询、能否合谋、能否拿到辅助数据）；
4. **可接受的泄露上界**（例如 ε、最小群体大小、误判率）；
5. **不可接受的后果**（再识别、歧视、伤害、监管处罚）。

没有威胁模型的 PET 只是“技术装饰”。

## AG.3 差分隐私：可量化的泄露上界

### AG.3.1 定义

一个随机化机制 M 满足 ε-差分隐私，如果对任意相邻数据集 D 与 D'（只差一条记录）以及任意输出集合 S：

```text
Pr[M(D) ∈ S] ≤ e^ε · Pr[M(D') ∈ S]
```

直观含义：**某一条记录在不在数据集里，对输出分布的影响被 ε 限制住。** ε 越小，隐私越强，噪声通常越大。

近似差分隐私 (ε, δ) 允许一个很小的失败概率 δ：

```text
Pr[M(D) ∈ S] ≤ e^ε · Pr[M(D') ∈ S] + δ
```

工程上不要把 δ 设成“看起来很小”的任意值；常见做法是要求 δ ≪ 1/n（n 为记录数），但具体要结合威胁模型与监管意见。

### AG.3.2 敏感度与机制

全局敏感度（L1）：

```text
Δ₁f = max_{D ~ D'} ||f(D) − f(D')||₁
```

- **Laplace 机制**：对数值查询 f，使用 L1 敏感度，返回 `f(D) + Lap(Δ₁f / ε)`；
- **Gaussian 机制**：用于 (ε, δ)-DP，使用 L2 敏感度 Δ₂f，噪声尺度约为 `Δ₂f · sqrt(2 ln(1.25/δ)) / ε`；
- **指数机制**：用于选择类查询（如“最常出现的类别”），按效用打分加噪选择；
- **随机化响应**：用于本地隐私下的布尔/枚举回答。

一个计数查询的例子：

```python
import numpy as np

def dp_count(true_count: int, epsilon: float) -> int:
    # 计数查询的 L1 敏感度为 1
    scale = 1.0 / epsilon
    noise = np.random.laplace(0, scale)
    return max(0, int(round(true_count + noise)))
```

对于求和查询，敏感度取决于单条记录的最大贡献。如果不做裁剪（clipping），一个极端值会让噪声大到不可用；如果裁剪，结果又会有偏。工程上常见：

```text
1. 对每条记录的贡献裁剪到 [0, C]
2. 按裁剪后的敏感度 C 加噪
3. 在文档中说明裁剪上界与偏差
```

### AG.3.3 组合与隐私预算

多次查询会累积泄露。基本组合：若 M₁ 是 ε₁-DP，M₂ 是 ε₂-DP，则依次发布两者满足 (ε₁+ε₂)-DP。

更强的方法包括：

- 高级组合（advanced composition）；
- Rényi DP（RDP）；
- zCDP；
- 集中差分隐私（concentrated DP）。

工程含义：

- **隐私预算要像配额一样管理**，按租户/用户/时间段分配；
- 每次查询消耗预算，预算耗尽后拒绝或降低精度；
- 预算消耗要在响应中可见，并写入审计；
- 不能允许客户端随意选择 ε 来“买”更高精度；
- 同一数据集上的多次查询要统一记账，而不是各服务各自为政。

### AG.3.4 本地、中心与混洗模型

| 模型 | 谁加噪 | 优点 | 缺点 |
|---|---|---|---|
| 中心 DP | 可信数据持有方 | 精度高 | 需要可信 curator |
| 本地 DP | 客户端 | 服务端看不到原始值 | 噪声大，需要大量用户 |
| 混洗 DP（shuffle） | 客户端加噪，混洗器匿名转发 | 介于两者之间 | 需要足够大的匿名集与抗流量分析 |

API 设计含义：

- 中心 DP 适合分析 API、报表 API；
- 本地 DP 适合设备遥测、浏览器上报；
- 混洗模型需要额外的匿名转发与批量窗口；
- 不要在客户端做“中心 DP”的假实现——客户端一旦被攻破，原始数据仍然泄露。

### AG.3.5 DP 的边界

DP 不是万能的：

- 它保护的是**个体是否在数据集中**，不保护群体层面的敏感结论；
- 它不防止数据本身在采集端被滥用；
- 它不替代访问控制、加密与合同；
- 它要求随机性；确定性查询无法满足 DP；
- 后处理是安全的（post-processing immunity），但“用 DP 结果再训练一个模型”不自动获得 DP；
- 如果相邻数据集的定义错了（例如一户人家的多条记录算一条还是多条），隐私保证就会失真；
- ε 的选择是政策与伦理问题，不只是技术参数。

## AG.4 k-匿名及其局限

k-匿名要求每个等价类至少包含 k 条记录，使一条记录无法与另外 k−1 条区分。

常见操作：

- 泛化：把年龄 34 → 30–39，邮编 10001 → 100**；
- 抑制：删除无法满足 k 的记录或字段；
- 分组：按准标识符组合分组。

问题：

- **同质性攻击**：一个等价类里所有人的敏感属性相同；
- **背景知识攻击**：攻击者知道目标在某个等价类中，结合外部信息推断；
- **维度灾难**：准标识符越多，满足 k 越难，泛化越严重；
- **新数据/增量发布**：每次发布都重新分组，可能通过差分推断；
- **k 不是隐私预算**：k=10 不代表泄露上界是 1/10。

改进：

- **l-多样性**：每个等价类中敏感属性至少有 l 个不同值；
- **t-closeness**：等价类的敏感属性分布与全局分布的距离不超过 t；
- **DP**：给出可组合的定量保证。

工程建议：

> k-匿名适合作为数据发布的最低门槛与合规沟通语言，但不应作为对外 API 的唯一隐私保证。对可重复查询的分析接口，优先使用差分隐私或查询审计 + 最小群体阈值。

## AG.5 聚合查询与差分攻击

### AG.5.1 小群体与补抑制

```http
GET /stats/orders?group_by=postal_code
```

如果某个邮编只有 2 个客户，返回精确计数与金额就等于泄露。常见规则：

- 最小群体大小 k（如 5、10、20）；
- 小格抑制（suppress cells below k）；
- 补抑制（complementary suppression）：抑制一个格后，防止通过总数相减反推，需要再抑制至少一个格；
- 对 `min`/`max` 特别小心：它们天然暴露极端个体；
- 对 `count=0` 与“不存在”区分要谨慎，避免存在性泄露。

### AG.5.2 差分攻击

攻击者可以问：

```text
Q1: 所有订单的总金额
Q2: 除用户 U 之外所有订单的总金额
Q1 - Q2 = 用户 U 的订单金额
```

防御：

- 查询审计：记录同一用户/租户的查询历史，检测相减模式；
- 查询集限制：不允许任意组合的过滤条件；
- 聚合阈值与补抑制；
- 差分隐私：对每次查询加噪，使相减结果仍然含噪；
- 预算：限制单位时间内的查询次数与覆盖范围；
- 结果缓存要考虑“缓存命中本身”是否泄露。

### AG.5.3 查询审计的局限

查询审计能提高攻击成本，但不是形式化保证：

- 攻击者可以用多个账号/租户分担查询；
- 可以通过时间维度慢慢逼近；
- 可以结合外部数据；
- 审计规则本身可能被绕过。

因此高风险场景应把 DP 作为主保证，审计作为纵深防御。

## AG.6 安全多方计算

安全多方计算（MPC）让多个参与方在不共享原始数据的情况下计算一个函数。

常见构件：

- **秘密分享**：把值拆成多份，单独一份没有意义；加法/乘法可在份额上计算；
- **混淆电路**：把函数编译成电路，逐门求值；
- **不经意传输（OT）**：一方在多个值中选择一个，而不暴露选择；
- **私有集合求交（PSI）**：只得到交集，不得到对方集合的其他元素；
- **私有连接（private join）**：按共同键连接两张表，不暴露非交集行。

安全模型：

- **半诚实（semi-honest）**：参与方遵守协议但好奇；
- **恶意（malicious）**：参与方可能偏离协议，需要额外证明与开销；
- **合谋阈值**：多少个参与方联合才能恢复秘密。

API 形态：

```http
POST /mpc/intersection
{
  "dataset_id": "ds_123",
  "protocol": "psi-v2",
  "output": "intersection_size_only"
}
```

或：

```text
POST /mpc/jobs
GET  /mpc/jobs/{id}
```

工程代价：

- 通信轮数与带宽可能是本地计算的几十到几千倍；
- 延迟高，适合离线/批处理，不适合交互式点查；
- 需要固定的参与方集合与网络拓扑；
- 输入格式、缺失值、类型对齐会显著影响结果；
- 结果仍然可能泄露信息，需要输出限制或 DP。

## AG.7 同态加密

同态加密允许在密文上计算：

- **部分同态**：如 Paillier 支持加法与数乘；
- ** leveled 同态**：BFV/BGV 支持有限深度的整数运算；
- **近似同态**：CKKS 支持浮点近似计算；
- **全同态**：TFHE 等支持任意布尔/整数电路，但性能代价高。

API 设计含义：

```http
POST /he/compute
{
  "ciphertext": "base64...",
  "operation": "sum",
  "params": { "scheme": "ckks", "scale": 40 }
}
```

响应仍是密文，由持有私钥的客户端解密。

关键限制：

- 密文膨胀：可能是明文的几十到上千倍；
- 计算慢，尤其是深层电路；
- 不支持任意分支、比较、查表；
- 需要密钥管理与参数选择（多项式模数、噪声预算）；
- 结果精度是近似的；
- 方案与库的互操作性有限；
- 不要把“同态加密”当成“把数据库加密后还能随便查”的万能答案。

适用场景：

- 隐私保护的聚合统计；
- 联邦场景下的模型更新聚合；
- 外包计算但不想暴露输入；
- 与 TEE/MPC 组合的混合方案。

## AG.8 可信执行环境与机密计算

TEE 通过硬件隔离保护运行时的代码与数据，常见实现：

- Intel SGX / TDX；
- AMD SEV-SNP；
- ARM CCA；
- AWS Nitro Enclaves；
- 机密容器与机密 GPU（如支持 confidential computing 的加速卡）。

核心能力：

- **隔离**：宿主/云厂商不能直接读内存；
- **远程认证（remote attestation）**：证明“运行的是哪段代码、在哪类 TEE 中、配置是什么”；
- **密封存储（sealing）**：只有同一 TEE 身份能解密持久化数据；
- **加密内存**：防止内存快照与冷启动攻击。

API 形态：

```http
GET /attestation
```

```json
{
  "tee_type": "sev-snp",
  "measurement": "sha256:...",
  "report": "base64...",
  "nonce": "client-provided",
  "policy_version": "2026-11-01"
}
```

客户端验证：

1. 报告签名链可信；
2. measurement 与预期镜像/配置一致；
3. nonce 新鲜，防重放；
4. 策略版本符合要求；
5. 只有验证通过才发送敏感数据。

边界：

- TEE 不防拒绝服务、侧信道、供应链攻击与物理攻击；
- 云厂商仍控制调度、网络与部分固件；
- 认证只证明“某段代码在 TEE 中运行”，不证明代码没有漏洞；
- 侧信道（缓存、功耗、计时）是真实风险；
- 机密 GPU 的成熟度与性能开销需实测；
- 密钥管理仍然关键，TEE 不是 KMS 的替代品。

## AG.9 联邦学习与安全聚合

联邦学习让多方在本地训练，只上传模型更新：

```text
Server → 选择客户端 → 下发全局模型
Client → 本地训练 → 上传更新（裁剪/加噪/加密）
Server → 安全聚合 → 更新全局模型
```

隐私风险：

- 原始梯度可能泄露训练样本（梯度反演、成员推断）；
- 恶意客户端可以投毒/后门；
- 服务器可以看到单个客户端的更新；
- 设备异质性与掉线导致偏差。

对策：

- **安全聚合**：服务器只能看到聚合结果，看不到单个更新；
- **DP-FL**：裁剪每个客户端的更新范数，加噪，跟踪隐私预算；
- **客户端采样**：每轮只选一部分客户端，提供隐私放大；
- **鲁棒聚合**：中位数/截断均值/信誉机制，抵抗投毒；
- **安全信道与认证**：防止中间人、伪造客户端。

API 设计：

```http
POST /fl/rounds
{
  "model_id": "mdl_123",
  "round": 42,
  "clients": ["c1", "c2", "..."],
  "dp": { "clip": 1.0, "noise_multiplier": 1.1, "delta": 1e-6 }
}
```

```http
POST /fl/rounds/{round}/updates
{
  "client_id": "c1",
  "encrypted_update": "base64...",
  "weight": 120
}
```

注意：

- 安全聚合不等于 DP；它防止服务器看到单个更新，但不防聚合结果的推断；
- 联邦学习不等于数据不出设备；模型更新仍然携带信息；
- 客户端掉线、重连、重复提交要有幂等与去重；
- 模型版本、数据分布与评估要可追溯。

## AG.10 合成数据与数据洁净室

### AG.10.1 合成数据

合成数据用生成模型产生“看起来像真数据”的记录，用于开发、测试、共享。

风险：

- 生成模型可能记忆训练样本；
- 没有 DP 保证的合成数据不提供形式化隐私；
- 分布偏移会让下游模型失效；
- 攻击者仍可做成员推断；
- 合成数据的“效用”与“隐私”都要独立评估。

如果目标是隐私，应使用 **DP 合成数据**：训练生成模型时使用 DP-SGD，并跟踪隐私预算。即使如此，也要评估：

- 最近邻距离；
- 成员推断攻击成功率；
- 下游任务效用；
- 少数群体覆盖。

### AG.10.2 数据洁净室

洁净室（data clean room）让多方在受控环境中联合分析，通常包含：

- 数据不落地到对方；
- 查询审批与白名单；
- 输出限制（最小群体、聚合、差分隐私）；
- 审计与合同；
- 有时结合 TEE/MPC。

典型流程：

```text
数据提供方上传/连接数据
  → 分析方提交查询
  → 策略检查（列、行、目的、时间）
  → 执行
  → 输出审查（小格抑制/DP）
  → 交付结果
  → 审计
```

注意：

- 洁净室是**流程 + 技术**，不是单一产品；
- 没有输出控制的洁净室等于“把数据复制到别人机器上”；
- 查询审批要防“合法查询组合出非法结论”；
- 最好把 DP 预算写进洁净室策略；
- 结果的水印、二次分发限制与合同同样重要。

## AG.11 元数据保护：OHTTP、Privacy Pass 与匿名凭证

即使内容加密，网络元数据仍然泄露：

- 谁在什么时候调用了什么服务；
- 客户端 IP 与请求频率；
- 请求大小与时间模式；
- 跨站点关联。

### AG.11.1 Oblivious HTTP（OHTTP）

OHTTP（RFC 9458）用两层：

```text
Client → Relay → Gateway → Origin
```

- 客户端用 Gateway 的公钥加密请求（HPKE）；
- Relay 看不到内容，只看到客户端 IP 与 Gateway；
- Gateway 能看到内容，但看不到客户端 IP；
- 响应同样加密。

适用：

- 隐私统计上报；
- 安全浏览/威胁情报查询；
- 不希望服务方关联用户身份的 API。

边界：

- 不防时间关联、流量分析、大规模监控；
- Relay 与 Gateway 不能合谋；
- 需要滥用控制时，通常结合 Privacy Pass 做“不可关联的配额”。

### AG.11.2 Privacy Pass 与盲签名

Privacy Pass 允许客户端用“令牌”证明自己获得授权，而不暴露身份：

- 客户端从发行方获得盲签名令牌；
- 使用时出示令牌，服务方验证但不关联发行时的身份；
- 可限制每个客户端的令牌数量，实现隐私友好的限流。

相关标准包括 Privacy Pass 架构、签发与 HTTP 认证方案，以及 RSA 盲签名等构件。具体 RFC 编号与状态会演进，落地前应核对 IETF 数据跟踪器与实现支持。

### AG.11.3 匿名凭证

BBS 等匿名凭证支持：

- 选择性披露（只证明“已成年”，不披露出生日期）；
- 多次出示不可关联；
- 撤销与过期。

API 含义：

- 认证不再等于“拿到唯一用户 ID”；
- 限流、计费、风控需要新的不可关联配额机制；
- 审计要区分“可追责”与“可关联”。

## AG.12 把 PET 写进 API 契约

PET 如果只停留在论文或数据平台内部，就不会被正确使用。它必须进入接口、配额、错误与审计。

### AG.12.1 隐私预算作为配额

```http
GET /analytics/orders/count?filter=status:paid
```

响应：

```json
{
  "value": 1532,
  "noise": { "mechanism": "laplace", "scale": 0.5 },
  "privacy": {
    "epsilon_spent": 0.1,
    "epsilon_remaining": 0.9,
    "budget_window": "2026-11"
  }
}
```

预算耗尽：

```http
HTTP/1.1 429 Too Many Requests
Content-Type: application/problem+json
```

```json
{
  "type": "https://api.example.com/problems/privacy-budget-exhausted",
  "title": "Privacy budget exhausted",
  "status": 429,
  "code": "PRIVACY_BUDGET_EXHAUSTED",
  "detail": "The monthly privacy budget for this dataset has been exhausted.",
  "retry_after": "2026-12-01T00:00:00Z"
}
```

设计要点：

- 预算按数据集 + 租户 + 时间窗记账；
- 客户端不能自行指定 ε 来绕过；
- 查询的敏感度由服务端根据查询计划计算，不能信任客户端声明；
- 预算消耗要幂等：重试同一请求不应重复扣预算；
- 预算与计费/配额是两套账，不能混用。

### AG.12.2 聚合阈值与抑制

```json
{
  "group_by": "postal_code",
  "min_group_size": 10,
  "suppression": "complementary",
  "dp": { "epsilon": 0.2 }
}
```

响应中要明确：

- 哪些组被抑制；
- 抑制是否影响总计；
- 是否使用了补抑制；
- 结果是否含噪；
- 噪声机制与参数（至少对内部审计可见）。

### AG.12.3 错误模型

隐私相关错误应可区分、可操作：

| 错误码 | 含义 | 客户端动作 |
|---|---|---|
| `PRIVACY_BUDGET_EXHAUSTED` | 预算耗尽 | 等待下个窗口或申请提升 |
| `AGGREGATION_TOO_SMALL` | 群体小于阈值 | 扩大分组/时间范围 |
| `QUERY_NOT_ALLOWED` | 查询模式被禁止 | 改用允许的聚合 |
| `ATTESTATION_REQUIRED` | 需要 TEE 认证 | 完成认证流程 |
| `CONSENT_REQUIRED` | 缺少数据主体同意 | 走同意管理 |
| `PURPOSE_NOT_ALLOWED` | 目的超出授权 | 修改 purpose 或申请授权 |

不要用 `400 Bad Request` 一把梭，否则调用方无法区分“参数错”与“隐私策略拒绝”。

### AG.12.4 同意、目的与数据来源

高风险 API 还应携带：

- `purpose`：数据使用目的；
- `legal_basis`：法律依据（由法务确认）；
- `consent_id`：同意记录；
- `data_provenance`：数据来源与处理链；
- `retention`：保留期。

这些字段不是装饰：它们决定查询是否被允许，并进入审计。

### AG.12.5 日志与可观测性

- 不记录原始敏感值；
- 记录查询模式、预算消耗、抑制原因；
- 对日志做访问控制与保留期管理；
- trace 中不携带 PII；
- 对模型调用记录 token 数而非完整 prompt；
- 审计日志本身要防篡改。

## AG.13 选型矩阵

| 目标 | 首选 | 次选 | 关键代价 | 常见误用 |
|---|---|---|---|---|
| 发布统计不泄露个体 | 差分隐私 | 聚合阈值 + 审计 | 精度、预算管理 | 以为 k-匿名够了 |
| 多方联合统计 | MPC / PSI | 洁净室 + 输出控制 | 通信、延迟 | 把 MPC 当实时 API |
| 密文计算 | 同态加密 | TEE | 性能、表达力 | 以为能跑任意 SQL |
| 不可信基础设施处理明文 | TEE | MPC | 侧信道、厂商信任 | 不做远程认证 |
| 设备端训练 | 联邦学习 + 安全聚合 + DP | 本地差分隐私 | 收敛、运维 | 以为 FL 自动隐私 |
| 数据共享/测试 | DP 合成数据 | 脱敏 + 合同 | 效用、验证 | 把合成数据当匿名数据 |
| 网络元数据保护 | OHTTP + Privacy Pass | 中继/代理 | 滥用控制、延迟 | 以为 OHTTP 等于匿名 |
| 监管报送/审计 | 可验证日志 + 最小化 | TEE/洁净室 | 工程与流程 | 只做加密不做访问控制 |

## AG.14 反模式

- **“去掉姓名就是匿名”**：准标识符组合仍可重识别；
- **k-匿名当万能药**：同质性、背景知识、增量发布都会击穿；
- **ε 剧场**：随便写一个 `epsilon: 0.1`，但敏感度、组合、预算都没算；
- **客户端中心 DP**：客户端被攻破后原始数据全泄露；
- **TEE 不做远程认证**：等于相信一个自称安全的黑盒；
- **同态加密跑通用查询**：忽略表达力与性能边界；
- **联邦学习自动隐私**：梯度仍可反演，服务器仍能看到单个更新；
- **洁净室没有输出控制**：只是把数据复制到另一个地方；
- **合成数据不评估**：既可能记忆训练样本，也可能完全不可用；
- **日志/trace 泄露**：主 API 做了脱敏，日志里却有原始请求体；
- **预算不限租户**：一个租户耗尽全部预算，或通过多账号绕过；
- **没有目的限制**：同一数据集被用于未授权的二次分析；
- **把 PET 当合规免死金牌**：技术保证不能替代法律评估与合同。

## AG.15 检查清单

### 威胁模型与治理

- [ ] 明确数据主体、敏感属性、攻击者能力与可接受泄露上界。
- [ ] 每个数据集有目的限制、保留期、所有权与访问审批。
- [ ] 有数据分类分级与字段级敏感标记。
- [ ] 有隐私预算/查询配额的责任人与审计。
- [ ] 有数据主体请求（访问、删除、更正）的 API 路径。

### 差分隐私

- [ ] 相邻数据集定义与敏感度计算有文档与测试。
- [ ] 噪声机制与参数经过评审，不由客户端任意指定。
- [ ] 组合与预算记账覆盖所有查询入口，而不是单个服务。
- [ ] 预算耗尽有明确错误、重试语义与审计。
- [ ] 结果的后处理不会破坏 DP 保证。
- [ ] 对极端值有裁剪策略，并说明偏差。

### 聚合与查询

- [ ] 最小群体阈值与补抑制已实现。
- [ ] `min`/`max`/`count=0` 等边界不会泄露个体。
- [ ] 有差分攻击检测或查询审计。
- [ ] 缓存命中不会绕过预算或抑制。
- [ ] 导出/批量接口与在线查询使用同一套策略。

### MPC / HE / TEE / FL

- [ ] MPC 的安全模型（半诚实/恶意）、合谋阈值与网络假设明确。
- [ ] 同态加密的参数、精度、密文大小与性能经过实测。
- [ ] TEE 有远程认证、measurement 校验、nonce 防重放与策略版本。
- [ ] TEE 的侧信道、供应链与厂商信任边界写入风险登记。
- [ ] 联邦学习有安全聚合、DP、客户端采样与投毒防护。
- [ ] 模型更新有幂等、去重、版本与评估。

### 接口与运营

- [ ] 隐私错误码可区分、可操作，不与其他错误混淆。
- [ ] 响应中可见预算消耗、抑制原因与噪声语义（按受众分级）。
- [ ] 日志、trace、指标不包含原始敏感值。
- [ ] 审计日志防篡改，保留期符合合同与监管。
- [ ] 对 PET 的性能、成本与可用性有真实基准。
- [ ] 有跨租户/跨账号的预算绕过测试。
- [ ] 合成数据经过成员推断、最近邻与下游效用评估。
- [ ] 洁净室有查询审批、输出审查、最小群体与 DP 预算。

## AG.16 小结

- 隐私风险的核心是“输出让攻击者能推断个体”，而不只是字段是否脱敏。
- 差分隐私提供可组合、可量化的泄露上界；预算必须像配额一样管理。
- k-匿名、聚合阈值与查询审计有位置，但不能替代形式化保证。
- MPC、同态加密、TEE、联邦学习各自解决不同问题，也各有明确边界。
- 合成数据与洁净室是流程与技术组合，输出控制比“数据不出域”更关键。
- 元数据也会泄露；OHTTP、Privacy Pass 与匿名凭证把隐私扩展到网络层。
- PET 必须写进契约：预算、错误码、审计、目的限制与可观测性，否则只是论文里的能力。
