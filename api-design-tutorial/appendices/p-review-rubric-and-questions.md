# 附录 P：API 设计评审 Rubric 与题库

设计评审最常见的失败，不是“没看出问题”，而是**每次都在看不同的问题**：这次评审纠结字段命名，下次只谈性能，再下次变成架构辩论。结果是评审很热闹，风险却没有被系统覆盖。

本附录提供一套可复用的评审 rubric、问题清单与练习题库。它既可以用于团队内部的设计评审，也可以用于面试、系统设计复盘与自我检查。

## P.1 使用原则

1. **先看约束，再看方案。** 不知道消费者、流量、一致性要求与合规约束，就无法判断设计好坏。
2. **区分事实、假设与偏好。** “这个字段是必填”是事实；“调用方会重试”是假设；“我觉得应该用 PUT”是偏好。评审要优先验证假设。
3. **按风险排序。** 不是所有问题都值得在会上讨论。先看不可逆、影响面大、失败代价高的决策。
4. **给可执行的结论。** “再想想”不是结论。结论应该是：通过、有条件通过、需要补充、拒绝，并写明条件与负责人。
5. **记录决策。** 评审的输出是 ADR 或设计记录，不是聊天记录。

## P.2 评分维度与权重

| 维度 | 权重 | 核心问题 |
|---|---|---|
| 领域与边界 | 15% | 资源是否来自领域？边界是否清晰？ |
| 契约与表示 | 15% | 语法、语义、错误、分页、版本是否自洽？ |
| 安全与隐私 | 15% | 谁能做什么？数据最小化了吗？ |
| 运行与可靠性 | 15% | 失败时如何表现？能否观测与恢复？ |
| 性能与容量 | 10% | 峰值、尾延迟、成本是否可承受？ |
| 工程与治理 | 10% | 测试、契约、发布、所有权是否到位？ |
| 产品与 DX | 10% | 开发者能否快速、正确地使用？ |
| 商业与合规 | 10% | 定价、合同、监管是否可持续？ |

权重不是绝对的。支付、医疗、开放银行可以提高安全与合规权重；内部工具可以降低产品与商业权重。关键是**在评审开始前明确权重**，避免事后争论。

一致性与数据语义是横切项：不单独占权重，但“一致性承诺不可验证”或“指标没有口径版本”应在对应维度直接判 0～1 分，而不是靠其他维度的高分抵消。

## P.3 0～4 分锚点

每个维度用 0～4 分打分：

| 分数 | 含义 | 典型表现 |
|---|---|---|
| 0 | 缺失 | 没有考虑，或存在明显致命问题 |
| 1 | 薄弱 | 有想法但不可执行，缺少关键细节 |
| 2 | 合格 | 覆盖主要问题，仍有明显风险 |
| 3 | 良好 | 覆盖完整，有权衡记录，有验证手段 |
| 4 | 优秀 | 不仅正确，还能演进、可观测、可运营 |

总分不是简单加权平均。一个维度 0 分（如对象级授权缺失）可以否决整体，即使其他维度很高。

### 各维度的评分要点

**领域与边界（0～4）**

- 0：资源直接映射数据库表；边界按团队而不是业务划分。
- 1：有资源清单，但聚合、状态机、不变量不清。
- 2：资源与状态机基本合理，跨上下文依赖有说明。
- 3：聚合边界清晰，读写模型与事件所有权明确。
- 4：边界能支撑未来演进，领域语言与业务一致，有反模式检查。

**契约与表示（0～4）**

- 0：字段含义靠猜；错误只有 400；分页不一致。
- 1：有 OpenAPI，但示例、错误、边界条件缺失。
- 2：命名、类型、错误、分页基本一致。
- 3：语义契约、幂等、版本、兼容性有明确规则。
- 4：契约可机器验证，有 lint、破坏性检测与消费者契约。

**安全与隐私（0～4）**

- 0：只校验登录，不校验对象权限。
- 1：有认证，但授权粒度粗，租户隔离靠应用层自觉。
- 2：功能级与对象级授权覆盖主要路径。
- 3：字段级/租户级隔离、审计、密钥轮换、威胁建模到位。
- 4：零信任、最小权限、可验证审计、隐私工程与应急演练。

**运行与可靠性（0～4）**

- 0：没有超时、重试、幂等；失败即未知。
- 1：有基本错误处理，但重试会放大故障。
- 2：超时、重试、熔断、限流基本可用。
- 3：有 SLO、错误预算、降级、演练与容量规划。
- 4：故障可注入、可观测、可恢复，爆炸半径受控。

**性能与容量（0～4）**

- 0：只看平均值；没有压测。
- 1：有压测，但不覆盖峰值与尾延迟。
- 2：知道瓶颈与容量上限。
- 3：有性能预算、过载保护与成本模型。
- 4：性能与成本可优化、可预测，峰值有演练。

**工程与治理（0～4）**

- 0：没有契约、测试、所有权。
- 1：有测试但不覆盖契约与并发。
- 2：CI 有 lint、测试、基本契约检查。
- 3：契约测试、破坏性检测、发布与弃用流程完整。
- 4：平台化、自动化、评分卡与持续改进。

**产品与 DX（0～4）**

- 0：只有接口，没有文档与示例。
- 1：文档存在但过时，快速开始跑不通。
- 2：参考文档与示例基本可用。
- 3：沙箱、SDK、错误信息、变更日志完整。
- 4：TTFC 可度量，开发者反馈闭环，文档与契约同源。

**商业与合规（0～4）**

- 0：没有定价与合规考虑。
- 1：有价格，但成本与条款不清。
- 2：定价、计量、SLA 基本可执行。
- 3：单位经济、合同、监管矩阵清晰。
- 4：商业模型可持续，风险有对冲，生态策略明确。

## P.4 评审流程

### 30 分钟快速评审

适用于内部服务、低风险变更。

1. 5 分钟：目标、消费者、约束；
2. 10 分钟：资源、契约、错误、版本；
3. 5 分钟：安全与失败模式；
4. 5 分钟：测试与上线计划；
5. 5 分钟：结论与行动项。

### 60 分钟标准评审

1. 10 分钟：背景与约束（含流量、SLO、合规）；
2. 15 分钟：领域模型与契约；
3. 10 分钟：安全、隐私、多租户；
4. 10 分钟：可靠性、性能、成本；
5. 10 分钟：DX、发布、弃用；
6. 5 分钟：结论与负责人。

### 90 分钟深度评审

适用于公开 API、支付、医疗、开放银行、AI Agent 等高风险场景。

在 60 分钟基础上增加：

- 15 分钟对抗性场景：重试、并发、断网、越权、提示注入；
- 10 分钟故障演练：依赖挂、区域故障、数据损坏；
- 5 分钟商业与合同：SLA、DPA、定价、退出。

### 评审的角色

| 角色 | 关注 |
|---|---|
| 提案人 | 约束、方案、权衡、验证计划 |
| 领域专家 | 业务语义、状态机、边界 |
| 安全评审 | 威胁建模、授权、密钥、审计 |
| SRE/平台 | SLO、容量、可观测性、发布 |
| 消费者代表 | DX、兼容性、迁移成本 |
| 记录人 | 决策、行动项、反对意见 |

不要所有评审都要求全员到场。低风险变更可以异步评审，但高风险变更必须有明确的安全与运维签字。

## P.6 必问问题：30 个基础 + 34 个进阶

### 领域与契约

1. 这个 API 服务谁？他们最常做的前三个任务是什么？
2. 哪些概念有身份与生命周期？哪些只是值？
3. 聚合边界在哪里？哪些不变量必须原子保证？
4. 资源是否直接映射了数据库表？如果是，为什么？
5. 状态机的状态、转换、非法转换分别是什么？
6. 哪些字段是快照，哪些是引用？快照何时失效？
7. 分页、过滤、排序的语义是否一致？总数是否准确？
8. 错误码是否稳定？调用方能否据此分支？
9. 幂等键覆盖哪些操作？相同键不同请求如何处理？
10. 版本策略是什么？什么算破坏性变更？

### 安全与隐私

11. 认证解决“你是谁”还是“你代表谁”？
12. 对象级授权在哪里执行？能否绕过？
13. 租户隔离在查询、缓存、存储、队列、日志中都成立吗？
14. 哪些字段永远不应返回？谁来决定字段级权限？
15. 密钥如何存储、轮换、吊销？泄露后多久能止血？
16. 令牌的 audience 是什么？能否被其他服务复用？
17. 高风险操作是否需要二次认证或人工确认？
18. 审计记录哪些字段？保留多久？谁能修改？
19. 数据最小化了吗？删除请求能传播到备份与索引吗？
20. 是否做过威胁建模？最危险的三个攻击路径是什么？

### 运行与商业

21. 依赖失败时 API 返回什么？调用方应该怎么做？
22. 重试会不会放大故障？重试预算与退避策略是什么？
23. SLO 的 SLI 如何计算？分母是什么？
24. 峰值流量是均值的多少倍？容量如何验证？
25. 尾延迟的来源是什么？是否做过压测？
26. 成本如何随用量增长？最贵的操作是什么？
27. 定价单位是否与成本驱动一致？账单能否解释？
28. 弃用与迁移路径是什么？谁负责通知消费者？
29. 合同中的 SLA、DPA、退出条款技术团队能否兑现？
30. 如果明天要支持 Agent 调用，契约缺什么？

### 一致性、数据与运行时（进阶）

31. 一致性承诺的范围、操作、时间上界与例外分别是什么？
32. 每个关键键的写权威在哪里？故障转移时如何阻止旧主继续写？
33. 读到旧数据时，客户端会看到什么？是重试、等待，还是拿到旧值？
34. 关键状态机的不变量是什么？用什么方式验证（状态机表/性质测试/TLA+）？
35. 指标或数据口径有版本吗？同名指标在 BI 与 API 中是否一致？
36. 数据 API 是否返回 data-through、质量与口径版本？消费者如何知道数据不完整？
37. 运行时超时、包大小、冷启动、并发配额是否写进 SLO 与容量模型？
38. 边缘或 WASM 插件失败时如何降级？ABI、能力授权与资源限制是否明确？

### 密码学、序列化与供应链（进阶）

39. 传输、消息、令牌、密钥四层信任分别由谁验证？TLS 之外还需要消息签名吗？
40. 签名覆盖哪些字节/组件？如何规范化、如何防重放、如何轮换密钥？
41. JWT 的 `alg`/`kid`/`iss`/`aud`/`exp`/`typ` 校验是否完整？令牌能否被其他受众复用？
42. 高价值 API 是否使用 DPoP 或 mTLS 绑定？令牌泄露后的影响范围与止血时间是多少？
43. 有 CBOM/密钥清单吗？后量子迁移的优先级、试点、混合模式与回退路径是什么？
44. 序列化格式的类型、精度、三态与时间语义是否写清？金额与大整数如何处理？
45. Schema 兼容性靠什么保证？CI 能否拦截破坏性变更？事件是否要求 full/transitive 兼容？
46. 签名与幂等指纹是否依赖确定字节？压缩是否考虑 BREACH 与压缩炸弹？流式响应如何处理中途错误？

### 基础语义（进阶）

47. 每个时间字段是时刻、本地日期时间、日期、时长还是区间？时区用 IANA 名称吗？DST 缺口/重叠如何处理？
48. 业务日、截止时间、账期锚点、按比例计算和舍入规则写清了吗？能否复现历史账单？
49. 金额是否带币种、按币种 exponent、避免浮点？舍入发生在哪一步？分摊后总额是否守恒？
50. 数量是否带单位？百分比/百分点/基点是否混用？坐标是否声明 CRS？
51. ID 是否不透明、不可枚举、不复用？游标是否签名、过期、绑定查询？外部 ID 如何映射？
52. 语言标签、Unicode 归一化、字符串长度口径、排序规则和搜索分词是否与目标语言匹配？

### 行业垂直（进阶）

53. 行业标准、版本、认证要求与监管义务是否映射到 API 能力与证据？
54. 标准契约与内部模型之间有没有防腐层？标准升级时影响范围多大？
55. 同意/授权是否是资源，有范围、目的、期限、撤回与传播？
56. 长流程是否有状态机、异步任务、查询、回调、补偿与对账？
57. 沙箱、模拟器、一致性测试、合作伙伴 onboarding 是否就绪？
58. 医疗、开放银行、电信、工业/汽车中，哪些高风险操作需要二次确认、联锁或人工兜底？

### 变更工程（进阶）

59. 沙箱与生产同源吗？模拟保真度处于哪一级？用什么机制证明沙箱没有漂移？
60. 测试密钥能否调用生产？跨租户读取返回 403 还是 404？数据如何重置、播种与清理？
61. 计费、试用、过期、DST 如何用测试时钟稳定测试？Webhook 能否重放、注入失败并查看投递日志？
62. 哪些变更用开关，哪些必须用新版本？配置服务故障时，各类型开关的默认值分别是什么？
63. 金丝雀样本是否包含真实大租户？kill switch 的生效时间如何测量和演练？过期开关由谁清理？
64. Terraform、CRD 与 GitOps 的字段所有权如何划分？漂移由谁检测、谁修复、如何审计？

## P.7 系统设计题库

以下题目用于练习“在约束下做取舍”。每题给出答题骨架，不给出唯一答案。

### 题目一：短链接服务

**要求**：把长 URL 转成短码；支持自定义短码、过期、访问统计、恶意链接拦截；读多写少。

**答题骨架**：

- 资源：`Link`、`CustomAlias`、`ClickEvent`、`Blocklist`；
- 标识：短码生成（Base62 + 随机/哈希）、冲突处理、不可猜测性；
- 读路径：缓存、CDN、301/302 选择、缓存穿透；
- 写路径：幂等、别名唯一约束、过期清理；
- 安全：开放重定向、SSRF、钓鱼拦截、滥用限流；
- 统计：异步事件、去重、隐私；
- 版本：短码永久性、域名迁移、弃用。

**追问**：如果短码被大量扫描，如何不影响真实用户？如果恶意链接在被举报前已传播，如何处理？

### 题目二：支付 API

**要求**：支持一次性支付、退款、部分退款、Webhook、对账；多渠道；高可用。

**答题骨架**：

- 资源：`PaymentIntent`、`Charge`、`Refund`、`Dispute`、`LedgerEntry`；
- 幂等：创建、确认、退款；相同键不同请求；
- 状态机：`requires_action`、`processing`、`succeeded`、`failed`；
- 一致性：支付成功与订单状态、出票/发货的解耦；
- Webhook：签名、重试、去重、顺序、查询兜底；
- 账本：复式记账、不可变、冲正；
- 对账：渠道流水、银行流水、内部账本；
- 合规：PCI、SCA、KYC/AML、数据保留。

**追问**：支付超时但渠道成功，如何避免重复扣款？部分退款如何记账？拒付后如何影响账本？

### 题目三：社交 Feed

**要求**：关注、发帖、时间线、点赞、评论、内容审核；读写比例约 1:100；明星用户粉丝千万。

**答题骨架**：

- 资源：`User`、`Follow`、`Post`、`Comment`、`Reaction`、`Feed`；
- 扇出：写扩散 vs 读扩散 vs 混合；
- 分页：游标、快照、排序稳定性；
- 一致性：计数、删除、审核状态；
- 缓存：热帖、时间线、失效；
- 安全：隐私、拉黑、举报、未成年人；
- 审核：异步、申诉、误杀；
- 事件：发帖、删除、审核结果。

**追问**：明星发帖如何避免扇出风暴？删除帖子后，已缓存的时间线如何处理？

### 题目四：实时协作文档

**要求**：多人同时编辑、离线编辑、冲突合并、评论、权限、版本历史。

**答题骨架**：

- 资源：`Document`、`Operation`、`Snapshot`、`Presence`、`Comment`、`Permission`；
- 同步：WebSocket/WebTransport、OT/CRDT、操作顺序；
- 离线：本地队列、合并、冲突解决；
- 权限：文档级、段落级、评论级；
- 版本：快照 + 增量、回滚、审计；
- 扩展：房间、连接路由、背压；
- 安全：XSS、越权、恶意操作、限流。

**追问**：两个用户离线修改同一段，如何合并？如何证明历史版本未被篡改？

### 题目五：IoT 设备平台

**要求**：百万设备接入、遥测、命令、OTA、离线、弱网；设备可能被物理攻击。

**答题骨架**：

- 资源：`Device`、`Telemetry`、`Command`、`Firmware`、`Shadow`；
- 接入：MQTT/CoAP/HTTP、设备身份、证书；
- 遥测：时序、幂等、乱序、压缩；
- 命令：至少一次、幂等、超时、离线队列；
- 影子：期望状态 vs 报告状态、冲突；
- OTA：分批、回滚、签名、断电恢复；
- 安全：物理攻击、密钥、固件签名、租户隔离；
- 成本：连接数、消息数、存储。

**追问**：设备离线三天后重连，命令如何排序？OTA 中途断电如何恢复？

### 题目六：LLM 应用 API

**要求**：多轮对话、流式输出、工具调用、RAG、配额、成本控制、安全拒绝。

**答题骨架**：

- 资源：`Conversation`、`Message`、`ToolCall`、`Usage`、`KnowledgeBase`；
- 流式：SSE、事件顺序、断线恢复、取消；
- 上下文：窗口管理、摘要、裁剪、token 计数；
- 工具：schema、错误、幂等、确认；
- RAG：检索、引用、权限、新鲜度；
- 成本：输入/输出/缓存/推理 token、预算；
- 安全：提示注入、数据外泄、输出审核、模型版本；
- 评估：金标准集、灰度、回滚。

**追问**：流式输出中途被安全策略拒绝，如何计费与展示？模型升级后行为变化，如何回滚？

### 题目七：活动票务平台

见附录 O。练习时先不看 O，自己写出资源、状态机、预占、支付、检票与峰值方案，再对照。

## P.8 评分示例

### 示例 A：一个“合格但危险”的设计

```text
GET /getOrders?userId=123
POST /updateOrderStatus
```

问题：

- URL 用动词，资源语义不清；
- `userId` 来自查询参数，未验证是否属于当前用户（IDOR）；
- 状态更新没有幂等与状态机；
- 没有分页、错误码、版本；
- 没有审计与限流。

评分：领域 1，契约 1，安全 0，运行 1，性能 2，工程 1，DX 1，商业 1。安全 0 直接否决。

### 示例 B：一个“过度设计”的设计

```text
GraphQL + gRPC + 事件溯源 + 自定义二进制协议
```

问题：

- 团队只有 3 人，却要维护四套协议；
- 没有明确的消费者需求；
- 调试、监控、SDK 成本被低估；
- 事件溯源用于简单 CRUD，增加复杂度而无收益。

评分：领域 3，契约 3，安全 3，运行 2，性能 3，工程 1，DX 1，商业 1。技术不差，但组织与产品维度不及格。

结论不是“技术越先进越好”，而是**设计与团队、消费者、成本匹配**。

## P.10 小结

- 评审的价值在于系统覆盖风险，而不是证明谁更聪明。
- 先用约束过滤方案，再按风险排序讨论。
- 评分锚点让“好”与“差”可比较，但一票否决项优先于总分。
- 题库用于练习取舍，不是背答案。
- 最好的评审，是让团队在发布前看见几年后的维护成本。
