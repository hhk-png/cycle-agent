# 附录 AD：API 密码学工程——消息签名、令牌约束与后量子迁移

> 密码学不是“加个 HTTPS”或“签个 JWT”。在 API 里，它是一组必须被写进契约、被实现验证、被运维轮换、被迁移计划覆盖的信任机制。

本附录讨论四件事：

1. 传输层信任：TLS、mTLS 与证书生命周期；
2. 消息层信任：当 TLS 不够时，如何对请求/响应/Webhook 做端到端签名；
3. 令牌层信任：JWT/JOSE 的正确校验、DPoP 与发送方约束；
4. 迁移层信任：当 RSA/ECC 需要让位于后量子算法时，API 契约如何保持可用。

它不替代密码学教材，也不提供“自研加密方案”。它关注的是 API 设计者最容易做错、且一旦做错很难回滚的决策。

---

## AD.1 先写威胁模型，再选算法

密码学机制只有在明确的威胁模型下才有意义。一个 API 通常同时面对：

| 威胁 | 典型场景 | 主要机制 | 机制不解决什么 |
|---|---|---|---|
| 网络窃听 | 公共 Wi-Fi、跨云链路 | TLS | 终端被攻破后的数据 |
| 中间人 | 恶意代理、DNS 劫持 | 证书校验、mTLS、消息签名 | 内部人主动转发 |
| 伪造请求 | Webhook 伪造、重放 | HMAC/非对称签名、时间戳、nonce | 密钥泄露后的冒充 |
| 令牌盗用 | XSS、日志泄露、设备丢失 | 短生命周期、DPoP、mTLS 绑定、轮换 | 已完成的恶意操作 |
| 数据篡改 | 网关转换、跨组织转发 | 消息签名、Digest | 接收方自身逻辑错误 |
| 内部越权 | 共享密钥、过度 scope | 最小权限、租户隔离、审计 | 合法权限内的滥用 |
| 供应链攻击 | SDK、依赖、构建产物 | 签名、SBOM、最小权限 | 运行时漏洞 |
| 未来量子对手 | 长期存档、长周期合同 | 后量子迁移、混合密钥交换 | 今天的实现错误 |

设计时至少要为每个信任边界回答五个问题：

1. **谁验证？** 网关、服务、SDK、接收方，还是最终用户？
2. **验证什么字节？** 原始 body、规范化 JSON，还是解析后的对象？
3. **密钥在哪里？** KMS、HSM、环境变量、配置文件，还是客户端？
4. **过期与轮换怎么做？** 双密钥窗口、`kid`、缓存 TTL、紧急吊销。
5. **失败时怎么办？** 拒绝、降级、告警，还是重试？

如果这些问题没有答案，所谓“已加密”“已签名”通常只是心理安慰。

### 一条实用原则

> **传输安全保护“链路”，消息签名保护“内容”，令牌约束保护“身份”，密钥管理保护“以上全部”。**

四者不能互相替代：

- 有 TLS 不等于 Webhook 不能被伪造；
- 有 JWT 不等于令牌不能被复制；
- 有 mTLS 不等于请求体没有被中间网关改写；
- 有签名不等于密钥不会泄露。

## AD.2 传输安全：TLS 是最低配，不是全部

### TLS 1.3 的默认假设

现代 API 应默认：

- 只启用 TLS 1.2+，优先 TLS 1.3；
- 禁用弱套件、压缩、重协商；
- 启用 HSTS（面向浏览器）；
- 证书链完整，OCSP stapling 或 CRL 可用；
- 证书自动轮换，监控到期时间；
- 不在 URL、日志、错误信息中泄露令牌。

TLS 1.3 的 0-RTT（early data）能降低重连延迟，但它**不保证抗重放**。对写操作、支付、Webhook 回调，0-RTT 请求必须要么禁用，要么配合幂等键与时间窗校验。

### TLS 终止在哪里

| 终止点 | 优点 | 风险 |
|---|---|---|
| 边缘/CDN | 卸载、缓存、WAF | 边缘到源站需再加密 |
| API 网关 | 集中证书与策略 | 网关成为信任瓶颈 |
| 服务网格 sidecar | 工作负载级 mTLS | 运维复杂、证书签发依赖 |
| 应用进程 | 端到端 | 证书管理与性能开销 |

终止点决定了“谁能看到明文”。如果网关会解析、改写、记录 body，那么 TLS 只保护了客户端到网关这一段；跨网关、跨组织、跨团队的完整性需要消息签名。

### mTLS 与工作负载身份

mTLS 适合：

- 服务到服务的东西向流量；
- 高价值合作伙伴的固定连接；
- 需要把令牌绑定到客户端证书的场景；
- 零信任网络中“每个请求都验证”。

落地时要注意：

- **证书签发**：不要让每个团队手工申请证书；使用 SPIFFE/SPIRE、cert-manager、云平台工作负载身份。
- **身份映射**：证书 SAN/URI 如何映射到租户、服务、环境？映射规则要写进契约。
- **吊销**：短生命周期证书优先；CRL/OCSP 要有兜底；吊销延迟要写进安全假设。
- **信任库**：根证书更新、交叉签名、私有 CA 的分布。
- **证书固定（pinning）**：移动端 pinning 能降低中间人风险，但会让证书轮换变得危险；需要可远程更新的 pin 集合与灰度机制。
- **代理透传**：mTLS 在网关终止后，后端如何知道客户端证书？通过受信任的内部头或重新建立 mTLS，且内部头必须由网关签名/清洗，不能被外部伪造。

### 传输层检查清单

- [ ] 是否禁用 TLS 1.0/1.1 与弱套件？
- [ ] 证书是否自动续期，并有到期告警？
- [ ] 0-RTT 是否只用于安全、幂等的请求？
- [ ] 网关到源站是否仍然加密？
- [ ] mTLS 的身份如何映射到租户与服务？
- [ ] 证书吊销与根证书轮换有演练吗？
- [ ] 是否区分“链路加密”和“内容完整性”？

## AD.3 消息级签名：当 TLS 不够

### 什么时候需要消息签名

以下场景，TLS 不足以证明“这个请求确实来自声称的发送方，且内容未被改写”：

- **Webhook**：接收方无法与发送方建立双向 TLS，回调又必须可信；
- **跨组织 API**：请求经过多个网关、代理、集成平台；
- **高价值操作**：转账、退款、权限变更、删除；
- **审计与不可否认**：需要证明某方在某个时间点发过某条消息；
- **网关会改写内容**：签名覆盖原始语义，接收方验证端到端完整性；
- **异步消息**：事件经过消息队列、桥接器、跨云复制。

### HMAC 还是非对称签名

| 维度 | HMAC | 非对称签名 |
|---|---|---|
| 密钥分发 | 双方共享一个秘密 | 发送方持私钥，接收方持公钥 |
| 验证方数量 | 每对双方一个密钥 | 多方可用同一公钥验证 |
| 不可否认 | 弱（双方都能生成） | 强（私钥持有者才能生成） |
| 轮换 | 双方同时更新 | 公钥可发布、可缓存 |
| 性能 | 快 | 较慢，签名更大 |
| 适用 | Webhook、内部回调 | 跨组织、审计、公开可验证 |

HMAC 的关键不是算法，而是**密钥如何分发、如何轮换、如何避免在多个租户间共享**。非对称签名的关键则是**公钥如何可信地发布**（JWKS、证书、配置），以及**算法标识如何不被攻击者替换**。

### 签什么：语义，而不是“整个 JSON”

一个常见的错误是：发送方把 JSON 解析后再序列化，然后对序列化结果签名；接收方也解析再序列化。两次序列化的键顺序、空格、数字格式、Unicode 转义可能不同，签名必然对不上。

正确做法：

1. 对**原始字节**签名；
2. 或者使用标准规范化算法（见附录 AE 的 JCS/CBOR 确定性编码）；
3. 明确签名覆盖哪些头部、方法、路径、查询参数与 body；
4. 把时间戳、nonce、密钥 ID、算法标识纳入签名或至少纳入验证上下文。

### RFC 9421：HTTP Message Signatures

RFC 9421 把“对 HTTP 消息的哪些组件签名”标准化。一个典型请求：

```http
POST /payments HTTP/1.1
Host: api.example.com
Content-Type: application/json
Content-Digest: sha-256=:d435t5...:
Signature-Input: sig1=("@method" "@target-uri" "content-digest");created=1764200000;keyid="payments-2026-11";alg="ed25519"
Signature: sig1=:5bG9...base64url-ed25519-signature...:
```

验证方按 `Signature-Input` 列出的组件重建签名基串，再用 `keyid` 对应的公钥验证 `Signature`。关键点：

- `@method`、`@target-uri`、`@authority`、`@path`、`@query` 是派生组件，避免代理改写路径后签名仍然通过；
- `content-digest` 绑定 body；`Content-Digest` 使用 RFC 9530 的字段语法；
- `created` / `expires` 限制有效期；`nonce` 可用于一次性请求；
- `keyid` 让轮换可行；`alg` 只是提示，**验证方必须用允许列表校验实际算法**，不能盲信头部；
- 头部名称大小写、重复头合并、空白处理都要按规范规范化。

伪代码：

```python
def verify_request(req, key_resolver, replay_cache, now):
    sig_input = parse_signature_input(req.headers["Signature-Input"])
    signature = parse_signature(req.headers["Signature"])
    key = key_resolver(sig_input.keyid)
    if key is None or key.alg not in ALLOWED_ALGS:
        raise Unauthorized("unknown key or algorithm")
    if now - sig_input.created > MAX_SKEW:
        raise Unauthorized("stale signature")
    if sig_input.expires and now > sig_input.expires:
        raise Unauthorized("expired signature")
    base = build_signature_base(req, sig_input.components)
    if not key.verify(base, signature):
        raise Unauthorized("bad signature")
    if replay_cache.seen(sig_input.nonce or signature):
        raise Conflict("replayed request")
    if not verify_content_digest(req.body, req.headers["Content-Digest"]):
        raise BadRequest("body digest mismatch")
    replay_cache.remember(sig_input.nonce or signature, ttl=MAX_SKEW)
```

验证顺序很重要：**先验证身份与新鲜度，再做副作用**。不要先执行业务逻辑，最后才检查签名。

### Standard Webhooks：更简单的 Webhook 签名

对 Webhook，完整的 HTTP Message Signatures 可能过重。Standard Webhooks 定义了一个更小的公共格式：

```http
webhook-id: msg_2b3c...
webhook-timestamp: 1764200000
webhook-signature: v1,Base64(HMAC-SHA256(secret, id + "." + timestamp + "." + body))
```

规则：

- 签名内容为 `${webhook-id}.${webhook-timestamp}.${rawBody}`；
- 密钥通常以 `whsec_` 前缀分发，Base64 解码后使用；
- 接收方允许例如 5 分钟的时间偏差；
- 轮换期间可以同时发送多个 `v1` 签名，接收方任一匹配即通过；
- 校验必须在处理业务之前，且对重复 `webhook-id` 做幂等。

它解决了“各家 Webhook 签名格式不同”的互操作问题，但不解决密钥泄露、SSRF、重放存储等工程问题。

### 非对称 Webhook 签名

当接收方很多、或需要第三方独立验证时，可以用：

- **分离式 JWS**：body 作为 payload，签名放在头部；
- **JWT 形式的回调令牌**：包含 `iss`、`aud`、`iat`、`exp`、`jti`、`event_id`，用 JWKS 发布公钥；
- **签名事件信封**：CloudEvents 的 `datacontenttype` + 签名扩展。

注意：JWS/JWT 的 `alg` 校验、`kid` 解析、JWKS 缓存与轮换，和下面令牌部分的问题完全相同。

### 消息签名的反模式

- 对解析后的对象签名，而不是原始字节；
- 只签 body，不签方法/路径/时间戳；
- 没有 `keyid`，无法轮换；
- 接受任意 `alg`，包括 `none` 与 HMAC/RSA 混淆；
- 没有时间窗，签名永久有效；
- 没有重放缓存，攻击者可重复提交；
- 先执行业务，再验签；
- 签名密钥与租户共享，泄露后全量失守；
- 把签名密钥放在客户端或前端代码里；
- 用自定义字符串拼接代替标准规范化，导致跨语言实现不一致。

## AD.4 令牌与凭证：JWT 不是“安全字符串”

### JWT 校验的最小清单

一个 JWT 只有在以下检查全部通过后才可信：

- [ ] 签名算法在允许列表中（不要信任头部的 `alg`）；
- [ ] `kid` 能解析到受信任的密钥，且密钥未过期；
- [ ] `iss` 与预期签发者完全匹配；
- [ ] `aud` 包含当前 API 的标识；
- [ ] `exp` 未过期，`nbf` 未到未来，`iat` 在合理偏差内；
- [ ] `typ`（如 `at+jwt`）符合预期；
- [ ] `azp`/`client_id` 与调用方一致（如适用）；
- [ ] `scope`/`roles` 经过授权层映射，不直接信任字符串；
- [ ] 令牌未被吊销（短 TTL、introspection、吊销列表或版本号）；
- [ ] 时钟偏差有上限，且所有服务使用可信时间源。

### 常见 JWT 攻击

| 攻击 | 原理 | 防护 |
|---|---|---|
| `alg=none` | 去掉签名，依赖库接受空算法 | 算法允许列表 |
| HMAC/RSA 混淆 | 把公钥当 HMAC 密钥 | 按密钥类型固定算法 |
| `kid` 注入 | 路径穿越、SQL 注入、命令注入 | `kid` 只做映射键，不拼路径 |
| `jku`/`x5u` SSRF | 让验证方拉取攻击者 JWKS | 禁止外部 URL，使用固定信任库 |
| 嵌入 JWK | 头部自带公钥，攻击者自签 | 忽略或严格限制 |
| `crit` 头 | 触发未实现的关键扩展 | 拒绝未知 `crit` |
| 重复 claim | 解析器取第一个/最后一个不一致 | 拒绝重复键 |
| 压缩炸弹 | JWE/JWS 压缩导致内存耗尽 | 限制解压大小 |
| 受众混淆 | 给 A 服务的令牌拿去调 B | 严格校验 `aud` |

### 令牌生命周期

- **Access Token**：短，通常 5～15 分钟；按受众、scope、租户限定。
- **Refresh Token**：长，但必须旋转；检测重用并立即吊销整个令牌族。
- **授权码**：一次性，短 TTL，绑定 PKCE 与 redirect URI。
- **客户端凭证**：只用于服务身份，不携带用户语义。
- **令牌交换**（RFC 8693）：在服务间代表用户或租户时，换取受众更窄的令牌，而不是透传原始令牌。

### DPoP：把令牌绑到客户端密钥

Bearer Token 的问题是“谁拿到谁能用”。DPoP（Demonstrating Proof of Possession）让客户端为每个请求生成一个短期 proof JWT，服务器把 access token 绑定到客户端公钥：

```http
Authorization: DPoP eyJhbGciOi...
DPoP: eyJ0eXAiOiJkcG9wK2p3dCIsImFsZyI6IkVTMjU2IiwiandrIj...
```

Proof 的关键 claim：

- `htm`：HTTP 方法；
- `htu`：目标 URI（不含 query 与 fragment）；
- `iat`：签发时间；
- `jti`：唯一 ID，用于重放缓存；
- `ath`：access token 的哈希（绑定到具体令牌）；
- 头部 `typ=dpop+jwt`，并携带客户端公钥 `jwk`。

服务器检查：

1. proof 签名有效；
2. `htm`/`htu` 与当前请求一致；
3. `iat` 在时间窗内；
4. `jti` 未重放；
5. `ath` 与 access token 匹配；
6. access token 的 `cnf.jkt` 与 proof 公钥指纹一致。

DPoP 降低了令牌泄露后的可用性，但不防止恶意客户端在合法会话内滥用权限；授权与审计仍然必要。

### mTLS 绑定令牌（RFC 8705）

令牌可以绑定到客户端证书：

```json
{
  "cnf": { "x5t#S256": "base64url-sha256-of-cert" }
}
```

验证方必须拿到**真实**的客户端证书指纹。如果 mTLS 在网关终止，后端只看到普通请求，就必须由网关把证书指纹以受信任的方式传下来；否则绑定形同虚设。

### Agent 与委托链

当 Agent 代表用户调用 API 时，令牌要能回答：

- 最终用户是谁？
- 哪个 Agent/客户端在代表他？
- 授权范围是什么？
- 用户是否明确确认了这次操作？
- 出了事如何追溯到具体委托？

常见做法：

- 使用 token exchange 换取受众窄、scope 小的令牌；
- 在令牌中加入 `act`（actor）或等价声明，表达“谁代表谁”；
- 高风险操作要求用户在场确认（step-up）；
- 不把用户的长生命周期令牌直接交给 Agent；
- 对 Agent 的每次工具调用记录委托链与决策依据。

## AD.5 密钥生命周期：比算法更容易出错

### 密钥层级

一个可运维的系统通常至少有：

```text
根密钥/信任根（离线或 HSM）
  └── KEK（密钥加密密钥，KMS/HSM）
        └── DEK（数据加密密钥，信封加密）
签名密钥（按用途、环境、租户隔离）
令牌签名密钥（JWKS，可轮换）
Webhook/合作伙伴密钥（按订阅或租户隔离）
```

原则：

- 用途分离：签名密钥不用于加密，测试密钥不用于生产；
- 环境分离：开发、预发、生产不共享密钥；
- 租户隔离：高价值租户或合作伙伴使用独立密钥；
- 最小权限：服务只能读取自己需要的密钥；
- 审计：每次使用、轮换、导出都有记录；
- 备份与恢复：密钥丢失等于数据丢失，必须有受控备份。

### 轮换

轮换不是“换一个字符串”，而是一个窗口：

1. 生成新密钥，发布公钥/新 `kid`；
2. 新旧密钥同时可用，新签名使用新密钥；
3. 验证方缓存新公钥，旧密钥只验不签；
4. 观察旧密钥使用量降为零；
5. 吊销旧密钥，清理缓存；
6. 记录演练与回滚路径。

对 HMAC，双方必须同时支持新旧密钥；对非对称，公钥可以提前发布，轮换更容易。紧急轮换（密钥泄露）需要：

- 立即吊销泄露密钥；
- 评估泄露时间窗内的所有请求；
- 强制相关令牌/会话失效；
- 通知受影响方；
- 复盘并修复泄露根因。

### 密钥管理的反模式

- 密钥写在代码、镜像、Helm values、CI 日志里；
- 所有租户共享一个 Webhook 密钥；
- 没有 `kid`，无法平滑轮换；
- 公钥缓存时间过长，吊销后仍然可用；
- 用环境变量传递长期云凭证，而不是工作负载身份；
- 没有密钥清单，不知道哪里还在用旧算法；
- 把“加密”与“编码”混淆（Base64 不是加密）；
- 自研密钥派生/签名方案。

## AD.6 后量子迁移：为什么 API 设计现在就要预留位置

### 威胁不是“明天量子计算机破解 RSA”

现实威胁是 **harvest now, decrypt later**：攻击者今天记录加密流量或签名数据，等未来量子计算机可用后再解密/伪造。对以下数据，时间窗尤其危险：

- 长期合同、医疗记录、身份档案；
- 支付与金融历史；
- 代码签名与固件更新；
- 长期存档的审计日志；
- 有十年以上生命周期的 IoT/工业设备。

即使量子计算机还没有到来，迁移本身也需要多年：盘点算法、升级库、换证书、改协议、更新 SDK、迁移密钥、验证互操作。**等到“确认威胁”再开始，通常已经太晚。**

### 哪些算法会受影响

| 类型 | 受影响 | 原因 |
|---|---|---|
| 密钥交换 | RSA、DH、ECDH | Shor 算法可解离散对数/大数分解 |
| 数字签名 | RSA、ECDSA、EdDSA | Shor 算法可伪造签名 |
| 对称加密 | AES-128 风险上升，AES-256 仍可用 | Grover 将暴力搜索平方根 |
| 哈希 | SHA-256 风险上升，SHA-384/512 更稳 | Grover 影响碰撞/原像安全边际 |
| HMAC | 不直接被 Shor 破解 | 但密钥长度与哈希强度要重新评估 |

一个常见误解是“换成 ML-KEM 就万事大吉”。ML-KEM 只解决**密钥封装**；签名需要 ML-DSA 或 SLH-DSA；证书、JWT、代码签名、Webhook 非对称签名各自需要迁移。

### NIST 标准与迁移时间线

2024 年 8 月，NIST 发布了首批后量子标准：

- **FIPS 203（ML-KEM）**：基于格的密钥封装，替代 RSA/ECDH 密钥交换；
- **FIPS 204（ML-DSA）**：基于格的数字签名，替代 RSA/ECDSA/EdDSA；
- **FIPS 205（SLH-DSA）**：基于哈希的签名，保守但签名大、速度慢；
- **HQC**：2025 年选出的额外基于码的 KEM，作为 ML-KEM 的多样化备份。

迁移时间线因地区和行业而异，下面是**规划假设**，不是法律承诺：

| 来源 | 目标（以官方最新文本为准） | 对 API 的含义 |
|---|---|---|
| NIST IR 8547（迁移草案） | 2030 年前弃用 RSA/ECC，2035 年后禁止 | 公开 API 与证书链要在此之前完成迁移 |
| NSA CNSA 2.0 | 国家安全系统优先采用 PQC，2030 年代全面过渡 | 高安全行业会先要求 PQC 套件 |
| 英国 NCSC | 2028 年规划、2031 年优先迁移、2035 年完成 | 关键基础设施与长周期系统提前 |
| 欧盟 NIS2 / DORA | 要求加密风险管理与韧性，未统一规定 PQC 日期 | 金融与关键实体需证明“密码敏捷” |
| PCI DSS | 要求强加密，尚未单独规定 PQC | 支付生态会跟随浏览器/卡组织时间表 |

### 混合模式：现在最现实的路径

在 PQC 完全成熟前，主流做法是**混合**：

- TLS 密钥交换同时使用 X25519 与 ML-KEM-768（如 `X25519MLKEM768`）；
- 即使其中一个算法被攻破，另一个仍然提供保护；
- 证书签名可以逐步从 RSA/ECDSA 过渡到 ML-DSA，或使用双证书/双签名；
- 客户端与服务端都要支持算法协商与回退。

混合模式的代价：

- 握手包更大（ML-KEM-768 公钥约 1.2 KB，密文约 1.1 KB）；
- 证书链更长，可能超过初始拥塞窗口，增加往返；
- 老客户端/老网关可能不支持，需要能力探测与回退；
- 性能与兼容性测试矩阵扩大。

### API 契约需要预留什么

后量子迁移不只是运维任务，它会改变契约：

1. **算法标识**：JWT 的 `alg`、Webhook 的签名算法、TLS 套件都要可配置、可协商、可拒绝。
2. **密钥 ID 与版本**：`kid`、证书指纹、密钥版本要能表达“同一身份的多把密钥”。
3. **双签名窗口**：迁移期允许旧签名与新签名并存，接收方按策略接受。
4. **大小限制**：更大的令牌、证书、签名可能触发头部/请求体/WAF 限制，要提前压测。
5. **错误语义**：客户端不支持新算法时，返回可操作的错误（例如 `unsupported_signature_algorithm`），而不是笼统 400。
6. **文档与 SDK**：SDK 要暴露算法配置、密钥轮换、重试与降级；文档要写清支持矩阵。
7. **审计与证据**：记录每次签名使用的算法与密钥 ID，便于迁移审计与事件调查。

### 迁移 playbook

```text
1. 盘点（CBOM）
   列出所有 TLS、证书、JWT、Webhook、代码签名、KMS、SDK 使用的算法与密钥。
2. 分类
   按数据寿命、暴露面、合规要求、供应商依赖排序。
3. 定义目标
   哪些链路先上混合 TLS？哪些签名先上 ML-DSA？哪些保持 HMAC？
4. 试点
   在非关键路径测量握手大小、CPU、延迟、失败率、客户端兼容性。
5. 双栈
   同时支持经典与 PQC，按客户端能力协商；保留回退。
6. 更新契约
   增加算法协商、密钥 ID、错误码、文档与 SDK 配置。
7. 淘汰经典
   监控旧算法使用量，设置弃用日期，强制迁移。
8. 演练
   模拟密钥泄露、算法禁用、证书链过大、老客户端失败。
```

### 后量子迁移的反模式

- 把“PQC”等同于“换一个 TLS 套件”，忽略签名与证书；
- 直接禁用 RSA/ECC，导致老客户端全部失败；
- 没有 CBOM/密钥清单，不知道影响面；
- 把算法硬编码在 SDK 或契约里，无法协商；
- 只测试新客户端，不测试老客户端与中间设备；
- 忽略更大的令牌/证书对网关、WAF、日志的影响；
- 认为 HMAC 可以替代密钥交换；
- 等到量子威胁“确认”才开始盘点。

## AD.7 密码学设计检查清单

### 传输

- [ ] 只启用 TLS 1.2+，优先 TLS 1.3；弱套件已禁用。
- [ ] 证书自动轮换、到期告警、吊销路径可用。
- [ ] 0-RTT 只用于安全/幂等请求，或有重放防护。
- [ ] 网关到源站仍然加密；内部头不可被外部伪造。
- [ ] mTLS 身份能映射到租户/服务，并有轮换与吊销演练。

### 消息签名

- [ ] 明确哪些场景需要消息签名，而不是只靠 TLS。
- [ ] 签名覆盖方法、目标 URI、关键头部、body digest、时间戳。
- [ ] 对原始字节或标准规范化结果签名，不签“解析后再序列化”的对象。
- [ ] 有 `keyid`、算法允许列表、时间窗、重放缓存。
- [ ] 先验签，再执行副作用。
- [ ] Webhook 使用标准格式（如 Standard Webhooks / RFC 9421），并有密钥轮换。

### 令牌

- [ ] JWT 校验覆盖 `alg`、`kid`、`iss`、`aud`、`exp`、`nbf`、`typ`。
- [ ] 不接受 `none`、未知 `crit`、外部 `jku`/`x5u`。
- [ ] Access Token 短生命周期；Refresh Token 旋转并检测重用。
- [ ] 高价值 API 使用 DPoP 或 mTLS 绑定，而不是纯 Bearer。
- [ ] Agent/委托场景有 `act` 链、窄 scope 与用户确认。

### 密钥

- [ ] 有密钥清单：用途、算法、长度、位置、owner、轮换周期。
- [ ] 签名/加密/派生密钥分离；环境与租户隔离。
- [ ] 密钥在 KMS/HSM 或受控 secret 管理中，不在代码/日志/URL。
- [ ] 轮换有双密钥窗口、监控与回滚。
- [ ] 有泄露响应 runbook 与演练。

### 后量子

- [ ] 有 CBOM/算法清单，覆盖 TLS、证书、JWT、Webhook、代码签名、SDK。
- [ ] 已按数据寿命与合规要求排序迁移优先级。
- [ ] 至少在高风险链路试点混合密钥交换。
- [ ] 契约支持算法协商、密钥 ID、双签名窗口与可操作错误。
- [ ] 测试矩阵覆盖新老客户端、网关、WAF、日志大小与性能。
- [ ] 有经典算法弃用时间表与回退方案。

## AD.8 小结

- 传输安全、消息签名、令牌约束、密钥管理是四层不同的信任机制，不能互相替代。
- 签名的难点不是算法，而是“签哪些字节、如何规范化、如何轮换、如何防重放”。
- JWT 的安全性取决于严格校验，而不是“用了 JWT”。
- DPoP/mTLS 绑定能降低令牌盗用风险，但不能替代授权与审计。
- 后量子迁移是多年的工程计划，不是换一个库；混合模式与密码敏捷是现实路径。
- API 契约要提前为算法协商、密钥 ID、双签名和更大的签名/证书留出空间。
