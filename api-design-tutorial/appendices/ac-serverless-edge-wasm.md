# 附录 AC：Serverless、边缘与 WebAssembly 运行时的 API 设计

> 第 27 章讨论了网关与边缘，第 33 章讨论了性能与容量，第 44 章讨论了平台工程。本附录聚焦一个更具体的问题：当 API 运行在 FaaS、边缘函数或 WebAssembly 沙箱里时，运行时的硬约束会直接改写契约。超时、包大小、冷启动、并发模型、状态生命周期、供应商锁定，这些不是“部署细节”，而是调用方可以观察到的 API 行为。

## AC.1 运行时约束会变成契约约束

同一个 HTTP 接口，跑在常驻容器和跑在 FaaS 上，契约可能完全不同：

| 约束 | 常驻容器 | FaaS/边缘 |
|---|---|---|
| 最长执行时间 | 自行控制 | 平台硬上限（秒到分钟） |
| 请求/响应体大小 | 受网关与内存限制 | 平台硬上限（KB 到 MB） |
| 并发模型 | 线程/协程池 | 每实例单并发或有限并发 |
| 冷启动 | 无 | 首次请求可能数百毫秒到数秒 |
| 本地状态 | 进程内可缓存 | 实例可能随时回收 |
| 连接池 | 长连接复用 | 实例间难以共享 |
| 后台任务 | 可常驻 | 请求结束后可能被冻结 |
| 流式响应 | 自由 | 受平台支持与缓冲策略限制 |

如果 API 文档写“同步返回结果”，但运行时 30 秒超时，而任务平均 45 秒，这份契约就是假的。**运行时的限制必须提前进入 API 设计，而不是上线后靠重试掩盖。**

## AC.2 FaaS 的请求/响应模型

### AC.2.1 同步调用

```text
客户端 → API Gateway → Function → 依赖 → 响应
```

约束：

- 网关与函数各有超时，取较小值；
- 请求体/响应体有上限；
- 函数冷启动计入端到端延迟；
- 函数并发受账户配额限制；
- 错误映射由网关与函数共同决定。

设计建议：

- 把同步接口控制在平台超时的 50% 以内；
- 大响应改用对象存储 + 预签名 URL；
- 大请求改用分片/预签名上传；
- 超时配置从外到内递减，并留缓冲；
- 返回 `Retry-After` 时考虑网关是否支持。

### AC.2.2 异步调用

```text
客户端 → 队列/事件源 → Function → 下游
                ↓ 失败
              DLQ/重试
```

异步调用通常至少一次投递：

- 事件可能重复；
- 顺序通常不保证（除非分区/FIFO）；
- 失败重试有次数与退避；
- 最终进入 DLQ；
- 调用方无法直接知道结果。

因此异步 API 必须提供：

- 操作资源/任务 ID；
- 状态查询；
- 幂等键；
- 结果查询或回调；
- DLQ 处理与重放；
- 可观测性。

### AC.2.3 响应流式

部分平台支持流式响应（如 Lambda response streaming、边缘平台的 `ReadableStream`）。以边缘运行时为例：

```javascript
export default {
  async fetch(request, env) {
    const { readable, writable } = new TransformStream();
    streamModelOutput(writable);
    return new Response(readable, {
      headers: {
        "Content-Type": "text/event-stream",
        "Cache-Control": "no-cache",
      },
    });
  },
};
```

注意：

- 流式响应可能绕过某些网关的缓冲/压缩；
- 错误可能发生在流开始之后，HTTP 状态码已经发出；
- 客户端必须能处理 `event: error`；
- 超时从请求开始计算，长流仍受平台限制；
- 连接断开要有取消信号，避免继续计费。

## AC.3 事件源与触发器

### AC.3.1 常见事件源

| 事件源 | 投递语义 | 顺序 | 典型问题 |
|---|---|---|---|
| HTTP 网关 | 同步 | 不适用 | 超时、payload 上限 |
| 队列（SQS） | 至少一次 | 标准队列无序 | 重复、可见性超时 |
| 流（Kinesis/Kafka） | 至少一次 | 分区内有序 | 分片吞吐、消费者 lag |
| 对象存储事件 | 至少一次 | 不保证 | 事件重复、丢失通知 |
| 数据库变更流 | 至少一次 | 按主键 | 重复、初始快照 |
| 定时器 | 至少一次 | 不适用 | 重叠执行、时区 |
| 消息总线 | 至少一次 | 视实现 | 路由、死信 |

### AC.3.2 事件处理的契约

```json
{
  "eventId": "evt_01J...",
  "eventType": "order.created",
  "occurredAt": "2026-11-26T10:00:00Z",
  "idempotencyKey": "order:ord_123:created",
  "attempt": 1,
  "data": { "orderId": "ord_123" }
}
```

处理函数应：

- 用 `eventId` 或业务唯一键去重；
- 去重记录与业务写入在同一事务；
- 区分可重试与不可重试错误；
- 不可重试错误直接进 DLQ，不要无限重试；
- 记录 `attempt`，但不要依赖它做业务判断；
- 处理超时要小于队列可见性超时。

### AC.3.3 定时任务

- 时区：按业务时区还是 UTC？
- 夏令时：每天 9 点还是每 24 小时？
- 重叠：上一次未完成时是否允许下一次？
- 失败：重试还是等下一次？
- 幂等：同一周期重复执行是否安全？
- 补跑：漏掉的周期如何补？

API 契约若暴露“每日结算”时间，必须说明时区与延迟容忍。

## AC.4 冷启动与延迟预算

### AC.4.1 冷启动的组成

```text
调度 → 拉取镜像/代码 → 启动运行时 → 初始化 SDK/连接 → 执行 handler
```

影响因素：

- 运行时（解释型 vs 编译型）；
- 包大小与依赖数量；
- 初始化逻辑（加载模型、建连接、读配置）；
- 网络（拉镜像、访问密钥服务）；
- 平台快照/预热能力；
- 并发突增。

### AC.4.2 延迟预算

```text
P95 目标 800ms
├── 冷启动 300ms（10% 请求）
├── 网关 30ms
├── 业务逻辑 150ms
├── 数据库 200ms
└── 序列化/网络 120ms
```

如果冷启动占 P95 预算的 40%，那么“平均延迟 200ms”没有意义。要分别监控：

- 冷启动比例；
- 冷启动初始化时长；
- 预热实例命中率；
- 突增时的冷启动排队；
- P99 端到端延迟。

### AC.4.3 缓解手段

- 预置并发/预留实例；
- 快照恢复（如 SnapStart 类能力）；
- 减小包体、延迟加载非关键依赖；
- 初始化阶段只做必要工作；
- 连接复用/代理；
- 定时预热（谨慎，可能浪费成本）；
- 把重初始化移到异步任务；
- 对延迟敏感的路由到常驻服务。

注意：预置并发有成本，且不保证容量；突增仍可能冷启动。API 的 SLO 要按“含冷启动”的真实分布制定。

## AC.5 状态、连接与事务

### AC.5.1 无状态不是“没有状态”

FaaS 实例可能被回收、复用、并发隔离。因此：

- 进程内缓存只能作为“可能命中”的优化，不能作为正确性依赖；
- 会话状态放外部存储（Redis/数据库）；
- 文件只写临时目录，且假定会被清理；
- 后台线程/定时器不可靠，请求结束可能被冻结；
- 全局变量可能跨请求复用，也可能不复用。

### AC.5.2 数据库连接

每个实例建连接会导致连接数爆炸：

```text
1000 并发实例 × 10 连接 = 10000 连接
```

措施：

- 连接代理（RDS Proxy 等）；
- 每实例限制连接数；
- 短事务；
- 只读副本分流；
- 连接超时与重试；
- 避免在 handler 外长期持有连接。

### AC.5.3 事务边界

FaaS 不改变事务语义，但会放大：

- 超时导致事务未提交；
- 重试导致重复事务；
- 跨函数调用无法共享事务；
- 事件发布与数据库写入需要 Outbox。

设计原则与第 10 章一致：幂等键、条件更新、Outbox、Saga。运行时只是让这些原则更重要。

## AC.6 边缘计算

### AC.6.1 边缘适合什么

- 认证令牌校验（JWKS 缓存）；
- 地理路由与 A/B 分流；
- 静态/半静态内容缓存；
- 请求/响应头改写；
- 简单重写与重定向；
- 限流（本地近似）；
- 小模型推理；
- 图片/视频转码的轻量部分；
- 边缘 KV 读取。

### AC.6.2 边缘不适合什么

- 复杂业务事务；
- 需要强一致的写；
- 大内存计算；
- 长时间任务；
- 需要完整数据库连接；
- 依赖大量原生库；
- 需要精确全局计数（边缘本地计数不一致）。

### AC.6.3 边缘的契约影响

```text
用户在 Tokyo → 边缘节点 → 本地缓存命中
用户在 Tokyo → 边缘节点 → 回源 Shanghai
```

API 需要说明：

- 哪些响应可缓存、缓存多久；
- 缓存键是否包含租户/语言/权限；
- 边缘认证失败时返回什么；
- 回源失败时的降级；
- 数据驻留（边缘节点可能在其他国家）；
- 日志与 Trace 是否在边缘采样；
- 配置变更的传播时间。

### AC.6.4 边缘状态

边缘 KV 通常最终一致：

- 写入后本地读可能看不到；
- 跨节点传播有延迟；
- 不适合做库存、余额、锁；
- 适合配置、灰度开关、静态映射；
- 需要版本号与过期时间。

如果业务要求“写入后立即全局可见”，边缘 KV 不是正确选择。

## AC.7 WebAssembly 插件与扩展 API

### AC.7.1 为什么用 WASM

- 沙箱隔离，比动态库安全；
- 跨语言（Rust/C/Go/AssemblyScript）；
- 启动快，适合按请求加载；
- 可限制 CPU/内存/系统调用；
- 插件与宿主解耦，便于第三方扩展。

典型场景：

- API 网关的自定义鉴权/限流/改写；
- 可观测性处理器；
- 数据转换；
- 多租户自定义逻辑；
- 边缘函数运行时。

### AC.7.2 插件契约

一个 WASM 插件 API 至少要定义：

```text
宿主 → 插件：
  - 请求头/方法/路径
  - 配置（JSON/字节）
  - 调用上下文（租户、trace_id）
插件 → 宿主：
  - 放行/拒绝
  - 修改后的请求
  - 自定义响应
  - 日志/指标
```

ABI 设计要点：

- 版本化 ABI，插件声明所需版本；
- 宿主函数（host functions）最小化；
- 能力授权（只能读请求头，不能读环境变量）；
- 内存限制与超时；
- 确定性：同一输入同一输出；
- 错误隔离：插件崩溃不能拖垮宿主；
- 资源计量：CPU、内存、调用次数；
- 插件签名与来源验证。

### AC.7.3 能力安全

```text
默认拒绝：
  - 无网络
  - 无文件系统
  - 无环境变量
  - 无时钟（或仅单调时钟）
按需授予：
  - 读取指定请求头
  - 写入日志
  - 调用指定宿主函数
```

不要因为“WASM 是沙箱”就默认安全。沙箱只限制能力，不阻止逻辑漏洞（如把敏感头写进日志）。

### AC.7.4 ABI 演进

- 新增宿主函数是兼容的；
- 删除/改签名是破坏性的；
- 插件要声明 `abi_version`；
- 宿主同时支持 N 和 N-1；
- 插件市场要标注兼容版本；
- 失败时回退到默认行为，而不是拒绝所有请求。

## AC.8 多租户与隔离

### AC.8.1 隔离级别

| 级别 | 实现 | 隔离 | 成本 |
|---|---|---|---|
| 每租户独立函数/实例 | 独立部署 | 强 | 高 |
| 共享函数 + 租户上下文 | 代码内隔离 | 中 | 低 |
| 共享实例 + 每请求沙箱 | WASM/进程 | 较强 | 中 |
| 完全共享 | 无隔离 | 弱 | 最低 |

选择取决于：

- 租户是否要求独立密钥/网络；
- 是否有合规隔离要求；
- 租户规模差异；
- 冷启动与成本；
- 故障爆炸半径。

### AC.8.2 噪声邻居

FaaS 的并发配额是账户级/区域级：

- 一个大租户的流量可能耗尽并发，导致其他租户 429；
- 预置并发可以隔离关键租户；
- 每租户限流与配额必须在网关/应用层做；
- 队列要按租户分区，避免一个租户的积压阻塞其他租户；
- 监控每租户的并发、错误率、延迟。

## AC.9 可观测性与调试

### AC.9.1 难点

- 实例短命，日志分散；
- 冷启动不在业务 Trace 内；
- 异步调用链路断裂；
- 本地难以复现平台行为；
- 边缘节点日志回传延迟；
- 采样可能错过冷启动。

### AC.9.2 必备指标

| 指标 | 用途 |
|---|---|
| invocation_count | 调用量 |
| error_rate | 错误率（区分 4xx/5xx/超时） |
| duration_p50/p95/p99 | 延迟分布 |
| cold_start_count / rate | 冷启动比例 |
| init_duration | 初始化耗时 |
| concurrent_executions | 并发使用 |
| throttles | 被限流次数 |
| queue_age | 异步积压 |
| dlq_size | 死信 |
| cost_per_invocation | 单次成本 |

### AC.9.3 Trace 传播

- 网关生成/透传 `traceparent`；
- 异步事件携带 trace 上下文；
- 冷启动初始化阶段也创建 span；
- 边缘节点采样后回传；
- 不要在日志中打印完整事件（可能含 PII）。

## AC.10 成本模型

### AC.10.1 计费维度

- 调用次数；
- 计算时长（GB-秒）；
- 预置并发/预留实例；
- 出口流量；
- 请求/响应流量；
- 存储与 API 调用（KV、对象存储）；
- 日志与 Trace 存储；
- 第三方依赖。

### AC.10.2 每请求成本

```text
单次成本 =
  (执行毫秒 / 1000) × 内存GB × GB-秒单价
  + 调用单价
  + 出口流量成本
  + 依赖成本
```

示例（仅示意）：

```text
256MB × 200ms = 0.05 GB-秒
假设 GB-秒单价 $0.0000166667 → $0.000000833
调用单价 $0.0000002
单次计算成本 ≈ $0.000001
1000 万次/月 ≈ $10
```

真正的大头常是：

- 出口流量；
- 日志；
- 数据库；
- 第三方 API；
- 预置并发闲置；
- 重试放大。

### AC.10.3 成本与架构

- 同步小请求适合 FaaS；
- 长任务用容器/批处理更便宜；
- 高频稳定流量用预留实例；
- 大量小文件用对象存储 + 批处理；
- 边缘计算减少回源，但边缘请求也有成本；
- 日志采样，避免“日志比计算贵”。

## AC.11 供应商锁定与可移植性

### AC.11.1 锁定来源

- 专有事件格式；
- 专有触发器/绑定；
- 专有身份与权限模型；
- 专有 KV/队列/数据库；
- 专有部署配置；
- 专有 SDK 中间件；
- 运行时 API（如 Workers 的 `env` 绑定）。

### AC.11.2 降低锁定

- 业务逻辑与运行时适配层分离；
- 事件用 CloudEvents 或自有标准信封；
- HTTP 接口保持标准；
- 配置外部化；
- 用容器作为可移植回退；
- 抽象存储/队列接口；
- 定期演练迁移；
- 在合同中约定退出条款。

完全避免锁定通常不经济。关键是评估“迁移成本”与“锁定带来的能力”是否匹配。

## AC.12 三个案例

### AC.12.1 图片处理 API

需求：上传图片，生成多尺寸缩略图。

同步方案的问题：

- 大图上传超过网关限制；
- 转码超过函数超时；
- 冷启动叠加转码延迟。

设计：

```text
POST /uploads → 预签名 URL
客户端直传对象存储
对象存储事件 → 队列 → 转码函数
转码结果写对象存储
更新操作资源状态
Webhook/轮询通知
```

契约要点：上传凭证 TTL、支持格式、最大尺寸、转码状态、结果 URL TTL、失败原因。

### AC.12.2 Webhook 接收端

需求：接收第三方 Webhook，写入内部系统。

FaaS 很适合，但要注意：

- 第三方重试导致重复；
- 签名验证需要原始请求体；
- 处理超时要快，重活转队列；
- 先持久化再处理，避免丢失；
- 返回 2xx 要谨慎，避免第三方停止重试；
- 失败要可重放。

```text
接收 → 验签 → 写原始事件表（幂等）→ 入队 → 200
异步 worker → 处理 → 更新状态
```

### AC.12.3 边缘鉴权

需求：在边缘校验 JWT，减少回源。

设计：

- 边缘缓存 JWKS，设置合理 TTL；
- 校验 `iss`、`aud`、`exp`、签名算法；
- 不在边缘做需要数据库的权限判断；
- 失败返回 401，并带 `WWW-Authenticate`；
- 回源时透传用户上下文（签名头）；
- 密钥轮换要能在 TTL 内生效；
- 边缘日志不记录令牌。

## AC.13 检查清单

- [ ] 同步接口的最坏执行时间小于平台超时，并留缓冲。
- [ ] 请求/响应体上限与平台限制匹配，大对象走对象存储。
- [ ] 异步接口有任务 ID、状态查询、幂等、DLQ 与重放。
- [ ] 冷启动计入 SLO，并分别监控冷启动比例与初始化耗时。
- [ ] 不在进程内保存正确性依赖的状态。
- [ ] 数据库连接有代理/上限，避免连接爆炸。
- [ ] 定时任务明确时区、重叠、补跑与幂等。
- [ ] 边缘缓存键包含租户/权限/语言，回源失败有降级。
- [ ] 边缘不承担强一致写与全局精确计数。
- [ ] WASM 插件有版本化 ABI、能力授权、资源限制与签名。
- [ ] 多租户有并发/队列隔离，监控噪声邻居。
- [ ] 可观测性覆盖冷启动、限流、队列年龄、DLQ 与单次成本。
- [ ] 评估供应商锁定与迁移成本，关键路径有可移植回退。

## AC.14 小结

- Serverless 的超时、包大小、并发、冷启动会直接改写 API 契约。
- 同步接口要留出平台超时缓冲；大对象与长任务走异步。
- 异步事件通常至少一次，必须幂等、去重、可重放。
- 冷启动要计入 SLO，不能只看平均值。
- FaaS 实例无状态，连接与事务要外部化。
- 边缘适合缓存、鉴权、路由与小计算，不适合强一致写。
- WASM 插件要用能力授权、版本化 ABI 与资源限制来治理。
- 成本与锁定是运行时选型的一部分，必须与架构一起评估。
