# 附录 V：API 计量、计费与收入工程

> 如果 API 契约回答“能做什么”，计量契约回答“做了什么、算多少、什么时候算、如何证明”。
> 很多 API 产品不是败在接口设计，而是败在账单：漏计、重计、迟到、口径不一致、无法解释、无法对账。

本附录讨论从一次调用到一张发票、再到收入确认的完整链路。它既是技术问题，也是财务与合同问题。文中的会计处理是工程视角的简化说明，不构成会计或法律意见；具体确认规则应以适用准则、审计师意见和合同条款为准。

---

## V.1 五个概念不要混

API 商业化最常见的错误，是把“用量”“计量”“计价”“账单”“收入确认”当成同一件事。它们其实是五个不同的系统，回答五个不同的问题。

| 概念 | 回答的问题 | 主要产物 | 典型负责人 |
|---|---|---|---|
| Usage（用量） | 发生了什么？ | 原始使用事件 | 工程 / 平台 |
| Metering（计量） | 如何把事件变成可计量的量？ | 计量事件、聚合用量 | 平台 / 数据 |
| Rating（计价） | 用量按什么规则变成金额？ | 计价明细 | 计费 / 财务 |
| Billing / Invoicing（账单） | 金额如何变成可支付的账单？ | 发票、账单明细 | 财务 / 计费 |
| Revenue recognition（收入确认） | 何时、多少计入收入？ | 收入分录、递延收入 | 财务 |

再加一个横向能力：

| 能力 | 回答的问题 | 产物 |
|---|---|---|
| Reconciliation（对账） | 前后是否一致？差异在哪里？ | 对账报告、差异单 |

五个概念混在一起，会出现典型症状：

- 用量 API 和账单对不上，客服无法解释；
- 重试被计费两次，但账单系统认为只调用了一次；
- 发票已经开出，迟到的事件只能偷偷改数；
- 收入按开票确认，但服务还没交付；
- 财务、产品、工程各自有一份“权威数字”。

**设计原则：原始事件不可变；计量可重放；计价可解释；发票不可变；收入按履约确认；对账可证明。**

## V.2 计量事件模型

计量事件是整条链路的“事实来源”。它应该像账本一样：只追加，不修改；可重放，可审计。

### V.2.1 一个最小但完整的计量事件

```json
{
  "eventId": "ue_01J8Z9K3Q7",
  "schemaVersion": "1.0",
  "tenantId": "t_123",
  "projectId": "proj_456",
  "environment": "production",
  "meter": "llm.output_tokens",
  "quantity": 350,
  "unit": "token",
  "occurredAt": "2026-11-26T10:00:00.123Z",
  "recordedAt": "2026-11-26T10:00:01.008Z",
  "source": "llm-gateway",
  "resource": {
    "type": "request",
    "id": "req_abc"
  },
  "idempotencyKey": "req_abc:llm.output_tokens",
  "attributes": {
    "model": "example-large-2026-10",
    "endpoint": "POST /v1/responses",
    "region": "ap-east-1",
    "apiKeyId": "key_789"
  },
  "tags": {
    "costCenter": "cc_42",
    "workload": "support-bot"
  }
}
```

字段设计要点：

- **`eventId`**：全局唯一，推荐 UUIDv7 或带时间前缀的 ULID，便于排序与排查。
- **`schemaVersion`**：事件结构会演进，必须能识别旧版本。
- **`tenantId` / `projectId`**：计费与隔离的最小维度。没有租户维度的事件，在共享平台上几乎无法正确出账。
- **`environment`**：生产、沙箱、测试必须可区分。沙箱是否计费要在契约中写清楚。
- **`meter`**：计量项名称，必须是稳定的业务语义，不是内部表名。
- **`quantity` / `unit`**：数量与单位必须成对出现。`350 token` 与 `350 requests` 是两件事。
- **`occurredAt` / `recordedAt`**：事件发生时间与系统接收时间。迟到、补录、重放都依赖这两个时间。
- **`source`**：事件由哪个组件产生。网关、业务服务、异步任务、模型供应商的计量点不同。
- **`resource`**：事件关联的业务对象，便于追溯与争议处理。
- **`idempotencyKey`**：去重键。它应来自业务操作，而不是随机生成，并且必须标识到“最小可计费单元”：流式/分块/批量请求要带 `chunkId`、`itemIndex` 或 `sequence`，或在请求完成时聚合成一条事件再按 `requestId + meter` 去重。只用 `requestId + meter` 会把同一请求的多个合法分块误判为重复。
- **`attributes`**：计价、分析、风控需要的维度。不要把高基数、敏感信息随意塞进去。
- **`tags`**：成本归因与运营维度，通常不参与计价。

本附录的事件字段是规范模型；教程中其他章节的简化示例（如第 15、41 章）应映射到 `occurredAt`/`recordedAt`、`unit` 与点分隔的 `meter` 命名。

### V.2.2 事件不可变与更正事件

计量事件一旦写入，不应更新或删除。发现错误时，写入一条**更正事件**：

```json
{
  "eventId": "ue_01J8ZA1B2C",
  "eventType": "correction",
  "correctsEventId": "ue_01J8Z9K3Q7",
  "tenantId": "t_123",
  "projectId": "proj_456",
  "environment": "production",
  "meter": "llm.output_tokens",
  "quantity": -50,
  "unit": "token",
  "idempotencyKey": "correction:ue_01J8ZA1B2C",
  "attributes": {
    "model": "example-large-2026-10",
    "region": "ap-east-1"
  },
  "reason": "provider_reported_usage_lower_than_gateway_estimate",
  "occurredAt": "2026-11-26T10:00:00.123Z",
  "recordedAt": "2026-11-27T02:15:00Z"
}
```

正确做法：

- 原始事件保留；
- 更正事件带 `correctsEventId` 与原因；
- 更正事件要么携带全部计价相关维度（`tenantId`、`projectId`、`environment`、`meter`、`attributes`），要么明确从 `correctsEventId` 继承；不能只带数量和币种；
- 更正事件有自己的 `idempotencyKey`，避免与原始事件或另一条更正冲突；
- 聚合时把正负数量一起计算；
- 如果已经开票，通过贷项通知单（credit note）或补充发票处理，而不是改历史发票。

### V.2.3 幂等：至少一次投递 + 幂等聚合

计量链路通常只能做到“至少一次”投递。不要追求理论上的 exactly-once，而应设计成：

```text
至少一次投递 + 按 idempotencyKey 去重 + 幂等聚合 = 事实上的 exactly-once
```

去重表的最小结构：

```sql
CREATE TABLE usage_dedupe (
  tenant_id       text        NOT NULL,
  idempotency_key text        NOT NULL,
  event_id        text        NOT NULL,
  first_seen_at   timestamptz NOT NULL,
  expires_at      timestamptz NOT NULL,
  PRIMARY KEY (tenant_id, idempotency_key)
);
```

注意：

- 去重键要带租户，避免跨租户撞键；
- 去重窗口要覆盖最大重试与补录周期；
- 去重表本身要能水平扩展；
- 去重与写入尽量在同一原子边界，或使用“先写事件、后聚合”的可重放设计；
- 不要用“查询是否已存在”再插入的竞态写法。

### V.2.4 事件时间、处理时间与迟到

计量里至少有三个时间：

- **事件时间**：业务实际发生的时间；
- **接收时间**：计量系统收到事件的时间；
- **处理时间**：聚合或计价任务处理它的时间。

三者不同会带来：

- 迟到的用量落在错误的账期；
- 重复处理导致重复计费；
- 补录事件无法归入原账期；
- 发票已经关账，事件才到。

处理策略：

1. **定义关账窗口**：例如账单周期结束后 3～5 个工作日为迟到事件窗口。
2. **允许补充发票**：关账后到达的用量进入下一期，或生成补充发票/贷项通知单。
3. **记录事件时间**：账单明细按事件时间归属，而不是按处理时间。
4. **估算与冲销**：关账时对已知迟到模式做估算，后续用实际数冲销。
5. **可重放**：聚合结果能从原始事件重建，避免“只改汇总表”。

### V.2.5 事件里不要放什么

- 完整请求体、响应体；
- 访问令牌、API Key、密码；
- 不必要的个人数据；
- 高基数且无业务意义的内部 ID；
- 会频繁变化的展示名称；
- 浮点数金额。金额字段统一用最小货币单位整数（如 `{ "amount": 11500, "currency": "USD" }`）；十进制字符串只用于展示字段，或用于小于最小货币单位的单价。

计量事件应尽量“薄”，但必须足以回答：谁、在什么环境、用了什么计量项、多少、何时、关联哪个业务对象。

## V.3 计量点设计

同一个 API 可以在多个位置计量。选择计量点，等于选择“相信谁的数字”。

### V.3.1 计量点对比

| 计量点 | 能看到什么 | 看不到什么 | 适合 |
|---|---|---|---|
| 边缘 / 网关 | 请求数、字节、状态码、延迟、API Key | 业务成功、实际资源消耗、异步完成 | 粗粒度调用量、流量、限流 |
| 业务服务 | 业务操作、成功/失败、资源 ID | 跨服务总成本、供应商真实用量 | 订单、支付、消息、任务 |
| 异步任务 | 任务完成、计算时长、输出大小 | 同步请求的即时成本 | 转码、导出、批处理 |
| 模型 / 第三方供应商 | 供应商口径的 token、字符、消息数 | 本地重试、缓存、内部调用 | LLM、短信、地图、支付 |
| 账本 / 快照 | 席位、存储量、设备数、库存 | 瞬时事件 | 订阅、存储、设备、座位 |

实践建议：

- **对外计费用业务服务或供应商口径**，不要只用网关请求数；
- **对内成本归因用网关 + 服务 + 基础设施指标**；
- **同一个计量项只选一个权威来源**，其他来源用于对账；
- **网关计量适合防滥用和粗粒度配额，不适合作为复杂业务的最终账单依据**。

### V.3.2 计量语义必须在契约里写清楚

以下问题没有写清楚，账单争议几乎必然发生：

- 请求开始时计数，还是成功完成后计数？
- 失败请求是否计费？
- 超时但后端实际完成的请求是否计费？
- 重试是否重复计费？
- 幂等重放是否计费？
- 缓存命中是否计费？按什么折扣？
- 用户取消的流式请求，已生成部分是否计费？
- 内部服务调用、健康检查、沙箱是否计费？
- 批量请求按批次还是按条计费？
- 部分成功如何计费？
- 免费额度按请求数还是按成本加权？
- 计量单位是否随实现变化而变化？

一个可用的写法：

```text
计费单位：成功完成的订单创建请求，每请求 1 单位。
失败请求、客户端取消、幂等重放不重复计费。
同一 Idempotency-Key 的重复请求只计一次。
沙箱环境默认不计费；如有例外（如高成本推理），在契约中明确列出。
计量以订单服务返回 201 为准；网关请求数仅用于限流。
```

### V.3.3 计量项命名

好的计量项名称应该让客户、支持、财务都能理解：

```text
api.requests
api.egress_bytes
orders.created
payments.captured_amount
messages.sms_segments
llm.input_tokens
llm.output_tokens
llm.cached_input_tokens
llm.reasoning_tokens
storage.gb_month
seats.active_day
devices.connected_month
```

不好的命名：

```text
svc_a_counter_3
db_rows_scanned
internal_rpc_calls
```

后者不是不能用于内部成本分析，但不适合直接作为客户账单单位。

### V.3.4 成本加权与原生单位

有些 API 的“一次请求”成本差异巨大：

- 文本摘要与长文档分析；
- 小图缩略图与 8K 视频转码；
- 国内短信与国际短信；
- 缓存命中与未命中；
- 轻量查询与全表扫描。

这时有两种选择：

1. **原生单位计量**：token、GB、分钟、像素、消息段。优点是透明、可解释；缺点是需要客户理解。
2. **成本加权单位**：1 次轻查询 = 1 unit，1 次重查询 = 20 units。优点是简单；缺点是权重可能被视为黑箱。

建议：

- 对外优先使用客户能理解的原生单位；
- 如果必须用加权单位，公开权重表和调整规则；
- 权重变更属于计费契约变更，要提前通知；
- 不要把内部 CPU 秒数直接卖给客户。

### V.3.5 维度与基数

常见维度：

- 租户、项目、环境；
- 用户、API Key、客户端；
- 端点、模型、区域；
- 套餐、合同、成本中心；
- 请求状态、错误码。

高基数维度（如请求 ID、完整 URL、用户邮箱）不适合直接做聚合标签，会导致存储与查询成本失控。把它们放在事件明细里，聚合时只保留必要维度。

## V.4 从事件到金额：Rating

Rating（计价）是把“用量”翻译成“金额”的规则引擎。它必须满足三个性质：

1. **确定性**：同样的用量、价格表、时间，必须得到同样的金额。
2. **可解释**：每一分钱都能追溯到计量项、价格规则和优惠。
3. **可重放**：价格表版本、汇率、税率、优惠都能还原。

### V.4.1 价格表模型

一个可用的价格表至少包含：

```json
{
  "priceBookId": "pb_2026_11",
  "currency": "USD",
  "effectiveFrom": "2026-11-01T00:00:00Z",
  "effectiveTo": null,
  "products": [
    {
      "productId": "llm_api",
      "meters": [
        {
          "meter": "llm.input_tokens",
          "aggregation": "sum",
          "unit": "token",
          "tierMode": "graduated",
          "fromInclusive": true,
          "toExclusive": true,
          "tiers": [
            { "from": 0, "to": 1000000, "unitPrice": "0.000003" },
            { "from": 1000000, "to": null, "unitPrice": "0.000002" }
          ],
          "includedQuantity": 0,
          "rounding": "per_invoice_line",
          "minimumCharge": { "amount": 0, "currency": "USD" }
        }
      ]
    }
  ]
}
```

关键字段：

- **`effectiveFrom` / `effectiveTo`**：价格生效区间。没有生效区间的价格表，无法处理历史重算。
- **`aggregation`**：`sum`、`max`、`unique`、`last`、`average`。不同聚合方式适合不同计量项。
- **`tierMode`**：`graduated`（分段累进）或 `volume`（整量统一）。没有这个字段，价格表无法唯一解释。
- **`fromInclusive` / `toExclusive`**：区间边界。默认建议 `from` 包含、`to` 不包含，避免 1,000,000 被计两次。
- **`tiers`**：阶梯价格。必须与 `tierMode` 一起解释。
- **`rounding`**：按事件、按日、按账单行、按发票舍入。舍入规则不同，金额会差几分钱。
- **`minimumCharge`**：最低消费，使用 Money 对象。
- **`includedQuantity`**：套餐包含量。
- **`commitment`**：承诺用量/最低消费，例如 `{ "amount": 120000, "currency": "USD", "period": "year" }`。
- **`discounts`**：折扣、优惠券、合作伙伴价。
- **`taxCategory`**：税分类。

### V.4.2 阶梯定价：分段累进 vs 整量统一

假设：

```text
0 - 1,000,000 tokens      $3 / 1M
1,000,000 以上            $2 / 1M
用量：1,500,000 tokens
```

**分段累进（graduated）**：

```text
前 1,000,000 × $3/1M = $3.00
后   500,000 × $2/1M = $1.00
合计 = $4.00
```

**整量统一（volume）**：

```text
1,500,000 × $2/1M = $3.00
```

两种算法都合法，但客户理解完全不同。价格页必须写清楚是哪一种，账单明细也要展示计算过程。

### V.4.3 套餐、包含量与超额

```text
Pro 套餐：$99/月，包含 1,000,000 次调用
超额：$0.00008/次
实际用量：1,200,000 次
```

账单：

```text
套餐费              $99.00
包含量              1,000,000
超额用量            200,000
超额单价            $0.00008
超额费              $16.00
合计                $115.00
```

必须明确：

- 包含量是否结转；
- 超额是按整量还是分段；
- 升级/降级时包含量如何按比例计算；
- 未使用部分是否退款；
- 超额是否自动升级套餐。

### V.4.4 承诺消费与最低消费

企业合同常见：

```text
年度承诺消费 $120,000
按月消耗，未用完不结转
超出部分按 $0.00006/次
```

工程上要区分：

- **承诺金额**：客户承诺支付的最低总额；
- **承诺用量**：客户承诺使用的最低数量；
- **预付费**：客户先付钱，形成余额；
- **后付费**：先用后付；
- **true-up**：期末补足承诺差额；
- **rollover**：未使用额度是否结转。

账单要能回答：

- 本月实际用量对应多少钱？
- 承诺还剩多少？
- 期末是否需要补收？
- 超额部分按什么价格？

### V.4.5 按比例计算（Proration）

月中升级：

```text
原套餐：$99/月，15 日升级
新套餐：$299/月
当月 30 天
```

常见算法：

```text
原套餐已用 14 天：$99 × 14/30 = $46.20
新套餐剩余 16 天：$299 × 16/30 = $159.47
当月合计：$205.67
```

需要明确：

- 按自然日还是按小时/秒；
- 升级立即生效还是下个周期；
- 降级是立即还是期末；
- 是否收取补差价；
- 是否退还已用部分的折扣；
- 时区与账单周期边界。

### V.4.6 折扣、优惠与 credits

折扣的叠加顺序会改变最终金额：

```text
原价
→ 合同折扣 10%
→ 促销折扣 5%
→ 优惠券 $20
→ credits 抵扣
→ 税
```

必须定义：

- 折扣是否可叠加；
- 折扣作用在用量费还是套餐费；
- 折扣是否影响税基；
- 优惠券是否有门槛、有效期、适用产品；
- credits 的购买、赠送、过期、退款规则；
- credits 是否可跨租户/跨产品使用；
- 退款时 credits 如何处理。

还要区分：

- **购买型 credits** 通常是预付款（支付后形成余额），税务处理与促销 credits 不同；
- **促销 credits/折扣** 通常作用在税前金额，但要看管辖区与合同；
- 多个百分比折扣是加法叠加（10% + 5% = 15%）还是乘法叠加（1 - 0.9 × 0.95 = 14.5%），必须在合同与账单中写清。

### V.4.7 币种、汇率与舍入

跨境 API 常见：

- 定价币种（USD）；
- 结算币种（EUR）；
- 支付币种（客户信用卡币种）；
- 展示币种（客户门户）。

必须明确：

- 汇率来源（央行、支付机构、内部财务）；
- 汇率日期（事件日、开票日、付款日）；
- 汇率精度；
- 舍入方向；
- 换汇手续费由谁承担；
- 发票币种与合同币种不一致时如何处理。

金额不要用浮点数。API 资源与事件统一用最小货币单位整数：

```json
{ "amount": 12900, "currency": "USD" }
```

十进制定点字符串（如 `"129.00"`）只用于：

- 人类可读的展示字段（如 `formattedAmount`）；
- 小于最小货币单位的单价（如每 token `"0.000003"`）；
- 发票 PDF/打印文本。

不要在同一个金额字段上混用整数与字符串。

### V.4.8 税

税的工程问题包括：

- 税号校验；
- 地址与管辖区；
- 数字服务税、增值税、销售税；
- B2B 反向征收；
- 免税证明；
- 税率版本与生效日期；
- 发票必须显示的字段；
- 红冲/贷项通知单的税务处理。

不要把税率硬编码在代码里。税率、规则、管辖区都应可配置、可审计、可按历史版本重放。

## V.5 账单与发票

发票是“金额的正式承诺”。它与计量事件不同：发票一旦开出，就不应被修改；更正通过贷项通知单、补充发票或重新开票完成。

### V.5.1 发票结构

```json
{
  "invoiceId": "inv_2026_11_00123",
  "tenantId": "t_123",
  "status": "FINALIZED",
  "currency": "USD",
  "period": {
    "from": "2026-11-01T00:00:00Z",
    "to": "2026-12-01T00:00:00Z"
  },
  "subtotal": 11500,
  "discountTotal": 500,
  "taxTotal": 920,
  "taxRate": "0.0836",
  "total": 11920,
  "amountDue": 11920,
  "dueDate": "2026-12-15",
  "lines": [
    {
      "lineId": "line_1",
      "description": "Pro plan",
      "meter": null,
      "quantity": 1,
      "unit": "month",
      "unitPrice": 9900,
      "amount": 9900,
      "servicePeriod": {
        "from": "2026-11-01",
        "to": "2026-12-01"
      }
    },
    {
      "lineId": "line_2",
      "description": "Overage: api.requests",
      "meter": "api.requests",
      "quantity": 200000,
      "unit": "request",
      "unitPrice": "0.00008",
      "amount": 1600,
      "priceBookId": "pb_2026_11",
      "usagePeriod": {
        "from": "2026-11-01",
        "to": "2026-12-01"
      }
    },
    {
      "lineId": "line_3",
      "description": "Contract discount",
      "amount": -500,
      "discount": true
    },
    {
      "lineId": "line_4",
      "description": "Tax (8.36%)",
      "amount": 920,
      "tax": true
    }
  ]
}
```

> 金额字段使用最小单位整数；`unitPrice` 只有在单价小于最小货币单位时才使用十进制字符串（如每 token `"0.00008"`）。折扣与税各占一行，这样“发票行 → 发票总额”的链路可验证：`9900 + 1600 - 500 + 920 = 11920`，税基为 `9900 + 1600 - 500 = 11000`，税率 8.36% 为示例假设。如需要人类可读文本，增加 `formattedAmount` 展示字段，而不是改变金额字段的类型。

发票必须能回答：

- 这是什么费用？
- 用量是多少？
- 单价是多少？
- 用了哪个价格表？
- 优惠是什么？
- 税是多少？
- 什么时候到期？
- 如何支付？
- 如何申诉？

### V.5.2 发票不可变

发票状态：

```text
DRAFT → FINALIZED → DUE → PAID
   │         │        ├→ OVERDUE → PAID
   │         │        └→ VOID（仅未支付且符合规则）
   │         └→ VOID
   └→ DISCARDED
```

规则：

- `DRAFT` 可以重算；
- `FINALIZED` 后金额、行项目不可改；
- 更正用 `CREDIT_NOTE` 或 `SUPPLEMENTAL_INVOICE`；
- `VOID` 只用于开票错误且未支付；
- 所有状态变更留审计；
- 发票编号连续、可验证；
- 发票 PDF/结构化数据长期保存。

### V.5.3 用量明细与账单解释

发票行通常是聚合结果。客户问“为什么这个月多了 30%”时，你需要能下钻：

```text
发票行 → 计量项 → 日/小时聚合 → 原始事件 → 请求 ID / 资源 ID
```

用量 API 的设计见 V.8。关键原则：

- 客户能看到与自己账单一致的聚合口径；
- 明细可分页、可导出、可签名；
- 聚合结果与原始事件可对账；
- 迟到事件与更正有标记；
- 不泄露其他租户数据。

### V.5.4 账单惊讶的预防

账单惊讶是 API 产品流失的高频原因。工程手段包括：

- **实时用量**：客户在调用后几分钟内看到用量；
- **预算与阈值告警**：50%、80%、100%、预测超额；
- **硬上限**：达到预算后拒绝或降级（需客户授权）；
- **用量预估**：根据当前速率预测月末；
- **异常检测**：用量突增、单 Key 异常、错误重试风暴；
- **明细解释**：每一行可追溯；
- **重试不计费**：或明确只计一次；
- **沙箱隔离**：默认不产生真实费用；如有例外，提前说明；计费沙箱的测试时钟、测试卡与账期推进见[附录 AJ](aj-sandbox-mock-test-data.md)；
- **变更通知**：价格、计量口径、折扣到期提前通知。

### V.5.5 催收、宽限与暂停

发票生命周期与服务生命周期是两个状态机，不要混在一张图里。

**发票**：

```text
DRAFT → FINALIZED → DUE → OVERDUE → PAID
                         └→ VOID（未支付且符合规则）
```

**服务**：

```text
ACTIVE → GRACE → SUSPENDED → TERMINATED
   ↑        │
   └────────┘（补款恢复）
```

需要定义：

- 到期日与账期；
- 宽限期；
- 暂停服务前通知；
- 暂停期间是否继续计量；
- 恢复条件；
- 终止后的数据保留与导出；
- 争议期间的暂停策略。

客户侧的订阅状态（`ACTIVE`/`PAST_DUE`/`PAUSED`/`CANCELED`/`EXPIRED`）见[第 41 章](../part-5-domain-playbooks/41-saas.md)；本附录的发票/服务状态只描述计费履约，不替代订阅状态。

## V.6 收入确认与财务对账

### V.6.1 为什么开票不等于收入

预付费年套餐：

```text
客户 1 月支付 $1,200，服务期 12 个月。
1 月开票 $1,200，但 1 月只交付了 1/12 的服务。
```

会计上通常不能把 $1,200 全部确认为 1 月收入，而是：

```text
1 月：确认收入 $100，剩余 $1,100 为递延收入/合同负债
2 月：确认收入 $100，剩余 $1,000
...
12 月：确认收入 $100，剩余 $0
```

按用量计费：

```text
11 月用量 1,000,000 次，单价 $0.0001，金额 $100。
服务已在 11 月交付，通常在 11 月确认收入（即使 12 月才开票）。
```

这时可能出现：

- **未开票收入**：服务已交付，但还没开票；可能记为合同资产或应收款，取决于是否已拥有无条件收款权，以会计政策为准；
- **递延收入 / 合同负债**：已开票/收款，但服务未交付；
- **应收账款**：已开票，未收款。

### V.6.2 收入确认的五个直觉问题

不需要成为会计师，但技术团队应能回答：

1. **合同中的履约义务是什么？** API 调用、支持、实施、培训是否可明确区分？
2. **交易价格是多少？** 固定费、用量费、折扣、退款、承诺消费如何组合？
3. **价格如何分摊到履约义务？** 套餐里 API、支持、存储各自值多少？
4. **何时确认？** 随时间（订阅）、随用量（按次）、还是某个时点（实施完成）？
5. **可变对价如何处理？** 超额、折扣、退款、SLA 赔偿如何估算与限制？

### V.6.3 典型分录（简化）

预付费年费：

```text
收款：
  借：银行存款            1,200
    贷：合同负债          1,200

每月确认：
  借：合同负债              100
    贷：收入                100
```

后付费用量：

```text
月末确认未开票收入：
  借：合同资产              100
    贷：收入                100

开票：
  借：应收账款              100
    贷：合同资产            100

收款：
  借：银行存款              100
    贷：应收账款            100
```

以上仅为工程沟通用的简化示例，实际科目、税额、确认时点以财务政策为准。

### V.6.4 对账链

一个可审计的 API 收入系统，应能沿这条链路逐步核对：

```text
原始计量事件
  → 去重后事件
  → 聚合用量
  → 计价明细
  → 发票行
  → 发票总额
  → 收款
  → 总账分录
  → 收入确认计划
```

每一层都要有：

- 数量总额（计价后还包括金额总额）；
- 时间范围；
- 租户/产品维度；
- 差异原因；
- 负责人；
- 证据链接。

对账不是“月底跑一次报表”，而是持续的控制活动。

### V.6.5 关账与迟到事件

关账流程：

```text
T+0  账单周期结束
T+1  冻结主要计量；生成预估
T+3  处理迟到事件；生成发票草稿
T+5  发票终审；发送客户
T+7  完成收入入账；关账（收入归属上一账单期，不是 T+7 当天）
```

关账后到达的事件：

- 进入下一期；
- 或生成补充发票；
- 或开贷项通知单；
- 记录差异与原因；
- 更新收入预估。

不要为了“数字好看”而修改历史事件或已开票发票。

## V.7 计量与计费系统架构

### V.7.1 参考架构

```text
API / Gateway / Service / Worker / Provider
        │
        ▼
  计量事件采集（SDK / sidecar / 日志 / webhook）
        │
        ▼
  事件总线（Kafka / Pulsar / Kinesis）
        │
        ├→ 校验与富化（schema、租户、价格维度）
        ├→ 去重（idempotency key）
        ├→ 原始事件存储（不可变、可重放）
        ▼
  聚合与计量（流式 + 批处理）
        │
        ▼
  计价引擎（价格表、折扣、承诺、税）
        │
        ▼
  发票引擎（账期、行项目、PDF、发送）
        │
        ▼
  总账 / 收入确认 / 对账
```

关键设计：

- **原始事件与聚合结果分开存储**：聚合可重建；
- **事件总线是缓冲，不是事实来源**：事实来源是不可变事件存储；
- **计价与采集解耦**：价格变化不应要求重新采集；
- **发票与计价解耦**：发票是快照；
- **所有组件幂等**：重放安全；
- **所有变更可审计**：价格、折扣、税率、额度调整。

### V.7.2 批处理、流处理与 Lambda 架构

| 方式 | 延迟 | 复杂度 | 适用 |
|---|---|---|---|
| 纯批处理 | 小时/天 | 低 | 账单周期、离线对账 |
| 纯流处理 | 秒/分钟 | 高 | 实时用量、预算告警 |
| 流批一体 | 秒/分钟 + 批 | 中高 | 大多数 API 计费 |
| Lambda（流+批） | 混合 | 高 | 已有两条链路的系统；必须严格对账 |

建议：

- 实时链路用于客户可见用量、预算告警、滥用检测；
- 批处理链路用于最终账单与对账；
- 两条链路使用同一套事件与计量定义；
- 定期对账两条链路的结果。

### V.7.3 数据模型

```sql
-- 原始事件（只追加）
usage_events (
  event_id, tenant_id, project_id, environment, meter,
  quantity, unit, occurred_at, recorded_at, source,
  resource_type, resource_id, idempotency_key,
  attributes jsonb, schema_version
)

-- 去重
usage_dedupe (tenant_id, idempotency_key, event_id, expires_at)

-- 聚合
usage_rollups (
  tenant_id, meter, period_start, period_end,
  dimension_hash, quantity, event_count
)

-- 价格
price_books (price_book_id, currency, effective_from, effective_to)
price_rules (price_book_id, meter, aggregation, tiers, rounding)

-- 发票
invoices (invoice_id, tenant_id, period, status, currency, totals)
invoice_lines (line_id, invoice_id, meter, quantity, unit_price, amount, price_book_id)

-- 贷项/调整
credit_notes (credit_note_id, invoice_id, amount, reason, status)

-- 总账
ledger_entries (entry_id, tenant_id, account, debit, credit, currency, posted_at, source)
```

### V.7.4 多租户与隔离

- 事件按租户分区，避免热点；
- 聚合键包含租户，防止跨租户串数据；
- 大租户单独分区/单独物化；
- 查询 API 强制租户过滤；
- 支持与财务跨租户访问需要理由与审计；
- 数据驻留要求可能要求区域化存储与计价。

### V.7.5 重放与回填

重放场景：

- 计价规则修复；
- 事件 schema 升级；
- 聚合逻辑变更；
- 数据丢失恢复；
- 历史账单重算（仅草稿）。

重放要求：

- 原始事件完整；
- 计价规则版本化；
- 重放任务有边界（租户、时间、计量项）；
- 重放结果与当前结果对比；
- 不直接影响已终态发票；
- 有审计与审批。

### V.7.6 监控与告警

关键指标：

- 事件摄入延迟；
- 事件重复率；
- 去重命中率；
- 聚合与原始事件差异；
- 计价失败率；
- 发票生成失败率；
- 账单与用量 API 差异；
- 未开票收入余额；
- 递延收入余额；
- 对账差异金额；
- 每租户用量异常。

告警要能回答：

- 是采集漏了，还是计价错了？
- 影响哪些租户、哪些账期？
- 是否需要停止开票？
- 是否需要通知财务/客户？


错误响应应包含：

- 哪个计量项/账期/发票；
- 当前状态；
- 可执行动作；
- 支持链接；
- 请求 ID。

### V.8.3 事件与 Webhook

```text
usage.threshold_reached
usage.anomaly_detected
invoice.finalized
invoice.paid
invoice.overdue
invoice.voided
invoice.credited
credit_note.issued
credit.applied
credit.expired
budget.exceeded
dispute.opened
dispute.resolved
```

Webhook 要求：

- 签名；
- 时间戳；
- 事件 ID 去重；
- 重试与死信；
- 顺序不保证；
- 客户可按事件类型订阅；
- 提供 replay/重放能力。

### V.8.4 版本化

计费契约的版本化比普通 API 更敏感：

- 计量项定义变化是破坏性变更；
- 价格表变化要带生效日期；
- 折扣规则变化要通知；
- 发票字段变化要兼容旧客户；
- 用量 API 的聚合口径变化要标注；
- 旧计量项下线要保留历史查询。

## V.9 十个真实失败模式

### V.9.1 重试导致重复计费

**失败链**：

```text
客户端超时 → 重试 → 网关计 2 次 → 服务实际成功 1 次 → 账单 2 次
```

**修复**：

- 计量以业务服务的幂等结果为准；
- 网关请求数只用于限流；
- 计量事件带 `Idempotency-Key`；
- 重试不重复计数；
- 账单明细可追溯到业务资源。

### V.9.2 迟到事件改历史发票

**失败链**：

```text
月末开票 → 3 天后供应商补报 token → 直接改发票 → 客户对账失败 → 审计问题
```

**修复**：

- 发票不可变；
- 迟到事件进入下一期或补充发票；
- 设置关账窗口；
- 对迟到模式做预估；
- 记录差异与原因。

### V.9.3 汇率日期不一致

**失败链**：

```text
定价 USD → 发票 EUR → 计价用开票日汇率 → 收款用付款日汇率 → 收入与现金差
```

**修复**：

- 明确汇率来源与日期；
- 记录汇率快照；
- 对账时区分收入、应收、现金；
- 换汇损益单独核算。

### V.9.4 Proration 算法错误

**失败链**：

```text
15 日升级 → 按整月收费 → 客户投诉 → 手工退款 → 账单口径混乱
```

**修复**：

- 明确按日/按秒；
- 升级/降级规则写进合同；
- 账单展示计算过程；
- 自动化测试覆盖月末、闰年、时区。

### V.9.5 Credits 未按顺序抵扣

**失败链**：

```text
赠送 credits 先过期 → 付费 credits 后过期 → 系统先扣付费 credits → 客户损失
```

**修复**：

- 明确抵扣顺序（先过期先扣、赠送先扣等）；
- credits 批次可追溯；
- 过期前通知；
- 退款时按批次处理。

### V.9.6 免费层被多账号滥用

**失败链**：

```text
免费额度 → 批量注册 → 成本失控 → 正常用户限流
```

**修复**：

- 身份与支付方式关联；
- 设备/IP/行为风控；
- 免费层成本预算；
- 滥用检测与封禁；
- 免费额度按成本加权。

### V.9.7 LLM token 口径不一致

**失败链**：

```text
本地 tokenizer 估算 1000 → 供应商计费 1200 → 客户账单高于预期 → 争议
```

**修复**：

- 以供应商返回的 usage 为准；
- 本地估算只用于预算；
- 账单展示供应商口径；
- 对差异做对账；
- 明确缓存 token、推理 token 的计费规则。

### V.9.8 发票行无法解释

**失败链**：

```text
账单多了 $500 → 支持查不到明细 → 工单升级 → 财务手工核对 → 客户流失
```

**修复**：

- 每行带计量项、数量、单价、价格表版本；
- 提供用量下钻 API；
- 支持按日/按 Key/按模型分组；
- 错误信息带文档链接。

### V.9.9 价格变更追溯生效

**失败链**：

```text
3 月改价 → 价格表生效日设为 1 月 → 历史账单重算 → 客户合同违约
```

**修复**：

- 价格表带生效日期；
- 历史价格不可变；
- 变更走审批与通知；
- 重算只影响草稿；
- 合同价单独管理。

### V.9.10 税额缺失

**失败链**：

```text
跨境数字服务 → 未收 VAT → 发票不合规 → 补税 + 罚款
```

**修复**：

- 税号与地址校验；
- 税率按管辖区配置；
- B2B 反向征收；
- 发票字段合规；
- 税务版本与历史重放。

## V.10 检查清单

### 计量

- [ ] 每个计量项有唯一、稳定的名称与单位。
- [ ] 计量语义写进客户契约：成功/失败、重试、取消、缓存、沙箱。
- [ ] 计量事件有唯一 ID、幂等键、租户、项目、环境、事件时间。
- [ ] 原始事件不可变，更正通过更正事件。
- [ ] 去重键带租户，去重窗口覆盖最大补录周期。
- [ ] 事件时间与处理时间分开，迟到事件有关账策略。
- [ ] 计量事件不含敏感数据与高基数无用字段。
- [ ] 聚合结果可从原始事件重建。

### 计价

- [ ] 价格表有生效区间与版本。
- [ ] 阶梯定价明确分段累进还是整量统一。
- [ ] 套餐包含量、超额、承诺消费、true-up 规则明确。
- [ ] Proration 规则覆盖升级、降级、月末、闰年、时区，并有可控测试时钟验证。
- [ ] 折扣叠加顺序、适用范围、有效期明确。
- [ ] Credits 的购买、赠送、过期、退款规则明确。
- [ ] 币种、汇率来源与日期、舍入规则明确。
- [ ] 税率、税号、反向征收、发票字段可配置。
- [ ] 计价确定性、可解释、可重放。

### 账单

- [ ] 发票终态不可变。
- [ ] 发票行可下钻到用量与原始事件。
- [ ] 发票包含价格表版本、期间、数量、单价、折扣、税。
- [ ] 支持贷项通知单、补充发票、争议流程。
- [ ] 账单惊讶有预算、告警、上限、预估、异常检测。
- [ ] 催收、宽限、暂停、终止流程明确。
- [ ] 发票 PDF/结构化数据长期保存。

### 收入与对账

- [ ] 区分开票、收款、收入确认。
- [ ] 预付费、后付费、承诺消费、超额的处理与财务对齐。
- [ ] 递延收入、未开票收入、应收账款可追踪。
- [ ] 对账链每一层有总额、差异、负责人、证据。
- [ ] 关账流程与迟到事件处理明确。
- [ ] 收入确认规则经过财务/审计确认。
- [ ] 重放与回填不影响已终态发票。

### API 与运维

- [ ] 用量、账单、预算、credits、争议 API 完整。
- [ ] 租户隔离与权限在授权层强制。
- [ ] 写操作幂等，查询最终一致有 `asOf`/`estimated`。
- [ ] Webhook 签名、去重、重试、重放。
- [ ] 计量链路有摄入延迟、重复率、差异、失败率监控。
- [ ] 计费契约变更走版本化、通知、迁移。

## 设计练习

为一个“多模型 LLM 网关”设计计量与计费系统：

- 输入 token、输出 token、缓存命中 token、推理 token；
- 不同模型不同单价；
- 免费层每月 100 万 token；
- Pro 套餐 $99/月含 1000 万 token；
- 企业合同有年度承诺消费与超额折扣；
- 支持预付费 credits 与后付费；
- 客户需要实时用量、预算告警、账单明细；
- 供应商账单可能迟到 48 小时。

## 小结

- 用量、计量、计价、账单、收入确认是五个不同系统；对账是贯穿它们的横向控制活动，不能混为一谈。
- 计量事件是不可变事实；更正用更正事件，不改历史。
- 至少一次投递 + 幂等去重 + 幂等聚合 = 事实上的 exactly-once。
- 计价必须确定性、可解释、可重放；价格表要版本化与生效区间。
- 发票终态不可变；更正用贷项通知单或补充发票。
- 开票不等于收入；收入按履约义务与交付进度确认。
- 对账链要能从原始事件走到总账，每一层有总额、差异与证据。
- 账单惊讶是留存杀手；预算、告警、上限、预估、明细缺一不可。
- 计量与计费 API 的租户隔离、幂等、审计、版本化要求高于普通业务 API。
