# 第 49 章 协议与架构的未来

## 49.1 判断趋势的标准

技术趋势很容易被夸大。判断一个协议或架构是否会长期留下，可以看四个信号：

1. **是否解决真实约束**：延迟、成本、安全、合规、协作。
2. **是否有互操作生态**：多实现、多语言、多供应商。
3. **是否被基础设施采纳**：代理、网关、云、CDN、可观测性。
4. **是否有迁移路径**：能与现有系统共存。

下面讨论的方向，按这四个标准评估，而不是按热度。

### 趋势判断的反面

- 只有 Demo，没有生产；
- 只有一个供应商；
- 没有调试工具；
- 迁移成本极高；
- 解决的是想象的问题。

## 49.2 HTTP 的演进

### HTTP/2 与 HTTP/3

- HTTP/2 已广泛部署，解决 HTTP/1.1 的队头阻塞（应用层），但仍有 TCP 层队头阻塞。
- HTTP/3 基于 QUIC/UDP，解决 TCP 队头阻塞，支持连接迁移、0-RTT/1-RTT，改善移动/弱网。
- 代价：UDP 可达性、代理支持、运维工具、CPU 成本。

对 API 的影响：

- 大量小请求更适合多路复用；
- 移动端/边缘场景受益；
- gRPC/WebTransport 依赖相应传输；
- 网关/CDN 需要支持。

### QUERY 方法

QUERY 用于“安全、幂等、可缓存，但需要请求体”的查询。它已于 **2026 年 6 月发布为 RFC 10008**（Proposed Standard），是自 PATCH 以来第一个新增的标准 HTTP 方法。

```http
QUERY /orders/search
Content-Type: application/json
Accept: application/json

{ "status": ["PAID"], "from": "2026-01-01" }
```

它解决：

- GET URL 过长、查询参数可能泄露敏感信息；
- 复杂查询放 body 但不想用 POST（POST 不保证安全/幂等/可缓存）；
- 缓存、重试与语义的一致性。

工程要点：

- 请求必须有 `Content-Type`，否则无法可靠解析；
- 响应可以通过 `Accept-Query` 声明支持的查询媒体类型；
- 可以用 `Location` / `Content-Location` 指向可 GET 的结果；
- 中间代理、网关、WAF、框架的支持仍在补齐，采用前要逐层验证；
- 不要把 QUERY 当成“所有复杂查询的默认答案”；如果查询本身有副作用，仍应使用 POST 或显式操作资源。

标准发布不等于生态立即就绪。生产采用要确认客户端库、CDN、负载均衡、可观测性与契约工具是否能正确处理新方法。

### 其他 HTTP 方向

- 更丰富的缓存指令；
- 结构化字段；
- 签名/来源验证；
- 早期提示；
- 压缩算法演进（zstd/br）；
- 隐私增强（如 Oblivious HTTP）。

## 49.3 RPC 与连接协议

### Connect

Connect 让同一套 Protobuf 服务同时支持：

- gRPC；
- gRPC-Web；
- HTTP/JSON。

它降低了浏览器/移动端接入 gRPC 的复杂度，适合内部服务 + 前端 BFF 的统一契约。

### gRPC

- 仍是内部服务的主流；
- 流式、强类型、代码生成；
- 与 HTTP/2/3 结合；
- 服务网格支持成熟。

### WebTransport

基于 HTTP/3 的多路复用流，适合：

- 实时协作；
- 游戏；
- 媒体；
- 低延迟双向通信。

生态仍在发展，需要回退方案。

### WebRTC

- 音视频与 P2P；
- 低延迟；
- 复杂信令与 NAT 穿透；
- 适合媒体，不适合普通 API。

## 49.4 事件与消息

- CloudEvents 继续作为事件信封标准；
- AsyncAPI 3 改进了通道/操作模型；
- Schema Registry 成为事件治理基础设施；
- Kafka 仍是大规模事件流主流；
- NATS/Pulsar/云消息服务在不同场景竞争；
- 事件网格（Event Mesh）连接多区域/多集群；
- 事件溯源与 CQRS 在特定领域成熟，但不是通用默认。

趋势：

- 事件契约化；
- schema 兼容性自动化；
- 事件目录与血缘；
- 端到端可观测性；
- 多租户事件隔离；
- 事件驱动 AI 工作流。

## 49.5 GraphQL

- Federation 继续在多团队聚合中应用；
- 持久化查询、复杂度限制、字段级授权成为生产标配；
- GraphQL over HTTP 标准化；
- 与 AI/Agent 的结合（按需字段、工具 schema）；
- 但 GraphQL 不会取代 REST/gRPC，仍是特定场景的工具。

## 49.6 契约描述

- **OpenAPI 3.2** 于 2025 年 9 月发布，向后兼容 3.1；新增流式媒体类型（SSE、JSONL、multipart/mixed）的 `itemSchema`、层级标签、`QUERY` 方法描述、`in: querystring` 参数、设备授权流程、`$self` 等能力。3.1 仍是大量工具的现实基线，但新项目应优先评估 3.2；
- OpenAPI 4.0（“Moonwalk”）仍在设计阶段，没有发布计划；不要把 4.0 当作可用目标；
- JSON Schema 2020-12 对齐；
- AsyncAPI 3.x 支持事件（3.0 是稳定基线，3.1 线已出现）；
- Protobuf 生态稳定；
- 契约注册中心、破坏性检测、代码生成成为平台能力；
- AI 辅助生成契约，但仍需人工评审；
- 契约将越来越多地包含“运行语义”（限流、幂等、SLO、成本）；
- MCP 工具描述与 A2A Agent Card 成为新的契约形态；
- MCP 2026-07-28 与 A2A 1.0 都强调版本协商、能力发现与机器可读的安全方案，这会把“发现入口”变成契约的一部分。

## 49.7 边缘与 WASM

边缘计算把逻辑下沉到离用户更近的节点：

- 认证；
- 个性化；
- A/B；
- 限流；
- 图像处理；
- 小模型推理。

WebAssembly（WASM）提供：

- 语言无关；
- 沙箱；
- 快速启动；
- 可移植。

挑战：

- 运行时限制；
- 调试；
- 状态；
- 供应商锁定；
- 冷启动；
- 安全；
- 生态碎片化。

工程细节（超时、包大小、冷启动、事件源、WASM 插件 ABI、成本）见[附录 AC](../appendices/ac-serverless-edge-wasm.md)。

## 49.8 架构趋势

### Cell-based Architecture

把系统划分为多个自包含的“单元”（cell），每个单元服务一部分租户/流量，故障隔离：

```text
Cell 1: 租户 A-D
Cell 2: 租户 E-H
Cell 3: 租户 I-L
```

优点：

- 爆炸半径小；
- 可独立扩展；
- 多区域；
- 渐进发布。

代价：

- 路由复杂；
- 数据迁移；
- 运维成本；
- 容量规划。

### 事件网格

跨区域/跨集群的事件路由与治理，支持：

- 事件目录；
- 过滤；
- 转换；
- 死信；
- 可观测性。

### 零信任与机密计算

- 每个请求认证/授权；
- mTLS/SPIFFE；
- 机密计算（TEE）保护运行时数据；
- 供应链签名；
- 策略即代码。

### 平台工程

- 内部开发者平台；
- 黄金路径；
- 自助服务；
- 策略即代码；
- 成本可见。

### 服务网格的演进

- Sidecar → Ambient；
- 更轻量；
- 与 eBPF 结合；
- 与网关融合；
- 多集群。

## 49.9 AI 对 API 设计的影响

- API 将被 Agent 消费，契约需要机器可读；
- 工具描述成为 API 文档的一部分；
- 错误信息影响 Agent 恢复；
- 权限需要更细；
- 评估与可观测性扩展到轨迹；
- API 发现/组合/市场；
- 自然语言接口与结构化接口并存；
- 设计辅助工具（生成、检查、模拟）增强，但架构判断仍由人负责。

### 不会被 AI 改变的东西

- 领域边界；
- 幂等；
- 错误语义；
- 版本与兼容；
- 安全；
- 可观测性；
- 成本；
- 人的信任。

AI 改变的是“如何表达和消费契约”，不是“契约为什么存在”。

## 49.10 技术采纳的节奏

知道一个方向“可能重要”和知道“现在该不该用”是两件事。技术采纳可以用一个简单的雷达：

| 象限 | 含义 | 行动 |
|---|---|---|
| Adopt | 已有多个生产案例与成熟工具 | 默认选型，进入标准架构 |
| Trial | 有真实价值，但生态仍在补齐 | 在非关键路径试点，设退出条件 |
| Assess | 值得跟踪，但证据不足 | 做原型与成本评估，不承诺 |
| Hold | 风险大于收益，或已被证伪 | 明确不采用，记录原因 |

一个技术从 Assess 进入 Adopt，通常需要同时满足：

- 至少两个独立实现，而不是只有一个供应商；
- 有可用的调试、测试与可观测工具；
- 有安全审查与漏洞响应机制；
- 有明确的版本与弃用政策；
- 在真实流量下有过公开或可验证的案例；
- 团队能在没有原厂驻场的情况下运维。

试点也要有纪律：

1. **绑定真实问题**：不要为了“支持新协议”而试点，要写清它解决哪个延迟、成本或协作问题；
2. **定义指标**：成功率、P95、成本、开发时间、故障恢复时间；
3. **时间盒**：例如 8 周，到期必须给出采用/放弃结论；
4. **回退路径**：网关转换、双写、特性开关，至少保留一条；
5. **所有权**：谁维护、谁 on-call、谁负责升级；
6. **退出成本**：数据能否导出、契约能否转换、客户端能否降级。

下表不是预测，而是“值得用雷达跟踪”的清单。每一项都应该用 49.1 的四个信号检验，而不是按热度下注。

## 49.11 被低估的标准与工具链

真正会长期影响 API 的，往往不是最热门的协议，而是那些“看起来很小、但被基础设施广泛采用”的规范。它们不改变 API 的风格，却改变 API 能否被安全地转发、签名、缓存、测试和治理。

### 49.11.1 结构化字段（Structured Fields）

RFC 8941（二进制）与 RFC 9651（日期类型等扩展）把 HTTP 头部值从“各写各的字符串”变成可解析的类型：

```http
Signature-Input: sig1=("@method" "@target-uri");created=1764200000;keyid="k1"
Cache-Status: "edge"; hit; ttl=300
```

收益：

- 代理、网关、可观测性工具可以可靠解析；
- 减少自定义头部的歧义；
- 为签名、缓存状态、限流参数提供统一语法；
- 跨语言库逐步成熟。

代价：

- 现有中间件不一定支持；
- 调试时需要理解类型语法；
- 不要为了“标准化”而重写所有自定义头。

### 49.11.2 消息签名与摘要（RFC 9421 / RFC 9530）

当 TLS 只保护链路时，RFC 9421 让发送方对方法、目标 URI、关键头部与 body 摘要签名；RFC 9530 定义 `Content-Digest` 字段。它适合：

- 跨组织、跨网关的请求完整性；
- Webhook 的非对称签名；
- 高价值操作的可审计证据；
- 经过会改写内容的代理链。

落地要点：

- 明确签名组件（`@method`、`@target-uri`、`content-digest` 等）；
- 使用 `created`/`expires`/`nonce` 防重放；
- `keyid` 支持轮换；算法用允许列表；
- 对原始字节或标准规范化结果签名；
- 中间件要能透传签名头，不能重写 body。

完整工程细节见[附录 AD](../appendices/ad-cryptography-pqc.md)。

### 49.11.3 规范化（JCS）

签名、幂等指纹、去重都要求“语义相同 → 字节相同”。JCS（RFC 8785）给出了 JSON 的规范化规则；CBOR 有确定性编码；Protobuf 的序列化字节通常**不是**规范化的。

设计含义：

- 不要把“解析后再序列化”的 JSON 当签名原文；
- 需要跨语言签名时，优先原始字节或标准规范化；
- 幂等指纹基于业务语义字段，而不是整个序列化字节；
- 规范化算法本身要版本化。

详见[附录 AE](../appendices/ae-serialization-schema-evolution.md)。

### 49.11.4 工作流描述（Arazzo）

OpenAPI 描述“单个操作”，但不描述“先创建订单、再支付、再轮询、再下载发票”这样的跨操作流程。Arazzo 1.x 用 YAML 描述 API 工作流：

```yaml
arazzo: 1.0.1
info:
  title: 下单并支付
  version: 1.0.0
sourceDescriptions:
  - name: orders
    url: ./openapi.yaml
    type: openapi
workflows:
  - workflowId: create-and-pay
    steps:
      - stepId: createOrder
        operationId: createOrder
        requestBody:
          payload:
            items: [{ sku: "SKU-1", quantity: 1 }]
        successCriteria:
          - condition: $statusCode == 201
      - stepId: pay
        operationId: createPayment
        requestBody:
          payload:
            orderId: $steps.createOrder.outputs.orderId
```

它适合：

- 文档中的端到端示例；
- 契约测试的流程编排；
- SDK/CLI 的工作流生成；
- Agent 工具链的多步任务描述。

但 Arazzo 不是运行时编排引擎，也不替代业务 Saga；它是**契约层的流程描述**。

### 49.11.5 Schema Registry 与契约注册中心

事件与数据 API 的演进，越来越依赖注册中心：

- 集中存放 schema 与版本；
- 兼容性模式（backward/forward/full/transitive）；
- CI 中做破坏性检测；
- 消费者按版本解析；
- 与数据目录/血缘关联。

它不是“多一个服务”，而是把“字段能不能删”从口头约定变成可执行门禁。

### 49.11.6 后量子密码

后量子迁移会同时影响 TLS、证书、JWT/JOSE、Webhook 签名、代码签名与 SDK。它不是某个协议的未来版本，而是整个密码学生命周期的迁移。API 设计要提前预留：

- 算法协商与允许列表；
- 密钥 ID 与双签名窗口；
- 更大的令牌/证书/签名对头部、WAF、日志的影响；
- 可操作的“不支持新算法”错误；
- CBOM 与迁移时间表。

详见[附录 AD](../appendices/ad-cryptography-pqc.md)。

### 49.11.7 工具链采纳建议

| 能力 | 现在（2026-11） | 建议 |
|---|---|---|
| 结构化字段 | 逐步采用 | 新自定义头优先用它；确认网关支持 |
| RFC 9421 签名 | 早期采用 | 跨组织/高风险场景试点；保留 HMAC 回退 |
| JCS/CBOR 确定性 | 成熟但工具不一 | 签名/指纹场景使用，做跨语言向量测试 |
| Arazzo | 早期 | 用于文档与契约测试，不用于运行时编排 |
| Schema Registry | 成熟 | 事件/数据平台默认；公开 API 可用契约注册中心 |
| 后量子混合 TLS | 试点 | 高风险/长周期系统先上；测量握手与兼容性 |
| OpenAPI 3.2 | 可用 | 新项目评估；工具链兼容性逐项验证 |
| OpenAPI 4.0 | 未发布 | 只跟踪，不用于生产 |

标准的价值不在于“新”，而在于它能否被网关、代理、WAF、可观测性、SDK 和 CI 同时理解。采用前逐层验证，采用后保留回退。

## 49.12 技术选型建议

- 不要为了新而新；
- 先解决真实问题；
- 评估生态与运维能力；
- 保留回退路径；
- 小范围试点；
- 度量收益；
- 避免供应商锁定；
- 关注总成本；
- 考虑团队能力；
- 考虑五年后的迁移。

## 49.13 本章小结

- HTTP/3、RFC 10008 QUERY、WebTransport、Connect 等演进改善延迟、语义与互操作。
- OpenAPI 3.2 已发布并兼容 3.1；4.0 仍在设计；AsyncAPI 与 CloudEvents 继续成熟。
- MCP 2026-07-28 走向无状态核心，A2A 1.0 支持多绑定与签名卡片；Agent 协议进入企业治理阶段。
- 边缘、WASM、cell 架构、零信任、平台工程改变系统形态。
- AI 让 API 的消费者与契约要求发生变化。
- 技术采纳要用雷达、试点门槛与退出路径管理，而不是追逐热度。
- 结构化字段、消息签名、JCS、Arazzo、Schema Registry 与后量子迁移，是容易被低估但会长期影响契约的标准与工具链。
- 协议会变，但领域、幂等、错误、版本、安全、可观测性和成本不会消失。
- 生成式接口与 BaaS 把契约下沉到数据库 schema 与策略，未来仍需要稳定视图与迁移路径，见[附录 AF](../appendices/af-database-as-api-baas.md)。
- 隐私正在从“合规附注”变成协议能力：预算、聚合阈值、认证与元数据保护，见[附录 AG](../appendices/ag-privacy-enhancing-tech.md)。
