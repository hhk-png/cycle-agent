# 第 48 章 AI 原生 API：当消费者不是人

## 48.1 “AI 原生”不是一个接口，而是一组假设

传统 API 假设：

- 调用方理解业务；
- 调用方会读文档；
- 调用方按固定流程调用；
- 调用方会处理边界；
- 调用方升级可控。

AI 原生 API 假设：

- 调用方是模型驱动的 Agent；
- 它会动态选择工具；
- 它按语义而非固定流程行动；
- 它会犯错、重试、组合；
- 它可能同时使用多个 API；
- 它的上下文有限；
- 它的行为需要评估与约束。

这改变了契约的设计重点。

### 两种消费者的契约重点

| 维度 | 人类开发者 | Agent |
|---|---|---|
| 发现 | 搜索、文档、示例 | 工具描述、能力目录 |
| 选择 | 阅读、比较 | 语义匹配 |
| 调用 | 固定流程 | 动态组合 |
| 错误 | 调试、查文档 | 依赖结构化错误 |
| 权限 | 账号 | 委托链 |
| 评估 | 测试 | 轨迹评估 |

## 48.2 从“端点”到“能力”

传统 API 以端点为中心：

```text
GET /orders/{id}
POST /orders/{id}/cancel
```

AI 原生 API 更应以“能力”为中心：

```text
能力：查询订单状态
输入：订单 ID
输出：状态、金额、可执行动作
约束：只能查自己的订单
成本：1 次调用
```

能力描述应机器可读：

```json
{
  "name": "get_order_status",
  "description": "查询订单当前状态。用户询问订单进度、是否发货、是否可以退款时使用。",
  "whenNotToUse": "不要用于创建订单或修改地址。",
  "inputSchema": { "type": "object", "properties": { "orderId": { "type": "string" } } },
  "outputSchema": { "type": "object", "properties": { "status": { "type": "string" } } },
  "sideEffects": "none",
  "idempotent": true,
  "auth": { "scopes": ["orders:read"] },
  "rateLimit": { "requestsPerMinute": 60 }
}
```

### 能力 vs 端点

- 端点：`POST /orders/{id}/cancel`；
- 能力：取消订单，需要订单 ID、原因，可能不可逆，需要权限，返回新状态。

Agent 需要的是能力语义，不是 URL。

## 48.3 机器可读的文档

人类文档是教程、指南、示例。机器文档是：

- OpenAPI/Proto/SDL；
- JSON Schema；
- 工具描述；
- 错误目录；
- 能力清单；
- 示例；
- 约束；
- 权限；
- 成本；
- SLA。

机器文档要：

- 结构稳定；
- 语义明确；
- 可解析；
- 有版本；
- 可验证；
- 不依赖隐含知识。

### 人类文档与机器文档的关系

```text
同一真相 → 生成人类文档 + 机器文档
```

不要让两者各自维护。

### 发现入口：从 llms.txt 到 Agent Card

Agent 需要知道“去哪里找契约”。常见的发现入口包括：

| 入口 | 面向 | 内容 |
|---|---|---|
| `llms.txt` | 通用 LLM 工具 | 文档结构、关键链接、使用建议 |
| OpenAPI | 传统 API 调用 | 端点、schema、示例、错误 |
| MCP Server | 工具型 Agent | 工具定义、资源、提示 |
| A2A Agent Card | Agent 协作 | 身份、技能、端点、安全方案 |
| API 目录/注册表 | 企业内部与市场 | 所有权、版本、SLA、价格、合规 |

这些入口不应各写一份。可靠的做法是维护一个“能力源”，再生成不同形态：

```text
能力与 schema 源
├── OpenAPI（REST）
├── MCP 工具定义
├── A2A Agent Card
├── llms.txt（文档导航）
└── 人类参考文档
```

`llms.txt` 不是 API 契约，它更像“给模型的 README”：告诉模型哪些文档重要、如何分块、哪些链接可抓取。它不能替代 OpenAPI，也不应包含无法验证的承诺。对 Agent 真正有用的是：稳定的 canonical URL、清晰的标题层级、可复制的示例、明确的版本与弃用说明。

## 48.4 语义契约

Agent 需要知道：

- 这个字段是什么意思；
- 这个状态意味着什么；
- 这个操作有什么副作用；
- 失败后应该做什么；
- 哪些操作不可逆；
- 哪些数据敏感；
- 哪些结果可信。

因此，语义契约比以往更重要。OpenAPI 的 `description` 不够；需要：

- 术语表；
- 状态机；
- 错误恢复指南；
- 示例；
- 不变量；
- 业务规则。

### 语义契约的机器表达

```json
{
  "stateMachine": {
    "states": ["PENDING_PAYMENT", "PAID", "SHIPPED", "CANCELLED"],
    "transitions": [
      { "from": "PENDING_PAYMENT", "action": "pay", "to": "PAID" },
      { "from": "PENDING_PAYMENT", "action": "cancel", "to": "CANCELLED" }
    ]
  },
  "invariants": [
    "已支付订单不能直接删除",
    "退款总额不能超过支付金额"
  ]
}
```

> 这里为了说明“机器可读的状态机”而做了简化；真实订单还有履约、退款、退货等状态维度，见[第 39 章](../part-5-domain-playbooks/39-ecommerce.md)的订单状态机。不要把这个四状态示例直接当成生产契约。

## 48.5 意图式接口

传统 API 要求调用方知道步骤：

```text
1. 创建订单
2. 预占库存
3. 发起支付
4. 确认
```

意图式接口允许调用方表达目标：

```json
{
  "intent": "book_trip",
  "constraints": {
    "destination": "Shanghai",
    "dates": ["2026-12-01", "2026-12-03"],
    "budget": { "amount": 5000, "currency": "CNY" }
  },
  "preferences": {
    "directFlight": true
  }
}
```

服务端负责规划、执行、补偿。

优点：

- 降低调用方认知负担；
- 适合 Agent；
- 可封装复杂流程。

缺点：

- 接口语义模糊；
- 难以测试；
- 失败恢复复杂；
- 权限与审计困难；
- 可能变成“万能接口”；
- 难以计费；
- 难以保证可解释性。

**建议**：意图式接口适合高层编排，底层仍应提供明确的能力 API。

### 意图式接口的设计

- 明确约束；
- 返回计划；
- 分步确认；
- 可取消；
- 可查询；
- 可审计；
- 失败可恢复；
- 成本可见。

## 48.6 动态组合

Agent 可能：

- 发现多个 API；
- 比较能力；
- 组合调用；
- 处理部分失败；
- 选择替代方案。

API 需要提供：

- 能力发现；
- 版本；
- 价格；
- 延迟；
- 可用性；
- 权限；
- 限制；
- 示例；
- 错误恢复。

这就是“API 市场”或“工具目录”的问题。

### 能力发现

```json
{
  "capabilities": [
    {
      "id": "order.query",
      "version": "1.2",
      "description": "查询订单",
      "regions": ["cn", "us"],
      "sla": "99.95%",
      "pricing": { "unit": "call", "price": 0.001, "currency": "USD" }
    }
  ]
}
```

## 48.7 信任、来源与可验证性

Agent 生成的内容可能：

- 幻觉；
- 引用错误；
- 使用过期数据；
- 被提示注入；
- 伪造来源。

API 应提供：

- 数据来源；
- 时间戳；
- 版本；
- 签名；
- 引用；
- 置信度（谨慎使用）；
- 可验证 ID；
- 审计。

```json
{
  "answer": "...",
  "sources": [
    {
      "id": "doc_123",
      "url": "...",
      "retrievedAt": "2026-11-26T10:00:00Z",
      "checksum": "sha256:..."
    }
  ],
  "model": { "id": "...", "version": "..." },
  "generatedAt": "..."
}
```

### 可验证性

- 内容哈希；
- 签名；
- 时间戳；
- 来源 URL；
- 版本；
- 审计日志。

## 48.8 Agent 商务

Agent 可能代表用户：

- 比较价格；
- 下单；
- 支付；
- 订阅；
- 退款。

需要：

- 用户授权；
- 预算；
- 确认；
- 支付令牌；
- 商家验证；
- 争议处理；
- 审计；
- 防止欺诈。

API 设计要区分：

- 浏览；
- 报价；
- 预留；
- 支付；
- 履约；
- 退款。

每个阶段有不同的权限与确认要求。

### 分阶段授权

```text
浏览 → 无需确认
报价 → 无需确认
预留 → 用户确认
支付 → 强确认 + 预算
退款 → 用户确认 + 审计
```

### 预算

```json
{
  "budget": {
    "amount": 50000,
    "currency": "CNY",
    "period": "month",
    "remaining": 32000
  }
}
```

### Agent 支付协议

当 Agent 真正开始“买东西”，支付协议会成为 API 契约的一部分。2025 年以来出现的方向大致分为三类：

1. **HTTP 402 + 支付证明**：服务端返回 402 与付款要求（金额、币种、收款地址、过期时间），客户端完成支付后携带支付证明重试。x402 是这一路线的代表，适合机器间微支付与按次调用。优点是贴近 HTTP 语义、无需账号；难点是合规、退款、汇率、争议处理与链上最终性。
2. **委托/授权链（mandate）**：用户先签署“意图委托”，Agent 在预算与条件下生成“购物车委托”，支付时验证委托链。AP2 等方案使用可验证凭证表达“谁授权谁买什么、上限多少、何时失效”。它更接近传统卡组织的授权模型，适合大额与可争议交易。
3. **平台内代理支付**：由电商平台或支付服务商提供 Agent 专用令牌，Agent 只能在平台内、限定商户与金额使用。它牺牲开放性，换取风控与责任边界清晰。

无论哪种协议，API 设计都要处理：

- **支付证明的验证**：签名、金额、币种、收款方、过期时间、一次性 nonce；
- **幂等**：同一支付证明只能使用一次，重试不能重复扣款；
- **预算与范围**：金额上限、商户白名单、时间窗口、用途；
- **用户确认**：超过阈值必须回到人类确认，确认记录要可审计；
- **退款与争议**：Agent 下单后谁负责、如何撤回、如何举证；
- **合规**：KYC/AML、消费者保护、税务、跨境资金流动；
- **最终性**：链上支付可能重组，不能把“已广播”当成“已结算”。

```http
HTTP/1.1 402 Payment Required
Content-Type: application/problem+json

{
  "type": "https://api.example.com/problems/payment-required",
  "title": "Payment required",
  "detail": "本次查询需要支付 0.002 USDC。",
  "payment": {
    "scheme": "x402",
    "amount": "0.002",
    "currency": "USDC",
    "payTo": "0x...",
    "expiresAt": "2026-11-26T10:05:00Z",
    "nonce": "pay_123"
  }
}
```

不要把 402 当成“免费额度用完”的通用错误。它应该只在“这次请求可以通过支付继续”时使用；普通配额耗尽仍应使用 429。

## 48.9 评估与可观测性

AI 原生 API 需要：

- 任务成功率；
- 工具选择正确率；
- 参数正确率；
- 恢复率；
- 人工介入率；
- 成本；
- 延迟；
- 安全事件；
- 轨迹回放。

评估集应覆盖：

- 正常；
- 边界；
- 对抗；
- 多语言；
- 长上下文；
- 工具失败；
- 权限拒绝。

## 48.10 设计原则

1. **机器可读优先**：契约、错误、能力、限制都可解析。
2. **语义明确**：字段、状态、副作用、恢复方式。
3. **最小权限**：Agent 不应拥有超过任务所需的权限。
4. **可确认**：高风险操作需要人类确认。
5. **可验证**：结果有 ID、来源、时间、签名。
6. **可恢复**：错误告诉 Agent 下一步。
7. **可审计**：记录谁、代表谁、做了什么。
8. **可评估**：有可重复的测试集。
9. **成本可见**：token、调用、副作用。
10. **人类兜底**：复杂/高风险场景可转人工。

## 48.11 风险

- 提示注入；
- 工具滥用；
- 数据外泄；
- 越权；
- 幻觉；
- 过度自动化；
- 责任归属；
- 监管；
- 供应商锁定；
- 成本失控；
- 可解释性不足；
- 评估偏差。

### 责任归属

当 Agent 做错事时：

- 谁负责？
- 用户、Agent 提供方、API 提供方？
- 合同如何约定？
- 审计是否足够？
- 能否回滚？

这些问题会逐渐进入 API 合同和监管要求。

### 监管与责任

AI 原生 API 至少会触及三类监管：

- **AI 系统监管**：欧盟 AI Act 按风险分级，对通用模型、透明度、高风险系统、风险评估与人类监督提出要求。你的 API 如果被客户用于高风险场景，合同里需要明确用途限制、评估责任与事件通知。
- **数据与隐私**：GDPR、PIPL、CCPA 等要求合法性基础、最小必要、可解释、可删除、跨境限制。Agent 的“记忆”、轨迹与工具结果都可能包含个人数据。
- **平台与消费者保护**：DSA/DMA、支付服务监管、自动决策与不公平商业行为规则。Agent 代用户下单、比价、订阅时，披露与撤销权不能因为“是机器做的”而消失。

API 合同应明确：

- 允许与禁止的用例；
- 谁负责模型输出、谁负责最终决策；
- 训练与改进是否使用客户数据；
- 事件通知时限与协作义务；
- 审计、解释与人工复核的可用性；
- 模型弃用、行为变更与迁移责任；
- 责任上限与保险。

监管不会等 API 设计完成。把合规字段、审计事件、用途限制和人工确认做进契约，比事后补一份政策文档更便宜。

## 48.12 本章小结

- AI 原生 API 的核心消费者是 Agent，契约要机器可读、语义明确、可恢复。
- 从端点思维转向能力思维。
- 意图式接口适合高层编排，底层仍需明确能力。
- 发现入口要统一：OpenAPI、llms.txt、MCP、Agent Card 应从同一能力源生成。
- 信任需要来源、版本、签名、引用和审计。
- Agent 商务需要分阶段授权、预算、支付证明验证与争议处理。
- 评估、可观测性、人类兜底是生产必备。
- 监管、责任与数据使用限制必须进入契约，而不是只写在政策页。
