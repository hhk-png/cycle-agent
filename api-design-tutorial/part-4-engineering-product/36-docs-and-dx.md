# 第 36 章 文档、示例与开发者体验

## 36.1 开发者体验是产品体验

开发者第一次接触你的 API，通常经历：

```text
搜索 → 官网 → 文档 → 注册 → 拿密钥 → 安装 SDK → 第一次调用
→ 处理错误 → 集成 → 上线 → 扩容 → 续费
```

每一步都有流失。开发者体验（DX）的目标是降低每一步的摩擦。

### 关键指标

- Time to First Call（TTFC）；
- Time to First Successful Integration；
- 文档搜索成功率；
- 沙箱使用率；
- 支持工单率；
- 首次调用错误率；
- 激活率；
- 留存率；
- 扩展收入。

### DX 的三个层次

```text
1. 能看懂：文档、示例、错误信息
2. 能跑通：认证、SDK、沙箱
3. 能上线：限流、SLA、支持、迁移
```

任何一层断裂，都会让开发者放弃。

## 36.2 文档的四种类型

### 1. 教程

面向学习，带步骤，有结果：

```text
30 分钟构建一个订单同步集成
```

特点：

- 从零开始；
- 有明确结果；
- 不解释所有细节；
- 引导下一步。

### 2. 操作指南

面向任务，解决具体问题：

```text
如何分页获取订单
如何处理 Webhook 重试
如何轮换 API Key
```

特点：

- 假设读者已有基础；
- 步骤清晰；
- 可复制；
- 解决一个问题。

### 3. 参考

面向查询，完整、精确：

```text
GET /orders/{orderId}
参数、响应、错误码
```

特点：

- 完整；
- 精确；
- 结构化；
- 可搜索；
- 与 schema 同步。

### 4. 概念

面向理解：

```text
订单状态机
幂等键如何工作
多租户模型
```

特点：

- 解释为什么；
- 建立心智模型；
- 连接多个端点；
- 减少误用。

四种文档服务不同需求，不能互相替代。

### 文档矩阵

| 类型 | 读者状态 | 目标 | 例子 |
|---|---|---|---|
| 教程 | 学习 | 学会 | 快速开始 |
| 指南 | 有目标 | 完成任务 | 分页、重试 |
| 参考 | 查询 | 查细节 | API 参考 |
| 概念 | 理解 | 建立模型 | 状态机 |

## 36.3 API 参考

应包含：

- 端点；
- 方法；
- 认证；
- 路径/查询/头参数；
- 请求体 schema；
- 响应 schema；
- 状态码；
- 错误码；
- 示例；
- 限流；
- 幂等；
- 弃用信息；
- 相关指南链接。

### 自动生成 vs 手写

- 从 OpenAPI 生成基础参考；
- 手写概念、指南、示例；
- 不要手写与 schema 重复的内容；
- 生成物要有搜索、导航、代码示例。

### 参考的质量标准

- 每个参数有类型、必填性、示例；
- 每个响应有示例；
- 每个错误有说明；
- 每个端点有认证要求；
- 每个端点有限流说明；
- 每个端点有幂等说明；
- 每个弃用有替代方案。

### Docs-as-code：让文档进入 CI

文档与 API 一样会漂移。把文档纳入 CI：

```yaml
name: docs
on: [pull_request]
jobs:
  docs:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Lint OpenAPI examples
        run: npx @redocly/cli lint openapi.yaml
      - name: Build docs
        run: npm run docs:build
      - name: Check links
        uses: lycheeverse/lychee-action@v2
        with:
          args: --no-progress 'docs/**/*.md'
      - name: Test code samples
        run: npm run docs:test-samples
      - name: Check generated reference is current
        run: git diff --exit-code -- docs/api-reference/
```

最低标准：

- OpenAPI 示例能被 schema 校验；
- 文档构建失败会阻断合并；
- 死链检查；
- 代码示例可执行（至少能编译/发请求到沙箱）；
- 生成的 API 参考与 schema 一致；
- 版本切换可用；
- 变更日志与弃用信息出现在文档中。

文档不是“写完就结束”，它需要和代码一样被构建、测试、发布、回滚。

## 36.4 示例

好的示例：

- 可运行；
- 使用真实但安全的数据；
- 覆盖成功与错误；
- 多语言；
- 有注释；
- 与 SDK 版本匹配；
- 可复制粘贴；
- 有输出。

坏的示例：

- 伪代码；
- 省略认证；
- 使用 `YOUR_API_KEY` 但不说明如何获取；
- 只展示 happy path；
- 与当前 API 不一致；
- 依赖未说明的环境。

### 示例的类型

- 快速开始；
- 端到端流程；
- 错误处理；
- 分页；
- Webhook；
- 异步任务；
- 流式；
- 批量。

## 36.5 快速开始

一个合格的快速开始：

1. 注册/获取测试密钥；
2. 安装 SDK；
3. 发一个请求；
4. 看到结果；
5. 处理一个错误；
6. 下一步链接。

目标：10 分钟内完成第一次成功调用。

### 快速开始的常见问题

- 注册后找不到密钥；
- 密钥权限不足；
- SDK 安装失败；
- 示例使用旧版本；
- 沙箱不可用；
- 错误信息不解释；
- 没有下一步。

## 36.6 沙箱

沙箱应：

- 与生产隔离；
- 使用测试密钥；
- 可重置数据；
- 模拟延迟/错误/限流；
- 支持 Webhook 测试；
- 有使用限制；
- 不产生真实费用；
- 与生产行为一致。

### 沙箱的测试场景

- 成功；
- 失败；
- 超时；
- 限流；
- 重复；
- 部分成功；
- 异步完成；
- 权限不足。

### 沙箱的保真度分级

沙箱不是二元的“有/没有”，而是有保真度阶梯：

| 等级 | 形态 | 适合 |
|---|---|---|
| L1 | 契约生成的静态 Mock | 前端并行开发 |
| L2 | 状态化 Mock | 消费者测试、状态机 |
| L3 | 隔离沙箱 | 真实联调、异步、Webhook |
| L4 | 影子/回放 | 高风险迁移 |
| L5 | 生产测试模式 | 支付、计费、清算 |

对外承诺的沙箱应优先使用与生产同源的实现，只隔离数据、密钥和外部依赖。独立手写的“演示沙箱”几乎一定会漂移。至少提供：测试密钥前缀、按租户隔离、重置/播种、可注入失败、Webhook 重放、测试时钟和投递日志。

### 沙箱是产品表面

沙箱的 TTFC、错误分布、支持工单和到生产的转化率，应该和文档、SDK 一起被度量。沙箱宕机不会立刻体现在生产错误率上，但会直接阻塞合作伙伴集成。沙箱的架构、隔离、安全与漂移检测，见[附录 AJ](../appendices/aj-sandbox-mock-test-data.md)。

## 36.7 错误信息与支持

错误信息是文档的一部分：

```json
{
  "code": "CARD_DECLINED",
  "message": "银行卡被拒绝",
  "detail": "发卡行返回 do_not_honor",
  "docsUrl": "https://docs.example.com/errors/card-declined",

}
```

支持渠道：

- 文档搜索；
- FAQ；
- 社区；
- 工单；
- 状态页；
- 邮件/Slack；
- 客户经理。

### 支持的分层

```text

社区：论坛、Slack、Stack Overflow
工单：技术支持
客户经理：商业客户
```

## 36.12 面向机器的文档

文档的第一读者仍然是人，但第二读者越来越常见：代码生成器、IDE、API Agent、MCP 客户端、内部 copilot。它们不会“浏览”你的门户，而是抓取、解析、嵌入、调用。

### 机器可读的入口

至少提供：

| 入口 | 用途 | 注意 |
|---|---|---|
| OpenAPI/AsyncAPI/Proto | 生成客户端、mock、测试 | 与实现同源，CI 校验 |
| JSON Schema | 参数/响应校验 | 版本化，带示例 |
| 错误目录（机器可读） | Agent 判断是否可重试 | 稳定错误码 + 修复建议 |
| `llms.txt` / `llms-full.txt` | 给 LLM 的站点摘要 | 不是标准，但要稳定、简洁 |
| MCP 工具描述 | Agent 发现与调用 | 描述、参数、权限、示例 |
| 示例集合 | few-shot/测试 | 可运行、可复制 |

`llms.txt` 不是正式标准，但它反映了一个真实需求：**让模型在有限上下文里快速找到“如何认证、如何调用、错误怎么处理、限制是什么”**。即使不提供这个文件，也应该把同样的信息组织成可抓取、可引用的页面。

### 为 Agent 写文档的原则

- **先结论，后背景**：Agent 需要“怎么调用”，不是品牌故事；
- **参数表要机器可读**：类型、必填、默认值、范围、示例；
- **错误要可操作**：`retryable`、`next_action`、文档链接；
- **限制要显式**：速率、分页上限、请求体上限、超时；
- **示例要完整**：认证 + 请求 + 响应 + 错误；
- **避免歧义**：同一概念只用一个词；
- **版本要标注**：Agent 可能抓到旧页面；
- **安全边界要写清**：哪些操作需要用户确认，哪些不可逆。

### 工具描述也是文档

MCP 工具或 Agent 工具的 `description`、参数 schema、示例，直接决定模型是否会正确调用。写得含糊，模型就会猜；猜错后，错误信息又决定它能否恢复。工具描述应包含：

```text
这个工具做什么、不做什么
何时使用、何时不要使用
参数含义与约束
返回值结构
可能的错误与恢复建议
权限/副作用/是否幂等
```

## 36.13 文档的测试、版本与供应链

### 文档也要进 CI

最容易腐烂的不是正文，而是示例与引用。至少做：

1. **代码示例可运行**：从文档中抽取代码块，在沙箱中执行；
2. **链接检查**：内部锚点、外部链接、版本切换；
3. **schema 校验**：示例请求/响应能通过 OpenAPI/JSON Schema；
4. **契约一致性**：文档字段与 OpenAPI 字段对拍；
5. **拼写与术语**：统一术语表，避免同一概念多套说法；
6. **截图/UI 测试**：门户改版后关键流程仍然可用；
7. **可访问性检查**：标题层级、对比度、键盘导航；
8. **本地化检查**：翻译缺失、日期/货币/术语不一致。

```yaml
# 概念示例：文档 CI
steps:
  - run: python tools/check_links.py docs/
  - run: python tools/extract_and_run_examples.py docs/
  - run: npx spectral lint openapi.yaml
  - run: python tools/check_docs_against_openapi.py docs/ openapi.yaml
  - run: python tools/check_i18n.py docs/
```

### 版本化文档

- 每个受支持的大版本保留独立文档；
- 默认展示最新稳定版，旧版本有醒目标识；
- 弃用页面有迁移指南与时间表；
- 旧 URL 做重定向，不要让外部链接腐烂；
- 搜索按版本过滤，避免用户复制到错误版本的示例；
- 变更日志与文档版本关联。

### 文档供应链

文档站点也是软件供应链的一部分：

- 静态站点生成器与主题依赖要锁定版本、扫描漏洞；
- 搜索索引、分析脚本、第三方嵌入要审查隐私与性能；
- 生成的 HTML 要防止 XSS（尤其是用户评论/示例）；
- 文档中的密钥、内部地址、客户数据要扫描；
- 发布产物要签名/校验，防止被篡改；
- 文档的构建权限与生产部署权限分离。

### 文档的度量

除了 TTFC，还可以看：

- 搜索无结果率；
- 页面跳出率与下一步点击；
- 文档到首次成功调用的转化；
- 支持工单中“文档缺失/错误”的比例；
- 示例复制率与运行成功率；
- 版本切换后的错误率；
- Agent 抓取时的 404/重定向比例。

## 36.14 反模式

- 文档与 API 不一致；
- 只有参考，没有指南；
- 示例不可运行；
- 认证说明缺失；
- 错误码无文档；
- 沙箱与生产行为不同；
- 变更日志缺失；
- 搜索差；
- 支持入口难找；
- 文档只有英文但客户在当地；
- 快速开始需要信用卡；
- 错误信息没有 requestId。

## 36.15 本章小结

- DX 是产品体验，影响激活、留存和扩展。
- 文档分为教程、指南、参考、概念四类。
- 参考可从契约生成，指南和示例应手写。
- 快速开始的目标是 10 分钟内成功调用。
- 沙箱、错误文档、变更日志、支持渠道缺一不可。
- 用指标和访谈持续改进 DX。
- 机器读者（代码生成器、Agent、IDE）需要机器可读的契约、错误与工具描述；`llms.txt` 只是入口之一。
- 文档要进 CI：示例可运行、链接有效、schema 对拍、可访问性与本地化检查。
- 文档也有版本与供应链：旧 URL 要重定向，依赖要锁定，敏感信息要扫描。
- 产品发现、路线图、DevRel 与增长方法，见[附录 W](../appendices/w-api-product-management.md)。
- 沙箱的保真度、隔离、测试时钟、Webhook 重放与漂移检测，见[附录 AJ](../appendices/aj-sandbox-mock-test-data.md)。
