# 第 38 章 发布、弃用与迁移

## 38.1 发布不是部署

部署是把代码放到服务器；发布是让消费者开始依赖新契约。

一次 API 发布应考虑：

- 契约是否变更？
- 是否兼容？
- 消费者是否需要行动？
- 文档/SDK 是否同步？
- 监控是否就绪？
- 回滚是否可行？
- 支持团队是否知情？
- 计费是否受影响？
- 法律/合规是否批准？

### 发布的风险

- 契约不兼容；
- 行为变化；
- 文档滞后；
- SDK 不同步；
- 监控缺失；
- 回滚失败；
- 支持不知情；
- 客户投诉。

## 38.2 发布类型

### 兼容性发布

- 新增可选字段；
- 新增端点；
- 性能优化；
- 文档修正。

通常不需要消费者行动，但仍需监控。

### 行为变更

- 默认值；
- 排序；
- 限流；
- 错误码；
- 一致性；
- 延迟；
- 分页大小。

即使语法兼容，也可能破坏消费者。

### 破坏性发布

- 删除字段；
- 改类型；
- 改认证；
- 改分页。

需要版本策略、迁移、弃用。

### 发布类型矩阵

| 类型 | 语法 | 行为 | 消费者行动 | 流程 |
|---|---|---|---|---|
| 兼容 | 兼容 | 兼容 | 无 | 正常发布 |
| 行为 | 兼容 | 变化 | 可能需要 | 通知 + 监控 |
| 破坏 | 不兼容 | 变化 | 必须 | 版本 + 弃用 |

### 发布节奏

- 固定节奏（如每周）降低协调成本；
- 紧急修复走独立通道；
- 大版本提前规划；
- 避免周五发布；
- 避开客户关键业务期；
- 发布窗口与支持团队对齐；
- 变更冻结期。

### 特性开关

```json
{
  "feature": "new-pricing",
  "enabled": false,
  "rollout": { "percentage": 10, "tenants": ["t_123"] }
}
```

特性开关适合：

- 行为变更；
- 灰度；
- 快速回滚；
- A/B 测试。

不适合：

- 长期版本管理；
- 替代契约设计；
- 隐藏不兼容变更。

开关需要：

- 所有权；
- 过期时间；
- 清理计划；
- 监控。

### 渐进发布的五种形态

| 形态 | 做法 | 适用 | 关键要求 |
|---|---|---|---|
| 暗发布 | 影子流量跑新实现，不返回给用户 | 验证容量与行为差异 | 无副作用、可差分 |
| 金丝雀 | 按比例/租户/地区逐步放量 | 大多数发布 | SLI 分析、自动回滚 |
| 环形发布 | 内部→设计伙伴→小客户→全量 | 高风险功能 | 明确的环与退出标准 |
| 蓝绿 | 两套环境整体切换 | 基础设施变更 | 数据兼容、快速切回 |
| Brownout | 弃用前按计划短暂关闭旧路径 | 弃用演练 | 提前公告、可恢复 |

金丝雀最常见的假阳性是只覆盖内部租户。内部流量规模小、模式单一，无法触发深分页、大租户配额和真实支付失败。样本必须包含真实租户，并按规模、地区、客户端版本分层。

### 开关的契约风险

开关一旦改变消费者可见行为，就不再是内部实现，而是契约的一部分。需要：

- 评估结果确定、可解释，分桶稳定；
- 默认值安全：配置服务故障时回到兼容行为；
- 缓存键包含变体，避免 A/B 串味；
- 开关变更进入变更日志和审计；
- 不用开关隐藏破坏性 schema 变更；
- 事件/Webhook 的 schema 版本化，实验不改变公开结构。

开关的类型学、分桶、实验指标、kill switch 演练与清理机制，见[附录 AK](../appendices/ak-feature-flags-experiments-progressive-delivery.md)。

## 38.3 语义化版本

API 版本可以借鉴 SemVer：

```text
MAJOR.MINOR.PATCH
```

- MAJOR：破坏性变更；
- MINOR：向后兼容的新功能；
- PATCH：兼容的修复。

但 API 与库不同：

- 消费者不会自动升级；
- 行为变更难以语义化；
- 版本号可能被营销影响；
- 多版本并行成本高。

**建议**：公开 API 用主版本 + 日期/变更日志；内部 API 用扩展—收缩，不频繁升主版本。

### 版本号的使用

- `v1`、`v2` 用于主版本；
- 不要用 `v1.2.3` 表示每次发布；
- 用变更日志记录细节；
- 用日期版本控制行为；
- 用特性开关做灰度。

## 38.4 弃用流程

```text
1. 标记弃用
2. 通知消费者
3. 提供迁移路径
4. 监控使用
5. 渐进限制
6. 最终关闭
7. 清理
```

### 标记

- 文档；
- OpenAPI `deprecated: true`；
- 响应头；
- 开发者门户；
- SDK 警告；
- 控制台。

### 通知

- 邮件；
- 站内信；
- 客户经理；
- 变更日志；
- 状态页；
- API 响应头；
- 定期提醒。

### 迁移

- 新旧并存；
- 映射表；
- 迁移工具；
- 示例；
- 支持；
- 测试环境；
- 迁移检查清单。

### 监控

- 旧端点调用量；
- 调用方列表；
- 错误率；
- 迁移进度；
- 大客户状态。

### 渐进限制

- 降低旧端点限流；
- 短暂停用（brownout）；
- 按租户关闭；
- 最终 410。

### 弃用时间表模板

```text
T-12 月：内部决策；确认替代方案、迁移工具、支持范围
T-9 月：公开公告；文档、变更日志、响应头、开发者门户
T-6 月：迁移检查点；按租户统计旧版本用量；大客户一对一
T-3 月：brownout 演练；逐步降低旧版本限流；迁移支持
T-1 月：最后通知；确认例外名单；准备关闭
T-0：关闭旧版本；保留只读/错误提示；监控
T+30 天：清理代码、文档、监控、证书、域名
```

每个阶段要有：

- 负责人；
- 目标租户/调用方；
- 进入/退出标准；
- 监控指标；
- 回滚条件；
- 客户沟通模板。

### 迁移作战室

大型弃用需要“作战室”：

- 一张迁移看板：租户、调用量、联系人、状态、阻塞原因；
- 每日/每周例会；
- 升级路径：支持 → 客户成功 → 销售 → 高管；
- 例外审批与期限；
- 关闭前的最后检查。

不要用“发了邮件”当作迁移完成的证据。证据是旧端点调用量、调用方列表、错误率和客户确认。

## 38.5 弃用响应头

```http
Deprecation: @1798761599
Sunset: Thu, 31 Dec 2026 23:59:59 GMT
Link: <https://docs.example.com/migrate/v2>; rel="deprecation"
```

RFC 9745 的 `Deprecation` 是结构化字段日期（`@` + Unix 秒），不是布尔值 `true`。`Sunset`（RFC 8594）使用 HTTP-date。具体头字段以团队采用的标准为准。关键是让调用方在运行时也能感知弃用，而不只是靠邮件。

版本策略与弃用流程的完整讨论见[第 11 章](../part-1-foundations/11-versioning.md)；本章侧重发布与迁移操作，避免两处各写一套互相冲突的政策。

### 响应头的注意点

- 旧客户端可能忽略未知头；
- 代理可能剥离；
- 需要文档说明；
- 不要影响响应体；
- 不要改变状态码。

## 38.6 迁移策略

### 双运行

新旧版本同时运行：

```text
/v1/orders → 旧实现
/v2/orders → 新实现
```

优点：安全、可回滚。缺点：维护成本。

### 适配层

新实现 + 旧契约适配：

```text
/v1/orders → adapter → new service
```

适合内部重构，不改变外部契约。

### 特性开关

按租户/客户端逐步启用新行为。

### 数据迁移

- 双写；
- 回填；
- 校验；
- 切换读；
- 清理旧数据。

### 迁移模式对比

| 模式 | 风险 | 成本 | 适用 |
|---|---|---|---|
| 双运行 | 低 | 高 | 公开 API |
| 适配层 | 中 | 中 | 内部重构 |
| 特性开关 | 低 | 中 | 行为变更 |
| 数据迁移 | 高 | 高 | 存储变更 |

## 38.7 沟通

- 提前通知（如 12 个月）；
- 明确时间表；
- 影响范围；
- 迁移步骤；
- 支持渠道；
- 定期提醒；
- 最后通知。

### 沟通的层次

```text
1. 变更日志
2. 邮件
3. 控制台横幅
4. 客户经理
5. 电话（大客户）
6. 响应头
```

### 沟通的反模式

- 只发一次邮件；
- 没有时间表；
- 没有迁移指南；
- 没有支持；
- 突然关闭；
- 不区分客户规模。

## 38.8 回滚

- 契约回滚；
- 数据回滚；
- 配置回滚；
- SDK 回滚；
- 文档回滚。

回滚计划应在发布前写好。

### 回滚的触发条件

- 错误率上升；
- 延迟上升；
- 客户投诉；
- 数据不一致；
- 安全事件。

### 回滚的演练

- 在预发环境演练；
- 验证数据；
- 验证配置；
- 验证 DNS；
- 记录时间。

### 回滚的顺序

```text
1. 停止继续扩散（暂停灰度/关开关）
2. 切回旧版本
3. 恢复配置
4. 校验数据
5. 通知客户
6. 观察指标
7. 复盘
```

关键原则：

- 先止血，再定位；
- 数据回滚最难，优先设计可逆写入；
- 回滚不等于恢复原状，可能留下部分新数据；
- 回滚后要防止再次自动发布。

## 38.9 发布检查清单

1. 契约变更是否检测？
2. 是否兼容？
3. 消费者是否知情？
4. 文档/SDK 是否更新？
5. 监控/告警是否就绪？
6. 回滚是否可行？
7. 支持团队是否培训？
8. 是否有迁移指南？
9. 是否有弃用时间表？
10. 是否演练？
11. 计费是否受影响？
12. 合规是否批准？

## 38.10 反模式

- 直接删除字段；
- 不通知消费者；
- 弃用无期限；
- 旧版本无限维护；
- 迁移工具缺失；
- 文档滞后；
- 没有监控旧版本使用；
- 回滚无计划；
- 用“内部 API”跳过弃用流程；
- 弃用期缩短；
- 大客户例外没有记录。

## 38.11 本章小结

- 发布是消费者开始依赖新契约，不只是部署。
- 兼容性发布、行为变更、破坏性发布需要不同流程。
- 弃用要标记、通知、迁移、监控、渐进关闭。
- 迁移可用双运行、适配层、特性开关、数据迁移。
- 沟通和时间表是弃用成功的关键。
- 回滚计划必须提前准备。
- 弃用硬切断、迁移遗漏导致的真实失败链，见[附录 U](../appendices/u-incident-postmortems.md)。
- 从遗留协议、旧模型到新契约的完整迁移方法，见[附录 X](../appendices/x-legacy-modernization.md)。
- 开关类型、暗发布/金丝雀/环形/brownout、实验指标与 kill switch 治理，见[附录 AK](../appendices/ak-feature-flags-experiments-progressive-delivery.md)。

## 设计练习

为一个“用户认证 API”设计从 v1 到 v2 的迁移：

- v1 使用 API Key；
- v2 使用 OAuth 2.1；
- 需要支持旧客户端 18 个月；
- 有企业客户无法快速升级；
- 安全要求逐步收紧。

写出弃用时间表、通知、迁移工具、监控和回滚方案。然后回答：

1. 如何识别仍在用 v1 的客户端？
2. 大客户拒绝迁移时怎么办？
3. 安全漏洞要求提前关闭 v1 时怎么办？
4. 如何验证迁移完成？
