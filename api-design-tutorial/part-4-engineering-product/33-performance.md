# 第 33 章 性能与容量：尾延迟、吞吐与成本

## 33.1 性能是契约的一部分

用户感受到的是延迟，业务承受的是容量，财务承受的是成本。API 性能设计要同时回答：

- 延迟目标是多少？
- 吞吐上限是多少？
- 尾延迟如何？
- 过载时如何降级？
- 每次调用的成本是多少？
- 容量如何规划？

性能不是“上线后优化”的问题。很多性能特征由 API 设计决定：

- 分页方式；
- 响应大小；
- 批量能力；
- 缓存策略；
- 一致性要求；
- 同步依赖数量。

## 33.2 延迟指标

### 平均值会骗人

```text
平均 100ms
P50 50ms
P95 500ms
P99 2s
P99.9 10s
```

平均值掩盖了长尾。一个用户可能正好落在 P99。

### 百分位

- P50：典型体验；
- P95/P99：大多数用户的最差体验；
- P99.9：大规模下的“常态”。

对于 100 万请求/天，P99.9 仍有 1000 次慢请求。

### 尾延迟放大

“10 个服务、每个 P99 1 秒，所以整体 P99 接近 10 秒”是一个常见但错误的直觉。分位数不能直接相加：串行请求的总延迟 P99，不等于各段 P99 之和。

更准确的理解：

- 如果每个服务独立地以 1% 概率进入“慢”状态，10 个服务中至少一个慢的概率是 `1 - 0.99^10 ≈ 9.6%`，而不是 99%；
- 也就是说，“至少一个服务慢”大致是一个 P90 事件；端到端 P99 对应的是单个服务约 P99.9 的分位点，总延迟约等于“一个慢服务 + 九个正常服务”，而不是 10 秒；
- 只有所有服务高度相关地同时变慢时，总延迟才可能接近各段慢延迟之和；独立假设下这种概率极低，但共享数据库、同一区域、同一重试风暴会显著提高相关性；
- 重试会把“一次慢”放大成“多次慢”，并进一步占用共享资源。

**尾延迟是分布式系统的核心问题，但不能用“分位相加”来建模。** 正确做法是通过追踪实测端到端分布，并单独分析相关性、重试和共享资源。

### 尾延迟的来源

- 共享资源竞争；
- GC；
- 慢查询；
- 网络抖动；
- 重试；
- 队列；
- 锁；
- 冷缓存；
- 跨区域调用。

### 尾延迟的缓解

- 减少同步依赖；
- 请求对冲（hedged requests）；
- 超时；
- 缓存；
- 预热；
- 隔离；
- 降级；
- 异步化。

## 33.3 吞吐与并发

### Little 定律

```text
L = λ × W
```

- L：系统中的平均请求数；
- λ：到达率；
- W：平均停留时间。

例如：每秒 1000 请求，平均延迟 200ms，则并发约 200。

### 利用率

```text
利用率 = 到达率 / 服务率
```

当利用率接近 100%，排队延迟急剧上升。通常应保持在 60%～70% 以下，留出突发余量。

### 排队论直觉

```text
利用率 50% → 排队延迟约等于服务时间
利用率 80% → 排队延迟约等于 4 倍服务时间
利用率 90% → 排队延迟约等于 9 倍服务时间
利用率 95% → 排队延迟约等于 19 倍服务时间
```

不是精确公式（取决于分布），但方向正确：**接近饱和时，延迟非线性上升。**

### 一个可算的近似

对单服务台、泊松到达、指数服务时间（M/M/1）：

```text
ρ = λ / μ                 利用率
Wq = ρ / (μ × (1 - ρ))    平均排队时间
W  = 1 / (μ - λ)          平均停留时间
Lq = ρ² / (1 - ρ)        平均排队请求数
```

其中 λ 是到达率，μ 是服务率（1 / 平均服务时间）。

假设平均服务时间 10ms（μ = 100/s）：

| 利用率 ρ | 平均排队 Wq | 平均停留 W |
|---|---|---|
| 50% | 10ms | 20ms |
| 70% | 23ms | 33ms |
| 80% | 40ms | 50ms |
| 90% | 90ms | 100ms |
| 95% | 190ms | 200ms |

这解释了为什么“CPU 还有 10% 空闲”时延迟已经翻倍：排队延迟对利用率是非线性的。

更接近真实系统的 Kingman 近似：

```text
Wq ≈ (ρ / (1 - ρ)) × ((Ca² + Cs²) / 2) × 服务时间
```

`Ca²` 是到达间隔的变异系数平方，`Cs²` 是服务时间的变异系数平方。它说明：

- 流量越突发（`Ca²` 大），排队越严重；
- 服务时间越长尾（`Cs²` 大），排队越严重；
- 降低平均服务时间有效，但降低长尾往往更有效。

这些公式假设独立同分布，真实系统有重尾、相关性、批处理与优先级，不能直接当容量承诺。它们的用途是建立直觉、做数量级估算、解释“为什么 70% 利用率是常见上限”。

### 并发与吞吐

- 并发不是越高越好；
- 超过服务能力后，吞吐下降；
- 队列增长；
- 延迟暴涨；
- 最终雪崩。

## 33.5 优化手段

### 减少往返

- 批量；
- 并行；
- 缓存；
- 连接复用；
- HTTP/2/3；
- 数据本地化；
- 边缘计算。

### 减少数据

- 分页；
- 字段裁剪；
- 压缩；
- 二进制协议；
- 增量更新；
- 只返回 ID。

### 减少工作

- 索引；
- 预计算；
- 物化视图；
- 异步；
- 缓存；
- 限流；
- 查询优化。

### 减少竞争

- 分片；
- 无锁；
- 乐观并发；
- 队列；
- 隔离；
- 连接池分区。

### 优化顺序

```text
1. 测量
2. 找瓶颈
3. 优化瓶颈
4. 再测量
5. 防止回归
```

不要优化非瓶颈。

## 33.6 负载测试

### 类型

- 基准测试；

- 浸泡测试；
- 尖峰测试；

### 指标

- 错误率；

### 工具

- Gatling；

### 真实场景

- 真实请求比例；

- 网络延迟；

只压一个端点会得出错误结论。

### 负载测试的陷阱

- 压测环境太小；
- 数据量不真实；
- 缓存全热；
- 没有认证；
- 没有网络延迟；
- 没有并发写；
- 只测平均；
- 没有长时间运行；
- 没有监控被测系统。

### 一份可执行的负载测试计划

```yaml
name: checkout-api-load
target: staging
dataset: 10M orders, 100k tenants, 30 days
scenarios:
  - name: browse
    mix: 60%
    request: GET /orders?limit=20
  - name: read_detail
    mix: 25%
    request: GET /orders/{id}
  - name: create
    mix: 10%
    request: POST /orders
    headers: { Idempotency-Key: random }
  - name: export
    mix: 5%
    request: POST /exports
stages:
  - duration: 10m, target: 100 rps
  - duration: 20m, target: 500 rps
  - duration: 10m, target: 1000 rps
  - duration: 30m, target: 500 rps   # 浸泡
passCriteria:
  - http_error_rate < 0.1%
  - p95 < 300ms
  - p99 < 800ms
  - db_cpu < 70%
  - no connection_pool_exhausted
abort:
  - error_rate > 5% for 2m
  - p99 > 5s for 2m
```

报告至少包含：

- 每个场景的吞吐、延迟分位、错误率；
- 瓶颈资源（DB、连接池、CPU、GC、网络）；
- 缓存命中率；
- 限流/熔断触发情况；
- 与基线的对比；
- 结论与后续动作。

只测一个端点、只测平均值、只在全热缓存下测，都会得到“看起来很好”的假结果。

## 33.7 容量规划

```text
峰值 QPS × 单请求成本 = 所需容量
```

需要考虑：

- 峰值/均值比；
- 增长趋势；
- 突发；
- 故障转移（N+1）；
- 区域冗余；
- 数据库连接；
- 队列积压；
- 成本；
- 发布余量。

### 示例

```text
峰值 5,000 QPS
每实例 500 QPS
需要 10 实例
N+1 故障转移 → 11 实例
预留 30% 余量 → ceil(11 × 1.3) = 15 实例
```

如果要按 N+2（同时坏两个实例/两个可用区）设计，则：

```text
N+2 → 12 实例
预留 30% → ceil(12 × 1.3) = 16 实例
```

把冗余假设写清楚，不要在没有说明的情况下从 10 直接跳到 12。

### 容量规划的输出

- 实例数；
- 数据库规格；
- 缓存大小；
- 队列容量；
- 带宽；
- 成本；
- 扩容阈值；
- 应急预案。

### 增长预测

- 历史增长；
- 新客户；
- 大促；
- 季节性；
- 产品发布；
- 价格变化。

## 33.8 过载保护

- 限流；
- 并发限制；
- 队列上限；
- 超时；
- 熔断；
- 降级；
- 负载削减；
- 优先级。

没有过载保护的系统会在峰值时雪崩。

### 过载的信号

- 队列增长；
- 延迟上升；
- 错误率上升；
- CPU/内存饱和；
- 连接池耗尽；
- GC 频繁；
- 超时增加。

### 过载的响应

```text
1. 限流
2. 降级非关键功能
3. 拒绝低优先级
4. 扩容
5. 告警
```

### 固定并发上限的问题

给每个实例设一个固定并发数（如 100）看似简单，但：

- 依赖变慢时，固定并发会让请求在池中排队，延迟上升；
- 扩容后每实例上限不变，总容量增长但单实例仍可能过载；
- 流量下降时，上限不会自动回收；
- 不同端点的成本差异很大，统一上限不公平。

### 自适应并发

自适应并发根据实时延迟调整允许的并发数：

```text
目标：P95 延迟 ≤ 300ms
观测：当前并发 120，P95 = 450ms
动作：降低并发到 90
观测：P95 = 280ms
动作：缓慢增加并发，直到再次接近目标
```

常见算法：

- **AIMD**：成功时加性增加，超时/排队时乘性减少；
- **梯度**：用延迟梯度估计排队量，`newLimit = limit × (targetLatency / observedLatency)`；
- **Vegas/BBR 式**：区分“网络延迟”和“排队延迟”，只在排队时降并发。

实现要点：

- 用滑动窗口而不是单点延迟；
- 区分客户端超时与服务端过载；
- 设置上下限，避免震荡；
- 每端点/每依赖独立控制；
- 变更要有审计与回滚；
- 与限流、熔断配合，不互相打架。

### 负载削减的顺序

过载时不是所有请求都同等重要：

| 优先级 | 例子 | 过载时 |
|---|---|---|
| 安全关键 | 支付确认、风控 | 保留 |
| 核心读 | 商品详情、订单状态 | 保留/降级 |
| 核心写 | 下单、退款 | 限流但保留 |
| 非关键 | 推荐、统计、导出 | 先降级 |
| 可延迟 | 报表、索引重建 | 排队/暂停 |

实现方式：

- 请求带优先级/截止时间；
- 网关按优先级限流；
- 队列按优先级出队；
- 低优先级任务可中断；
- 返回明确的 429/503 + `Retry-After`；
- 记录被削减的请求量与业务影响。

### 重试预算

重试会放大过载。服务端应给客户端一个重试预算：

```http
RateLimit-Limit: 1000
RateLimit-Remaining: 120
RateLimit-Reset: 30
Retry-After: 5
```

客户端应：

- 只在幂等请求上重试；
- 指数退避 + 抖动；
- 限制重试比例（如不超过总请求的 10%）；
- 不多层重试；
- 熔断持续失败的依赖；
- 对非幂等写使用幂等键。

## 33.9 性能与成本

- 计算；
- 存储；
- 网络出口；
- 数据库；
- 缓存；
- 日志；
- 追踪；
- 第三方 API。

优化性能不一定降低成本：

- 缓存增加内存；
- 预计算增加存储；
- 多区域增加复制；
- 更快的实例更贵；
- 更多副本增加网络。

需要做单位成本分析（第 52 章）。

### 性能与成本的权衡

```text
延迟降低 50% 可能成本增加 3 倍；
吞吐提升 2 倍可能延迟增加 20%；
缓存命中率提升可能降低数据库成本但增加内存成本。
```

没有免费的优化。

## 33.10 性能预算

为 API 设定预算时，要区分“均值预算”和“分位预算”。组件 P95 之和不是端到端 P95：

```text
组件均值预算：
网关 5ms
认证 10ms
业务逻辑 50ms
数据库 80ms
序列化 10ms
网络 50ms
合计均值约 205ms
```

端到端 P95 目标 300ms 时，205ms 的均值预算只留下约 95ms 的尾部缓冲。实际是否达标，要看追踪测得的端到端分布，而不是把各组件 P95 相加。

更可执行的写法：

```text
端到端 P95 < 300ms（以生产追踪为准）
端到端 P99 < 800ms
各组件均值预算合计 < 210ms
任一组件 P99 超过 200ms 需要评审
```

预算帮助定位和防止回归，但不能替代端到端测量。

### 预算的执行

- 在 CI 中做性能测试；
- 设置阈值；
- 回归阻断；
- 追踪每个环节；
- 定期复查。

## 33.11 反模式

- 只测平均延迟；
- 压测环境与生产差异大；
- 只压一个端点；
- 忽略数据库；
- 忽略尾延迟；
- 没有过载保护；
- 用缓存掩盖慢查询；
- 过早优化；
- 优化了非瓶颈；
- 不监控成本；
- 容量规划只看均值；
- 没有故障转移余量。

## 33.12 本章小结

- 性能是契约的一部分，需定义延迟、吞吐、容量目标。
- 关注分位数和尾延迟，不只看平均。
- Little 定律帮助理解并发与延迟。
- 接近饱和时延迟非线性上升；M/M/1 与 Kingman 近似可用于数量级估算。
- 瓶颈可能在数据库、依赖、序列化、锁或网络。
- 负载测试要真实、全面、可重复。
- 容量规划要留余量和故障转移。
- 过载保护是生产必备；自适应并发、优先级削减与重试预算比固定阈值更抗变化。
- 性能优化要同时考虑成本。
- 成本归因、showback/chargeback 与优化闭环，见[附录 Y](../appendices/y-cost-engineering-finops.md)。
- FaaS/边缘的冷启动、超时与并发配额会改变容量模型，见[附录 AC](../appendices/ac-serverless-edge-wasm.md)。
