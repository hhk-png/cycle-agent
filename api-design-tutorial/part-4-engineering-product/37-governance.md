# 第 37 章 API 治理、评审与平台化

## 37.1 治理不是审批

API 治理的目标是：

- 降低跨团队协作成本；
- 保证契约质量；
- 防止碎片化；
- 管理版本与生命周期；
- 让好实践可复制；
- 让例外可追踪。

如果治理变成“每件事都要开会审批”，团队会绕过它。好的治理是**默认路径好用，例外路径可见**。

### 治理的悖论

- 管得太松：碎片化、重复、事故；
- 管得太紧：团队绕过、发布变慢、创新受阻。

好的治理像交通规则：

- 默认路径清晰；
- 违规有成本；
- 例外有流程；
- 执行自动化。

## 37.2 治理的层次

### 1. 标准

- 命名；
- 错误格式；
- 分页；
- 认证；
- 版本；
- 安全；
- 文档。

### 2. 工具

- Lint；
- 契约检查；
- 破坏性变更检测；
- 目录；
- 代码生成；
- 测试。

### 3. 流程

- 设计评审；
- 发布评审；
- 弃用审批；
- 例外申请。

### 4. 组织

- API Guild；
- 平台团队；
- 所有权；
- 培训；
- 指标。

四层缺一不可：

- 只有标准没有工具 → 无法执行；
- 只有工具没有流程 → 例外失控；
- 只有流程没有组织 → 无人负责。

## 37.3 API 风格指南

应包含：

- 资源命名；
- URL 结构；
- 方法；
- 状态码；
- 错误；
- 分页；
- 过滤；
- 版本；
- 认证；
- 限流；
- 幂等；
- 事件；
- 文档。

风格指南应：

- 有示例；
- 有反例；
- 可执行（lint）；
- 定期更新；
- 有例外流程；
- 有变更记录。

模式与反模式的速查表见[附录 M](../appendices/m-patterns-antipatterns.md)。

### 风格指南的结构

```text
1. 原则
2. 资源与 URL
3. 方法
4. 请求/响应
5. 错误
6. 分页/过滤
7. 认证/授权
8. 版本
9. 事件
10. 文档
11. 检查清单
```

### 风格指南的反模式

- 只写“应该”，不给示例；
- 规则互相矛盾；
- 无法 lint；
- 过长，没人读；
- 不更新；
- 没有例外流程。

## 37.4 设计评审

评审应关注：

- 领域边界；
- 资源模型；
- 契约完整性；
- 错误与失败模式；
- 安全；
- 性能；
- 可演进性；
- 消费者影响。

评审形式：

- 轻量异步（文档 + 评论）；
- 会议（复杂 API）；
- 原型/契约先行；
- 消费者参与。

### 评审检查清单

1. 消费者是谁？
2. 资源/操作是否清晰？
3. 错误是否可恢复？
4. 认证/授权是否明确？
5. 幂等/并发是否处理？
6. 分页/限流是否设计？
7. 版本/弃用策略？
8. 可观测性？
9. 文档/示例？
10. 安全威胁？
11. 数据分类/合规？
12. 成本/计费？

可复用的评分锚点、30 个必问问题与系统设计题库见[附录 P](../appendices/p-review-rubric-and-questions.md)。

### 评审的节奏

- 小 API：异步评审；
- 大 API：会议 + 原型；
- 高风险 API：安全评审 + 消费者试用；
- 紧急修复：事后评审。

### 决策记录（ADR）

评审通过不等于决策可追溯。每个不可逆或高成本的决定，应该有一份简短的 ADR（Architecture Decision Record），放在仓库里，而不是散落在聊天记录中。

```markdown
# ADR-0042：订单列表使用游标分页，而不是 offset

## 状态
已接受（2026-11-20）

## 背景
订单量增长后，offset 深分页变慢；对账脚本报告重复/遗漏。

## 决策
列表与导出统一使用 keyset 游标，排序键为 (created_at, id)。

## 备选方案
- 继续 offset + 限制深度：改动小，但对账仍不稳定。
- 快照 + offset：一致性好，但存储与清理成本高。

## 后果
- 客户端需要适配不透明游标；
- 旧 offset 参数保留一个弃用周期；
- 导出任务改用快照游标。

## 失效条件
如果产品需要随机跳页且数据量很小，游标带来的复杂度可能不值得。
```

ADR 的价值不在于格式，而在于强迫团队写下：背景、备选方案、后果、失效条件。评审时先读 ADR，再讨论实现，能显著减少“上次为什么这么定”的重复争论。

## 37.5 API 目录

目录应记录：

- API 名称；
- 所有者；
- 消费者；
- 版本；
- 生命周期状态；
- 文档链接；
- 契约；
- SLO；
- 依赖；
- 安全等级；
- 数据分类；
- 环境。

目录是治理的基础：不知道有什么，就无法治理。

### 目录的自动化

- 从网关发现；
- 从 OpenAPI 导入；
- 从代码扫描；
- 从服务目录同步；
- 定期更新；
- 影子 API 检测。

## 37.6 所有权

每个 API 应有：

- 产品负责人；
- 技术负责人；
- on-call；
- 安全联系人；
- 文档负责人。

所有权不清的 API 会变成“公共孤儿”。

### 所有权的信号

- 没有 on-call；
- 没有文档负责人；
- 变更无人审批；
- 事故无人认领；
- 消费者不知道找谁。

## 37.7 生命周期

```text
设计 → 实验 → 内测 → 公测 → 正式 → 弃用 → 下线
```

每个阶段定义：

- 支持级别；
- SLA；
- 版本策略；
- 变更通知；
- 文档要求；
- 安全评审。

### 生命周期状态

| 状态 | 支持 | SLA | 变更 |
|---|---|---|---|
| 实验 | 无 | 无 | 随时 |
| 内测 | 有限 | 无 | 提前通知 |
| 公测 | 有 | 有限 | 兼容优先 |
| 正式 | 完整 | 有 | 弃用流程 |
| 弃用 | 维护 | 有 | 只修复 |
| 下线 | 无 | 无 | 410 |

## 37.8 例外管理

不是所有团队都适合同一套规则。例外应：

- 有申请；
- 有理由；
- 有期限；
- 有补偿措施；
- 有记录；
- 定期复审。

### 例外的例子

- 遗留系统无法满足新认证；
- 性能要求需要非标准分页；
- 合作伙伴强制特殊格式；
- 监管要求特殊字段。

例外不是失败，而是治理的一部分。

## 37.9 指标

治理指标：

- 契约覆盖率；
- Lint 通过率；
- 破坏性变更数；
- 版本分布；
- 弃用完成率；
- 文档完整率；
- 安全评审覆盖率；
- 消费者满意度；
- 事故数；
- TTFC；
- API 复用率。

避免用“API 数量”作为成功指标。

### 好的治理指标

- 发布频率；
- 变更失败率；
- 平均恢复时间；
- 契约覆盖率；
- 消费者满意度。

### 坏的治理指标

- API 数量；
- 审批数量；
- 文档页数；
- 会议次数。

## 37.10 API Scorecard

为每个 API 打分：

```text
契约：       ✅ OpenAPI 完整
文档：       ✅ 参考 + 指南 + 示例
安全：       ⚠️ 缺少威胁模型
可观测性：   ✅ SLO + Trace
版本：       ✅ 弃用政策
所有权：     ✅ 明确
测试：       ⚠️ 缺少契约测试
```

Scorecard 用于改进，不是惩罚。

### Scorecard 的使用

- 季度评审；
- 改进计划；
- 分享最佳实践；
- 不公开排名；
- 不用于绩效。

## 37.11 平台化

把治理能力做成自助平台：

- 模板；
- 脚手架；
- 自动生成；
- 自助沙箱；
- 自助发布；
- 自助文档；
- 自助监控；
- 自助审批。

平台化降低合规成本，让团队愿意使用。

### 黄金路径

```text
创建服务 → 选择模板 → 生成 API 骨架 → 自动 CI → 自动文档
→ 自动监控 → 自动发布
```

目标是让“正确的方式”成为“最省事的方式”。

## 37.12 可执行的治理：从“应该”到 CI 门禁

风格指南如果不能被机器执行，最终会退化成一份没人读的文档。可执行的治理至少包含三层：

```text
规则（人类可读 + 机器可读）
  → Lint / diff / 测试（CI 自动执行）
    → 例外与豁免（有期限、有记录）
```

### 一个最小 Spectral 规则集

[Spectral](https://stoplight.io/open-source/spectral) 是 OpenAPI/AsyncAPI 常用的 lint 工具。规则要少而硬，先覆盖最贵的错误：

```yaml
extends: ["spectral:oas"]

rules:
  operation-operationId: error
  operation-operationId-unique: error
  operation-tags: error
  info-contact: error
  info-description: error
  oas3-api-servers: error
  no-$ref-siblings: error

  # 自定义：所有集合端点必须分页
  collection-requires-pagination:
    description: 集合响应必须包含分页参数或游标
    given: "$.paths[*][get].parameters"
    severity: warn
    then:
      function: schema
      functionOptions:
        schema:
          type: array
          contains:
            anyOf:
              - properties: { name: { const: limit } }
              - properties: { name: { const: cursor } }

  # 自定义：错误响应必须引用 Problem Details
  error-response-problem:
    description: 4xx/5xx 响应应使用 application/problem+json
    given: "$.paths[*][*].responses[?(@property >= '400')]"
    severity: warn
    then:
      field: content
      function: truthy
```

规则分级：

| 级别 | 含义 | CI 行为 |
|---|---|---|
| error | 破坏契约/安全/兼容 | 阻断合并 |
| warn | 可能有问题，需要解释 | 不阻断，但记录 |
| info | 风格建议 | 仅提示 |
| off | 明确不检查 | 需要理由 |

不要让所有规则都是 `error`：团队会集体绕过。也不要让所有规则都是 `warn`：治理形同虚设。

### 目录条目的最小 schema

API 目录不是一张 Excel，而是可查询、可关联的元数据。一个最小条目：

```yaml
api:
  name: orders
  display_name: 订单服务
  owner:
    team: commerce-platform
    product: commerce-api
    on_call: commerce-oncall
  lifecycle: ga            # experimental | beta | ga | deprecated | retired
  contract:
    type: openapi
    version: 3.2.0
    url: https://git.example.com/apis/orders/openapi.yaml
  consumers:
    - type: internal
      name: checkout-bff
    - type: partner
      name: partner-acme
  slo:
    availability: 99.95
    latency_p95_ms: 300
  security:
    auth: oauth2
    data_classification: confidential
  dependencies:
    - payments
    - inventory
  environments:
    - production
    - staging
```

目录要能回答：

- 谁拥有它？
- 谁在调用？
- 契约在哪？
- SLO 是什么？
- 数据等级是什么？
- 依赖谁？
- 处于什么生命周期？
- 有没有影子 API？

### CI 门禁的推荐顺序

```text
1. schema 解析与 lint
2. 破坏性变更检测（与上一个发布版本 diff）
3. 契约测试（消费者驱动）
4. 示例/文档中的代码片段校验
5. 安全规则（认证、敏感字段、错误泄露）
6. 目录元数据完整性（owner、SLO、数据分类）
7. 生成 SDK/文档并做编译/链接检查
8. 发布制品与签名
```

顺序的原则是：**越便宜、越确定的检查越靠前**。lint 失败不应该等到跑完 20 分钟集成测试才发现。

### 开关与基础设施配置也是治理对象

API 治理不能只盯着 OpenAPI 文件。两类配置同样会改变契约：

- **特性开关**：谁创建、什么类型、默认值、影响哪些租户、何时清理、变更是否审计；
- **基础设施声明**：Terraform 资源、CRD、GitOps 清单的所有权、漂移处理、删除保护与策略门禁。

建议把开关和 IaC 资源也纳入目录：至少记录负责人、环境、影响面、过期时间和关联服务。没有目录的开关会变成隐形版本；没有所有权的 IaC 会在事故中变成无人认领的爆炸半径。具体方法见[附录 AK](../appendices/ak-feature-flags-experiments-progressive-delivery.md)与[附录 AL](../appendices/al-infrastructure-as-api-terraform-crd-gitops.md)。

### 豁免不是绕过

豁免要可审计：

```yaml
waiver:
  rule: collection-requires-pagination
  api: legacy-orders-v1
  reason: 遗留客户端不支持游标，计划 2027-Q2 迁移
  approved_by: api-guild
  expires_at: 2027-06-30
  compensating_control: 强制 limit 上限 + 深分页告警
```

关键点：

- 有到期日，到期自动重新评估；
- 有补偿措施，而不是“先放过”；
- 有批准人/委员会；
- 有数量上限，豁免过多说明规则或平台有问题；
- 豁免本身要出现在治理看板里。

## 37.13 例外的生命周期与联邦治理

### 例外的五个阶段

```text
申请 → 评估 → 批准（带期限/补偿） → 复审 → 关闭或续期
```

| 阶段 | 输入 | 输出 | 负责人 |
|---|---|---|---|
| 申请 | 规则、场景、影响 | 例外单 | API 所有者 |
| 评估 | 风险、替代方案、补偿 | 风险结论 | 安全/架构 |
| 批准 | 风险结论、期限 | 批准记录 | Guild/委员会 |
| 复审 | 使用量、事故、迁移进度 | 续期/关闭 | 规则 owner |
| 关闭 | 迁移完成/规则变更 | 归档 | 平台团队 |

例外单至少包含：

- 哪条规则、哪个 API、哪个版本；
- 为什么不能遵守；
- 影响哪些消费者；
- 补偿控制是什么；
- 到期日与复审日；
- 谁批准、谁负责迁移；
- 迁移计划与阻塞项。

### 联邦治理：中心定标准，领域做决策

集中式治理容易变成瓶颈，完全自治又会碎片化。联邦模型通常更可持续：

| 职责 | 中心（平台/Guild） | 领域团队 |
|---|---|---|
| 标准 | 制定最小规则集、参考实现 | 在边界内选择 |
| 工具 | 提供 lint/CI/目录/模板 | 接入并反馈 |
| 评审 | 高风险/跨域 API | 日常 API |
| 例外 | 审批高风险例外 | 申请、执行补偿 |
| 指标 | 汇总、对比、分享 | 改进自己的 scorecard |
| 事故 | 复盘方法、跨域协调 | 具体修复 |

中心团队的关键不是“审批更多”，而是**降低正确做事的成本**：

- 一条命令生成合规骨架；
- CI 默认带 lint/diff/契约测试；
- 目录自动从仓库/网关同步；
- 文档模板与示例可复制；
- 常见例外有标准补偿方案。

### 决策权要写清楚

用 RACI 避免“大家都觉得别人负责”：

```text
规则制定：中心 A，领域 C，安全 C
日常评审：领域 A，中心 C
高风险例外：中心 A，领域 R，安全 C
目录元数据：领域 A，平台 R
事故复盘：领域 A，中心 C
```

RACI 不是组织图，而是“这件事卡住时找谁”的契约。

## 37.14 AI 辅助评审：把模型放在正确的位置

大模型可以显著降低评审的机械成本，但不能替代责任。

### 适合交给模型的工作

- 检查命名一致性（单复数、大小写、术语）；
- 找缺失的错误响应、未定义的枚举、未说明的空值；
- 对比 OpenAPI 与示例、文档、SDK 是否一致；
- 识别潜在的破坏性变更；
- 生成评审摘要与问题清单；
- 把自然语言需求转成候选 schema（需人工确认）。

### 不适合交给模型的工作

- 最终批准高风险契约；
- 判断业务语义是否正确；
- 决定权限边界与数据分类；
- 替代安全评审；
- 处理法律/合规承诺；
- 在缺少上下文时“猜”意图。

### 一个可用的评审提示结构

```text
角色：你是 API 评审助手，只做检查，不做最终批准。
输入：
  - OpenAPI diff
  - 风格指南规则
  - 消费者列表与关键场景
  - 变更说明/ADR
任务：
  1. 列出破坏性变更与受影响消费者；
  2. 列出缺失的错误路径与安全考虑；
  3. 对每个问题给出证据（文件/行/规则）；
  4. 标注不确定项，不要编造。
输出：按严重性排序的表格 + 需要人工确认的问题。
```

### 风险与控制

| 风险 | 表现 | 控制 |
|---|---|---|
| 幻觉 | 编造字段/消费者 | 要求引用证据，人工复核 |
| 过度阻断 | 把风格问题当阻断项 | 规则分级，模型只建议 |
| 泄露 | 把密钥/客户数据发给模型 | 脱敏、私有部署、最小上下文 |
| 偏见 | 只认某种风格 | 以团队风格指南为准 |
| 责任稀释 | “模型说没问题” | 人类签字，记录模型版本与提示 |

AI 评审最好的定位是**第二双眼睛**：它让人类评审更快看到机械问题，把时间留给边界、语义、商业与组织判断。

## 37.15 反模式

- 治理 = 审批；
- 标准不可执行；
- 没有例外流程；
- 目录缺失；
- 所有权不清；
- 只考核 API 数量；
- 工具链割裂；
- 评审滞后；
- 安全评审走过场；
- 治理团队与业务脱节；
- 标准过多，无法遵守；
- 没有培训。

## 37.16 本章小结

- 治理目标是降低协作成本，不是增加审批。
- 标准、工具、流程、组织四层缺一不可。
- 风格指南要可执行、有示例、有例外。
- 设计评审要覆盖领域、契约、安全、演进。
- 目录与所有权是治理基础。
- 生命周期、scorecard、平台化让治理可持续。
- 好的治理让正确路径更省事。
- 治理要落到 CI：lint、破坏性检测、契约测试、目录完整性与文档检查，越便宜越靠前。
- 豁免要有期限、补偿与复审；联邦治理让中心定标准、领域做决策。
- AI 可以辅助评审机械问题，但最终责任仍由人承担。

- 产品侧的组织协作与路线图，见[附录 W](../appendices/w-api-product-management.md)；遗留系统迁移的治理，见[附录 X](../appendices/x-legacy-modernization.md)。
