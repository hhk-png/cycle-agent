# 第 28 章 服务网格、东西向流量与内部 API

## 28.1 东西向与南北向

- **南北向**：外部客户端 → 系统入口。通常由 API 网关、负载均衡、CDN 处理。
- **东西向**：服务与服务之间。通常由服务网格、RPC 框架、消息系统处理。

内部 API 设计常被忽视，因为“都是自己人”。但内部 API 同样需要契约、版本、权限、可观测性和故障隔离。规模越大，内部 API 的质量越决定交付速度。

### 内部 API 的特殊性

- 消费者数量不可见；
- 没有正式合同；
- 变更协调靠沟通；
- 故障传播快；
- 依赖图复杂；
- 团队边界模糊。

这些特点让内部 API 更容易腐化，而不是更安全。

## 28.2 服务网格是什么

服务网格把服务间通信的横切能力下沉到基础设施：

- mTLS；
- 服务发现；
- 负载均衡；
- 重试/超时；
- 熔断；
- 流量拆分；
- 访问策略；
- 遥测；
- 故障注入；
- 速率限制。

### Sidecar 模式

每个 Pod 注入代理（如 Envoy）：

```text
Service A → Envoy A → Envoy B → Service B
```

优点：

- 语言无关；
- 统一策略；
- 可观测性；
- 渐进迁移；
- 细粒度流量控制。

缺点：

- 资源开销；
- 延迟；
- 运维复杂；
- 调试困难；
- 升级需重启；
- 每 Pod 一个代理。

### Ambient 模式

使用节点级代理 + 按需 waypoint，减少 sidecar 开销。适合大规模集群，但能力与成熟度需评估。

### 网格的核心能力

| 能力 | 说明 |
|---|---|
| mTLS | 自动证书、轮换、身份 |
| 服务发现 | 动态端点 |
| 负载均衡 | 轮询/最少连接/区域感知 |
| 重试/超时 | 统一策略 |
| 熔断 | 故障隔离 |
| 流量拆分 | 灰度/金丝雀 |
| 访问策略 | 服务间授权 |
| 遥测 | 指标/日志/追踪 |
| 故障注入 | 混沌测试 |

## 28.3 mTLS 与零信任

服务网格通常提供：

- 自动证书签发；
- 轮换；
- 身份（SPIFFE）；
- 双向认证；
- 授权策略。

```yaml
apiVersion: security.istio.io/v1
kind: AuthorizationPolicy
metadata:
  name: orders-allow-payment
spec:
  selector:
    matchLabels:
      app: orders
  rules:
    - from:
        - source:
            principals: ["cluster.local/ns/payments/sa/payment-service"]
      to:
        - operation:
            methods: ["POST"]
            paths: ["/v1/payments"]
```

零信任意味着：

- 不因网络位置信任；
- 每个请求都认证；
- 最小权限；
- 加密；
- 审计；
- 持续验证。

### mTLS 的陷阱

- 开启了 mTLS 但授权策略全放行；
- 证书轮换失败导致大面积故障；
- 证书过期未监控；
- 外部流量绕过网格；
- 调试时关闭 mTLS；
- 身份与业务权限未映射。

### SPIFFE 身份

```text
spiffe://cluster.local/ns/payments/sa/payment-service
```

身份应映射到：

- 服务名；
- 命名空间；
- 服务账号；
- 环境；
- 集群。

## 28.4 内部 API 的契约

内部 API 也需要：

- 明确的 schema；
- 版本策略；
- 错误模型；
- 超时/重试；
- 幂等；
- 认证；
- 所有权；
- SLO；
- 文档。

不能因为“可以协调”就随意破坏。内部消费者数量可能远超预期。

### 内部 API 风格

- gRPC/Protobuf：强类型、高性能；
- REST/OpenAPI：易调试、跨语言；
- 事件：异步解耦；
- GraphQL：聚合层；
- 共享库：谨慎，容易耦合。

### 内部 API 的版本

- 内部 API 也需要兼容性；
- 消费者可能滞后；
- 发布节奏不同；
- 不要用“我们会一起改”作为借口；
- 使用契约测试；
- 使用服务目录。

## 28.5 服务发现与负载均衡

- DNS；
- Kubernetes Service；
- 服务注册中心；
- xDS；
- 客户端负载均衡；
- 服务网格。

需要处理：

- 健康检查；
- 优雅下线；
- 连接 draining；
- 重连风暴；
- 区域感知；
- 权重；
- 端点更新；
- 连接池。

### 长连接的负载均衡

gRPC/HTTP2 长连接会绕过 L4 负载均衡：

- 客户端需要 L7 感知；
- 服务网格；
- 客户端负载均衡；
- 连接数控制。

### 优雅下线

```text
1. 从服务发现移除
2. 等待连接 draining
3. 拒绝新请求
4. 完成进行中请求
5. 关闭
```

## 28.6 超时与重试

网格可以统一配置：

```yaml
timeout: 2s
retries:
  attempts: 2
  perTryTimeout: 1s
  retryOn: 5xx,reset,connect-failure
```

但要注意：

- 重试放大流量；
- 非幂等请求不能盲目重试；
- 总预算（timeout budget）；
- 重试风暴；
- 与网关/客户端重试叠加；
- 重试导致延迟增加；
- 重试导致重复副作用。

**原则**：只在分层中的一层做重试，或用预算控制总重试次数。

### 超时预算

```text
Client timeout: 3s
Gateway timeout: 2.5s
Service A timeout: 2s
Service B timeout: 1.5s
DB timeout: 1s
```

每一层都应小于上层，留出处理时间。

### 故障注入

```yaml
# 通用伪配置，不是某个具体 mesh 的完整 schema
fault:
  delay:
    percentage: 10
    fixedDelay: 5s
  abort:
    percentage: 5
    httpStatus: 503
```

如果使用 Istio，`percentage` 的实际结构是 `percentage: { value: 10 }`；不要把通用示例直接粘贴到生产配置。

用于验证：

- 超时；
- 重试；
- 熔断；
- 降级；
- 告警。

## 28.8 可观测性

网格可以提供：

- 服务间请求指标；
- 分布式追踪；
- 访问日志；
- 拓扑图；
- 错误率；
- 延迟分布；
- 连接数；
- 证书状态。

但要注意：

- 高基数标签；
- 日志成本；
- 采样；
- 敏感数据；
- 跨集群关联；
- 网格代理自身指标。

## 28.9 复杂度与适用性

服务网格不是默认答案。适合：

- 多语言服务；
- 大量服务；
- 强安全/合规；
- 需要统一流量治理；
- 有平台团队维护；
- 需要细粒度 mTLS/授权。

不适合：

- 少量服务；
- 团队没有运维能力；
- 延迟极度敏感；
- 简单单体；
- 无法承担资源开销。

替代方案：

- RPC 框架内置能力；
- API 网关；
- 共享库；
- 云托管服务网格；
- 客户端负载均衡。

## 28.11 反模式

- 网格承担业务逻辑；
- 所有服务强制 sidecar 但无人维护；
- 多层重试叠加；
- 没有超时预算；
- mTLS 开启了但授权策略全放行；
- 内部 API 无版本；
- 服务发现绕过网格；
- 网格配置手工修改；
- 观测数据成本失控；
- 证书轮换无监控；
- 网格升级导致大面积故障。

## 28.12 出口流量、网格边界与多集群

多数服务网格的讨论集中在“服务到服务”，但生产事故更常发生在另外两个方向：**出站**与**跨边界**。

### 28.12.1 出口流量（Egress）

默认情况下，Pod 往往可以访问任意公网地址。这带来三类风险：

- **数据外泄**：被攻陷的服务把数据发往外部；
- **命令与控制**：恶意代码连接外部 C2；
- **隐蔽依赖**：服务悄悄依赖某个外部 API，SLO 与合规都没有覆盖。

出口网关（egress gateway）把出站流量收敛到一个可审计的出口：

```text
Pod → Egress Gateway → 外部服务
        ├─ SNI/DNS 允许列表
        ├─ TLS 发起/透传
        ├─ 凭证注入
        ├─ 速率限制
        └─ 审计日志
```

设计要点：

- **允许列表**按域名/SNI，而不是按 IP（CDN 的 IP 会变）；
- **TLS 发起**让网关持有外部服务凭据，服务本身不接触密钥；
- **DNS 策略**要防止 DNS 隧道与外带；
- **静态出口 IP** 便于合作方做允许列表；
- **按目的地的超时/重试**，避免外部慢依赖拖垮内部线程池；
- **审计**记录谁访问了哪个外部服务、传输了多少字节。

出口策略是 API 契约的一部分：如果某个内部 API 依赖外部服务，它的 SLO、错误码与降级行为必须显式声明，而不是隐藏在某个库的默认配置里。

### 28.12.2 网格边界

服务网格不是一个无限大的信任域。常见边界包括：

| 边界 | 典型组件 | 关键问题 |
|---|---|---|
| 南北向入口 | Ingress Gateway / API Gateway | 外部身份如何映射到内部身份 |
| 网格扩展 | VM、裸金属、其他集群 | 工作负载身份如何签发与轮换 |
| 多集群 | East-West Gateway | 信任域、服务发现、故障域 |
| 外部依赖 | Egress Gateway | 允许列表、凭证、审计 |
| 管理面 | 控制平面 | 配置权限、爆炸半径、升级 |

**多集群**尤其容易把“高可用”做成“高耦合”：

- 每个集群有独立信任域，跨集群 mTLS 需要显式信任；
- 服务导出/导入要有命名空间与所有权；
- 跨集群重试会放大故障；
- 区域故障时的流量切换要与数据驻留一致；
- 控制平面故障不能让数据面全部失效（理想情况下数据面可继续按最后配置运行）。

### 28.12.3 对内部 API 契约的影响

- 跨边界调用的超时预算要重新计算，不能沿用同集群的假设；
- 错误码要区分“本地失败”“跨区失败”“外部依赖失败”；
- 重试策略要按路由配置，而不是全局一刀切；
- 身份要从“服务账号”扩展到“信任域 + 服务账号 + 集群”；
- 审计要能跨集群关联同一个业务请求；
- 数据驻留要求可能禁止某些跨区路由，网格配置必须能表达。

## 28.13 数据面演进：eBPF、Ambient 与无 Sidecar

Sidecar 不是服务网格的唯一形态。过去几年数据面经历了三代演进：

```text
每 Pod Sidecar → 节点级代理 → 内核态 eBPF / 按需 L7 代理
```

### 28.13.1 Sidecar

- 每个 Pod 一个代理，能力最完整；
- 资源开销与 Pod 数量线性增长；
- 升级需要重启工作负载；
- 调试链路长，但边界清晰。

### 28.13.2 Ambient / 节点级代理

以 Istio Ambient 为代表：

- **ztunnel**：节点级 L4 代理，负责 mTLS、身份、基础策略；
- **waypoint**：按需部署的 L7 代理，只有需要 L7 治理的命名空间/服务才启用；
- 好处是减少 sidecar 数量与升级成本；
- 代价是 L4/L7 能力分层，排障时要理解两段路径；
- waypoint 的部署位置会影响延迟与故障域。

### 28.13.3 eBPF

eBPF 把部分网络、安全与可观测性逻辑放进内核：

- 减少用户态转发；
- 细粒度流量可见性；
- 与 Kubernetes CNI 深度集成（如 Cilium）；
- 可以做强制的网络策略与身份感知。

代价：

- 内核版本与发行版兼容性；
- 调试与排障需要内核知识；
- 部分能力依赖特定内核特性；
- 安全边界从“用户态代理”转移到“内核程序”，供应链与加载权限要严控；
- 不是所有 L7 能力都适合放内核。

### 28.13.4 选型表

| 维度 | Sidecar | Ambient | eBPF |
|---|---|---|---|
| 资源开销 | 高 | 中 | 低 |
| L7 能力 | 完整 | 按需 waypoint | 部分/需配合代理 |
| 升级成本 | 高（重启 Pod） | 中 | 低（节点级） |
| 排障难度 | 中 | 中高 | 高 |
| 内核依赖 | 无 | 低 | 高 |
| 成熟度 | 高 | 中高 | 中高 |
| 适合 | 强 L7 治理、多语言 | 大规模、想降开销 | 高性能、CNI 一体化 |

### 28.13.5 迁移建议

1. 先量化 sidecar 的资源与升级成本，不要凭感觉换；
2. 把策略从“代理实现”抽象成“意图”（允许/拒绝、超时、重试），避免绑定某个数据面；
3. 在非关键集群试点 ambient/eBPF，验证 L7 能力缺口；
4. 保留回退路径：数据面替换不应要求应用改造；
5. 对 eBPF 程序做签名、版本与加载权限控制；
6. 用同一套 SLO 与混沌测试比较新旧数据面，而不是只看基准吞吐。

## 28.14 本章小结

- 东西向流量与南北向流量需要不同的治理。
- 服务网格统一 mTLS、流量治理和遥测，但有复杂度和成本。
- 零信任要求每个请求认证与授权。
- 内部 API 同样需要契约、版本、SLO 和所有权。
- 重试要避免多层叠加。
- 网格不是所有团队的默认选择。
- 服务目录和所有权是内部 API 治理的基础。
- 出口流量与跨集群边界是事故高发区，需要允许列表、身份映射与审计。
- 数据面从 sidecar 演进到 ambient 与 eBPF，能力、开销与排障难度要一起评估。
