# 第 29 章 BFF、聚合层与后端边界

## 29.1 为什么需要 BFF

不同客户端对同一业务的需求不同：

- Web 需要丰富字段与实时更新；
- 移动端需要小响应、省流量；
- TV 需要大屏布局数据；
- 合作伙伴需要稳定、简单、可缓存；
- 内部工具需要批量与导出；
- AI Agent 需要工具化、结构化、可恢复。

如果让一个通用 API 满足所有客户端，它通常会变成：

- 字段越来越多；
- 参数越来越复杂；
- 响应越来越大；
- 权限越来越难管；
- 每个客户端都抱怨。

BFF（Backend for Frontend）为每类客户端提供专门的聚合层，把客户端需求与领域服务解耦。

### BFF 不是 API 网关

- 网关做横切（认证、限流、路由）；
- BFF 做面向客户端的聚合与裁剪；
- 两者可以合并，但职责不同。

## 29.2 BFF 的职责

- 聚合多个服务的数据；
- 裁剪字段；
- 适配客户端协议；
- 处理客户端特定的认证/会话；
- 缓存；
- 降级；
- 错误转换；
- 边缘逻辑（排序、分页、格式化）；
- 客户端版本适配。

BFF 不应该：

- 拥有核心业务不变量；
- 直接访问其他服务的数据库；
- 成为新的单体；
- 复制领域逻辑；
- 承担事务；
- 做复杂业务编排。

### BFF 的边界

```text
客户端需求 ← BFF ← 领域 API
```

BFF 可以知道：

- 客户端要什么字段；
- 客户端如何分页；
- 客户端如何展示错误；
- 客户端版本。

BFF 不应该知道：

- 库存如何扣减；
- 支付如何清算；
- 订单状态机；
- 领域不变量。

## 29.3 聚合模式

### 1. 客户端聚合

客户端直接调用多个服务。简单，但：

- 往返多；
- 客户端逻辑复杂；
- 每个客户端重复实现；
- 难以统一降级。

### 2. 网关聚合

网关调用多个服务并合并。适合简单聚合，但网关容易变成业务逻辑黑洞。

### 3. BFF 聚合

专门服务负责聚合。适合多客户端、复杂裁剪。

### 4. GraphQL BFF

客户端声明字段，BFF 负责解析与批处理。适合字段需求高度动态。

### 5. 编排服务

BFF 调用一个编排服务，编排服务负责业务流程。适合复杂工作流，但增加一层。

### 模式对比

| 模式 | 往返 | 客户端复杂度 | 治理成本 | 适用 |
|---|---|---|---|---|
| 客户端聚合 | 多 | 高 | 低 | 简单场景 |
| 网关聚合 | 少 | 低 | 中 | 简单聚合 |
| BFF | 少 | 低 | 中 | 多客户端 |
| GraphQL BFF | 少 | 低 | 高 | 字段动态 |
| 编排服务 | 少 | 低 | 高 | 复杂流程 |

## 29.4 编排 vs 协同

### Orchestration（编排）

一个中心协调者调用多个服务：

```text
Order Orchestrator → Inventory → Payment → Shipping
```

优点：流程可见、错误处理集中、易于补偿。缺点：中心化、耦合、单点。

### Choreography（协同）

服务通过事件响应彼此：

```text
OrderCreated → Inventory reserves → InventoryReserved → Payment charges → ...
```

优点：解耦、可扩展。缺点：流程分散、调试困难、全局状态难追踪。

BFF 通常适合编排“读聚合”，而业务流程本身更适合领域服务或 Saga。

### 读聚合 vs 写编排

- 读聚合：并行调用、合并结果、降级；
- 写编排：顺序、补偿、事务、幂等；
- 不要把写编排塞进 BFF。

## 29.5 BFF 与认证

BFF 可以：

- 持有会话；
- 处理 OAuth 回调；
- 在服务端保存 token；
- 向客户端发放安全 Cookie；
- 统一 CSRF 防护；
- 统一令牌刷新；
- 统一登出。

这种模式减少浏览器暴露 token 的风险。

### BFF 会话

```text
Browser → BFF (HttpOnly session cookie) → API (Bearer token)
```

优点：

- token 不暴露给浏览器；
- 可以用 HttpOnly cookie；
- CSRF 防护集中；
- 令牌刷新集中；
- 多 API 聚合方便。

缺点：

- 多一层；
- 会话存储；
- 跨域 cookie；
- 水平扩展需要共享会话；
- 单点。

## 29.6 聚合的失败处理

一个 BFF 请求可能依赖多个服务：

```text
Order + Customer + Inventory + Recommendations
```

需要定义：

- 哪些数据必须成功（关键路径）；
- 哪些可以降级（推荐）；
- 超时预算；
- 部分成功如何返回；
- 缓存兜底；
- 错误如何映射；
- 重试策略；
- 熔断。

示例：

```json
{
  "order": { "id": "ord_123", "status": "PAID" },
  "customer": { "name": "Alice" },
  "recommendations": {
    "items": [],
    "degraded": true,
    "reason": "RECOMMENDATION_UNAVAILABLE"
  }
}
```

### 关键路径

- 订单详情：订单必须成功；
- 用户信息：可以降级为 ID；
- 推荐：可以空；
- 库存：可以显示“未知”；
- 评价：可以空。

### 部分成功的语义

- 返回 200 + `degraded` 标志 + 每个区块的状态；
- 或返回 200 + 缺失字段；
- 文档说明哪些依赖可降级、降级时字段是什么；
- 不要把 207 当作通用“部分成功”：207 是 WebDAV Multi-Status（RFC 4918），要求 `multistatus` 响应体；普通 JSON 聚合使用它会让客户端与代理困惑。

不要让一个非关键依赖的失败导致整个页面 500。

## 29.7 缓存与性能

- BFF 可以缓存聚合结果；
- 缓存键包含用户/租户/语言；
- 失效复杂；
- 需要防止缓存放大；
- 并发请求合并（request coalescing）；
- 超时与熔断；
- 限制聚合深度；
- 并行调用；
- 连接池。

### 请求合并

多个客户端同时请求同一数据：

```text
100 个请求 → BFF 只调用一次下游 → 分发结果
```

可以显著降低下游压力。

### 缓存放大

BFF 缓存可能导致：

- 每个用户一个缓存条目；
- 内存爆炸；
- 失效困难；
- 权限泄露。

对私有数据，缓存要谨慎。

## 29.8 GraphQL 作为 BFF

优点：

- 客户端声明字段；
- 减少往返；
- schema 强类型；
- 适合多端；
- 自省。

挑战：

- N+1；
- 复杂度和深度限制；
- 字段级授权；
- 缓存；
- 查询治理；
- 团队技能；
- 监控。

GraphQL BFF 不是“免费”的；它把复杂性从端点数量转移到了查询执行与治理。

## 29.9 所有权与团队边界

BFF 应由客户端团队或专门的平台团队拥有：

- 理解客户端需求；
- 快速迭代；
- 不拥有核心领域；
- 与领域团队有清晰契约。

如果 BFF 由后端团队拥有，可能又变成“通用 API”；如果由每个前端团队各自建，可能重复造轮子。需要根据组织规模选择。

### 所有权模式

| 模式 | 优点 | 缺点 |
|---|---|---|
| 客户端团队拥有 | 贴近需求 | 重复建设 |
| 平台团队拥有 | 统一 | 远离需求 |
| 领域团队拥有 | 领域知识 | 又变通用 API |
| 每个客户端一个 BFF | 定制 | 维护成本 |

## 29.10 可观测性：看见聚合的每一跳

BFF 的失败往往不是“整个服务挂了”，而是“某个依赖慢了，页面某个区块空了，但 HTTP 仍然是 200”。如果只监控 BFF 的入口状态码，你会错过大部分真实故障。

至少要采集四类信号：

| 信号 | 回答的问题 | 维度 |
|---|---|---|
| 入口 SLI | 客户端体验是否正常 | 客户端类型、版本、地区、租户 |
| 下游调用 | 哪个依赖慢/错 | 依赖名、端点、状态码、重试次数 |
| 降级事件 | 哪些区块被降级、为什么 | 区块、原因、持续时间 |
| 响应形态 | 响应是否变大/变慢 | 字节数、字段数、序列化耗时 |

### 入口 SLO 要按客户端拆分

同一个 BFF 端点，Web 与移动端的超时预算、可接受延迟、降级容忍度不同。至少按 `client_type`、`client_version`、`region` 拆分 SLI：

```text
bff_home_requests_total{client="ios",version="7.2",region="cn-east"}
bff_home_duration_p95{client="ios",version="7.2"}
bff_home_degraded_total{block="recommendations",reason="timeout"}
```

否则一个老版本客户端的长尾会把整体 P95 拉高，或者移动端的降级被 Web 的平均值掩盖。

### Trace 要贯穿聚合

一个首页请求可能 fan-out 到 8 个下游。Trace 要能回答：

- 哪个下游最慢？
- 是串行还是并行？
- 超时预算是多少？
- 哪个区块触发了降级？
- 重试放大了多少流量？

建议在 span 上标注：

```text
bff.block=recommendations
bff.critical=false
bff.timeout_ms=150
bff.degraded=true
bff.cache=miss
```

不要在 BFF 里重新发明一套 tracing；复用 OpenTelemetry，并把客户端版本、租户、路由规则作为属性传播。

### 降级要有原因与计数

降级不是布尔值，而是可解释的状态：

```json
{
  "block": "recommendations",
  "status": "degraded",
  "reason": "UPSTREAM_TIMEOUT",
  "observed_at": "2026-11-26T10:00:00Z",
  "fallback": "popular_items"
}
```

指标要按 `reason` 分桶，否则你只知道“降级变多了”，不知道是超时、熔断、限流还是权限失败。

### 告警要区分“客户端受影响”和“内部降级”

- 关键区块降级率超过阈值 → 告警；
- 非关键区块降级 → 趋势与日报，不一定要夜间呼叫；
- 下游错误率上升但 BFF 已成功降级 → 依赖团队告警，BFF 侧记录；
- BFF 自身 5xx → 高优先级；
- 响应体积/延迟突变 → 可能是字段膨胀或缓存失效。

### 可观测性反模式

- 只监控 BFF 入口，不监控下游；
- 降级没有原因标签；
- Trace 在 BFF 断链；
- 用平均延迟掩盖尾延迟；
- 没有按客户端版本拆分；
- 日志里打印完整响应（泄露隐私、放大成本）；
- 采样率对所有端点一刀切，关键写路径采样不足。

## 29.11 测试：BFF 的契约在两边

BFF 同时面对客户端和领域服务，所以它有两套契约：

1. **对客户端**：响应结构、字段语义、错误、缓存、版本兼容；
2. **对领域服务**：请求参数、超时、重试、错误映射、幂等。

只测其中一边，都会在生产环境补课。

### 测试矩阵

| 测试 | 目标 | 典型工具/方法 |
|---|---|---|
| 单元测试 | 聚合、裁剪、错误映射 | 普通单测 |
| 契约测试（下游） | 领域 API 变更不破坏 BFF | Pact、schema diff |
| 契约测试（客户端） | BFF 变更不破坏客户端 | 消费者驱动契约、golden response |
| 组件测试 | 多下游并行、超时、降级 | 依赖 mock/容器 |
| 故障注入 | 下游超时、500、限流、部分失败 | Toxiproxy、chaos |
| 性能测试 | fan-out、连接池、缓存 | k6、wrk |
| 安全测试 | 字段级授权、租户隔离 | 越权用例、跨租户 |
| 兼容测试 | 多客户端版本 | 版本矩阵、录制回放 |

### 黄金响应（golden response）

为每个客户端版本保存一组“典型请求 → 期望响应”的快照，在 CI 中比较：

- 字段增删、类型变化、空值变化；
- 错误结构；
- 降级标记；
- 分页/游标；
- 本地化字段。

黄金响应不是万能的：它只能覆盖已录制的场景，不能证明所有路径。它适合拦截“无意中的契约漂移”，不适合替代契约测试与故障注入。

### 下游契约测试

BFF 是领域 API 的消费者，应该参与消费者驱动契约：

```text
BFF 定义它需要的字段/状态/错误
→ 领域服务验证自己能满足
→ CI 中双向验证
```

这样领域服务删除字段时，会在自己的 CI 中看到 BFF 的失败，而不是等首页崩了才发现。

### 故障注入要覆盖“部分成功”

至少测试：

- 一个非关键依赖超时；
- 一个关键依赖 500；
- 一个依赖返回 429；
- 两个依赖同时慢；
- 缓存不可用；
- 下游返回不符合 schema 的数据；
- 客户端断开连接；
- 重试导致下游压力放大。

断言不只是“返回 200”，而是：

- 关键区块存在；
- 非关键区块有降级标记；
- 延迟在预算内；
- 没有泄露其他租户数据；
- 重试次数有上限；
- 日志/Trace 能定位原因。

## 29.12 版本化与迁移：BFF 是兼容层，不是永久层

BFF 常被用来吸收客户端版本差异。但如果每个客户端版本都在 BFF 里加分支，BFF 会变成“版本考古现场”。

### 客户端版本协商

常见做法：

```http
X-Client-Platform: ios
X-Client-Version: 7.2.0
```

服务端按版本范围决定：

- 返回哪些字段；
- 使用哪种分页；
- 是否启用新错误结构；
- 是否降级某个区块。

规则要写进契约：

- 版本号格式与比较规则；
- 未知版本的处理（拒绝、回退到最低支持版本、还是按最新处理）；
- 版本支持窗口；
- 强制升级的策略与错误码。

### 分支爆炸的替代方案

| 方案 | 适用 | 代价 |
|---|---|---|
| 版本分支 | 差异大、短期 | 维护成本高 |
| 字段开关 | 字段级差异 | 组合爆炸 |
| 能力协商 | 客户端声明能力 | 需要能力注册 |
| 适配层 | 老客户端 → 新模型 | 多一层转换 |
| 独立 BFF 实例 | 客户端差异极大 | 部署/运维成本 |

优先用**能力协商 + 适配层**，把“版本判断”集中在一处，而不是散落在每个 handler。

### 迁移步骤

1. **盘点**：哪些客户端版本还在调用？各自需要什么？
2. **定义目标**：新 BFF 契约与领域契约。
3. **双跑**：新旧 BFF 并行，按客户端/租户灰度。
4. **对拍**：同一请求比较响应语义、延迟、错误。
5. **切流**：按版本/比例逐步切换。
6. **回退**：保留旧路径与开关，定义回退条件。
7. **退役**：监控旧版本调用量，通知、强制升级、下线。

### BFF 也会退役

BFF 不是永久层。当客户端统一、领域 API 足够稳定、或 BFF 的聚合逻辑被下沉时，应该有退役计划：

- 停止新增客户端专属逻辑；
- 把通用能力下沉到领域 API；
- 把客户端差异收敛到能力协商；
- 删除无消费者的分支；
- 记录 ADR，避免“以后还有人需要”。

## 29.13 案例：多端电商首页的降级矩阵

假设首页有五个区块：

```text
banner（运营配置）
recommendations（推荐服务）
flash_sale（促销服务）
orders_preview（订单服务，需登录）
cart_badge（购物车服务）
```

先定义关键性：

| 区块 | 关键 | 超时预算 | 降级策略 |
|---|---|---|---|
| banner | 否 | 80 ms | 本地缓存/空 |
| recommendations | 否 | 150 ms | 热门商品/空 |
| flash_sale | 否 | 120 ms | 隐藏区块 |
| orders_preview | 是（登录用户） | 250 ms | 显示“暂时无法加载”+ 重试 |
| cart_badge | 是 | 100 ms | 显示未知角标，不阻断 |

响应示例：

```json
{
  "blocks": {
    "banner": { "status": "ok", "items": [] },
    "recommendations": {
      "status": "degraded",
      "reason": "UPSTREAM_TIMEOUT",
      "items": []
    },
    "flash_sale": { "status": "hidden" },
    "orders_preview": { "status": "ok", "recent": [] },
    "cart_badge": { "status": "ok", "count": 3 }
  },
  "meta": {
    "request_id": "req_...",
    "degraded_blocks": ["recommendations"]
  }
}
```

关键设计点：

- 关键区块失败时，不要用一个非关键区块的降级掩盖；
- 每个区块独立超时，不要共享一个总超时导致尾部互相拖累；
- 并行调用，但限制并发度，避免下游被打爆；
- 缓存按区块、租户、语言、客户端版本分层；
- 降级状态要可观测，客户端可以选择是否展示提示；
- 不要返回 207；用 200 + 区块状态，或对关键区块失败返回明确错误。

## 29.14 反模式

- BFF 里写核心业务规则；
- BFF 直接连数据库；
- BFF 变成分布式单体；
- 每个页面一个 BFF；
- BFF 无缓存/无限流；
- 聚合失败导致整个页面失败；
- BFF 复制权限逻辑但不一致；
- 没有契约测试；
- 客户端直接绕过 BFF 访问内部服务；
- BFF 承担写事务；
- BFF 调用链过深。

## 29.15 本章小结

- BFF 为不同客户端提供定制聚合，保护领域服务。
- BFF 不应拥有核心业务不变量。
- 聚合要明确关键路径、降级和超时预算。
- GraphQL 可以作为 BFF，但治理成本高。
- 所有权应靠近客户端，契约靠近领域。
- 避免 BFF 变成新的单体或分布式泥球。
- BFF 适合读聚合，不适合写编排。
- 可观测性要覆盖入口 SLI、下游调用、降级原因与响应形态，并按客户端版本拆分。
- 测试要同时覆盖“对客户端”和“对领域服务”两套契约，故障注入必须覆盖部分成功。
- 版本化优先用能力协商与适配层，避免每个客户端版本都长出一个分支；BFF 也要有退役计划。

## 设计练习

为“视频流媒体平台”设计 BFF：

- Web、iOS、Android、TV；
- 首页推荐、播放页、搜索、个人中心；
- 多语言；
- 弱网；
- 推荐服务可能超时。

为每个客户端设计聚合接口与降级策略。然后回答：

1. 首页推荐超时时，返回什么？
2. 播放页的哪些数据必须成功？
3. 移动端如何减少响应体积？
4. BFF 缓存如何处理用户权限？
