# 第 27 章 API 网关与边缘架构

## 27.1 网关是“所有请求的公共走廊”

API 网关位于客户端与后端服务之间，承担跨切面能力：

- TLS 终止；
- 路由；
- 认证；
- 授权（粗粒度）；
- 限流；
- 缓存；
- 请求/响应转换；
- 日志、指标、追踪；
- 灰度/金丝雀；
- 熔断/重试；
- API 版本管理；
- 开发者门户集成；
- 请求大小限制；
- CORS。

它让每个服务不必重复实现这些能力。

### 网关的价值

- 统一安全策略；
- 统一可观测性；
- 统一流量治理；
- 服务解耦；
- 协议转换；
- 开发者体验。

### 网关的风险

- 单点故障；
- 性能瓶颈；
- 配置错误影响全局；
- 成为业务逻辑黑洞；
- 供应商锁定；
- 团队职责不清。

## 27.2 网关的职责边界

### 适合放在网关

- 协议终止；
- 身份验证（token 校验）；
- 粗粒度限流；
- 路由与版本；
- CORS；
- 请求大小限制；
- 基础 WAF；
- 可观测性；
- 缓存公开资源；
- 请求 ID 注入；
- 负载均衡；
- 灰度分流。

### 不适合放在网关

- 复杂业务规则；
- 对象级授权（需要领域数据）；
- 数据聚合；
- 事务；
- 业务状态机；
- 敏感数据转换（容易泄露到日志）；
- 计费逻辑；
- 复杂重试。

**原则**：网关做“与业务无关的横切”，业务逻辑留在服务内。

### 判断标准

问三个问题：

1. 这个能力是否需要领域数据？是 → 服务内。
2. 这个能力是否对所有服务都一样？是 → 网关。
3. 这个能力出错时，谁负责？网关团队 → 网关；业务团队 → 服务。

## 27.3 网关、Ingress、Mesh、BFF 的区别

| 组件 | 流量方向 | 主要职责 |
|---|---|---|
| API Gateway | 南北向 | 外部 API 管理、认证、限流、路由 |
| Ingress | 南北向 | Kubernetes HTTP 入口 |
| Service Mesh | 东西向 | 服务间 mTLS、重试、遥测、流量治理 |
| BFF | 客户端到后端 | 面向客户端的聚合与裁剪 |
| Load Balancer | 南北/东西 | 四/七层负载均衡 |
| WAF | 南北向 | Web 攻击防护 |
| CDN | 南北向 | 静态/动态内容加速与缓存 |

它们可以重叠，但目标不同。不要用一个网关解决所有问题。

### 常见组合

```text
Client → CDN → WAF → API Gateway → BFF → Service Mesh → Services
```

每一层都应职责清晰，避免重复。

## 27.4 路由

```yaml
routes:
  - match:
      path: /v1/orders
      method: POST
    service: order-service
    timeout: 5s
    rateLimit:
      key: tenant
      requestsPerMinute: 1000
```

路由设计要考虑：

- 路径匹配优先级；
- 方法匹配；
- 主机/域名；
- 头部匹配；
- 权重/灰度；
- 重写规则；
- 超时；
- 重试策略；
- 请求体大小；
- 路径参数；
- 尾斜杠；
- 大小写。

### 版本路由

```text
/v1/orders → order-service-v1
/v2/orders → order-service-v2
```

网关可以做版本转换，但转换层会变成隐性契约，需谨慎。

### 路由的陷阱

- 路径前缀匹配导致 `/v1/orders` 匹配 `/v1/orders-archive`；
- 正则路由性能差；
- 重写规则导致签名失效；
- 尾斜杠处理不一致；
- 编码路径未解码；
- 路径参数未校验。

## 27.5 认证与授权

网关通常负责：

- 验证 JWT 签名、过期、issuer、audience；
- 查询 introspection（如需要）；
- 注入用户/租户头；
- 拒绝无效请求；
- 限流。

但对象级授权必须在服务内完成。网关不知道 `order_123` 属于谁。

### 头注入安全

网关注入的头（如 `X-User-Id`）必须：

- 从外部请求中剥离；
- 只由网关设置；
- 服务只信任来自网关的流量；
- 使用 mTLS/网络策略。

否则客户端可以伪造身份头。

```text
错误：Client → Gateway → Service（Service 信任 X-User-Id）
攻击：Client 直接带 X-User-Id 访问 Service
```

### 网关认证的边界

- 网关可以做“认证”；
- 网关可以做“粗粒度授权”（scope/角色）；
- 网关不能做“对象级授权”；
- 网关不应做“字段级授权”；
- 网关不应缓存授权决策过久。

### 一个请求穿过网关的顺序

网关的中间件顺序会直接影响安全与性能。一个可用的顺序：

```text
TLS 终止
→ 生成/透传 Request-Id
→ 路由匹配（主机、路径、方法）
→ 请求体大小/超时上限
→ 认证（JWT 校验、API Key、mTLS）
→ 粗粒度授权（scope/角色）
→ 限流（IP/Key/租户）
→ WAF/输入过滤
→ 缓存查找
→ 上游连接池/负载均衡
→ 上游调用（带超时）
→ 响应压缩/头处理
→ 访问日志与指标
```

几条硬规则：

- **先拒绝，再做昂贵工作**：认证、限流、体大小检查应尽早，别等解析完大 body 才拒绝。
- **未认证流量按 IP 限流，认证后按主体/租户限流**：只按 IP 会误伤 NAT，只按租户会让未认证攻击穿透。
- **对象级授权不在网关**：网关不知道 `order_123` 属于谁。
- **缓存键必须包含认证/租户维度**，否则会串数据。
- **上游超时小于网关超时**，给网关留出返回错误与记录日志的时间。
- **重试只对幂等请求**，并且要有预算，避免与 mesh/服务内重试叠加。

### 网关的故障模式

| 故障 | 表现 | 降级 |
|---|---|---|
| 认证服务不可用 | 所有请求 401/500 | 本地公钥校验、短期缓存、fail-closed 或 fail-open（按风险） |
| 限流存储不可用 | 429 误判或全部放行 | 降级为本地限流，记录降级指标 |
| 配置推送错误 | 路由 404/500 | 配置版本化、灰度、自动回滚 |
| 证书过期 | TLS 握手失败 | 到期监控、自动续期、双证书 |
| 上游连接池耗尽 | 502/503、延迟上升 | 连接池隔离、排队上限、快速失败 |
| DNS 故障 | 上游不可达 | 本地缓存、静态 IP、备用域名 |
| 网关自身过载 | 全站延迟 | 自限流、降级非关键路由、扩容 |

网关是单点，必须假设它会坏。关键不是“永不出错”，而是“出错时影响可控、可观测、可回滚”。

## 27.6 限流与缓存

网关适合：

- 按 IP/Key/租户的粗粒度限流；
- 公开资源的 CDN 缓存；
- 响应压缩；
- 连接池。

不适合：

- 需要业务语义的配额；
- 需要对象级权限的缓存；
- 复杂计费。

### 网关缓存的危险

- 缓存键不包含租户；
- 缓存了带 `Authorization` 的响应；
- 缓存了 POST 响应；
- 缓存未遵守 `Cache-Control`；
- 清除不彻底。

## 27.7 灰度与流量治理

- 按权重分流；
- 按 Header/用户/租户；
- 金丝雀发布；
- 蓝绿部署；
- 故障注入；
- 镜像流量；
- 熔断；
- 超时；
- 重试预算。

```yaml
trafficSplit:
  - service: orders-v1
    weight: 90
  - service: orders-v2
    weight: 10
```

网关可以成为发布控制面，但要有回滚和可观测性。

### 灰度的一致性

- 同一用户的请求应路由到同一版本；
- 会话粘性；
- 数据兼容；
- 回滚路径；
- 监控指标对比。

## 27.8 多区域与边缘

### 多区域

```text
用户 → GeoDNS/Anycast → 最近边缘 → 区域网关 → 服务
```

需要考虑：

- 数据驻留；
- 跨区域一致性；
- 故障转移；
- 延迟；
- 成本；
- 证书；
- 配置同步；
- 区域故障隔离；
- 流量回切。

### 边缘计算

把部分逻辑下沉到 CDN 边缘：

- 认证（短期令牌校验）；
- 个性化缓存；
- A/B 测试；
- 请求聚合；
- 限流；
- 图像处理；
- AI 推理（小模型）；
- 地理路由。

优点：低延迟、减少回源。缺点：运行时限制、调试困难、配置复杂、供应商锁定。

### 边缘的适用性

- 静态/半静态内容；
- 认证卸载；
- 简单重写；
- 地理路由；
- 小模型推理。

不适合：

- 复杂业务逻辑；
- 大数据处理；
- 需要强一致的写；
- 长时间任务。

## 27.9 配置即代码

网关配置应：

- 版本化；
- 代码评审；
- 自动化测试；
- 渐进发布；
- 可回滚；
- 环境隔离；
- 审计。

```yaml
# gateway/routes/orders.yaml
route:
  id: orders-v1
  upstream: order-service
  timeout: 5s
  retries:
    attempts: 2
    retryOn: [502, 503, 504]
    # 只对幂等请求重试；POST 只有在带 Idempotency-Key 时才允许
    idempotentOnly: true
```

避免在 UI 上手工点击修改生产路由而不留痕迹。

### 配置测试

- schema 校验；
- 路由冲突检测；
- 网关超时略大于后端超时（留出缓冲，避免后端还在处理时网关先放弃）；
- 重试次数合理；
- 认证配置；
- 限流配置；
- 灰度权重。

## 27.10 性能与容量

网关是单点：

- 连接数；
- TLS 握手；
- 请求解析；
- 规则匹配；
- 日志缓冲；
- 插件链；
- 后端连接池；
- 内存；
- GC。

需要：

- 压测；
- 容量规划；
- 水平扩展；
- 无状态；
- 配置热更新；
- 故障隔离；
- 限流自保护；
- 连接复用；
- 超时控制。

### 网关的性能陷阱

- 每个请求调用外部认证服务；
- 同步日志写入；
- 复杂正则；
- 大响应缓冲；
- 插件链过长；
- TLS 握手未复用；
- 连接池过小。

## 27.11 可观测性

- 每路由的 QPS、延迟、错误率；
- 上游健康；
- 限流命中；
- 认证失败；
- 缓存命中；
- 重试；
- 超时；
- Trace 注入；
- 访问日志（脱敏）；
- 配置变更审计。

## 27.12 反模式

- 网关里写业务逻辑；
- 网关成为唯一单点；
- 信任客户端传入的身份头；
- 所有服务共享一个超级网关配置；
- 没有配置版本与回滚；
- 缓存私有数据；
- 无限重试；
- 网关超时小于或等于后端超时（没有缓冲，容易把成功请求误判为超时）；
- 不监控网关自身；
- 网关与 mesh 重复做重试；
- 网关规则手工修改。

## 27.13 本章小结

- 网关承担跨切面能力，不应承担领域逻辑。
- 区分 Gateway、Ingress、Mesh、BFF 的职责。
- 认证可在网关，对象级授权必须在服务。
- 头注入必须防伪造。
- 多区域与边缘要处理数据驻留、一致性和成本。
- 配置即代码、可观测性、容量规划是生产必备。
- 网关是单点，必须自保护和可回滚。
- 多区域的写权威、故障转移与一致性承诺，见[附录 Z](../appendices/z-distributed-consistency-multi-region.md)；边缘运行时限制与冷启动，见[附录 AC](../appendices/ac-serverless-edge-wasm.md)。

- 灰度发布；
