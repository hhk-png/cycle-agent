# 第 19 章 多租户与数据隔离

## 19.1 多租户是架构约束，不是加个字段

多租户意味着一个系统同时服务多个客户（租户），每个租户的数据、配置、权限、计费和使用量必须隔离。

它不是“在表里加 `tenant_id`”这么简单。多租户影响：

- 认证与令牌；
- 授权；
- 数据模型；
- 查询与索引；
- 缓存键；
- 限流与配额；
- 背景任务；
- 日志与监控；
- 备份与恢复；
- 合规与数据驻留；
- 计费；
- 发布与升级。

一个租户隔离漏洞，可能导致客户数据泄露、合同违约和监管处罚。

### 租户、组织、项目、用户

这些概念经常混用，需要先定义：

- **租户（tenant）**：计费与隔离的最高单位，通常是企业客户；
- **组织（organization）**：租户内的业务单位，可能多个；
- **项目（project）**：组织内的工作空间；
- **用户（user）**：可以属于多个租户/组织；
- **成员（member）**：用户在某个租户中的身份。

API 必须明确每个资源属于哪个层级，以及令牌代表哪个层级。

## 19.2 隔离模型

### 1. Silo（独立实例/数据库）

每个租户独立数据库或实例。

优点：

- 最强隔离；
- 单租户故障不影响他人；
- 易于按租户备份/迁移；
- 满足数据驻留要求；
- 易于按租户升级/回滚；
- 性能可预测。

缺点：

- 成本高；
- 运维复杂；
- 租户数量受限于实例数；
- 升级需要逐个迁移；
- 新租户开通慢。

适合：大型企业、强合规、金融/医疗。

### 2. Pool（共享数据库，共享表）

所有租户共享表，用 `tenant_id` 区分。

优点：

- 成本低；
- 资源利用率高；
- 运维简单；
- 适合大量中小租户；
- 新租户开通快。

缺点：

- 隔离靠应用逻辑；
- 单租户可能影响他人（噪声邻居）；
- 大租户数据量影响索引；
- 备份/恢复粒度粗；
- 合规难度高；
- 跨租户查询容易出错。

### 3. Bridge（共享数据库，独立 schema）

每个租户一个 schema。

优点：

- 隔离比 Pool 强；
- 备份/迁移较容易；
- 共享数据库资源；
- 单租户 schema 可以独立升级。

缺点：

- schema 数量多时管理复杂；
- 迁移需要遍历；
- 连接池与元数据压力；
- 跨 schema 查询困难。

### 混合模式

- 中小租户 Pool；
- 大客户 Silo；
- 敏感数据独立；
- 按区域部署；
- 按合规要求分区。

这是最常见的生产方案。

### 隔离模型对比

| 维度 | Silo | Bridge | Pool |
|---|---|---|---|
| 隔离强度 | 最高 | 高 | 中 |
| 成本 | 高 | 中 | 低 |
| 运维复杂度 | 高 | 中 | 低 |
| 租户规模 | 少 | 中 | 多 |
| 备份粒度 | 租户 | 租户 | 全库 |
| 数据驻留 | 易 | 中 | 难 |
| 噪声邻居 | 无 | 低 | 高 |

## 19.3 租户识别

租户 ID 应来自可信来源：

- 令牌中的 `tenant_id` / `org_id`；
- API Key 绑定的租户；
- mTLS 证书；
- 子域名（需防伪造）；
- 请求头（仅内部可信网关）。

**不要**从请求体或查询参数中直接信任租户 ID：

```http
GET /orders?tenantId=t_456   # 攻击者可以改
```

正确做法：

```text
令牌中的租户 → 服务端解析 → 强制注入查询条件
```

如果必须支持跨租户管理，使用显式角色与审计。

### 租户上下文传播

在服务内部，租户上下文应：

- 放入请求上下文（context）；
- 传递给所有下游调用；
- 写入日志/Trace；
- 用于缓存键；
- 用于数据库会话变量；
- 用于消息属性；
- 用于审计。

不要让每个函数都从请求头重新解析，容易遗漏。

### 子域名租户

```text
https://acme.api.example.com/orders
```

风险：

- 子域名可以被伪造（如果 DNS 配置错误）；
- 通配符证书；
- 子域名枚举；
- 与令牌租户不一致。

应校验：

- 子域名对应的租户；
- 令牌中的租户；
- 两者是否一致；
- 不一致时拒绝。

## 19.4 数据隔离

### 查询层

每个查询都必须带租户条件：

```sql
SELECT *
FROM orders
WHERE tenant_id = $1 AND id = $2;
```

不要依赖“上层已经检查过”。防御性编程要求数据访问层强制租户过滤。

### 数据库层

- PostgreSQL Row-Level Security（RLS）；
- 视图；
- 独立 schema；
- 独立数据库。

RLS 示例：

```sql
ALTER TABLE orders ENABLE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation ON orders
USING (tenant_id = current_setting('app.tenant_id')::text);
```

RLS 的注意点：

- 连接池需要正确设置会话变量；
- 超级用户可能绕过；
- 迁移需要权限；
- 性能开销；
- 测试要覆盖跨租户。

### 缓存层

缓存键必须包含租户：

```text
tenant:t_123:order:ord_456
```

不要使用全局键：

```text
order:ord_456   # 可能跨租户冲突
```

### 对象存储

- 按租户前缀；
- 访问策略；
- 签名 URL 绑定租户；
- 防止路径穿越；
- 加密密钥隔离。

### 搜索索引

- 文档包含 `tenant_id`；
- 查询强制过滤；
- 防止跨租户召回；
- 向量检索同样需要命名空间/过滤；
- 索引分片按租户；
- 大租户独立索引。

### 消息队列

- 消息带 `tenant_id`；
- 消费者按租户处理；
- 死信按租户隔离；
- 防止一个租户的消息阻塞其他租户；
- 顺序按租户分区。

### 备份与恢复

- 能否按租户恢复？
- 恢复会不会影响其他租户？
- 备份是否加密？
- 备份是否跨区域？
- 合规保留。

## 19.5 噪声邻居

共享资源下，一个租户可能耗尽：

- 数据库连接；
- CPU；
- 内存；
- 带宽；
- 队列；
- 缓存；
- 第三方配额；
- 线程池。

防护：

- 按租户限流；
- 按租户并发限制；
- 队列隔离；
- 资源配额；
- 优先级；
- 大租户隔离到独立实例；
- 监控每租户资源使用；
- 预算告警。

### 噪声邻居案例

一个租户发起全量导出：

- 占用数据库连接；
- 扫描大量行；
- 拖慢其他租户查询；
- 占满出口带宽。

防护：

- 导出走独立队列；
- 导出限流；
- 导出使用只读副本；
- 大导出拆分；
- 按租户配额。

## 19.6 每租户配置

租户可能有不同配置：

- 功能开关；
- 品牌/主题；
- 时区/语言；
- 税率；
- 数据保留；
- 认证方式（SSO）；
- Webhook 端点；
- 限流套餐；
- 密码策略；
- IP 白名单。

设计：

```json
{
  "tenantId": "t_123",
  "features": { "advancedReports": true },
  "limits": { "requestsPerMinute": 5000 },
  "locale": "zh-CN",
  "timeZone": "Asia/Shanghai"
}
```

配置应有版本、审计、回滚，并避免把业务逻辑写死在代码里。

### 配置的优先级

```text
租户配置 > 套餐默认 > 系统默认
```

需要明确：

- 哪些配置可被租户修改；
- 哪些只能平台管理员修改；
- 配置变更是否即时生效；
- 配置缓存 TTL；
- 配置错误的回滚。

## 19.7 租户生命周期

- 创建/开通；
- 配置；
- 试用；
- 付费；
- 暂停；
- 注销；
- 数据导出；
- 数据删除；
- 合规保留。

API 需要支持：

```text
POST /tenants
GET  /tenants/{id}
PATCH /tenants/{id}
POST /tenants/{id}/suspend
POST /tenants/{id}/export
DELETE /tenants/{id}
```

注销尤其复杂：需要处理数据删除、备份、法律保留、第三方系统、审计。

### 删除流程

```text
1. 停用（禁止新请求）
2. 导出（给客户）
3. 软删除（标记）
4. 硬删除（主数据）
5. 清理衍生数据（缓存、搜索、对象存储）
6. 备份过期
7. 审计记录保留
```

删除应有：

- 确认机制；
- 冷静期；
- 审计；
- 不可恢复警告；
- 合规保留例外。

### 暂停

暂停与删除不同：

- 暂停可恢复；
- 暂停保留数据；
- 暂停可能仍计费；
- 暂停影响 API 访问；
- 暂停通知客户。

## 19.8 计费与用量

多租户通常按租户计量：

- 请求数；
- 存储；
- 计算；
- 用户数；
- 模型 token；
- 导出流量；
- 活跃设备。

用量记录必须：

- 带租户 ID；
- 可追溯；
- 可对账；
- 处理重试/重复；
- 按账单周期聚合；
- 支持配额与超额；
- 支持调整/退款。

### 用量与配额的一致性

- 配额检查与用量记录使用同一事件源；
- 避免“配额显示 0 但账单继续涨”；
- 计量事件幂等；
- 延迟可接受但有上界；
- 跨时区账单周期明确。

## 19.9 可观测性

- 每租户的请求量、错误率、延迟；
- 每租户的资源使用；
- 跨租户异常检测；
- 租户 ID 进入日志/Trace/Metric；
- 避免高基数标签导致监控爆炸；
- 大租户单独看板；
- 租户级别的 SLO。

### 高基数问题

把 `tenant_id` 作为指标标签会导致：

- 时间序列爆炸；
- 存储成本上升；
- 查询变慢。

解决：

- 只对 Top N 租户打标签；
- 其他租户聚合；
- 使用日志/Trace 做细粒度；
- 使用采样。

## 19.10 合规与数据驻留

- 数据存储区域；
- 跨境传输；
- 数据保留；
- 删除权；
- 审计日志；
- 子处理者；
- 加密密钥隔离（BYOK/HYOK）；
- 数据分类。

这些要求可能直接决定 Silo/Bridge/Pool 的选择。

### 数据驻留

如果租户要求数据留在某个区域：

- 部署区域化实例；
- 数据不跨区复制；
- 备份不跨区；
- 日志不跨区；
- 支持人员访问也受限制；
- 密钥不跨区。

### BYOK / HYOK

- BYOK：客户提供密钥，平台使用；
- HYOK：客户持有密钥，平台无法单独解密；
- 密钥轮换；
- 吊销；
- 审计。

## 19.11 反模式

- 只加 `tenant_id` 但不强制过滤；
- 从请求体信任租户；
- 缓存键不带租户；
- 全局唯一 ID 假设（跨租户冲突）；
- 共享队列无租户隔离；
- 大租户拖垮全体；
- 注销只删主表，不删衍生数据；
- 日志混入其他租户数据；
- 备份恢复无法按租户进行；
- 管理后台跨租户查询没有审计；
- 租户切换不重新授权。

## 19.12 本章小结

- 多租户是贯穿认证、数据、缓存、限流、计费、合规的系统约束。
- Silo/Bridge/Pool 各有成本与隔离权衡，混合模式常见。
- 租户 ID 必须来自可信令牌，不能信任请求参数。
- 数据层、缓存层、搜索层、对象存储都要强制隔离。
- 噪声邻居需要配额、隔离与优先级。
- 租户生命周期与计费必须被设计。
- 合规要求可能决定隔离模型。
- 如果使用 BaaS 或数据库自动生成接口，租户隔离最终落在 RLS/Security Rules 与跨租户测试上，见[附录 AF](../appendices/af-database-as-api-baas.md)。
- 聚合/分析接口的租户隔离还要考虑差分隐私与查询预算，见[附录 AG](../appendices/ag-privacy-enhancing-tech.md)。

## 设计练习

为“企业项目管理 SaaS”设计多租户：

- 免费小团队；
- 大型企业（要求独立数据库、SSO、审计）；
- 跨组织协作；
- 按用户数计费；
- 数据驻留。

选择隔离模型，并写出认证、数据、缓存、限流、计费方案。然后回答：

1. 跨组织协作时，数据属于哪个租户？
2. 大客户要求独立数据库，如何路由？
3. 租户注销后，备份中的数据如何处理？
4. 如何证明租户 A 看不到租户 B 的数据？
