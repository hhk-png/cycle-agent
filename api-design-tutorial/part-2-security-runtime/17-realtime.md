# 第 17 章 实时 API：SSE、WebSocket、WebTransport 与 WebRTC

## 17.1 实时不是“更快地轮询”

实时 API 的核心是让状态变化在发生时被推送，而不是由客户端反复询问。常见需求：

- 聊天与通知；
- 协同编辑；
- 金融行情；
- 订单状态更新；
- 物流轨迹；
- 在线游戏；
- AI 流式输出；
- 设备遥测；
- 在线状态（presence）；
- 直播互动。

选择哪种技术，取决于方向性、延迟、可靠性、网络环境和运维能力。

实时系统的难点不在“建立连接”，而在：

- 连接断了怎么办？
- 消息丢了怎么办？
- 消息重复怎么办？
- 客户端太慢怎么办？
- 用户权限变了怎么办？
- 十万连接怎么扩展？
- 如何知道系统正在出问题？

## 17.2 四种主要技术

### SSE（Server-Sent Events）

基于 HTTP 的单向服务器推送：

```http
GET /events/orders
Accept: text/event-stream
```

```text
event: order.updated
id: evt_123
data: {"orderId":"ord_123","status":"SHIPPED"}

```

优点：

- 简单，基于 HTTP；
- 自动重连（浏览器内置）；
- 文本协议，易调试；
- 适合通知、流式输出；
- 经过代理和 CDN 相对友好；
- 支持 `Last-Event-ID` 恢复。

缺点：

- 单向；
- 浏览器并发连接限制（HTTP/1.1 每域名约 6 个）；
- 代理/缓冲可能干扰；
- 不支持二进制（需 Base64）；
- 不能客户端推送。

### WebSocket

全双工协议：

```text
GET /ws/chat
Upgrade: websocket
```

优点：

- 双向；
- 低延迟；
- 适合交互式应用；
- 支持二进制；
- 帧开销小。

缺点：

- 连接管理复杂；
- 需要心跳、重连、恢复；
- 代理/负载均衡支持需配置；
- 安全与限流更复杂；
- 不是 HTTP 语义，缓存/监控工具支持弱；
- 连接数扩展难。

### WebTransport

基于 HTTP/3 和 QUIC：

- 多路复用流；
- 可靠与不可靠传输；
- 低延迟；
- 适合实时媒体、游戏、协作；
- 支持单向/双向流、数据报。

缺点：

- 生态与浏览器支持仍在演进；
- 运维复杂；
- 回退方案需要设计；
- 对 UDP 的网络限制。

### WebRTC

点对点实时通信：

- 音视频；
- 数据通道；
- NAT 穿透（STUN/TURN）；
- 低延迟；
- 端到端加密。

缺点：

- 信令复杂；
- 网络环境复杂；
- 服务端录制/转发成本；
- 不适合普通 API 推送；
- 需要 TURN 中继，成本高。

### 技术对比

| 维度 | SSE | WebSocket | WebTransport | WebRTC |
|---|---|---|---|---|
| 方向 | 单向 | 双向 | 双向 | 双向/P2P |
| 传输 | HTTP | TCP | QUIC | UDP |
| 浏览器支持 | 好 | 好 | 较新 | 好 |
| 二进制 | 否 | 是 | 是 | 是 |
| 自动重连 | 是 | 否 | 否 | 部分 |
| 代理友好 | 好 | 中 | 中 | 差 |
| 运维复杂度 | 低 | 中 | 高 | 高 |
| 典型场景 | 通知/流式 | 聊天/协作 | 实时媒体 | 音视频 |

## 17.3 选择矩阵

| 需求 | 推荐 |
|---|---|
| 服务器单向推送通知 | SSE |
| AI 流式文本 | SSE |
| 双向聊天/协作 | WebSocket |
| 低延迟游戏/媒体 | WebTransport / WebRTC |
| 音视频通话 | WebRTC |
| 简单状态更新 | 轮询/长轮询也可 |
| 大规模广播 | SSE + 消息总线 |
| 高频双向数据 | WebSocket / WebTransport |
| 文件/消息混合 | WebSocket |

不要因为 WebSocket “更实时”就默认选它。SSE 在单向场景中更简单、更易运维。

### 选择顺序

1. 需要客户端发消息吗？否 → SSE。
2. 需要二进制/超低延迟吗？是 → WebTransport/WebRTC。
3. 需要 P2P 音视频吗？是 → WebRTC。
4. 否则 → WebSocket。
5. 更新频率低（>30 秒）→ 轮询可能更便宜。

## 17.4 连接生命周期

一个健壮的实时连接需要：

1. **认证**：连接建立时验证令牌；
2. **授权**：订阅的频道/资源是否允许；
3. **心跳**：检测半开连接；
4. **重连**：指数退避 + 抖动；
5. **恢复**：从上次事件继续；
6. **背压**：慢消费者处理；
7. **限流**：连接数、消息数；
8. **关闭**：明确关闭码与原因；
9. **清理**：连接关闭后释放资源；
10. **审计**：记录连接与订阅。

移动端离线优先、断线后的增量同步与冲突解决，见[附录 L](../appendices/l-mobile-offline-sync.md)。

### 认证

不要在 URL 中放长期令牌：

```text
/ws?token=...   # 会进入日志、代理、浏览器历史
```

更好的方式：

- 短期一次性 ticket；
- 连接后首帧认证；
- Cookie + CSRF 防护；
- WebSocket 子协议携带令牌（仍需谨慎）。

一次性 ticket 流程：

```text
1. 客户端 POST /realtime/tickets（带 Bearer token）
2. 服务端返回 ticket（30 秒有效、一次性）
3. 客户端连接 /ws?ticket=...
4. 服务端验证 ticket 并建立连接
```

### 授权

连接建立后，客户端可能订阅多个频道：

```json
{ "type": "subscribe", "channel": "order:ord_123" }
```

服务端必须检查：

- 用户是否属于该租户；
- 用户是否有权查看该订单；
- 频道是否存在；
- 订阅数量是否超限。

不要在连接建立时只检查一次权限，然后允许订阅任意频道。

### 心跳

```json
{ "type": "ping", "ts": 1795688130 }
```

```json
{ "type": "pong", "ts": 1795688130 }
```

心跳间隔应小于负载均衡/代理的空闲超时。

SSE 可以用注释行作为心跳：

```text
: keep-alive

```

### 重连

- 指数退避；
- 抖动；
- 上限；
- 认证失败不重试；
- 服务端关闭码区分可重试/不可重试；
- 重连后恢复订阅；
- 重连后补齐事件。

### 关闭码

WebSocket 关闭码：

```text
1000 正常关闭
1001 离开
1008 策略违规
1011 服务端错误
4000-4999 应用自定义
```

应用应定义：

- 哪些码可重试；
- 哪些码需要重新认证；
- 哪些码表示权限不足；
- 哪些码表示客户端版本过旧。

## 17.5 事件信封与恢复

统一事件格式：

```json
{
  "id": "evt_01J9Z6...",
  "type": "order.updated",
  "version": 1,
  "occurredAt": "2026-11-26T10:15:30Z",
  "sequence": 42,
  "data": {
    "orderId": "ord_123",
    "status": "SHIPPED"
  }
}
```

### 断线恢复

客户端记录最后收到的 `id` 或 `sequence`：

```http
GET /events/orders?lastEventId=evt_123
```

或 WebSocket 重连后：

```json
{ "type": "resume", "lastEventId": "evt_123" }
```

服务端需要：

- 保留一段时间的事件缓冲；
- 能判断游标是否过期；
- 过期时要求客户端做全量同步；
- 保证顺序或明确乱序；
- 按频道/租户隔离缓冲。

### 恢复的三种结果

```text
1. 游标有效 → 补发缺失事件
2. 游标过期 → 返回 410，要求全量同步
3. 游标无效 → 返回 400，要求重新订阅
```

客户端应能处理这三种情况。

### 事件缓冲的存储

- 内存（短时间、单实例）；
- Redis Stream（多实例、中等保留）；
- Kafka（长保留、可回放）；
- 数据库（审计、长期）。

选择取决于保留时长、吞吐和成本。

## 17.6 投递语义

**裸传输通常是“至多一次”或有损的，不是“至少一次”。**

- SSE 没有内建的持久化与确认；断线期间的事件默认丢失，除非服务端实现事件缓冲与 `Last-Event-ID` 重放；
- WebSocket 没有内建的消息确认与重放；连接断开时在途消息可能丢失；
- WebTransport 提供可靠流或数据报，但“传输可靠”不等于“应用层事件不丢”；连接关闭后仍需应用层恢复；
- 多副本、多分区还可能乱序。

只有同时具备以下条件，才能对客户端承诺“至少一次”：

1. 服务端按频道持久化事件；
2. 事件有单调递增的序号或游标；
3. 客户端确认（ack）已处理的位置；
4. 服务端支持从确认位置重放；
5. 客户端按事件 ID 去重；
6. 有保留期与过期游标的明确语义。

| 传输 | 默认投递 | 恢复手段 | 应用层要求 |
|---|---|---|---|
| SSE | 有损/至多一次 | `Last-Event-ID` + 服务端缓冲 | 去重、游标、过期处理 |
| WebSocket | 有损/至多一次 | 自定义序号 + ack + 重放 | 去重、顺序、全量对账 |
| WebTransport | 流可靠，但会话可断 | 应用层序号 + 重放 | 同上 |
| WebRTC DataChannel | 可配置可靠/有序 | 应用层恢复 | 同上 |

客户端必须：

- 按 `id` 去重；
- 处理乱序；
- 定期全量对账；
- 不假设消息只来一次；
- 不假设顺序（除非明确保证）；
- 对 410/游标过期做全量重置。

如果需要“恰好一次”，通常要在应用层实现幂等和版本号。

### 顺序保证

- 单连接内通常有序；
- 跨连接不保证；
- 多分区不保证；
- 重连后可能乱序。

如果需要顺序：

- 按聚合 ID 分区；
- 单分区单消费者；
- 使用序列号；
- 客户端缓冲排序。

### 状态同步 vs 事件流

- **事件流**：发送增量，客户端应用；
- **状态快照**：发送完整状态，客户端替换；
- **混合**：快照 + 增量，定期对账。

状态更新类场景（如在线状态、光标位置）适合“只保留最新值”，可以丢弃中间事件。交易类场景必须保留每个事件。

## 17.7 背压

慢消费者会拖垮服务端：

- 发送缓冲区增长；
- 内存耗尽；
- 影响其他连接。

策略：

- 限制每连接缓冲；
- 丢弃不可靠的中间更新（保留最新状态）；
- 断开持续慢的客户端；
- 对可靠事件使用持久队列；
- 提供快照 + 增量；
- 限制消息大小；
- 限制发送速率。

```text
如果事件是“状态更新”，可以合并为最新值；
如果事件是“交易记录”，不能丢弃，必须持久化并重放。
```

### 背压信号

- 发送队列长度；
- 发送延迟；
- 客户端确认（如果支持）；
- 连接内存占用。

### 慢消费者处理

```text
1. 警告（发送控制消息）
2. 降级（只发关键事件）
3. 断开（让客户端重连并全量同步）
```

不要无限缓冲，否则一个慢客户端可能拖垮整个服务。

## 17.8 扩展

单机连接容易，多实例扩展难：

```text
Client → Load Balancer → Gateway → Pub/Sub → Service Instances
```

需要：

- 粘性会话或连接路由；
- 发布/订阅（Redis、NATS、Kafka）；
- 频道分片；
- 在线状态存储；
- 广播风暴控制；
- 跨区域延迟；
- 连接数上限；
- 优雅下线。

### 扇出模式

- 小房间：服务端直接广播；
- 大频道：消息总线 + 分片消费者；
- 超大规模：边缘节点 + 分层聚合。

### 连接路由

负载均衡需要知道哪个实例持有哪个连接：

- 一致性哈希；
- 连接注册表；
- 粘性会话；
- 服务网格。

### 优雅下线

实例下线时：

- 停止接受新连接；
- 通知客户端重连；
- 等待连接迁移；
- 强制关闭剩余连接；
- 释放资源。

## 17.9 安全

- 认证与授权；
- 频道级权限；
- 防跨租户订阅；
- 消息大小限制；
- 速率限制；
- 输入校验；
- 防注入；
- 日志脱敏；
- 连接数限制；
- DDoS 防护；
- 来源校验（Origin）；
- CSRF 防护（Cookie 认证时）。

WebSocket 不自动提供 CSRF 保护，使用 Cookie 认证时需要额外防护。

### 跨站 WebSocket 劫持

攻击者页面可以发起 WebSocket 连接到你的服务，并携带用户的 Cookie。防护：

- 校验 `Origin`；
- 使用一次性 ticket；
- 不使用 Cookie 作为唯一认证；
- 要求首帧认证。

### 消息注入

客户端发送的消息应：

- 校验类型；
- 校验大小；
- 校验字段；
- 转义/过滤；
- 限制频率；
- 不要直接拼接 SQL/HTML。

## 17.10 可观测性

- 当前连接数；
- 连接建立/关闭率；
- 认证失败率；
- 消息吞吐；
- 端到端延迟；
- 重连率；
- 丢弃/背压次数；
- 每频道订阅数；
- 错误关闭码分布；
- 每租户连接数；
- 消息大小分布。

### 端到端延迟

从事件产生到客户端收到的时间，需要：

- 事件时间戳；
- 服务端发送时间；
- 客户端接收时间（需客户端上报）；
- 各段延迟分解。

## 17.11 反模式

- 用 WebSocket 做请求—响应；
- 没有心跳，半开连接堆积；
- 没有恢复机制，断线即丢数据；
- 在 URL 放长期令牌；
- 无限缓冲慢消费者；
- 所有消息广播给所有连接；
- 没有消息 ID，无法去重；
- 把实时连接当数据库；
- 连接建立后不检查订阅权限；
- 没有优雅下线，发布时连接全断；
- 没有连接数上限，被 DDoS 打满。

## 17.12 本章小结

- SSE 适合单向推送，WebSocket 适合双向交互，WebTransport/WebRTC 适合低延迟媒体。
- 实时连接需要认证、心跳、重连、恢复、背压和关闭语义。
- 事件应有 ID、类型、版本、时间和顺序。
- 裸传输默认有损/至多一次；只有持久化、序号、ack 与重放齐备时，才能承诺至少一次。
- 扩展需要发布/订阅、分片和连接路由。
- 安全与可观测性不能因为“实时”而省略。
- 慢消费者必须有背压和降级策略。

## 设计练习

为“协同文档编辑 API”设计：

- 文档加载；
- 实时编辑同步；
- 断线恢复；
- 冲突解决；
- 权限变更；
- 大规模广播。

选择传输方式，并写出连接生命周期、事件格式和恢复流程。然后回答：

1. 两个用户同时编辑同一段落，如何合并？
2. 用户断线 10 分钟后重连，如何补齐？
3. 权限被撤销后，已建立的连接如何处理？
4. 100 万人同时观看同一文档，如何扩展？
