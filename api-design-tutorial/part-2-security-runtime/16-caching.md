# 第 16 章 缓存与条件请求

## 16.1 缓存是 API 设计的一部分

缓存不是“后面加个 Redis”的运维优化。缓存策略直接影响：

- 延迟与吞吐；
- 数据一致性；
- 权限与数据泄露；
- 成本；
- API 契约（ETag、Last-Modified、Cache-Control 是契约的一部分）。

如果 API 设计时没有考虑缓存，后期通常无法安全地加。

一个典型例子：API 返回用户私有数据，但没有设置 `Cache-Control: private`。CDN 按 URL 缓存了响应，下一个用户请求同一 URL 时看到了前一个人的数据。这不是 CDN 的 bug，而是 API 契约没有表达“这个响应不能被共享缓存”。

## 16.2 HTTP 缓存模型

HTTP 缓存有两个核心机制：**新鲜度（freshness）** 和 **验证（validation）**。

### 新鲜度（Freshness）

```http
Cache-Control: max-age=60, public
```

- `max-age`：缓存可以复用多久；
- `s-maxage`：共享缓存（CDN）的时长；
- `public`：任何缓存可存；
- `private`：仅浏览器/私有缓存；
- `no-cache`：可以缓存，但每次使用前必须验证；
- `no-store`：不得存储；
- `must-revalidate`：过期后必须验证，不能用旧值；
- `immutable`：资源在有效期内不会变化，浏览器不重新验证。

### 验证（Validation）

```http
ETag: "v42"
Last-Modified: Thu, 26 Nov 2026 10:00:00 GMT
```

客户端下次请求：

```http
If-None-Match: "v42"
```

如果未变化：

```http
HTTP/1.1 304 Not Modified
```

304 不返回响应体，节省带宽。

### 强 ETag 与弱 ETag

```http
ETag: "v42"        # 强 ETag，字节级相同
ETag: W/"v42"      # 弱 ETag，语义等价但字节可能不同
```

强 ETag 适合范围请求、缓存、并发控制；弱 ETag 适合语义比较，不能用于 `If-Match`。

### 重新验证与过期

```http
Cache-Control: max-age=60, stale-while-revalidate=30, stale-if-error=600
```

- `stale-while-revalidate`：过期后先返回旧数据，同时后台刷新；
- `stale-if-error`：源站故障时返回旧数据。

这些指令能显著提升可用性，但要求业务能接受短暂陈旧。

### 缓存决策流程

```text
请求 → 有缓存吗？
  ├── 没有 → 回源 → 存储 → 返回
  └── 有 → 还在新鲜期？
        ├── 是 → 直接返回
        └── 否 → 必须验证？
              ├── 是 → 带条件请求回源
              │       ├── 304 → 返回缓存
              │       └── 200 → 更新缓存
              └── 否 → 回源
```

## 16.3 条件请求

### GET

```http
GET /orders/ord_123
If-None-Match: "v42"
```

### 写操作

```http
PATCH /orders/ord_123
If-Match: "v42"
```

如果版本不匹配：

```http
HTTP/1.1 412 Precondition Failed
```

`If-Match` 是乐观并发控制的标准方式，也能防止“丢失更新”。

### 其他条件头

- `If-Modified-Since`；
- `If-Unmodified-Since`；
- `If-Range`（范围请求）；
- `If-None-Match: *`（仅当资源不存在时执行）。

### 条件请求的语义

- `If-None-Match` 匹配 → 304（GET/HEAD）或 412（其他方法）；
- `If-Match` 不匹配 → 412；
- `If-Modified-Since` 用于没有 ETag 的场景；
- 多个 ETag 用逗号分隔；
- `*` 表示“任意当前表示”。

### ETag 与并发控制

```http
GET /orders/ord_123
ETag: "v42"

PATCH /orders/ord_123
If-Match: "v42"
Content-Type: application/merge-patch+json

{ "shippingAddressId": "addr_456" }
```

如果两个客户端同时拿到 `v42`：

- 第一个成功，ETag 变为 `v43`；
- 第二个返回 412；
- 第二个需要重新读取、合并、重试。

这比“后写覆盖先写”安全得多。

## 16.4 缓存键与 Vary

缓存键通常包括：

- URL；
- 方法；
- 查询参数；
- 请求头（通过 `Vary` 声明）。

```http
Vary: Accept, Accept-Encoding, Authorization
```

注意：

- `Vary: *` 通常导致不可缓存；
- 按 `Authorization` 缓存会降低命中率，但共享缓存必须避免跨用户泄露；
- 租户 ID 应进入缓存键；
- 不应把敏感信息放在 URL 中作为缓存键；
- 查询参数顺序应规范化；
- 大小写、尾斜杠、编码应统一。

### 缓存键设计

```text
key = method + canonical_url + tenant_id + auth_scope + accept_encoding
```

不要只用 URL：

- 同一 URL 可能因用户不同而返回不同数据；
- 同一 URL 可能因 `Accept` 不同而返回不同格式；
- 同一 URL 可能因租户不同而返回不同数据；
- 同一 URL 可能因语言不同而返回不同文本。

### Vary 的代价

`Vary: Authorization` 意味着每个用户的每个令牌都是一个缓存条目：

- 命中率极低；
- 缓存存储爆炸；
- CDN 可能拒绝缓存。

对私有数据，更好的策略是：

- 不缓存；
- 或按用户 ID 缓存，并确保键不可猜测；
- 或使用 BFF 在服务端缓存。

## 16.5 分层缓存

```text
浏览器缓存
  ↓
CDN / 边缘缓存
  ↓
API 网关缓存
  ↓
应用层缓存（Redis/Memcached）
  ↓
数据库缓存/物化视图
```

每一层都有不同的：

- 生命周期；
- 失效机制；
- 一致性要求；
- 安全边界。

### 浏览器

- 私有数据用 `private`；
- 静态资源用长缓存 + 内容哈希文件名；
- HTML 用短缓存或 `no-cache`；
- API 响应根据敏感性设置。

### CDN

- 公开、可缓存的 GET；
- 按地理位置；
- 缓存键规范化；
- 清除（purge）能力；
- 动态加速；
- 边缘计算；
- 签名 URL。

### 应用缓存

- 热点数据；
- 会话；
- 权限；
- 限流计数；
- 分布式锁；
- 去重。

### 数据库缓存

- 查询缓存；
- 物化视图；
- 连接池；
- 缓冲池。

## 16.6 缓存失效

“计算机科学只有两个难题：缓存失效和命名。” API 场景中常见策略：

### TTL

简单，但可能读到旧数据。

适合：

- 数据变化不频繁；
- 能接受短暂陈旧；
- 无法可靠失效。

### 写时失效

写入后删除缓存：

```text
写数据库 → 删除缓存 → 下次读回填
```

竞态：删除缓存后，旧读请求可能把旧值写回。可用延迟双删、版本号或消息队列解决。

### 写时更新

写入后更新缓存。适合读多写少，但并发写可能乱序。

### 事件驱动

通过 CDC/事件使缓存失效：

```text
DB change → outbox → event → cache invalidator
```

适合多实例、跨区域。

### 版本化键

```text
order:ord_123:v42
```

新版本写入新键，旧键自然过期，避免删除竞态。

### 延迟双删

```text
读请求 A 读到旧值（尚未写缓存）
写请求 B 写数据库
写请求 B 删除缓存
读请求 A 把旧值回填缓存   ← 竞态发生在这里
写请求 B 延迟 500ms 再删除缓存
```

第一次删除发生在写数据库之后；真正的问题是“读请求在写之前读到旧值，却在删除之后才回填”。延迟双删通过第二次删除清掉这段窗口内的旧回填，但延迟时间难以精确设置，且第二次删除仍可能失败。

更稳妥的方案：

- 版本化缓存键（写新版本，旧键自然过期）；
- Outbox/CDC 事件驱动失效；
- 写后短 TTL + 读时校验版本；
- 对强一致读绕过缓存。

延迟双删应作为兜底，而不是唯一正确性机制。

### 缓存失效的可靠性

- 失效消息可能丢失；
- 多级缓存可能不同步；
- 跨区域复制有延迟；
- 失效失败应有重试和告警；
- 最终一致性需要兜底 TTL。

## 16.7 缓存与权限

这是最危险的部分。

- 共享缓存不能缓存用户私有数据，除非缓存键包含用户/租户且隔离严格；
- `Vary: Authorization` 可能导致缓存碎片化；
- CDN 默认可能忽略 `Authorization`，需要显式配置；
- 错误配置可能让用户 A 看到用户 B 的数据；
- 缓存清除后，旧副本可能仍在边缘节点。

**原则**：

- 绝不能缓存的秘密（令牌、一次性链接、密钥、完整个人数据导出）使用 `no-store`；
- 用户特定但可短期复用的数据，使用 `private, max-age=0, must-revalidate` 或很短的 `private, max-age`，并确保缓存键包含认证主体；
- 共享缓存不得存储用户特定数据，除非有明确的安全设计、键隔离与验证；
- `private, no-store` 同时出现是自相矛盾的：`no-store` 已经禁止任何存储，`private` 不会增加安全性。不要把两者当成“更安全”的组合。

### 权限变更与缓存

用户权限变更后：

- 缓存中的旧权限可能继续生效；
- 需要主动失效；
- 或使用短 TTL；
- 或在每次请求时重新检查权限。

对撤销权限，不能依赖缓存 TTL。

### 多租户缓存

- 缓存键必须包含租户 ID；
- 不要让租户 ID 来自请求体；
- 跨租户共享的缓存条目必须显式标记；
- 缓存清除按租户维度；
- 监控跨租户缓存命中。

## 16.8 缓存一致性

需要明确：

- 允许的最大陈旧时间；
- 写入后多久可见；
- 跨区域复制延迟；
- 缓存故障时的行为（回源、拒绝、返回旧值）。

例如：

```text
商品目录：允许 5 分钟陈旧；
库存：不允许缓存，或最多 1 秒；
用户权限：写入后立即失效；
报表：T+1。
```

不同数据需要不同策略。不要用一个全局 TTL 解决所有问题。

### 一致性等级

| 等级 | 含义 | 适用 |
|---|---|---|
| 强一致 | 缓存与源站同步 | 库存、余额、权限 |
| 读己之写 | 写入者立即看到 | 用户资料 |
| 有界陈旧 | 最大延迟 N 秒 | 商品目录 |
| 最终一致 | 可接受较长延迟 | 报表、分析 |

## 16.9 缓存穿透、击穿与雪崩

- **穿透**：查询不存在的数据，缓存不命中，每次都打数据库。解决：空值缓存、布隆过滤器、参数校验。
- **击穿**：热点 key 过期瞬间大量请求回源。解决：互斥锁、逻辑过期、后台刷新。
- **雪崩**：大量 key 同时过期或缓存故障。解决：TTL 抖动、多级缓存、熔断降级。

### 穿透

```text
GET /users/not-exist
→ 缓存未命中 → 查数据库 → 不存在 → 不缓存
→ 下次再查 → 又打数据库
```

解决：

- 缓存空值（短 TTL）；
- 布隆过滤器；
- 参数格式校验；
- 限流。

### 击穿

```text
热点 key 过期 → 1000 个请求同时回源 → 数据库压力骤增
```

解决：

- 互斥锁，只允许一个请求回源；
- 逻辑过期，后台异步刷新；
- 永不过期 + 主动更新；
- 热点 key 预热。

### 雪崩

```text
大量 key 同一时间过期 → 数据库被压垮
```

解决：

- TTL 加随机抖动；
- 多级缓存；
- 熔断降级；
- 缓存集群高可用；
- 限流。

## 16.10 应用缓存模式

### Cache-Aside

```text
读：查缓存 → 未命中 → 查数据库 → 写缓存
写：写数据库 → 删除缓存
```

最常用，简单灵活。

### Read-Through

缓存层负责回源，应用只与缓存交互。

### Write-Through

写操作同时写缓存和数据库，缓存与数据库同步更新。

### Write-Behind

写操作先写缓存，异步写数据库。性能高，但可能丢数据。

### 模式对比

| 模式 | 一致性 | 性能 | 复杂度 | 适用 |
|---|---|---|---|---|
| Cache-Aside | 中 | 高 | 低 | 通用 |
| Read-Through | 中 | 高 | 中 | 缓存库 |
| Write-Through | 高 | 中 | 中 | 强一致 |
| Write-Behind | 低 | 最高 | 高 | 可容忍丢失 |

## 16.11 缓存与 API 契约

缓存相关头应被视为契约：

```http
Cache-Control: public, max-age=300, stale-while-revalidate=60
ETag: "catalog-v123"
Vary: Accept-Encoding
```

文档应说明：

- 哪些端点可缓存；
- 缓存时长；
- 是否支持条件请求；
- 数据陈旧的上界；
- 权限与缓存的关系；
- 缓存失效的触发条件。

## 16.12 反模式

- 所有响应都 `no-store`，CDN 形同虚设；
- 所有响应都 `public, max-age=3600`，导致敏感数据泄露；
- ETag 使用弱且不唯一的版本；
- 缓存键忽略租户；
- 写后不失效；
- 缓存故障时直接打垮数据库；
- 用缓存掩盖慢查询，而不优化根因；
- 缓存负结果但 TTL 太长；
- 缓存权限决策但不在变更时失效；
- 多级缓存 TTL 倒挂（上层比下层长）。

## 16.13 本章小结

- 缓存是契约的一部分，应在设计时考虑。
- HTTP 缓存通过新鲜度与验证机制工作。
- ETag/If-Match 同时服务缓存与并发控制。
- 分层缓存需要不同的 TTL、失效和安全策略。
- 私有数据缓存必须严格隔离租户/用户。
- 缓存一致性要明确陈旧上界。
- 穿透、击穿、雪崩需要专门防护。
- 应用缓存模式各有取舍，Cache-Aside 是默认选择。

## 设计练习

为“商品目录 + 库存 API”设计缓存：

- 商品详情可公开缓存；
- 价格因用户等级而异；
- 库存实时性要求高；
- 大促期间流量突增；
- 需要快速失效。

写出 Cache-Control、Vary、ETag、缓存键和失效方案。然后回答：

1. 用户等级影响价格，缓存键如何设计？
2. 大促时如何防止缓存击穿？
3. 库存能否缓存？如果不能，如何降低数据库压力？
4. 价格更新后，用户多久能看到新价格？
