# 第 15 章 限流、配额、并发与成本控制

## 15.1 限流的目的不是“拦住用户”

限流至少服务四个目标：

1. **保护系统**：防止流量压垮数据库、下游服务或自身；
2. **公平性**：防止单个租户/用户占用全部资源；
3. **商业计量**：套餐、配额、超额计费；
4. **安全与滥用防护**：阻止爬取、撞库、短信轰炸、模型滥用。

不同目标需要不同的机制。把所有限制都做成一个“每分钟 100 次”的规则，通常会既伤害正常用户，又挡不住真正的滥用。

### 四种目标对应四种机制

| 目标 | 机制 | 时间尺度 | 典型响应 |
|---|---|---|---|
| 保护系统 | 并发限流、队列、负载削减 | 毫秒~秒 | 429/503 |
| 公平性 | 按租户/用户配额、权重 | 秒~分钟 | 429 |
| 商业计量 | 用量配额、套餐 | 月/年 | 402/429 |
| 安全 | 异常检测、行为限流 | 分钟~天 | 403/429 |

一个成熟的系统通常同时使用多种机制，而不是一个全局阈值。

## 15.2 限流的维度

- 按 IP；
- 按 API Key；
- 按用户；
- 按租户/组织；
- 按端点；
- 按资源（如某个订单）；
- 按操作成本（读 1 点、写 5 点、模型调用按 token）；
- 按并发连接数；
- 按日/月配额；
- 按地理位置/区域；
- 按客户端版本。

### 组合维度

```text
每租户 10,000 次/分钟
每用户 1,000 次/分钟
每端点 2,000 次/分钟
每次请求最多 100 条批量
每租户 5 个并发导出任务
每月 1,000,000 次模型调用
```

组合限流能防止“多个维度都刚好不超”的绕过。

### 维度选择的陷阱

- **只按 IP**：NAT 后的用户共享 IP，会互相误伤；攻击者可以换 IP。
- **只按 API Key**：一个客户多个 key 可以绕过；泄露的 key 会拖垮整个租户。
- **只按端点**：攻击者可以分散到多个端点。
- **只按用户**：服务间调用没有用户身份。
- **只按租户**：单个用户可能拖垮整个租户。

好的限流通常有“租户 + 用户 + 端点 + 成本”的多层结构。

## 15.3 常见算法

### 固定窗口

```text
每分钟计数，窗口结束清零。
```

优点：简单。缺点：窗口边界突发（最后一秒 100 次 + 下一秒 100 次 = 瞬间 200 次）。

适合：粗粒度、低成本的限制。

### 滑动窗口

记录每个请求的时间戳或使用近似桶，计算过去 N 秒的请求数。

优点：平滑。缺点：存储/计算成本高。

实现方式：

- 精确时间戳列表（内存大）；
- 分桶近似（如 10 秒一个桶，6 个桶滚动）；
- Redis ZSET（精确但成本高）。

### 漏桶

请求以固定速率流出，桶满则拒绝或排队。

优点：输出平滑。缺点：突发流量被延迟，不适合低延迟 API。

适合：需要平滑输出的场景，如向第三方发送请求。

### 令牌桶

桶以固定速率补充令牌，请求消耗令牌，桶空则拒绝。

优点：

- 允许一定突发；
- 实现简单；
- 适合 API 限流。

参数：

- `capacity`：桶容量（突发上限）；
- `refill_rate`：每秒补充令牌数。

例子：

```text
capacity = 100, refill_rate = 10/s
空闲 10 秒后，桶满 100；
突然来 100 个请求，全部通过；
之后只能以 10/s 通过。
```

### 并发限流

限制同时处理的请求数，而不是速率。

适合：

- 长任务；
- 数据库连接池；
- 模型推理；
- 大文件上传；
- 慢查询。

并发限流通常用信号量实现。超过上限时：

- 排队（有超时）；
- 拒绝（429/503）；
- 降级。

### 成本加权

每个请求消耗不同配额：

```text
GET /orders          1 unit
POST /orders         5 units
POST /exports        50 units
LLM 1K input tokens  1 unit
```

适合 API 商业化与 AI 成本控制。

### 算法对比

| 算法 | 突发 | 平滑 | 实现复杂度 | 适用 |
|---|---|---|---|---|
| 固定窗口 | 边界突发 | 差 | 低 | 粗粒度 |
| 滑动窗口 | 较平滑 | 好 | 中 | 精确限流 |
| 漏桶 | 无 | 很好 | 中 | 平滑输出 |
| 令牌桶 | 允许 | 好 | 低 | API 限流 |
| 并发 | 不适用 | 不适用 | 中 | 长任务 |
| 成本加权 | 视实现 | 好 | 中 | 商业化/AI |

## 15.4 分布式限流

单机限流简单，但多实例部署需要共享状态。

### Redis + Lua

```lua
-- 令牌桶的简化实现
local key = KEYS[1]
local capacity = tonumber(ARGV[1])
local rate = tonumber(ARGV[2])
local requested = tonumber(ARGV[3])

-- 使用 Redis 服务端时间，避免各实例时钟不一致或客户端伪造时间
local t = redis.call("TIME")
local now = tonumber(t[1]) + tonumber(t[2]) / 1000000

local bucket = redis.call("HMGET", key, "tokens", "last")
local tokens = tonumber(bucket[1]) or capacity
local last = tonumber(bucket[2]) or now

local delta = math.max(0, now - last)
tokens = math.min(capacity, tokens + delta * rate)

local allowed = tokens >= requested
if allowed then
  tokens = tokens - requested
end

redis.call("HMSET", key, "tokens", tokens, "last", now)
redis.call("EXPIRE", key, 3600)
return { allowed and 1 or 0, tokens }
```

注意：

- 原子性；
- 时钟漂移；
- Redis 故障时的降级策略；
- key 的过期与内存；
- 热点 key；
- 多区域一致性。

### 时钟问题

使用客户端时间可能导致：

- 不同实例时钟不一致；
- 攻击者伪造时间；
- 补充速率错误。

应使用 Redis 的 `TIME` 命令或统一时间源。

### Redis 故障时的降级

选项：

- **放行**：保护可用性，但可能压垮后端；
- **拒绝**：保护后端，但影响所有用户；
- **本地限流**：降级为单机限流，精度下降但可用；
- **排队**：缓冲请求，等待 Redis 恢复。

没有一种选择永远正确。应根据业务优先级决定，并在文档中说明。

### 本地 + 全局

- 本地令牌桶做粗粒度保护；
- 全局 Redis 做精确配额；
- 本地允许一定误差，避免每个请求都访问 Redis。

```text
本地：每实例 1000 req/s，超出直接拒绝
全局：每租户 5000 req/s，Redis 精确计数
```

### 多区域

跨区域限流需要：

- 区域本地计数；
- 定期同步；
- 全局配额分配；
- 容忍短暂超限；
- 或使用全局服务（延迟高）。

## 15.5 响应头

常用：

```http
RateLimit-Limit: 1000
RateLimit-Remaining: 42
RateLimit-Reset: 30
Retry-After: 30
```

或结构化：

```http
RateLimit: "default";r=42;t=30
```

需要明确：

- 单位是请求数还是配额单位；
- 窗口是固定还是滑动；
- 多维度限制如何暴露；
- 超额时返回 429 还是 403；
- 重置时间是秒数还是时间戳。

**建议**：使用 `429 Too Many Requests`，带 `Retry-After`，响应体使用标准错误格式并包含限制维度。

### 429 响应示例

```http
HTTP/1.1 429 Too Many Requests
Content-Type: application/problem+json
Retry-After: 30
RateLimit-Limit: 1000
RateLimit-Remaining: 0
RateLimit-Reset: 30
```

```json
{
  "type": "https://errors.example.com/rate-limited",
  "title": "请求过于频繁",
  "status": 429,
  "code": "RATE_LIMITED",
  "detail": "已超过每租户 1000 次/分钟的限制。",
  "meta": {
    "limit": 1000,
    "window": "1m",
    "scope": "tenant",
    "retryAfterSeconds": 30
  }
}
```

### 多维度限制的响应头

如果同时有多个限制：

```http
RateLimit-Policy: "tenant";q=1000;w=60
RateLimit-Policy: "user";q=100;w=60
RateLimit: "tenant";r=42;t=30
RateLimit: "user";r=8;t=30
```

不要让调用方猜测哪个限制触发了。

## 15.6 配额与套餐

限流是短时间保护，配额是长期计量。

```text
Free:   1,000 requests/month
Pro:    100,000 requests/month, 100 req/s
Scale:  10,000,000 requests/month, 1,000 req/s
```

配额设计要考虑：

- 计量单位（请求、token、GB、分钟、订单数）；
- 计量时间（请求开始时还是完成时）；
- 失败请求是否计数；
- 重试是否重复计数；
- 超额行为（拒绝、降速、自动升级、后付费）；
- 配额共享（组织内多项目）；
- 配额结转；
- 时区与账单周期；
- 用量延迟；
- 退款/调整。

### 超额策略

- 硬限制：直接 429；
- 软限制：告警但继续；
- 降速：降低优先级；
- 后付费：继续服务，账单增加；
- 自动升级：需用户授权；
- 按量计费：超出部分单价更高。

### 配额与账单的一致性

常见问题：

- 配额显示剩余 0，但账单还在增加；
- 重试被重复计数；
- 失败请求被计费；
- 跨时区账单周期不一致；
- 缓存命中被计费；
- 内部调用被计费。

配额系统应与计费系统使用同一套计量事件，避免双口径。

### 计量事件

```json
{
  "eventId": "usage_123",
  "tenantId": "t_123",
  "meter": "api.requests",
  "quantity": 1,
  "unit": "request",
  "occurredAt": "2026-11-26T10:00:00Z",
  "recordedAt": "2026-11-26T10:00:01Z",
  "idempotencyKey": "req_abc:api.requests",
  "attributes": {
    "endpoint": "POST /orders",
    "status": 201
  }
}
```

计量事件应：

- 幂等；
- 可重放；
- 可审计；
- 带租户；
- 带计量维度；
- 有延迟但可接受。

## 15.7 成本控制与 AI

LLM API 的成本与 token 数相关，传统“请求数限流”不够。

需要：

- 输入/输出 token 分别计量；
- 按模型定价；
- 按租户预算；
- 单次请求最大 token；
- 并发请求限制；
- 缓存命中折扣；
- 滥用检测（提示注入、批量生成）；
- 预算告警与熔断；
- 失败/拒绝是否计费。

```json
{
  "usage": {
    "inputTokens": 1200,
    "outputTokens": 350,
    "cachedInputTokens": 800,
    "costUsdMicros": 12300
  }
}
```

> LLM 单次成本可能小于 1 分钱。金额不要用浮点数；可以用最小货币单位整数，或像这里用微单位整数（百万分之一美元），并在契约中写明单位。

### AI 限流的特殊性

- 成本在请求完成前未知；
- 输出长度不可控；
- 流式响应可能中途取消；
- 同一请求可能重试；
- 缓存命中降低成本；
- 模型升级改变成本；
- 推理 token 可能隐藏计费。

### 预算熔断

```text
租户月预算 $1000；
达到 80% 告警；
达到 100% 拒绝新请求或降级到便宜模型；
管理员可临时提额。
```

预算熔断应：

- 实时或准实时；
- 可配置；
- 可覆盖；
- 有审计；
- 不影响已开始的请求。

### 防滥用

- 单用户并发限制；
- 单 IP 限制；
- 异常模式检测；
- 内容审核；
- 账号年龄/信用；
- 验证码；
- 人工审核。

## 15.8 公平性与优先级

- 大客户与小客户共享资源时，按权重分配；
- 付费用户优先；
- 内部服务与外部流量隔离；
- 关键业务预留容量；
- 批处理使用低优先级队列。

### 加权公平队列

```text
租户 A 权重 5
租户 B 权重 2
租户 C 权重 1
总容量 1000 req/s
→ A 最多 625，B 250，C 125（有空闲时可借用）
```

### 优先级

```text
P0：支付、登录、健康检查 → 保留 40% 容量
P1：核心查询 → 40%
P2：报表、导出 → 15%
P3：批处理、分析 → 5%
```

### 负载削减

当系统过载时，主动拒绝低优先级请求，保护核心功能。

```text
优先级 0：支付、登录 → 保留
优先级 1：查询 → 降级/缓存
优先级 2：报表、导出 → 拒绝
```

负载削减应：

- 基于实时指标；
- 有明确阈值；
- 可手动触发；
- 有告警；
- 快速恢复。

## 15.9 反模式

- 只按 IP 限流，误伤 NAT 后的用户；
- 只按 API Key 限流，忽略租户；
- 所有端点同一阈值；
- 429 不返回 `Retry-After`；
- 限流阈值不可配置；
- 没有监控限流命中率；
- 配额与账单不一致；
- 重试请求重复计数导致客户被误伤；
- 限流状态存储故障时直接放行或全部拒绝，没有预案；
- 限流在网关做，但内部调用绕过；
- 只限流不排队，导致突发全部失败；
- 免费层无限，被滥用拖垮成本。

## 15.10 本章小结

- 限流服务保护、公平、计量和安全四个目标。
- 维度应组合使用，避免单点绕过。
- 令牌桶适合 API，并发限流适合长任务，成本加权适合 AI。
- 分布式限流需要原子性、时钟和故障降级设计。
- 429 要带 `Retry-After` 和明确错误。
- 配额与账单必须一致，失败/重试的计量规则要明确。
- 过载时要能分级降级。
- AI 成本控制需要 token 计量、预算熔断和防滥用。
- 从计量事件到发票、收入确认与对账的完整链路，见[附录 V](../appendices/v-metering-billing.md)。

## 设计练习

为“AI 图像生成 API”设计限流与配额：

- 免费用户、付费用户、企业客户；
- 按请求数、并发数、生成像素/张数计量；
- 高峰期保护；
- 滥用检测；
- 预算熔断。

写出限制维度、响应头、错误码和降级策略。然后回答：

1. 生成失败是否计费？
2. 用户取消生成，已消耗的算力如何计费？
3. 高峰期如何保护付费用户？
4. 如何防止一个用户用多个账号绕过免费额度？
