# 前言：为什么 API 设计是一门独立学科

## 一次看似简单的接口变更

设想一个团队要修改订单接口中的一个字段：

```diff
- "status": "PAID"
+ "status": "paid"
```

在代码评审里，这几乎是微不足道的改动。数据库里的枚举没有变，业务逻辑没有变，测试甚至可能全部通过。但对调用方而言，字符串比较、状态机映射、报表分组、Webhook 过滤器、移动端缓存、合作伙伴的对账脚本，都可能在同一时刻失效。

更麻烦的是，这类变更往往不会以“报错”的形式出现。它可能让某个下游把已支付订单当成未支付，把退款重试三次，或者在财务报表里悄悄少算一笔收入。API 的错误会被放大，因为它跨越了组织边界：**你不知道谁在依赖你，也常常无法强迫对方立刻升级。**

这就是 API 设计的第一条现实：**发布不是终点，而是承诺的开始。**

## 三个视角，同一个对象

同一份 API，在不同人眼里是完全不同的东西。

**工程师看到的是契约。** 请求方法、路径、字段类型、状态码、错误结构、超时、幂等性、版本策略。契约的价值在于“可验证”：双方可以独立实现，并通过测试确认彼此理解一致。

**架构师看到的是边界。** 哪些能力属于哪个团队，哪些数据可以跨域流动，哪些失败必须被隔离，哪些一致性只能做到最终一致。API 是把组织切面固化成技术切面的工具。康威定律之所以反复应验，不是因为组织决定架构，而是因为**接口天然会复制沟通结构**。

**产品与商业负责人看到的是产品。** 开发者是不是能在十分钟内完成第一次调用？用量如何计费？免费额度能否形成转化？合作伙伴为什么选择你而不是自建？API 的留存、扩展和生态效应如何衡量？

这三种视角并不冲突，反而是同一枚硬币的三面。只懂协议的人会设计出“语法正确但没人想用”的接口；只懂业务的人会承诺系统无法兑现的 SLA；只懂架构的人可能把一次简单查询做成需要三支团队排期的分布式事务。

本教程的核心主张是：

> **好的 API 设计，是在明确约束下，同时照顾契约、边界与产品三种视角的持续决策过程。**

## 为什么现在更需要这门学科

过去十年，API 从“系统集成手段”变成了“产品交付方式”。今天几乎所有的软件能力都以某种 API 形态存在：云资源、支付、地图、消息、模型推理、数据检索、身份认证，甚至是 Agent 的工具。

与此同时，API 的消费者发生了三次迁移：

1. **从内部到外部。** 早期 API 主要供同一公司的系统调用；现在它直接面对合作伙伴、开发者和最终用户。
2. **从人到机器。** OpenAPI 文档、SDK、开发者门户原本是给人看的；现在它们还要被代码生成器、API Agent 和工具调用协议读取。
3. **从单次调用到持续协作。** Webhook、事件流、长任务、实时连接让 API 从“请求—响应”变成“持续状态同步”。

AI 的加入让第三点变得尤其明显。当一个大模型 Agent 调用你的 API 时，它不会阅读你的营销页面，也不会容忍含糊的错误信息。它依赖的是：工具描述是否准确、参数 schema 是否严格、错误是否可恢复、权限边界是否清晰、操作是否幂等、结果是否可验证。**API 设计中的含糊，在 Agent 时代会直接变成错误行为。**

## 这门学科包含什么

API 设计不是“HTTP + JSON”的同义词。它至少包含八个相互作用的层面：

| 层面 | 核心问题 | 典型产出 |
|---|---|---|
| 领域 | 世界如何被切分？哪些概念有身份和生命周期？ | 资源模型、状态机、领域事件 |
| 契约 | 双方如何确认理解一致？ | OpenAPI / Protobuf / GraphQL SDL / JSON Schema |
| 协议 | 用什么承载调用与事件？ | HTTP、gRPC、WebSocket、消息队列 |
| 安全 | 谁可以做什么，在什么条件下？ | 认证、授权、租户隔离、审计 |
| 运行 | 失败时系统如何表现？ | 超时、重试、限流、熔断、降级 |
| 工程 | 如何保证质量与可演进？ | 实现架构、测试、CI、契约检查、可观测性 |
| 产品 | 开发者如何理解并愿意使用？ | 文档、SDK、沙箱、定价、支持 |
| 商业 | 价值如何被度量与捕获？ | 用量计量、套餐、单位经济、生态 |

书中的章节大致沿着这八个层面展开，但它们不是孤立的模块。一个定价决策会改变限流设计；一个多租户模型会改变授权与缓存键；一个事件契约会改变版本策略；一次 AI 工具接入会重新定义错误信息的消费者。

## 一条贯穿全书的设计循环

面对一个新 API，不要从“用 GET 还是 POST”开始。更可靠的顺序是：

1. **识别消费者与任务。** 谁在什么场景下，为什么需要这个能力？
2. **划定边界。** 哪些数据与不变量属于这个上下文？哪些失败必须由调用方处理？
3. **建立领域语言。** 用业务词汇命名资源、状态和事件，而不是数据库词汇。
4. **选择交互风格。** 请求—响应、事件、流、批量、异步任务，按任务形态选择。
5. **写契约。** 先写示例和 schema，再写实现。
6. **做对抗性评审。** 假设调用方会重试、并发、传错、断网、被攻击、几年不升级。
7. **验证。** 契约测试、负载测试、故障注入、安全测试、真实开发者试用。
8. **上线并观测。** 用 Trace、指标、错误率和支持工单验证假设。
9. **演进。** 通过扩展—收缩、弃用和迁移管理生命周期。

这条循环会在每一章以不同形式出现。你不需要一次记住所有细节，但应该逐渐把它变成直觉。

## 关于“最佳实践”

书里会出现很多“应该”。请把它们理解为**有条件的默认值**，而不是不可质疑的教条。

例如，“用复数名词命名资源”在大多数 REST API 中成立，但在 RPC 风格中可能完全不适用；“所有写操作都要幂等”在支付场景是硬要求，在某些低价值日志写入中则可能不值得成本；“公开 API 必须版本化”对快速迭代的内部接口未必成立，因为你可以协调所有消费者。

真正可迁移的能力，是判断：

- 这个约束在这里成立吗？
- 违反它的代价由谁承担？
- 如果未来要改，代价有多大？
- 有没有更便宜的方式获得同样的确定性？

## 本书的技术基准

教程以 2026 年的技术 landscape 为背景，但刻意避免把内容绑定到某个版本或供应商。涉及具体标准时，优先使用稳定且广泛采用的部分：

- HTTP 语义以 RFC 9110 系列为基础；QUERY 方法以 2026 年发布的 RFC 10008 为代表；
- 错误格式以 RFC 9457（Problem Details）为代表；
- 契约描述以 OpenAPI 3.2（向后兼容 3.1）、AsyncAPI 3.x、Protobuf、GraphQL SDL 为主；OpenAPI 4.0 “Moonwalk” 尚未发布，书中不把它当作可用基线；
- 可观测性以 OpenTelemetry 的概念模型为主；
- 形式化与验证以状态机、不变量、性质测试、TLA+/Alloy 的工程化用法为主，不要求读者具备数学证明背景；
- 数据契约以“schema + 语义 + 新鲜度 + 质量 + 所有权”为核心，具体标准（Data Contract Spec、ODCS 等）只作参考，不作为唯一答案；
- AI 工具协议以 MCP 2026-07-28 修订与 A2A 1.0 的设计问题为主，而不是逐条复述字段。MCP 在这一版中从“有状态会话”转向无状态请求上下文，A2A 已发布 1.0 并支持多种绑定；Agent 支付（x402、AP2 等）仍处于早期，书中只讨论其契约问题，不把任何方案当作定论；
- 合规部分以“义务 → API 能力 → 证据”的工程映射为主，具体法律适用与时限以法务意见和官方文本为准；
- 密码学部分以 TLS 1.3、RFC 9421（HTTP Message Signatures）、RFC 9530（Content-Digest）、FIPS 203/204/205 与 NIST IR 8547 的公开文本为参考；后量子迁移时间线只作规划假设，不构成合规承诺；
- 序列化部分以 JSON（RFC 8259）、JCS（RFC 8785）、CBOR（RFC 8949）、Protobuf、Avro 与 JSON Schema 2020-12 为基线；性能与压缩结论要求读者用自有数据复测，书中不把厂商基准当定论；
- 隐私增强部分以差分隐私的形式化定义与组合、聚合阈值、MPC/TEE/同态加密/联邦学习的威胁模型为参考；ε、δ 与 k 的取值属于政策、伦理与合规判断，书中只给工程方法、代价与边界，不构成法律意见；
- 基础语义部分以 RFC 3339 / ISO 8601、IANA 时区数据库、ISO 4217、SI / UCUM、RFC 9562（UUIDv7）、BCP 47、Unicode UAX 系列与 CLDR 为基线；具体的业务日历、舍入模式、分摊规则与税率由契约声明，不能靠“行业惯例”默认；
- 行业垂直部分以 FHIR R4/R5、SMART App Launch、OBIE / Berlin Group / FDX、TM Forum Open API、CAMARA、OPC UA、MQTT Sparkplug B、COVESA VSS 的设计问题为主，具体版本与认证要求以各标准组织与监管机构的官方文本为准；
- 沙箱与测试数据部分以 OpenAPI/AsyncAPI mock、状态化 mock、测试时钟、数据工厂与合成数据的工程实践为主；具体工具只作参考，保真度要求由契约与风险决定；
- 实验与渐进发布部分以特性开关、稳定分桶、曝光日志和 SLI 驱动回滚的工程方法为主；统计显著性与实验周期应结合样本量、业务周期和团队分析能力判断；
- 基础设施 API 部分以 Terraform Plugin Framework、Kubernetes CRD（`apiextensions.k8s.io/v1`）与 Argo CD / Flux 的公开行为为参考；具体 Provider、云厂商 API 与集群版本以官方文档为准。

标准会演进，供应商会消失，但“如何让两个独立系统在不确定环境中可靠协作”这个问题不会消失。

## 最后

API 设计最迷人的地方，在于它同时要求**精确**与**克制**。

精确，是因为每个字段、每个状态码、每个错误分支都可能成为别人的生产依赖。克制，是因为每增加一个概念、一种风格、一个可选参数，都会增加理解成本和长期维护成本。

好的 API 不是“功能最多”的 API，而是让正确的事情容易做、错误的事情难以做、未来的变化可以承受的 API。
