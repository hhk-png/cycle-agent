# 第 44 章 商业分析 II：TCO 与成本模型

> 本章数字均为**示例假设**，用于展示计算框架，不是报价。实际价格随地区、
> 合同、GPU 代际、利用率和电价变化。

## 44.1 训练成本的四个乘数

```text
训练成本 ≈ GPU-hours × $/GPU-hour × (1 + 失败/重试) × (1 + 数据/人力/存储)
```

GPU-hours 由模型、token 数、硬件、MFU 决定：

```text
FLOPs ≈ 6ND
GPU-hours ≈ FLOPs / (GPU峰值 × MFU × 3600)
```

例子：70B 模型，2T token，1000×H100，MFU=40%：

```text
FLOPs = 6 × 70e9 × 2e12 = 8.4e23
有效算力 = 1000 × 989e12 × 0.4 = 3.96e17 FLOP/s   # H100 SXM bf16 dense
时间 = 8.4e23 / 3.96e17 ≈ 2.12e6 秒 ≈ 24.6 天
GPU-hours ≈ 1000 × 24.6 × 24 ≈ 5.9e5
```

按 $2.5/GPU-hour（示例）≈ **148 万美元**。若 MFU 从 40% 降到 30%，时间约
32.8 天、成本约 197 万美元；若故障/重试 10%，再加约 15 万。**MFU 和稳定性
直接等于钱。**

> 口径提醒：如果误把 H100 的 TF32 dense 峰值 `495 TFLOP/s` 当成 BF16，成本
> 会被高估一倍。MFU 的分母必须是所用精度的 dense 峰值。

### 44.1.1 成本敏感性：哪个变量最值钱

以 70B/2T tokens/1000×H100 为基线，单变量变化：

| 变量 | 基线 | 变化 | 训练时间 | 成本变化 |
|---|---:|---:|---:|---:|
| MFU | 40% | 30% | 24.6 → 32.8 天 | +33% |
| MFU | 40% | 50% | 24.6 → 19.7 天 | -20% |
| 失败/重试 | 0% | 10% | — | +10% |
| 失败/重试 | 0% | 30% | — | +30% |
| GPU 单价 | $2.5/h | $2.0/h | 不变 | -20% |
| GPU 单价 | $2.5/h | $3.5/h | 不变 | +40% |

结论：MFU、故障率和单价都是乘法因子。区别在于**可控性**：MFU/故障率通常能
通过软件与运维改善，单价多是合同/市场决定的外生变量。因此“先优化 MFU 和
故障率”成立的前提是它们仍有改善空间；如果 MFU 已接近硬件上限，继续压单价
或提高利用率才是主要杠杆。

## 44.2 自建 TCO

一个 8×H100 节点的示例（仅用于建模）：

| 项 | 示例值 | 说明 |
|---|---:|---|
| 节点 capex | $350k | GPU/CPU/内存/网卡/机箱 |
| 折旧年限 | 3 年 | 会计/实际可用寿命 |
| 年电费 | $6k–10k | 8×H100 IT 功耗 8–10 kW + PUE（44.2.3） |
| 网络/存储分摊 | $20k–50k/年 | IB/并行存储 |
| 运维/平台人力 | capex 的 15%–30%/年 | 小团队更高 |
| 利用率 | 50%–80% | 研究/训练负载 |

每 GPU-hour 成本（简化）：

```text
annual = capex/3 + power + network + staff
gpu_hours = 8 × 8760 × utilization
cost_per_gpu_hour = annual / gpu_hours
```

capex $350k、3 年、电费 $8k、网络 $30k、人力 $70k：

```text
annual ≈ 116.7k + 8k + 30k + 70k = 224.7k
gpu_hours = 8 × 8760 × 0.7 ≈ 49,056
≈ $4.58/GPU-hour
```

如果利用率 40%，成本升到约 $8/GPU-hour；如果人力/网络更高，还会升。**自建
不一定比云便宜**，尤其当利用率低、团队小、硬件迭代快时。

### 44.2.1 盈亏平衡利用率

把自建和云的每 GPU-hour 成本相等，解出盈亏平衡利用率：

```text
capex/3 + power + network + staff
--------------------------------- = cloud_price
8 × 8760 × utilization

utilization* = annual_cost / (8 × 8760 × cloud_price)
```

用前面的例子（annual ≈ $224.7k，云价 $2.5/GPU-hour）：

```text
utilization* = 224,700 / (8 × 8760 × 2.5) ≈ 1.28 → 128%
```

这说明在该假设下，自建即使 100% 利用率也比 $2.5/h 的云贵；如果云价是
$4.5/h，盈亏平衡约 71%。**先算这个数，再谈“自建更便宜”**。

### 44.2.2 三年现金流与残值

自建不是一次性 capex，而是：

```text
year 0: -capex
year 1..3: -power -network -staff + 折旧税盾
year 3: +残值（若有）
```

云则是逐年 opex。比较时要用 NPV/IRR，而不是“三年总价”：

```text
NPV = Σ (cashflow_t / (1+r)^t)
```

GPU 代际更新快，3 年后的残值可能很低；如果 2 年就落后，折旧假设要更激进。
很多“自建更便宜”的结论，来自把残值/人力/利用率假设得过好。

### 44.2.3 电、冷却与机房：被低估的 capex/opex

8×H100 节点的**IT 功耗**常见 8–10 kW（GPU 700W×8 + CPU/内存/网卡/风扇），
再加 PUE（1.2–1.5）和配电/冷却余量，机房侧常见 10–15 kW/节点。1000 卡
（125 节点）、9 kW/节点、PUE 1.3、$0.08/kWh 时，年电费约
**$1.02M/年**；完整推导与敏感性表见 I.3.1，这里不重复。

容易被漏掉的不只是电费：变压器/配电改造、液冷/风冷、机架承重、消防、
带宽/跨区传输。很多 TCO 表只写 GPU 价格和电费，漏掉**配电容量**和
**冷却改造**，导致“自建便宜”的结论在落地时反转。

### 44.2.4 资金成本、折旧与残值

自建是重资产：钱先花出去，折旧分期摊。比较时必须考虑：

- **资金成本**：同样的钱如果用于业务/投资，回报率是多少？用 WACC/利率
  折现，而不是无风险利率。
- **折旧年限**：GPU 代际 1.5–2 年就落后，会计 3 年折旧可能仍偏乐观；
  残值假设要保守。
- **技术过时**：新卡能效/吞吐更高，旧卡即使还能用，单位 token 成本也会
  被拉开。
- **合同灵活性**：云/长约/预留/spot 的价格和锁定程度不同；自建锁定的是
  硬件和机房。

一个实用的敏感性表：

| 假设 | 悲观 | 基准 | 乐观 |
|---|---:|---:|---:|
| 利用率 | 30% | 60% | 80% |
| 折旧年限 | 2 年 | 3 年 | 4 年 |
| 电价 $/kWh | 0.12 | 0.08 | 0.05 |
| 残值 | 0% | 10% | 25% |
| 人力/年 | 高 | 中 | 低 |

如果结论只在“乐观列”成立，就不要把它当成决策依据。

## 44.3 云 vs 自建

| 维度 | 云 | 自建 |
|---|---|---|
| 前期 capex | 低 | 高 |
| 单价 | 高（含利润/运维） | 低（高利用率时） |
| 弹性 | 强 | 弱 |
| 最新硬件 | 快 | 采购/交付周期 |
| 合规/数据主权 | 依赖云 | 可控 |
| 运维 | 云负责 | 自建团队 |
| 锁定 | 云 API/网络 | 硬件/软件栈 |

决策因素：

- 训练任务是否连续/大规模（自建更划算）；
- 是否需要最新 GPU（云更快）；
- 团队是否有集群/调度/NCCL 能力；
- 合规/数据驻留；
- 云的当量单价与自建 break-even 利用率。

break-even 的算法是

```text
u* = 自建年成本 / (卡数 × 8760 × 云 $/GPU-hour)
```

仍以上面的 8 卡节点（年成本 $224.7k）为例：云价 $3/h 时需要 `u* ≈ 107%`
（不可能），$4/h 时需要 80%，$4.6/h 时需要 70%。也就是说，**在 $3/h 的云价
面前，这个自建模型满负荷也不便宜**；自建的成本理由必须来自更低的 capex、
更高的云价，或云无法提供的合规/可控性。

## 44.4 推理成本

推理成本按 token：

```text
$/1M tokens = (GPU $/hour) / (tokens/s × 3600) × 1e6 / 利用率
```

示例：8 卡节点 $4/GPU-hour（$32/节点-hour），吞吐 20k tokens/s，利用率 70%：

```text
每小时 token = 20,000 × 3600 × 0.7 = 50.4M
$/1M tokens ≈ 32 / 50.4 ≈ $0.63
```

实际还要加：

- KV cache 显存/带宽；
- prefill vs decode 成本差异；
- 批处理/延迟 SLA；
- 模型大小/量化/MoE；
- 网络/存储/冷启动。

推理的规模效应很强：利用率从 30% 到 70%，单位成本降一半以上。

### 44.4.1 推理成本的 TTFT/TPOT 分解

推理不是单一吞吐，至少两类请求：

- **prefill 主导**：长 prompt，成本 ≈ `prompt_tokens / prefill_tokens_per_s`；
- **decode 主导**：长输出，成本 ≈ `output_tokens / decode_tokens_per_s`。

一个请求的总成本可以近似为：

```text
cost ≈ (prefill_FLOPs / prefill_throughput + decode_FLOPs / decode_throughput)
       × $/GPU-hour / 3600
```

其中 decode 往往受 **KV cache 带宽**限制，而不是算力；这就是 GQA/MLA、量化
KV、PagedAttention 的价值。容量规划时分别测：

```text
TTFT(p50/p99)、TPOT(p50/p99)、tokens/s/GPU（prefill/decode 分开）
```

只看“总 tokens/s”会把 prefill 的高吞吐误当成 decode 能力。

### 44.4.2 序列长度与 KV cache 的成本敏感性

推理成本不是只随“模型大小”变，序列长度会通过 KV cache 和 attention
计算放大成本：

```text
KV bytes/token ≈ 2 · L · n_kv · d · bytes
attention FLOPs/token ≈ 4 · L · n_h · d · s   # 非因果上界
```

以 80 层、8 KV heads、d=128、bf16 为例，KV 约 0.32 MB/token；32K 上下文
就是约 10 GB/请求。并发 64 个请求、每个 32K，KV 就需要 640 GB，超过多数
单机显存，必须靠 TP/量化/分页/offload。结果：

- **长上下文推理的 capex 往往由 KV 决定，不是权重**；
- 同样的 tokens/s，长上下文请求的 $/1M tokens 可能高一个数量级；
- GQA/MLA/FP8 KV/prefix cache 的收益要按“能多放多少并发”算，而不是只看
  单请求显存。

容量规划时至少跑三档序列长度（如 4K/32K/128K），分别测 TTFT、TPOT、
tokens/s/GPU 和最大并发，再做加权成本。

### 44.4.3 推理的单位经济：价格、毛利与 goodput

知道 $/1M tokens 只是成本的一半；商业化还要看售价、毛利和 SLO：

```text
gross_margin = (price_per_1M - cost_per_1M) / price_per_1M
goodput = 满足 TTFT/TPOT SLO 的 output_tokens/s
cost_per_1M = GPU $/h / (goodput × 3600) × 1e6 / utilization
```

**口径必须先定义**：如果 `goodput` 按**墙钟时间**平均（已经包含空闲/低载
时段），公式里不要再除 `utilization`；如果按**忙碌服务时间**平均（只统计
有请求在跑的时间），才需要除以 `utilization` 换算到墙钟成本。两种写法差
`1/utilization` 倍，是推理成本表最常见的 2–3 倍误差来源。下面默认 goodput
是“忙碌时间”口径。

关键点：

- **用 goodput，不用峰值吞吐**：为了满足 p99 延迟，实际 batch 往往小于
  峰值 batch；
- **输入/输出比**：长 prompt 的 prefill 成本高但输出计费少，定价要区分
  input/output token；
- **cache 命中率**：prefix cache 命中可显著降低 prefill 成本，但会改变
  毛利率结构；
- **利用率**：30% → 70% 可能让单位成本降一半以上，但需求不足时降价换量
  未必改善毛利；
- **MoE/量化**：降低单 token 成本，但可能增加工程/质量风险。

一个简单的敏感性表：

| 变量 | 变化 | 对 $/1M 的影响 |
|---|---|---|
| goodput | -30% | +43% |
| GPU 单价 | +20% | +20% |
| 利用率 | 70%→40% | +75% |
| prefix 命中率 | 0→50% | prefill 成本近似减半（取决于输入占比） |
| 输出长度 | ×2 | decode 成本约 ×2 |

定价低于成本不是“规模效应”，是补贴；大规模推理的毛利必须建立在可测的
goodput 和利用率上。

### 44.4.4 后训练与 RL 的 TCO：rollout 才是大头

预训练的成本是“一次性的 GPU-hours × 单价”；后训练的成本结构不同：

```text
SFT/DPO ≈ 训练 GPU-hours + 数据标注/清洗
RL(GRPO/PPO) ≈ rollout 推理成本 + 策略更新 GPU-hours
              + reward/评测 + 权重同步 + 被丢弃的样本
```

**SFT。** 与预训练同口径，只是 token 少、epoch 多：

```text
GPU-hours ≈ 6 · N · tokens · epochs / (峰值 · MFU · 3600)
```

8B 模型、1B token、3 epoch、MFU 40%、1000×H100：
`6·8e9·1e9·3 ≈ 1.44e20 FLOPs`，约 100 GPU-hours（量级），成本远低于预训练；
真正的成本往往在数据标注、去重、评测和反复实验。

**DPO。** 每个偏好对要做 policy（可训练）与前向 reference（可冻结/预计算）
的 log-prob；reference 若能预计算并缓存，成本接近 SFT；否则每个 pair 多一次
前向。长 response、多轮对话会把序列长度和显存拉高，不能只按 pair 数估。

**RL/GRPO。** 成本由 rollout 主导。设每轮 `P` 个 prompt、每个 `G` 个
rollout、平均输出 `L_out` token、输入 `L_in`：

```text
rollout_tokens ≈ P · G · (L_in + L_out)
rollout_cost   ≈ rollout_tokens/1e6 × 推理 $/1M tokens / goodput
update_flops   ≈ 6 · N · rollout_tokens        # 只算被采用的轨迹
update_hours   ≈ update_flops / (峰值 · MFU · 3600)
```

例子（仅示意）：`P=10k, G=8, L_in=1k, L_out=4k` → 400M token/轮；
若推理成本 $0.5/1M、goodput 70%，rollout 约 $286/轮；100 轮约 $28.6k。
策略更新 8B 模型对 400M token 约 `6·8e9·4e8=1.92e19` FLOPs，约 13.5
GPU-hours/轮（1000 卡），按 $2.5/GPU-h 约 $34/轮。**rollout 和“被丢弃的
轨迹”才是预算的主要不确定性**：本例中 rollout 约 $286/轮，是更新的 8 倍。

**colocated vs disaggregated。**

| 形态 | 优点 | 代价 |
|---|---|---|
| colocated（训练/rollout 同卡） | 无 KV/权重传输，资源复用 | 显存争抢、sleep/wake、利用率切换损失 |
| disaggregated（独立推理集群） | 各自调优、推理可弹性 | 权重同步、KV 传输、网络与队列 |

权重同步的成本容易被忽略：一次全量 `N` 参数 bf16 同步是 `2N` 字节；8B
模型约 16 GB，经 100 GB/s 链路约 0.16 s，但每轮同步一次、还要等所有副本
就绪，实际开销取决于拓扑和并行切分。LoRA/增量同步能降低这部分，但会改变
训练动态。

**goodput 的定义。** RL 的“有效产出”不是生成的 token 数，而是**通过过滤/
奖励门槛、可用于更新的轨迹数/小时**。截断、重复、低奖励、解析失败都会降低
goodput；只按 GPU 利用率或 tokens/s 看，会高估产能。预算表至少要有：

```text
[ ] rollout tokens/轮、采用率、平均长度分布
[ ] 推理 $/1M（含 KV cache/批处理/量化假设）
[ ] 策略更新 GPU-hours/轮、MFU
[ ] reward/评测/解析成本
[ ] 权重同步频率与每次字节数
[ ] 失败/重跑/过滤导致的额外轮次
```

## 44.5 隐藏成本

- **失败/重试**：千卡训练每周故障，重跑/恢复；
- **数据**：清洗/标注/存储/合规；
- **人才**：分布式系统/编译器/性能工程师稀缺；
- **机会成本**：晚上市 3 个月；
- **锁定**：CUDA/TE/云 API；
- **安全/合规**：审计/隔离/许可证；
- **闲置**：采购过度/任务不连续。

### 44.5.1 失败成本模型

千卡训练的失败不是“偶发事件”，而是成本项：

```text
期望浪费 = 失败次数 × (检测时间 + 恢复时间 + 丢失进度) × GPU 成本
         + 重跑数据/评估成本
```

例子：1000 卡，$2.5/GPU-hour，每周 1 次故障，平均检测 10 分钟、恢复 20 分钟、
丢失 30 分钟进度：

```text
每次浪费 ≈ (10+20+30)/60 h × 1000 × 2.5 ≈ $2,500
一年 ≈ $130k
```

这还没算“故障导致实验错过窗口”的机会成本。降低故障率（检查点、监控、
自动恢复）通常比谈 GPU 单价更有杠杆。

## 44.6 一个决策框架

```text
如果 训练任务 > 6–12 个月连续、利用率 > 60%、团队有集群能力
    → 自建/长期云合约
否则如果 任务波动、需要最新硬件、团队小
    → 云/按需
如果 合规/数据主权强
    → 私有云/一体机
如果 只做微调/推理
    → 托管 API/推理服务，不必自建训练集群
```

## 44.7 三种情景：乐观、基准、悲观

| 情景 | 利用率 | 故障率 | 云价 | 自建 $/GPU-h（含失败） | 结论 |
|---|---:|---:|---:|---:|---|
| 乐观 | 80% | 5% | $4/h | `224.7k/(8·8760·0.8)·1.05 ≈ $4.21` | 自建略贵；长约/合规可能胜出 |
| 基准 | 60% | 15% | $3/h | `224.7k/(8·8760·0.6)·1.15 ≈ $6.15` | 云便宜约 51% |
| 悲观 | 30% | 30% | $2/h | `224.7k/(8·8760·0.3)·1.30 ≈ $13.9` | 云/按需明显更便宜 |

表中 MFU 不进入 $/GPU-hour 的计算；它决定**完成一个任务需要多少
GPU-hours**。因此“每 GPU-hour 自建 vs 云”和“单任务总成本”是两个问题：
前者只看利用率/故障/价格，后者还要乘 `1/MFU`。如果把 MFU 50%/40%/30%
也塞进 per-hour 对比，会把两个口径混在一起。按单任务比较时，直接算
`任务 GPU-hours = FLOPs/(峰值·MFU·3600)`，再乘含失败的 $/GPU-h。

做法不是“选一个情景赌”，而是：

1. 给每个变量一个区间；
2. 做敏感性分析，找出结论翻转的临界点；
3. 设计合同/架构保留切换权（预留+按需混合、多云、可迁移 checkpoint）；
4. 每季度用实际数据重算。

## 44.8 本章小结

- 训练成本由 GPU-hours × 单价 × 失败/隐藏成本决定；MFU 是核心杠杆。
- 自建 TCO 要算折旧/电/网络/人力/利用率，并用盈亏平衡利用率检验。
- 云 vs 自建要用 NPV/现金流和敏感性分析，不只看单价或三年总价。
- 推理按 token 成本 = GPU 单价 / 有效吞吐；prefill/decode 要分开测。
- 隐藏成本（数据/人才/故障/锁定）常被低估。
- 决策看任务连续性、利用率、团队能力、合规，并保留切换权。
