# 第 45 章 商业分析 III：自建、云、托管与竞争

## 45.1 四种交付形态

| 形态 | 典型 | 适合 |
|---|---|---|
| 自建集群 | 买 GPU/建机房/自研平台 | 大模型公司、主权 AI、长期高利用率 |
| 云 IaaS | 租 GPU/IB/存储 | 弹性训练、短期项目、最新硬件 |
| 托管训练 | SageMaker/Vertex/NeMo/云 AI 平台 | 团队小、要 SLA/集成 |
| API/推理服务 | OpenAI/Anthropic/Together/Fireworks 等 | 只做应用、不想碰基础设施 |

Megatron 在四种形态中的角色不同：

- 自建：核心训练框架；
- 云 IaaS：镜像/托管服务的一部分；
- 托管训练：平台封装 Megatron/NeMo；
- API：通常不直接暴露 Megatron，但后端可能用类似技术。

## 45.2 自建的门槛

技术：

- 集群设计（GPU/IB/存储/供电/散热）；
- 调度（Slurm/K8s）、配额、多租户；
- NCCL/网络调优；
- 故障检测/恢复；
- 训练框架/检查点/监控。

组织：

- 分布式系统/性能工程师；
- 运维/值班；
- 安全/合规；
- 采购/供应链。

经济：

- 利用率 >50%–60% 才可能比云便宜；
- 硬件 3 年折旧，GPU 代际更新快；
- 电价/机房/网络长期成本。

### 45.2.1 自建成熟度模型

| 级别 | 能力 | 典型表现 |
|---|---|---|
| L0 | 单机/少量 GPU | 手工跑脚本，无调度 |
| L1 | 单集群 + Slurm | 能跑多机，故障靠人 |
| L2 | 监控/检查点/配额 | 有值班和恢复流程 |
| L3 | 自动化/多租户 | 自助提交、计费、隔离 |
| L4 | 弹性/多集群 | 故障自愈、跨云调度 |

大多数企业不需要 L4；L2 就能支撑稳定的中等规模训练。跳到 L4 的代价常被
低估：多集群一致性、网络、数据同步、安全审计都是长期投入。

## 45.3 云的优势与锁定

优势：

- 快速获得最新 GPU；
- 弹性扩缩；
- 免运维；
- 全球区域/合规；
- 托管服务（存储/网络/监控）。

锁定：

- 专有加速器（Trainium/TPU）与 CUDA 不兼容；
- 云厂商的托管训练 API/格式；
- 网络/存储/身份体系；
- 出口流量/数据迁移成本。

缓解：

- 用 Hugging Face/ONNX 等开放格式；
- 训练/推理栈可移植；
- 多集群/多云策略；
- 保留自建能力/备份。

### 45.3.1 锁定成本的量化

锁定不是“能不能迁”，而是“迁一次要多少钱/多久”：

```text
迁移成本 ≈ 数据出口费 + 重新调优人力 × 时间 + 停机损失
         + 重新验证/评测成本 + 合同违约/最低消费
```

一个可操作的指标是 **迁移月数（months to migrate）**：

- <1 个月：低锁定；
- 1–3 个月：中等，需预案；
- >3 个月：高锁定，应在架构上避免。

降低锁定的具体做法：开放 checkpoint（HF/Megatron 双向）、容器化、基础设施
即代码、数据分层（热/温/冷）、避免专有算子进入关键路径。

### 45.3.2 Neocloud、容量块与 GPU 融资

除了“大云 vs 自建”，还有几类中间形态：

| 形态 | 特点 | 适合 | 风险 |
|---|---|---|---|
| Neocloud（CoreWeave/Lambda 等） | 纯 GPU、价格低、上架快 | 训练/推理突发、初创 | 规模/网络/合规不如大云；合同锁定 |
| 容量块/预留 | 按周/月锁定一批 GPU | 可预测的训练任务 | 闲置仍付费；跨区迁移难 |
| Spot/抢占式 | 价格低、可被回收 | 容错训练/实验 | 频繁中断；检查点/弹性要求高 |
| GPU 融资/租赁 | 厂商/金融公司持有硬件，按使用付费 | 想自建但不想一次性 capex | 总成本可能高于自建；退出条款 |
| 托管训练平台 | 平台管集群，按 GPU-hour 计费 | 团队小、要快速上线 | 平台溢价/抽象层限制 |

决策时把“单价”换成“**有效 $/可用 GPU-hour**”：

```text
有效成本 = 名义单价 / (1 - 中断率) / 利用率 + 迁移/运维/合规成本
```

Spot 的名义单价可能只有按需的 30%，但如果每天被回收多次、每次恢复 20 分钟，
有效成本可能反超。容量块则相反：单价低但闲置率高。**先估中断率和恢复
时间，再谈价格**。

### 45.3.3 采购/合同要看的条款

GPU 采购/云合同的坑通常不在单价，而在条款：

| 条款 | 要问什么 | 风险 |
|---|---|---|
| 容量保证 | 承诺的卡数/型号/可用区？ | “尽力而为”等于没有保证 |
| 价格保护 | 降价/涨价如何调整？ | 长约锁在高位 |
| 最低承诺 | 未用完是否照付？ | 闲置也计费 |
| 中断/回收 | Spot 的回收通知/频率？ | 恢复成本吃掉折扣 |
| SLA/赔偿 | 可用性/网络/存储的赔偿？ | 赔偿上限远低于损失 |
| 出口/迁移 | 数据导出/网络出口费？ | 迁移成本锁定 |
| 数据删除 | 合同结束如何删除/证明？ | 合规风险 |
| 硬件刷新 | 新一代 GPU 的置换/升级？ | 3 年后的残值/兼容 |
| 维护窗口 | 计划内停机如何计费？ | 训练窗口被打断 |
| 税务/出口管制 | 跨境/许可证？ | 交付/合规风险 |

做 RFP 时把“有效 $/可用 GPU-hour”和“退出成本”一起算，而不是只比单价。

## 45.4 托管平台

托管平台（NeMo/SageMaker/Vertex/Databricks 等）提供：

- 数据/实验管理；
- 分布式训练封装；
- 超参/调优；
- 模型注册/部署；
- 合规/审计。

代价：

- 抽象层多，深度调优受限；
- 价格包含平台溢价；
- 版本/功能滞后；
- 迁移成本。

选择：

- 团队小/要快速上线 → 托管；
- 要极致性能/自定义 kernel → 自建/裸云 + Megatron；
- 合规/私有化 → 一体机/私有云。

### 45.4.1 托管平台评估矩阵

| 维度 | 权重 | 要问的问题 |
|---|---:|---|
| 性能可控性 | 25% | 能否改并行度/精度/kernel？能否拿到 NCCL/step time？ |
| 成本透明度 | 20% | 计费粒度？闲置/存储/出口费？ |
| 可迁移性 | 20% | checkpoint/数据/镜像能否导出？ |
| 功能完整度 | 15% | 预训练/后训练/推理/评测是否覆盖？ |
| 合规/隔离 | 10% | 多租户/审计/数据驻留？ |
| 支持/SLA | 10% | 故障响应/专家支持？ |

权重按业务调整；关键是**不要只用“功能列表”打分**，性能可控性和可迁移性
通常在使用 6 个月后才暴露。

## 45.5 竞争：谁会替代 Megatron

### PyTorch FSDP/compile

- 原生、易用、生态好；
- 对大模型/长序列的极致性能仍在追赶；
- 与 Megatron 的 TP/PP/EP 组合仍有差距；
- 但“够用”的场景会越来越多。

### DeepSpeed

- ZeRO 系列易用；
- 3D 并行/MoE 大规模积累不如 Megatron；
- 微软生态/推理（DeepSpeed-Inference）。

### JAX/MaxText

- XLA 编译、TPU 生态；
- NVIDIA GPU 上的算子/社区不如 PyTorch；
- Google 内部栈强。

### 云自研栈

- Trainium/Neuron、TPU；
- 与自家硬件/云绑定；
- 对 NVIDIA 生态形成替代。

### 推理引擎

- vLLM/SGLang/TensorRT-LLM 在推理侧更专注；
- 训练框架需要与它们互操作，而不是竞争。

### 45.5.1 替代威胁模型

不要问“谁会完全替代 Megatron”，而问“在什么场景下替代”：

| 场景 | 最可能的替代 | 触发条件 |
|---|---|---|
| 单机/小集群微调 | FSDP + HF Trainer | 易用性优先、规模小 |
| 中等规模预训练 | FSDP/DeepSpeed | “够用”且团队熟悉 |
| 千卡+ 预训练 | Megatron/自研 | 需要 TP/PP/EP/CP 组合 |
| 长上下文 | Megatron + CP/ring | 需要系统级优化 |
| MoE 大模型 | Megatron/DeepSpeed-MoE | 需要 EP/all-to-all |
| 非 NVIDIA 硬件 | JAX/MaxText/厂商栈 | 硬件绑定 |
| 推理 | vLLM/TensorRT-LLM | 推理专用优化 |

Megatron 的防守策略不是“所有场景都赢”，而是守住**超大规模、异构并行、
新硬件/新精度**这些高价值场景，同时通过 Bridge/NeMo 降低迁移门槛。

## 45.6 NVIDIA 的护城河

- 硬件（H100/B200/GB300）+ NVLink/IB；
- 软件（CUDA/cuDNN/NCCL/TE/Megatron/NeMo）；
- 生态（框架/模型/云/企业）；
- 性能基准/话语权；
- 人才/支持。

风险：

- 云厂商/超大规模客户自研芯片；
- PyTorch 原生能力提升；
- 开源社区分叉；
- 监管/出口管制；
- 硬件供应/能耗。

## 45.7 企业选型清单

1. 训练规模/频率/序列长度？
2. 是否需要最新 GPU/FP4？
3. 团队是否有分布式系统能力？
4. 利用率能否 >50%？
5. 合规/数据主权要求？
6. 推理侧用什么引擎？
7. 预算是 capex 还是 opex？
8. 迁移/锁定风险？
9. 供应商支持/SLA？
10. 3 年 TCO，而不是单价。

### 45.7.1 一个加权评分示例

假设企业要选“自建 vs 云 IaaS vs 托管训练”：

| 维度 | 权重 | 自建 | 云 IaaS | 托管 |
|---|---:|---:|---:|---:|
| 3 年 TCO | 30% | 4 | 3 | 2 |
| 性能可控性 | 25% | 5 | 4 | 2 |
| 上线速度 | 15% | 1 | 4 | 5 |
| 合规/数据主权 | 15% | 5 | 3 | 3 |
| 运维负担（越低越好） | 10% | 1 | 3 | 5 |
| 可迁移性 | 5% | 4 | 3 | 2 |
| **加权分** | 100% | **3.65** | **3.40** | **2.90** |

这个例子说明：如果 TCO/性能/合规权重高，自建胜出；如果上线速度和运维权重
高，托管胜出。**分数不是结论，而是把争论变成可调整的假设**。

## 45.8 三个案例

### 案例 A：前沿实验室

- 规模：数千卡，连续训练，追求 MFU/新架构；
- 选择：自建 + Megatron Core + 自研 kernel/调度；
- 关键：网络/存储/故障恢复/人才，而不是“买哪家云”；
- 风险：硬件代际/供应链/电力。

### 案例 B：行业模型企业

- 规模：几十卡，微调/后训练为主，数据敏感；
- 选择：私有云/一体机 + NeMo/Bridge，训练用 Megatron，推理用 vLLM；
- 关键：合规/隔离/可维护性，性能不是第一优先级；
- 风险：团队小、平台依赖供应商。

### 案例 C：AI 应用公司

- 规模：无自有 GPU，按 API 调用；
- 选择：先用 API/托管验证场景，有稳定需求后再考虑微调；
- 关键：单位经济/上市时间，而不是训练框架；
- 风险：API 价格/供应商锁定/数据合规。

三个案例的共同点：**先明确约束，再选形态**；没有“最好的架构”，只有“匹配
当前约束的架构”。

## 45.9 本章小结

- 自建/云/托管/API 各有适用场景，没有绝对最优。
- 自建看利用率/团队/长期任务；云看弹性/最新硬件；托管看集成/合规。
- 用成熟度模型评估自建能力，用“迁移月数”量化锁定。
- Megatron 的竞争来自 FSDP/DeepSpeed/JAX/云自研/推理引擎，要按场景看威胁。
- NVIDIA 的护城河是软硬协同，但并非不可替代。
- 选型用加权评分 + 3 年 TCO + 风险清单，而不是单卡价格。
