# 第 47 章 从实验到产品：模型迭代、组织与决策

第 43–46 章讨论了市场、TCO、选型和开源治理；第 48 章会给出一个 1B 模型的
端到端技术链路。中间缺一层：**一个组织怎样把“训练一个模型”变成“持续交付
模型能力”**。这一章讨论迭代闭环、团队分工、决策门、算力预算和技术债。

它不教你某个命令，而是回答管理者/技术负责人最常问的问题：

- 一次预训练要占多少算力，怎样在“探索”和“交付”之间分配？
- 数据、训练、后训练、评测、推理团队怎样接口，哪些东西必须统一？
- 什么时候该停一个训练任务？什么时候该加算力？
- 哪些“工程债”会在第二代模型上爆炸？

## 47.1 模型迭代的闭环

一个可运行的闭环至少包含七个环节：

```text
需求/能力目标
   → 数据与 tokenizer
   → 预训练
   → 后训练（SFT/偏好/RL）
   → 评测（离线 + 在线）
   → 部署（推理/服务）
   → 反馈（bad case/成本/延迟）
   → 下一轮数据与配方
```

每一环都有“输入契约”和“输出契约”：

| 环节 | 输入 | 输出 | 最容易断的地方 |
|---|---|---|---|
| 需求 | 产品/客户需求 | 可评测的能力目标 | 目标不可量化 |
| 数据 | 原始语料/标注 | 版本化 shard + manifest | 版本/去重/合规 |
| 预训练 | 数据 + 配置 | checkpoint + 训练报告 | 复现性/故障恢复 |
| 后训练 | checkpoint + 偏好数据 | 对齐后的 checkpoint | 数据质量/奖励作弊 |
| 评测 | checkpoint + 评测集 | 分数 + 置信区间 | 污染/协议不一致 |
| 部署 | checkpoint + 服务配置 | API/延迟/成本 | 训练-推理不一致 |
| 反馈 | 线上日志/工单 | 数据/配方变更 | 隐私/归因 |

闭环的关键不是“每一环都做到最好”，而是**每一环的产出能被下一环消费**。
例如：预训练报告没有记录 tokenizer hash，后训练就无法判断数据是否需要
重 tokenize；评测集没有版本，两代模型的分数就不可比。

## 47.2 团队分工与接口

一个中等规模的模型团队通常分成五个功能组：

| 组 | 核心职责 | 关键产出 | 常见冲突 |
|---|---|---|---|
| 数据 | 采集/清洗/去重/混合/tokenizer | 版本化数据 + 质量报告 | 与训练组对“token 预算/配比”的分歧 |
| 预训练 | 并行配置/训练稳定性/吞吐 | checkpoint + 训练报告 | 与平台组对“故障/重试”的责任 |
| 后训练 | SFT/LoRA/偏好/RL | 对齐 checkpoint + 评测 | 与评测组对“什么算提升” |
| 评测 | 离线/在线/红队/污染检测 | 可信的分数 + 置信区间 | 与产品对“分数 vs 体验” |
| 推理/平台 |  serving/调度/监控/成本 | API/SLA/成本报告 | 与训练组对“权重格式/并行布局” |

接口契约建议写成文档并进 CI：

```text
数据 → 训练：manifest（tokenizer hash、shard checksum、token 数、来源）
训练 → 后训练：checkpoint（格式、并行度、dtype、step、config）
后训练 → 评测：checkpoint + 评测配置 + 变更说明
评测 → 产品：分数 + 置信区间 + 失败案例 + 成本/延迟
推理 → 训练：bad case、延迟/成本、KV/精度约束
```

没有契约，团队会陷入“这个 checkpoint 能不能用”“这个分数可不可信”的
反复扯皮。

## 47.3 算力预算：探索 vs 交付

把算力想成一个投资组合：

```text
总预算 = 交付（must-ship） + 探索（research) + 基础设施/故障余量
```

一个可用的起点（按团队阶段调整）：

| 用途 | 占比（示例） | 说明 |
|---|---:|---|
| 主线预训练/后训练 | 60%–70% | 有明确交付目标 |
| 消融/配方实验 | 15%–25% | 小规模、可复现 |
| 长上下文/新结构 | 5%–10% | 高风险、可回退 |
| 故障/重跑余量 | 10%–15% | 不是浪费，是保险 |

判断一个实验是否值得跑：

```text
信息价值 = 可能改变的决策 × 决策的影响 / 实验成本
```

如果实验无论结果如何都不会改变下一步，就不要跑。如果两个实验只能选一个，
选“能证伪当前主线假设”的那个。

### 47.3.1 什么时候停

- 损失/评测连续多个检查点不改善，且没有新假设：停；
- 训练不稳定（NaN/spike）反复出现，回退后仍复现：停，先修数据/精度；
- 吞吐低于基线 50% 且 30 分钟不恢复：停，查硬件/网络；
- 成本超出预算 20% 且没有明确收益信号：停，重新评估；
- 关键假设被小规模实验证伪：停，改配方。

“沉没成本”是最大的敌人。把“停止条件”写进实验计划，而不是事后找理由。

## 47.4 决策门（go/no-go）

在算力花出去之前设门，比事后复盘便宜：

| 门 | 时机 | 要回答的问题 | 不过门的动作 |
|---|---|---|---|
| G0 需求 | 立项 | 能力目标可量化吗？有评测吗？ | 回产品/评测 |
| G1 数据 | 预训练前 | 数据版本/质量/合规/配比 OK？ | 补数据/过滤 |
| G2 小规模 | 1%–5% 算力 | loss/评测/吞吐符合预期？ | 调配方/停 |
| G3 中期 | 30%–50% | 与基线比有优势？成本可控？ | 缩减/转向 |
| G4 交付 | 训练后 | 评测/安全/推理成本达标？ | 后训练/量化/延迟 |
| G5 上线 | 部署前 | SLA/监控/回滚/合规 OK？ | 灰度/回滚 |

每一道门都要有**可验证的证据**，而不是“大家觉得还行”。证据的形式可以是
loss 曲线、评测分数、吞吐/成本报告、故障演练记录。

## 47.5 技术债：第二代模型才会爆炸的东西

以下问题在第一代小模型上通常“能跑”，在第二代大模型/多模态/长上下文上
会集中爆发：

1. **配置漂移**：同名参数在不同脚本/版本里含义不同，checkpoint 无法复现。
2. **数据版本缺失**：只知道“用了某批数据”，不知道过滤规则/tokenizer hash。
3. **评测污染**：训练数据混入评测集，分数虚高，上线后打脸。
4. **并行布局硬编码**：换 TP/PP/DP 就要改代码，checkpoint 不能重分片。
5. **训练-推理不一致**：RoPE/attention mask/tokenizer 在两边不同。
6. **监控只覆盖 loss**：没有 grad norm/吞吐/数据 stall/故障率。
7. **检查点不可恢复**：半写、RNG/sampler 丢失、布局不兼容。
8. **权限/合规债**：数据/模型许可证不清，出海/行业合规未评估。
9. **单点知识**：只有一个人会跑训练/恢复/转换。
10. **成本不可见**：不知道每个实验/每个 token 的真实成本。

还债的顺序：先修“会让训练不可复现/不可恢复”的（1/2/4/7），再修“会让
决策错误”的（3/5/6/10），最后修“组织风险”的（8/9）。

## 47.6 组织学习的机制

- **实验登记**：每个实验有 id、假设、配置、数据版本、结果、结论；失败
  实验也要登记，否则会重复踩坑。
- **复盘**：故障/事故按“症状 → 根因 → 修复 → 预防”写，进入 runbook；
  第 42 章给了模板。
- **变更管理**：升级 Megatron/TE/PyTorch/驱动前，跑回归矩阵（单元 +
  等价性 + 小规模训练 + 转换）。
- **知识轮转**：训练/推理/数据/评测定期换人评审，避免单点。
- **对外口径**：所有性能/成本数字按附录 J 的 E/L 分级披露。

## 47.7 一个 90 天落地计划

| 阶段 | 周 | 目标 | 产出 |
|---|---|---|---|
| 基线 | 1–2 | 跑通 mini + 一个真实小模型 | `verify.py` 全绿；基线吞吐/显存 |
| 链路 | 3–4 | 数据 → 训练 → 检查点 → 生成 | 端到端脚本 + manifest |
| 并行 | 5–6 | TP/PP/DP 配置搜索 | 配置/成本报告 |
| 恢复 | 7–8 | 故障注入 + 恢复演练 | runbook + 恢复时间 |
| 评测 | 9–10 | 离线评测 + 去污染 | 评测报告 + 置信区间 |
| 上线 | 11–12 | 转换 + 推理 + 监控 | SLA/成本/回滚方案 |
| 复盘 | 13 | 技术债/下一轮计划 | 决策 memo |

这份计划假设团队已有 GPU 和数据；如果从零开始，先把“数据 + 评测”做出来，
再谈训练规模。没有评测的模型迭代，只是随机漫步。

## 47.8 本章小结

- 模型迭代是一个闭环，每一环都要有可被下一环消费的契约。
- 团队分工的核心是接口：数据 manifest、checkpoint 格式、评测协议、
  推理约束。
- 算力是投资组合：交付、探索、基础设施/故障余量要分开预算。
- 设 go/no-go 门和停止条件，比事后复盘便宜。
- 技术债按“复现/恢复 → 决策正确性 → 组织风险”的顺序还。
- 组织学习靠实验登记、复盘、变更管理和知识轮转，而不是个人英雄主义。
